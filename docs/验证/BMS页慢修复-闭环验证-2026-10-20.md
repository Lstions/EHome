## 0. 结论摘要

1. **SQL 分桶下推（P0-1）生效**：5 个页面历史请求串行从本机 before **6.64 s → 3.07 s（新 SQL，无索引）/ 3.12 s（+新索引）**；
   响应体 3.28 MB → **1.04 MB（-68%）**；单点 500 点、protection change 语义与 DB 完全一致（193 点 = lag distinct 193）。
2. **复合索引（P0-2）在 v1 实现下未被查询计划采用**：单测点 24h 仍扫 **2,505,600 行**（目标 ≤86,400），
   整页 24h category 行访问仍约 **7,517 万**（目标 <400 万），latest-data 仍全分区 seq scan 读 1.04 GB。
   根因：`dataScopeCond` 的 OR scope 条件挡住 `(logical_device_id, sensor_name, timestamp)` 前导列；
   控制实验证明是代价模型选择而非索引不可用（详见 §4.3）。**因此契约两项 PG 行访问目标 v1 = FAIL**，
   已开 task-8 以 UNION ALL 分支重写消除 OR 障碍（进行中，完成后重测）。
3. **前端修复（并发≤3 / 懒挂载 / 失败可见 / 降级限流）本机 E2E 全部按预期工作**：
   窄屏首屏 0 个 historical-batch（旧构建 5 个）、batch 并发峰值 3（旧 5）、主图与诊断卡注入 500 时
   均显示「加载失败 + 重试」并在重试后恢复；本机 desktop loading 2.33 s（旧构建 5.17 s）。
4. **前端全量门禁**：`pnpm test:run --maxWorkers=4` 全绿（176 files / 2093 tests，125.74 s）、
   `pnpm typecheck`、`pnpm build` 全绿；默认并发 `pnpm test:run` 仅 2 个**既有负载敏感 flake**
   （单跑均通过，见 §6.1）。
5. **后端门禁**：全量 `go test ./...` 首跑有 3 类失败，其中 2 类为「只挂 backend 目录」的挂载假红
   （pkg/frame、commandexec 需要 repo-root 下的 `protocol/`、`esp32-collector/`）；repo-root 挂载重跑
   关键包后 database/cmd/server/pkg/frame/commandexec 全绿；`internal/api` 的
   `TestHistoryAggregateSQLShape` 失败属 **v2 进行中**（测试仍是旧 SQL 形状断言，backend-fix 正在更新），
   `internal/datalifecycle` 当时 [build failed] 为 **backend-fix 正在改代码的瞬时状态**。最终门禁待 v2 完成后重跑。

### 4.3 FAIL：复合索引未被采用（含控制实验）

``.bench/explain-after.txt` / `explain-after-noidx.txt`：

| 查询 | after-noidx | after-idx（已建索引） | 目标 |
|---|---|---|---|
| 单测点 24h（avg SQL） | timestamp_idx 扫 2,505,600 行 | **仍 timestamp_idx 扫 2,505,600 行**（207.5 ms） | ≤86,400 ⇒ **FAIL** |
| protection 30d（change SQL） | sensor_name bitmap，heap ≈6.23M 行 / read 271,812 | **同上**（824 ms） | — |
| latest-data | 全分区 seq scan，read 133,335 | **同上** | 索引加速 ⇒ **FAIL** |

**根因**：scope 条件 `(logical_device_id IN (14) OR (logical_device_id IS NULL AND device_id IN (14)))`
的 OR 表达式使 `(logical_device_id, sensor_name, timestamp)` 前导列无法作为单一 index qual 下推。
控制实验（同一 bench 库）：
- `SET random_page_cost=1.1` 后同一查询立即改走 `Index Scan using ...logical_device_id_sensor_name_timestamp_idx`
  （cost 39,245 vs timestamp 83,030）⇒ 是**代价模型选择**而非索引不可用；
- `count(*)`（index-only）在默认参数下即走新索引（cost 4,236）；
- 同数据形态的 2.5M 行同构临时表会选中该索引；22.5M 行生产量级 + 全索引集合下不选。
生产 PG 参数相同（random_page_cost=4）⇒ 生产会复现同样计划，故 v1 不满足契约两项 PG 行访问目标。

**处置**：Lead 已开 task-8，backend-fix 正在将历史聚合 SQL 与 latest-data 改为 **UNION ALL 分支重写**
（已验证工作树代码已出现 UNION ALL 形态），并加 EXPLAIN 断言门禁。完成后本文档 §1/§4 数字重测更新。

  窄屏正常流程（展开历史趋势/保护历史）新增降级 0。

  22 个降级请求的风暴**（本机 before 仅 18 个 API 请求 vs 生产 44）。本机 E2E 只证明「请求编排/懒挂载/
  并发上限/失败可见性」的行为正确与功能不回退；**生产绝对耗时与超时风暴需部署后按同一 CDP 场景复测**。

## 8. 未验证项与风险

1. **backend v2 数字缺失**：UNION ALL 重写后的单测点扫描行数、整页行访问、端点耗时、latest-data、

3. **生产外部网络链路未验证**（本轮不测；根因报告 §R6 已量化）。
4. **冷缓存未测**：本机无 root 无法 drop OS page cache；PG `shared_buffers=128MB` < 表 3.9GB，
   计时主要在热 OS page cache 下取得（每轮内置预热 + 3 轮中位数）。
5. **索引维护窗口为估算**：本机 22.47M 行实测 17.97–24.5 s；生产 24M 行按行数折算 ≈21 s，
   叠加 3 vCPU/写压力/磁盘差异，保守按 1–2 分钟低峰窗口（估算，非实测）。
6. **E2E 在线态是模拟的**：bench 无实时设备，用 DB status=active + 响应改写模拟在线；请求编排断言不受影响，
   但「真实在线采集态」下 latest-data/WS 推送路径未覆盖。
7. **物理写入顺序敏感性**（环境坑，已排除）：若 bench 行按 category 分组写入（timestamp correlation≈0.37），
   planner 会改走并行 BitmapAnd，16 路 batch 并发会耗尽容器 `/dev/shm=64MB` 动态共享内存，且旧代码吞错返回
   `data:null`；本 bench 已按时间升序写入（correlation=1）复现生产计划形状。
