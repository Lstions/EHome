## 0. 结论摘要

1. **服务端耗时**：5 个页面历史请求串行 **before 6.64 s → v4 0.73 s（9.1×）**；cells 响应体 1.70 MB → **548 KB**，5 请求响应体合计 3.28 MB → **1.04 MB（-68%）**。
   （生产 before 20.6–21.1 s；生产绝对耗时需部署后复测，见 §8。）
2. **PG 行访问**（本轮最关键的修复闭环）：
   - 单测点 24h：**2,505,600 行扫描 → 86,400 行**（Parallel **Index Only Scan**，Heap Fetches 0，Execution 210→**33 ms**，buffers read 35,938→**620**）；
   - 30d protection change：heap 访问 **约 623 万行 / 读 2.1 GB / 824 ms → 697,519 行（语义必需）/ 读 45 MB / 380 ms**，且消除 external merge sort；
   - latest-data：**全分区 seq scan 200 万行 / 读 1.04 GB / 180 ms → Index Scan 0.19 ms**。
3. **v1→v2 的验证发现（重要）**：v1（仅加普通复合索引）实测 **索引未被 planner 采用**（OR scope 条件挡前导列），
   verifier 用控制实验定位为代价模型选择 → Lead 开 task-8；v2 改为 **UNION ALL 分支重写 + covering 索引
   `INCLUDE ("value")`** 后上述指标全部达标。详见 §4（FAIL 证据）与 §5（修复后）。
4. **前端**：窄屏首屏 **0 个 historical-batch**（旧构建 5 个，lazy 生效）；batch 并发峰值 **3**（旧 5）；
   注入 500 时主图/诊断卡均显示「加载失败 + 重试」并在重试后恢复；desktop loading **0.51 s**（v1 2.33 s / 旧 5.17 s）。
5. **门禁**：前端 `test:run --maxWorkers=4` / `typecheck` / `build` 全绿（默认并发仅 2 个**既有**负载 flake，单跑通过）；
   后端最终代码 `go test -count=1 ./...`（repo-root 挂载）**EXIT=0 全绿**（37 个包 ok）。

## 4. v1 阶段：SQL 分桶生效，但复合索引未被计划采用（FAIL → 促成 task-8）

原始记录：`.bench/after-backend-summary.md`、`explain-after-noidx.txt`、`explain-after.txt`。

v1 端点：5 请求串行 **3.07 s（无索引）/ 3.12 s（+普通新索引）**，响应体 1.04 MB（-68%）；API 语义正确
（cells 16×500 点、protection change 193 点 = DB 期望 193、agg=raw 兼容、latest-data 正常）。

**但** EXPLAIN 显示新索引（非 covering）完全未被采用：

| 查询 | v1（普通复合索引） | 契约目标 |
|---|---|---|
| 单测点 24h avg | 仍 `timestamp_idx` 扫 **2,505,600 行**（207.5 ms） | ≤86,400 ⇒ **FAIL** |
| protection 30d change | 仍 sensor_name bitmap，heap ≈6.23M 行 / read 271,812 | — |
| latest-data | 仍全分区 seq scan | 索引加速 ⇒ **FAIL** |

**根因（verifier 控制实验）**：`dataScopeCond` 的 OR scope
`(logical_device_id IN (14) OR (logical_device_id IS NULL AND device_id IN (14)))` 使复合索引前导列无法作为单一
index qual 下推；`SET random_page_cost=1.1` 后同一查询立即改走新索引（cost 39,245 vs 83,030）⇒ 代价模型选择，
非索引不可用；生产同参数会复现。**处置**：Lead 开 task-8（UNION ALL 分支重写 + covering 索引），本文件 §5 为最终结果。

## 5. v2/v4 修复与最终 after（UNION ALL + covering 索引，verifier 独立复测）

### 5.1 最终索引定义（bench 实测，与代码一致）

| 索引 | 定义 | 用途 |
|---|---|---|
| `idx_unified_logical_sensor_ts` | `(logical_device_id, sensor_name, "timestamp") INCLUDE (value)`（covering） | 历史聚合 A 分支；index-only scan |
| `idx_unified_legacy_null_ts` | `(device_id, sensor_name, "timestamp") INCLUDE (value) WHERE logical_device_id IS NULL`（部分） | backfill 前 NULL-logical 分支（生产 backfill 后 0 行） |
| `idx_devdata_logical_created` | `(logical_device_id, created_at DESC)` | latest-data A 分支 |
| `idx_devdata_legacy_null_created` | `(device_id, created_at DESC) WHERE logical_device_id IS NULL`（部分） | latest-data B 分支 |

（SQLite 用无 INCLUDE 的普通复合索引，DDL 由 `PGDDL` 分支区分；SQLite 行为不变。）

**建造成本（本 bench 22.47M 行实测，`.bench/index-create-v4-covering.txt`）**：
covering `idx_unified_logical_sensor_ts` **CREATE INDEX = 18.36 s**，分区索引体积 **1282 MB**
（非 covering 版 24.5 s / 1086 MB；覆盖 value 后 +196 MB）；`device_data` 两索引 ≈1.9 s + 60 MB；legacy 部分索引 0 行 ≈ 0 s。
生产 24M 行按行数外推：≈18.36×(24/22.47) ≈ **19.6 s**（估算）；叠加 3 vCPU/写压力/磁盘差异，**保守按 1–2 分钟低峰维护窗口**
（分区母表必须先 `ehomectl datalifecycle ensure-indexes`，非并发 CREATE INDEX 会短暂阻塞写入）。生产统一分区总大小 4.42 GB → 约 +1.34 GB 索引。

7. **E2E 在线态为模拟**：bench 无实时设备；真实在线采集态的 latest-data/WS 推送路径未覆盖。
