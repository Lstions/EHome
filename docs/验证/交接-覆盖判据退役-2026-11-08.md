## §2 为什么删（不是「没人调用」，是「不该存在」）

### 它是什么

`probeFrameCoverage` / `frameCovered` 是一个**选源判据**：回答「帧表覆盖了这个窗口吗？
不覆盖就回落 `unified_data`」。

注意：它**不是**一个独立的业务功能，它是一次决策的一半 —— 另一半是「回落」。

### 前提消失

硬切换之后：

| 事实 | 后果 |
|---|---|
| 回落目标 `unified_data` 已 DROP | 「不覆盖就回落」这个动作**无处可去** |
| `selectHistorySource` 改成两档（帧表可用/不可用） | 不再询问覆盖情况 |
| `probeFrameCoverage` 生产零调用者 | grep 确认只剩自身定义 + 3 条注释 |

### 为什么留着比删掉更危险（这是关键，不是「清理死代码」）

覆盖判据的**四种成因**需要的动作各不相同：

| 成因 | 应该做什么 |
|---|---|
| ① 无帧 | 返回空点集（确无数据） |
| ② 帧数超 `MaxDecodeFrames` | **报错**（数据变了但读不出来，静默返回空是骗人） |
| ③ 头部未覆盖 | 只给窗口内部分（前面那段确实没有） |
| ④ 尾部写入滞后 | 给已有数据（不是没数据，是还没落盘） |

而一个布尔值只能表达「覆盖 / 不覆盖」。压成布尔之后，**其中三种会变成错误的「返回空」**
—— 用户看到空图表，而后端一切正常、日志干净。

这就是「**前提消失后，依赖该前提的机制会从保护变成伤害**」：
判据的全部合理性建立在「不覆盖时能回落到另一份数据」之上。前提没了，
它剩下的唯一行为是「决定要不要返回空」。

### 分组完整性说明（先说清 12 条怎么分成 7 行）

12 条按**性质**分 6 组，覆盖 10 条；另有 **2 条不属于任何单一性质**，单列在最后：

## §4 我想加回一个覆盖判据，行不行

先回答三个问题，再动手：

1. **有没有第二个数据源？** 没有 => 判据判断出来也做不了任何事（§2）。
2. **判断后要做什么？** 如果答案是「回落」，那要先有回落目标；如果是「报错 / 降级 / 提示」，
   那需要的不是「覆盖判据」而是**具体的错误处理**，而且应该按成因分开（§2 的四种）。
3. **判据的产出是什么形状？** 如果还是 `bool`，请重读 §2 —— 四种成因压不成一个布尔。
   正确形状是「带原因的枚举」或「直接返回数据 + 一个可选的诊断」。

**总之：「加回判据」不是把旧代码抄一遍，是先确定「判断后要做什么」。**

**只有一个地方还在判，而且只用来告警，不再影响选源：**

```go
// rollup_read.go 的 rollup 读路径尾巴诊断
if tailEmptyLooksLikeLag(probeDeviceLastDataAt(ctx, db, id), from) {
    logger.Warnf("[rollup-read] live tail empty although device reported at %s ...")

```

守卫：`rollup_tail_lag_predicate_test.go` 的 3 条断言。

**能力边界要说清**：

| 维度 | 旧覆盖判据 | 现在的 tailEmptyLooksLikeLag |
|---|---|---|
| 区分「设备安静」vs「落盘滞后」 | 是 | 是（同一种区分） |
| 区分后做什么 | **选数据源**（帧表 / unified_data） | **打一条 Warn** |
| 影响用户可见结果 | 是（走哪条路径） | 否（只是日志） |

所以「性质被接手」这句只对一半：**区分能力被接手，区分后的动作没有替代物** ——
因为那个动作是「切到另一个源」，而另一个源不存在了。

## §7 我把 unified_data 加回来，这个判据需要恢复吗

**需要，但恢复的不是判据本身。**

判据的价值不在「判断」，在「判断后能做什么」。所以顺序是：

### 第一步：先回答「为什么会有两张表」

| 场景 | 需要的机制 |
|---|---|
| **回滚**（新表有问题，暂时切回旧表） | 需要的是**开关**，不是覆盖判据 —— 覆盖判据是「按数据分布自动选」，而回滚是「人为决定全局切」 |
| **归档**（旧表只读保留，新写入走新表） | 需要的是**按时间分界**（旧表负责 T 之前）—— 这是确定性规则，不需要探测 |
| **双写过渡期**（两表都在写） | 这才是覆盖判据的原始场景：两表都可能有数据，需要判断谁更全。**但双写结束后它又该删** |

### 第二步：按场景选正确形状

- 回滚 => 环境变量开关（本仓已有先例：`EHOME_TELEMETRY_ROLLUP_READ` 的 fail-open 约定）
- 归档 => 时间分界常量（比探测更简单、更可预测、可单测）
- 双写 => 覆盖判据（**带原因的枚举，不是 bool**）

### 第三步：别照抄

旧判据的四层容忍度（头部 5min / 尾部 5s / 自适应 2×间隔 / 锚点 min(lastDataAt, end)）
是**为「双写过渡期」这个具体场景**调出来的。换场景后那些数字全部要重算。
把它们抄过来，等于把「过渡期的经验」当成「通用规律」。

⚠ 最后一句留给未来的自己：**「问题不再有答案」和「问题消失了」是两件事。**
本文 §3 里标为「问题仍在但无关」的那几行，在你加回第二数据源的那天会**立刻相关**。
