## 1. 核心设计：为什么必须按表分支

契约 §4 的 ⚠ 是本任务的技术核心。三张时序表的**形状不同**：

| | `unified_data` | `device_data` | `telemetry_frame` |
|---|---|---|---|
| 时间列 | `timestamp` | `timestamp` | **`ts`** |
| 主键 | `(id, timestamp)` | `(id, timestamp)` | **`(device_id, ts, seq)`** |
| 有 `id` 列 | 是 | 是 | **否** |
| 分区 | 月分区 | 月分区 | 月分区（按 `ts`） |

把 `telemetry_frame` 塞进既有的 `for _, table := range []string{"unified_data","device_data"}` 会**立刻 SQL 报错**：

```sql
-- 既有形状（对帧表执行必挂）
DELETE FROM telemetry_frame WHERE id IN (SELECT id FROM telemetry_frame WHERE timestamp < ?)
--                                  ^^ 列不存在        ^^ 列不存在
```

因此新增 `backend/internal/datalifecycle/telemetry_frame_lifecycle.go`，用 `TimeseriesTable{Name, TSColumn, HasID}` 描述形状，六个调用点按 spec 生成 SQL。

### 2.1 第 5 处的特殊处理（最容易写错的一处）

`unified_data`/`device_data` 的迁移是 `UPDATE ... SET device_id = ? WHERE id IN (...)` —— 直接改归属即可。

**帧表不能这么做**：主键是 `(device_id, ts, seq)`。把源行改成目标 `device_id` 时，若目标在同一 `(ts, seq)` 已有行，**主键冲突 ⇒ 整批失败**（不是丢一行，是整个合并 500）。

实现（`MigrateTelemetryFramesToDevice`）：

1. 读一批源行（有界，≤5000 行）；
2. 以目标 `device_id` 重新插入，`ON CONFLICT DO NOTHING`（撞主键的帧丢弃并**计数**）；
3. 按**精确 `(device_id, ts, seq)` 三元组**删除本批源行 —— 不是按 `ts` 列表删，那会误删目标设备同一时刻的帧。

重试幂等：第 2 步 DO NOTHING、第 3 步删已删过的行零影响。

### 2.2 保留期用分区 DROP（O(1)）

`telemetry_frame` 是月分区表，保留期与另两张表同款走 `DropPartitionsBeforeFor`（元数据操作）。这是「帧数据真的会按保留期消失」的唯一可靠实现 —— 1 Hz × 每设备的数据量下逐行 `DELETE` 永远跑不完。

PG 集成用例 `TestPGTelemetryFramePartitionedLifecycle` 真的断言了 4 个月前的分区被 DROP、当月分区还在。

### 2.3 「表不存在时跳过」的边界

新增 `existingTimeseriesTables(db)`：过滤出库里真存在的表。

不加这层会**把既有功能打成故障**：精简测试库与「迁移尚未跑过」的库没有 `telemetry_frame`，purge 会整批报 `no such table: telemetry_frame` 导致**设备删不掉**（第一轮实现后实测红：`TestDevicePurger_HardDeletesDataAndDeviceRow` / `_Idempotent` / `_StaleClaimThreshold` 三条同时失败）。

生产上迁移是 Fatal 的，所以这条跳过路径只可能在测试库或人为改库时出现。

### 4.4 踩坑记录（两个「假绿」隐患 —— 后来人最容易重犯）

这两条都不是「写错了马上报错」，而是**在特定环境下静默通过或静默失败**。记在这里是因为它们的表现形态与真正的 bug 完全不同，第一次遇到几乎认不出来。

### 坑 1：给清理路径加表，把「设备删不掉」这个既有功能打成故障

**现象**：把三张表直接塞进 `purge_edge_device.go` 的循环后，三条既有 purge 用例同时红：

```
--- FAIL: TestDevicePurger_HardDeletesDataAndDeviceRow
    outcome = failed, want purged (err=batch delete telemetry_frame: no such table: telemetry_frame)
--- FAIL: TestDevicePurger_StaleClaimThreshold
--- FAIL: TestDevicePurger_Idempotent
```

**为什么**：`testutil.OpenTestDB` 的 SQLite 建表清单（`allModels`）**不含** `TelemetryFrame`（`models/telemetry_frame.go` 明确要求分区母表不进 AutoMigrate），所以 SQLite 测试库与「迁移尚未跑过」的库都没有这张表。`DELETE FROM telemetry_frame` 直接报 `no such table` ⇒ 整批 purge 失败 ⇒ **设备永远删不掉**。

注意失败方向很反直觉：不是「新表没被清理」，而是「**原来能用的删除功能坏了**」。一个新增的可选表，把既有的核心功能打成故障。

**正确做法**：所有清理路径先过滤「库里真存在的表」（`existingTimeseriesTables(db)`），与 `cleanLedgerRows` 对 `sensor_field_obs` / `data_sources` 的既有约定一致。生产上 `main.go` 的迁移是 Fatal 的，所以这条跳过路径只可能出现在测试库或人为改库时。

**扩散风险**：以后任何「给生命周期加一张表」的改动都会踩同一个坑。判据是「这条 SQL 在表不存在时会不会把整批操作打挂」。

### 坑 2：PG 清理助手的顺序依赖 —— 同一个用例可能真绿也可能假绿

**现象**：`telemetry_frame_pg_test.go` 的清理助手第二次运行时炸出：

```
telemetry_frame_pg_test.go:50: drop telemetry_frame_pkey: ERROR: "telemetry_frame_pkey" is not a table (SQLSTATE 42809)
```

**为什么**：清理用 `relname LIKE 'telemetry_frame%'` 找表，但这个模式**同时命中主键索引** `telemetry_frame_pkey`（它也以 `telemetry_frame` 开头）。`DROP TABLE IF EXISTS` 打到索引上就报 `is not a table`（`IF EXISTS` 挡不住「存在但不是表」）。

**最阴的地方**：它是否炸出来**取决于** `pg_class` **的返回顺序** ——

- 母表排在索引前 ⇒ `DROP TABLE ... CASCADE` 顺带删掉索引 ⇒ 用例**假绿**；
- 顺序反过来 ⇒ 红。

同一个用例、同一份代码，可能连续通过十次然后第十一次红。这种「偶发红」最容易被当成 flaky 加点 `t.Skip` 糊弄过去，而真实缺陷（清理不彻底 → 用例间互相污染）留了下来。

**正确做法**：

```sql
SELECT c.relname FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p')          -- ← 只取表/分区母表，不取索引
  AND c.relname LIKE 'telemetry_frame%'
  AND n.nspname = current_schema()
ORDER BY (c.relkind = 'r') DESC        -- ← 先删分区，再删母表
```

**扩散风险**：任何「按名字前缀清理 PG 对象」的助手都有这个问题（索引、序列、视图的 relname 都可能撞前缀）。判据是「`LIKE` 模式会不会命中非表对象」。

## 5. 残余风险（诚实清单）

1. **合并历史的有损窗口（Lead 裁决：接受现状，不追做 InvalidateDevice）**

   帧表的增量链按 `(device, slot)` 维护。源设备的最后一帧通常是**增量帧**（相对源设备上一帧），搬到目标设备后解码顺序里它前面是目标设备的帧 ⇒ 该 slot 要等到下一个**关键帧**才能重新对齐。

   **最坏影响（量化，不留模糊）**：

   - 源设备在合并前已**软删**（merge-history 的前置校验强制要求），因此不再产生新帧；
   - 目标设备的该 slot **最多等一个关键帧周期**（`KeyFrameInterval`，默认 60s；配置上限 90s）才重新对齐；
   - 在这 ≤ 90s 的窗口内，对该 slot 的**解码查询会返回旧值**（不是空、不是错，是上一个关键帧时刻的值）—— 这段时间里图表上该字段是一条平线，之后跳到真值；
   - 窗口**有界且不传播**：下一个关键帧到达后增量链完全恢复，之后所有帧解码正确（0 漂移）；
   - 影响**仅限被合并的那台设备**，且只有「源帧在目标帧之后被解码」的 slot 受影响；两侧时间不重叠时通常 0 影响。

   为什么实际窗口很小：源设备已软删 ⇒ 不再写入，所以「最后一个源帧」与「下一个目标帧」之间通常夹着一次关键帧（60s 心跳本身就是关键帧），真正受影响的概率远低于 100%。

   **已知边界**：当前**没有**「让在线编码器对某设备重发关键帧」的钩子 —— 编码器实例在 `DualWriter` 内部，HTTP handler（merge-history 的调用方）拿不到它。若将来要求合并后 0 漂移，需在 `DualWriter` 上加 `InvalidateDevice` 并跨包注入 handler，属独立改动。

2. **`data_count` / `points_stored` 口径未包含帧表**（Lead 已同意）：`row_estimate.go` 的 `EstimateDeviceRows`/`CountDeviceRowsCapped` 刻意**不**算帧表。理由：帧表是同一观测的压缩表示，加进来会让「预计删除 N 行」把同一个数字数两遍。清理动作（purge/retention）仍然两账都清 —— 那是存续问题不是计数口径问题。已在 `row_estimate.go` 注释里写明，并补充了运维必须知道的一句：**实际删除量会大于预计值**（清理会多删帧表与其它 6 张清理器管的表），「预计删除 100 万行」执行完看到 130 万行是正确行为。

3. **帧表读路径仍未接入**：本次只做写入侧 + 生命周期，读路径（`DecodeRange`）仍是骨架，不在契约 §4 范围。

4. **`EHOME_DATA_RETENTION_DAYS` 90→45 是部署项**（契约 §5），不改代码。本次未动。

5. **旧库升级路径**：`MigrateTableToPartitioned` 支持从普通表迁移（复用既有机制），但生产从未建过 `telemetry_frame`，因此实际走的是「无 legacy 表，直接建分区母表」分支 —— PG 用例日志可见该分支。

6. **启动期依赖顺序**（Lead 第 3 点要求确认）：`MigrateTelemetryFrameToPartitioned` 在 `main.go:211`，`SetTelemetrySink` 在 `main.go:574` —— **迁移早 363 行**，中间还隔着 warmup、rollup 迁移、索引收尾、ensurePartitions 等步骤。因此不存在「sink 已注入但表不存在」的窗口：表不存在 ⇒ `abortStartup` 直接退出进程，根本走不到 sink 注入。另外 `NewDualWriter` 内部还有一道 `HasTables()` 兜底（返回 `ErrTablesMissing` ⇒ 同样 `abortStartup`），双保险。
