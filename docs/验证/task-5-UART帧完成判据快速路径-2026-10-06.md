# task-5 交付：UART 帧完成判据快速路径（2026-10-06）

**任务**：修复"100Hz 受 UART 帧完成判据 10ms 固定静默约束"。
**结论先行**：**代码已修并自证，但任务的原始前提被实测推翻** —— 该 10ms 判据**不是**
实测 26.1 Hz 的成因。详见 §3。

---

## 1. 改了什么

**文件**：`esp32-collector/components/bus_worker/bus_worker.c`（`uart_collect_response()`，+25 行）

在原有 10ms 静默判据**之前**插入快速路径：

```c
if (expected > 0 && len >= expected) {          /* 新增 */
   memcpy(out, state->data, (size_t)expected);  /* 只交付声明长度 */
   *out_len = (size_t)expected;
   return true;
}
if (len > 0 && state->last_rx_us > 0 &&          /* 原有兜底，未改 */
    esp_timer_get_time() - state->last_rx_us >= 10000) { ... }
```

- `expected == 0`（变长协议）**行为完全不变**，仍走 10ms 静默兜底。
- 判据是 `>=` 而非 `==`：**收满才返回，绝不截断**。
- **只交付 `expected` 字节**：同一 RX 里紧跟的多余字节**不并入本步载荷**。
  `execute_uart_batch()` 每步 TX 前重置 `s_batch_rx[ch].len`，进入时又已用
  `bus_dma_read` 循环 drain 过驱动环，因此它们既不会进本步载荷，也不会被当作下一步响应。

**改动后 md5**（Lead 提交前可核对，**这是最终值**）：`bus_worker.c = dc05cdafdf05d0abc98f3791705763f0`

> 说明：代码主体写完后我修正过一处自相矛盾的注释（原写"多余字节留给 rx_task 通用路径"，
> 实际是"本步结束时丢弃"），因此 md5 从中间态的 `deaa0f321a237a301776f059fb808a43` 变为最终值。
> **§5.2 的 3 组变异自证已在最终 md5 上重跑确认**，不是中间态的结果。

## 2. `read_size` 语义结论（不是猜的）

`read_size` **不是单一语义，而是三条路径三种含义**：

| 路径 | 字段 | 语义 | 依据 |
|---|---|---|---|
| legacy WriteCmd(0x06) | field 4 | **期望长度**；短读判 error 0x03 | `docs/协议/二进制帧协议.md:223,260` |
| ChannelCmdV2(0x15) | field 9 | **RX 窗口上限**（不是期望长度）；行空闲(10ms)才是权威边界 | `docs/协议/二进制帧协议.md:256-268` |
| 批处理步骤 | `batch_step.read_size` | 厂商协议真实帧长（JBD read_basic_info = 60 B 精确 Modbus 帧） | `jiabaida_control.go:485`、`inject 证据` |

**关键推论**：只有"批处理步骤"这一条路径可以安全地按 `read_size` 定帧（因为它来自
ControlAction 编译出的协议帧长）。legacy/V2 路径的 `read_size` 不能当帧长用 ——
JBD 是变长帧（LEN = 23 + 2*NTC），后端**刻意**把 `ReadLength` 钉死为 0
（`jiabaida_control.go:1133-1155`，2026-10-02 实测事故：非 0 值导致 **100% 数据静默丢弃**）。

## 3. 为什么"改了也不达标"：实测 26.1 Hz 的真实成因（推翻任务书前提）

### 3.1 step2 的 ch8 根本不在批处理路径上

`step2-ch8-115200-100hz-console.log`：`V2 execute` 出现 **0 次**，`CMD_U0: Stats` 出现 12 次。
⇒ 26.1 Hz 走的是 **legacy `CMD_SAMPLE`** 路径，**不经过** `uart_collect_response()`。
**只修 `uart_collect_response`，台架 ch8 的 Hz 不会有任何变化。**

### 3.2 legacy 路径**本来就已经**在 `read_size` 处立即完成

`emit_ready_stream_chunks()` → `bus_rx_boundary_length()` 已是"攒够 `read_size` 即返回"，
**不等 10ms**。宿主用例 `test_rx_append_with_read_size`（既有）+ 本轮新增的
`test_legacy_read_size_completes_without_idle` 都锁死了这一点。
⇒ 任务书所述"10ms 静默是 100Hz 上限"在 legacy 路径上**不成立**。

### 3.3 step2 的 ch8 `read_size == 0`，走的是变长分支

解注入 manifest（`step2-inject-output.txt` 的 hex 与 `field-manifest-groundtruth.json`）：

```
field 3 (template 675): 08 a3 05 | 12 07 dda50300fffd77 | 20 64
  → id=675, write_data=dda50300fffd77, delay_ms=100
  → read_length 字段不存在 ⇒ read_size = 0
```

`read_size == 0` ⇒ 任何"有 read_size 就早返回"的改动对它**完全无效**。

### 3.4 24.4 ms/事务的真实拆解

`CMD_U0: waiting...` 行间隔直方图（step2 console，n=400）：**{26ms:170, 21ms:138, 25,27,20,22}**，
中位数 ≈24 ms，与 `txn≈410/10s`（24.4 ms/事务）吻合。

| 项 | 值 |
|---|---:|
| 7 B 请求 + 60 B 响应 @115200 8N1 | ≈5.8 ms |
| **10 ms 静默（cmd 侧，`UART_IDLE_THRESHOLD_US` bus_worker.c:1555）** | 10 ms |
| **rx_task 唤醒节拍（同一枚 10ms 在 `rx_wait_ticks()` 又付一次）** | ≈8.6 ms |
| 合计 | ≈24.4 ms |

`rx_wait_ticks()`（bus_worker.c:2007-2020，关键行 **:2017**）用 `s_last_rx_us[i] + UART_IDLE_THRESHOLD_US`
决定唤醒时刻 —— **cmd 侧去掉 10ms 而 rx 侧不去，`wait_for_uart_response_slot()` 仍以
10 ms 粒度醒来消费 pending，整体不会变快**。

**结论**：即便把两处 10ms 都去掉，24.4 → ≈14.4 ms（≈69 Hz），**仍到不了 100 Hz**。

## 4. 要达到 100 Hz 必须同时解决（三条，都不是"改一行"）

1. **变长协议的无长度定帧**：现场 JBD/Techfine 的 `read_length` 必须保持 0（否则重现
   2026-10-02 的 100% 静默丢弃）。要 100 Hz 就得为变长帧设计不依赖长度的定帧机制
   （如帧尾校验 + 最短帧长下界），这需要按厂商协议单独设计。
2. **rx_task 的 10 ms 唤醒节拍**：`rx_wait_ticks()` 的 idle 截止必须与 cmd 侧解耦，
   否则 rx 侧仍以 10 ms 粒度消费 pending。
3. **scheduler 队列满**（step2: `full=582 min_free=2`，队列深度 16、控制预留 2）：
   入队侧需要背压/加深，而不是丢弃（`missing_reports=1762 seq_gaps=84` 与此相关）。

### 5.5 为什么不做 A（不注入 read_size=60 追求台架 100 Hz 数字）

对 JBD 注入 `read_size=60` 会重现 2026-10-02 的**100% 数据静默丢弃**事故
（变长帧 LEN = 23 + 2*NTC，非 60 时短读判 error 0x03 并丢弃整帧）。
拿一个**现场不合法**的配置测出的 Hz 宣称"用户硬需求达标"是粉饰 —— 故不做。
