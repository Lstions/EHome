## 二、🔴 核心结论：真实峰值远高于此前报告

### 2.1 修正测量后的实测（115200 baud，UART1/CH340）

| 运行 | req/s | 中位间隔 | avg | max |
|---|---|---|---|---|
| 1（30s） | **56.02** | 7.43 ms | 17.8 ms | 4460 ms |
| 2（25s） | 41.36 | 7.45 ms | 24.2 ms | 4224 ms |
| 3（40s） | 30.59 | 7.44 ms | 31.9 ms | 4806 ms |

```
⇒ **中位间隔高度一致（7.43~7.45ms）**，这是稳定的单事务延迟
⇒ 但吞吐波动 30~56 req/s：每次都有 ~4.8s 的周期性停顿
⇒ avg(17.8~31.9) >> median(7.44) ⇒ **长尾主导吞吐**
⇒ 停顿原因【已定位，2026-10-11】—— **设备在崩溃重启**，见 §十

诚实口径：
  · 可复现的结论：单事务中位延迟 = 7.44ms
  · 不可复现的结论：吞吐（30~56 req/s 区间内波动）
  · 此前报告的 27 req/s 是测量伪影 + 长尾的混合结果
```

## 三、⚠⚠ 测量方法缺陷（本版最重要的发现）

### 3.1 缺陷：slave_ts.py 的 read 超时被算进帧间隔

```python
# slave_ts.py（旧，有缺陷）
s = serial.Serial(port, baud, timeout=0.01)   # 10ms 读超时
...
chunk = s.read(512)                            # 每轮最多等 10ms
time.sleep(0.0005)                             # 再加 0.5ms/轮
# 分帧还要等 FRAME_GAP = 6ms 静默才结算
```

```
后果：每帧结算至少要"等 6ms 静默 + 一次 10ms read 超时 + 0.5ms sleep"
      => 测量到的"帧间隔"被人为抬到 21ms
      => 我据此得出"设备上限 27 req/s"，**这是错的**
```

### 3.2 决定性对照（同设备、同配置，只换从机脚本）

| 从机脚本 | read 超时 | 帧间隔 | req/s | 中位间隔 | min |
|---|---|---|---|---|---|
| `slave_ts.py` | 10 ms | 6 ms | 29.5 | **21.26 ms** | 21.21 ms |
| `slave_now.py` | 2 ms | 定长 | 61.1 | **10.32 ms** | 4.10 ms |
| `slave_fast2.py` | 1 ms | 0.4 ms | **56.0** | **7.43 ms** | 6.28 ms |

```
⇒ 间隔从 21.26ms 降到 7.43ms，**设备固件一行没改**
⇒ 结论：21.26ms 主要是测量伪影，不是设备能力上限
```

## 四、P2：命令 fence 轮询 → 事件等待（已实施）

```
原实现：wait_for_uart_response_slot 用 while(has_pending_cmd) vTaskDelay(5ms)
新实现：pending 出队方在清空后 notify_pending_done()，等待者用二值信号量阻塞
覆盖：7 个 pending 出队点全部加唤醒（rx_task 5 条路径 + RX timeout + discard）
效果：吞吐 27 -> 37 req/s（+37%），但中位间隔未变（见 §三：间隔由测量决定）
```

⚠ **诚实登记**：P2 的**唤醒路径无法用 host 测试验证** ——
host 的 `xSemaphoreTake` stub 立即返回、无阻塞语义。变异自证确认：
把 `notify_pending_done` 改成空操作后 host 测试**仍然全绿**。
该测试只锁住"无 pending 时不引入延迟"这一条。

## 五、P3：被动路径 —— 尝试后**回退**（诚实记录失败）

```
原假设：bus_rx_boundary_length 无 pending 时 target=512B，
        导致 Modbus 9B 响应永远攒不够 ⇒ 被动路径不可用

尝试：改为"无 pending 时有字节就交出"
结果：**host 测试当场抓到会破坏半帧**
  test_emit_partial_block_no_emission 期望 300B 时**不**发射

根因：emit_ready_stream_chunks 在**每批字节到达后立即**被调用，
      不是只在静默窗口后调用 ⇒ "有字节" != "一帧收完"

⇒ 已回退逻辑，在 bus_rx_boundary.h 记录正确解法：
   被动路径的权威边界应是**硬件 timeout_flag**
   （uart_set_rx_timeout(port,4) = 4 字符静默，P3-1 已实现）
```

## 六、P4：UART_IDLE_THRESHOLD_US 10ms → 2ms（已实施）

```
先证明它是不是瓶颈，再决定改：
  · 主动轮询路径（有 pending + read_size）**不经过**它
    —— bus_rx_boundary_length 一收满 read_size 就返回
  · 但 **V2 命令被显式排除在 read_size 快速完成之外**
    （emit_buffered_frame: `... && !pcmd.channel_cmd_v2`）
    注释：V2 的 read_size 是"RX 窗口"不是帧长承诺
    ⇒ V2 必须等行静默 ⇒ 本常量**在 V2 关键路径上**

取值依据：硬件 timeout 在 115200 是 4 字符 = 347us、921600 是 43us
  2ms 留 5.8x~46x 余量覆盖调度延迟
  不能降到 ~0：IDF 不保证 FIFO 溢出时发 TOUT 事件，软兜底必须仍在
```

## 十、⭐ 待办 1「~4.8s 周期性停顿」的结论：设备在崩溃重启（2026-10-11）

完整分析见 [被动上传支持分析-2026-10-11.md](../分析/被动上传支持分析-2026-10-11.md) §四。

### 10.1 结论

**「停顿」不是调度、协议或波特率问题 —— 设备因堆 double-free 崩溃重启。**

```
E (7257) esp-tls-mbedtls: write error :-0x6C00
E (7258) esp-tls-mbedtls: read error :-0x004C
assert failed: tlsf_free tlsf.c:630 (!block_is_free(block) && "block already marked as free")
Rebooting...
```

backtrace 解码（`fence_s3p-n16` ELF，SHA256 与设备一致）：

```
tlsf_free <- esp_tls_internal_event_tracker_destroy(esp_tls_error_capture.c:50)
         <- esp_tls_conn_destroy(esp_tls.c:188)
         <- tls_esp_close(tls_esp.c:253)
         <- tcp_release_handle(link_tcp.c:170)
```

### 10.2 根因

`link_tcp.c:166 tcp_release_handle()` 对 `c->handle` 的「检查 → 释放 → 置 NULL」**无任何锁**，
而**两个任务**都能走到它：

| 任务 | 调用链 |
|---|---|
| `dev_link`（prio 5） | `session_poll` → `rx_pump_step` → `link_tcp_read`（`link_tcp.c:82`） |
| `report_tx` | `msg_handler_send_data_report` → `msg_handler_publish` → `sess_tx_send` → `session_send` → `tcp_send`（`link_tcp.c:235`） |

两者同时读到 `c->handle != NULL` ⇒ 都调 `io->close()` ⇒
`esp_tls_conn_destroy()` 对同一 `error_handle` 二次 `free()`。

⚠ **口径**：ESP-IDF Backtrace 是栈扫描不是精确调用链，不能据此断言帧间调用关系；
可靠的是「二次 free 的崩溃点」这一条。**「两个任务并发释放」的依据是上述代码事实**
（`c->handle` 无锁 + 两条路径都能关闭），不是栈。

### 10.3 A/B 实测（同一台 S3P，无代码改动）

| 场景 | 时长 | `tlsf_free` 崩溃 | 重启 |
|---|---|---|---|
| 空闲（无配置活动） | 70s | **0** | 0 |
| 被动配置 + 无负载 | 80s | **0** | 0 |
| 主动轮询 + **从机不应答** | 60s | **0** | 0 |
| 被动 5 fps | 58s | **0** | 0 |
| **主动轮询 + 从机应答 47.85 req/s** | 60s | **9** | 9 |
| **被动 100 fps** | 78s | **9** | 10 |
| **被动 100 fps（复现）** | 78s | **9** | 10 |

⇒ **与上行负载量正相关**，与被动/主动无关。每次重启前 uptime：4293~9362 ms。

### 10.4 与本文档 §二 数据的对应

`slave_fast2.py` 60s 实测：`req_per_s=47.85, median=7.47ms, max=4205.79ms`，
**同一时段设备重启 9 次**。⇒ §二 表里的 `max` 4460/4224/4806 ms
**就是重启时长**，`avg >> median` 也是被重启拉高的。

⇒ 这解释了：(a) 中位高度稳定（7.43~7.47ms）而均值波动大；
(b) 吞吐在 30~56 req/s 随机波动（取决于窗口撞上几次重启）；
(c) 与波特率无关。

### 10.5 修法（待实施）

`tcp_release_handle` 加互斥，锁内**先摘指针置 NULL**、**出锁后再 close**；
并审计 `tcp_send` / `link_tcp_read` 对 `c->handle` 的**读取**是否也走同一把锁
（否则 TOCTOU 仍在）。验收：补并发 close 的 host 用例
（现有 `test_close_is_idempotent` 是单线程幂等，覆盖不到竞态）+ 真机 60s 零崩溃。
