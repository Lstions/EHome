## 二、🔴 瓶颈定位（决定性数据）

### 2.1 UART0 波特率趋势（同工具 `slave_ts.py`，dma=off，同板同配置）

| 波特率 | req/s | crc_bad | 中位间隔 | 纯传输 |
|---|---|---|---|---|
| 9600 | 0.70 | 38 | 1053 ms | 17.7 ms |
| 115200 | **27.02** | 6 | **21.26 ms** | 1.5 ms |
| 921600 | 26.97 | 9 | 21.27 ms | 0.18 ms |

```
⇒ 115200 起就【饱和在 27 req/s / 21.26ms】
⇒ 再提高 8 倍波特率，吞吐【零提升】
⇒ 瓶颈是固定的 ~21ms 软件开销，与波特率无关
⇒ 9600 的 0.70 req/s 是因为：17.7ms 纯传输 + 软件开销，
   且 crc_bad=38 说明分帧在低波特率下也失败
```

### 2.2 21ms 的成分

```
日志证据：wait_for_uart_response_slot 的实测轮询间隔 = 21ms
          而 UART_RESPONSE_WAIT_MS = 5ms（4 倍差距）

链条：
  cmd_task 发命令 → pending 入队 → wait_for_uart_response_slot
    while (has_pending_cmd) vTaskDelay(5ms);     ← 轮询粒度 5ms
  rx_task 完成响应 → 清空 pending
    完成判据 = read_size 到齐 或 UART_IDLE_THRESHOLD_US(10ms) 静默

⇒ 10ms(idle 判定) + 5ms(轮询粒度) + 任务调度延迟 ≈ 21ms
```

## 三、🔴 被动上传路径的问题（回答"为什么还要主动轮询"）

```
bus_rx_boundary_length(buffered, pending, channel_cmd_v2, read_size):
    if (buffered == 0 || (pending && v2 && read_size == 0)) return 0;
    target = read_size > 0 ? read_size : BUS_RX_FIXED_BLOCK_SIZE(512);
    return buffered >= target ? target : 0;

⇒ 无 pending 命令时（真被动）: target = 512 B
⇒ 被动数据必须【攒够 512 字节】才会上报
⇒ 对小报文（Modbus 9 B 响应）永远攒不到 ⇒ 被动路径形同虚设
⇒ 所以只能主动轮询

⚠ 补充：rx_task 还有【硬件 idle 边界】兜底（静默 >10ms 也算完成），
   所以被动路径不是完全不可用，而是对短报文有 10ms+ 延迟。
```

## 四、🔴 `dma_enabled` 对 UART 的真实作用（更正）

```
代码证据链：
  1. esp_driver_uart/src/uart.c 中 "uhci" 命中 = 0
  2. uart.h 中 "dma" 命中 = 0（无公开 UART DMA API）
  3. uart_driver_install(port, rx, tx, depth, &q, 0)
     第 6 参数 = intr_alloc_flags（中断标志，非 DMA）
  4. 本工程 uhci_* 调用 = 0（3 处命中全在注释）

⇒ dma_enabled 对 UART【只改驱动缓冲大小】(512 vs 256 B)
   —— bus_dma.c:748-753 注释已写明

严格 A/B（同工具、同板、同波特率，只改 dma_enabled）：
  | 波特率 | dma=on | dma=off | 结论 |
  |--------|--------|---------|------|
  | 9600   | 0.95   | 0.90    | 无差异 |
  | 921600 | 20.91  | 23.46   | 差异在噪声内 |

⇒ **上一版"UART0 DMA=on 导致劣化 16 倍"的结论不成立**
   当时的差异来自配置/工具/时机的混淆变量，不是 DMA。
```

## 五、实测峰值（修正后）

| 配置 | 单通道吞吐 | 说明 |
|---|---|---|
| 9600 | 0.7~16 req/s | 物理受限 + 分帧失败 |
| **115200** | **27 req/s** | 软件上限（21ms/事务）|
| 921600 | 27 req/s | 同上，无提升 |

```
单通道软件上限: 27 req/s（21.26ms/事务）
两路闭环合计: ~54 req/s
理论目标（3 通道 x 5 从机 / 100ms）: 150 req/s

⇒ 若消除 21ms 软件开销（改事件驱动而非轮询等待），
  115200 下可达 ~660 req/s/通道（纯传输 1.5ms）
⇒ 当前 27 req/s 的瓶颈【完全在软件】，不在硬件/波特率
```

## 七、⚠ 本版更正的三处结论（诚实记录）

| # | 上一版结论 | 事实 | 更正依据 |

| 1 | 用 9600 波特率压测 | 9600 是我沿用旧脚本的参数，**不是约束** | 文档 §201.4 早已写明需用户裁决；用户明确"所有波特率都可用" |

## 八、待办

1. **消除 21ms 软件开销**（最高价值）—— 把 `wait_for_uart_response_slot`
   的轮询等待改为事件驱动（`xTaskNotify`/信号量），消除 5ms 粒度与调度延迟
2. **被动路径可用化** —— 评估把 `BUS_RX_FIXED_BLOCK_SIZE`(512) 改为
   可配置/更小值，或为"无模板通道"提供协议级帧边界
3. 评估 `UART_IDLE_THRESHOLD_US`(10ms) 是否可降至 1~2ms
4. 三路全开压测（UART2 需 C6 侧配合或改接宿主）
