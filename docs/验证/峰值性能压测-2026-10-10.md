## 三、🔴 发现 1：命令级 interval 的**真实来源**（配置陷阱）

```
现象：配置 interval_ms=100，实测恰好 1.00 帧/s（间隔 1.0077s）

根因：edge_devices.interval_ms 只是"设备级"字段，**不生效**。
      真正生效的是【命令级】interval：
        command_intervals 覆盖值 > 驱动 CommandTemplate.IntervalMs
      prs3001.read_rainfall 的 IntervalMs = 5000（builtin.go:288）

证据（解码后端日志里的 manifest hex）：
  command 子帧 f3.interval = 0x1388 = **5000 ms**
  => 5 从机 / 5s = 1.00 命令/s  ← 与实测完全吻合

修复：UPDATE edge_devices SET command_intervals = '{"read_rainfall": 10}'
效果：0.96 -> 16 req/s（17 倍）
```

## 四、🔴🔴 发现 2：UART0 开 DMA 导致链路严重劣化（最重要）

| 实验 | UART0 模式 | 从机侧 req | crc_bad | CMD_U0 txn/10s |
|---|---|---|---|---|
| 1 | **DMA=on** | 22 | **263** | 1.0 |
| 2 | polled | 194 | 24 | **16.0** |
| 3 | polled | 23 | 89 | —（链路不稳）|

```
⇒ DMA=on 时：从机收到的几乎全是坏帧（crc_bad=263 > req=22），
  设备侧每 ~1005ms 一次 RX timeout => 卡在 1 req/s
⇒ DMA=off 后：从机 req=194（能正确分帧），设备侧 16 txn/s
   **提升 16 倍**

⚠ 但实验 3 又退化（req=23, crc_bad=89）=> UART0 的**物理链路本身不稳定**，
  DMA 只是放大了它。UART1（CH340）全程 crc_bad=0，链路干净。

可疑点（未定论）：
  · CP2102 与 S3 UART0 之间的电平/接线质量
  · S3 UART0 的 GPIO43/44 与 USB-JTAG 复用引脚相邻（板级串扰）
  · 已排除：控制台占用（CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y，UART_NUM=-1）
```

## 五、🔴 发现 3：命令队列深度是真瓶颈

```
SCHEDULER: Stats: samples=196 full=10064 min_free=2   （每 10s）
  samples = 成功入队；full = 因队列压力**丢弃**

⇒ 想发的命令数远超消费能力，队列只剩 2 个空位，每 10s 丢弃 1 万条
  队列：uart*_cmd_queue 深度 16 x sample_cmd_t(180B)
  消费端：worker 每通道 ~16 req/s

⇒ 深度 16 对"满配 100Hz"是不够的 —— 但**加深队列不是解法**，
  因为瓶颈在物理层（9600 波特率）与 rx_task 的 10ms idle 窗口。
```

## 六、实测峰值汇总

| 通道 | 模式 | 实测吞吐 | 中位间隔 | crc_bad |
|---|---|---|---|---|
| ch103/UART0 (CP2102) | DMA | 1.0 req/s | 1005ms | 263 |
| ch103/UART0 (CP2102) | polled | 16.0 req/s | — | 24~89 |
| ch104/UART1 (CH340) | polled | **12.0~16.1 req/s** | **42.5ms** | **0** |
| ch105/UART2 (→C6) | polled | 无对端 | — | — |

```
实测峰值（2 路真实收发闭环）: ~32 req/s
单通道瞬时上限（UART1 中位间隔 42.5ms）: ~23.5 req/s
理论目标（3 通道 x 5 从机 / 100ms）: 150 req/s
物理上限（9600 8N1，17B/事务 + 间隔）: ~56 req/s/通道

⇒ 单通道 23.5 req/s 已达物理上限的 42%
⇒ 差距主因：rx_task 的 UART_IDLE_THRESHOLD_US=10000（每条响应等 10ms）
            + 模板 delay_ms（原为 100，已归零测试）
```

## 八、待办

1. **UART0 物理链路诊断**（换线/换板对比，确认 CP2102 侧问题）
2. **DMA 与 polled 的性能边界**：本次仅证明 DMA=on 时劣化，
   但未定位是 DMA 本身还是 DMA+该链路组合
3. **提升单通道吞吐**：评估降低 `UART_IDLE_THRESHOLD_US`（10ms）
   与 `UART_RESPONSE_WAIT_MS`（5ms）的影响
4. 队列深度 16 是否需调整 —— 需先解决物理层瓶颈
