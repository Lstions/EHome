**通用证据纪律**（方法论 §6）：
- 串口必须**复位后**抓启动段（`s.setDTR(False); s.setRTS(True); sleep(0.15); s.setRTS(False)`），
  不能 attach 到已经跑起来的设备；

**证据落点**：`docs/验证/证据/<date>-ipv6-<profile>.log` + broker clients 输出

## 附 A：来自 task-4 / protocol-v3 的硬发现（必须纳入本矩阵验收）

以下三条已在各自工作流中被实测/代码核验，与内存门禁直接相关，因此列入本矩阵。

### A1. SoftAP=n + 空 SSID 的链接风险（task-8 首启验收）

- **发现**：`sdkconfig.defaults` 已将 `CONFIG_ESP_WIFI_SOFTAP_SUPPORT=n`；
  而 `components/wifi_mgr/wifi_mgr.c:110` 的无凭据 fallback 仍调用 SoftAP provisioning 路径。
  当前能编译/链接只是因为默认 SSID 非空、编译器把 AP 分支 dead-strip；
  当 `CONFIG_COLLECTOR_WIFI_SSID=""` 时会在链接期直接缺 `esp_netif_create_default_wifi_ap`（实测链接错误）。
- **验收判据（task-8 / 首启配网）**：
  1. 以空 SSID 配置构建仍必须 **链接通过**（该路径在 `#if CONFIG_ESP_WIFI_SOFTAP_SUPPORT` 之内）；
  2. `CONFIG_COLLECTOR_WIFI_SSID=""` 且无凭据时，设备应进入明确的"待配网/失败上报"状态，而不是 panic/静默重启；
  3. 参考证据：`esp32-collector/sdkconfig.defaults:105-110` 的注释与实测链接错误。
- **自动化**：构建期即可（`CONFIG_COLLECTOR_WIFI_SSID=""` + `SOFTAP_SUPPORT=n` 组合链接）；实机首启步骤人工。

### A2. IPv6-only 缺口（`IP_EVENT_GOT_IP6` 未注册）

- **发现**：`components/wifi_mgr/wifi_mgr.c` 只在 `IP_EVENT_STA_GOT_IP`（IPv4）上注册事件；
  全仓库没有 `IP_EVENT_GOT_IP6` 的注册或处理（实测 grep 为 0）。
- **后果**：IPv6-only 或"IPv6 先拿到地址"的网络里，WiFi 状态机不会因 IPv6 地址就绪而前进，
  MQTT 可能用它不该用的时序启动；场景 4 的"IPv6 连接正常"不能只看 `CONFIG_LWIP_IPV6=y`。
- **验收判据（场景 4 增强）**：
  1. 必须观测到 `IP_EVENT_GOT_IP6`（或等价的 `esp_netif` IPv6 地址事件）被处理；
  2. IPv6-only（无 IPv4 地址）环境下 WiFi 状态可以前进到 MQTT 连接；
  3. 双栈环境下 IPv4 与 IPv6 路径都不回归。
- **自动化**：host 不可测（IDF 事件语义）；必须实机 + IPv6-only 环境。

### A3. R1：MQTT 单帧下行上限 2,011 B vs 最坏 Manifest 2,463 B

- **发现**：`CONFIG_MQTT_BUFFER_SIZE=2048`；esp-mqtt 对超过 `in_buffer_length` 的 PUBLISH
  拆成多个 `MQTT_EVENT_DATA`，而固件**无重组逻辑**（`current_data_offset` 全仓库只出现在
  `managed_components/`）。按 node_id 16 字符计算，单事件 payload 上限 **2,011 B**；
  而协议 v3 文档 §3.1 实测 S3 最坏 Manifest **2,463 B**（12 GPIO/8 PWM/8 DMA/log_stream 全顶满）。
- **后果**：极端配置第一段被当完整 Manifest 解析（失败→`ConfigResult(false)`），第二段首字节被忽略，
  **该配置永远下发失败**（不是"慢"，是"永远失败"）。
- **验收判据（场景 2 增强）**：
  1. 后端 publish 前必须有"编码后字节 ≤ 2,011"的门禁（或按 node_id 精确计算），超限拒绝并给可诊断错误；
  2. 固件在解析失败时必须 fail-closed 并上报（现状已满足）；
  3. 一期后补；在该门禁上线前，场景 2 的"满配 manifest"必须显式记录实际编码字节数，不能默认它 ≤2,011。
- **自动化**：后端单测（编码字节断言）+ host 侧（构造 >2,011 B 帧验证固件 fail-closed）；实机为最终确认。
- **来源**：`docs/设计/协议v3-私有变长二进制-评估与设计.md` §3.1 / §8 R1（protocol-v3 task-7 实测）。
