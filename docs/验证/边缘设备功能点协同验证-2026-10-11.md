# 边缘设备功能点协同验证（S3 真机 + 本地后端 + CP210X/CH340 从机）

日期：2026-10-11　分支：`feat/v3-refactor`　提交：`66ee7257` / `5eafe39e`

## 0. 一句话结论

在 **S3 真机（30EDA0A9A808, esp32s3p, fw 2.8.0）+ 本地后端（8081/8443）** 上，
用 **CP210X（ch103/UART0）与 CH340（ch104/UART1）** 模拟 PRS-3001 从机，
逐项验证了边缘设备的数据采集、启停、CRUD 契约、继承候选、init 与受控操作。
过程中发现并修复 **3 个真实缺陷**（其中 1 个使整条采集链从未成功过），
另有 **3 项既有问题** 独立登记。

### 帧契约（从 `backend/internal/drivers/builtin.go:283` 读出）

```
请求  01 03 00 00 00 02 C4 0B        8 B   (FC03 读 2 个保持寄存器)
应答  01 03 04 <d0 d1 d2 d3> <CRC>   9 B   (bytecount=4)
  rainfall    = be16(d0 d1) / 10.0  mm
  illuminance = be16(d2 d3)         Lux
```

## 2. 缺陷 1（阻断级）：PRS3001 `byteCount=4` 解析缺口

**现象**：15 个 `edge_devices` 全部 `enabled=true` 却永远 `status=pending/offline`，
`device_data`/`unified_data` 一条不落。

**根因**：shipped 模板 `read_rainfall` 的 `WriteData=010300000002C40B` 读 2 个寄存器 ⇒
`ReadLength=9` ⇒ 应答 `bytecount=4`；但 `PRS3001Driver.parseLegacy` 的 `switch byteCount`
只有 `{2,6,8}` 三个分支，**恰好没有 4**，于是必然走 `default` 报
`prs3001: unexpected byte count 4, expected 2/6/8`，采样被 `consumers_heavy.go` 丢弃。

**证据（修复前，探针实测）**：

```
PROBE byteCount=2 raw=01030200c8b9d2 -> fields=[{rainfall 20 mm}] err=<nil>
PROBE byteCount=4 raw=01030400c801f47b4 -> fields=[] err=prs3001: unexpected byte count 4, expected 2/6/8
```

**修复**：`parseLegacy` 增加 `case 4`（rainfall + illuminance），并把错误文案更新为 `2/4/6/8`。

**回归钉死**（2 条新测试）：
- `TestPRS3001Driver_ParseData_4ByteCount` —— 值语义（20mm / 500Lux）
- `TestPRS3001Driver_ShippedTemplateIsParsable` —— 用模板 `ReadLength` 反推 bytecount 造帧，
  必须可解析。这条防的是「模板与解析器再次漂移」。

**修复后真机结果**：

| 设备 | 通道 | 从机 | status | error_code | 解析结果 |
|---|---|---|---|---|---|
| 187 | 103 | CP210X | **active** | 0 | rainfall 20 mm + illuminance 500 Lux |
| 188 | 104 | CH340 | **active** | 0 | rainfall 35 mm + illuminance 777 Lux |
| 189 | 105 | 未接 | offline | 3 | —（对照） |

## 3. 缺陷 2：创建路径 node 不存在返回 400 而非 404

设计文档 §7.2 要求「node 不存在 404」。实现缺少 node 存在性前置校验，
不存在的 node 会先撞 channel 归属校验，返回 `400 channel does not belong to node`。

修复：事务内先查 node，用哨兵 `errNodeNotFound` 在出口映射 404。

## 4. 缺陷 3：三元重复返回 400 而非 409

`checkDeviceUniqueness` 返回裸 `error`，而事务出口只有 `conflictError` 才映射 409。
文档 §7.2 与 §1.1 冲突文案（前端按 409 渲染）都要求 409。

修复：`newConflictError` 包装。

> 同时修正 3 个既有测试：它们此前断言 400（即把缺陷本身钉成了契约）。
> 这类「绿」是假绿 —— 锁定了实现而非契约。

## 5. 启停验证（真机）

| 阶段 | ch103 请求速率 | ch104 请求速率 | 结论 |
|---|---|---|---|
| 启用 | ~18/s | ~20/s | 采集进行中 |
| 禁用 10 台设备后 | **0/s** | **0/s** | 完全停止 |
| 重新启用后 | ~18/s | ~20/s | 恢复 |

禁用期间两个从机 20 秒内零请求 —— 节点确实停止下发，不是仅前端状态变化。

## 6. 继承候选与删除接续（§7.4 E2E）

1. 创建 `ch103 hw=6` → `201 id=202 logical_device_id=41`
2. 删除（软删）→ 行保留，`deleted_at` 有值，`logical_device_id` 保留
3. `GET /candidates?node_id=…&channel_id=103&hardware_id=6&type=prs3001`
   → **逻辑设备 41 `match_weight=100` 排第一**（同 node+channel+hardware_id+type，原位置重建）
   其余同类型候选 60（同 node 同 type，非原位置）
4. 重建并继承 `logical_device_id=41` → `201 id=203`
5. `GET /edge-devices/203/logical-device-info` → `instance_count=2`（新旧两实例同一逻辑身份）

**身份作用域**：已软删实例 `latest-data` → 404；存活实例 → 200。

## 8. 受控操作（真机闭环）

```
GET  /edge-devices/187/actions
     -> read_rainfall  available=true
     -> reset_rainfall available=false (availability_code=protocol_unverified)

POST /edge-devices/187/operations   (Idempotency-Key 必填)
     -> 202 QUEUED  command_id=76b26d13-…
同 key 重放
     -> 202 同一 command_id（幂等；不产生第二条物理指令）
GET  /device-operations/76b26d13-…
     -> status=SUCCEEDED
        verified_result=[{rainfall,20,mm},{illuminance,500,Lux}]
POST reset_rainfall（高风险未验证）
     -> 409 action unavailable（门禁生效）
```

`verified_result` 来自真机读回并核对，不是模拟值 —— 这是本轮最强的端到端证据。

## 9. 门禁与容量（负向验证，均为正确拒绝）

- 通道有存活设备时禁用 → `500 cannot disable channel referenced by edge devices`
- 腾空设备后禁用 → 200（放行）
- 内联通道引脚冲突 → `400 GPIO pin 4 已被通道 104 (UART1) 占用`
- 通道容量上限 → manifest 被拒 `channel 103 has 6 edge devices; collector limit is 5`
