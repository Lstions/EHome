# 测试判据反模式 —— 那些「返回了看起来正确的结果」的验证

> **状态**: 生效中

> **触发**: 本轮（容量优化 task-17/18/19/20）连续踩到 8 个**同族**缺陷，形态各异但根因是同一句话。

## 0. 一句话

**假绿不是「测试没写」，而是「判据本身不成立，但它返回了一个看起来正确的结果」。**

这类缺陷比"没有测试"更危险：没有测试时人是警惕的；假绿时人**拿着一个证据去下结论**，
而那个证据是空的。本轮 11 个反模式里，有 4 个直接导致了错误的技术决策
（#2 差点删掉唯一一条 `(device_id, timestamp)` 索引；#5 让 44 个包"全绿"而 PG 用例一个都没跑；
#4 让 EXPLAIN 断言在错的 schema 上稳定红/绿）。

判断一条验证是否可能假绿，问三个问题：

1. **这个判据在「被测对象错误」时会返回什么？** 如果答案是"也返回成功"，它就是假绿。
2. **这个视图/接口本身能不能表达这件事？** 如果它天然看不到目标对象，空结果不代表"没有了"。
3. **这条用例在什么情况下根本不会执行？** Skip、build tag、env 未转发、条件编译 —— 都是静默的。

## 1. 反模式 1：断言写松了就等于没写

### 现场（2026-11-07，task-20 索引瘦身）

删掉 `(device_id)` 单列索引的前置条件是「它被某条 `(device_id, ...)` 复合索引前缀覆盖」。
第一版守卫用例这么写：

```go
// ❌ 第一版
for _, norm := range templateColumnLists(table) {
    if strings.HasPrefix(norm, "device_id, ") {   // ← 太松
        covered = true
    }
}
```

变异验证：把 `device_data` 的 `device_ts_idx (device_id, timestamp)` 从模板里删掉。

**期望**：用例变红。
**实际**：**绿的**。因为剩下的 `(device_id, created_at DESC)` 也满足 `HasPrefix("device_id, ")`。

而 `(device_id, created_at DESC)` **救不了** data-summary 的
`ORDER BY timestamp ASC LIMIT 1` —— 它能过滤 device_id，但给不了 timestamp 有序，
规划器只能扫该设备全部行再排序，等价于退化。

改成**必须具体是 `(device_id, timestamp)` 开头**之后才真红：

```go
// ✅ 第二版
if norm == "device_id, timestamp" || strings.HasPrefix(norm, "device_id, timestamp, ") {
    covered = true
}
```

### 同族变体：`strings.Contains(body, "processAlive(pid)")`

`backend/testutil/reap_test.go:95` 记录了同一件事的另一例：

> 这里**不再**用 `strings.Contains(body, "processAlive(pid)")` 断言安全规则。
> 该判据在 `if processAlive(pid) && false {…}` 之下依然成立 —— 变异已证明它是假绿。

### 判据

**变异验证的价值不在「证明代码是对的」，而在「证明断言会在代码错的时候变红」。**
写完一条安全断言后，必须手动造一次违规，看着它红。红不了 ⇒ 重写断言。

### 自查清单

- 只断言「有 X」而不断言「X 是哪一条」⇒ 松
- 只断言「不 panic」而不断言「返回值是什么」⇒ 松
- 只断言「长度 > 0」而不断言「长度是 3」⇒ 松
- 用 `Contains` / `HasPrefix` 断言一个本应精确相等的东西 ⇒ 松

## 2. 反模式 2：0 次扫描 ≠ 没有读路径

### 现场（2026-11-07，生产索引盘点）

`pg_stat_all_indexes` 40 小时窗口：

| 索引 | 大小 | idx_scan | last_idx_scan |
|---|---:|---:|---|
| `device_data_device_id_timestamp_idx` | 225 MB | **0** | **从未** |

按「0 次扫描 + 不在模板里」⇒ 判定为**遗留垃圾，可删**。

**这个判定是错的。** 两条原因叠加：

**① 它的读路径是低频的。** 它服务的是 `/:id/data-summary` 端点 ——
即「删除设备确认弹窗」和「合并历史」时才触发。用户不删设备，这条查询就一次都不跑。
40 小时里 0 次完全正常，**不代表没有读路径**。

**② 更关键：它是模板的事实实现，只是名字是老的。**
`ensurePartitionParentIndexes` 判「索引是否已存在」用的是**列清单包含**
（`strings.Contains(normalizeIndexColumns(def), "(device_id, timestamp)")`），**不是索引名**。
模板里那条叫 `device_data_device_ts_idx`，列一模一样 ⇒ 只要老名字那条在，
模板那条**永远不会被创建**。删老名字那条 = 删掉唯一那条。

### 实测代价（隔离 PG bench，30 万行 device_data）

构造一台「只在分区末尾有数据」的新设备（data-summary 的最坏情形：`ORDER BY timestamp ASC LIMIT 1`
要从分区头部一路扫到该设备第一行）：

```
保留 (device_id, timestamp) : Index Only Scan              0.074 ms      7 buffer
删掉                        : Index Scan on timestamp_idx  17.77 ms  2394 buffer
                              Rows Removed by Filter: 216000
```

扫描量与**分区总行数**成正比，不是 O(log n)。千万行分区上就是秒级弹窗。

### 判据

判一条索引/缓存/代码路径"死了"之前，必须先回答：

1. **它的调用频率上界是多少？**（每次设备删除一次 ≠ 每天百万次，但也是"有调用"）
2. **统计窗口够不够长到能看见它？**（40 小时窗口看不见「每月一次」的东西）
3. **它是不是被别的机制间接依赖着？**（名字不同但列相同的等价索引、按列匹配的补齐逻辑）

更根本的一条：**"未使用"和"不可删除"是两个不同的判断。**
`idx_scan = 0` 只能支持第一个，第二个必须单独论证（这里是"删了会退化多严重"）。

## 3. 反模式 3：判据存在性要问「这个视图/接口本身能不能表达这件事」

### 现场（2026-11-07，task-20 验收 SQL）

Lead 给的验收判据：

```sql
select indexrelname, idx_scan from pg_stat_all_indexes
where relname like 'unified_data%' or relname like 'device_data%';
-- 期望：两条索引消失
```

**这条查询的"空结果"证明不了任何事**，因为 `pg_stat_all_indexes` 对分区表
**只有子分区级行，没有父索引行**。实测（PG 18）：

```
$ select distinct relname from pg_stat_all_indexes where relname like 'device_data%';
 device_data_202610
 device_data_202611        ← 只有子分区，没有 'device_data'

$ select c.relname, (select count(*) from pg_stat_all_indexes s where s.indexrelid=i.indexrelid) stat_rows
  from pg_index i join pg_class t on t.oid=i.indrelid join pg_class c on c.oid=i.indexrelid
  where t.relname='device_data';
 device_data_device_id_idx | 0     ← 父索引在这个视图里恒为 0 行
```

⇒ 父索引名 `device_data_device_id_idx` 在这个视图里**从来就不存在**，
无论删没删。用它判"删掉了" ⇒ 恒通过 ⇒ 假绿。

### 正确判据（两类问题要分开问）

**① 「删没删」⇒ `pg_indexes`（按 indexname 精确查）：**

```sql
select indexname from pg_indexes
where indexname in ('unified_data_device_id_idx','device_data_device_id_idx');
-- 期望 0 行
```

**② 「扫描转移到哪了」⇒ 仍用 `pg_stat_all_indexes`，但按去掉月份前缀的名字聚合：**

```sql
select regexp_replace(indexrelname, '_[0-9]{6}_', '_') as index_name,
       pg_size_pretty(sum(pg_relation_size(indexrelid))) as total_size,
       sum(idx_scan) as scans, max(last_idx_scan) as last_used
from pg_stat_all_indexes s join pg_class c on c.relname = s.indexrelname
where s.relname ~ '^(unified_data|device_data)_2026[0-9]{4}$'
group by 1 order by 3 desc;
```

这样 `unified_data_device_id_idx` 才会**整行消失**（而不是"一直就没有"）。

### 判据

看到一个"空结果"时，先问：**这个视图/接口能不能表达"存在"这件事？**
如果不能，空结果 = 无信息，不是"否"。

同族例子：
- 用 `GET /api/x` 的 404 判"记录被删了" —— 也可能是路由没注册（两者都返回 404）
- 用 `git diff HEAD` 判"文件没改" —— 也可能是文件未被追踪
- 用 `pg_stat_all_indexes` 判"索引被删" —— 也可能是这个视图根本看不到它

## 4. 反模式 4：测试 schema ≠ 生产 DDL（AutoMigrate vs 裸 DDL）

### 现场（2026-11-07，`TestPostgresDeviceScopedPlan`）

测试库走 `testutil.OpenTestDB` → `AutoMigrate(allModels)`，
而`models.UnifiedData` 的 `SensorName` 字段带 `gorm:"index"` ⇒ AutoMigrate 建出单列索引
`idx_unified_data_sensor_name`。

**生产 DDL 刻意不建这条**（`partition_mgr.go` 的阶段0 死索引清理，理由写在模板注释里），
并且生产有两条复合索引是 AutoMigrate **不会建**的：

```
unified_data_device_sensor_ts_idx  (device_id, sensor_name, timestamp) INCLUDE (value)
unified_data_device_ts_idx         (device_id, timestamp)
```

后果：EXPLAIN 计划的断言在**错误 schema** 上跑 ⇒ 稳定红（或稳定绿），
而它与生产是否正常**无关**。真实数据 1,276 万行时红得最明显。

修复：`history_points_pg_test.go` 的 `alignUnifiedDataSchemaToProduction()` ——
显式 DROP 掉 AutoMigrate 多出来的、显式建出生产有而 AutoMigrate 没有的，
并在建完后**自检**（0 条 sensor_name 前导、≥3 条 device_id 前导）。

### 判据

**任何"在测试库上 EXPLAIN 之后下结论"的用例，都必须先证明测试 schema 与生产同形。**
否则它测的是"测试库的 schema"，不是生产。

自查：把 `partitionParentIndexes`（生产 DDL 的唯一真源）与被测库的实际索引清单对一遍，
不等就先对齐。

## 5. 反模式 5：跨方言的时间精度不等价（SQLite 纳秒 vs PG 微秒）

### 现场（2026-11-07，回填游标）

第一版游标推进用 `watermark + 1ns`（"跳过已处理的那一条"的经典写法）。

- SQLite 用例**全绿**（SQLite 时间精度足够区分 `t` 与 `t+1ns`）；
- PostgreSQL 的 `timestamptz` 精度是**微秒** ⇒ `t+1ns` 存回去还是 `t` ⇒
  游标永不推进 ⇒ **无限重复处理同一批**（生产上表现为静默烧 CPU，无报错）。

修复：复合游标 `(timestamp, device_id)`，**绝不做时间加法**
（`backend/internal/backfill/partition_job.go:14` 文件头已写成硬约束）。

### 判据

**任何"边界 + 1"的写法，都要先确认目标存储的精度的量级。**
更一般地：**SQLite 绿 ≠ PG 绿**。凡涉及时间精度、排序稳定性、NULL 语义、
字符集比较的地方，方言差异都会让 SQLite 用例给出错误的信心。

## 6. 反模式 6：条件用例被静默 Skip（环境变量没转发）

### 现场（2026-11-07，`gow.sh` 不转发 `EHOME_*`）

本仓 PG 用例用 `requirePostgres(t)` 判跳过：

```go
func requirePostgres(t *testing.T) {
    if !testutil.IsPostgres() { t.Skip("requires PostgreSQL") }
}
```

而 `gow.sh` 用 `docker run` 跑测试，**原先不转发 `EHOME_*` 环境变量**。
于是 `EHOME_TEST_DB=postgres gow.sh test ./...` 里所有 PG 用例**全部 Skip**，
包级结果仍是 `ok`。

这是最坏的一类假绿：**用例根本没执行，但看起来像通过**，且不加 `-v` 完全看不出来。

修复：`gow.sh` 自动收集并注入全部 `EHOME_*` 变量。

自查（**2026-11-08 修正，三条都已实测**）：

```bash
# ① 最直接：看 docker run 命令里有没有 -e EHOME_XXX=...（bash -x 打印实际命令）
EHOME_PROBE=1 GOW_WORKDIR=backend bash -x scripts/gow.sh env 2>&1 | grep -o '\-e EHOME_PROBE=1'
# 实测输出：-e EHOME_PROBE=1

# ② 看转发计数（gow.sh 往 stderr 打一行）
EHOME_TEST_DB=postgres GOW_WORKDIR=backend scripts/gow.sh version 2>&1 | grep 转发
# 实测输出：[gow] 转发 2 个 EHOME_* 变量进容器

# ③ 负向对照：不设任何 EHOME_* 时，那行必须**不出现**（否则说明它在瞎打）
env -u EHOME_TEST_DB GOW_WORKDIR=backend scripts/gow.sh version 2>&1 | grep -c 转发
# 实测输出：0
```

> ⚠ **本节原先写的自查命令是坏的，而且坏了很久没人发现**：
>
> ```bash
> GOW_VERBOSE=1 scripts/gow.sh env | grep EHOME     ← 两个缺陷叠加
> ```
>
> ① `GOW_VERBOSE` **从未被实现过** —— `grep -c GOW_VERBOSE scripts/gow.sh` = 0。
>    它只是一个「看起来该存在」的开关名，写进了文档就成了「文档说的功能」。
> ② 即使变量存在，`go env` **只打印 Go 自己的环境变量**，自定义的 `EHOME_*`
>    永远不在它的输出里（实测 `gow.sh env | grep -c '^EHOME_'` = 0）。
>
> 所以那条命令**无论 gow.sh 怎么改都不可能通过** —— 它是一句从未被执行过的验证命令。
>
> **这是一个「反模式文档自己犯了它记录的错」的例子**：
> 本文档通篇在讲「假绿 / 从未执行的验证」，而它自己的自查命令正是一条从未执行的验证。
> 教训：**写进文档的命令必须当场跑一遍**，否则它不是验证，是愿望。

### 判据

**任何"条件跳过"的用例，都必须有办法证明它这次真的执行了**：

- 跑 PG 用例时看 `-v` 输出里是 `--- PASS` 而不是 `--- SKIP`；
- 或者让关键用例在 state 不满足时 `t.Fatalf` 而不是 `t.Skip`（本轮 `EHOME_PARITY_OUT`
  就是这么改的：从 Skip 改 Fatalf，防止环境变量没传到时静默跳过）。

## 7. 反模式 7：并发测试互踩（隔离机制的判据失效）

### 现场（2026-11-07，`testutil.reapStaleSchemas`）

PG 用例用隔离 schema `test_<pid>_<nano>`，并用 `reapStaleSchemas` 回收
"pid 已死"的残留 schema（判据：`syscall.Kill(pid, 0)`）。

但 `gow.sh` 每次 `docker run` 都是**新的 PID namespace** ⇒ 容器内看到的 pid
与宿主/其它容器的 pid 不可比。并发跑两个 PG 测试时，A 的 schema 会被 B 判为
"pid 已死"而 DROP 掉（实测：A 的 schema 数从 1 变 0，而 A 仍在运行）。

后果：**并发跑 PG 测试 = 随机假失败/假通过**。

当前纪律：**PG 测试必须串行**（`-p 1`，且不并发跑两个 `gow.sh test`）。
根治需要把判据从 pid 换成"持有时间 + 心跳文件"，尚未做。

### 判据

**隔离机制本身也需要判据。** 用隔离资源（schema / 数据库 / 端口 / 临时目录）时，
必须回答：**这个隔离靠什么判"该回收了"？那个判据在运行环境里成立吗？**

`Kill(pid, 0)` 在"PID namespace 不共享"的环境里**恒返回 ESRCH**（进程不存在），
于是"已死"恒为真 ⇒ 回收器会删掉一切看到的 schema。

## 8. 反模式 8：**「没验成」被统计成「验了且通过」**（2026-11-07 收工前最后一次抓到）

同一天在同一份验收脚本（A6）里连抓**三个**同族缺陷：

```
① fields 为空     ⇒ for 循环零次 ⇒ a6_fail=0 ⇒ 输出「A6 通过」
   （一个字段都没验，却报通过）
② 全部 ERR        ⇒ 每个字段 warn + continue ⇒ a6_fail=0 ⇒ 输出「A6 通过」
   （TOKEN 失效 / API 不通，一个都没验成）
③ fields 为空时   ⇒ 「A6 硬失败」和「A6 通过」两条矛盾结论同时打印
```

**根因是同一个**：`a6_fail` 只统计「验了并且失败」，不统计「压根没验成」。

### 修法

加一个`a6_checked` 计数器，末尾判 `a6_checked == 0` ⇒ **硬失败**（既不是通过，也不是跳过）：

```bash
# 三种情形必须可区分
fields 空      => [X] 没有选出任何可验字段        => FAILS+1
全 ERR         => [X] 0 个字段验成 = 未验证        => FAILS+1
验了且越界      => [X] N/M 个字段点数比越界          => FAILS+1
验了且都在区间   =>     A6 通过：M 个取样字段...      => 0
```

### 为什么这条比前 7 条更隐蔽

前 7 条是**判据本身错了**（阈值、锚点、精度、视图语义）。
第 8 条是**判据对了，但没被执行**（或者执行了没成功），而汇总逻辑把「零次执行」当成「零次失败」。

```
「零失败」和「零检查」在计数器上完全相同。
这也是为什么纯计数式的验收（PASS 数 / FAIL 数）不够 ——
必须同时统计「检查了多少次」，并与预期次数比对。
```

### 通用形态

```
任何汇总逻辑都必须区分三种状态：
  通过（验了且对）/ 失败（验了且错）/ 未验证（没验成）
只统计前两者、把第三种归入「通过」的，都是这一类。
```

### 自查问题

- 这条判据**执行了吗**？执行**成功了吗**？我有没有把「没跑」和「跑对了」混为一谈？
- 我的汇总有没有统计「检查次数」？它等于预期次数吗？
- 如果全部跳过，脚本会输出「通过」还是「未验证」？

---

### 8.1 变体：**副作用没发生，测试当然绿**（同一母题的另一面）

第 8 条讲的是「判据没执行，却统计成通过」。
本条讲得更底层：**判据执行了，但它检查的对象根本没被改动。**

两者归到同一个母题：

```
「零次 X」和「X 成功」在观测上同形。
  第 8 条：零次检查 = 零次失败
  本条  ：零次改动 = 全绿（因为代码根本没变）
```

#### 现场（2026-11-07，同一天同一机制踩了三次）

```
变异/注入脚本用 JS 模板字面量嵌 python/heredoc
⇒ 脚本里的反斜杠 n 被 JS 转成**真实换行**
⇒ 目标脚本 SyntaxError
⇒ **注入从未发生**
⇒ 测试跑的是未变异的代码 ⇒ 当然全绿
```

三次分别是：变异验证 A/B、同一坑第二次、slot 守卫的变异验证。

**第三次尤其危险**：当时的结论是「守卫是摆设」——
如果据此把守卫拆掉，就是**因为工具坏了而删掉了一个好机制**。
⇒ **假绿和假红在这里会合流**：
```
假绿：改动没生效 + 测试绿  ⇒ 以为代码对
假红：改动没生效 + 测试红  ⇒ 以为代码错，去追不存在的 bug
```

#### 修法：把「确认改动」变成可执行的一步

```
# 注入/变异之后，先确认它真的在文件里
grep -c '<变异标记>' <目标文件>    # 必须 >= 1
```

**不要用「我看了一眼」** —— 「我看了一眼」和「我没看」在结果上也能同形。

更好的做法：把注入写成独立脚本文件（不要内联在命令里），
并在脚本里 `assert target in source`，断言失败就 `exit 1`。

#### 自查问题

- 我这次「改动」有没有一个**独立的、可执行的**确认步骤？还是只靠「我写了」？
- 我的变异/注入脚本内联在命令行里吗？内联就意味着转义层级不可见。
- 如果改动没生效，我的测试是会绿还是会红？（答「绿」就是本条）

---

#### 第四种形态：**连「脚本失败」都被静默了**（2026-11-07 晚，同一母题第 4 次）

```
补丁脚本内部 assert anchor in source 失败
⇒ 但脚本没带 2>&1，报错被吞掉
⇒ 文件根本未改动
⇒ vet 在未改动的文件上当然是绿的
```

**比前三次更隐蔽**：前三次至少命令行有 SyntaxError 冒出来；
这次连「脚本自己失败了」这件事都不可见 ⇒ 「改了东西 → 跑检查 → 绿」这条链上前两环都是黑的。

发现方式：**靠刚立的纪律**（落盘后 grep 断言）才抓到 ——
`grep -c allWarm → 0`，而预期是 3。

#### 由此补两条纪律

```
① 任何改写文件的命令必须带 2>&1
   否则「失败」与「没有输出 = 成功」在终端上同形

② 落盘后必须 grep 断言
   grep -c '<标记>' <目标文件>    # 必须 >= 1
```

**「靠纪律抓到自己的错误」比「刚好没错」有意义** ——
前者说明纪律在起作用，后者只说明运气好。

### 8.2 变体：**执了的检查，观察范围没覆盖改动范围**

第 8.1 条是「检查没执行」。本条是「检查执行了，但它看不见你改的东西」。

```
「build 绿」  ≠ 「test 绿」   （go build 不编译 _test.go）
「单包 PG 绿」≠ 「全量绿」    （全量默认 SQLite）
「单跑 -run」≠ 「全量绿」    （运行环境的方言不同）
```

**共同点：你用的那个检查，观察范围没有覆盖你改动的范围。**

#### 现场（2026-11-07，同一天两次）

```
① impl-l2 给 datalifecycle 加了 import telemetry（为用帧解码器）
   全量跑出：internal/telemetry [setup failed]
             imports ... from pg_partition_test.go
             import cycle not allowed in test
   **而 go build ./... 全绿 —— 因为 build 不编译测试文件**
   这是一个纯 test-only 的环

② impl-l2 的新用例用了 PG 专有 DISTINCT ON
   单跑 -run（PG 环境）绿，全量跑（SQLite）FAIL：43 包而非 44
   —— 没报错，只是少了一个 ok
```

#### 为什么危险

```
build 绿 ⇒ 你以为「仓库是好的」⇒ 继续下一步
但 test 已经在敲环，只是没人在那个时刻看
⇒ 下一个跑全量的人（可能是 CI、可能是别人）才撞上
⇒ 而那时你已经推进了很远，归因成本高
```

#### 修法：把 checklist 写成「观察范围 ≥ 改动范围」

```
改了什么          必须跑什么
----------------  ------------------------------------
函数签名/新增调用  go build ./...              （秒级，先跑）
任何 .go 文件      go vet ./...  +  全量 test    （build 不够）
新增 _test.go      全量 test（不是单包 -run）
涉及 SQL 方言      PG 模式 + SQLite 模式 各一遍
```

**关键：全量测试是唯一能看见「环」和「方言差异」的检查，**
**而它恰好是最慢的那个 ⇒ 最容易被跳过。**

#### 自查问题

- 我这个检查，编译/执行到我要改的那个文件了吗？
- 我改的文件里有没有 `_test.go`？有的话 build 一定看不见。
- 我跑的是单包还是全量？单包能不能看见跨包的环？

### 8.3 变体：**断言里的数字，来自一个恒为常数的字段**

8 / 8.1 / 8.2 三条的共同点是「该发生的事没发生，但结论是绿的」。
本条更隐蔽：**事情都发生了，但度量它的那个数根本没在度量。**

#### 现场（2026-11-07，impl-l1 的行数上限断言）

需求：断言「SQL 实际拉取的行数 <= 96」（防止有人把分页去掉变回全表扫）。

```
第一版：tx.RowsAffected 读数
  但 GORM 在 Raw().Scan() 路径上**不填 RowsAffected** ⇒ 每条记录都是 0
  ⇒ maxRows 返回 -1
  ⇒ 断言 -1 > 96 恒假
  ⇒ **用例永远绿，即使实现退化成全表拉取**
```

**断言写对了、被测代码也没改、用例也是绿的 —— 但那个数不来自任何真实观测。**

#### 与前面几条的关系

```
第 8 条  ：零次检查      ⇒ 记成零失败
第 8.1 条：零次改动      ⇒ 检查全绿
第 8.2 条：观察范围不够  ⇒ 检查看不见
本条     ：度量恒常数    ⇒ 断言在数一个假数字
```

**本条的特殊性：计数器不是「偏大」或「偏小」，而是「恒定」** ——
所以最容易被接受，因为「它有个值」看起来就像测过了。

#### 修法

```
① 换官方口径：GORM Logger.Trace(ctx, begin, fc, err) 的 fc() 第二返回值
   （不依赖回调时机，是最终行数）

② 加自检：**一条都没数出来就 Fail**
   测量不到 ≠ 没有违规 —— 这是反模式 8 的正向落地
```

#### 更一般的判据

```
任何「断言 X <= N」的用例，先问：如果 X 恒为 0 / 恒为 -1 / 恒为 nil，
这条用例会不会永远绿？
会 ⇒ 加一条下限断言（X > 0），让「没测到」变成红。
```

#### 自查问题

- 我断言的这个数字，来源路径有没有可能恒返回零值？
- 如果度量函数返回 -1 / 0 / nil，我的用例是绿还是红？
- 我有没有一条断言，专门证明「我确实测到了东西」？

### 8.4 变体：**扫到关键词，就推断因果**

8.1/8.2/8.3 都是「检查有缺陷」。本条是「检查根本不存在 —— 但结论已经下了」。

#### 现场（2026-11-08，一天内三次）

```
① impl-l2 看到 unitMapForDevice 里有个 if !has，以为那是回落控制流
   => 实际是「合并优先级」，第二层查询无条件执行 => 33 秒

② impl-l1 看到 categoryObserved 出现在「数据源健康」相关代码里
   => 推断「它影响健康判定，可能触发主备切换」=> 定性 P0
   => 实际只出现在**写路径的入参校验**（CreateGroup / UpdateGroup）
   => failover 的真实依据是 SourceGroupMember.LastSuccess（全链路 category 出现 0 次）

③ boot-api grep 到 tailSlack=5s 常量，推断「会误杀慢设备」
   => 实际下面 9 行有自适应逻辑 max(5s, 2*avgInterval)，锚点也不是 end
```

**共同形状：grep 给出的是「关键词出现过」，而结论需要的是「它在什么条件下被调用、影响了什么」。**

#### 为什么这类错误特别危险

```
它产出的结论**听起来很专业**（有文件名、有函数名、有后果推演）
=> 别人不会去查，因为「看起来已经查过了」
=> 而它可能是完全反的
```

本次实例：我用它定了一个 P0，并排进了第一批任务。

#### 判据：从「关键词」到「因果」要跨过三步

```
① 它在哪些地方被调用？（数调用点，不是 grep 出现次数）
② 那些调用点的执行路径是什么？（写路径 / 读路径 / 定时任务？）
③ 它的返回值影响了什么？（被 return 掉？被存库？被用于分支？）
```

**三步都走完才叫「读了代码」；只做第 0 步（grep）叫「知道它存在」。**

#### 自查问题

- 我这个结论是「它存在」还是「它如何生效」？
- 我数了调用点吗？还是只 grep 了名字？
- 如果要证伪我的结论，需要看哪段代码？我去看了吗？

## 9. 九条自查问题（贴在 PR 模板里用）

1. **反证过吗？** 我人为造一次违规，这条断言真的红了吗？
2. **判据能表达这件事吗？** 我查的这个视图/接口，能不能区分"不存在"与"看不见"？
3. **测试环境同形吗？** 测试 schema / 配置 / 精度，与生产是否一致？不一致的地方我有显式对齐吗？
4. **用例真的执行了吗？** 有没有可能被 Skip / build tag / env 缺省静默跳过？
5. **统计窗口够长吗？** 我判"从未使用"的窗口，覆盖了它的最低调用频率吗？
6. **非代码引用还指得准吗？** 文档里的**行号/路径/URL/截图编号**也是判据 ——
   它们会随代码演进而腐烂，**且腐烂时不会报错**（没有编译器、没有 CI 会告诉你"这个行号指向别的函数了"）。
7. **这条判据执行了吗？执行成功了吗？** 我有没有把「没跑」和「跑对了」混为一谈？
8. **我的汇总统计了「检查次数」吗？** 它等于预期次数吗？
9. **如果全部跳过，脚本会输出「通过」还是「未验证」？**

### 9.1 第 6 条的具体做法（可脚本化）

写文档时每引用一个代码位置，就用一次性脚本把它全部抽出来重放一遍。2026-11-07 实测：

```bash
# 抽出文档里所有 `backend/...go:NN` 形式的引用，逐条打印目标行
grep -oE '`backend/[a-zA-Z0-9_/]+\.[a-z]+:[0-9]+`' "$DOC" | tr -d '`' | while read ref; do
  f=${ref%:*}; l=${ref#*:}
  [ -f "$f" ] && echo "✅ $ref → $(sed -n "${l}p" "$f" | cut -c1-60)" || echo "❌ $ref"
done
```

这一步**当天就抓到一个真错**：文档里写的是 `backfill/partition_job.go:14`（简写），
而仓库里只有 `backend/internal/backfill/partition_job.go` —— 读者照简写路径找不到文件。
这种错误如果没人重放，会一直躺在文档里。

**同一个反模式的另一种形态**：路径/行号"看起来填了"，所以审阅时会跳过；
但"填了"和"指得准"是两件事 —— 和 §3 `pg_stat_all_indexes` 返回空一样，
**"有输出"不等于"输出表达了正确的信息"**。

## 11. 反模式 9：**「重跑变绿」被当成「那次红不存在」**（2026-11-08，impl-l1 自查）

### 现场

删除 `api/unifiedData.ts`（前端死封装）后，提交前最后一次全量跑：

```
Test Files  1 failed | 199 passed (200)
Tests       1 failed | 2505 passed | 1 skipped (2507)
```

当时的动作是：**先写提交信息**（「vitest run => 2506 passed」），**后做查证**。
写进提交信息的那个数字，来自**几十分钟前**那次通过，不是当次结果。

随后 4 次重跑全部 0 failed，于是判定「偶发，与我无关」——**这个判定可能对，但得出它的顺序是错的**：

```
错误顺序：跑绿一次 => 回填提交信息 => （如果想起来）再查那次红
正确顺序：那次红的用例名是什么？=> 与本改动有关吗？=> 才决定提交信息怎么写
```

那一轮的代价是「无法证明 flaky 与改动无关，只能证明 4 次不复现」。
真正的风险是：**如果那条红是本改动引入的低频确定性失败，回填的动作会把它永久埋进历史**。

### 与反模式 8 的关系：同一条母题的两个方向

```
反模式 8  ：观测缺失（没跑/没改/跳过）=> 统计成「通过」
反模式 9  ：观测转好（重跑绿了）    => 统计成「没红过」
```

看起来方向相反，实际是同一条：

> **「观测结果」不等于「事实」** —— 无论观测是缺失，还是转好。

一个容易被忽略的推论：**失败的可复现性本身不是判据**。
低频 flaky 与「本改动引入的偶发缺陷」在「重跑几次」这个观测下**完全同形** ——
重跑 N 次都无法区分它们。要区分，只能去抓失败当时的**具体用例名**。

### 为什么这类错误难自查

因为它**伪装成「严谨」**：注意到有红、重跑了、确认了不复现 —— 每一步看起来都对。
错的那一步藏在顺序里：**已经写好的结论没有随新观测更新**。

这和 §3「有输出 ≠ 输出表达了正确信息」是同族：
**有复查动作 ≠ 复查改变了结论**。

### 修法：提交信息里的每个数字必须能指回当次命令输出

```bash
# 提交前跑，把结果直接落成文件，提交信息只从这个文件抄
go test ./... 2>&1 | tee /tmp/test-final.log | tail -3
grep -c "^ok  " /tmp/test-final.log   # 这个数字才能写进提交信息
```

关键不是「跑一遍」，是**结果先落盘、提交信息从盘上抄** ——
这样「记忆」这个环节被物理移除，没有可出错的余地。

### 自查问题

- 我提交信息里的每个数字，能指回**当次**的一条命令输出吗？
- 如果最后一次跑是红的，我是**先查清用例名**，还是先把它归档成"偶发"？
- 我判定"偶发"的依据，是「重跑绿了」，还是「失败点与本改动无交集」？**这两者不是一回事。**

## 12. 提交前 checklist（贴在 PR 模板 / 每轮收工流程里）

### A. 数字来源

```
□ 最后一次全量跑的结果是什么？（不是「我记得上次是绿的」）
□ 结果落在文件里了吗？（tee 到日志，提交信息从日志抄，不从记忆抄）
□ 提交信息里的每个数字，都能指回一条命令输出吗？
□ 如果有红：先抓到用例名了吗？判"偶发"的依据是「重跑绿了」还是「无交集」？
```

### B. 改动有效性（反模式 8.1）

```
□ 注入/变异之后，先确认它真的在文件里了吗？
□ 每条断言都人为造过一次违规、确认它真的红了吗？
□ 有专门一条断言证明「我确实测到了东西」吗？（测量不到 = 失败）
```

### C. 观察范围

```
□ 观察范围 ≥ 改动范围了吗？（改了 A，验的是 A 还是 A 的邻居）
□ 条件用例真的执行了吗？（Skip / build tag / env 缺省 —— 反向确认一次）
□ 汇总里能把「0 次执行」和「0 次失败」分开了吗？
```

### D. 守卫的另一支（反模式 14）

```
□ 我写了一个守卫（if ... { continue / return / skip }）——
  另一支（条件不成立时走的那条路径）我验了吗？
  没有 => 这是「负向断言缺正向见证」，补一条正向用例。

□ 正向用例能归因吗？（枚举出目标对象，是不是也可能来自另一条路径？
  例：discoverDevices 有 4 条来源，只断言「找到了」无法归因到被试那一条）

□ 红的时候，人还需要做下一步动作吗？
  需要再跑一次 / 需要打开另一个文件 / 需要推断为什么错
  => fatalf 要么让人不用再动手，要么告诉人该动什么手
```

> **为什么单列 D 组**：A/B/C 三组都是「怎么确认验到了」，
> 而 D 组问的是「**没验的那一半在哪**」。
>
> 本轮实例（impl-l2，2026-11-08）：给 `discoverDevices` 加了
> `if !HasTable { continue }` 守卫，在 DROP 后的生产上验了「表不存在 => 跳过」，
> 但**没验**「表存在 => 仍然查」。而后者才是守卫会误伤的那一支：
> 若 `HasTable` 恒返回 false，前者照样绿，后者永远不执行 ——
> 症状是「迁移期回填静默少一批设备」。
>
> 这是「负向断言需要正向见证」在**守卫**这种结构上的具体形态。
> 而它容易被漏，因为写完守卫时注意力在「它挡住了什么」，
> 不在「它不该挡什么」。

### E. 改文档也要跑文档自检（反模式 15）

```
□ 我改了 docs/ 下的任何文件吗？
  改了 => 跑两个脚本，两个都跑：

    bash scripts/check_doc_structure.sh 'docs/验证/测试判据反模式-2026-11-07.md'
    ./scripts/check_doc_commands.sh
```

> **为什么单列 E 组**：前四组都在问「代码改动的验证够不够」，
> 而 E 组问的是「**文档改动的验证**」—— 它是一个被默认跳过的东西。
>
> 本轮实例（impl-l2，2026-11-08）：我在 `a6a061b8` 加了 §16「反模式 13」，
> 但**没加 §10 汇总表的第 13 行**，也没改 §10 标题的「本轮 12 个反模式」。
> 而 `check_doc_structure.sh` **正是为了抓这个错而存在的** —— 它抓到了，
> 只是**没人跑它**。
>
> 没跑的原因是 impl-l1 那句自陈：
>
>> 「我以为『他加的是文档，风险低』。」
>
> **而「文档改动风险低」这个假设是错的 —— 这个脚本的存在本身就说明它风险不低。**
>
> 这类「跳过检查」的共同形态是：**不是基于评估，是基于印象。**
>
> 判据：
>
> - **印象**：说不出「我评估了哪些风险、为什么认为它们都不存在」。
> - **评估**：能说出「这类改动历史上出过什么错」——
>   而本次的答案就摆在那份脚本的注释里（它就是为这个错而写的）。
>
> 所以 E 组的操作含义是：**凡是仓里有对应自检脚本的目录，改动后必须跑对应脚本，
> 而不是判断「这次改动风险低所以不跑」。**

## 13. 反模式 10：**否定断言可能是空跑**（2026-11-08，impl-l1 自查）

### 现场

为「DROP `unified_data` 后不会被重建」写了三条门禁：三条都断言「没有发生什么」，全绿。

**然后把 `database.AutoMigrate()` 改成开头 `return nil`（完全空跑）：三条门禁全部照旧 PASS。**

机制彻底不工作时，否定断言当然全部成立。

### 判据

**每条否定断言（「不许 X」「不会 Y」「没有 Z」）都必须配一条正向见证，证明被测机制确实执行了。**

范本：删掉 3 张见证表 + unified_data => 跑 AutoMigrate()。
正向：3 张见证表必须被建回来（证明它真的在执行）；负向：unified_data 必须不在（这才是要的）。
缺正向 ⇒ 负向可能是空跑的产物；缺负向 ⇒ 只证明了它能建表。

### 见证物的选择本身是判据的一部分

impl-l1 选了 `device_configs` / `alert_rules` / `vendors` —— **三个不同模块**的表。

```
只选一张        =>「AutoMigrate 只跑了某一段」这种失效骗得过断言
选同一模块三张   => 同上，覆盖面没有变宽
三个不同模块     => 空跑 / 半跑 / 只跑某段，都能被抓到
```

见证物要满足的是**独立性**，不只是「存在」：

```
见证物与被测机制弱相关  => 否则空跑也绿
见证物彼此弱相关        => 否则半跑也绿、巧合也绿
```

后一条最容易漏 —— 人们通常只想到第一条。

### 可操作判别句（impl-l1 提炼）

> 看到断言里只有「没有」/「不存在」/「不包含」时，问一句：**这个「没有」能由多少种错误原因产生？**
> 如果答案 > 1，就必须为每一种配一个见证物。

### 与反模式 8、9 的关系

同一个母题第 6 次出现（两天内）：

| # | 形态 | 断言的是 |
|---|---|---|
| 8 | 没验成被统计成验了且通过 | 「通过」的来源不可靠 |
| 8.1 | 副作用没发生，测试当然绿 | 「没变化」可以是没执行 |
| 8.3 | 断言里的数字来自恒为常数字段 | 「数字对了」但该字段永远对 |
| 9 | 重跑变绿被当成那次红不存在 | 「复查」没改变结论 |
| **10** | **否定断言可能是空跑** | **「没发生」≠「机制在跑但克制」** |

**共同形状：一个断言可以用无数种「错误原因」被满足，而断言本身不区分它们。**
这是「假绿」的最小生成式。

### 自查问题

- 我这条断言是**正向**（必须发生）还是**否定**（不许发生）？
- 如果是否定：我有什么证据表明被测机制**确实执行了**？
- 我的见证物选的是「容易通过的那个」还是「最能暴露失效的那个」？
- 把被测函数改成直接 `return nil`，我这条断言会红吗？（不会红 ⇒ 它是废命题）

## 14. 反模式 11：**满足了一个没人提出的需求**（2026-11-08，impl-l1 自查）

### 现场

为了让两份交织的改动能拆成两个提交，准备用 `git plumbing`（`hash-object` / `write-tree` / `commit-tree`）手工构造中间态，并已生成出正确的中间态文件、验证过可解析。

**而拆分的前提是「中间态必须可编译」。**

### 判据

```
「中间态可编译」是为了让 git bisect 能找到罪犯。
而这个仓库：主干直提、无 PR 审阅、无 bisect 工作流。
=> 为一个不存在的需求，付出了真实代价（plumbing / 挪文件 / 造中间态）。
```

**当一个约束让你开始写 plumbing、挪文件、造中间态时，先问「解除它会怎样」。**
如果答案是「没人会受影响」，它就不是约束，是自己发明的。

### 与前面几条的区别

反模式 1~10 都是「判据错了」。这一条是**判据对了，但它在回答一个没人问的问题**。
危害方式不同：不是给出错误结论，而是**消耗掉本可用在正确事情上的注意力**。

### 自查问题

- 这个约束是谁提出的？有具体的人/流程需要它吗？
- 解除它会导致什么？能说出一个**具体的**后果吗（不是「不严谨」这种抽象词）？
- 我为了满足它，正在做哪些「正常开发不会做」的动作？

## 15. 反模式 12：**把 cap 当 step（只看到一个约束源）**（2026-11-08，Lead 自查）

### 现场

判断「rollup 回填的帧解码窗口是 6h，余量只有 1.5 倍，接入 2 fps 设备就会静默截断」，
并据此定为 P0（比 preview 那条更严重）。

**而实际窗口是 1h，余量 9 倍。**

```go
// 外层（rollup_backfill.go:568-572）：STEP = batch = BatchSeconds（默认 3600 = 1h）
for t := dayStart; t.Before(dayEnd); t = t.Add(batch) {
    to := t.Add(batch)
    rows, err = r.aggregateBatchFromFrames(ctx, u.DeviceID, t, to)   // 传 [t, t+batch)
}

// 内层（rollup_backfill_frames.go:171-178）：CAP = framesBatchLimit
for t := from; t.Before(to); t = t.Add(framesBatchLimit) {
    segTo := t.Add(framesBatchLimit)
    if segTo.After(to) { segTo = to }        // ← 真正的上限是 to，不是固定 6h
    points, err := frameDecoder(ctx, r.db, deviceID, t.UTC(), segTo.UTC())
}
```

```
内层循环次数 = ceil(batch / framesBatchLimit)
=> 只有当 batch > 6h 时才会切出多段；默认 batch = 1h ⇒ 内层 1 次 ⇒ 窗口 1h
```

错误来源：**看到常量 `framesBatchLimit = 6h` 就认定「窗口 = 6h」**，
没有读完它在循环里的角色（既是步长，又被外层的 `to` 夹住）。

### 判据

```
凡是「一个常量参与决定某个量」的地方，必须问：这个量还有没有**别的**约束源？

  framesBatchLimit 决定「段宽」
  但段宽 = min(framesBatchLimit, 外层 batch)   ← 两个约束源，只看到一个

检测方法：找那个量被用到的每一处，看有没有 min/max/if 把它夹住。
```

### 为什么它比「看错一个常量」更根本

这是「**局部正确、整体错位**」的典型形态：

| # | 错误 | 局部正确的地方 | 整体错位的地方 |
|---|---|---|---|
| ① | 「A1 是 DROP 的唯一入口」 | 观察到的现象是真的 | 前提（表会被重建）没验，结论挂在空前提上 |
| ② | 「实现切 6h」 | 常量值 6h 是真的 | 把 cap 当成了 step，漏掉外层约束 |
| ③ | 「24h 页跨度会截断 2.6 倍」 | 24h×0.98fps=84,836 算得对 | 对象错：那个 24h 窗口不存在（跨度 ≠ 帧数） |

**共同点：每个错误里都有一个真实成立的局部事实。**
正因为局部是真的，结论看起来「有数据支撑」，最容易被人直接采信。

### 对决策者的补充判据

```
凡带以下特征的判断，无论谁说的，都必须先核事实再动手：
  · 含具体数字（21,600 帧 / 1.5 倍余量 / 6h）
  · 含「会 / 不会发生」的预测
  · 含「唯一 / 必然 / 只有」这类全称量词
  · 给出优先级（P0/P1）

理由：这四类判断的错法都一样 —— 局部正确、整体错位，
      而它们看起来都「有数据支撑」，所以最容易被直接采信。
```

### 一个不对称，比上面任何一条判据都重要

```
我要求所有人为每个结论配证据、配正向见证、配变异验证；
但我自己的技术判断，没有一条走过同样的流程。

2026-11-08 的记录：Lead 给出 3 个错判断，0 个由自查发现，3 个由执行侧核出。
```

**流程只约束被执行者时，前者的严谨会被后者的错判断抵消。**
所以本文档的自查清单对**提出结论的人**同样适用，不区分角色。

### 自查问题

- 这个量由哪些地方决定？我是否读完了**全部**约束源（含 min/max/if 夹取）？
- 我引用的常量，在循环/条件里的角色是 step 还是 cap？两者混淆会得到什么错误结论？
- 我这条结论里，有哪个数字是「真的但对象错了」的？
- 如果有人把这条判断当假设去核，他会先查什么？我查过那件事吗？

### 12.1 变体：**改了实现、没改解释**

同一个提交里把 `framesBatchLimit` 从 `6h` 改成 `time.Hour`，但同文件第 185 行还写着：

```go

```

常量那行改了、注释没改。**这比「整体没改」更容易骗人**，因为读者看到常量已经对了，
就会以为整处都对。

### 检测方法（工具层形态）

```bash
# ❌ 错：grep 常量名 —— 查不出「写了字面值的地方」

# ✅ 对：grep 旧值

判据（grep 常量名）的覆盖范围 < 声称范围（所有提到该值的地方）。

### 12.2 变体：**加了检测字段，但没给所有产生点赋值**

给 `DecodeStats` 加了 `FramesTruncated` 字段，在 `decode_anchored.go` 里赋了值，

// decode_anchored.go（已改）

```

### 自查问题（补充）

- 我加的这个字段，`grep 字段名` 出来的每一处赋值点，覆盖了所有产生该现象的地方吗？
- 有没有第二条代码路径能产生同样的现象，但它走的是另一个函数？
- 把检测条件改成 `> 0`，有没有哪条路径**永远不满足**？（那就是漏赋值）

## 16. 反模式 13：**用「例外」描述一条规则**（2026-11-08，impl-l2 自查）

### 现场

这一轮有两次，我（以及 Lead）都用「例外」这个词描述过一个规则：

```
① 文档命令不得引用 .tmp-* 路径
   「但 .tmp-telemetry/realdata/ 是例外 —— 它是仓外数据夹具」

② rollup_parity 的 skip
   「这是**唯一允许 skip 的场景**：被测对象永久不存在 + 已有明确替代」
```

两句话都读起来很清楚，但它们都**留了一个后门**。

### 「例外」和「两类」的差别

| 措辞 | 隐含意思 | 后果 |
|---|---|---|
| 「X 是例外」 | 原则上不该出现，这次放行 | 存在「放行」这个动作 => 坏的东西也能被放行 |
| 「X 是另一类」 | 各有各的要求，不存在放行 | 坏的东西**没有归属** => 无处可塞 |

具体到上面两例：

```
① 「realdata 是例外」
   => 下一个人遇到别的 .tmp-* 路径，会想「那这个能不能也算例外？」
   => 正确的说法：
      「可执行命令里的路径（clone 后必须存在）」
      「仓外数据夹具路径（本来就不该进仓，读者自行准备）」
      两类各有各的判定标准，而 fail 的那种「clone 后不存在且不是夹具」没有归属。

② 「这是唯一允许 skip 的场景」
   => 下一个人遇到别的想 skip 的情况，会想「这算不算那个场景？」
   => 正确的说法：
      「两类用例的合法终态不同：
        对象仍存在的  => 必须 PASS 或明确 FAIL
        对象已退役的  => SKIP，且消息里必须写明替代物」
      而「对象仍在但环境不满足」的那种，两类都不是 => 无处可塞。
```

### 为什么这是「反模式」而不是「措辞偏好」

因为**措辞决定了后来人的搜索空间**：

- 说「例外」=> 后来人找的是「这件事能不能也算例外」=> 他在找一个**判定边界**，
  而边界由谁定？由当时的说话人。他找不到 => 只能猜 => 或者直接加一个。
- 说「两类」=> 后来人找的是「这件事属于哪一类」=> 他在找一个**分类标准**，
  而标准写在规则里，不依赖说话人。

**「例外」把判断权留给未来的人，「两类」把判断权留在规则里。**

### 一个相关但不同的现象（不是例外，是反效果）

同一天还发生了一次「安全规则的实现错了」：

```
需求：引用块（>）内的代码块**不豁免**（读者可能照抄被引用的坏命令）
第一版实现：只判断「引用块不豁免」，但**没剥掉 > 前缀**

后果："> ```bash" 不以 fence 开头 => 整个引用块内的代码块**根本不会被识别**
      => 「不豁免」变成了「看不见」
      => 规则检查的引用块数量是 **0**
```

| 状态 | 你以为的 | 实际的 |
|---|---|---|
| 没有规则 | 没检查 | 没检查 |
| 规则实现错 | **检查了** | 检查了 **0 个对象** |

**规则实现错比没有规则更危险** —— 因为前者你知道要自己看，后者让你放心。

而它的发现方式只有一个：**变异验证**（塞一个违规进去，看它报不报）。
如果不做变异验证，这条规则会以「我实现了不豁免」的状态上线，而它实际检查的引用块数是 0。

### 判据

**描述一条规则时，不要说「X 是例外」，要说「存在哪几类，各有什么要求」。**

自查问法：

- 我把这句话写成「例外」了吗？如果改成「另一类」，规则要不要重写？
- 后来人遇到新的边界情况，他是要**猜我的意思**，还是要**查规则里的分类标准**？
- 这条规则的实现，我**塞过一个违规进去看它报不报**吗？

第三条尤其重要：前两条靠改措辞就能修，第三条不测就是 0。
