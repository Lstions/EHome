## 2. 为什么磁盘反而少了 2 GB（最重要的一节）

### 2.1 实测数据

```
device_data 物理大小   4,408 MB → 5,366 MB   （+958 MB）
  ├─ heap               —     → 3,934 MB
  └─ indexes            —     → 1,432 MB
device_data 逻辑数据       —     → 1,558 MB
⇒ 堆内空闲空间约 2,400 MB（可复用，但不还给操作系统）
```

### 2.2 机制

`UPDATE` 在 PostgreSQL 里 = 标记旧行死 + 插新行。剥离 346 万行的过程中，
表文件涨到能同时容纳新旧两份数据；`VACUUM`（剥离任务结束时自动跑的）把死元组清成 0（实测 `n_dead_tup = 0`），
但它的职责是「让空间可复用」，**不是「让文件变小」**。

⇒ **文件大小会停在 UPDATE 期间的峰值。**

### 2.3 准确表述

| 说法 | 对错 |
|---|---|
| 「剥离省了 4.9 GB 逻辑空间」 | ✅ 对（5,524 → 655 MB） |
| 「剥离让 device_data 从此不再增长」 | ✅ 对（新写入复用堆内 2.4 GB 空闲） |
| 「剥离让磁盘多了 4.9 GB」 | ❌ **错** |
| 「剥离让磁盘变少了」 | ✅ 对（-2 GB，因为峰值超过了原来的大小） |

### 2.4 要真正拿回磁盘：`VACUUM FULL`

```
可回收   约 2,400 MB（重写整表，把堆内空闲还给文件系统）
代价     ACCESS EXCLUSIVE 锁（写不进 device_data）+ 约等于表大小的临时空间
时长     估 2~4 分钟（5.4 GB 表）
影响     期间 device_data 写入失败；unified_data / telemetry_frame 不受影响
```

`pg_repack`（在线重打包，无排他锁）**不可用**（`pg_available_extensions` 查无此项）。

## 4. 本轮连带修掉的真 bug（都是静默错数，不报错）

| bug | 后果 | 谁发现 |
|---|---|---|
| `DecodeRange` 从窗口起点解码 | 窗口开头 ≤60 秒静默消失 | impl-l2 |
| `DecodeFrames` 有帧但全解不开时 `err==nil` | 读路径第二道回落永远不触发，空图且无日志 | impl-l2 |
| 批端点 `BatchHint` 挂错位置 | 全部用例绿、生产批请求从 0.61× 退化到 2.75× | impl-l2 |
| `+1ns` 游标依赖时间精度 | PG 上回填永不完成（frames_done 虚涨 1016 倍） | boot-api |
| `gow.sh` 不转发 `EHOME_*` | 全仓 28 个 PG 用例从未真跑（静默 Skip） | boot-api |
| `pg_stat_all_indexes` 看不到父索引 | 「索引删没删」的验收会假绿 | boot-api |
| 剥离完成判据 `n==0` 有歧义 | 一批坏行能让任务提前标 done，日志显示「完成」 | impl-l1 |

共性：**两条路径各自自洽，交叉点上从没有过用例**（详见 `测试判据反模式-2026-11-07.md`）。

## 6. VACUUM FULL 实测（执行于 2026-11-07 18:05）

| 分区 | 前 | 后 | 释放 | 耗时 |
|---|---:|---:|---:|---:|
| `device_data_202610` | 4,000 MB | **2,242 MB** | 1,758 MB | **26 秒** |
| `device_data_202611` | 1,366 MB | **771 MB** | 595 MB | **8 秒** |
| **合计** | 5,366 MB | **3,013 MB** | **2,353 MB** | **34 秒** |

**磁盘：14.1 GB → 16.36 GB**

### 6.1 风险实测低于预估一个量级

预估「ACCESS EXCLUSIVE 锁 2~4 分钟」，实测 **34 秒**。期间：

```
写入未中断：最近 3 分钟 device_data 630 行 / unified_data 3,691 行 / telemetry_frame 273 帧
错误日志：0 条
```

原因：表只有 5.4 GB 且在 page cache 里，重写很快。按「5.4 GB 顺序写盘」的保守估算高估了。
**下次可以直接做，不必等维护窗口。**

### 7.1 为什么中途会跌到 14.1 GB

UPDATE（剥离）产生的死元组在 `VACUUM` 之前一直占着页；plain VACUUM 只让空间可复用、
不缩文件。必须 `VACUUM FULL` 才把空间还给文件系统。

**这段是给运维看的：看到「剥离完成」后磁盘没变大，不是失败，是还差一步 VACUUM FULL。**
