## 1. 为什么需要这个任务

帧表已完整覆盖历史，但读路径分派是：

| 窗口 | 数据源 |
|---|---|
| ≤ 1h | 帧表解码（task-18，已验证） |
| 1h ~ 6h | unified_data SQL |
| > 6h | rollup（开关关闭）→ 回落 unified_data SQL |

**只要 >1h 的窗口还读 unified_data，老的 12 GB 分区就删不掉。**
本任务把 rollup 的历史补齐（回填前只有 1,526 行、2 MB），让长窗改读 rollup。

规模：36 天 × 1440 分钟 × 5 设备 ≈ 259,200 行 × ~2 KB ≈ **500 MB**，
相对 unified_data 的 15 GB 是 25 倍压缩。

## 2. 三个关键设计决策（含"为什么不是别的做法"）

### 2.1 覆盖率判据用**元数据表**，不是运行时推断

这是本任务最容易出事的地方。旧实现只要 `len(buckets) > 0` 就 handled=true；
回填进行到一半时，窗口里一半分钟有 rollup、一半没有 ⇒ 返回**半截数据** ⇒
用户看到图表中间凭空少一段。**这比空图更难发现：横轴还在，只是那几天的线没了。**

直觉做法是运行时算「应有桶数 vs 实际桶数」，**有两个致命缺陷**：

1. **设备天然有停机间隙。** 设备 10:00 上线、10:30 下线，真实分钟桶是 30 个，
   按窗口长度硬算 60 个 ⇒ 永远判「覆盖不足」⇒ 永远回落 ⇒ 回填白做。
   **它在正确的系统上判错，把好数据当坏数据。**
2. **算「应有桶数」必须知道源数据实际有哪些分钟，而那个源就是 unified_data
   —— 正是回填完成后要删掉的表。** 用即将被删除的表当运行时判据 = 自相矛盾：
   删完之后判据失效，而那恰恰是最需要它工作的时候。

⇒ **覆盖率是回填时写下的元数据**（telemetry_rollup_coverage），不是运行时推断。
回填本来就要逐天扫 unified_data，顺手数出「这台设备这一天实际有多少个分钟桶」。

**state 的取值（关键：用"行不存在"表达"没验证过"）**

| state | 含义 | 读路径 |
|---|---|---|
| complete | 已回填且源数据有内容（buckets ≥ 1） | 可用 |
| missing | 已回填且源数据**这一天本来就没有** | 可用（可信结论） |
| partial | 回填开始过但没跑完 | **必须回落** |
| （行不存在） | 从没验证过 | **必须回落** |

missing 与「行不存在」必须区分：设备 A 从 11-03 才上线 ⇒ 11-01 是 missing（可信）；
设备 B 的回填还没跑到 11-01 ⇒ 行不存在（未知）。混同 ⇒ 未回填窗口被当成
"本来就没数据" ⇒ **返回空图**。空图比回落更糟。

**day 存定长文本 YYYY-MM-DD 而不是 SQL date**：SQLite 没有真正的 date 类型，
AutoMigrate 会退化成 datetime/TEXT，而 PG 的 date 与字符串比较会走隐式转换 ⇒
同一份判据在两方言上可能判定不同。定长文本两方言逐位相同、可直接排序，
且判据逻辑能在 SQLite 上测（不需要 PG 才能验证）。

### 2.2 读路径口径必须是 **Last**，不是 Avg

rollup_read.go 旧实现返回 `stats[i].Avg`，而 unified_data 路径的 D1 口径是
**桶内最后值**：

```
rollup 旧：   Value: stats[i].Avg                       <- 均值（平滑线）
unified D1：  (array_agg(value ORDER BY ts DESC))[1]    <- 桶内最后值（阶梯线）
```

为什么 unified_data 不能用 avg：L1 收窄后它不再是完整 1 Hz 序列（恒定值段每 60s
只有一个心跳行），avg(value) 按**行数**平均 = 按变化频率加权，图表被系统性拉偏。
**这是 D1 改造的全部理由。**

**两种口径混用的后果不是"数值差一点"，是视觉语义的突变**：同一个图表，窗口从 5h
拉到 7h（跨过 6h 的 rollup 分界），线条会从阶梯线变成平滑线 —— 用户会以为数据变了。

修正：改用 Last，并用与 D1 **完全相同**的桶宽公式
W = ceil(windowSeconds/maxPoints) 把 1 分钟行重新分桶（绝对 epoch 对齐
floor(epoch/W)*W），每桶取「桶内最后一个分钟」的 Last。
⇒ 点时间戳与点数与 unified_data 路径逐点对齐，可直接对拍。

**Avg 不删除**（payload 里本来就有），将来要开均值视图再加**显式参数**
（如 agg=avg_true），不在本次偷偷换口径。

> Lead 裁决（2026-11-07）：长窗不该显示均值，至少现在不该。unified_data 的 avg
> 在 L1 之后本来就是错的，rollup 的 avg 是对的，两者混用会让「同一个 agg=avg
> 参数在不同窗口有不同含义」—— 最坏的一种 API 语义。

### 2.3 回填**不覆盖** live 已写的行（ON CONFLICT DO NOTHING）

live 的 RollupCollector 喂的是**全部解析帧**（L1 跳过入库的也喂，见
consumers_heavy.go 的 telemetryRollupSink 注释）；回填只能从 unified_data 聚合
（L1 收窄后的行）。所以同一分钟的同一字段：

| 统计量 | live vs 回填 | 结论 |
|---|---|---|
| Avg | **不同**（分母不同：live 全采样 vs 回填已落库行） | 覆盖会把 live 更准的 Avg 换成回填这份偏的 |
| Last | **一致**（L1 只跳过"值未变"的行 ⇒ 最后一个已落库值 == 最后一个真实采样值） | 这正是 D1 成立的前提 |

**「Last 一致、Avg 不一致」是整个回填正确性的基础。** 后人若想"都是聚合值，
为什么不能覆盖"，答案就在这里。

### 3.3 回填执行顺序（不可变）

```
1. 聚合这一天全部批次，**数出 buckets**（在写之前一次性数完）
2. 写 rollup 行（ON CONFLICT DO NOTHING）
3. 最后写覆盖元数据 complete / missing
```

- 第 1 步必须在写之前：若 buckets 是边写边数，它与真实写入量**天然相等**，
  中途断掉时缺的半天永远看不出来 ⇒ 判据失去鉴别力。
  **buckets 必须是独立于写入过程的观测值。**
- 第 3 步必须在写完之后：先写 complete 再写数据，崩在中间就是"宣称完整但其实没有"，
  那是本任务最坏的故障形态。反过来的窗口（数据齐但标 partial）只会多回落一次。

## 4. 验收证据

### 4.1 逐点对拍 1d/7d/30d（核心）

```
覆盖：31 天有元数据，其中 31 天 complete
1d：499 点，严格相等 250 (50%)，最大偏差 0.0052（上界 delta=0.0104）
7d：500 点，严格相等 251 (50%)，最大偏差 0.0052
30d：500 点，严格相等 300 (60%)，最大偏差 0.0052
--- PASS
```

**点数与时间戳逐点完全相同。** 严格相等的 50% 正好对应「桶边界未跨分钟」的那一半；
另一半的偏差 = 跨边界 1 分钟内的信号变化。

**残余偏差是 1 分钟预聚合的固有信息损失，不是缺陷**：rollup 粒度是 1 分钟，而
D1 的桶宽 W 一般不是 60 的整数倍（1d/500 → W=173s；7d → 1210s；30d → 5184s），
每个 W 桶的最后一个分钟可能跨过桶边界。想消除它就必须保留秒级数据，等于不压缩。

用例断言三条：点数/时间戳完全相同 + 每点偏差 ≤ delta + **至少 50% 点严格相等**。
第三条是专门抓 Avg 误用的守卫。

### 4.2 end=now 的截断 + 帧表尾巴

**这是"删 12 GB"的最后一道闸。** 前端 preset（1h/24h/7d）与后端 hours=N 的 End
**都是 time.Now()**。若按整窗回落处理，长窗 rollup 永远不生效 ⇒ 删掉
unified_data 之后 7d/30d 图表就是空页。

所以读路径截断 + 拼接：

```
rollup   服务 [Start, now-liveLag)   <- 主体
帧表解码  服务 [now-liveLag, now)     <- 尾巴
```

```
--- PASS: TestRollupLiveTailParity
    end=now 7d：500 点，最大偏差 0.1972（帧表量化上界 0.5）
```

设计要点：

1. **尾巴必须用帧表，不能用 unified_data** —— 那正是要删的表。
2. **尾巴聚合必须传原始 q 的 Start/End** —— aggregateFramePoints 用窗口算桶宽 W，
   传尾巴子窗口会得到更小的 W ⇒ 桶边界错开 ⇒ 拼接处出现假跳变。**最容易写错的一点。**
3. **同一时间戳尾巴优先** —— 跨 cutoff 的桶，rollup 只能给到"cutoff 前最后一个分钟"，
   帧表给的是该桶内真正的最后一个采样，后者才符合 D1。
4. **尾巴取不到 ⇒ 整窗回落**，绝不只返回主体（那会让图表右边凭空消失 = "数据停了"）。

### 4.3 覆盖率判据（变异验证）

去掉 `to.After(now-liveLag)` 判定后：

### 4.5 Avg → Last（变异验证）

把 Last 换回 Avg：


**注意偏差本身（0.0925）仍小于上界 delta（0.37），所以"偏差断言"抓不住它 ——
真正抓住它的是「至少 50% 点严格相等」那条。** 这是本次设计里最值得记的一点：
单靠"偏差在容差内"会漏掉口径错误。

### 4.6 回填正确性（PG 逐分钟对拍）


### 4.7 降级路径（生产真实形态）


## 5. 已知限制（如实记录）

### 5.1 帧表实际滞后是「128 帧批量」级，不是秒级 —— 尾巴当前基本补不到那 2 分钟

boot-api 2026-11-07 审计发现，我逐行复核确认：

```
dualwrite.go:201   const dualWriteBatchSize = 128
run() 的 select 只有 <-w.stop / <-w.queue 两个分支，满 128 才 flush
grep -cE "time\.(Ticker|NewTicker|After|NewTimer)" dualwrite.go -> 0
```

**落盘只有「攒满 128 帧」「进程退出」两个触发点，没有时间驱动的 flush。**

按生产历史帧速率折算：

```
3,454,432 帧 / 36 天 = 66.6 帧/分 ≈ 1.11 帧/秒
128 ÷ 1.11 ≈ 115 秒 ≈ 1.9 分钟
（全速双设备 99 帧/分 ≈ 77 秒；设备越慢越久，无上界）
```

而 liveLag = 120 秒，两者同量级 ⇒ 最近 120 秒的帧大概率还在内存 batch 里。

**影响**：end=now 的窗口右边缘会短约 2 分钟（有界、确定性、自愈）。
**不影响"删 12 GB"的目标能否成立** —— 只是体验与排障噪音。

**修法状态：已落地（2026-11-07，由 Lead 指派他人完成，非本任务写作用域）。**
`DualWriter` 已加定时 flush（`dualWriteFlushInterval`），帧滞后从「128 帧批量」
降到「秒级」。对方在同一处记录的生产实测：

```
修复前：telemetry_frame max(ts) = 34 秒前   unified_data max(ts) = 1 秒前
        帧速率 87.8 帧/分 ⇒ 填满 128 帧需 87 秒
```

⇒ **本任务的「帧表尾巴」前提现已成立**，尾巴能真正补到 ≈ now，
`end=now` 的窗口右边缘不再短 2 分钟。
本任务的 `liveLag = 120s` 保持不动：它同时要给 rollup 自身的 flush 滞后（60s ticker +
最多 60s 的分钟完成等待）留余量，不是只为帧表设的。

### 5.2 1 分钟粒度的固有误差

见 §4.1。要点是**它可量化、有上界、且无法在不放弃压缩的前提下消除**。

### 5.3 帧表尾巴的量化容差

尾巴走帧表解码，值是量化的（rsoc 的 spec Step=1 ⇒ 误差 ≤ 0.5）；
主体走 rollup（无量化）。所以拼接结果的误差上界是尾巴那段的 Step/2。
这个容差**只覆盖量化，不覆盖口径错误**：若拼接把主体和尾巴的桶边界对错了，
偏差会是"整条曲线的量级"（第一版实测 4135），远超量化上界。

### 5.4 测试构造踩过的值域坑

对拍数据要同时被帧表编码，而 rsoc 的 spec 是 Min=0/Step=1/**Bits=7** ⇒ 只能表示
**0..127**。第一版把每分钟斜率取 0.37，8 天后值到 4262 ⇒ 量化 code 溢出 ⇒
帧表解码出完全不同的数（对拍偏差 4135，**而时间戳全对得上**）——
典型的"值错了但形状对"，最难查的一类。改取 0.0104 后落在可表示区间内。

> 与 task-18 的 snapOnGrid 是同一族问题：**测试数据必须落在 spec 的量化网格/值域内**。

### 5.5 EHOME_TELEMETRY_ROLLUP_READ 默认值建议

**保持 false，等生产回填跑完 + 生产实测通过后再翻 true。**

翻 true 的前置条件（按序）：

1. 生产回填跑完，GET /api/v1/system/rollup-backfill 显示 units_done == units_total；
2. SELECT count(*) FROM telemetry_rollup_coverage WHERE state NOT IN (complete, missing) = 0；
3. 挑 1d/7d/30d 各一个窗口做 rollup vs unified_data 逐点对拍，偏差在界内；
4. 观察 24h：确认无 [rollup-read] window not fully backfilled 刷屏（那是回填有洞的信号）。

| EHOME_TELEMETRY_ROLLUP_BACKFILL_BATCH_SECONDS | 3600 | 单次聚合跨度（**自动向上取整到 60 的倍数**） |
| EHOME_TELEMETRY_ROLLUP_BACKFILL_SLEEP_MS | 50 | 批次间休眠（限速，避免与其它重 IO 任务抢） |

**BATCH_SECONDS 必须是 60 的整数倍**：backfillUnit 用覆盖赋值写桶，批次若不落在
分钟边界上，同一个分钟桶会被两个批次各聚合一部分、后者覆盖前者 ⇒ Avg/Count 只是
"半个桶"的值（实测 batch=90s 时 cnt=3 而真值 6）。
normalizeRollupBatchSeconds 会强制向上取整，不会再静默出错。

| # | 检查 | 判据 |

## 9. 协作记录（值得留档的两条过程教训）

### 9.1 我和 boot-api 的写盘撞车造成了假红

我跑全量 go test 时拿到 `zz_bootapi_probe5_test.go:56:4: expected }, found EOF`。
30 秒后重跑 vet 是 EXIT=0。**根因不是他的语法错，是他用"先写一半再 append"的方式
建测试文件，我正好读到中间状态。** Go 的测试是整包编译，一个文件不完整 ⇒ 整包
setup failed ⇒ 拿到假红。

教训：**Go 源文件必须一次性 write 完整内容，不要写一半再补丁**；探针/脚手架不要建
在包目录里（应放 /tmp 或 .tmp-*），否则会污染别人的构建与 CI。

### 9.2 「偏差在容差内」不足以保证口径正确

Avg vs Last 的变异实测偏差只有 0.0925，**小于**上界 delta=0.37 ——
如果只断言"偏差 ≤ 容差"，这个 bug 会**完全漏过**。
真正抓住它的是「至少 50% 的点严格相等」这条结构性断言。

**结论：口径类 bug 要用"结构断言"抓（点数/时间戳/严格相等比例），
不能用"数值容差"抓。** 这个经验对后续任何"换数据源"的改造都适用。
