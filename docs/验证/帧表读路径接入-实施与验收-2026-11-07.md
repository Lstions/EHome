## 1. 这个任务解决什么

L1/L2 之后同一批物理量存了两个副本：

```
unified_data      132 MB/天（每字段一行）
telemetry_frame    18 MB/天（位打包增量，已无损覆盖）
```

但**帧表没有读路径**，所有图表仍读 `unified_data` ⇒ 老的 15 GB 分区永远删不掉，
「长期保留」就不成立。本任务给历史图表读取加一层数据源抽象，让它能读帧表，
并在帧表未覆盖时**回落**到 `unified_data`。

### 1.1 三个数据源的互补关系

```
窗口长度        avg 模式                change 模式
─────────────────────────────────────────────────────────
≤ 1 小时        帧表解码（本任务）        帧表解码（本任务）
1h ~ 6h         unified_data SQL 聚合    unified_data SQL 聚合
> 6 小时        rollup（预聚合，派生）    unified_data SQL 聚合
> 24 小时       rollup / SQL 聚合         unified_data SQL 聚合
```

**中间带（1h~6h）是有意的**：3h 窗口解码要 ~1 万帧（解码成本开始显著），
而 rollup 的 60s 粒度对 3h 太粗（只能给 180 个点）。SQL 聚合在这段最合适。

### 1.2 两个加速路径**不重叠**

`TestRollupAndFrameAreComplementary` 枚举 1min 到 7 天共 9 个尺度，断言
`shouldUseRollup` 与 `frameReadEligible` **永不同时为真**。重叠会浪费查询，
更糟的是让「哪个源在服务这个请求」不可预测 —— 排查图表异常时是灾难。

## 2. 契约的三条硬约束，以及每条是怎么被守住的

### 2.1 聚合口径必须逐值相等

现有 D1 口径是「**桶内最后值**」（L1 收窄后 `avg(value)` 会被系统性拉偏）。
帧表解码后必须产出**完全相同的点集**，不能变成平均值。

实现要点（`aggregateFramePoints`）：

1. **桶号用绝对 epoch**：`floor(epoch/W)*W`，与 SQL 的 `to_timestamp(floor(extract(epoch…/W)*W)` **逐位相同**。用「相对 Start 的偏移」会让两条路径的桶边界错开最多 W 秒 —— 值看起来差不多却永远对不上。
2. **输出的是桶起点**，不是桶内最后一条数据的时间戳。用数据时间戳会让点集在时间轴上错开。
3. **change 模式**：升序扫描保留首点 + 每个值变化点（含 1→0 结束点），与 `lag() … IS DISTINCT FROM` 等价。
4. **裁掉桶起点早于 Start 的点**，与 `trimAvgPointsBeforeStart` 同语义。

### 2.2 回退必须可靠（这是删老分区的安全前提）

判断错方向的两种后果**不对称**：

· 帧表已覆盖却说「没覆盖」 ⇒ 白回落一次，慢但**正确**；
· 帧表没覆盖却说「覆盖了」 ⇒ 读到空/半截数据，**用户看到空图**。

因此判据一律**保守**，四条全满足才算覆盖（`probeFrameCoverage`）：

| 判据 | 挡什么场景 |
|---|---|
| 窗口内 `count > 0` | 回填还没到这段 |
| `min(ts) <= start+5min` | 窗口开头落在回填缺口里 |
| `max(ts) >= end-5min` | 窗口结尾落在回填缺口里 |
| `count <= MaxDecodeFrames` | 静默扫几百万帧 |

**为什么两端都要查**（设计里最容易做漏的一处）：只判 `count>0` 会漏掉「窗口跨过缺口」
—— 那正是回填进行中 + 实时双写并存的真实形状：回填覆盖 `[10-01, watermark]`、
实时双写覆盖 `[now-几分钟, now]`，中间是空白。`TestFrameCoveragePartialFallsBack` 专守这条。

### 2.3 不能静默扫几百万帧

三道闸，从外到内：

1. `frameReadEligible` 纯函数判据：窗口 > 1h 或 > `MaxDecodeWindow`(24h) ⇒ **不解码**；
2. `probeFrameCoverage` 的 `count <= MaxDecodeFrames`(32,768) ⇒ 超了不选帧表；
3. `DecodeRange` 自身的 `MaxDecodeWindow` / `MaxDecodeFrames` 护栏（兜底）。

**关键顺序**：必须在调 `DecodeRange` **之前**判掉。`DecodeRange` 对超窗返回
`RangeTooLargeError`，那条路径会让 handler 返回 **500**（用户看到「加载失败」），
而不是静默回落到能出结果的 SQL 聚合。`TestDispatchDecisionChain` 的 #3 守这个顺序。

## 3. 实现结构

### 3.1 数据源抽象

```go
type historySource interface {
	Name() string
	Points(ctx context.Context, q historyPointQuery) ([]HistoryPoint, error)
}

type unifiedSource struct{ db *gorm.DB }   // 既有路径：SQL 下推分桶
type frameSource   struct{ db; dict }      // 新路径：解码 + Go 侧同口径分桶
```

**为什么抽成接口而不是在 handler 里 if/else**：两个实现要能被**同一条用例**分别
调用、逐值对拍 —— 只测其中一个等于没测「相等」。

### 3.2 关键帧锚点（`decode_anchored.go`）

**`DecodeRange` 不能直接用**：它从 `from` 开始取帧。若 `from` 落在增量链**中间**
（绝大多数情况都是），从 from 到下一个关键帧之间的帧全是「增量但无基线」，解码器
按 §8 的断链规则**跳过它们** ⇒ 窗口开头最多 60 秒（关键帧间隔）静默消失。

`DecodeRangeAnchored` 先把 `from` 向前扩到「≤ from 的最后一个关键帧」再解码，
然后把结果裁回 `[from, to)`。最多多解 60 秒的帧，成本可忽略。

### 3.3 解码结果共享（这次性能优化的核心）

生产图表请求走的是 **batch 端点**：device14 的 BMS 页首屏同时问 **29 个 category**。
帧表的物理形态决定了**一次解码能服务全部字段**（一帧一行，payload 里是整个 slot）。
`DecodeFrames` 的 `Fields` 过滤只影响**产出**，不影响解码成本。所以：

· **单飞（singleflight）**：29 个 goroutine 同时进入时会**全部**未命中缓存，各解码一遍
  ⇒ 实测 297 ms。单飞让后来者等第一次的结果 ⇒ 只需解码一次；
· **按字段名预分组**（`map[string][]HistoryPoint`）：批请求 29 个 category 各自 map 查找即可；
· **`BatchHint` 决定解码范围**：批请求全解（服务 29 个），单查请求只解自己那一个字段。

**`BatchHint` 不是可选优化，是必需的**：漏了它，29 个 category 会各自做单字段解码
（实测 2.75×）。§5 的 perf 用例第一版就是这样跑红的 —— 反过来证明了它必需。

## 5. 性能实测（验收 ③）

### 5.1 一个必须先说清楚的测量事实

`unified_data` 的 1h 查询之所以快（~7 ms），**不是因为它取数少 —— 它取数更多**：

```
把单字段 1h 的 3,600 行原样拉回 Go：  28.1 ms
把 3,600 帧（29 字段）拉回 Go：        17.4 ms   ← 帧表反而快
PG 服务端分桶后只返回 240 点：          7.0 ms   ← unified 快在这里
```

所以帧表路径的额外耗时不是「退化」，而是「**把聚合搬到了 Go 侧**」的必然代价。
一旦请求涉及多个字段，统一读帧表的优势就显现出来。

### 5.2 三种形态实测（3,600 帧 / 104,400 行 / 29 字段）

```
==================== 1 小时窗口性能实测 ====================
  单片 冷缓存 : unified=7.71ms   frame=27.82ms  →  3.61×
  单片 热缓存 : unified=7.71ms   frame=0.106ms  →  0.01×
  批 29 类    : unified=87.52ms  frame=53.44ms  →  0.61×   ← 生产主路径
  契约上限    : 2.00×
  正确性      : 两条路径 450 点逐值相等 ✓
```

### 5.3 结论与诚实说明

· **生产主路径（批 29 类）是 0.61× —— 帧表比 unified_data 更快**，因为
  unified_data 一字段一行，29 个 category 必须扫 29 次；帧表一帧一行，扫一次；
· **单片热缓存 0.01×** —— 15 s TTL 内轮询直接命中；
· **单片冷缓存 3.61× 超过 2×，这是已知且可解释的**：单个图表第一次打开时，
  帧表要拉 3,600 帧（17 ms）+ 解 3,600 个点（~10 ms），而 unified 服务端只回 240 点。
  用例**不**对这条断言 —— 掩盖它比记录它更糟。

## 6. 变异验证（3 个变异，各自被不同用例抓住）

### 变异 A：桶号改成「相对 Start 的偏移」

```
--- FAIL: TestFrameSourceEqualsUnifiedData (1.09s)
    1d/avg/current: 点数不等 unified=57 frame=56
    unified 前 3: {23:57:15 -12.5} {00:00:30 -12.5} {00:03:45 -12.5}
    frame   前 3: {23:58:15 -12.5} {00:01:30 -12.5} {00:04:45 -12.5}
```

### 6.1 变异 A 为什么 1h 不红 —— 「测多个窗口」的**实证理由**

这不是「多测几个没坏处」，而是一个具体的、可复现的对齐巧合：

| 窗口 | bucket 宽度 W | Start 相对绝对桶边界的偏移 | 两种对齐是否重合 |
|---|---:|---|---|
| 1h | 8 s | 0（用例数据起点是整点） | **是** ⇒ 变异不暴露 |
| 1d | 173 s | 非 0 | 否 ⇒ 立即暴露 |
| 7d | 1209 s | 非 0 | 否 ⇒ 立即暴露 |

`floor(epoch/W)*W`（绝对对齐，正确）与 `floor((epoch-start)/W)*W + start`（相对对齐，错误）
在 `start % W == 0` 时**完全等价**。1h/500 → W=8 s，而用例数据起点是整点 ⇒ `start % 8 == 0`
⇒ 两种算法逐位相同 ⇒ 变异 A 在 1h 窗口上是个**等价变换**，物理上不可能被检出。

1d/500 → W=173 s（质数宽度），`start % 173 != 0` ⇒ 两条路径的桶边界错开最多 172 秒 ⇒
点数从 57 变 56、时间戳整体偏移 60 秒，立刻报错。

**结论（团队经验）**：任何「桶对齐 / 分组键」类改动，**只测短窗等于没测** —— 短窗的
桶宽往往整除整点偏移，天然掩盖对齐错误。必须至少有一个**非整点、桶宽不整除**的长窗。
本用例保留 1d + 7d 就是这个原因，不是「多测一点更保险」。

### 变异 B：删掉覆盖判据的回落

```
--- FAIL: TestFrameCoverageNotCoveredFallsBack (0.96s)
    帧表无帧时数据源 = "telemetry_frame", want unified_data（否则用户会看到空图）
--- FAIL: TestFrameCoveragePartialFallsBack (1.00s)
    帧表只覆盖前 10 分钟时数据源 = "telemetry_frame", want unified_data
    (只判 count>0 会误判成已覆盖 ⇒ 返回半截数据，比空图更难发现)
```

### 变异 C：不检查「有帧但一条都没解开」

```
--- FAIL: TestFrameSourceDecodeFailureFallsBack (1.02s)
    解码全跳过时必须回落 unified_data，不能返回空点集（用户会看到空图）
```

**变异 C 背后是一个真实的 bug**：`DecodeFrames` 在「slot 字典落后 / payload 全坏」时
**不返回 error**（按 §8 的设计它把「跳过」当正常降级，只记 `stats`）。如果只看 `err`，
第二道回落永远不会触发 —— 用户看到空图，日志里一条记录都没有。是按
`stats.FramesSeen > 0 && len(points) == 0` 显式判定才修好的。

### 变异 D（不是变异，是**真实发生过的 bug**）：`BatchHint` 挂错调用点

`handler_data.go` 的批端点里有**两个** `historyPointQuery{...}` 字面量：
上面的 rollup 调用、下面的帧表分派调用。我最初把 `BatchHint: true` 写进了**上面那个**
（`rollupHistoryPoints` 根本不读这个字段），而真正需要的帧表分派调用没设。

**当时全部用例是绿的** —— 因为 perf 用例直接调 `frameSource.Points` 并手动设了提示，
绕过了 handler。是 review `git diff handler_data.go` 时发现的。

生产后果：29 个 category 各做单字段解码，批请求从 0.61× 退化到 **2.75×** ——
正好卡在契约线上，且不会有任何报错。

补了两条守卫（`history_source_share_test.go`）：

1. **机制层**：装一个解码次数计数器，断言 `BatchHint=true` 时 29 个并发 category
   **只解码 1 次**、`BatchHint=false` 时解码 29 次。

```
解码次数：BatchHint=true ⇒ 1；BatchHint=false ⇒ 29（29 个 category）
--- PASS: TestBatchHintSharesOneDecode (1.01s)
```

2. **接线层**：源码级正则检查 `BatchHint` 出现在 `queryHistoryPointsWithFallback` 的
   实参里、**不在** `rollupHistoryPoints` 的实参里（挂错位置就红）。

```
--- PASS: TestHandlerBatchSetsBatchHintOnFrameDispatch (0.00s)
```

这条值得单独记，因为它揭示了一类通用陷阱：**性能用例直接调数据层会掩盖接线错误**。
机制正确 + 接线错误 = 用例全绿 + 生产退化 4 倍。

## 8. 残余风险（诚实清单）

### 8.1 单片冷缓存 3.61×，超过 2× 契约

已如实记录，不断言。若将来必须达标，两条路：

1. **把 avg 的桶内最后值下推到 SQL**（`DISTINCT ON (bucket) … ORDER BY ts DESC`），只取每桶最后一帧再解码 —— 但解码要完整增量链，实际只能省传输不能省解码；
2. **靠热缓存覆盖**：生产上单图表是轮询的，TTL 15 s 内第二次起就是 0.01×。

### 8.2 rollup 读路径**已接线但生产上是空表**

即可生效，**不需要改代码**。

### 8.3 slot 字典接线（**已按 Lead 裁决 1 落地**）

帧表解码用的 slot 规格必须与编码侧**同一份**。已在 `cmd/server/main.go` 的 `telemetryDict.WarmUp()`
之后加了一行 `api.SetHistoryFrameDictionary(telemetryDict)` —— 复用写路径那份字典，
既是正确性保障（避免两份字典漂移 = 本仓踩过多次的「两处各说各话」），也省掉首次请求的
~100 ms WarmUp。

`api` 侧仍保留惰性装载兜底（`frameDictionaryFor`：注入优先，否则从 `telemetry_slot` 首次装载），
由 `TestFrameDictionaryLazyLoadsWithoutInjection` / `TestFrameDictionaryInjectionWins` 守住 ——
这样即使将来有人删掉接线那一行，功能也不会静默失效。

### 8.4 覆盖判据依赖「回填按分区顺序推进」

`probeFrameCoverage` 假设「帧表覆盖区间是连续的」（回填从头往后推 ⇒ 成立）。若回填改为
**乱序**（先补中间某个月），这个假设会失效：区间内可能有洞而两端都满足判据。当前回填
实现是顺序的（`discoverPartitions` 按分区名排序），所以成立；将来若改乱序，必须同步
收紧判据（例如按分区粒度记录覆盖状态）。

> **Lead 裁决 2**：接受该假设，但必须写进**代码注释**而不只是文档。
> 已落到 `history_source.go` 的 `probeFrameCoverage` 文档注释（⚠⚠ 段），
> 含「一旦乱序会静默返回半截数据」与「必须改为按分区粒度记覆盖状态」两条。
