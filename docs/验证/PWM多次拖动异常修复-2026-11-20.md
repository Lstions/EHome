# PWM 多次拖动后无法应用：根因与修复（2026-11-20）

## 现象

在节点页 `外设 → PWM` 连续拖动占空比滑块，前几次正常；多次后行内出现“设备操作失败 · 重试”，占空比不再变化，后续拖动也无法应用。

## 复现证据

- 第 1 次拖动：`duty=1464`，设备 `PeriphRsp success=1`。
- 0.7 秒后设备收到 **完整 ConfigManifest** 并执行配置事务。
- 紧接着第 2 次拖动：`PeriphCmd action=0 value=2160` → `PeriphRsp success=0 err=5`。
- 日志序列（设备）：

```text
07:35:06.186 PeriphRsp: req=... success=1, value=1464, type=2, action=0
07:35:06.940 ConfigManifest 下行 ⇒ 进入应用路径
07:35:07.945 Config transaction committed
07:35:08.444 PeriphCmd: req=... type=2, action=0, value=2160
07:35:08.444 PeriphRsp: req=... success=0, value=0, err=5
```

## 根因

后端 `POST /nodes/:id/pwm/:hardware_id/duty` 在发送运行时命令前，先执行了：

```go
db.Model(&cfg).Update("duty", *req.Duty)
```

PWM 的 `duty` / `frequency` 同时是 `PWMConfig` 的配置字段，参与 ConfigManifest 的哈希与编码。于是每次拖动都会：

1. 改变数据库中的 PWM 配置；
2. 配置哈希失配，后端下发整份 ConfigManifest；
3. 固件配置事务重新初始化外设，PWM 因 `auto_start=false` 被停止；
4. 下一次 SET_DUTY 落在“已停止/未重新配置”的 PWM 上，返回 `error_code=5`。

这不是 UI 滑块本身的问题，而是“**运行时控制写入了持久配置**”。

## 修复

- `duty`：只下发 `PeriphCmd(SET_DUTY)`，不再更新 `pwm_configs.duty`。
- `frequency`：同样只下发 `SET_FREQ`，不再更新 `pwm_configs.frequency`。
- 持久化的 `duty/frequency` 只由“配置/编辑 PWM”入口修改；运行时值由 `GET /pwm/:hardware_id/state` 读取并回填。
- 新增回归测试 `TestPWM_SetDuty_DoesNotMutateConfig`：调用运行时 duty 接口后断言数据库 duty 不变。

## 复验

修复后真实浏览器连续拖动 **12 次**：

- 12 次 `POST /pwm/PWM0/duty` 全部 200；
- 设备 12 次 `PeriphRsp success=1`；
- 占空比从 14.64% 连续变化到 75.00%；
- 期间 **没有任何新的 ConfigManifest**；
- 数据库 `pwm_configs.duty` 保持 1464，未被运行时拖动污染；
- UI 不再出现“设备操作失败 · 重试”。

另验证运行态频率：设置 1200Hz 后设备 `success=1`，数据库 frequency 仍为 1000；再设回 1000Hz 设备成功。
