# 实机压测发现：100 Hz 受两个结构性上限约束（2026-10-05/06）

**来源**：loadtest（task-3）在 S3 台架（`30EDA0A9A808`，s3p-n16）上的第 2 步实测。
**证据**：`docs/验证/证据/2026-10-05-实机压测/step2-ch8-115200-100hz-report.json`

---

## 1. 实测结果：目标 100 Hz，实际 26.1 Hz

台架条件：只把 ch8 的 `baud 9600→115200`、`interval_ms 5000→10`（最小改动），
从机（CP2102 侧）同步切 115200，跑 120 s。

| 指标 | 实测 | 目标 | 判定 |
|---|---:|---:|---|
| ch8 观测速率 | **26.13 Hz** | 100 Hz | ❌ 差 3.8× |
| ch8 报告数 | 3,139 | 12,000 | — |
| ch8 `missing_reports` | **1,762** | 0 | ❌ |
| ch8 `seq_gaps` | **84** | 0 | ❌ |
| `report_drop` | 0 | 0 | ✅ |
| PANIC/WDT | 0 | 0 | ✅ |
| MQTT 掉线 | 0 | 0 | ✅ |
| scheduler | `samples=422 full=582 min_free=2` | — | ⚠️ 队列打满 |

**这不是固件 bug，而是两个结构性上限叠加的结果。**

---

## 2. 上限一：UART 帧完成判据的 10 ms 固定空闲

> ⚠️ **本节的路径归属已更正（2026-10-06 01:4x，由 uart-throughput 指出、Lead 复核）**：
> step2 的 ch8 实测走的是 **legacy CMD_SAMPLE 路径**，**不是** `uart_collect_response`。
> 证据：step2 console 里 `V2 execute` 出现 **0 次**、`V2 command` **0 次**，
> 而 `CMD_U0` 出现 **4957 次**；且 `V2 execute` 在源码里是 `ESP_LOGI`（info 级，可见）。
> ⇒ **下面这段代码不是 step2 26.1Hz 的直接原因**。
> 10 ms 静默判据在**两条路径上都存在**（legacy 在 `complete_idle_response`/`emit_ready_stream_chunks`，
> batch 在 `uart_collect_response`），所以结论方向仍成立，但"哪条路径限制了什么"必须以实测为准。
> 详见 §2.1。

`components/bus_worker/bus_worker.c:1181-1186`（`uart_collect_response`）：

```c
if (len > 0 && state->last_rx_us > 0 &&
    esp_timer_get_time() - state->last_rx_us >= 10000) {   /* 10 ms 固定 */
    memcpy(out, state->data, len);
    *out_len = len;
    return expected == 0 || len >= expected;
}
```

判据是"**收到最后一字节后必须静默 10 ms** 才算一帧结束"（Modbus RTU 风格）。
无论波特率多高，每个事务都要额外付出 **10 ms 尾部等待**：

```
单事务最短耗时 = 传输时间 + 10 ms 静默
115200 baud、67 B 传输 ≈ 5.8 ms
⇒ 单事务 ≈ 15.8 ms ⇒ 上限 ≈ 63 Hz
```

**结论**：即使 115200 baud，**理论上限也只有约 63 Hz**，到不了 100 Hz。
实测 26 Hz 比这个理论上限还低，说明还有第二个上限。

### 2.1 路径归属与单事务耗时的反推（更正后）

```
step2: CMD_U0 txn ≈ 410 / 10 s = 41 事务/s
⇒ 单事务 ≈ 24.4 ms（不是 15.8 ms）

而"传输 67B@115200 ≈ 5.8 ms + 10 ms 静默 ≈ 15.8 ms"只解释 16 ms
⇒ **还有约 8 ms 未被解释**（疑为 scheduler 1 ms tick 的调度粒度、
   或多步 plan 的逐步开销、或队列满时的重试）
```

**这直接影响修复的收益预期**：若 legacy 路径的主要瓶颈不是那 10 ms 静默，
则只改静默判据**不会**把 Hz 提到 100。需先定位那 8 ms 花在哪（见 task-5 的要求）。

## 3. 上限二：scheduler 队列被打满（`full=582, min_free=2`）

`scheduler.c:840-847` 每轮记录最忙队列的剩余空间；
`full=582`（10 s 窗口内队列满 582 次）、`min_free=2`（最少只剩 2 个空位）
说明**命令入队侧已成为瓶颈**：调度器按 1 ms tick 轮询，但队列在 10 ms 事务期间持续被填。

配合 `missing_reports=1762` 与 `seq_gaps=84`，可以判断：
**在 10 ms 静默窗口内到达的后续命令被丢弃/覆盖**，而不是"发得慢"。

## 4. 这对"满配 5 路 × 100 Hz"意味着什么

用户需求是"满配每条总线 100 Hz 收发，要有余量"。
实测表明：**当前实现结构上达不到 100 Hz/路**，与内存无关，与 PSRAM 无关。

要达到 100 Hz，需要动的是：

1. **帧完成判据改为基于 read_size / 协议长度**，而不是固定 10 ms 静默。
   现有代码其实已经支持 `expected`（`return expected == 0 || len >= expected`），
   但**前提是必须先满足 10 ms 静默**才检查 `expected` —— 顺序反了。
   把 `len >= expected` 提到静默判据之前，即可在拿到完整帧时立即返回。
   风险：变长协议（GB3024 一行 ASCII）无法预知长度，仍需静默兜底 —— 可对
   "有 read_size 的模板"启用快速路径，对变长协议保留 10 ms。
2. **scheduler 队列深度/入队策略**：`full=582` 表明需要背压而非丢弃；
   或提高 `CMD_QUEUE_DEPTH` 并让调度器在队列满时**跳过**而不是覆盖。
3. 两条都改完后重新实测，才能回答"能否 100 Hz"。

---

## 5. 诚实性说明

- 本结论**不代表**现场 2 路链路有问题：现场 manifest 是 5000/1000 ms，
  实测 0.200/1.007 Hz 与配置完全一致，`error_reports=0`。
- 本结论**只**说明"把 interval 调到 10 ms 后，固件在 115200 下只能跑到 26 Hz"。
- `step3` 的 5×100 Hz 是 **MQTT 层仿真**（`loadtest-sim5x100`，后端 500 report/s、
  157 KB/s、`processed_delta=30000`、`errors=0`），验证的是**后端吞吐**，
  **不是**真实 UART 链路。且该步 `dropped_delta=76` → `overall_pass=false`。
