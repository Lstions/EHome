## 2. 五个核心设计决策（都有翻车记录）

### 2.1 一次取「整帧」而不是「一行」

unified_data 一行是一个**字段**。逐行编码 ⇒ 每行变一帧 ⇒ 帧数放大 29 倍、压缩率归零。

两步走：① 取帧键 `(device_id, timestamp)` 有序分页；② 按 `[minTS, maxTS]` 一次范围查询取回整帧的全部行，内存里按 `(device, ts)` 分组。

为什么不在循环里逐帧查：2000 帧 × 342 批 = **68 万次往返**。范围查询把每批压到 1 次。

### 2.2 watermark 必须落在「帧边界」上（断点续跑的命门）

若一批在某个 timestamp 中间截断，watermark 记成该 ts，恢复时 `timestamp > watermark` 会**永久跳过**没处理完的帧 —— 静默丢数据。

实现：取帧键时多取 1 条做前瞻，若第 `batch+1` 条与第 `batch` 条同 ts，把该 ts 整组让给下一批（`truncateAtCleanBoundary`）。

### 2.3 ⚠ watermark 恢复必须 +1ns（实测踩到）

`fetchFrameKeys` 的下界是**闭区间**（`timestamp >= from`），而 watermark 的语义是「这条 ts 已完整处理」。直接用 watermark 当 from 会把最后一帧**重新编码一次**：

行不会重复（`ON CONFLICT DO NOTHING`），但 **frames_done 多加 1**，对账口径就错了。实测症状：

```
最终 frames_done = 41, want 40（必须是真实帧数，不能累加两次）
```

修复：`from = row.Watermark.UTC().Add(time.Nanosecond)`。

### 2.4 关键帧策略：必须按设备分组 + 周期 Reset（最关键的一条）

契约 §4.5 要求「每 60s 强制一个关键帧」。但 `telemetry.Encoder` 的关键帧判定是**基于时间间隙**的 —— 那是为线上流式写入设计的「丢帧后重建链」语义，在持续 1 Hz 的密集数据上**不会**定期发关键帧。

直接用会发生什么：回填 device14 一个月的 220 万帧只有第一帧是关键帧，之后是一条 220 万帧的增量链。一旦某帧损坏，解码器标记该 slot 链失效并丢弃后续所有增量帧直到下一个关键帧 —— **而下一个关键帧可能永远不来**。

实现：按设备分组（编码器状态本就按 `(deviceID, slot签名)` 分键，分组是**等价变换**），设备内按时间序编码，每跨过 `KeyFrameInterval` 就 `enc.Reset()` 一次。

顺带解决内存：`Encoder` 内部的 `seqs map[(device,ts)]` 是**无界**的，3.42M 帧会累计 3.42M entry（约 160 MB）。周期 Reset 把它钉在批内量级。

### 2.5 超量程原文进 raw 列

契约 §2.2 的 5 行 `battery_voltage = 1e12`：编码时被 clamp，但原文写进 `telemetry_frame.raw`（JSON），常规帧 raw 留 **NULL**。

为什么常规帧必须留 NULL：raw 是原始总线帧（平均 78 B），全写会让 463 MB 涨到几十 GB。

```sql
{"clamped":[{"field":"battery_voltage","value":1e12,"spec_min":0,"spec_max":204.7,"spec_step":0.1}],
 "note":"1 个字段超出量化量程，已被 clamp；原文见 clamped 数组（契约 §2.2 的 battery_voltage 1e12 类数据）"}
```

## 3. 真实数据对拍（契约 §6.1 核心验收）

命令：

```
GOW_WORKDIR=backend scripts/gow.sh test -count=1 ./internal/backfill/ \
  -run 'TestRealDataBackfillRoundTrip' -v -timeout=40m
```

实测输出：

```
真实数据：142467 帧（2026-11-04 ~ 2026-11-05）
已灌入 unified_data：2811888 行（142467 帧）
slot 规模：8 行（契约要求 < 10,000）
device 14：帧=86342 解码点=2503918 坏帧=0 断链=0 缺基线=0
device 15：帧=56125 解码点=307970 坏帧=0 断链=0 缺基线=0
对拍结果：已比对 2811888 个值 | 缺失 0 | 超差 0 | 超量程(走 raw) 0
最大误差：9.094947017729282e-13  (total_energy @ 2026-11-04T00:24:05.016802Z 原值=4762.9 解码=4762.900000000001 误差=9.09e-13 (Step/2=0.05))
--- PASS: TestRealDataBackfillRoundTrip (79.38s)
```

**解读三点**：

1. **帧数逐位相等**：86,342 + 56,125 = 142,467，与方案 §1.1「真实帧数（微秒精度去重）」完全一致 —— 分组逻辑没多切也没少切。
2. **解码点 = 原表行数**：2,503,918 + 307,970 = 2,811,888，与灌入的 unified_data 行数逐位相等 ⇒ **每个字段值都还原出来了**，没有稀疏帧丢字段。
3. **最大误差 9.09e-13 是浮点表示误差**，不是量化误差：`total_energy` 的 Step/2 = 0.05，实际误差比其小 11 个数量级 —— 那是 `Dequantize` 的一次乘加在 float64 上的舍入，远小于阈值。

### 3.1 为什么真实数据能测出合成数据测不出的东西

- device15 的 **7 种帧类型**（字段集合各不相同）⇒ 验证 slot 派生真的分开了（实测 8 个 slot）；
- L1 之后的**稀疏帧** ⇒ 验证增量链跨 slot 累积正确；
- 真实量化边界（cell_voltage 两位小数 vs spec 1mV）。

### 3.2 ⚠ 踩坑：SQLite 绑定变量上限

第一次跑真实数据直接失败：

```
回填失败: persist 5000 frames: too many SQL variables
```

7 列 × 5000 帧 = 35,000 个绑定变量 > SQLite 上限（32,766）。合成数据只有几十帧测不出来，**真实数据 142,467 帧一跑就炸**。

修复：分块写，500 行/块（3,500 变量，两方言都安全）。

## 6. 不阻塞启动（契约 §6.4）

`cmd/server/main.go` 在 `StepStartupTasks` 的 `Done` 之前启动 goroutine：

```go
backfillRunner := backfill.NewRunner(db, telemetryDict, backfillCfg, !backfillEnabled, backfillWarns)
if backfillRunner.Enabled() {
    go func() {
        prog, err := backfillRunner.RunOnce(context.Background())
        ...
    }()
}
```

- 两个 env 参数：`EHOME_BACKFILL_ENABLED`（默认 true，应急阀）、`EHOME_BACKFILL_BATCH_FRAMES`（默认 2000）；
- 状态表建不出来 ⇒ **跳过回填，不 Fatal**（不挡主写入）；
- 回填失败 ⇒ 只 Warn，服务照常。

## 7. 残余风险（诚实清单）

1. **slot 规模依赖数据形态，不是恒定的**：单日 8 个，但全库 36 天预期约 7,400（device14 的 L1 稀疏帧每天产生大量不同字段集合）。若 L1 的心跳策略或字段集合进一步碎片化，可能超过 10,000 上界。**建议**：T2 的进度接口里暴露 slot 行数，上线后观察一周。

2. **回填与实时写入并发**：回填在写 `telemetry_frame`，L2 实时双写也在写同一张表。两者都用 `ON CONFLICT DO NOTHING`，不会冲突；但**同一 (device, ts, seq) 谁先写谁生效** —— 若回填与实时写入覆盖同一时刻（不可能：回填只处理 watermark 之前的历史），理论上无重叠。当前实现按分区月边界切分，实时数据在当月分区，回填跑的是历史月分区，天然隔离。

3. **编码器 Reset 带来的额外关键帧**：每批每设备首帧都是关键帧。342 批 × 5 设备 × 约 35 B ≈ 60 KB，相对 463 MB 可忽略（0.013%）。

4. **eta_seconds 未实现**：契约 §4.6 要求，本任务只做了 `Percent`（按分区时间跨度加权）。ETA 需要按实测速率外推，属 T2 的进度接口范畴。

5. **老 unified_data 不 DROP**：契约 §7 裁决 2 建议「迁移 → 验证 1 周 → 再 DROP」。本任务只做迁移，**不删任何老数据**。

6. **单进程**：`RunOnce` 不可重入（同一 Runner 不能并发跑）。当前部署是单容器，若将来多实例，需要状态表加「租约」列（与 purge 的认领协议同型）。

### 7.7 与保留期（task-13）的接口：回填**从不自动删老数据**

task-13 落地了「保留期 0 = 永久保留」。对回填的含义是：**迁移完成后老 `unified_data` 分区是否 DROP，永远是人决策**。

代码保障（两道）：

1. **源码级门禁** `TestBackfillNeverDeletesSourceData`：扫描本包全部非测试 .go，禁止 `DROP TABLE` / `DROP PARTITION` / `DROP INDEX` / `DELETE FROM` / `TRUNCATE <table>`。
   用**词边界正则**而不是 `strings.Contains`：本包有个函数叫 `truncateAtCleanBoundary`（截断批边界，与删数据无关），朴素 Contains 会把它判成违规 —— 那是假红，假红比没门禁更糟（维护者会去改名迎合门禁或直接注释掉）。
2. **进度字段透出** `Progress.RetentionPermanent`：取快照时实时读 `datalifecycle.IsRetentionPermanent()`，让上层（T2 进度接口 / 运维按钮）知道「现在是永久保留模式，删了不可恢复且违背配置」。

门禁的变异验证（真做）：在 `runner.go` 里加一行 `var mutationProbe = "DELETE FROM unified_data WHERE 1=1"`，门禁立刻红：

```
--- FAIL: TestBackfillNeverDeletesSourceData (0.00s)
    backfill_test.go:434: runner.go 含有 "DELETE FROM" —— 回填引擎绝不能删老数据
（契约 §7 裁决 2：DROP 必须由人触发）。永久保留模式下删数据不可恢复，且直接违背用户需求。
```

去掉后恢复 `ok ehome/backend/internal/backfill 73.241s`。

## 10. 2026-11-07 修复：进度 percent 严重偏低（生产实测 13.1% vs 实际 45.2%）

### 10.1 现象

```
GET /api/v1/system/backfill → percent=13.1, frames_done=1,546,000
实际：1,546,000 / 3,419,991 = 45.2% 的帧已回填
```

### 10.2 两个**叠加**的成因（必须分别修，只修一个都不够）

**成因 1：权重口径错了（时间跨度 ≠ 工作量）**

生产 6 个月分区里 **4 个是空分区**（0 行），只有 202610/202611 有数据。原 `recomputePercent` 按分区**时间跨度**等权 ⇒ 分母恒为 6 个月、分子最多 2 个月 ⇒ **percent 天花板 33%**。

**成因 2：mark* 只写库，不更新内存快照**

`markPartitionRunning` / `markPartitionDone` / `markPartitionFailed` 只 UPDATE 数据库，不碰 `r.progress.Partitions`。而 `recomputePercent` 读的是内存快照。

空分区**不经过** `advanceWatermark`（那里才有内存同步），只在 `markPartitionDone` 里被标 done ⇒ 内存里它们的 `State` 永远是 `pending` ⇒ `switch` 不匹配任何分支 ⇒ 计 0 分。

**为什么不能只修成因 2**：把空分区也标 done 并同步内存，会让 4 个空分区在**启动瞬间**各贡献 1/6 ⇒ 进度条一开局跳到 66.7%，是另一种谎报（更糟 —— 用户会以为快好了）。

### 10.3 修复

**权重改成实测行数**：`discoverPartitions` 时对每个分区跑一次 `count(*)`（生产 72.7M 行 ≈ 1.5s，相对 20~40 分钟任务可忽略）。

```go
// partition.rows = 该分区总行数
// 空分区 rows=0 ⇒ 权重 0，既不进分母也不进分子
percent = Σ(已消费行数) / Σ(总行数)
```

**内存同步**：新增 `setPartitionState(name, mutate)`，三个 mark* 都调它，就地更新 `r.progress.Partitions` 并重算 percent。

**降级**：`count(*)` 全失败（rows 全为 0）时退回时间跨度加权，并 `addError` 提示 —— 绝不因为算不出权重就显示 0%。

### 10.4 量化对照（按生产分布计算）

生产行数分布：202610 ≈ 52M、202611 ≈ 20M、其余 4 个月 0 行。在 frames_done = 45.2% 那一刻：

| 口径 | percent |
|---|---:|
| 修复前（时间跨度等权） | **10.4%** |
| 生产实际观测 | **13.1%** |
| 修复后（行数加权） | **45.2%** |

修复前的计算值与生产观测吻合（差 2.7 个百分点来自 frame 数在两个月间并非严格按行数比例分布）。

### 10.5 PG 用例实测（TestPGPercentTracksFrameRatio）

### 10.8 契约要求 2 的核实结论

Lead 问：「`reloadProgressRows` 之后，为 `r.parts` 里每个分区都在 `r.progress.Partitions` 建一条（现在似乎只给「跑过的」建）」

**核实：原代码已经是全覆盖的** —— `reloadProgressRows` 的 `for _, p := range parts` 显式遍历 `r.parts` 全量建条目（`persist.go:64-80`）。空分区**在列表里**。

真正的问题是它们的 `State` 停在 `pending` 且 `rows` 权重不存在。已用 `TestPGProgressPartitionsCoverAllDiscovered` 钉住「列表覆盖」这一不变量，防止将来退化。

### 10.9 生产影响与残余风险

· 生产回填**无需重启即可修好显示**（接口读的是 `Runner.Progress()`，重新部署后新逻辑生效，回填从 watermark 续跑）；
· `count(*)` 一次性成本 ≈ 1.5s（72.7M 行，实测 14.3M 行 313ms），发生在后台 goroutine 的 discovery 阶段，不影响 ready；
· 若某分区 `count(*)` 失败，该分区 `rows=0` ⇒ 权重 0 ⇒ 会**低估**它的工作量。已在 `fillPartitionRows` 里 `addError`，进度接口的 `errors` 字段能看到。
