# 节点页七类外设失败项修复与复验（2026-11-20）

> 目标：在上一轮《节点页七类外设功能验证》基础上，把设备/后端/前端所有失败项逐项定位、修复并复验，不以“页面能打开”代替真实回执。

## 1. 复验结论

| 功能 | 上一轮结论 | 本轮结论 | 证据 |
|---|---|---|---|
| GPIO | PASS | **PASS**（回归未破坏） | 输出/输入、UI、设备回执均正常 |
| PWM | 控制 PASS，READ 失败 | **PASS（控制+读取）** | 停止后读取成功，duty=4540、running=false；UI 显示“已停止/启动”，启动后“运行中”，停止后恢复 |
| ADC | FAIL（固件无 ADC 路径） | **PASS（配置/规划）**；数据读取未开放 | `ConfigResult success=1`，`ADC1_CH1 init`；节点页无 ADC 实时读数入口 |
| UART | TX PASS，RX 未测 | **PASS（TX）**；RX 无回环条件 | 终端页发送 A5 5A，TX 计数 1、2B；RX 无对端 |
| I2C | 扫描桩 | **PASS（真实往返）** | ScanReq→ScanRpt，0x08–0x77 探测；无从机时返回 0 个地址（真实空结果） |
| SPI | FAIL（ConfigResult=false） | **PASS（配置/初始化）**；数据面未接从机 | `ConfigResult success=1`，SPI2 轮询初始化成功 |
| DMA | 控制面 PASS，设备不回显 | **PASS（控制/UI）**；数据面未验证 | UI 显示 CH1→UART0；GET 合并配置意图；设备 ResourceReport 仍不回显 bound_to |

## 2. 失败根因与修复

### 2.1 SPI：控制器号把“端口号 2”当成了 `spi_host_device_t`

- 固件 `hw_spis[0].port = 2`（SPI2 的人类端口号），而 IDF 枚举 `SPI2_HOST = 1`。
- `bus_manager` 把 `port` 直接写进 `plan[].controller_id`；`spi_init()` 再强转 `(spi_host_device_t)2`，在 C6 上 `2 >= SPI_HOST_MAX(2)` ⇒ `ESP_ERR_NOT_SUPPORTED`。
- 修复：`hw_tables.c` 的 `hw_derive_spi_host()` 与 `bus_manager` 的控制器映射统一使用 `port - 1`；`SPI2 → SPI2_HOST(1)`。
- 前端另有一个输入端错误：资源字段实际是 `default_mosi_pin/default_miso_pin/default_sclk_pin`，旧代码读 `default_mosi/default_miso/default_sclk` 得到 `undefined`，被 `|| -1` 写成 `0xFF`（GPIO 255）。已修正字段并禁止缺失时写入 0xFF，缺能力直接返回空 busConfig 交给提交守卫。
- 修复后日志：`SPI config: CS=5, mode=0, freq=1000000, MOSI=23, MISO=19, SCLK=18, dma=0`、`SPI polled device init`、`ConfigResult success=1`。

### 2.2 ADC：固件没有 bus_type=5 的执行路径，且 unit 枚举差一

- 原 `bus_manager/bus_dma` 只实现 UART/I2C/SPI/USB，`bus_type=5` 走到 `default` 返回 `ESP_ERR_NOT_SUPPORTED`。
- 修复：新增 `BUS_TYPE_ADC=5`，bus_config 五字节 `[unit, channel, pin, attenuation, bit_width]`；`adc_init()` 用 `adc_oneshot_new_unit/adc_oneshot_config_channel` 建通道；引脚参与资源冲突检查；`ResourceReport` 已能上报 ADC。
- 第二个现场错误：`hw_adcs[].unit=1` 是“ADC1”的人类编号，`adc_unit_t` 从 `ADC_UNIT_1=0` 开始。直接强转 1 会请求不存在的 `ADC_UNIT_2`，日志为 `adc_oneshot_new_unit(86): invalid unit`。修复为 `unit - 1`。
- 后端新增加固件一致的 5 字节补齐：即使旧调用方传空 `bus_config`，也会按节点 ResourceReport 生成合法配置（本次用 `PUT bus_config:""` 验证，返回 `010101030c`，配置 applied）。

### 2.3 I2C 扫描：设备钩子是空实现，后端是桩，ScanRpt 字段编码也不一致

- 固件 `on_scan_req_received()` 只打 WARN，不发回执；后端 `/nodes/:id/bus/i2c/scan` 恒返回空数组。
- 后端 `handleScanReport()` 用 `GetBytes(field 4)`，固件却用 repeated varint 编码 field 4 ⇒ 即使回执到了也解析成空。
- 修复：固件实现 `bus_dma_i2c_scan()`（`i2c_master_probe` 扫 0x08–0x77），按 channel id 找到 I2C lease 并发送 ScanRpt；字段 4 改为 bytes（每地址 1 字节）；后端增加 `SendI2CScan(ctx, deviceID, channelID)`，用 request_id 关联异步 ScanRpt，HTTP 等待真实结果。
- 实测：`ScanReq I2C: req=... hw=9` → `I2C scan 0x08-0x77: 0 device(s)` → `Sending ScanRpt ... success=1, addrs=0`；后端日志同 request_id；HTTP 83ms 返回 `devices:[]`。

### 2.4 PWM READ：停止后读取被当成错误

- `pwm_ctrl_get_duty()` 旧实现要求 `running==true`，用户先 STOP 再刷新页面就返回 `ESP_ERR_INVALID_STATE`（error_code=5）。
- 修复：已配置（`configured`）即返回最后已知 duty；`running` 由 PeriphRsp 单独携带。实测停止后 `success=1, value=4540`，UI 显示“已停止 45.40% 启动”。

### 2.5 日志无法定位事务失败：环形缓冲只有 4 条

- 配置事务一次会输出 10+ 条步骤日志，4 条环形缓冲在 log_tx 发送前就被覆盖，导致 `ConfigResult=false` 在节点日志里只剩一行“result=2”。
- 修复：`RING_CAPACITY 4 → 24`、发送周期 `1000ms → 250ms`、RAM 预算 `6656 → 10240`；`tx_begin/tx_snapshot` 增加阶段日志；事务门增加 5s 超时，卡死时返回可见错误而不是永久挂起。

### 2.6 UI 配置状态真实性

- 旧 `syncStateLabel` 只看 `config_sync_state`；设备 `ConfigResult=false` 时服务端可能仍显示 `in_sync`。
- 修复：优先看 `node.config_status==='failed'` 显示“配置失败”，`pending` 显示“配置处理中”。

## 3. 逐项复验步骤与结果

### 3.1 SPI

1. `POST /api/v1/channels` 创建 `SPI2`，bus_config=`0500000F4240171312`（CS5/mode0/1MHz/MOSI23/MISO19/SCLK18）。
2. 等待配置事务完成。
3. 设备日志：`ch=15 type=3` → `SPI config` → `SPI polled device init` → `ConfigResult success=1`。
4. 节点配置：`config_status=applied`，`Config transaction committed: channels=3`。

### 3.2 ADC

1. `POST /channels` 创建 `ADC1_CH1`，bus_config=`010101030C`（unit1/channel1/pin1/atten3/12bit）。
2. 设备日志：`ADC1_CH1 init (pin=1 atten=3 bits=12)`、`ConfigResult success=1`。
3. 额外验证旧空 bus_config：`PUT /channels/19 {"bus_config":""}`，后端补成 `010101030c`，同步后 applied。

### 3.3 PWM

1. 停止状态调用 `GET /nodes/F0F5BD02F35C/pwm/PWM0/state`。
2. 返回 `code=200, duty=4540, auto_start=false`（旧版本为 error_code=5）。
3. UI 外设→PWM：显示“已停止 45.40% 启动”；点击启动→“运行中 停止”；点击停止→“已停止 启动”。

### 3.4 UART

1. 终端页选择 UART0，HEX 输入 `A5 5A`，发送。
2. UI 下行 TX 计数 1，显示 `A5 5A`；提示“已发送 2 字节”。
3. 无物理回环/对端，RX 仍为 0；本轮不能声称 RX 已验证。

### 3.5 I2C

1. 节点页 总线与通道→I2C→地址扫描。
2. UI 显示“扫描完成：未发现设备”。
3. 设备日志与后端日志为同一 request_id，证明不是桩返回；总线上没有从机，空结果是真实结果。

### 3.6 DMA

1. `GET /nodes/:id/dma-channels` 显示 CH1 已分配 `uart/UART0`（后端把 node.Config 的绑定意图合并进查询结果）。
2. UI DMA 分配页显示“已分配 UART0（UART）”，解绑入口可用。
3. 设备原始 ResourceReport 当时仍 `state=0, bound_to=""`；即控制面/配置意图已对齐，但设备回报与真实 DMA 数据面仍未闭环。**该问题已在同日补验中修复，见 [DMA数据面与ADC实时读数-2026-11-20.md](DMA数据面与ADC实时读数-2026-11-20.md)。**

## 5. 尚未闭环（必须如实保留）

1. ~~**ADC 数据读取未开放**~~ **已闭环（2026-11-20 补验）**：节点页增加「读取」，真实返回 raw/百分比；见 [DMA数据面与ADC实时读数-2026-11-20.md](DMA数据面与ADC实时读数-2026-11-20.md)。
2. **UART RX 未验证**：没有物理回环或对端设备；本轮只补了 TX + DMA 数据面。
3. **DMA 资源上报已闭环**：设备原始 ResourceReport 为 `state=1, bound_to=uart/UART0`；真实 GDMA 2KB 内存自检 10/10 通过。**但 UART0 的 UHCI 硬件 DMA 仍未实现**（`bus_dma.c` 对 UART 仍是中断驱动），不能把 CH1→UART0 说成 UART DMA 搬运；详见补验报告。
4. **SPI/I2C 没有接从机**：只验证了控制器初始化/扫描请求-回执；没有验证真实读写时序与数据。

## 6. 本轮代码改动

- `esp32-collector/components/hw_profile/hw_tables.c`：SPI port→controller enum 映射。
- `esp32-collector/components/bus_manager/bus_manager.c`：ADC 规划、SPI controller 映射、诊断日志。
- `esp32-collector/components/bus_dma/{bus_dma.c,include/bus_dma.h}`：ADC 总线、I2C 扫描、PWM 无关。
- `esp32-collector/components/pwm_ctrl/pwm_ctrl.c`：停止状态读取。
- `esp32-collector/components/periph_owner/periph_owner.c`：ADC 引脚占用、事务门超时。
- `esp32-collector/components/config_mgr/config_mgr.c`：ADC 引脚冲突。
- `esp32-collector/components/log_stream/log_stream.c`：24 条环形缓冲、250ms、预算。
- `esp32-collector/main/main.c`：I2C 扫描钩子。
- `esp32-collector/main/app_callbacks.c`、`config_apply_transaction.c`：事务诊断/超时。
- `backend/internal/nodemgr/{i2c_scan.go,handler_response.go,manager.go}`：ScanRpt 关联。
- `backend/internal/api/{handler_node.go,handler_device.go,handler_periph.go}`：真实 I2C 扫描、ADC 补齐。
- `backend/internal/nodemgr/manifest_codec.go`：ADC 引脚冲突。
- `frontend-shared/.../channelFormModel.ts`、`channelBusConfig.ts`：SPI 默认引脚字段、ADC 五字节、缺失值保护。
- `frontend-shared/.../useNodeOverviewData.ts`：配置失败文案。
