## 四、本轮的核心技术发现

### 1. 一个「功能正确但性能极差」的代码，在依赖被删前完全不可见

```

**判据：删除一张表的彻底性，只能由「表不存在时的运行期日志」证明。**

### 3. `/tmp` 在沙箱里每次 bash 调用都不持久（impl-l2 发现，三人独立复现）

```

CALL B: ls /tmp/probe.txt             => No such file
=> 任何「锁文件放 /tmp」的跨调用互斥机制**静默失效**
正确位置: git rev-parse --path-format=absolute --git-common-dir

**而它的危险在于「看起来是有效的」** —— 有实现、注释对、单进程测过能互斥，
却在真实使用场景（两次独立 bash 调用）里 100% 失效。

```

**E4 落在 ② 而不是 ①。** 而我上面 八附 的表格里把它记作「可核对位置」——
**严格说我高估了一级**：它可核对的是「我做过这个修正」，不是「我当时判断错了什么」。

### 按这三类重分我那 6 条

| # | 原判断 | 痕迹类型 | 说明 |
|---|---|---|---|
| ① | 生产代码不再有任何 unified_data 读路径 | **①结果** | 42P01 原文在容器日志里，且修复前后可对比 |
| ② | implementation segments 6h | **①结果** | `framesBatchLimit` 的值与调用点当场可读 |
| ③ | 24h page span truncates 2.6× | **①结果** | 被截的那一层代码可读 |
| ④ | #1 的 43 ok/4 FAIL = 中途有别人的容器 | **③无痕迹** | 只有「我们都没测过 mid-run 快照」这个否定事实 |
| ⑤ | A1 是 DROP 的唯一入口 | **①结果** | grep 调用点即可证伪 |
| ⑥ | 16 字段各查一次 = 6,286 条 | **①结果** | 763 次重复查询在日志里 |
| （E4 那条）| 「没覆盖到 ⇒ unified_data 里也不会有行」 | **②记录** | 只有注释自陈 + 一个未保存的查询数字 |

**所以准确的比例不是「5 条有痕迹 + 1 条无痕迹」，而是：**

```
① 结果痕迹  5 条
② 记录痕迹  1 条（E4）
③ 无痕迹    1 条（④）
```

而这个分布比 5/6 更能说明问题：

> **①类是可以被别人独立复核的；
> ②类只能复核「作者做过修正」，不能复核「作者曾判断错什么」；
> ③类只能信任。**

而作者（我）最容易犯的错，是**在分类时把 ② 类当成 ① 类**——
因为「我在注释里写了」感觉上就等于「有据可查」。

### 这条判据的可执行形式

```
当你声称「我曾判断错 X」时，问一句：
  我手上的证据，是「当时的事实」还是「我后来的自陈」？

  是事实（日志/数据/可复现命令）  => ①类，可以要求别人复核
  只是自陈（注释/文档/对话）      => ②类，只能要求读者信任，必须标注
  什么都没有                      => ③类，必须标注「无痕迹」

**关键：②类不能标成 ①类 —— 那是把这个判据本身变成不可信的东西。**
```

而这条判据最难的地方不在分类，在于：**分类是作者自己做的，而作者有动机高估。**
 => 所以外部复核（像 impl-l2 这次做的）是唯一有效的发现方式。
