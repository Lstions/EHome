# 多总线事件驱动测试验证方案

## 1. 文档状态

本文档是《多总线事件驱动开发实施计划》的配套验证方案，覆盖 UART/SPI/I2C 动态接口分配、UART 事件驱动接收、独立软件队列、统一透明接收和 DMA 可配置能力。

本 worktree 已开始按方案实施。P0～P5 的 host/后端/目标编译自动化验证已执行；
实机写配置、长稳、网络故障和 1 Mbps 闭环仍需在目标板和固定测试拓扑上按本方案
执行，不能以目标编译替代实机验收。

基线信息：

- 开发分支：`codex/multi-bus-event-driven-plan`

## 2. 验证目标与边界

### 2.1 总体验证目标

验证改造后同时满足以下要求：

1. 逻辑 Channel 与物理 UART/SPI/I2C controller 解耦，接口由运行时动态分配；
2. UART0 与 UART1 使用完全一致的规划、执行、接收、上报和错误恢复流程；
3. UART 从固定周期轮询改为 driver event queue 驱动，不再依赖 5 ms 数据扫描；
4. 对外只有一套通用透明接收流程，不要求用户预先选择“命令模式”或“流模式”；
5. UART、SPI、I2C 使用独立 controller 软件队列，单一接口拥塞不扩散到其他接口；
6. DMA 保持显式可配置，配置请求、硬件能力、资源分配和实际 driver 状态一致；
7. 新增功能通过验收，所有受影响的既有功能完成回归；
8. 配置失败、资源不足、网络中断和队列拥塞时行为可控、可观测且可恢复。

### 2.2 不属于本方案的内容

- 不新增供用户选择的 UART 接收模式；
- 不承诺在没有流控、网络长期断开且输入无限持续时永久零丢失；
- 不把 SN-3001 提升到 1 Mbps，SN-3001 按设备支持的 4800/9600 baud 验证；
- 不以 UART0 或 UART1 的当前接线作为固定业务约束；
- 不以模拟测试替代必须完成的真实硬件闭环；
- 不在本轮计划阶段修改生产数据、设备地址、设备波特率或固件。

### 2.3 测试原则

- **先建立基线再改造**：相同硬件、配置、数据和测试脚本在改造前后各执行一次；
- **按变更影响回归**：直接修改、间接依赖和共享资源三类功能均纳入测试；
- **物理接口对称**：UART0/UART1 交换设备后必须得到等价结论；
- **分阶段门禁**：P0～P7 每阶段完成其新增测试和指定回归后才进入下一阶段；
- **可追溯**：需求、代码改动、用例、结果和缺陷必须有稳定编号；
- **失败优先**：资源冲突、队列满、断网、超时、回滚和重启是正式验收项；
- **结果可量化**：使用字节计数、sequence、CRC、延迟、错误计数、队列水位、heap 和栈余量判断结果；
- **实机恢复**：涉及 SN-3001 写操作或临时 manifest 的测试结束后必须读回并恢复基线。

## 5. 新增功能测试方案

## 5.1 资源规划器和动态 lease

### 正常分配

- 单个 UART Channel 在 UART0 空闲时可分配 UART0；
- UART0 已占用或不满足引脚约束时，同一 Channel 可分配 UART1；
- 两个 UART Channel 可分别获得两个不同 controller；
- UART、SPI、I2C 混合配置可一次生成完整 allocation plan；
- SPI 多 CS 设备按共享总线规则复用同一 controller；
- I2C 多地址设备按相同 SDA/SCL 和速率约束复用 controller；
- manifest 顺序变化但资源约束不变时，规划结果保持确定性；
- 无关 Channel 更新时，兼容的现有 lease 保持不变。

### 冲突与拒绝

- UART TX/RX 引脚与其他 UART、SPI、I2C、GPIO、PWM 冲突；
- UART controller 数量不足；
- SPI controller 数量不足或共享设备配置不兼容；
- I2C controller 数量不足或共享设备时钟/引脚不兼容；
- console/boot/flash 等保留资源冲突；
- 同一 UART 的 TX/RX 非法、重复或 capability 不支持；
- DMA 请求超过硬件能力或 pool 可用数量；
- field 缺失、显式 false、显式 true 三种 DMA 配置分别解析；
- 任一资源不可满足时，在 teardown 前拒绝完整 plan，不留下半应用状态。

### 生命周期与回滚

- 成功 apply 后 Channel、lease、driver、worker、DMA pool 和 ResourceReport 一致；
- suspend 请求能唤醒阻塞中的 worker，并返回 ACK；
- worker ACK 前不得删除 driver/event queue；
- apply 中任一阶段失败，原 driver、lease、队列和 DMA allocation 恢复；
- apply 失败后原 Channel 仍能执行一次真实读写；
- 节点重启后由持久 manifest 得到等价 lease；
- 旧 generation 的迟到 event/descriptor 不得投递到新 Channel；
- 连续快速切换配置不发生 double-free、use-after-free、死锁或任务泄漏。

### 结果判定

- planner 对相同输入输出确定；
- 每个 active Channel 恰好对应一个有效 lease；
- 同一不可共享资源最多被一个 lease 持有；
- runtime 实际状态与 ResourceReport 完全一致；
- 失败路径的状态与 apply 前快照一致。

## 5.2 UART0/UART1 对称性

至少执行以下对称矩阵：

| 用例 | UART0 | UART1 | DMA | 目的 |
|---|---|---|---|---|
| U-SYM-01 | 1 Mbps 输入 | SN-3001 9600 | 均关闭 | 非 DMA 对称并行 |
| U-SYM-02 | SN-3001 9600 | 1 Mbps 输入 | 均关闭 | 交换 controller |
| U-SYM-03 | 1 Mbps 输入 | SN-3001 9600 | 高速侧开启 | DMA 分配与隔离 |
| U-SYM-04 | SN-3001 9600 | 1 Mbps 输入 | 高速侧开启 | DMA 交换分配 |
| U-SYM-05 | 模拟协议 A | 模拟协议 B | 能力允许组合 | 双命令并发 |
| U-SYM-06 | 禁用后重配 | 保持工作 | 分别开/关 | 单接口生命周期隔离 |

两组交换用例必须使用相同 payload、时长、命令频率和判断标准。分别记录：

- UART 输入/输出字节计数；
- sequence gap、CRC 错误和不连续标记；
- FIFO overflow、ring overflow、block pool exhausted；
- control/sample/report queue depth 和 high-water；
- critical normal/emergency block 的可用量、占用、耗尽和丢弃计数；
- SN-3001 成功数、超时数、p50/p95/p99；
- heap、minimum heap、两个 UART worker 栈余量；
- MQTT publish 延迟和 critical report 延迟。

UART0/UART1 的结论只有在交换后均通过才成立。某一个 controller 单独通过不能视为对称性通过。

## 5.3 UART driver event queue

### 事件覆盖

- `UART_DATA` 单次事件包含完整帧；
- 一个帧拆成多个 `UART_DATA` 事件；
- 一个事件包含多个完整帧；
- 事件指示长度大于单个 RX block；
- burst 输入与长时间连续输入；
- `UART_FIFO_OVF`；
- `UART_BUFFER_FULL`；
- frame error、parity error 和 break（硬件/driver 支持时）；
- 数据事件与 suspend/reconfigure 同时发生；
- driver 删除前仍有排队事件；
- event queue 满或事件通知丢失的恢复与统计。

### 行为要求

- RX task 阻塞等待事件，不使用固定 5 ms 扫描作为主接收机制；
- 每次 event 尽可能清空 driver 已报告的数据，避免只读取固定 512 B；
- RX task 只完成搬运、边界判断和 descriptor 投递，不调用 MQTT/TCP；
- 错误事件不会悄悄清零统计或伪装成完整帧；
- overflow 后产生明确 discontinuity，后续有效数据仍可恢复处理；
- suspend/reconfigure 不依赖等待数据事件才能退出。

### 验证手段

- host stub 精确注入事件序列并校验状态机；
- 实机用不同 chunk、不同帧间隔和持续写入触发事件；
- 临时诊断计数确认事件数、读取字节数和提交字节数闭合；
- 静态检查 RX 路径不存在 transport publish 调用。

## 5.4 通用透明接收与自动边界

系统对外只有一种接收流程。以下差异由运行时上下文自动判断，不形成用户可配置的“模式”。

### 有 pending command

- 提供 `read_size` 时，累计到指定长度立即完成；
- 一个 event 不足 `read_size` 时跨 event 累计；
- 一个 event 超出 `read_size` 时，仅目标字节归属当前响应，剩余字节继续进入同一通用接收链路；
- 已知协议长度、结束符、CRC 完整时及时完成；
- 协议头有效但数据不足时不得提交半帧；
- 未知长度响应按 pending command idle timeout 完成；
- transaction timeout 到达时返回明确超时，不把残缺响应标成成功；
- 错地址、错 CRC、噪声前缀和多个候选帧按现有 parser 语义处理；
- response 与主动上报数据相邻到达时不串帧、不丢剩余数据。

### 无 pending command

- 短 burst 在最大等待时间内聚合后提交；
- 达到最大 block 大小时不等待 idle，立即提交并继续接收；
- 数据持续到达时能周期性提交固定上限的 block；
- block 边界不会丢字节或重复字节；
- sequence 单调递增，重启或重配时有明确 reset/generation 语义；
- 发生 overflow 时下一条 report 携带 discontinuity/错误统计；
- 没有数据时不产生空 DataReport。

### 边界优先级测试

逐项验证以下优先级不会被低优先级条件提前截断：

1. 明确 `read_size`；
2. 可验证的协议长度、结束符或 CRC；
3. pending command idle timeout；
4. 无 pending command 的最大 block/最大等待时间；
5. transaction timeout 或 driver 错误。

## 5.5 RX block pool 与 descriptor 队列

- block pool 初始化数量、block 大小和总 RAM 与配置一致；
- 队列中传 descriptor，不复制超大 payload；
- block 的 acquire/release 恰好配对；
- publisher 成功、失败、超时、丢弃、重连和 shutdown 路径均释放 block；
- pool 耗尽时按既定策略拒绝 telemetry，并记录 drop/discontinuity；
- critical report 不依赖 telemetry block 可用性；
- 重配置只回收属于旧 generation 且不再被消费者持有的 block；
- 重复 release、越界长度、悬空 descriptor 在 host test 中被检测；
- 长稳结束后 pool 可用数回到稳态，不随运行时间持续下降。

## 5.6 独立软件队列、优先级和背压

### controller 隔离

- UART0 sample queue 满，不影响 UART1 control queue；
- UART1 高速 RX，不影响 UART0 SN-3001 命令；
- UART 高负载不影响 SPI/I2C control command 入队；
- SPI transaction 超时不阻塞 UART/I2C worker；
- I2C NACK/超时不阻塞 UART/SPI worker；
- 某一 controller suspend/rebuild 不暂停其他无关 controller。

### control/sample 隔离

- sample queue 满时，control command 仍有保留容量；
- control command 按定义优先，但 sample 不永久饥饿；
- 重复采样在本 controller 高水位时按策略跳过并计数；
- control queue 满时快速返回明确拒绝，不无限阻塞；
- 不同 queue depth 使用各自真实容量计算压力；
- queue high-water、skip、reject、timeout 指标准确。

### report 隔离

- telemetry report queue 满时 ChannelCmdV2 ACK/Final 仍可发送；
- UART/SPI/I2C command task 产生的普通 WriteRsp 进入独立 control-response queue，
  queue 满时不允许同步调用 transport callback；
- ConfigResult、StatusReport、OTA 状态和关键告警有保留容量；
- publisher 卡顿时总线 worker 不被 transport 同步阻塞；
- 断网期间内存保持有界；
- 重连后不重复发布已确认的控制 Final，不破坏 replay 语义；
- telemetry 丢弃顺序和 discontinuity 可解释。

## 5.7 DMA 配置和能力

### 通用语义

- field 缺失走兼容默认值；
- `dma_enabled=false` 明确不申请 DMA；
- `dma_enabled=true` 必须获得兼容 DMA，否则配置整体拒绝；
- requested/allocated/actual driver/ResourceReport 四者一致；
- 配置从 false→true、true→false 和 controller 交换均正确释放/重分配；
- 分配失败后原 DMA pool 和原 Channel 工作状态恢复；
- 重启后实际 DMA 状态与持久 manifest 一致。

实际观测结果：

1. MQTT 控制消息确实到达 C6，控制台出现 `Received message type=0x04`；因此节点、

3. 修复内容：状态任务栈提高到 6144 words；publisher queue-set 改为 1 s 有界等待并
   周期喂狗；UART BREAK/奇偶/帧错误不再直接 flush 整个输入环，而是先排空已到达数据，

4. 修复后 C6/S3 均重新构建：C6 应用镜像 1,406,032 B，SHA256

   1,224,992 B，SHA256 `3134fe7ad2b2958e9f29358673d8f83cca81ccd97a6d02e723458939a40ed616`。
   Host CTest 20/20 通过。C6 只写入应用分区 `0x10000`，未擦除 NVS。

6. 1 Mbps 物理全流程（`/tmp/c6-full-1m-fixed.json`）的配置切换、DMA 分配、10 帧、

   5260 B 总量虽闭合，CRC 不一致（非 DMA `af4e9bc1`、DMA `39ff78d7`），属于当前
   CP2102/接线端的物理链路错误，不能记为 1 Mbps 无损通过。对照同一设备 115200 完整

7. 测试结束已发送原始 `v2-59739be4` Manifest；ConfigResult/ResourceReport 恢复成功。

   处于空配置安全状态。当前实机仅连接 UART0 模拟器，UART1/SN-3001、SPI/I2C 和断网
   恢复未由这两个 tty 设备覆盖，不能从本轮结果推导其通过。

此前的旧固件串口脚本曾完成 PTY smoke 和发送端 CRC 计算，但由于设备当时没有活动
UART Channel，未观察到 UART0 RX hit；那次结果同样保持为 inconclusive，不计入通过。

### UART

- UART0 和 UART1 申请 DMA 使用同一 planner 路径；
- 唯一 UART DMA 资源已占用时，第二个强制 DMA 请求被预检拒绝；
- UART0/UART1 交换 lease 后 DMA 权限不会跟随固定编号泄漏；
- DMA 开/关不改变 UART framing、校验位、停止位、地址或 parser 结果；
- DMA 开启和关闭分别完成 1 Mbps 与 SN-3001 并行矩阵。

### SPI

- DMA false 映射为实际 disabled，true 映射为有效 DMA allocation；
- 同一共享 SPI bus 的多个 CS 对 DMA 属性要求一致；
- 共享设备出现冲突 DMA 要求时预检拒绝；
- DMA 开/关下相同设备寄存器读取结果一致；
- 大于非 DMA 临时缓冲上限的 transaction 行为明确；
- SPI bus remove/add 和 DMA pool 回收正确。

### I2C

- DMA 配置不得改变 write+read 的 repeated START/STOP 语义；
- 当前目标不支持 I2C DMA 时，显式 true 在预检阶段拒绝；
- false 或兼容缺省配置继续使用非 DMA 路径；
- 在判断 controller 数量不足前先正确识别可共享的既有 I2C bus；
- 同总线多地址设备可工作，地址冲突或引脚/速率冲突被拒绝。

## 7. 故障注入方案

## 7.1 配置与资源故障

- planner 资源不足；
- DMA pool 分配失败；
- queue/task/block pool 创建失败；
- driver install、start、suspend、delete 任一步失败；
- ResourceReport 发布失败；
- apply 后 commit 前重启；
- 高频重复 manifest、乱序 epoch 和重复 ConfigChange；
- 旧 generation 事件在新 driver 启动后到达。

判定：不存在半配置；失败原因明确；旧配置能继续工作或节点进入明确安全状态；下一次合法 manifest 可恢复。

## 7.2 UART 故障

- FIFO overflow、driver ring buffer full；
- parity/frame/break 错误；
- 响应分片、粘连、少一字节、多余尾随数据；
- 错 CRC、错地址、迟到响应；
- response 到达时触发重配置；
- 连续输入期间 publisher 停顿；
- USB 串口发送端突然断开和恢复；
- SN-3001 断电、重新上电和速率不匹配。

判定：错误可观测；不把错误数据报告为成功；无跨 Channel 错配；恢复后无需整机刷写即可继续工作。

## 7.3 SPI/I2C 故障

- SPI 无响应、非法 transaction 长度、CS 配置错误；
- SPI 共享设备中的一个故障；
- I2C NACK、timeout、设备拔出；
- I2C bus busy/卡低（具备安全 fixture 时）；
- 故障期间切换 manifest；
- UART 高压同时注入 SPI/I2C 故障。

判定：故障限定在所属 controller/Channel；其他总线继续工作；队列、driver 和 DMA 可恢复。

## 7.4 网络与服务故障

- MQTT 断开 10 秒、60 秒和超过 telemetry 缓冲能力的时间；
- broker 重启；
- Wi-Fi 重连；
- 后端短时不可用或重启；
- publish 延迟、失败和重试；
- 前端 WebSocket 断开后重连。

判定：内存有界；critical report 处理符合定义；发生 telemetry 丢弃时 sequence/discontinuity 可解释；重连后无命令重复执行。

## 7.5 压力下重配置和重启

- 1 Mbps 输入时禁用/启用高速 UART Channel；
- 1 Mbps 输入时交换 UART0/UART1 lease；
- SN-3001 命令执行前、执行中、Final 前触发配置变更；
- SPI/I2C 周期采样期间应用新 manifest；
- 全总线并行时软重启和硬复位；
- OTA 重启后重新分配资源。

判定：无 watchdog、panic、死锁和资源泄漏；命令结果不出现错误成功；重启后配置最终 `in_sync`。

## 8. 性能与长稳验证

## 8.1 1 Mbps 核心场景

1 Mbps、8N1 的理论有效 payload 约为 100 KB/s。测试数据必须带递增序号和 CRC，不能只比较总字节数。

本轮提供不改设备状态的串口验证程序
`scripts/c6_uart0_serial_validation.py`：`ttyUSB0` 作为 C6 UART0 外部设备，
`ttyACM0` 只读采集 C6 控制台；程序可执行固定间隔分帧、连续输入、外设回显/固定回帧，
并统计 C6 控制台中的 RX overflow、UART error、RX timeout 和 event/report 线索。它不刷写固件、
不下发 ConfigManifest，也不把 host `write()` 成功误判为固件无损接收；无 MQTT/DataReport 或设备
资源计数时，结果只能作为串口层观察或 `inconclusive`。

示例：

```bash
python3 scripts/c6_uart0_serial_validation.py --mode all \
  --baud 1000000 --duration 30 --idle-ms 50 --echo \
  --json /tmp/c6-uart0-serial.json
```

2026-07-20 实际串口观察（不刷写、不改配置）：`ttyUSB0` 和 `ttyACM0` 均可打开；
10 个 512B payload frame（含 framing/CRC 共 5260B，CRC32 `07d4e5b2`）已发送到
`ttyUSB0`，但 C6 控制台仅报告旧固件格式 `RX_TASK: Stats: reads=2001 hits=0`，没有
UART0 外设回帧、RX hit、overflow、UART error 或 timeout。因此该结果为
`inconclusive`，不是 1 Mbps 无损通过证据。当前日志字段与本分支 `events/completions`
实现不一致，说明连接中的 C6 尚未运行本分支构建；在用户不允许刷写/改配置的约束下，
不继续扩大压力，也不将该结果计入 P6 门禁。

修复后本分支已在同一 C6 上完成 MQTT+tty 全流程回归：115200 baud 的非 DMA/DMA
切换和 5260 B CRC 闭合通过；1 Mbps 的 ConfigResult、DMA allocation、WriteRsp、
恢复和总字节数通过，但 CP2102 产生 UART_BREAK 并污染 CRC，见 9.1，暂不计入
“1 Mbps 无损”门禁。

必测：

```text
A：UART0 持续 1 Mbps 输入，UART1 同时操作 SN-3001 9600
B：UART1 持续 1 Mbps 输入，UART0 同时操作 SN-3001 9600
```

每组至少包含：

- 10 分钟功能压力，用于快速门禁；
- 1 小时稳定性测试，用于阶段 P6；
- 发布候选版本 4～24 小时长稳；
- DMA 关闭和能力允许的 DMA 开启；
- MQTT 正常、短时断开、恢复；
- SPI/I2C 周期采样并行；
- SN-3001 周期读取和人工控制混合。

发送器记录 `tx_bytes`、chunk 大小、发送时间和 CRC；固件/后端记录 `rx_bytes`、`committed_bytes`、sequence 和 discontinuity。三方数据用于闭合核对。

## 8.2 建议性能门禁

以下为开发阶段的建议门禁，P0 冻结时根据基线确认最终数值：

| 指标 | 建议门禁 |
|---|---|
| 正常联网持续输入 | 无未解释字节丢失、重复或 sequence gap |
| UART FIFO/ring/block overflow | 正常容量设计场景为 0；故障注入时必须准确计数 |
| SN-3001 命令 | 无超时；成功率 100%；p95 不劣于基线 20% 以上 |
| UART0/UART1 对称性 | 吞吐和控制延迟差异不超过基线确认阈值，功能结论一致 |
| SPI/I2C 周期采样 | 无新增 timeout/CRC/parser 错误，延迟不劣于基线 20% 以上 |
| critical report | telemetry 满载下不丢，p95 不劣于基线确认阈值 |
| 队列与内存 | 无无界增长；稳态 high-water 低于容量；保留 critical 容量 |
| ESP32 稳定性 | 无 watchdog、panic、异常重启和持续 heap 下降 |
| 配置切换 | 成功时状态一致；失败时原功能可恢复，无资源泄漏 |

“无未解释丢失”不表示无限离线缓存。达到已定义容量而丢弃 telemetry 时，必须有准确计数、sequence gap 和 discontinuity，且不能影响 critical report。

## 8.3 内存与实时性

每轮压力测试采集：

- 启动后、开始压力、峰值、结束、恢复后 free/minimum heap；
- controller worker、RX event task、publisher、scheduler 的栈高水位；
- block pool 和所有队列当前值/峰值；
- 每秒 UART RX 和 publish 吞吐；
- control command 排队、总执行、ACK 和 Final 延迟；
- CPU 高负载时的 watchdog 和任务饥饿情况。

数值门禁以 P0 基线和最终静态内存预算为准。不能只验证“未崩溃”，还要证明资源有余量且长时间不单调恶化。

## 9. 分阶段测试门禁

| 阶段 | 新增测试 | 必须回归 | 进入下一阶段条件 |
|---|---|---|---|
| P0 | manifest/DMA 字段、资源协议、兼容解析 | Go、前端配置、现有 host tests、双目标构建 | wire 语义一致且运行行为未改变 |
| P1 | planner、lease、冲突、确定性、事务回滚 | 配置同步、GPIO/PWM、UART/SPI/I2C 基本读写 | 动态分配和失败恢复均通过 |
| P2 | UART event、lifecycle、generation、错误事件 | UART0/UART1、SN-3001、模拟协议、配置切换 | 行为等价且无轮询依赖 |
| P3 | 自动边界、block pool、descriptor、report 隔离 | DataReport、终端、ChannelCmdV2、MQTT 重连 | 持续输入与控制结果均正确 |
| P4 | per-controller 背压、control/sample 优先级 | scheduler、全总线并行、后端/前端实时数据 | 拥塞不跨 controller 扩散 |
| P5 | UART/SPI/I2C DMA 能力和语义 | SPI/I2C 全回归、ResourceReport、配置回滚 | requested/allocated/actual 一致 |
| P6 | 1 Mbps 对称、故障注入、长稳 | 全量自动化、全功能实机、E2E | 所有性能和稳定性门禁通过 |
| P7 | 灰度、升级、回滚演练 | 一个完整业务周期 | 灰度无回滚触发项 |

阶段内发现缺陷后，修复必须重新执行：缺陷复现用例、直接影响集、共享基础设施回归和该阶段门禁。不能只重跑失败的单个用例。

## 11. 用例与证据管理

### 11.1 用例编号

建议按领域编号：

- `PLAN-*`：planner/lease；
- `UART-EVT-*`：UART event；
- `UART-BND-*`：自动边界；
- `QUEUE-*`：队列/背压；
- `DMA-*`：DMA；
- `SPI-*`、`I2C-*`：总线；
- `CFG-*`：配置事务；
- `CMD-*`：ChannelCmdV2；
- `REG-*`：既有功能回归；
- `PERF-*`：性能和长稳；
- `FAIL-*`：故障注入；
- `E2E-*`：浏览器/实机闭环。

### 11.2 每轮结果必须包含

- 分支、commit、dirty 状态；
- 固件 hash、构建 profile、烧录设备；
- manifest ID/epoch 和完整资源快照；
- 物理接线与 UART0/UART1 lease；
- 测试起止时间、持续时间和工具版本；
- 自动化命令与退出码；
- 发送/接收/提交/发布字节闭合数据；
- sequence、CRC、timeout、overflow、drop；
- queue/pool high-water、heap、stack；
- SN-3001/SPI/I2C 成功率和延迟；
- 故障注入时间线和恢复时间；
- 失败日志、复现步骤、缺陷编号；
- 测试后恢复和最终读回证据。

### 11.3 证据目录建议

每个阶段在 `docs/验证/` 提交摘要报告；体积较大的串口原始数据、pcap、构建产物和完整日志存放在外部测试制品库，在摘要中记录校验值和链接，不直接提交仓库。

## 12. 准入、完成与发布标准

### 12.1 阶段准入

- 上一阶段门禁通过；
- 变更设计、影响文件和测试映射已评审；
- 测试节点、仪器、账号和恢复手段可用；
- 基线数据完整；
- 会修改设备状态的用例已明确恢复步骤。

### 12.2 功能完成标准

必须全部满足：

1. 新增需求 R01～R12 均有自动化和适用的实机证据；
2. UART0/UART1 交换矩阵全部通过；
3. UART 接收不依赖固定 5 ms 数据轮询；
4. 通用接收流程同时正确处理 pending response 和无 pending 输入，不存在用户模式开关；
5. 独立队列和 critical report 保留容量经压力证明有效；
6. DMA requested、allocated、driver actual、ResourceReport 一致；
7. SPI/I2C 协议和现有数据结果无回归；
8. 配置失败可恢复旧 lease/driver/DMA，并能完成真实读写；
9. 后端、前端、host tests、C6/S3 构建和实机回归均通过；
10. 所有已知丢弃都有明确容量原因、计数和 discontinuity，没有未解释数据缺口。

### 12.3 发布阻断条件

出现任一项不得发布：

- UART0/UART1 交换后行为不同或存在固定编号业务分支；
- ResourceReport 与实际 lease/DMA 不一致；
- 响应串到错误 Channel 或错误 command；
- ChannelCmdV2 重复执行、Final 丢失或错误成功；
- 正常容量范围内出现未解释 sequence gap；
- telemetry 压力导致 critical report 丢失；
- SPI/I2C 新增协议错误或采样明显退化；
- 配置失败无法恢复原工作状态；
- heap 持续下降、block 泄漏、task 泄漏、watchdog 或 panic；
- 真实浏览器闭环未执行且没有被明确标记为未完成；
- SN-3001 或 manifest 未恢复到测试前状态。

## 13. 测试后恢复清单

每次实机测试结束后执行并记录：

1. SN-3001 地址恢复为 1；
2. SN-3001 波特率恢复为 4800；
3. 灵敏度等可写参数恢复为测试前读值；
4. 临时高速 UART Channel 禁用或恢复测试前配置；
5. 原始 manifest 重新应用并记录 manifest ID；
6. 数据库 `config_sync_state=in_sync`；
7. ResourceReport 与原始 lease/引脚/DMA 一致；
8. ESP32 使用最终配置真实读回 SN-3001；
9. SPI/I2C 临时接线和配置恢复；
10. 开发环境中的高风险操作开关恢复默认值；
11. 记录无法恢复的任何差异并停止后续共享环境测试。

## 14. 首轮执行顺序

开发开始后的首轮验证按以下顺序执行：

1. 冻结基线并完成全量自动化；
2. 为 planner、lease、UART event 和自动边界先写 host tests；
3. 完成 P0/P1 后验证配置兼容和动态 lease，不引入高负载；
4. 完成 P2 后做 UART0/UART1 行为等价和 SN-3001 基本回归；
5. 完成 P3/P4 后做 1 Mbps、队列背压、MQTT 断连和全总线并行；
6. 完成 P5 后执行 DMA 开关、SPI/I2C 完整矩阵；
7. 执行后端、前端、浏览器和所有受影响既有功能回归；
8. 执行 1 小时与发布候选长稳；
9. 演练配置失败、升级和回滚；
10. 输出 P6 验证报告，评审通过后才进入灰度。

该顺序不允许跳过“旧功能回归”直接以 1 Mbps 压测结果作为完成证据。
