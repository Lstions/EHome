### 1.2 生产实况对齐（`\d unified_data_202611`）

生产索引集合（`.tmp-telemetry/regression/sql/prod_probe.sql`）：

```
 unified_data_pkey               | CREATE UNIQUE INDEX ... ON ONLY public.unified_data USING btree (id, "timestamp")
 unified_data_device_id_idx      | ... btree (device_id)
 unified_data_sensor_name_idx    | ... btree (sensor_name)
```

**与代码模板的差异（重要）**：代码模板 `partition_mgr.go:602-621` 现有 **6 条** unified_data 索引模板，生产只有 **4 条**——缺 `device_sensor_ts_idx` 与 `device_ts_idx`（2026-10-24/25 的 F-10 修复）。

**原因**：生产 backend 镜像构建于 2026-10-24（`docker ps` 显示 `ehome-new:sg-11f4cfd7` / 2026-10-24 13:38），而 `ensurePartitionParentIndexes` 的补齐逻辑是 2026-10-25 才加入的（`partition_mgr.go:224-226` 注释明确写了这个坑）。
**⇒ 方案 §7「下一个镜像启动会补建 F-10 复合索引」是真实存在的**，本报告 §8.4 量化了它的代价（+4.51 GB）。

## 4. §1.3「51.6% 的行与前一条完全相同」—— ❌ 证伪


### 4.1 四种口径全部算过（11-04 单日与全窗口各一组）

| 口径 | 11-04 单日 | 全窗口（5.1 天） | 方案声称 |
|---|---:|---:|---:|
| (a) 行级：同 `(device, sensor)` 相邻行值相同 | **76.70%** | 70.98% | — |
| (b) 帧级：整帧（字段集合 + 全部值）与上一帧完全相同 | **4.34%** | 4.37% | — |
| (c) 按 `id`（真实写入顺序）相邻行**完全元组**相同 | — | **0.00%** | — |
| (d) 按 `id` 序只比 `value`（忽略字段名） | — | 7.37% | — |
| (e) 帧级 + **按 slot 分组**（同 `(device, 字段数)` 才比较上一帧） | 14.11% | — | — |
| | | | **51.6%** |

**没有一种口径能得到 51.6%**。最接近的是 (a) 的 76.70%（高 25.2 个百分点），其次是 (e) 的 14.11%（低 37.5 个百分点）、(b) 的 4.34%（低 47.3 个百分点）。

(e) 的逐 slot 明细（可解释为什么 device15 的"整帧比较"不可用）：

| device | 字段数 | 帧数 | 与同 slot 上一帧相同 | 占比 |
|---|---:|---:|---:|---:|
| 14 | 29 | 86,342 | 4,554 | 5.27% |
| 15 | 2 | 8,635 | 358 | 4.15% |
| 15 | 3 | 17,269 | 3,273 | 18.95% |
| 15 | 4 | 1,439 | 1,424 | **98.96%** |
| 15 | 5 | 17,269 | 10 | 0.06% |
| 15 | 9 | 2,878 | 1,847 | 64.18% |
| 15 | 14 | 8,635 | 8,630 | **99.94%** |

> ⚠️ 这张表暴露了 device15 的一个危险信号：**14 字段（告警位图）帧 99.94% 与上一帧相同、4 字段（累计电量）帧 98.96% 相同**，而 **5 字段帧只有 0.06% 相同**。⇒ L1 对 device15 的收益**几乎全部来自这两类"慢变帧"**，方案 §3.2 的 36.9% 跳过率成立，但实现时必须**按 slot 独立维护"上次落库值"**，否则混算会失真。

**穷举说明**：除上表 5 种口径外，还试过「只看 device14」（76.64%）、「分母去掉每字段首行」（76.70%）、「全窗口跨天」（70.98%）、「`distinct(dev,sensor,value)/rows`」（0.45%）等，**均无法得到 51.6%**。
⚠️ 本批判定**不构成对方案作者的指控**：51.6% 很可能来自另一个数据窗口（例如含已停写 device 2/12/13 的 10 月数据，它们的值完全不变）或另一套去重口径。**建议作者补充原始 SQL 与数据窗口**，而不是直接删除该数字。

### 4.2 为什么 (c) 是 0.00%

`consumers_heavy.go:355-366` 每帧 `Create(&records)` **一次性批量插**该帧的全部字段行（device14 = 29 行）。因此：

- **帧内相邻**：`(device_id, timestamp)` 相同，但 `sensor_name` 必然不同（29 个不同字段）+ `value` 不同 ⇒ 元组不等；
- **帧间相邻**：`timestamp` 不同 ⇒ 元组不等。

⇒ "相邻行完全相同"在 id 序下**恒为假**，与观测到的 0.00% 一致。
（说明：本地 `bench_a` 的 id 序来自 CSV，已按 `device_id, timestamp, sensor_name` 排序；与生产"帧内按解析顺序"不同，但**帧内 sensor_name 必不相同**这一点两者一致，结论不受影响。）

### 4.3 放大倍数（方案 §1.3「300–400 倍」）

```
每帧现状字节 = 29 行 × 175.9 B = 5,101 B
每帧有效信息 = 11.62 B（§6 实测平均 payload）
放大 = 5,101 / 11.62 = 439 倍
```
⚠️ **实测 439 倍，略超方案给的上界 400**。结论方向正确，区间应改为「400–450 倍」。

⚠️ **额外发现（方案未覆盖）**：device_id=0 的 159,745 行里，除了 142,467（device 14/15）还有 **17,278 行属于 device 16**：

### 5.1 语义实现（关键，否则结论完全不同）

方案 §3.1 写成「对每台设备、**每个字段**维护最后已落库值 + 落库时间」，而 §3.2 的结果表是**帧级**。正确语义：

```
一帧写 <=> (该帧至少一个字段 != 该字段上次落库值)   -- §3.1 变化
       OR (距上次落库 >= 60 s)                      -- 心跳
```

**实现要点**：`该字段上次落库值` **等于** `该字段上一次出现的值`（被跳过的帧其值不变），因此用逐字段 `lag(value)` 精确实现；心跳用**闭式解**（分段起点 = 本行之前最后一个变化帧的时刻，写入数 = `count(distinct floor((ts - seg_start)/60))`），与递归判定数学等价、但快 3 个数量级。

> ⚠️ **反面结果（重要）**：如果按「整帧 vs 上一帧」直接比较（`.tmp-telemetry/regression/sql/70_l1_sim.sql`），device15 跳过率会从 39% 掉到 **4.22%**、合计从 18.17% 掉到 **4.37%**——因为 device15 的 7 种帧类型交替出现，**字段集合差异会被误判成"值变化"**。方案若按整帧比较实现，收益会大幅缩水。这条应写进实现约束。

### 11.2 device 16（光学雨量计）解析失败 —— 独立取证

§11 第 6 条的深挖已单独成文：[遥测存储-雨量计device16解析失败取证-2026-11-06.md](遥测存储-雨量计device16解析失败取证-2026-11-06.md)。

**结论摘要**（三句话）：

1. **不是驱动 bug**——`SN3001RainDriver.ParseData`（`backend/internal/drivers/builtin.go:363-386`）对协议文档的黄金帧（`01 03 02 00 0A 38 43`）逐条判据全部通过；
2. **不是"解析失败"**——device16 的 323,900 行 `device_data` 里 **323,828 行（99.98%）`error_code=1` 且 `raw=""`**：固件根本没收到任何字节（RX 超时），唯一一条 `error_code=0` 的 `raw=1e07073ee6ffff` 也不是合法 Modbus 响应（首字节 0x1e≠0x01，CRC 不自洽）；
3. **所以 unified_data 0 行是正确行为**——后端连解析的机会都没有（`ShouldParse()` 要求 `ErrorCode==0 && len(RawData)>0`，见 `backend/internal/databus/bus.go:33-35`）。

**真实代价**：0.28 GB/月 的 `device_data` 噪音（17,278 行/天 × 573.8 B/行），占现状月增量的 **1.5%**；若修复后按驱动实际产出 1 字段估算，会额外增加 **0.085 GB/月** 的 `unified_data`。
**真问题不是存储**，而是「一台 enabled 的现役设备静默 18.8 天、0 条告警」（`alert_rules` 表 0 行、`notifications` 0 行、`node_logs` 该节点 0 行）。

## 12. 局限性

1. **本地库只有一个 202611 分区有数据**（14.3 M 行 ≈ 5.1 天）。生产 30 天查询跨 202610（56.2 M 行）+ 202611，**本地无法完全复现 30 天窗口的真实代价**，§7.1 的 30 天数字来自生产只读实测。
2. **PG 配置**：本地与生产均为默认 `shared_buffers=128MB / work_mem=4MB / max_parallel_workers_per_gather=2`（已核对），版本同为 18.6，硬件不同（生产为 PVE VM 50 G 盘，本地 12 核/30 G）。
3. **行成本受 REINDEX/VACUUM 状态影响大**（154.8 ~ 177.0 B 同数据同 schema），§3.2 给了两档实测值，生产真值 175.9 B 落在中间。
4. **51.6% 的原始数据窗口未知**：本次只有 11 月数据，若方案作者用的是 10 月（含 device 2/12/13 等已停写设备）数据，口径可能不同 —— 但即使如此，76.7% 与 4.3% 都无法凑出 51.6%，仍建议作者给出原始 SQL。
5. **未验证 `telemetry_frame` 双写路径的真实写入吞吐**：本报告只在 SQL 层模拟了表结构与 payload 长度，未跑 `consumers_heavy` 的双写分支（该项属 task-3 L2 实现范围）。
6. **未验证 rollup（§5.2）**：L3 的宽行 rollup 只在 §3.2 里测了行成本（328.7 B/行，与方案 327.3 吻合），**未实现旁路聚合、也未测长窗读加速**。
7. **未验证量化编解码往返**：§4.3 的位宽表只用于算 payload 字节数，**未跑「值 → 量化 → 还原」的误差验证**（这项在 task-3 的 Go 测试里）。
8. **本地 `bench_a` 的 `id` 序来自 CSV 排序**（`device_id, timestamp, sensor_name`），与生产真实写入序（帧内按解析顺序、帧间按到达顺序）不同。因此 §4.1 的 (c)(d) 两种"id 序"口径只能说明"帧内 sensor_name 必不相同"这一结构事实，**不能作为生产 id 序的精确复现**；而 (a)(b)(e) 三种口径与 id 序无关，结论可靠。
