## 1. 前置分析（全库实测，不是估算）

```
总行数      72,695,394    unified_data 15 GB
总帧数       3,419,991    按 (device_id, timestamp) 去重
时间跨度     2026-10-02 ~ 2026-11-07（36 天）
设备数       5（14 / 15 / 2 / 12 / 13）
sensor_name  110 个
```

### 1.1 无损性判定（决定性证据）

对全库每一行按 `spec.go` 的 (Min, Step, Bits) 算「非整数码点」与「越界」：

| 字段族 | 非整数码点 | 越界 |
|---|---:|---:|
| cell_voltage_* | **0** | 0 |
| temperature_* / *_temp | **0** | 0 |
| current / total_voltage / rsoc / cycle_count / fet_status / protection_status | **0** | 0 |
| *_frequency / *_energy / alarm_* / fan*_* | **0** | 0 |
| Fallback 字段（19 个未登记字段） | **0** | 0 |
| **battery_voltage** | **0** | **5** ⚠ |

**唯一问题**：`battery_voltage` 有 5 行 = 1e12，集中在 2026-10-19 08:53~08:55
（逆变器解析器一次已知缺陷，历史坏数据）。spec 量程 0~204.7 V ⇒ 会被 clamp。

**处置**：编码时预判 clamp，命中则把原始值序列化进该帧的 `raw` 列并计数。
常规帧 raw 留 NULL（否则 raw 平均 78 B 会让 463 MB 涨到几十 GB）。

### 1.2 slot 字典规模

| 设备 | 帧数 | 不同字段集合数 |
|---|---:|---:|
| 14 | 2,205,222 | **7,351** |
| 15 | 1,098,090 | 116 |
| 2 / 12 / 13 | 116,596 | 1~2 |

device14 的 7,351 种按天拆开：2026-10-06 有 7 帧异形（早期解析器遗留），
10-07~11-05 全为 0，**11-06 起出现大量异形 = L1 上线后「值不变跳过」的正常结果**。

**生产实测 slot 数 = 13**（远低于契约预估的 7,400）——
因为 L1 后的稀疏帧在 device14 上仍命中同一个 29 字段 slot（`Invalid` 掩码表达缺失），
不会为每种字段子集建新 slot。契约的 7,400 是保守上界。

## 2. 实施（三个任务，8 个提交）

### T1 回填引擎（`backend/internal/backfill/`，9 个文件）

- 状态表 `telemetry_backfill_progress`：分区粒度 + watermark 断点 + frames_done/rows_done
- 按 `(device_id, timestamp)` 取整帧（逐行处理是 68 万次往返）
- **关键帧策略**：按设备分组 + 每 60s `Reset()`
  （`telemetry.Encoder` 原本靠时间间隙判关键帧，1 Hz 密集数据上**永不触发** ——
  直接用会让 device14 一个月 220 万帧只有第一帧是关键帧，坏一帧整链不可解）
- **源码门禁** `TestBackfillNeverDeletesSourceData`：禁止 DROP/DELETE/TRUNCATE 源数据
  （词边界正则，避免 `truncateAtCleanBoundary` 被误判）
- 超量程原文进 `raw` 列

### T2 进度接口 + 前端

- `GET /api/v1/system/backfill`（免鉴权，8 个 key 恒定出现、无 omitempty、errors 恒 `[]`）
- ETA 用**行速率**而非帧速率（device14 一帧 29 字段 vs device13 一帧 1 字段，差 54 倍）
- 前端 Monitor 页卡片 + 5s 链式轮询 + **定时器泄漏门禁**（7 条用例）

### T3 保留期支持永久保留

修了一个**反向 bug**：`days <= 0` 原本兜底成 1 天 ⇒ `EHOME_DATA_RETENTION_DAYS=0`
反而按 1 天删，且不报错、数据一天天变少。

现在 `0` = 永久：跳过分区 DROP + 行级 DELETE，但 **8 个旁路清理器照跑**
（通知/审计/事件等元数据表没有独立 goroutine，整体 return 会把「保留数据」变成「全库膨胀」）。

## 3. 两个 P0（都是队友发现，都不是实现者的自述）

### 3.1 回填游标依赖时间精度 → PG 上无限重复处理同一批

**现象**：回填 3 分钟仍 running、percent 卡 20.5%，但 frames_done 涨到 112,520（源数据 6,000 帧）。
不报错、不失败，表现为「回填永不完成 + 一个核 100% + 磁盘 IO 持续」。

**根因**（SQL 验证）：

```sql
SELECT (timestamptz x + interval '0.000000001 second') = timestamptz x;  -- t（加 1ns 等于没加）
SELECT (timestamptz x + interval '0.000001 second')    = timestamptz x;  -- f
```

PG `timestamptz` 精度是微秒 ⇒ `WHERE timestamp >= from` 每轮取回同一批。

**量化证据**：`rows_done 1,219,176 ÷ 1200 = 1015.98`；`frames_done 101,598 ÷ 100 = 1015.98`
—— 两个商完全相等。

**为什么 142,467 帧真实数据对拍全绿却漏了**：对拍跑在 SQLite 上（纳秒精度，`Add(1ns)` 真的前进）。

**修复**：游标改为 `(timestamp, device_id)` 复合键

```sql
WHERE (timestamp > ? OR (timestamp = ? AND device_id > ?))
```

- 彻底不依赖时间精度
- 天然处理「同 ts 多设备」⇒ 删掉 `truncateAtCleanBoundary` + 前瞻取 1 条那套补丁逻辑
- 上界方向相反：原 `hi.Add(1ns)` 在 PG 上也等于没加 ⇒ **会漏最后一行**（数据丢失，比重复更严重）。
  改为 `partition.hiInclusive` 标志 + `upperOp()`，不做任何时间加法

**变异验证（两次，都真做）**：
1. 删掉 device_id 分量 ⇒ `TestPGCursorSameTimestampMultipleDevices` 红：「帧数 = 20, want 30」
2. 整体改回 `+1ns` ⇒ `TestPGCursorTerminates` 红：63.82s 撞用例自身 60s ctx 超时，复刻生产症状

### 3.2 `gow.sh` 不转发 `EHOME_*` ⇒ 全仓 28 个 PG 用例从未在本地真跑过

`EHOME_TEST_DB=postgres gow.sh test ...` 里的 PG 用例全部被 `requirePostgres(t)` **静默 Skip**，
包级仍是 `ok`。这是最坏的一类假绿：**用例根本没执行，但看起来像通过**，不加 `-v` 完全看不出来。

修复：`scripts/gow.sh` 自动收集 shell 里全部 `EHOME_*` 注入容器。

**影响范围收窄**（重要，决定返工量）：
- CI 的 `backend-integration` job 直连 `go test` + 显式 env，**不经 gow.sh** ⇒ 不受影响
- Makefile `test-integration` 同样直连 ⇒ 不受影响
- **只有走 gow.sh 的本地/teammate 手工验证受影响**

⇒ 准确表述是「**凡是自述『我用 gow.sh 跑过 PG 用例』的都不成立**」，而非「过去几个月所有 PG 结论都不可信」。

修好之后真跑，露出 1 个真红：`TestPostgresDeviceScopedPlan`（见 §4.1）。

## 4. 「假绿」四连 —— 本月的核心教训

| # | 假绿形态 | 抓法 |
|---|---|---|
| 1 | **L3 rollup 列漂移**：SQLite 走 AutoMigrate（有 updated_at），PG 走裸 DDL（没有）⇒ 单测全绿、生产每分钟报 42703 | 源码门禁 + PG 端到端 + 运行期自动补列 |
| 2 | **`+1ns` 游标**：SQLite 纳秒能前进，PG 微秒原地踏步 ⇒ 146 万帧对拍全绿、生产永不完成 | 复合游标 + 真 PG 用例（变异验证证明有鉴别力） |
| 3 | **`TestPostgresDeviceScopedPlan` 测错形状**：断言生产形状，却跑在 AutoMigrate 形状上 | 测试 schema 显式对齐生产 DDL + 3 个变异体 |
| 4 | **`gow.sh` 不转发 EHOME_***：PG 用例静默 Skip，包级 `ok` | 修转发层 + 全仓普查（28 个用例） |

**共同形状：两条路径各自自洽，交叉点上从没有过用例。**
- #1/#3：SQLite/AutoMigrate 路径 vs PG/裸 DDL 路径
- #2：SQLite 纳秒 vs PG 微秒
- #4：显式 env 路径 vs docker 转发路径

### 4.1 `TestPostgresDeviceScopedPlan` 的修复

只用「DROP sensor_name 索引」不够：avg 模式绿了但 change 模式仍红。
因为 AutoMigrate 形状比生产**还少两条复合索引**：

| 索引 | AutoMigrate | 生产 DDL |
|---|---|---|
| sensor_name 单列 | **有（多）** | 无（刻意不建） |
| (device_id, sensor_name, timestamp) | 无（缺） | 有 |
| (device_id, timestamp) | 无（缺） | 有 |

change 模式带 `ORDER BY timestamp`，在「只有单列索引」的形状下 planner 选 timestamp 索引
把 device_id 降级成 Filter —— **是合理的代价选择，不是缺陷**。

修复：`alignUnifiedDataSchemaToProduction()`（删多的 + 补缺的 + 自检），
断言口径从「某一条 device_id 前导索引」放宽到「任意一条」（生产有 3 条，planner 按查询形态各选其一；
钉死单条 = 把用例绑死 PG 代价模型细节）。

变异验证 3 个，其中第 3 个（删掉自检只留计划断言）证明**计划断言本身有鉴别力**。

### 5.4 ETA 偏高（已知，可接受）

`eta_seconds` 在 3,283s → 9,283s 之间**递增**，而实际按帧速率算剩余只需 ~2,000s。
原因是 ETA 用「日进度百分比 × 行速率」反推，而**行数在分区内不是均匀分布**的
（October 2.2M 帧 vs November 1.1M 帧，但两者时间跨度相同）。

真实完成时间按帧速率估算 **~35 分钟**，ETA 显示会持续偏高 3~4 倍。
属 boot-api 在 R3 里已声明的限制（「跨分区切换时 ETA 可能偏差 2~3 倍，可接受量级」）。

## 6. ⚠ 「所有数据长期保留」的硬约束（必须裁决）

### 6.1 迁移解决的是「历史数据的存量」，不是「未来的增量」

| 表 | 日增（实测） | 受 L1/L2 影响 |
|---|---:|---|
| `telemetry_frame` | **17 MB** | 是（L2 编码后） |
| `unified_data`（L1 后） | **~40 MB** | 是 |
| **`device_data`** | **368 MB** | **否**（仍全量写原始 JSON） |

```
永久保留（含 device_data）: 稳态 425 MB/天 ⇒ 17 GB 可用只够 40 天
device_data 保留 90 天     : 稳态 148 MB/天 ⇒ 够 115 天
```

### 6.2 三个选项（需要用户拍板）

| 选项 | 5 年 device_data | 说明 |
|---|---:|---|
| A. 全量永久保留 | **~660 GB** | 50 GB 盘装不下，必须扩盘或外置存储 |
| B. 保留最近 90 天，更早按月归档压缩到冷存 | ~17 GB + 冷存 | 需做归档机制（**未实施**） |
| C. 迁移后 DROP 老 `device_data` | 4.36 GB → 0 | 帧表能还原物理量，但丢「原始总线字节」 |

**建议 B**：`device_data` 的独特价值是「原始总线帧」（排查解析问题），
帧表已能还原物理量。保留最近 90 天 + 更早归档即可。

### 6.3 老 `unified_data` 分区是否 DROP

回填完成后，老 `unified_data` 的 15 GB 就是**冗余副本**（帧表已无损覆盖）。
但按契约 §7 裁决 2，建议**先验证 1 周，再决定 DROP**。当前未 DROP。

## 7. 已知遗留

1. **`device_data` 归档未实施** —— 「长期保留」能否成立取决于它（§6.2 选项 B）。
2. **ETA 偏高 3~4 倍** —— 行数在分区内不均匀，属已知限制。
3. **`-tags=integration` 的 6 个用例本地不编译** —— 需在纪律文档里写明 gow.sh 用法。
4. **`internal/e2e` 22 个用例永不执行** —— 任何地方都没有入口，需单独立项。
5. **`testutil.reapStaleSchemas` 的 PID 命名空间问题** —— gow.sh 每次 `docker run` 是新 PID 命名空间，
   容器内 pid 恒两位数 ⇒ 两个 agent 同时跑 PG 用例会互相 DROP schema。**纪律：PG 用例必须串行跑**。
6. **回填 `RunOnce` 不可重入** —— 多实例部署需给状态表加租约列。
7. **帧表读路径未接入** —— 回填进去的数据目前没有任何读路径消费（与 L3 rollup 同状态）。
8. **`testutil.allModels` 不含帧表** —— 导致 4 份重复的建表 helper，是刻意设计的直接成本
   （帧表分区母表必须走 partition_mgr 裸 DDL，AutoMigrate 会建成普通表破坏分区）。

## 8. 独立复核（boot-api，非实现者自述）

复核在 `4216c368` 上重跑，5 项全部完成：

| # | 复核项 | 结论 |
|---|---|---|
| ① | 真 PG 用例（要求不 skip） | 3 条 PASS，**无 SKIP**（专门加 `grep -- '--- SKIP'` 判据） |
| ② | 变异验证（2 个变异体） | 都真红，且红的原因正是目标 bug |
| ③ | `-race` 全量（api/backfill/cmd-server） | 全绿，无 DATA RACE |
| ④ | 端到端 running 态复测 | **P0 确认修复**：6,000/6,000 帧、rows 72,000/72,000、state→done、percent→100 |
| ⑤ | 方言一致性对照 | **逐字节一致**（三层比：payload sha256 / 解码 %.17g 全精度值 / 五项计数） |

### 8.1 ② 变异验证的细节（两次独立复现同一 bug）

| 变异体 | md5 | 红的原因 |
|---|---|---|
| A：游标去掉 device_id 分量 | `06b4e950…` | `帧数 = 20, want 30`（丢了同 ts 的其它设备） |
| B：改回 `timestamp >=` 不带 device_id | `1bec0fb7…` | `context deadline exceeded`（无限重复处理同一批，63.82s） |

**B 的 md5 正好等于 boot-api 第一次抓到的中间态快照** —— 同一条 bug 的两次独立复现。

**变异验证本身也需要验**：第一版变异脚本用 `? = ?` 占位导致 PG 类型推断报错，
那是**假红**；重写成占位符与参数 1:1 才作数。教训：**变异体必须先能编译，且红的原因必须是目标 bug**。

### 8.2 ⑤ 方言对照的做法（三层，不是只比行数）

数据集：200 点，device {2,14,15}，每 7 点三设备共用同 ts，base `2026-10-31T23:59:30.123456Z`
（**跨月边界** + 微秒尾巴），batch=7 强制大量批边界。

```
两边各 1038 行指纹；diff 结果：✅ 两方言产出逐字节一致
FRAMES_DONE=258  ROWS_DONE=774  FRAME_ROWS=258  DECODED_POINTS=774
```

比的是：帧级 `(device_id, ts, seq, frame_kind, payload sha256)`
+ 解码级 `(device, ts, name, %.17g 全精度值)` + 计数级 5 项。

### 8.3 复核过程中发现的**假绿 #4 的第二次同形状复现**

boot-api 写方言对照探针时，输出路径变量用 `PARITY_OUT`（**无 `EHOME_` 前缀**）
⇒ gow.sh 不转发 ⇒ 用例 Skip ⇒ 包级 `ok`。

这是同一个坑的第二次出现：**「环境变量驱动的条件用例」在转发层缺失时静默变绿**。
处置：改名为 `EHOME_PARITY_OUT`，并**禁止 Skip**（不产出指纹就 Fatal）。

⇒ 结论：`gow.sh` 那个修复只解决了**症状**（转发 EHOME_*），
根因是「条件用例用 Skip 表达未执行」。任何新写的条件用例都应
**优先 Fatal 而不是 Skip**，除非确实允许该环境不跑。

第二个坑：指纹输出路径用宿主绝对路径，而 gow.sh 挂载点是 `/ws` ⇒ 容器内写不进去。
第一版 diff 报「文件不存在」而不是「一致」，正好避免了把空文件当成通过。
