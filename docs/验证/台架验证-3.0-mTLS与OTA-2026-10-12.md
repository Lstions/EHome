## 3. 证据 ②：设备证书（读回验证，最硬）

读设备 flash `0x9000` 的 NVS 分区并用 `nvs_tool.py` 提取：

```
$ python3 __scratch_v3/bin/extract_nvs_certs.py /tmp/dev_nvs.bin <out>
  ca   -> ca.crt   586 B
  cert -> dev.crt  606 B
  key  -> dev.key  226 B

$ openssl x509 -in dev.crt -noout -subject -issuer
  subject=CN=F0F5BD02F35C        <- = node_id
  issuer=CN=EHOME-Dev-CA

$ 证书公钥 md5 == 私钥公钥 md5   7f2d9bf1dcb04b5c8dff394b1f8499d5   <- 配对
$ CA 指纹  设备 == 后端 client_ca_file   46:33:89:A2:...:68:8F:19    <- 一致
```

### 3.1 对先前判断的纠正

`tools/README-nvs-certs.md` 说「仓库里**没有任何代码会写** ca/cert/key」—— **属实**。
但据此推出「真机上这条 3.0 链路**永远**停在 SESSION_FATAL」—— **错了**。

证书**不需要运行时写入**：它是作为 **NVS 分区镜像**在烧录时铺进去的
（`tools/nvs_certs_gen.py` 生成 `eh_tls_nvs.bin`，与固件一起烧）。

⇒ 正确表述：**设备侧证书供给有可行路径（烧 NVS 镜像），但尚未用于现场设备。**

这是本项目反复记录的那类错误：**把「代码里没有」当成「现实中不可能」。**

## 5. 重要修正：OTA 不必然依赖 MQTT

设计文档 §7.3 说「设备只能通过它**当前懂的**通道（MQTT 下行 OtaCmd 0x0A）拿到新固件」。
这对 **2.8.0 设备**成立；对**已跑 3.0 固件的设备**，`OtaCmd 0x0A` 经 TCP 会话同样能收到
（本次实测 `rx type=0x0A`）。

⇒ **只有「2.8.0 → 3.0」这第一次跨越必须走 MQTT**；此后 OTA 可全程走 TCP。
