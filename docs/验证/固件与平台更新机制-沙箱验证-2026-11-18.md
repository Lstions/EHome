### D3（交付缺陷，必修）两份 e2e 用例的登录助手与真实 DOM 失配 ⇒ 10/10 不可运行

- 位置：`frontend-shared/e2e/update-banner.spec.ts:77-88`（`route.fetch()` → `route.fulfill({ response, … })`）
- 根因：拦截 `**/api/**` 后用 `route.fetch()` 取真实响应再补头；若此时页面发生整页导航/刷新，已取到的 Fetch 响应会失效（`disposed`），或同一 route 被并发处理（`Route is already handled!`）。属 Playwright 路由代理在导航竞态下的已知形态。
- 归属：**用例基建缺陷**，产品无关（横幅/节流逻辑本身在两栈的功能断言全部通过）。
- 建议修法（一处即可）：

```
    let response
    try {
      response = await route.fetch()
    } catch {
      await route.continue().catch(() => undefined)
      return
    }
    try {
      await route.fulfill({ response, headers: { ...response.headers(), [BUILD_HEADER]: payload.build_id } })
    } catch {
      // 页面导航导致响应失效 / 该 route 已被处理：请求已无意义，吞掉，别让测试因竞态变红
    }

## 13. 实机验证（2026-11-19，ESP32-C6 8MB）

### 13.1 台架与前置

- `/dev/ttyACM0` = ESP32-C6 (QFN40) rev0.1，8MB，BASE MAC `f0:f5:bd:02:f3:5c`（= F0F5BD02F35C）⇒ profile **c6-n8**；`/dev/ttyACM1`（S3P）本轮无法同步，未使用。
- 写前必备份整片：`/tmp/c6-backup-8mb.bin`，sha256 `f536497638f0107a132bb82def36e898f3c1641beb6d9c2eda57b7111f3c6551`；每次写前 `flash-id` 校验芯片与容量；结束后整片写回并回读 `cmp`，**逐字节一致**，otadata 亦与备份一致。
- 台架限制：只有 CH34x→UART0，产品 console 在原生 USB-JTAG ⇒ app 日志不可见；验证镜像用 `tools/qemu-console-uart.defaults` 把 console 临时挪到 UART0（仅测试构建）。
- otadata 语义按 IDF 源码核对（与常见说法不同）：`NEW=0x0`、`PENDING_VERIFY=0x1`、`VALID=0x2`、`INVALID=0x3`、`ABORTED=0x4`；CRC **只覆盖 4 字节 `ota_seq`**；槽位 `(seq-1)%2`。

### 13.2 四场景结果

| 场景 | 结果 | 关键日志（设备时间戳） |
|---|---|---|
| FW-RB-01 坏镜像自动回退 | **PASS** | `Loaded app from partition at offset 0x10000` → `abort() was called` → `rst:0xc (SW_CPU)` → `Loaded app from partition at offset 0x390000`；事后 otadata `seq=3 ABORTED` / `seq=2 VALID` |
| FW-RB-02 断网仍确认 | **PASS** | 清 NVS + 无 AP 镜像：多次 `Disconnected from AP, reason=201`，`30.515 OTA: boot validation PASSED ... uptime=30s`；复位后仍 `0x390000` |
| FW-RB-03 安全模式不确认 | **PASS** | `BOOT_GUARD: *** SAFE MODE: 17 rapid reboots ... ***` → `deferred - boot_guard safe mode ... NOT confirming`；40s 抓取内 `PASSED` 次数 **0**；再复位回 `0x10000` |
| FW-RB-04 主动 invalid | **PASS** | `marking running image INVALID and rebooting` → `esp_ota_ops: Rollback to previously worked partition.` → `Loaded app from partition at offset 0x10000`；otadata `seq=2 INVALID` / `seq=1 VALID` |
| `ESP_ERR_OTA_ROLLBACK_FAILED` 降级分支 | **未覆盖** | 需「另一分区无可用镜像」，不改产品逻辑难以稳定构造 |

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 联网基线 | 31.453s（`uptime=30s`） | **30.707s**（`uptime=30s`） |

### 13.4 本次暴露并修掉的产品缺陷

1. **确认点被同步 WiFi 连接阻塞**：确认原跑在 `status_task` 里，而 `status_task` 在 `wifi_mgr_start()` 之后才创建；后者无 AP 时同步阻塞满超时。修复：`s_core_ready` 前移到 `wifi_mgr_start()` 之前（口径改为「本地关键初始化，不含网络」），并新增独立 `ota_confirm_task`（200ms 周期）在 `wifi_mgr_start()` 之前创建；确认轮询不再读 `status_task` 维护的 `uptime` 字段。
2. **日志重复前缀** `OTA: OTA:`（`TAG` 已是 OTA）已清理。
3. 台架认知：RTS 复位是掉电型（`rst:0x1 POWERON`），`boot_guard` 计数不累积；验证安全模式必须用**软件复位**（本条已写入方案 §6.6）。

### 14.3 E1 失败：既存缺陷，非本次引入

前端 `getDownloadUrl()` 拼接的是 `?token=<JWT>`，而后端下载路由只校验 HMAC `expires + signature`：

```text
GET /api/v1/firmwares/ehome_collector.bin/download?token=<JWT>  → 401 invalid or expired firmware ticket
GET /api/v1/firmwares/ehome_collector.bin/download                → 401
```

两侧代码（`frontend-shared/src/api/firmware.ts`、`backend/internal/api/handler_ota.go` 的下载处理器）在 HEAD 即为此形态，本次暂存区**没有修改**它们，因此是既有缺陷。
影响面：固件页「下载」与「复制链接」不可用；设备 OTA 下载走后端签发的签名 URL，不受影响。
建议单独修复（前端改为调用签发接口取签名 URL，或后端为管理员 JWT 增加一条受控分支），不并入本次更新机制改动。

## 15. 第六轮：下载缺陷修复 + 剩余证据补齐（2026-11-19）

### 15.1 修复：固件页「下载 / 复制链接」401

根因见 §14.3（前端拼 JWT，公开下载路由只认 HMAC）。修复取向是**不给公开端点加 JWT 旁路**——
那会把长期凭证留在 URL 里、并扩大匿名端点鉴权面；改为管理员在已鉴权接口换一张 30 分钟票：

| 位置 | 变更 |
|---|---|
| `POST /api/v1/firmwares/:id/download-ticket` | 新增（JWT 组）。按 `StoragePath` basename 签名，返回 `{url, expires_at}`；基址取请求 origin（反代由 `X-Forwarded-Proto` 修正） |
| 前端 `firmwareApi` | `getDownloadUrl()`（拼 JWT）删除，改为 `createDownloadTicket(id)`；无兼容分支 |
| 前端固件页 | 下载与复制链接都先换票；复制的是**带有效期的票据 URL**，JWT 不再进入剪贴板 |

路由用 POST 的原因写在 handler 注释里：gin 同一方法树中 `:id` 与公开路由的 `:filename` 会因通配符名冲突 panic。

D2 的产物文件在 snap chromium 下取不到（浏览器写进 snap 私有临时目录，宿主路径 ENOENT），因此改用「下载事件 URL + 页面内 fetch 校验字节」取证；这是测试环境限制，不是产品行为。

### 15.4 实测推翻的一条说法：上传并没有省内存

6 MB 合法镜像上传时采样服务进程 `VmHWM`：

```text
首次 6MB 上传（201）        VmHWM +12,528 KB
第二次 6MB（409 重复）      VmHWM +8,284 KB
第三次 6MB（409 重复）      VmHWM +8,232 KB
```

连**被拒绝**的上传也涨约 8 MB ⇒ 请求体在进入 handler 前就已被缓冲。根因是 `c.FormFile()` 内部调用
`ParseMultipartForm(32MB)`，文件部分整包驻留内存；`io.Copy` 到临时文件只是把**已驻留**的字节再写一遍。

结论：

- 「流式落盘」只在「内存 → 磁盘」这一段成立，**整包不进内存的说法不成立**；
- 影响有界：`firmwareUploadMaxBytes = 8MB`，峰值约为镜像大小 + 开销；
- 是否改成 `MultipartReader()` 真流式，作为独立优化项评估（改的是上传主路径，收益 ≈ 8MB 瞬时峰值），本轮不动；
- 更新说明中该条已改为「落盘走临时文件并同步算哈希」，不再声称降低内存。

| `ESP_ERR_OTA_ROLLBACK_FAILED` 分支 | 需构造「另一分区无可用镜像」，硬件上难稳定复现 |

### 15.6 结论

下载缺陷已修复并有接口 + 浏览器双重证据；此前 7 项未验证中，10 条闸门、强制审计、指标、verify-release、断网优先级、强制标签全部补齐。

## 16. 第七轮：真机全链路 OTA（2026-11-19）

前一轮把「平台下发→设备下载→安装→确认→VALID」列为唯一缺口。本轮用本机真机 + docker 沙箱把这条链路跑通。

### 16.1 环境

| 项 | 值 |

### 16.3 一次失败：沙箱装配问题，不是产品缺陷

首次建任务后设备报 `Download failed after retries`。原因：后端容器的 `WORKDIR` 是 `/`，上传落到了容器内 `/firmwares`（非卷），而下载路由按相对路径找 `firmwares/…`；重建容器后文件随容器丢失。
修正：compose 增加 `working_dir: /app` 并重新上传，第二次即成功。生产镜像的 Dockerfile 自带 `WORKDIR /app`，不受影响。

### 16.4 边界

- 串口（USB-Serial/JTAG）本轮未采集到应用日志（打开端口后无输出，属采集环境限制），因此**确认时刻**未直接观测；`VALID` 状态证明 `mark_app_valid` 已执行，30.5s 的计时证据来自第六轮台架。
- 下载速率约 70 KB/s（WiFi 环境），1.36 MB 用时约 19s。
- 设备已整片还原为实验前镜像：`0x10000` app 版本 2.8.0、otadata `seq=1 VALID slot=0`。
