| `/health` | `{"status":"ok","commit":"unknown","ready":false,"phase":"failed","percent":0}` |

> 这是设计里最关键的一条：**升级失败时用户看到的是「哪个阶段失败、为什么」，而不是"连接被拒绝"**。

## 补充（2026-11-06 18:00 之后的收尾）

### 场景 5：时区缺陷（本次改造暴露出的既有 bug，已修复）

boot-api 在造数据时撞到迁移 Fatal，我独立复现并定性：

| 实验 | 数据 | TZ | 结果 |
|---|---|---|---|
| 对照 A | 3 行，最早 = `2026-10-31T16:30Z`（本地 +08 的 11-01 00:30） | `Asia/Shanghai` | **FATAL** `row count mismatch: src=3 dst=1` |
| 对照 B | 同上 | `UTC` | **migration complete rows=3** |

根因：pgx 解码 `timestamptz` 返回 **time.Local** 视角的 `time.Time`，而 `monthStart` 用
`t.Year()/t.Month()`（本地视角）却构造 `time.UTC` 月初 ⇒ TZ≠UTC 时最早 UTC 月整体右移，
该月前 8 小时的行落在所有 COPY 窗口外。

**生产容器恰好没有 `/etc/localtime` 且未设 `TZ` ⇒ Go 的 `time.Local` 退化成 UTC ⇒ 现在没炸是碰巧安全。**

修复（commit `dbf7c691`）：`monthStart` / `partitionName` 一律先 `t.UTC()` 再取年月。
回归测试 `partition_mgr_tz_test.go` 三层防线（纯逻辑用 `time.FixedZone` 不依赖 TZ 环境变量 /
缺陷现场钉桩 / PG 端到端把 `time.Local` 设成 +08 跑完整迁移并带前提断言防假绿）。
变异验证：把修复回退后 3 条用例变红，其中 PG 那条报的错误与独立复现逐字相同。

**修复后复验**（TZ=Asia/Shanghai，生产同款 schema + 281 万行）：

```

  db_connect / auto_migrate / partition_unified_data / partition_device_data /

  warmup / startup_tasks               全部 done
索引结果：device_id / device_sensor_ts(F-10) / device_ts(F-10) / pkey / timestamp
        ⇒ F-10 两条已补建，sensor_name 与 edge_device_id 死索引已退役
```

### 场景 6：编排就绪探针（compose）

`docker-compose.yml` + `docker-compose.example.yml` 的 `ehome` 服务加：
```yaml
healthcheck:
  test: ["CMD", "wget", "-qO-", "http://localhost:8080/readyz"]
  interval: 10s / timeout: 5s / retries: 3 / start_period: 300s
```
- **必须 `/readyz` 不是 `/health`**：维护期 `/health`=200、`/readyz`=503；探 `/health` 会把流量过早放进来
- **代理坑（实测）**：运行镜像是 alpine，busybox wget **不认 `no_proxy`**。本机 docker 守护进程级注入
  `HTTP_PROXY` 后，容器连 `localhost` 也走代理 ⇒ 探针永远 unhealthy。清空代理后语义正确
  （200→exit 0 / 503→exit 1 / 连接拒绝→exit 1）。警告已写进两份 compose 的 YAML 注释。

### CI 护栏

`.github/workflows/test.yml` 的 backend job 新增 `TZ=Asia/Shanghai` 步骤跑时区相关用例子集
（0.009s，成本可忽略）。理由：runner 与生产容器恰好都是 UTC ⇒ 这类缺陷在默认环境**测不出来**。
