# 吞吐上限与被动路径实测（2026-10-11）

> 承接 [link_tcp并发释放修复-2026-10-11.md](../分析/link_tcp并发释放修复-2026-10-11.md) §六 遗留 1、2。

口径：**实测** = 真机 S3P 30EDA0A9A808 测得；**读码** = 源码确认；**推算** = 由前两者推导。

## 一、遗留 1：126.49 req/s 不是上限

### 1.1 结论

| 波特率 | 从机实现 | 吞吐 | 中位间隔 |
|---|---|---|---|
| 115200 | slave_fast2（静默分帧） | 126.49 req/s | 7.45 ms |
| 921600 | slave_fast2（静默分帧） | 156.23 req/s | 6.38 ms |
| 115200 | **slave_imm**（定长立即回） | **152.9 req/s** | 6.46 ms |
| 921600 | **slave_imm**（定长立即回） | **190.1~195.6 req/s** | 5.04 ms |

**⇒ 126.49 既不是设备上限，也不是链路上限。**

### 1.2 测量工具本身贡献了相当一部分「地板」

`slave_fast2.py` 用 Modbus 3.5 字符静默窗口分帧（0.4ms）+ 1ms read 超时，
每帧至少引入约 1ms。换成按**定长 8 字节**立即结算的 `slave_imm.py` 后，
同一波特率下吞吐立刻从 126.49 → **152.9 req/s**（+21%），中位 7.45 → 6.46 ms。

⚠ **这是本仓反复踩的同一个坑**：把测量工具的开销当成被测对象的能力。
`slave_ts.py` 时代（10ms read 超时）曾把设备上限误判成 21ms；
这次是 0.4ms 静默窗口 + 1ms 超时。**任何上限结论必须先排除测量工具。**

### 1.3 剩下的 ~4.9ms 地板与波特率无关

```
921600：8 字节线上传输 = 8x10/921600 = 0.087 ms
        实测中位间隔      = 5.04 ms
        => 非 UART 部分     = 4.95 ms

115200：8 字节线上传输 = 0.69 ms
        实测中位间隔      = 6.46 ms
        => 非 UART 部分     = 5.77 ms
```

两个波特率下「非 UART 部分」接近（4.95 / 5.77 ms）⇒ **存在一个与线速无关的固定开销**。
读码定位到三处（**推算**，未逐项 A/B）：

| 来源 | 量级 | 位置 |
|---|---|---|
| `UART_IDLE_THRESHOLD_US = 2000` | 2 ms | `bus_worker.c:1792` —— 帧结束判据是「静默 2ms」，每帧都要等满 |
| 调度 tick `has_fast_channel ? 1 : 10` | ~1 ms | `scheduler.c:844` —— 命令下发有 1ms 粒度 |
| fence `UART_RESPONSE_WAIT_MS = 5` | 0~5 ms | `bus_worker.c:114` —— 事件等待的**超时兜底**（正常由信号量唤醒，不走满） |

⚠ 2ms 空闲阈值是**协议中立**的设计（`bus_worker.c:1784-1791` 有完整推导：
不能降太低，否则与硬件 TOUT 事件竞争）。**不要为了吞吐去降它** ——
那会把「帧完整」换成「帧更早」，属于拿正确性换指标。

### 1.4 能确定与不能确定的

- ✅ 能确定：**吞吐随波特率上升**（115200→921600 提升 24~28%），所以 UART 线速仍是瓶颈之一。
- ✅ 能确定：测量工具影响 >20%，历史上限结论需重新校准。
- ❌ 不能确定：**4.95ms 的精确构成**。上表是读码推算，未做「逐个关掉再测」的 A/B。
  若要继续压，下一步应是**单独**测这三项各自的贡献，而不是直接改常量。

## 二、遗留 2：被动路径的 72% 丢失 —— 已消失（但原因不是 DataBatch）

### 2.1 现象（11:46 固件，只含 link_tcp 修复）

真被动 100fps 发 4835 帧，后端只收到 **1336 条**（**丢失 72%**）。
到达间隔中位 10.0ms（与发送一致），但夹着 **12 个约 2.8s 的空洞**。

同时设备日志里 TLS 每 ~2.8s **重连一次**：
```
I (3865) tls_esp: mTLS 连接建立 -> 192.168.20.3:8443
E (6276) esp-tls-mbedtls: read error :-0x7780     <- 断开
I (9130) tls_esp: mTLS 连接建立 -> 192.168.20.3:8443   <- 2.8s 后重连
```
重连次数：**14 次 / 47s**。

### 2.2 复测（12:11 固件，含 tx_lock 串行化）

| 场景 | 发送 | 收到 | 丢失 | TLS 重连 |
|---|---|---|---|---|
| 被动 100fps（旧） | 4835 | 1336 | **72%** | 14 |
| 被动 100fps（新） | 3870 | **3870** | **0%** | **1** |
| 被动 200fps（新） | 7498 | **7498** | **0%** | 1 |
| 被动 300fps（新） | 11413 | 11304 | 0.96% | 1 |
| 被动 500fps（新） | 17125 | 2073 条 | 见 2.3 | 1 |

两个日志的 `Compile time` 可区分固件：
`fixIso.log = Oct 11 2026 11:39:15`（仅 link_tcp 修复）
`p2.log / txlock.log = Oct 11 2026 12:11:07`（+ tx_lock）。

**⇒ 72% 丢失与 2.8s 重连风暴都是 §258 那一族并发缺陷的后果**：
并发写破坏 TLS 上下文 ⇒ 连接被对端/本端判为损坏 ⇒ 重连 ⇒ 重连期间上行全丢。
`tx_lock` 一并消除了它们（重连 14 → 1，丢失 72% → 0%）。

⚠ 诚实边界：这是**相关性**证据（同一负载、仅固件不同、两次复现），
不是「已定位到具体哪一次内存写导致 TLS 报错」。根因链的最后一环未闭合。

### 2.3 500fps 的「丢失」其实是**合并**，不是丢帧

按帧长分布看 500fps 的输出：
```
9 字节   : 1529 条   <- 单帧
261 字节 :  526 条   <- 29 x 9B，连续帧被合并成一帧
折算总帧数 = 1529 + 526x29 = 16783
实发       = 17125
差额       = 342 帧（2.0%）
```
**⇒ 98% 的字节都到了**，只是 29 帧被并成一条上报。

原因（读码）：发送间隔 2.1ms **小于** `UART_IDLE_THRESHOLD_US = 2000`（2ms），
空闲判据永远等不到「静默 2ms」，于是多帧在缓冲区里累积，一次交出。

⚠ 这**不是缺陷**：`emit_buffered_frame` 是唯一写者，缓冲区没有溢出（`report_drop=0`）。
后端按 `raw_hex` 原样存储与广播（`consumers_heavy.go:477/510`），
合并帧对「取原始字节」的消费者是**无损**的；
只有**按固定帧长解析传感器**的路径会因长度不符而解析失败 —— 属已知限制。

### 2.4 被动路径当前的真实上限

- ✅ **200fps：0 丢失**（实测，7498/7498）。
- ✅ **300fps：0.96% 合并**（实测，几乎无损）。
- ⚠ **500fps：98% 字节到达，但按帧计数只有 12%**（合并）。

⇒ 被动路径**不需要**为了吞吐去接 `DataBatch`：
在 200fps（远高于任何当前真实传感器速率）下它已经零丢失。
`DataBatch` 的价值是把「每帧一次同步 TLS record 写」变成「多帧一次写」，
省的是**设备侧 CPU/网络包数**，不是当前已观测到的瓶颈。
**⇒ 遗留 2 结论：优先级低，暂不做**（与 §258 报告 §六 的判断一致，现有实测支持它）。
