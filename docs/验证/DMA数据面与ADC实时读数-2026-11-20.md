# DMA 数据面与 ADC 实时读数收尾验证（2026-11-20）

> 目标：把上一轮报告里明确标注为“未闭环”的两项真正做完 —— ADC 从「配置成功」补到「页面可读真实样本」，DMA 从「UI 合并配置意图」补到「设备原始 ResourceReport 回显 + 真实 GDMA 数据拷贝」。
>
> ⚠️ 边界：`dma_pool` 的 CH1→`uart/UART0` 是**逻辑资源预留**；当前 UART 驱动仍走中断 + 驱动环形缓冲，并没有启用 UHCI 硬件 DMA。本轮另外用 C6 AHB-GDMA 做了真实内存拷贝自检，证明 DMA 引擎/数据面可用；这不等于“UART0 已由 DMA 搬运”。

## 2. ADC 实时读数

### 2.1 协议与执行路径

1. 前端 `POST /api/v1/nodes/F0F5BD02F35C/adc/ADC1_CH1/read`。
2. 后端按 `hardware_id + bus_type=ADC + bus_config 非空` 选择当前有效通道（id=19），下发 `PeriphCmd(periph_type=3, action=0, resource_id=19)`。
3. 固件 `handler_periph.c` 进入 `PERIPH_TYPE_ADC` 分支，调用 `main.c` 的 `on_adc_read_received()`。
4. main 按 `bus_ch == 19 && bus_type == ADC` 找到 ADC lease，调用 `bus_dma_adc_read()`。
5. 固件通过 `msg_handler_send_periph_rsp()` 把 raw 放入 `PeriphRsp.value`。
6. 后端 `WaitPeriphResult(request_id)` 等到同一条回执，HTTP 同步返回 raw/percent，而不是只返回 ACK 让 UI 等 WebSocket。

### 2.2 真机结果

```json
{"bit_width":12,"channel_id":19,"hardware_id":"ADC1_CH1",
 "max_raw":4095,"percent":17.97,"raw":736,"request_id":345582805}
```

连续 10 次读取：`768 / 736 / 704 / 688 / 689 / 688 / 689 / 689 / 689 / 688`，全部 200；设备日志同一 `request_id` 有 `PeriphCmd type=3` 与 `PeriphRsp success=1, type=3, resource_id=19`。

### 2.3 UI

节点页 → 总线与通道 → ADC → ADC1_CH1 → 通道行「读取」，行下方显示：

```text
ADC1_CH1  raw 736 / 4095  17.97%  刚读取
```

加载中按钮显示「读取中…」，离线/失败有独立错误提示；不把「通道配置存在」当成读数成功。

## 3. DMA ResourceReport

### 3.1 问题

旧固件原始上报里 CH1 始终是：

```json
{"dma_id":1,"state":0,"bound_to":""}
```

但同一份 ResourceReport 的 `channels[8]` 却是 `dma_enabled=true, dma_allocated=true`。两者矛盾，说明 DMA 池条目与总线实际分配状态脱节。

### 3.2 修复

- `dma_pool` 新增 `dma_pool_mark_bound(pool, dma_id, hw_id)`：幂等重写 `state=ALLOCATED` 与 `bound_to`，拒绝覆盖用户显式禁用的通道。
- `bus_manager` 在 `bus_dma_init_preferred()` 成功后，用本次真实 `dma_id` 与 `hw_id` 调一次自愈；这样 ResourceReport 编码时池条目与「UART 驱动确实拿到 DMA」一致。
- 后端 `GET /dma-channels` 增加 `device_allocated`：从 `hardware_info.channels[].dma_allocated` 读取设备确认，不再只显示配置意图。
- DMA 页 CH1 显示「设备已确认分配」；只有配置已下发但设备未确认时显示「配置已下发，等待设备确认」。

### 3.3 真机结果

烧录后原始 `nodes.dma_channels`：

```json
{"dma_id":1,"state":1,"bound_to":"uart/UART0"}
```

再次触发 `POST /nodes/F0F5BD02F35C/config/sync` 后仍为 `state=1, bound_to=uart/UART0`，不是一次性快照。

## 4. DMA 数据面

### 4.1 逻辑预留与真实 DMA 必须分开

设备 ResourceReport 的通道 8 是：

```json
{"id":8,"bus_type":1,"dma_enabled":true,"dma_allocated":true}
```

原始 DMA 为 `GDMA_CH1 -> uart/UART0`。但代码事实是：`bus_dma.c` 对 UART 走 `uart_driver_install` + 事件队列 + 驱动环形缓冲，**没有调用 UHCI**。因此：

- `dma_enabled=true` 对 UART 的作用是扩大驱动缓冲，不是 UHCI 搬运；
- CH1→UART0 是**资源预留/控制面**，不能说成“UART0 已用 DMA 收发”。

### 4.2 真实 GDMA 自检

新增 `POST /nodes/:id/dma/selftest`，固件用 `esp_async_memcpy` 驱动 C6 AHB-GDMA：

1. 分配两块 2048B 内部 DMA 内存；
2. 源缓冲区填入 `i*31+7`；
3. 发起异步内存到内存拷贝，等待完成信号（2s 上限）；
4. `memcmp` 校验并计算 FNV checksum；
5. `PeriphRsp(periph_type=4)` 返回结果。

真机结果：

```json
{"passed":true,"bytes":2048,"checksum":514084864,"request_id":1228819106}
```

连续 10 次全部 `passed=true`，checksum 恒为 `514084864`（0x1EA45000），单次约 57ms。设备日志：

```text
DMA selftest: passed=1 bytes=2048 checksum=0x1ea45000 err=ESP_OK
```

这证明 C6 的 GDMA 引擎能真实搬运数据且目的内容一致；它**不**证明 UART0 的 UHCI DMA（该项仍是独立实现缺口）。

### 4.3 UART0 写入回归（非 DMA 证明）

通过 UART0 终端通道连续发送 10 帧、每帧 120 字节：

- `WriteRsp success=1`：**10/10**；
- `CMD_U0 Stats`: `txn=10 err=0 (100%) no_ctx=0`。

这只证明 UART0 中断驱动写路径正常，不作为 DMA 搬运证据。
