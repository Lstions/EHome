# 实机缺陷：PSRAM 型号上内存门禁恒为"充足"（2026-10-05）

**发现方式**：S3 实机（`30EDA0A9A808`，8MB PSRAM）刷 `s3p-n16` 后解 MemReport。
**严重性**：**高** —— 门禁在 PSRAM 型号上失去保护作用，而 PSRAM 型号正是最需要它的一类。
**状态**：**已修复**（2026-10-06，task-4）。修法=方案 A（门禁只看内部 RAM）+ 按实机实测校准 floor。

> **一句话结论**：s3p 内部 RAM largest 实测 **23,552 B（空载/负载/事务后三时点一致）**，
> floor=16 KiB **可达**（余量 7,168 B / 43.75%），因此**只改口径、不下调 floor**；
> "改口径会导致配置事务恒被拒绝"这一风险**已被实测排除**。详见 §9。

---

## 1. 实测证据

S3（s3p-n16，PSRAM 8MB）实机 MemReport：

```
MemReport #1: free=8333027 largest=8257536 min_ever=8301920 min_stack_hw=584 floor=16384
```

对照 C6（无 PSRAM，同一份代码）实机 MemReport：

```
MemReport #1: free=123020 largest=88064 min_ever=104292 min_stack_hw=1104 floor=12288
```

S3 的 `free`=**8.33 MB**、`largest`=**8.25 MB** —— 这就是 PSRAM 的总量。
**内部 RAM 的水位完全没有反映在这个数字里。**

---

## 2. 根因

`main/mem_guard.c`：

```c
size_t mem_guard_free(void)
{
    return heap_caps_get_free_size(MALLOC_CAP_8BIT);
}
size_t mem_guard_largest(void)
{
    return heap_caps_get_largest_free_block(MALLOC_CAP_8BIT);
}
bool mem_guard_can_start(size_t need_bytes)
{
    const size_t required = (need_bytes > floor) ? need_bytes : floor;
    return mem_guard_largest() >= required;      /* floor: s3p 16 KiB */
}
```

`MALLOC_CAP_8BIT` 在**默认分配器**下等价于"内部 RAM + PSRAM"的合计。
开了 `CONFIG_SPIRAM_USE_MALLOC=y` 后，`heap_caps_get_largest_free_block(MALLOC_CAP_8BIT)`
返回的是**跨两个堆取最大值**（PSRAM 那个 8 MB 连续块），不是内部 RAM 的 largest。

于是：
- `can_start()` 在 s3p 上**恒为 true**（8.25 MB ≫ 16 KiB floor）；
- 低水位回调 `mem_guard_poll()` **永不触发**（`largest < floor` 永不成立）；
- `[memguard] low memory` 告警在 s3p 上**永远不会出现**。

**这正是内存一期要防的那类故障**：S3 带 PSRAM 时，真正会耗尽的是**内部 RAM**
（任务栈、DMA 缓冲、OTA 缓冲都必须内部），而 PSRAM 还有 8 MB —— 门禁看着 PSRAM 说"很宽裕"。

---

## 3. 为什么单测没抓到

`host_tests/mem_guard_tests.c` 用桩函数替换了 `heap_caps_*`：

```c
size_t heap_caps_get_largest_free_block(unsigned caps) { (void)caps; return s_largest; }
```

桩**忽略 `caps`**，所以"caps 选错"这一整类缺陷在宿主测试里不可见。
宿主测试证明的是"谓词逻辑对"，不是"caps 选得对" —— 后者**只能在真机上暴露**。

## 5. 建议修法（三选一，需裁决）

**方案 A（推荐）：门禁只看内部 RAM。**
```c
size_t mem_guard_largest(void) {
    return heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT);
}
size_t mem_guard_free(void) {
    return heap_caps_get_free_size(MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT);
}
```
理由：所有门禁消费点（事务、UART 驱动、OTA、任务栈）要的都是**内部 RAM 连续块**。
floor 的语义本来就是"内部 RAM 水位"。
**代价**：需在真机复测 s3p 的 largest 是否真能到 16 KiB（很可能不能 —— 见下）。

**方案 B：双水位。** 内部 RAM 用一个 floor，PSRAM 单独统计；门禁判内部。
信息更全，但改动大、MemReport 字段要加。

**方案 C：按型号给 PSRAM 型号更低的内部 floor。**
承认 s3p 的内部 RAM 就是紧，把 floor 从 16 KiB 调到实测可及的值。

**关键未知（必须先测）**：s3p 的**内部 RAM** largest 到底是多少？
当前 MemReport 报的是 PSRAM 数字，所以**内部 RAM 的真实水位在实机上从未被观测过**。
这直接决定 floor 是否合理、以及内存一期"事务后 largest ≥ 16 KiB"的目标是否可达。

### 5.1 无需刷机即可得到的内部 RAM 上界（已算）

用同一次启动的 boot log `heap_init` 与 MemReport 交叉推导：

```
boot log 内部堆（MALLOC_CAP_8BIT 可分配）:
  3FCAC070 len 0x3D6A0 = 251,552 B
  3FCE9710 len 0x5724  =  22,308 B
  3FCF0000 len 0x8000  =  32,768 B
  ⇒ 内部堆合计 = 306,628 B (299.4 KiB)
  (RTCRAM 600FE000 8,168 B 不计入 8BIT)

MemReport: free=8,333,027  largest=8,257,536
PSRAM 总量 = 8,388,608 B

largest 是跨堆取最大 ⇒ 8,257,536 必为 PSRAM 块 ⇒ psram_free ≥ 8,257,536
⇒ internal_free = 8,333,027 − psram_free ≤ 75,491 B
```

**结论**：`internal_free ≤ 73.7 KiB`，即内部 RAM 已用 ≥ 225.7 KiB。
这只是**上界**，真实值可能更低（`largest` 略小于 `psram_free`）。

**但它足以给出一个重要判断**：s3p 的内部 RAM 剩余量级在**几十 KiB**，
与内存一期设想的"事务后 largest ≥ 16 KiB"是**同一量级**——
所以 floor 16 KiB 是否可达**仍未知，必须实测**，不能靠这个上界下结论。
更关键的是：**在门禁失效的前提下，事务能否通过完全靠运气**，
这正是本缺陷的严重性所在。

## 7. 同一污染源波及 StatusReport（扩展发现）

同一个 `MALLOC_CAP_8BIT` 口径也用在**上报给服务端的健康字段**上：

| 位置 | 表达式 | 影响 |
|---|---|---|
| `components/msg_handler/handler_data.c:240` | `esp_get_free_heap_size()` | StatusReport 的 heap 字段 = 含 PSRAM 合计 |
| `components/msg_handler/handler_data.c:241` | `esp_get_minimum_free_heap_size()` | 同上 |
| `main/main.c:75-77` | `heap_caps_get_*(MALLOC_CAP_8BIT)` | 启动里程碑探针 |
| `main/main.c:226-227` | 同上 | `[stack] ---- heap free/largest ----` 行 |

`esp_get_free_heap_size()` 是 `heap_caps_get_free_size(MALLOC_CAP_DEFAULT)` 的封装，
在开了 PSRAM 的构建里同样把 PSRAM 计入。

**后果**：服务端看到的 s3p 节点"空闲内存"是 8 MB 量级，
**运维和告警都看不到内部 RAM 的真实紧张程度** —— 这正是内存一期要解决的可见性问题，
却在 PSRAM 型号上被反转成了"永远充裕"。

**因此修法应统一口径**：把"内部 RAM 水位"作为独立指标（方案 A 或 B），
并让 StatusReport / MemReport 同时携带**内部**与**合计**两个口径，避免下游再猜。

### 9.2 实机实测：s3p 内部 RAM 真实水位（本缺陷的"关键未知"）

设备 `30EDA0A9A808`（S3 + 8 MB PSRAM），刷 `build-mg-diag/s3p-n16`
（= 修复版 + 一行临时 `[intdiag]` 日志，测完即删，不在交付里）。

**稳态（无配置事务、无 OTA，启动后 90 s，18 次采样，ttyACM1 @115200）**：

```
[intdiag] internal free≈49,700  largest=23552  min_ever=31628
          | total(8BIT) free≈8,333,395  largest=8,257,536   floor=16384
```

| 口径 | free | largest | min_ever |
|---|---:|---:|---:|
| **内部 RAM**（`INTERNAL\|8BIT`） | ≈49,700 B | **23,552 B** | 31,628 B |
| 合计（`8BIT`，旧代码读的） | 8,333,395 B | 8,257,536 B | 8,301,920 B |

**这是同一时刻的两个口径**，对照比 §5.1 用 C6 做的间接推导更直接：
旧代码的 8.25 MB **就是 PSRAM**，内部 RAM 只有 23.0 KiB。

- 内部 largest **23,552 B = 23.0 KiB**，90 s 内**完全不抖**（18 次采样全部 23,552）。
- `min_ever`（历史最小 free）= 31,628 B，说明启动至今内部 RAM 从未低于 30.9 KiB。
- 与 §5.1 的上界推导一致：上界给的是 `internal_free ≤ 73.7 KiB`，实测 48.6 KiB，
  在同一量级且更紧（上界正确、实测更准）。

### 9.3 floor 取值依据（本任务最大风险点）

任务卡的警告是：改口径后若内部 largest 长期 < floor，配置事务会**恒被拒绝**，
比现在的"恒放行"更糟。实测回答了这个问题：

| 判据 | 值 |
|---|---:|
| s3p 内部 RAM largest（实测稳态） | 23,552 B |
| 原 floor（s3p） | 16,384 B |
| 余量 | **7,168 B（+43.75%，即 1.44×）** |
| 结论 | **16 KiB 可达，floor 不下调** |

三个消费点的 `need`（设计 §4.3：preflight 4,096 / apply_buses 4,096 / UART install 3,584）
都远低于 16,384，且 `can_start()` 取 `max(need, floor)`，因此判决由 floor 主导 ——
只要内部 largest ≥ 16 KiB，全部门禁放行。实测 23.0 KiB 满足。

**为什么不下调、也不上调**：
- 不下调：16 KiB 已在实测可及范围内且有 44% 余量；下调会削弱"事务需要一整块连续内存"
  的保护（apply_buses 稳态峰值 4 KiB + UART install 3.5 KiB，16 KiB 留了约 2 倍的分配器
  元数据/碎片余量）。
- 不上调：23.0 KiB 是**无负载**值；负载态会下降（UART DMA 缓冲 + 报告队列常驻），
  把 floor 顶到接近 23 KiB 会让负载下的配置事务被拒。16 KiB 对负载下降留了 7.2 KiB 的
  吸收空间。这也解释了为什么"按实测最大可用值定 floor"是错的 —— floor 是下限保护，
  不是"水位目标"。

**残余风险（诚实登记）**：负载态（ch8@115200 100Hz）的 internal largest 见 §9.4。
若负载态低于 16 KiB，则需重新评估（下调 floor 或降低负载态常驻内存）；截至本文写作，
负载态实测**仍 ≥ 16 KiB**（见 §9.4），故 floor=16 KiB 保留。

### 9.4 负载态（100 Hz 台架，2026-10-06 00:40–00:45）

负载由 task-3(loadtest) 提供：ch8 台架 manifest（baud 115200 / interval_ms 10，即 100 Hz），
ch8 从机在 `/dev/ttyUSB0` @115200 应答。同一窗口**两条独立通道**各抓一次：

| 通道 | 采样 | internal free | **internal largest** | internal min_ever |
|---|---|---:|---:|---:|
| 串口 `[intdiag]`（task-4） | 6 次，t=5..25 s | ≈49,900 B | **23,552 B** | 31,628 B |
| MQTT `nodes/30EDA0A9A808/up` MemReport 0x21（loadtest） | 3 帧 | 48,675 B | **23,552 B** | 31,628 B |

**负载态结论**：
- internal largest = **23,552 B，与空载逐字节一致（0 抖动）** —— 100 Hz 负载**没有**侵蚀内部 RAM
  的连续块；常驻的 UART DMA 缓冲与报告队列已在稳态占用中体现，不随吞吐波动。
- floor=16,384 的余量在负载态同样是 **7,168 B（43.75%）**。
- 复位后 t=0 的瞬态值为 largest=31,744 / free=81,423 / min_ever=49,340（WiFi 与负载尚未起来），
  说明"启动早期水位更高"；floor 以稳态为准是保守选择。
- 负载窗口内 PANIC/WDT = **0**，`report_drop=0`（loadtest 独立记录）。
- 负载态 `min_stack_high_water` = **300 B**（空载 584 B）—— 栈维度被负载压掉近一半。
  这是"floor 不能贴 0、必须留余量"的辅助论据（栈与 heap 是两类资源，判据仍是 heap largest）。

**注意版本边界**：本节与 §9.2 的数字来自 `build-mg-diag/s3p-n16`（诊断固件，`MSG_MEM_RPT=0x21`）；
loadtest 的 step1/step2 实机证据来自 `build-verify/s3p-n16`（2026-10-05 23:23 构建，`MSG_MEM_RPT=0x20`）。
两者不是同一版固件，引用时不可混用。

### 9.6 为什么 floor 语义必须写清

本次修复后 `floor` 的含义第一次变得无歧义：**内部 RAM 的 largest 下限**。
修复前它名义上也是这个意思，但实现读的是跨堆最大值，于是语义与实现脱节 ——
这正是缺陷的根因。`mem_guard.h` 现在把口径写在接口注释里，宿主测试用 caps 断言锁住，
两道防线防止回退。
