## 4. 删表前的端到端演练（这一步抓到 2 个真 bug）

用 `DETACH PARTITION`（可逆、0 秒）模拟删除，然后逐字段逐窗口对拍。

### 4.1 抓到的 bug 1：字段级静默截断

```
dev15 30d（10月已摘）:
  grid_voltage         133 pts   ← rollup 生效
  pv1_voltage           44 pts   ← 回落 unified（只剩 11 月）
  alarm_fan_error       44 pts   ← 同上
```

根因：`decodeFrameWindowNow` 里「0 点 + 有帧 ⇒ 解码故障」这条判据，
在**整窗**路径上正确（有帧却解不出 = 解码坏了），被复用到 `[now-120s, now)` 的 **2 分钟尾巴**上 ——
某字段在这 2 分钟没采样是**正常状态**，却被判故障 ⇒ 整窗回落。

**不删表时完全隐形**（回落照样有数据，只是慢一点）。删了就是永久静默丢失，**比空页更难发现**。

修：给 `decodeFrameWindow` 加 `allowEmpty bool`（整窗 false / 尾巴 true），
**并把 `AllowEmpty` 放进缓存键** —— 否则尾巴缓存的空结果会被整窗路径复用成「静默返回空点集」。

### 4.2 抓到的 bug 2：1h~6h 历史窗口变空

`unified_data` 删掉后，1h~6h 的窗口既不走帧表（`frameDecodeMaxWindow` 默认 1h）也不走 rollup（>6h 才走）
⇒ **10 月历史的 2h / 6h 窗口返回空**。

修：`EHOME_TELEMETRY_FRAME_DECODE_MAX_WINDOW=6h`（无需改代码；`MaxDecodeFrames=32,768` 本就是为了 6 小时 1 Hz 设计的）。

### 4.3 最终对拍

```
18 个序列（2 设备 × 3~6 字段 × 7d/30d）在「10 月已删」与「10 月还在」两种状态下
→ 点数相同、时间戳相同、值逐点相同（0/18 不同）
```

## 6. 一个贯穿全程的模式（5 次，值得单独记）

**一个判据带着它诞生场景的隐含假设，被搬到假设不成立的场景。**

| 判据 | 诞生场景 | 被复用到 | 后果 |
|---|---|---|---|
| 5 分钟覆盖余量 | 容忍 60s 心跳 | 帧表落盘滞后 | 静默短尾 |
| `end` 当锚点 | 设备持续上报 | 设备离线/夜间关机 | 完整历史被判未覆盖 ⇒ 删表后空页 |
| 120s liveLag | rollup 的 60s flush | 帧表兜尾 | 兜不到（帧表滞后无上界） |
| `FramesSeen>0` 报错 | 整窗解码失败 | 2 分钟尾巴子窗口 | 某字段没采样 ⇒ 整窗回落 |
| `frameDecodeMaxWindow=1h` | 当时 unified_data 还在 | unified_data 被删后 | 1h~6h 历史窗口空 |

**共同点：单测抓不到**（每个场景自己的测试都是绿的），只有端到端演练能抓。
所以「删表前的 DETACH 演练」不是走形式 —— 它抓到的两个 bug 里，
一个会造成**永久静默数据丢失**，一个会造成**整类查询返回空**。

**但这不是最终账** —— `unified_data` 有 45 天保留期，稳态下它约 15.5 GB 不再增长。
真正的长期增长是：`device_data`（45 天保留）+ `telemetry_frame`（永久 19 MB/天）
+ `telemetry_rollup`（永久 3 MB/天）。

### 7.3 下一轮最大的单点：`unified_data` 的**历史**部分，不是全部

⚠ **我一度说「它已经没有任何读者了」—— 这是错的，已纠正。**

「≤6h 走帧表、>6h 走 rollup」只对**历史曲线**成立。`unified_data` 还有 6 个读者：

| 读者 | 位置 | 删表后 |
|---|---|---|
| 历史回落源 | `history_source.go:136` / `history_points.go:319` | 空页（已知） |
| **最新值 as-of 基线** | `device_data_sensors.go:167/175` | 历史行 sensors 丢（**已发生**，见 §8） |
| **`/nodes/:id/latest`** | `handler_data.go:134/138` | **每次请求直查 DB，无缓存** |
| 设备列表 latest 兜底 | `handler_edge_device.go:439` | 仅对 missed 查 |
| overview latest 兜底 | `handler_overview.go:96` | 仅对 missed 查 |
| 启动预热 | `main.go:516`（全表 DISTINCT ON） | 每次启动扫全部剩余分区 |

**关键区分**：这些读者需要的是「每设备每字段一行最新值」，**不需要任何历史**。

所以下一轮正确的做法**不是**「停写 unified_data」，而是：
```
1. 把「最新值」查询迁到 latest-value 缓存 + 帧表兜底
2. 给 /nodes/:id/latest 加缓存（现在是唯一无缓存、每次直查的：实测 0.863s）
3. warmup 限定时间窗（现在全表 DISTINCT ON）
4. 上面做完，才谈停写 unified_data 的历史部分
```

生产实测这几个读者目前都正常（`/nodes/1/latest` 0.863s、`/edge-devices/14/latest-data` 0.003s、`/overview` 0.153s）。

## 8. ⚠ 删表引入的一个功能回归（已定位，修复中）

`GET /api/v1/edge-devices/:id/data`（前端 `DataPanel.vue` 的「解析数据」列）的历史行丢失 sensors：

```
10 月行 → 键 = [channel_id, raw_hex, timestamp]          sensors = 0    ← 回归
11 月行 → 键 = [channel_id, raw_hex, sensors, timestamp]  sensors = 29
```

根因：sensors 合成走 `unified_data` 的 as-of 查询（`timestamp <= 本行时刻` 的最新值），
10 月删了就是空。

修法：改成从**帧表**合成（帧表是全字段的长期存储），unified_data 仅作过渡期回落。

**这条是「删表前演练」的漏网**：我只演练了图表接口，没演练列表接口。
教训：演练要覆盖**所有读被删表的接口**，不只是主路径。

### 8.1 已修复（b552de95，已验证）

改用**帧表合成**：整页解码一次 → 每行取「本行时刻前最后一个帧的全部字段值」；
帧表不可用才回落 unified_data（三层回落）。

```
修复前  10 月行 → sensors = 0
修复后  10 月行 → sensors = 29，29 个全部有单位
        11 月行 → sensors = 29，29 个全部有单位（对拍一致）
```

顺带把「每行一次 SQL」换成「一次解码服务整页」：50 行 **3.6 ms**。

**过程中还抓到一个潜伏 bug**：第一版用 `DecodeRangeAnchored`（内部套 `MaxDecodeWindow=24h`），
页内跨度 > 23.83h 时会 RangeTooLarge ⇒ 回落 ⇒ 10 月行仍丢 sensors。换算：
```
page_size=200 时：10 行/小时 → 跨度 20h  OK
                  8 行/小时 → 跨度 25h  FAIL
                  1 行/小时 → 跨度 200h FAIL
```
改用 `DecodeRangeAnchoredBounded`，maxWindow 按页内跨度给（页内跨度由 page_size 决定，不是恶意输入），
maxFrames 仍用生产值。

**生产实测当前不触发**（设备 2,332~6,638 行/小时，远高于 8.4），但下一台温湿度传感器（1 次/5 分钟）就会踩。
