# OTA 缺陷登记：升级成功但后端永远收不到成功（2026-10-12 台架实测）

> 设备：ESP32-C6 `F0F5BD02F35C`（8MB=C6N8）　后端：本机 3.0（8081/8443）
> 发现方式：真机完整 OTA 闭环 + 观察后端状态收敛

## 摘要

OTA 本身**成功**（下载、校验、A/B 切换、重启、mTLS 重连全部通过），
**但后端任务永远停在 `installing`，30 分钟后被判 `timeout`。**

⇒ **运维看到"升级失败"，而设备其实已成功升级。** 属"静默不一致"，
且分叉方向是**假失败**。

根因是**两个独立缺陷叠加**。

## 缺陷 A：固件版本号硬编码，OTA 后仍报旧版本

```
esp32-collector/CMakeLists.txt:13:  set(PROJECT_VER "2.8.0")
```

实测（设备 OTA 后重启，Hello 上报）：

```
[F0F5BD02F35C] Hello: fw=2.8.0 model=esp32c6 channels=0 ... proto=2.6
```

而目标固件版本是 `2.9.0-otatest`。

后端有一段自动完成兜底（`backend/internal/ota/ota.go:706`）：

```go
if task.ToVersion != "" && task.ToVersion == firmwareVersion {
    task.Status = StatusSuccess
    task.Progress = 100
    task.ErrorMsg = "Auto-completed via Hello (device reported target firmware)"
}
```

⇒ 固件永远报 `2.8.0`，该兜底**永不匹配**。

### 影响

- 后端无法感知设备已升级（`nodes.firmware_version` 长期停在旧值）；
- OTA 任务无法经 Hello 路径收敛；
- `AutoRollback` 找 `lastSuccess` 的逻辑受影响。

## 缺陷 B：回滚保护关闭 ⇒ `status=2`（成功确认）永不发送

```
esp32-collector/sdkconfig.defaults:220:  CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=n
```

固件侧成功确认链路（`main/main.c`）：

```c
// main.c:556
if (esp_ota_get_state_partition(running, &ota_state) == ESP_OK) {
    if (ota_state == ESP_OTA_IMG_PENDING_VERIFY) {
        s_ota_pending_verify = true;          // <- 唯一置位点
    }
}
// main.c:574
s->ota_need_confirm = s_ota_pending_verify;
// main.c:331-332
if (s->ota_need_confirm && status_err == ESP_OK) {
    if (ota_confirm_valid() == ESP_OK) s->ota_need_confirm = false;
}
```

`ota_confirm_valid()` 成功后才会发 `OtaProg status=2`。

**IDF 语义**（`bootloader_utility.c:444-450`）：

```c
#ifdef CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE
    if (otadata[active_otadata].ota_state == ESP_OTA_IMG_NEW) {
        otadata[active_otadata].ota_state = ESP_OTA_IMG_PENDING_VERIFY;
    }
#endif
```

宏未定义 ⇒ **`PENDING_VERIFY` 永不写入** ⇒ 固件分支永不进入。

### 四层互相印证

| 层 | 证据 |
|---|---|
| IDF 源码 | 写 `PENDING_VERIFY` 的代码在 `#ifdef CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` 内 |
| 构建配置 | `sdkconfig.defaults:220 =n`；产物 `# CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE is not set` |
| 串口日志 | 重启后**无** `running partition is PENDING_VERIFY` 行 |
| **otadata 二进制** | `ota_state=2 (VALID)`，**非** `PENDING_VERIFY` |

otadata 读回（`offset 0xd000`，`len 0x2000`）：

```
otadata[0]: ota_seq=0x00000001 ota_state=2 (VALID)        crc=0x4743989a
otadata[1]: ota_seq=0x00000002 ota_state=0xFFFFFFFF (UNDEFINED) crc=0x55f63774
```

### 后果

`backend/internal/ota/ota.go:623-624`：

```go
case WireSuccess:   // = 2
    task.Status = StatusSuccess
```

永不执行 ⇒ 任务停在 `installing` ⇒ 30 分钟后 `timeoutScanner` 判 `timeout`
（`timeoutThreshold = 30 * time.Minute`）。

## 叠加净效果

| 时刻 | 设备实际 | 后端显示 |
|---|---|---|
| T+0 | OTA 下载中 | downloading 0→100% |
| T+55s | 校验通过、A/B 切换、重启 | installing 100% |
| T+60s | mTLS 重连、Hello（fw=2.8.0） | 兜底不匹配（2.8.0 ≠ 目标） |
| T+30min | **正常运行新固件** | **status=timeout** |

## 修复方向（未实施，待决策）

### 缺陷 A

把 `PROJECT_VER` 与 OTA 目标版本解耦：构建时按发布版本注入（CI 传参），
而不是硬编码在 `CMakeLists.txt`。

### 缺陷 B（两个选项）

1. **启用回滚保护** `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`
   —— 恢复 `PENDING_VERIFY` 语义，`status=2` 链路自动打通；
   代价：引入回滚保护语义，需确认"自检 3 次失败即回滚"的判定符合预期。
2. **解耦确认与回滚**：`ota_need_confirm` 的判据改为不依赖 `PENDING_VERIFY`
   （例如启动时 `ota_get_nvs_state() != 0` 即需确认）。
   改动更小，但需确认在"回滚保护关闭"时不会误报。

## 为什么此前没被发现

- 单元测试不覆盖"**重启后状态收敛**"（各层分别测，接缝没测）；
- 只看串口"OTA 成功"就收工会漏掉"后端永远收不到成功"这一半；
- 属本项目反复记录的教训：**"固件刷进去了" ≠ "系统知道它刷进去了"**。
