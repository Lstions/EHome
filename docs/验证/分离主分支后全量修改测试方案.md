# 分离主分支后全量修改测试方案（multi-bus 分支）

## 1. 范围与结论边界

本方案针对 `codex/multi-bus-event-driven-plan`，不是 `codex/edge-control-worktree`。

```text
共同基线：9a20c63
测试分支：codex/multi-bus-event-driven-plan
当前 HEAD：7526588
提交范围：9a20c63..7526588，共 50 个提交
```

本文件是 [多总线事件驱动测试验证方案](多总线事件驱动测试验证方案.md) 的全量回归补充，覆盖分离主分支后的所有代码影响面：

- multi-bus：动态 controller lease、manifest 资源预检、UART event-driven RX、control/sample 队列、report task、DMA、SPI/I2C controller 推导、运行时 ResourceReport 和性能指标；
- 后端：统一 Driver/Action、CommandExecution、确认、幂等、Inbox/Outbox、通道租约、UNKNOWN、审计、认证、配置和 API；
- 固件协议：ChannelCmdV2、ConfigManifest、ResourceReport、DataReport、WriteCmd 兼容路径、frame varint 和边界错误；
- 前端：登录、设备详情、受控操作、WebSocket 操作时间线、监控、缓存和真实 SN-3001 浏览器流程；
- 基础设施：Docker/Makefile/CI、C6/S3 构建脚本和验证脚本。

本方案不解除现有门禁：高风险 setter/reset/BMS/清零、持久 NVS at-most-once、完整断电 replay、未完成的 legacy 初始化迁移，必须以“正确拒绝”或“未完成”记录，不得用模拟成功代替实机证据。

关键影响点不变量：

1. 一个逻辑 Channel 在任一时刻只有一个有效物理 lease；旧 generation 的事件不能投递到新 Channel。
2. UART0/UART1 的 planner、worker、RX、DMA、错误恢复和上报路径等价，业务不能依赖 controller 编号。
3. control/critical report 不得因 telemetry/sample 背压而丢失；数据丢弃必须可计数、有 discontinuity 语义。
4. `dma_requested`、实际 driver 模式、ResourceReport 和后端 capability 必须一致。
5. 同一用户意图最多创建一个物理操作；ACK/Final 必须绑定 command、attempt、boot、digest、channel。
6. 生产环境无法证明安全的动作必须不可用或拒绝，不得因开发环境变量绕过门禁。

## 10. 生产环境 API 验证

### 10.1 生产安全约束

- 使用最小权限测试账号和经批准的专用节点；不直接写生产数据库。
- 正向测试只做 GET、健康检查、能力查询、状态查询和一次明确批准的低风险 read。
- 禁止生产执行地址/波特率修改、清零、reset/reboot、BMS、Techfine setter、GPIO/PWM 输出、raw terminal、OTA 和 batch。
- 对不可用高风险 API 做“拒绝测试”即可；通过条件是 403/409/429 和无 Execution/Attempt/Outbox/物理发布。
- 任何会改变设备/配置的请求必须先有审批、快照、恢复值和观察窗口；条件不足直接标记未执行。

| PROD-API-08 | 若批准：`POST /api/v1/nodes/$NODE_ID/query-resources`、`ping` | 只产生查询/探测，不创建设备动作 |
| PROD-API-09 | 若批准：一次 `POST /api/v1/edge-devices/$EDGE_ID/operations`，带唯一 `Idempotency-Key`，仅使用 available read | 202；command 可追踪至 verified Final；无重复发布 |
| PROD-API-10 | 重发 PROD-API-09 完全相同 body/key | 同 command 或明确 replay；不新增物理命令 |
| PROD-API-11 | 提交 unavailable setter/reset/BMS 或请求 confirm | 403/409/429；无可发布 Execution、Attempt、Outbox、MQTT 下发 |
| PROD-API-12 | `GET /api/v1/metrics/prometheus`，logout 后再访问 account | 指标符合策略；退出后旧 JWT/session 失效 |

生产证据包括脱敏 HTTP、command/attempt/digest、broker/设备日志、前后状态摘要、拒绝项无下发证据和清理结果。没有专用设备时 PROD-API-09/10 必须写“未执行”，不能写“通过”。

## 14. 通过、缺陷和执行顺序

### 14.1 发布阻断

以下任一项失败即阻断：重复物理下发、错误成功、响应串 Channel、lease/DMA/ResourceReport 不一致、critical report 丢失、未解释 sequence gap、配置失败无法恢复、heap/task/block 泄漏、watchdog/panic、生产越权、真实浏览器闭环未执行却宣称通过。

高风险动作、NVS durable replay、完整 R1/R3/R5/R8/R9/R10 以外的未实现能力必须保持 fail-closed；“拒绝”是安全门禁通过，不是功能完成。

### 14.2 证据记录

每个用例记录：测试 ID、commit、环境/构建 SHA、输入配置、预期/实际、日志、HTTP/MQTT/串口/DB 证据、command/attempt/digest、截图/HAR、缺陷编号、清理和回滚结果。

### 14.3 执行顺序

1. 固定 `7526588` 和构建 SHA，完成 L0。
2. 完成后端、固件 Host、前端白盒；运行全部 CTest target。
3. 执行 DB/MQTT/host 集成和错误注入。
4. 执行 C6/S3 构建，再按 UART 交换、DMA、SPI/I2C、SN3001 实机矩阵执行。
5. 执行性能、断线、重启、租约和回滚测试。
6. 执行生产 API 只读/拒绝验证。
7. 执行真实浏览器操作，保存 Network/HAR/Console/截图。
8. 复查 Outbox、audit、metrics、设备配置和 worktree 清理，输出最终报告。
