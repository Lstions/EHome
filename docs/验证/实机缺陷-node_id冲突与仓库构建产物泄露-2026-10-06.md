# 两块 C6 node_id 冲突（已修）与公开仓库构建产物泄露（已摘除）— 2026-10-06

> 来源：现场报「两个 ESP32-C6 都在线、后台重叠」。本文同时记录根因、修复、
> 验证证据，以及审计中发现的公开仓库泄露与**未完成项**。

## 一、node_id 冲突：两块不同 C6 算出同一个 ID

### 现象

- 后端节点列表同时出现两个在线 C6；同一 `node_id` 反复 online/offline。
- 串口实测：MQTT 每 **5.1 s** 断开重连一次（45 s 窗口内 5 次连接 / 4 次断开），
  每次重连 Hello 都被服务端**接受**（`HelloAck accepted=1`）后又被踢。

### 根因（IDF 源码 + 实机 efuse 双向确认）

`main/app_state.c:generate_node_id()` 用 `esp_efuse_mac_get_default()` 取 MAC，
再只格式化**前 6 字节**。但该 API 在带 IEEE 802.15.4 的芯片上有额外一步
（`components/esp_hw_support/mac_addr.c:256` → `insert_mac_ext_into_mac()`）：
把 `mac[3..4]` 覆盖为 `MAC_EXT` efuse（`0xFFFE`），真 MAC 的 `mac[3..5]` 被挪到 `mac[5..7]`。
于是**能区分两块芯片的字节正好被丢掉**：

```
两板 MAC_FACTORY efuse:  bd 02 dd 84 ff fe f0 f5   (ttyACM2)
                        bd 02 f3 5c ff fe f0 f5   (ttyACM0)
旧代码算出 node_id:      F0 F5 BD FF FE 02         ← 两板完全相同
```

实机 efuse dump 佐证：`MAC_SPI_8M_0 dump: bd02dd84 fffef0f5` vs `bd02f35c fffef0f5`。
`fffe` 是常量，真正的身份是第三/四字节。

### 为什么表现为「互踢」

`node_id` 同时是 **MQTT client_id** 与**主题前缀**（`nodes/<id>/up|down|control`）。
两板同 ID ⇒ 同 client_id ⇒ broker 后到者顶掉先到者，5 s 重连循环。

### 决定性实验（可复现）

| 实验 | 结果 |
|---|---|
| 全新 client_id 连生产 broker，保持 25 s（含定期 PINGREQ） | **无任何断开** |
| 全新 client_id 连上后**完全不发包**（真 idle）20 s | **无断开** ⇒ broker 不会因空闲踢人 |
| 换用设备 client_id `F0F5BDFFFE02` 连接 | **t=4.89 s 被 EOF 踢出** ⇒ 存在竞争客户端 |

⇒ 排除网络/broker 问题，坐实「同 client_id 抢号」。

### 修法

改用 `esp_read_mac(mac, ESP_MAC_WIFI_STA)`。IDF `mac_addr.c` 中该分支是
`memcpy(mac, base_mac_addr, 6)`，**不做** MAC_EXT 插入；实机 `wifi:mode : sta(...)`
打印值与之一致且三块板互不相同。

**兼容性**：无 802.15.4 的 S3 不受影响 —— 现场 S3 `30EDA0A9A808` 刷机前后 ID 不变
（实测 STA MAC `30:ed:a0:a9:a8:08`）。

### 验证证据

| 项 | 修复前 | 修复后 |
|---|---|---|
| node_id（ttyACM2） | `F0F5BDFFFE02` | `F0F5BD02DD84` |
| node_id（ttyACM0） | `F0F5BDFFFE02` | `F0F5BD02F35C` |
| 45 s 内 MQTT 断开次数 | 4 | **0** |
| broker 上不同 node_id 数 | 2（含重复） | **3**（`30EDA0A9A808` / `…DD84` / `…F35C`） |

- **变异自证**：把 `app_state.c` 改回 `esp_efuse_mac_get_default()` 重编，用例转红并复现症状：
  `FAIL test_node_id_is_unique_per_chip:363: 两块不同 C6 的 node_id 必须不同` … `5 FAILURES`；
  还原后 md5 与变异前一致（`4fd69a8d…`），47/47 宿主机用例全绿。
- 三 profile 实编通过：`c6-n8` / `s3-n16` / `s3p-n16`，IRAM 门禁均 OK。

## 二、需要现场决策的遗留项（本轮未做）

### 1. 幽灵节点行 `F0F5BDFFFE02` 仍在库里（目前 offline）

后端节点表**以 node_id 字符串为主键语义**，改 ID 必然新增行（现 4 行：S3 + 幽灵 + 两个 C6）。
该幽灵行历史上被**两块** C6 共用，其名下的历史数据/通道配置无法归属到任一真实设备。
删除需 `DELETE /api/v1/nodes/:id`（硬删）；**删前务必确认其历史数据是否需要保留**。
本轮**未自动删除**，以免误删两板共用期间的数据。

### 2. 新增的两个 C6 需要重新下发通道/设备配置

新 node_id 是全新节点，原挂在 `F0F5BDFFFE02` 下的 edge-device/通道不会自动继承。
独立佐证：`/api/v1/firmwares` 里 C6 固件库为空，且新节点 `channels=0`。
（ttyACM0 那块虽连在 192.168.110.x，仍能到达 192.168.20.6 的 broker，已实测在线。）

### 3. `ehome_nodes_online` 指标是陈旧值（**既有缺陷，与本轮无关**）

`backend/internal/nodemgr/manager.go:209-212` 只在 `NewManager` 时 `Set()` 一次，
全仓无 `Inc/Dec` ⇒ 该 gauge 永远是**进程启动时**的在线数。
实测：DB 里 3 节点 online，该指标仍报 `2`（启动时只有 2 个）。
前端若读它会长期显示错误的在线数。属独立缺陷，建议单独立项。
（`handler_metrics.go:171` 另有 `_ = metrics.NodesOnline // suppress unused`，可见该指标处于半废弃状态。）

## 三、公开仓库泄露（已摘除，但历史仍在）

仓库 `Lstions/EHome` 为 **public**。审计发现 **17687 个构建产物文件 / 554 MB** 被跟踪并已推送，
最早由 `6e778c95` 引入：

| 泄露内容 | 位置 | 值 |
|---|---|---|
| Wi-Fi 明文口令 | `.fwbuild_netperf*/s3-n16/sdkconfig` | `sunwork123` |
| 生产 MQTT 地址 | `…/.broker.defaults` | `mqtt://192.168.20.6:1883` |
| 可 strings 提取的 elf | `.fwbuild_netperf*/s3-n16/ehome_collector.elf` | 5.7 MB |

旁证：`gh api repos/Lstions/EHome/contents/.fwbuild_netperf/s3-n16/sdkconfig` 曾返回 size 94099。

**根因**：`.gitignore` 只写了 `.fwbuild/` `.fwbuild_c6/` `.fwbuild_probe/` `.fwbuild_fallback/`
四个**具体名字**，漏掉 `.fwbuild_netperf` / `_candA` / `_empty_ssid`；且 `.gitignore` 对
**已跟踪**文件无效。这是该文件注释里第三次记录的同类事故 —— 共同模式都是
「规则只写了一半却以为写全」。

**已做**：`git rm -r --cached` 三个目录（仅取消跟踪，磁盘文件保留）+ 规则改通配 `.fwbuild*/`
（已验证真实路径命中，且覆盖 `.fwbuild_c6_61` 这类此前漏网的新名字）。
验证：`gh api …contents/.fwbuild_netperf/s3-n16/sdkconfig?ref=main` 现返回 **404**。

**未做（需人工决策）**：

1. **历史 blob 仍在** —— 本次只让 HEAD 不再提供；彻底清除需 `git filter-repo` + force push
   （改写全部 commit hash，且本仓有并发提交者，需协调）。
2. **已公开的凭据必须轮换** —— `EHOME_JWT_SECRET`（`deploy/blackbox/evidence/` 历史中的 46 字符密钥，
   可伪造管理员令牌）、PG 口令 `ehome123`、Wi-Fi 口令 `sunwork123`。**历史清除不能替代轮换。**
3. `esp32-collector/components/wifi_mgr/Kconfig` 仍把真实 Wi-Fi 口令写成 `default`
   （`sunwork123`），建议改为每部署注入（与 `mqtt-broker.defaults` 同模式）；
   因空 SSID 会触发已知 SoftAP 分支问题，属设计改动，需单独评估。
4. `backend/config.yaml` 的 `password: ehome123`、`.github/workflows/test.yml` 的
   `POSTGRES_PASSWORD: ehome123` 属 CI/本地默认值，建议改为显式占位符以免被误当生产口令。
