## 3. 三条核心分支的行为

### ① ready=true（正常路径，不得回归）

- 渲染 `ErrorBoundary > NetworkBanner > RouteProgressBar > router-view`，顺序与改造前一致（有单测逐节点断言）。
- **首次探测就 ready 时不 reload** —— 否则每次正常打开应用都会整页重载一次，形成自我循环（单测钉住 reload 未被调用）。

### ② ready=false（维护期）

- `<Maintenance/>` **替换** router-view（业务路由完全不参与，未登录也不会被守卫弹去 /login）。
- 总进度条按 `percent`；阶段列表五态：pending 灰 / running 主色+转圈+步骤内进度条 / done 绿勾 / failed 红 + error 文本 / skipped 灰删除线。
- 已耗时：服务端 `elapsed_ms` 为基准 + 前端每秒 +1s（**只增不减**，防时钟回拨）。
- 版本 + 短 commit（7 位）小字。
- 轮询 2s；**就绪后 `location.reload()`**。

### ③ 请求失败（后端未监听 / 已崩）

- **仍渲染维护页**，文案「正在连接服务器 / 无法连接服务器，正在重试…」，绝不展示正常页。
- 轮询**永不停止**，退避 2s → 3s → 5s 封顶（单测按毫秒断言每个档位）。
- 失败时**保留上一份快照**：从「启动失败：xxx」不会退化成一片「连接中」把原因抹掉。
- 后端恢复 → 自动 `reload()` 回正常页（单测覆盖"失败 2 次后 ready"的完整链路）。

## 4. 两条 fail-open（Lead 已裁决接受，附推理链）

| 触发条件 | 行为 | 为什么必须这样 |
|---|---|---|
| 后端 404 / 返回非 envelope / 非快照 | 直接进正常页 | 旧后端与 **vite preview 静态托管**没有该接口。不放行的话，既有 `e2e/render-contract.spec.ts`（用 vite preview 跑）会被**永久锁在维护页** |
| 收到 401/403 | 直接进正常页 + 挂**看门狗**（5s） | 维护期后端对业务请求统一回 **503**，而 `/api/v1/system/maintenance` 是免鉴权白名单的一员 ⇒ 维护引擎**不可能**对它回 401/403。能收到 401/403 说明请求已穿过维护引擎、打到完整引擎的鉴权中间件 ⇒ **全量路由已注册完成，后端已完全就绪**。不是"凭次数放行"，是凭状态码语义 |

看门狗细节：放行后继续 5s 轮询；若拿到**合法的 ready=false 快照**（后端重启又进维护态），把用户**带回维护页**；
网络抖动则不回切（那是业务页错误横幅的职责）。三条都有单测。
**503 绝不放行**（单测：`503 是维护期的正确信号：绝不能放行`）。

## 5. 首次探测宽限期（Lead 已裁决接受，附耗时记录）

- `PROBE_GRACE_MS = 800`（`progress.ts`）。正常启动探测只需几十毫秒；无宽限期则每次正常打开都会**闪一帧「系统升级中」**。
- 宽限期内**不渲染维护页、也不渲染业务内容**，渲染**与维护页同构的轻量骨架**：
  品牌 logo + 名称 + 转圈 + 「正在检查系统状态…」，带 `role="status" aria-live="polite"`。
  ⇒ **"无内容可见"的上限 = 800ms，且这 800ms 内始终有可见内容，不是白屏。**
- 宽限期内收到响应立刻按响应处置（不等宽限期走完）。
- 宽限期到点仍无响应 → 切维护页的「连接中」态（`connectionFailed=true`，文案「正在连接服务器」），不再停留在骨架。
- 两个方向都有单测：骨架存在且有内容 / 到点切"连接中"。

## 7.1 联调前主动加固：Go null slice 陷阱（交付后补）

在等真实后端联调时复核了 Go 侧的序列化细节，发现一处**类型系统看不见、联调才会炸**的缝隙，已加固：

`var steps []Step` 为 nil 时 `json.Marshal` 得到的是 `"steps": null` 而**不是** `[]`。
我原来的 `isMaintenanceSnapshot` 要求 `Array.isArray(steps)` —— 一旦后端某个路径返回 nil steps，
前端会判「不是合法快照」→ **fail-open 直接进业务页** → 维护期用户撞满 503。这是最坏方向。

加固内容（`src/api/system.ts`）：
- `isMaintenanceSnapshot`：**只要求 `ready` 是布尔**；`steps` 缺失/null 视为合法（归一成 `[]`）；
  `steps` 存在但非数组仍判非法（那是真形状不对）。
- 新增 `normalizeSnapshot()`：`steps:null → []`、`percent/elapsed_ms/current_*` 缺失 → 安全默认值、
  步骤内 `progress/weight` 缺失 → 0（防 `NaN%`）。
- 单测补 4 条（含「steps 为 null 的正常快照 → 成功返回且 steps 归一成 []」）。

推而广之的判据：**fail-closed 只应该用在「我无法决策」的地方**（ready 缺失），
不能用在对「空集合」的严格性上 —— 对空集合严格会把用户推进更坏的状态。

## 7.2 空值兜底加固（交付后补，Lead 联调前提醒）

### ① `current_label` / `current_step` 可能为空（契约允许，failed 时尤甚）

原实现 `if (label) return '当前阶段：'+label; return '总体进度'` —— 不会渲染悬空标签，但会把「停止在某一步」误述成「总体进度」。
加固后（`progress.ts: currentStageText()`）：

| 情形 | 文案 |
|---|---|
| 有 current_label | `当前阶段：补齐父表索引` |
| 空 / undefined / 纯空白 | `当前阶段：已停止` |
| failed=true（优先级最高） | `中断时的总体进度` |

`failed=true` 时 percent 停在任意值（12/50/99）都**如实显示**，并有参数化用例逐个钉住。

**顺带修的同类缺口**：阶段列表原本裸渲染 `{{ step.label }}`，空 label 会渲染成**一行什么都没有**（比悬空标签更糟）。
新增 `stepDisplayLabel(step)`：label 非空 → label；空 → **回落 id**（`parent_indexes` 这类 id 用户报障时有用得多）；id 也空 → `—`（全站占位符规范）。失败摘要用同一函数。

### ② `started_at` 缺失会不会算出 NaN 秒

**不会 —— 组件完全不解析 `started_at`**：
`grep "new Date|Date.parse|getTime()" views/maintenance/ api/system.ts` → **零命中**。

已耗时**唯一来源是 `elapsed_ms`**：`watch(() => snapshot?.elapsed_ms)` → `Math.max`（只增不减）→ `formatElapsed`；
且 `formatElapsed` 内还有 `Number.isFinite && > 0` 兜底，负数 / NaN / Infinity 一律渲染成「0 秒」。

两个方向都有用例：`started_at: 'not-a-date'` + `elapsed_ms: 7000` → 显示「7 秒」且不含 NaN/Invalid；`elapsed_ms` 整个缺失 → 「0 秒」。

### 变异验证（证明新用例不是恒真）

| 变异 | 结果 |
|---|---|
| `stepDisplayLabel(step)` 改回 `step.label` | 「步骤 label 为空 → 回落 id」变红 ✅ |
| `currentStageText` 改回原逻辑 | 「current_label 为空 → 当前阶段：已停止」变红 ✅ |
