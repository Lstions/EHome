## 3. 根因定位（逐层排除）

### 3.1 排除：驱动解析 bug

用协议文档 [SN-3001-GYL-N01通信协议.md](../archive/v4.0-重建前归档/协议/SN-3001-GYL-N01通信协议.md) 的**黄金帧**跑 `SN3001RainDriver.ParseData`（`backend/internal/drivers/builtin.go:363-386`）的判据：

```
TX: 01 03 00 00 00 01 84 0A   → CRC 0x0A84 == 计算值 ✅
RX: 01 03 02 00 0A 38 43      → CRC 0x4338 == 计算值 ✅

驱动判据逐条：
  1) len(raw)=7 >= 5                        ✅
  2) raw[0]=0x01 == 0x01 && raw[1]=0x03     ✅
  3) dataLen=0x02=2; 3+2+2=7 == len=7       ✅
  4) CRC LE: got 0x4338 == want 0x4338      ✅
  5) dataLen == 2                            ✅
  ⇒ 解析成功，rainfall = 0x000A/10 = 1.0 mm
```

**⇒ 驱动完全能解析协议文档的合法响应。不是驱动的错。**

### 3.2 排除：设备回应了但内容不对

```
实际唯一"成功"帧 raw = 1e 07 07 3e e6 ff ff  (7 字节)
  raw[0]=0x1e  期望 0x01 (从机地址)     ❌
  raw[1]=0x07  期望 0x03 (功能码)       ❌
  raw[2]=0x07  dataLen=7，期望 2         ❌
  CRC LE: got 0xffff，want 0x5dad        ❌（任何切法都对不上）
```

| 切法 | 计算 CRC | 帧尾 LE |
|---|---|---|
| 前 3 字节 | 0x3452 | 0x0707 |
| 前 4 字节 | 0x2d34 | 0x3e07 |
| 前 5 字节 | 0x5dad | 0xe63e |
| 前 6 字节 | 0xfddc | 0xffe6 |
| 前 7 字节 | 0xd9bc | 0xffff |

**⇒ 没有任何切法 CRC 自洽。这不是 Modbus 响应，是 4800 8N1 线路上的噪声/浮空读法**（末两字节 `ff ff` 是浮空线的典型上拉读法）。

⚠️ **同时这也暴露了一个固件侧缺陷**：固件把「收到字节但内容非法」报成了 `error_code=0`。`error_code=0` 的语义应该是"成功采样"，而这一帧根本不是合法响应 —— **固件缺少"响应合法性"判据（至少 CRC 校验）**。

### 3.3 确认：RX 全程超时

`error_code=0x01` 在固件里是**唯一**的 RX 超时发射点：

```c
// esp32-collector/components/bus_worker/bus_worker.c:19-20（文件头注释）
// P1-6: RX timeout drain — if a pending cmd has rx_timeout_ms > 0 and no
// data received within that window, rx_task emits DataReport with error_code=0x01.

// bus_worker.c:2276-2313（实际发射点）
if (elapsed_ms <= (int64_t)pcmd.rx_timeout_ms) continue;
...
  report_enqueue(rt->bus_ch[i], (uint64_t)now_us, ++s_rx_sequence[i], NULL, 0, 0x01,
                 pcmd.request_id, pcmd.edge_device_id, pcmd.command_template_id,
                 pcmd.command_index);
```

且 `report_enqueue` 的第 4 个参数是 `raw`、第 5 个是 `raw_len`，这里传 `NULL, 0` ⇒ **raw 必然为空**，与数据侧 `raw=""` 完全吻合。

**⇒ 根因确定：设备（或它的 RS485 物理链路）在 18.8 天（2026-10-18 08:47 ~ 2026-11-06 04:13，精确 18 天 19 小时 26 分）里从未回应过一次合法的 Modbus 请求。**

### 3.4 排除：后端没有下发请求

如果后端根本没下发，通道就不会有轮询，也不会有 `sequence` 递增的 17,278 帧/天。而且：

- `config_templates` 有且仅有 1 条（id=692），`edge_device_id=16`；
- `channels.template_ids = '692'`，通道启用；
- `device_data.command_index` 恒为 0（单指令设备）。

⇒ **后端下发链路是通的**。

### 3.5 证据链总览

```
  后端：expanded manifest → ch12 (UART1, 4800, tx20/rx21) → template 692: 01 03 0000 0001 840A ✅
    ↓
  固件：scheduler 每 5.0 s 发一次 → rx_task 等 1000 ms（bus_worker.c:1287：CMD_SAMPLE 固定 rx_timeout_ms=1000）
    ↓
  总线：SN-3001 @4800 8N1（协议文档：出厂默认 4800 ✅，从机地址 1 ✅）
    ↓
  设备：不回应（或回应非 Modbus 数据 —— 18.8 天内仅 1 次，且那 1 次是噪声）
    ↓
  固件：error_code=0x01, raw=""  → MQTT DataReport
    ↓
  后端：ShouldPersist()=true（!IsPassive）→ DBPersistConsumer 写 device_data（device_id=0，consumers_heavy.go:100-127）
        ShouldParse()=false（ErrorCode!=0）→ SensorParserConsumer 不处理（:307-309）→ unified_data 0 行 ✅ 正确
        edge_devices.error_code 由 StatusReport 的 EdgeDeviceHealth 置 3（FAULT），永不回 0
```

## 4. 为什么"静默 18.8 天没人发现"（比存储更严重）

| 检查项 | 结果 | 说明 |
|---|---|---|
| `edge_devices.status` | `offline` ✅ 有标记 | 但这只是"最后一次数据的时间"推导，不代表告警 |
| `edge_devices.error_code` | `3`（FAULT）✅ 有标记 | 同上，只在 UI「异常」列可见 |
| `alert_rules` | **0 行（全库）** | **没有任何阈值告警规则被配置** |
| `notifications` | **0 行（全库）** | 从未发出过通知 |
| `node_logs`（节点 `F0F5BD02F35C`） | **0 行**（全库 0 行） | 该节点 `log_stream_enabled=f`、`log_persist_enabled=f` ⇒ 日志从未上传（与 device14 所在节点 `F0F5BD02DD84` 设置相同，全库都没有日志） |
| 文档记录 | 有 —— [雨量计静默事故-根因与修复方案-2026-09-22.md](../评审/雨量计静默事故-根因与修复方案-2026-09-22.md) | 2026-09-22 有过同型号事故（`error_code=1` 3714 帧），**根因不同**（那次是 FreeRTOS QueueSet 自锁，复位即恢复） |

⚠️ **重要区分**：2026-09-22 那次事故的机制是「QueueSet 成员必须为空 ⇒ 自锁」，症状也是 `error_code=1 raw=""`。本次是否同一缺陷？**证据不支持**：

| 判据 | 09-22 事故 | 本次（10-18 起） |
|---|---|---|
| 持续时间 | 7 小时，手动复位后立即恢复 | **18.8 天，无恢复** |
| 复位是否解决 | ✅ 是 | ❌ 未记录尝试过 |
| 节点 | (旧库，edge_devices.id=1) | `F0F5BD02F35C`（未变） |
| `error_code=0` 帧数量 | 故障期间 0 帧 | **1 帧**（噪声，非真恢复） |

⇒ **更可能是物理层/接线问题**（RS485 A/B 接反、屏蔽接地、从机地址错、供电），而非 09-22 的固件自锁。**这需要现场检查才能定案**（见 §6）。

### 5.3 结论：存储不是问题

**0.28 GB/月 在 18.66 GB/月的总盘子里完全可忽略。** 这件事的价值在于：

1. **数据完整性**：一台现役设备 18.8 天的雨量数据**永久丢失**（雨量是累计量，无法补采）；
2. **可观测性**：`alert_rules` 全库 0 行 ⇒ **任何设备静默都不会告警**，这是系统级缺陷，不止 device16；
3. **对存储方案的影响**：方案 §1.1 的基线（2,811,888 行/天）**不含 device16**，若它修好，基线会变成 2,811,888 + 17,278 = **2,829,166 行/天（+0.6%）**，L1/L2 的收益数字需微调但结论不变。

## 8. 局限性

1. **无固件日志**：`node_logs` 该节点 0 行（`log_stream_enabled=f`），无法从固件侧看到 `RX timeout slot1` 的实际打印。根因判定依赖「`error_code=0x01` 的唯一发射点」这一代码事实 + 数据侧统计。
2. **无现场信息**：未到现场确认 RS485 接线/供电/地址，§6 建议 1 是**推断**而非确诊。
3. **未做物理层实验**：无法判断是"设备不回应"还是"回应被线路吞掉"（二者在 `error_code=1 raw=""` 下不可区分）。
4. **09-22 事故的对照基于文档**：那次事故的 `edge_devices.id=1` 与本次 `id=16` 是不同库/不同时期的记录，不能直接当同一台设备。
5. **"5.0 s/帧 vs interval_ms=10000" 未定位**：只给出两种假设，未读固件调度器源码定案。
