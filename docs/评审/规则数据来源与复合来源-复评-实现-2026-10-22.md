## ① N-12 的 build-tag 对照用例：机制可执行吗（5 项缺口）

方向成立（基线 fd7e6393 是当前 HEAD，可复现；E6 只需单设备 + logical 绑定，不依赖组表），但按现文 CI 跑不通：

1. **测试文件怎么进基线树**：带 build tag 的用例是 M0 提交新增的，基线 fd7e6393 里不存在 ⇒ CI 必须 git worktree 基线 → copy M0 的测试文件进去 → 再跑。N-12 没写步骤（copy 哪些文件、放哪、go 命令与 tag）。
2. **基线 API 约束**：copied test 只能用基线 API/测试助手，不能引用 M0 新增符号（SourceKind/GroupOptions/SourceRef…），否则基线编译失败＝红，但不是"行为红"，机制失去意义。需在 N-12 写"对照用例禁止依赖 M0 新增符号"并在脚本里用 go vet/编译白名单校验。
3. **"必须 FAIL"的判定方式**：只断言退出码非 0 会被"编译失败/启动失败"伪装成红。应断言具体失败形态：基线跑 ⇒ 无 executed 事件且出现 unresolved/condition_changed 行；M0 跑 ⇒ 恰有 1 条 executed。CI 写成"倒置断言"（expect non-zero + grep 事件行）。
4. **ID 分歧夹具从哪来**：要造 logical_id ∉ 所有 edge_device_id，需要直接写 logical_devices / 改 edge_devices.logical_device_id（无产品 API），与 §8.4"禁止 db.Create 直插"冲突。N-12 只说"合并链/序列错位"，未给可制造路径，也未声明该 e2e 的 DB 直插豁免 ⇒ E6 仍不可构造。建议：§8.4 明确"仅为 E6 造 ID 分歧允许 fixture 直写 logical/edge 行（不涉组表）"，或提供 test-only 助手并登记。
5. **基线库自检**：基线 schema 无 M0 列（source_kind/source_group_id）；对照用例不能用这些列构造（否则失败原因错位）。用例开头需显式断言"只用基线列"（或由 CI job 强制）。

## ④ H2/N-16 为什么是部分闭环（实测证据）

- 实测：TriggerEvent{ 在 automation 包测试中出现 **47 处 / 7 个文件**（planner_test.go 18、planner_multi_action_test.go 13、f5_residue_test.go 9、notify_wiring_test.go 3、pg_y_cascade_test.go 2、cooldown_anchor_test.go 1、notification_result_test.go 1），全部为命名字段字面量。Go 给结构体加字段不会破坏这些构造 ⇒ N-16 的"漏改测试点 ⇒ 编译红"**不成立**。
- 真实后果：F4 改读 ev.SourceEdgeDeviceID 后，这 47 处构造的零值会让 F4 走"取不到值 ⇒ unresolved/condition_changed"（静默 fail-closed，测试可能仍绿但语义已变），比编译红更隐蔽。
- 修法：a) 生产侧只允许一个 newTriggerEvent(rule, deviceID, at, ...) 构造器（语义放构造器里），禁止散落字面量（grep 门禁）；b) SourceEdgeDeviceID==0 的显式策略（拒绝复核/回落规则列/报错，三选一并测试）；c) "漏改"的保证改为行为断言（F4 用帧设备而非规则列），而不是编译错误。
