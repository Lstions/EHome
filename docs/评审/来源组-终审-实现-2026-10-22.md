## 回答提纲

**① 热路径性能**：evaluator 求值侧命中路径基本零 DB、零全局锁（sourceref 用 `atomic.Pointer` 读无锁；窗口锁是既有 per-evaluator mutex）：**MatchFrame 每规则每帧一次 atomic load + map 查询 + 成员线性扫描，可接受**；新增成本主要是 `deviceIntervalFn` 的 mutex（每规则每帧 1–2 次，实测量级 50–100ns）+ 偶发失败审计/健康回调（5min/1min 节流）。**不合格的是两处 DB 在路径上**：摄入侧 `GroupService.MarkSuccess` 每帧 JOIN 查询（B-3）与 deviceIntervalFn TTL miss（H-1）。**判定：deviceIntervalFn 每帧调用本身可接受，但应把 DB 移出帧路径。**

## 合进 main 最坏会发生什么（具体场景）

1. **管理员新建一条普通单设备自动化规则（不填 cooldown_sec）** → 落库 300s（B-1）。设备每 5s 上报且条件持续满足：旧行为首次动作后仍可按策略再次动作，新行为**5 分钟内静默不再执行**；用户会报"规则不生效/变慢"，排查难（DB 里看到 300 但没人配过）。
2. **某设备 IntervalMs 与实际上报稀疏不符**（离线重连/解析失败频繁）→ S8 反复截断窗口（H-2），既有 `DurationSec>0` 保护规则**永不触发**；无 metric，只能靠现场复现。
3. **DB 抖动时**：每帧 MarkSuccess 的 JOIN（B-3）与 deviceInterval TTL miss（H-1）同步阻塞 parser consumer ⇒ ingest 反压/帧延迟；sink 内 DB 慢查询会放大为数据丢失窗口。
4. **pending_confirm + 来源组**：来源切换后 confirm 的 source_hash 拒绝路径无任何自动化测试（H-3），错误放行会让"用户确认过的决策"被换源执行；错误拒绝则策略静默不执行——合并后 CI 都无法发现。
5. 可观测性缺口：非 active 帧被丢弃不落任何事件（B-2），运维无法区分"设备正常备机"与"求值静默"。
