## 1. C1：数据模型与 GORM 双库成立性（实测证据）

### 1.1 实测结论（两新表 tag 可用，无需改）

用与 §4.1/§4.2 **逐字节相同**的 tag 写临时程序，`gorm.io/gorm v1.31.2 + gorm.io/driver/sqlite v1.6.0`（`backend/go.mod:19-21`）AutoMigrate 后实查 `sqlite_master`：

```
[index] ux_sgm_member      :: CREATE UNIQUE INDEX ux_sgm_member ON source_group_members(group_id,edge_device_id)
[index] ux_sgm_one_active  :: CREATE UNIQUE INDEX ux_sgm_one_active ON source_group_members(group_id) WHERE status = 'active'
[index] idx_source_group_members_group_id / status / edge_device_id  (均可创建)
create readback: enabled=false combine="" on_degrade="" min=0 rev=0   （default:'' / default:0 不覆盖显式零值）
create m2(同组第二条 active) → UNIQUE constraint failed: source_group_members.group_id   （I1 生效）
create m3(同组重复 edge_device) → UNIQUE constraint failed: group_id, edge_device_id      （I3 生效）
create m4(同一 edge_device 加入另一组) → 成功                                          （I3 未过紧，合理）
create m5(status="") → 成功                                                            （无词表约束，见 H2）
```

- **"两个 uniqueIndex 同挂 GroupID 会互相覆盖"不成立**：GORM 的 `schema.parseFieldIndexes`（`gorm@v1.31.2/schema/index.go:90-140`）按**原始 tag 字符串 `;` 切分**逐项解析，不是走 `map` 去重——两个索引都会被收集，且 `priority:1/2` 复合顺序正确。
- **`where:` 的解析**：`tagSetting = ParseTagSetting(..., ",")`，`where:status = 'active'` 的冒号只在第一个 `:` 处分割，空格/单引号原样保留（实测 DDL 正确）。仓库已有同款 tag 先例：`models.go:460`（`idx_users_active_subject,where:subject_key = 'system_admin' AND retired_at IS NULL`）。
- **PG 可行**：`gorm.io/driver/postgres@v1.6.0/migrator.go:150-158` 的 `CreateIndex` 在 `idx.Where != ""` 时拼 `WHERE <raw>`，与 SQLite 同一实现路径。
- **`defaults_gate_test.go` 不会命中**：该门禁正则 `gorm:"[^"]*default:([^;"]+)` 只登记**非零** default；`default:''`/`default:0` 被显式排除（`defaults_gate_test.go` `val == "0" || val == "'0'" || val == "false" || val == "''"` 分支）。§4 两表无任何非零 default，因此**不需要**新增登记项、也不会被门禁判红。`Enabled bool gorm:"not null"`（无 default）在实测中 `enabled=false` 正确保留——与门禁注释描述的陷阱方向一致。
- **环境陷阱提醒（不阻断）**：测试库用 `testutil.OpenTestDB`（SQLite/PG 均只 `AutoMigrate(allModels...)`，`testutil/db.go:120-131/226+`），不执行 `database.AutoMigrate()` 尾部迁移函数（全仓仅 `cmd/server/main.go:70`、`cmd/ehomectl/main.go:53` 调用）。因此**凡不能由 model tag 表达的 DDL（B6 的列变更、旧表部分索引）在测试库都不存在** → 见 H5。

### 1.2 实测发现的问题（进阻断/高优）

- **B1（阻断）**：§4.3 的列语义与代码不自洽。表格写 `source_kind VARCHAR(20) NULL`、`NULL ⇒ 存量走老路`（:191），但"唯一实现" `SourceRef()`（:206-211）用 `r.SourceKind == string(...)` 非指针判断——Go 侧 `string` 无法承载 NULL（pg/sqlite 扫描 NULL 到 string 会报 `converting NULL to string is unsupported`），实现者只能二选一：柱改成 NOT NULL DEFAULT ''（则"NULL=老路"的 SQL 审计/盘点口径失效），或字段改 `*string`（则示例代码与 SG-01 的一致性判据都要改）。**必须钉死**：列 nullable + Go 字段类型 + `source_kind ∈ {NULL,'','edge_device','source_group'}` 的三态处置。
- **B6（阻断）**：§4.4 给既有表加组列，但未处理既有 NOT NULL 列。`failover_logs.DeviceID NOT NULL`、`Category size:64 NOT NULL`（`models/models.go:385-387`）——组级切换事件没有"逻辑设备 ID + 类别"这两个必填值；`data_source_health.SourceID NOT NULL`（:370）同理——组级健康事件不属于任何 `data_sources` 行，SourceID 无值可填。写 0 脏值还是把旧列改可空？§4.4 只列了新增列名，没有 DDL、没有既有列处置、没有 `R10 冷却锚点改 (source_group_id, id DESC)` 后旧列是否必须继续填的规则。**迁移会失败或写脏数据，必须在 §9.1 增列级 DDL 与既有契约裁决。**
- **S3（建议）**：§4.4 只有列名没有 Go 字段/类型。`source_evidence JSONB` 是 PG 专有类型名，SQLite 虽能建列（无 JSON 函数）但 GORM 双库 tag 需显式 `type:text`/`serializer:json`；建议给出 struct 定义并写入 `testutil` 双库用例。
- **S1（建议）**：`SourceGroupMember.Status default:''`（§4.2:172）不在 {active,standby,error,disabled} 词表内，且与同词表的旧列先例不一致——`DataSource.Status` 是 `default:'standby'` 并登记在 defaults_gate（`models/models.go:359` + `defaults_gate_test.go` 登记表）。建议 `default:standby` 或保存期强制赋值 + 词表 CHECK。
- **S2（建议）**：§7.3 V 表只校验 `combine`；`kind`（非 composite/primary_backup 的任意串）、`on_degrade`（非 fail_closed/use_available 的任意串）、`min_members<0`、`staleness_sec<0` 均无校验行。**kind 非法时 V-1/V-2 都不命中，可直接入库**（I2 只覆盖两个合法 kind 的组合）。

## 3. C3：§7 失败矩阵漏分支（required × on_degrade × min_members）

### 3.1 三向交互的现状：两处规定互相矛盾

- §5.3 矩阵（:277-284）：`fail_closed` 只要"部分缺席"⇒ **unbound**（不区分 min_members）；`use_available` ⇒ 按可用合并 + Degraded。
- E-5（:385）："composite 缺席数使**可用 < min_members** ⇒ unbound（fail_closed）**或按可用合并**（use_available）"。
  → 字面读法：use_available 下即使可用 < min_members 也合并 ⇒ **min_members 失效**；fail_closed 下从不引用 min_members ⇒ 同样失效。而 §4.1(:125-127) 与 D-4(:88) 都说 min_members 是"最少可用成员数"（聚合类有意义）。**三向组合没有任何一张表，且两处文本对 min_members 的效力相反。**

### 3.2 必须补的组合表（当前未定义 = 实现者自由发挥）

| required 成员 | on_degrade | 可用数 vs min_members | §5.3 说 | E-5 说 | 应裁决 |
|---|---|---|---|---|---|
| 无 required | fail_closed | 可用 ≥ min | unbound | unbound | 一致但 min_members 无意义 |
| 有 required 缺席 | fail_closed | 可用 ≥ min | unbound | unbound | 一致 |
| 无 required | use_available | 可用 < min | 合并 | 合并（与 min 冲突） | **未定义：应 unbound？** |
| 有 required 缺席 | use_available | 可用 ≥ min | 合并 | 合并 | **required 被静默忽略？应 400 或显式"required 仅在 fail_closed 生效"** |
| 有 required 缺席 | use_available | 可用 < min | 合并 | 合并 | 未定义 |
| `first_available` | 归一 use_available | — | D-4/V-3 已闭环 | — | 一致 |

**修法**：在 §5.3 后加一张 3 维真值表并写死两条：① `use_available` 下 `required` 的语义（建议：`required=true` 与 `use_available` 互斥 → V-5 新校验 400）；② `min_members` 的适用条件（建议：仅 `use_available` 且可用 < min ⇒ unbound；fail_closed 恒 unbound 时不引用 min）。同时删/改 E-5 的括号表述。

### 3.3 主备组与 FC 的衔接缺口

- **E-4 的到达路径缺失**：`degraded = 无 active` 由 R4 产生，但 R4 需要"成员失败/停滞被检测"；§5.4 的 R1–R11 映射表**没有停滞扫描器**（旧设计里它是独立"内置扫描器，60s 一轮"，旧文档 §74；实现 `service.go:689 ScanStale`），I5 又要求"ScanStale 跳过 composite"——**组级 ScanStale 谁写、按什么周期、是否触发 R3/R4、与求值期 E-2 的关系全部未定义**（H7）。后果：主备组可能永远不 degraded（E-4 死代码），或实现者自己造一个第二时钟（违反 §5.2 非目标）。
- **主备"active 存在但值陈旧"无行**：E-2 把该分量视为缺席 ⇒ 主备组唯一权威缺席，但矩阵没有"active 存在且陈旧"的整组行为（应 unbound + `source_stale`，且是否触发 failover 未说）。E-4 只写"无 active"。
- **FC 缺"组/成员行不存在"分支**：FC-1 只判"触发成员已非 active"；若回滚/运维删除成员行、或 I6 未被实现的组删除发生，F4 查不到成员应返回什么（当前只有 FC-4 resolver 未接线）未定义。建议加 FC-5：组/成员不存在 ⇒ `source_member_changed` 或新码 + 不执行。
- **"成员 error 但仍有新鲜值"**：E-3 按主备`status ∉ {active,standby}` ⇒ **缺席（即使值新鲜）**；§5.3(:284) 缺席判定的③只在"主备组"生效，**composite 成员 status 不参与**。两种 kind 语义不同本身合理，但方案没有显式写"composite 的 status 不参与缺席判定/由谁维护"；且 §4.2 说 composite "只维护 last_success 供观测"——status 默认 `''` 会永久不在词表（H2）。
- **E-6 未限定 source_group 规则**（:386 "resolver 未接线 ⇒ 不求值"）：G0 开关默认 false、resolver 可能未注入，若实现按字面对所有规则不求值，**存量规则全部停摆 = G-1 直接违反**。必须改为"（仅 source_group 规则）resolver 未接线 ⇒ 不求值；`source_kind IS NULL` 规则不经过 resolver"（H3）。

## 4. C4：D-6 存量和来源组行为不同 ⇒ 新不一致（高优 H1）

- **证据**：旧路径 F4 用 `rule.TriggerEdgeDeviceID` 直接查 latest cache，**没有时间谓词**：`planner.go:579-582`（`deviceID := rule.TriggerEdgeDeviceID`）、`:663-664`（`rec, found := p.latestValueFn(deviceID)` 后只比值），缓存只在收到新帧时覆盖（`api/latest_value_cache.go:41-58`）⇒ **设备离线 8 小时后，旧规则仍可用 8 小时前的值通过 F4 并执行动作**（现有行为，D-6 明确保留）。
- 组路径 FC-2（:393）对同条件加 `now - SourceAt > staleness` ⇒ 拒绝。
- **矛盾点 1**：G-4（:36）写"三种来源失败语义全 fail-closed…**禁止 fallback 到…陈旧值**"——这句对旧路径为假；D-6 是有意豁免，但 G-4 没有加限定，验收口径自相矛盾。
- **矛盾点 2**：同一条物理条件，用户"A 规则绑设备 / B 规则绑组"表现不同（A 可陈旧执行、B 拒绝），且没有任何 UI/文档提示；运维看到"同阈值两条规则一条动一条不动"会误判。
- **修法**：① G-4 改为"来源组路径全 fail-closed；存量单设备路径行为不变（D-6 豁免，已知可陈旧）"；② §7.2 加一行显式说明 + 审计/指标区分（如 `source_staleness_checked=false`）；③ 可选的远期项：给旧路径加默认关闭的 staleness 开关（不影响 G-1）。

## 5. C5：§9.2 回滚铁律「双写非 0 锚点」有没有门禁？（阻断 B2）

**答案：没有门禁，且告警侧不可实施。**

1. **无门禁**：§4.3(:214) 说"必须同时双写非 0 的 trigger_edge_device_id"，§9.2(:487) 说"保存期强制双写非 0 锚点"。但：
   - §7.3 V-1..V-6（:405-410）**没有**"绑组规则必须有非 0 anchor"这一条；
   - §8.1 SG-01..SG-09（:422-430）**没有** anchor 项（SG-01 只查 source_kind↔group_id 一致性）；
   - §9.2 的"盘点 SQL（4 条：绑组规则/危险编码/双 active/pending）"**没有脚本路径、没有执行点、没有门禁**——纯靠人记。
   → 一旦漏写/被人用旧前端保存清空，回滚后旧二进制走 `evaluator.go:872-877` 的"trigger_edge_device_id=0 ⇒ 任意设备触发"，**静默乱触发**（方案自己标"禁止出现"）。
2. **告警规则没有锚点列**：`alert_rules` 只有 `TargetType/TargetID`（`models/alert.go:36-37`），没有 `trigger_edge_device_id`；旧 alert evaluator 只认 `target_type ∈ {edge_device, logical_device}`（`alert/evaluator.go:282-287`）。§4.3(:192) 却只给 alert 加了 `source_kind/source_group_id`，**没有定义绑组告警的回滚锚点**（target_type 写什么？target_id 写组主成员？），铁律对前半句"绑组规则"里 50% 的对象不可实施。
3. **composite 无"组主成员"**：铁律写"= 组主成员"，但 composite 是 I5 定义"没有 active"的组 ⇒ "组主成员"未定义；若取 priority 第一台，方案没写。
4. **修法**：① V 表加 V-7（自动化：source_kind=source_group ⇒ trigger_edge_device_id != 0 且属于该组或为组 anchor）；② alert 定义锚点（target_type='edge_device', target_id=anchor）或声明"告警一期不支持组引用"并缩 G-2 范围；③ §9.1 明确 anchor 列对 composite 的取值规则（建议：成员按 priority DESC 第一台，并在 active 变化时不重写 anchor——回滚是降级不是等价）；④ §9.2 盘点 SQL 落成 `backend/scripts/rollback_source_group_preflight.sql` + SG-10 门禁（`--strict` 下必跑）。
