## 0. 四个专项回答（lead 点名）

### 0.1 N-9 的 GORM `check:` tag 在 SQLite + PG 双库是否可行 —— **可行（实测）**

用与 N-9 描述的表达式一致的模型（`kind IN ('primary_backup','composite')`、`combine IN ('first_available','avg','max','min','sum') OR combine = ''`）实测 AutoMigrate：

- **SQLite**：`CREATE TABLE ... CONSTRAINT chk_sg_kind CHECK (kind IN (...)), CONSTRAINT chk_sg_combine CHECK (... OR combine = '')`；插入 `kind='nonsense'` ⇒ `CHECK constraint failed: chk_sg_kind`；插入 `combine='median'` ⇒ `CHECK constraint failed: chk_sg_combine`。
- **PostgreSQL**：AutoMigrate 成功，`pg_constraint` 查到 2 条（`contype='c'`，形如 `CHECK (kind::text = ANY (ARRAY[...]))`）；非法值报 `SQLSTATE 23514` 并点名 `chk_sg_kind`/`chk_sg_combine`。
- **实现路径**：GORM 在 CREATE TABLE 语句内拼 CHECK（`gorm@v1.31.2/migrator/migrator.go:297-299`）；对**已存在表**走 `ALTER TABLE ADD CONSTRAINT`（同文件 `:61-63/762-775`）。PG 支持 ALTER ADD CONSTRAINT，**SQLite 不支持** ⇒ 要求「首次建表即带 tag」，不能先建表再补 tag（否则 SQLite 测试库会显式报错；是失败不是静默，可接受）。
- **两点局限（不阻断，需写进 N-9）**：① DB 只保证 kind 白名单与 combine 白名单，**kind×combine 交叉规则（primary_backup⇒combine=''／composite⇒combine≠''）DB 不保证**（实测 `primary_backup + combine='avg'` 可通过 CHECK，只能靠 V-2/V-1 API 400）。可在 `combine` 字段挂一条引用两列的表级表达式补齐（GORM check 表达式可引用其它列，实测机制可行）。② GORM check tag 语法为 `check:约束名,表达式`（`schema/constraint.go:25-42`：首段匹配 `^[\w-]+$` 才当名字，逗号后的表达式原样保留）——方案应给一条**可直接抄的 tag 样例**，避免实现者把表达式写成被误解析的形式。

### 0.2 N-6 双指针 NULL 三态是否真的解决「静默回落成任意设备触发」—— **部分**

- **已解决**：Go 侧能承载 NULL（`SourceKind *string`/`SourceGroupID *uint`）；NULL＝老路；非白名单 `source_kind` 保存 400 + 加载期跳过告警（不再静默当老路）。
- **未解决（残留危险态）**：N-6 自己写"**否则 ⇒ 单设备**"，于是 `SourceKind!=nil && *SourceKind=='source_group' && (SourceGroupID==nil || *SourceGroupID==0)` 这一行**在运行期仍会落到单设备分支**：
  - 若 `TriggerEdgeDeviceID != 0` ⇒ 静默盯错设备；
  - 若 `TriggerEdgeDeviceID == 0` ⇒ 回到 v0.1 点名的"任意设备触发"。
  N-6 的"加载期跳过"只覆盖"非白名单 `source_kind` 值"，**没有覆盖"白名单值 + group_id 缺失/矛盾"**；而这一态正是 v0.1 B1 的原始缺陷形态（旧二进制/手工改库都可能造出）。
- **差什么（具体条款）**：① `SourceRef()` 增错误返回（`(SourceRef, error)` 或 `KindInvalid`），矛盾行 ⇒ 加载期跳过 + 落审计/指标，**不得回落单设备**；② 加载期校验与 SG-01 用同一判据：`source_group ⇒ group_id 非空非 0 且存在；edge_device ⇒ group_id 必须 NULL`；③ SG-01 的"双指针 NULL 三态"建议写成 5 行真值表（(NULL,NULL)/(edge_device,NULL)/(source_group,id)/(source_group,NULL)/(NULL,id) 的判定与错误码），"三态"目前无定义。

### 0.3 N-7 锚点定义是否足以支撑回滚、是否与 I6 冲突 —— **部分**

- **已闭环的主体**（v0.1 B2 的核心）：锚点定义（primary_backup = priority DESC,id ASC 首成员；composite = 最高 priority）；写回 legacy 列（automation `trigger_edge_device_id`；alert `target_type='edge_device'+target_id`）；V-9（非 0 且须为组员）400；SG-12 + `check_source_group_rollout.sh` 4 条 SQL 进 CI。✅
- **未闭环（3 条具体缺口）**：
  1. **成员变更后未写"回写既有规则 legacy 列"**：N-7 只说"保存/成员变更时重算"锚点，但 V-9 只在**规则保存**时校验。成员被移出/删除后，已存在规则的 legacy 列不会自动更新 → 回滚后旧二进制盯一个已不在组内的设备（不会乱触发，但**静默不触发**，与"退化为只看主成员"的承诺不符）。需加一句：**成员变更事务内重算 anchor 并回写所有绑组规则的 legacy 列（或复校验 V-9 并在失配时拒绝变更/告警）**；盘点 SQL 加第 5 条 "anchor ∉ group members"。
  2. **active 切换不重算锚点未声明回滚语义**：回滚后旧二进制看 priority 首成员（可能恰是已故障的那台）⇒ 规则可能永久不触发。这是安全方向但必须写清"回滚后的降级形态"（v0.1 B2 要求可解释），建议写进 §9.2 表第一行。
  3. **与 I6 的依赖关系**：I6 只保护"组不被删除/停用"，**不保护"成员不被移出组 / 成员设备不被删除"**（I4 删除守卫无落点，见 B4 残留）→ 锚点悬空的唯一实际路径正是这两条缺口叠加。**N-7 的闭环以 I4/I6 补齐为前提**，否则 V-9 只在保存瞬间成立。
  - 次要：composite 锚点 tie-break 未定（priority 相同取 id ASC？）；空成员组时 V-9 的 400 文案/是否允许保存空组未写。

  2. **【高优】E7 断言仍未改**：`§8.3 E7`（L452）断言"**`failover_logs` 只 1 条**"；组切换不写旧表 ⇒ 该断言在新方案下要么恒过（0 条，假绿）要么恒红；且**没人断言 `source_group_failover_logs` 恰好 1 条** ⇒ "切换不双计"在组路径上无门禁。SG-08（L701）也只查既有审计列，不含新表。

  4. 新表 retention/清理未定义（旧设计承诺 30 天；N-11 说"retention 独立"但无策略）——建议级。
