## 二、方案 A：原生 USB 作数据通道

### 目标
UART1/RS485 留给雨量计（4800bps），ESP32 原生 USB-Serial-JTAG 承载 BMS 数据（9600bps JBD 协议）。两者波特率冲突，无法共用一条 UART。

### 实现
| 层 | 改动 |
|---|---|
| 总线类型 | 新增 `BUS_TYPE_USB = 4`（`bus_dma.h`） |
| DMA 层 | USB pump 任务 + 环形缓冲 + `bus_dma_flush_input()` |
| 总线管理 | manifest 资源规划、命令路由（USB → uart0 worker 队列） |
| worker | 事件集、RX 槽位、批量执行均接受 USB |
| scheduler | 队列映射 USB → UART0 |
| 平台 | `BusType` 仅接受字符串 `"USB"`（数字 `4` 保留给 GPIO，避免冲突） |

### 验证证据（效果层）
```
BUS_DMA: USB data channel init (ref=1, console shares endpoint)
BUS_MGR: ch=2 type=4 dma=0 idx=1 SUCCESS
```
- 设备上报 `{id:2, bus_type:4}`
- 主机嗅探到 299+ 个 JBD 读帧 `dd a5 03 00 ff fd 77`
- **console 与数据共存**（同一端点，日志正常输出）
- 注入值解析一致：`total_voltage=53.61V`、`current=23.39A`、`rsoc=85%`、`cell_count=16`

## 五、模拟器（`.logs/bms_sim_all.py`）

JBD 从机，支持全部 26 动作的帧序列。

### 关键协议事实（全部经实测确证）
- 读请求：`DD A5 CMD 00 CK_H CK_L 77`，checksum = `cs([CMD, 0x00])`
- 写帧：`DD 5A CMD LEN DATA... CK_H CK_L 77`，checksum = `cs(raw[2 : 4+LEN])`
- **`0x77` 必须在结构位置 `4+LEN+2`**；补零放 `0x77` **之后**（`jiabaida_parse.go:126`）
- 重启帧是固定向量 `DD 5A 0E 00 81 18 CK CK 77`：**LEN 字段=0 但含 2 字节魔数**，帧长恒为 9，通用长度算法会算错

### 写→读耦合
- `write_custom_attributes`：写入 6 字节，`0xF0` 读回逐字节对账
- `write_internal_resistance`：写入 60 字节，`0xF6` 读回逐字节对账
- `set_mos_policy`：写帧 MOS 位=1 表示软件关断，读回 fet 位=1 表示导通（**互逆**）
- `test_charge_mos` 等：写后读回状态必须 = 1(OK)

## 六、并发行为观察（重要，非缺陷）

首次批量下发时 **17 个命令在同一秒并发**（05:57:11），其中 3 个 FAILED。
串行重跑后 **3/3 SUCCEEDED**。

**结论**：USB 通道是单工的，多命令并发争抢时部分失败是**预期行为**，不是功能缺陷。但这说明：

> 生产使用时不应对同一 USB 通道上的 BMS 动作做无节流的并发下发。

## 八、我犯的错误（如实记录）

1. **`git checkout` 丢了修复**：变异自证后用 `git checkout` 恢复，把工作区未提交的改动一起丢弃。已改用 `cp` 备份恢复。教训：工作区有未提交改动时，`git checkout` 不是「恢复变异」的安全手段。
2. **模拟器补零位置错**：把零插在校验和与 `0x77` 之间 → `ErrInvalidStopByte(=2)`。正确是 `0x77` 之后。
3. **模拟器 0x0F 布局错**：复用 0x03 布局，产生 `617.05V` 假值。
4. **FET 位语义反了**：导致前两次 `set_mos_policy` 假失败。
5. **确认门禁前提错误**：我告诉 teammate「清空 AvailabilityCode 即可自动启用」，但该重算逻辑只覆盖 set/reset，2 个读动作需显式 `Enabled: true`。teammate 纠正了我，我核实后确认其正确。
6. **第一版锁步测试断言过严**：要求空 DATA 也能解析成功，7 个动作全红；实际是校验器正确地检查数据长度。
