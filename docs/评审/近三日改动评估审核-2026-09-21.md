## 2. 改动全貌（按子系统）

### 2.1 后端：设备地址语义门禁（主线）

事故根因（2026-09-20）：创建向导把**总线名** `UART1` 写进 `edge_devices.hardware_id`（该字段语义是**设备从站地址** 1-254），写时无人拦，派发时在 `deviceaction.ParseHardwareAddress` 才失败，操作静默停在 QUEUED 约 120s 后报"超时"。

本轮在**四条写入路径**上收敛（均复用同一真值源）：

| 路径 | 门禁 | 位置 |
|---|---|---|
| `POST /edge-devices` | 已有（R2） | [handler_edge_device.go](backend/internal/api/handler_edge_device.go#L590-L600) |
| `PUT /edge-devices/:id` | 已有 + 候选值校验 | [handler_edge_device.go](backend/internal/api/handler_edge_device.go#L803-L825) |
| `PUT /nodes/:id/config`（侧门） | **本轮新增 G1 地址门禁 + G6 唯一性** | [handler_node.go](backend/internal/api/handler_node.go#L1062-L1086) |
| `POST/PUT /device-configs` | **本轮新增 G7 型号注册表校验（入口治理）** | [handler_device.go](backend/internal/api/handler_device.go#L280-L300) |

其中 **G2** 修正了一个连带数据丢失：侧门在请求未携带 `device_config_id` 时会把 `type` 覆写为空串 —— 而 `type` 正是地址门禁的输入，空 type 使门禁整体失效（[handler_node.go](backend/internal/api/handler_node.go#L971-L1005)）。**这是本轮最有价值的一处修复**：它不仅补漏，还消掉了"未知型号 = 放行"这一语义本身。

### 2.2 后端：命令可诊断性（G5）

派发失败时把具体原因写进 `command_executions.final_reason`（[dispatcher.go](backend/internal/commandexec/dispatcher.go#L187-L212)），并向成功路径清除陈旧原因（[dispatcher.go:287-291](backend/internal/commandexec/dispatcher.go#L287-L291)）；超时回收不再用笼统文案覆盖具体原因（[inbox.go](backend/internal/commandexec/inbox.go#L175-L211)）。这把"120s 静默"变成"立刻可见原因"。

- **证据**：运行中的 `ehome-web` 镜像 `ghcr.io/lstions/ehome:verified-20260921-184839`（image 构建于 2026-09-21T13:08:19+08:00）；容器启动于 **10:50:45**。关键文件 `channel_cmd_v2_transport.go` 的 mtime 是 **13:10:53**，晚于镜像构建时刻。
- **独立佐证**：镜像内二进制 strings 命中新门禁文案 `is not a registered driver` ×1、`is not registered: unknown driver types` ×1、`cancelled by user (during download)` ×1、`dispatch rejected:` ×1 —— 说明 13:08 的镜像**已包含 G1/G6/G7 与 OTA/派发改动的大部分**；但**构建时文件仍可能被判为"发布后又改过"**，按"文件变更 ⇒ 产物失效"的纪律，当前无法用任何已有产物宣称"这批改动已交付"。

**B-2 `-tags=simulation` 与场景仿真不在常态 CI 门禁内（新增代码零编译校验）**

- **证据**：`.github/workflows/test.yml` 中 `backend` job 只跑 `go vet ./...` 与 `go test -race ./...`（:57、:61），`backend-scenarios` job（:181）依赖真实 PG/EMQX（`needs: backend`）。本次新增的 `drivers_sim.go`、`internal/simdrivers/register.go` **全部（且仅）在 `//go:build simulation` 下编译**，因此在不带标签的常态检查中**一个都编译不到**。

## CI 抓到的一个真实缺陷（本轮最有价值的产出）

首次推送后 **CI 的 `Backend (PostgreSQL integration)` 变红**：

```
--- FAIL: TestComposedDeadlineReasonFitsColumnBudget
    ERROR: value too long for type character varying(256) (SQLSTATE 22001)
--- FAIL: TestComposedDeadlineReasonFromAttemptLevelFitsColumnBudget
```

**根因是测试种子缺陷 + 方言盲区，不是产品缺陷**：两个用例为了构造"未经上游预截断的原因"，
把 400 字直接 UPDATE 进 `varchar(256)` 列。**SQLite 不强制 VARCHAR 宽度**（本地 `EHOME_TEST_DB` 默认
sqlite ⇒ 全绿），PostgreSQL 在**种数据**这一步就拒绝，用例根本走不到它想验证的组装逻辑。

这与本轮刚修掉的 `go vet -tags=simulation` 盲区**同一族**：门禁覆盖不到的分支 = 假绿。

修法（`c05b2fcf`）：新增 `columnFillingCause()` 返回恰好等于列宽（256 runes）的多字节原因。
它仍满足原用例意图 —— 派发器自身预算 200 runes，256 > 200 ⇒ 种进来的仍是**未预截断**的值，
组装边界必须自己压到 222（256 − 后缀 34）以内，因此仍能证伪"只在 200 那一层截断"的实现。
"远超列宽"的输入存不进 DB、不属可达状态，该边界改由**不落库的纯函数用例**覆盖。

本机复现与验证（真实 PG 18-alpine，端口 15436）：修复前 FAIL×2 且报错与 CI 逐字一致；修复后
`ok ehome/backend/internal/commandexec 88.257s`，全量 PG 集成 **33 包 ok / 0 FAIL**。

## 现场故障：雨量计总线读取失败（**与本轮改动无关**）

真实设备下发 `read_rainfall` / `read_baud_rate` 全部以 `FAILED / final_failed` 结束。
我按"先证明是回归、再排除回归"的顺序做了完整判定：

### 判定 1：设备上行本身在报错（根因指向设备侧）

```
data_json = {"channel":1,...,"error_code":1,"raw":"","sequence":175}
```
固件源码：`bus_worker.c:20` —— `error_code=0x01` 即**窗口内未收到设备数据**（总线无应答）。
也就是说：**雨量计本身没有回应采集**，采集在报错，而链路是活的。

### 判定 2：故障起点晚于部署 7 小时（决定性）

| 时刻（UTC） | 事件 |
|---|---|
| 09-21 15:52:36 | 我部署新镜像 |
| 09-21 16:52:57 | **最后一次** `error_code=0`（设备正常） |
| 09-22 00:07:46 | **首次** `error_code=1`（设备开始读取失败）← 故障起点 |
| 09-22 00:18:14 | 我发第一条测试指令 |

故障起点比部署晚 **7 小时**，其间设备一直正常。

### 判定 3：A/B 回滚对照（新旧镜像行为一致）

把生产切回**部署前镜像**（`701dbaa9…`）发 3 条同样指令，再切回新镜像发 3 条：

```
旧镜像（部署前）: FAILED, FAILED, FAILED   （终态均为 final_failed）
新镜像（部署后）: FAILED, FAILED, FAILED   （终态均为 final_failed）
```

两轮**终态完全一致**。
> ⚠️ 过程中的一个自我纠错：A/B 当时我的探针把轮询窗口内的**中间态** `DEVICE_ACCEPTED`
> 读成了结果，一度看起来"旧镜像全成功、新镜像失败"。稍后复查 DB 终态才发现三轮全是
> `FAILED`。**中间态不是终态**，这是本次记录里最值得留下的方法教训。

### 结论

**该故障与本次部署无关**，是雨量计/R485 侧的物理或设备侧问题（总线无应答）。
部署保持现状；雨量计读取失败需要现场排查（接线/供电/从站地址/波特率）。
