## 必答：按 kind 分流与窗口身份自洽性

- 分流实现与 §12.2.1 一致：`FrameMatch.Accepts()`（`sourceref/registry.go:31-42`）primary_backup 要求 `IsMember && IsActive`；composite 只要求 `IsMember`。`MatchFrame` 对 composite 设 `IsActive=IsMember`（`registry.go:186-191`），语义自洽。
- 身份：`automation/source.go:196-250` `identityForFrame`，composite 不含 `edgeDeviceID`、含 `groupID+Revision+MembersHash`；primary_backup 含 `edgeDeviceID`。**为什么 composite 不含触发成员**：复合值是"整组合成值"，观测单位是组；若含触发成员，A/B 交替帧会每帧换身份、S1 清窗 ⇒ DurationSec 永不满足（v0.1 B-4）。不含成员后 S1 对 composite 无意义（正确，S1 只约束主备"跨成员拼接"），改用 S7（组值连续满足）覆盖；S8 gap 用组内成员最大间隔兜底（`groupGap`）。**S1 仍防什么**：主备组内"A 的旧样本 + B 的新样本"拼接成连续满足（切换瞬间最危险方向），identity 中 active 成员 ID + revision 变化即清窗，且不依赖钩子。判定：**自洽，闭环**。
- 残留（不阻断）：`evalCompositeRule`（`automation/source.go:270-276`）`if g == nil { e.recordSourceFailure(rule.ID, g.ID, ...) }` 对 nil 指针取字段——当前从 `matchSourceRule` 入口不可达（Configured=true 时 Group 必非 nil），属潜在 panic 分支（alert 版已正确用 `0` 或日志）；建议改成 `ref.GroupID` 或 0。

## 必答：如果现在合进 main，最坏会发生什么

**最坏场景（回滚路径，H-2）**：用户建了"1 号光照 / 2 号光照 / 1+2 三种组合"规则，组锚点最初是 A。之后 A 被移出组（或优先级调整使锚点变为 B），规则的双写 `trigger_edge_device_id` 仍是 A（无回写）。某天因故回退到旧二进制：旧代码只读锚点列，看到 A 就按 A 的 illuminance 触发规则——**A 可能放在另一个房间且已不属于该来源组**，于是"1+2 融合"规则变成"用另一房间的传感器单边动作"，且旧代码没有任何来源身份/审计可发现。这是安全方向的静默错源动作，且回滚盘点脚本（只查五态矛盾）不会拦住。

**次坏场景（B-1/H-1 组合）**：主备组 R10 冷却抑制 + active 连续失败 ⇒ 组静默无权威 5 分钟以上、规则停止求值且零审计；同时 legacy 与 group 两份状态机若后续只修一侧，同一"主备"产品语义在两处行为不同（data_sources 页面 vs 规则引擎）。

**已确认不会发生**：① 数据面（databus/ingest）因本 diff 变慢或新增 DB 依赖（零改动、零 import）；② sensorfield 被污染（零改动）；③ 快照双写导致"规则读到旧 active"（唯一写路径 + identity revision 兜底）。
