# BMS 功能分析与 CP2102 模拟验证方案

> 2026-09-23 ｜ 阶段一：功能分析（本文档）；阶段二：验证方案

## 一、硬件现状（实测确认）

| 项 | 值 | 证据 |
|---|---|---|
| `/dev/ttyACM0` | Espressif USB-JTAG (`303a:1001`) | `lsusb`；实测输出 ESP32 日志 |
| `/dev/ttyUSB0` | Silicon Labs CP2102 (`10c4:ea60`) | `lsusb`、`udevadm`（`ID_MODEL=CP2102_USB_to_UART_Bridge_Controller`） |
| ESP32-C6 UART0 | **GPIO16(TX) / GPIO17(RX)** | `hw_tables.c:156` |
| ESP32-C6 UART1 | **GPIO20(TX) / GPIO21(RX)**，当前 **4800 8N1** | `hw_tables.c:158`；固件日志 `UART1 polled init (TX=20 RX=21 baud=4800)` |
| UART1 占用者 | 光学雨量计（`edge_devices.id=1`，Modbus addr 1） | `channels` 表：`id=1, hardware_id=UART1` |
| **UART0 可用性** | **空闲可用**（控制台走内置 USB-JTAG） | 固件日志 `UART0 available for data use (console on USB)`；`bus_dma.c:168,240` |

### 关键实测：CP2102 当前未与 ESP32 通信

在 **6 个波特率**（4800/9600/19200/38400/57600/115200）× 各 8 秒只读监听下，
`/dev/ttyUSB0` 收到 **0 字节**。同期 UART1 正在活跃轮询（近 2 分钟 48 帧落库）。

⇒ **结论：CP2102 目前未接到正在工作的 UART1 总线上，或线缆未接通。**
（若它接在 UART1 上，4800 下必然能听到雨量计的 Modbus 请求帧 `01 03 00 00 00 01 84 0A`。）

## 二、BMS 功能面分析

### 2.1 协议：嘉佰达 JBD V19（**非 Modbus**）

```
帧格式: 0xDD | CMD | STATUS/LEN | DATA... | CHECKSUM_H | CHECKSUM_L | 0x77 | [CALLBACKID 4B]
波特率: 9600bps   字节序: 大端
```
来源：`backend/internal/drivers/jiabaida.go:11-12`

### 2.2 遥测传感器（12 项）

`total_voltage`(V)、`current`(A)、`remaining_capacity`(Ah)、`nominal_capacity`(Ah)、
`cycle_count`(次)、`rsoc`(%)、`protection_status`(bitmask)、`fet_status`(bitmask)、
`cell_count`(串)、`cell_voltage_max`(V)、`cell_voltage_min`(V)、`cell_voltage_avg`(V)

来源：`jiabaida.go:24-38`

### 2.3 采集模板（5 个，**已从生产 API 取到真实 TX 帧**）

`GET /api/v1/drivers/jiabaida_bms/commands` 返回：

| 模板 ID | 名称 | CMD | TX 帧 | 期望长度 | 周期 |
|---|---|---|---|---|---|
| `read_basic_info` | 读取基本信息 | 0x03 | `dd a5 03 00 ff fd 77` | 60 | **5000ms** |
| `read_cell_voltage` | 读取单体电压 | 0x04 | `dd a5 04 00 ff fc 77` | 50 | 0（按需） |
| `read_hardware_version` | 读取硬件版本 | 0x05 | `dd a5 05 00 ff fb 77` | 40 | 0 |
| `read_comprehensive` | 读取综合信息 | 0x0F | `dd a5 0f 00 ff f1 77` | 100 | 0 |
| `read_protection_count` | 读取保护历史次数 | 0xAA | `dd a5 aa 00 ff 56 77` | 40 | 0 |

注：帧中 `a5` 是 BMS 地址（0xA5 = 165），`ff` 是 status，末两字节为校验和。

### 2.4 控制操作（20 个）

来源：`jiabaida_control.go`，解析自 `ControlAction` 定义。

| 风险 | enabled=true | enabled=false |
|---|---|---|
| `low` | `find_car`、`write_custom_attributes`、`set_static_correction_time` | `read_test_mos_status`、`read_custom_attributes`、`write_sn` |
| `medium` | `read_protection_parameters`、`read_system_parameters`、`clear_alarm`、`set_report_interval`、`set_charge_time_window` | — |
| `high` | `test_charge_mos`、`test_discharge_mos`、`force_balance`、`auto_test_edv`、`write_internal_resistance` | — |
| `critical` | `bms_restart`、`write_protection_parameters`、`write_system_parameters`、`set_discharge_time_limit` | — |

**统计**：read 5 / reset 2 / set 13；enabled 17 / disabled 3。

### 2.5 重要设计约束（影响验证方案）

1. **波特率冲突（决定性）**：JBD = **9600**，雨量计 = **4800**
   ⇒ **两者无法共存于同一 UART**。BMS 必须独占一个 UART。
2. **写路径未开放**：`GetCommandTemplates` 注释明确说明——
   「BMS writes must be represented by a verified Action Catalog definition instead,
   and **none is enabled until real-device evidence covers the two MOS bits, priority, ACK and readback**」
   （`jiabaida_control.go:1091-1096`）
3. **UART0 可用**：固件 boot manager 判定 UART0 未被下载模式占用时，可作为数据通道
   （`bus_dma.c:168`、`bus_manager.c:437`）。

## 三、验证方案

### 3.1 物理接入方案（决策）

**核心矛盾**：JBD BMS = **9600bps**，雨量计 = **4800bps** ⇒ **不能共用 UART1**。

| 方案 | 描述 | 评价 |
|---|---|---|
| **A（推荐）** | CP2102 接 **UART0 (GPIO16=TX, GPIO17=RX)**，9600 8N1 | 与雨量计**完全隔离**，互不影响；UART0 已被节点上报为可用资源，平台侧无冲突 |
| B | 临时停用雨量计通道，CP2102 接 UART1 @9600 | 需改波特率重配；**会中断雨量计采集**；验证后需回滚配置 |
| C | 不模拟，直接接真实 BMS | 无真实 BMS 硬件时不可行 |

**方案 A 的可行性已逐项确认**：
- ✅ 节点 capabilities 含 `UART0`（`default_tx_pin=16, default_rx_pin=17`）；
- ✅ GPIO16/17 **未被占**（当前 GPIO 占用仅 0-7；UART1 占 20/21）；
- ✅ 固件 boot manager 判定 UART0 可用（`UART0 available for data use (console on USB)`）；
- ✅ 控制台走内置 USB-JTAG（ttyACM0），不占用 UART0。

### 3.2 模拟器职责（CP2102 侧程序要做什么）

模拟器必须实现一个 **JBD V19 从机**：

1. 在 `/dev/ttyUSB0` @ **9600 8N1** 上监听；
2. 识别 5 类请求帧（已从生产 API 取得真实字节）：

| 请求 TX 帧 | 应答内容 | 应答长度 |
|---|---|---|
| `dd a5 03 00 ff fd 77` | 基本信息（总压/电流/容量/SOC/温度） | 60 |
| `dd a5 04 00 ff fc 77` | 单体电压 | 50 |
| `dd a5 05 00 ff fb 77` | 硬件版本 | 40 |
| `dd a5 0f 00 ff f1 77` | 综合信息 | 100 |
| `dd a5 aa 00 ff 56 77` | 保护历史次数 | 40 |

3. 按 JBD 帧格式构造应答：`0xDD | CMD | STATUS | LEN | DATA | CRC_H | CRC_L | 0x77`；
4. 校验和算法 = **对帧内字节求和取反 +1**（需由子代理的 Python 复现确认）。

### 3.3 验证分层（每层都要有可复跑的判据）

**L1 — 链路层**：模拟器能否被 ESP32 轮询到？
- 判据：模拟器收到真实请求帧（字节级比对 `dd a5 03 00 ff fd 77`），且 ESP32 侧 `CMD_U*` 统计 `err=0`。

**L2 — 采集层**：BMS 遥测能否落库？
- 判据：`device_data` 出现 BMS 数据行，`raw` 为模拟器应答的十六进制，
  且解析出的 `total_voltage`/`rsoc` 等与模拟器**注入的已知值精确一致**（这是分辨力所在）。

**L3 — 操作层**：20 个 ControlAction 能否执行？
- 判据：`command_executions.status=SUCCEEDED` **且** `verified_result_json` 有值，
  且模拟器侧确认收到了对应的写帧。
- **注意**：`202 Accepted` / `QUEUED` 只是受理，**不是成功**——必须等终态。

**L4 — 安全层**：闸门是否生效？
- 判据：需确认的操作在被拦截时返回 409/403（负向验证，证明闸门有效）。

### 3.4 分辨力设计（避免"无论对错都通过"）

模拟器**必须注入已知的、非平凡的值**：
- `total_voltage = 52.30V`、`current = -12.34A`、`rsoc = 77%`、`cell_count = 16`、
  `cell_voltage_max = 3.352V`、`cell_voltage_min = 3.298V`；
- 这些值**互不相同且非零非默认**，一旦解析错位（字节序/缩放/偏移）立刻暴露；
- 额外注入一个**边界值**（如 `cell_voltage_max - cell_voltage_min = 54mV`）验证差值计算。

### 3.5 前置条件（必须由用户确认/完成）

1. **接线**：CP2102 的 TX→ESP32 GPIO17(RX)，RX→ESP32 GPIO16(TX)，GND 共地。
   ⚠️ **当前实测 CP2102 在所有波特率下 0 字节** ⇒ 现在**没有接通**，需先接线。
2. **电平**：CP2102 是 3.3V（确认跳线在 3.3V 档，非 5V）。
3. **平台配置**：需建立 BMS channel（UART0@9600）+ edge_device + 关联模板，
   **这是一次生产写操作**，需你授权。
4. **高风险操作**：需要 `recent_auth`（10 分钟内真实登录）才能通过确认闸门。

### 3.6 风险与回滚

- 新增 UART0 通道**不影响**现有 UART1/雨量计（不同 UART、不同引脚、不同波特率）；
- 回滚 = 删除 BMS channel + edge_device，设备侧 manifest 自动回退；
- 若模拟器应答导致 ESP32 解析异常，最坏情况仅 BMS 通道报错，雨量计不受影响；
- **建议**：先做 L1（只收不发），确认链路后再让模拟器应答。

## 五、Lead 独立复现的关键结论（硬证据）

### 5.1 JBD 帧布局（已用 5 个真实帧验证）

```
DD | ADDR | LEN | CMD | CK_H | CK_L | 77
 0     1      2     3     4      5     6
```

**注意**：`verifyJiabaidaChecksum`（`jiabaida.go`）里的 `cmd = raw[1]` 与实际帧不符——
真实帧 `raw[1]` 是**地址 0xA5**，`cmd` 在 `raw[3]`。代码的 `isSend` 判定之所以"碰巧"成立，
是因为 ADDR 恰好等于 0xA5，与 `isSend = (cmd == 0xA5 || cmd == 0x5A)` 撞上了。

**校验和算法（已独立复现，5/5 通过）**：
```python
def checksum(data):
    s = 0
    for b in data: s = (s + b) & 0xFFFF
    return ((~s) + 1) & 0xFFFF

# 发送帧: 校验范围 = raw[2 : 4 + raw[2]]
# 例: dd a5 03 00 ff fd 77  ->  checksum(bytes([0x03, 0x00])) == 0xFFFD  ✓
```

| 模板 | 帧 | ADDR | LEN | CMD | 校验和 | 验证 |
|---|---|---|---|---|---|---|
| `read_basic_info` | `dd a5 03 00 ff fd 77` | A5 | 00 | **03** | FFFD | ✓ |
| `read_cell_voltage` | `dd a5 04 00 ff fc 77` | A5 | 00 | **04** | FFFC | ✓ |
| `read_hardware_version` | `dd a5 05 00 ff fb 77` | A5 | 00 | **05** | FFFB | ✓ |
| `read_comprehensive` | `dd a5 0f 00 ff f1 77` | A5 | 00 | **0F** | FFF1 | ✓ |
| `read_protection_count` | `dd a5 aa 00 ff 56 77` | A5 | 00 | **AA** | FF56 | ✓ |

复现脚本：`.logs/jbd_layout.py`（可复跑）。

### 5.2 应答帧构造规则（供模拟器实现）

```
应答: DD | ADDR | LEN | CMD | DATA(LEN 字节) | CK_H | CK_L | 77
校验范围（响应帧，按 verifyJiabaidaChecksum 的 else 分支）: raw[3:4+LEN]
```

⚠️ **待确认**：响应帧的 `cmd` 位置与发送帧是否一致（代码读 `raw[1]` 判 isSend，
而真实帧 `raw[1]` 是地址）。**模拟器应答前必须先用真实 BMS 抓一次帧**，
或让子代理从 `jiabaida_parse.go` 的解析路径反推。

### 6.2 创建 BMS 通道（`POST /api/v1/channels`）

契约来源：`handler_device.go:680-750`

```json
{
  "node_id": "F0F5BDFFFE02",
  "hardware_type": "UART",
  "hardware_id": "UART0",
  "bus_type": "UART",
  "bus_config": "101100258000000000",
  "interval_ms": 5000,
  "enabled": true,
  "template_ids": "<BMS 模板 id，创建模板后回填>"
}
```

**`bus_config` 编码规则**（`config_mgr.c:589` + `manifest_codec.go:61`）：
- 前 2 字节 = **TX pin, RX pin** ⇒ UART0 = `0x10=16, 0x11=17` ⇒ 前缀 `1011`；
- 之后为波特率等参数；作为对照，雨量计 UART1@4800 的完整值为：
  `1415000012C008010000`（`14`=20, `15`=21, `0012C0`=4800）；
- ⇒ BMS 应为 `1011` + `00002580`（9600 = 0x2580）+ 其余同构参数。
  ⚠️ **必须先解码雨量计的完整 bus_config 结构再构造 BMS 的**，不能凭猜。

**校验约束**（会拒绝的情况）：
1. `hardware_type` 必须 **等于** `bus_type`（`handler_device.go:66`）；
2. GPIO/PWM 属外设资源，不能建通道（`:58`）；
3. 引脚不得与已有通道/GPIO/PWM 冲突（`validateChannelPeripheralConflicts`）；
4. Manifest 编码时要求引脚在节点上报的 capabilities 里（`manifest_codec.go` `validateManifestAuthority`）。

## 九、`bus_config` 完全解码（不靠猜，已自校验）

### 9.1 解码规则（源码依据）

`bus_manager.c:145-149` —— **UART 只使用前 6 字节**：
```c
case BUS_TYPE_UART:
    return config_len >= 6 &&
           ctx->cfg.uart.tx_pin == config[0] &&
           ctx->cfg.uart.rx_pin == config[1] &&
           ctx->cfg.uart.baud == read_be32_config(&config[2]);
```

| 字节 | 含义 |
|---|---|
| `[0]` | TX pin |
| `[1]` | RX pin |
| `[2:6]` | 波特率（**big-endian uint32**） |
| `[6:]` | **UART 不使用**（现有值为 `08 01 00 00`，平台侧固定尾部；`config_len>=6` 即通过） |

### 9.2 现有雨量计通道解码（验证规则正确）

```
1415000012C008010000
 [0]=0x14=20  TX pin   ✓ 与固件日志 TX=20 一致
 [1]=0x15=21  RX pin   ✓ 与固件日志 RX=21 一致
 [2:6]=0x000012C0=4800 ✓ 与固件日志 baud=4800 一致
 [6:]=08 01 00 00     (UART 不读)
```

**三个字段全部与固件实测日志吻合** ⇒ 解码规则确认无误。

### 9.3 BMS 通道的 `bus_config`（构造结果）

```
101100002580 08010000
 ^^^^ TX=16(0x10) RX=17(0x11)
     ^^^^^^^^ baud=9600(0x00002580)
             ^^^^^^^^ 沿用现有尾部

=> bus_config = "10110000258008010000"
```

**自校验**：回读解码得 TX=16、RX=17、baud=9600 ✓

⚠️ **保守做法**：为避免平台/固件对 `[2:6]` 之外的字节有未知依赖，
实施时**只改前 6 字节**，尾部 `08010000` 原样沿用（与雨量计一致）。

# 【重大更正】BMS 功能面的权威数字（2026-09-23 实测）

## 一、更正我先前文档中的错误数字

我在第三节用**正则解析源码**得到「20 个 action」，这个数字**是错的**。
实际用 **Go 代码调用生产 registry** 枚举的结果是 **26 个**。

差异根因：源码里有两种 action 构造形式，我的正则只匹配了 `ControlAction{ID: "..."}`，
漏掉了 `jiabaidaReadAction("...")` 辅助函数构造的 6 个读操作。

**这正是 evidence-discipline 说的"口径错误"**：用文本模式匹配代替真实调用，
在存在语法糖时必然漏数。教训：枚举注册表必须调用注册表本身。

复现命令（已在仓库外运行，未提交代码）：
`docker run --rm -v "$PWD:/w" -w /w/backend golang:1.26.5-alpine sh -c "go run ./cmd/bmsavail"`

## 二、真实可用性矩阵（26 个定义）

| 状态 | 数量 | 明细 |
|---|---|---|
| **ENABLED** | **1** | `set_mos_policy`（set / high / bounded_sequence / readback） |
| disabled（`protocol_unverified`） | 15 | 全部写操作除 `set_mos_policy` |
| disabled（无 AvailabilityCode） | 10 | **全部读操作** |

### 2.1 全部 10 个读操作均 disabled

```go
// jiabaida_control.go:189-192
func jiabaidaReadAction(id, name string, tx []byte, readSize uint32, description string) ControlAction {
	return ControlAction{ID: id, ..., Semantics: "read", Risk: "low", Enabled: false, ...}
//                                                                       ^^^^^^^^^^^^^^
}
```

读操作不参与 `definition.go:597-604` 的写操作覆盖规则（该规则只对 `set`/`reset` 生效），
所以 driver 的 `Enabled: false` 被**原样保留**。

### 2.2 唯一可用的操作是写操作

```go
// definition.go:601-603 —— 具备完整执行链的写操作强制启用
if action.Semantics == "set" || action.Semantics == "reset" {
	if verifier != nil && action.Verification != "" && action.AvailabilityCode == "" {
		enabled = true    // set_mos_policy 命中此分支
	}
}
```

## 三、这对验证方案的影响（关键）

**必须区分两条独立路径**：

| 路径 | 入口 | 门禁 | 可否验证 |
|---|---|---|---|
| **遥测采集** | `GetCommandTemplates`（5 个模板，`schedulable=true`） | **不受 Enabled 门禁** | ✅ **可以**——这是主要可验证面 |
| **控制操作** | `ControlActions`（26 个） | 25 个 disabled | ⚠️ 仅 `set_mos_policy` 可验证 |

证据：`GET /api/v1/drivers/jiabaida_bms/commands` 返回 5 个模板，
其中 `read_basic_info` 的 `schedulable: true`、`interval_ms: 5000` ⇒ 会被周期性轮询采集。

### 3.1 因此验证方案要调整

- **P4（采集验证）仍然可行且最有价值**：接入设备后，模拟器应答 5 类帧，
  平台应周期性落库 BMS 遥测（总压/电流/SOC 等 12 项）。
- **P5（操作验证）范围大幅缩小**：只能验证 `set_mos_policy` 1 个操作，
  且它是 **high 风险写操作**（会改 MOS 软件开关状态）——
  **在模拟器上安全**（模拟器可忽略/记录该写），但需 `recent_auth`。
- 其余 25 个操作的"验证"只能是**负向验证**：确认它们被正确拒绝（409/403），
  证明门禁有效——这本身也是有价值的验证。

## 四、诚实边界

1. 我先前文档里的「20 个 action」已作废，正确值是 **26 个**，可用 **1 个**。
2. 「读操作全禁用」是**设计如此**（driver 显式 `Enabled: false`），不是 bug——
   但我**没有**找到解释"为何读操作也要禁用"的注释（`protocol_unverified` 只标在写操作上）。
   读操作没有 AvailabilityCode，禁用原因需向作者确认。
3. 以上数字来自**代码调用**，不是生产 API 实测——因为 **BMS 设备尚未接入平台**，
   `GET /edge-devices/:id/actions` 无法调用。接入后应用 API 复核。
