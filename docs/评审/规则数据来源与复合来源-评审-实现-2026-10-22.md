## I2 五个改动点的相互踩踏与依赖顺序

**互相踩的点（会冲突/放大的）**：
1. **evaluator 匹配处加 MatchFrame（热路径）**：automation `Evaluate` 先 RLock 快照 rules 再锁外匹配（:856-882，可安全插 atomic 快照读取）；alert 的匹配循环在 **RLock 内**且已有 DB 查询（:278-299）→ 直接加 MatchFrame 会再叠一层锁内查询（H1，必须先修锁再插）。
2. **TriggerEvent 结构变更**：3 个生产构造点 + ≥8 个测试构造点（H2）；字段来源必须在 evaluator 侧填（deviceID=帧设备、TransitionSeq=快照 revision），否则 planner F4 读到零值 ⇒ 全部 auto 动作 fail-closed。
3. **alert 同款改动**：alert 没有 TriggerEvent，"钉成员"等价物是 `evalRule` 已收 deviceID 入参（:323 注释已说明勿用 TargetID）；但 alert 的 active 过滤/窗口 identity/陈旧 firing 关闭三件事都在同一函数链，需一次改完，不能拆 PR。
4. **窗口 identity（两引擎各改）**：sample 结构变更 + 写入点 + windowSatisfied + pruneWindow 边界保留语义（:1038-1060）都要一起改；只改 sample 不改 prune 判据不能解决 B2 的长 gap 拼接。
5. **钩子（并发/dispatcher）**：钩子既是 dispatcher 又是 snapshot 更新路径（B2）；若不先定 snapshot 所有者，两引擎会各自缓存 active ⇒ 漂移（SG-09 只测输出，不测内部快照一致）。
6. **同文件冲突**：automation/evaluator.go 同时被"匹配 + TriggerEvent 构造 + window identity"三处修改，M1 内必须按 4→5 顺序或同一 PR 内分阶段 commit，否则 rebase 冲突成本高。

**建议依赖顺序（M1 内部）**：
`models/迁移(两表两列+event列) → sourceref 快照骨架+原子发布接口 → datasource R1–R11 组适配+ActiveChange 统一 helper（含 R4 Next=0）→ sourceref MatchFrame/Combine → 先修 alert Evaluate 锁 → 两引擎 sample identity+MatchFrame 接入 → TriggerEvent 扩字段(3生产+8测试) → planner F4 改用 ev.SourceEdgeDeviceID → alert events 审计列 → E5/E6 与门禁 SG-01/04/05/07`。M2 的组 CRUD/前端必须早于 E2/E7（U7 也承认）。

## I3 S3"正确性不依赖钩子"是否成立

**不成立（至少方案没给出成立的充分条件）**。反例（钩子丢失 + 成员 A 死亡 + B 变 active）：

1. 前提：primary_backup 组 {A(active), B}；A 已连续 satisfied（窗口里有 A 的样本）；钩子通道丢失（未接线或静默丢事件），sourceref 快照停在 active=A。
2. A 死亡，DB/状态机切到 B（R2→R3），但 evaluator 侧快照仍旧：**B 的帧被当成非 active 直接丢弃**（§5.2 步 3）⇒ 规则永远不再求值（**G-2 liveness 失效**，不只是"慢一点"）。
3. A 网络恢复后继续上报，且**它仍被陈旧快照当作 active** ⇒ 其帧被接受。identity 若只由"同一次陈旧快照"派生，A 的 identity 前后相同 ⇒ S1 不清窗；automation `pruneWindow` 保留 cutoff 前最后一个样本（:1038-1060）⇒ A 的旧 satisfied 样本 + 恢复后新 satisfied 样本被拼成"连续满足"（跨 10 分钟 gap 也可能成立）⇒ **误触发**。
4. 若 identity 的 TransitionSeq/MembersHash 由 DB 状态机直接递增（非钩子）且快照能被独立刷新，则 S1 会清窗、误触发可避免——**但方案没写这条唯一所有者/发布路径**，反而把"正确性不依赖钩子"当作结论（D-11）。

**修法**：见 B2——快照必须由状态机事务提交后原子发布（钩子只做加速/审计），identity 用 DB 递增的 revision，pruneWindow 加 gap 上限；S3 红判据按上述三阶段场景实测。

另：S3 的"切断钩子 ⇒ 不误触发"这个实验本身也不能证明安全——它只覆盖"清窗失效"一种后果，不覆盖"陈旧 active 继续接收帧"这种更坏的方向。
