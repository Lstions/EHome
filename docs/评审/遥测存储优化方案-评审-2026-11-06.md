## 结论

**返修（不阻断方向，阻断落地顺序）**：三层分层（L1 写入收窄 → L2 帧级编码 → L3 rollup）方向正确，**容量结论在实测下成立**（§3.2 写入收益、§4.5 payload 体积、§6 收益表算术、§4.4 帧类型数量 均被独立复现，误差 ≤4%）；但方案有 **8 处会直接让落地出事的问题**，集中在三类：

1. **顺序反了**（B-1/B-2）：§7 阶段0 先「删 sensor_name_idx」，而支撑同一查询的 F-10 复合索引**在生产上还不存在**（下一个镜像才建）⇒ 中间窗口内长窗图表会退化；且「删模板」不等于「删索引」，生产上那 1.35 GiB 一条都不会消失。
2. **接线点不完整**（B-3）：§4.1 说「四处一致」，漏了 `createPartitionedParent` 的 **unified_data 回退语义**（未登记表会被套上 unified_data 的 DDL 与 6 条索引 ⇒ 启动 Fatal）和 **8 处硬编码 `{"unified_data","device_data"}` 清单**（保留期/彻底删除/合并历史/行数估算全都不碰新表）。
3. **引用的事实不存在**（B-4）：§5.4 要求「门禁名单更新」，而 `datalifecycle/rollup_retirement_gate_test.go` **在 main 上已被删除**（`bb19ee30` 删 490 行），现实是「没有名单可更新」。

另有 4 条（B-5~B-8）属于「照方案写完会在生产上表现为错误数据/缺口」：§4.3 量化表缺 9 个真实上报字段、§3.1 的 60 s 心跳对 device15 的 35/42 个字段从未生效（最大空档 9.4 小时）、§1.3 的 51.6% 无法复现、§5.3 读路径清单漏了生产实测 **211 秒**的 `latest-values`。

#### (b) 方案漏掉的两条索引，以及它反过来制造的**顺序错误**

方案 §7 阶段0 说「删 4 条死索引」，并在同段注释里说「下一个镜像启动会补建 F-10 复合索引（估算 +2–4 GB），**发版前必须先清盘**」。两句合起来意味着：**阶段0（删索引）发生在 F-10 索引创建之前**。

生产库当前真实索引集合（`pg_class` 只读查询）：

```
unified_data : pkey(id,timestamp) + device_id + sensor_name + timestamp + edge_device_id   （5 条）
device_data  : pkey(id,timestamp) + device_id + node_id + timestamp + edge_device_id        （5 条）
SELECT relname FROM pg_class WHERE relname LIKE '%device_sensor_ts%' OR relname LIKE '%device_ts_idx%';
=> (0 rows)      ← F-10 两条索引在生产上根本还不存在
```

而**生产现网的长窗单字段图表正靠 `sensor_name_idx` 支撑**（EXPLAIN ANALYZE，device14 / rsoc / 30 天）：

```
Parallel Bitmap Heap Scan on unified_data_202610
  ->  Bitmap Index Scan on unified_data_202610_sensor_name_idx
        Index Cond: ((sensor_name)::text = rsoc)
        rows=1802080
  Rows Removed by Index Recheck: 17041980
Execution Time: 12165.066 ms
```

禁掉 bitmap scan 后（模拟无 `sensor_name_idx`）同一查询退化为：

```
Parallel Seq Scan on unified_data_202610
  Rows Removed by Filter: 18174839
Execution Time: 9050.369 ms   ← 单分区；实际查询还含 202611 分区
```

反过来，**只要 F-10 索引存在，`sensor_name_idx` 就是冗余的**。在 `ehome_review_bench2`（14.3 M 行真实数据、代码模板 7 索引）实测：

| 配置 | 30 天单字段（device14/rsoc）执行计划 | 耗时 |
|---|---|---:|
| 7 索引（含 F-10） | `Index Only Scan using ..._device_id_sensor_name_timestamp_value_idx`，`Heap Fetches: 0` | **47.3 ms** |
| 7 索引但已 `DROP INDEX ..._sensor_name_idx` | 同上（仍走 F-10） | **34.4 ms** |

⇒ 两个事实同时成立：① F-10 建好后 `sensor_name_idx` 可安全删；② F-10 建好前删它是退化。方案 §7 把「删」放在阶段0、「建」放在下一个镜像，**中间窗口正是生产现网的状态**。这是阻断项 **B-1**。

### 1.2 §4.1 `telemetry_frame` 表设计 vs `partition_mgr.go` 四处一致性

**结论：方案把「四处」当成充分条件，实际不充分 —— 漏掉的两处会让新表建不起来，另有两处会让新表变成「永远不被清理的第二张无界表」。**

方案 §8 风险表最后一条写：「同改 `partitionParentDDL` / `partitionCopyColumns` / 索引模板 / GORM models 四处」。代码事实：

| # | 位置 | 真实语义 | 方案是否覆盖 |
|---|---|---|---|
| 1 | `partitionParentDDL`（:420-443） | 每表 DDL 模板 | ✅ 覆盖 |
| 2 | `partitionParentIndexes`（:602-621） | 通用索引模板 | ✅ 覆盖 |
| 3 | `partitionParentIndexesPG`（:626-630） | PG 增强版，**按索引名「替换」而非追加**（`:487-505` `effectiveParentIndexTemplates`） | ❌ **未覆盖** |
| 4 | `partitionCopyColumns`（:635-638） | 迁移 INSERT...SELECT 的列清单 | ✅ 覆盖 |
| 5 | `createPartitionedParent`（:645-675） | **未登记表回退到 `partitionedTable`（= unified_data）的 DDL 与索引清单** | ❌ **未覆盖，且致命** |
| 6 | 8 处硬编码 `[]string{"unified_data", "device_data"}` | 保留期 / 彻底删除 / 合并历史 / 行数估算 | ❌ **完全未覆盖** |

**#5 的机制**（`partition_mgr.go:645-667`）：

```go
ddlTable := table
if _, ok := partitionParentDDL[ddlTable]; !ok {
    ddlTable = partitionedTable          // partitionedTable = "unified_data"（:29）
}
if err := db.Exec(fmt.Sprintf(partitionParentDDL[ddlTable], name)).Error; err != nil { ... }
for _, tmpl := range effectiveParentIndexTemplates(db, ddlTable, name) { ... }
```

⇒ 只在 `partitionParentDDL` 登记而**没在 `partitionParentIndexes` 登记**的新表，会被套上 unified_data 的 6 条索引模板，而其中 `sensor_name` / `edge_device_id` / `created_at` 等列在新表里**不存在** ⇒ `CREATE INDEX ... (sensor_name)` 直接报 `column "sensor_name" does not exist`，**启动 Fatal**（建表错误一路返回到 `main.go:94-99` 的 `logger.Fatalf`）。

所以 `partitionParentIndexes["telemetry_frame"] = {}` 这个**空登记是强制项**，不是可选优化 —— 方案一个字都没提。同理 `partitionCopyColumns` 未登记时也会回退到 unified_data 的列清单（`:699-704`）。

**#6 的机制**（生产代码，逐条）：

| 文件:行 | 用途 | 新表不登记时的后果 |
|---|---|---|
| `datalifecycle/retention_task.go:316` | 分区 DROP（保留期） | 帧表分区**永不随保留期淘汰** |
| `datalifecycle/retention_task.go:353` | 精确 DELETE | 同上 |
| `datalifecycle/purge_edge_device.go:421` | 设备「彻底删除」 | 删设备后帧数据**永久残留**（产品承诺的彻底删除破约） |
| `api/handler_edge_device.go:2184` | merge-history 改 device_id | 合并历史后帧数据**留在源设备**，历史分裂 |
| `api/handler_edge_device.go:1539` | data-summary 时间范围 | 弹窗数字不含帧数据 |
| `api/handler_edge_device.go:2314` | latestDeviceTimestamp | 同上 |
| `datalifecycle/row_estimate.go:46` | 行数估算 | 同上 |

这 8 处在方案里**没有任何提及**。方案 §5.3 只把所有读路径改成读新表，却没把「新表加入生命周期管理」写进任何一节。这是阻断项 **B-3**。

### 3.1 §3.1 的 60 s 心跳对 device15 的 35/42 个字段从未生效

用 §3.1 的规则在 11-04/11-05 两天数据上模拟（帧级规则，与 §3.2 的 117,195 完全一致），统计每个 `(设备, 字段)` 相邻两次落库的最大间隔：

| 设备 | 字段数 | 最大落库间隔 > 60 s 的字段数 | 最坏情况 |
|---|---:|---:|---|
| device14 | 29 | **0** | 23 s（源数据本身最大帧间隔 23.1 s） |
| device15 | 42 | **35** | `work_mode` / `fault_code` / `alarm_*` 等 **33,671 s ≈ 9.4 小时** |

⇒ 方案宣称的「心跳保证时间轴连续、图表不空档」对 device15 的绝大多数字段**不成立**：这些字段在 L1 后会出现最长 9.4 小时的空档，图表上就是断线。根因是「心跳按设备判」而「字段按帧类型出」，两者粒度不匹配。

（回归基线 §11.1 第 3 条独立观察到「60 s 心跳在本批数据里从未触发（max gap 33.7 s / 16 帧）」，与我这里的「35 个字段出现 >60 s 空档」是同一现象的两种表述：**心跳条件本身触发过，但它写的那一帧并不包含这些字段**。）

### 3.2 §1.3「51.6% 的行与前一条完全相同」证伪，且 §1.4 混用两个口径

- 我独立按四种口径算 2026-11-04 全天 2,811,888 行：**按字段序相邻同 (设备,字段) 值相同 = 2,156,694 / 2,811,888 = 76.70%**（dev14 76.64% / dev15 77.20%）。回归基线另算得 4.34%（整帧与上一帧相同）、0.00%（按 id 序完全相同）、7.37%、14.11% —— **五种口径里没有一种给出 51.6%**。
- §1.4 写「1 Hz 全量数据本身只有约 1.6 MB/天（142,467 帧 × 12.1 B）」。12.1 B 是**编码后 payload**，不是「原始信息量」。原始总线帧实测：device14 **恒 78 B**（443,400 行全部 78.00 B），device15 **40–60 B（均值 48.7 B）** ⇒ 原始帧字节 ≈ 86,342×78 + 56,125×48.7 = **9.5 MB/天**，不是 1.6 MB。两数差 6 倍，混在同一段论证「放大 300–400 倍」里会让人算不出正确结论（按原始字节算放大 ≈ **52 倍**，按 payload 算是 **439 倍** —— 两个都「对」，但必须说清分母）。

### 3.3 写路径既有语义：`Create(&records)` 批量插入 + `time.Now()` + latestSink 位置

方案 §7 阶段1 指出「把 `latestSink` 调用提到 INSERT 之前（现在它在 `Create` 成功的 else 分支里）」。**核实结论：✅ 方案识别完全正确**。HEAD `a0a983bf` 的 `consumers_heavy.go:354-380`：

```go
now := time.Now()                       // :354  <- 服务器时间，不是设备时间
records := make([]models.UnifiedData, 0, len(sensorData))
for _, sd := range sensorData { records = append(records, ... Timestamp: now) }   // :355-364
if len(records) > 0 {
    if err := c.db.Session(&gorm.Session{}).Create(&records).Error; err != nil {   // :366
        metrics.DataConsumerDBWriteFailures...
    } else if c.latestSink != nil {                                                 // :369  <- 成功才更新缓存
        for i := range records { c.latestSink(records[i]) }                         // :376-378
    }
}
```

但方案**没有覆盖**以下三点：

1. **`Timestamp: now` 是服务器接收时间，不是设备采样时间**。`DataEvent` 里有 `Timestamp uint64`（`databus/bus.go:16`）与 `ReceivedAt time.Time`（`:24`），两者在 unified_data 写入路径上**都没有被使用**。L2 的 `telemetry_frame.ts` 直接继承这个口径（`telemetry/encoder.go:254-259` 用 `at.UnixNano()` 做 seq 键）⇒ 一旦设备时钟/NTP 有偏差，帧时间轴仍以服务器为准。方案 §4.1 把 `ts` 当「帧时间」讲，却没说明它与设备采样时间的差异；§9.1「解码重建的 1 Hz 序列与旧表逐值对比」也只能比出「和旧表一样」，比不出「和物理世界一样」。
2. **`now` 是每帧算一次，同一帧内 29 行共用同一个 `now`** —— 这是 `latestValueCache` 按 `created_at` 相等取整帧的前提（`api/latest_value_cache.go:139-140` 注释明说）。L1 过滤后**同一帧只剩「变化的行」**，若某帧只有 1 个字段变化，则该帧在 unified_data 里只有 1 行 ⇒ `/overview` 回落 SQL「按 created_at 取整帧」拿到的就是 1 个物理量，**形状从 N 个变成 1 个**。这正是 `latest_value_cache.go:15-23` 记录过的历史缺陷（「实测一帧 14 个物理量最后只剩 1 个」）在 L1 后的**复发路径**。方案 §3.3 只写了「写库成功才更新缓存」，没写这个形状问题。
3. **`Create(&records)` 的 GORM 语义**：对 slice 调用 `Create` 会生成**一条多值 INSERT**（不是 N 条），这是 L1 收窄后仍然成立的前提（`persist` 子切片也是一条语句）。但方案 §7 阶段1 写「增加『值不变且未到心跳 ⇒ 跳过 INSERT』」在语义上意味着「每行一次 INSERT 判断」，与实际的批量语义不符 —— 实现时若真逐行 Create，写入次数会从 1 涨到 29，反而更慢。这是一句会导致错误实现的表述。

### 3.4 §9 验收标准里有 2 条现在就无法通过

- §9 第 3 条「写入行数 ≤ 150k/天」：L1 后 117,195 帧 = 2,500,195 行/天（每帧 29 行）⇒ **行数不是 117k，是 2.5M**。方案把「帧数」和「行数」混用了。真实达标要等 L2 落地（§6 的 117,195 是**帧级行**）。
- §9 第 4 条「24 h 单字段图表 ≤ 300 ms（**现 5.3 s**）」：**口径错**。5.3 s 是 `partition_mgr.go:583` 注释里记的**30 天**窗口历史值；生产实测 24 h 单字段 = **368.7 ms**（raw）/ **329.3 ms**（SQL 分桶），30 天 = **12,165 ms**。把 24 h 的现状写成 5.3 s 会让「改造收益」虚高一个数量级。

### 3.5 device 16（光学雨量计）完全不在方案视野内

方案 §1.1 的基线只统计 device 14/15，但生产上还有一台 **enabled 的 device 16**：每天写 17,278 行 `device_data`（`error_code=1`、`raw=""`）、`unified_data` **0 行**。取证结论：不是驱动 bug、不是解析失败，而是固件 RX 全程超时 18.8 天、0 条告警。它占 0.28 GB/月的纯噪音。
