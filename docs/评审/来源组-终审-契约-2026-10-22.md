## 0. 必答：如果现在合进 main，最坏会发生什么

**场景 A（阻断 B1，无需回滚即可触发）**：用户建一个 **composite（1+2 光照）组**，在规则里把来源选为该组并把 `cooldown_sec` 设为 0（默认值或用户填 0）。保存**不会被拒绝**——保存期 cooldown 下限校验被写死为只对 `primary_backup` 生效（`source_group_guard.go:133`）。于是两台光照传感器 5s 交错上报时，每一帧都驱动整组求值且冷却为 0 ⇒ **一次物理变化可以连续触发多次动作**（G-2/S5 的"同一次变化 1 条事件 1 次动作"被直接违背，例如反复下发开/关灯或反复写 MOS）。
**场景 B（阻断 B3，回滚时触发）**：绑组规则保存时锚点=A；此后管理员把 A 移出组、把 B 调成最高优先（组更新 API 允许，`group_crud.go` 成员整体替换无规则引用检查）。此时若回退旧二进制，旧路径按 `trigger_edge_device_id=A` 只读 **A**——A 仍在其他业务上报 ⇒ **规则用已不属于该来源组的设备读数触发动作**（"作用到错误物理量"的回滚版本）。

## 1. 阻断项（4）

### B1【阻断】V-8/F-3 只对 primary_backup 生效，composite 规则可保存低于成员采集间隔的 cooldown

- **契约**：方案 §12.9.1 **F-3**（L750）："`cooldown_sec ≥ max(成员采集间隔)`…用户输入更小值 ⇒ 400 并给出推导值"；动机原文就是"挡不住**成员 5s 采集间隔下的交错帧双动作**（架构 B-5）"，并新增 E11 交错帧用例。**未按 kind 限缩**。
- **代码**：`backend/internal/api/source_group_guard.go:133` — `if requireCooldownFloor && group.Kind == models.SourceGroupKindPrimaryBackup {`。composite 分支直接跳过，任何 `cooldown_sec`（含 0）都保存成功。
- **测试缺口**：`source_group_guard_test.go` 只有 primary_backup floor 用例（:214-224）；`internal/e2e/source_group_e2e_test.go:217` 的 E11 只测 Combine 纯函数"退化不静默"，**没有保存期 floor 断言**。gates 20/20 不覆盖此格。
- **修法**：去掉 kind 条件（对 source_group 一律检查 floor；alert 无 cooldown 不受影响），并在 guard test 增加 composite `cooldown=0 ⇒ 400` 负例。

### B2【阻断】I6/"停用"侧未实现：被规则引用的组/成员设备可被 enabled=false，规则静默变 unbound

- **契约**：§2.2 **I6**"被任何规则引用的组**禁止删除、禁止 enabled=false**"；F-5/V-13 明确列"删除/停用/合并…共 5 处"。
- **代码**：① `internal/datasource/group_crud.go:434-436`（UpdateGroup）：`if in.Enabled != nil { updates["enabled"] = *in.Enabled }` — 无 `GroupRuleReferences` 检查（该检查只在 `DeleteGroup` `group_crud.go:537` 使用）；② `internal/api/handler_source_group.go:276-315` update 直接调 gsvc.UpdateGroup，无 409 分支；③ 边缘设备更新路径 `handler_edge_device.go:870` `updates["enabled"] = *dto.Enabled` 无任何来源组守卫（`source_group_guard.go` 只挂在单删 :1063 / 批量删 :1139 / 逻辑合并 :116）。
- **后果**：前端/API 停用被规则引用的组或组成员设备 → 规则下一次求值 `group_disabled`/成员缺席 ⇒ **静默不触发**（只有审计可查），正是本方案要消灭的"静默失效"类。删除路径有 409（证据：`handler_source_group.go:315` 注释 + DeleteGroup），停用路径没有。
- **修法**：UpdateGroup 在 `enabled=false` 时复用 GroupRuleReferences（组被直接引用 ⇒ 409）；边缘设备 update 在 `enabled=false` 且是成员时 409；补两条负例测试。

### B3【阻断】回滚锚点只在"规则保存"时写；组成员/优先级变更后不重算 ⇒ 回滚旧二进制可能对"已移出组的设备"触发

- **契约**：§12.1 **N-7**（v0.3 未覆盖该句）：锚点"保存/**成员变更时重算**"；方案 §9.2 回滚铁律 = 绑组规则必须双写非 0 锚点，旧二进制退化为"只看主成员"。
- **代码**：`grep -rn 'trigger_edge_device_id' internal/datasource` 在非测试代码中**零写入**（唯一命中是 `group_service.go:485` 注释"规则保存期把它写入…"）。锚点写入路径只有规则侧：`handler_automation.go:246/477`（创建/更新）与 `handler_alert.go:121/232`。组成员变更（`group_crud.go:380 replaceMembers` / `:288 UpdateGroup`）不触碰任何规则行。
- **后果**：见 §0 场景 B。方向是"可能用错误来源触发"，不是安全方向；且 N-7 的"可接受降级"承诺不再成立（降级到的是历史上曾是主成员、现已被移出组的设备）。
- **修法**（二选一）：① 成员/priority 变更事务内重算 anchor 并回写该组全部绑组规则的 `trigger_edge_device_id`（automation）/`target_id`（alert）；② 若判定成本过高，则在成员变更时对"该组被规则引用"返回 409（把不变量从"自动维护"改成"禁止变更"，需 lead 裁决并改方案）。任一都需要测试：改成员后读规则锚点断言。

### B4【阻断】F-8 `source_frame_discarded` 节流事件与 `source_rule_silent_seconds`/`source_frame_discarded_total` 指标**完全未实现**，而 §12.9.3 R-9 把它列为放行项并声称 E3a 必落

- **契约**：§12.9.1 **F-8**（L755）：求值期丢帧路径新增节流健康事件 `source_frame_discarded` + 两个指标；E3a 断言"钩子不接线 + active 静默 ⇒ 必落 `source_frame_discarded`（reason=not_active_or_silent）"；§12.9.3 **R-9** 为放行条件。
- **代码**：全仓非测试代码仅 `internal/models/source_group.go:137` 的注释提到该事件；`grep -rn 'frame_discarded' backend/internal backend/scripts backend/internal/e2e` 无任何写点/断言；`source_rule_silent_seconds` 零命中。丢帧路径本身存在（`automation/source.go:266-267`、`alert/source.go:229` `if !m.Accepts() { return m, false }`——静默 return，无审计）。
- **危害**：合入后 §12.9.3 的放行证据（"E3a 断言必落"）不成立，且"备成员帧被丢"这一 S1 前提在运维侧不可观测；门禁 20/20 不含此项。
- **修法**：在 `!Accepts()` 与 stale/not-eligible 丢弃点调用节流 health 写入（复用 `notifySourceHealth`/group_service.writeGroupHealth，按 (group,reason,1min) 节流）并注册两个指标；补 E3a 断言。若本期不做，必须从方案 §12.9.1 F-8/§12.9.3 R-9 删除并由 lead 显式豁免（不能保留"已收口"表述）。
