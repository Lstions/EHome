## 结论

**仍有 3 项阻断部分闭环 + 1 项高优部分闭环，暂不能判"全部闭环"**：B-3（required 语义被 §12.3 真值表变成死字段）、B-4（12.2.2 的 `group.revision+1` 写在与 R1 运行态同一事务里，按字面实现会每帧换 identity ⇒ 反而打死刚修好的 DurationSec）、B-5（硬拒 `cooldown<1` 只挡 cooldown=0，不挡成员采集间隔 >1s 时的同一物理变化重复动作，G-2/S5 仍不可证伪）；H-6（独立表方向正确，但 §12.5 M0 迁移清单只写"两表+两列"，把 N-11 新增的两张组日志/健康表漏了）。B-1/B-2/H-1/H-2/H-3/H-4/H-5 判闭环（B-2 有细小残留）。另发现 2 处 §12 自身引入的新矛盾（见 §4），其中修订 2 直接影响 B-4 判定。

## 3. 任务点名三问的直接回答

1. **§12.2.1 按 kind 分流是否真解决 B-1？** 是。判定表把"帧进入求值条件"和"identity 组成"按 kind 分开，composite 无 active 概念与 N-1 的 V-7/SG-10 自洽；未发现与 12.2.3 S1/S7 的冲突（S1 只约束 primary_backup，S7 补 composite DurationSec）。**唯一衔接风险在 GroupRevision（见 §1 B-4）**，不在分流本身。
2. **§12.2.2 是否真解决 B-4 身份悖论？** identity 组成解决了；**但 12.2.2 的所有权/发布段把 `group.revision+1` 与每帧运行态写并列，按字面实现会重新制造"每帧换 identity"，B-4 修复失效**。这不是文字瑕疵：R1 的调用点是每帧解析成功（nodemgr sourceHealthSink→datasource.MarkSuccess），实施者按 §12.2.2 伪代码写即中招；且"每事务提交后发布全量不可变快照"在每帧调用下是 O(组×成员) DB 重建，与 U3（MatchFrame ≤20ns）及"热路径零 DB"精神冲突。修法同 §1 B-4：revision bump 白名单 + 发布节流（仅拓扑/active 变更即时发布；运行态字段由 60s 扫描周期或 delta 更新），并把"快照里 last_success 的新鲜度"单独定义（否则 E-2 staleness 判据用的是旧快照时间）。
3. **N-5 硬拒 cooldown<1 是否可接受的产品取舍？** **方向可接受，当前参数不可接受，本质仍是把问题推给用户**：①1s 与成员轮询（默认 5s）无关，不能保证 G-2/S5；②用户不知道自己的 composite 该填多大 cooldown；③S5 门禁只验 400、不验行为，会用"配置红"冒充"语义闭环"。可接受方案：保存期把 cooldown 下限**推导**为组内成员最大采集间隔（与 Q-3 同源，UI 回填并展示理由），或诚实把 G-2/S5 改写为"冷却窗内至多一次动作"并补交错帧行为用例；不可接受的是维持 `<1` 字面门槛。

## 4. §12 本轮新引入的矛盾（需在 v0.3 修）

1. **revision bump 与 identity**（§12.2.2:611 步骤① vs §12.2.1:602 identity）：见 B-4，后果是 S1 每帧清窗 + 全量快照每帧重建。
2. **required 死字段**（§12.3:639-640 vs D-4/V-3/E-5）：见 B-3，需删字段或恢复 D-5 原始语义。
3. **迁移清单缺表**（§12.5:678 "两表" vs N-11 新增两表）：见 H-6，M0 迁移/门禁/批次验收需同步。
4. 次要不阻塞：V-5b/V-8 未进 §7.3；`source_silent`/`source_rule_silent_seconds` 未进 §10；§4.4 旧表加列正文与 §12 冲突（已声明 §12 优先，建议在 §4.4 行内标注"由 N-11 替换"防实施者误读）。
