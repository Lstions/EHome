# 雨量计 7 小时静默事故：根因结论（已独立核实）

> 2026-09-22 ｜ 参与：Lead + 2 名独立核实者（verify-uart-queue / verify-silent-swallow）
> 核实方式：**以证伪为默认姿态**，Lead 主动提交自我反证；结论经第三方代码路径与 RED/GREEN 复现验证。

## 一、事故现象

主机断电 7 小时恢复后，真实雨量计（SN-3001，ESP32-C6 UART1 = GPIO20/21 @4800 8N1）
持续读不到数据：设备上行 3714 帧全部 `error_code=1 raw=""`；服务端侧无任何告警。
手动复位 ESP32 后立即恢复（`RX events=2`、无 timeout、采集与指令均正常）。

## 二、根因（已确证）：FreeRTOS QueueSet 的「成员必须为空」约束 + 静默失败 + 自锁

### 机制链

1. `uart_driver_install()` 立即注册 RX 中断（IDF `uart.c:1525` `xQueueSendFromISR(p_uart->event_queue, ...)`）
   ⇒ **从装好那一刻起**，只要总线上有字节，事件队列就会非空。
2. `rebuild_uart_event_set()` 里 `xQueueAddToSet(event_queue, set)`（`bus_worker.c:634`）；
   真实 FreeRTOS 有**两条**拒绝条件（已由 Lead 亲自读到 `queue.c:3260-3272`）：

   ```c
   if (pxQueueOrSemaphore->pxQueueSetContainer != NULL)      return pdFAIL;  // 已属别的集合
   else if (pxQueueOrSemaphore->uxMessagesWaiting != 0)      return pdFAIL;  // ★ 队列非空
   ```

3. 若雨量计恰好在 `install → rebuild` 窗口内回了一个字节 ⇒ 队列非空 ⇒ `pdFAIL`；
   而现场代码**只打一条日志**（`ESP_LOGE("failed to add UART channel slot %d event queue")`），
   **不重试、不上报、不记录到 `s_uart_event_members[]`**。
4. **自锁**：队列集里没有该成员 ⇒ `rx_task` 的 `xQueueSelectFromSet` 永远 select 不到 ⇒
   永不 `xQueueReceive` ⇒ 队列**永远保持非空** ⇒ 后续每次 `suspend/resume` 重建时**继续 pdFAIL**。
   `destroy_uart_event_set()` 只遍历 `s_uart_event_members[]`（失败的队列从未进入该数组）⇒
   **连 reset 都轮不到它**。
5. 于是 `expire_uart_state()` 的超时分支成为**全仓唯一的 `error_code=0x01` 发射点**
   （`bus_worker.c:1423`）——精确对应现场每一帧 `error_code=1`。

### 为什么「断电恢复」中招而「手动复位」不中招

**不是**「清单晚到 13.5 分钟」本身，而是**真实字节是否落在 install→rebuild 的窗口内**：

| 场景 | 雨量计状态 | 窗口内是否有字节 | 结果 |
|---|---|---|---|
| 断电恢复 | 与主机**同时上电**，持续主动上报 | **几乎必然有** | 命中缺陷，永久自锁 |
| 手动复位 | 早已上电，**只在被轮询时才应答** | 通常静默 | 不命中，正常 |

清单晚到只是**把窗口拉长**（提高命中概率），不是机制本身。

## 三、为什么潜伏至今：测试桩与真实内核不一致

仓库自带的 host 测试桩 `esp32-collector/host_tests/stubs/freertos/queue.h:196-206`：

```c
if (q->set_container != NULL || s->member_count >= MAX_QUEUE_SET_MEMBERS)
    return pdFAIL;                  // ← 缺少真实内核的 uxMessagesWaiting != 0 检查
```

**⇒ 现有 host 测试在结构上不可能发现本缺陷。**（核实者用「忠实桩」重跑，测试立即变红，反证了这一点。）

## 四、第二个缺陷：设备健康上报假绿（独立存在，且足以让事故静默 7 小时）

1. `uart_cmd_loop` 的 CMD_SAMPLE 分支（`bus_worker.c:949-955`）在 **TX 被接受**时就调用
   `scheduler_notify_channel_success()`，与 RX 结局无关。
2. 该函数（`scheduler.c:432-441`）会**递减** `error_count`。
3. 而 `error_count == 0` 时 `handler_data.c:146` **整条跳过 EdgeDeviceHealth 子帧**：
   `if (!cmd->enabled || cmd->error_count == 0) continue;`

**⇒ 每次采样都失败时，error_count 反被清零，服务端 `comm_status` 永远显示 OK。**
**⇒ 本次事故持续 7 小时，运营侧没有任何来自该通道的健康告警。**

> 核实者对本缺陷的裁定是「**部分属实**」：Lead 原先「既不报错也不上报」的表述**不成立**
> （0x01 确由 rx_task 独立上报，服务端 3714 帧正是证据）；真正的缺陷是
> **「已上报失败」与「同一事务又计入成功」并存**，导致健康面假绿。此项已按核实结论重新定级。

## 五、修复方案（可破坏性更新）

### 修复 1：attach 前排空 + 临界区（根治自锁）

```c
taskENTER_CRITICAL(&s_uart_set_mux);
uart_event_t stale;
while (xQueueReceive(event_queue, &stale, 0) == pdTRUE) { }   /* 满足「必须为空」 */
BaseType_t added = xQueueAddToSet(event_queue, set);
taskEXIT_CRITICAL(&s_uart_set_mux);
if (added != pdPASS) { ESP_LOGE(...); /* 不再静默 */ }
```

字节不丢：被排空的事件只是「有数据」通知，`rx_append_from_event` 会循环 `bus_dma_read` 直到读空。

### 修复 2：attach 失败不再是静默

把「只打日志」升级为返回错误 / 重试 / 计数上报；否则同类静默失败必然复发。

### 修复 3：健康语义从 TX-accept 改为 RX-complete

- 删去 `bus_worker.c:955` 的 `scheduler_notify_channel_success()`；
- RX 超时路径（:1417-1426）补 `scheduler_notify_channel_error()`；
- `0x01/0x02/0x03` 的 owner **唯一化到 rx_task**（防重复计数）；
- 成功率统计迁到 rx_task，或改为分别打印 tx / rx_ok / rx_timeout。

### 修复 4：测试桩与真实内核对齐

- `host_tests/stubs/freertos/queue.h` 的 `xQueueAddToSet` 补上 `uxMessagesWaiting != 0` 检查；
- 补回归：① 队列非空时 attach 必须走修复路径；② TX 成功但 RX 超时时 `error_count` **递增**；
  ③ `error_count > 0` 时 EdgeDeviceHealth 子帧必须出现。

2. **命中窗口概率未量化**：install→rebuild 窗口长度与 4800 baud 下的命中概率需仪器或故障态日志。

# 独立核实结论与修复实施（2026-09-22）

## 一、核实结果：三个断言，一个被证伪、一个部分属实、一个找到真根因

| 我（Lead）的原断言 | 独立核实裁定 | 依据 |
|---|---|---|
| **C1**「UART 驱动晚于队列集 ⇒ 事件永远进不了集合」 | **证伪** | `bus_worker_resume()`（`bus_worker.c:1577`）**会**重建队列集；时序上 `config_apply_transaction_execute`(315) 在 `resume`(371) **之前**，所以首次安装的驱动必在被重建的集合之前。我主动提交了这条自我反证 |
| **C2**「`rl==0` 被静默吞掉，既不报错也不上报」 | **部分属实** | UART 的 CMD_SAMPLE 走 `bus_dma_write`（fire-and-forget），**根本不产生 `rl`**；真实 `0x01` 由 rx_task 独立上报。但**统计口径确实误导**：`rate=(txn-errs)*100/txn` 不含 RX 超时 |
| **D**「现场证据支撑 C1」 | **不足以支撑** | 我引用的 `RX_TASK events=0` 原文未留存于仓库；且无法与「设备侧无应答」区分 |

### 真正的根因（核实者发现，经我独立确证）

**FreeRTOS `xQueueAddToSet` 的「成员必须为空」约束 + 静默失败 + 自锁**：

1. 我亲自读到内核源码 `queue.c:3266-3271`：
   `else if (pxQueueOrSemaphore->uxMessagesWaiting != 0) xReturn = pdFAIL;`
2. `uart_driver_install()` 立即注册 RX 中断（IDF `uart.c:1525`），**从装好那一刻**队列就可能非空。
3. 若雨量计在 `install → rebuild` 窗口内回一字节 ⇒ `xQueueAddToSet` 返回 `pdFAIL`，
   而 `bus_worker.c:634` **只打一条日志**，不重试、不记录。
4. **自锁**：队列进不了集合 ⇒ rx_task 永不 select 它 ⇒ 永不消费 ⇒ 永远非空 ⇒
   后续每次 rebuild 继续失败；`destroy_uart_event_set()` 只遍历 `s_uart_event_members[]`，
   失败的队列从未入该数组 ⇒ **连 reset 都轮不到它**。
5. 于是 `expire_uart_state()` 成为全仓唯一 `error_code=0x01` 发射点 —— 精确对应现场症状。

**为什么断电恢复中招、手动复位不中招**：不是「清单晚到」本身，而是**真实字节是否落在窗口内**
（断电恢复时雨量计与主机同时上电、持续主动上报；手动复位时雨量计早已上电、只在被轮询时应答）。

### 我的独立复现（不依赖核实者产物）

`/tmp/lead_repro.c`（我自写，按 `queue.c` 源码语义）：
```
[A] 队列空   -> attach=pdPASS members=1  => PASS(正常路径)
[B] 队列非空 -> attach=pdFAIL members=0  => PASS(复现了缺陷)
[C1..C3] 连续 3 次 rebuild 均 pdFAIL waiting 恒为 1 => PASS(确证自锁)
```

## 二、已实施的修复（可破坏性更新）

### 修复 1：attach 前排空 + 临界区（根治自锁）

`components/bus_worker/bus_worker.c`：
- 新增 `static portMUX_TYPE s_uart_set_mux`；
- `xQueueAddToSet` 前先 `taskENTER_CRITICAL` + 排空事件队列，再 attach，再 `taskEXIT_CRITICAL`；
- **attach 失败不再静默**：记录进 `s_uart_event_members[]`（使后续 destroy 能 reset 它），并升级日志。

字节不丢：被排空的只是「有数据」通知，`rx_append_from_event()` 会继续 `bus_dma_read()` 直到读空。

### 修复 2：通道健康从 TX-accept 改为 RX-complete

`components/bus_worker/bus_worker.c`：
- **删除** CMD_SAMPLE 在 TX 被接受时的 `scheduler_notify_channel_success()`；
- RX **超时**路径补 `scheduler_notify_channel_error(rt->bus_ch[i])`；
- RX **短读**路径补 `scheduler_notify_channel_error(rt->bus_ch[idx])`；
- RX **完整响应**路径补 `scheduler_notify_channel_success(rt->bus_ch[idx])`；
- 健康 owner 唯一化到 rx_task（cmd_task 只报 TX 失败），避免重复计数。

### 修复 3：测试桩与真实内核对齐

- `host_tests/stubs/freertos/queue.h`：`xQueueAddToSet` 补上真实内核的 `count != 0` 拒绝条件；
- `host_tests/stubs/freertos/FreeRTOS.h`：补 `portMUX_TYPE` / `taskENTER_CRITICAL`（host 空实现）；
- `host_tests/bus_worker_rx_tests.c`：
  - `scheduler_notify_channel_*` 从**空桩**改为**可观测计数器**（这是缺陷能躲过全部现有测试的直接原因）；
  - 新增 4 条回归：非空队列仍须 attach、跨 resume 幂等、RX 超时须报 error、完整响应须报 success。

1. **缺陷 2 的 CMD_SAMPLE 路径未被测试覆盖**：变异 M3（把 TX-accept success 加回）**没有让测试变红**，
   因为 `uart_cmd_loop` 在 host 测试中难以驱动（需构造完整运行时与队列）。该修复靠**代码审查 + 
   目标平台编译**保证，**未**由自动化测试锁定 —— 这是已知缺口，应补一个 `uart_cmd_loop` 级测试。
2. **假绿主因更正**：我原以为「测试桩漏掉 count 检查」是主因；变异 M2 证明即使桩弱化，新测试**仍会变红**。

   因此「本根因」与「设备侧无应答」在现有证据下仍不能 100% 排他。要定案需抓一次故障态串口日志。
4. **未烧写设备**：修复已编译通过，但**尚未刷入 ESP32**；线上仍运行旧固件（当前采集正常）。
