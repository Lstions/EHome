## 2. 保留期裁决 (含与 D-1「审计价值」的一致性论证)

### 2.1 不变式 (核心)

> **投递证据的保留期 ≥ 被审计对象 (通知本体) 的最长保留期。**

D-1 保留投递审计, 为的是事后追溯"**某条通知当时是否送达**"。这个追问的**窗口长度由通知本体决定** —— 通知本体还在 (用户还能在通知中心看到、还能追问), 证据就必须还在。证据早死一天, 就是删掉 D-1 要保的东西。

### 2.2 一个已被证伪的错误论据 (留档防回归)

第一版曾以 "delivered 行是 notifications 行的**冗余第二份拷贝**" 为由, 把成功记录压到短窗 (基准/2 = 45 天)。**领队独立复核把这条论据当可证伪断言跑, 推翻了它**:

- `models.Notification` (models.go:376-386) 字段只有 `ID/Type/Message/Title/Description/Source/SourceID/Read/CreatedAt` —— **没有任何投递状态列**;
- 全仓只有 `dispatcher.go` **写** `notification_deliveries`, 无第二处**读**;
- 领队的反证 (`leadproof/proof_test.go`) 实测: 60 天前的未读通知本体**存活** (180 天窗内), 而 45 天窗把它的 delivered 证据**删了** ⇒ 追问对象在、证据没了。

**结论**: delivered 与 failed **同样是唯一证据** —— 前者答"送达没有"(问题 A), 后者答"为什么没送到"(问题 B), 两个问题都只有这张表答得了。第一版把 "**诊断**价值" 当成了 "**审计**价值"; 而预期路径 (成功) 恰恰是审计要证明的东西 ("我说发了, 证据呢")。

### 2.3 修正后的策略

| state | 窗口 | 理由 |
|---|---|---|
| `delivered` | 180 天 (= 通知本体最长窗) | 唯一证据, 必须活得比被审计对象久 |
| `failed` | 180 天 (同上) | 唯一证据 (诊断信息), 同上 |
| `pending` | 180 天 (同上) | 崩溃窗口证据 (dispatcher.go:186-204), 同窗 |
| 未知 state (白名单外) | **永不删除** | fail-closed: `state IN (...)` 白名单而非 `state <> 'delivered'` |

**为什么不再分档 (某档更短或更长)**:
- 更短: 支撑它的唯一论据 (冗余) 已被证伪, 无新理由;
- 更长 (如 only-failures 永久保留): 会让表重新**无界增长** —— 那正是 D-1 明写的代价 ("需要一条清理策略") 要避免的。在满足不变式的前提下, **三档等长是最省且仍然完整的保守解**。

**窗口不写死**: `retentionWindowDays()` 调 `notificationBodyMaxRetentionDays()`, 后者调 `notificationRetentionWindows(0,0)` —— 与 `NotificationCleaner` **同一个解析函数**。通知侧窗口将来变长, 投递窗口自动跟随, 不存在两处常量各自漂移的可能 (结构性保证, 不只是注释约定)。

### 2.4 与 D-1 裁决的一致性 (自圆其说)

裁决要求 "保留这条审计证据链", 同时明写代价是 "需要一条清理策略"。本策略**删的只是被审计对象已经不在的旧记录** (通知本体已按 90/180 天窗口清除, 追问对象消失, 证据不再可行动); **只要追问对象还在, 证据就一定还在** (不变式)。通道/通知被删除**不**触发提前清理 —— 只按 `created_at` 时间窗, 与 "删通道不级联删审计" (裁决 3 的实现要求) 完全一致。

**按时间删而非按条数删**: 条数上限会按写入速率反推保留时长 (突发告警时保留期被压缩到几小时), 审计保留期必须可预期、与写入量无关。
