# GPIO0 恢复出厂死循环事故（2026-10-04）

## 一句话

压力测试把 PWM 配到 S3 的 GPIO0（BOOT 按键引脚），PWM 以 3% 占空比把它拉低 97% 的
时间，固件的 `factory_reset_task` 把它读成「用户长按 BOOT 键」，于是**设备每 8.8 秒**
擦一次 NVS 并重启，连续 10 分钟 67 次，配置永远 `success=false`。

## 现象

| 观测 | 值 |
| --- | --- |
| USB 指示灯 | 红（FACTORY_RESET）→ 蓝（WIFI_CONNECTING）→ 紫（WAITING_CONFIG）循环 |
| 重启频率 | 67 次 / 10 分钟（正常应为 0） |
| 单次运行时长 | 约 8.8s（= 5s 长按判定 + 2s 擦除延迟 + ~1.8s 启动） |
| ConfigResult | 每次都 `success=false` |
| 崩溃诊断上报 | `reset_reason=3(SOFTWARE)`，**不是** `4(PANIC)`，`reboot_reason` 为空 |

## 根因链

1. 固件 `hw_gpios` 表把 GPIO0 当作普通可分配 GPIO 上报（S3 profile 的 12 个引脚含 GPIO0）。
2. 服务端 `validateReportedGPIO` 的判据是「节点上报过这个引脚」⇒ 放行。
3. `pwm_ctrl.c` 的 `is_valid_pin` 只查「引脚在不在 hw_gpios 表里」⇒ 放行。
4. PWM0 落盘：`pin=0, frequency=1000, duty=500, resolution=14` ⇒ 占空比 500/16384 ≈ 3%。
5. `factory_reset.c` 每 100ms 轮询 `gpio_get_level(GPIO0)`，读到低电平就累加 `held_ms`；
   走满 `HOLD_TIME_MS`（5000）即判定长按 ⇒ 擦 `{wifi_cfg, config, ota}` ⇒ `esp_restart()`。

关键点：**PWM 占空比只要不是 100%，在按键轮询看来就等于「一直按着」。**

## 为什么所有门禁都是绿的（本次最重要的教训）

事故当天的门禁全绿：后端单测、140 个仿真场景、固件 host 测试（35/35）、前端类型检查。
原因是它们断言的全是「服务端看到的 API 行为」——设备列表、配置下发响应、事件落库。
**没有任何一条门禁去看设备的真实运行状态。**

而「设备在重启」这件事本来就只存在于设备侧：API 层看到的只是「ConfigResult 成功/失败」，
一个每 8.8s 重启一次的设备和一个正常设备，在 API 上的差别仅仅是前者永远同步不完配置。
是用户看到 LED 灯色交替闪烁才发现的。

### 补救：`tools/device-stability-gate.sh`

直接查库，断言三条硬事实（uptime 单调上升 / 窗口内无新增 PANIC / 节点 online 且 last_seen 新鲜）。
前两条都取自设备自报字段，不依赖任何 API 语义：

```bash
# 部署后或压力测试后执行（需要能访问生产库）
tools/device-stability-gate.sh 180
```

退出码：0 稳定 / 1 检测到重启或 panic / 2 环境不可用。

为什么用 `uptime_seconds` 而不是「重启次数」：这是固件自报的**本次运行秒数**，
设备一重启就归零，是最直接、最难被上游掩盖的证据。

## 修复（纵深四道闸）

| # | 位置 | 做法 |
| --- | --- | --- |
| 1 | `hw_tables.c` | S3 的 GPIO0 标 `HW_GPIO_FLAG_RESERVED` |
| 2 | `hw_profile.c` | reserved 引脚**不进 ResourceReport** ⇒ 服务端白名单天然不含它 |
| 3 | `handler_periph.go` | 服务端按 `node.Platform` 拒绝 BOOT 引脚（防旧固件/手改库） |
| 4 | `factory_reset.c` | 只有上电后 10s 窗口内的长按才触发；窗口外读到低电平只告警不动作 |

第 4 道闸是**语义正确性**而不只是防误配：真正的「我要恢复出厂」操作是「按住 BOOT 再上电」，
本来就在启动瞬间；限定窗口后，运行期的引脚干扰（外设误配、总线串扰）不再被解释成用户意图。

## 回归锁

- `esp32-collector/host_tests/reserved_pin_contract_tests.c`：**S3 与 C6 各编一份**。
  在此之前该目录所有 host test 都只编 C6，而 GPIO0 在 C6 上是普通引脚 —— S3 上出问题的
  那条路径在 CI 里连编译都没编译过。这是「全绿却现场翻车」的结构性原因。
- `backend/internal/api/handler_periph_reserved_pin_test.go`：服务端拒绝方向 + 放行方向都锁。

两处都做过变异自证（改坏 → 必须红 → 恢复 → md5 一致）。

## 顺带发现

- `sdkconfig` 被 gitignore，而 flash size / 分区表只存在于其中：跑一次 `idf.py set-target`
  就重置回 2MB 默认值，构建失败且无法从仓库复现产线固件。已把这两项写进
  `sdkconfig.defaults.esp32s3` / `.esp32c6`（属产品形态，不是个人偏好）。
- S3 的 SPI2（GPIO 10/11/12/13）与 I2C0（SDA 8 / SCL 9）默认引脚**不在**
  `hw_gpios` 可分配清单里（清单是 0-8、15、16、17）⇒ 这两条通道一旦启用，配置事务
  必然失败且服务端只记 `success=false`、不记原因。待修。

## 复盘：我在这次排查中犯的三个错

1. **早前把「ch4 导致重启」当作结论并据此收窄排查面** —— 那是被 BOOT 按键状态混淆的
   假相关，已撤回。真实原因是 GPIO0 被 PWM 驱动。
2. **为提速把仿真离线阈值压到 6s**，低于夹具 30s 的上报周期 ⇒ 备用设备被误判离线，
   场景前提先坏。阈值不能为了跑得快而离开被验证的物理条件，已回退为生产 60s。
3. **在测试进程里调用读环境变量的函数**（`commandexec.CommandDeadline()`、
   `offlinedetector.EdgeOfflineThreshold()`），而环境变量只注入给子进程 ⇒ 推导出与
   真实值不符的超时。已统一改用 harness 常量（就是注入给子进程的那个值）。
