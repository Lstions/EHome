# 固件单文件包与构建打包规范

> **状态**: 已实现（v2.0，评审后；验收证据见文末链接）
> **版本**: v2.0（评审后）
> **日期**: 2026-11-19

> **一句话**：把「构建期才知道的事实」从**操作者的记忆**挪进**固件包本身**——上传只需要一个文件，ESP32 工程一条命令产出这个文件。

> **实现与验收**：[验证/固件单文件包-集成验证-2026-11-19.md](../验证/固件单文件包-集成验证-2026-11-19.md)（AC-P1~P11 逐条留证；唯一未覆盖项：设备端真实 OTA）。§14 是评审闭环。

## 0. 一页结论

| 维度 | 现状（两文件） | 本方案（单文件） |
|---|---|---|
| 上传动作 | 选 `.bin` + 选同名 `.meta.json`，缺一个直接 400 | 选**一个** `.ehfw` 文件 |
| 配对保证 | 靠文件名一致 + 操作者记得两个一起传 | 结构性保证：一个包 = 一次构建 |
| 身份来源 | 镜像头 + 侧车 7 个键（6 个可从镜像导出） | **镜像头 + 包内清单 2 个字段**（`psram` / `profile`） |
| 构建产物 | `.bin` + `.meta.json` 两件，散落在多个 build 目录 | `dist/<version>/<profile>/` 下 1 个包 + 1 份 `SHA256SUMS` |
| 版本号 | `CMakeLists.txt` 手写常量 | 单一真源：`FW_VERSION` > git tag > `VERSION` 文件 |
| 出错时 | 「缺少 .meta.json，去构建机跑 meta-gen 再传」 | 「这不是固件包，用 `pack_firmware.py` 打包」 |

**工作量**：**5.7 人日**（评审后：−2.0 删减、+0.6 必要修正。明细见 §11）。CI 6 档位另计 +1.0（P2，可延后）。

**前提**：固件表与 `backend/firmwares/` 已于 2026-11-19 清空——本次**不含任何存量迁移**。

**切换方式**：硬切换，不同时保留两文件路径（依据原方案 §2.4「允许破坏性更新、能不负债就不写兼容代码」）。

**评审闭环**：独立评审给出「有条件可落地 + 5 条 must-fix + 9 项删减」，逐条处置见 [§14](#14-评审闭环)。

## 1. 背景与问题

### 1.1 割裂发生在哪里

| 位置 | 现状 |
|---|---|
| `frontend-shared/src/views/firmware/components/FirmwareUploadDialog.vue:20` | 提示条：「必须同时选择 .bin 与同名 .meta.json」 |
| 同文件 `:28-58` | 两个 `el-upload`，一个收 `.bin`，一个收 `.meta.json` |
| 同文件 `:170-178` | 缺 sidecar 时前端**自己**复述一遍服务端规则 |
| `frontend-shared/src/api/firmware.ts:118-127` | 表单固定两个字段：`file` + `meta` |
| `backend/internal/api/handler_ota.go:270-283` | sidecar 必填 → 结构解析 → 交叉校验 |
| `backend/internal/api/handler_ota.go:577-634` | 为找到「那个」sidecar，按**三种**规则在 multipart 里翻找 |
| `backend/internal/firmwareid/sidecar.go:14-24` | 7 个键，`DisallowUnknownFields` |
| `esp32-collector/build_firmware.sh:484-513` | 构建末尾调 `emit_meta.py` 产出 `.meta.json` |

### 1.2 根因：判断 1 是对的，落地方式把成本推给了操作者

原方案判断 1 正确：**PSRAM 无法从 ESP 镜像头导出**（`s3-n16` 与 `s3p-n16` 的前 0x100 字节除 `elf_sha256` 外完全相同）。必须有构建期元数据。

问题在下一步：把它做成了**第二个上传文件**，而不是**产物的一部分**。于是配对靠文件名与记忆，元数据里 6 个可从镜像导出的字段被写了一遍、读了一遍、又比对了一遍。

**本次的收敛**：清单只保留**镜像无法自证的两项**——`psram`（布尔位）与 `profile`（档位名，用于交叉核对镜像的 chip/flash）。其余全部由服务端从镜像现读。

### 1.3 代价：已经写进代码的五处补丁

1. **三层兜底找 sidecar**（`handler_ota.go:585-613`）：字段名 `meta` → 同名 `.meta.json` → 任意 `.meta.json` 后缀。
2. **专门的补录命令**（`backend/cmd/ehomectl/firmware.go:34-93`）：`meta-gen` 从 `.bin` 反推身份、人工给 `psram`。
3. **前端复刻服务端规则**（`FirmwareUploadDialog.vue:170-178`）。
4. **错误文案指回构建机**（`api/firmware.ts:215`）。
5. **legacy 就地补齐**（`handler_ota.go:292-310`）——**本次随空库删除**。

### 1.4 第二个问题：构建产物不成形

| 现象 | 证据 | 后果 |
|---|---|---|
| 版本号是手写常量 | `esp32-collector/CMakeLists.txt:13` | 改代码不改版本 → 同版本两个二进制，只有上传时才撞出来 |
| 构建目录四处开花 | 根目录 10+ 个 `.fwbuild*`、`esp32-collector/build*/` | 不知道哪个目录的产物是哪一次的 |
| 没有打包步骤 | 只有 `emit_meta.py` 产侧车 | 「发布产物」由操作者手工组装 |
| 烧录脚本已过期 | `esp32-collector/flash_and_verify.sh:7` 硬编码旧路径 | 无人维护的入口静默腐坏 |
| 无 CI 固件构建 | `.github/workflows/` 只有 docker-publish / test | 6 个档位只能本机手跑 |

**门禁本身做得扎实**（IRAM ISR 安全、静态内存预算、sdkconfig 漂移、符号生效），缺的是**把检查结果固化成产物的那一步**。

### 1.5 三个「不确定」

| 不确定 | 现状如何暴露 |
|---|---|
| 这两个文件是不是一对？ | 靠文件名与人工 |
| 这个版本对应哪份源码？ | 靠版本号，而版本号是手写的 |
| 这份产物完整吗？ | 靠上传时恰好比对了 sha256 |

## 2. 目标与非目标

### 2.1 目标（可度量）

| 编号 | 目标 | 判据 |
|---|---|---|
| G1 | 上传只需一次文件选择 | 对话框内只有 1 个文件输入；`FirmwareUploadDialog.vue` 不再出现 `metaFile` |
| G2 | 配对由文件结构保证 | 服务端删除 `readFirmwareSidecar` 及三层兜底 |
| G3 | 清单不重复镜像能说的话 | 清单 `identity` 仅 `psram` + `profile` 两个字段 |
| G4 | 构建一条命令出成品 | `make fw-package PROFILE=c6-n8` → `dist/<ver>/c6-n8/*.ehfw` |
| G5 | 版本单一真源 | 仓库内不存在第二处手写版本号 |
| G6 | 产物可比对 | 同输入两次打包字节一致；`ehomectl verify` 与 `--verify` 结论一致 |
| G7 | 设备侧零变更 | 下载到的仍是裸 app image（首字节 0xE9） |

### 2.2 非目标

- 不做包签名（格式预留一段规则，本期不实现字段）。
- 不改设备 OTA 协议（在网设备无法回滚升级）。
- 不做增量 OTA、不做多档位合并包。
- **不做产线烧录包**（bootloader / 分区表不进包，见 §3.7）。

### 2.3 约束

1. 设备零变更：`esp_ota_write`（`esp32-collector/components/ota/ota.c:631`）逐块写收到的字节，下载链路必须继续给裸 image。
2. 涉库变更走启动迁移（`dbschema.MigrateFirmwareIdentity`，双挂载点 `backend/testutil/db.go:149` 与 `:715`），**本次只增列**。
3. 不保留两文件并行路径。

## 3. 方案选型

### 3.1 候选对比

| | 方案 | 单文件 | 设备兼容 | 可扩展 | 结论 |
|---|---|---|---|---|---|
| A | 保持现状（两文件） | ✗ | — | 差 | 不满足需求 |
| B | 前端合成两文件后上传 | 半 | ✓ | 差 | 只改入口，不改契约 |
| C | **单文件容器（ZIP + 清单）** | ✓ | ✓ | 好 | **推荐** |
| D | JSON 追加到 `.bin` 尾部 | ✓ | ✗ | 差 | 否决（§3.3） |

### 3.2 为什么 B 不够

产物仍是两个文件：磁盘/聊天工具里可以只传一半；后端仍要保留「按名字找 sidecar」与 `FW_META_REQUIRED`；构建侧仍产两件。**B 改入口，C 改契约。**

### 3.3 为什么否决 D（尾部追加）

1. `ota.c:631` 把收到的每块原样写 flash，尾部多出的字节会写进应用分区末尾——把包格式压在 bootloader 的宽容度上。
2. `esptool`/`idf.py` 直接烧录会因尾部数据报错，现场应急烧录失效。
3. 没有扩展位。

### 3.4 为什么不用 merged-flash bin

`idf.py merge-bin` 的全片镜像不能用于 OTA（只写应用分区）。

### 3.5 为什么容器选 ZIP

| 备选 | 取舍 |
|---|---|
| ZIP（推荐） | Go `archive/zip`、Python `zipfile` 都是标准库；`unzip -l` 可人工检查；STORE/DEFLATE 可控 |
| tar / gzip | 无随机访问索引，gzip 无条目级校验 |
| 自定义 TLV 头 | 两份手写解析器；收益不值 |

代价是攻击面（bomb / slip / 重名），用「扁平命名空间 + 解压前三重上限 + 1:1 清单」关掉（§4.4）。

### 3.6 为什么不是「把现有 .meta.json 塞进 ZIP」

最小改动确实存在（< 1 人日），但会把 7 键形状永久钉死、没有溯源位、没有扩展位，且第一次加字段时要再改一次格式。成本差值约 0.8 人日，而本次 5.7 人日里约 3.5 是**构建规范化**，与容器选型无关。

### 3.7 为什么包内只有两个条目

**评审后的修订**：原方案在包里放了 `bootloader.bin` / `partition-table.bin` / `flash_args` / `sdkconfig` 与 `components[]` 清单，但服务端**完全不消费**它们（不落盘、不入库、不校验内容），产线烧录在方案里也只是「可选」。

本次删除 `components[]`：包内**恰好两条**，`fw-manifest.json` + artifact。产线需要的其它文件在 `dist/<version>/<profile>/` 平铺（§7.2），真需要进包时再升 `format_version`。

## 4. 固件包格式规范 v1

### 4.1 基本定义

| 项 | 值 |
|---|---|
| 名称 | EHome Firmware Package |
| 扩展名 | `.ehfw`（`.zip` 同格式别名） |
| 容器 | ZIP（PKZIP 2.0，不启用 ZIP64） |
| 识别 | **按内容**：首 4 字节 `50 4B 03 04`；不看扩展名 |
| 条目数 | **恒为 2** |

**清单文件名用 `fw-manifest.json` 而不是 `manifest.json`**：本仓 `manifest` 已是**设备配置下发事务**的专名（`ConfigManifest`，backend 127 处命中、设备侧有 `config_manifest_t`），同名会让全仓 grep 失去意义。`firmwarepkg.Manifest` 类型有包名限定，不冲突。

### 4.2 包内布局

```text
ehome_collector-2.9.0-c6-n8.ehfw
├── fw-manifest.json      # 必需
└── ehome_collector.bin   # 必需：OTA 应用镜像（artifact），STORE 方式
```

```text
$ unzip -l ehome_collector-2.9.0-c6-n8.ehfw      # 条目按名排序（确定性要求，§7.5）
  Length      Date    Time    Name
---------  ---------- -----   ----
  1356128  1980-01-01 00:00   ehome_collector.bin
      812  1980-01-01 00:00   fw-manifest.json
---------                     -------
  1356940                     2 files
```

**条目全部在根、无目录**：`zip slip` 的前提是「条目名被当路径用」；扁平命名空间让这个前提不存在——服务端永远把条目名当**键**。

### 4.3 `fw-manifest.json`（format_version = 1）

```json
{
  "format": "ehome-firmware",
  "format_version": 1,
  "packer": { "name": "pack_firmware.py", "version": "1.0.0" },
  "artifact": {
    "name": "ehome_collector.bin",
    "size": 1356128,
    "sha256": "5f2c0e9d1b8a7c3e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c"
  },
  "identity": {
    "psram": false,
    "profile": "c6-n8"
  },
  "build": {
    "source_commit": "5edb8bc0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5f6",
    "source_branch": "main",
    "source_dirty": false,
    "git_tag": "fw-v2.9.0",
    "idf_version": "v6.1",
    "sdkconfig_sha256": "..."
  }
}
```

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `format` | string | ✓ | 恒为 `ehome-firmware` |
| `format_version` | int | ✓ | 本期必须为 `1`；更大值 → `FW_PKG_UNSUPPORTED` |
| `packer.name/version` | string | ✓ | 谁打的包 |
| `artifact.name` | string | ✓ | 与包内条目同名，以 `.bin` 结尾 |
| `artifact.size` / `sha256` | int / 64 hex | ✓ | 与实测一致 |
| `identity.psram` | bool | ✓ | **唯一无法从镜像导出的位**；来源 `sdkconfig` 的 `CONFIG_SPIRAM` |
| `identity.profile` | string | ✓ | 档位名（`c6-n8` / `s3p-n16` …），用于与镜像交叉核对 |
| `build.*` | object | ✗ | 溯源信息；服务端**不据此拒绝**，也不入库（随 `dist/` 归档） |

**为什么 `identity` 只有两个字段**：评审指出原方案的 7 个字段里有 6 个可以从镜像头导出（chip/flash/version/idf_ver/elf_sha256/built_at），在包里再存一遍等于把 §1.2 批判过的问题搬进包内。本次只保留「镜像说不了的话」，外加 `profile` 一个字符串——它编码了 (chip, flash, psram)，正好能在服务端与镜像交叉核对（INV-3）。

### 4.4 不变量

| 编号 | 不变量 | 违反时 |
|---|---|---|
| INV-1 | 包内**恰好两条**：`fw-manifest.json` + `artifact.name`；无未声明条目、无重复条目 | `FW_PKG_INVALID` |
| INV-2 | `artifact.size` / `artifact.sha256` 与实测一致 | `FW_PKG_DIGEST_MISMATCH` |
| INV-3 | `identity.profile` == `BuildProfile(镜像 chip, 镜像 flash_mb, identity.psram)` | `FW_PKG_CONFLICT` |
| INV-4 | 条目名匹配 `^[a-z0-9][a-z0-9._-]{0,63}$` | `FW_PKG_INVALID` |
| INV-5 | 条目数 ≤ 16、解压总量 ≤ 16 MiB、单条目压缩比 ≤ 100:1 | `FW_PKG_TOO_LARGE` |
| INV-6 | 清单是输入的纯函数（不含时间戳/随机数/绝对路径） | 确定性测试（AC-P11） |

**INV-3 顶替了原方案的 INV-3 + INV-4**：原方案要求清单里的 chip/flash/version/elf_sha256 与镜像逐字段相等，而那 6 个字段本来就从镜像读出——两者矛盾时「谁说了算」本身就是双真源。现在只比一个 `profile` 字符串：它必须能被镜像的 (chip, flash) 加上清单的 `psram` 还原出来。**能抓住的**：清单与镜像错配（例如 s3p 的清单配了 s3 的 bin）；**抓不住的**：`psram` 本身（镜像里没有这一位，这是原方案判断 1 的固有约束，不是本方案的缺陷）。

### 4.5 大小与安全上限

| 限制 | 值 | 理由 |
|---|---|---|
| 请求体上限 | **8 MiB（不变）** | 16MB 档槽上限 `0x680000` = 6.5 MiB（`firmwareid/hardware.go:12-15`）+ 清单 ≤64 KiB + ZIP 头 ≈ 6.6 MiB；实测产物 1.2–1.45 MB |
| 条目数 | ≤ 16 | 实际恒为 2；上限只为拦住异常包 |
| 解压总量 | ≤ 16 MiB | 8 MiB 包解不出 16 MiB 以上（STORE 时约 1:1） |
| 单条目压缩比 | ≤ 100:1 | 挡 1KB→100MB 的 zip bomb；`.bin` 用 STORE，天然 1:1 |
| 清单 | ≤ 64 KiB | 与现有 `firmwareMetaMaxBytes` 对齐 |
| 压缩方法 | 仅 0（STORE）/ 8（DEFLATE） | 其余（bzip2/lzma/aes）一律拒绝 |

**上限必须在解压前判定**：中央目录自带 `UncompressedSize64` / `CompressedSize64`，`Open` 遍历条目时即可算出三项，**一个字节都不解压**就能拒绝。

**内存峰值**：`c.FormFile` 走 gin 的 `ParseMultipartForm`（`MaxMultipartMemory` 默认 32 MiB），8 MiB 包在 multipart 层已驻留内存；解压**不再把解压后内容读进内存**（流式写临时文件 + 边写边算 sha256）。峰值约 2×8 MiB，可控。

### 4.6 版本演进

| 变更类型 | 做法 |
|---|---|
| 新增可选字段 | 不改 `format_version`；解析端**忽略未知键**并记日志 |
| 新增必需字段 / 改语义 | `format_version += 1`；旧服务端返回 `FW_PKG_UNSUPPORTED` |
| 容器换格式 | `format` 改值，服务端按 `format` 分派 |

**为什么这里允许忽略未知键**：sidecar 是 7 键一次性契约（多一个键几乎必然是写错了，所以用 `DisallowUnknownFields`）；而包清单是长期格式。折中：未知键忽略但记日志，结构性变更走 `format_version`。

### 4.7 签名（本期不做）

签名将来以**顶层** `signature` 键加入：`{"alg":"ed25519","key_id":"...","sig":"..."}`，签名对象为去掉 `signature` 后的规范化 JSON（键排序、无空白）。新增顶层键不升 `format_version`。本期服务端遇到它视为未知键忽略。

## 5. 服务端改造

### 5.1 新增模块 `backend/internal/firmwarepkg`

```go
package firmwarepkg

const (
    FormatName    = "ehome-firmware"
    FormatVersion = 1
    ManifestEntry = "fw-manifest.json"
)

type Limits struct {
    MaxEntries      int   // 默认 16
    MaxUncompressed int64 // 默认 16 MiB
    MaxManifest     int64 // 默认 64 KiB
    MaxRatio        int   // 默认 100
}

// DefaultLimits 返回生产默认值；Open 内部对零值字段做 normalized()，
// 因此 Limits{MaxEntries: 4} 只改一项、其余仍是默认 —— 避免「零值上限=全拒」。
func DefaultLimits() Limits

func Open(r io.ReaderAt, size int64, limits Limits) (*Package, error)

// Manifest 返回只读副本（handler 需要 artifact.name / identity.*）。
func (p *Package) Manifest() *Manifest

// ExtractArtifactTo 流式写出 artifact 并返回 (字节数, sha256)。
// **只解出、不比较** —— INV-2 的比较与错误出口留在 handler，避免两处都校验一遍。
func (p *Package) ExtractArtifactTo(w io.Writer) (int64, string, error)
```

**错误类型复用 `*firmwareid.Error`，不新造**：
- `firmwarepkg` 定义码常量（`CodePkgRequired` 等），错误值直接构造 `&firmwareid.Error{Code: …, Detail: …}`；
- 这样 `firmwareid.Code(err)` 与 `rejectFirmwareUpload`（`handler_ota.go:702-720`）原样可用；
- 若新造一个 `Error` 类型，`Code()` 会返回空串 → 指标全落到 `FW_UNCLASSIFIED`，排障断链（评审 A-3）。

**依赖方向**：`api → firmwarepkg → firmwareid`。`firmwareid` 是叶子包（只 import 标准库），**禁止**往它里面加新依赖。

### 5.2 上传 handler 新流程

```text
POST /api/v1/firmwares/upload   （multipart，字段 file，单文件）

 0. MaxBytesReader(8 MiB) —— 不变
 1. 收字节到临时文件（边写边算整包 sha256）—— 沿用 receiveFirmwareUpload
 2. 内容嗅探：PK\x03\x04 → 3；0xE9 → 400 FW_PKG_REQUIRED；其它 → 400 FW_NOT_IMAGE
 3. firmwarepkg.Open：INV-1 / INV-4 / INV-5 / 清单必需字段
 4. ExtractArtifactTo → 临时文件，得 (size, sha)
 5. size/sha 与清单比对 → FW_PKG_DIGEST_MISMATCH
 6. firmwareid.ReadIdentity(artifact) → FW_NOT_IMAGE / FW_TRUNCATED / …
 7. BuildProfile(image.Chip, image.FlashMB, manifest.PSRAM) != manifest.Profile
      → 400 FW_PKG_CONFLICT
 8. 槽容量 → FW_TOO_LARGE
 9. elf_sha256 查重 → FW_DUPLICATE（无补齐分支）
10. 落盘 firmwareStorageName(elf, manifest.artifact.name)；入库
11. 任一步失败：删临时文件与已落盘文件，不留孤儿
```

**两个容易写错的落点**：
- `Filename` 必须存 `manifest.artifact.name`，`StoragePath` 恒非空——否则 `firmwareBinaryDiskPath` 的兜底分支会去 `firmwares/x.ehfw` 找文件，删除固件时留孤儿（评审 A-7）。
- `firmwareStorageName` 现在的规则会给非 `.bin` 名字**强行补** `.bin`、并按「最后一个扩展名」截断。入参改成 artifact.name 后这条规则自然正确，但**必须**补一个用例锁住（§5.7）。

**`sidecar.go` 不能整体删除**（评审 A-1）：`BuildProfile` 住在 `sidecar.go:113`，而 INV-3 与 `pack_firmware.py` 都依赖它。搬迁清单：

| 从 | 到 |
|---|---|
| `firmwareid/sidecar.go` 的 `BuildProfile` | 新建 `firmwareid/profile.go` |
| `sidecar_test.go:123-144` 的 `TestBuildProfile` | 随实现移到 `profile_test.go` |
| `sidecar.go` 其余（`Sidecar` / `ParseSidecar` / `CheckSidecar` / `PSRAMValue`） | **删除** |

### 5.3 错误码变更

| 机器码 | HTTP | 语义 | 前端动作建议 |
|---|---|---|---|
| `FW_PKG_REQUIRED` | 400 | 上传物不是包（裸 `.bin`） | 「这是裸镜像；用 `esp32-collector/tools/pack_firmware.py` 打包后上传」 |
| `FW_PKG_INVALID` | 400 | ZIP 坏 / 缺清单 / 条目数≠2 / 名字非法 / **条目 CRC 不符** | 「包结构不合法；用 `ehomectl firmware verify --pkg <file>` 看第一个错误」 |
| `FW_PKG_DIGEST_MISMATCH` | 400 | 清单摘要 ≠ 实测摘要（结构本身没坏） | 「包已损坏或被改动，重新打包」 |
| `FW_PKG_UNSUPPORTED` | 400 | `format` 或 `format_version` 不认识 | 「包格式版本高于服务端，请升级平台」 |
| `FW_PKG_DIGEST_MISMATCH` | 400 | artifact 摘要/大小与清单不符 | 「包已损坏或被改动，重新打包」 |
| `FW_PKG_CONFLICT` | 400 | `profile` 与镜像不符 | 「包内档位与镜像不一致，用构建产出的原始包重传」 |
| `FW_PKG_TOO_LARGE` | 413 | 条目数/解压量/压缩比超限 | 「包异常膨胀」 |
| `FW_META_REQUIRED` / `FW_META_CONFLICT` | — | **废弃**，不再产生 | — |

### 5.4 数据模型

**机制**（评审 A-11）：本项目加列的落地方式不是手写 `ALTER TABLE`，而是**给 `models.Firmware` 加字段 + `default:` 标签**，由 `dbschema.MigrateFirmwareIdentity` 的 step 0 `tx.AutoMigrate` 生成（`firmware_identity.go:82`）。因此：

```go
// models.go · Firmware
PackageName          string `gorm:"column:package_name;size:128;default:''" json:"package_name,omitempty"`
PackageFormatVersion int16  `gorm:"column:package_format_version;default:1" json:"package_format_version"`
```

| 列 | 用途 |
|---|---|
| `package_name` | 原始上传文件名（排障：谁传的哪一份） |
| `package_format_version` | 恒为 1；将来格式升版时用于区分 |

`firmwares.checksum` / `size_bytes` 存的是 **artifact** 的摘要与大小（设备下载的就是它，`ota.go` 用它填 `OtaCmd.checksum/size`），**不是容器**的大小——容器摘要不入库。

**删掉原方案的两列**：`manifest_json` 与 `package_sha256`。前者与身份列重复（双真源），后者无消费方（查重键是 `elf_sha256`）。溯源信息随 `dist/` 归档，不入库。

**另一处必须改的默认值**：`models.Firmware.IdentityState` 现在是 `default:legacy`（`models.go:466`）。空库 + 无补齐分支之后，`legacy` 是不可达状态；若保留默认值，任何漏写该字段的 INSERT（种子、夹具、将来的导入）都会造出「不可选」的行。**改为 `default:verified`**。

> ⚠ 新加的 `default:` 标签必须登记到 `backend/internal/models/defaults_gate_test.go` 的默认值映射表，否则该门禁会红。

### 5.5 存储布局

```text
backend/firmwares/
├── elfafd137254e2b54fd_ehome_collector.bin   # 落盘的 artifact（设备下载的就是它）
└── .tmp/                                      # 上传临时文件
```

**不归档原始容器**：容器 ≈ artifact + 1KB，可无损重建；需要时 `pack_firmware.py` 重新打包即可。

### 5.6 下载链路（不变）

公开下载路由是 `GET /api/v1/firmwares/:filename/download?expires=&signature=`（`handler_ota.go:764-778`），只认 HMAC 票，`c.File("firmwares/"+name)` 原样返回；取票端点是 `POST /api/v1/firmwares/:id/download-ticket`（`handler_firmware_download.go`）。

### 7.2 产物布局

```text
esp32-collector/
├── build/<profile>/                 # 中间产物
└── dist/<version>/                  # 发布产物（dist/ 已 gitignore）
    ├── c6-n8/

    │   ├── bootloader.bin            # 产线烧录用，不进包

```

**不再产 `build-manifest.json`**（评审 C-8）：它想表达的东西（版本 / commit / 6 个摘要）是第三个真源，`SHA256SUMS` + 包内清单已经够用。

### 7.3 版本：单一真源

现状是 `CMakeLists.txt:13` 手写 `set(PROJECT_VER "2.8.0")`。两条风险：
1. 改代码不改版本 → 两个不同二进制同版本号；
2. **版本串不能带后缀**：`firmwareid.CompareVersion`（`compat.go:276-294`）只比前 3 段数字，`2.9.0-dirty.abc` 与 `2.9.0` 被判**相等**，闸门会当成「不是升级」。所以 commit / dirty 一律只进清单，**不进 version**。

解析顺序（`build_firmware.sh` 内实现，唯一入口）：

```text
1. FW_VERSION 环境变量
2. git describe --tags --exact-match --match 'fw-v*'
3. VERSION 文件（仓库根）
4. 都没有 → 构建失败
```

**本次新增**仓库根 `VERSION` 文件，内容 `2.8.0`（与当前 `CMakeLists.txt` 的 `PROJECT_VER` 对齐，避免引入无法解释的版本跳变）。发版时改这一处或打 `fw-v*` tag，两者取值相同时无歧义。

**CMake 落点（评审 A-5）**：必须替换 `CMakeLists.txt:13`，且在 `include(project.cmake)`（`:42`）与 `project()`（`:46`）**之前**——写晚了镜像里仍是旧版本，而且无声。

```cmake
# 唯一真源是构建脚本传入的 -D FW_VERSION；缺省值只保证「直接 idf.py build 也能编」，
# 但它不是可发布产物：pack_firmware.py 会拒绝 0.0.0-dev。
set(FW_VERSION "" CACHE STRING "firmware version injected by build_firmware.sh")
if(FW_VERSION STREQUAL "")
    set(PROJECT_VER "0.0.0-dev")
else()
    set(PROJECT_VER "${FW_VERSION}")
endif()
if(NOT PROJECT_VER MATCHES "^[0-9]+\.[0-9]+\.[0-9]+$")
    message(FATAL_ERROR "PROJECT_VER=${PROJECT_VER} is not X.Y.Z; pass -DFW_VERSION=<x.y.z>")
endif()
```

**版本一致性检查不能照搬 `emit_meta.py`**（评审 A-2）：它现在是**从 CMakeLists 正则抓字面量**（`emit_meta.py:189`），而这条字面量正是本次要替换掉的。新做法：**镜像内 `version[32]` 必须等于 `--version` 实参**，不再读 CMakeLists；`--project-cmakelists` 参数删除。

### 7.4 构建入口改造点

| 文件 | 改动 |
|---|---|
| `esp32-collector/CMakeLists.txt` | §7.3 的版本注入（替换第 13 行） |
| `esp32-collector/build_firmware.sh` | ① 解析版本并传 `-D FW_VERSION`；② 门禁后调用 `pack_firmware.py` + 自检；③ 复制到 `dist/<version>/<profile>/`；④ 生成**排序后**的 `SHA256SUMS` |
| `esp32-collector/scripts/emit_meta.py` | **删除**，拆成 `tools/fwimage.py`（解析库）+ `tools/pack_firmware.py`（CLI） |
| `Makefile`（根） | 新增 4 个目标 + `.PHONY` + help |

### 7.5 打包工具 `tools/pack_firmware.py`

```text
  pack_firmware.py --bin build/<p>/ehome_collector.bin \
                   --sdkconfig build/<p>/sdkconfig \
                   --profile c6-n8 \
                   --version 2.9.0 \
                   --out dist/<version>/<profile>/x.ehfw

  pack_firmware.py --verify dist/<version>/<profile>/x.ehfw   # 与服务端同规则的离线自检
```

| 要点 | 做法 |
|---|---|
| 复用解析 | `fwimage.py` 承载镜像头解析与 sdkconfig 读取；**偏移表仍以 `identity.go` 为唯一真源**（`emit_meta.py:13-18` 的告诫保留） |
| 确定性 | 条目按名排序；`date_time=(1980,1,1,0,0,0)`；`ZIP_STORED`；**必须用 `writestr(ZipInfo)`，禁止 `zf.write(path)`**（后者会从 `os.stat` 取 `external_attr`/`create_system`，Linux 与 Windows 打包字节不同）；`external_attr = 0o100644 << 16`（**要带 S_IFREG 文件类型位**；只写 `0o644` 会落进 DOS 属性位、`0o644<<16` 会让 `zipinfo -l` 显示成 `?rw-r--r--`） |
| fail-closed | 任一交叉校验失败 → 不写文件（临时文件 + `os.replace`） |
| 版本校验 | 镜像内 version == `--version`，否则「stale .bin，重新构建」 |
| profile 校验 | `--profile` 必须等于 `BuildProfile(chip, flash_mb, psram)` 反推值 |
| psram | `--psram yes/no` 可覆盖，但必须与 sdkconfig 的 `CONFIG_SPIRAM` 和 profile 名一致 |
| 自检 | 打包后立即 `--verify` 一遍，不通过就删包并失败 |

### 7.6 新增门禁

| 门禁 | 挡住什么 |
|---|---|
| 包自检（`--verify`） | 打出来的包自己过不了服务端规则 |
| 版本 ↔ 镜像 | `.bin` 是上一次构建的陈旧产物 |
| `dist/<version>/` 完整性 | 6 档位缺一却当成全量发布（`SHA256SUMS` 校验 6 行） |

### 7.7 可复现构建（P2）

本 IDF 已有 `CONFIG_APP_REPRODUCIBLE_BUILD`（当前 `is not set`）。开启后时间字段固定，配合 `SOURCE_DATE_EPOCH` 可让同一源码产出字节相同的 `.bin`。代价是 `built_at` 失去意义。**先不做**，等 AC-P11 证明有必要再开。

## 8. 一致性保障

### 8.1 问题

打包在 Python（构建机），解析在 Go（服务端）。两份实现必然存在，风险是「各自自洽却互相不通」——本仓在帧协议上吃过这个亏，因此有 `protocol/vectors/` + `tools/check_golden_vectors.py`（第三份实现交叉验证）。

补充事实：仓库目前**没有任何固件打包先例**（`zip`/`tar`/`.xpk` 在 backend/scripts/esp32-collector 中零命中），没有可借用的门禁——vectors 是唯一防漂移手段。

### 8.2 golden vectors

```text
protocol/firmware-package/
├── vectors/
│   ├── ok_c6-n8.ehfw + ok_c6-n8.expected.json
│   ├── bad_entry_count.ehfw
│   ├── bad_digest.ehfw
│   ├── bad_entry_name.ehfw          # ../evil.bin
│   ├── bad_format_version.ehfw
│   └── cases.json                    # 文件 → 期望错误码
└── README.md                         # 生成方法（固定输入）
```

| 消费方 | 测试 |
|---|---|
| Go | `firmwarepkg/vectors_test.go` |
| Python | `esp32-collector/tools/test_pack_firmware.py` |
| 后端集成 | `handler_ota_upload_test.go` 直接引用 `ok_c6-n8.ehfw` |

`cases.json` 契约（**每个用例必须同时带两个键**，缺键会让消费方写 `.get()` 兜底，而兜底分支没人测）：

```json
{"generator":"gen_vectors.py","format":"ehome-firmware","format_version":1,
 "cases":[
   {"file":"ok_c6-n8.ehfw","open_error":"","handler_error":"","expected_file":"ok_c6-n8.expected.json"},
   {"file":"bad_digest.ehfw","open_error":"","handler_error":"FW_PKG_DIGEST_MISMATCH"},
   {"file":"bad_entry_count.ehfw","open_error":"FW_PKG_INVALID","handler_error":""}
 ]}
```

- `open_error`：`firmwarepkg.Open` 期望的码，空串 = 必须成功；
- `handler_error`：摘要比对那一步（§5.2 步骤 5）期望的码，空串 = 摘要必须一致；
- `gen_vectors.py --check` 同时断言「`.ehfw` 未漂」与「两个键都在」。

**消费方必须从 JSON 读取，禁止手抄常量**：向量是**生成的**，生成器修 bug 时二进制会变（2026-11-19 就发生过一次——合成镜像用 `bytearray` 切片赋值写 32 字节版本字段，6 字节的值把 header 收缩了 26 字节，只有 `elf_sha256` 露馅）。把 size/sha256 硬编码进断言，等于在别处又立了一份会漂的真源。

**判据**：新增一条格式规则必须同时加一个 vector；两侧都绿才算改完。CI 落点是 §5.8#11 的 pytest 步骤 + 现有 `go test`。
