## 0. 关键变化速览（v1.1 修订 + v1.2 更正 + v1.4 收紧 + v1.5 补充）

| # | v1.0 的做法 | v1.1 的做法 | 为什么 |
|---|---|---|---|
| 1 | 唯一键 `(model_key, version, channel)` | 唯一键 **`elf_sha256`**；`(model_key, version)` 降为普通索引 | 镜像头无 PSRAM 位，`s3-n16` 与 `s3p-n16` 会撞成同一个 `model_key`，唯一索引必然失败并 abort 启动 |
| 2 | `psram_required` 布尔、靠 `model_key` 推导 | **三态** `psram`（`yes`/`no`/`unknown`），来源为**构建期 sidecar** | 布尔无法表达「不知道」；`model_key` 也没有 PSRAM 位。**v1.4 再收紧为两值 + `identity_state`，见第 13 行** |
| 3 | 回滚开关当作 app 侧任务（0.8 人日） | 拆为 **M3a app 侧判据**与 **M3b 现场 bootloader 重烧** | 该开关编译进 `bootloader.bin`，OTA 写不到；存量机必须现场重烧 |
| 4 | 闸门放在 `CreateTask`，统一校版本方向 | 闸门带 **`Source`/`Force`**；系统回滚只校硬件、不校版本方向 | 否则 `AutoRollback`（目标是更旧版本）每天被 `NOT_AN_UPGRADE` 拒掉 |
| 5 | 迁移只挂在生产 `AutoMigrate` | 索引与回填下沉 **`internal/dbschema`**，`database` 与 `testutil` 各调一次 | 测试库不走生产迁移，否则唯一索引只在生产存在，验收假绿 |
| 6 | Hello 补完成加「校验和比对」分支 | 只保留「**已离开 pending** + 版本相等」，并改条件更新 | Hello 不上报指纹，该分支恒真且与语义相反；整行 `Save` 有 TOCTOU |
| 7 | `0x1A HwInfo` 新消息 | **删除**；硬件档案复用 `nodes.platform` / `hardware_info` | `0x1A` 已被 `MSG_QUERY_RESOURCES` 占用 |
| 8 | 上传先落最终路径再校验 | **临时文件 → 解析 → 唯一命名 → 入库** | 拒绝会留孤儿文件；同名重传会覆盖旧二进制而 DB 校验和不变 |
| 9 | 公开版本端点写在 v1 组、响应裸 JSON | 注册在**根路由**（与 `/health` 同级），响应走**统一 envelope** | v1 组统一 JWT；裸 JSON 与全仓契约冲突 |
| 10 | 12 项「待裁决」 | 收敛为 **3 项**，其余落为决策记录 | 大多数选项已有明确推荐，不构成决策阻塞 |
| 11 | 回滚确认挂在「首条 StatusReport 成功」 | 改为**本地自检**（uptime + 关键子系统 + 非安全模式）；崩溃由引导器自动回退 | 回滚由「未确认即复位」触发，确认不能依赖网络；否则断网设备会被误滚 |
| 12 | 旧前端只靠 30 分钟轮询，chunk 失败无提示 | 增加**响应头 `X-EHome-Build` 秒级检测** + **chunk 失败强提示**；4 态状态机 | 「正在使用」的用户必须马上知道；页面已不可导航时不能只显示可推迟的横幅 |
| 13 | 无 sidecar 也允许入库，`psram=unknown`，闸门可 `force` 放行 | 上传**必须**带 sidecar；存量二进制由 `ehomectl firmware meta-gen` 一次性补齐；补不齐的置 `identity_state='legacy'` 且**不可选** | 三态 + 未知分支 + force 豁免都是为旧数据写的兼容代码，长期存在即负债 |
| 14 | `stable`/`target_model` 保留列但不再写入，读时派生 | 迁移中**显式 DROP COLUMN**；`channel` 与 `model_key`/`build_profile` 成唯一真源 | 两个真源必然漂移；「不再写入」比删列更容易被后人误读为仍有效 |
| 15 | `gateMode` warn/enforce 双模式 | **删除**；改为只读的 `ehomectl ota gate-check` 预检报告 | 请求路径只保留一种行为，不留「要改常量重发版才能切换」的开关 |
| 16 | force 可放行除撤回外的所有闸门 | force **仅用于版本方向**（同版本重刷/降级）；硬件类不匹配一律不可 force，改为更正节点硬件档案 | 「放行未知」等于把误刷的结构性通道按设计重新打开 |
| 17 | 只提示「有新版本」，不说改了什么 | `/system/version` 返回 `notes`（构建期从 `release.json` 嵌入）；横幅与「关于」共用同一弹窗 | 用户只能「先刷新再说」；发布说明也无处落地 |

## 1. 背景与需求

### 1.1 触发与范围

两条用户反馈指向同一根因：**系统缺少「制品身份」与「基于身份的判断」**。

1. 「参照桌面软件的自更新机制，本站如何实现类似能力」——平台与前端没有版本身份、没有更新感知；
2. 「节点固件型号不规范、固件与节点关联有问题、可能误刷误升级」——固件与设备之间没有兼容性契约。

本方案先建立这套底座，再分别接到三条替换链路上。

### 1.3 需求

| 编号 | 需求 | 可验证形式 |
|---|---|---|
| REQ-1 | 制品版本可查询且唯一 | 存在只读版本端点，三端不再依赖手写常量 |
| REQ-2 | 固件可被机器识别 | 上传后 `chip/flash/psram/version/elf_sha256` 与镜像及 sidecar 一致 |
| REQ-3 | 不兼容固件不得下发 | 不兼容组合默认被拒；`force` 需理由并落审计 |
| REQ-4 | 同版本或降级不得静默执行 | 需显式 `force`，或由系统回滚通道发起 |
| REQ-5 | 升级结果可信 | 同版本「假成功」消失；未开始的 pending 不会被 Hello 判成功 |
| REQ-6 | 平台发布可对账 | 一条命令比对清单 / commit / 实例版本 |
| REQ-7 | 已打开页面能感知新版本 | 部署后旧标签页在约定时间出现提示 |
| REQ-8 | 危险操作留审计 | `force`、撤回、强制删除写入 `security_audit_events` |
| REQ-9 | 存量数据可迁移、可回退 | 迁移幂等、纯增列；回退不需删数据 |
| REQ-10 | 不破坏既有协议 | 不改任何已有帧字段；旧固件与旧后端仍可工作 |
| REQ-11 | 更新内容可见 | 提示与「关于」都能读到本次变更条目；无条目时不出现空弹窗 |

### 1.4 本方案不做

- 不做固件数字签名与设备端验签（另立评估）。
- 不做增量升级、不做 OTA 专用服务。
- 不做设备主动拉取更新（服务端已掌握版本）。
- **不做 bootloader 的 OTA 化**（物理上不支持，见 §3.4）。

## 2. 目标与非目标

### 2.1 目标（可度量、并标注达成阶段）

| 目标 | 度量 | 达成阶段 |
|---|---|---|
| 关闭误刷的结构性通道 | 芯片、容量、PSRAM 三类错配默认被拒 | M1a（芯片/容量）+ M3a（PSRAM 精确） |
| 固件身份以二进制与 sidecar 为准 | `version/chip/flash` 与镜像一致；`psram` 与 sidecar 一致 | M0 |
| 升级结果可信 | 「同版本重刷」「pending 未开始」不再被判 success | M1a |
| 平台发布可对账 | 脚本比对清单与 `/health.commit`、`/system/version` | M2 |
| 前端更新可感知、可读内容 | **活跃页面下一次 API 响应即提示**；空闲页面 ≤35 分钟；chunk 失败立即强提示；提示内可展开本次变更条目 | M2 |
| 存量数据可整形 | 迁移一次性回填/去重/删列；补不齐的标 `legacy` 并在报告中列出 | M0 |

### 2.2 非目标

- 不做灰度百分比投放（渠道 + 人工选择足够）。
- 不做多实例版本编排（当前单实例）。
- 不改 OTA 既有 8 态语义（只加固判定）。
- 不重构下载票据形态（仍用 HMAC 短票，只改为发送时签发）。

### 2.4 破坏性变更与迁移原则（v1.4）

项目开发原则：**允许破坏性更新；涉库变更必须在程序启动时完成迁移适配；能不负债就不写兼容代码。** 本方案据此收紧，逐条落点如下。

| 规则 | 内容 | 对本方案的强制要求 |
|---|---|---|
| R1 | 平台侧允许破坏性变更 | 数据库列、HTTP 契约、前端资源一次性切换；**不做双写、不做双读、不做版本共存** |
| R2 | 涉库变更只在启动迁移里适配 | 迁移固定在 `internal/dbschema`，由 `database/gorm.go` 与 `testutil/db.go` 两处调用；**单事务、幂等、失败即拒绝启动** |
| R3 | 用数据状态表达「不知道」，不用运行期分支 | 新增 `identity_state`（`verified`/`legacy`/`duplicate`）；`legacy` 行**从可选集合里排除**，闸门不再有「未知放行」分支 |
| R4 | 过渡开关必须带删除条件 | 删除 `gateMode`；上线前用只读预检（`ehomectl ota gate-check`）替代「先 warn、观察期后再改常量重发版」 |
| R5 | 未知即拒绝，不猜、不放行 | 硬件类不匹配**不可 force**；节点档案缺字段先更正数据（`ehomectl node hw set`），不放宽判定 |
| R6 | 存量数据由迁移一次性整形 | 回填、去重、删列、产出「待重传清单」都在迁移内完成，不保留「老行为」分支 |

**边界（必须区分）**：破坏性只适用于**平台自身**（数据库、HTTP、前端）。**已在现场的固件协议不可破坏**——`OtaCmd`/`HelloAck`/`StatusReport` 是 fail-closed 解码（遇到未知字段整帧丢弃）且设备无法回滚升级，因此帧结构**零变更**。这是硬件约束，不是代码债务。

**代价（明确接受）**：删列后**不能再用「回退上一镜像」回滚**（旧镜像读不到 `stable` 列）。回滚手段改为：发布前 `pg_dump` 备份 + 迁移单事务（失败整体回滚、服务拒绝启动）+ 前滚修复。换来的是不背双真源、不留迁移期技术债。

### 2.5 预期收益（v1.4 补充）

**口径与假设**（用于判断量级；投产 4 周后用 §9.5 的实测指标回填替换）：

| 编号 | 假设 | 取值 |
|---|---|---|
| H1 | 单台误刷的恢复工时（拆机/接串口 + `esptool` 重烧 + 联网验证，不含上门差旅） | ≈ 2 小时/台 |
| H2 | 旧前端调用已下线接口后的人工排查 | ≈ 10 分钟/次 |
| H3 | OTA 任务卡在 `upgrading` 的人工发现与处置 | ≈ 10 分钟/次 |
| H4 | 上传后人工核对版本/型号/大小 | ≈ 5 分钟/次 |
| H5 | 每次「这次更新了什么」的支持问询 | ≈ 10 分钟/次 |

**A. 直接收益（缺陷关闭后）**

| 收益 | 机制 | 指标 | 量化口径 |
|---|---|---|---|
| 结构性误刷归零 | chip / flash / PSRAM 三类判定在服务端，命中即 409 | `ehome_ota_gate_rejected_total{reason}` 硬件类计数；误刷事故数 | 每次拦截 = 省 H1 + 少 1 台停机 |
| 不可恢复损失归零 | 16MB 镜像刷进 8MB 设备 → `Probe failed` panic 循环，只能 USB 救 | 同上 | 该类故障原本**无法远程修复**，成本只能落在现场 |
| 「同版本不同二进制」不再撞车 | 唯一键用 `elf_sha256`，而非 `(model_key, version, channel)` | `FW_DUPLICATE` 命中数 | 消除「同版本号静默刷错包」这类不可复现故障 |
| 升级结果可信 | `pending` 不判成功、Hello 对账、超时扫描 | 误判 success 数（目标 0） | 每次误判至少 1 小时排查（≥6×H3） |
| 上传不再靠人核对 | 身份取自镜像 + sidecar；表单不再填 `version`/`target_model` | 因填错导致的返工次数 | 每次上传省 H4 |
| 旧页面秒级可感知 | 响应头 `X-EHome-Build` + 4 通道 | 活跃页提示延迟（目标 ≤1 次请求） | 每次「旧前端报错」= 省 H2 |
| 更新意图可解释 | 提示与「关于」直接展示 `notes` | 「更新了什么」问询次数 | 每次省 H5 |
| 发布可对账 | `release.json` + 校验脚本 | 漂移检出率 | 发布事故从「用户发现」提前到「部署后 1 分钟」 |

**B. 工程侧收益（不写兼容代码省下的维护面）**

| 项 | v1.3 兼容路线 | v1.4 | 差额 |
|---|---|---|---|
| 闸门分支 | 11 条（含 3 条 unknown 分支） | **10 条**，0 条 unknown 放行 | −1 分支、−2 个 unknown 机器码 |
| 固件 PSRAM 表达 | 三态字符串，读侧多处判断 | 两值 + `identity_state` 一道门槛 | 运行期无三态分叉 |
| 固件列 | `stable`/`target_model` 保留、不再写、读时派生 | 迁移中 DROP | −2 列、无派生逻辑、无死列 |
| 运行模式 | `gateMode` warn/enforce | 单一模式 + 只读预检 | −1 开关、无需「改常量重发版」 |
| force 作用面 | 10 条分支可 force | **2 条**（版本方向） | force 不再需要硬件豁免分支 |
| 旧查询参数 | `status`/`model` 保留但忽略 | 前端同批删除，后端不承诺 | 无「保留」承诺要维护 |

粗估可少写 **150–200 行**分支与派生代码及其测试（三态分叉 ≈40、warn 双模 ≈30、`stable` 派生 ≈60、force 硬件豁免 ≈40）。这是量级判断，不是承诺。

**C. 一次性成本与回本点**

| 项 | 量 | 说明 |
|---|---|---|
| 增量开发 | **+0.5 人日** | 补 `meta-gen`、删列与调用点清理、预检命令（相对 v1.3） |
| A 档更新内容（v1.5） | **+1.1 人日** | `release.json` notes + 端点字段 + 弹窗 + e2e |
| 存量固件重传 | N × 5 分钟 | N = 迁移报告里 `identity_state='legacy'` 的行数；sidecar 由 `meta-gen` 生成 |
| 节点硬件补录 | M × 2 分钟 | M = `hw_flash_mb=0` 的行数；`ehomectl node hw backfill` 可批量 |
| 迁移窗口 | < 1 分钟（固件量为两位数） | 单事务；期间拒绝写入 |
| **回本点** | 拦截 **1 台**误刷（≈2h），或避免 6 次旧前端报错排查（6×10min） | 与增量操作成本（≈1 小时）同量级；此后为净收益 |

**D. 不量化但确实存在**

- 可解释性：用户能看到「为什么不能升」的具体原因，而不是点了没反应；
- 审计：force 必须带理由并落 `security_audit_events`；
- 安全：下载票据在发送时签发（30 分钟 TTL 不再提前过期）、SHA256 全链路校验；
- 可回归：运维动作收敛为 `ehomectl` 命令，不再依赖个人记忆。

**E. 明确不带来的收益（避免过度期待）**

- 不减少「人工选固件」这一步：仍是人工选择 + 服务端校验；
- 不验证 sidecar 里 PSRAM 声明的真伪（写错仍会错，见 RK-11）；
- 不覆盖不可接触设备的 bootloader 回滚（D-1）；
- 不做灰度百分比投放（渠道 + 人工选择已足够）。

## 3. 总体设计

### 3.1 四层模型与落点

| 层 | 要解决的问题 | 本方案交付物 |
|---|---|---|
| **L1 身份** | 我是谁 | 固件：镜像头解析 + 构建 sidecar → `chip/flash/psram/version/elf_sha256`；平台：`buildinfo` + 根路由 `GET /api/v1/system/version` |
| **L2 决策** | 该不该升 | `firmwareid.CheckCompat` 纯函数 + 闸门（建任务为主，下发前只复检撤回） |
| **L3 执行** | 怎么升、失败怎么办 | 保持 push 流程；补发送时签票、回滚判据、成功判定加固 |
| **L4 呈现** | 怎么让人知道 | 固件页/对话框的兼容性呈现、状态文案单一真源、`UpdateBanner` |

### 3.2 三条链路 × 四层

| 链路 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| 设备固件 | 镜像头 + sidecar | 闸门（芯片/容量/PSRAM/方向） | 现有 OTA + 签票 + 回滚 | 固件页 / 节点页 |
| 服务端镜像 | `buildinfo` + digest | 清单与实例对账 | 容器替换 + 回退镜像 | `release check` 脚本 |
| Web 前端 | `VITE_BUILD_ID/TIME` | `build_id` 等值 + 方向 | 浏览器刷新 | `UpdateBanner` |

### 3.3 端到端流程（v1.1 目标态）

```text
[构建期]
  build_firmware.sh <profile>
      ├─ 注入 EHOME_HW_PROFILE=esp32c6-n8（编译期常量 → Hello model）
      └─ 产出两件：ehome_collector.bin + ehome_collector.meta.json
         meta = {profile, chip, flash_mb, psram, version, idf_ver, sha256}

[上传]
  POST /firmwares/upload  (bin + 可选 sidecar)
      ├─ 写临时文件 → 解析镜像头 → 若带 sidecar 则交叉校验（chip/flash/version 必须一致）
      ├─ 拒绝：非 ESP / project 不符 / chip 不支持 / 版本不一致 / 超过该容量槽上限 / 重复 elf_sha256
      ├─ 以 elf_sha256 前 16 位唯一命名落盘，入库（version 以镜像为准）
      └─ 失败即删临时文件，不留孤儿

[选择]
  GET /firmwares?node_id=<id>
      └─ 每行带 compatible / reasons；前端置灰 + 原因（单一模式：命中即置灰）

[建任务]
  POST /ota/tasks {node_id, firmware_id, force?, force_reason?}
      ├─ 闸门：撤回 → 节点硬件 → 芯片 → 容量 → PSRAM → 槽容量 → 版本方向 → 最低版本
      ├─ 不兼容 → 409 + 机器码 + reasons；force 需理由并写审计
      └─ 通过 → 建任务（记录 forced/force_reason/source）

[下发]
  SendOtaCommand
      ├─ 复检：固件是否已撤回（唯一允许在下发前重判的条件）
      └─ 按发送时刻现签下载票据（不再复用上传时 URL）→ OtaCmd

[执行/回报]
  设备下载 → SHA256 → esp_ota_end（chip 校验）→ 切分区 → 重启 → Hello
      └─ OtaProg 为权威；Hello 补完成仅在「任务已离开 pending」时生效

[平台]
  构建 → 推镜像 → 读 digest → 写 deploy/release.json → 部署 → 脚本对账 + 浏览器横幅提示
```

### 3.4 六个关键设计判断

**判断 1：PSRAM 不可能从镜像头导出，必须有构建侧元数据。**
`spi_size` 与 `chip_id` 在镜像头里，PSRAM 不在。实测 `s3-n16` 与 `s3p-n16` 的前 0x100 字节除 `elf_sha256` 外完全相同。
因此 PSRAM 只能来自构建期 sidecar（`sdkconfig.json` 已含 `SPIRAM`）。**缺失 sidecar 的固件不入库**：存量二进制由 `ehomectl firmware meta-gen` 一次性补齐 sidecar 后重传，而不是在运行期用三态兜住（§2.4 R3）。

**判断 2：回滚由引导器完成，应用只负责「确认」，而且确认不能依赖网络。**
`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` 编译进 `bootloader.bin`，OTA 只写应用分区，因此能力本身拆成「app 侧确认逻辑」（可 OTA）与「现场重烧」（作业项），**无法重烧的设备不具备自动回滚**。
更关键的是语义（见 §6.6）：只要应用**没调 `mark_valid` 就复位**，下一次启动引导器会把该镜像标为 `ABORTED` 并自动退回旧分区——不需要应用调用 `mark_app_invalid_rollback_and_reboot()`。
所以「有效」判据必须**完全本地可达成**；把确认挂在 StatusReport 成功上，会让「应用正常但网络不通」的设备在下次重启时被误滚。

**判断 3：设备侧不引入「主动检查更新」。**
服务端每次 Hello 都拿到 `firmware_version`，让设备再查一次不产生新信息。自动升级的节流应落在服务端策略扫描。

**判断 4：兼容性判定只放服务端，不加帧字段。**
`OtaCmd` 与 `HelloAck` 都是 fail-closed 解码；往老消息加字段会砸掉在线设备。设备端只保留 `esp_ota_end` 的 chip 校验兜底。

**判断 5：固件版本以镜像为唯一真源；PSRAM 以 sidecar 为唯一真源。**
两者分别来自「镜像自证」与「构建自证」，都不接受人手填写。

**判断 6：未知一律拒绝——把「不确定」放进数据状态，而不是放进请求路径。**
`psram`/`flash_mb`/`platform` 缺失时的正确处理是「该固件/该节点不参与升级」，由 `identity_state` 与单条 `OTA_GATE_HARDWARE_UNKNOWN` 表达，并配 `ehomectl` 更正命令；而不是给每个字段各开一个 unknown 分支再用 `force` 放行——那等于按设计把误刷通道重新打开。

## 4. 协议与接口契约

### 4.1 固件身份解析（`internal/firmwareid`）

**输入**：文件句柄（读前 0x100 字节），加完整文件长度。

**输出**：

```go
type Identity struct {
    ChipID     uint16 // 0x000D=C6, 0x0009=S3
    Chip       string // "esp32c6" / "esp32s3"
    FlashMB    uint16 // 镜像头 spi_size：3→8、4→16
    Version    string // 镜像内 version[32]
    Project    string // 期望 "ehome_collector"
    ElfSHA256  string // 镜像内 app_elf_sha256（hex）
    BuiltAtRaw string // 镜像内 date+time 原文（不做时间解析）
    IDFVersion string // 镜像内 idf_ver[32]
    SizeBytes  int64
}
```

**偏移表**（实现与测试的唯一依据，已用 4 份真实产物逐字节核对）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0x00 | magic | 必须 `0xE9` |
| 0x03 | `spi_size`（高 4 位） | 0..3→1/2/4/8MB，4→16MB；**只接受 3 与 4** |
| 0x0C | `chip_id`（u16 LE） | C6=0x000D、S3=0x0009 |
| 0x20 | desc magic（u32 LE） | 必须 `0xABCD5432` |
| 0x30 | `version[32]` | 按 32 字节截断并 trim |
| 0x50 | `project_name[32]` | 同上 |
| 0x70 / 0x80 | `time[16]` / `date[16]` | 原文保存（`__DATE__` 形如 `Oct  5 2026`，双空格） |
| 0x90 | `idf_ver[32]` | 原文保存 |
| 0xB0 | `app_elf_sha256[32]` | 转 hex |

**解析错误码**（上传 400）：`FW_NOT_IMAGE`、`FW_TRUNCATED`、`FW_PROJECT_MISMATCH`、`FW_CHIP_UNSUPPORTED`、`FW_FLASH_UNSUPPORTED`、`FW_META_REQUIRED`、`FW_META_CONFLICT`、`FW_TOO_LARGE`、`FW_DUPLICATE`。

### 4.2 构建侧 sidecar 契约（新增）

`build_firmware.sh <profile>` 除 `.bin` 外产出同名 `.meta.json`：

```json
{
  "profile": "s3p-n16",
  "chip": "esp32s3",
  "flash_mb": 16,
  "psram": true,
  "version": "2.8.0",
  "idf_ver": "v6.1",
  "sha256": "9f86d0818..."
}
```

| 项 | 来源 | 说明 |
|---|---|---|
| `chip` | `build/<profile>/config/sdkconfig.json` 的 `IDF_TARGET` | 与镜像头 `chip_id` 交叉校验 |
| `flash_mb` | 同上 `ESPTOOLPY_FLASHSIZE_*` | 与镜像头 `spi_size` 交叉校验 |
| `psram` | 同上 `SPIRAM` | **唯一 PSRAM 真源** |
| `version` | `PROJECT_VER` | 与镜像内 `version` 交叉校验 |
| `sha256` | 对 `.bin` 计算 | 传输完整性 |

**上传规则**：

- **sidecar 必填**：缺 `.meta.json` → 400 `FW_META_REQUIRED`（不再有「入库但身份未知」的第三条路）；
- `chip`/`flash_mb`/`version` 三者与镜像必须一致，否则 `FW_META_CONFLICT`；
- sidecar 的 `sha256` 与上传内容不一致 → `FW_META_CONFLICT`；
- 存量二进制补 sidecar：`ehomectl firmware meta-gen --bin <file>` 从镜像解析 chip/flash/version，**只有 `psram` 一位需要人工给定**（镜像头里唯一不可导出的信息），产出同名 `.meta.json` 后走正常上传；
- 表单**不再接收 `version`**：版本一律取自镜像，sidecar 的 `version` 只作交叉校验，少一条人工填错路径；
- **legacy 补齐**：`elf_sha256` 命中且 `identity_state='legacy'` 时**就地补齐**（更新身份列与 sidecar 字段、置 `verified`、保留 id，响应 `completed_legacy=true`），而不是 409；命中 `verified`/`duplicate` 才 409 `FW_DUPLICATE`。没有这条，「存量重传补 sidecar」会被唯一索引挡死，legacy 永远补不回来。

### 4.3 HTTP 契约

> 统一 envelope：`{"code":200,"data":...,"message":"..."}`；错误走 `Error` / `ErrorWithCode` / **新增 `ErrorWithCodeData`**。

| 方法 | 路径 | 注册位置 | 变更 |
|---|---|---|---|
| GET | `/api/v1/system/version` | **根路由**（与 `/health` 同级，不进 v1 JWT 组） | 新增 |
| GET | `/api/v1/firmwares` | v1（登录） | 新增过滤 `chip`/`flash_mb`/`channel`/`q`/`include_withdrawn`；`node_id` 是**标注参数**（提供时每行追加 `compatible`/`reasons`，不筛行——前端用它做置灰）；**保持 `data: Firmware[]` 数组形状不变**（不做分页） |
| POST | `/api/v1/firmwares/upload` | v1（登录） | 临时文件 + 解析 + sidecar 交叉校验 + 唯一命名 |
| PUT | `/api/v1/firmwares/:id` | v1（登录） | 只允许 `changelog`/`channel`/`min_from_version`；`version` 由镜像决定、`target_model`/`stable` 列已删除，三者都不再出现在请求体 |
| POST | `/api/v1/firmwares/:id/download-ticket` | v1（登录） | 新增（DEF-3 修复）：为浏览器签发 30 分钟 HMAC 下载 URL；前端不再拼 JWT（路由用 POST 是为了避开 gin 同树 `:id`/`:filename` 通配符冲突） |
| POST | `/api/v1/firmwares/:id/withdraw` | v1（登录） | 新增；有在途任务 → 409 |
| DELETE | `/api/v1/firmwares/:id` | v1（登录） | 有在途任务 → 409；默认软删 |
| POST | `/api/v1/ota/tasks` | v1（登录） | 新增 `force`/`force_reason`；409 带 `data.reasons` |
| GET | `/api/v1/ota/tasks/:id` | v1（登录） | 响应增加 `forced`/`force_reason` |

**列表默认语义**（P1-9 修订）：

- 默认只返回 `withdrawn_at IS NULL AND deleted_at IS NULL` 的固件；`include_withdrawn=true` 才含已撤回；
- 旧参数 `status`、`model` **删除**：前端随同一镜像改掉；后端不声明、不承诺语义（未声明的 query 参数本就被忽略，不为它写兼容分支）；
- 返回形状保持 `data: Firmware[]`（**不做分页**，固件量级为几十条），避免连带改 `stores/firmware.ts` 与既有契约测试。

**版本端点**（公开、根路由）。请求：`GET /api/v1/system/version`，响应体：

```json
{
  "code": 200,
  "message": "ok",
  "data": {
    "version": "2.9.0",
    "build_id": "a1b2c3d",
    "commit": "a1b2c3d9e8f7...",
    "build_time": "2026-11-18T06:12:00Z",
    "notes": [
      "固件上传改为必填 sidecar，存量固件需重传",
      "固件闸门新增节点硬件档案校验"
    ]
  }
}
```

**`notes` 契约**（v1.5）：

- 恒为数组：无内容时返回 `[]`，**不省略字段、不返回 `null`**——前端据此决定是否显示「查看更新内容」；
- 上限 **10 条、每条 120 字**；超限由 `scripts/verify-release.sh` 在**构建期**拒绝，运行期不截断；
- 端点加 `Cache-Control: no-store`：版本与说明随发布变化，任何缓存都会让「关于」页显示旧内容；
- 该端点**公开**，`notes` 只写用户可见的变化；安全类修复统一写「若干问题修复」，不写可利用细节。

**版本探测响应头**（活跃用户的秒级通道）：

- 所有 `/api/*` 响应（含错误响应）都带 `X-EHome-Build: <build_id>`，值与 `buildinfo.BuildID` 同源；
- 前端 `apiClient` 响应拦截器在读 `response.data` 之前比对 `response.headers["x-ehome-build"]` 与 `import.meta.env.VITE_BUILD_ID`；不一致即进入 `stale`；
- 静态资源请求不经过 axios，不受影响；
- 同源部署无需 CORS 暴露；跨源部署需 `Access-Control-Expose-Headers: X-EHome-Build`；
- **长度必须一致**：`VITE_BUILD_ID` 与后端 `BuildID` 同为 7 位短 SHA。构建期在 Dockerfile 断言长度（传 12 位直接构建失败），前端**不做截断/补齐**——静默修正只会把 CI 传错藏起来，后果是旧页面常驻横幅且点刷新也不消失。

**建任务 409**：

```json
{
  "code": 409,
  "message": "node hardware profile is incomplete",
  "error_code": "OTA_GATE_HARDWARE_UNKNOWN",
  "data": {
    "reasons": ["OTA_GATE_HARDWARE_UNKNOWN"],
    "node_hw": { "chip": "esp32s3", "flash_mb": 0, "psram": "" },
    "firmware": { "model_key": "esp32c6-n8", "chip": "esp32c6", "psram": "no", "version": "2.8.0" },
    "forceable": false,
    "fix": "ehomectl node hw set --id F0F5BD02F35C --flash-mb 16 --psram no"
  }

```

## 5. 数据模型

### 5.1 盘点与复用

| 表 | 已有什么 | 本方案只加什么 |
|---|---|---|
| `firmwares` | `version/checksum/size_bytes/url/filename/storage_path/changelog/target_model/min_from_version/stable` | 身份列（chip/flash/psram/model_key/elf_sha256/profile/built_at_raw/idf_ver）、`channel`、`withdrawn_at`、软删 |
| `nodes` | **`platform`（size 16）、`hardware_info`（jsonb）、`resource_reported_at`、`model`（size 20）** | 只加 `hw_flash_mb`、`hw_psram`（`yes`/`no`/空=未识别）；**不重复加 chip/profile/上报时间** |
| `ota_tasks` | `ota_id/node_id/firmware_id/status/progress/error_msg/to_version/时间戳` | 只加 `forced`、`force_reason`、`source` |

### 5.2 `firmwares` 扩展

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `chip` | varchar(16) | `''` | `esp32c6` / `esp32s3`，来自镜像头 |
| `flash_mb` | smallint | 0 | 8 / 16；0 = 未知 |
| `psram` | varchar(8) | `''` | **只有 `yes` / `no`**（来自 sidecar）；`''` 只出现在 `identity_state='legacy'` 的行，且这类行不可选（回填行因 PSRAM 不可导出，一律 legacy） |
| `model_key` | varchar(32) | `''` | `chip-flash`，如 `esp32c6-n8`；**不含 p** |
| `build_profile` | varchar(32) | `''` | sidecar 的 `profile`，如 `s3p-n16`；仅展示与排障 |
| `elf_sha256` | varchar(64) | `''` | **唯一键**（部分索引） |
| `built_at_raw` | varchar(32) | `''` | 镜像内日期时间原文（`Oct  5 2026 07:37:54`），**不做时区解析** |
| `idf_ver` | varchar(32) | `''` | 构建用 IDF 版本 |
| `channel` | varchar(16) | `stable` | `stable` / `beta` / `internal`（**不含 withdrawn**） |
| `withdrawn_at` | timestamptz | null | 撤回时间；撤回状态由该列表达 |
| `identity_state` | varchar(16) | `legacy` | `verified` / `legacy` / `duplicate`；**只有 `verified` 可选**（来源只写日志，不落列） |
| `DeletedAt` | timestamptz | null | 软删（`gorm.DeletedAt`） |

`stable` / `target_model` **在本次迁移中 DROP COLUMN**（GORM `AutoMigrate` 不删列，需显式 DDL）：迁移前把 `stable=true` 映射为 `channel=stable`、其余 `internal`；`target_model` 的展示信息由 `model_key` + `build_profile` 承担。二者不参与任何 OTA 判定，只被上传/编辑接口、`simulation/catalog` 与 `handler_ota_update_test.go` 读写，这些调用点随本次改动一并删除。

### 5.3 `nodes` 扩展

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `hw_flash_mb` | smallint | 0 | 0 = 未知；来自型号字符串解析或未来上报 |
| `hw_psram` | varchar(8) | `''` | `yes` / `no` / `''`（未识别）；`''` 只由「硬件未识别」单条闸门拒绝，不在各字段上分叉 |

`chip` 用既有 `platform`；`model` 保留为展示；原始上报串若要留存，写入既有 `hardware_info`（jsonb），不新增列。

### 5.4 `ota_tasks` 扩展

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `forced` | boolean | false | 是否绕过闸门 |
| `force_reason` | varchar(256) | `''` | 强制原因 |
| `source` | varchar(16) | `user` | `user` / `system`（系统回滚） |

### 5.5 索引与约束

```sql
-- 唯一：同一构建只允许一份（部分索引，排除未识别与已删）
CREATE UNIQUE INDEX IF NOT EXISTS uq_firmwares_elf
  ON firmwares (elf_sha256)
  WHERE elf_sha256 <> '' AND deleted_at IS NULL;

-- 普通：按档位检索与展示（非唯一，允许「同版本多构建」）
CREATE INDEX IF NOT EXISTS idx_firmwares_model_version
  ON firmwares (model_key, version, channel);
```

**为什么唯一键不是 `(model_key, version, channel)`**：

- PSRAM 不在镜像头里，`s3-n16` 与 `s3p-n16` 的 `model_key` 相同；若按档位建唯一索引，两份真实产物必然冲突；
- `elf_sha256` 是「同一构建」的客观指纹，语义正好对应「重复上传」；
- 同档位同版本的两份不同构建（s3 与 s3p）允许并存，选择时由闸门按 PSRAM 判定，而不是靠唯一键拦截。

### 5.6 迁移编排

新增 `backend/internal/dbschema/firmware_identity.go`（与既有 `EnsureSourceGroupSchema` 同包范式）：

| 顺序 | 函数 | 行为 | 幂等条件 |
|---|---|---|---|
| 0 | `AutoMigrate` | 增列（可空/带默认）与软删列；**不含索引、回填、删列** | GORM 自带 |
| 1 | `BackfillFirmwareIdentity` | `identity_state='legacy'` 的行：按 `storage_path` → `filename` 定位二进制 → 解析 → 回填 chip/flash/model_key/elf_sha256，**仍保持 `legacy`**（PSRAM 不可导出，按 §2.4 R3 不可选；解析出的列只用于诊断与去重）；文件缺失/解析失败 → 保持 `legacy` | 同条件 |
| 2 | `EnforceImageVersion` | 已 `verified` 的行：以镜像内 version 覆盖 `version` 列（**镜像为准**），差异写日志 | 同条件 |
| 3 | `DedupeFirmwareIdentity` | 按 `elf_sha256` 分组 `count > 1`：保留最小 id 标 `verified`，其余置 `elf_sha256=''`、`identity_state='duplicate'` | 仅当存在重复 |
| 4 | `DropLegacyFirmwareColumns` | `ALTER TABLE firmwares DROP COLUMN stable` / `target_model`（SQLite ≥3.35 原生支持，否则重建表） | 列不存在则跳过 |
| 5 | `EnsureFirmwareIdentityIndex` | 执行 §5.5 DDL | `IF NOT EXISTS` |
| 6 | `BackfillNodeHardware` | `platform`/`model` 可解析时写 `hw_flash_mb`/`hw_psram`；解析失败留空 | 同条件 |
| 7 | `ReportLegacyFirmware` | 输出 `legacy`/`duplicate` 清单与条数到启动日志；可由 `ehomectl firmware migrate-report` 复现 | 只读 |

**挂载位置**（两处，缺一不可）：

- `backend/internal/database/gorm.go`：在现有 `MigrateAutomationRuleActions`、`MigrateNodeIDFromJTAGMAC` **之后**显式调用（不是「AutoMigrate 末尾」，其后仍有迁移）；
- `backend/testutil/db.go`：在 `AutoMigrate(models)` 之后调用同一组函数（与 `EnsureSourceGroupSchema` 并列）。

**失败处理**：任一函数返回错误 → 启动失败（与现有 `abortStartup` 口径一致）；建索引前必须先跑步骤 3，**不允许**把重复数据留给索引去发现。

**一次性与不可逆**：

- 整个迁移在**单事务**内执行（PG 的 DDL 可事务；SQLite 亦逐条 DDL 在事务内），失败整体回滚，不留半态；
- 步骤 4 不可逆：删列后**不能回退旧镜像**（旧代码读不到 `stable`）。发布前 `pg_dump` 是唯一回滚手段（见 §9.3）；
- 步骤 7 列出的 `legacy` 行需人工重传（sidecar 由 `meta-gen` 生成）。这是刻意的取舍：宁可一次性重传 N 个文件，也不在运行期长期维护三态与 force 豁免。

**回退**：应用层前滚修复；数据层靠 `pg_dump` 恢复（删列不可逆，见 §9.3 / §9.4）。

## 6. 状态机

### 6.1 固件生命周期

```text
上传解析通过 → active ──withdraw──► withdrawn（不可选，可恢复）
                  └──delete（无在途任务）──► deleted（软删）
```

| 状态 | 可选于 OTA | 可下载 | 可删除 |
|---|---|---|---|
| `active` | 是 | 是 | 仅在无在途任务时 |
| `withdrawn` | 否 | 是（历史任务） | 是 |
| `deleted` | 否 | 否 | — |

### 6.2 OTA 任务（不新增状态，只加前置条件）

现有 8 态不变。两处判定改造：

| 位置 | 现状 | 改造后 |
|---|---|---|
| 建任务 | 无校验 | 先过闸门；不通过 409，不产生任务行；`force` 才放行并写审计 |
| Hello 补完成 | `ToVersion == firmwareVersion` 即 success | 追加「任务必须已离开 `pending`」；改条件更新 |

**Hello 补完成最终逻辑**（删除了 v1.0 的「指纹比对」分支——Hello 不上报指纹，该分支恒真）：

```text
latest = 该节点最新的一条 active 任务
if latest == nil: return
if latest.ToVersion == "" or latest.ToVersion != firmwareVersion: return
if latest.Status == "pending":                 # 从未开始，不能凭版本相等判成功
    log warn(reason=hello_without_progress); return
rows = UPDATE ota_tasks SET status='success', progress=100, completed_at=now,
                              error_msg='auto-completed via Hello'
       WHERE id=? AND node_id=? AND status=?    # 读到的状态，条件更新
if rows != 1: log warn(concurrent_change); return
broadcast ota_progress
```

### 6.3 闸门决策树（10 分支，v1.4 收紧）

按顺序判定，**第一个命中即返回**。`force` 只对**版本方向**两条生效（需理由 + 审计）；硬件类判定**不可 force**——放行未知等于按设计重开误刷通道（§2.4 R5）。

| # | 条件 | 机器码 | 可 force |
|---|---|---|---|
| 1 | `withdrawn_at != null` | `OTA_GATE_WITHDRAWN` | 否 |
| 2 | `identity_state != 'verified'`（`legacy`/`duplicate`） | `OTA_GATE_FIRMWARE_UNVERIFIED` | **否** |
| 3 | 节点硬件档案不完整：`platform` 为空 / `hw_flash_mb = 0` / `hw_psram` 为空 | `OTA_GATE_HARDWARE_UNKNOWN` | **否** |
| 4 | `firmware.chip != node.platform` | `OTA_GATE_MODEL_MISMATCH` | **否** |
| 5 | `firmware.flash_mb != node.hw_flash_mb` | `OTA_GATE_FLASH_MISMATCH` | **否** |
| 6 | `firmware.psram = yes` 且 `hw_psram != yes` | `OTA_GATE_PSRAM_REQUIRED` | **否** |
| 7 | `firmware.psram = no` 且 `hw_psram = yes` | `OTA_GATE_PSRAM_MISMATCH` | **否** |
| 8 | `size_bytes > slotCapacity(node.hw_flash_mb)` | `OTA_GATE_IMAGE_TOO_LARGE` | **否** |
| 9 | `compareVersion(target, current) <= 0` | `OTA_GATE_NOT_AN_UPGRADE` | 是（系统回滚跳过） |
| 10 | `min_from_version` 高于当前版本 | `OTA_GATE_BELOW_MIN_VERSION` | 是（系统回滚跳过） |

`slotCapacity` 为代码常量表（与分区 CSV 同源）：8MB→`0x380000`、16MB→`0x680000`。

**为什么不再有 unknown 分支**：三条「未知」判定（`platform`/`flash`/`psram`）收敛为第 3 条；固件侧的「未知」不允许存在（`identity_state` 已把它挡在可选集合外）。命中第 3 条时 409 的 `data.fix` 直接给出更正命令，例如 `ehomectl node hw set --id F0F5BD02F35C --flash-mb 8 --psram no`。

**系统回滚例外**：`source = system` 时跳过第 9、10 条（回滚目标必然更旧），其余照常判定；`AutoRollback` 以 `source=system` 调 `CreateTask`。

**不做双模式**（v1.4 删 `gateMode`）：请求路径只保留「命中即 409」一种行为。上线前的观察改由**只读预检**承担，它复用同一个纯函数，因此「预检通过」与「建任务通过」判定同源：

```text
ehomectl ota gate-check --all                  # 逐 (节点, 固件) 打印会命中的分支，不改库
ehomectl ota gate-check --node F0F5BD02F35C
```

### 6.4 旧前端提醒刷新（4 态 + 四通道检测）

**需求**：部署新版本后，**正在使用旧页面的用户必须被提醒刷新**，且不得因为提醒而丢失未提交的输入。

**检测通道（按响应速度排序）**：

| # | 通道 | 覆盖场景 | 延迟 | 落点 |
|---|---|---|---|---|
| 1 | **响应头 `X-EHome-Build`** | 任何正在操作的标签页 | 下一次 API 响应（通常秒级） | 后端中间件写头；axios 响应拦截器比对自身 `VITE_BUILD_ID` |
| 2 | WebSocket 重连成功 | 部署必然断链再连 | 1 次重连后 | `wsStore.onConnected` 触发一次 `/system/version` |
| 3 | 轮询 + 可见性 | 纯浏览、长时间空闲 | ≤30 分钟（硬节流 5 分钟） | 首屏、`visibilitychange`、30 分钟定时 |
| 4 | **chunk 加载失败** | 懒加载路由引用的旧 hash 已不存在 | 立即 | `vite:preloadError` + `router.onError` 识别模块加载失败 |

**状态机（4 态）**：

| 状态 | 进入条件 | UI | 可否推迟 |
|---|---|---|---|
| `same` | `build_id` 相同，或检查失败 | 无 | — |
| `stale` | `build_id` 不同 **且** 服务端 `build_time` 更新 | 顶部公告：`[立即刷新] [稍后]` | 是 |
| `blocked` | chunk 加载失败，或 `stale` 期间页面导航失败 | **模态**：新版本已发布，需刷新后继续 | **否** |
| `dismissed` | 用户点「稍后」 | 无（同一 build 不再**主动**提示） | — |

「稍后」的边界：只压制 `stale` 的主动提示；一旦进入 `blocked` 仍会强提示——因为此时页面已经无法正常导航，继续使用只会不断撞 404。

**UX 规则**：

1. **不自动刷新**：刷新必须由用户点击，避免丢失表单与未提交操作。
2. 与 `NetworkBanner` 共用顶部公告栈：**断线优先显示**（断线时刷不刷新都无意义），更新提示次之。
3. 刷新按钮走 `location.reload()`；若页面登记了 `isDirty`，先 `confirm`（P2 可选，本期不做强制拦截）。
4. 多标签页各自独立判断（`sessionStorage` 按标签），都会提示——这是期望行为。
5. 部署**回滚**（`build_time` 更旧）不提示，避免把回滚误报成新版本。
6. 关闭后重开自然拿到新 `index.html`，无需提示。

**更新内容弹窗（A 档，v1.5）**：

- 数据来源只有一个：`GET /system/version` 的 `data.notes`；不额外加端点、不在前端写死文案；
- 两个入口共用组件 `ReleaseNotesDialog.vue`：① `stale` 横幅上的「查看更新内容」；② 版本号（侧栏底部与移动端抽屉）点击进入「关于」；
- `notes` 为空 —— **不渲染入口**（`[]` 与 `undefined` 同等处理），避免出现只有版本号的空弹窗；
- 弹窗只读，按钮为「关闭」，以及在 `stale`/`blocked` 下追加「立即刷新」；
- 打开/关闭弹窗**不改变**更新状态、不触发重试；`blocked` 时弹窗可关，但模态仍在。

**实现约束**：

- `index.html` 已是 `no-cache`（`cmd/server/static.go:9-14`），刷新即生效；`/assets/*` 是 immutable hash，旧文件随镜像替换消失——这正是通道 4 的根因。
- 部署窗口内（容器重启）API 可能 502/503 且无响应头 ⇒ 通道 1 静默，由通道 2/3 兜底。
- 跨源部署（`EHOME_ALLOWED_ORIGINS` 非空）时需在 CORS 中 `Access-Control-Expose-Headers: X-EHome-Build`。
- 通道 1 只在 `axios` 覆盖的 `/api/*` 上生效；静态资源与第三方请求不参与。

### 6.5 平台发布对账（降级为脚本）

| 结果 | 判定 | 动作 |
|---|---|---|
| `consistent` | `release.json` 的 commit 与 `/health.commit`、`/system/version.commit` 一致 | 通过 |
| `drifted` | 任一不一致 | 退出非 0，提示回退镜像 |
| `unknown` | 清单缺失或端点不可达 | 告警，人工确认 |

**`release.json` 与 `notes` 的归属（v1.5）**：仓库内 `deploy/release.json` 是**模板**，人只维护 `version` 与 `notes`；`commit`/`build_time` 留空，由 CI 在构建时填入并写入 `backend/internal/buildinfo/release.json`，再 `go:embed` 进二进制。这样「构建时说的版本」与「运行时报告的版本」是同一份文件，不因挂载或环境差异而漂移。

```json
{
  "version": "2.9.0",
  "commit": "",
  "build_time": "",
  "notes": ["固件上传改为必填 sidecar，存量固件需重传"]
}
```

- 对账**只看 `commit`**：改 `notes` 文案不算漂移，否则补一句说明就会触发告警；
- `verify-release.sh` 额外校验 `notes` 的 schema（数组、≤10 条、每条 ≤120 字、剔除空串），不合法即非 0 退出——让超长说明在构建期失败，而不是在界面上被截断。

### 6.6 设备回滚语义与判据（v1.2 更正）

三种结果（依据 [ESP-IDF OTA 文档](https://docs.espressif.com/projects/esp-idf/zh_CN/stable/esp32/api-reference/system/ota.html) 与 `bootloader_utility.c:393-400`）：

| 场景 | 应用要做什么 | 引导器行为 | 设备结果 |
|---|---|---|---|
| 新版本正常 | 调 `esp_ota_mark_app_valid_cancel_rollback()` | otadata 置 `VALID` | 正常启动，不再回滚 |
| 能跑但确定不可用 | 主动调 `esp_ota_mark_app_invalid_rollback_and_reboot()` | 置 `INVALID` 并复位 | 立即退回旧版本 |
| 启动即崩 / 复位前未确认 | **什么都不用做** | 下次启动把 `PENDING_VERIFY` 置 `ABORTED` | 自动退回旧版本 |

**判据对照**：

| 维度 | v1.1（错误） | v1.2（定稿） |
|---|---|---|
| 确认触发 | 首条 `StatusReport` 成功 | **本地自检**：`uptime ≥ N 秒` 且关键子系统就绪 且 `!boot_guard_in_safe_mode()` |
| 是否依赖网络 | 是 | **否** |
| 崩溃处理 | 依赖主动 invalid（崩溃时往往来不及） | 不确认即可，由引导器回退 |
| 主动 invalid 的用途 | 通用失败分支 | 仅用于「能跑但确定不可用」（如关键外设初始化失败） |

**实施要点**：

1. 删除 `main.c:331-332` 把确认挂在 `msg_handler_send_status` 成功之后的分支；改为独立确认点：
   `if (s->ota_need_confirm && uptime >= OTA_CONFIRM_DELAY_S && !boot_guard_in_safe_mode() && critical_ready()) ota_confirm_valid();`
2. 安全模式下**不确认**——否则「降级但活着」会把坏固件钉死；安全模式持续且反复重启时，由引导器回退。
3. 判据必须**永远能在本地达成**，不得包含联网 / DNS / NTP / 服务端应答等外部条件；否则设备长期停在 `PENDING_VERIFY`，任何意外复位都会触发回滚。
4. 重复调用 `mark_valid` 是安全的（状态已是 `VALID` 时直接返回）。
5. 主动 `mark_invalid_and_reboot` 有前置条件：另一分区必须可用；若返回 `ESP_ERR_OTA_ROLLBACK_FAILED` 则**不会复位**——此时应记日志并退化为「不确认 + 主动复位」，仍由引导器处理。
6. **确认时刻不得被网络阻塞**：确认执行体必须在任何可能阻塞的网络初始化（`wifi_mgr_start()` 等）之前创建；「关键初始化完成」不得把 WiFi 连接计入。实机实测（2026-11-19）：修复前 31.45s（联网）/ 31.94s（断网，被 WiFi 超时推迟），修复后 30.71s / 30.54s。
7. **确认轮询不得依赖网络相关任务的创建顺序或状态**：例如不能读由 `status_task` 维护的 `uptime` 字段（无 AP 时该值晚 30s 才有），应由确认任务自行取单调时钟。

> 台架注意：本机 CH34x 只接 UART0，产品 console 在原生 USB-JTAG ⇒ app 日志不可见，验证时需临时把 console 挪到 UART0（见 `tools/qemu-console-uart.defaults` 注释）。另外 RTS 复位是掉电型（`rst:0x1 POWERON`），`boot_guard` 计数不累积，验证安全模式必须用软件复位。

**服务端记账（新增，必须配套）**：

- 设备自动回滚后，Hello 上报的是**旧版本** ⇒ `ToVersion != firmwareVersion`，任务不会被补完成，最终由 30 分钟超时扫描置 `timeout`；
- 为了可诊断并避免误动作，在 `HandleHelloOTACompletion` 同一入口增加「版本回退分支」：
  若节点当前版本等于该固件**上一个成功版本**且任务处于 **`verifying`/`installing`**，则置 `failed`、`error_msg = "device rolled back"`，
  并**不计入** `AutoRollback` 的失败计数（否则会出现「回滚的回滚」）。
  **不能**用 `active` 全集判定：下载阶段设备仍在跑旧版本，而 Hello 是周期上报（约 600s），判据会恒真、把每一次正常升级都误判成回滚；漏判的情况由 30 分钟超时扫描兜底（实施中由 `ota_gate_test` 的 `DownloadingOldVersionIsNotRollback` 钉住）。
- 设备回滚不会上报 `OtaProg failed`（已重启到旧版本），因此**只能以版本回退作为判据**。

```text
2. M0 起是破坏性变更：删列 + 响应字段减少，**必须与前端同批**（同一镜像，不允许旧前端连新后端）；
   因此 M0 需带上「前端停止读取 stable/target_model」的最小改动
3. M1a / M1b / M2 各自可独立发布（前端随镜像）
4. 固件最后上（M3a）：必须在服务端已能解析新 profile 之后
5. M3b（现场重烧）在 M3a 之后按批次进行
```

### 9.2 灰度

| 层 | 方式 |
|---|---|
| 服务端闸门 | **无模式开关**：上线前跑 `ehomectl ota gate-check --all` 出只读预检报告，先补齐数据（节点硬件档案 / 固件重传）再放开建任务 |
| 固件 | 1 台 → 3 台（不同档位各 1）→ 全量，每档 ≥24h |
| 前端 | 与容器同生共死；靠横幅提示刷新，不强刷 |

### 9.3 回滚剧本

| 场景 | 动作 | 耗时 |
|---|---|---|
| M-1 误拒正常固件（未动库） | **回退上一镜像** | 分钟级 |
| M0 迁移/校验误伤（已删列，不可退镜像） | **前滚修复**：修正解析/校验后重新发布；数据异常从发布前 `pg_dump` 恢复 | 数十分钟 |
| M1a 闸门误伤 | 无 `warn` 降级路径：按 `gate-check` 报告更正数据（节点档案 / 固件重传），或改判定常量后重新发布 | 数十分钟 |
| M1b/M2 前端异常 | 回退到 **M0 之后**的镜像（同 schema）；不可退到 M0 之前 | 分钟级 |
| M3a 回滚逻辑异常 | `sdkconfig` 关闭回滚开关后重编重刷（仅覆盖可接触设备） | 现场作业 |
| 数据层 | 迁移为单事务；异常用发布前 `pg_dump` 恢复；删列不可逆 | 分钟级–数十分钟 |

### 9.4 迁移窗口

- 回填与删列在启动时自动执行；固件行数通常两位数，秒级完成。
- 若固件行数 >1k，改为 `ehomectl firmware migrate` 显式执行（本期不做，留作后续）。
- 建索引前先去重（§5.6 步骤 3），**不允许**让索引失败暴露问题（那会 abort 启动）。
- 迁移**不可回退到旧镜像**（列已删）：发布前 `pg_dump`；迁移失败则服务拒绝启动，恢复备份后前滚修复。
- 迁移报告里的 `legacy` 行需重传；报告同时出现在启动日志与 `ehomectl firmware migrate-report`。

## 10. 风险登记册

| 编号 | 风险 | 触发 | 缓解 |
|---|---|---|---|
| RK-1 | 存量固件无法解析 | 二进制已被清理 | 保持 `identity_state='legacy'`（不可选、不可 force），迁移报告列出并要求重传；提供按 id 重跑回填 |
| RK-2 | 存量节点无容量档案 | 旧固件只报 `esp32s3` | `OTA_GATE_HARDWARE_UNKNOWN`（不可 force）；上线前用迁移步骤 6 + `ehomectl node hw set` 补录；M3a 固件上线后自动补齐 |
| RK-3 | 闸门误伤 | `min_from_version` 填错、节点档案错 | 上线前 `gate-check` 预检报告 + `reasons` 明示；数据类误伤靠更正档案，配置类靠版本类 force |
| RK-4 | SQLite 不支持部分索引 | 版本过旧 | 已有 `source_group` 先例；CI 双库各跑一次，不支持则退化为应用层校验 |
| RK-5 | 横幅打断操作 | 用户正在填表单 | 不强刷；刷新前仅提示未保存 |
| RK-6 | bootloader 重烧影响面 | 重烧失败/版本不兼容 | 单台验证 → 分批；保留回刷旧 bootloader 的镜像 |
| RK-7 | 型号格式变更导致显示异常 | 前端未更新映射 | **不做新旧双格式兼容**：迁移把身份字段规范化为 `esp32c6/esp32s3/esp32s3p` + 容量；解析不出来即留空并走硬件未识别分支 |
| RK-8 | 回填与库内版本不一致 | 历史上传填错版本 | **镜像为准覆盖**并写日志（迁移步骤 2）；不保留「以库内为准」的分支 |
| RK-9 | 删除固件后被历史任务引用 | 任务已终态 | 软删 + 列表可显示「已删除」；任务保留 `firmware_id` |
| RK-10 | **回滚误触发（已规避）** | 若把确认挂在网络成功上，断网设备会在下次重启时被误滚 | v1.2 已改为纯本地判据（§6.6）；故障注入用例②专门验证 |
| RK-12 | **「回滚的回滚」循环** | 设备自动回滚 → 服务端任务 timeout/failed → `AutoRollback` 再下发旧版任务 | 版本回退分支标 `device rolled back` 且不计入失败计数；`AutoRollback` 仅对真失败生效 |
| RK-11 | **PSRAM 声明与实际不符** | sidecar 写错、板子无 PSRAM | 构建期从 `sdkconfig.json` 生成、运行时探测结果写日志；不一致时 `hw_psram` 记实际值 |
| RK-13 | **删列后无法回退镜像** | M0 上线后需紧急回退 | 发布前 `pg_dump`；迁移单事务、失败即拒绝启动；回退手段是前滚修复而非退镜像（§9.3） |
