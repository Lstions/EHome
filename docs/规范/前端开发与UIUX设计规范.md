## 1. 目的与适用范围

本规范约束 `frontend-shared/` 的 Vue 3 + TypeScript 前端开发、页面设计、组件设计、测试和验收。目标是让 EHomeSystem 保持一致的运维工具体验：信息密度高但可扫描，状态可信，操作可预期，桌面、平板与手机均可完成核心任务。

本规范优先级高于历史 UI 审计、已归档方案和个人习惯；具体模块的已批准设计若与本规范冲突，应在设计评审中明确例外、影响范围与验证方法。

术语遵循 [00-术语表.md](../设计/00-术语表.md)：ESP32 实体称“节点”，物理传感器或执行器称“边缘设备”，总线通信端口称“通道”。禁止在新增中文 UI 中混用“采集器”“设备模板”等旧称。

### 1.1 规范等级

- `MUST`：不满足不得合入。
- `SHOULD`：默认必须遵守；确有产品、技术或兼容性原因时，可在 PR 或设计中说明例外和替代验收。
- `MAY`：可选能力，不能成为阻塞交付的前置依赖。
- `禁止`：除经过设计评审的兼容改造外不得采用。

### 1.2 基本原则

1. **领域事实优先**：界面不能用模拟数据、猜测状态或前端默认值伪造设备事实；未知应明确显示“未知”或“—”，并给出可用时的原因或补救入口。
2. **一处定义，多处复用**：领域状态、格式化、主题 token、反馈逻辑和响应式模式应只有一个权威实现；页面不复制同一套规则。
3. **先保证任务，再做装饰**：这是 IoT 运维后台，不做营销式大卡片、无意义插画、浮夸渐变或为视觉而增加信息层级。
4. **最小结构差异**：仅当手机和桌面信息架构确实不同，才使用 JS 切换不同结构；纯布局差异由 CSS 处理。
5. **失败可理解、可恢复**：加载、空、离线、权限不足、请求失败、异步执行中和成功后的状态，必须各自可辨。

## 2. 当前工程基线

### 2.1 固定技术栈与边界

- 框架：Vue 3、`<script setup lang="ts">`、Composition API。
- 类型：TypeScript strict，启用 `noUnusedLocals`、`noUnusedParameters`、`noFallthroughCasesInSwitch`（`frontend-shared/tsconfig.json:17-20`）。
- UI：Element Plus + `@element-plus/icons-vue`；禁止引入第二套组件库、第二套状态库或第二套 HTTP 客户端。
- 状态：Pinia；路由：Vue Router；HTTP：统一 Axios client；实时通道：WebSocket store。
- 图表：ECharts；Canvas/图表色值通过 `utils/theme.ts` 解析当前主题，不在组件内复制亮色 hex。
- 测试：Vitest + Vue Test Utils（`happy-dom`）和 Playwright。前端覆盖率门槛为 lines/functions/statements 25%、branches 20%（`frontend-shared/vitest.config.ts:12-31`）。

### 2.2 目录职责

| 目录 | 职责 | 禁止放入 |
|---|---|---|
| `src/views/` | 路由页面、页面组装、路由参数与页面级状态 | 可跨页复用的业务逻辑、通用展示组件 |
| `src/components/common/` | 全局通用呈现与交互组件，如页头、空态、状态徽标、统计卡 | 领域 API 调用、节点或边缘设备专属规则 |
| `src/components/<领域>/` | 领域内复用的展示、表单或操作组件 | 跨领域的状态全局单例 |
| `src/composables/` | 可复用的响应式行为、异步生命周期、查询或操作守卫 | 单页模板细节、直接拼装整页布局 |
| `src/stores/` | 跨路由或跨组件共享的业务状态、缓存、WebSocket 状态 | 一次性表单输入、仅单组件可见的临时 UI 状态 |
| `src/api/` | 后端端点、请求/响应 DTO、兼容解包与输入输出归一化 | DOM、消息弹窗、路由跳转 |
| `src/utils/` | 无页面归属的格式化、校验、主题、会话、反馈等纯或基础设施工具 | 业务页面状态与组件实例 |
| `src/types/` | 跨模块类型 | API 调用或运行时副作用 |
| `src/styles/theme.css` | 全局 token、Element Plus 主题桥接、全局响应式兜底 | 单页面业务布局 |
| `src/locales/` | 已纳入国际化的稳定文案 | 临时调试文本 |

新增目录或跨层依赖必须说明职责。页面直接调用多个后端端点、管理多个独立 loading 状态且超过单一流程边界时，应优先抽取 composable，而不是继续膨胀页面组件。

## 3. 前端开发规范

### 3.1 Vue 组件与类型

1. `MUST` 使用 `<script setup lang="ts">`、显式 `defineProps`、`defineEmits` 和 TypeScript 类型；对外组件 props 与 emits 是契约，不得依赖父组件访问 `wrapper.vm` 或子组件内部变量。
2. `MUST` 将页面级组装留在 `views/`，通用视觉模式优先复用 `PageHeader`、`StatCard`、`EmptyState`、`StatusBadge`、`SkeletonCard`、`ErrorBoundary` 等既有组件。
3. `MUST` 为可点击的非原生容器补齐 `role`、`tabindex`、明确 `aria-label`，并让 Enter/Space 与 click 调用同一行为。`StatCard.vue:2-10` 是现有参照。
4. `MUST` 在可复用组件中处理 slot 的边界：scoped CSS 不会穿透 slot 内容。若消费者需要样式，提供明确 props、slot class 契约或页面侧样式，不得假设子组件 scoped CSS 会作用于父插槽。
5. `SHOULD` 单个 `.vue` 文件超过约 300 行时审查其职责：若同时含列表查询、筛选、删除、对话框、格式化和大块 CSS，优先按“页面组装 / composable / 领域组件”拆分；纯设备详情、图表 option 或不可拆的流程可保留，并在评审中说明。
6. `禁止` 为仅有视觉差异复制整段模板并以 `v-if="isMobile"` 维护两套业务分支；仅结构和交互模型确实不同的场景（例如桌面侧栏与移动抽屉）可使用，现有 `MainLayout.vue:4-73` 是允许的参照。
7. `禁止` 新增未经说明的 `any`。边界数据先用 `unknown` 再收窄；允许的临时兼容 `any` 必须紧贴后端不稳定契约并带出迁移目标。测试 stub 的最小 `any` 可保留，但不能把它复制到生产业务代码。

### 3.2 数据流、API 与状态

1. `MUST` 按“视图 -> composable/store -> api -> 后端”的方向组织依赖；`api/` 不得引入 Vue 组件、Pinia 页面 store、Element Plus 弹窗或 Router。
2. `MUST` 经 `src/api/client.ts` 发出 REST 请求。该 client 统一附带会话、转为 `ApiError`、处理非登录接口 401 的会话清理（`client.ts:28-76`）；业务页不得各自再实现 JWT 注入或全局 401 跳转。
3. `MUST` 在新增 API 方法时同时定义请求、响应和异常语义；不得假定调用方获得的是 AxiosResponse、业务 envelope 或内层 `data`。项目现有 client 返回业务 envelope（`client.ts:50-58`），新增方法须明确沿用并在同一 API 模块完成唯一解包。
4. `MUST` 区分数据库主键、业务 ID、物理节点 ID 和硬件地址。路由 `:id` 不能未经验证直接用作 `node_id`、设备地址或通道筛选值；不同大小写、数字/字符串边界必须规范化后比较。
5. `MUST` 由后端事实驱动状态。接口缺字段、设备离线、资源未上报时显示未知或不可用，不得以本地默认值伪造“正常”“停止”“无占用”。
6. `MUST` 对会改变查询范围的输入（节点、设备、型号、时间范围、筛选）重置或失效其派生状态：选中项、分页、异步结果、表单合法选项和缓存。创建向导中选择解析器后，应同步其总线类型等依赖字段，不能保留不再合法的默认值。
7. `SHOULD` 对跨页面可复用、需要缓存或由 WebSocket 更新的数据用 Pinia；单页面筛选词、对话框可见性、未提交表单值优先留在组件/组合式函数。
8. `MUST` WebSocket 事件建立联合类型或领域解析层；新业务不得继续扩散 `payload?: any`、`send(data: any)` 之类的无边界接口。外部消息解析失败必须可观察且不能破坏整个页面。
9. `禁止` 在视图中散布接口返回格式猜测，如 `res.data || res`、多层 `as any`、重复 `response.data.data`。兼容逻辑应收敛到对应 API 模块，逐步消除。

### 3.3 异步、并发与副作用

1. `MUST` 为每个异步操作提供精确的 loading 范围：刷新只锁刷新按钮；表格行操作只锁该行；表单提交只锁提交区。不得因单行请求阻塞全列表。
2. `MUST` 对可被重新触发的异步流程防止过期结果回写。可复用 `generation + 当前实体身份 + unmount` 模式；`useGuardedOperation.ts:26-91` 是节点切换、离线保护、乐观回滚的参照。
3. `MUST` 对乐观更新定义回滚点；请求失败后恢复服务端已确认值，显示操作级错误，不清空仍可用的数据。
4. `MUST` 在组件卸载、实体切换、会话失效时取消订阅、计时器或使异步结果失效；避免旧页面响应覆盖新页面。
5. `SHOULD` 列表搜索使用统一防抖，筛选变化重置页码；服务端分页时不得把当前页本地筛选伪装成全局检索。
6. `禁止` 用固定 `setTimeout` 或 `waitForTimeout` 等待请求、动画或数据就绪；使用 DOM 状态、网络 mock、条件等待、Promise 或事件完成信号。

### 3.4 错误、反馈与危险操作

1. `MUST` 使用 `feedback` 或领域对话框统一反馈。`utils/feedback.ts:12-103` 定义成功、错误、警告、信息及危险确认；新代码不能直接散布风格、时长、HTML 渲染策略各异的消息。
2. `MUST` 区分：首次加载、后台刷新、无数据、筛选无结果、权限不足、离线、接口失败和操作失败。空状态不是错误状态的替代品。
3. `MUST` 破坏性动作使用 danger 视觉层级、二次确认和影响说明；确认文案必须包含对象身份、不可逆影响或数据影响。删除必须与常规主操作隔离，不能靠颜色或图标单独承担风险。
4. `MUST` 禁用操作给出原因，尤其是设备离线、数据未准备、权限不足或前置条件缺失。用 tooltip 包裹 disabled Element Plus 控件时，应按 `NodeDetail.vue:10-49` 用可接收 hover 的外层元素。
5. `MUST` 未知、空值和未配置统一优先显示 `—` 或明确状态文案；不能出现空白单元格、空 Tag 或看似渲染失败的占位。
6. `禁止` 把请求失败 catch 后静默吞掉，除非失败确实是非阻塞的辅助信息，且 UI 有明确退化路径。禁止把网络失败、429、401、字段校验失败都显示为“密码错误”或“操作失败”。

### 3.5 路由、会话与安全

1. `MUST` 新业务路由注册到受保护主布局或明确 public 白名单；`router/index.ts:18-157` 的登录、主布局、404 路由分层是当前参照。
2. `MUST` 路由守卫和 API 401 处理都保留原目标或给出恢复路径，避免用户在会话过期后丢失工作上下文。
3. `MUST` 所有认证状态以用户 store 和服务端返回为准；仅凭 localStorage 中有字符串不能作为敏感操作授权依据。
4. `MUST` 日志、错误提示、浏览器控制台、URL、截图和测试产物不得包含密码、完整 JWT、初始化凭据或敏感请求体。WebSocket URL 中的 token 必须脱敏后才允许记录。
5. `禁止` 用前端隐藏/禁用按钮充当授权边界；后端接口仍必须鉴权。禁止将未验证 HTML 传给 `v-html` 或消息组件的 HTML 模式。

### 3.6 样式、主题与国际化

1. `MUST` DOM/CSS 颜色、表面、文字、边框、阴影使用 Element Plus CSS 变量或 `theme.css` 的语义 token。`utils/theme.ts:4-13` 规定 JS/Canvas 才允许用受控 hex fallback。
2. `MUST` 新增图表颜色通过 `getThemeColors()` / `getThemeSurfaceColors()` 或等价 token 解析，以支持亮暗主题；禁止组件内写独立亮色调色盘。
3. `MUST` 保持一套主题状态：`theme` store 同步 `mode`、storage、`data-theme`、`html.dark`（`stores/theme.ts:12-55`）。不得新增第二个主题开关或局部暗色 class。
4. `SHOULD` 用 class 和 scoped CSS 表达稳定布局；业务页面新增大量 inline style 时应先判断是否应归入组件 CSS、页面 CSS 或公共 token。单次尺寸/动态进度宽度等可保留 inline style。
5. `禁止` 在业务 CSS 新增硬编码语义 hex、渐变或阴影以绕开 token。终端、Canvas、外部内容对比度等确有技术边界时，必须说明并使用主题 fallback。
6. `MUST` 新增面向用户的稳定文案以中文为默认，并使用权威领域术语。项目虽注册了 `vue-i18n`，现有页面尚未使用 `$t`；在未完成全量迁移前，不得对单个新页面引入局部翻译体系。若启动全局 i18n 改造，必须另立设计并全链路迁移。

### 3.7 测试与代码评审

1. `MUST` 每个行为变更至少有一种真实行为测试：用户 DOM 交互、父级 listener、API 参数、路由结果或状态变化。源码字符串断言只能覆盖无法在测试环境可靠表达的 CSS/模板契约，不能替代交互测试。
2. `MUST` 在 Vue 状态赋值后等待 `nextTick()` 或 `flushPromises()` 再断言 DOM；不得依赖 `wrapper.vm` 访问 `<script setup>` 私有实现来替代用户交互。
3. `MUST` 复用 `src/test-setup.ts` 的可交互 Element Plus 全局 stub；新增组件 API 时先补齐其真实交互语义，再修改受影响 spec。
4. `MUST` 图表同时有数据转换单测和浏览器渲染验收；Vitest 不足以证明 Canvas/ECharts 实际展示。
5. `MUST` 修改 Vue SFC 模板后运行至少覆盖该组件的 Vitest；修改共享布局、主题、路由、API client、store、公共组件或全局 CSS 后运行完整 `pnpm test:run` 与 `pnpm typecheck`。
6. `MUST` 使用 `pnpm`，不使用 npm 修改 lockfile。新增依赖须说明现有依赖不能解决的原因、体积影响、许可和卸载策略。
7. `禁止` 使用恒真断言、`catch` 吞没 `expect`、硬等待、只检查源码包含字符串而声称覆盖交互。禁止把既有失败数量下降当作通过结论。

## 4. UI/UX 设计规范

### 4.1 页面信息架构

页面只能从以下三种模板中选择，特殊页面在设计中说明例外：

| 模板 | 适用范围 | 固定信息顺序 |
|---|---|---|
| 资源列表 | 节点、边缘设备、通道、配置、固件、逻辑设备 | 页面标题 -> 筛选与操作 -> 范围明确的统计（可选）-> 列表/表格 -> 分页或空状态 |
| 资源详情 | 节点、边缘设备及设备专属详情 | 返回与实体身份/状态/操作 -> 概览 -> 领域分区 -> 历史/日志/明细 |
| 数据分析 | 仪表盘、数据面板、系统监控 | 页面标题 -> 对象与时间筛选 -> KPI -> 图表 -> 可追溯明细 |

1. `MUST` 使用页面标题或等价的清晰标题；主内容区由 `MainLayout` 统一提供外层空间，页面不得再无理由叠加同级大留白。
2. `MUST` 详情页标题优先使用用户可识别的实体名称，次级位置再显示型号、ID 或技术标识。面包屑至少表达“列表 -> 当前实体”。
3. `MUST` 页面首屏只保留当前任务所需内容。不可把同一事实在页面级空态、卡片空态、表格空态重复呈现。
4. `SHOULD` 顶部每个上下文最多一个实心 primary 主操作；其余使用次操作、文本按钮、图标工具或更多菜单。
5. `禁止` 在页面区段之间嵌套“折叠面板 -> 卡片标题 -> 灰面板 -> 行卡片”等多层容器。默认视觉层级不超过两层；高密度资源控制采用分组标题 + 行列表。

### 4.2 视觉 token 与排版

1. `MUST` 颜色遵循语义：primary 为主要确认与进入；success 为成功/正常；warning 为需关注或占用；danger 仅用于错误与破坏性动作；info 为离线、未知或中性状态。LOW、OFF、停止、未选中不得使用 danger。
2. `MUST` 状态同时使用文字和颜色；图标可作为第三重表达，不能只用颜色或红绿圆点。
3. `MUST` 保持目前的紧凑运维密度：内容卡圆角默认不超过 8px；现有统计卡和设备指标卡作为固定例外可用 12px。页面区段不应设计为悬浮大卡。
4. `MUST` 文字层级清晰：页面标题、区段标题、数值、标签、辅助说明各有稳定角色。紧凑面板中不得使用 hero 级大字；数字单位紧跟数值但视觉降级。
5. `MUST` 中文文本防逐字竖排：标签使用 `word-break: keep-all`，必要时缩短移动端文案或限制为两行；关键数值不得因 `ellipsis` 被截断。
6. `SHOULD` 术语中英混排时提供中文解释、tooltip 或统一术语映射；技术标识（DMA、UART、ID、协议字段）可保留原文但不应成为普通用户唯一可见信息。
7. `禁止` 新增装饰性渐变球、无语义 bokeh、超大营销式 hero、过度圆角或同色系一色到底的界面。

### 4.3 组件与操作模式

#### 统计卡

1. `MUST` 复用 `StatCard` 或与其等价的语义契约；统计值必须标明范围，例如“本页”“当前筛选”“全局”。
2. `MUST` 统计卡只有存在明确钻取结果时可点击；点击卡按键盘可操作，参照 `StatCard.vue:2-53`。
3. `MUST` 页面顶部恰有四个简短 KPI 时，移动端 <=768px 采用单行四列紧凑卡：`repeat(4, minmax(0, 1fr))`、gap 8px、图标 22px、数值 16px、标签 10px。长标签使用 `mobile-label` 简写，但读屏保留全称。
4. `SHOULD` 非四项或不可读的 KPI 使用二列或单列特例，并在页面 CSS 中说明信息容量原因；不得为坚持四列截断关键含义。

#### 表单与对话框

1. `MUST` 表单按任务分组，标签、校验错误、帮助文本与提交动作在同一阅读路径；窄屏标签改上置或单列，避免标签压缩输入框。
2. `MUST` 创建与编辑的交互模型分离：编辑不得展示或接受创建专属的节点、解析器、设备型号等字段，除非后端确实支持修改且设计明确。
3. `MUST` 弹窗使用全局 `max-width: 92vw` 兜底（`theme.css:369-373`），弹窗内容超高时主体可滚动、footer 保持可见。Teleport 的弹窗样式必须是全局选择器或 Element Plus 变量，不能依赖 scoped CSS 穿透。
4. `MUST` 危险确认使用 danger 确认按钮；默认焦点和文案应避免诱导性确认。
5. `SHOULD` 复杂创建流程用步骤向导，逐步校验并说明无法继续的前置条件；简单编辑直接显示表单，不复用整套向导。

#### 表格、列表与资源行

1. `MUST` 宽表格在 <=768px 用 `.mobile-table-wrapper` 和 `.mobile-table-hint` 包裹，或经设计评审转换为卡片/行列表。当前全局模式见 `theme.css:375-401`。
2. `MUST` 重要操作列保持可达；固定操作列、最小宽度、横向滚动提示和分页换行共同验收，不能只确认没有页面级 overflow。
3. `MUST` 行内有 Switch、Slider、状态和多个操作的资源管理界面使用纵向行列表，不强行塞入 `el-table`。参照 [GPIO与PWM界面重设计规格.md](../设计/GPIO与PWM界面重设计规格.md) 的“分组标题 + 行列表 + 行内反馈”模式。
4. `MUST` 行操作请求中显示 `aria-busy` 或 loading，并只锁相关控件；离线行内容仍可读，只禁用不可执行操作。
5. `SHOULD` 长 ID、设备名、原始帧或地址可以截断，但需保留复制、tooltip 或可展开路径；关键值不应无提示地省略。

#### 状态、空态、加载与错误

1. `MUST` 使用 `EmptyState` 的 `initial`、`filtered`、`empty`、`error`、`permission` 语义，或保持等价区分。`EmptyState.vue:45-66` 为现有 props 契约。
2. `MUST` 首次加载显示与内容结构相近的 skeleton；刷新已有数据时保留旧数据，仅在触发控件显示 loading，避免闪回空态。
3. `MUST` 离线、占用、未知、失败均不是空状态：离线说明数据时效和操作限制；占用说明占用方；未知不得默认成正常；失败提供重试或退化路径。
4. `MUST` 数值、状态和时间逻辑自洽。页面显示“上线时间 + 在线时长”时，二者必须与当前时间和在线状态相容；“共 N 条”必须与实际渲染记录一致。

### 4.4 响应式与触控

1. `MUST` 先保证 360px 宽可完成核心操作，再增强到 768px、1024px 和桌面。响应式仅用结构切换、流式 grid、flex-wrap、Element Plus 栅格或必要断点解决，不靠缩小到不可读。
2. `MUST` 断点以 480、768、1024、1200 为项目既有体系；新增自定义断点必须有现有断点无法表达的布局依据。CSS 自定义变量不能用于 `@media` 条件，断点值需与 `useResponsive.ts:4-11` 和 `theme.css:8-13` 同步。
3. `MUST` 纯视觉布局优先 CSS；JS `useResponsive` 仅用于侧栏/抽屉等结构或数据逻辑确实不同的场景。
4. `MUST` <=768px 输入控件字体至少 16px，以避免 iOS Safari 聚焦缩放（`App.vue:60-68`）。
5. `MUST` 移动端图标按钮和 Switch/Slider 的实际可点击区域不小于 44x44px；仅在极高密度、非主要任务的工具栏中可降到 36px，并保证相邻间距与可访问名称。
6. `MUST` 页头在小屏允许标题与操作区换行；操作区不能把标题压至零宽或逐字竖排。多个详情动作应换行、收进更多菜单，或采用移动端专属操作排列。
7. `SHOULD` 在 `pointer: coarse` 环境增加紧凑控件的可点击区域与行间距；不以浏览器宽度单独推断输入方式。

### 4.5 深色主题、图表与数据表达

1. `MUST` 每次触及全局颜色、卡片、表格、弹窗、popover、终端或图表时，验证亮色与暗色；移动抽屉是历史高风险交叉区域，必须同时验证暗色小屏。
2. `MUST` 图表 tooltip、图例、网格线、文字、背景和系列色随主题变化。共享 `LineChart` 的改动需检查所有消费者，不能只在单一页面截图中通过。
3. `MUST` 数据比较只允许相同语义且相同单位的指标；图表空态说明缺的是数据、选择条件还是共同单位，不用零值伪造趋势。
4. `SHOULD` 高频实时数据做降采样、虚拟列表或显示上限，避免长时间打开页面无限增长；这一策略在数据层/组合式函数定义，视图只负责展示。

## 5. 验收与门禁

### 5.1 每次前端改动的最低门禁

| 改动范围 | 必须执行 |
|---|---|
| 任意 TypeScript/Vue 逻辑 | 受影响单测 + `pnpm typecheck` |
| 公共组件、全局样式、路由、API client、store、主题 | `pnpm test:run` + `pnpm typecheck` + `pnpm build` |
| CSS/响应式/交互视觉 | 上述静态门禁 + 浏览器/CDP 量化与截图复核 |
| 表单、删除、控制、OTA、通道或设备操作 | 行为测试 + API 参数/失败路径 + 浏览器实际交互或受限时 API 闭环 |
| 图表或实时数据 | 数据转换单测 + 运行时渲染检查；tooltip 用 ECharts 实例程序化触发验证 |

`make test` 与 `make lint` 是项目级收口门禁；如果历史基线存在失败，必须以同一工作区基线证明“零新增失败”，不能把未执行或既有失败表述为通过。

### 5.2 浏览器验证矩阵

默认视口：1440x900、1024x768、768x1024、390x844；对高风险窄屏补 360x800 或 480px。核心页面为仪表盘、节点列表/详情、边缘设备列表/详情、通道、数据面板、固件、配置、系统监控、个人设置和登录。

每个受影响页面至少检查：

1. 正确路由与关键标题存在，无错误边界和未捕获控制台异常。
2. `document.documentElement.scrollWidth <= clientWidth`，同时检查内部主滚动容器和表格横滚容器。
3. 标题、主要按钮、表单标签、统计卡数值与标签没有重叠、逐字竖排或无提示截断。
4. loading、empty、error、offline、disabled、success 至少覆盖变更涉及的状态。
5. 亮暗主题均可读；移动端抽屉、dialog、popover、table、分页和操作区可操作。
6. 视觉结论用 DOM 事实复核：`location.pathname`、`getComputedStyle`、`getBoundingClientRect`、`scrollWidth/clientWidth`。截图/视觉模型只作为发现问题的辅助证据。

### 5.3 评审清单

评审前必须逐项回答：

- 是否复用了现有 API、store、composable、状态组件与 token，而非复制实现？
- API 请求/响应、业务 ID、后端枚举和界面字段是否通过真实接口或类型确认？
- 选择变化、并发请求、卸载和会话过期会不会使旧结果回写？
- 创建与更新、单项与批量、桌面与移动、亮色与暗色路径是否对称？
- 是否新增了硬编码主题色、重复空态、危险操作直达、无原因禁用、仅颜色状态或无障碍缺口？
- 测试是否验证真实行为，而不是 `wrapper.vm`、源码字符串或等待时间？
- 是否更新与源码一致的设计、实现或验证文档？

## 7. 禁止的过度设计

以下内容没有明确产品驱动时不得纳入常规前端规范或作为功能交付前置：

1. 为每个组件建立完整 Design Token 子系统、Storybook、视觉快照平台或多套主题，而不先复用已有 `theme.css`、Element Plus 与 CDP 验收。
2. 因单用户后台假设未来多租户、工作流审批、国际化全面切换、微前端或可配置页面搭建器。
3. 为低频静态页面引入复杂状态机、全局缓存层、请求取消框架或动画系统；先用现有 composable、store 和明确的 generation guard。
4. 把所有表格一律卡片化、所有页面一律单列化或所有 KPI 一律四列化；应由信息容量、操作频率和可读性决定。
5. 为达成覆盖率数字删除有效测试、加入无意义断言，或对所有旧 `any` 做一次性大重写。应按 API/实时/控制等高风险边界渐进收敛。
6. 将审查发现全部升级为全局硬门禁。只有可自动判断、影响面明确且已经证明能防真实回归的规则，才进入强制门禁。

## 8. 维护方式

1. 新发现的跨页面模式先在本规范补充“规则 + 反例 + 验收方法”，再在后续功能中采用；不得只在单个页面留下隐性经验。
2. 若规范与当前代码不一致，先以源码和运行时事实确认，再更新本规范或建立带时限的整改项；不能以旧文档替代现状证据。
3. 修改本规范时同步更新 `docs/README.md` 的前端阅读路径和变更清单，并运行项目的文档链接检查。
