# 分区表列一致性 与 detached 分区 —— 运维手册

> 面向：运维 / 值班同学
> 起因：2026-11-07 生产事故 —— L3 rollup 每分钟报 `column "updated_at" of relation "telemetry_rollup_1m" does not exist`，rollup 表 0 行（L3 完全没工作）
> 关联代码：`backend/internal/datalifecycle/partition_columns.go`（列校正器）、`partition_ddl_model_gate_test.go`（源码门禁）

---

## 1. 这次事故是怎么发生的（60 秒版）

本仓的时序表在 PostgreSQL 上是**分区母表**，由裸 DDL 建（`partition_mgr.go` 的 `partitionParentDDL`），不走 GORM AutoMigrate。于是每张表有**两份列定义**：

| 来源 | 用在哪 |
|---|---|
| `partitionParentDDL`（裸 DDL） | **生产 PG** 建表 |
| `models.TelemetryXxx`（GORM 模型） | **SQLite 单测**（AutoMigrate）+ 读写代码 |

`telemetry_rollup_1m` 的 model 有 `UpdatedAt`，而裸 DDL 里漏了这一列。后果：

- 生产：写入 SQL 带 `updated_at` ⇒ 报 42703 ⇒ **每一分钟都失败**；
- 单测：AutoMigrate 从 model 反向建表 ⇒ 一定有该列 ⇒ **全绿**。

两条建表路径各自自洽，交叉点没人验 —— 这是「假绿」的典型形态。

## 2. 列一致性体检（每次升级后跑一次）

### 2.1 一键体检：四张分区表的列是否与代码预期一致

```sql
-- 期望结果：每张表都列出 4~7 列，且没有 missing_in_ddl 提示（见下面第 3 节比对方法）
SELECT table_name, column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN ('unified_data','device_data','telemetry_rollup_1m','telemetry_frame')
ORDER BY table_name, ordinal_position;
```

### 2.2 重点确认 `telemetry_rollup_1m.updated_at` 存在

```sql
SELECT count(*) AS has_updated_at
FROM information_schema.columns
WHERE table_schema='public' AND table_name='telemetry_rollup_1m' AND column_name='updated_at';
-- 期望 1；0 表示 L3 会继续报错
```

### 2.3 L3 是否真的在工作（最直接的判据）

```sql
SELECT count(*) AS rows_now, max(updated_at) AS last_write, now() AS now
FROM telemetry_rollup_1m;
-- 期望：rows_now 持续增长；last_write 在两分钟内
-- rows_now=0 或 last_write 长时间不前进 ⇒ L3 没在工作
```

## 3. 手工补列（列缺失时的止血）

### 3.1 通用形式

```sql
ALTER TABLE <表名> ADD COLUMN IF NOT EXISTS <列名> <类型/约束>;
```

**分区母表上这条会自动传播到全部分区**，不需要逐个分区补。实测（PG 18，母表 + 3 分区 + 已有数据）：

```
ALTER 前: partitions with updated_at = 0
ALTER TABLE
  t_prop             | 母表      | has_col=1
  t_prop_202610      | 分区 1    | has_col=1   ← 自动传播
  t_prop_202611      | 分区 2    | has_col=1   ← 自动传播
  t_prop_202612      | 分区 3    | has_col=1   ← 自动传播
存量行回填: updated_at IS NOT NULL = t   ← 自动取默认值 now()
```

原理：`ADD COLUMN` 在分区母表上是**元数据操作**（PG 11+ 带 DEFAULT 用 fast default，不重写数据页），通过继承自动传播给所有 ATTACH 的分区。

### 3.2 本次事故的具体语句（留档）

```sql
-- 止血
ALTER TABLE telemetry_rollup_1m
  ADD COLUMN IF NOT EXISTS updated_at TIMESTAMPTZ NOT NULL DEFAULT now();

-- 回滚（回滚后 L3 会重新开始报错，需同时回退服务版本）
ALTER TABLE telemetry_rollup_1m DROP COLUMN IF EXISTS updated_at;
```

### 3.3 校验补列真的生效

```sql
SELECT c.relname, count(*) FILTER (WHERE a.attname='updated_at') AS has_col
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
JOIN pg_attribute a ON a.attrelid = c.oid AND a.attnum > 0
WHERE n.nspname='public' AND c.relkind IN ('r','p')
  AND (c.relname='telemetry_rollup_1m' OR c.relname LIKE 'telemetry\_rollup\_1m\_%')
GROUP BY c.relname ORDER BY c.relname;
-- 期望：母表 + 全部分区，has_col 全为 1
```

## 4. detached 分区：检测与处置

### 4.1 什么是 detached 分区

分区可以被人为 `DETACH`（或迁移中断、早期手工维护）脱离母表。脱离后：

- 它**不再参与母表查询**（数据"消失"但不报错）；
- 母表 `ADD COLUMN` **不会**传播给它（传播走继承，它已不在继承树里）。

代码里的列校正器（`ensurePartitionParentColumns`）**刻意不遍历 detached 分区**，三条理由：

1. detached 分区对母表查询不可见，补列不会让任何读路径变好；
2. 盲目补列/重新 ATTACH 可能把一张**形状不对的旧表**挂回母表 —— 那是数据事故，比缺列严重得多，而代码无法判断那张表到底是什么；
3. 处置是明确的运维动作（见 4.3），不该由启动流程自动决定。

### 4.2 检测 SQL（怀疑有 detached 分区时跑）

```sql
-- 找出名字符合分区命名约定、但没有父表的分区
SELECT c.relname AS orphan_relation,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size,
       (SELECT count(*) FROM pg_attribute a
         WHERE a.attrelid = c.oid AND a.attnum > 0 AND NOT a.attisdropped) AS col_count
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind = 'r'
  AND c.relname ~ '^(unified_data|device_data|telemetry_rollup_1m|telemetry_frame)_[0-9]{6}$'
  AND NOT EXISTS (SELECT 1 FROM pg_inherits i WHERE i.inhrelid = c.oid);
```

**空结果 = 正常**。有结果就进入 4.3。

### 4.3 三种判定与处置

| 情况 | 判据 | 处置 |
|---|---|---|
| **A. 废弃残留** | `col_count` 与母表当前列数一致或只有旧列；`size` 只有几 MB；母表里 `SELECT count(*) FROM ONLY <母表> WHERE ...` 无对应数据 | `DROP TABLE <orphan_relation>;`（先 `\d` 看清列，确认是历史残留） |
| **B. 需要 ATTACH 回来** | 该分区的月份在母表的 `pg_inherits` 里**缺失**（即母表没有那个月的数据），且列形状与母表一致 | 先补列到与母表一致，再 `ALTER TABLE <母表> ATTACH PARTITION <orphan> FOR VALUES FROM (...) TO (...);` —— ATTACH 会**校验形状**，不一致会直接报错（这是保护，不是障碍） |
| **C. 不确定** | 无法判断来源 | **不要动。** 先取证（`\d+`、行数、最早/最晚时间、大小），必要时先 `pg_dump -t <orphan>` 备份再决定。**绝不要盲目 DROP 或 ATTACH。** |

**红线**：不要为了让体检"全绿"而去 DROP 一个你不认识的表。分区命名是约定，不是所有权证明。

## 5. 为什么现在不用怕同类问题（两道防线）

### 5.1 开发期：源码门禁 `TestPartitionDDLMatchesModels`

位置：`backend/internal/datalifecycle/partition_ddl_model_gate_test.go`

它**不需要 PG、不依赖任何环境变量**，常规 `go test ./...` 就会跑：

- 反射读每个 model 的 GORM column tag；
- 解析 `partitionParentDDL` 的列清单；
- **双向**断言差异：model 有而 DDL 没有 ⇒ 生产必炸；DDL 有而 model 没有 ⇒ 读回来对不上。

覆盖四张分区表，并有一条元门禁（`TestPartitionDDLModelPairsCoversAllRegisteredTables`）确保**新加分区表忘记登记**也会红。

### 5.2 运行期：列校正器 `ensurePartitionParentColumns`

位置：`backend/internal/datalifecycle/partition_columns.go`，挂在启动的 `finalizePartitionParentIndexes` 里。

- 真源 = `partitionParentDDL`（与建表同一份模板，不引第二处列清单）；
- 对比 `information_schema.columns`，缺失列自动 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`；
- **失败只 Warn 不阻断启动**（补列修的是 schema 漂移，后果是某张表写不进去，不是服务不可用；挡启动等于把小故障放大成停机）。

存量生产表就在这一步被自动修好 —— 即使运维忘了手工 ALTER，**重启服务也会自愈**。

## 6. 值班速查卡

| 症状 | 先查 | 判据 |
|---|---|---|
| L3 图表空白 / rollup 表 0 行 | 日志有无 `column ... does not exist` | 有 ⇒ 列缺失（第 3 节补列）；无 ⇒ 查 `max(updated_at)` 是否前进 |
| 某个月的数据"消失" | 第 4.2 节 detached 分区检测 SQL | 有孤儿关系 ⇒ 按 4.3 处置 |
| 升级后启动慢 | 日志有无 `creating missing parent index` | 首次升级补索引是预期行为（分钟级），见 `ensurePartitionParentIndexes` 注释 |
| 启动日志有 `reconcile partitioned parent columns failed` | 该 Warn 的 `error` 字段 | 说明补列没成功，按第 3 节手工补 |
