# 数据库备份与恢复指南

> 适用范围：EHomeSystem 统一 PostgreSQL（docker compose 服务 `postgres`，容器 `ehome-postgres`）。
> 本文档所有命令均已在真实环境实测通过（实测基线：生产库 46 表 / 30 分区片 / 188 索引 / 0 视图，约 904 MB，`pg_dump (PostgreSQL) 18.4`）。

## 1. 备份

### 一键备份（推荐）

```bash
cd /path/to/EHomeSystem
make backup
```

或直接调用脚本：

```bash
bash scripts/backup_pg.sh
# 可覆盖变量：
BACKUP_DIR=/data/pgbackups BACKUP_KEEP=14 bash scripts/backup_pg.sh
```

脚本内部执行（生产库只读，不写任何数据）：

```bash
docker compose exec -T postgres pg_dump -U ehome -d ehome \
    --format=custom --compress=6 > backups/ehome_YYYYmmdd_HHMMSS.dump
```

每次备份产出三个文件（`backups/` 已被 .gitignore 忽略，不会入库）：

| 文件 | 内容 |
|---|---|
| `ehome_<时间戳>.dump` | custom 格式 dump（gzip 压缩 level 6） |
| `ehome_<时间戳>.dump.sha256` | sha256 校验和 |
| `ehome_<时间戳>.dump.meta` | 时间、大小、pg_dump 版本、TOC 条目数、耗时 |

### 自校验机制

备份完成后脚本立即执行 `pg_restore --list` 读取 TOC（目录）。**列不出 TOC 的 dump 视为损坏**，脚本删除半成品并以非零码退出——防止截断文件（磁盘满、管道中断）被当成"好备份"。基线参考：2026-09-12 实测 TOC 共 **445 个条目**，meta 中的 `toc_entries` 应与该量级一致（schema 变更后随之更新）。

### 保留策略

- 默认 `BACKUP_KEEP=7`：只保留最近 7 个 `ehome_*.dump`（按 mtime），超出的最旧备份连同其 `.meta`/`.sha256` 一起删除，**删除前逐个打印文件名**。
- 定时备份示例（crontab，每天 03:30）：

```cron
30 3 * * * cd /home/sun/workspace/EHomeSystem && make backup >> /var/log/ehome_backup.log 2>&1
```

## 2. 恢复

```bash
# 用法
bash scripts/restore_pg.sh <dump_file> <target_db> [--drop] [--force]
# 经 Make 透传
make restore DUMP=backups/ehome_20260912_033000.dump DB=ehome_restore_drill
```

- 目标库不存在则自动创建；存在时**必须**加 `--drop` 才会删库重建（`DROP DATABASE ... WITH (FORCE)`）。
- 恢复命令固定为 `pg_restore --no-owner --no-privileges`（跨环境恢复不携带原库属主/权限）。
- 恢复完成后自动打印表数 / 分区片数 / 索引数，供与生产基准（46 / 30 / 188）对照。

### ⚠️ 安全护栏

- **目标库为生产库 `ehome` 时必须额外传 `--force`**，否则脚本直接拒绝并非零退出。
- 任何恢复演练一律使用临时库名（如 `ehome_restore_drill`），演练后清理：

```bash
docker exec ehome-postgres psql -U ehome -d postgres \
    -c "DROP DATABASE ehome_restore_drill;"
```

- 脚本对非生产目标会明确打印「恢复演练，生产库未受影响」。

## 3. 恢复演练标准步骤（建议每季度执行一次）

```bash
cd /path/to/EHomeSystem

# 1) 备份
make backup
DUMP=$(ls -t backups/ehome_*.dump | head -1)

# 2) 校验文件完整性（对照 .meta 里的 sha256 / 大小）
( cd backups && sha256sum -c "$(basename $DUMP).sha256" )

# 3) 恢复到临时库
bash scripts/restore_pg.sh "$DUMP" ehome_restore_drill

# 4) 核对统计：应输出 表 46 / 分区片 30 / 索引 188
# 5) 抽样查询（见下方清单第 4 条）
docker exec ehome-postgres psql -U ehome -d ehome_restore_drill \
    -c "SELECT count(*) FROM users;"

# 6) 清理临时库
docker exec ehome-postgres psql -U ehome -d postgres \
    -c "DROP DATABASE ehome_restore_drill;"

# 7) 确认生产库未受影响
docker exec ehome-postgres psql -U ehome -d ehome \
    -t -c "SELECT count(*) FROM pg_tables WHERE schemaname='public';"   # 应为 46
```

## 4. 「备份未经验证不可信」核对清单

一个备份只有**完成一次真实恢复**才算备份。定期演练时逐项核对：

- [ ] **TOC 可读**：`docker compose exec -T postgres pg_restore --list < 备份文件 | head` 正常列出条目，且条目数与 `.meta` 中 `toc_entries` 一致（实测基线 445）。
- [ ] **表数对照**：恢复到临时库后 `SELECT count(*) FROM pg_tables WHERE schemaname='public';` = **46**（与生产一致）。
- [ ] **分区片数对照**：`SELECT count(*) FROM pg_inherits i JOIN pg_class c ON c.oid=i.inhrelid JOIN pg_namespace n ON n.oid=c.relnamespace WHERE n.nspname='public';` = **30**（分区表结构完整恢复）。
- [ ] **抽样查询**：对核心表（如 `users` 及最大的时序分区表）各跑一条 `count(*)` / 最近记录查询，与生产库同日结果一致。
- [ ] **sha256 校验通过**：`sha256sum -c xxx.dump.sha256`。
- [ ] **备份异地/异卷**：`backups/` 与数据卷 `ehomesystem_ehome-pgdata` 不在同一故障域时才有意义。
- [ ] **演练收尾**：已 DROP 临时库，且生产库表数复核仍为 46。

## 5. 故障排查

| 症状 | 处理 |
|---|---|
| `无法连接 postgres 容器` | `make infra` 或 `docker compose up -d postgres`；确认容器名 `ehome-postgres` 健康 |
| pg_dump 中途失败、半成品被删 | 查看退出前错误；多为磁盘不足（`df -h`）或容器 OOM（`docker inspect ehome-postgres`） |
| 恢复报大量 `already exists` | 目标库非空且未加 `--drop`；临时库建议直接换新库名或加 `--drop` |
| TOC 条目数与基线偏差大 | 检查是否有大版本迁移/表增删；先 `git log backend/migrations`（由主仓库流程处理）确认 schema 变更，再更新本文档基准 |
