# 本仓开发环境事实（2026-09-13 固化）

> **用途**: 派发给执行者/子代理前先读本文件，避免重复踩环境坑。
> **来源**: 全部由主控或执行者**实测**得出，不是推测。

## 1. Go 的 PATH（最容易误报的一处）

Go **不在默认 PATH** 中。两个可用入口指向同一个工具链：

| 路径 | 说明 |
|---|---|
| `/snap/bin/go` | **标准入口**（snap 维护的 shim，推荐） |
| `/snap/go/11262/bin/go` | 版本化内部路径（随 snap 更新可能失效） |

两者实测均为 `go version go1.26.7 linux/amd64`。

**后果**：若命令里不带 PATH，后端门禁全部返回 `exit 127 / bash: go: command not found`，
执行者会**误报「后端门禁失败」** —— 本轮已实际发生过（一位执行者在报告里把它列为"环境事实"）。

**统一写法**：
```bash
export PATH=/snap/bin:/home/sun/.local/share/pnpm/bin:$PATH
export HOME=/home/sun
```

## 2. 后端构建必须带 -buildvcs=false

`go build ./...` 在无 .git 元数据的环境会报 VCS 错误。统一用：
```bash
go build -buildvcs=false ./...
```

## 5.1 并发跑测试会互相干扰（已实测两次，**不是缺陷**）

多个执行者同时跑 `go test ./...` 时，`internal/api` 会**间歇性 FAIL**，
但**单独重跑立刻全绿**（连续 3 次通过）。

**原因**：该包的测试共享进程级资源（SQLite 内存/临时库、端口、全局 registry），
并发执行时互相踩踏。

**判据（不要误报为缺陷）**：
1. 看失败是否**在同一包内跳变**、用例名与你的改动无关；
2. **单独重跑 2-3 次** —— 全绿即 flake；
3. 检查是否有其他 `go test` 进程在跑：`pgrep -af 'go test|api.test'`。

**纪律**：执行者在**验证阶段**应避免与他人并发跑全量；
若必须并发，请在报告里标注"该次结果可能受并发干扰"，并在收尾时单独复跑确认。

> 同类现象也出现在前端：多个任务并发 `pnpm build` 会让 dist 处于"别人改到一半"的状态
> （曾导致全站白屏 `Cannot access '$' before initialization`）。
> **正解：由主控统一构建一次并广播 entry hash**，而不是各自重建。

**需要新后端行为时**：自己另起一个端口（如 8099）连同一个库，用完杀掉自己的，
**不要重启 8082**（它是主控持有的共享实例）。

## 5.2 沙箱的执行环境：`/tmp` 每次 bash 调用都**不持久**（2026-11-08 实测）

这条是 5.1 的**加强版**：5.1 说「并发会互相干扰」，本节说「**用 `/tmp` 做的防并发机制 100% 失效**」。

### 事实

```
调用 A：  echo marker > /tmp/probe.txt            => 写入成功
          grep ' /tmp ' /proc/mounts              => tmpfs /tmp tmpfs rw,...

调用 B：  ls /tmp/probe.txt                       => **No such file or directory**
          ls /tmp                                 => 空
```

    => **agent 沙箱每次 bash 调用都挂一个全新的私有 tmpfs 到 /tmp。**
       文件在调用之间不持久，而 `/proc/mounts` 看起来「就是 /tmp」，
       所以这个事实**不会自己暴露** —— 必须用「跨调用写一个文件再读」才能测出来。

### 后果：所有「锁文件放 /tmp」的跨调用互斥机制**静默失效**

实例（2026-11-08）：`scripts/check_all.sh` 用 `flock` 防并发，锁路径是
`${TMPDIR:-/tmp}/ehome_check_all.lock`。

```
进程 1 => 在自己的 /tmp 里创建并获取锁
进程 2 => 在自己的 /tmp 里创建并获取锁（因为看不到进程 1 的那个）
=> **互斥从不发生，而日志里一切正常**
```

而它**骗过了三重复核**：实现有、注释写得对、单机用「同进程 fork 两个子 shell」测过能互斥。
同进程 fork 共享 `/tmp`，而真实场景是两次**独立的 bash 调用**，各有私有 `/tmp`。

### 正确位置：`git rev-parse --path-format=absolute --git-common-dir`

```bash
LOCK="$(git rev-parse --path-format=absolute --git-common-dir)/some.lock"
```

实测三条（都是跨**独立调用**验的，不是同进程 fork）：

| 性质 | 结果 |
|---|---|
| 跨调用可见（holder 持锁时别人被拒） | ✓ |
| 不产生未跟踪文件（`.git/` 内不进 `git status`） | ✓（实测 0 行） |
| 跨 worktree 共享（4 个 worktree 的 common-dir 都指向同一个 `.git`） | ✓ |

⚠ 必须加 `--path-format=absolute`：裸 `--git-common-dir` 在仓库根返回 `.git`、
在 `backend/` 返回 `../.git` —— 拼出的**字符串**不同（指向同一 inode，所以 flock 仍有效），
但日志里的锁路径会不一致，且任何「按路径字符串比对」的逻辑会误判。
`--path-format` 需要 git >= 2.31。

### 还有一个陷阱：锁创建失败会被误报成「锁被占用」

```bash
exec 9>"$LOCK"        # 目录不存在 / 无权限 => 失败，fd 9 未打开
if ! flock -n 9;      # => 非 0（bad file descriptor）
then  echo "另一轮在跑"   # ← 误报：实际是「锁坏了」
fi
```

两者处置完全不同：锁被占用等一会儿就行，锁创建失败等多久都没用。
**正确写法是先单独检查 `exec` 的返回值**：

```bash
if ! exec 9>"$LOCK"; then
    echo " 锁文件创建失败: $LOCK（不是「另一轮在跑」—— 查目录权限）" >&2
    exit 2
fi
if ! flock -n 9; then ... "另一轮在跑" ... fi
```

### 判据

**验证一个跨进程/跨调用机制时，必须用「真正独立的进程/调用」去验，
不能用同一进程内 fork** —— 后者共享了真实场景下不共享的资源（这里共享的是 `/tmp`）。

这个形态今天出现过三次（见 `docs/验证/测试判据反模式-2026-11-07.md` 反模式 14）：
验 `HasTable` 用普通表（验错对象）、验 rollup 用 on-grid 值（验不到量化误差）、
验 flock 用同进程 fork（环境不对）。
**共同形态是「验证环境 ≠ 运行环境」，而它的危险在于验证会通过。**

### 临时替代方案（改动脚本之前用）

需要一段「无并发窗口」但不想改脚本时，用工作区内的 flag 而不是 `/tmp` 的锁：

```bash
FLAG="$(git rev-parse --path-format=absolute --git-common-dir)/test_running.flag"
touch "$FLAG"     # 跑之前
# ... 跑测试 ...
rm -f "$FLAG"     # 跑之后
```

其他人只读检查 `$FLAG` 是否存在（不启动任何东西），存在则不跑。
不是完整互斥，但对「一次几分钟的人工窗口」够用，且**不需要改任何脚本**。

## 7. 派发纪律（血泪总结）

1. **禁止执行者运行 git 命令**（提交由主控统一做）。
2. **同一文件绝不允许两个执行者并发修改** —— 本仓有过"互相覆盖"事故。派发前先做**写者矩阵**核对文件集合是否互斥。
3. **通知执行者：`dist` 是共享构建产物** —— 并发 build 会让 DOM 实测看到"别人改到一半"的状态。
4. **要求变异自证**：任何修复都要能回答"把修复回退，哪个测试会变红"。看不到红点的断言不守护任何不变量。
5. **"计数为 0"必须能回答分母** —— 一个恒为 0 的统计量既可能意味着"没问题"，也可能意味着"选择器什么都没扫到"（本轮在探针上犯过这两个方向的错）。
