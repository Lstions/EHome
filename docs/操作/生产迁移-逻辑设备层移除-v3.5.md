## 一、这次迁移做什么

逻辑设备（LogicalDevice）概念层被整体移除。数据层动作：

| 对象 | 动作 | 生产实测规模（2026-10-23） |
|---|---|---|
| 表 `logical_devices` | DROP | 16 行 / 72 kB |
| 表 `merge_jobs` | DROP | 0 行 / 24 kB |
| 表 `backfill_jobs` | DROP | 2 行 / 40 kB |
| 列 `edge_devices.logical_device_id` + 索引 | DROP | 10 行 / 224 kB |
| 列 `unified_data.logical_device_id` + 每个分区 2 个复合索引 | DROP | 父表 0 B；202610 分区数据 8254 MB，其中两个 logical 索引 2167 MB + 463 MB |
| 列 `device_data.logical_device_id` + 每个分区 2 个索引 | DROP | 同上量级 |
| 列 `data_sources.device_id` + 2 个索引 | DROP | 71 行 / 304 kB |
| 索引 `ux_ds_one_active` | 按新组键 `(edge_device_id, category)` 重建 | — |
| 列 `edge_devices.data_purge_requested` | 新增（默认 false） | — |

**数据零丢失**：`unified_data` / `device_data` / `edge_devices` 的行都不动，只删「归属」列。历史数据在迁移后**全部可读** —— 这正是移除逻辑层的目的。

## 二、执行前检查（必须逐条确认）

```bash
# 1) 备份（必须先做，且要验证备份可读）
ssh <prod> 'docker exec ehome-prod-postgres pg_dump -U ehome -d ehome -Fc' > ehome-pre-v3.5-$(date +%F).dump
pg_restore -l ehome-pre-v3.5-*.dump | head    # 确认目录可读

# 2) 确认没有未完成的合并任务（有则会随 merge_jobs 一起消失）
docker exec ehome-prod-postgres psql -U ehome -d ehome -c \
  "select count(*) from merge_jobs where status='pending';"   # 期望 0

# 3) 确认 purge 没有在途请求（否则删数据意图会丢失）
docker exec ehome-prod-postgres psql -U ehome -d ehome -c \
  "select count(*) from logical_devices where purge_requested;"  # 期望 0

# 4) 记录迁移前基线（迁移后用同样的数对比）
docker exec ehome-prod-postgres psql -U ehome -d ehome -c \
  "select (select count(*) from unified_data) u, (select count(*) from device_data) d,
          (select count(*) from edge_devices) e, (select count(*) from data_sources) ds;"
```

若第 2 或第 3 条不为 0：**停下来**，先让那些任务跑完或确认可丢弃，再继续。

## 三、执行步骤

```bash
# 1) 停旧容器（写入停止）
ssh <prod> 'docker stop ehome-prod-web'

# 2) 拉新镜像（含 v3.5 代码）
ssh <prod> 'docker pull <registry>/ehome:v3.5'   # 或按现有发布流程

# 3) 【推荐】先用 ehomectl 单独跑数据层退役
#    与起容器时 AutoMigrate 自动跑的是同一段代码，但它把 DDL 从启动流程里
#    解耦：可以在停写后单独观察、单独重试。
ssh <prod> 'docker run --rm --network host \
  -e EHOME_DB_HOST=... -e EHOME_DB_NAME=ehome -e EHOME_DB_USER=ehome -e EHOME_DB_PASSWORD=... \
  <registry>/ehome:v3.5 ehomectl retire-logical-device'

# 4) 起新容器
ssh <prod> 'docker start ehome-prod-web'   # 新镜像
```

**预计耗时**：`unified_data_202610` 上有 2 个 logical 索引（2167 MB + 463 MB）要 DROP。
DROP INDEX 是元数据操作 + 文件删除，通常秒级到十几秒；`DROP COLUMN` 本身也是元数据操作
（PG 11+ 不再重写整表）。**总时间预计 < 2 分钟**，但请在维护窗口内做（`ALTER TABLE`
需要短暂 ACCESS EXCLUSIVE 锁，会阻塞该表的读写）。

## 五、回滚

**结构回滚不可行**（DROP COLUMN 不可逆，但也没有数据需要恢复 —— 被删的都是归属标记，真数据全在）。若新版本有问题：

```bash
ssh <prod> 'docker stop ehome-prod-web'
ssh <prod> 'docker run ... <registry>/ehome:<上一个 tag>'
```

但**旧镜像会坏**：它的 model 里有 `LogicalDevice`，AutoMigrate 会把 `logical_devices`
表**重建出来**（空表），随后所有涉及 `logical_device_id` 列的查询都会报 `column does not exist`。所以：

> **回滚 = 从第二节的 pg_dump 恢复整个库 + 回旧镜像。**
> 这是本次迁移的**唯一**回滚路径，也是为什么第二节第 1 步是硬要求。

## 六、已知的生产现状（迁移后仍然是问题，但不再是逻辑设备的锅）

1. **孤儿历史 292 万行**：`unified_data.device_id=2` 有 2,923,306 行，但 `edge_devices`
   里没有 id=2（该行早被硬删）。迁移后这些数据**依然无 API 可读**，retention 依然会按
   90 天窗口硬删它们（2026-12-31 起）。迁移**不解决**这个问题，但现在有了解法：
   `POST /edge-devices/:id/merge-history {"source_ids":[2]}` 可以把它们并到任意存活设备
   （如 14「bms」）名下，从此可读、可查、可保留。**建议在 2026-12-31 之前处理**，
   否则 292 万行历史会被静默删除。

2. **`device_data.device_id=0` 的 171 万行**：`DBPersistConsumer` 写的原始帧审计行，
   不归属任何设备（设计如此：三类不可解析事件只有它会写）。它们不受本次迁移影响，
   也不属于任何设备的保留期范围 —— 这是已知的、独立的清理议题。

3. **5 个逻辑设备只有 1 台还有存活实例**：迁移后不再是问题（身份层没了，数据直接挂在
   device_id 上），但上面第 1 条的孤儿数据仍在。

```bash

  -e EHOME_DB_HOST=127.0.0.1 -e EHOME_DB_NAME=ehome -e EHOME_DB_USER=ehome ... \
  --entrypoint /app/ehomectl ehome-new:lv-removal-dirty retire-logical-device

docker rename ehome-prod-web ehome-prod-web-prev
# 4) 用新镜像重建容器（env 与旧容器逐行 diff 确认一致）
docker create --name ehome-prod-web --network ehomesystem_ehome-internal \
  --network-alias ehome --restart unless-stopped -p 18090:8080 -p 8443:8443 ... \
  ehome-new:lv-removal-dirty

```

**踩到的坑**：网络名是 `ehomesystem_ehome-internal`（不是 `ehomesystem_default`），
且旧容器在该网络上有别名 `ehome`（postgres 靠这个别名解析）。重建时必须一起带上
`--network-alias ehome`，否则容器起不来（实测报 `network not found`）。
