# 老数据迁移到帧表（长期保留）—— 分析报告与实施契约（2026-11-07）

<div align="left">（用户需求：分析已有老数据如何完成迁移，在更新应用启动时做；所有数据要长期保留）</div>

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| **能否无损迁移** | **能**。全库 72,695,394 行扫描：非整数码点 0 行、越界 5 行（见 §2） |

## 2. 无损性验证（决定性证据）

### 2.1 判定方法

对全库每一行按 `spec.go` 的 (Min, Step, Bits) 算：

```sql
-- 非整数码点 = 量化必然有损
abs((value-Min)/Step - round(((value-Min)/Step)::numeric)::float8) > 1e-6
-- 越界 = 会被 clamped（真实精度损失）
(value-Min)/Step < 0  OR  (value-Min)/Step > 2^Bits-1
```

### 2.2 结果（72.7M 行全扫描）

| 字段族 | 非整数码点 | 越界 |
|---|---:|---:|
| cell_voltage_* | **0** | 0 |
| temperature_* / *_temp | **0** | 0 |
| current / total_voltage / rsoc / cycle_count / fet_status / protection_status | **0** | 0 |
| *_frequency / *_energy / alarm_* / fan*_* | **0** | 0 |
| Fallback 字段（19 个未登记字段） | **0** | 0 |
| **battery_voltage** | **0** | **5** ⚠ |

**唯一问题**：`battery_voltage` 有 5 行 = **1,000,000,000,000**（1e12），
集中在 2026-10-19 08:53~08:55（逆变器解析器一次已知缺陷，历史数据）。
该字段 spec 量程 0~204.7 V ⇒ 这 5 行会被 clamp，**有损**。

**处置建议**：迁移时把原始 value 写进帧表的 `raw` 列并计数 —— 既保住「长期保留」的承诺，
又不阻塞迁移。预期只占 5 × 几十字节。（另两个选项：直接丢弃这 5 行 / 篡改成邻近值，均不推荐）

### 2.3 精度实测支撑

- 全库所有值都在 **3 位小数内**（`abs(value - round(value,3)) > 1e-9` 的行数 = 0）
- 每个字段的 `unit` **唯一**（跨设备同名不同单位 = 0 例）⇒ 量化规格可按字段名全局套用
- `cell_voltage_*` 实测两位小数（3.25/3.26），spec 步长 1 mV ⇒ 无损
- `temperature_*` 两位小数，spec 步长 0.01 ℃ ⇒ 无损

## 4. 启动期迁移设计

### 4.1 为什么必须「可中断续跑的增量回填」

现有 `MigrateTableToPartitioned` 是同步阻塞 + 失败 Fatal。但老数据回填：
- 3.42 M 帧，按 10k 帧/批 ≈ 342 批，预计 **20~40 分钟**
- 期间不能阻塞启动（否则维护页要挂 40 分钟）
- 必须可中断（重启后从断点继续，不重做已完成的月份）

⇒ **后台任务 + 状态表 + 进度接口**，与现有 bootstrap tracker 并存但独立。

### 4.2 slot 字典膨胀的对策（核心设计点）

7,351 种字段集合（device14），每 slot 最多 29 字段 × 70 B ≈ 2 KB ⇒ **上界约 15 MB**。

- 回填按 `(device_id, timestamp)` 分组，同一帧所有行一次取齐
- `SignatureOf` 用字典序（与发射顺序无关）⇒ 字段集合相同必然命中同一 slot，自然收敛
- `DBSlots.WarmUp()` 全量装载 15 MB 到内存 —— **可接受，但要在验收里量化**

### 4.3 状态表

```sql
CREATE TABLE telemetry_backfill_progress (
    table_name  varchar(64) NOT NULL,
    part_name   varchar(64) NOT NULL,   -- 分区名，如 unified_data_202610
    state       varchar(16) NOT NULL,   -- pending/running/done/failed
    watermark   timestamptz,            -- 断点（复合游标第一分量：时间戳）
    watermark_device_id integer NOT NULL DEFAULT 0,  -- 断点第二分量（见 §4.4 游标设计）
    frames_done bigint NOT NULL DEFAULT 0,
    rows_done   bigint NOT NULL DEFAULT 0,
    started_at  timestamptz,
    finished_at timestamptz,
    error       text,
    PRIMARY KEY (table_name, part_name)
);
```

### 4.4 回填流程

**游标设计（2026-11-07 修复 P0 后定稿）**：游标是 **(timestamp, device_id) 二元组**，不是单纯时间戳。

```sql
WHERE (timestamp > ? OR (timestamp = ? AND device_id > ?))
```

为什么不用「时间戳 + 加常量推进」：PG 的 `timestamptz` 精度是**微秒**，
`ts + interval '1 nanosecond'` 在 PG 上等于没加（`SELECT (ts + '1ns') = ts` 返回 `t`）⇒
`WHERE timestamp >= from` 每轮取回同一批 ⇒ **无限重复处理**（实测 frames_done 虚涨 1016 倍、回填永不完成）。

为什么不用行值语法 `(a,b) > (?,?)`：SQLite 不支持，会引入方言分支与行为差异。
上面的「或」写法两方言语义一致（有方言一致性对照用例守着）。

Γ 上界不用「hi 加 1ns 求闭区间」（同理会漏最后一行），而是 `partition.hiInclusive` 标志 + `upperOp()` 返回 `<` 或 `<=`。

```
启动完成（第 11 步之后）→ 后台 goroutine：
  1. 查 telemetry_backfill_progress，找 state != done 的分区
  2. 每个待回填分区：
     a. 按 (device_id, timestamp) 分页扫 unified_data（watermark 续跑）
     b. 每帧：取全部行 → 按 device 聚合 → 判定关键帧
     c. Encoder.EncodeFrame → PersistFrames（批写）
     d. 每批更新 watermark + frames_done
  3. 全部 done → backfill_complete=true
  4. 老分区 DROP 与否见 §7 裁决 2（用户要求长期保留 ⇒ 默认不 DROP）
```

### 4.5 关键帧策略

老数据没有关键帧概念，迁移时必须自己定：

- 每个 `(device, 连续时间块)` 的首帧标记为关键帧
- 之后每 60s（可配）强制一个关键帧，与 L2 线上编码同口径
- 这样解码器可从任意关键帧分段独立解码，不依赖迁移前状态

### 4.6 进度可见性

```
GET /api/v1/system/backfill
→ { state, percent, current_partition, frames_done, frames_total, eta_seconds, retention_permanent, errors }
```

**⚠ 本仓有两套 state，不是同一个东西（不要合并理解）**：

| 位置 | 取值 | 粒度 | 说明 |
|---|---|---|---|
| §4.3 DB 状态表 | `pending` / `running` / `done` / `failed` | **每分区** | 落库；**永不出现 disabled**（`EHOME_BACKFILL_ENABLED=false` 时根本不建行） |
| §4.6 接口载荷 | `idle` / `running` / `done` / `failed` / `disabled` | **全局 Runner** | 内存态，从不落库 |

`disabled` 只在 `NewRunner` 短路时设置（关掉回填），`idle` 是「未注入 source」的兜底。

**载荷字段纪律（8 个 key 恒定出现，全部不加 omitempty）**：
- 契约把 `0` 定义成「未知」（`frames_total` / `eta_seconds`），有明确语义 ⇒ 不存在「不该出现」；
- `errors` 恒为 `[]` 而非 `null`（前端 `.length` 在 null 上直接抛）；
- 前端类型用**必选**字段（`frames_total: number`），不用可选 —— 可选会把「0 = 未知」这个信息在类型层面丢掉。

维护页（已有）增加回填进度块；**服务 ready 后回填仍在后台继续**，两者解耦。

## 5. 「长期保留」与保留期的冲突（必须同时改）

| 项 | 现状 | 改为 |
|---|---|---|
| `EHOME_DATA_RETENTION_DAYS` | 45 | **0 = 永久保留**（需代码支持该语义） |
| `RetentionTask` 的 DROP/DELETE | 按 45 天执行 | 保留期 <= 0 时**整体跳过** |
| 分区滚动创建 | 建未来 3 月 | 不变 |

⚠ **这是最大风险**：永久保留意味着存储只增不减。帧表可控（5 年 23 GB），
但 `device_data` 必须同时处置，否则 5 年 323 GB 一定撑爆。

## 6. 验收标准

1. **无损**：随机抽 1,000 帧解码，与原 `unified_data` 逐值比对，误差 ≤ Step/2、缺失 0
   （例外：`battery_voltage` 5 行 1e12 保留在 `raw` 列）
2. **完整性**：`telemetry_frame` 帧数 == `SELECT count(DISTINCT device_id, timestamp)`
3. **可续跑**：中途 kill 进程，重启从 watermark 继续，不重复不遗漏
4. **不阻塞**：回填期间服务 ready、业务接口正常、延迟无劣化
5. **可观测**：`/api/v1/system/backfill` 准确；维护页可见
6. **slot 规模**：`telemetry_slot` < 10,000 行、表 < 20 MB
7. **体积**：迁移完成 `telemetry_frame` < 600 MB

## 7. 需要裁决的三件事

### 裁决 1：`device_data` 怎么办（长期保留的真瓶颈）

| 选项 | 5 年占用 | 说明 |
|---|---:|---|
| A. 全量保留 | **323 GB** | 50 GB 盘装不下，必须扩盘/外置 |
| B. 保留最近 90 天，更早按月归档压缩到冷存 | ~17 GB + 冷存 | 需做归档机制 |
| C. 迁移后 DROP 老 `device_data` | 4.36 GB → 0 | 帧表能还原物理量，但丢「原始总线字节」 |

**建议 B**：`device_data` 的独特价值是「原始总线帧」（排查解析问题），
帧表已能还原物理量；保留最近 90 天 + 更早归档即可。

### 裁决 2：老 `unified_data` 迁移后是否 DROP

| 选项 | 释放 | 风险 |
|---|---:|---|
| A. 保留双份 | 0 | 安全但占 15 GB |
| B. 验证通过后 DROP 老分区 | **15 GB** | 帧表无损（已证），但丢「原始行形态」 |

**建议 B 分两步**：先迁移 → 验证 1 周 → 再 DROP。

### 裁决 3：`battery_voltage` 那 5 行 1e12

**建议**：原文写进 `raw` 列（不丢信息、不篡改）。
