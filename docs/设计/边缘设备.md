## 1. 功能概述与端点

**边缘设备 (EdgeDevice)** = **节点 + 通道 + 设备配置（+ hardware_id）** 三元组的**实例化**，是数据采集的**实际载体**。每个边缘设备在中心端是一条 DB 记录；节点**不感知"边缘设备"概念**——节点只接收展开后的通道配置与挂载设备表（见 §5）。

- 唯一性：同一通道 + 同一从机地址 + 同一型号不可重复（`(channel_id, hardware_id, type)` 三元唯一；`hardware_id` 空白降级为 `(channel_id, type)`）——允许同通道不同地址的多从机（multi-drop）。
- 数据身份（v3.3）：创建即绑定**逻辑设备**（数据生命周期锚点，见[边缘设备数据生命周期.md](边缘设备数据生命周期.md)）；删除默认**软删保留数据**，可选 `delete_data=true` 标记清除。
- 受控操作：**改走统一控制域**（ChannelCmdV2），本模块不直接执行远程写；见[边缘设备控制.md](边缘设备控制.md)。
- 初始化：`POST /:id/init` → deviceinit.Orchestrator → **sendAndWait**（非 time.Sleep），节点按展开后的 init_flow 步骤执行。

> **命名历史**：v2.1 曾称"设备"（Device），v2.2 改名"边缘设备"并引入 device_config_id。v2.1 路径 `/api/v1/devices*` 已不再作为兼容路径保留（旧文档归档），现状以 `/api/v1/edge-devices*` 为准。

## 2. 数据模型

模型：`backend/internal/models/models.go` 的 `EdgeDevice`（表 `edge_devices`）+ `LogicalDevice`（表 `logical_devices`）。

```text
edge_devices:
  id                SERIAL PK
  type              VARCHAR(32) NOT NULL DEFAULT ''   -- 兼容字段（从 DeviceConfig.DeviceType 派生或显式指定）
  parser_id         VARCHAR(32)                       -- v2.1 保留字段（从 DeviceConfig.Parser.ID 同步）
  name              VARCHAR(64) NOT NULL              -- 业务名 ("BMP280 现场 A 屋顶")
  node_id           VARCHAR(32) NOT NULL (index)      -- 节点物理 ID（hex）
  channel_id        INT NOT NULL (index)              -- 通道 FK
  device_config_id  INT (index)                       -- 设备配置 FK；0 = 无配置（驱动兜底）
  hardware_id       VARCHAR(16) DEFAULT ''            -- 通道上的从机地址（"0x76"/CS 线名；VARCHAR 非 INT）
  interval_ms       INT DEFAULT 5000                   -- 0 = 显式禁止调度
  enabled           BOOLEAN DEFAULT true
  status            VARCHAR(20) DEFAULT 'active'       -- active/error/disabled/initializing
  error_code        INT DEFAULT 0
  last_data_at      TIMESTAMP NULL
  last_error        VARCHAR(256)
  config_version    VARCHAR(64)                        -- 已应用 manifest 版本
  logical_device_id INT NULL (index)                   -- v3.3 数据身份锚点（FK 不带级联）
  init_state        VARCHAR(20) DEFAULT 'pending'      -- pending/running/completed/failed
  init_last_step / init_total_steps INT DEFAULT 0
  command_intervals JSONB DEFAULT '{}'                 -- 按命令的轮询间隔（对驱动可调度命令校验）
  created_at / updated_at / deleted_at
  （非库字段）last_data map — 列表接口携带的实时数据
```

```text
logical_devices（v3.3 数据生命周期 P0）:
  id              SERIAL PK
  identity_key    VARCHAR(64) UNIQUE NOT NULL   -- "type:hardware_id" 或 uuid v5 派生；创建后只读
  name            VARCHAR(128) NOT NULL          -- 用户可编辑
  device_type     VARCHAR(32) NOT NULL (index)
  retention_days  INT DEFAULT 365               -- 创建时快照系统保留期
  merged_into     INT NULL                       -- 合并目标（自引用，无级联）
  merge_status    VARCHAR(16) NULL               -- NULL/pending/done
  purge_requested BOOLEAN DEFAULT false         -- 勾选"同时删除数据"置位
  created_at / updated_at
```

### 2.1 三元唯一约束（应用层）

数据库层以模型字段 + 应用校验实现；`handler_edge_device.go` 的 `checkDeviceUniqueness` 是权威实现：

```text
checkDeviceUniqueness(channelID, devType, hardwareID, excludeID)
  ├─ hardware_id TrimSpace 非空 → WHERE channel_id=? AND type=? AND hardware_id=?
  └─ hardware_id 空白        → 降级为 WHERE channel_id=? AND type=?（无地址设备仍去重）
冲突 → 409："channel N already hosts a "T" device at address "A" / a "T" device"
```

设计意图（源码注释原文语义）：同一从机地址不能挂两个同型号设备；multi-drop 总线（SPI 多 CS 线 / I2C 多地址）因映射到不同通道或不同 hardware_id 而合法。更新时 `excludeID` 排除自身。

### 2.2 类型与解析器派生

- 指定 `device_config_id`：`type` 从 DeviceConfig.DeviceType 派生（同时传 type 与 device_config_id → 400）
- 未指定：`type` 必填并经 driver 注册表校验（未注册 → 错误），`device_config_id=0`
- `validateDeviceConfigForChannel`：设备配置 hardware_type（缺失时回退 connection.bus_type）必须与通道 hardware_type/bus_type 等值（大小写不敏感）匹配，否则拒绝

## 3. 状态机

### 3.1 设备状态

```text
       创建
        ↓
    ┌─────────┐ 触发 init        ┌──────────────┐
    │ pending ├─────────────────►│ initializing │
    └────┬────┘                  └──────┬───────┘
         │ 首次采集成功                  │ init 全成功
         │                              ▼
         │                        ┌──────────┐
         └───────────────────────►│  active  │◄────┐
                                  └─────┬────┘     │ 错误恢复（收到正常数据）
                                        ▼          │
                                  ┌──────────┐     │
                                  │  error   ├─────┘
                                  └─────┬────┘
                                        │ 手动禁用
                                        ▼
                                  ┌──────────┐
                                  │ disabled │
                                  └──────────┘
```

转移触发：pending→initializing（节点上线 + 触发 init）；initializing→active（init 成功）/ error（超时或 step 失败）；active→error（DataReport error_code≠0）；error→active（自动恢复）；active↔disabled（PUT enabled）；任意态→pending（重新初始化）。

### 3.2 初始化状态机（init_state，实现语义）

```text
pending → running → completed | failed
            │（无 init 序列的型号：直接置 completed/not_required，不上进度条 —— G3K）
            └─ 每步 sendAndWait，超时 3 次重试；step 失败 → failed
```

实现注：`POST /:id/init` 经 `orchestrator.InitIfNeeded` 单入口（关闭与节点自动初始化的竞态）；冲突（已在初始化/已完成）→ 409。

## 4. 关键流程

### 4.1 创建边缘设备（事务 + 逻辑身份绑定）

```text
POST /api/v1/edge-devices（DTO 白名单绑定；B1 修复）
  1. 通道解析：channel_id 存在 → 行锁校验（属于该节点 + transport 通道）
               否则内联 Channel 对象同事务创建（F：消灭两阶段提交孤儿）
               内联路径 hardware_type → bus_type = ToUpper(hwType)，hardware_type 存原样
  2. 类型解析：device_config 路径派生 type / 无配置路径校验 driver 注册表
  3. checkDeviceUniqueness（三元唯一，hardware_id 空白降级 (channel,type)）
  4. 逻辑身份（v3.3 §3.3）：
       body.logical_device_id 指定 → validateInheritanceTarget
         （目标存在 + device_type 匹配 + merged_into IS NULL + purge_requested=FALSE；
          行锁串行化并发继承）→ checkLivingInstanceUniqueness
         （同一 logical_device 至多一个存活实例；冲突 409 携带旧实例定位）
       未指定 → 新建逻辑设备（"作为新设备创建" PathCreateNew，永不复用既有 key；
         identity_key = type:hardware_id 或空地址确定性 uuid v5 派生）
  5. 插入边缘设备 → 回写 logical_device_id
  6. 权重 100 档"原位置重建"复制校准行
  7. command_intervals 对驱动可调度命令校验（未知名/不可调度拒绝；负值归一 0）
  8. createTemplatesFromDriver（驱动注册表为单一事实源，出错仅警告）
  9. EmitConfigChange → 节点拉 ConfigManifest → 启动采集 + init
```

### 4.2 创建继承候选（candidates）

`GET /edge-devices/candidates?type=&node_id=&channel_id=&hardware_id=`：Unscoped 聚合（含已软删实例的可继承逻辑设备），按匹配权重**五档**排序，全部列出由用户选择、**不做自动继承**：

| 权重 | 匹配 |
|------|------|
| 100 | 同 node + 同 channel + 同 hardware_id + 同 type（原位置重建） |
| 80 | 同 node + 同 hardware_id（不同 channel） |
| 60 | 同 node + 同 type |
| 40 | 不同 node + 同 hardware_id |
| 20 | 不同 node + 同 type |

hardware_id 比较为 TrimSpace + 小写归一；数据量 row_estimate 用估算（PG reltuples / SQLite 截断 COUNT），共享 3s 超时预算，超时候选降级为不含 row_estimate（仍可用）；retention_days 显式返回。

### 4.3 删除（软删默认保留数据）

```text
DELETE /api/v1/edge-devices/:id?delete_data=false|true
  事务内：
  1. 实例缺逻辑身份 → EnsureLogicalDevice 补建（PathDelete）
  2. handleConfigTemplateOnDelete：归属模板引用检查（同通道同 type 仍有存活实例则保留），
     无引用则从 channel.template_ids 移除并删 ConfigTemplate 行（防 ESP32 16 模板溢出）
  3. GORM 软删实例（历史数据保留，身份锚点不变）
  4. delete_data=true → logical_devices.purge_requested=true（数据硬删由 purge
     后台任务异步分批执行，API 事务不删数据）
POST /api/v1/edge-devices/batch-delete { ids[], delete_data }：逐条复用单删事务
  （≤100），返回 { total, succeeded, failed, results[] }
```

### 4.4 初始化（sendAndWait，G6 修复）

```text
POST /:id/init
  ├─ 设备禁用 → 400；通道非 transport/禁用 → 400；节点不存在 → 400
  ├─ GetInitSequence(type) 为空 → init_state=completed，返回 "not_required"（G3K）
  └─ orchestrator.InitIfNeeded（单入口 + reservation）→ init_state=running(total_steps=N)
节点执行：按展开的 init_flow 逐步 sendAndWait（WriteCommand + 等回执，
  超时 3 次重试；read_calib 等 store_as 步骤的校准数据上行中心端保存）
```

### 4.5 数据采集与查询

节点周期读取上报 → 中心端 DataReport 处理 → 写 device_data（关联边缘设备 + logical_device_id 回填）→ WS 推送。`GET /:id/data` 经 `datalifecycle.ResolveDataQueryScope` 作用域（已删实例 404；存活实例查全量历史含继承/合并前数据）；`GET /:id/latest` 同理取最新一条。

## 5. 协议与外部契约

### 5.1 节点侧协议（节点不感知边缘设备）

ConfigManifest（0x04）`channel_info` 内嵌挂载表：

```text
channel_config_t:
  channel_id, bus_type, bus_config
  edge_devices[]:                       # 节点侧命名，语义为"通道上挂的子设备"
    edge_device_id（中心端 PK，仅追踪）、hardware_id、parser_id、interval_ms、
    enabled、init_flow_steps[]（从设备配置展开）
节点 NVS 只存 (channel_id, hardware_id, parser_id, interval_ms, init_flow)；
不存 device_config_id / logical_device_id（中心端抽象）
```

数据上报（DataReport 0x03）字段携带 channel/设备定位信息，中心端按实例血缘归集。

### 5.2 受控操作契约（统一控制域）

- 创建/执行受控操作走 `/edge-devices/:id/operations`（Idempotency-Key 必填），执行面为 ChannelCmdV2（0x15/0x16/0x17）：**dry-run → 九项门禁 → 编译 → ActionConfirmationDialog 确认 → 执行时间线**；critical 动作 at_most_once 限频 + 设备互斥锁。详细契约见[边缘设备控制.md](边缘设备控制.md)。
- 本模块不再直接构造 "WriteCommand 远程操作" 路径；device_config.actions 由驱动声明并进控制域。
- legacy `/edge-devices/:id/execute`（DeviceConfig.operations 模板引擎）仍然存在但受控制策略门禁（legacy 写已禁用 → 410），读取路径亦逐步收敛，见[边缘设备控制.md](边缘设备控制.md) §门禁。

### 5.3 WS 事件

`edge_device_status` / `data_update` / `notification`；事件字段：id、node_id、channel_id、device_config_id、status、error_code、init_*，见[同步机制.md](同步机制.md)与[数据采集与数据链路.md](数据采集与数据链路.md)。

### 7.2 后端验收

- [ ] 创建：node 不存在 404；channel 不属于 node 或非 transport/禁用 → 错；type 与 device_config_id 同传 → 400；三元重复 → 409

- [ ] init：无序列 → not_required（不残留 running）；进行中重复触发 → 409；启用/通道校验拒绝
- [ ] data/latest：身份作用域正确（已删 404、继承历史可见）；分页与时间过滤生效
- [ ] `go test ./internal/api/... ./internal/deviceinit/... ./internal/datalifecycle/...` 通过

### 7.3 节点端 / 协议验收

- [ ] 节点 NVS 存 (channel_id, hardware_id, parser_id, interval_ms, init_flow)，不存边缘设备 PK / 逻辑身份
- [ ] 采集周期 = interval_ms（0/禁用不调度）；错误 error_code 上行
- [ ] init 每步 sendAndWait；校准数据上行；失败上报

### 7.4 集成验收（E2E）

- [ ] 创建（BMP280 配置）→ 节点收到 → init → 校准成功 → 采集温度气压
- [ ] 禁用/启用 → 节点停止/恢复采集，状态同步
- [ ] 删除（默认）→ 数据保留；重建设备（同位置）→ candidates 权重 100 → 继承后历史数据接续
- [ ] 受控操作：dry-run → 确认弹窗 → 执行 → 时间线（与[边缘设备控制.md](边缘设备控制.md)验收联动）
- [ ] 前端 `npm run typecheck` + 相关 spec 通过

## 8. 已知限制与债务

| 限制/债务 | 说明 |
|-----------|------|
| 三元唯一为应用层 | 数据库候选 (channel_id, hardware_id, type) 无独立唯一索引，权威实现是 checkDeviceUniqueness；并发窗口依赖事务与行锁 |
| hardware_id 语义漂移 | 模型中 hardware_id 为 VARCHAR(16)（"0x76" / CS 名 / ""），非 v2.1 设计的 INT——与[通道.md](通道.md) hardware_id 同源，比较统一 TrimSpace+小写 |
| type / parser_id 冗余字段 | 模型保留兼容字段（从设备配置派生，deprecated 但仍在用），全量消除依赖后续迁移 |
| init_state 字面量 | 实现为 pending/running/completed/failed（v2.2 设计文件中 in_progress 已被替换）；状态与 status 双轨并存 |
| legacy execute 路径 | DeviceConfig.operations 模板引擎端点未删除（读取路径可用、写被门禁），受控面已切换 ChannelCmdV2（见技术债台账） |
| 双协议并存 | DataReport 字段归属（channel 定位 vs 实例血缘）在协议演进中保留兼容语义，见[../协议/二进制帧协议.md](../协议/二进制帧协议.md) |
