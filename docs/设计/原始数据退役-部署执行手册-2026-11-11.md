### 步骤 3：执行迁移校验 + DROP

**方式 A（推荐）：用 ehomectl（校验与删表在同一流程里）**

> ⚠ 2026-11-11 生产实测校准：以下命令与输出**均为真实跑过的**，不是设计稿。
> 关键：`--dry-run` 与 `--yes` 都**必须在 ehome 容器内执行**（PG 不对宿主暴露端口，
> 且 ehomectl 要读 `EHOME_DB_*` 环境变量）。不要用 `docker run --network` 起临时容器 ——
> 生产 compose 的网络名与凭据注入方式见下方。

```bash
# ① 把 ehomectl 二进制放进运行中的容器（镜像里已有 /app/ehomectl，此处用容器内路径即可跳过本步）
#    若镜像尚未更新，可临时 docker cp：docker cp ./ehomectl ehome-prod-web:/tmp/ehomectl

# ② 从**运行中的容器**读取真实 DB 密码（不要手工传 PGPASSWORD，容易漏）
PW=$(docker inspect ehome-prod-web --format '{{range .Config.Env}}{{println .}}{{end}}' \
     | grep '^EHOME_DB_PASSWORD=' | cut -d= -f2-)

# ③ dry-run（只校验、只打印，绝不改库 —— 已实测 schema 指纹前后一致）
docker exec -e EHOME_DB_PASSWORD="$PW" ehome-prod-web /app/ehomectl retire-device-data --dry-run
```

**实测输出（2026-11-11 生产）**：

```
表 device_data: 行数=8,715,226  大小=3.4 GB
删表前校验（方案 §3.4）：
  ❌ = 阻塞项（不通过则拒绝 DROP）；⚠  = advisory（只提示，不影响 DROP）
  ✅ orphan_parsed_rows       value=0
  ⚠  orphan_frame_devices     value=1
       advisory（不阻塞）: 帧表里有指向不存在设备的帧（孤儿历史，既有脏数据）…
  ✅ recent_frames            value=2
  ✅ rollup_coverage_recent   value=77

⚠ 有 1 条 advisory 提示（不阻塞 DROP，但建议记录到运维日志）：
   · orphan_frame_devices = 1

✅ 校验全部通过。以上是**将要删除**的内容（当前是 --dry-run，未做任何修改）。
```

**四条校验的含义**（阻塞项必须全绿）：

| 校验项 | 含义 | 不通过的后果 |
|---|---|---|
| `orphan_parsed_rows` | **阻塞** — device_data 里有解析值但帧表没覆盖 | DROP 会**丢解析数据** |
| `orphan_frame_devices` | **advisory** — 帧表里有指向已删设备的帧 | 不阻塞；是既有脏数据，用 purge 清理 |
| `recent_frames` | **阻塞** — 近 24h 帧表没有任何设备在写 | 说明新容器没起来，DROP 后系统彻底无实时数据 |
| `rollup_coverage_recent` | **阻塞** — 近 7 天无覆盖率记录 | 长窗图表会没有 rollup 可用 |

```bash
# ④ 正式执行（校验全绿才会 DROP；任一条阻塞项失败会 exit 2 并保持表与数据原样）
docker exec -e EHOME_DB_PASSWORD="$PW" ehome-prod-web /app/ehomectl retire-device-data --yes
```

**实测输出**：

```
⏳ 执行 DROP TABLE device_data CASCADE ...
✅ DROP 完成：母表 + 子分区剩余 0 张（期望 0）
✅ 附带清理：已 DROP watermark 表 device_data_strip_progress（已退役的 sensors 剥离任务遗留）
```

> **`--dry-run` 是真正只读的**：它走 `connectDBNoMigrate()`（只 Connect，不跑 AutoMigrate）。
> 这一点有源码门禁用例守着 —— 别把它改成 `connectDB()`，否则「只读工具」会在连库瞬间改 schema。

**方式 B（手工 SQL，ehomectl 故障时兜底）**

```sql
-- ⚠ 必须关并行：PG 容器 /dev/shm 只有 64 MB（docker 默认），这条带 NOT EXISTS
--   相关子查询的 SQL 会因并行 hash 表申请 32 MB 共享内存失败而报
--   "could not resize shared memory segment ... No space left on device"。
SET max_parallel_workers_per_gather = 0;
SET max_parallel_workers = 0;

-- ① 帧表覆盖检查（期望 0）
SELECT count(*) AS orphan_parsed_rows
FROM device_data d
WHERE d.data_json LIKE '%"sensors"%'
  AND NOT EXISTS (SELECT 1 FROM telemetry_frame f
                  WHERE f.device_id = d.device_id
                    AND f.ts BETWEEN d.timestamp - interval '5 seconds'
                                 AND d.timestamp + interval '5 seconds');

-- ② 孤儿设备（生产实测 = 1：device_id=2，100,806 帧，2026-10-02~10-04，设备行已被硬删）
--    ⚠ 这是**既有脏数据**，不阻塞删表；要清理走 purge
SELECT DISTINCT f.device_id FROM telemetry_frame f
WHERE NOT EXISTS (SELECT 1 FROM edge_devices e WHERE e.id = f.device_id);

-- ③ 活跃设备帧数（期望 dev14/dev15 各 5 万~9 万/24h）
SELECT device_id, count(*) FROM telemetry_frame
WHERE ts >= now() - interval '24 hours' GROUP BY 1 ORDER BY 2 DESC;

-- ④ rollup 覆盖（生产实测 77 行 / 近 7 天）
--    ⚠ day 列是 **character varying**（'2026-11-10'），不是 date！
--      写成 day >= (now() - interval '7 days')::date 会报
--      "operator does not exist: character varying >= date"
SELECT device_id, day, state FROM telemetry_rollup_coverage
WHERE day >= to_char(now() - interval '7 days', 'YYYY-MM-DD')
ORDER BY day DESC, device_id;

-- ⑤ DROP（**不可回滚**）
-- CASCADE 是必须的：device_data 是分区母表，子分区通过 pg_inherits 依附。
-- 生产实测依赖只有它自己的月分区与索引，无视图/外键引用。
DROP TABLE IF EXISTS device_data CASCADE;
-- 一并清掉已退役剥离任务的水位表（与 device_data 同生共死）
DROP TABLE IF EXISTS device_data_strip_progress;
VACUUM FULL node_logs;
```

- [ ] 校验 ① 返回 **0**
- [ ] 校验 ② 返回 **1**（已知：device_id=2 的孤儿帧，advisory，不阻塞）
- [ ] 校验 ③ 返回 **2**（dev14 / dev15 在写帧）
- [ ] 校验 ④ 返回 **约 77 行**
- [ ] `DROP TABLE device_data CASCADE` 执行成功
- [ ] `DROP TABLE device_data_strip_progress` 执行成功
- [ ] `SELECT count(*) FROM pg_tables WHERE tablename LIKE 'device_data%'` = **0**

## 4. 失败处置

### 4.1 决策树

```
发现问题？
├─ 步骤 3（DROP）之前
│   └─ → docker 回滚旧镜像 + 重启。表还在，零数据损失。
├─ DROP 之后、步骤 4 之前
│   └─ → 继续走完（起新容器），因为新代码不依赖 device_data；
│      若新容器起不来，回滚旧镜像会 42P01 ⇒ **必须**从备份恢复后再回滚。
└─ DROP 之后、T+7 内
    ├─ 只有前端小问题 → 修前端，不用恢复数据
    └─ 需要 device_data 数据 → 恢复备份：
         make restore DUMP=backups/<file>.dump DB=ehome FORCE=1
         停机约 10~20 分钟
```

### 4.2 恢复备份的完整步骤

```bash
$SSH 'docker stop ehome-prod-web'
make restore DUMP=backups/<file>.dump DB=ehome FORCE=1
# 恢复后确认表回来了
$SSH 'docker exec ehome-prod-postgres psql -U ehome -d ehome -At -c \
  "SELECT count(*) FROM pg_tables WHERE tablename LIKE \"device_data%\""'  # 期望 4（父+3分区）
# 回滚镜像到旧版本（因为新版本不认 device_data）
$SSH 'cd /srv/ehomesystem && EHOME_IMAGE_TAG=<OLD_TAG> docker compose -f deploy/prod/docker-compose.prod.yml up -d ehome'
```
