## 1. 设计动机与目标

配置同步是 IoT 系统最常见的翻车点。EHomeSystem 的目标是**配置最终一致**：任何时刻节点持有的配置要么是最新，要么在一个自愈周期内收敛到最新。

v2.0 方案的 4 个 P0 缺陷（夜间重启丢配置、幂等缺失、双写不一致、无兜底）由 v2.1 同步机制修复，现行设计核心自 v2.1 起保持稳定：

1. **ConfigEventBus + EpochGenerator**：全部配置变更走统一事件管道，epoch 全局单调递增（DB 持久化）。
2. **SyncGate 统一决策中心**：所有同步入口收敛为同一决策逻辑。
3. **节点 NVS 持久化**：cfg_epoch + manifest_id 存 NVS，重启后可比较。
4. **周期 sync 兜底**：节点周期（默认 10min）自愈性请求同步。

## 2. 架构组件

```
配置变更入口（7 个）：
  CRUD Handler（EmitConfigChange）
  Server Startup（OnStartup）
  Hello（OnHello）
  StatusReport（OnStatus）
  ConfigQuery（OnQuery）
  离线重连（OnReconnect）
  恢复出厂（FactoryReset 检测）
        └──► ConfigEventBus（Go chan, 有界）
               └──► SyncGate（统一决策中心）
                      ├─ 读 DB：节点 epoch / manifest_id / nvs_has_config
                      ├─ 决策矩阵（§3）
                      └─ SendConfigManifest（带 sync_id）
                             → MQTT nodes/{id}/down
                             → Node config_mgr_apply_manifest()
                               ├─ 事务化应用
                               └─ ConfigResult（success + manifest_id）
```

## 3. SyncGate 决策矩阵

| 条件 | 决策 | 理由 |
|------|------|------|
| `has_active_manifest=0`（重启后无活动配置/NVS 空/恢复出厂） | 强制全量下发 | 节点无可用配置 |
| epoch 落后（节点 < 中心端） | 强制全量下发 | 配置已变更 |
| manifest_id 不匹配 | 强制全量下发 | 版本漂移 |
| sync_state=error | 重发 | 上次应用失败 |
| 其余 | dedup（不重发） | 已一致 |
| 节点周期请求（10min） | 仅在 epoch 不匹配时下发 | 自愈兜底 |

**v3.4 相关事实（Redis 退役）**：EpochGenerator 与决策全部在 DB 上，不依赖 Redis；退役不影响同步路径。

## 4. 节点侧事务化应用

ConfigManifest 应用顺序（config_mgr，保证失败可恢复）：

```
挂起总线 worker → 暂存+校验新清单 → 停止旧调度 → 快照当前运行时
  → 应用：DMA → 外设(GPIO/PWM) → 总线 → 调度器 → 日志流
  → 提交活动清单 → 激活调度器
任一失败 → 恢复旧运行时；无法恢复 → 进入安全状态重启
→ 成功后持久化同步元数据（epoch/manifest_id）→ 发 ConfigResult success=1
```

中心端约束：

- 收到 `success=1` 前不得标为已部署。
- `success=0` 保留原配置，按错误上下文重试或修正。
- ConfigResult 必须以 `manifest_id + sync_id` 去重。

## 5. 兜底与容错

| 场景 | 兜底 |
|------|------|
| 中心端重启丢内存态 | 启动后向所有 online 节点 push |
| 节点重启 | Hello 上报 epoch + has_active_manifest，落后即下发 |
| ConfigEventBus 满 | drop + alarm（ehome_event_bus_dropped_total） |
| 下发失败 | 退避重试 3 次；失败进 notifications |
| 节点周期 sync 失败 | 下一个周期兜底（10min） |
| 恢复出厂（NVS 清空） | has_active_manifest=0 → 强制下发 |

## 6. 协议契约

- Hello (0x01)：field 5 epoch、6 has_active_manifest、7 last_known_manifest_id、8 proto_version
- ConfigManifest (0x04)：field 1 manifest_id（必填非空）、field 8 sync_id（必填非空）
- ConfigResult (0x05)：field 1 success、2 error_code、3 error_msg
- ConfigQuery (0x10) / ConfigReport (0x11)：主动查询当前配置版本
- 详细字段定义见 [../协议/二进制帧协议.md](../协议/二进制帧协议.md)

## 7. 观测与指标

| 指标 | 类型 | 含义 |
|------|------|------|
| ehome_sync_decisions_total | counter | 按 reason/action 的决策计数 |
| ehome_sync_duration_seconds | histogram | 每次同步耗时 |
| ehome_sync_inflight | gauge | 在途同步数 |
| ehome_config_epoch | gauge | 当前 epoch |
| ehome_event_bus_dropped_total | counter | 事件总线丢弃数 |

WS 事件：`node_config_synced`（node_id, sync_id, manifest_id, epoch, reason, result）。前端可据此展示配置同步状态。

## 8. 验收标准（现行）

- [ ] 节点首次上线（无配置）→ 强制下发 → ConfigResult success → in_sync
- [ ] CRUD 变更 → 节点收到新 manifest（epoch 递增）
- [ ] 中心端重启 → online 节点全部收到 push
- [ ] 节点恢复出厂 → has_active_manifest=0 → 强制下发
- [ ] 下发失败 → 退避重试 3 次 → 通知中心可见
- [ ] ConfigEventBus 满 → drop 且 alarm 指标递增
- [ ] 周期 sync（10min）→ epoch 匹配时不产生冗余下发
- [ ] 集成测试：manifest 应用失败路径恢复旧配置

## 9. 已知限制

- 全量下发（非增量）：当前 ConfigManifest 为全量配置；ConfigPatch 增量下发未实施（评估中）。
- NVS 只存同步元数据，不存完整运行配置（节点重启依赖重下发，这是设计选择）。
- 灰度双 topic（devices/ 旧 topic）已随 v2.2 迁移窗口关闭而不再双订阅。
