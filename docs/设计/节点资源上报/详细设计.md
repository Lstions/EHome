# 节点资源上报 (ReportResources) — 详细设计

> **版本**: v2.3
> **状态**: 设计中
> **关联**: [节点/详细设计.md](../节点/详细设计.md) | [通道/详细设计.md](../通道/详细设计.md) | [00-术语表.md](../00-术语表.md)

## 1. 功能概述

v2.2 删除了 v1 的 ReportResources 消息，导致前端"硬件资源与通道关联"页面始终为空。本设计重新引入该功能，让 ESP32 节点在启动时主动上报其可用硬件资源（I2C/SPI/UART/GPIO/ADC 的端口、引脚、参数），中心端存入 DB 后供前端展示和通道配置。

### 1.1 为什么要重新加入

| 维度 | v2.2 现状 | 问题 |
|------|-----------|------|
| capabilities API | 硬编码 `["i2c","spi","uart","gpio","adc"]` | 无具体端口/引脚信息，前端无法渲染硬件卡片 |
| hardware_info 字段 | DB 为 `{}` | 从未被写入 |
| 前端 ChannelPanel | 期望 `{buses: {uart:[...], i2c:[...]}}` | 拿到空数据 → "暂无通道" |
| ESP32 固件 | bus.c 中有完整硬件初始化逻辑 | 但服务端不知道有哪些可用资源 |

### 1.2 与 v1 的区别

v1 使用 protobuf 的 `ReportResources` / `ReportChannels` 消息，类型多、字段复杂。v2.3 精简为：

- **一条消息**: `ResourceReport` (type=0x19)
- **上报两样内容**: ①硬件资源（可用总线/引脚/参数） ②当前通道配置（NVS 中已应用的活跃通道）
- **JSON 结构**: 内部用简单 key-value，不用嵌套 sub-message
- **触发方式**: HelloAck 确认握手成功后自动上报，确保服务端可达

## 2. 协议设计

### 2.1 消息类型分配

| type | 消息 | 方向 | 说明 |
|------|------|------|------|
| 0x01-0x18 | (已分配) | - | 见 requirements.md |
| **0x19** | **ResourceReport** | **ESP→SVR** | **v2.3 新增: 硬件资源上报** |

> 0x19 = 25，紧跟现有 0x18 (PongAck) 之后，不与任何已分配类型冲突。

### 2.2 ResourceReport 消息格式 (type=0x19)

采用 **JSON 字符串 + varint 计数** 的混合格式，兼顾编码简洁和可扩展性：

```
Field #1: resource_count (varint) — 硬件资源条目数 (buses 中所有数组长度之和)
Field #2: resources_json (string) — 完整资源描述 JSON (含 buses + channels)
Field #3: platform (string) — 平台标识, e.g. "ESP32C6"
```

JSON 包含两个顶层键：
- `buses`: 可用硬件资源（静态，由芯片/板子决定）
- `channels`: 当前活跃通道配置（动态，来自 NVS 中 ConfigManifest 下发后的运行时状态）

### 2.3 Pin Role 枚举

复用前端已有的映射（ChannelPanel.vue 中 PIN_ROLE_LABELS）:

| 值 | 名称 | 说明 |
|----|------|------|
| 0 | UNSPECIFIED | 未指定 |
| 1 | TX | UART 发送 |
| 2 | RX | UART 接收 |
| 3 | SDA | I2C 数据 |
| 4 | SCL | I2C 时钟 |
| 5 | MOSI | SPI 主出从入 |
| 6 | MISO | SPI 主入从出 |
| 7 | SCLK | SPI 时钟 |
| 8 | CS | SPI 片选 |
| 9 | GPIO | 通用 IO |
| 10 | CH | ADC 通道 |

### 2.4 为什么选 JSON 而非纯二进制 sub-message

| 方案 | 优点 | 缺点 |
|------|------|------|
| **JSON (选定)** | 编码简单 (~50行C)、可读、前端直接用、易扩展 | 额外 ~2KB flash (cJSON) |
| 纯二进制 sub-message | 省带宽 | 编码复杂 (~300行C)、前端需二次解析、ESP32 和 Go 两端都要实现 |
| 合并到 Hello | 无新消息类型 | Hello 膨胀、每次心跳都带资源数据 |

**决策**: JSON。理由:
1. 该消息极低频（仅 Hello 后发一次），带宽不是瓶颈
2. ESP32-C6 4MB flash，2KB cJSON 完全可接受
3. 前端 `ChannelPanel` 已直接消费 `{buses: {...}}` 格式
4. 服务端解析只需 `json.Unmarshal`

## 3. 交互流程

### 3.1 上报时序

**核心原则**: ResourceReport 必须在 Hello 握手成功（收到 HelloAck）后发送。此时 MQTT 通道已确认双向可达，服务端已为该节点创建/更新 DB 记录。

```
ESP32                            Server                          Frontend
  │                                │                                │
  │── Hello (0x01) ──────────────→│                                │
  │                                │  UPSERT nodes 表               │
  │                                │  SyncGate 决策                  │
  │←── HelloAck (0x12) ──────────│  ← 握手成功                     │
  │                                │                                │
  │  (等 200ms, 确保下行通道稳定)   │                                │
  │── ResourceReport (0x19) ─────→│                                │
  │    {buses: {...},             │  解析 JSON                     │
  │     channels: [...]}          │  nodes.capabilities = buses    │
  │                                │  nodes.hardware_info = full    │
  │                                │  同步 channels 到 DB            │
  │                                │  DB UPDATE                     │
  │                                │  WS push: node_resources_updated│
  │                                │                                │
  │←── ConfigManifest (0x04) ────│  (如果 SyncGate 决策需要下发)    │
  │── ConfigResult (0x05) ──────→│                                │
  │                                │                                │
  │                                │←── GET /api/v1/nodes/1/capabilities
  │                                │─── {buses: {uart:[...], ...}} ─│
  │                                │                                │
  │                                │←── GET /api/v1/nodes/1/hardware/config
  │                                │─── {hardware: {buses: {...}}} ─│
  │                                │                                │
  │                                │                   渲染硬件资源卡片 ✓
```

### 3.2 ESP32 端触发条件

ResourceReport 在以下时机发送，**均以 HelloAck 确认为前提**：

| 触发条件 | 时机 | 说明 |
|----------|------|------|
| **首次握手** | MQTT 连接后 Hello → HelloAck 成功 | 最常见路径，main.c 中 `hello_confirmed=true` 后立即发送 |
| **重连握手** | MQTT 断线重连后 Hello → HelloAck 成功 | 同上，每次重连都重新上报 |
| **手动查询** | 收到 QueryReq (0x0E, query_type=1) | 服务端主动请求刷新（如前端点"同步硬件"按钮） |

**不会触发的场景**:
- ❌ Hello 发出但未收到 HelloAck — 握手未完成，不发
- ❌ 周期性 StatusReport — 资源不随时间变化，无需重复上报
- ❌ ConfigManifest 接收后 — 资源是硬件固有属性，不因配置改变

### 3.3 握手成功的判定

ESP32 端已有现成机制：

```c
// main.c on_mqtt_state() 中
msg_handler_reset_hello_ack();
// ... 发 Hello, 等待 ...
if (msg_handler_is_hello_ack_received()) {
    hello_confirmed = true;
    // ★ 在此处发送 ResourceReport
    msg_handler_send_resource_report();
}
```

`msg_handler_is_hello_ack_received()` 是已有的全局标志，收到 HelloAck (0x12) 时置 true。ResourceReport 在此标志为 true 后发送，保证握手已完成。

### 3.4 服务端处理

1. 解析 ResourceReport 的 JSON 字段
2. 提取 `buses` 部分 → `UPDATE nodes SET capabilities=$buses_json WHERE node_id=$id`
3. 完整 JSON → `UPDATE nodes SET hardware_info=$full_json WHERE node_id=$id`
4. 提取 `channels` 部分 → 同步到 channels 表（upsert by node_id + hardware_id）
5. WebSocket 推送 `node_resources_updated` 事件（前端可自动刷新）

## 4. API 变更

### 4.1 GET /api/v1/nodes/:id/capabilities

**v2.2 (当前)**: 硬编码 `{capabilities: ["i2c","spi","uart","gpio","adc"]}`

**v2.3 (新)**: 从 DB 读取

```
Response:
{
  "code": 200,
  "data": {
    "capabilities": ["i2c","spi","uart","gpio","adc"],
    "buses": {
      "uart": [
        {"id":"UART0","port":0,"default_tx":16,"default_rx":17,"pins":[...]},
        {"id":"UART1","port":1,"default_tx":21,"default_rx":20,"pins":[...]}
      ],
      "i2c": [...],
      "spi": [...],
      "gpio": [...],
      "adc": [...]
    }
  }
}
```

**Fallback**: 如果 DB 中 `capabilities` 为空或不是合法 JSON，返回 ESP32-C6 默认硬件资源。

### 4.2 GET /api/v1/nodes/:id/hardware/config

**v2.2 (当前)**: 返回 `{hardware: {wifi_ssid, wifi_rssi, free_heap}}`

**v2.3 (新)**: 从 DB `hardware_info` 字段读取

```
Response:
{
  "code": 200,
  "data": {
    "hardware": {
      "buses": { ... },       // 用户自定义的总线配置 (enabled, config_id 等)
      "wifi_ssid": "...",
      "wifi_rssi": -45,
      "free_heap": 81920
    }
  }
}
```

### 4.3 PUT /api/v1/nodes/:id/hardware/config

**v2.2 (当前)**: 忽略请求体，直接返回假数据

**v2.3 (新)**: 写入 DB `hardware_info` 字段

```
Request:
{
  "hardware": {
    "buses": {
      "uart": [{"id":"UART1","enabled":true,"config_id":3}],
      "i2c": [{"id":"I2C0","enabled":true}]
    }
  }
}

Response:
{
  "code": 200,
  "data": {"node_id": 1, "status": "updated"}
}
```

## 5. 数据库变更

**无需 schema 变更**。`nodes.capabilities` 和 `nodes.hardware_info` 已是 JSONB 类型，当前为 `{}`。只需后端实际写入即可。

存储策略:
- `capabilities`: 存 ResourceReport 上报的原始 JSON（含 buses 结构）
- `hardware_info`: 存用户自定义的总线启用/禁用配置

## 10. channels 同步策略

ResourceReport 中的 `channels` 数组反映 ESP32 NVS 中**当前正在运行**的通道配置。服务端收到后：

1. **比对**: 以 `(node_id, hardware_id)` 为唯一键，与 DB 中现有 channels 比较
2. **新增**: NVS 中有但 DB 无 → INSERT
3. **更新**: 两边都有但 config 不同 → UPDATE（以 NVS 为准，节点是 truth）
4. **标记离线**: DB 中有但 NVS 无 → 不删除，仅标记 `enabled=false`（中心端可能配置了但节点未应用）

> **原则**: 节点上报的通道是"运行时真相"，中心端配置的通道是"期望状态"。两者可能不同步（如 ConfigManifest 刚下发但 ESP32 还未应用）。ResourceReport 让中心端了解实际状态，而非覆盖期望状态。
