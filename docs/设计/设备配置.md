## 1. 功能概述与端点

**设备配置 (DeviceConfig)** = 一种**设备型号**的协议无关元数据定义，回答"这个型号是什么 / 怎么初始化 / 怎么解析数据"。一个型号一份，多节点复用，由中心端统一管理；它的实例化对象是[边缘设备](边缘设备.md)。

核心三部分（v2.2 起结构化）：

1. **connection**（设备连接参数）：总线协议 + 默认参数（可被通道 `bus_config` 覆盖）
2. **parser**（数据解析器）：注册的解析器 ID + options
3. **init_flow**（业务配置流程）：校准 / 初始化命令步骤序列

另外承载该型号的**操作集**（`operations` JSONB，模板引擎 + CRC），与驱动声明的受控动作共同定义可执行操作（执行面见[边缘设备控制.md](边缘设备控制.md)）。

> **命名历史**：v2.1 曾称"设备模板"，v2.2（2026-06-04）改为"设备配置"。旧名仅历史文档使用；旧路径 `/api/v1/device-templates` 已不再保留，详见 §8。

## 2. 数据模型

模型：`backend/internal/models/models.go` 的 `DeviceConfig`（GORM，表 `device_configs`）。

```text
device_configs:
  id              SERIAL PK
  name            VARCHAR(128) NOT NULL        -- 型号名 (e.g. "BMP280 大气压传感器")
  device_type     VARCHAR(64)  NOT NULL        -- 型号代码 (e.g. "bmp280")
  vendor_id       INTEGER NULL                 -- 厂商 (可选)
  device_model_id INTEGER NULL                 -- 型号库 (可选)
  connection      JSONB        NOT NULL        -- 设备连接参数
  parser          JSONB        NOT NULL        -- 数据解析器
  init_flow       JSONB        DEFAULT '[]'    -- 业务配置流程 (步骤序列)
  operations      JSONB NULL                   -- 操作集 (模板引擎 + CRC)
  description     TEXT
  protocol        VARCHAR(32)                  -- 兼容旧字段
  hardware_type   VARCHAR(32)                  -- uart/i2c/spi/adc (兼容旧字段)
  parser_id       VARCHAR(64)                  -- 兼容旧字段 (从 parser.id 推导)
  default_params  JSONB                        -- 兼容旧字段
  is_default      BOOLEAN DEFAULT false
  status          VARCHAR(20) DEFAULT 'active'
  created_at / updated_at / deleted_at
  UNIQUE (device_type, name)
```

### 2.1 connection 结构

```json
{
  "protocol": "SPI",
  "default_params": { "clock_hz": 10000000, "mode": 0 },
  "optional": { "interrupt_pin": 0 }
}
```

### 2.2 parser 结构

```json
{ "id": "bosch.bmp280", "options": { "temperature_unit": "celsius" } }
```

### 2.3 init_flow 结构（步骤序列）

```json
{
  "steps": [
    { "name": "soft_reset", "data": "\\xE0", "read_size": 0, "timeout_ms": 100, "description": "软复位" },
    { "name": "read_chip_id", "data": "\\xD0", "read_size": 1, "timeout_ms": 50,
      "expected_value": "0x58", "description": "读芯片 ID (期望 0x58，校验失败则 step 失败)" },
    { "name": "read_calib", "data": "\\x88", "read_size": 26, "timeout_ms": 100,
      "store_as": "calibration", "description": "读校准数据 (26 字节，响应命名存储)" }
  ]
}
```

步骤字段：`name`（不重复）/ `data`（hex 命令）/ `read_size` / `timeout_ms`（10–10000 范围）/ `expected_value`（期望返回值校验）/ `store_as`（命名存储响应，后续步骤可引用）/ `description`（运维注释）。

## 3. 状态机

### 3.1 设备配置状态

```text
创建 → active ──禁用──→ inactive ──恢复──→ active
               │
               └──软删除──→ archived（deleted_at 置位，历史数据保留）
```

### 3.2 引用关系与删除约束

- 设备配置被 `edge_devices.device_config_id` 引用（RESTRICT：有引用时 DELETE 返回 409，需先迁移引用）
- 设备配置可选引用厂商/型号库（软删除时 SET NULL，不级联）
- `device_type + name` 唯一，重复创建返回 409

## 4. 关键流程

### 4.1 创建设备配置

```text
POST /api/v1/device-configs
  1. 服务端兜底校验：name / device_type / hardware_type 必填；status 缺省 active
  2. 创建 device_configs 记录（UNIQUE(device_type, name) 冲突 → 409）
  3. 推 notification 事件（新设备配置可用）
```

已实现为 DTO 直接绑定 + 服务端兜底（handler_device.go 的 device-configs 段）；v2.2 设计文档中的"parser.id 注册校验 / init_flow Zod 校验"以服务端兜底与创建后 test-parser 自测替代（见 §8）。

### 4.2 修改设备配置（G1 修复）

```text
PUT /api/v1/device-configs/:id
  1. 更新记录
  2. 旁路影响分析出引用此 device_config_id 的边缘设备
  3. EmitConfigChange → 对每个相关节点推 ConfigManifest
  4. 节点重新 apply init_flow（变了才重新触发 init）
```

### 4.3 删除（RESTRICT）

```text
DELETE /api/v1/device-configs/:id
  ├─ 存在 edge_devices 引用 → 409（提示先迁移引用）
  └─ 无引用 → 软删除（数据保留）
```

### 4.4 parser 在线测试（test-parser）

```text
POST /api/v1/device-configs/:id/test-parser { "raw_data": "..." }
  1. raw_data 若为合法 hex 先解码（decodeHexString，支持 "\\x" 前缀）
  2. 主路径：DeviceConfig.Parser JSONB → parser.NewConfigParser → Parse(rawBytes)
  3. 回退路径：legacy driver 注册表驱动 ParseData
  4. 回退路径：basic JSON 解析
  响应携带 "parser": "device_config" | "driver" | ... 指明实际采用的解析路径
```

### 4.5 节点侧应用（节点不感知设备配置概念）

节点不存 `device_config_id`。创建边缘设备时，中心端把设备配置内容**展开写入边缘设备行**（`type` 派生、`parser_id` 同步），并经 ConfigManifest 以 `channel.edge_devices[].parser_id + init_flow` 形式下发；节点的执行载体是 [边缘设备.md §5](边缘设备.md) 的协议结构，直接来源是逐指令采集模板（ConfigTemplate）。

## 5. 协议与外部契约

- **不下发 DeviceConfig 本体**：中心端的 device_config 完整定义（含 init_flow）不经协议下发，节点只收到展开后的 edge_devices[] 字段。
- **init_flow 展开**：中心端把 init_flow 步骤解析为二进制命令序列；节点在初始化时以 sendAndWait 执行（见[边缘设备.md §4.4](边缘设备.md)）。
- **WS 事件**：`device_config_created`（notification 总线）；更新影响范围推 `node_config_synced`（见[同步机制.md](同步机制.md)）。
- **受控操作契约**：本模块只**声明**操作集；执行走[边缘设备控制.md](边缘设备控制.md)统一控制域（ChannelCmdV2、dry-run、九项门禁）。

## 7. 验收标准

### 7.1 前端验收

- [ ] 列表：名称 / device_type / 厂商 / 协议 / 默认标记 / 状态 / 分页与过滤（device_type、hardware_type、status）
- [ ] 详情：Connection（JSON 展示）/ Parser（id + options）/ Init Flow（步骤时间线）/ Operations 四区
- [ ] 创建向导：基本信息 → Connection（按协议表单）→ Parser（下拉已注册 + 从驱动树选择）→ Init Flow 步骤构建 → 提交
- [ ] test-parser 面板：输入 mock raw_data（HEX）→ 展示 parsed 结果与生效路径（device_config / driver）
- [ ] 删除有引用配置 → 提示先迁移引用的边缘设备

### 7.2 后端验收

- [ ] 创建：name/device_type/hardware_type 缺失 → 400；重复（device_type, name）→ 409
- [ ] 更新：保存后 EmitConfigChange，引用此配置的边缘设备所在节点收到 ConfigManifest
- [ ] 删除：有边缘设备引用 → 409；无引用 → 软删除（可查询范围缩减，历史保留）
- [ ] `GET /:id/init-flow` 只回 `data: InitFlow`，不泄漏其他字段
- [ ] `POST /:id/test-parser`：HEX 解码 / Parser JSONB 主路径 / driver 回退 / JSON 回退，三条路径均有测试覆盖；解析失败不 500（错误携带于响应）
- [ ] `GET /default/:device_type` 返回 is_default=true 的配置；`POST /:id/default` 正确置标记
- [ ] 单元测试：`go test ./internal/api/... ./internal/deviceinit/...` 通过

### 7.3 集成验收（设备配置 + 边缘设备 + 节点）

- [ ] 创建设备配置 → 创建边缘设备（引用之）→ 节点收到（parser_id + 展开 init_flow）→ 触发 init → 采集开始
- [ ] 修改 init_flow → 引用该配置的所有边缘设备重新 init（5s 内下发）
- [ ] 删除被引用配置 → 409；先删/迁移边缘设备后可删除
- [ ] 前端 `npm run typecheck` + DeviceConfigList.spec.ts 通过
