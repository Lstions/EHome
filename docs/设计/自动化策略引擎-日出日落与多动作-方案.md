## 1. 背景与需求

### 1.1 用户原始需求（引自任务书 §1，不得裁剪）

1. 规则引擎要能**按日出/日落**实现 BMS 的 MOS 开关自动化（当前做不到）。
2. 自动化规则要支持**添加多个操作**（当前一条规则只能一个动作）。
3. 修改**高风险确认制**：所有边缘设备操作分为**两个等级**——普通 / 风险；风险等级在以下场景**都要二次确认**：
   - 用户在设备页**手动开关**操作时；
   - **任何其它使用到该操作的场景**（例：用户在前端制定"日出日落开关 BMS"规则时），界面中该操作的相关元素要**展示风险颜色或提示**，**保存时弹窗列出风险操作并二次确认**。

## 3. 架构/方案设计

### 3.1 日出日落架构

选型依据见 [日出日落天文计算选型-2026-10-14.md](../分析/日出日落天文计算选型-2026-10-14.md)。本节只定架构归属与运行时行为。

#### 3.1.1 经纬度与时区配置的归属层

**四个候选层与本仓现状**：

| 层 | 本仓是否存在 | 候选理由 | 反证/代价 |
|----|-------------|---------|----------|
| 节点（`Node`，`models/models.go:19`） | **存在** | 节点是物理安装位置，一台节点=一个地理点位；同节点下所有边缘设备共享坐标 | 节点迁移（换场地）需重配；多节点同场地时重复填 |
| 边缘设备（`EdgeDevice`，`models/models.go:98`） | **存在** | 粒度最细 | 同节点下多台设备坐标必然相同（同一根总线/同一机柜），冗余且易不一致 |
| 站点（新建实体） | **不存在**（`grep -rniE '\bsite\b\|站点\|station' backend/internal/models/` 无实体定义） | 语义最贴合"一个安装地点多台节点" | 新增实体 + CRUD + 前端页面，**超出本批范围**；且当前系统无站点概念，引入会波及设备/节点/告警多域 |
| 规则（`AutomationRule`） | 存在 | 与"时区在规则上显式标注"的既有文档声称（`自动化策略引擎方案.md:179`）一致 | 每条规则重复填坐标，易填错；同一物理点位的多条规则可能出现坐标不一致 |

**推荐：节点级为权威 + 规则级可选覆盖**（`NULL` = 继承节点值）。

- 新增 `nodes` 列：`latitude`（可空 float64）、`longitude`（可空 float64）、`timezone`（可空 string，IANA 名）。
- 新增 `automation_rules` 列：`latitude` / `longitude` / `timezone`（均可空，`NULL`=继承）。
- 解析顺序：规则值 → 节点值 → **无值则按 §7 O-7 拍板结果处理**（推荐 fail-closed 拒绝保存）。

**为什么不是规则级单独承载**：规则级单独承载会让"同一节点下 N 条日出规则"重复 N 份坐标，任一处填错即产生物理上不可能的行为（例如同一 BMS 的两条规则在不同日出时刻动作）。节点级权威 + 规则级覆盖同时满足"默认正确"与"特例可改"。

**该推荐是待裁决项 O-3，不自行批准。**

#### 3.1.2 计算位置

**结论：后端（Go 进程内）计算，前端与固件均不参与。**

| 候选 | 裁决 | 理由 |
|------|------|------|
| 后端 | **采纳** | ① 触发求值已在后端（`evaluator.go:317` `evalTimeWindows`）；② 计算需与规则缓存、冷却、审计同进程，跨进程会引入一致性问题；③ 后端持有权威坐标（节点表）；④ 纯函数可单测 |
| 前端 | 否决 | ① 前端算出的时刻无法作为**权威**触发依据——页面关闭则规则失效，与"自动化"语义矛盾；② 前端时区来自浏览器，与节点时区可能不同（本仓已有"浏览器时区 unavailable"的场景）；③ 需把坐标下发到浏览器，扩大暴露面 |
| 固件（ESP32） | 否决 | ① 任务书 §2.1 A4 与 `自动化策略引擎方案.md:179` 已裁决"与 ESP32 uptime 无关，一切以后端时间为准"；② 节点离线时规则仍须可判定（见 §3.1.4）；③ 固件加天文计算会侵入只读的 `esp32-collector/` |

**前端仍会用到日出日落时刻**，但只用于**展示**（如规则编辑器里预览"今天的日落是 18:32"）。这走一个只读预检接口（§4.2），前端**不自行计算**。

#### 3.1.3 缓存与日界刷新

**缓存设计**：

- 缓存单位 = `(nodeID, localDate, kind)` → 时刻 + 状态。
- 缓存内容为**次日预计算**：在计算"今天"时一并计算"明天"，避免午夜后首个 tick 前出现无事件可判的空窗。
- 失效条件：坐标变更、时区变更、规则覆盖值变更、节点时区下日期翻转。
- **缓存规模上界（结构性推导）** = 节点数 N × 2 日 × 2 事件（日出/日落）= 4N 项；每项为 `(时刻 time.Time 24B + 状态枚举 1B + 对齐)` ≈ 32 字节 ⇒ 内存 ≈ 128·N 字节。**节点数 N 是部署参数，不是本文档断言的常量**——单机承载量级下该占用为常数级，故无需淘汰策略。
  - 现网规模参考（非本文档的容量结论，仅作量级锚点）：`docs/验证/实机缺陷-node_id冲突与仓库构建产物泄露-2026-10-06.md:88` 记载 "实测：DB 里 3 节点 online"。
  - **勘误留痕**：本节初稿曾以 "11902 节点" 论证规模，该数字系**误引**——`11902` 的真实出处是 UIUX 审计的前端 **DOM 元素计数**（`docs/分析/UIUX审计报告-配置与管理类页面-D3D5.md:105` 探针 `body *` 节点数 = 11902；`docs/分析/UIUX审计合并结论与优化方案-2026-09-13.md:126` `totalEls=11902`），与节点数无关。结论（缓存为常数级、无需淘汰）不受影响，论证已改为上述结构性推导。
- 缓存**必须**在节点删除时清理（与 `evaluator.go:223-234` 的既有清理风格一致），否则删除的节点会残留条目。

**日界刷新**：以**节点时区**的本地日期为"日界"，不是后端进程时区。这是与既有 `time_window` 的关键差异——`evaluator.go:412-414` 用 `now.Location()`（后端本地时区）构造窗口，跨时区部署会整体偏移（§3.1.5 收口）。

**为什么不能只按后端时区**：后端可能部署在 UTC 容器中而节点在 UTC+8。若按后端时区归日，节点本地 23:30 的日落会落到"次日"，日熔断与冷却的当日计数（`planner.go:131`）也会跨错日。

#### 3.1.4 离线、重启、跨时区、极昼极夜的行为

| 场景 | 行为 | 依据 |
|------|------|------|
| **节点离线** | 日出日落规则**照常求值**（时钟驱动不依赖节点数据），执行阶段被 `node_status` gate fail-closed 拦截，落 `failed_gate` | 与既有裁决一致：`自动化策略引擎方案.md:179` "节点离线时时间窗口规则照常求值，执行阶段被 node_status gate fail-closed 拦截" |
| **后端重启** | 冷却锚点由 `last_triggered_at` 持久化恢复（`evaluator.go:121-142`）；**日出日落缓存纯内存，重启后首次 tick 重算**——重算成本是纯函数调用，无外部依赖，故可接受 | 与 `evaluator.go:85-87` 的 `windowStates` 重启清空同族 |
| **重启后首 tick 的边沿语义** | **必须显式定义**。既有 `windowStates` 的保守策略（`evaluator.go:364-371`）：enter 规则首 tick 在窗口内则触发；exit 规则首 tick 若在窗口内则不触发。日出日落是**瞬时点事件**而非区间，不能照搬区间边沿语义——见 §6.2 | 任务书 §2.4 指出的既有软肋 |
| **跨时区部署** | 每条规则按**其解析出的节点时区**归日与求值；不同节点的规则互不影响 | 本方案新增能力，收口 §3.1.5 |
| **极昼/极夜** | 不触发 + **显式审计**（不得静默 return，不得 clamp）。前端事件表可见 | [选型文档 §6.1](../分析/日出日落天文计算选型-2026-10-14.md)；O-6 |
| **节点迁移** | 坐标变更 → 缓存失效 → 次日按新坐标计算；**当日已过事件不补触发** | 避免"迁移后补发历史动作" |

#### 3.1.5 与现有 1min ticker 和 windowStates 的衔接

**衔接方式：复用同一个 ticker，扩展同一个 tick 求值函数。**

现状：`StartWindowTicker`（`evaluator.go:298-313`）每 `WindowTickInterval()`（默认 1 分钟，`evaluator.go:283-293`）调用 `evalTimeWindows(time.Now())`（`:309`），后者只筛选 `TriggerType == time_window` 的规则（`:320-324`）。

**方案**：`LoadRules` 的筛选条件（`evaluator.go:211-212` 的 `trigger_type IN (sensor_threshold, time_window)`）增加 `sun_event`；`evalTimeWindows` 内按 `TriggerType` 分派到 `evalWindowRule` 或新的 `evalSunEventRule`。**不新增 ticker**（新增 ticker 会让两条时钟驱动路径的求值时刻错开，冷却判定与日熔断的"当日"口径出现竞态）。

**tick 粒度充分性**：1 分钟周期 = 事件时刻判定精度上限 1 分钟。与选型的分钟级精度目标一致（[选型文档 §2.3](../分析/日出日落天文计算选型-2026-10-14.md)）。**不收紧周期**——收紧只增加求值次数，无产品收益（`evaluator.go:267-270` 的既有裁决同旨）。

**windowStates 缺陷的收口（任务书 §2.4 第 2 条）**：

现状缺陷（复核后精确表述）：`LoadRules` 只在规则**从缓存移除**时清 `windowStates`（`evaluator.go:229-234`），规则**内容变更但仍在缓存**时旧状态保留。

**收口方案**：`LoadRules` 对每条规则比较新旧值，**任一影响求值的字段变化**即清除该规则的窗口/日界状态。影响字段白名单（显式枚举，不靠"全部字段"——`UpdatedAt` 等非语义字段变化不应清状态）：
`TriggerType`、`TriggerWindowStart`、`TriggerWindowEnd`、`TriggerWindowEdge`、`TriggerSunEventKind`、`TriggerSunOffsetMin`、`Latitude`、`Longitude`、`Timezone`、`Enabled`。

**为什么必须显式白名单**：`LoadRules` 每 30 秒由 `Start` 兜底调用（`evaluator.go:244-257`），若按"任何差异"清状态，则 `UpdatedAt` 或无关字段的漂移会导致状态每 30 秒被清空，边沿反复触发——比原缺陷更危险。

**同时必须清理**：`windowStates`、新的日出日落"上次已触发日"状态、以及缓存条目。

#### 3.1.6 时区字段缺失（A6）的收口

**问题**：`自动化策略引擎方案.md:179` 声称"时区在规则上显式标注（默认 Asia/Shanghai）"，但 `models/automation.go:102-169` 无该列，`evaluator.go:412-414` 用后端进程本地时区。

**收口三步**：

1. **文档更正**：`自动化策略引擎方案.md:179` 改为与实现一致的表述，并指向本文件 §3.1.1 的新字段设计。**不得**保留"声称有时区"的悬空表述。
2. **新增字段**：`automation_rules.timezone`（可空，IANA 名）+ `nodes.timezone`（可空，IANA 名）。**不用 UTC 偏移**——偏移无法表达夏令时（[选型文档 §4](../分析/日出日落天文计算选型-2026-10-14.md)）。
3. **既有 `time_window` 的时区语义**：本次**不改变**既有 `time_window` 的求值时区（仍为后端本地时区），以避免破坏既有规则行为——但**必须**在文档与 UI 中显式标注该差异，并记 O-9 由用户决定是否统一。理由：静默改变既有规则触发时刻是行为破坏（任务书 §4.1 只读红线之外的行为兼容约束）。

**不引入 `EHOME_DEFAULT_TIMEZONE` 环境变量的理由**：隐式全局默认会让"未配时区的规则"在不同部署下行为不同，且无法审计。默认值必须显式落在数据行上或按 O-7 fail-closed。

### 3.2 多动作模型

#### 3.2.1 候选方案

| 方案 | 形态 |
|------|------|
| **M1 独立子表（one-to-many）** | 新表 `automation_rule_actions`（`rule_id`, `seq`, `action_type`, `action_device_id`, `action_id`, `action_params_json`, `action_level`, `enabled`）；`automation_rules` 的动作列**保留但不再写入**（兼容期只读） |
| **M2 JSON 数组列** | `automation_rules.actions_json`（`type:text`），形如 `[{"seq":1,"action_type":"device_action",...}]`；原动作列保留为兼容 |
| **M3 动作实体 + 关联表** | 抽出全局 `actions` 实体，规则与动作多对多 |
| **M4 单动作规则 + 组合规则** | 不引入多动作模型，改为"父规则触发时按序触发 N 条子规则" |

#### 3.2.2 逐项对比

| 维度 | M1 子表 | M2 JSON 列 | M3 实体+关联 | M4 组合规则 |
|------|--------|-----------|-------------|------------|
| **迁移成本** | 中：新表 + 数据回填（每行 1 条子记录）+ 双写期 | **低**：加 1 列 + 回填 JSON | 高：新实体 + 关联表 + 全链路改造 | 低：不动数据模型，只改 planner 分发 |
| **可编译中间态** | 好：子表可先建、先双写、后切读 | 好：加列即编译 | 差：多表同时改 | 好 |
| **幂等** | 好：幂等键可含 `seq`（`action` 维度天然唯一） | 中：需从 JSON 内取 `seq`，且 JSON 无 schema 约束 | 好 | 差：子规则各自幂等，父规则无法保证整体 |
| **部分失败语义** | **好**：每个动作一行审计，天然表达"第 2 个失败" | 中：需在 JSON 里记录状态，或另开审计表 | 好 | 差：失败归因落在子规则事件上，父规则事件无法表达 |
| **审计** | **好**：`automation_events` 可按 `(rule_id, action_seq)` 关联 `command_id`，与既有"事件 JOIN command_executions"（`自动化策略引擎方案.md:259`）同构 | 差：需解析 JSON 才能回答"这条规则今天哪个动作失败了" | 好 | 差：跨两条规则 JOIN |
| **查询** | **好**：SQL 直接 `WHERE rule_id=? ORDER BY seq`；可加 `(rule_id, seq)` 唯一索引 | 差：无法在 SQL 层过滤"含某动作的规则"，只能全表读 + 应用层解析 | 好 | 中 |
| **前端复杂度** | 中：列表接口需聚合子表（一次 JOIN 或两次查询） | **低**：一次读取即得完整规则 | 中 | 中 |
| **DB 约束能力** | **好**：`NOT NULL`、`seq` 唯一、外键可表达 | **差**：JSON 内容无 DB 级约束，非法 JSON 只能应用层 fail-closed | 好 | 好 |
| **与既有 `CanonicalizeParams` 校验的契合** | 好：每行独立校验，与 `handler_automation.go:315-320` 同路径 | 中：需遍历 JSON 数组逐项校验 | 好 | 好 |
| **回滚难度** | 中：需双写期保持两处一致 | **低**：删列即回滚（旧动作列未被覆盖） | 高 | 低 |

#### 3.2.3 推荐：M1 独立子表

**推荐理由**（按权重排序）：

1. **部分失败语义**与**审计**是本需求的核心（任务书要求多动作，而多动作的必然后果是"第 k 个失败"），M1 是唯一能在**不做应用层 JSON 解析**的前提下回答"这条规则的第 2 个动作今天为什么失败"的方案。
2. **DB 级约束**：`seq` 唯一索引 + `NOT NULL` 是"顺序"这一语义的物理保证；M2 的顺序只存在于 JSON 文本中，任何写路径的 bug 都会静默产生重复/缺失 `seq`。
3. **幂等键扩展自然**：既有键 `automation:<rule_id>:<yyyymmdd>:<seq>`（`planner.go:219`）中的 `seq` 语义在 M1 下可平滑重定义为**动作序号**（§3.2.4），无需新解析器。
4. **查询能力**：运营侧"哪些规则包含 set_mos_policy"这类问题在 M1 下是一条 SQL，在 M2 下需全表扫描。

**代价（明示）**：

- 新增 1 张表 + 1 次数据回填迁移；读路径从"单行"变"行 + N 子行"（列表接口需 JOIN 或预加载），前端列表接口的响应组装复杂度上升。
- 需要**双写兼容期**：写入时同时写子表与原动作列，避免回滚时丢数据。
- `automation_events` 需加 `action_seq` 列以关联具体动作（§5.1）。

**非目标（明示）**：

- 不做动作的**并行**执行（顺序语义固定为串行，见 §3.2.4）。
- 不做动作间的**数据传递**（第 2 个动作不能引用第 1 个动作的结果）。
- 不做**条件动作**（每个动作不可带独立条件）——任务书未要求。
- 不做**跨规则的动作复用**（M3 的能力，本批明确不做）。

#### 3.2.4 多动作运行时语义（必须显式定义）

| 语义 | 定义 | 理由 |
|------|------|------|
| **执行顺序** | 按 `seq` **升序串行**执行。任一动作完成后才开始下一个。**不并行** | 并行会让部分失败语义不可判定（无法回答"最终是成功还是失败"）；且多个 BMS 动作并行会争用同一串口通道 |
| **部分失败** | 第 k 个动作失败时：**继续执行剩余动作**还是**中止**？→ **推荐：中止剩余，已执行的不回滚**（记 O-1 待拍板）。理由：对 BMS 这类动作，"关充电 MOS"失败后继续"关放电 MOS"可能造成不可预期的电池状态；中止是保守选择 | 回滚在物理世界不可行（MOS 已切换无法"撤销"，只能再发一次反向命令，那是新动作不是回滚） |
| **整体结果** | 规则级事件结果 = 全部成功→`executed`；部分成功→新枚举 `partial_failure`；全部失败→`failed_dispatch`/`failed_gate`（按失败原因） | 前端需区分"部分成功"（危险状态，需人工介入）与"完全失败" |
| **超时** | 每个动作沿用 `commandexec` 的既有 Deadline（`service.go:52-59` `CommandDeadline()` 默认 2 分钟，`EHOME_COMMAND_DEADLINE` 可覆盖）。**规则级不设额外总超时**——总超时会与单动作 Deadline 竞争，且`Create` 返回的是"已排队"而非"已完成"（`service.go:465-466` 注释：Create 不触碰 transport） | 不引入第二套超时语义 |
| **每日熔断口径** | 既有口径按 **rule** 计数（`planner.go:130-144` `WHERE rule_id = ? AND triggered_at >= ? AND result = ?`）。多动作后**推荐仍按 rule 计数**，但计数单位改为"规则级触发次数"而非"动作执行次数" | 按 action 计数会让 `MaxDailyExec` 的语义从"这条策略今天最多跑几次"变成"这条策略今天最多动几个动作"，与用户直觉不符。**该口径是 O-1 的一部分，待拍板** |
| **冷却口径** | 冷却锚点 `last_triggered_at`（`models/automation.go:164`）语义 = **规则级触发时刻**，与动作数量无关。多动作下**不变** | 锚点已被 `evaluator.go:129-135` 与 `planner.go:712-725` 双向消费；改语义会破坏既有恢复逻辑 |
| **部分失败的锚点**（P2-C 显式裁决，2026-10-14） | 部分失败（`partial_failure`）**不写**冷却锚点 `last_triggered_at`。锚点只在**全部动作成功**（`executed`）后写入，且取**触发时刻** `at`（非动作完成时刻）。 | **理由**：锚点表达的是"该规则**完整触发过**"这一事实。只执行了一部分动作既不是"已完整触发"，也不是"没触发"——写锚点会让规则被静默冷却整个冷却窗，用户在窗口内无法重试恢复（P1-A 的恢复路径被堵死）；不写则行为与"本次触发不成立"一致，用户可立即修复后重试。**失败方向**：宁可让用户重试（可能重复已成功的动作，审计可见 `partial_failure`），不可静默冷却掉一条规则（用户看不到、也无法恢复）。**与部分失败"不回滚"一致**：已执行的物理动作无法撤销，锚点同样不应假装"整条规则已触发"。**实现**：`planner.go` 的 `recordActionFailure` / `recordManualActionFailure` / `recordConfirmFailure` 三条失败路径都不触碰锚点；回归锁见 `TestMultiActionPartialFailureDoesNotWriteAnchor` 与 `TestConfirmEventPartialFailureAbortsRemaining`。 |
| **幂等键** | 既有：`automation:<rule_id>:<yyyymmdd>:<seq>`（`planner.go:219`），其中 `seq` = 当日该规则已 `executed` 行数 + 1。多动作后 **`seq` 重定义为"当日该规则的触发决策序号"，动作维度加入新的段**：`automation:<rule_id>:<yyyymmdd>:<trigger_seq>:<action_seq>`。**`trigger_seq` 的计数口径修正（P1-A/P2-B 修复，2026-10-14）**：不是"当日已 `executed` 行数 + 1"（部分失败不写 `executed` 行 ⇒ 重试时键与上次重合：参数相同则 replay 静默复用旧结果、参数不同则 `ErrIdempotencyCollision` 当天永久失败），而是**当日该规则 `automation_events` 行数 + 1**（被抑制/失败/条件失效的事件一并计入，单位从"成功次数"改为"触发决策次数"）。计数职责只是"单调递增且不复用"，失败方向应为**跳号**而非**复用** | | 既有 `seq` 在单动作下 = 触发序号；多动作后若仍用它表示触发序号，则同一触发内的 N 个动作会**共用同一幂等键**——而 `service.go:493` 的 scope 是 `user:<actor>:edge:<edge>:action:<action_id>:v:<version>`，不同动作的 scope 不同，故实际不会碰撞。**但仍必须加 `action_seq` 段**，因为同一规则的两个动作若指向**同一设备的同一 action_id**（例如"关充电 MOS"两次），scope 相同、键相同 → 第二次会被幂等 replay 吞掉，**静默少执行一个动作** |
| **审计** | 每个动作落**独立**的 `command_executions` 行（由 `commandexec.Create` 天然保证）；规则级落**一条** `automation_events` 行，新增 `action_seq` 列记录失败发生在第几个动作 | 保持"一行 = 一次触发决策"的既有语义（`models/automation.go:173`），同时保留动作级归因 |

**幂等键的具体反例（必须被测试钉死）**：规则含两个动作，均指向设备 A 的 `gpio_set`，参数不同（pin 1 与 pin 2）。若两个动作共用幂等键：`scope` 相同（同 actor、同 edge、同 action_id、同 version），第二个动作的 `Create` 命中 `service.go:495-501` 的既有行 → 比对 `RequestHash`（`:497-499`）→ 参数不同则返回 `ErrIdempotencyCollision`（`:498`），**规则落失败**；参数相同则 replay 返回第一行的结果，**第二个动作被静默吞掉**。两种情况都不可接受。加 `action_seq` 段即消除。

#### 3.2.5 消除 C5 缺陷（自动路径静默失败）

**C5 的精确链路**（复核见 §1.2.3）：`planner.executeDeviceAction` 不带 token（`planner.go:232-240`）→ `service.Create` 的确认门（`service.go:520-531`）→ `consumeConfirmation` 空 token 返回 `ErrConfirmationRequired`（`confirmation.go:170-171`）→ `isGateError` 只认 `ErrActionUnavailable`（`planner.go:376-378`）→ 落 `failed_dispatch`（`planner.go:243-247`）→ 广播 `automation_event`（`planner.go:405-414`）→ 前端 **0 订阅** → 用户无实时感知。

**新设计下的消除（四步，缺一不可）**：

1. **结果枚举显式化**：新增 `confirmation_required` 结果枚举（区别于 `failed_dispatch`），使"被确认门拦住"这一**预期安全行为**在审计上与"传输失败"分离。
2. **错误分类修正**：`isGateError` 扩展为识别确认门错误（`ErrConfirmationRequired` / `ErrRecentAuthRequired` / `ErrConfirmationInvalid`）。**注意**：这不是把确认门归为 gate——而是新增第三类 `confirmationRequiredError(err)`，映射到 `confirmation_required` 结果。保持 `failed_gate` 只表示 availability gate。
3. **前端可感知**：新增 WS 事件 `automation_confirmation_required`，且**必须**在前端订阅（现状：`automation_event` 无人订阅，这是 C5"前端无任何提示"的直接成因）。事件载荷含 `rule_id` / `action_seq` / `action_id` / `event_id`，前端据此弹提示并跳转确认入口。
4. **规则保存前置拦截**：规则编辑器保存时，若规则含风险动作且 `require_confirmed=false`，**预检接口直接拒绝**（§4.2），从源头避免"配了一条永远不会执行的规则"。这是比事后通知更强的收口——C5 的根因之一是用户不知道自己的规则不可能成功。

**与 §7 O-2 的关系**：若 O-2 拍板"风险动作可被自动执行（白名单）"，则第 4 步的拒绝条件需按白名单调整；第 1-3 步在任何选项下都必须做（因为白名单之外的动作仍会遇确认门）。

### 3.3 风险分级：4 级 → 2 级的单一事实源收敛

#### 3.3.1 收敛原则

**单一事实源的定义**：风险等级在系统中只有**一处**定义（一个 Go 类型 + 一个枚举集合），所有其它位置（前端、文档、审计展示、仿真断言）都从它**派生**，不得出现第二份字面量。

#### 3.3.2 映射表

| 现有 4 级 | 驱动侧出现次数（口径 A，§1.2.5 N1） | 映射到 2 级 | 确认要求 |
|----------|-----------------------------------|-----------|---------|
| `low` | 12 | **普通** | 无 |
| `medium` | 7 | **待裁决 O-5**（推荐：**风险**） | 有 |
| `high` | 11 | **风险** | 有 |
| `critical` | 6 | **风险** | 有 |

**`medium` 的取舍（O-5）**：
- 现有语义：`confirmation.go:53-55` `confirmationRequired` 对 `medium|high|critical` 都要求确认；但 `service.go:521-523` 对 **system actor 豁免 medium**。
- 若 medium → **风险**：与现有"人工路径要确认"一致，但会**改变** system 路径行为（现在豁免 medium，收敛后若"风险必须确认"则不再豁免）——这是**行为破坏**，必须记 O-2/O-5。
- 若 medium → **普通**：保持 system 路径现状，但**改变**人工路径行为（现在要确认，收敛后不要）——同样破坏。
- ⇒ **无论怎么选都有行为变更**，故这是必须用户拍板项，不是技术细节。

#### 3.3.3 落点与防漂移

**推荐落点**：

1. **唯一枚举定义**：在 `backend/internal/deviceaction` 包定义 `type RiskLevel string` 与两个常量（`RiskNormal` / `RiskElevated`），以及 `func (r RiskLevel) RequiresConfirmation() bool`。这是**唯一**判定确认要求的地方。
2. **驱动字面量的处置**：36 处驱动字面量（口径 A）**不立即改写**（改写会波及 4 个文件 36 处，且 `ControlAction` 是驱动出厂声明）。改为：`deviceaction.Registry.Register` 在 `definition.go:96` 的既有校验链中，把 4 级字面量**归一化**为 2 级（`allowedRisk`（`:186-193`）改为返回归一化后的 `RiskLevel`）。即"4 级是驱动的出厂方言，2 级是系统的对外契约"。
3. **对外契约只暴露 2 级**：`Definition.Risk`（`definition.go:69`）序列化给前端的值改为 2 级。**这是破坏性修改**（前端现有 `risk === 'high'` 判断失效）——列入 §3.4。
4. **前端不出现 risk 字面量**：前端只用后端下发的 2 级值做**样式映射**（一个 `Record<RiskLevel, Style>` 表），且加**防漂移门禁**：一条可失败检查，断言 `frontend-shared/src/` 下不出现 `'low'|'medium'|'high'|'critical'` 作为 risk 比较的字面量（白名单：测试夹具）。

**为什么不让驱动直接写 2 级**：36 处改动面大、且驱动的 4 级语义承载了"严重度排序"信息（`critical` 与 `high` 在 UI 文案上原本不同："严重风险" vs "高风险"，`DeviceControlPanel.vue:40-41`）。保留驱动方言 + 归一化层，既满足用户"两级"要求，又不丢失驱动层的严重度信息（可用于未来再细分）。

#### 3.3.4 防漂移门禁（必须可失败）

| 门禁 | 检查 | 反向验证（注入违规必须失败） |

### 5.2 迁移方式与回滚

**本仓迁移机制（实测）**：`backend/internal/database/gorm.go:57` `func AutoMigrate() error` → `:65` `DB.AutoMigrate(...)`；由 `cmd/server/main.go:70` 与 `cmd/ehomectl/main.go:53` 调用。另有**幂等手工迁移**先例：`backend/internal/database/migrate_ota_collector_id.go`（`MigrateOTATaskDropLegacyCollectorID`）。

**关键约束（来自既有事故记录）**：`migrate_ota_collector_id.go:14-25` 记载——"PostgreSQL 不会因为 AutoMigrate 就把这列去掉"，且"测试默认跑 SQLite 内存库，压根不存在这列；只有老 PG 库才有"⇒ **模型与代码都自洽，唯一的问题是旧库 schema 漂移**。

**本方案的迁移设计**：

| 项 | 方式 | 回滚 |
|----|------|------|
| 新表 `automation_rule_actions` | AutoMigrate 建表 | `DROP TABLE`（幂等，数据可重建） |
| 新列（全部可空） | AutoMigrate 加列 | `DROP COLUMN`（幂等，参照 `migrate_ota_collector_id.go` 范式） |
| 数据回填（原动作列 → 子表） | **幂等**手工迁移：仅当该 `rule_id` 无子行时插入 `seq=1` | 无需回滚（原列未动） |
| 唯一索引 `(rule_id, seq)` | AutoMigrate | `DROP INDEX` |

**回填幂等性判据**：`INSERT ... WHERE NOT EXISTS (SELECT 1 FROM automation_rule_actions WHERE rule_id = ?)`。可失败验证见 §8 A-19。

**PG/SQLite 双库差异（必须显式处理）**：`DROP COLUMN` 在 SQLite 需 `ALTER TABLE ... DROP COLUMN`（SQLite ≥ 3.35 支持）；本仓 SQLite 驱动为 `mattn/go-sqlite3 v1.14.48`（`go.mod`），需在迁移中按方言分支或统一用"仅 PG 执行、SQLite 空转"（`migrate_ota_collector_id.go:27` 的做法："只在列存在时执行，SQLite（无此列）与已修好的库都是空转"）。

## 6. 状态机

### 6.1 规则求值状态机（既有，`evaluator.go:64-72`）

既有 `sensor_threshold` 的 armed → triggered →（冷却到期）→ armed 不变。**本方案不改**。

### 6.2 新增：日出日落求值状态机

日出日落是**瞬时点事件**，与区间窗口的本质差异：区间有"在/不在"，点只有"已过/未过"。

```
per (rule, node-local-date):
  未求值 ──(tick 且 now >= eventTime)──▶ 已触发
  未求值 ──(tick 且 now <  eventTime)──▶ 未求值
  已触发 ──(节点本地日期翻转)──────────▶ 未求值（新一日）
  未求值 ──(极昼/极夜)─────────────────▶ 本日不触发（落审计，状态保持"未求值"）
```

| 转换 | 条件 | 副作用 |
|------|------|-------|
| 未求值 → 已触发 | `eventTime + offset <= now` 且**本次 tick 之前未触发过本日事件** | 提交 Planner；写冷却锚点（`recordExecuted` 同事务） |
| 已触发 → 未求值 | 节点本地日期 `!= ` 上次触发日期 | 无（新一日） |
| 未求值 → 未求值 | `now < eventTime` | 无 |
| 任意 → 本日不触发 | 状态为 `always_up`/`always_down` | **落一条显式审计**（`suppressed_no_solar_event`），每节点每日本事件只落一次（防刷量，参照 `recordSuppressed` 的同窗节流，`evaluator.go:552-575`） |

**重启后首 tick 的语义（必须显式）**：区间窗口的既有保守策略（`evaluator.go:364-371`）不适用于点事件。本方案：

- 首 tick 时若 `now >= eventTime` **且** 节点本地日期 == 当日 → **不触发**（保守：无法区分"重启前已触发"与"重启错过了"）；
- 依据：冷却锚点 `last_triggered_at`（`models/automation.go:164`）已在 `rebuildCooldowns`（`evaluator.go:121-142`）恢复，若当日已触发过，冷却判定会拦；若未触发过，则说明重启发生在事件时刻之前——此时 `now >= eventTime` 不成立。**故"保守不触发"与锚点恢复配合后不会漏触发真实事件**。

**该语义必须被测试钉死**（§8 A-3 的反向验证）。

### 6.3 多动作执行状态机

```
触发 ──▶ [动作1] ──成功──▶ [动作2] ──成功──▶ ... ──▶ executed
              │                  │
              │失败               │失败
              ▼                  ▼
        partial_failure（中止剩余，记录 failed_seq）
              │
        全部失败（动作1 即失败）──▶ failed_dispatch / failed_gate / confirmation_required
```

| 转换 | 结果枚举 |
|------|---------|
| 全部动作成功 | `executed` |
| 第 k 个失败且 k < N | `partial_failure`（`action_seq=k`） |
| 第 1 个失败 | `failed_dispatch` / `failed_gate` / `confirmation_required`（按原因，`action_seq=1`） |
| 日熔断命中 | `suppressed_daily_limit`（**规则级**，不进入动作循环） |
| 冷却命中 | `suppressed_cooldown`（规则级） |

### 6.4 风险确认状态机（不变，仅判定源收敛）

既有 `pending_confirm` →（人工确认）→ `executed` / `failed_*` /（24h）→ `expired` 不变（`planner.go:831-928`、`:948-963`）。**唯一变化**：`needsConfirmation` 的判定源从 `service.go:520-523` 的字面量比较改为 `RiskLevel.RequiresConfirmation()`。
