## 0. 一页纸摘要

### 0.1 与 v1.0 的差异（本版是破坏性更新）

| 项 | v1.0（渐进式） | **v2.0（本版）** |

## 3. 数据迁移（本版核心，v1.0 缺失）

> 破坏性更新允许「数据不迁」，但产品裁决是「**做好数据迁移就行**」——
> 所以必须明确：**哪些数据要迁、迁到哪、怎么校验**。

### 3.1 迁移需求分析（关键结论：**几乎不需要迁**）

| 数据 | 现在在哪 | 是否需要迁 | 理由 |
|---|---|---|---|
| **解析值（时序）** | `telemetry_frame` + `telemetry_rollup_1m` | ❌ **不需要** | 已在正确的表里，本方案不动这两张表 |
| **原始字节** | `device_data.data_json.raw/raw_hex` | ⚠ **按裁决不迁** | 产品裁决「原始数据不入库」 |
| **帧元数据**（channel_id/command_index/error_code） | `device_data.data_json` | ❌ **不需要** | 帧表有 `slot_id` + 时间戳；error_code 由日志承载 |
| **StringValue**（hardware_version/serial_number） | `device_data.data_json.str_values` | ❌ **不需要** | 生产实测**全表 0 行** |

### 3.2 唯一需要验证的迁移问题：帧表是否覆盖了所有解析值？

生产实测（按小时对比两张表的时间覆盖）：

```
device_data 覆盖小时数:        800
telemetry_frame 覆盖小时数:    753
device_data 独有小时数:         47  （2026-10-01 23:00 ~ 2026-10-18 08:00）
device_data 独有小时的行数:  93,255
```

**这 93,255 行是什么？**

```sql
-- 全部是 device_id = 0 的 db_persist 行（raw 原始字节），含 sensors 的 0 行
SELECT sum(n), sum(dev0), sum(sensors) FROM (按小时统计) ...
-- → 93,255 行，其中 device_id=0: 93,255 行，含 sensors: 0 行
```

即：**这段「缺失」里根本没有解析值**，只有原始字节（2026-10-01~10-02 是系统首日，
10-04 之后 `telemetry_frame` 才成为主写入路径）。

**三项决定性证据**（生产实测，全部通过）：

```sql
-- ① 两表设备集合完全一致（没有任何设备只在 device_data 里）
SELECT string_agg(DISTINCT device_id::text, ',' ORDER BY device_id::text) FROM device_data WHERE device_id > 0;
-- → 12,13,14,15,2
SELECT string_agg(DISTINCT device_id::text, ',' ORDER BY device_id::text) FROM telemetry_frame;
-- → 12,13,14,15,2   ✅ 完全一致

-- ② 只在 device_data 里出现的设备：0 个
SELECT dd.device_id FROM (SELECT DISTINCT device_id FROM device_data WHERE device_id>0) dd
WHERE NOT EXISTS (SELECT 1 FROM telemetry_frame f WHERE f.device_id = dd.device_id);
-- → 空  ✅

-- ③ 2026-11-07 的老数据迁移任务已全部完成
SELECT table_name, state, count(*) AS parts, sum(frames_done) AS frames
FROM telemetry_backfill_progress GROUP BY 1,2;
-- → unified_data | done | 6 个分区 | 3,454,432 帧   ✅
```

⇒ **结论：解析值数据零迁移风险。** 帧表已完整覆盖所有设备的所有解析值，
**不需要搬运任何数据**，只需「校验 + 备份 + 删表」。

### 3.3 迁移作业（真正要做的事：校验 + 备份 + 删表）

**不是数据搬运，而是「删表前的完整性校验 + 备份」**：

#### 步骤 1：冻结写侧（靠部署顺序，无开关）

```
旧容器 running（继续写 device_data）
   ↓
1. 停旧容器（写侧停止，零新增）
   ↓
2. 备份（pg_dump，含 device_data 全量）
   ↓
3. 执行校验 SQL（§3.4 四条全绿才继续）
   ↓
4. DROP TABLE device_data CASCADE
   ↓
5. 起新容器（新代码已无 device_data 引用，不会 42P01）
```

> **为什么必须「先停再删再起」**：如果先起新容器，会出现「表存在但无人写」的中间态；
> 且 DROP 时新容器可能仍有连接持有该表的锁。顺序执行是破坏性更新的唯一正确姿势。

#### 步骤 2：备份（必须成功）

```bash
# 必须做（即使不做冷归档）
docker compose exec -T postgres pg_dump -U ehome -d ehome \
  --format=custom --compress=6 > backups/ehome_before_dd_drop.dump

# 可选：只归档 device_data（若需要冷归档）
docker compose exec -T postgres psql -U ehome -d ehome \
  -c "\copy (SELECT * FROM device_data) TO '/tmp/device_data.csv' CSV HEADER"
# → 3.4 GB CSV，压缩后约 400 MB
```

#### 步骤 3：DROP

```sql
DROP TABLE device_data CASCADE;   -- 连同 16 个分区一起删
VACUUM FULL node_logs;            -- 顺手清理（0 行占 17 MB）
```

**耗时**：DROP 是元数据操作，**秒级**（不重写数据页）。

### 3.4 删表前校验清单（四条必须全绿）

## 4. 可观测性（「日志排查」的完整设计）

> 产品裁决「解析失败打印日志就好了」—— 但**当前日志不足以支撑排查**，必须先补齐。

### 4.1 现状缺口（逐条实测）

| 缺口 | 现状 | 证据 |
|---|---|---|
| **① `ErrorCode != 0` 完全不落日志** | 只 `metrics.DataReportErrors.Inc()`，零日志 | `consumers_light.go:49-55` |
| **② 解析失败不带原始字节** | `logger.Infof("[%s] Failed to parse data: %v", ...)` | `consumers_heavy.go:415` |
| **③ 用 INFO 级且生产 0 条** | `docker logs --since 24h \| grep -c "Failed to parse data"` = **0** | 实测 |
| **④ 无结构化字段** | 格式化字符串，无法按 reason/device 聚合 | 同上 |
| **⑤ docker 日志无轮转** | `LogConfig={"Type":"json-file","Config":{}}`，单容器 24h 已 **67 MB** | `docker inspect` |

```go
        "channel_id",     evt.ChannelID,
        "command_index",  evt.CommandIndex,
        "reason",         string(reason),   // 有界枚举（5 值），可聚合
        "adapter",        outcome.Adapter,  // 新增字段
        "err",            outcome.Err,
        "raw_len",        len(merged),
        "raw_hex",        hex.EncodeToString(truncateBytes(merged, 128)),
    }
    if ingestReasonIsConfigDefect(reason) {
        logger.Warn("databus: decode failed (config defect)", fields...)
    } else {
        logger.Warn("databus: decode failed (data defect)", fields...)
    }
    c.reassembler.Consume(evt.DeviceID, uint32(evt.RequestID))
    return
}
```

⚠ `decodeOutcome` 当前没有 `Adapter` 字段，需从 `ingest.DecodeError` 提取
（`ingest/errors.go:44` 已有 `Adapter string`），改动约 3 行。

#### 4.2.3 docker 日志轮转（**必须做**）

```yaml
# docker-compose.yml — ehome 服务
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "5"
```

依据：当前 67 MB/24h。50m × 5 = 250 MB 可容纳约 3.7 天。
**这是删 DB 取证后的必须配套**，否则日志会成为新的无界增长。

### 4.3 日志字段规范与排查手册

```
WARN  databus: decode failed (data defect)  node_id=F0F5BD02DD84 edge_device_id=14
      device_type=jiabaida_bms channel_id=10 command_index=0 reason=decode_failed
      adapter=driver err="jiabaida: [3] checksum mismatch" raw_len=78
      raw_hex="dd0f0047001536000064268e268e00010e050d12...f78477"
```

| 问题 | 查法 |
|---|---|
| 某设备图表没数据 | ① `grep "edge_device_id=<id>" \| grep "decode failed"` ② 查 `/devices/:id/history` ③ 查 `telemetry_rollup_coverage` |
| 某命令一直失败 | `grep "command_index=<n>" \| grep "decode failed"` → 检查 `config_templates` |
| 设备 16 从来没数据 | `grep "edge_device_id=16" \| grep "rejected at ingest"` → `error_code=1` |

### 4.4 ⚠ 能力损失与缓解（需决策）

| 能力 | 现在 | 改造后 |
|---|---|---|
| 事后回放任意一帧原始字节 | ✅ `SELECT data_json FROM device_data` | ❌ 仅日志窗口（约 3.7 天） |
| 解析成功但数值错误的追溯 | ✅ 可对比 raw 与解析值 | ❌ 无法追溯 |

**缓解方案（推荐 A）**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 保留 `telemetry_frame.raw` 列，**只在关键帧填充** | **+0.13 MB/天**，可 SQL 查询 |
| B | 关键帧 raw 打进日志 | +1.6 MB/天（hex 膨胀），不可查询 |
| C | 接受损失 | 0 |

> **为什么 A 更好**：`raw` 列本来就在（`models/telemetry_frame.go:56`），
> 当前生产 **4,022,931 行里只有 5 行非空**（实时写路径从不填，只有回填填）。
> 关键帧实测 **10,270 帧/24h（7.1%）**，原始帧平均 78~256 B
> ⇒ 填满约 **+0.13 MB/天**，比打日志更省且**可 SQL 按时间/设备查询**。
