## 一、当前数据流实况（我逐行核对的）

### 1.1 真实链路

```
设备上报帧
  ↓  databus.DataEventBus
SensorParserConsumer.consume()
  ├─ 摄入边界门（节点注销 → 拒收）
  ├─ 解析（两条路径）
  │    ① ConfigParser(device_configs.parser)  ← 优先，非标定驱动
  │    ② Driver(edge_devices.type)           ← 兜底
  │        └ CalibrationAware / CommandAware 两个子接口分支
  ├─ logicalTarget 解析（datalifecycle.ResolveMergeTarget）
  ├─ 落库 unified_data（含 logical_device_id 双写）
  └─ 解析成功 ⇒ 4 个 sink 依次触发
       ├─ latestSink(record)                       → api.SetLatestValue + sensorfield.Observe
       ├─ alertSink(edgeID, fields, at)            → alert.Evaluator
       ├─ automationSink(edgeID, fields, at)       → automation.Evaluator
       └─ sourceHealthSink(edgeID, names, at)      → datasourceSvc.MarkSuccess + groupSvc.MarkSuccess
```

### 1.2 关键事实（决定了方案形态）

| 事实 | 证据 |
|---|---|
| **解析产物没有统一的中间抽象** —— `parser.Field` 与 `drivers.SensorData` 是两套类型，在 consumer 里手工转换 | `consumers_heavy.go:355-360` |
| **`data_sources` 不参与数据流** —— 它是纯配置台账，4 个 sink 里只有 `sourceHealthSink` 碰它，且只用来 `MarkSuccess` 记状态 | `grep 'DataSource' automation/ alert/` → 零引用 |
| **主备已经有两套实现** —— `datasource.Service`（R1–R11，消费 `data_sources`）与 `GroupService`（R1–R11，消费 `source_groups`），后者是超集 | 两处 `maybeFailover` |
| **规则只认 `source_groups`** —— `SourceKind` 只有 `edge_device` / `source_group`，**没有** `data_source` | `models/source_ref.go:19-24` |
| **前端两页独立** —— `/data-sources`（882 行）与 `/source-groups`（563 行），菜单两个条目 | `menuModel.ts:46-47` |

### 1.3 问题诊断

你说的「数据流架构要理顺」，我理解成三个具体的断裂点：

| # | 断裂 | 后果 |
|---|---|---|
| **D1** | 解析产物类型不统一（`parser.Field` vs `drivers.SensorData`），在 consumer 里手工转换 | 新增解析后端要改 consumer，耦合点集中在一处 |
| **D2** | `data_sources` 既不喂规则、也不参与数据流，却占着「数据源」这个名字 | 用户以为它是数据入口，实际是台没人读的账本；两套主备状态机并存 |
| **D3** | 没有「数据源」这一层的**运行时对象** —— 数据从设备直接跳到规则/告警 | 无法表达「同一类别多设备」的统一来源，规则只能绑单设备或绑组 |

**D3 是核心。** 你要的「数据源层」目前**在运行时不存在**，只有一张空配置表。

## 三、L1 统一接入层设计（「灵活、兼容性强」的落点）

### 3.1 现状问题

```go
// 两套解析产物
type parser.Field struct { Name string; Value float64; Unit string; StringValue string }
type drivers.SensorData struct { /* 另一个结构 */ }

// consumer 里手工转换（consumers_heavy.go:355）
sensorData = make([]parser.Field, len(drvData))
for i, sd := range drvData {
    sensorData[i] = parser.Field{Name: sd.Name, Value: sd.Value, Unit: sd.Unit, StringValue: sd.StringValue}
}
```

问题：新增解析后端（如 Modbus 寄存器表、MQTT JSON、OPC UA）时，**必须改 consumer**。

### 3.2 目标接口

```go
// internal/ingest/adapter.go —— 接入层契约（唯一扩展点）
type Sample struct {
    EdgeDeviceID    uint
    LogicalDeviceID *uint
    At              time.Time
    Fields          []Field          // 统一字段（见下）
    Method          string           // 自描述："ConfigParser(x)" / "Driver(prs3001)" / "Modbus(...)"
    Quality         Quality          // ok / partial / degraded
}

type Field struct {
    Name        string
    Value       float64
    Unit        string
    StringValue string   // 兼容既有（硬件版本/序列号等非数值）
}

// Adapter 是**唯一**扩展点：新解析后端只需实现它。
type Adapter interface {
    // Supports 报告能否处理该设备（由 consumer 用于选择，替代现在的硬编码 if/else）
    Supports(ctx SupportContext) bool
    // Decode 解析原始帧为统一 Sample
    Decode(ctx DecodeContext, raw []byte) (Sample, error)
    // Name 用于 Method 自描述与指标标签（有界枚举）
    Name() string
}
```

### 3.3 为什么这样设计（对照你的「低耦合 + 灵活 + 兼容」）

| 要求 | 设计点 |
|---|---|
| **低耦合** | consumer 只依赖 `Adapter` 接口，不 import 任何具体解析实现。`internal/ingest` 不依赖 `databus`（方向单向） |
| **灵活** | 新增后端 = 新增文件 + 注册一行，**不改 consumer**。`Supports` 让选择逻辑从硬编码 if/else 变成声明式 |
| **兼容性强** | 现有两个后端**先包一层 adapter 直接上线**，行为零变化；`parser.Field` 保留 `StringValue` 兼容非数值字段；`Method` 字符串保留原格式（`Driver(prs3001)`）让既有日志/审计不受影响 |
| **可测试** | adapter 是纯函数（raw → Sample），单测无需 DB/databus |

### 3.4 迁移策略（关键：不破坏现有行为）

```go
// 现有两条路径各包一层 adapter，行为逐字节等价
internal/ingest/adapter_configparser.go  // 包装 parser.NewConfigParser
internal/ingest/adapter_driver.go        // 包装 drivers.Driver（含 Calibration/Command 子接口）
```

consumer 里把现在的 if/else 换成：
```go
for _, a := range c.adapters {          // 按注册顺序
    if !a.Supports(sctx) { continue }
    sample, err := a.Decode(dctx, merged)
    if err == nil { break }
}
```

**验收判据**：改造前后对同一批真实帧，`unified_data` 落库结果**逐字段相同**（用生产 30 分钟数据回放对比）。

## 四、L2 来源层设计（「数据源」成为运行时对象）

### 4.1 核心：SourceRegistry

```go
// internal/source/registry.go
type Handle struct {
    LogicalDeviceID uint
    Category        string
    GroupID         uint   // 0 = 无来源组（单设备直连）
    // Authoritative 报告这台设备的这一帧是否代表该来源
    Authoritative func(edgeDeviceID uint) bool
    // OnSuccess 记录健康（替代现在两处 MarkSuccess）
    OnSuccess func(edgeDeviceID uint, fields []string, at time.Time)
}

// 快照式（与 sourceref.Registry 同范式：atomic.Pointer + 事务后发布）
type Registry struct { snap atomic.Pointer[map[key]*Handle] }

func (r *Registry) Resolve(edgeDeviceID uint, category string) (*Handle, bool)
```

### 4.2 它解决什么

| 现在 | 之后 |
|---|---|
| 4 个 sink 各自 `MarkSuccess`，两套服务各跑一套状态机 | **一个** Registry 统一回答「这帧算不算权威」，两处状态机合并为一处 |
| `data_sources` 空表，用户困惑 | `data_sources` 由 Registry 自动投影，页面直接读它，**永不空**（有设备就有行） |
| 规则只能绑 `edge_device` 或 `source_group` | 规则绑 `source_group`（主备）或 `edge_device`（直连），语义清晰无歧义 |

### 4.3 与来源组的关系（明确边界）

```
来源组（用户手工创建，可编辑）
  ├─ primary_backup：定义「多台设备里谁是 active」
  └─ composite     ：定义「多台设备的值如何合并」
        │
        ▼ 发布快照
SourceRegistry（自动构建，只读）
  ├─ 有来源组 ⇒ 引入组语义（active 判定 / 合并求值）
  └─ 无来源组 ⇒ 单设备直连（存量语义，行为不变）
```

**这条边界正是你要的**：来源组是唯一可编辑入口；数据源/Registry 全部自动。

## 五、前端整合设计

### 5.1 页面结构

```
数据来源（单页，两个 Tab）
├─ Tab1 「来源总览」  ← 原 /data-sources，**只读**
```

### 5.3 「只读」的严格含义

|---|---|---|
