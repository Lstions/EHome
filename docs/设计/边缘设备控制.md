## 1. 架构分层（控制域现状）

```
驱动声明 → 目录装配 → 执行域
────────────────────────────────────────────────
① 驱动层（drivers/，声明）
   Driver 接口: Info / ControlActions() / Verifier / PlanCompiler
   动作声明: Action Schema v1（读/写/动作、验证方式、风险分级、
   AvailabilityCode 证据门禁、bounded batch 能力声明）

② 目录层（deviceaction/，装配）
   Action Catalog: 九项可用性检查（注册/白名单已删→实现即默认启用/
   CurrentEngineAllows/证据门禁/capability 刷新）
   PlanCompiler: 动作 → CompiledControlPlan（bounded_sequence 步进、
   verifier 校验、address 绑定族 ControlActionPlanCompilerForAddress）

③ 执行域（commandexec/，执行）
   CommandExecution: QUEUED → DISPATCHED → ACCEPTED → VERIFYING → 终态
   Outbox/Inbox: 持久化 + 幂等重投（at-least-once）+ boot_id 绑定
   设备互斥锁 + critical at_most_once 限流
```

## 2. 核心设计原则

1. **后端承担复杂度**：业务编排、厂商协议解析、权限、持久化、验证全在中心端；ESP32 只做有界、静态内存优先的通道字节事务执行——**不实现通用工作流语言、JSON 规则引擎或厂商协议解释器**。
2. **资源原则**：ResourceReport 是 V2 命令准入依据（最新报告 + boot_id 一致 + command_engine 声明）。
3. **实现即默认启用**（2026-08-14 起）：删除 EHOME_ENABLED_DEVICE_ACTIONS 白名单。动作默认启用判定 = `verifier != nil && Verification != "" && AvailabilityCode == ""`。DeviceControlV2Enabled 仅作 kill switch（false 时 dispatcher 整个不启动）。
4. **证据门禁**：AvailabilityCode（protocol_unverified 等）的写动作——可见但不可执行，schema 冻结、开放执行待证据。BMS F2/F3/GB3024 setter 无一票 evidence。
5. **身份四元组**：command_id + payload_digest + attempt + boot_id 唯一标识一次命令；传输重投与物理 attempt 分离；Final 才是执行终态，replayed=1 返回缓存终态。

## 3. 执行状态机

```
QUEUED → DISPATCHED → ACCEPTED → VERIFYING → SUCCEEDED
   │          │            │            └──────► FAILED（含 error_code）
   │          │            └── 超时未 ACK（deadline 过期）
   │          └── MQTT QoS1 投递（control topic）
   └── 门禁拒绝 / dry-run 失败（不进入执行域）

取消与裁决：UNKNOWN 语义无冲突；批步骤 batch_step 支持
bounded_sequence（bms.restart、rain.reset 等多步动作编译为批）
```

## 5. dry-run 与验证链

1. 目录九项检查：动作存在、目标可见、证据门禁、CurrentEngineAllows（协议版本/引擎能力）、设备/通道/节点可用。
2. **编译**：CompileControlPlan / CompilePlanForAddress（地址绑定版）→ 步进序列 + 每步 verifier。
3. **双重 verify 入口**（同一实现源）：VerifyControlAction（非地址）与 VerifyControlActionForAddress（dispatch 实际路径）——两者都测，单入口实现（verifyBatchSteps / verifyBatchForAddress 逐帧验址）。
4. dry-run 结果展示：预计步数、读回校验点、风险分级。确认后才进入执行域（IssueConfirmation/Create）。

## 6. 幂等、重放与结果不确定性

- **Outbox 持久化**：命令先落库再发 MQTT（QoS1 control topic）；中心端重启后按 Outbox 重投。
- **Inbox**：节点 RAM 槽位 at-most-once（V2 槽位状态机），身份四元组比较（16B digest）拒重放。
- **ACK-before-Final**：0x16 接纳 ≠ 执行成功；0x17 Final 唯一终态；Final 丢失时中心端按四元组重查询或超时裁决。
- **bounded_sequence + finally**：多步写序列即使中途失败也执行 finally（退出工厂模式等）。读回在参数生效点之前完成（协议依据注释 jiabaida.go:589-592）。
- **applySideEffect**：地址/波特率 setter 在可信 Final 后同步 EdgeDevice/DeviceConfig 与 bus_config 并重下发 manifest，读回在 ConfigResult in_sync 后执行。

## 7. 安全、门禁与审计

| 门禁 | 现状 |
|------|------|
| BMS（嘉佰达） | 写动作 evidence 门禁冻结：F2/F3 整块、0xE1 MOS、reset 等 15 个未实机验证动作 protocol_unverified 可见不可执行；bms_restart 已 0x0E 指令待实机确认 |
| GB3024 | CRC 缺黄金向量 → setter 不注册（只读 11 action） |
| SN-3001 | set_rain_sensitivity/set_device_address/set_baud_rate 已实机闭环（地址/波特率写后跨生命周期读回对账，同 batch 读回不可行——物理参数域已切换） |
| critical 动作 | at_most_once 限流 + 设备互斥锁 + topic 隔离（control QoS1） |
| raw diagnostics | 生产 410；channel 直写走终端 WS（有审计） |
