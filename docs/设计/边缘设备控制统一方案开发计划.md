## 1. 开发目标

建立一条可靠、可审计、可恢复的边缘设备控制链路：

```text
ActionDefinition
→ 后端参数/权限/前置条件校验
→ 持久化 CommandExecution + Outbox
→ ChannelCmdV2
→ ESP32 有界单步字节事务
→ 目标设备协议响应
→ 后端验证
→ 状态、审计、WebSocket 和前端时间线
```

只有确有 Channel 原子和 finally 清理需求时，才增加：

```text
ChannelBatchCmd（固定步骤上限，无分支、循环、脚本和厂商语义）
```

本计划不以“同时实现所有设备动作”为首要目标。第一目标是先完成一个只读动作的端到端可靠闭环，再逐级开放普通 setter 和破坏性动作。

## 2. 实施原则

### 2.1 纵向切片

每个可合并阶段都必须形成可验证的纵向能力，避免长期存在只有数据库、只有固件或只有前端的半成品分支。

推荐切片顺序：

1. 后端领域模型和只读 Action Catalog；
2. ChannelCmdV2 单步只读闭环；
3. 前端只读动作与操作时间线；
4. 逆变器普通绝对值 setter；
5. BMS MOS 完整双 bit policy（仅在硬件确认无需工厂模式时）；
6. bounded batch，以及需要工厂模式时的 BMS MOS；
7. 雨量清零和 reboot/reset。

### 2.2 Fail-closed

- 未冻结协议、节点能力缺失或 ResourceReport 过期时，动作 `available=false`；
- 旧固件不支持 ChannelCmdV2 时，不开放危险写；
- 无法映射到可信 Driver action 的旧 raw Operation 禁止执行；
- 审计或 NVS seen-ring 写入失败时，高风险动作拒绝执行；
- UNKNOWN 不自动重试 at-most-once 动作。

### 2.3 ESP32 性能优先

- 复用现有 per-bus FreeRTOS 队列和 bus worker；
- 不新增逐命令 task，不要求 PSRAM；
- 普通动作只实现单步命令；
- RAM replay cache 使用编译期固定容量；
- 普通命令不写 NVS；
- 默认每个命令只有 accept/reject 和 final；
- batch 使用固定 slot/arena，队列只传小 descriptor 或 slot index；
- 任何 step、TX/RX、总响应和 timeout 上限都由 ResourceReport 上报并由后端校验。

### 2.4 后端承担复杂度

权限、schema、Driver 编译、厂商 ACK 解析、状态机、Outbox/Inbox、验证、审计和恢复都在后端完成。ESP32 不理解 BMS、逆变器、雨量计或业务动作名称。

## 3. 发布策略与功能开关

开发期建议使用两个控制开关，具体配置载体在 Phase 1 冻结：

| 开关 | 默认值 | 作用 |
|---|---|---|
| `device_control_v2_enabled` | false | 是否注册新 Action/Execution API 和 dispatcher |
| `legacy_device_write_mode` | disabled | 只允许 `disabled` 或 `bridge`；禁止保留 `direct` fire-and-forget 模式 |
| `raw_diagnostics_enabled` | false | 是否允许 raw channel/terminal 写；即使开启也要求独立 capability、理由和审计 |

发布规则：

1. 新数据库表和只读 API 可以先部署，但 dispatcher 保持关闭；
2. 节点只有上报 `supports_channel_cmd_v2=true` 才进入单步灰度；
3. bounded batch 由节点能力和动作需求共同开启，不设置全局强制开启；
4. 每个设备动作独立启用，未通过实机门禁的动作不出现在有效目录；
5. 关闭 V2 时停止新 dispatch，不删除 Execution 历史，也不回退到旧直接写路径。
6. `legacy_device_write_mode=bridge` 只允许已映射到可信 Action 的兼容调用；不允许 raw frame 或 fire-and-forget。
7. raw diagnostics 不属于业务 Action Catalog，默认关闭且不能用于绕过危险动作门禁。

## 4. 阶段与依赖总览

本文件与统一方案统一使用 Phase 0-A、0-B、1–6；更细的 P0/BE/FW/INT 编号只表示可独立合并的任务，不改变架构门禁和动作风险顺序。

| 阶段 | 主要交付物 | 前置依赖 | 是否阻塞首个只读闭环 |
|---|---|---|---|
| Phase 0-A | 当前 master 安全止血、Registry DI、真实 Wire、路径盘点 | 无 | 是 |
| Phase 0-B | 厂商证据和 C6/S3 性能基线 | 可与 0-A 并行 | 通用 read 仅受性能基线阻塞 |
| Phase 1 | 后端 Action/Execution/Outbox/API | Phase 0 schema 冻结 | 是 |
| Phase 2 | ChannelCmdV2 单步 Go/C 闭环 | Phase 0 Wire Spec、Phase 1 repository | 是 |
| Phase 3 | 前端控制面与旧接口迁移 | Phase 1 API；可与 Phase 2 后半并行 | 是 |
| Phase 4 | 设备动作逐个上线 | Phase 2/3 | 否，按动作独立 |
| Phase 5 | bounded batch 和 NVS seen-ring | 明确硬件需求与性能余量 | BMS 参数/at-most-once 动作需要 |
| Phase 6 | 安全和运维强化 | 基础闭环稳定 | 不阻塞低风险试运行 |

关键路径：

```text
legacy 安全止血 / 协议与性能基线
→ Action Schema
→ Execution + Outbox
→ ChannelCmdV2 Go/C
→ 单步只读闭环
→ 前端切换
→ 普通 setter
→ 按需 batch / at-most-once
```

嘉佰达原始协议归档、MOS 工厂模式和 0x0E 复位帧验证是 BMS 动作的独立硬件关键路径，不应阻塞逆变器普通 setter 和通用控制面开发。

## BE-04 Outbox、Inbox 和轻量 Dispatcher

工作内容：

- 使用 owner/lease/fencing 支持进程崩溃恢复；
- 重发复用 command ID；
- Inbox 去重后再驱动状态机；
- dispatcher 接口先使用 fake transport 做单元测试，Phase 2 再接 MQTT。

当前实现状态（2026-07-19）：Outbox 领取已满足跨实例 `node_id + channel_id` 单有效租约不变量。

按 Outbox ID 保序，通过 Channel 行锁和锁后二次检查防止两个 PostgreSQL 实例同时领取同一物理通道；
不同 Channel 仍可独立推进。发布或取消提交必须以 `state + fencing_token` CAS 影响恰好一行，
租约已被接管时整笔数据库事务回滚。`CommandExecution(node_id, channel_id)` 复合索引用于这条热路径。

建议位置：

- change-address 迁移为 Action，验证后才更新实例；

# 9. Phase 4：单步设备动作逐个上线

每个动作独立完成以下交付物：

```text
Driver ActionDefinition
参数 schema
可信 compiler
协议黄金向量
ACK parser
verification

API/前端测试
```

## A-01 逆变器普通参数 setter

优先顺序：一个可安全恢复且能 readback 的参数，例如工作模式或受限充电参数。使用 `single + readback`，验证闭环稳定后再复制模式到其他参数。

禁止一次提交所有逆变器 setter；每个参数先验证协议范围和设备实际响应。

## A-02 逆变器绝对开关机

使用 `inverter.set_power_state(on)`，不使用 toggle。关机可能导致通信变化时，动作定义必须明确 ACK、遥测和断线的成功语义。

## A-03 BMS MOS policy

前置硬件门禁：

- 0xE1 工厂模式结论；
- wake 条件；
- YY 优先级；
- ACK 和可读取状态字段。

动作必须一次提交：

```text
charge_software_closed
discharge_software_closed
priority=user|operator
```

四个 XX 组合都要有黄金向量，证明修改任一意图不会无意释放另一 bit。acknowledged policy 和物理 `fet_status` 分开存储和展示。

如果硬件验证结论是无需工厂模式，使用单步或后端 readback；不要为了 MOS 强行启用 batch。

如果硬件验证结论是必须进入工厂模式，则 A-03 只完成 schema、compiler 向量和 unavailable 目录项，真实启用推迟到 Phase 5 的 bounded batch 完成之后。

## Phase 4 门禁

- 每次只灰度一个动作；
- 普通 setter 可先灰度到明确测试设备；
- BMS 未决协议动作保持 unavailable；
- 所有动作失败和 UNKNOWN 均可从历史中复核；
- 不包含雨量清零、reboot/reset 等 at-most-once 动作。

# 10. Phase 5：按需 bounded batch 和 at-most-once

Phase 5 分为两个可独立交付的能力，不应捆绑成一个大型固件重构。

## FW-04 Bounded batch

只有 BMS F2/F3 参数读写或实机确认 MOS 必须进入工厂模式等实际需求成立后实施。

功能范围：

- 编译期 step 上限；
- NORMAL/FINALLY；
- stop-on-error；
- Channel admission 排他；
- 固定 batch slot 和 TX/response arena；
- queue 只传 slot index；
- accept/reject + 聚合 final；
- 无分支、循环、变量、脚本和厂商解析。

第一批唯一目标场景：

```text
wake（若需要）
→ enter factory
→ F2/F3 operation
→ finally exit factory
→ 可选 readback
```

如果实测步骤超过节点上报上限，后端必须拒绝编译，不能静默拆分破坏排他语义。

当前代码已交付统一 Action Catalog 的 bounded-plan 元数据与校验（固定步骤、最多 8 步、
`at_most_once`、`finally` 约束），但尚未接通节点端批处理/NVS replay，因此不会把它误报为
可执行能力。

## FW-05 NVS seen-ring

只为 `at_most_once + high/critical` 实施：

- 固定容量；
- 严格校验和执行槽预留后、物理 TX 前记录 SEEN；
- NVS 失败拒绝执行；
- 重启后相同命令返回 REPLAY_UNKNOWN；
- 不保存完整 payload/raw response；
- 不为普通 read/set 写 NVS。

## A-04 雨量累计清零

- high、at-most-once；
- 必须要求 persistent replay capability；
- 当前累计值和数据时间进入确认；
- 不自动重试；
- readback 为零后完成对账。

实现状态：已从普锐森 OCR 协议确认 `SN-3001-GYL-N01` 清零帧
`01 06 00 00 00 5A 09 F1` 及回显，并在 `sn3001_rain` Driver 中冻结 CRC 黄金向量和
“读当前值→写清零→读回零” bounded plan。仍缺真实写入 ACK、读回为零、断电/恢复证据以及
节点 durable at-most-once，因此前端继续显示 `protocol_unverified`，不会向实机发送写命令。

## A-04a BMS 操作能力登记

- `set_mos_policy` 已登记完整参数 schema 和 V19 `0xE1` 编译黄金向量；保持
  `hardware_evidence_required`，未接入真实 BMS ACK/`fet_status` 读回/恢复证据；
- F2/F3 参数读取和 BMS restart 已登记 bounded workflow/observation 元数据，保持
  `protocol_unverified`；
- 未接通 durable NVS at-most-once 和节点批处理前，所有上述动作不得启用。

## A-05 BMS/逆变器 reboot/reset

- critical、at-most-once；
- 未冻结帧保持 unavailable；
- 不以同连接 WriteRsp 作为成功；
- 必须观察离线窗口、boot/uptime/restart counter 变化之一；
- 无充分证据进入 UNKNOWN。

## Phase 5 性能门禁

- 最大 batch slot/arena 的静态 RAM 已测量；
- 同一物理总线等待有上限，无关总线不停止；
- final 聚合响应不超过 ResourceReport 总预算；
- NVS 写次数、磨损估算和断电窗口通过评审；
- C6/S3 都不依赖 PSRAM；
- 任何不满足门禁的构建上报 batch/persistent replay 能力为 false/0。

# 13. PR 与合并顺序

推荐一个 PR 只跨越一个清晰门禁，避免后端、固件、前端在同一超大 PR 中难以回滚。

建议序列：

1. `P0-Registry-DI`：单一 Registry、生产依赖注入和现有 7 Driver 回归；
2. `P0-Legacy-Hardening`：strict WriteCmd、超长/非法 bus 拒绝、reset 禁用和 TX 路径清单；
3. `P0-Wire-Freeze`：现有协议文档/注释/Go-C 黄金与 malformed 向量；
4. `P0-Schema-Identity`：Action Schema、错误码、request hash/wire digest、状态机；
5. `BE-Models`：Execution/Attempt/Outbox/Inbox 与迁移；
6. `BE-StateMachine`：repository/idempotency/状态 CAS；
7. `BE-ActionCatalog`：Driver 接口、overlay、availability；
8. `BE-Outbox-API`：service、API、旧接口和 diagnostics 门禁；
9. `PROTO-ChannelCmdV2`：schema version、消息号、Go/C 黄金向量；
10. `FW-ChannelCmdV2`：boot identity、严格解码、RAM replay、single bus execution；
11. `BE-Resource-Capability`：Node report time/boot/revision 持久化和事件接入；
12. `INT-Read-Slice`：首个只读端到端动作并删除 legacy read adapter；
13. `FE-Control-Plane`：store、组件和兼容切换；
14. `BE-Setting-State` + `A-Inverter-Setter`：第一个普通写动作；
15. `A-BMS-MOS-Single`：仅在硬件确认不需工厂模式时启用；否则只提交 unavailable 定义和测试向量；
16. `FW-Bounded-Batch` + `BE-Step-Result`：F2/F3 或 MOS 工厂模式需求确认后；
17. `A-BMS-MOS-Batch`：仅在 MOS 确认需要工厂模式时；
18. `FW-At-Most-Once`：NVS seen-ring；
19. `SEC-Node-Topic-Isolation`：第一个 high/critical 动作前；
20. `A-Destructive`：雨量清零、reboot/reset 逐个 PR。

协议 PR 必须同时包含 Go/C 和 Wire Spec；设备动作 PR 必须同时包含 schema、Driver 测试向量、验证策略和动作 availability。

## 14.5 实机

风险顺序固定为：

1. 只读；
2. 可 readback 的普通 setter；
3. BMS MOS；
4. bounded factory workflow；
5. 雨量清零；
6. reboot/reset；
7. 断网、ACK 丢失、后端重启、ESP32 重启和断电窗口。

任何高风险实机步骤都必须有测试设备、回退方法、操作者、观察窗口和审计记录。

# 15. 建议排期与人员协作

以下仅用于初始排期，不是工期承诺。假设 1 名后端、1 名固件、1 名前端，测试和硬件由团队共享；硬件等待时间不计入开发工作量。

| 迭代 | 目标 | 可并行工作 |
|---|---|---|
| Iteration 0 | Phase 0-A Registry DI、legacy hardening、路径盘点 | Phase 0-B 协议归档与性能基线并行 |
| Iteration 1 | 后端模型、状态机、Action Catalog | 前端 API 类型和只读组件骨架 |
| Iteration 2 | Outbox/API/旧接口封堵 | ChannelCmdV2 Go/C 黄金向量 |
| Iteration 3 | ESP32 单步执行、ResourceReport | 后端 event/inbox；前端 Operation Store |

关键协调点：

# 16. 风险与停止条件

| 风险 | 处理 |
|---|---|
| 嘉佰达协议已归档但无 BMS 实机证据 | MOS/F2/F3/reset 保持 unavailable，通用控制面继续 |
| MOS 工厂模式结论相反 | 选择实测步骤最少方案；不兼容时提高 action version |
| ESP32 RAM/stack 超预算 | 保持 single；降低 cache/slot；不上 batch，不引入 PSRAM 依赖 |
| 同物理总线 batch 阻塞采集 | 收紧 total timeout/step 数；必要时拒绝该动作 |
| NVS 磨损不可接受 | 不开放对应 at-most-once 动作，不用普通命令 NVS 替代 |
| 旧客户端依赖 `/execute` | read bridge；write 202 bridge 或 410，不恢复 direct 模式 |
| 数据库恢复语义不清 | dispatcher 保持关闭，先补齐 Outbox/Inbox/UNKNOWN 测试 |
| 协议事件身份不完整 | 不合并固件/后端协议 PR |
| 硬件无法提供 reboot 证据 | 动作最多 ACKED/UNKNOWN，不宣告 VERIFIED |

立即停止某动作上线的条件：

- 出现重复物理执行；
- stale event 覆盖新意图；
- verify 失败仍显示成功；
- ESP32 watchdog、heap 泄漏或无关总线饥饿；
- finally 未执行或 cleanup failure 被吞；
- 旧 API 可以绕过新安全边界；
- 审计和物理结果不一致。

# 17. 总体验收定义

开发计划完成不等于所有设备动作都已开放。基础平台完成需同时满足：

- 唯一 Action Schema 和可信 Driver 编译链；
- CommandExecution/Outbox/Inbox 可恢复；
- 旧写旁路已封堵；
- ChannelCmdV2 单步在 C6/S3 满足性能门禁；
- 首个只读和首个普通 setter 完成端到端闭环；
- 前端只使用 EffectiveActionCatalog 和真实操作历史；
- FAILED/UNKNOWN 不显示成功；
- 未验证动作保持 unavailable；
- 审计、REST、WebSocket、ESP32 final 和目标设备结果可相互追溯。

bounded batch、NVS seen-ring 和每个破坏性动作分别验收，不作为单步控制平台首发的隐性必选项。
