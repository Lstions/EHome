# ADR：来源组（source group）的核心不变量与取舍

- 状态：**已生效**（2026-10-22）
- 适用代码：`backend/internal/{models,dbschema,sourceref,datasource,automation,alert,api}` 中与来源组相关的部分
- 替代：方案 v0.3 中 §12.9 的部分放行条件（已标注）
- 为什么写这份：这套代码里有 **376 条**带「必须/禁止/铁律」的执行性注释。它们是防御性资产，
  但也是新人不敢改的原因。这份 ADR 把它们**收敛成 12 条**：4 条安全底线 + 8 条核心不变量。
  其余注释是实现细节说明，**不构成修改约束** —— 改实现时它们可以跟着改。

---

## 一、四条安全底线（改动必然引入事故，评审必拒）

### L1. 求值不读配置列，只读触发证据
`F4 复核` 必须用 `TriggerEvent.SourceEdgeDeviceID`（触发那一刻的成员），
**禁止回读 `rule.trigger_edge_device_id`**。

- 为什么：配置列可以随时被改。用"当前配置"给"过去的决策"背书，会在成员切换后
  对**错误的设备**下发物理动作（开泵/断电）。
- 代码位置：`automation/source_f4.go`（`checkConditionsStillSatisfiedWithSource`）
- 怎么防回归：`scripts/check_e6_prefix_bug.sh`（基线必红 / 修复后必绿 的双向证明）

### L2. `revision` 只由身份变化推进
运行时写（`MarkSuccess` / `MarkFailure` / 失败计数 / standby↔error）**不得** bump `revision`。
只有拓扑/成员/优先级/required/active 变化才 bump。

- 为什么：`revision` 进窗口 identity。若每帧都变，`DurationSec` 的窗口每帧被清空，
  **持续满足类规则永不触发** —— 而且不报任何错，是最难查的一类 bug。
- 代码位置：`datasource/group_crud.go`（`bumpGroupRevision` 的唯一白名单）
- 怎么防回归：门禁 SG-13 的反向断言（100 次 `MarkSuccess` 后 revision 不变）

### L3. 快照只有一个写入者
`sourceref.Registry` 的 `Publish` / `ReplaceAll` / `Remove` **只能**由
`datasource.GroupService` 在**事务提交后**调用。任何 handler / main / 引擎都不得直接写。

- 为什么：两处写入 = 两个真值来源 = 求值与 F4 复核可能看到不同 revision，
  出现"求值时 A 供数、复核时已切到 B"的口径分裂。
- 代码位置：`datasource/group_service.go`（`commitGroupChange` 是唯一出口）
- 怎么防回归：门禁 SG-06（依赖边界）+ 代码审查（grep 所有 `registry.Publish` 调用点）

### L4. 热路径零 DB
`Registry.MatchFrame` 与两引擎的`帧求值`路径**不得**出现数据库查询。

- 为什么：这是 `databus` 解析消费者的同步回调。一次慢查询直接反压 ingest，
  表现为"设备数据延迟"/"入库堆积"，而根因在规则引擎。
- 代码位置：`sourceref/registry.go`（`atomic.Pointer` 读快照）、
  `automation/evaluator.go`（`rulesSnap` 零拷贝读）
- 怎么防回归：门禁 SG-14（静态扫锁内 DB）+ 性能硬判据 `#10a-2`（≤基线 +5%）

## 二、八条核心不变量（改这些地方时必须同时满足）

### C1. 按 kind 分流的帧接受规则
| kind | 接受谁的帧 | 组 active 概念 |
|---|---|---|
| `primary_backup` | **仅 active 成员** | 有（且唯一） |
| `composite` | **任一成员**（整组求值） | **无**（不维护 active） |

- 违反后果：主备组会把备成员的帧当权威来源（`DurationSec` 被跨成员拼接）；
  复合组会被误加 active 语义（成员互相抢权）。
- 位置：`sourceref/registry.go` `Accepts()`、门禁 SG-10

### C2. 窗口 identity 的字段集必须按 kind 区分
- `primary_backup`：`{Kind, GroupID, GroupRevision, MembersHash, EdgeDeviceID}`
- `composite`：`{Kind, GroupID, GroupRevision, MembersHash}`（**不含 EdgeDeviceID**）

- 为什么复合组不含设备 ID：两个成员交替上报是**正常供数**，若把它当身份变化，
  每帧清窗 ⇒ `DurationSec` 永不满足。
- 位置：`automation/source.go` `identityForFrame`

### C3. 单活动成员由部分唯一索引兜底
`source_group_members(group_id) WHERE status='active'` 与
`data_sources(device_id,category) WHERE status='active'` 各有唯一索引；
**切换必须"先降旧、再升新"**。

- 为什么顺序不能反：同一事务内出现两条 active 会撞索引（PG/SQLite 语句级检查）。
  早期实现反了，被测试抓出来后改成现在的顺序。
- 位置：`dbschema/source_group.go`、`datasource/service.go`（Deactivate）、
  `datasource/group_state.go`（R5）

### C4. 缺员处置：fail_closed 是默认，use_available 必须可见
- 默认 `fail_closed`：不足 `EffectiveMinMembers` ⇒ **不触发**。
- `use_available`：允许触发，但必须同时写 `result=source_degraded` +
  `members_json` + 健康事件，否则用户以为"1+2 融合"其实只有一台。
- 位置：`sourceref/combine.go`、`automation/source.go` `evalCompositeRule`

### C5. 降级必须三层可见
任何"来源不可用"都必须同时落到：
1. `automation_events.result`（source_* 三码之一）
2. `source_group_health`（运维看板 `GET /source-groups/:id/health`）
3. 指标（`ehome_source_frame_discarded_total{reason}`）

- 为什么三层：只落审计 ⇒ 看板空白；只落看板 ⇒ 无法按规则聚合；
  只落指标 ⇒ 不知道是哪个组。
- 位置：`automation/source.go` `recordSourceFailure`（单一出口）

### C6. 冷却抑制 ≠ 失去权威
R10 冷却期内不切换，但若 active 已被置 error，**组已经失去权威**，
必须发 `ActiveChange{Next:0, Reason:"cooldown_suppressed"}` + bump revision。

- 为什么容易错：直觉上"冷却 = 什么都不做"。实际上"不切换"和"不通知失去权威"是两件事。
  不通知 ⇒ 引擎继续按旧 active 过滤 ⇒ 静默丢帧、规则停求值、告警停在 firing。
- 位置：`datasource/group_state.go` `maybeGroupFailover`
- 防回归：`TestGroupCooldownSuppressedEmitsNextZeroAndHealth` + 变异 M18

### C7. 回滚锚点必须跟着成员变
规则保存时把"锚点成员"双写到 `trigger_edge_device_id` / `alert.target_*`
（供回退旧二进制时使用）。**成员/优先级变更时必须在同一事务内重算**。

- 为什么：回退旧版本时，旧代码只认这一列。锚点指向已移出组的设备 ⇒ **错源触发物理动作**。
- 位置：`datasource/group_crud.go` `reconcileRuleAnchors`

### C8. 结果码三向一致
`source_*` 结果码必须同时存在于三处：`models` 常量、`simulation/catalog/audit.go` 白名单、
前端 `AutomationEventResult` union。

- 为什么：仿真/前端若缺少某码，会把该结果当成未知或显示空白，运维看到的是"没有异常"。
- 位置：门禁 SG-16

## 三、本轮（2026-10-22）删除清单：砍了什么、为什么安全

用户判断这套实现超出需求 3 倍以上，要求砍掉过度设计。以下为实际删除项及安全性论证。

| # | 删除项 | 规模 | 为什么安全 | 什么时候该加回来 |
|---|---|---|---|---|
| 1 | **S8 窗口 gap 判据** | 两引擎 + helper + 测试 | 它用**配置的** `IntervalMs` 判实际 gap；稀疏上报（解析失败/按变化上报/重连）时会反复截断窗口 ⇒ 存量 `DurationSec>0` 规则可能**永不触发**（false negative 且无指标）。风险大于收益。删除后跨长断流仍由 `durationSec` cutoff 自然截断。**附带收益：热路径彻底零 DB**（`deviceIntervalFn` 的 TTL miss 同步查库问题消失） | 真有"长断流导致误拼接"的真实事故时，且用**实际上报节奏**（而非配置）判定 |
| 2 | **combine `max`/`min`/`first_available`** | 3 个算子，跨 5 处同步 | 每多一个算子要同步 5 处（白名单/case/真值表/前端/门禁），而后端只多 6 行。`first_available` 与 `on_degrade=use_available` 语义重叠（N-8）。**生产 `source_groups` 表 0 行，无历史值** | 有真实需求时加一个 case + 一行白名单 |
| 3 | **结果码 `source_resolver_not_configured`** | 1 个码 | 它是"上线顺序错了"的运维态，不是业务结果。映射到既有 `unresolved_selector`，**原因字符串保留在 detail**（`f4_fail_reason=source_resolver_not_configured`），诊断能力不丢 | 不需要 —— detail 已足够 |
| 4 | **结果码 `source_group_shadow`** | 1 个码 | **死常量**：全仓无产出点（灰度 G1 从未实现）。留着会让"三向一致"门禁为不存在的能力背书 | 真要上灰度时 |
| 5 | **门禁 SG-21（TriggerEvent 唯一构造）** | 1 条门禁 | 代码风格强制，已两次误报（函数体内字面量）。"加字段不编译错"由编译器 + SG-07 行为测试覆盖 | 不需要 |
| 6 | **门禁 SG-11（状态词表/默认值）** | 1 条门禁 | 与 `TestGroupCreate*` 单测完全重复 | 不需要 |
| 7 | **门禁 SG-02** | 1 条空位 | N-8 已废弃，脚本里只留 SKIP 占位 | 不需要 |
| 8 | **门禁 SG-06/17/19 合并** | 3 → 1 | 三条都是"依赖边界"断言，合并后**断言一条不少**，只是不再各占一行汇总 | 不需要 |

**净效果**：门禁 20 → 16 条；combine 5 → 2；结果码 5 → 3；
热路径从"1 次 DB 风险"回到"零 DB"。

## 四、维护指引：改哪里要同步哪里

| 你要改 | 必须同步 |
|---|---|
| 加一个 combine 算子 | `models.CombineWhitelist` → `sourceref/combine.go` case → `combine_test.go` 真值表 → 前端 `SourceGroupCombine` union + 下拉项 → 门禁 SG-03 |
| 加一个 source_* 结果码 | `models/automation.go` → `simulation/catalog/audit.go` → 前端 `AutomationEventResult` → 门禁 SG-16 |
| 改组成员/优先级 | 记得 `reconcileRuleAnchors` 会在同事务回写锚点（C7），不要绕过 `replaceMembers` |
| 改状态机（R1–R11） | 门禁 SG-15（状态迁移数 == ActiveChange 事件数）+ `TestVerifyDiff` 等价性差分（legacy ↔ group）必须仍等价 |
| 改求值热路径 | 必须跑 `BenchmarkEvaluateFrame`，硬判据 ≤ 基线 +5%（门禁 #10a-2） |
| 改窗口 identity | 门禁 SG-05 + `TestM0SourceWindowNoCrossMemberSplice`（跨成员交替不得拼接） |

## 五、什么情况下**不要**碰这套代码

- 若只是为了"让某个测试变绿"：先确认测试断言的是行为还是实现。本套代码的注释里
  大量是**行为契约**，改实现前请先对照本文档的 L1–L4 / C1–C8。
- 若要"加一道保险"：先问它是否可观测。本套代码的教训是 —— **不可观测的保险等于没有保险**
  （S8 就是典型：它"保护"了窗口，却在稀疏上报时静默杀掉规则，且没有任何指标说明）。
