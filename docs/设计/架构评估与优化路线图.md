## 1. 评估基线与结论

**证据基线**（2026-08-21，commit cc40e3c6 + 工作区）：

| 维度 | 事实 |
|------|------|
| 后端 | 34,757 行 Go（非测试）+ 36,236 行测试（测试:代码 > 1:1） |
| 固件 | 20,524 行 C，21 个 component |
| 前端 | 39,627 行 TS/Vue，40 组件 + 36 视图 |
| 部署 | docker-compose 4 服务：postgres + redis + emqx + ehome |
| 协议 | 二进制帧 v2.5+，20+ 消息类型，MQTT 三 topic |
| 数据 | unified_data 单表 b-tree（评估时未分区） |

**总结论**：当前架构是这套需求的"良好解"而非"最优解"；偏离最优的部分是局部的、可增量修正的，**重写不成立**。正确性关键路径（配置同步自愈、OTA 可靠性、fail-open 容错）质量高于同类系统平均水平。

## 2. 做对了什么（不应动的部分）

| # | 设计决策 | 为什么对 |
|---|---------|---------|
| 1 | 三层模型（中心端/节点/边缘设备） | 节点无业务逻辑、中心端持有全部状态——全系统最重要的抽象 |
| 2 | 二进制帧协议而非 protobuf | 实测 -67% 体积、-50x 解析、hex 可调试、C/Go 共享语义头文件 |
| 3 | SyncGate + Epoch + Hash 三重兜底 | 配置最终一致的三重保险，质量最高的设计 |
| 4 | 资源全部来自 ResourceReport | 新硬件型号零后端改动（通用性） |
| 5 | Driver Registry + ConfigTemplate + 逐指令 Manifest | 新设备多数不改代码 |
| 6 | 进程内 DataEventBus（分片+消费者分离） | ingest→persist→push 单二进制扇出，复测 84%→0% 丢率 |
| 7 | OTA：HTTPS + SHA256 + A/B + mark-valid | 失败路径全覆盖（帧丢 Hello 补、并发 supersede） |
| 8 | 测试纪律与文档治理 | 测试:代码>1:1、固件 host_tests ~6000 行 |

三份以上内容与 [概念模型.md](概念模型.md) §4 一致，此处为评估存档。

## 3. 偏离最优的点（按影响排序）

### 3.1 数据层缺时序化设计（影响最大）

- 问题：DELETE 式 retention 随数据量线性上涨；b-tree 写入放大与查询退化（已撞过 84% 丢率墙）；读时降采样每次重算。
- 改法：原生月分区 + 写时 1min rollup + retention 改 DROP partition。**不引入 TimescaleDB**。

### 3.2 Redis 近乎冗余（部署重量）

- 现状：仅 4 处消费方（心跳 TTL、响应去重、登录限流、ping 时间戳）。
- 改法：三处进程内化 + DB 兜底；多实例时再引回（接口不变）。

### 3.3 EMQX 对家庭规模过重

- 现状：README 架构图 EMQX vs 总体设计 §5.1 Mosquitto vs compose 实际 EMQX——文档互相矛盾。
- 改法：先修文档一致性；切 Mosquitto 为独立决策项（不捆绑实施）。

### 3.4 API 层业务逻辑下沉不彻底

- 现状：handler_edge_device.go 1666 行、handler_device.go 1096 行；对照 commandexec/datalifecycle 的正确 service 形态。
- 改法：渐进下沉，edge-device 域优先；新代码强制 service 层。

### 3.5 驱动命令式大文件

- 现状：jiabaida.go 1929 行、inverter_techfine.go 1096 行；每加一个厂商 ≈ 新增 1-2K 行。
- 改法：表驱动（RegisterMap）**时机**——第 4-5 个厂商出现时再做（现在动手=为未验证场景增复杂度）；当前保持"表驱动风格"留缝。

### 3.6 产品缺口：无阈值告警

- 改法：规则 CRUD + DataEventBus 求值挂点（解析后回调，避免重复解析）+ 通知复用 + 前端规则页。

### 3.7 前端响应式维护成本

- 改法：断点 token 收敛 theme 变量，布局组件统一消费；不重写。

## 4. 绿地方案（假设从零设计，差异仅在六处）

骨架 80% 一样：三层模型、二进制帧、MQTT、SyncGate、驱动注册、资源上报、OTA 全保留。差异：

1. 部署 3 服务：ehome 单二进制（进程内化心跳/限流/去重）+ postgres + mosquitto
2. 数据层分区 + rollup 从第一天就有
3. handler=transport 强制（<300 行/文件），service 为业务家
4. 驱动接口不变、实现表驱动（RegisterMap + 通用帧引擎）
5. 告警引擎一等公民
6. Hello 上报"协议能力位图"替代版本号推断

绿地方案明确不做：微服务/服务网格、protobuf/gRPC、TimescaleDB/InfluxDB、NATS/Kafka、多租户/RBAC 界面、K8s。

## 5. 落地路径（增量，非重写）

按投入产出排序，每步独立可验证可回滚：

| 步骤 | 内容 | 规模 |
|------|------|------|
| 1 | unified_data 月分区 + rollup + retention 改 drop | 中 |
| 2 | 阈值告警引擎 | 中 |
| 3 | Redis 退役 | 小 |
| 4 | EMQX→Mosquitto 决策 + 文档一致性 | 小 |
| 5 | edge-device handler → service 下沉（随下次改该域） | 中 |
| 6 | 驱动 RegisterMap 抽取（第 4 个厂商时启动） | 大 |

## 6. 历史决策点（已拍板）

1. Redis 退役：认可（进程内化，多实例时再引回）。
2. 告警引擎 v3.4 级：认可（见优化实施计划任务 C）。
3. 驱动表驱动化时机：按"第 4 个厂商触发"执行。
4. EMQX：运行中保持，切换为独立决策（任务 D 只修文档一致性）。
