# 同步机制 v2 — 详细设计

> **模块**: 同步机制 (Sync Mechanism) — 跨模块的横切关注点
> **协议版本**: v2.1 (兼容 v2.0)
> **关联**: [总体设计.md §3 协议规范](../总体设计.md) | [节点/详细设计.md](../节点/详细设计.md) | [固件OTA/详细设计.md](../固件OTA/详细设计.md)
> **状态**: 草案 (2026-06-04)

## 1. 设计动机

### 1.1 v2.0 方案的 4 个 P0 GAP

通过 2026-06-04 全栈代码审计,识别出当前同步机制在 v2.0 下的 4 个 P0 GAP,均源于"**单一触发点 (Hello-only)** + **被动同步**"的架构假设:

| # | GAP | 触发条件 | 后果 |
|---|-----|---------|------|
| **G1** | 中心端改配置后不通知 | PUT /channels/123 | 节点**永远**拿不到新配置,除非重启/重连 |
| **G2** | 中心端重启后丢同步 | Center restart | 内存态 `hashMgr` 清空,在线边缘设备**永不**重新同步 |
| **G3** | 恢复出厂卡死 | 长按 BOOT 5s | NVS 清空 + hash 不变 + 不强制下发 = 边缘设备**永远**等不到 ConfigManifest |
| **G4** | WS 事件名错位 | Center push `collector_status` / FE subscribe `status` | 状态变化**不实时**推到前端 |

此外还有 3 个 P1 缺口:
- **G5**: StatusReport 触发 `triggerDeviceInit` 但**不**触发 config 重发 (offline→online 路径)
- **G6**: `deviceinit.InitDevice` 用 `time.Sleep` 等待响应 (T10 标完成但实现没改)
- **G7**: `hashMgr.Reset` 是死代码 (无调用点)

### 1.2 根因分析

```
┌──────────────────────────────────────────────────────────────────┐
│  v2.0 架构假设 (错误)                                              │
│                                                                  │
│  假设 1: 同步 = 一次性握手 (Hello 即可)                            │
│  假设 2: 中心端"改完就好", 节点会"自己来拿"                       │
│  假设 3: 内存态 = 持久态 (无显式 reconciliation)                   │
│  假设 4: WS 事件名 = 自由文本 (无规范)                            │
└──────────────────────────────────────────────────────────────────┘
                              ↓
              4 个 P0 GAP + 3 个 P1 缺口
                              ↓
              生产环境条件评分: 51% (节点-后端同步维度)
```

### 1.3 v2.1 设计目标

| 目标 | 衡量标准 |
|------|---------|
| **中心端是配置的唯一权威源 (SSoT)** | 任何配置变更在 5s 内推到所有相关边缘设备 |
| **节点可恢复 (Restorable)** | 任意时刻可从中心端拉取完整状态 (NVS 只是 cache) |
| **多通道同步 (Multi-Channel)** | 不只 Hello,任何 sync 信号都走同一管道 |
| **可观测同步 (Observable)** | 每次同步都有 `sync_id` 贯穿日志, 可追踪 |
| **协议向后兼容 (BC)** | v2.0 固件可与 v2.1 中心端互通 (字段 optional) |

## 2. 设计原则

### 2.1 五条铁律 (新增)

#### 铁律 1:中心端单一权威源 (Center-Source-of-Truth, SSoT)

中心端**永远**是配置的最终持有者:
- 任何配置变更都通过 `ConfigEventBus` 发出
- 不允许"节点自己决定改配置"
- 节点**只读**自己的 NVS (视为 cache, 可丢弃)

#### 铁律 2:配置变更 = 事件 (Config-as-Event)

不允许在 CRUD handler 里"手动调 sendConfigManifest":
- 任何对 `channels` / `templates` / `device_configs` / `firmwares` 的修改
- 必须通过 `ConfigEventBus.Publish()` 发出
- 订阅者统一处理推送
- 杜绝"漏改一个 handler 就不通知"的人为错误

#### 铁律 3:多通道同步 (Multi-Channel Sync)

不允许"只靠 Hello 触发":
- 同步入口: `SyncGate` (单一)
- 触发源: Hello / StatusReport / Center Startup / Config Change / 主动 Ping / ConfigQuery
- 所有触发源走 `SyncGate.OnXxx()` 同一管道
- 决策逻辑**集中** (不再散落在各 handler)

#### 铁律 4:版本化现实 (Versioned Reality)

不允许"对比黑盒 hash":
- 中心端维护单调递增的 `config_epoch` (uint64)
- 协议携带 epoch
- 任何 sync 路径都做 epoch 比对
- 节点 NVS 存 epoch
- epoch + manifest_id + nvs_has_config = 三轴决策

#### 铁律 5:可观测同步 (Observable Sync)

不允许"沉默的同步":
- 每次同步操作分配 `sync_id` (UUID)
- 日志/指标/前端通知**都**带 sync_id
- 可重现: 给定 sync_id 可查完整链路

### 2.2 与 v2.0 5 大设计原则的关系

| v2.0 原则 | v2.1 强化 |
|----------|----------|
| 协议优先 | ✅ 协议扩展字段必须版本化, 不允许"私加字段" |
| 状态机显式 | ✅ 同步决策用显式 SyncDecision enum, 不返回 magic number |
| 容错优先 | ✅ SyncDecision 包含 `fallback` 字段, 显式降级 |
| 可观测性 | ✅ sync_id 贯穿全链路 |
| 三层分离 | ✅ 同步机制是横切关注点, 但**不**破层依赖 |

## 4. 中心端架构

### 4.1 ConfigEventBus — 配置变更事件总线

**核心目标**: 杜绝"CRUD 后忘记调 sendConfigManifest"的人为错误。

```go
// internal/collector/config_event_bus.go
package collector

// ConfigChangeType 配置变更类型
type ConfigChangeType string
const (
    CfgChangeTemplate    ConfigChangeType = "template"
    CfgChangeChannel     ConfigChangeType = "channel"
    CfgChangeDevice      ConfigChangeType = "device"
    CfgChangeNode   ConfigChangeType = "collector"
    CfgChangeDeviceConfig ConfigChangeType = "device_config"
)

// ConfigChangeAction CRUD 操作
type ConfigChangeAction string
const (
    CfgActionCreate ConfigChangeAction = "create"
    CfgActionUpdate ConfigChangeAction = "update"
    CfgActionDelete ConfigChangeAction = "delete"
)

// ConfigChangeEvent 配置变更事件
type ConfigChangeEvent struct {
    EventID     string             // UUID v4
    Type        ConfigChangeType
    Action      ConfigChangeAction
    NodeID uint               // 受影响的 collector
    EntityID    uint               // 变更的实体 ID
    Epoch       uint64             // 全局 epoch (递增后)
    Timestamp   time.Time
    Actor       string             // 触发者: "api:admin", "init:factory_reset", "system:startup"
}

// ConfigEventBus 事件总线
type ConfigEventBus struct {
    ch       chan ConfigChangeEvent
    epochGen *EpochGenerator
    logger   Logger
}

func NewConfigEventBus(bufferSize int) *ConfigEventBus
func (b *ConfigEventBus) Publish(evt ConfigChangeEvent) error
func (b *ConfigEventBus) Subscribe() <-chan ConfigChangeEvent
func (b *ConfigEventBus) CurrentEpoch() uint64  // 全局 epoch
```

**关键不变量**:
- `Publish` 不会阻塞 (bufferSize ≥ 1024, 满了 WARN + drop + alarm)
- `Subscribe` 只能注册一次 (单订阅者 = SyncGate)
- Epoch 单调递增, 持久化到 DB `config_meta.epoch`

### 4.2 EpochGenerator — 全局 epoch 生成器

```go
// internal/collector/epoch.go
type EpochGenerator struct {
    mu       sync.Mutex
    current  uint64
    db       *gorm.DB
}

func (g *EpochGenerator) Next() uint64 {
    g.mu.Lock()
    defer g.mu.Unlock()
    g.current++
    // 持久化 (异步, 不阻塞)
    go g.db.Model(&ConfigMeta{}).Where("id = 1").Update("epoch", g.current)
    return g.current
}

func (g *EpochGenerator) Current() uint64 {
    g.mu.Lock()
    defer g.mu.Unlock()
    return g.current
}

// 启动时从 DB 恢复
func (g *EpochGenerator) Restore() error {
    var meta ConfigMeta
    if err := g.db.First(&meta, 1).Error; err == nil {
        g.current = meta.Epoch
    } else {
        // 首次启动, init epoch = time-based
        g.current = uint64(time.Now().UnixMilli())
    }
    return nil
}
```

### 4.3 SyncGate — 统一同步决策中心

**核心目标**: 所有 sync 入口走同一管道, 决策逻辑集中。

```go
// internal/collector/sync_gate.go
package collector

// SyncReason 同步触发原因
type SyncReason string
const (
    SyncReasonHello            SyncReason = "hello"             // 边缘设备首次/重连
    SyncReasonStatusReport     SyncReason = "status_report"     // 周期/触发
    SyncReasonConfigChange     SyncReason = "config_change"     // 中心端改了 config
    SyncReasonCenterStartup    SyncReason = "server_startup"    // 中心端启动
    SyncReasonConfigQuery      SyncReason = "config_query"      // 节点主动查
    SyncReasonOfflineReconnect SyncReason = "offline_reconnect" // offline→online
    SyncReasonFactoryReset     SyncReason = "factory_reset"     // 恢复出厂
    SyncReasonPeriodic         SyncReason = "periodic"          // 周期 sync (10min)
    SyncReasonEpochLag         SyncReason = "epoch_lag"         // 收到上报发现 epoch 落后
)

// SyncAction 同步动作
type SyncAction int
const (
    SyncActionNone    SyncAction = iota // 不下发
    SyncActionFull                       // 全量 ConfigManifest
    SyncActionPatch                      // 增量 ConfigPatch (v2.1 未来)
    SyncActionDefer                      // 延后下发 (dedup window)
)

// SyncDecision 同步决策结果
type SyncDecision struct {
    Action   SyncAction
    Reason   string             // 详细原因 (for log)
    SyncID   string             // UUID
    Epoch    uint64             // 中心端当前 epoch
    ManifestID string           // 拟下发的 manifest_id
}

// SyncGate 同步决策中心
type SyncGate struct {
    mgr       *Manager
    eventBus  *ConfigEventBus
    dedupTTL  time.Duration     // 30s
}

func (g *SyncGate) OnHello(deviceID string, hello *HelloMsg) SyncDecision
func (g *SyncGate) OnStatusReport(deviceID string, rpt *StatusReport) SyncDecision
```

### 4.4 SyncGate 决策算法 (核心)

```go
// OnHello 决策逻辑 (v2.1)
func (g *SyncGate) OnHello(deviceID string, hello *HelloMsg) SyncDecision {
    syncID := uuid.New().String()
    serverEpoch := g.eventBus.CurrentEpoch()
    
    // === 三轴决策 ===
    
    // 轴 1: NVS 状态 (恢复出厂修复 G3)
    if !hello.NvsHasConfig {
        return SyncDecision{
            Action: SyncActionFull,
            Reason: "nvs_empty_force_sync",
            SyncID: syncID,
            Epoch:  serverEpoch,
            ManifestID: g.mgr.BuildManifestID(),
        }
    }
    
    // 轴 2: Epoch 比对 (修复 G1, G2)
    if hello.ConfigEpoch < serverEpoch {
        return SyncDecision{
            Action: SyncActionFull,
            Reason: fmt.Sprintf("epoch_lag: device=%d server=%d", 
                                hello.ConfigEpoch, serverEpoch),
            SyncID: syncID,
            Epoch:  serverEpoch,
            ManifestID: g.mgr.BuildManifestID(),
        }
    }
    
    // 轴 3: Hash 比对 (保留, 兜底)
    serverHash := g.mgr.CalcConfigHash(deviceID)
    if hello.LastManifest != serverHash.ManifestID {
        return SyncDecision{
            Action: SyncActionFull,
            Reason: "manifest_id_mismatch",
            SyncID: syncID,
            Epoch:  serverEpoch,
            ManifestID: g.mgr.BuildManifestID(),
        }
    }
    
    // === Dedup ===
    if g.mgr.hashMgr.ShouldSendConfig(deviceID, serverHash.Hash) {
        return SyncDecision{
            Action: SyncActionFull,
            Reason: "dedup_expired_or_first_time",
            SyncID: syncID,
            Epoch:  serverEpoch,
            ManifestID: g.mgr.BuildManifestID(),
        }
    }
    
    return SyncDecision{
        Action: SyncActionNone,
        Reason: "in_sync",
        SyncID: syncID,
        Epoch:  serverEpoch,
    }
}
```

**关键设计**:
- **三轴优先**: NVS 状态 > Epoch > Hash (从最严格到最宽松)
- **任何同步决策都带 sync_id**, 可观测
- **dedup 只在"决策下发"时生效**, 不影响 epoch 强制下发

### 4.5 Config CRUD 接入 ConfigEventBus

**所有 CRUD handler 末尾必须发事件**, 通过统一的辅助函数:

```go
// internal/collector/event_helper.go

// EmitConfigChange 是 CRUD handler 的"通知出口"
// 调用示例: defer EmitConfigChange(bus, CfgChangeChannel, CfgActionUpdate, collectorID, channelID)
func EmitConfigChange(bus *ConfigEventBus, 
                      t ConfigChangeType, 
                      a ConfigChangeAction,
                      collectorID, entityID uint) {
    evt := ConfigChangeEvent{
        EventID: uuid.New().String(),
        Type: t,
        Action: a,
        NodeID: collectorID,
        EntityID: entityID,
        Epoch: bus.CurrentEpoch(),  // 当前 epoch
        Timestamp: time.Now(),
        Actor: actorFromContext(),   // 从 gin.Context 取 user/role
    }
    bus.Publish(evt)
}
```

**所有 CRUD handler 必须修改**:
```go
// 之前 (有 GAP):
v1.PUT("/channels/:id", func(c *gin.Context) {
    // ... update logic
    db.Save(&channel)
    c.JSON(200, ...)
})

// 之后 (零 GAP):
v1.PUT("/channels/:id", func(c *gin.Context) {
```

```go
func (app *App) Start() {
    // ... 现有 init 逻辑
    
    // 启动 SyncGate 订阅
    app.syncGate.Start()
    
    // 启动时主动 push 所有在线 collector (修复 G2)

                logger.Infof("[sync_id=%s] Center-startup push to %s", 
                             d.SyncID, d.Reason)
            }
        }
    }()
}
```

## 5. 节点侧架构

### 5.1 SyncManager — 统一同步管理器

**目标**: 取代散落在 `main.c` / `on_mqtt_state` / `on_mqtt_msg` 的同步逻辑。

```c
// components/sync_manager/sync_manager.h
typedef enum {
    SYNC_REASON_NONE,             // 不需要同步
    SYNC_REASON_PERIODIC,         // 周期 (默认 10min/次)
    SYNC_REASON_EPOCH_LAG,        // 收到响应发现 epoch 落后
    SYNC_REASON_NVS_EMPTY,        // NVS 空 (恢复出厂)
    SYNC_REASON_FORCED,           // 收到 force_sync 标志
    SYNC_REASON_USER_ACTION,      // 用户操作触发
    SYNC_REASON_DOUBT,            // 怀疑状态不一致 (如 esp_restart 后)
    SYNC_REASON_MANIFEST_MISMATCH,// 收到的 manifest_id 异常
} sync_reason_t;

typedef struct {
    uint64_t epoch;              // 当前本地 epoch
    char manifest_id[64];        // 当前本地 manifest_id
    bool nvs_has_config;         // NVS 是否有 manifest
    uint32_t last_sync_time_sec; // 上次同步时间
    uint32_t last_sync_id_hash;  // 上次 sync_id 哈希 (去重用)
} sync_state_t;

void sync_manager_init(void);
void sync_manager_request_sync(sync_reason_t reason);

// 在 on_mqtt_msg 中调用 (任何下行消息都可触发)
void sync_manager_on_downlink_received(uint8_t msg_type);

// 周期性 task
void sync_manager_periodic_task(void *pvParameters);
```

### 5.2 同步决策 (节点侧)

```c
// sync_manager.c - 决策逻辑
static bool should_request_sync(sync_reason_t reason) {
    sync_state_t *st = sync_get_state();
    uint32_t now = esp_timer_get_time() / 1000000;  // 秒
    
    switch (reason) {
        case SYNC_REASON_NVS_EMPTY:
        case SYNC_REASON_FORCED:
        case SYNC_REASON_USER_ACTION:
            return true;  // 强制发
        
        case SYNC_REASON_EPOCH_LAG:
        case SYNC_REASON_MANIFEST_MISMATCH:
            return true;  // 状态不一致, 发
        
        case SYNC_REASON_PERIODIC:
            // 10min 一次, 不需要每次都发
            return (now - st->last_sync_time_sec) > 600;
        
        case SYNC_REASON_DOUBT:
            // 30s 一次防抖
            return (now - st->last_sync_time_sec) > 30;
        
        default:
            return false;
    }
}
```

### 5.4 周期 Sync 任务 (新增)

```c
// components/sync_manager/sync_manager.c
static void sync_manager_periodic_task(void *arg) {
    while (1) {
        vTaskDelay(pdMS_TO_TICKS(60 * 1000));  // 60s 检查一次
        
        sync_state_t *st = sync_get_state();
        if (!st->nvs_has_config) {
            sync_manager_request_sync(SYNC_REASON_NVS_EMPTY);
            continue;
        }
        
        uint32_t now = esp_timer_get_time() / 1000000;
        if (now - st->last_sync_time_sec > 600) {  // 10min
            sync_manager_request_sync(SYNC_REASON_PERIODIC);
        }
    }
}
```

## 8. 错误处理

### 8.1 中心端错误

| 错误 | 处理 |
|------|------|
| ConfigEventBus 缓冲区满 | WARN + drop + alarm (`metrics.bus_dropped.Inc()`) |
| Epoch 持久化失败 | CRITICAL + 不阻塞, 下次 startup 重新生成 |
| SyncGate 决策时 collector 不在 DB | WARN + skip + 不报错 (边缘设备可能即将 Hello) |
| ConfigManifest 编码失败 | ERROR + log + 跳过该边缘设备, 不影响其他 |
| ConfigManifest MQTT 发送失败 | 退避重试 3 次 (1s, 3s, 9s) + 失败进 notifications |

### 8.2 节点端错误

| 错误 | 处理 |
|------|------|
| 收到 ConfigManifest 解码失败 | WARN + 不写 NVS + 不发 ConfigResult (fail) |
| apply_manifest 失败 | 重试 1 次, 失败上报 ConfigResult success=false |
| NVS 写入失败 | 重试 3 次, 失败进入 error state, LED 红闪 |
| ConfigQuery 发送失败 | 退避重试 + 周期 task 自动兜底 |

### 8.3 同步失败兜底 (关键)

**原则**: 任何同步失败都不能让边缘设备"卡死等"。

| 失败点 | 兜底机制 |
|--------|---------|
| 中心端 ConfigManifest 发送失败 | 30s 后节点周期 sync 再次触发 |
| 节点 apply 失败 | 5min 后周期 sync 再次触发 |
| Epoch 持久化失败 | 中心端使用内存 epoch, 启动时重建 |
| ConfigEventBus 满 | alarm + 运维介入 (1min 内 drop 必报警) |
| MQTT 断 | 客户端重连, 触发新 Hello |

## 10. 兼容性矩阵

### 10.1 协议兼容

| 组合 | Center=v2.0 | Center=v2.1 |
|------|------------|------------|
| **Device=v2.0** | ✅ 完整 | ⚠️ 降级: hash-only, 失去 epoch 优势 |
| **Device=v2.1** | ⚠️ 降级: epoch/nvs_has 字段被中心端忽略 | ✅ 完整功能 |

降级行为细节:

**Center=v2.1, Device=v2.0**:
- 中心端 SyncGate.OnHello 收到无 epoch/nvs_has 字段
- 视为: `nvs_has_config=true, epoch=0`
- 走 hash-only 路径
- 失去的功能: 恢复出厂自动重发、中心端变更主动 push

**Center=v2.0, Device=v2.1**:
- 节点发 Hello 带新字段
- v2.0 handler 忽略未知字段 (binary frame 默认行为)
- 但中心端会**误读** v2.1 字段偏移!
- 解决: Center 端**必须**升级到 v2.1 才能用 v2.1 固件

### 10.2 灰度策略

1. **Phase 1** (1 周): 后端升级到 v2.1, 不强制节点升级
2. **Phase 2** (2 周): 灰度 OTA 推 v2.1 固件, 监控 epoch 字段是否正常
3. **Phase 3** (1 周): 全量推 v2.1, 老固件淘汰
