# 方案 C 详细设计：ChannelCmdV2 事务化（消除 plan_data 内联）

> 状态：**待评审** | 日期：2026-10-10 | 作者：主 Agent
> 目标：消除「多步序列塞进队列元素」的设计违规，让命令元素 ≤ 256 B。

---

## 1. 问题陈述

### 1.1 违规事实
```
约束: 一条命令 ≤ 256 B（用户 2026-10-10 明确）
现状: bus_cmd_t = 700 B  ❌ 超 2.7 倍
根因: plan_data[512] 内联在命令元素里（占 73%）
```

### 1.2 连带问题
```
① 同一份 plan 在内存里存两遍:
     v2_control_slot_t.cmd.plan_data[512]   (msg_handler, s_slots[] = 4,560 B)
     bus_cmd_t.plan_data[512]                (bus_dma, 3 队列 = 16,800 B)
② 队列元素尺寸失控: 3 个 control 队列 = 17,112 B
③ 职责错位: 队列元素承担了「协议状态机」职责
     · 需要 2 B 长度前缀 + protobuf 编码
     · worker 里要 decode_batch_step 解析
     · 产生「sample_cmd_t 必须是精确前缀」这类脆弱约束
```

### 1.3 当初引入的原因（必须保留的语义）
```
提交 df6ec37c (2026-07-20)，业务场景 = SN-3001 光学雨量计:
  · reset_rainfall「清零累计雨量」 MaxSteps=3, AtMostOnce, Risk=high
  · set_rain_sensitivity「设置雨量灵敏度」MaxSteps=2, AtMostOnce, Risk=high

设计意图（definition.go:263 原文）:
  "The current dispatcher intentionally does not flatten it into a single
   request, which prevents a destructive action from silently losing
   readback/finally semantics."

⇒ 必须保留的三个语义:
   ① 原子性: 序列执行期间不被其他命令插入
   ② readback 验证: 写后必须读回确认
   ③ AtMostOnce: 破坏性操作只执行一次
```

## 3. 设计方案

### 3.1 核心思路

```
把「一次多步序列」从【一个队列元素】改为【一组带事务标识的独立命令】:

  改造前:  后端 --1 条命令(含 plan[512])--> 固件一次执行完

  改造后:  后端 --N 条命令(每条 ≤ 256 B)--> 固件逐条执行
              每条带 transaction_id + step_index + step_count
              固件按 transaction_id 串联，事务期间锁定该 channel
```

### 3.2 ⭐ 关键设计决策：复用 `attempt` 字段承载事务序号

**理由**（避免改 wire 协议版本）:
```
现有 `attempt`（字段 3，uint32）语义 = "第几次投递尝试"
  · 后端 dispatcher.go: 今天只有 attempt=1（firstPhysicalAttemptNo）
  · 固件: 仅用于重放识别（same_identity 比较里**没有** attempt）

⇒ 该字段今天**几乎闲置**，且语义天然是"同一条命令的第 N 次"
  可以扩展为「事务内的第 N 步」，无需新增字段号。
```

**但需要额外字段**，方案有两条路径：

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **C1** | 复用 `attempt` 高 16 位 = transaction_id 低位，低 16 位 = step_index | **零协议变更** | 语义混淆、可读性差 |
| **C2** | 提升 `V2_PROTOCOL` 1→2，新增字段 16/17/18 | 语义清晰 | 需协议版本升级、固件兼容处理 |

**推荐 C2**（语义清晰优先，且工程已有协议版本机制）:
```
新增 wire 字段（仅在 V2_PROTOCOL=2 时允许）:
  16  txn_id       varint  uint32  事务标识（同一次用户操作的 N 步共享）
  17  step_index   varint  uint32  本步在事务中的序号（0-based）
  18  step_count   varint  uint32  事务总步数（用于校验完整性）

向后兼容策略:
  · V2_PROTOCOL=1 的命令: 字段 16-18 缺失 ⇒ 走原有单步路径（plan 仍可用）
  · V2_PROTOCOL=2 的命令: 字段 16-18 必填 ⇒ 走事务路径
  · 固件同时支持两者 ⇒ 后端可灰度
```

### 3.3 固件侧设计

#### 3.3.1 新增事务表
```c
/* 事务表：按 channel 索引（一个 channel 同时只有一个在途事务）*/
typedef struct {
    uint32_t txn_id;        /* 0 = 空闲 */
    uint8_t  next_step;     /* 期望的下一个 step_index */
    uint8_t  step_count;    /* 事务总步数 */
    uint32_t started_ms;    /* 用于超时清理 */
    uint8_t  final_raw[V2_MAX_RX];  /* 最后一步的 raw（复用现有）*/
    size_t   final_raw_len;
} v2_txn_t;

static v2_txn_t s_txns[CHANNEL_CMD_V2_SLOT_COUNT];   /* = MAX_CHANNELS */
```

⚠ **内存代价**: `sizeof(v2_txn_t)` ≈ 4+1+1+4+128+4 = 142 B（含对齐约 144 B）
   × MAX_CHANNELS(5) = **720 B**（.bss，不占堆）

#### 3.3.2 事务处理流程
```
收到命令（V2_PROTOCOL=2）:
  if (step_index == 0) {
      /* 事务首步：建立事务 */
      t = &s_txns[slot];
      t->txn_id = txn_id; t->next_step = 0; t->step_count = step_count;
      t->started_ms = now;
  } else {
      /* 后续步：校验 */
      if (t->txn_id != txn_id)         => ACK failed, V2_ERR_TXN_MISMATCH
      if (t->next_step != step_index)  => ACK failed, V2_ERR_TXN_OUT_OF_ORDER
  }
  /* 执行本步 */
  execute_step(...);
  t->next_step++;
  if (t->next_step == t->step_count) {
      /* 事务完成 */
      send_final(...);
      t->txn_id = 0;   /* 释放 */
  } else {
      send_ack(...);   /* 中间步只 ACK，不发 FINAL */
  }
```

#### 3.3.3 新增错误码
```c
#define V2_ERR_TXN_MISMATCH    1007U  /* txn_id 与在途事务不符 */
#define V2_ERR_TXN_OUT_OF_ORDER 1008U /* step_index 不是期望值 */
#define V2_ERR_TXN_STALE       1009U  /* 事务超时（> V2_TXN_TIMEOUT_MS）*/
```

#### 3.3.4 事务期间的 channel 锁定
```
⚠ 这是**保留原子性语义**的关键：
  · 事务进行中，同 channel 的其他命令一律拒绝（V2_ERR_BUSY）
  · 事务超时（建议 30 s，与 deadline 一致）自动释放
  · 后端中断（如用户取消）⇒ 事务超时后自动清理
```

### 3.4 后端侧设计

#### 3.4.1 序列下发改造
```go
// 改造前（channel_cmd_v2_transport.go:175-200）
plan := definition.CompilePlanForAddress(...)
envelope.Plan = planSteps      // 全部步骤塞进一个 envelope

// 改造后
plan := definition.CompilePlanForAddress(...)
txnID := newTransactionID()    // 后端生成
for i, ps := range plan.Steps {
    env := baseEnvelope(ps.SingleStep)
    env.TxnID     = txnID
    env.StepIndex = uint32(i)
    env.StepCount = uint32(len(plan.Steps))
    // 逐条发布，等上一条 FINAL/ACK 后再发下一条
    publishAndAwait(env)
}
```

#### 3.4.2 复用已有状态机
```
每条命令走原有生命周期:
  QUEUED -> DISPATCHED -> DEVICE_ACCEPTED -> [VERIFYING] -> SUCCEEDED

事务语义由**后端聚合**:
  · 事务 = 一组 command_id，共享 txn_id
  · 任一步 FAILED ⇒ 整个事务 FAILED（后续步不再下发）
  · 全部 SUCCEEDED ⇒ 事务 SUCCEEDED
  · 中间步的 readback 结果作为下一步的输入（如需要）
```

⚠ **后端需要新增**：事务表的持久化（txn_id -> 步骤状态）
   可复用 `command_executions` 表加一列 `txn_id` + `step_index`，
   或新建 `command_transactions` 表。**倾向后者**（职责清晰）。

### 3.5 迁移路径（灰度）

```
阶段 1: 固件支持 V2_PROTOCOL=2（事务模式），保留 V2_PROTOCOL=1 路径
阶段 2: 后端能力协商 —— 设备上报 supports_transaction 能力位
阶段 3: 后端对支持事务的设备走新路径，其余走旧路径（plan 内联）
阶段 4: 全量切换后，删除 plan_data 相关代码

⇒ 阶段 1–3 可独立验证，且**可回退**。

⚠ **更正（评审指出）**：我原先写"随时可回退"是**错的**。
   阶段 4（删除 plan_data 旧路径）之后，**旧固件不再可用** ⇒ 该断言在 P4 之后不成立。
   正确表述：P1–P3 可回退；P4 是**单向门**，需单独评估并冻结旧固件版本。
```

## 8. 评审前补充核实（2026-10-10，5 个未决点已全部查清）

### 8.1 ⚠⚠ 点1 核实结果：`attempt` **不可挪用**（推翻我原设计的 C1 路径）

```
我原以为 attempt "几乎闲置"，实测是错的：

后端用途（不可挪用）:
  · channel_cmd_v2_transport.go:165  envelope.Attempt = attempt.AttemptNo
  · channel_cmd_v2_transport.go:221  **参与 wireDigest 计算**
       channelCmdV2WireDigest(execution, attempt.AttemptNo, bootID, ...)
  · dispatcher.go:301  创建 CommandAttempt{AttemptNo: firstPhysicalAttemptNo}
  · inbox.go:55        CommandInbox{AttemptNo: event.AttemptNo}
  · 是 attempt-scoped 记录与 fencing 的载体

固件用途:
  · same_identity() **不含** attempt（注释明说 attempt/boot_id/deadline 是 delivery metadata）
  · 但收到时校验 `!cmd.attempt` ⇒ 0 视为 malformed

⇒ **结论：必须走 C2（协议版本升级 + 新增字段）**，不能复用 attempt。
   我原设计的「C1 复用 attempt」路径作废。
```

### 8.2 点2 核实：`command_executions` 表已有完整结构

### 8.3 点3 核实：`V2_MAX_RX=128` 是**单槽存储**，中间步会覆盖

```
handler_channel_cmd_v2.c:21,28,219
  V2_MAX_READ_SIZE = 256  协议准入窗口（可读 256 B）
  V2_MAX_RX        = 128  单槽实际存储（注释：Storage is 128 B while admission accepts 256 B）

⇒ 事务的中间步 readback **会覆盖同一槽的 final_raw**。
  ⚠ 这是设计必须处理的点：
     · 若中间步 readback 需要保留 ⇒ 事务表需为每步留缓冲（内存↑）
     · 若只有最后一步 readback 重要（当前语义：Verification=readback 看最终值）
       ⇒ 可只保留最后一步（**推荐**，与现状语义一致）
```

### 8.7 修正后的 wire 设计（C2）

```
V2_PROTOCOL: 1 -> 2

新增字段（仅 V2_PROTOCOL=2 允许）:
  16  txn_id      varint  uint32   事务标识
  17  step_index  varint  uint32   本步序号（0-based）

固件解析（handler_channel_cmd_v2.c:311 的 switch）:

  case 17: if (v2_proto < 2) goto malformed; cmd.step_index = (uint32_t)v; break;
  case 18: if (v2_proto < 2) goto malformed; cmd.step_count = (uint32_t)v; break;

⚠ 注意：固件当前是「先解析完再校验协议版本」（case 14 只校验值）。
   新增字段后需要**两遍**或**记录 v2_proto 后置校验** —— 实现细节。
```
