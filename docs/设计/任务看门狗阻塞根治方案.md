# 任务看门狗阻塞根治方案

- 状态：设计 + 可编译原型（未提交，待评审）
- 日期：2026-10-04 ~ 2026-10-05
- 适用：ESP32-S3 / ESP32-C6，ESP-IDF v6.0.2，`esp32-collector` 固件
- 复核基线 commit：`2ce7109`
- 原型位置：独立 git worktree `/tmp/wtdtwd`（`git -C /tmp/wtdtwd diff`）

---

## 0. 结论先行（TL;DR）

**推荐方案：P0 解耦 + P1 有界 + P2 进度感知看门狗 + P3 安全模式 四层组合。**

一句话根因：`report_tx` 把**网络 socket 写**放在了**订阅了 TWDT 的任务**里，
而这次写的阻塞上限（esp-mqtt 默认 `network_timeout_ms = 10000ms`）**恰好等于**
TWDT 超时（`10000ms`）。于是"一次正常的慢发布"在算术上必然等于"任务卡死"，
看门狗只能误杀。

因此根治不是"把 `esp_task_wdt_add` 删掉"，而是**同时**做三件事：

1. **让阻塞不再发生在被监控任务上**（P0：所有帧改走 `esp_mqtt_client_enqueue`，
   调用者不写 socket）；
2. **重新定义"什么算卡死"**（P2：发布回调期间退订 TWDT，改用**独立任务**按
   "发布阶段是否推进"判定；等队列期间仍然订阅）；
3. **即使仍然重启，也不能自持**（P3：启动熔断 / 安全模式）。

三者缺一不可：只做 P0，未来任何一次新增同步 I/O 都会复发；只做 P2，等于
放弃对发布链的保护；只做 P3，设备仍然会周期性重启，只是不再无限循环。

## 1. 根因分析（复核后的行号）

> 本节所有行号均在 commit `2ce7109` 上复核过。

### 1.1 触发链路

`bus_worker.c:355` 的 `report_task`（任务名 `report_tx`）：

```
:362  esp_task_wdt_add(NULL);              // 订阅 TWDT
:363  for (;;) {
:364    esp_task_wdt_reset();              // 喂狗
:365    ... 三个非阻塞队列预扫描（:369 :376 各自喂狗）...
:396    xQueueSelectFromSet(..., 1000ms);  // 有界等待
:419    if (s_data_rpt_cb) {
:420      s_data_rpt_cb(...);              // ★ 同步调用发布链，期间无法喂狗
:424    }
:425    esp_task_wdt_reset();              // 回来才喂
```

`s_data_rpt_cb` 由 `main/main.c` 注册为 `msg_handler_send_data_report`。
调用链：

```
msg_handler_send_data_report   components/msg_handler/handler_data.c:254
  -> msg_handler_publish       handler_data.c:278
  -> msg_handler_publish_checked   components/msg_handler/msg_handler.c:55
  -> transport->ops->send / transport_broadcast
  -> mqtt_client_publish_impl  components/ehome_mqtt/ehome_mqtt.c:537
```

### 1.2 阻塞点：`esp_mqtt_client_publish` 在调用者上下文同步写 socket

这是本方案最重要的复核结论，**修正了"阻塞在等 PUBACK"的表述**：

- `esp_mqtt_client_publish()`（`managed_components/espressif__mqtt/mqtt_client.c:2568`）
  **不等待 PUBACK**。它把报文放入 outbox 后，直接调用 `esp_mqtt_write()`
  （`mqtt_client.c:2644`）在**当前任务**里把整条报文写进 socket。
- `esp_mqtt_write()`（`mqtt_client.c:818`）→
  `esp_transport_write(..., client->config->network_timeout_ms)`（`:823`）。
- 断连 / 半开连接时该写会一直阻塞到 `network_timeout_ms` 耗尽。默认值
  `MQTT_NETWORK_TIMEOUT_MS = 10000`（`lib/include/mqtt_config.h:57`）。
- 本固件 TWDT 超时也是 `10000`（`main/main.c:359-364`，
  `.timeout_ms = 10000, .trigger_panic = true`）。

**两个 10 秒相等 ⇒ 一次同步写就能吃光整个看门狗预算。这不是竞态，是算术**，
所以能稳定复现（实测 11 次 / 506s）。

串口证据里的 `E mqtt_client: Writing didn't complete in specified timeout: errno=119`
正是 `esp_mqtt_write()` 的 `wlen == 0` 分支（`mqtt_client.c:836`）。

### 1.3 QoS 差异（`ehome_mqtt.c:551-556`）

- 日志帧 `MQTT_FRAME_TYPE_LOG_STREAM`（`0x1D`）→ `MQTT_PUBLISH_QOS_NO_ACK` → 原本
  走 `esp_mqtt_client_enqueue`（**不写 socket**，非阻塞）。
- 其它所有帧 → `MQTT_PUBLISH_QOS_RELIABLE` → 原本走 `esp_mqtt_client_publish`
  （**同步写 socket**）。

所以业务帧（含 StatusReport、WriteRsp、ChannelCmdV2 final）都会走阻塞路径。
日志开启时 `report_tx` 每秒多投 1 帧日志，**放大了同一条 MQTT 连接上的流量**
（`LOG_STREAM_TX_CYCLE_MS=1000`、`LOG_BATCH_MAX=4`、`RING_CAPACITY=4`，
`components/log_stream/log_stream.c:25,48-63`），提高了撞上"半开连接 + 同步写"
的概率，也提高了 `report_tx` 调用发布回调的频次 —— 这就是"开日志更容易崩"的机制。

### 1.4 放大器的第二个来源：MQTT 内部任务也持有同一把 API 锁

`esp_mqtt_task` 主循环在 `MQTT_STATE_CONNECTED` 分支里**全程持有**
`client->api_lock`（`mqtt_client.c:1982` 加锁，`:2175` 解锁），其间执行
`esp_mqtt_write()`（重传队列）。因此：

- 即使调用者改走 `esp_mqtt_client_enqueue`，`enqueue` 也要 `MQTT_API_LOCK`
  （`mqtt_client.c:2729`）；
- 若 MQTT 任务正卡在一次 10s 的 socket 写上，`enqueue` 会在锁上**最多等约 10s**。

**这条路径同样会把 `report_tx` 拖到 TWDT 超时。** 因此 P0 必须配合
**缩短 `network_timeout_ms`**（原型取 `3000ms`），把锁的最坏持有时间压到
TWDT 预算的 1/3 以下。这是"解耦"之外必须补的一刀，仅靠 enqueue 不够。

### 1.5 已有但未用上的机制

- `bus_worker.c:70-73` 已有有界报告队列
  （`REPORT_CRITICAL_QUEUE_DEPTH` / `REPORT_TELEMETRY_QUEUE_DEPTH` /
  `CONTROL_FINAL_QUEUE_DEPTH` / `WRITE_RSP_QUEUE_DEPTH`）与丢弃计数
  `bus_worker_get_report_drop_count()`（`:1853`）、高水位
  `bus_worker_get_report_queue_high_water()`（`:1858`）。
- 也就是说"有界缓冲 + 过载丢弃"在本代码库里是既有范式，本方案只是把**同一范式
  补到发布链上**，而不是发明新机制。

## 2. 核心张力：TWDT 的存在意义 vs. "正常但慢"

TWDT 的语义是"**任务在预算内没有推进 ⇒ 系统可能已经无法自愈 ⇒ 重启**"。
本缺陷的本质是：

> 系统把"**正常的、有界的、慢的 I/O**"和"**任务卡死**"用了同一个判据。

因此只有三种出路，任何方案都必须归入其中之一：

| 出路 | 做法 | 代价 |
|---|---|---|
| A. 让阻塞有界且短于预算 | 缩短超时 / 限制单次写 | 慢网络下更早失败；需要重传兜底 |
| B. 把"订阅 TWDT"与"会阻塞的调用"解耦 | 发布移出被监控任务 / 缩小订阅窗口 | 该窗口内失去 TWDT 覆盖，**必须**有等价替代检测 |
| C. 重新定义"什么算卡死" | 从"固定周期喂狗"改为"**进度**是否推进" | 需要额外的进度探针与判定逻辑 |

**本方案 = A + B + C 的组合**，并对每一处移除的保护给出等价替代：

- P0（A+B）：发布一律 `enqueue`，调用者不写 socket；同时把
  `network_timeout_ms` 从 10000 压到 3000。
- P1（B）：`report_tx` 在**进入发布回调前退订 TWDT**，返回后重新订阅。
- P2（C）：用**独立任务**（`status_task`）按"发布阶段是否推进"判定停滞。
  **这不是"删掉 `esp_task_wdt_add`"，而是把覆盖窗口缩小 + 用独立探针补齐。**
- P3：安全模式，保证任何残余崩溃都不自持成循环。

## 3. 候选方案对比

### 方案 1：只缩短 `network_timeout_ms`（放弃）

把 10000 → 3000，让单次同步写不再吃光预算。

- **优点**：一行改动，无新任务、无新 RAM。
- **放弃理由**：这是"把窗口缩小"，不是"消除根因"。`report_tx` 仍然在**自己的
  上下文里**做 socket 写；只要出现一次慢于 3s 的写（弱网、大量重传、TCP 零窗口），
  仍然会阻塞 `report_tx`。而且它把 `report_tx` 的阻塞预算和 MQTT 任务的锁持有时间
  绑定在一起，任何未来的超时调整都会再次引入同类问题。
- **保留其合理部分**：作为 P0 的**配套加固**保留（见 §5.2）。

### 方案 2：把整个发布链移到独立任务（部分采纳，但本环境不可行）

新增一个 `mqtt_tx_task`，`report_tx` 只把帧投进队列，由 `mqtt_tx_task` 执行发布。

- **优点**：彻底解耦，`report_tx` 永不碰网络；`mqtt_tx_task` 可以不订阅 TWDT
  （或用更长的超时），语义最干净。
- **放弃理由（本环境硬约束）**：
  1. **RAM**：满负载时空闲堆仅约 **9–13KB**。新任务栈（发布链需要 ≥4KB，见
     `bus_worker.c:71-90` 对 `send_data_report` 2416 字节栈帧的分析）+ TCB +
     队列，会直接吃掉一半以上余量，与"任何新增常驻内存都要过这道坎"的既有约束冲突。
  2. **任务创建可靠性**：最近刚修过 `log_tx_task` 在满负载下 `xTaskCreate` 必然失败
     （已改 `xTaskCreateStatic`）。新增动态任务会重蹈覆辙。
  3. 现有 `report_tx` **已经**是"发布任务"——它的问题不是"跑在错误的任务里"，
     而是"**在订阅了 TWDT 的窗口里调用了会阻塞的函数**"。方案 4 用更小的改动
     达到同样的隔离效果。
- **结论**：方向正确但代价过高，本环境放弃；若未来 RAM 预算放宽，可作为演进方向。

### 方案 3：干脆去掉 `report_tx` 的 TWDT 订阅（放弃）

直接删 `bus_worker.c:362` 的 `esp_task_wdt_add(NULL)`。

- **优点**：立刻不误杀。
- **放弃理由**：**这等于放弃保护**。`report_tx` 一旦真的卡死（队列 API 死锁、
  传输层永不返回），将没有任何机制发现它，设备会静默僵死——比重启更糟（重启至少
  能自愈）。**任何"删除保护"的方案都必须给出等价替代检测**，本方案选择用
  P2 的独立进度探针替代，而不是裸删。

### 方案 4（推荐）：进度感知看门狗 + 发布解耦 + 安全模式

见 §4。核心是把"**在哪个任务里阻塞**"和"**用什么判据判卡死**"两个问题分开解：

- `report_tx` 的 TWDT 订阅**只覆盖等队列**（有界，≤1000ms）；
- 发布回调期间退订，由**独立的 `status_task`** 每秒检查"发布阶段是否推进"；
- 发布路径本身改为 `enqueue`（不写 socket），把最坏阻塞压到锁等待。

## 4. 推荐方案详细设计

### 4.1 P0：发布解耦（`components/ehome_mqtt/ehome_mqtt.c`）

`mqtt_client_publish_impl()` 不再区分 QoS 决定同步/异步，**一律**
`esp_mqtt_client_enqueue(op.client, s_up_topic, data, len, qos, 0, true)`：

- 调用者不再执行 socket 写（`enqueue` 内部不调 `esp_mqtt_write`，
  `mqtt_client.c:2741` 只入 outbox）；
- QoS1 的重传语义由 outbox 承担（`store=true`），断连期间消息排队等重连，
  **比原来"直接失败"更可靠**；
- outbox 满时返回 `-2`，是**可见的背压**而非静默阻塞。

配套（`mqtt_client.c:949` 一带的 `create_and_start_client`）：

```c
mqtt_cfg.network.timeout_ms = 3000;   /* 原为 IDF 默认 10000 == TWDT 超时 */
mqtt_cfg.outbox.limit       = 4096;   /* 原为 0（无界），断连期会吃光堆 */
```

### 4.2 P1+P2：进度感知看门狗（`components/bus_worker/bus_worker.c`）

新增两个内联助手（原型 `bus_worker.c` 的 `report_twdt_disarm/arm`、
`report_publish_begin/end`）：

- `report_publish_begin(stage)`：记录 `stage` 与起始时刻 → `esp_task_wdt_delete(NULL)`；
- `report_publish_end()`：记录本次发布耗时 → 清 `stage` → `esp_task_wdt_add(NULL)`。

`report_task` 的**四处**调用点全部包裹（`control_final` / `write_rsp` 的预扫描、
set 路径、以及 `s_data_rpt_cb`）。

独立探针 `bus_worker_poll_publish_stall()`（由 `main.c` 的 `status_task` 每秒调用）：

```
若 stage != 0 且 (now - since) > 15s:
    s_report_publish_stalls++，打 ERROR 日志
```

**这是"删掉保护"的等价替代**：

| | 原 TWDT | 新探针 |
|---|---|---|
| 覆盖"等队列不返回" | 是 | 是（仍订阅 TWDT） |
| 覆盖"发布回调永不返回" | 是（但会误杀慢发布） | 是（独立任务，只认 15s） |
| 误杀"正常但慢的发布" | 会发生 | 不会（<15s 不报） |
| 需要新任务/新 RAM | — | 复用 `status_task`，仅几个 `volatile` 变量 |

### 4.3 P3：安全模式（`main/boot_guard.c`，主流程并行实现）

**本原型不重复实现**（主工作树已有 `boot_guard.c/h`，见 §7），此处只记录它必须
满足的设计约束，作为本方案的组成部分：

1. **判据是"短命启动次数"**，不是"启动次数"——否则正常重启也会触发；
2. **安全模式必须能自动退出**，退出条件是"完成一次服务端往返"（强证据），
   而不是"等够时间"（弱证据，会让仍在崩溃循环里的设备自己解除降级）；
3. **安全模式必须覆盖服务端配置**：日志开关随 `ConfigManifest` 持久化，
   重启后会重新应用同一个坏配置——不覆盖就永远停在循环里；
4. 安全模式**只关可选特性**（日志上报），核心能力（联网、心跳、收命令、收配置）
   全部保留，保证仍可远程诊断与恢复。

## 5. 破坏性改动、代价与迁移

> 破坏性修改是允许的，但每一处都必须写明**代价**与**迁移方式**。

### 5.1 【破坏】非日志帧从 `publish` 改为 `enqueue`

- **改了什么**：`mqtt_client_publish_impl` 的返回语义。原来 QoS1 返回
  "已写入 socket"；现在返回"已交给 outbox"。
- **代价**：
  1. **返回值不再代表已上线路**。任何把 `mqtt_client_publish_impl() == true`
     当作"对端一定能收到"的调用方，语义被弱化。当前代码里没有这样的调用方
     （`msg_handler_publish_checked` 只用它做失败回退判断），但**这是接口契约
     变化**，必须在头文件写清。
  2. **outbox 占用堆**：断连期间 QoS1 消息在 outbox 排队，最多 `4096` 字节。
     这是新增的常驻上限（原来同步写不排队）。在 9–13KB 空闲堆下，
     4096 是刻意的保守值。
  3. **内存受限时 enqueue 返回 -2**，消息被**丢弃**（而不是阻塞重试）。
- **迁移方式**：
  - 头文件 `ehome_mqtt.h` 已注明"返回值只表示已交给 outbox"；
  - 新增 `mqtt_client_get_publish_fail_count()` /
    `mqtt_client_get_publish_backpressure_count()` 暴露背压，便于观测；
  - 依赖"发布成功"语义的上层，应改为依赖 QoS1 重传 + 服务端 ACK
    （现有 `crash_diag_on_ack` 已是这一范式）。

### 5.2 【破坏】`network_timeout_ms` 10000 → 3000

- **代价**：弱网下单次写更容易被判失败 → 触发 `esp_mqtt_abort_connection` +
  重连（`mqtt_client.c:997`）。即"更容易重连"。
- **迁移方式**：这是有意的取舍——"本次写中断 + 重连"远优于"整个设备重启"。
  重连由既有 supervisor（`mqtt_client_owner_step`）负责，无需上层改动。

### 5.3 【破坏】`report_tx` 在发布期间不订阅 TWDT

- **代价**：该窗口内没有 TWDT 覆盖。若发布回调永不返回，TWDT 不会 Aborting。
- **迁移/补偿**：P2 的独立探针（15s 阈值）+ 传输层自身的 3s 超时。
  **两个独立机制**共同保证"卡死可被发现"，不是单点。

### 5.4 【非破坏，但需说明】`outbox.limit = 4096`

- **代价**：极端拥塞时业务帧可能被丢弃（原来会阻塞直到成功）。
- **迁移**：丢弃是**有界且可观测**的（backpressure 计数 + ERROR 日志），
  且 `CONFIG_MQTT_OUTBOX_EXPIRED_TIMEOUT_MS=30000` 另有一道 30s 过期淘汰。

## 6. 验证方式

### 6.1 怎么证明"修好了"

| 层 | 验证 | 结果（本次） |
|---|---|---|
| 编译 | `./build_firmware.sh s3-n16` | 通过，`ehome_collector.bin 0x12f760`，82% 余量 |
| 单测 | `ctest`（host_tests） | 37/37 通过 |
| 新测试有效性 | 变异测试：把 `bus_worker_poll_publish_stall` 改成恒返回 false | 变红（2 条断言失败）；恢复后 md5 一致、重新变绿 |
| 效果层（**未做，需设备**） | 满负载反复切换日志开关，观察 `report_tx` 是否仍被 TWDT 杀 | 见 §8 未解决问题 |

新增 host 测试 `test_publish_progress_watchdog`（`bus_worker_report_tests.c`）断言：

1. 空闲时 `poll` 返回 false；
2. 进入发布后、未到 15s 阈值，`poll` 返回 false（**不误报**）；
3. 越过阈值，`poll` 返回 true 且计数 +1（**独立于 `report_tx` 是否推进**）；
4. 发布返回后 `stage` 清零、记录最坏耗时、不再报停滞；
5. 一次快速发布**不会**拉低已记录的最坏值。

### 6.2 怎么证明"没有把保护关掉"

这是本方案最容易被质疑的点，逐条给出反证：

1. **TWDT 仍然订阅**：`esp_task_wdt_add` 没有从代码中删除，只是**缩小了窗口**
   （等队列时仍订阅）。原型里 `bus_worker.c` 有 **4 个订阅点**：`report_task`
   （经 `report_twdt_arm()` 助手，发布前 `report_twdt_disarm()` 退订、发布后重订阅）、
   `uart_cmd_loop`、`spi_i2c_cmd_loop`、`rx_task`（后三者不变）。
   可 `grep -n "esp_task_wdt_add" components/bus_worker/bus_worker.c` 复核：`report_task`
   仍在循环里喂狗，退订/重订阅成对出现（`esp_task_wdt_delete` 仅在 `report_twdt_disarm` 一处）。
2. **新增了等价探针**：`bus_worker_poll_publish_stall()` 由**另一个任务**调用，
   其存在性由 §6.1 的变异测试证明——**测试能发现它失效**。
3. **退化路径可观测**：即使 TWDT 真的漏过，stall 计数与 ERROR 日志会在
   15s 内报出，而不是静默。
4. **端到端回归绊线**：`mqtt_recovery_tests.c` 的 `mock_publish_calls` 断言为 0，
   一旦有人把发布路径改回同步写（重新引入根因），测试立即变红。

## 8. 未解决的问题与不确定项

1. **未做设备级效果层验证**（禁区：不接触 `/dev/ttyACM0`）。因此"11 次/506s →
   0 次"这一效果层结论**尚未取得**。需要主流程在真实设备上按 §6.1 复现压测。
2. **`status_task` 的 1s 轮询对 15s 阈值的检出延迟**：最坏情况停滞发生后
   约 16s 才报出。若要求更快，可把探针改挂到 `esp_timer` 周期回调
   （但 `boot_guard` 已在用 `esp_timer`，需评估定时器数量）。
3. **`enqueue` 在 `api_lock` 上的等待仍未彻底消除**：P0 把最坏锁等待从
   "同步写 10s"压到"MQTT 任务写 3s"，但**没有归零**。若未来把
   `network_timeout_ms` 调回大值，锁等待会同步变大——这是一个**隐式耦合**，
   目前只能靠注释与 `outbox.limit` 约束，缺少编译期门禁。
4. **`outbox.limit = 4096` 的具体取值未经实测**：在 9–13KB 空闲堆下，
   4096 是否最优（vs 2048 / 6144）需要现场数据；本原型只保证"有界"，
   不保证"最优"。
5. **安全模式未纳入本原型**：P3 依赖主工作树的 `boot_guard`，其正确性
   （尤其"NVS 只在每次启动写一次"与"自动退出判据"）应由主流程单独验证。
6. **`report_publish_begin/end` 不是可重入的**：若未来发布回调内部再次调用
   `report_publish_begin`，`since_us` 会被覆盖、`stage` 会错乱。当前调用链是
   单向的（不会重入），但这是一个**隐含假设**，值得加断言或注释固化。
7. **`REPORT_PUBLISH_STALL_US = 15s` 是拍脑袋的**：取 1.5×TWDT。它应随
   `network_timeout_ms`（3s）与 outbox 重传行为一起标定，目前没有实测依据。
