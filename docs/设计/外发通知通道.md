## 1. 为什么不是「加一个 webhook 动作」

用户原始需求是「雨量中雨大雨给用户发 QQ/微信机器人消息」。取证后发现**缺的不是一个功能，是三样基础设施**：

| # | 缺口 | 取证事实 | 若不先补的后果 |
|---|---|---|---|
| 1 | **统一通知下游** | 通知写入点分布在 **4 个包 11 处、6 种写法、无共用函数**；失败全部静默吞掉，其中 datasource 与 datalifecycle **连指标都没有** | 外发若只挂 automation，告警/数据源/生命周期三域的通知**永远不外发** |
| 2 | **出站 HTTP 能力** | 运行时后端**零出站 HTTP**；`internal/{homeassistant,ota,datasource,alert}` 与 `pkg/*` 无任何 `http.Client`/`.Do()`。唯一可参考的 client 封装在 `simulation` 构建标签内 | 超时/重试/退避/SSRF 限制全部要从零建 |
| 3 | **敏感凭据存储** | 全仓无 `crypto/aes`/`cipher`/密文列；凭据一律**环境变量且不可回读**（MQTT/DB/JWT）；`DataSource.Config` 是**明文 text 列** | webhook 密钥「用户可配置 + 可回读」在本仓**无先例**，必须显式裁决 |

**因此本期只做**：通用 webhook + 上述三样基础设施 + 可观测性。
QQ（OneBot）与企业微信群机器人**都是 HTTP POST JSON**，作为两个预设模板由同一通道机制承载。

## 2. 已冻结的设计决策

### 2.1 外发挂在「共同下游」而不是某个调用者

**决策**：外发不在 11 个写入点各处调用，而是**订阅通知的产生**。

实现取向（二选一，实现前由主见 Agent 定）：
- **取向 A（推荐）**：新增 `internal/notify` 包，提供 `Dispatcher`，**所有通知写入点改为经它落库**。
  它同时负责：写 `notifications` 行（保持现有语义）+ 按通道配置投递。
  优点：单一入口，天然覆盖 4 个包；缺点：要改 11 处调用（机械改动，风险低）。
- **取向 B**：保持各写入点不变，新增**轮询扫描** `notifications` 表新行（outbox 模式，复用
  `commandexec/dispatcher.go` 的 lease 范式）。优点：零侵入；缺点：延迟、需额外的"已投递"标记。

**取向 A 更符合「一处定义，多处复用」**（规范 §1.2.2 的同源原则），且避免为新行加标记列。

### 2.2 失败必须旁路且可观测

沿用既有铁律（取证 §2）：通知写入失败**不影响主流程返回码**（datasource `service.go:857` 注释
`fail-open`；`migrate.go:411-412` `best-effort`）。外发同理：
- 投递失败**不回滚**业务事务、**不阻塞**采集热路径；
- **但必须可观测**：新增指标（现有 `ehome_data_consumer_db_write_failures_total` 只统计库写入失败，
  且 2/6 路径没打指标）。

### 2.3 凭据存储的裁决

本仓无应用层加密先例。三个选项：

| 选项 | 说明 | 评价 |
|---|---|---|
| (a) 明文列 | 与 `DataSource.Config` 一致 | **不可接受**：webhook 密钥泄露可直接向用户群发消息 |
| (b) **只写不读**（推荐） | 存列但 API **永不回显**（返回 `has_secret: true`），与 `users.password_hash` 的 `json:"-"` 同思路 | 无需引入加密体系，符合本仓既有范式；代价：用户无法查看只能重设 |
| (c) 应用层加密 | 引入 AES-GCM + 密钥管理 | 过度设计（规范 §7.1 明确禁止无产品驱动的子系统） |

**采用 (b)**：密钥列 `json:"-"`，列表接口只回 `has_secret` 与 `secret_hint`（末 4 位）。
**这既满足「可配置」又不引入加密体系** —— 用户拿到机器人的 token 后填一次，之后只验证不显示。

### 2.4 预设模板（用户裁决的两项）

两者都是 HTTP POST JSON，差异只在 **URL 形态**与**请求体形状**：

| 模板 | URL 形态 | 请求体 | 备注 |
|---|---|---|---|
| **企业微信群机器人** | `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<key>` | `{"msgtype":"markdown","markdown":{"content":"..."}}` | key 在 **URL 里**，需脱敏日志 |
| **QQ 机器人（OneBot v11）** | `http://<host>:<port>/send_msg` | `{"user_id":<id>,"message":"..."}` 或 `{"group_id":<id>,"message":"..."}` | 需 access_token（可选，放 header） |

设计上**不写死这两者**：`notification_channels` 表存 `type` + `target_url` + `secret` + `template`，
预设只是**前端表单的预填值**（选"企业微信"自动填 URL 前缀与 body 模板）。

## 3. 数据模型（冻结）

```go
// NotificationChannel 外发通知通道（通用 webhook）
type NotificationChannel struct {
    ID          uint       `gorm:"primaryKey" json:"id"`
    Name        string     `gorm:"size:64;not null" json:"name"`
    Type        string     `gorm:"size:24;not null" json:"type"`        // webhook | wecom | onebot（预设模板标识）
    TargetURL   string     `gorm:"size:512;not null" json:"target_url"` // 出站地址
    Secret      string     `gorm:"size:512" json:"-"`                   // 只写不读（裁决 §2.3-b）
    SecretHint  string     `gorm:"size:8" json:"secret_hint"`           // 末 4 位，供用户辨认
    Template    string     `gorm:"type:text" json:"template"`           // 请求体模板（JSON with {{.Title}} 等）
    MinLevel    string     `gorm:"size:16;not null;default:info" json:"min_level"` // info|warning|critical
    Enabled     bool       `gorm:"default:true" json:"enabled"`
    TimeoutSec  int        `gorm:"default:10" json:"timeout_sec"`
    MaxRetries  int        `gorm:"default:2" json:"max_retries"`
    CreatedAt   time.Time  `json:"created_at"`
    UpdatedAt   time.Time  `json:"updated_at"`
}
func (NotificationChannel) TableName() string { return "notification_channels" }

// NotificationDelivery 投递审计（每次尝试一行）
type NotificationDelivery struct {
    ID           uint64     `gorm:"primaryKey" json:"id"`
    NotificationID uint     `gorm:"index" json:"notification_id"`
    ChannelID    uint       `gorm:"index" json:"channel_id"`
    State        string     `gorm:"size:24;not null;index" json:"state"` // pending|delivered|failed
    AttemptNo    uint32     `gorm:"not null;default:1" json:"attempt_no"`
    StatusCode   int        `json:"status_code"`
    ErrorMessage string     `gorm:"size:512" json:"error_message"`
    DurationMs   int64      `json:"duration_ms"`
    CreatedAt    time.Time  `gorm:"not null;index" json:"created_at"`
}
func (NotificationDelivery) TableName() string { return "notification_deliveries" }
```

**为什么要 `NotificationDelivery` 而不是只在 notifications 上加标记列**：一次通知可投多个通道，
每个通道可重试多次 —— 这是 1:N:M 关系，压进一张表会丢失"哪个通道、第几次尝试、响应码多少"。

## 4. 接口契约（冻结：路径 + 方法 + 语义）

**必须先读**：全部写路径的 DTO 白名单范式见 `api/handler_alert.go:34-58`（create/update 分离，
指针字段区分「未传」与「显式零值」）。

| 方法 | 路径 | 语义 |
|---|---|---|
| GET | `/api/v1/notification-channels` | 列表。**永不返回 Secret**，只返回 `secret_hint` |
| POST | `/api/v1/notification-channels` | 创建。body 含 `secret`（可空） |
| PUT | `/api/v1/notification-channels/:id` | 更新。`secret` **未传 = 不改**，传空字符串 = 清空 |
| DELETE | `/api/v1/notification-channels/:id` | 删除（连带删除其 deliveries？**否** —— 审计记录保留） |
| POST | `/api/v1/notification-channels/:id/test` | **发送测试消息**（本期关键：让用户能立即验证配置对不对） |
| GET | `/api/v1/notification-deliveries` | 投递审计（可按 channel_id / state 过滤，分页） |

**响应信封**一律走 `api/envelope.go` 的 `Success`/`Error`/`ErrorWithCode`（本仓已全仓收敛）。

## 5. 状态机（冻结）

```
通道:  enabled=false → 不投递（不是失败，不写 delivery 行）
       enabled=true  → 参与投递

投递:  pending ──成功──→ delivered
          │
          └──失败──→ 可重试(max_retries) ──→ failed（终态）
                          │
                     指数退避: 1s, 2s, 4s...（上限 30s）
```

**退避必须与既有实现同风格**：参考 `ota.go:107` 的 MQTT 重试退避（本仓已有先例）。

## 6. 可观测性（冻结）

新增指标（沿用 `pkg/metrics/metrics.go` 的 `ehome_` 前缀与 `_total` 后缀）：

| 指标 | 类型 | 标签 | 用途 |
|---|---|---|---|
| `ehome_notification_deliveries_total` | CounterVec | `channel_type`, `result`(delivered/failed/retrying) | 投递结果分布 |
| `ehome_notification_delivery_duration_seconds` | Histogram | `channel_type` | 出站耗时 |
| `ehome_notification_channels_enabled` | Gauge | — | 启用通道数 |

**标签必须是有界基数**（沿用 `DeviceActionCreatedTotal` 的注释纪律：不用 node/command/参数标识做标签）。
**通道 id / URL 绝不进标签**（基数爆炸 + 泄露）。

## 7. SSRF 与安全（冻结）

出站 HTTP 是本仓第一个，必须一次做对：

1. **禁止内网地址**：解析目标 URL 后拒绝 private/loopback/link-local/ULA（`127.0.0.0/8`、`10/8`、
   `172.16/12`、`192.168/16`、`169.254/16`、`::1`、`fc00::/7`）。
   **例外**：允许用户显式开启 `allow_private`（家庭内网部署 OneBot 是合法场景）——
   默认关闭，开启时在 UI 与审计里明确警示。
2. **超时必设**（默认 10s，上限 60s）；**禁止无限重定向**（`CheckRedirect` 限制 3 跳）。
3. **密钥不落日志**：URL 中的 `key=`/`token=` 与 header 中的 Authorization 必须脱敏
   （沿用 `MainLayout`/WS 已有的 `token=***` 脱敏范式）。
4. **响应体读取上限**（如 4KB）：避免恶意/异常端点导致内存问题。
5. **投递不得回显响应原文给未授权用户**：`error_message` 截断到 512 且去除密钥。

## 7.5 实现补强（实施时超出设计的三处安全判断，已验证）

实施过程中工程师做了三处设计文档**未明确要求但正确**的判断，主控已独立验证（23 个边界用例全通过）：

| # | 补强 | 为什么重要 |
|---|---|---|
| 1 | **拨号时校验并直接用解析出的 IP 连接**：`DialContext` 里 `net.JoinHostPort(ip.String(), port)`，不把主机名交给网络栈二次解析 | 设计 §7.1 只写了"DNS 解析后校验"，但**发送前解析 ≠ 真正连出去的 IP**（DNS rebinding：两次解析给不同答案）。用解析结果直接拨号，使"判定过的地址"与"实际连接的地址"**必然同一**，这是不可绕过的强制点 |
| 2 | **`Transport.Proxy = nil`** | 若允许代理，地址判定发生在本进程、实际连接由代理发起 → **判定完全失效**。堵住 `HTTP_PROXY` 绕过 |
| 3 | **跨主机重定向丢弃 `Authorization`** | 目标站返回 302 到第三方主机时，密钥会跟着跑出去 |

**边界覆盖实测**（主控独立验证）：4-in-6 绕过（`::ffff:10.0.0.1`）、CGNAT（`100.64/10`）、
benchmarking（`198.18/15`）、`0.0.0.0/8`、multicast/reserved（`224/4`）、ULA（`fc00::/7`）
全部正确拒绝；同时**无误杀**（`172.32.0.1` 正确放行，因 `172.16/12` 只到 `172.31`）。

> **可复用结论**：出站 HTTP 的地址校验必须落在 `DialContext`（连接点），
> 而不是请求构造处。任何"先校验再交给标准库连接"的写法都留着 DNS rebinding 窗口。

## 7.6 【已发现】零值语义缺陷：`max_retries: 0` 会被 GORM 静默改写为 2

**与 `automation_rule.cooldown_sec: 0`（本仓已记录的另一缺陷）完全同类**，
说明这是本仓的**系统性陷阱**：带 `gorm:"default:N"` 的 int 列，**无法表达"显式零值"**。

**实测证据**（`internal/notify` 测试，主控独立复现）：
- 测试配 `TimeoutSec: 1, MaxRetries: 0`（意图：1s 超时、不重试）
- 实测投递耗时 **3.004s** ≈ 1s 超时 + 1s 退避 + 1s 超时 ⇒ **实际重试了 1 次**
- 根因链：`models.NotificationChannel.MaxRetries` 的 `gorm:"default:2"` →
  GORM 把 int 零值当"未设置"省略该列 → DB 用 default **2** →
  `NormalizeRetries(2)` 返回 2 ⇒ 用户配的"0=不重试"被静默改成"重试 2 次"
- 而 `NormalizeRetries` 的注释写"**负值**按默认值" ⇒ 实现与模型 default **语义冲突**

**影响**：用户设 `max_retries: 0`（明确不想重试，例如目标端点幂等性未知）会被静默改成 2 次重试，
**投递耗时变成 3 倍**，且用户无从察觉。

**裁决（未发布产品，直接改契约而非兼容）**：
- `MaxRetries` 与 `TimeoutSec` 都改用**指针类型** `*int`（`nil` = 用默认值，`0` = 显式零值），
  与自动化规则 `createAutomationRuleRequest` 的既有范式一致（"指针字段区分未传与显式零值"，
  见 `docs/设计/自动化策略引擎接口设计.md`）；
- 或去掉 `gorm default` 并在应用层显式赋默认值（创建时 `if nil { 2 }`）。
**两种都可行，实现时择一并说明理由。**

> **可复用结论**：本仓凡是"用户可配 + 有默认值 + 0 是合法取值"的 int 列，
> **一律用指针或去掉 gorm default**。已发现的两例（`cooldown_sec`、`max_retries`）都属此列。

## 9. 验收（实现后必须全部满足）

### 9.1 单测
- 通道 CRUD + 密钥只写不读（列表响应中**断言不含 secret 字段**）
- 投递成功/失败/重试/退避/终态
- SSRF 拒绝内网地址（表驱动覆盖 IPv4/IPv6/域名解析后为私网）
- 超时、重定向上限、响应体截断
- MinLevel 过滤（info 通道不接收 warning）

### 9.2 场景仿真（本仓已有 harness，必须用）
在 `backend/simulation/catalog/` 新增 `NTFY` 域场景（保持 ≥3 个/域的门禁）：
- **SIM-NTFY-004**：起一个**测试 webhook 接收端**（harness 内 `httptest.Server`），
  配通道 → 触发自动化通知 → 断言**真实收到 HTTP POST** 且 body 含预期标题
- **SIM-NTFY-005**：接收端返回 500 → 断言**重试**发生（收到 N 次）且最终 `failed`，
  同时**主流程仍成功**（旁路语义）
- **SIM-NTFY-006**：接收端 hang 住 → 断言**超时**且不阻塞主流程
- **SIM-NTFY-007**：删除/禁用通道后不再投递

> 这正是取证 §8 指出的「本仓无出站 mock 接收端范式」的补齐 —— 用真实 HTTP 验证，
> 不依赖真实 QQ/微信账号。

### 9.3 变异验收（套件可信的唯一证据）
- 关掉外发调用 → NTFY 场景必须变红
- 去掉 SSRF 检查 → 对应单测必须变红
- 让重试次数恒为 1 → SIM-NTFY-005 必须变红

### 9.4 门禁
`go build` / `go vet` / `gofmt` / `go test ./...` / 前端 `typecheck`+`test:run`+`build` 全绿。

## 11. 未决项（实现前需确认）

1. **取向 A vs B**（§2.1）：主见 Agent 在派发时定。倾向 A。
2. **删除通道时 deliveries 是否保留**：本文档倾向保留（审计价值），但若用户要求"删干净"需改。
3. **`MinLevel` 与通知 `Type` 的映射**：通知表用 `type`(info/warning/error/success)，

   （`models.NotificationType` 已是 critical→error、warning→warning、其余→info，反向映射需明确 `error`→critical）。
