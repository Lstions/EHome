## 零、设计公理（所有接口都遵守）

| # | 公理 | 为什么 |
|---|---|---|
| A1 | **依赖单向**：`databus → ingest → source → api`。任一层不得反向 import | 防倒灌；现有 `sensorfield`/`sourceref` 已遵守 |
| A2 | **热路径零 DB**：帧路径上的方法不得查库 | 生产每 10min 1.9 万行，DB 抖动会反压 ingest |
| A3 | **快照式共享**：跨 goroutine 的只读状态用 `atomic.Pointer` 整体替换 | 已由 `sourceref.Registry` 验证（`registry.go:42-56`） |
| A4 | **fail-closed 优先**：不确定时选择「不触发」而非「猜一个」 | 错源触发物理动作的代价远高于不触发 |
| A5 | **自描述**：每个可观测对象带 `Name()`/`Kind()`，用于日志与指标标签（**有界枚举**，禁止高基数） | 防止指标爆炸 |

## 一、L1 接入层（`internal/ingest`）

### 1.1 包定位

```
internal/ingest/
├── types.go        Sample / Field / Quality / Context（纯数据）
├── adapter.go      Adapter 接口 + Registry（选择器）
├── adapter_config.go   ConfigParser 后端适配
├── adapter_driver.go   Driver 后端适配（含 Calibration/Command 子分支）
└── errors.go       错误类型与哨兵
```
**依赖**：只依赖 `pkg/parser`、`internal/drivers`（类型转换用）、`internal/models`（只读模型）。
**不依赖**：`databus`、`gorm`（除 Context 里传 db 句柄）、`api`。

### 1.2 核心类型

```go
// Sample 是一次成功解析的统一产物。**唯一**跨层数据契约。
type Sample struct {
    EdgeDeviceID    uint
    LogicalDeviceID *uint   // nil = 未绑定逻辑设备（存量数据兼容）
    At              time.Time
    Fields          []Field
    Method          string  // 自描述，如 "ConfigParser(bms-v2)" / "Driver(prs3001)" / "Driver(prs3001)+"
    Quality         Quality
}

// Field 与 parser.Field 逐字段等价（保留 StringValue 兼容非数值量）。
// 为什么新建而不直接复用 parser.Field：parser 是 pkg（对外契约），
// ingest 是 internal 领域层。ingest 需要演进 Field（如加 Quality/Source），
// 复用 pkg 类型会把领域演进泄露成对外兼容负担。
type Field struct {
    Name        string
    Value       float64
    Unit        string
    StringValue string
}

// Quality 是解析质量。为将来的「部分解析」预留，当前只有 Ok。
type Quality uint8

const (
    QualityOk       Quality = 0 // 全部字段解析成功
    QualityPartial  Quality = 1 // 部分字段成功（当前不产出，预留）
    QualityDegraded Quality = 2 // 用了降级路径（当前不产出，预留）
)
```

### 1.3 Adapter 接口

```go
// Adapter 是接入层的**唯一扩展点**。
//
type Adapter interface {
    // Name 返回后端标识，用于 Sample.Method 与指标标签。
    // 约束：必须是**有界枚举**（常量集合），禁止拼接设备 ID/字段名。
    Name() string

    // Supports 报告本 adapter 能否处理该设备。
    // 由 Resolver 按注册顺序询问，第一个返回 true 的胜出。
    // 约束：必须是**纯判断**（不产生副作用、不写库）。
    Supports(ctx SupportContext) bool

    // Decode 把原始字节解析为统一 Sample。
    // 失败时返回 *DecodeError（含 Reason 枚举，供审计与指标）。
    Decode(ctx DecodeContext, raw []byte) (Sample, error)
}

// SupportContext 是 Supports 的输入（只读快照，已由调用方查好，避免 adapter 查库）。
type SupportContext struct {
    EdgeDevice     models.EdgeDevice   // 设备行（含 Type / DeviceConfigID）
    HasDeviceConfig bool               // 是否配了 device_configs
    DriverKind     DriverKind          // Plain / Calibration / Command
}

// DecodeContext 是 Decode 的输入。
type DecodeContext struct {
    EdgeDevice     models.EdgeDevice
    Raw            []byte  // 已重组的完整帧
    LogicalDeviceID *uint
    At             time.Time
    // DriverContext 只在 DriverKind 需要时非 nil（标定字节 / 命令 write_data）
    DriverContext  *DriverContext
}

type DriverContext struct {
    Calibration []byte  // CalibrationAware 时的标定字节
    CommandWriteData string // CommandAware 时的模板 write_data
}
```
### 1.4 选择器（替代硬编码 if/else）

```go
// Resolver 按注册顺序选择 adapter。
//
// 为什么用注册顺序而不是 map：顺序**就是语义**（ConfigParser 必须优先于 Driver，
// 否则标定驱动会被通用解析绕过 —— 见 consumers_heavy.go:270 的既有注释）。
type Resolver struct {
    adapters []Adapter   // 有序
}

// NewResolver 按给定顺序注册。顺序即优先级。
func NewResolver(adapters ...Adapter) *Resolver

// Select 返回第一个 Supports 成功的 adapter。nil = 无可处理者（fail-closed）。
func (r *Resolver) Select(ctx SupportContext) (Adapter, bool)

// Decode 是便捷方法：Select + Decode，返回首个成功结果。
// 所有 adapter 都失败 ⇒ 返回聚合错误（含每个 adapter 的 Reason，便于排查）。
func (r *Resolver) Decode(ctx DecodeContext, sctx SupportContext) (Sample, error)
```
### 1.5 错误契约

```go
type Reason string

const (
    ReasonNoAdapter      Reason = "no_adapter"        // 没有 adapter 支持该设备
    ReasonDecodeFailed   Reason = "decode_failed"     // 解析器返回错误
    ReasonEmptyResult    Reason = "empty_result"      // 解析成功但零字段
    ReasonCalibrationMiss Reason = "calibration_missing" // 标定驱动缺标定
    ReasonCommandCtxMiss Reason = "command_ctx_missing"  // 命令驱动缺模板
)

// DecodeError 是可分类的解析失败。
type DecodeError struct {
    Adapter string
    Reason  Reason
    Err     error   // 底层错误（可为 nil）
}
func (e *DecodeError) Error() string
func (e *DecodeError) Unwrap() error
```
### 1.6 与现状的等价性保证（M1 验收判据）

| 现有行为 | 适配后 |
|---|---|
| `calibrationAware` 驱动**绝不**走 ConfigParser | `adapter_driver.Supports` 对 Calibration 返回 true 且 **注册在 ConfigParser 之前** |
| `DeviceConfigID > 0` 且 parser 非空 ⇒ 走 ConfigParser | `adapter_config.Supports` 判断同样条件 |
| 解析失败 ⇒ `reassembler.Consume` 释放缓冲 + return | Resolver 返回错误 ⇒ consumer 走同一释放路径 |
| `parseMethod` 字符串格式 | `Sample.Method` 保持完全相同的格式 |

**回放验证**：用生产 30 分钟真实帧（约 5.7 万帧）跑改造前/后两版，逐帧比对 `Sample.Fields` 与 `unified_data` 落库结果，要求**零差异**。

## 二、L2 来源层（`internal/source`）

### 2.1 包定位

```
internal/source/
├── types.go     Handle / SourceKey / Status（纯数据）
├── registry.go  快照式注册表（atomic.Pointer）
├── derive.go    从设备+组派生期望态（纯函数）
└── errors.go
```

**依赖**：`internal/models`（只读）、`internal/sourceref`（复用 GroupSnapshot）。
**不依赖**：`internal/datasource`（防循环）、`gorm`（derive 是纯函数）、`api`。

### 2.2 核心类型

```go
// SourceKey 唯一标识一个「数据来源」。
//
// 与现有 data_sources 表的分组键一致：(LogicalDeviceID, Category)。
type SourceKey struct {
    LogicalDeviceID uint
    Category        string
}

// Handle 是一个来源的运行时句柄（不可变，随快照整体替换）。
type Handle struct {
    Key SourceKey

    // GroupID = 0 表示无来源组（单设备直连，存量语义）。
    GroupID uint
    // Kind = "" | "primary_backup" | "composite"
    Kind string

    // Members 是该来源的全部候选边缘设备（自动派生）。
    Members []Member

    // Snapshot 是来源组快照（GroupID=0 时 nil）。
    Snapshot *sourceref.GroupSnapshot

    // Revision 用于窗口身份（与 sourceref 同源）。
    Revision int64
    // TransitionSeq 权威成员变化计数（主备）；composite 恒 0。
    TransitionSeq uint64
}

// Member 是一个候选成员。
type Member struct {
    EdgeDeviceID uint
    Priority     int
    Active       bool   // 仅 primary_backup 有意义
    Enabled      bool
}
```
### 2.3 判定方法（热路径，零 DB 零锁）

```go
// Accepts 报告该帧是否代表本来源。
//
// 语义（与 sourceref.FrameMatch.Accepts 完全一致，不另造第二套）：
//   - 无来源组（GroupID==0）⇒ 仅该设备自己是成员时 true
//   - primary_backup ⇒ 仅 active 成员 true
//   - composite      ⇒ 任一成员 true（整组求值）
func (h *Handle) Accepts(edgeDeviceID uint) bool

// Authoritative 报告该设备是否当前唯一权威（用于「要不要清窗」的判断）。
// primary_backup：active 且 enabled
// composite：恒 false（无单一权威）
func (h *Handle) Authoritative(edgeDeviceID uint) bool
```
### 2.4 注册表（关键：新增反向索引）

```go
type Registry struct {
    mu sync.Mutex
    v  atomic.Pointer[view]
}

type view struct {
    byKey   map[SourceKey]*Handle
    // byDevice 是**反向索引**：设备 → 它参与的所有来源键。
    //
    // 为什么必须有：consumer 手里只有 edgeDeviceID，不知道它属于哪个
    // (logicalDevice, category)。没有反向索引就得每次查库或用 O(n) 线性扫。
    // 现有 sourceref.Registry **没有**这个索引（它只有 groups map，
    // 查询必须先知道 groupID），所以 L2 不能复用它做入口 —— 这是新增层的必要性。
    byDevice map[uint][]SourceKey
}

func NewRegistry() *Registry

// Publish 整体替换快照（唯一写入路径，事务提交后调用）。
func (r *Registry) Publish(handles []*Handle)

// Resolve 按「设备 + 类别」解析来源（热路径：无锁、无分配）。
func (r *Registry) Resolve(edgeDeviceID uint, category string) (*Handle, bool)

// ResolveByKey 按来源键解析。
func (r *Registry) ResolveByKey(k SourceKey) (*Handle, bool)

// Handles 返回全部来源（只读快照，用于投影与前端）。
func (r *Registry) Handles() []*Handle

// Len 返回来源数量（O(1)，用于 0 组短路）。
func (r *Registry) Len() int
```
### 2.5 派生（纯函数，零 DB）

```go
// DeriveInput 由收敛器一次性查库填充。
type DeriveInput struct {
    Devices  []models.EdgeDevice                 // 已绑逻辑设备的
    Observed map[uint][]string                   // edgeDeviceID → 观测过的 category 列表
    Groups   []*sourceref.GroupSnapshot          // 现有来源组快照
}

// Derive 输出期望态（纯函数：无 DB、无时钟、无随机、可重复）。
//
// 判定：
//   1. 遍历 Groups：每个 enabled 组产生一个 Handle（带 GroupID/Kind/Snapshot）
//   2. 遍历 Devices+Observed：对未被任何组覆盖的 (logicalDevice, category)，
//      产生一个单设备 Handle（GroupID=0，Members=[该设备]）
//   3. 同一 key 同时有组与单设备 ⇒ **组优先**（组是用户显式配置）
func Derive(in DeriveInput) []*Handle
```
### 2.6 与 sourceref 的关系（明确不重复造轮子）

| 能力 | 归属 | 说明 |
|---|---|---|
| 组的不可变快照 | `sourceref.GroupSnapshot` | **复用**，不复制 |
| 帧-组匹配 | `sourceref.FrameMatch` | 规则层继续用它（已上线，不动） |
| 设备→来源反查 | **`source.Registry.byDevice`（新增）** | sourceref 没有 |
| 单设备直连语义 | **`source.Handle`（新增）** | sourceref 只认组 |
| 来源健康记账 | **`source.Handle.OnSuccess`（新增）** | 合并现有两处 MarkSuccess |

## 四、HTTP API 契约

### 4.1 新增：来源总览（只读）

```
GET /api/v1/data-sources/overview?kind=&category=&logical_device_id=
```
**响应**：
```json
{
  "code": 0,
  "data": {
    "items": [{
      "logical_device_id": 14,
      "logical_device_name": "bms",

      "group_id": 0,
```

**字段约定**：
| 字段 | 类型 | 说明 |
|---|---|---|

| `status` | `ok` / `degraded` / `unconfigured` / `disabled` | 从 Handle + health 派生 |
| `derived_at` | RFC3339 | 快照生成时间；前端用它显示「数据新鲜度」 |
**约束**：此接口**不可写**。无 `POST/PUT/DELETE /overview`。

### 4.2 既有：`data-sources` CRUD → deprecated

| 端点 | 处置 | 理由 |
|---|---|---|
| `GET /data-sources` | **保留**，标注 deprecated | 老客户端兼容 |
| `POST /data-sources` | **保留**，标注 deprecated + 响应头 `Deprecation: true` | 运维脚本可能仍在用 |
| `PUT /data-sources/:id` | 同上 | |
| `DELETE /data-sources/:id` | 同上 | |
| `POST /data-sources/:id/activate` | **保留但前端不再调用** | 主备交给来源组 |
| `POST /data-sources/:id/deactivate` | 同上 | |
| `GET /data-sources/:id/health` | 保留（只读，有诊断价值） | |
**为什么保留不删**：删接口会破坏运维脚本；M3 阶段可评估删除。**标注 deprecated 比删除更保守。**

### 4.3 既有：`source-groups` —— 唯一可写入口，保持不动

9 条路由全部保持现状（`handler_source_group.go`）。**本次不新增、不删减来源组接口。**

### 4.4 错误码契约（新增 3 个）

| code | HTTP | 场景 |
|---|---|---|
| `source_overview_unavailable` | 503 | 来源层未接线（启动顺序错误） |
| `deprecated_endpoint` | 200（仅 header） | 走 deprecated 的写端点时不报错，只加 `Deprecation: true` header |
| `source_not_found` | 404 | `ResolveByKey` 未命中 |
**约束**：错误码必须三向一致（backend 常量 / simulation 白名单 / 前端 union），由门禁 SG-16 同款机制校验。

## 八、接口稳定性承诺

| 层 | 稳定性 | 允许的变更 |
|---|---|---|
| HTTP API | **稳定** | 只能加字段（不可改/删既有字段） |
| 前端类型 | 跟随 HTTP | 同上 |
| `ingest.Adapter` | **稳定** | 新增方法需提供 default 实现（Go 无默认方法 ⇒ 用可选接口） |
| `source.Registry` | 内部 | 可自由演进 |
| `models.*` | 跟随 DB | 加列可，删列需迁移 |
**`ingest.Adapter` 的演进策略**：若将来需要新能力（如 `Warmup()`），新增**可选接口**：
```go
type WarmupAdapter interface {
    Adapter
    Warmup() error
}
```
consumer 用类型断言检查，不做全局接口变更 —— 避免所有 adapter 被迫改。

## 十、接口设计的自查（写完后回头挑的毛病）

写完后我拿既有代码逐个对照，发现并修正了 4 处设计缺陷。记录在此，因为它们反映了真实约束。

### 缺陷 1：`source.Registry` 必须新增反向索引（已修正）

我最初设想直接复用 `sourceref.Registry`。但核对了它的 `view` 结构：

```go
// sourceref/registry.go:46-48
type view struct {
    groups map[uint]*GroupSnapshot   // key = groupID
}
```

**它只能「已知 groupID 查组」，不能「已知设备查它属于哪些来源」。** 而 consumer 手里只有 `edgeDeviceID`，不知道 `groupID`。

⇒ 必须在 L2 新增 `byDevice map[uint][]SourceKey` 反向索引。**这也是「为什么需要新增一层而不是改造 sourceref」的直接证据** —— `sourceref` 已上线且被规则求值链路消费（`MatchFrame` 在每帧热路径上），往里加索引会动到已验证的热路径，风险不成比例。

### 缺陷 2：`Adapter.Supports` 不能让 adapter 查库（已修正）

最初想的是 `Supports(deviceID)` 让 adapter 自己查设备。但：

- `Supports` 在每帧路径上被调用 → 违反公理 A2（热路径零 DB）
- adapter 查库会引入 `gorm` 依赖 → 破坏 L1 的可测试性

⇒ 改为 `Supports(SupportContext)`，**由调用方查好设备行一次性传入**。adapter 只做纯判断。

### 缺陷 3：`Kind` 的取值集合需精确对齐既有词表（已修正）

我最初写 `kind: direct/none/group`。但核对了 `source_groups` 的实际取值：

```go
// models/source_group.go:19-21
SourceGroupKindPrimaryBackup = "primary_backup"
SourceGroupKindComposite     = "composite"
```

⇒ L2 的 `Kind` 必须用 `direct` + 这两个既有值，**不能另造词表**。否则前端/后端/仿真三处词表漂移（现有门禁 SG-16 就是为这类漂移设的）。

### 缺陷 4：`data_sources` 的「只读」不能靠「前端不调用」保证

我最初写「前端不再调用 CRUD 即为只读」。但这只是 UI 层约束，运维脚本/老客户端/curl 仍可写。⇒ 补充两点：

1. 写端点返回 `Deprecation: true` header（可观测，不阻断）
2. **`/overview` 端点无任何写方法**（HTTP 405）—— 只读语义由路由层保证，不靠前端自律

### 自查结论

| 缺陷 | 若不修正的后果 |
|---|---|
| 1 | L2 无法在热路径反查 ⇒ 只能每帧查库 ⇒ 违反 A2，生产会反压 ingest |
| 2 | adapter 带 gorm 依赖 ⇒ 无法纯单测；且每帧多一次 DB 往返 |
| 3 | 三处词表漂移 ⇒ 前端显示空白、仿真白名单失配 |
| 4 | 「只读」只是口头约束，实际仍可写 ⇒ 用户信任被破坏 |

### 12.2 关键实现细节（与本文设计的差异）

落地时发现设计需要微调，记录在此以免后来者困惑：

| 设计原文 | 实际实现 | 为什么改 |
|---|---|---|
| `DecodeContext.DriverContext *DriverContext` | 增加 `DriverContextFn func() *DriverContext`（惰性） | 改造前标定/命令上下文的查询**只在 driver 分支发生**。提前查会让配置解析成功的帧（生产绝大多数）白多两次 DB 查询 —— 热路径不可接受 |
| `Supports(ctx SupportContext) bool` | 保持一致，但 `DriverKind` 由调用方用 `ingest.ResolveDriverKind` 算好 | 保证「Supports 判定」与「Decode 内部分支」用**同一个函数**，防止静默分裂 |
| resolver 由 main.go 注入 | **构造函数内默认装配**，`SetIngestResolver` 仅用于定制 | 实测：做成纯可选（nil⇒no_adapter）会让既有测试静默全失败（`TestS3_Probe_OneEventWritesTwoRows` 从绿变红）。接入层是必经路径，不是可插拔旁路 |
| `ActiveMemberID` 视为设备 ID | 用 `g.ActiveEdgeDeviceID()` | `ActiveMemberID` 是**成员行 ID**（`SourceGroupMember.ID`）。曾写错且旧测试因 MemberID 缺省为 0 而完全掩盖。已加回归测试（刻意让 MemberID=101/102 ≠ EdgeDeviceID=1/2） |
| 只注册 GET 即只读 | 显式注册写方法返回 405 | 实测 gin `HandleMethodNotAllowed` 默认 false ⇒ 未注册方法返 **404**。404 表达「资源不存在」，405 才准确表达「端点存在但不允许该方法」 |

### 12.3 M3 的明确决策：**暂不下线**旧主备状态机

评估后决定只做 M3 的第一步（合并重复注入），不下线 `datasource.Service` 的 R1–R11。

**技术理由（三条，按重要性）**：

1. **会让 7 个既有测试失效**：R1/R2(×2)/R3/R4/R10 六个规格测试 + `TestVerifyDiff_LegacyVsGroupEquivalence` 等价性差分门禁。
   它们是既有资产，编码了旧契约。把它们当「过时测试」删掉是危险的 —— 差分门禁曾是
   「决策逻辑只有一份」的反向证明，删掉后就没有任何机制防止两套判定漂移了。
2. **当前无实际危害**：生产 `data_sources` = 0 行、`automation_rules` = 0、`alert_rules` = 0。
   没有数据就没有状态可冲突，旧状态机的自动切换跑不起来。
3. **存在更稳妥的路径**：先观察 M2 投影器与旧状态机的 `status` 写冲突是否在
   真实使用中出现（两者都写 `status`，理论上会来回跳）。若真出现，
   可以只做「给 status 指定唯一写者」而不整体下线 —— 改动面小得多。

**这是一笔刻意保留的技术债，已登记而非遗忘。** 触发条件：当生产开始配置 `data_sources`
（或旧状态机与投影器出现状态抖动）时，必须处理。
