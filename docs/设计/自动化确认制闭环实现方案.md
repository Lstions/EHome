## 一、目标与已拍板决策

补齐 `require_confirmed=true` 规则触发后的"建议执行→人工确认→真正下发"链路。

| 决策项 | 拍板结果 |
|---|---|
| 语义路径 | **路径B**：planner 落 pending_confirm + 通知；新增 `POST /automation-events/:id/confirm`，人工点击当下由**操作者**走人工确认制铸 token 并 Create。系统常驻 actor **不豁免**近认证门。 |
| pending_confirm 超时 | **24h 超时 + 新增 `expired` 枚举 + 后台清扫**（挂 Planner 独立 goroutine，非 evaluator ticker） |
| §5.3 创建校验补强 | **本轮不做**（未拍板，留后续） |

## 二、评审复核后的关键设计修正（不盲信 subagent，逐项亲验）

1. **幂等键不在落 pending 时预存 detail**（评审①原建议被否）——`AutomationEvent.Detail` 是 `size:512` 的失败/抑制原因审计字段（models/automation.go:144），塞机器幂等键污染失败语义；且 event.ID 落库后才生成，落库时无法预存。**改**：confirm 端点用确定性键 `automation:confirm:<ruleID>:<eventID>`，confirm 时 eventID 已知，与事件 1:1 天然唯一；重复 confirm 同 eventID 必命中同一 `(scope,key)`，`command_executions.idx_command_idempotency` 唯一索引兜底 → 第二次走 replay 只读不写。
2. **状态翻转 UPDATE 原事件行，不新增行**（采纳评审③）——"一行=一次决策"；条件 UPDATE `WHERE id=? AND result='pending_confirm'` 作第一道防重闸；CommandID 本就标注"执行时回填"（models/automation.go:143）。
3. **TOCTOU 处置**：confirm 时**现读 rule**（updateAutomationRule:205-247 无 enabled 检查，rule 中途可改）+ 条件 UPDATE 闸门 + rule 被删/改 action 时 confirm 明确报错 fail-closed。**不存 params 快照到 detail**（size:512 装 params 污染失败语义）。人工确认的就是将要下发的当前 rule 内容，语义自洽。
4. **超时清扫挂 Planner 独立 goroutine**（采纳评审①，否决我原拟挂 evaluator ticker）——evaluator 30s ticker 只缓存 `sensor_threshold` 规则（evaluator.go:67-69），time_window 事件会漏扫且职责错位。SQL `result='pending_confirm' AND triggered_at < now-24h` 走 `(result)` 与 `(triggered_at)` 索引安全。
5. **校验收紧**：`validateAutomationRuleFields` 加 `requireConfirmed` 参数，`require_confirmed=true && action_type!='device_action'` → 拒绝。event 触发器**创建时禁配、更新时兼容存量**（不锁死存量规则）。
6. **通知须携带 event_id**——`notifyConfirmation`（planner.go:179-195）当前只带 rule_id，人工无法定位具体 pending 事件去 confirm，须补。

## 三、落点清单（文件 + 改动）

### 3.1 models/automation.go
- `AutomationEvent` result 枚举新增 `expired`（注释"pending_confirm 24h 未确认超时"）。

### 3.2 automation/planner.go
- `notifyConfirmation`：`broadcast` payload 与 Notification.Description 携带 `event_id`（record 返回 ev.ID 后透传）。
- 新增 `ConfirmEvent(ctx, eventID uint, actorID uint, confirmToken string) (models.AutomationEvent, error)`：
  1. 读 event，三路分支（NotFound→404；其他→500）；
  2. 条件闸门：event.Result != pending_confirm → 返回业务错（expired→"已超时"、executed→"已执行"幂等提示）；
  3. 现读关联 rule（NotFound→"规则已删除"；rule.ActionType 已 != device_action → "规则动作已变更，无法确认"）；
  4. `rule.ParseActionParams()` 取 params（与落 pending 同源）；
  5. **即铸即销**：`cmdSvc.IssueConfirmation(ctx, ConfirmationInput{EdgeDeviceID:rule.ActionDeviceID, ActorUserID:actorID, ActionID:rule.ActionID, Params:params, Reason:"automation:confirm:<ruleID>", SourceIP:...})`——若 `ErrRecentAuthRequired` 直接透传给前端（前端先做 manual-confirmation）；
  6. `cmdSvc.Create(ctx, CreateInput{EdgeDeviceID, ActorUserID:actorID, ActionID, Params, IdempotencyKey:automation:confirm:<ruleID>:<eventID>, ConfirmationToken:grant.Token, Reason})`——走全 11 项 availability gate + 幂等 + 审计 + readback；
  7. 成功 → 条件 UPDATE 原事件行 `result=executed, command_id=exec.CommandID`（RowsAffected=0 说明已被并发 confirm/expired，幂等返回现值）；失败 → UPDATE `result=failed_dispatch/failed_gate`（isGateError 分流）。
- 新增 `StartCleanup(ctx)`：独立 goroutine，每 5min 扫 `result='pending_confirm' AND triggered_at < now-24h` → 批量 UPDATE `result=expired, detail='pending_confirm 超时未确认'`。

### 3.3 api/handler_automation.go
- 新增 `confirmAutomationEvent(planner)`：`POST /automation-events/:id/confirm`。
  - body 可选 `{ "reason": string }`；token 由 planner 内部即铸即销，**不要求前端预先持有**。
  - `actor, _ := c.Get("subject_id")` 取操作者；`c.ClientIP()` 作 SourceIP。
  - 错误映射：`ErrRecentAuthRequired`→`ErrorWithCode(c,403,"recent_auth_required",...)`（前端据此引导 manual-confirmation）；gate/params/幂等冲突按 commandexec 错误谱映射。
- `validateAutomationRuleFields` 加 `requireConfirmed bool` 参数；`createAutomationRule`/`updateAutomationRule` 传入。交叉校验 `requireConfirmed && actionType!=device_action` → `"invalid_automation_rule"`。event 触发器 + require_confirmed 创建拒绝、更新放行存量。

### 3.4 api/routes.go
- 注册 `automation.POST("/events/:id/confirm", confirmAutomationEvent(automationPlanner))`（在现有 automation-rules 组内，JWTAuthWithDB 已挂）。

### 3.5 main.go / nodemgr / databus
- Planner 实例化处补 `go planner.StartCleanup(ctx)`。

### 3.6 frontend-shared/src/api/automation.ts
- **同步修正字段名对齐后端**（评审⑥：当前严重脱节）：`state`→`result`、枚举补 `expired`、`device_state`→`event` 等；
- 新增 `confirmAutomationEvent(id, {reason?})`。

## 四、测试（sqlite 内存 + 真实 GORM，对齐既有 planner 测试）

1. confirm 成功流转：pending_confirm → executed + commandID 回填 + command_executions 落行。
2. 幂等防重：同 eventID 二次 confirm → 不新增 command_executions 行（唯一索引 replay）。
3. 并发 confirm：两请求同 eventID → 仅一行 command_executions。
4. 超时清扫：造 triggered_at=25h 前的 pending_confirm → StartCleanup 一轮后 result=expired；confirm expired 事件被拒。
5. TOCTOU：rule 被改 action_type → confirm 报错 fail-closed。
6. 校验收紧：require_confirmed + notification → 创建 400；event + require_confirmed 创建 400、存量更新放行。
7. recent_auth_required：操作者 LastLoginAt 超窗 → confirm 403 recent_auth_required。
