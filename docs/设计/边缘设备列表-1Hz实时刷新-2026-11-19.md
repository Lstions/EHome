# 边缘设备列表 · 1Hz 实时刷新 — 设计记录（2026-11-19）

> 状态：已落地（前后端）
> 关联代码：
> - 前端：`frontend-shared/src/stores/edgeDeviceLive.ts`、`frontend-shared/src/views/edge-device/EdgeDeviceList.vue`
> - 后端：`backend/internal/livedevices/publisher.go`、`backend/internal/websocket/websocket.go`（ClientCount）、`backend/cmd/server/main.go`

## 1. 问题

边缘设备列表页的卡片（状态 / 最新读数 / 更新时间）与顶部统计**只在挂载时取一次**
（`EdgeDeviceList.vue` 的 `onMounted`），此后没有任何自动更新：用户必须整页刷新，
或者点「刷新列表」。数据本身其实一直在到达浏览器 —— 详情页早就在用 WebSocket 实时流，
只有列表页没接。

两个容易踩的隐性原因（都必须在设计里处理掉）：

1. `stores/edgeDevice.ts` 的列表快照有 **30s 缓存**（`LIST_CACHE_TTL`），
   非 `force` 的重复取数会直接命中缓存返回 —— 所以"加个 setInterval 调 fetchDevices"
   在前 30 秒里什么都不会发生。
2. 页面原来的统计是 `reactive` 对象、在 fetch 回调里**赋值**，因此即使读数变了，
   统计也不会跟着变（它只对"请求完成"有反应，不对"状态变化"有反应）。

## 2. 结论：状态与状态流分开，各管一段

| 层 | 负责 | 频率 | 载体 |
|---|---|---|---|
| HTTP 列表快照 | 成员 / 配置 / 分页 / 排序 | 低（筛选变化、30s 对账） | `GET /edge-devices` |
| **状态快照流（后端）** | `status` / `lastData` / `lastDataAt`（全体设备） | **1Hz，1 条/秒** | WS `edge_devices_live` |
| 逐帧事件流（后端） | 「刚收到了什么」 | 按采集帧（1~N 条/秒/设备） | WS `data_update` / `edge_device_status` |
| 前端实时层 | 把上面两条收敛成一份 1Hz 可渲染状态 | 1Hz flush | `stores/edgeDeviceLive` |

HTTP 快照与实时层**只在视图层合成**，谁也不写回对方：

```
                 ┌───────────────────────────┐
GET /edge-devices│ stores/edgeDevice (快照)  │──┐
                 └───────────────────────────┘  │   displayDevices (computed)
                                                ├──►  卡片 / 表格 / 统计
                 ┌───────────────────────────┐  │
 WS live(1Hz) ───┤ stores/edgeDeviceLive     │──┘
 WS data_update ─┤ 唯一订阅点 · 1Hz 合帧     │
    /status      └───────────────────────────┘
```

**通道分工（长期约定）**：详情页、图表、终端用**逐帧事件流**（要"刚收到了什么"）；
列表、看板用**状态快照**（要"现在是什么状态"）。前者对后者只是噪声 —— 100 台设备
各开 3 条 1s 指令就是 300 条/秒，而快照永远是 1 条/秒。

为什么不让实时值写回 `stores/edgeDevice` 的缓存：快照缓存还要服务 NodeDetail /
NodeOverview / DataPanel 三处固定参数的读取（见该文件头的缓存键说明），把会变的读数
写进去会让"缓存"同时承担两种生命周期，下一次谁覆盖谁就得靠猜。

## 3. 1Hz 渲染契约（本设计的核心）

**消息到达速率 ≠ 渲染速率。** `data_update` 是按**帧**推送的：一台设备开了 7 条轮询
指令、每条 1s，就是 7 条消息/秒；24 张卡片如果每条消息都触发响应式更新，主线程会被
重绘吃掉。所以实时层：

1. `ingest()` 只把补丁写进 `pending` Map（每设备只留最后一条，内存与消息速率无关）；
2. 每 1000ms 的 `flush()` 才把 `pending` 合并成一份新的 `live` 快照（`shallowRef`
   **整体替换**，一次 flush 只产生一次依赖失效）；
3. `flush()` 同时推进 `now`（1Hz 时基），模板里的「更新于 N 秒前」因此不需要第二个定时器。

因此无论 WS 每秒来 1 条还是 50 条，**页面每秒最多重算一次**。这条契约由
`stores/__tests__/edgeDeviceLive.spec.ts` 钉死（同一秒内 20 条消息，`live` 引用不变）。

### 为什么相对时间必须到秒

原 `formatRelativeTime` 的 <1 分钟恒返回「刚刚」。实时刷新后读数每秒都在变、时间戳
却一动不动，用户仍然会读成"没刷新"。现在 <60s 显示「刚刚 / N秒前」，`now` 由实时层
传入（同一帧内共用同一基准，不会出现 2秒前/3秒前 抖动）。

## 4. 生命周期

- `useEdgeDeviceLive()` 组合式在页面 `onMounted` 调 `start()`、`onUnmounted` 调 `stop()`；
- store 内部**引用计数**：多个消费者时只有最后一个 `stop()` 才退订 + 停表；
- **后台标签页不 flush**（`document.hidden`）：消息照收（缓冲只留最后一条），回到前台由
  `visibilitychange` 立刻补一拍；
- 会话失效/登出时 `clearSessionCaches()` 会清空实时层（与 `stores/edgeDevice` 同一时机）。

## 5. 降级与对账

页面挂在实时层的 1Hz 节拍上（`onTick`），**不自己开定时器**：

- WS 正常：每 **30s** 强制取一次列表，只用于对账成员/配置/排序（读数不依赖它）；
- WS 断开（反向代理挡掉 upgrade 等）：退回 **3s** 轮询，让页面仍然动起来，重连后自动停；
- 自动同步带 in-flight 守卫：上一拍没回来就跳过，绝不叠请求；
- 自动同步失败**不弹 toast**（3s 一次会刷屏），用户手动「刷新列表」仍能得到明确错误。

## 6. 后端 1Hz 状态快照通道（已落地）

`internal/livedevices.Publisher` 每秒构建一份全体边缘设备的状态快照并广播：

```jsonc
// WS 事件 edge_devices_live
{
  "at": "2026-11-19T02:00:00Z",            // 快照生成时刻（UTC / RFC3339）
  "items": [
    { "id": 12, "status": "active",
      "last_data_at": "2026-11-19T01:59:58Z",
      "data": { "temperature": 21.5, "humidity": 60 } },
    { "id": 13, "status": "pending" }      // 从没采到数据 ⇒ data 省略
  ]
}
```

设计要点：

1. **只查三列**（`id/status/last_data_at`）。快照里没有配置字段 —— 那些是 HTTP 列表
   的职责、且不会每秒变化；把它们塞进 1Hz 快照等于每秒重发静态配置（这正是"用列表
   接口做 1Hz 轮询"最大的浪费）。
2. **读数是内存缓存**（注入 `api.LatestValues`），不查库、不写库、不阻塞数据面；
   缓存冷（刚启动/该设备确实没数据）时该项省略 `data`，客户端回落到 HTTP 快照。
3. **无客户端不发**：`Hub.ClientCount() == 0` 时连查询都不做（空闲系统零成本）。
   注意这是"有没有人看"的门控，不是"有没有数据"。
4. **软删除自动生效**：GORM 的默认 scope 让已删除设备从快照消失，客户端"整体替换"
   因此不会留下幽灵行。
5. **单 goroutine 单拍**：不会并发堆积；构建失败只记一条 Warn（同一错误 60s 内抑制），
   下一拍自动重试（快照幂等，丢一拍不影响正确性）。
6. 事件名必须与 `backend/internal/events/events.go` 同步 —— CI 的
   `scripts/check_ws_event_names.sh` 做并集校验（该脚本已固定 `LC_ALL=C`：`comm`
   要求字节序，而 en_US.UTF-8 会忽略下划线导致假红）。

前端合并优先级（`stores/edgeDeviceLive.ts` 的 `applyPending`）：

1. **快照是基底** —— 它表达"现在系统里有哪些设备"，缺席即删除；
2. **逐帧补丁叠在上面** —— 同一拍内它通常比快照更新鲜；
3. **没有快照时**（旧后端 / 还没收到第一拍）退回"在上次结果上合并"，
   行为与引入快照通道之前完全一致。

因此前端同时兼容新旧后端：新后端吃 1 条/秒，旧后端仍按逐帧事件工作。

## 7. 已知限制（裁决点，不是遗漏）

1. **状态筛选下的"越过筛选"**：实时补丁可能让"状态=离线"筛选页里出现刚上线的设备
   （HTTP 查询不会）。当前裁决：接受 —— 信息是真实的，下一次对账会收敛。若产品要求
   严格不越界，应在筛选生效时关闭该页的实时叠加（`liveStore` 本身支持按需不 start）。
2. **成员变化不实时**：别处新建设备不会立刻出现在本页（成员靠 30s 对账/手动刷新）。
3. **实时层保留 10 分钟**：超过 `LIVE_ENTRY_TTL_MS` 无消息的条目会被丢弃，视图回落
   HTTP 快照（真源永远在）。
4. **批量选择保存的是旧对象**：`selectedDevices` 按 id 比较（`useEdgeDeviceBatch`），
   选中态不受刷新影响；但对象里的 `config.interval_ms` 可能是点击那一刻的快照值。
5. **今天的带宽是叠加的**：WS 是一条共享连接、服务端广播给所有客户端，因此快照与逐帧
   事件**并存**时客户端会同时收到两份。快照换到的是"速率上界 + 状态一致性"，真正的
   减法需要服务端按客户端订阅过滤（协议里没有 subscribe 机制，未做）。在几十台设备的
   部署上，快照约占几 KB/s～几十 KB/s，可接受；设备规模再上一个量级时应优先做
   **按订阅过滤**，而不是把快照改小/改成增量（增量会丢掉幂等性，这是净损失）。

## 9. 维护规则（新增"实时列表"页面时）

1. 不要在页面里 `wsStore.subscribe(DATA_UPDATE)` —— 用 `useEdgeDeviceLive()`；
2. 页面自己不要开 1s 定时器 —— 用 `liveStore.onTick(fn)`，保证全站只有一个渲染节拍；
3. HTTP 快照仍然由 `stores/edgeDevice` 负责；实时层只覆盖 status / lastData / lastDataAt；
4. 任何新的"会变字段"要加进 `DeviceLiveState` 与 `displayDevices` 的合成，不要各自临时拼；
5. **不要把配置类字段加进 `edge_devices_live`**（名称/配置/指令间隔/分页信息）：快照每秒
   一次，配置型字段放进去就是每秒重发一份静态数据；它们属于 `GET /edge-devices`。
6. 新增事件名必须同时改 `backend/internal/events/events.go` 与
   `frontend-shared/src/events/events.ts`，并跑 `scripts/check_ws_event_names.sh`。
