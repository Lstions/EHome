# 场景仿真验证框架（Scenario Simulation Validation）

- 版本：v1.0
- 日期：2026-09-12
- 状态：已定稿（本文件是 harness API 与场景目录的**唯一契约**，实现不得偏离）

---

## 1. 为什么需要这一层

现有测试分三层，各有一处够不到的盲区：

| 层 | 位置 | 跑在什么上 | 盲区 |
|---|---|---|---|
| 单元测试 | `backend/internal/**/*_test.go` | 内存 SQLite + mock | 看不见真实 PG 方言、分区、EMQX、组合根接线 |
| 集成测试 | `-tags=integration` | 真实 PG | 仍然只组装**部分路由**，MQTT 是假的，无真实设备 |
| 浏览器 E2E | `frontend-shared/e2e` | 真实前后端 | 只覆盖 UI 能触达的路径，节点/固件行为不可达 |

历史缺陷反复落在这些缝里：

- 消费者 sink 未二阶段注入 —— 引擎永不触发（SQLite 单测全绿）；
- 分区迁移水位推进错误 —— 整月只搬一个批次（`ehome_test` 全绿，真数据才暴露）；
- 整分区 DROP 建立在单设备保留期上 —— 会删掉别人的历史（无任何一层能发现）。

**结论：需要一层"黑盒 + 真实组合根"的仿真验证**，用真实 HTTP、真实 MQTT、真实 PG，扮演真实用户在真实时序里操作。本框架即此层。

## 2. 定位与非目标

**是**：功能正确性的端到端仿真 —— 真实用户视角的场景、真实基础设施、真实固件协议。

**不是**：
- 不是性能/容量压测（见 `docs/测试/性能压测与容量验证记录.md`）；
- 不是固件 host 单测（见 `esp32-collector` 侧测试）；
- 不是浏览器像素级回归（见 Playwright）。

```
   │          │◄─────────┤   ├─ Session（真实 JWT + 信封解包）        │
   │  真实     │          │   ├─ Eventually（轮询断言，杜绝 sleep）    │
   │  ehome   │          │   ├─ DB（场景库只读断言）                  │
   │  server  │◄─────────┤   └─ Devices（节点仿真器）                 │
   │ (子进程)  │  MQTT    │                                          │
   └────┬─────┘          │  catalog.All() ──► 72 个场景             │
        │                └──────────────────────────────────────────┘
        │      ┌──────────────┐        ┌──────────────┐
        └─────►│ 真实 PG      │        │ 真实 EMQX    │◄── 节点仿真器
               │ ehome_sim_*  │        │ 127.0.0.1:1883│
               └──────────────┘        └──────────────┘
```

三条不可动摇的设计原则：

### 原则 1：真实组合根（Real Composition Root）
harness **编译并启动真正的 `./cmd/server` 子进程**，绝不复制 `main.go` 的接线逻辑。
理由：`main.go` 的接线本身是被验证对象（sink 注入、评估器注入、迁移、保留期任务）。
一旦在 harness 里重写一遍接线，这层就退化成"又一个集成测试"，盲区原样保留。

### 原则 2：黑盒断言优先，白盒仅作兜底
场景通过 **HTTP 响应 + MQTT 下行帧 + WebSocket 推送** 断言用户可见结果。
直连数据库只用于两类断言：（a）用户界面看不到的持久化事实（审计行、分区、保留期清理）；（b）轮询等待的收敛条件。**不得**用直连 DB 替代本可走 API 的断言。

### 原则 3：确定性，不靠 sleep
所有时序断言走 `Eventually(ctx, timeout, interval, cond)`。
`time.Sleep` 只允许出现在"模拟真实上报节奏"的仿真器内部（如每 200ms 上报一次），且该 sleep 不得被用作断言同步手段。

### 4.1 包级命名空间规则（v1.2 补充 —— 覆盖一次真实的并行冲突）

`catalog` 是**一个 Go 包**，13 个域文件共享同一个包级命名空间。v1.0 只规定了"一域一文件"，
没有规定包级标识符的归属，导致并行实现中两个域各自声明了 `simNodeStatus`（签名还不一样），
编译期才暴露。规则补上：

| 位置 | 允许声明的包级标识符 | 命名要求 |
|---|---|---|
| `catalog.go`（主控维护） | 跨域共用助手、`Scenario`/`Domain`/门禁 | 一律 `sim` 前缀（如 `simCountRows`） |
| `<域>.go`（域作者维护） | 仅本域使用的助手与类型 | **必须**用该域小写短名做前缀 |

域小写短名前缀：`dep`、`auth`、`node`、`chan`、`edge`、`data`、`ds`、`auto`、`alert`、`cmd`、`ota`、`rt`、`err`。

即：`node.go` 里只能出现 `nodeXxx`；`data.go` 里只能出现 `dataXxx`；以此类推。
唯一例外是 `Register(...)` 调用本身。

**推论：文件名必须等于前缀（v1.5 补充，一处真实的设计更正）**

门禁第 8 条是用 `strings.TrimSuffix(name, ".go")` 从**文件名**推导期望前缀的。
因此 `xxx_yyy.go` 要求前缀 `xxx_yyy`，而不能是 `yyy` —— 也就是**子域不能靠文件名分层**。

这条约束曾经真的咬到过我：自动化专项设计了 11 个子域（TRIG/COND/WIND/…），
最初定的文件名是 `auto_trig.go` + 前缀 `trig`，**提交时必然门禁失败**。

遇到这种冲突只有两种解法，选择规则如下：

| 解法 | 何时选 |
|---|---|
| **改名让文件名 = 前缀**（默认） | 几乎总是。门禁保持「一条简单、可机械校验、零特例的不变量」 |
| 给门禁加豁免 | 仅当目录结构本身是硬需求（例如文件必须按上游工具约定命名） |

**默认必须选改名**：为目录美观去给门禁加特例，等于让每新增一个子域都要动门禁 —— 那是设计上的退步。
自动化专项的 11 个文件因此是 `trig.go` / `cond.go` / `wind.go` / …（详见自动化专章 §6）。

**此外，子域之间不要建 `xxx_shared.go` 这类共用文件**：
同包跨文件调用本来就是允许的（本规则只约束**声明名**，不约束调用写法），
共用代码直接落在某个既有域文件里被调用即可。
多一个共用文件 = 多一个多写者冲突点（本仓已因双写者覆盖过两次文件）。

**这条规则由门禁第 8 条机器校验**（见 §5.5），不靠自觉：新增场景文件时若前缀越界，
`TestCatalogGate` 直接失败并指出违规标识符与文件。

### 4.1b run 之间会通过共享 EMQX 互相污染（v1.8 补充 —— 一条使「全绿」失去意义的 P0）

**机制**（三处叠加，已逐行复核）：

| # | 位置 | 事实 |
|---|---|---|
| 1 | `internal/mqtt/mqtt.go:116` | 服务端订阅是**无 run 作用域的通配** `nodes/+/up` —— A run 的 server 会收到 B run 的节点上行 |
| 2 | `internal/databus/consumers_heavy.go:189-193` | 摄入按**数字 `edge_device_id`** 查库，**不校验帧来自哪个 node** |
| 3 | 每个 run 一个空库 | 边缘设备 ID 从 1 自增 → **两个 run 的第 k 个设备几乎必然同号** |

后果：B run 的一帧会被 A run 当成「自己设备的真实上报」——落库、更新最新值缓存、
**触发 A 的告警与自动化规则**。

现场证据：某 run 的 `server.log` 里出现了**另一个 run 的节点 ID**，
且其自动化规则被外来帧按 200ms 节奏反复求值（日志里连续刷同一条 warning）。

**为什么这使「全绿」失去意义**：污染是**单向**的 —— 它只会把绿的弄红、引入杂音，
不会把红的弄绿。所以：
- 「全绿」在**串行**前提下可信；
- 「红了」在并发前提下**不可信**（可能是别人的帧打进来的），不得据此改断言。

**修法**：harness 用 **run 级排他锁**（`flock LOCK_EX`）强制串行。
选 `flock` 而非 PID 文件的原因：持有者进程崩溃时内核自动释放，不会留下永久死锁。
锁文件 `.logs/simulation/.run.lock` 内写 PID 与开始时间，便于诊断「谁持有」。

**产品侧观察（不在本期范围，留待裁决）**：摄入路径不校验「帧所属节点」与「边缘设备所属节点」是否一致，
意味着**任何能向 `nodes/<任意>/up` 发布的 MQTT 客户端，只要猜中一个数字 ID，就能伪造他人设备的数据**。
生产环境靠 broker 认证限制发布者，但这是**纵深防御的缺口**：
建议摄入时校验 `edge_device.node_id == evt.DeviceID`（帧来源主题里的节点 ID）。

### 4.1c 孤儿库清扫必须收窄谓词（v1.9 补充 —— 一次差点造成数据丢失的教训）

排他锁带来一个便利：持有锁期间可以安全清扫「上一个 run 崩溃留下的孤儿库」。
但**第一版实现用了宽谓词** —— `^ehome_sim_[a-z0-9_]+$` 且非当前 run 的一律 DROP。
结果第一次真跑就删掉了一个**手工命名**的 `ehome_sim_recon`（人用来做侦察的库）。

**为什么这是个设计错误而不只是手滑**：`ehome_sim_` 这个前缀正是设计 §7-1 为了**安全**划定的白名单前缀 ——
它表达的是「这个库可以被 harness 操作」，**不是「这个库可以被自动删除」**。
把前者当作后者，等于**把安全机制误用成破坏机制**；任何按文档合法起名的人都会中招。

**正确做法**：只清扫**确切匹配 harness 自己生成形态**的库名
（`ehome_sim_sim_<yyyymmdd>_<4 位十六进制>`，以 `db.go` 的 RunID 生成规则为准；
`Options.RunID` 自定义的名字**也不该**被自动删）。
原则：**宁可漏删，不可误删** —— 匹配不到就跳过并记 Info（列出「疑似手工库，未清理」）。

### 4.2 「写库先于求值」的观测窗口（v1.7 修正 —— 原表述的适用范围是错的）

`SensorParserConsumer.Handle` 的执行顺序是：

```
解析 → 落库(≈355) → rollup/latest → alertSink(370) → automationSink(376) → sourceHealth(381) → WS广播(≈489)
```

**这带来一个通用陷阱：任何一个「先写库、后求值/广播」的异步链，都会让「我查到库里有了」早于「本帧的副作用已发生」。**

#### 4.2.1 哨兵帧的形态（只影响用 `ProvisionSimpleDevice` 的域）

`ProvisionSimpleDevice` 的自检（`fixture.go:189-213`）**只等落库**就返回，于是它那帧哨兵（`sim_temp=21.37`）的
求值与广播可能在夹具返回之后才发生。实测证据（SIM-RT-001）：

```
推送里的 sim_temp = 21.37，期望 23.5        # 21.37 正是夹具哨兵值
```

当时它只按 `edge_device_id` 过滤，把**连接之前**产生的哨兵推送当成了「连上之后收到的」。

**影响范围（v1.7 更正）**：只有调用 `ProvisionSimpleDevice` 的域（`ds.go` / `rt.go` / `data.go`）会有**哨兵帧**。
`autoProvisionDevice`（`auto.go:191-263`）**不做任何上报**（它只建节点/配置/边缘设备 + `Connect()`），
因此自动化域**没有**哨兵帧。我在 v1.6 里写的「用 autoProvisionDevice 也一样」是**错的**，
由子代理逐行核对源码后证伪 —— 记此更正。

此外哨兵帧携带的是**夹具自己那台 edge_device 的 ID**，而 `evaluator.go:366-368` 的第一道匹配就是
`TriggerEdgeDeviceID != 0 && r.TriggerEdgeDeviceID != target → continue`，
所以**跨场景的哨兵不可能触发别的场景的规则**（除非规则显式把目标设为 0 = 任意设备，那是文档注明「不推荐」的配置）。

#### 4.2.2 真正通用的形态：**自己上报的帧，求值也可能晚于落库**

即使没有哨兵，`persist(352) → automationSink(376)` 的顺序依然成立。
场景若用「查 `unified_data` 出现该行」当作「本帧已求值完毕」的证据，就会**读得太早**：
对「断言没有事件」的场景造成**假绿**（读的时候事件还没写），对「断言恰好 N 条」造成**计数漂移**。

**正确做法（与是否有哨兵无关，所有域都适用）**：

| 修法 | 适用 |
|---|---|
| 1. **有界负向观察 + 终判**：先 `EventuallyError(短窗)` 观察，再读一次列表做最终判定（事件只增不删，终判覆盖观察窗） | 「不应触发」「事件数为 0 / 恰好 N 条」类断言 —— **推荐** |
| 2. **断言锚定自己上报的特征值**（如 `trigger_value == 本次值`，用与哨兵不同的值） | 「触发了」类断言 —— 比「收到任意事件」更强 |
| 3. **同设备、同帧、只差一个条件的对照策略**：先等对照策略触发，再断言被守护规则沉默 | 需要证明「不是没跑到，而是不该触发」时 —— 最强 |
| 4. 阈值与哨兵值不重叠（哨兵 = `21.37` / `0`） | 仅对用 `ProvisionSimpleDevice` 的域有意义 |

**为什么不在 harness 里修**：让夹具等到「广播已发出」需要它建立 WS 连接并匹配事件，
会把夹具与 WS 层耦合、并给每个场景加一次连接开销；而修法 1–3 本来就让断言更强。
因此选择**在场景侧规避 + 写进 README 的「必须知道的坑」**。

## 5. Harness API 契约（冻结）

### 5.1 Env 生命周期

```go
package harness

// Start 完成一次仿真运行的全部准备，返回的 Env 供全部场景复用。
// 任一步失败 → 以可执行的错误信息终止（例如"PG 不可达，请先 make infra"）。
func Start(t *testing.T, opts Options) *Env

type Options struct {
    RunID    string        // 缺省 = sim-<UTC 时间戳>-<4 位随机>
    DSN      string        // 缺省从 EHOME_DB_* 环境变量组装
    MQTTAddr string        // 缺省 tcp://127.0.0.1:1883
    AdminUser string       // 缺省 "admin"
    AdminPass string       // 缺省随机强口令
    KeepDB   bool          // 缺省 false：运行结束 DROP 场景库
    LogLevel string        // 缺省 "info"
}
```

Env 暴露：

```go
type Env struct {
    T        *testing.T
    RunID    string
    BaseURL  string   // http://127.0.0.1:<随机空闲端口>
    Admin    *Session // 已登录的管理员会话
    DBName   string   // ehome_sim_<runid>
    Logs     *LogBuffer
}

func (e *Env) Session(user, pass string) (*Session, error) // 新建独立会话
func (e *Env) Login(user, pass string) (*Session, error)
func (e *Env) Device(nodeID string) *Device  // nodeID 自动加 e.RunID 命名空间前缀
func (e *Env) Eventually(timeout time.Duration, cond func() error) // 轮询直到 cond 返回 nil
func (e *Env) SQL() *sql.DB
func (e *Env) Evidence(name string, value any) // 记录证据，进 summary.json
```

**启动序列（必须按此顺序，不得简化）**：

1. 解析并**校验** DSN：库名必须匹配 `^ehome_sim_[a-z0-9_]+$`，否则拒绝启动（见 §7 红线）。若库已存在则先 DROP（幂等重跑）。
2. 创建场景库（连 `postgres` 维护库执行 `CREATE DATABASE`）。
3. 取一个空闲端口（`net.Listen(":0")` 后关闭）。
4. `go build -buildvcs=false -o <tmp>/ehome-sim-server ./cmd/server`（整个运行只编译一次）。
5. 启动子进程，**工作目录设为临时目录**（不得是仓库根：固件上传会落盘到 `<cwd>/firmwares/`），
   注入环境变量：
   `EHOME_DB_*`（指向场景库）、`EHOME_SERVER_ADDR=:<port>`、`MQTT_BROKER`、
   `EHOME_MQTT_CLIENT_ID=ehome-sim-<runid>`、`EHOME_JWT_SECRET`（随机）、
   `EHOME_ENV=development`、`GIN_MODE=debug`、`LOG_LEVEL=info`、`SEED_TEST_DATA` 不设置。

   `EHOME_EXTERNAL_HOST=127.0.0.1:<port>` **必须设置**：`POST /firmwares/upload` 在
   `EHOME_EXTERNAL_HOST` 为空且非开发模式时直接返回 500（`handler_ota.go:174-183`）；
   而 `isDevelopmentMode()` 的实现是 `EHOME_ENV=development` **且** `GIN_MODE=debug` 的与运算
   （`middleware.go:31-33`），仅设 `EHOME_ENV` 不够。设 `EHOME_EXTERNAL_HOST` 同时也让下载 URL
   的 host 与 `BaseURL` 一致，是首选做法；`GIN_MODE=debug` 一并设置以消除歧义。

   子进程 stdout/stderr 全量进 `LogBuffer`（失败时打印尾部）。
6. 轮询 `GET /health` 直到 200（上限 60s）。
7. 从启动日志解析一次性初始化凭据（`Initialization credential (valid for 10 minutes): <cred>`）。
8. `POST /api/v1/auth/initialize` 建立管理员账号；`POST /api/v1/auth/login` 拿到 `Env.Admin`。
9. `t.Cleanup`：杀子进程（先 SIGTERM，超时 SIGKILL）→ 按 `KeepDB` 决定是否 DROP 场景库 → 写 summary。

### 5.2 HTTP 会话与断言

```go
type Session struct{ /* token, baseURL */ }

func (s *Session) Get(path string) *Response
func (s *Session) Post(path string, body any) *Response
func (s *Session) Put(path string, body any) *Response
func (s *Session) Delete(path string) *Response
func (s *Session) Do(method, path string, body any) *Response

type Response struct {
    Status  int
    Code    string          // 信封 code（成功码）
    ErrorCode string        // 信封 error_code（可读原因）
    Message string
    Data    json.RawMessage
    Raw     []byte
    Duration time.Duration
}

func (r *Response) Expect(status int) *Response  // 失败 → 立即失败，附带完整 body 与耗时
func (r *Response) ExpectError(status int, code string) *Response
func (r *Response) Decode(out any) *Response
func (r *Response) DataInt(path string) int64    // 点路径取值，缺路径即失败
func (r *Response) DataString(path string) string
```

**强制要求**：所有断言必须走 `Expect*` / `Data*`，不得手写 `if resp.Status != 200 { t.Fatalf }` —— 前者统一携带证据与失败上下文。

### 5.3 节点仿真器

```go
type Device struct {
    NodeID string  // 已带命名空间
}

func (d *Device) Connect() error                       // 真实 MQTT 连接，订阅 nodes/<id>/down 与 /control
func (d *Device) Hello(version, model string, channelCount int) *frame.Decoder
func (d *Device) AwaitFrame(msgType uint8, timeout time.Duration) (*frame.Decoder, error)
func (d *Device) DataReport(channelID uint32, tsMillis uint64, payload []byte) error
func (d *Device) StatusReport(uptimeSec uint64, status string, rssi int) error

// —— 设备侧运行时事实上报（v1.1 补充，见下方"为什么必须有"）——
func (d *Device) ResourceReport(r ResourceReportData) error
func (d *Device) ConfigResult(manifestID, syncID string, success bool) error
func (d *Device) ConfigReport(manifestID string, channelCount int) error

func (d *Device) Close()
```

**为什么必须有 `ResourceReport` / `ConfigResult`（v1.1 补充，三条独立侦察一致确认）**

`commandexec` 的动作可用性门禁全部 fail-closed，且这些运行时事实**只能由 MQTT 帧写入**，
HTTP 侧没有任何写入口（已全仓 grep 确认）：

| 门禁 | 依赖的节点事实 | 唯一写入点 |
|---|---|---|
| `currentCapabilities` | `boot_id` != ""、`resource_reported_at` 在 5 分钟内、`command_engine_revision` != 0、`command_engine_capabilities` 四件套齐全 | ResourceReport |
| `requireReportedActionChannel` | `hardware_info.channels[]` 含 `{id, enabled:true}` | ResourceReport |
| `requireAppliedManifest` | `config_version` == manifest && `config_status`=="applied" && `config_sync_state`=="in_sync" | ConfigResult |

**关键陷阱**：`handler_hello.go:222` 在**每次 Hello 时主动清空** `BootID`/`ResourceReportedAt`/
`CommandEngineRevision`/`CommandEngineCapabilities`（"Hello 开启新的固件世代，旧能力报告作废"）。
所以节点仿真器**必须在每次 Hello 之后重新发 ResourceReport**，顺序不能反。

帧结构（`handler_resources.go`，MsgResourceReport = 0x19）：

- 顶层：field1=platform(string)、field2=resource_count(varint)、field3=buses_blob(bytes)、
  **field4=channels_blob(bytes)**、field9=command_engine(bytes)、field10=manifest_capacity(bytes, 可选)
- `channels_blob`：repeated field1 = channel_entry，entry 内 field1=id(varint)、field5=enabled(bool)
- `command_engine` 子消息**十个字段全部必填**（缺一即拒收），且带边界校验：
  | 字段 | 含义 | 约束 |
  |---|---|---|
  | 1 | revision | uint32 |
  | 2 | boot_id | string，长度 1..32 |
  | 3 | supports_channel_cmd_v2 | bool |
  | 4 | supports_bounded_batch | bool |
  | 5 | supports_finally | bool |
  | 6 | max_batch_steps | supports_bounded_batch 时 2..8；否则必须为 0 |
  | 7 | max_tx_bytes | 1..128 |
  | 8 | max_rx_bytes | 1..256 |
  | 9 | max_step_timeout_ms | 1..30000 |
  | 10 | ram_dedup_entries | uint32 |

  另：`supports_channel_cmd_v2` 为真时必须 `supports_finally` 也为真，否则拒收。

`Device.DataReport` **必须产生非 passive 事件**：`databus.DataEvent.IsPassive()` 定义为
`RequestID == 0 && EdgeDeviceID == 0`，而 `ShouldParse()` 直接依赖它 —— 两个都为 0 时数据不会落库。
因此 `DataReport` 内部必须按 `(node_id, channel_id)` 反查出 `edge_device_id` 并填入其中的一个字段。

- 帧编解码**必须复用 `backend/pkg/frame`**，不得在 harness 里另写一套（协议漂移是致命缺陷）。
- **WebSocket 地址必须做 scheme 归一化**（v1.4 补充）：`Session.WSURL` 基于 `BaseURL`（`http://…`）构造，
  必须在返回前把 `http`→`ws`、`https`→`wss`，并自检产出地址以 `ws`/`wss` 开头。
  原因是一次真实缺陷：`WSURL` 原样返回 `http://` 地址，而 gorilla 的 `Dialer.Dial` 只接受
  `ws`/`wss`，于是**每一次** WS 拨号都在客户端失败（`malformed ws or wss URL`，`resp == nil`、`status=0`），
  RT 域全部场景连同"未鉴权应 401"的断言一起被堵死。表现具有误导性：看起来像服务端拒绝，实际请求从未发出。
- `Connect` 前必须断言 `strings.HasPrefix(NodeID, "sim-")`，否则拒绝发布（见 §7）。
- 提供 `Device.Loop(ctx, interval, fn)` 用于"虚拟家庭"持续上报。

### 5.4 场景模型

```go
package catalog

type Domain string // 见 §6 表

type Scenario struct {
    ID     string // SIM-<DOMAIN>-<NNN>，全局唯一
    Title  string // 中文，真实用户口吻（"管理员…后可…"），不写实现细节

func Register(s Scenario)

```

**`Domain` 取值已冻结**（v1.1：此前只写了"见 §6 表"，导致并行实现可能各写各的）。
取值为 §6 表"前缀"列的**去 `SIM-` 短名**，即 `"DEP"`、`"AUTH"`、`"NODE"`、`"CHAN"`、`"EDGE"`、
`"DATA"`、`"DS"`、`"AUTO"`、`"ALERT"`、`"CMD"`、`"OTA"`、`"RT"`、`"ERR"`，共 13 个。

不变量：`ID == "SIM-" + string(Domain) + "-" + NNN`。这样 `Domain` 与 `ID` 互为校验，

### 5.5 测试入口与门禁

```go
//go:build simulation

func TestMain(m *testing.M)          // 起 harness，跑 m.Run()，收尾
func TestScenarios(t *testing.T)      // 顺序遍历 catalog.All()，t.Run(ID+" "+Title)
func TestCatalogGate(t *testing.T)    // 目录门禁（见下）
```

`TestCatalogGate` 必须校验并**失败**于：

1. 场景总数 **< 50**；
2. 场景 ID 重复，或不符合 `^SIM-[A-Z]+-\d{3}$`；
3. 场景 `Title` 为空 / `Doc` 为空 / `Run` 为 nil（禁止占位场景）；
4. 域数量 < 10；
5. 任一域场景数 < 3；
6. `ID` 的域段与 `Domain` 字段不一致（即 `ID != "SIM-"+string(Domain)+"-"+NNN`）；
7. `Domain` 取值不在 §5.4 冻结的 13 个之内；
8. **包级命名空间越界**（§4.1）：用 `go/parser` 解析 `catalog` 包全部源文件，
   检查每个文件的包级声明（func/type/var/const）是否符合该文件的前缀要求。
   违规时报出「文件:标识符」，明确指出它应当用的前缀。
   这条门禁的存在理由见 §4.1 —— 它守护的是"新增域文件不会撞名"这一可持续演进能力。

**禁止** `t.Skip` 出现在场景里。基础设施缺失时 `TestMain` 直接失败并给出可执行提示，不静默跳过。

### 5.6 隔离与命名

- 全程**单进程单库**，场景**顺序执行**（`TestScenarios` 不开 `t.Parallel`）。
- 每个场景创建的所有实体名必须带本场景命名空间：`sim-<runid>-<domain>-<n>`；
  harness 提供 `e.NS(scenarioID, suffix)` 生成，避免跨场景撞名。
- 场景必须自我清理（`t.Cleanup` 删除自己创建的资源），保证后续场景从干净状态出发。

**节点 ID 必须走 `e.DeviceFor(scenarioID, suffix)`，不得直接用 `e.Device(suffix)`（v1.3 补充）。**

理由是一次真实事故：`e.Device(local)` 只把 `RunID` 拼在前面，**不含场景标识**，
于是隔离性变成了"所有域的作者必须恰好选中互不相同的后缀"这一脆弱假设。实际已被打破：

```
SIM-ALERT-001  autoProvisionDevice(..., "rule", ...)   → nodes.sim-<runid>-rule
SIM-AUTO-001   autoProvisionDevice(..., "rule", ...)   → nodes.sim-<runid>-rule   ← 409 already exists
```

且长度受限：`nodes.node_id` 是 `varchar(32)`，`RunID` 已占 17 字符（`sim-YYYYMMDD-NNNN`），
留给局部名的只有 14 字符。直接用 `sceneSlug`（如 `auto-006-manual` = 15 字符）会**超长**。

因此 harness 提供 `e.DeviceFor`，内部使用**紧凑且唯一**的场景码（2 字母域名 + 3 位序号）：

| 域 | 码 | 域 | 码 | 域 | 码 |
|---|---|---|---|---|---|
| DEP | `dp` | EDGE | `eg` | ALERT | `al` |
| AUTH | `au` | DATA | `dt` | CMD | `cm` |
| NODE | `nd` | DS | `ds` | OTA | `ot` |
| CHAN | `cn` | AUTO | `at` | RT | `rt` |
| | | | | ERR | `er` |

例：`SIM-AUTO-006` + `manual` → `at006-manual`（12 字符），`node_id` 全长 30，安全。
超长时 `e.DeviceFor` 必须给出指明"把后缀缩短到 N 字符"的错误，不得静默截断
（静默截断会重新引入撞名）。

## 7. 安全红线（违反即视为任务失败）

1. **绝不接触生产/开发库**：harness 只允许 `CREATE`/`DROP` 名称匹配 `^ehome_sim_[a-z0-9_]+$` 的库。
   `ehome`、`ehome_test`、任何线上库一律拒绝连接。
2. **绝不干扰真实设备**：MQTT 只允许发布/订阅 `nodes/sim-*/...`。
   `Device.Connect`/`DataReport`/`Hello` 内部对 NodeID 前缀做强校验，不合规直接 error。
3. **绝不执行 git 命令**（提交由主控统一处理）。
4. **不修改白名单之外的文件**。
5. 不使用 `as any` / `@ts-ignore` / `t.Skip` / 空断言；不弱化既有断言。

## 13. 验证过程中发现的、**尚未修复**的产品不一致（待裁决）

以下不是场景缺陷，是被场景/子代理分析暴露出来的产品行为问题。已如实记录，**未擅自修改产品代码**。

### 13.1 概览 `latest_data` 的形状取决于缓存是否命中（`/overview`）

`handler_overview.go` 的 latest_data 有两条取值路径：

| 路径 | 行为 |
|---|---|
| 缓存命中（`LatestValue`） | 每设备**恰好一个**物理量 —— 缓存是 `map[edge_device_id]UnifiedData`，**只存一条** |
| 回落 SQL（`DISTINCT ON (device_id) ... ORDER BY created_at DESC`） | 先取时间戳最大的那一行，再 `JOIN ... ON created_at = latest.created_at` —— 因时间戳相同而**匹配该时刻的全部行**，可能返回**多个**物理量 |

诱因：`SensorParserConsumer` 把同一帧解析出的多个物理量用**同一个 `now`** 作 timestamp 批量写入（`consumers_heavy.go:341-346`），
所以同一设备的多个物理量**时间戳完全相等**。

后果：
1. **同一份数据，`latest_data` 的形状随缓存冷热而变**（1 个类别 vs N 个类别）；
2. 回落路径的 `DISTINCT ON` 在同时间戳下**选取是任意的**（PG 不保证 tie-break），
   叠加外层 JOIN 后甚至可能把多个类别的值混进同一个 map。

**为什么没修**：这是数据层缓存优化（v3.4 §3.2.4）遗留的语义分歧，修它要决定「latest_data 到底该表达什么」——
是「每设备一条最新记录」还是「每设备每个类别的最新值」。后者才是用户直觉，但缓存结构（一设备一条）不支持。
属于**产品语义裁决**，不是实现缺陷。

**场景侧的应对**：SIM-RT-003 已按「出现的那一个类别必须是本场景刚上报的值」断言，
对两种路径都成立且不放宽鉴别力（哨兵 21.37 与初始 0 都满足不了）。
