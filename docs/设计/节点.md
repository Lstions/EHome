## 1. 功能概述与端点

节点是 EHomeSystem 四层概念模型中的 **Layer 2 物理整机**（ESP32-S3 / ESP32-C6，运行 EHomeSystem 固件），是"现场总线和外设的受管执行端"。中心端是配置的单一事实来源，节点接收配置后驱动总线采集与控制，并持续回传运行状态、原始数据与命令结果。权威术语定义见 [术语表.md](术语表.md) §2.1；历史旧名已废弃。

节点侧职责与中心端要求的对照：

| 业务域 | 节点实际能力 | 中心端要求 |
|---|---|---|
| 网络接入 | STA 自动重连；无凭据时 SoftAP + HTTP 配网页；凭据存 NVS | 不参与配网页协议；等待 MQTT 上线 |
| 身份 | 优先用 eFuse Wi-Fi MAC 生成 12 位大写十六进制 `node_id` | 以 Hello 的 `node_id` 与 MQTT topic 为身份依据 |
| 配置 | 事务化重建 DMA、GPIO/PWM、总线、调度器、日志流 | 下发完整 ConfigManifest；仅在 `ConfigResult success=1` 后认定生效 |
| 现场采集 | UART / I2C / SPI / ADC 通道，每通道多边缘设备、每设备 3 命令 | 解析 DataReport 按边缘设备/命令索引路由原始数据 |
| 现场控制 | 兼容旧 WriteCmd；优先 ChannelCmdV2；GPIO/PWM 走 PeriphCmd | 按 V2 协议处理 ACK/终态，按身份四元组去重 |
| 可观测性 | 5 秒 StatusReport、ResourceReport、通道健康、运行时性能 | 刷新在线状态与能力快照；按需消费日志流 |
| 运维 | OTA 下载/校验/进度回传；长按 BOOT 5 秒擦 NVS | 依 OtaProg 跟踪；工厂重置后按新会话重配 |

## 2. 数据模型

后端模型 `models.Node`（backend/internal/models/models.go，表 `nodes`）：

```sql
CREATE TABLE nodes (
  id                    SERIAL PRIMARY KEY,
  node_id               VARCHAR(32) UNIQUE NOT NULL,
  name                  VARCHAR(64) NOT NULL,
  model                 VARCHAR(20),
  firmware_version      VARCHAR(32),
  protocol_version      VARCHAR(16) DEFAULT '2.2',
  platform              VARCHAR(16),            -- ESP32 / ESP32S3 / ESP32C6
  status                VARCHAR(20) DEFAULT 'offline',
  config_version        VARCHAR(64),            -- 当前已生效 manifest 哈希
  config_status         VARCHAR(20) DEFAULT 'pending',
  last_seen             TIMESTAMPTZ,
  last_ping_at          TIMESTAMPTZ,
  uptime_seconds        INTEGER DEFAULT 0,
  ping_latency_ms       INTEGER DEFAULT 0,
  mqtt_topic_up         VARCHAR(128),
  mqtt_topic_down       VARCHAR(128),
  wifi_ssid             VARCHAR(64),
  wifi_rssi             INTEGER,
  free_heap_bytes       INTEGER,
  capabilities          JSONB,
  hardware_info         JSONB,                   -- 含 runtime_performance / control_statistics
  dma_channels          JSONB,
  boot_id               VARCHAR(32),
  resource_reported_at  TIMESTAMPTZ,
  command_engine_revision        INTEGER DEFAULT 0,
  command_engine_capabilities     JSONB,
  connection_type       VARCHAR(32),
  connection_quality    INTEGER DEFAULT 100,
  latency_ms            INTEGER DEFAULT 0,
  online_duration       BIGINT DEFAULT 0,
  last_online_time      TIMESTAMPTZ,
  config                JSONB,
  config_epoch          BIGINT DEFAULT 0,
  last_manifest_id      VARCHAR(64),
  config_sync_state     VARCHAR(20) DEFAULT 'unknown',
  last_sync_at          TIMESTAMPTZ,
  last_sync_id          VARCHAR(64),
  log_stream_enabled    BOOLEAN DEFAULT false,
  log_stream_level      INTEGER DEFAULT 2,       -- 0=ERROR..4=VERBOSE
  created_at / updated_at TIMESTAMPTZ,
  deleted_at            TIMESTAMPTZ              -- 软删除
);
```

`node_id` 为 eFuse Wi-Fi MAC 派生的 12 位大写十六进制（如 `F0F5BD02F35C`），UNIQUE；MQTT 路由身份以 topic 为准，帧内 `node_id` 仅做一致性校验。状态变化留痕表 `node_events`（node_id / event_type / old_status / new_status）。

## 3. 状态机

### 3.1 节点在线状态

```text
创建(默认 offline？见下) → unknown → online ⇄ offline；disabled 为人工终态
```

| 状态 | 触发 |
|---|---|
| `unknown` | 新节点创建时默认（DB 默认值 `offline`，行为上以 unknown 语义处理首 Hello 前） |
| `online` | 收到合法 Hello / StatusReport，写入 `last_seen = now` |
| `offline` | 离线检测器判定（`last_seen` 超过 90s），推 `node_status` 事件 |
| `disabled` | 管理员手动禁用 |

### 3.2 在线/离线转换（v3.4 事实）

- 上行 StatusReport 由 `handler_status.go` 处理：`node.Status = status`、`node.LastSeen = now`；**offline→online 转换时**写 `last_online_time`。
- **离线检测唯一路径 = DB last_seen**（`backend/internal/offlinedetector/offlinedetector.go`）：
  - `Start()` 每 **5 秒** tick 一次；
  - `checkDBLastSeen`：查 `status='online'` 的节点，`now - last_seen > 90s` 则 `markOffline`（置 `offline`、写 `node_events`、WS 广播 `node_status`，reason=`db_last_seen_timeout`）。
  - **Redis 已退役**（方案 v3.4 §4 任务B）：`UpdateHeartbeat()` 保留为 no-op 待多实例分布式心跳接入。旧文档的"Redis TTL 15s"叙述已过时，不再适用。
- 心跳事件计数语义：90s 阈值 ≈ 18 个 5s 心跳周期，节点断电约 90s 后前端看到离线。

### 3.3 配置同步状态（节点层）

```text
unknown → syncing ⇄ in_sync；lag / error 为分支态
```

| sync_state | 触发 |
|---|---|
| `unknown` | 新节点，等待首次同步 |
| `syncing` | ConfigManifest 已发，等 ConfigResult |
| `in_sync` | ConfigResult success / StatusReport 自愈确认（hash+sync_id 双匹配） |
| `lag` | epoch 落后 |
| `error` | ConfigResult fail / NVS 写失败 |

同步状态权威逻辑在 [同步机制.md](同步机制.md)（SyncGate）；StatusReport 只能自愈（syncing→in_sync），不得覆盖同步代际。

## 4. 关键流程

### 4.1 会话建立与 Hello 握手

```text
ESP32                        MQTT / 中心端
 | Wi-Fi 就绪                     |
 |-- connect / subscribe -------->| nodes/{id}/down (QoS0)
 |                                | nodes/{id}/control (QoS1)
 |-- Hello (0x01, nonce) -------->|
 |<-------- HelloAck (0x12, 同 nonce)
 |-- ResourceReport (0x19) ------>|
 |<-------- ConfigManifest (0x04) | 需要配置或配置变更时
 |-- ConfigResult (0x05) -------->| 仅完整应用成功后 success=1
 |-- ResourceReport (0x19) ------>| 成功后刷新运行时能力
 |-- StatusReport (0x02, 每 5 秒)->|
```

- 中心端订阅 `nodes/+/up`（QoS1）；下行发布到 `nodes/{id}/down`（QoS0）与 `nodes/{id}/control`（QoS1）。
- 节点 client_id 即 `node_id`，keepalive 30s；重连指数退避，最多 3 次后重建客户端。
- 严格校验：Hello 缺字段 / 重复字段 / 未知字段 / 协议版本不符 / nonce 为 0 均拒绝；**HelloAck 必须回显同 nonce** 才完成握手，旧会话 ACK 不得确认新会话。
- `parseHello` 将帧内 `node_id` 与路由身份（topic）做一致性校验；`proto_version` 必须等于服务端 `ServerMaxProtocolVersion = "2.6"`（sender.go），协商版本 = min(节点报告, 2.6)。

### 4.2 心跳（StatusReport，5 秒）

节点每 **5 秒**发 StatusReport，中心端 `handler_status.go` 处理：刷新 `last_seen` / `uptime_seconds` / `config_epoch`，可选写 `runtime_perf`→`hardware_info`，offline→online 时记 `last_online_time` 并强制走 SyncGate 补同步，状态变化写事件并推 `node_status`。

### 4.3 主动 Ping

`POST /api/v1/nodes/:id/ping` → 下行 Ping(0x08) → 节点回 Pong(0x09)（回显时间戳）→ `ping_tracker` 计 RTT → 更新 `ping_latency_ms` → WS `ping_result`。

### 4.4 配置下发

触发源：Hello / StatusReport / 服务端启动 / CRUD 配置变更 / ConfigQuery。全量流程见 [同步机制.md](同步机制.md)；节点侧事务化应用顺序：挂起总线 worker → 暂存校验 → 停止旧调度 → 快照 → 应用 DMA → 外设 → 总线 → 调度器 → 日志流 → 提交 → 激活调度器。中心端收到 `ConfigResult success=1` 前不得标记已部署。

## 5. 协议与外部契约

契约以 [../协议/二进制帧协议.md](../协议/二进制帧协议.md) 为准；本节列现行实现要点。

### 5.1 MQTT 会话

| Topic | 方向 | QoS | 用途 |
|---|---:|---:|---|
| `nodes/{node_id}/up` | 节点 → 中心端 | 1（日志流 0） | 全部上行二进制帧 |
| `nodes/{node_id}/down` | 中心端 → 节点 | 0 | 常规下行：配置/采集/OTA/查询 |
| `nodes/{node_id}/control` | 中心端 → 节点 | 1 | 可靠控制入口 |

ACL（backend/config/emqx/acl.conf）：节点仅能 `publish nodes/${clientid}/up`、`subscribe nodes/${clientid}/down`；`ehome-server-v2` 全权；默认 deny。

### 5.2 上行帧（节点 → 中心端）

| 类型 | 名称 | 关键字段 |
|---:|---|---|
| 0x01 | Hello | 1 node_id, 2 firmware_version, 3 model, 4 active_channel_count, 5 epoch, 6 has_active_manifest, 7 last_known_manifest_id(可选), 8 proto_version="2.6", 9 handshake_nonce |
| 0x02 | StatusReport | 1 uptime_sec, 2 status(固定"online"), 3 active_channel_count, 4 epoch, 5 sync_state(0 idle/1 syncing/2 error), 6 manifest_id, 7 channel_health, 8 sync_id, 9 runtime_perf, 10 control_stats |
| 0x03 | DataReport | 1 channel_id, 2 timestamp_us, 3 sequence, 4 raw_data, 5 error_code, 6 request_id, 7 edge_device_id, 8 command_index, 9 command_template_id |
| 0x05 | ConfigResult | manifest_id + sync_id |
| 0x07 | WriteRsp | request_id |
| 0x09 | Pong | 回显时间戳 |
| 0x0B | OtaProg | ota_id, status 0 downloading/1 completed/2 verifying/3 failed |
| 0x0C | ScanRpt | 发现地址列表 |
| 0x0F | QueryRsp | request_id |
| 0x11 | ConfigReport | 当前 manifest/模板/通道数量 |
| 0x16 / 0x17 | ChannelCmdV2Ack / Final | 身份四元组 + event_sequence；Final 为执行终态 |
| 0x19 | ResourceReport | 平台/资源总数/总线/通道/DMA/command_engine(含 boot_id)/manifest_capacity |
| 0x1C | PeriphRsp | request_id, error_code, 返回值, PWM running |
| 0x1D | LogStream | QoS0，仅诊断用 |

### 5.3 下行帧（中心端 → 节点）

| 类型 | 名称 | 关键字段 |
|---:|---|---|
| 0x04 | ConfigManifest | 1 manifest_id、3 templates、4 channels、5 dma、8 sync_id(必填)、10 log_stream、11 gpio、12 pwm |
| 0x06 | WriteCmd(legacy) | request_id, channel_id, data |
| 0x08 | Ping | timestamp |
| 0x0A | OtaCmd | ota_id, URL, checksum, size, version, sequence |
| 0x0D | ScanReq | request, hardware_id, 地址范围, 超时 |
| 0x0E | QueryReq | request_id, query_type |
| 0x10 | ConfigQuery | request_id |
| 0x12 | HelloAck | 1 server_time_ms、2 features、3 handshake_nonce（回显） |
| 0x15 | ChannelCmdV2 | 身份四元组 + deadline_unix_ms + TX/RX 参数 + 可选批步骤 |
| 0x1A | QueryResources | request_id |
| 0x1B | PeriphCmd | 1 request_id, 2 periph_type(1 GPIO/2 PWM), 3 resource_id, 4 action, 5 value, 6 config |

固件容量上限：16 模板 / 8 通道 / 每通道 5 边缘设备 / 每边缘设备 3 命令 / 8 DMA / 12 GPIO / 8 PWM。`bus_type`：1 UART、2 I2C、3 SPI、5 ADC（legacy GPIO=4 不接受）。

### 5.4 WebSocket 事件（backend/internal/events/events.go 常量）

`node_status`、`node_config_synced`、`node_config_changed`、`node_resources_updated`、`ping_result`、`scan_result`、`channel_data`、`node_log`、`periph_result`、`periph_state`。事件名前后端共享常量，CI 校验。

### 6.5 运维约束

- 周期同步请求默认 10min；NVS 只存同步元数据（epoch、manifest_id），重启不恢复活动硬件配置
- OTA 双分区 mark-valid；新镜像须完成 Wi-Fi+MQTT+首个 StatusReport 才确认
- BOOT 键长按 5s 擦除 NVS 并重启（S3 GPIO0 / C6 GPIO9）
- 调试 TCP transport（默认 8088）仅在 `CONFIG_DEBUG_TCP_ENABLED` 时开放，非生产协议入口

## 8. 已知限制与债务

| 限制/债务 | 说明 |
|---|---|
| Redis 退役扩展点 | 离线检测现在只走 DB last_seen；`UpdateHeartbeat` no-op 保留，多实例部署时再接入分布式心跳 |
| 90s 判定粒度 | 心跳 5s 但离线判定 90s（18 周期），断电→离线最长约 90s；如需更快需调整阈值或引入 LWT |
| 协议硬性 2.6 | `parseHello` 严格校验 `ServerMaxProtocolVersion="2.6"`，旧版固件无法混部（需升级）；协议向后兼容仅体现在帧编码规则（可忽略未知字段） |
| 边缘设备离线判定 | 与节点判定分离（`checkEdgeDevicesOffline`，60s 无数据），归属边缘设备文档 |
| 调试 TCP 8088 | 仅调试开关开放，勿当生产入口 |
| 通知联动 | 节点 offline 事件是否产生通知消息由 [通知中心.md](通知中心.md) 的触发源覆盖 |
| 通道扫描 | Modbus 扫描只作用于第一个 UART 通道（固件约束） |
| 状态历史 | `node_events` + `/status-history` 已实现，聚合展示细节随前端迭代 |
