## 1. 为什么单独立文档

审计报告把这两项列为「必须先契约裁决」的高风险项，但报告本身**不能执行**：
改 `hardware_id` 涉及 DB 列 / API / 前端三层，改 `active|online` 涉及跨实体语义统一。
两者都**不是前端单方面能改的**（改一边即造成前后端不一致的线上故障）。
故 Phase 0.4 的产出是**本裁决请求**，而不是代码改动。

**本轮复测修正了审计的一处低估**：`hardware_id` 不是「两处同名异物」而是**三处**
（`EdgeDevice` / `Channel` / `PWMConfig`），见下。

## 2. B1：`hardware_id` 三处同名异物（复测后由 2 处升为 3 处）

### 2.1 事实（逐处给类型 + JSON 名 + 注释 + 实际读法）

| # | 模型 | 定义位置 | JSON 名 | 该字段**实际语义** | 证据 |
|---|---|---|---|---|---|
| 1 | `EdgeDevice` | `backend/internal/models/models.go:90` | `hardware_id` | **从站地址**（Modbus slave / 设备地址） | 注释「v2.2 新增 (从 Channel 移过来)」；`handler_edge_device.go:514-515` 由 DTO 直接写入 |
| 2 | `Channel` | `backend/internal/models/models.go:159` | `hardware_id` | **总线上的硬件地址**（如 I2C 0x76）/ 总线名 | 注释「总线上的硬件地址 (e.g. I2C 0x76)」；`handler_device.go:820-821` 可被用户改写 |
| 3 | `PWMConfig` | `backend/internal/models/models.go:493` | `hardware_id` | **PWM 资源标识**（如 `PWM0`），与 `pin` 联合唯一 | `gorm:"unique index idx_pwm_node_hw"`；`handler_periph.go:132,137,656` 用 `resolveReportedPWMResources(node, hardware_id, pin)` 校验 |

**危害**：同一 JSON 字段名在三个资源上语义不同，调用方极易把
`EdgeDevice.hardware_id`（从站地址）当成 `Channel.hardware_id`（总线名）。
生产事故族已由 `frontend-shared/src/utils/deviceAddress.ts:133` 记录。

### 2.2 为什么不能"前端先改"

前端若把 `Channel.hardware_id` 显示为「总线名」而 API 字段不变，只是**掩盖**而非修复：
后端 `handler_device.go:820` 仍接受用户改写该字段，语义仍会在 DB 里漂移。
反之若前端按新语义传值，后端未同步则写入错误数据。

### 2.3 三个候选方案（择一，需裁决）

| 方案 | 做法 | 优点 | 代价 | 推荐度 |
|---|---|---|---|---|
| **A（推荐，最小可逆）** | **不改字段名**，在 `docs/设计/术语表.md` 与三个 model 的注释里**冻结三处语义**，并要求前端在类型注释中标注所属资源 | 零 DB/API 风险，立刻消除"读错"的可能 | 字段名仍同名，新人仍需查注释 | ★★★ |
| B | 给 `Channel` 加 `bus_name` 新列并双写，旧 `hardware_id` 保留只读至兼容期结束 | 名实相符 | 迁移 + 双写 + 兼容期，跨前后端 | ★★ |
| C | 三处全部改名（`slave_address` / `bus_name` / `pwm_resource_id`） | 彻底 | 破坏性 API 变更 + DB migration + 前端全改；未发布产品仍要动固件契约 | ★ |

> **本轮倾向 A**：项目未发布、也没有第三方消费方，B/C 的收益（可读性）与代价（跨层改契约）
> 不成比例；且 A 可以在**任何时刻**升级为 B/C（先冻结再改名不冲突），是可逆选择。

## 3. B2：`active | online` 双在线值

### 3.1 事实

| 实体 | 字段 | 取值 | 位置 |
|---|---|---|---|
| `Node` | `status` | `online` / `offline` / `unknown` / `disabled` | `docs/设计/节点.md:99-105` |
| `EdgeDevice` | `status` | `active` / `inactive`（`models.go:93` default **active**） | 后端无显式枚举注释 |
| `DeviceConfig` | `status` | `active` / `inactive`（`models.go:226` default **active**） | 注释「active / inactive」 |
| `DataSource` | `status` | `active` / `standby` / `error` / `disabled`（`models.go:289` default **standby**） | 与上面的 `active` **语义又不同**（主备角色） |

前端 `StatusBadge.vue:43-45` 把 `online` 与 `active` **都译成「在线」**：

```js
case 'online': return '在线'
case 'active': return '在线'
```

**危害**：`active` 在三处含义不同（EdgeDevice=启用、DeviceConfig=启用、DataSource=主用），
统一译成「在线」会让「数据源：在线」被读成"连接正常"，而它实际表示"当前是主用来源"。
反过来，真正的"在线"（Node/EdgeDevice 连通性）与"启用"（配置开关）被混为一谈。

### 3.2 候选方案（需裁决）

| 方案 | 做法 | 说明 |
|---|---|---|
| **A（推荐）** | **不改后端取值**，改前端**按实体分译**：`online/offline` → 在线/离线；`active/inactive` → 启用/停用；DataSource 的 `active/standby` → 主用/待命 | 纯前端、零契约风险；修正"一词两义被同一句译法掩盖"。**代价已实测修正：需改 16 处硬编码**（见 §5），故应分两步（先建集中映射 + 新代码强制走，再按页迁移存量） |
| B | 后端统一为 `online/offline`，其他语义另立字段 | 语义最干净，但 `active` 在不同实体本就不同义，合并会**丢信息** |
| C | 保持现状，只在术语表登记 | 不解决用户误读 |

> **本轮倾向 A**，且**可与 A(B1) 一并执行**：两者都是"冻结语义 + 修正译法"，不动契约。
> 注意方案 A 需先确认一处：`EdgeDevice.status` 的 `active` 到底是**连通性**还是**启用态**
> —— 这决定它该译「在线」还是「启用」。**该确认是执行前的前置条件**（见 §4）。

> 故方案 A 成本低」。**实测不成立**：生产代码里「在线」硬编码 **16 处**

> 强制走它，再按页迁移存量 16 处（避免一次性大改引发文案回归）。
