## 1. 通用契约

### 1.1 传输与认证

- 基路径：`/api/v1`（routes.go:84 `v1 := r.Group("/api/v1")`）
- 认证：`JWTAuthWithDB(db)`（routes.go:85）——所有自动化接口**登录即可**，无角色分级（对齐告警引擎单主体模式）。
- Content-Type：`application/json`

### 1.2 统一响应封装（envelope.go）

成功（HTTP 恒 200，envelope.go:22-28 源码核实）：

```json
{ "code": 200, "data": <payload>, "message": "ok" }
```

失败（HTTP = status，envelope.go:66-72）：

```json
{ "code": <http_status int>, "data": null, "message": "<人类可读原因>" }
```

带业务码失败（`ErrorWithCode`，envelope.go:77-84）：

```json
{ "code": <http_status int>, "data": null, "message": "<人类可读原因>", "error_code": "<业务码字符串>" }
```

- `code` **恒为 int（HTTP 状态码）**，成功=200；**无 `error` 字段**；机器可读业务码在独立的 `error_code` 键（omitempty），如 `invalid_automation_rule`。
- `message` 为人读提示（可本地化，非机器契约）；成功固定 `"ok"`（`SuccessMsg` 可自定义）。
- 前端 `client.ts` 拦截器统一解包 `data`；非 2xx 抛 `ApiError`（实际以 client.ts 实现为准，envelope.code 恒为 HTTP 状态而非业务码）。

### 1.3 命名与字段风格

- JSON 字段 snake_case，与 GORM 模型 `json` tag 一致。
- 时间戳 ISO8601（`time.Time` 默认序列化）。
- 主键 `id` 为自增 uint。

## 2. 数据模型（AutomationRule / AutomationEvent）

模型定义见 `backend/internal/models/automation.go`。

### 2.1 AutomationRule（策略规则）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uint | 主键 |
| name | string | 规则名（必填，唯一性未强制） |
| enabled | bool | 启用开关，**应用层默认 true**（见 §6 缺陷修复说明） |
| trigger_type | string | `sensor_threshold` \| `time_window` \| `event` |
| trigger_sensor_name | string | 触发传感器字段（sensor_threshold 必填） |
| trigger_comparator | string | `gt` `gte` `lt` `lte` `eq` `neq` |
| trigger_threshold | float64 | 阈值（sensor_threshold 必填） |
| trigger_duration_sec | int | 持续满足秒数（防抖） |
| trigger_window_start/end | string | `HH:MM` 时间窗（time_window 必填） |
| trigger_window_edge | string | `enter` \| `exit` \| `inside` |
| trigger_edge_device_id | uint | 触发源边缘设备。⚠️ 语义张力：模型注释允许 `0=任意设备上报该字段即触发`（automation.go:111），但接口校验（handler:411）强制 sensor_threshold 必填且非 0。**实际以接口校验为准——当前无法经 API 创建「任意设备触发」规则**，0 语义仅存在于模型层，属有意收紧（防误配全网广播式触发）。 |
| conditions_json | string | 附加条件 JSON 数组（AND 语义） |
| action_type | string | `device_action` \| `notification` |
| action_device_id | uint | 目标边缘设备（device_action 必填） |
| action_id | string | 设备动作 ID（device_action 必填，须存在 Catalog） |
| action_params_json | string | 动作参数 JSON 对象 |
| action_level | string | 通知级别（notification 必填） |
| cooldown_sec | int | 冷却秒数，应用层默认 300 |
| max_daily_exec | int | 每日执行上限（熔断），0=不限 |
| require_confirmed | bool | 高风险动作确认制开关，默认 false |
| created_at / updated_at / deleted_at | — | GORM 软删审计 |

### 2.2 AutomationEvent（触发/执行审计）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uint | 主键 |
| rule_id | uint | 关联规则（index） |
| triggered_at | time | 触发时刻 |
| trigger_value | float64 | 触发时传感器值（`*float64` 指针，可空） |
| result | string | 见 §2.3 |
| command_id | string(36) | 回填 command_executions 主键（执行时），可空 |
| detail | string(512) | 失败/抑制原因 |
| created_at | time | — |

> ⚠️ `command_id` 为 string(36)（与 command_executions 主键同型），**非 uint**。前端 TS 类型应为 `string`。

### 2.3 result 枚举（执行侧决策结果）

模型实际常量（models/automation.go:39-47，已核实）：

```
executed                  已受理 (commandexec.Create 成功落 command_outbox PENDING; 语义=已受理 queued, 非已物理执行)
pending_confirm           高风险待人工确认 (require_confirmed=true; 通知 + §5.2 confirm 端点闭环)
suppressed_cooldown       冷却期抑制
suppressed_daily_limit    达每日执行上限 (熔断)
condition_changed         触发后窗口内条件失效 (evaluator 防抖复核, 非 planner 二次校验)
failed_gate               availability gate 拒绝
failed_dispatch           下发失败 (Create 调用失败)
notification              纯通知动作已发出 (action_type=notification)
expired                   pending_confirm 超时未确认 (24h 清扫置位, models/automation.go:47)
```

> ⚠️ 修正：模型常量中**没有 `failed_condition`**（方案草稿用语），evaluator 的条件复核失败归 `condition_changed`；纯通知动作成功记 `notification`（非 `executed`）。
>
> ✅ **死常量已清零（2026-08-25 闭环）**：`suppressed_cooldown` 由 evaluator 冷却命中落审计（evaluator.go:308-331 recordSuppressed，同窗节流防高频刷量）；`condition_changed` 由 planner 执行前条件复核落审计（planner.go:106-109 F4 checkConditionsStillSatisfied，latestValueFn 注入最新值缓存）。两个 result 值均有真实写入点，事件查询可按此过滤。

执行状态推进（queued→dispatched→succeeded/failed）**不新增枚举**，沿用 `command_executions.status`；策略执行历史 = `automation_events JOIN command_executions`（command_id 关联）。

> ⚠️ **`result=executed` 语义=已受理（queued），非已物理执行**（2026-08-25 对账修订，subagent M3 实证）：`commandexec.Create` 同步边界只到 `command_outbox` 落 PENDING，真正 MQTT 下发在 dispatcher 异步执行。若 dispatcher 后续失败，只更新 `command_executions.status=failed`，`automation_events.result` 仍是 `executed`。前端要看真实物理执行结果须 JOIN `command_executions.status`，不得仅凭 `automation_events.result=executed` 判定「已执行成功」。


**列表查询参数**（listAutomationRules，handler_automation.go:101）：

**创建请求体**（createAutomationRuleRequest，handler_automation.go:35）：

```json
{
  "name": "夜间关闭充电 MOS",
  "enabled": true,
  "trigger_type": "sensor_threshold",
  "trigger_sensor_name": "pv1_power",
  "trigger_comparator": "lt",
  "trigger_threshold": 10,
  "trigger_duration_sec": 600,
  "trigger_edge_device_id": 5,
  "conditions_json": "[{\"sensor\":\"soc\",\"comparator\":\"lt\",\"threshold\":95}]",
  "action_type": "device_action",
  "action_device_id": 3,
  "action_id": "set_mos_policy",
  "action_params_json": "{\"charge_mos\":0,\"discharge_mos\":1}",
  "cooldown_sec": 3600,
  "max_daily_exec": 1,
  "require_confirmed": true
}
```

`enabled` / `trigger_threshold` / `trigger_edge_device_id` / `action_device_id` / `cooldown_sec` / `require_confirmed` 共 6 个为指针字段（createAutomationRuleRequest:37-55）——**区分「未传」与「显式零值」**（如 `require_confirmed:false` 与未传的语义不同，`trigger_threshold:0` 与未传不同）。`enabled` 未传时应用层置 true；`cooldown_sec` 未传置 300。

**更新**：`updateAutomationRuleRequest` 全字段指针（部分更新）。合并候选值后走与创建一致的 fail-closed 校验（handler_automation.go:244）。

**启停 PATCH**（patchAutomationRuleEnabled:345）请求体 `{ "enabled": true }`，响应 `{ "id": <id>, "enabled": <bool> }`。

**写路径副作用**：创建/更新/删除/启停成功后均调用 `evaluator.Invalidate()` 失效规则缓存，下一次数据到达即按新规则求值。

### 3.2 事件查询

```
GET /api/v1/automation-events    全局触发历史
```

查询参数（listAutomationEvents:375）：`rule_id`、`result`。返回 `AutomationEvent[]`（`id DESC`，**硬上限 500 条**）。⚠️ 无分页游标。

### 3.3 创建/更新校验（fail-closed）

`validateAutomationRuleFields`（handler_automation.go:396）：

- `name` 非空
- `trigger_type` / `action_type` 在合法枚举集内
- `sensor_threshold`：`trigger_edge_device_id` / `trigger_sensor_name` / `trigger_comparator`（合法比较符）/ `trigger_threshold` 全必填
- `time_window`：`trigger_window_start` / `trigger_window_end` / `trigger_window_edge` 全必填且 edge 合法
- `event`：仅占位，无额外约束
- `device_action`：`action_device_id` / `action_id` 必填
- `notification`：`action_level` 必填

非法时 `400 + ErrorWithCode("invalid_automation_rule", msg)`。

> ⚠️ **当前校验未含**方案 §4.1 草稿中的两项：`action_id` 调 Catalog 验证存在性、`action_params_json` 走 `deviceaction.CanonicalizeParams`。见 §5 待补齐。

## 4. WS 事件（实时推送）

策略触发并落库 `automation_events` 后，planner 经 `Hub.BroadcastEvent`（websocket.go:223）广播。WS 帧由 `Event{Type, Payload}` 包装（websocket.go:232）：

```json
{
  "type": "automation_event",
  "payload": {
    "rule_id": 12,
    "rule_name": "夜间关闭充电 MOS",
    "event_id": 87,
    "result": "executed",
    "value": 3.5,
    "command_id": 1042
  }
}
```

payload 字段（planner.go:167-174 实际构造，**已核实**）：

| 字段 | 说明 |
| --- | --- |
| rule_id / rule_name | 触发规则 |
| event_id | 落库的 automation_events 主键 |
| result | §2.3 决策结果枚举 |
| value | 触发时传感器值（trigger_value，可空） |
| command_id | 回填的 command_executions 主键（**string(36)**；未下发时为空字符串 `""`，非 0） |

> ⚠️ 事件名 `automation_event` 是 planner.go:167 直接广播的**字符串字面量**，`events.go` 中**并无** `EventAutomationEvent` 注册常量（subagent 评审 G4 实证）。方案 §4.2 草稿原拟名 `automation_triggered`，实现更名为 `automation_event`。前端订阅以实际字面量 `"automation_event"` 为准。

策略执行产生的 `device_operation_update` 沿用现有事件（执行状态推进），前端历史页零新增订阅。

> **pending_confirm 的可感知路径**：require_confirmed=true 触发时，除 `automation_event`（result=pending_confirm）外，**同时**落 `notifications` 表（planner.notifyConfirmation:179），前端通知中心轮询/订阅既有通知事件即可感知「待确认建议」。当前确认分流为纯通知、无 token——确认执行闭环见 §5.2。

## 5. 待补齐设计（与裁决/方案的 gap）

以下五项是**裁决/方案已确立但脚手架未实现**的接口面（§5.1-§5.5）。文档如实标注，避免「方案写了=已实现」的认知错位。其中 §5.1/§5.2/§5.3 为接口面 gap，§5.4 为有意不做记录，§5.5 为非接口面但影响接口语义。

### 5.1 [待补齐] 手动触发端点

方案要求支持「立即执行一次（旁路防抖/冷却，用于调试）」。

```
POST /api/v1/automation-rules/:id/trigger
```

- 语义：旁路三态机与冷却/熔断，直接进 Planner 二次校验 + gate + Create。
- 仍受 `require_confirmed` 约束（高风险动作手动触发也走确认制）。
- 响应：202 + `{ command_id, result }` 或 `pending_confirm`。
- **动机**：调试期验证动作链路，不依赖真实传感器条件满足。

### 5.2 [已实现 v0.2 落地] 高风险确认制执行端点

裁决 4 已闭环。planner 的确认分流（planner.go handleTrigger `require_confirmed` 分支）落 `pending_confirm` 事件 + 通知（`notifyConfirmation` 通知载荷含 `event_id`），并提供独立 confirm 端点即时下发。

```
POST /api/v1/automation-events/:id/confirm
```

**真实契约（与下方初稿的差异已修正）**：

- **无请求 body**。confirmation token **即铸即销、不跨请求存储**——planner.ConfirmEvent（planner.go:268）在 confirm 当下先调 `commandexec.IssueConfirmation` 铸 token、随即 `commandexec.Create` 携 token 消费（planner.go:304-323），全程单事务边界内。前端**不传 token**，仅传路径参数 `:id`。
- **前置**：操作者须先 `POST /auth/manual-confirmation` 核密码刷 `LastLoginAt`（10min 近认证窗），IssueConfirmation 内核强制（confirmation.go:104，要求 `SystemAdminSubjectKey`）。操作者身份取自 JWT `subject_id`，sourceIP 取自请求。
- **幂等防重（双闸）**：①确定性幂等键 `automation:confirm:<ruleID>:<eventID>` 与事件 1:1，重复 confirm 命中 `command_executions` 唯一索引走 replay 只读；②条件 UPDATE `WHERE result='pending_confirm'` 作应用层第一道闸，并发 confirm/已被清扫置 expired 时 `RowsAffected=0` 不覆写。
- **超时**：`pendingConfirmTTL = 24h`（planner.go 常量），非初稿的 1h。独立清扫 goroutine `StartCleanup`（挂 cmd/server/main.go cleanup ctx，`automationCleanupInterval=5min`）将超窗 `pending_confirm` 置 `expired`。ConfirmEvent 内另有双保险：落库时刻 `triggered_at` 已超窗即按超时拒绝（planner.go:283-285），不等清扫跑到。
- **TOCTOU**：现读 rule 最新动作，rule 被删（`ErrConfirmRuleMissing`）/ 改 `action_type`（`ErrConfirmActionChanged`）/ params 非法（`ErrConfirmInvalidParams`）fail-closed 报错；不存 params 快照。
- **错误哨兵**（均可 `errors.Is` 判定）：`ErrConfirmEventNotFound` / `ErrConfirmEventExpired`（expired 或落库超窗）/ `ErrConfirmNotPending`（非 pending_confirm 状态）/ `ErrConfirmRuleMissing` / `ErrConfirmActionChanged` / `ErrConfirmInvalidParams`。
- **Create 失败翻转**：`isGateError(err)` 为 true 置 `failed_gate`（availability gate fail-closed），否则置 `failed_dispatch`（planner.go:339-341），不留 pending 悬置。
- **成功**：事件置 `result=executed` + 回填 `command_id`，`command_outbox` 落 PENDING 走既有 dispatcher。

**实现落点**：`backend/internal/automation/planner.go`（ConfirmEvent/StartCleanup/notifyConfirmation）+ `api/handler_automation.go`（confirmAutomationEvent handler，无 body 绑定）+ `api/routes.go`（路由注册）+ `cmd/server/main.go`（planner 提取 + StartCleanup goroutine 注入）。行为测试 `automation/planner_test.go`（5 用例：失败路径翻转 / 非 pending 状态闸 / 超时清扫 / 错误分支 / require_confirmed 分流）。

**前端两步契约**（`frontend-shared/src/api/automation.ts` `confirmEvent`，无 body）：
1. `POST /auth/manual-confirmation` 核密码刷 `LastLoginAt`（10min 窗）。
2. `POST /automation-events/:id/confirm`（无 body）即时下发。

> ✅ **伴生 gap 已闭环**（原 subagent 评审 G3/B4）：超时清扫 goroutine `StartCleanup` + `expired` 枚举（models/automation.go:47 `AutomationResultExpired`）均已实现。`pending_confirm` 事件不再永久悬挂——可被 confirm 闭环、超时置 expired、或被 Create 失败翻转。

**架构约束（测试实证）**：`commandexec` 的 `CurrentEngineAllows`（deviceaction/definition.go:408-430）只放行 `single+read+low` 或 `set/reset+bounded_sequence` 动作——medium/high single-read 动作在 Create 时被 `command_engine_gate` 拦（这正是设计目标：高风险动作须 bounded_sequence）。confirm 端点的真下发端到端验证属 commandexec bounded 链既有职责；automation 层单测验证幂等键防重 + 状态闸 + 失败翻转 + 清扫逻辑。

### 5.3 [已实现] 创建校验补强（对齐方案 §4.1）

- 注入方式：`automationCatalogQuerier` 接口注入 handler 层，避免 api→commandexec 编译期反向依赖。

### 5.5 [已实现] time_window 触发器求值 / [仍禁配] event 触发器

## 6. 模型层缺陷修复记录（影响接口语义）

`Enabled bool` 的 GORM tag 曾带 `default:true`：**GORM 会把 bool 零值 false 在 INSERT 时序列化为 SQLite 字面量 `true`**（2026-08-23 探针实锤，`alert.go` 同缺陷）——禁用规则被静默存为启用。

**修复**：`automation.go` 模型去掉 `default:true` tag，默认 true 由 handler Create 显式赋值（fail-closed，handler_automation.go:180-184）。接口语义：`enabled` 未传 → true；显式传 `false` → 正确落库为禁用。

> `alert.go` 同缺陷未在本次范围修复，留待告警引擎专项（线上告警创建 disabled 规则会失效）。
