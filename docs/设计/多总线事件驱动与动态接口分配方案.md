# 多总线事件驱动与动态接口分配方案

## 1. 文档状态

本文档是 UART/SPI/I2C 性能与资源调度改进方案。当前 worktree 已完成 P0～P5
实现（配置契约、动态资源规划/lease、UART event queue、统一自动边界、异步
payload/critical 队列、scheduler 背压和 DMA 语义统一）；P6～P7 仍按阶段门禁
推进，主要是实机长稳、故障注入和灰度发布。

基线分支为 `codex/edge-control-worktree`，方案开发分支为
`codex/multi-bus-event-driven-plan`。分阶段开发任务见
`docs/设计/多总线事件驱动开发实施计划.md`，完整验证矩阵见
`docs/验证/多总线事件驱动测试验证方案.md`。

目标场景是：设备的逻辑 Channel 不绑定固定的 UART0、UART1、SPI 或 I2C 编号；系统在配置应用时，根据硬件能力、引脚、DMA、占用状态和业务要求动态分配物理接口。

UART0 与 UART1 必须使用相同的处理流程。某次测试中 UART0 接入高速数据、UART1 接入 SN-3001，只是运行时绑定结果，不是架构角色。

## 2. 背景与现状

### 2.1 已知硬件事实

- ESP32-C6 有两个 HP UART：UART0 和 UART1。
- UART0/UART1 均具备配置到高波特率的能力，芯片能力上限由硬件 profile 声明为 5,000,000 baud。
- UART0/UART1 的实际选择应由运行时资源分配决定，不应由设备类型或业务逻辑决定。
- C6 的 UART DMA/UHCI 资源有限，不能假设 UART0 和 UART1 同时拥有独立 UART DMA 资源。
- C6 I2C 硬件 profile 当前不声明 DMA 能力。
- SPI DMA 开关当前由 SPI driver 的 `SPI_DMA_CH_AUTO` 与 `SPI_DMA_DISABLED` 控制。

### 2.2 当前固件结构

当前固件已经具有按总线划分的命令队列：

- UART0 command queue；
- UART1 command queue；
- SPI command queue；
- I2C command queue。

UART RX 已改为共享 event-driven `rx_task`，每通道使用 1KB 线性化缓存和统一自动边界；
连续输入按 512B block 提交，pending command 优先按 `read_size` 完成，尾部再由约
10ms idle 收尾。

相关代码：

- [bus_worker.c](../../esp32-collector/components/bus_worker/bus_worker.c)
- [bus_worker.h](../../esp32-collector/components/bus_worker/include/bus_worker.h)
- [bus_dma.c](../../esp32-collector/components/bus_dma/bus_dma.c)
- [app_state.c](../../esp32-collector/main/app_state.c)

### 2.3 现有瓶颈

1. 1 Mbps、8N1 下有效字节速率约为 100,000 byte/s，512 字节约 5.12 ms 即可填满。
2. 5 ms 轮询没有足够调度余量，任务被 MQTT、日志或其他业务打断后可能溢出。
3. 连续流不会产生 10 ms idle，导致线性缓存最终溢出。
4. 缓存溢出时当前逻辑会丢弃已有数据并重置缓存，缺少字节级丢包统计。
5. DataReport 编码缓冲也是 512 字节，无法安全承载完整 512 字节原始负载。
6. RX 处理路径最终会调用 MQTT 发布，总线接收和网络发送没有充分解耦。
7. 后端 DataEventBus 与 WebSocket 具有限队列，更适合状态数据，不适合无限速率的无损原始字节流。

## 3. 需求定义

### 3.1 功能需求

#### R1：动态接口分配

逻辑 Channel 只声明所需总线类型和参数，不绑定固定物理控制器编号。

UART Channel 可以在配置应用时动态获得 UART0 或 UART1；SPI/I2C Channel 也按相同原则选择可用的物理 controller。

#### R2：UART0/UART1 流程完全一致

UART0 和 UART1 必须：

- 使用同一套命令 worker 逻辑；
- 使用同一套 RX event worker 逻辑；
- 使用相同的透明接收与自动边界状态机；
- 使用相同的 DMA 开关语义；
- 使用相同的错误、溢出和高水位统计；
- 不根据 UART 编号决定设备类型、波特率档位或优先级。

#### R3：UART 事件驱动接收

UART RX 从固定周期轮询改为 UART driver event 驱动。事件包括数据到达、FIFO 溢出、driver ring 满、帧错误、校验错误等。

RX 任务只负责从 driver ring 搬运数据、更新状态和投递描述符，不执行 MQTT 发布、数据库操作或复杂协议解析。

#### R4：独立软件队列

每个物理 controller 必须具有独立的命令处理上下文。至少包括：

- controller command queue；
- UART driver event queue（仅 UART）；
- UART RX block/ring queue（仅 UART）；
- 事务完成后的上报队列描述符。

一个 UART 的高负载不能阻塞另一个 UART、SPI 或 I2C。

#### R5：DMA 保持可配置

现有 DMA 开关保留，但必须统一配置语义：

- DMA 关闭时仍可使用事件驱动和软件 ring；
- DMA 开启时由资源规划器申请可用 DMA 资源；
- 硬件不支持 DMA 时，配置应被拒绝或明确降级，不得静默改变协议语义；
- DMA 不能与 UART0/UART1 编号绑定。

#### R6：保持请求—响应兼容

SN-3001、Modbus、GB3024、嘉佰达和 ChannelCmdV2 等请求—响应业务必须保持原有语义：

- 响应不能因固定分片而被错误判定为完整；
- `read_size`、协议长度、CRC 或 idle timeout 仍可参与判帧；
- pending request 只能由完整响应或明确超时完成。

#### R7：统一透明接收与自动边界

对外只有一种 UART 数据处理模式：统一透明接收。不存在需要用户或设备类型预先选择的模式字段。所有 UART Channel 使用同一条透明接收链路，由运行时可观察到的状态自动决定数据提交边界：

- 存在 pending command 且有 `read_size` 时，达到期望长度即可完成响应；
- 有协议长度、结束符或 CRC 时，优先使用协议边界；
- 存在 pending command 但没有明确长度时，使用 idle timer 作为 fallback；
- 没有 pending command 且数据持续到达时，按最大 chunk 大小或最大等待时间提交数据；
- pending response 完成后仍到达的剩余字节，作为后续透明数据继续进入同一接收链路；
- 每个提交单元具备 channel、sequence、length、timestamp 和状态标志；
- 出现溢出或缺口时可被后端识别。

边界判断依据是 pending command、协议元数据、实际输入和缓冲状态，而不是预先要求用户知道设备属于哪一种模式。

#### R8：控制消息优先

ChannelCmdV2 ACK/Final、ConfigResult、WriteResponse、Hello、Status 和 OTA 状态不得被高速 UART 流挤占。

高速数据流必须使用独立的普通上报队列或保留容量。

#### R9：配置变更可回滚

配置应用、失败回滚和安全状态处理必须覆盖：

- 动态 controller lease；
- GPIO route；
- DMA binding；
- driver event queue；
- RX block pool；
- pending response；
- command worker 和 RX worker 生命周期。

#### R10：可观测性

系统至少记录以下统计：

- 接收总字节数；
- 上报总字节数；
- UART FIFO 溢出；
- driver ring 溢出；
- 软件 block pool 耗尽；
- 上报队列丢弃；
- sequence gap；
- 当前/最大队列深度；
- SPI/I2C 事务成功、失败和超时；
- DMA 请求、分配和冲突；
- 当前和最小 free heap；
- worker 栈余量；
- 看门狗和重启原因。

### 3.2 非目标

- 不要求所有网络中断都无限时长无损保存；有限 RAM 无法提供该保证。
- 不把前端终端页面作为 1 Mbps 原始流的可靠存储端。
- 不强制 SPI/I2C 改成类似 UART 的常驻 RX 事件任务。
- 不把 UART0 固定为高速接口，也不把 UART1 固定为 SN-3001 接口。

## 4. 总体架构

```text
逻辑 Channel
      │
      ▼
Bus Resource Planner
      │
      ├── UART controller lease
      ├── SPI controller/bus lease
      └── I2C controller/bus lease
      │
      ▼
Controller Runtime
      ├── control command queue
      ├── sample command queue
      ├── event queue（UART）
      ├── RX/transaction state
      └── statistics
      │
      ▼
分级上报队列
      ├── critical/control report queue
      └── telemetry/raw-data report queue
      │
      ▼
MQTT / TCP transport
```

上层只通过 `channel_id` 查询 runtime lease，不直接判断 `UART_NUM_0` 或 `UART_NUM_1`。

建议将当前固定变量逐步抽象为数组化 runtime：

```text
uart_runtime[HW_UART_COUNT]
spi_runtime[SPI_CONTROLLER_COUNT]
i2c_runtime[I2C_CONTROLLER_COUNT]
```

每个 runtime 使用同一个 worker 入口函数，实例参数只包含 controller index 和当前 lease。

## 5. 动态资源分配

### 5.1 Channel 与物理 controller 解耦

逻辑 Channel 的配置包括：

- bus type；
- TX/RX 或 SDA/SCL/MOSI/MISO/SCLK/CS 引脚；
- baud/frequency；
- 数据位、校验、停止位和流控；
- DMA 请求；
- enabled 状态；
- 可选 preferred controller。

物理 controller 由资源分配器在 manifest 应用时选择。

### 5.2 UART 分配规则

建议按以下优先级选择：

1. 复用当前 Channel 已使用且仍兼容的 controller；
2. 满足显式 preferred controller；
3. 满足 GPIO、console、boot 和硬件 capability；
4. 满足 DMA 请求；
5. 选择空闲且资源冲突最少的 controller；
6. 保持分配结果稳定，避免无关配置变化导致 UART0/UART1 对调。

默认 TX/RX 引脚对只作为 profile 建议或兼容旧配置的匹配条件，不作为 UART 身份的强绑定。

### 5.3 UART lease

运行时需要保存类似以下信息：

```c
typedef struct {
    bool active;
    uint32_t channel_id;
    uart_port_t controller;
    int tx_pin;
    int rx_pin;
    bool dma_requested;
    bool dma_allocated;
    uint32_t generation;
} uart_lease_t;
```

`channel_id → uart_lease → uart_runtime` 是唯一的运行时路由关系。

### 5.4 UART Channel 共享规则

一条逻辑 UART Channel 应独占一个物理 UART controller；一条 Channel 下可以挂多个 EdgeDevice。

不建议让两个独立 Channel 同时共享一个 UART controller，因为 UART RX 字节没有 Channel 标识，无法可靠判断响应属于哪一个 Channel。

如果多个设备共享一条 RS485/UART 总线，应建模为：

```text
一个 UART Channel
  ├── EdgeDevice A
  ├── EdgeDevice B
  └── EdgeDevice C
```

### 5.5 DMA 分配规则

DMA 请求和 controller 选择应联合规划：

```text
Channel request DMA
      ↓
选择 UART/SPI/I2C controller
      ↓
申请兼容 DMA resource
      ↓
验证所有 Channel 后一次性提交
```

如果某 Channel 将 DMA 视为强制要求而资源不足，应拒绝整个 manifest；不得让两个 UART 都显示已获得同一 DMA，也不得无提示地降级。

ESP32-C6 上 UART0/UART1 可平等申请有限 UART DMA 资源，但两者同时要求独占 DMA 时应按硬件能力拒绝或由明确的配置策略解决。

## 6. UART 事件驱动方案

### 6.1 Driver event queue

每个物理 UART 安装 driver 时获得独立事件队列：

```text
UART driver
  ├── RX ring
  └── event queue
```

当前实现已为每个 UART runtime 保存 driver event queue，并由统一 RX task 通过 QueueSet
等待；DMA 开关只改变 driver ring 大小，不改变事件与上报流程。

RX task 阻塞等待事件，不再扫描所有 Channel。

### 6.2 RX task职责

RX task 只做：

1. 等待 UART_DATA 或错误事件；
2. 从 driver ring 搬运数据；
3. 分配/填写 RX block descriptor；
4. 写入软件 ring 或 block queue；
5. 更新 sequence、时间戳和统计；
6. 通知统一透明接收与自动边界状态机。

ChannelCmdV2 的多步请求也遵守单一 UART reader 原则：RX event task 将批处理响应写入
有界 hand-off，批处理命令任务只等待 notification 并读取副本，避免命令任务与透明
接收任务竞争同一个 driver ring。

RX task 不做：

- MQTT publish；
- TCP send；
- JSON/hex 编码；
- 数据库写入；
- 复杂协议解析；
- 长时间等待网络或其他锁。

### 6.3 统一透明接收与自动边界

所有 UART 只有一套“统一透明接收”状态机，不提供需要用户选择的模式字段。内部根据 pending command 和输入状态选择边界，不构成对外的模式切换。状态机按照以下优先级确定提交边界：

1. pending command 的明确 `read_size`；
2. 协议长度、结束符或 CRC；
3. pending command 的 idle timer；
4. 无 pending command 时的最大 chunk 大小或最大等待时间；
5. 达到 timeout 后提交错误结果或标记不完整数据。

当同一 UART 在响应完成后继续收到数据，剩余数据不丢弃，而是回到同一透明接收队列，按 chunk 大小或时间边界继续提交。

每个提交单元至少携带：

- channel_id；
- sequence；
- timestamp；
- payload length；
- overflow/discontinuity 标志；
- 可选 CRC。

这样既能处理 SN-3001 之类的请求—响应，也能处理没有明确帧间空闲的连续输入，且不要求配置阶段预先知道设备行为。

### 6.5 UART 错误事件

发生 FIFO overflow、driver ring full 或软件 block pool 耗尽时：

- 累加错误计数；
- 标记当前 chunk 不完整；
- 记录丢弃字节数；
- 必要时重置当前分帧状态；
- 通过后续上报通知后端存在 gap；
- 不静默清空数据。

## 7. SPI 方案

### 7.1 保留事务型 worker

SPI 没有被动 RX，不需要常驻 RX task。推荐保持：

```text
SPI command queue
      ↓
SPI worker
      ↓
spi_device_transmit
      ↓
异步上报队列
```

SPI worker 只阻塞当前 SPI controller，不阻塞 UART 或 I2C。

### 7.2 DMA 开关

保留当前 DMA 语义：

- 开启：`SPI_DMA_CH_AUTO`；
- 关闭：`SPI_DMA_DISABLED`。

DMA 属性应属于物理 SPI bus，而不是单个 CS 设备。共享相同 MOSI/MISO/SCLK 的多个设备必须统一 DMA 状态。

### 7.3 SPI 异步化边界

首版不建议把 `spi_device_transmit()` 改为 driver transaction callback。当前 SPI worker 已经是独立事务队列，改成底层异步会增加：

- transaction buffer 生命周期管理；
- 取消和配置切换复杂度；
- DMA buffer 所有权问题；
- 回调与上报队列的关联复杂度。

只有在未来 SPI 产生大块、高频数据并证明同步 worker 成为瓶颈时，再评估 `queue_trans/get_trans_result`。

## 8. I2C 方案

### 8.1 保留事务型 worker

I2C 同样是主机发起事务，不增加常驻 RX task：

```text
I2C command queue
      ↓
I2C worker
      ↓
transmit / transmit_receive
      ↓
异步上报队列
```

I2C 设备无应答造成的 50 ms 超时只应阻塞 I2C worker。

### 8.2 DMA 开关不能改变 I2C 协议

当前代码根据 `dma_enabled` 在 combined `transmit_receive` 和 split `transmit` + `receive` 之间切换。这可能改变 repeated START/STOP 行为，不应继续作为 DMA 语义。

推荐：

- write+read 始终使用协议要求的 `transmit_receive`；
- DMA 开关只表示底层传输资源；
- C6 不支持 I2C DMA 时，`dma_enabled=true` 应被能力校验拒绝或显式降级；
- 不允许 DMA 开关改变设备所看到的 I2C wire sequence。

### 8.3 I2C 共享 bus

多个 I2C 地址可以共享 SDA/SCL，物理 I2C bus 只创建一次，设备 handle 分别加入。

初始化顺序必须是：

1. 先按 SDA/SCL 查找已存在 bus；
2. 已存在则复用；
3. 不存在时才检查硬件 I2C controller 数量；
4. 创建 bus 并添加 device。

## 9. 命令队列与上报队列

### 9.1 命令队列

每个物理 controller 至少具有独立命令上下文：

```text
UART runtime 0/1：control queue + sample queue
SPI runtime：control queue + sample queue
I2C runtime：control queue + sample queue
```

如果首版不拆 control/sample 两条队列，也必须为控制命令预留容量，不能由 scheduler 把普通采样填满全部槽位。

不建议在队列中复制大尺寸 `bus_cmd_t`；后续可改为固定 payload pool + 小描述符队列。

### 9.2 上报队列

建议分为：

- critical/control report queue：控制响应、配置结果和命令相关 DataReport；
- telemetry/raw-data report queue：普通采集和透明原始数据。

消息发布任务按优先级发送，但同一 Channel 的 sequence 必须保持顺序。

MQTT 断开期间不能无限缓存。必须选择：

- 丢弃并计数；
- 上游硬件流控；
- 本地持久化；
- 让业务停止发送。

## 10. Scheduler 调整

当前 scheduler 使用所有总线队列中最小剩余空间作为全局压力，导致 UART0 队列满时可能连 SPI/I2C/UART1 采样也被跳过。

应改为按目标 controller 计算压力：

```text
UART Channel → 只看其 UART runtime queue
SPI Channel  → 只看其 SPI runtime queue
I2C Channel  → 只看其 I2C runtime queue
```

需要分别统计：

- 当前深度；
- 最大深度；
- 普通采样被跳过次数；
- 控制命令入队失败次数；
- 事务超时次数。

## 11. 配置格式与兼容性

当前 DMA 配置存在两套语义来源：

- backend Channel field 8 的 `dma_enabled`；
- UART `bus_config[6]` 的 flags bit。

相关代码：

- [sender.go](../../backend/internal/nodemgr/sender.go)
- [config_mgr.c](../../esp32-collector/components/config_mgr/config_mgr.c)
- [bus_dma.h](../../esp32-collector/components/bus_dma/include/bus_dma.h)

建议兼容规则：

1. 新 manifest 明确提供 field 8 时，以 field 8 为准；
2. 老 manifest 没有 field 8 时，才读取旧 bus_config flags；
3. 两者冲突时使用 field 8，并记录告警；
4. 前端不再把 data bits、flow control 和 DMA flags 混入同一未版本化字节；
5. backend 统一生成 wire bus_config，前端只提交结构化参数；
6. 旧配置仍能被解析，不因新增字段而改变统一透明接收流程。

DMA 开关建议含义明确为：

- `false`：明确不使用 DMA；
- `true`：请求并要求分配 DMA，资源不足时拒绝配置。

如果以后需要“优先使用 DMA、不可用时允许降级”，应新增显式的 `preferred/required/off` 模式，而不是复用 bool。

## 12. 配置事务与生命周期

事件驱动任务阻塞在 event queue 上，不能只依靠共享布尔变量检查 suspend。

推荐使用 lifecycle control queue 或 QueueSet：

```text
driver event queue ─┐
                    ├─ QueueSet → controller task
lifecycle queue ────┘
```

配置切换流程：

1. 计算新的资源分配计划；
2. 验证 UART/SPI/I2C、GPIO、DMA 和内存约束；
3. 停止 scheduler；
4. 通知所有 controller task suspend；
5. 等待任务确认不再访问旧 driver/context；
6. 处理或取消 pending response；
7. 清理 RX block、事件队列和旧 lease；
8. 应用 DMA、GPIO 和 bus controller；
9. 创建新的 driver/event queue/runtime；
10. 恢复 scheduler 和 controller task；
11. 提交 manifest；
12. 上报实际 channel-to-controller 映射。

失败时必须完整回滚，不能只恢复数据库中的 manifest。

## 13. 内存预算

以当前实机最低 free heap 约 167 KB 为参考，首版建议将新增内存控制在约 24～40 KB：

| 项目 | 建议预算 |
|---|---:|
| 高速 UART driver RX ring | 8 KB |
| 低速 UART driver RX ring | 1～2 KB |
| 共享 RX block pool | 16 KB |
| event/descriptor queue | 1～2 KB |
| 发布任务栈 | 3～4 KB |
| RX task 增量 | 0～4 KB |
| 合计 | 约 29～36 KB |

不应为所有最大 Channel 槽位静态分配大 ring。应按启用的高速 Channel 动态分配，并设置全局预算。

建议初始运行门禁：

- current free heap 不低于 120 KB；
- minimum free heap 不低于 100 KB；
- 所有 block pool 和 report queue 有固定上限；
- MQTT outbox 不允许无限增长。

## 14. 对现有功能的影响

| 功能 | 风险 | 保护措施 |
|---|---:|---|
| UART0/UART1 任意动态绑定 | 中 | lease、稳定分配、配置事务回滚 |
| SN-3001 | 中 | `read_size`/CRC/idle 自动边界判定 |
| UART0 现有协议设备 | 中 | 旧配置默认 response |
| UART 连续 1 Mbps | 正向 | event + ring + 自动 chunk 边界 |
| ChannelCmdV2 | 中高 | control queue 和 critical report queue |
| scheduled sample | 中 | 按目标 controller 独立背压 |
| SPI | 低 | 保留事务 worker，异步上报 |
| I2C | 中 | 修正 DMA 不改变 repeated START |
| 配置同步 | 中高 | lease、driver、queue 一起回滚 |
| MQTT | 中高 | 发布任务与总线解耦 |
| 后端 | 低到高 | 仅事件化低；全量流传输高 |
| 前端 | 低到高 | 不默认展示完整高速流 |

## 15. 实施阶段建议

### 阶段 A：统一资源模型

- 引入 Channel-to-controller lease；
- 去除上层对 UART0/UART1 的业务判断；
- 允许 UART controller 动态分配；
- 统一 DMA capability 和配置来源；
- ResourceReport 上报实际绑定。

### 阶段 B：行为等价的 UART 事件化

- 每个物理 UART 建立 driver event queue；
- 每个物理 UART 建立同构 RX task；
- 保留现有 pending/idle 语义并纳入统一自动边界状态机；
- 不改变 DataReport wire format；
- 完成所有旧协议回归。

### 阶段 C：总线上报异步化

- 总线 worker 不直接调用 MQTT；
- 新增 critical/telemetry report queue；
- 控制消息保留容量；
- 增加队列和溢出统计。

### 阶段 D：自动边界与连续输入

- 不增加需要人工选择的接收模式配置；
- 根据 pending command、协议元数据和输入状态自动选择边界；
- 无 pending command 时按固定 chunk 或最大等待时间分片；
- 启用 sequence 和 discontinuity 标志；
- 对后端和前端增加流量限制、采样或专用原始数据接口。

### 阶段 E：调度与多控制器优化

- scheduler 使用 per-controller 背压；
- control/sample queue 分离；
- SPI/I2C controller 动态分配；
- 完成多总线并行和配置切换压力测试。

## 16. 验收标准

### 16.1 动态分配

- 同一 Channel 可在不同 manifest 中分配到 UART0 或 UART1；
- 上层命令、采样和 RX 处理流程不变；
- ResourceReport 与实际 controller lease 一致；
- 无关配置变化不会导致不必要的接口切换。

### 16.2 UART

- UART0 绑定连续高速输入、UART1 绑定 SN-3001 时通过；
- UART1 绑定连续高速输入、UART0 绑定 SN-3001 时同样通过；
- 两个 UART 都分别验证 DMA 开和关；
- pending response 不出现半帧误完成；
- 无 pending command 的连续输入可检测 sequence gap 和 overflow；

### 16.3 SPI/I2C

- SPI DMA 开关切换不改变业务数据；
- SPI 多 CS 设备共享 bus 时事务串行且不互相破坏；
- I2C write+read 的 repeated START 语义与 DMA 开关无关；
- I2C 无应答只阻塞 I2C worker，不影响 UART；
- C6 I2C DMA 请求被正确拒绝或明确声明不可用。

### 16.4 并行和故障

- 任一 UART 连续高负载时，另一 UART 成功率和延迟保持在门限内；
- UART0 queue 满不会跳过 SPI/I2C 的所有采样；
- MQTT 断开时控制消息仍有独立处理结果；
- 配置切换、失败回滚和重启恢复无旧数据串入；
- 长稳期间 heap、栈、watchdog 和重启原因正常。

## 17. 最终建议

推荐实施“统一动态资源分配 + UART RX 事件驱动 + SPI/I2C 事务 worker 保持不变 + 分级异步上报”的组合方案。

该方案的关键不是把 UART0 做成高速专用口，而是把 UART0/UART1 抽象成两个平等的物理资源实例：

- Channel 动态租用接口；
- runtime 统一处理流程；
- DMA 作为独立资源能力；
- 业务只依赖 Channel，不依赖 UART 编号；
- 当前测试中的 UART0/UART1 角色不进入架构约束。

## 18. 开发实施方案

本节将方案拆成可独立验收的阶段。每一阶段都应先通过门禁，再进入下一阶段；任何阶段失败，都应能够回退到上一阶段可工作的固件和协议行为。

### 18.1 实施原则

1. 先建立动态资源模型，再改 UART 接收机制。
2. 先做行为等价改造，再引入吞吐优化。
3. 先解耦总线与 MQTT，再扩大缓冲和提高分片吞吐。
4. UART0/UART1 使用同一份代码和同一套测试，只改变运行时 lease。
5. SPI/I2C 不为了形式上的“事件驱动”而增加不必要的异步复杂度。
6. 每个阶段都保留可回滚的 manifest、固件和数据库状态。
7. 不把当前实机接线角色写进代码、配置模板或验收脚本。

### 18.2 阶段总览

```text
P0 需求和配置契约冻结
      ↓
P1 动态资源分配与 runtime lease
      ↓
P2 UART 事件驱动（行为等价）
      ↓
P3 统一透明接收边界与异步上报
      ↓
P4 调度器和总线级背压隔离
      ↓
P5 DMA/SPI/I2C 语义统一
      ↓
P6 1 Mbps 并行压力和长稳验证
      ↓
P7 灰度发布与运行监控
```

### 18.3 P0：需求、配置和协议契约冻结

#### 目标

在修改运行时代码前，先统一“逻辑 Channel、物理 controller、DMA 和 UART 接收边界”的定义，避免新旧配置含义继续分裂。

#### 工作内容

- 明确 Channel 不绑定 UART0/UART1，只申请 UART 资源；
- 明确 UART 对外只有统一透明接收流程，不增加可选接收模式字段；
- 明确 pending command、`read_size`、协议长度、CRC、idle timer 和最大 chunk 的边界优先级；
- 明确 DMA `false/true` 的含义；
- 明确 C6 UART DMA 资源冲突时的拒绝策略；
- 明确 C6 I2C DMA 不支持时的配置行为；
- 确定 `channel_id → controller lease` 的 ResourceReport 表达方式；
- 统一 `dma_enabled` 与旧 `bus_config` flags 的兼容规则；
- 规定 sequence、overflow、discontinuity 和 queue high-water 字段。

#### 主要涉及文件

- `docs/设计/多总线事件驱动与动态接口分配方案.md`
- `backend/internal/nodemgr/sender.go`
- `esp32-collector/components/config_mgr/config_mgr.c/.h`
- `esp32-collector/components/bus_dma/include/bus_dma.h`
- ResourceReport/StatusReport 相关编码和解码文件

#### 验收门禁

- 新旧 manifest 示例可以明确解析；
- 老 manifest 无新增字段时行为定义不变；
- 两个 UART 同时请求不可共享的 DMA 资源时，能够在设备重建前拒绝；
- 文档、backend、firmware 对字段含义一致；
- 不存在“页面显示 DMA 已开、固件实际按另一字段解释”的歧义。

#### 回滚点

本阶段只允许文档、协议测试和 host-side parser 变化，不改变实机运行时。

### 18.4 P1：动态资源分配与 runtime lease

#### 目标

将逻辑 Channel 与 UART0/UART1、SPI controller、I2C controller 解耦，建立可查询、可回滚的运行时资源租约。

#### 工作内容

- 增加统一的 bus resource planner；
- 为 UART、SPI、I2C 建立 controller runtime 数组；
- 将当前固定的 `uart0_cmd_queue/uart1_cmd_queue` 路由改为 Channel lease 路由；
- 允许 UART0/UART1 使用相同的 worker 入口；
- 保留默认引脚对作为 profile 匹配或分配评分，不作为硬绑定；
- 资源规划同时检查 GPIO、console/boot、DMA、bus sharing 和内存预算；
- 保持当前 lease，避免无关 manifest 变化导致 controller 随机切换；
- ResourceReport 上报实际 controller、DMA 和引脚绑定。

#### 主要涉及文件

- `esp32-collector/components/hw_profile/*`
- `esp32-collector/components/bus_manager/*`
- `esp32-collector/components/bus_dma/*`
- `esp32-collector/main/app_state.*`
- `esp32-collector/main/config_apply_transaction.*`
- `backend/internal/nodemgr/handler_resources.go`
- Channel 配置相关 API 和模型

#### 验收门禁

至少使用两份 manifest 验证同一个逻辑 Channel 可以分别租用 UART0 和 UART1：

- 命令路由正确；
- RX 数据回到正确 Channel；
- ResourceReport 与实际硬件一致；
- 配置失败后原 lease、driver 和数据库状态保持不变；
- 两个 UART runtime 使用同一套 worker 代码路径。

#### 回滚点

保留旧的固定端口路由作为兼容 fallback，但只能在 planner 无法识别旧配置时使用，并记录告警。新配置不得依赖 fallback。

### 18.5 P2：UART 事件驱动改造（行为等价）

#### 目标

删除 UART RX 的固定 5 ms 数据轮询，同时保持现有请求—响应行为和 DataReport wire format 不变。
状态：已完成，P3 已在此基础上启用统一自动边界。

#### 工作内容

- 每个物理 UART 安装并保存独立 driver event queue；
- 每个 UART runtime 创建同构 RX event task；
- 处理 `UART_DATA`、FIFO overflow、ring full、frame/parity error 等事件；
- 事件驱动阶段保留兼容边界；P3 阶段将上层缓存扩展到 1KB，并以 512B 固定
  block 自动提交连续输入，避免无间隔数据只能等待 idle；
- RX task 只负责搬运数据和更新统计；
- 将配置 suspend/resume 纳入 event task 生命周期；
- 为 event queue、driver ring 和 task 增加退出与重建路径。

#### 主要涉及文件

- `esp32-collector/components/bus_dma/bus_dma.c/.h`
- `esp32-collector/components/bus_worker/bus_worker.c/.h`
- `esp32-collector/main/app_state.c/.h`
- `esp32-collector/main/app_callbacks.c`
- UART host tests 和硬件测试脚本

#### 验收门禁

- UART0 和 UART1 分别运行相同的请求—响应测试；
- SN-3001 读取、写入、改波特率和读回全部通过；
- UART0 现有模拟协议回归通过；
- 5 ms 轮询不再作为接收数据的必要条件；
- FIFO/ring/frame/parity 计数可被读取；
- 配置切换时不存在 driver 已删除但 RX task 仍访问的情况；
- event task 不直接调用 MQTT。

#### 回滚点

保留旧 `rx_task` 实现一个发布版本周期。新 event task 可以通过构建开关或运行时 capability 回退，但二者不能同时消费同一 UART driver。

### 18.6 P3：统一透明接收边界与异步上报

状态：已实现，等待 P6 实机验收。

#### 目标

在不增加人工模式配置的前提下，让同一条 UART 接收流程同时处理请求—响应和持续输入，并解除总线接收与 MQTT 发布的耦合。

#### 工作内容

- 引入统一透明接收状态机；
- 按 pending command、`read_size`、协议边界、idle timer、最大 chunk 和最大等待时间自动选择提交边界；
- 对响应完成后剩余的字节继续进入同一透明接收队列；
- 引入固定 RX block pool 和小描述符队列；
- 增加 critical/control report queue；
- 增加 telemetry/raw-data report queue；
- 将 DataReport 编码和 MQTT publish 移出 UART RX task；
- 调整 DataReport 编码容量，避免 raw payload 与协议字段共用 512 字节上限；
- 保证同一 Channel 的 sequence 有序；
- 控制消息保留独立容量。

#### 主要涉及文件

- `esp32-collector/components/bus_worker/*`
- `esp32-collector/components/msg_handler/*`
- `esp32-collector/components/ehome_mqtt/*`
- `esp32-collector/components/transport/*`
- `esp32-collector/components/frame/*`
- 后端 DataReport/DataEventBus 入口和 metrics

#### 验收门禁

- SN-3001 短响应不被拆成错误结果；
- 无 pending command 的持续输入能按 chunk/时间边界持续提交；
- 同一 Channel sequence 连续；
- 控制 Final 不会排在普通原始数据之后超时；
- MQTT 短时阻塞不导致 UART driver FIFO 立即溢出；
- report queue 满时有明确计数和策略；
- 断网期间不会无限制分配内存。

#### 回滚点

本阶段完成后，仍可以关闭统一透明接收的大块提交，仅保留事件驱动和旧 DataReport 路径。新上报队列必须可停止并清理，不得遗留 block ownership。

### 18.7 P4：调度器和总线级背压隔离

状态：已实现 per-controller pressure 与独立 control/sample queue；worker 对四类
controller 共用控制优先且有界让渡采样的消费流程。

#### 目标

让 UART、SPI、I2C 的队列压力互不扩散，并为控制命令和普通采样保留不同的容量和策略。

#### 工作内容

- scheduler 按目标 controller 计算 queue pressure；
- UART0 压力不再导致 SPI/I2C/UART1 采样全部跳过；
- 为 control 和 sample 保留容量或拆分逻辑队列；
- 使用小 descriptor/payload pool，避免复制巨大 `bus_cmd_t`；
- 增加每队列 current/high-water/skip/reject 指标；
- 为控制命令设置优先处理路径；
- 将普通采样跳过和数据流溢出区分统计。

#### 主要涉及文件

- `esp32-collector/components/scheduler/*`
- `esp32-collector/components/bus_worker/*`
- `esp32-collector/components/bus_manager/*`
- `esp32-collector/main/app_state.*`

#### 验收门禁

- 人工制造 UART 高负载时，SPI/I2C 和另一 UART 仍能入队并执行；
- 普通采样队列满不会拒绝控制命令；
- 控制命令不会被无限增长的采样任务饿死；
- 各总线的 queue pressure 与实际目标 queue 一致；
- 运行时内存无持续增长。

### 18.8 P5：DMA、SPI 和 I2C 语义统一

状态：已实现，等待 P6 实机矩阵验收。

#### 目标

在保持 DMA 可配置的同时，确保 DMA 开关只表示传输资源，不改变 UART/SPI/I2C 的业务协议语义。

#### 工作内容

- UART DMA 请求由 planner 和 DMA pool 联合处理；
- C6 UART DMA 冲突在 manifest 阶段拒绝；
- SPI 保持 `SPI_DMA_CH_AUTO`/`SPI_DMA_DISABLED`，并按物理 bus 统一 DMA 状态；
- I2C write+read 始终保持协议要求的 combined/repeated START 语义；
- C6 I2C DMA true 按 capability 拒绝或明确声明不可用；
- 修正 I2C bus 复用检查顺序；
- 检查 S3/C6 resource report、DMA binding 和实际 driver 行为一致性。

#### 主要涉及文件

- `esp32-collector/components/dma_pool/*`
- `esp32-collector/components/hw_profile/*`
- `esp32-collector/components/bus_dma/*`
- `esp32-collector/components/bus_manager/*`
- `backend/internal/nodemgr/handler_resources.go`
- DMA、SPI、I2C host tests

#### 验收门禁

- UART0/UART1 交换 lease 后 DMA 行为一致；
- DMA 开关切换不改变 SPI/I2C 返回数据；
- I2C 设备对 repeated START 的要求不受 DMA 配置影响；
- 不支持 DMA 的资源不会被报告为已分配；
- DMA 冲突 manifest 在运行时重建前被拒绝；
- 失败后原 DMA pool 状态可恢复。

### 18.9 P6：1 Mbps 并行压力和长稳验证

#### 目标

验证动态分配和统一接收链路在不同 UART 实际绑定结果下均能工作。

#### 测试矩阵

至少执行以下两组对称测试：

```text
组合 A：UART0 连续 1 Mbps，UART1 SN-3001 9600
组合 B：UART1 连续 1 Mbps，UART0 SN-3001 9600
```

每组还要分别测试：

- 高速 UART DMA 开、低速 UART DMA 关；
- 两个 UART DMA 都关；
- 可行时测试高速 UART 绑定不同 GPIO；
- MQTT 正常在线；
- MQTT 短时断开和恢复；
- 配置重建和失败回滚；
- SPI/I2C 同时采集；
- OTA、StatusReport 和日志任务并行。

#### 数据校验

- 发送递增序列或伪随机数据；
- 校验 UART 输入字节数；
- 校验上报字节数；
- 校验 sequence 连续性；
- 校验 CRC 或端到端摘要；
- 统计 FIFO、ring、block pool、report queue 所有丢弃点；
- 统计另一 UART 的成功率、p95/p99 延迟和超时。

#### 建议时长

- 冒烟测试：30 秒；
- 功能压力：10 分钟；
- 长稳门禁：至少 1 小时；
- 发布前 soak：按现场业务要求延长到 4～24 小时。

#### 通过条件

- 无未解释的 sequence gap；
- 无 FIFO/ring/software overflow；
- UART0/UART1 交换绑定后结果一致；
- SN-3001 成功率达到既定门限；
- SPI/I2C 无新增超时；
- heap 不持续下降；
- 无 watchdog、panic 或异常重启；
- 控制消息延迟不超过既定门限。

### 18.10 P7：灰度发布和运行监控

#### 发布策略

1. 先在 host tests 和模拟串口完成协议回归；
2. 在专用 C6 测试节点验证动态 lease；
3. 使用当前 SN-3001 设备执行 UART controller 交换测试；
4. 小范围启用高速输入；
5. 观察一个完整业务周期后再扩大范围；
6. 最后才更新默认固件或默认配置。

#### 运行监控

至少观察：

- channel-to-controller 实际映射；
- DMA request/allocated/conflict；
- UART overflow 和 sequence gap；
- 各总线 queue high-water；
- critical report 延迟；
- telemetry report 丢弃；
- MQTT reconnect/outbox；
- current/minimum free heap；
- worker 栈余量；
- SN-3001 和其他边缘设备成功率。

#### 回滚触发条件

出现以下任一情况应回滚到上一阶段固件或配置：

- UART controller lease 与 ResourceReport 不一致；
- 任一 UART 出现未解释的响应错配；
- ChannelCmdV2 Final 超时或重复；
- SN-3001 成功率下降；
- sequence gap 无法归因于外部输入；
- SPI/I2C 出现新增错误；
- free heap 持续下降或 watchdog 重启；
- 配置回滚无法恢复原 lease。

### 18.12 方案完成定义

该方案只有在以下条件全部满足时才算完成：

1. 逻辑 Channel 可以稳定动态租用 UART0 或 UART1；
2. UART0/UART1 交换实际设备后，功能和性能结论一致；
3. UART RX 不依赖固定 5 ms 轮询；
4. UART 使用统一透明接收和自动边界，不要求用户选择模式；
5. UART 高负载不会阻塞控制消息、另一 UART、SPI 或 I2C；
6. DMA 开关和硬件 capability 一致；
7. SPI/I2C 事务语义不因 DMA 开关改变；
8. 配置失败可以恢复原 controller lease、DMA 和 driver；
9. 1 Mbps 对称压力、MQTT 故障和长稳测试通过；
10. 所有丢包、溢出、队列和资源冲突均可被观测和解释。
