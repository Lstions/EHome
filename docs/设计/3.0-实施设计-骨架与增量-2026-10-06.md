## 1. 组件结构（新建 5 个，均宿主可测）

沿用既有命名习惯（`transport`/`frame`/`scheduler` 不加前缀），新组件取**不与现有冲突**的名字：

| 组件 | 职责 | 对应设计文档 | 依赖 |
|---|---|---|---|
| `variant` | 型号能力描述（P8） | §1.13 | **无**（纯数据） |
| `link` | 上行链路抽象（五态结果） | §1.2 | `variant` |
| `wire` | 定界与重组 | §1.3 | **无**（纯算法） |
| `msgcodec` | 消息编解码（纯函数） | §1.3 | **无**（纯算法） |
| `dispatch` | 分发表 | §1.3 | `msgcodec` |

**依赖方向单向**：`dispatch → msgcodec`、`link → variant`，**无环**（P4；现状有唯一环 `msg_handler ↔ bus_worker`，D-14）。

**命名说明**：用 `msgcodec` 而非 `msg`，避免与既有 `msg_handler` 在阅读与搜索上混淆。

## 2. 接口设计（骨架的"合同"，实现前先定稿）

### 2.1 `variant` —— 型号能力（P8）

```c
/* components/variant/include/variant.h */
typedef enum { VARIANT_S3 = 0, VARIANT_S3P, VARIANT_C6, VARIANT_COUNT } variant_id_t;

typedef struct {
    const char *name;
    variant_id_t id;
    bool     has_psram;
    uint32_t psram_bytes;
    uint32_t internal_heap_bytes;      /* 预算断言用（P5） */
    uint32_t internal_contiguous_max;  /* 放置判据：> 此值的连续需求必失败 */
    bool     has_iram_segment;         /* S3/S3P=1；C6=0 */
    uint8_t  max_channels;
} variant_caps_t;

const variant_caps_t *variant_caps(void);                 /* 构建期选定，运行期只读 */
const variant_caps_t *variant_caps_for(variant_id_t id);  /* 宿主测试用：显式取任一型号 */
```
**要点**：`variant_caps_for()` 让**三型号的差异都能在宿主上被测试**，无需 ifdef。

### 2.2 `link` —— 上行链路（P1/P2/P3）

```c
/* components/link/include/link.h */
typedef enum {
    LINK_SENT = 0,        /* 已交给链路层并计入账 */
    LINK_NOT_READY,       /* 链路未就绪：调用方【不应】换路重试 */
    LINK_BACKPRESSURE,    /* 缓冲满：调用方【应】稍后重试（不是错误） */
    LINK_PAYLOAD_TOO_BIG, /* 超 MTU：调用方【必须】分片或拒绝 */
    LINK_FATAL,           /* 链路不可用：调用方【应】通知上层重建 */
    LINK_RESULT_COUNT
} link_result_t;

typedef struct link link_t;   /* opaque —— 外部不能读写字段（P4） */

typedef struct {
    link_result_t (*open)(void *ctx);
    void          (*close)(void *ctx);
    link_result_t (*send)(void *ctx, const uint8_t *data, size_t len);
    uint32_t      (*mtu)(void *ctx);
    bool          (*is_ready)(void *ctx);
} link_driver_t;

typedef struct {
    bool     ready;
    uint32_t mtu;
    uint32_t tx_sent;        /* P3：每条路径都要可观测 */
    uint32_t tx_too_big;     /* P3：被 MTU 门禁拒绝的次数 */
    uint32_t tx_backpressure;
    uint32_t tx_not_ready;
    uint32_t tx_fatal;
} link_stats_t;

link_t *link_create(const link_driver_t *drv, void *drv_ctx);
void    link_destroy(link_t *l);
link_result_t link_send(link_t *l, const uint8_t *frame, size_t len);
const char   *link_result_name(link_result_t r);   /* 日志/测试用，避免散落字符串 */
void    link_get_stats(const link_t *l, link_stats_t *out);   /* 一次一致快照（P4） */
```

**`link_send` 的确定性行为（这是骨架的核心语义，必须先定死）**：
1. `l == NULL || frame == NULL || len == 0` ⇒ `LINK_FATAL`（参数错，不是背压）；
2. **`len > drv->mtu()` ⇒ `LINK_PAYLOAD_TOO_BIG`，且【不调用】drv->send**（P2：发出前校验）；
3. `!drv->is_ready()` ⇒ `LINK_NOT_READY`，**不调用** send；
4. 否则转发 `drv->send`，**原样返回其结果**（不压平 —— 这正是 D-01 的病根）；
5. **每条返回路径都累加对应计数器**（P3）。

### 2.3 `wire` —— 定界与重组（P2）

**3.0 帧格式（定稿）**：TCP 是字节流 ⇒ 必须自定界。
```
frame := varint(payload_len) || payload[payload_len]
```
- `payload_len` 为 **LEB128 无符号 varint**（复用既有 varint 风格）；
- 长度**只计 payload**，不含自身；
- 这样任何字节切分下都能正确重组（治 D-09："一次 recv = 一条消息"的错误前提）。

```c
typedef enum {
    REASM_NEED_MORE = 0, REASM_FRAME_READY,
    REASM_ERROR_TOO_LARGE,   /* 声明长度 > max_msg_bytes ⇒ 立刻拒绝，不缓冲（P3） */
    REASM_ERROR_MALFORMED    /* varint 非法（如超 5 字节） */
} reasm_result_t;

typedef struct reassembler reassembler_t;
reassembler_t *reasm_create(uint32_t max_msg_bytes);   /* 上界是构造参数（P5） */
void           reasm_destroy(reassembler_t *);
reasm_result_t reasm_push(reassembler_t *r, const uint8_t *in, size_t n,
                          const uint8_t **frame_out, size_t *frame_len_out);
```
**确定性行为**：
- **超限立即报错且不分配**（对比现状"静默保留尾部" —— 后端 M11、固件 D-09 同型）；
- `frame_out` 指向**重组器内部缓冲**（零拷贝），**下一次 `reasm_push` 前有效**；
- 一次 push 最多产出一帧（多次 push 消化多帧）—— **简化接口，行为可证**。

### 2.4 `msgcodec` —— 纯编解码（P7）

**纯函数、无全局、无硬件** ⇒ 宿主可 100% 覆盖。
```c
typedef enum { ENC_OK = 0, ENC_NO_SPACE, ENC_BAD_ARG } enc_result_t;
typedef enum { DEC_OK = 0, DEC_TRUNCATED, DEC_BAD_TYPE, DEC_BAD_WIRE } dec_result_t;

/* 字段级原语（先做原语，消息表随后）*/
enc_result_t enc_varint(uint8_t *out, size_t cap, size_t *used, uint64_t v);
enc_result_t enc_bytes (uint8_t *out, size_t cap, size_t *used, uint8_t type, const void *p, size_t n);
dec_result_t dec_varint(const uint8_t *in, size_t n, size_t *used, uint64_t *v);
```
**确定性行为**：`cap` 不足 ⇒ `ENC_NO_SPACE`（**不截断**）；varint 超 10 字节 ⇒ `DEC_BAD_WIRE`。

### 2.5 `dispatch` —— 分发表（P3/P4）

```c
typedef enum { DISP_OK = 0, DISP_UNKNOWN_TYPE, DISP_BAD_FRAME, DISP_HANDLER_ERR } disp_result_t;
typedef disp_result_t (*disp_handler_fn)(void *ctx, const uint8_t *payload, size_t len);

typedef struct { uint8_t type; disp_handler_fn fn; const char *name; } disp_route_t;

disp_result_t dispatch_frame(const disp_route_t *table, size_t n,
                             const uint8_t *payload, size_t len, void *ctx);
const char   *disp_result_name(disp_result_t r);
```
**确定性行为**：**未知类型 ⇒ `DISP_UNKNOWN_TYPE`（不静默）** 且可计数（P3）。

### 7.2 ⭐ 测试当场抓到的 2 个真实缺陷（写代码时就发生，不是事后发现）

**缺陷 A：`wire.c` 产出帧后立即压缩 → 覆盖掉刚返回给调用方的帧**

我原来的 `reasm_push` 在返回 `REASM_FRAME_READY` **之前**就 `memmove` 前移剩余字节，
而 `*frame_out` 恰好指向被覆盖的区域 ⇒ **调用方拿到的是已被改写的内存**。
契约写的是"frame_out 在下次 push 前有效"，实现却当场自毁。
**修复**：改为**惰性压缩** —— 只在**下一次 push 的开头**压缩
（此时调用方已用完上一帧）。新增 `start` 字段，产出帧只推进 `start` 不搬数据。
**抓到它的用例**：`test_multiple_frames_sequential`。

**缺陷 B：`msgcodec.c` 容量检查算错 → 放得下的调用被判 NO_SPACE**

`enc_field_u64` 用 `1 + VARINT64_MAX_BYTES + vlen` 作为总长，
但长度前缀编码的是 `vlen`（≤10）**只需 1 字节**，不是 10 字节。
⇒ 明明 4 字节就够的字段，要求 cap ≥ 13 才肯写 —— **过度保守，浪费缓冲、假报错**。
**修复**：按实际前缀长度计算。**抓到它的用例**：`test_field_no_space` 的边界断言。

> **这两条都不是"设计错了"，而是"实现没照设计做"** —— 且都**只能在运行时暴露**。
> 这正是 C2（宿主优先）在第一小时就回本的地方。

### 7.3 ⚠ 我自己的自证脚本有坑（重要的方法论记账）

第一版变异自证脚本报 **M1 "变异后仍 PASS"** —— 看起来像"测试没测到这条语义"。
**真相是**：那个变异（`if (mtu == 0 || ...)` → `if (false)`）让 `mtu` 变成未使用变量，
触发 `-Werror=unused-variable` ⇒ **编译失败** ⇒ 脚本跑了**上一次的旧二进制** ⇒ 得到 PASS。

**这是 silent-failure 的"假绿"族**：结论看起来是"测试无效"，
实际是"**根本没有测试新代码**"。
**修正**：自证脚本必须**先确认"变异后仍能编译"**，编译失败时结论无效（应换一个能编译的变异）。
修正后 M1 换成 `mtu == 0 && len > mtu`（能编译、语义确实被破坏）⇒ 变异后 FAIL ✓。

**另一处（同一次）**：M4 的变异**打错了目标** —— 模式匹配到了 `enc_field_u64`，
而测试覆盖的是 `enc_field_bytes`（两处注释文字不同）⇒ 报"仍 PASS"。
这反而**暴露了一个真实覆盖缺口**：`enc_field_u64` 的容量检查**当时无人看管**。
补上边界用例后，**立刻抓出了缺陷 B**。
⇒ **"自证报绿"有两种含义：测试无效，或者变异打错了地方 —— 必须逐条查明，不能想当然。**

## 8. I6 实施记录：B0 修复

### 8.1 D-03 TCP 启动死代码 —— 已修（2026-10-06）

**缺陷**：`main/app_callbacks.c` 的 `case WIFI_MGR_CONNECTED:` 在 `break;` **之后**
才写 TCP start 块，其后又一个 `break;` ⇒ **不可达**。
`sdkconfig` 里 `CONFIG_DEBUG_TCP_ENABLED=y`（**已编译进去**），

### 9.1 D-09 定帧契约

**问题**：`transport_msg_cb_t` 只写"消息回调"，从未声明"一次回调 = 一条完整消息"。
MQTT 恰好满足（自带分帧），**TCP 不满足**（字节流）⇒ `ehome_tcp.c` 把一次
`recv()` 的字节块当完整消息回调。

**修法**：交付语义升级为**契约的一部分且有唯一来源**（P4）——
`transport_framing_t`（`MESSAGES`/`STREAM`/`UNKNOWN`）+ `transport_framing_of()`。
**未知类型返回 `UNKNOWN` 而非乐观默认 `MESSAGES`** —— 乐观默认正是 D-09 的成因。

**诚实说明其强制力**：`transport_type_t` **没有 COUNT 哨兵**，故新增类型时编译器
**不会**因表里缺项而报错；未表态者走 `UNKNOWN`（**失败可见，但非编译期失败**）。
升级为编译期强制需给枚举加哨兵并同步所有 switch —— 独立改动，不塞进 B0。

### 9.2 D-10 短写静默发半帧

`ehome_tcp.c` 原把 `send() > 0` 记为成功 ⇒ **短写静默发出半帧**。
修法：`net_policy_classify_write()`（`COMPLETE`/`PARTIAL`/`NOTHING`/`ERROR`，
**只有 COMPLETE 算成功**）+ 循环续写 + 部分写不计入成功。
硬错误**优先于**"写了多少"（部分写后 EPIPE 应是 ERROR，重试无意义）。

### 9.3 D-21 生命周期契约 —— **含一处审计误判更正**

> ⚠ 审计称"init/deinit 在两个实现里都是 no-op/空函数"，并引 `ehome_tcp.c:153-161`。
> **实测：153 行是 `tcp_init`，不是 deinit。**

| 实现 | init | deinit | 判定 |
|---|---|---|---|
| TCP | no-op（配置在 create 时已设 ⇒ 无可获取，合理） | `tcp_stop()`，**真实工作** | ✅ **履行**契约 |
| MQTT | no-op | **空函数**（注释自陈 `ehome_mqtt` 无 deinit API） | ❌ 未履行 |

且 `tcp_transport_destroy()` 会**先调 deinit 再释放内存** ⇒ TCP 的两个生命周期是完整的。

**真正的问题不是"没人实现"，而是【契约没写下来】**：没人能判断 `deinit` 该不该释放
`priv_data`。`destroy` 假定它**不**释放（自己释放）；若有人把释放写进 `deinit`
⇒ **double free**。

**修法**：`transport.h` 明确划分 —— `create/destroy` 拥有**内存**；
`init/deinit` 拥有**运行时资源**（socket/任务/信号量），**不释放 priv_data**；
三条约定（deinit 幂等、destroy 先 deinit、init/deinit 可为 NULL 但必须是有意的）。
加 `transport_audit_ops()` 让钩子有无变成可断言数据。

3. 这正是 **P4（语义只有一处定义）**。

## 18. B3 实施记录：D-01（代理判据）—— 已完成（2026-10-06）

### 18.1 缺陷（L-02 的结构成因）
`msg_handler_publish_checked()` 需要回答"广播刚才有没有尝试过 MQTT？"，
用的是 `transport_registry_has_type(TRANSPORT_TYPE_MQTT)` —— **代理判据**，
实际回答的是"**MQTT 是否已注册**"。

两者在"**已注册但未连接**"时**不等价**：
`transport_broadcast()` 只在 `is_connected()` 为真时才调用 send
⇒ 那一刻它**从未尝试过 MQTT**，而日志却说 "MQTT already attempted inside
broadcast" —— **那句话是假的**。
当前行为碰巧安全（未连接时重试也会失败），但那是巧合：
一旦"未连接"变成可恢复状态，错误的判据会导致**漏发**。

### 18.2 顺带更正适配器里一处**错误的理由**
`mqtt_transport_adapter.c` 原注释称：把三态压平是因为
"改动它会连带改变 `transport_broadcast` 的 `sent_count` 判定"。
**实测不成立**：`transport_broadcast` 只在 `err == ESP_OK` 时 sent_count++，
而 NOT_CONNECTED 与 FAILED **都**映射为 ESP_FAIL（都是失败）
⇒ **无论是否压平，sent_count 都不受影响**。

真正的原因更简单也更诚实：`transport_ops.send` 返回 `esp_err_t`，
**没有"未连接"这一档**；要表达三态得先扩展接口 —— 那是 3.0 `link_result_t` 的事。
（注释已改为这个说法。）

### 18.3 修复：让调用方问对问题
新增 `transport_broadcast_ex(data, len, &report)`，回报**实际发生了什么**：
`attempted` / `sent` / `connected` / **`mqtt_attempted`** / **`tcp_attempted`**。
**只有真的调用过 send 才算 "attempted"** —— 未连接时不计。
`transport_broadcast()` 保留原签名（内部转调 `_ex` 并丢弃报告）。
`msg_handler` 改为判 `rep.mqtt_attempted`。

## 28. 主线起步：3.0 link 迁移（背压成为一等状态）（2026-10-06）

### 28.1 底层：把背压从"失败"里分出来
`mqtt_client_publish_ex` 原本把三种情况压进 `MQTT_PUBLISH_FAILED`：

| enqueue | 含义 | 应当 |
|---|---|---|
| `-2` | **outbox 满 = 背压** | **退避重试** |
| `-1` | 编码/内存失败 | 不重试 |
| `valid == 0` | client 换代（重连/重建） | 不重试 |

**处置方式完全相反，却共用一个返回值。**
新增 `MQTT_PUBLISH_BACKPRESSURE = 3`，`-2 && valid` 走它，单独打 WARN。

### 28.2 新增 `components/link_mqtt/` —— 四态如实映射，**不压平**
| 底层 | link_result_t | 调用方应当 |
|---|---|---|
| `MQTT_PUBLISH_OK` | `LINK_SENT` | 继续 |
| `MQTT_PUBLISH_NOT_CONNECTED` | `LINK_NOT_READY` | 降级/入队，**不换路重试** |
| `MQTT_PUBLISH_BACKPRESSURE` | `LINK_BACKPRESSURE` | **退避重试**（不是故障） |
| `MQTT_PUBLISH_FAILED` | `LINK_FATAL` | 上报故障，**不重试** |

这是 **D-01 那条链的终点**：旧 `transport_ops.send` 返回 `esp_err_t`（两档），
把底层已经分好的区分又压平；`link` 把它保留到调用方。

### 28.3 `link_result_is_error()`：把"该不该重试"写成可执行定义
`SENT` / `BACKPRESSURE` / `NOT_READY` **不是**错误；
`PAYLOAD_TOO_BIG` / `FATAL` 是。避免每个调用方各自判断（P4）。

### 28.4 P2 落点：MTU 在**发出前**生效
驱动如实报出 `LINK_MQTT_MTU_BYTES`（2011，源自 R1 实测），
`link_send` 在调用底层**之前**拒绝超长帧 ⇒ 不会"发出去了才发现太大"。

### 28.5 新门禁：手抄枚举必须与生产一致
`tools/check_stub_enum_sync.py`（已进 `ctest`）。
两个测试用 `#define EHOME_MQTT_H` 挡掉真实头（esp-mqtt 不能在宿主编译）

**编译器这次帮了忙**，但只在"新值恰好被判断"时才说话；
若新值只被赋值、从不被判断，漂移会**静默**存活。
门禁把漂移变成确定的红：**落后 / 凭空多出 / 值不同**，三种都报。

## 30. 骨架自审：link_send 的 TOCTOU 预检（我自己的骨架违背了它自己的设计）（2026-10-06）

### 30.1 缺陷
设计文档 §1.2 判 `transport_ops` 的**缺陷①**是"调用方须'先查再发' = TOCTOU"，
并明确要求新接口"**唯一的上行入口。P1：不做'先查再发'，结果即决策依据**"，
同时把 `link_stats_t.ready` 注为"**只读观测（诊断用），不参与决策**"。

而我写的 `link_send` 规则 3 正是那个形态：

```c
if (!l->drv->is_ready(l->ctx)) { l->stats.tx_not_ready++; return LINK_NOT_READY; }
link_result_t r = l->drv->send(...);
```

**同一份头文件里既写着"不预检"又写着"预检"** —— 而且测试把它锁死了
（`test_not_ready_skips_driver` 断言 `send_calls == 0`）。

### 30.2 为什么预检不只是风格问题
1. **查与发之间链路可变** ⇒ 预检**不能**替代结果：通过≠成功，失败≠必失败；
2. "为什么没就绪"的权威来源是**驱动** ⇒ 预检把该语义复制到 link 层（P4）；
3. 省下的调用没有价值 —— 驱动在未就绪时本就立即返回 NOT_READY。

### 30.3 修复
- **删除规则 3**。"未就绪"现在只有**一个**来源：`drv->send` 的返回值。
- `stats.ready` 退回只读观测（发送后刷新快照）。
- 头文件契约同步改写，并把三条理由写进去（**防止再被加回来**）。

### 30.4 顺带修掉一个同源缺陷：把观测量当控制量
`link_destroy()` 原先用 `stats.ready` 决定要不要调 `close()` ——
**一次诊断刷新会顺手改变生命周期行为**。新增独立的 `opened` 事实
（`link_open` 成功时置位，不被任何观测刷新），二者语义分离（P1/P4）。

### 30.5 测试同步（关键：旧测试固化了错误行为）
- `test_not_ready_skips_driver` → `test_not_ready_comes_from_driver_result`：
  断言驱动**被调用**且结果透传；并加**竞态反面**用例 ——
  `is_ready()==true` 但 `send` 返回 NOT_READY **仍必须是 NOT_READY**
  （预检实现会误判成"可以发"，这正是 TOCTOU 的危害）。
- `link_mqtt_tests` 的 `test_is_ready_forwards` 同样改为"结果来自驱动"。
- 新增**生命周期分歧**用例：open 成功后一次 send 把 `stats.ready` 刷成 false，
  destroy 仍须 `close` 一次 —— 这是唯一能抓到 M41 的断言。

## 32. S0：冻结契约 —— 共享 golden vector 抓出【骨架自己发明了不兼容格式】（2026-10-06）

### 32.1 为什么先做 S0
设计 §3 迁移路径规定 **S0（冻结契约）先于 S1（link 迁移）**，原文：
"**必须先有 S0 契约，否则重构中两端会各自漂移**"。

现状证实该风险是**具体的**：ESP32 端（`components/msgcodec`，C）与后端
（`backend/pkg/frame`，Go）是**两套独立实现、各自带各自的黄金向量、无任何共享物**。
两端可能**同时自洽却互相不通**。

### 32.2 新增：唯一向量来源 + 三方校验
`protocol/vectors/wire_primitives.txt`（12 条，语法极简、语言中立）：

| 消费者 | 说明 |
|---|---|
| 后端 Go | `backend/pkg/frame/golden_vectors_test.go`（**待补**） |
| ESP32 C | `host_tests/golden_vectors_tests.c`（读同一文件，对真实 `msgcodec` 断言） |
| 独立第三份 | `tools/check_golden_vectors.py`（Python 重实现；已进 `ctest`） |

**第三份实现是关键**：只用某一端去"验"契约，等于让它给自己打分。

### 32.3 ⭐ 发现：I1 骨架发明了一个**不兼容的**线路格式
C 端 `msgcodec` 初版：
```
[field_id 1 字节][varint 长度][值]
```
生产 ESP32 `frame_codec.c:38` 与后端 `frame.go:253`：
```
tag = (field_num << 3) | wire_type     （protobuf 风格）
```
**完全不兼容** —— 共享向量 12 条里 **5 条**当场对不上。

> **一个定义了"另一个格式"的骨架，比没有骨架更危险：它看起来能用。**
> 一旦接线就是全线不通。这正是 S0 必须在 S1 之前做掉的理由。

**已核实**：后端既有 Go 向量 `06081110091a04010300002008282130c413` 按 tag 规则解析
恰好得到 `(1,17),(2,9),bytes(3,01030000),(4,8),(5,33),(6,2500)` —— 与 Go 测试意图一致
⇒ **生产格式确认是 tag 制，骨架是错的那一方**。

### 32.4 修复
- `msgcodec` 改为 tag 制：新增 `enc_tag()`、`field_view_t.wire_type`；
  `enc_field_u64`/`enc_field_bytes`/`dec_next_field` 全部改写；
  非法 wire_type **不"尽量解析"**。
- 头文件写明格式的**唯一权威是生产代码+后端**，并记下此次错误。
- `msgcodec_tests` 的 3 处尺寸/布局断言按新格式更新（tag 制比旧格式少 1 字节）。
