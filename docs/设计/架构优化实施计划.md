## 2. 任务 A — unified_data 时序化

### 现状事实（多轮审查实证）

- models.UnifiedData：ID/SensorName(32)/Value/Unit/Timestamp/CreatedAt/EdgeDeviceID/LogicalDeviceID，b-tree 索引 4 个
- 全仓零 FK 引用 unified_data.id → 主键改复合不破坏任何外键
- persist consumer 显式设 Timestamp=now → 分区键恒有值
- merge 是 UPDATE logical_device_id 原地改写 → rollup 无需合并后重算（rollup 保持 device 维度）**（状态补注：该设计已于 2026-09-15 退役，见 `docs/分析/rollup-退役裁决-2026-09-15.md`）**
- 最新值查询面：DISTINCT ON (device_id) 无时间谓词 → v0.2 补 latestValueCache 改造

### 设计要点

- **月分区**：PG 声明式 RANGE，分区键 (timestamp)；主键 (id, timestamp)；DDL 走手写迁移（AutoMigrate 移除 UnifiedData 加注释）；SQLite 不分区走同构路径
- **迁移**：unified_data_new 建表 → 按批搬迁（10K/批断点续跑）→ RENAME legacy 观察一个 retention 周期不删
- **[已退役 2026-09-15] RollupConsumer**：挂在 persist 之后，UPSERT ON CONFLICT；独立邮箱 fail-open；丢率 >0.1% 降级微批（rollup.batch_ms 开关）——该消费者、`rollupSink` 机制与 `rollup.batch_ms` 开关已随 `unified_data_rollup_1m` 整体删除（该开关在代码中从未存在过，仅为本节设计里的留开关意图）。本条仅存历史，不再是待做项。裁决与证据：`docs/分析/rollup-退役裁决-2026-09-15.md`。
- **[已退役 2026-09-15] 查询精度路由**：historical API 加 precision=rollup|raw（auto：>48h 强制 rollup；仅 device 过滤允许 rollup，logical scope 强制 raw）——**该路由从未接线且在生产不可达**：`precisionFor` 零生产调用者（在 2026-09-14 停写裁决时删除），本仓查询恒有 logical scope（`BackfillLogicalDevices` 全量回填、新实例创建即赋逻辑身份），且 rollup 表无 `logical_device_id` 列 ⇒ 该分支恒不可达、恒返回 raw。`/api/v1` 中不存在 `precision` 参数（实测 grep 零命中）。裁决与证据：`docs/分析/rollup-退役裁决-2026-09-15.md`。
- **retention**（2026-09-12 更新，2026-09-15 复核）：raw 系统级默认 90 天，可经 EHOME_DATA_RETENTION_DAYS 覆盖（30 天仅作推荐配置示例）——**该 raw 部分现仍有效**（复核：`config.DefaultDataRetentionDays = 90`，`.env.example` 同步标注为「系统级默认 90」）。**[已退役 2026-09-15]** 后半句「rollup 保留 365 天，为独立策略，与 raw 默认解耦（当前代码未见自动清理路径，待确认）」**作废**：表已整体退役，该「无自动清理路径」待确认项随之关闭，不再是遗留待办。裁决与证据：`docs/分析/rollup-退役裁决-2026-09-15.md`。
- **latestValueCache**：概览/最新值 API 改内存缓存（persist 旁路更新 + 启动回填 + miss 回落 SQL）
  - **2026-09-16 复核：其中「启动回填」自 2026-08-21 引入起一直未接线**（`WarmupLatestValues` 零生产调用者、零测试）。
    机械原因：初版参数是自定义窄接口 `Raw(...) queryResult`，而 `*gorm.DB.Raw` 返回 `*gorm.DB` —— **接口不被满足、无法编译**。
    已改为函数注入（`SetLatestValuesSource` + `cmd/server/main.go` 接线）并补 4 条回归测试；
    含**接线判据**（源码断言启动路径确实调用），因为「实现了但没人调」这种形态在行为测试下永远是绿的。
    端到端实证：启动日志出现 `Latest value cache warmed up: 29 rows`。详见 `docs/分析/后续工作计划与方案-2026-09-15.md` §1.7 (20.2)。

## 4. 任务 C — 阈值告警引擎

### 数据模型

```go
AlertRule  { ID, TargetType(edge_device|logical_device), TargetID, SensorName,
             Comparator(gt|gte|lt|lte|eq|neq), Threshold, DurationSec(0=立即),
             SilenceSec(默认300), Level(info|warning|critical), Enabled, Name }
AlertEvent { ID, RuleID, State(firing|resolved), Value, FiredAt, ResolvedAt, NotifiedAt }
```

### 求值引擎（挂接点裁决 v0.4：解析后回调）

DataEvent 只携带 RawData 字节，物理量在 SensorParserConsumer 内解析为 []parser.Field。独立 consumer 方案=每事件重复解析（10000 evt/s 基线 CPU 翻倍，不可接受）。**改法**：SensorParserConsumer 增加 alertCallback（复用 deviceActivity 回调先例），分片模式天然并行。

- 规则缓存：CRUD 写路径直接失效+重载（30s 刷新仅兜底）
- 状态机：normal → firing（连续满足 DurationSec）→ resolved；抑制：firing 未 resolved 不重发
- Notification 复用：Source="alert_rule"、SourceID=ruleID、Type 映射（critical→error 图标）
- 超载保护：ring buffer 1000 规则×窗口，超出丢弃计数暴露 metrics

### API 与前端

- /api/v1/alert-rules（CRUD + PATCH enabled）；/api/v1/alert-events（list + read）
- 权限对齐现状：单主体模式下登录即可
- 前端：/alerts 页（规则表格 + 创建/编辑对话框 + 事件时间线）；复用 LogicalDeviceCandidateSelect 模式

### 验收

- [ ] 状态机单测全覆盖（直通/持续窗口/恢复/静默/抑制）
- [ ] 集成：超阈值序列 → firing + Notification + WS；回落 → resolved
- [ ] 前端 vitest：表单校验 + 列表渲染；CDP 走查创建→触发→通知可见

## 7. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 分区迁移数据丢失 | 双表并存 + 断点续跑 + 行数校验门禁；legacy 保留 |
| 主键变更破坏引用 | 零 FK 引用已实证；id 序列全局不变 |
| rollup/raw 口径跳变 | auto 边界（48h）前后端同参数；logical scope 强制 raw 消除第三口径 **（历史陈述：该风险随 rollup 于 2026-09-15 退役而消失——无 rollup 口径即无口径跳变；本行保留作历史记录，非待办。见 `docs/分析/rollup-退役裁决-2026-09-15.md`）** |
| 最新值查询退化 | latestValueCache + miss 回落双路径断言 |
| Redis 删除离线检测变化 | checkDBLastSeen 本就是 L3 兜底，阈值不变 |
| 告警风暴 | SilenceSec 300s + firing 抑制 + 过载丢弃计数 |
