> **状态**: 已实施（2026-11-15）
> **裁决**: 用户 —— "修复而且把那个需要输入用户密码验证的环节给去掉，只要用户二次点击确认就可以了，整个程序都不需要用户输入密码二次确认"
> **关联**: [认证授权](./认证授权.md) | [认证与账户运维指南](../操作/认证与账户运维指南.md) | [BMS-MOS实机无法控制-代码缺陷定位](../分析/BMS-MOS实机无法控制-代码缺陷定位-2026-11-15.md)

## 1. 改了什么

### 1.1 语义变化

| 项 | 改前 | 改后 |
|---|---|---|
| 高风险动作确认 | 确认弹窗 → 若 `LastLoginAt` 超过 **10 分钟** → 再弹「验证当前身份」要求输入当前密码 → `POST /account/reauthenticate` → 重跑确认+执行 | 确认弹窗（**二次点击**）→ 直接取单次令牌 → 执行 |
| 后端判定 | `recentAuthenticationWindow`（10 min）+ 系统管理员主体 | 只保留**授权**判定：`Enabled` 且 `subject_key = system_admin` |
| 错误码 | `recent_auth_required`（403）触发密码框 | 删除；改为 `confirmation_forbidden`（403，账户无权确认） |
| 端点 | `POST /api/v1/account/reauthenticate` | **删除**（404） |

**为什么不只是删前端**：前端弹框只是表象，真正的门在 `commandexec.issueConfirmation` /
`consumeConfirmation` 里的 `user.LastLoginAt` 窗口；只删 UI 会让确认永远 403。所以必须
"门 + 弹框 + 端点 + 测试"四处一起删，才能既有 UX 又无死路。

## 2. 保留的安全不变量（没有一起删）

1. **单次确认令牌**：`command_confirmations` 一行一用，绑定 `actor + 设备 + 动作版本 + params sha256`，5 分钟有效。
2. **限流**：同一 (actor, 设备, 动作) 每分钟最多 5 次铸令牌；登录仍有限流 + `Retry-After`。
3. **审计**：`device_action.confirmation_issued` 照常写（action/version/params hash/reason/IP）。
4. **授权**：只有 `system_admin` 主体且 `enabled` 的账户能确认高风险动作（`confirmation_forbidden`）。
5. **幂等**：每次执行新 `Idempotency-Key`；命令状态机（QUEUED→…→SUCCEEDED/FAILED/UNKNOWN）不变。
6. **改密/登出** 仍原子递增 `session_version` 使旧 Token 失效。

## 3. 风险与取舍

| 风险 | 评估 |
|---|---|
| 误触风险上升（少了"输密码"这道摩擦） | 由「确认弹窗 + 单次令牌 + 限流 + 审计」兜底；确认弹窗文案仍写明物理后果（如"关断后禁止充电，充电回路会被切断"） |
| 共享电脑上他人可点确认 | 会话本身仍是 JWT；产品为单主体自托管，本次裁决接受该取舍 |
| 旧客户端仍调 `/account/reauthenticate` | 返回 404；前端已无调用方，第三方客户端需改（本文档负责说明） |
