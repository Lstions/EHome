## 0. 问题一句话

给 >1h 的图表接 rollup 之前，必须先能回答「这个窗口 rollup 的全不全」。
**而最直觉的判法（拿窗口长度算应有桶数）是自相矛盾的**：算它要查 `unified_data`，
而做这件事的目的就是删掉 `unified_data`。

---

## 1. 为什么不能用「窗口长度 ÷ 60s」当应有桶数

### 1.1 第一层：设备不是 7×24 满桶的

生产实测（bench 库，生产数据副本，设备 14/15，2026-11-01 ~ 11-06）：

| 设备 | 日期 | 实际分钟桶数 |
|---|---|---:|
| 14 | 11-01 | 1440（满） |
| 14 | 11-05 | **1413** |
| 14 | 11-06 | **166**（当天只跑到 02:46） |
| 15 | 同 14 | 同上 |

按 1440 硬算 ⇒ 11-05 判「缺 27 个」、11-06 判「缺 1274 个」⇒ 永远 partial ⇒ 永远回落。
**回填白做，而且是从第一天就白做。**

### 1.2 第二层（更根本）：判据的数据源要被删掉

「应有桶数」只能从 `unified_data` 数出来。而 `unified_data` 是要删的那个。
**用即将删除的表当判据 = 判据有保质期，且到期日和功能上线日是同一天。**

### 1.3 第三层：即使数出来了，也不能在查询时数

查询时数「该窗口应有几个桶」= 对整个窗口做 `count(distinct date_trunc('minute', ...))`，
正是要避免的那种大范围扫描。**判据本身不能比被优化的路径更贵。**

---

## 2. 核心结论：覆盖率是**回填时写下的元数据**，不是查询时算出来的推断

一句话：**回填时数一次，之后永远查表。**

## 3. 表设计（提案，比原方案多三列）

```sql
telemetry_rollup_coverage
  device_id      int         NOT NULL
  day            date        NOT NULL   -- ⚠ 时区见 §4.1
  buckets        int         NOT NULL   -- 该设备这一天 unified_data 里实际有多少个分钟桶
  covered_until  timestamptz NOT NULL   -- ★ 回填覆盖到的**时刻**（见 §4.2）
  state          text        NOT NULL   -- complete / partial / missing
  rows_written   int         NOT NULL   -- ★ 实际写进 rollup 的桶数（校验用，见 §4.3）
  verified_at    timestamptz            -- ★ 最后一次写后校验的时间
  PRIMARY KEY (device_id, day)
```

### 3.1 多出来的三列各解决什么

**`covered_until` 是最关键的一列**，理由见 §4.2 —— 没有它，`day + buckets` 无法表达
「这一天我只回填到 02:46」这件事，于是当天剩余的部分会被误判为已覆盖。

另两列是**自校验**用的（§4.3），成本是每设备每天 8 字节，收益是能发现
「写了一半就崩了但 state 已置 complete」这种最难查的状态。

### 3.2 体积

36 天 × 设备数。5 台设备 = **180 行**，约 20 KB。可忽略，不需要分区。

## 4. 四个必须定死的语义

### 4.1 `day` 的时区

生产是 `Asia/Shanghai`，前端图表按本地日划界。
**建议 `day` 用 UTC 日**，而不是本地日，理由：

- UTC 日 = 固定 86400 秒，无夏令时（本地区无 DST，但规则要写死不依赖这个巧合）；
- 判据「窗口内每一天都 complete」在 UTC 日边界上做区间比较最简单：
  `[start, end)` 覆盖的 UTC 日集合是可直接枚举的。

⚠ **代价**：查询窗口若从本地 00:00 开始，会跨越两个 UTC 日 ⇒ 需要两天都 complete。
这是**正确的保守行为**（宁可多判一天），不是缺陷。

**不要**用本地日 + 假定 86400 秒 —— 一旦将来部署到有 DST 的时区，
那天是 23 或 25 小时，判据会静默错位。

### 4.2 `covered_until` —— 回填的水位线

```
state = complete  当且仅当  rows_written >= buckets 且 covered_until >= 该天 24:00（UTC）
state = partial   其它有行的情况
state = missing   （无此行）
```

**为什么必须有 `covered_until` 而不是只用 `buckets`：**

回填是**分天、分批**推进的。若某天回填到一半崩了，用 `covered_until` 记录写到哪一刻；
若 `buckets` 是**边写边数**的（数到哪写到哪），两者会相等，**缺的那半天被判 complete**。

⇒ `buckets` 必须在**该天开始回填前一次性数完**，
`covered_until` 在**该天写完时**置为该天末尾。两者配合才能表达「这一天的全部已知桶都写了」。

### 4.3 写后校验（`rows_written` / `verified_at`）

回填单天完成后、置 `state='complete'` 之前，做一次：

```sql
SELECT count(*) FROM telemetry_rollup_1m
WHERE device_id = ? AND bucket >= day_start AND bucket < day_end
```

要求 `>= buckets` 且不缺桶。不满足 ⇒ 置 partial 并记录实际值，**绝不置 complete**。

这条的成本是每设备每天一次索引范围 count（1,440 行），可忽略；
收益是**把「状态表说成功但数据没写完」从静默失败变成可查的数字**。

### 4.4 「完整」的精确含义 —— 与 unified_data 逐分钟一致，不是物理满桶

这一条最容易误解，必须写进代码注释：

> **L1 写门控后 `unified_data` 本身是稀疏的**：某个物理量值不变就不写。
> 如果某一分钟**所有**物理量都没变化，`unified_data` 里根本没有那一分钟的行。
>
> ⇒ **rollup 也不会有那个桶，而且这是正确的。**
> ⇒ 覆盖率判据的目标是「rollup 与 unified_data 逐分钟一致」，
>    **不是**「物理上每一分钟都有桶」。

如果反过来要求物理满桶，就会被迫在 rollup 里造出 unified_data 里不存在的桶
（比如线性插值），那才是把历史伪造成现状 —— 和 task-19 列表端点必须用 as-of 语义是同一个原则。

## 5. 查询时的判据（O(天数)，不扫数据）

```
给定 [start, end)：
  days := 枚举 [start, end) 覆盖的所有 UTC 日
  rows := SELECT * FROM telemetry_rollup_coverage
          WHERE device_id = ? AND day = ANY(days)

  若 len(rows) < len(days)                      ⇒ 回落（某天 missing）
  若 任一 row.state != 'complete'                ⇒ 回落
  若 start 落在最前一天的 covered_until 之后       ⇒ 回落
  ⇒ 否则 handled = true，读 rollup
```

7 天窗口 = 7 行查询。30 天 = 30 行。**与窗口内数据量无关。**

## 6. 三个边界情形

### 6.1 窗口尾部还在实时写入（今天/最近几小时）

实时 `RollupCollector` 每分钟在写当前桶，但**回填不会跑今天**（数据还在变）。
所以今天的 coverage 行要么 missing，要么 partial（如果回填跑到今天为止）。

⇒ **包含今天的窗口一律回落**。这是正确的（今天的数据本来就应该走 unified_data 的精确路径），
但如果用户在 7d 视图里每次都碰到回落，就失去了优化的意义。

**建议**：判据里把「窗口尾部的实时段」单独处理 —— 但**我建议 task-22 先不做**
（先做保守版：含今天即回落），因为它本身是一个独立风险点，值得单独验证。

### 6.2 回填重跑

`upsertRollupRow` 是 `ON CONFLICT DO UPDATE`，天然幂等 ⇒ 重跑安全。
coverage 行也应当是 upsert，且**重跑后必须重新校验**（`rows_written` / `verified_at` 更新）。

⚠ 若某次重跑发现 `rows_written > buckets`（rollup 里有 unified_data 里没有的桶），
先别当异常 —— 实时 collector 与回填在时间边界上重叠是**正常现象**。
所以校验判据是 `rows_written >= buckets` 且「缺的桶为 0」，不是严格相等。

### 6.3 设备是后来新增的

coverage 行只对「回填时存在且有数据的 (device, day)」写。
新设备的历史窗口查不到 coverage 行 ⇒ missing ⇒ 回落 ⇒ 正确。

---

## 7. 回填顺序建议

**按天推进、从最近往前**（不是从最早往后）。理由：

- 用户最常看的是最近 7d / 30d ⇒ 先让近期 complete，收益出现得早；
- 老的（36 天前）本来就快超出保留期，优先级低；
- 出问题时影响的是「最老的那几天」，用户感知最小。

## 8. 实测数据（本次验证产出，供 task-22 估算用）

### 8.1 单桶 payload 体积（真实编码 `EncodeRollupPayloadV1`）

| 设备 | 字段数 | payload 字节 | 说明 |
|---|---:|---:|---|
| 14 | 29 | **1,503 B** | 生产实测公式 `3 + Σ(38 + len(name))` |
| 15 | 42 | **2,201 B** | 同上 |

### 8.2 PG 实际存储（含 TOAST）

隔离 bench 实测（`bytea` 列 + `(device_id, bucket)` 主键，用真实编码的 payload）：

| 设备 | 行数 | payload | 存储后行大小 | 备注 |
|---|---:|---:|---:|---|
| 14 | 1,440 | 1,453 B | **1,512 B** | 未触发 TOAST |
| 15 | 720 | 2,145 B | **2,200 B** | **触发了 TOAST** |

⚠ **42 字段设备的 payload（2,201 B）跨过了 PG 的 TOAST 阈值（约 2,032 B / 行）**，
于是被搬到 TOAST 表外联存储：实测 TOAST 表 1,920 kB + 主表 2,304 kB，
合计每行约 **2.0 KB**（比 inline 多一份指针与外联开销），读取时每条多一次 TOAST 抓取。

⇒ **task-22 若要压体积，v2（slot 量化）的收益不只是「小一点」，
而是「把 42 字段设备从 TOAST 里捞回 inline」** —— 单这一项就能省掉一次额外的磁盘寻道。

### 8.3 全量规模估算

生产 36 天 × 5 设备 × 1,440 桶/天 ≈ **259,200 行**。
按每行约 1.8 KB（29/42 字段设备混合）估算 ⇒ **约 466 MB**，
与 task-22 里「~500 MB」的估算一致。

### 8.4 聚合成本（回填单天）

在 1,276 万行真实数据上跑「每 (device, field, minute) 的 avg/min/max/last/count」：

```
1 天数据（2026-11-03）→ 102,240 行 (device, field, minute) 聚合结果
耗时 1,996 ms
```

⇒ 36 天全量回填的**纯聚合**时间约 72 秒（不含写 rollup）。
**这不是瓶颈**，瓶颈在写 259,200 行（每行约 2 KB ⇒ 466 MB 写入）。

## 9. 给 task-22 的五条落地要求（可当作验收判据）

1. **`buckets` 必须在该天开始回填前一次性数完**，不能边写边数（否则 §4.2 的缺口被掩盖）。
2. **`state='complete'` 之前必须做写后校验**，且校验数是**查 rollup 表本身**，不是内存计数器。
3. **校验判据用 `>= buckets` 且「缺的桶为 0」**，不是严格相等（实时 collector 重叠是正常的）。
4. **`day` 用 UTC**，并把「窗口跨 2 个 UTC 日就要 2 天都 complete」写成明确行为（不是 bug）。
5. **查询判据不得读 `unified_data`** —— 这是本方案存在的全部理由。

### 9.1 第 5 条可以写成一条真正的门禁

**PG 用例**：建 coverage 表 + rollup 表 → **`DROP TABLE unified_data`** → 调判据函数 →
断言 `handled` 结果正确。

这条用例的意义不是「测函数」，而是**把「判据不依赖将被删除的表」这个设计约束钉成可执行的**。
删掉 `unified_data` 这个动作，正是将来真实会发生的事 —— 用例直接模拟它。

## 10. 与 impl-l2 实际实现的对照（2026-11-07 17:25 观察）

写完本文时发现 impl-l2 已在 `backend/internal/datalifecycle/rollup_coverage.go` 落地了一版。
对照如下，**结论：他的方案在本节列出的关键不变式成立时，等价且更简单**；本文多出的三列
只在「无法保证不变式」时才需要。

| 本文提案 | impl-l2 实现 | 评价 |
|---|---|---|
| `covered_until` | 无，用 `state='partial'` 表达「开始过没跑完」 | **等价**，前提见 §10.1 |
| `rows_written` / `verified_at` | 无 | 见 §10.2 |
| `state: complete/partial/missing` | 同，且**多区分了「行不存在」** | **他的更好**，见 §10.3 |
| `day` 用 date | 用定长 `YYYY-MM-DD` 文本 | **他的更好**，见 §10.4 |

### 10.1 `partial` 能替代 `covered_until` 的唯一前提

`covered_until` 解决的是「某天回填到一半崩了，但状态已是 complete」⇒ 假绿。
`partial` 用「开始时先写 partial、成功后才写 complete」达到同样效果，**但必须满足：**

> **不变式：回填某天之前，必须先 `MarkRollupCoverage(..., state=partial)`；
> 只有该天全部写完且写后校验通过，才升为 `complete`。**

若反过来（只在成功时写 complete，中间不写 partial）也安全 —— 因为崩溃时行仍是上一次的
状态或不存在，窗口判据会回落。**唯一危险的是「写完桶 A 就 Mark complete，再继续写桶 B」**：
那一刻状态说 complete 但数据只有一半，而窗口判据只看状态 ⇒ 假绿。

⇒ **建议 task-22 在 `MarkRollupCoverage` 上写明这条不变式**，并加一条用例：
「Mark complete 之后不得再写该天的桶」，或者在回填循环里断言这一点。

### 10.2 `rows_written` / `verified_at` 只在「buckets 边写边数」时才必要

本文加这两列，是因为我担心 `buckets` 是增量数出来的（数到哪写到哪），
那样 `buckets` 与真实写入量天然相等，缺的半天看不出来。

**如果 impl-l2 的 `buckets` 是「该天开始前一次性 `count(distinct date_trunc('minute',...))` 数完」，
那这两列可以不加** —— 因为 `buckets` 是**独立于写入过程**的外部事实。

⇒ 请在 `buckets` 的赋值处写明它是**写之前一次性数完**的（他的注释已写「实际数出来的」，
但没写「什么时候数的」）。**这是一个代码注释就能消掉的风险，比加两列划算。**

### 10.3 他多出来的「行不存在 ≠ missing」是本文漏掉的好设计

本文 §4.4 只说了「完整」的语义，没区分：

- 设备 A 从 11-03 才开始上报，11-01 它**确实没有数据** ⇒ `missing`，可信结论；
- 设备 B 的历史回填**还没跑到** 11-01 ⇒ 那一行**不存在**，是未知。

两者在库里都是「查不到行」，但一个是结论、一个是未知。混同会让未回填窗口被当成
「这几天本来就没数据」而返回**空图** —— 比回落更糟，因为用户以为数据丢了。

**本文采纳他的设计，撤回「只用 buckets 表达」的隐含简化。**

### 10.4 `day` 用文本不用 date：他的理由比本文的时区论证更实际

本文 §4.1 论证了要用 UTC 日。他进一步指出：SQLite 没有真 date 类型，AutoMigrate 会退化成
TEXT/datetime，而 PG 的 date 与字符串比较走隐式转换 ⇒ **同一份判据代码在两方言上可能判定不同**。
定长 `YYYY-MM-DD` 文本两方言逐位相同 ⇒ **判据逻辑能在 SQLite 上测**，不必等 PG 环境。

⇒ 本文 §4.1 的 UTC 结论保留，实现方式采纳他的（文本）。

### 10.5 一条仍然存在的缺口（两边都没有）

**窗口尾部实时段**（§6.1）：`RollupCollector` 正在写的当前桶，回填永远追不上。
他当前的 `RollupWindowCovered` 对「今天」这一天，若回填跑过且置 complete，
则今天剩余尚未发生的分钟也算「覆盖」了 —— 这在**过去**的日期上正确，在**今天**上不成立。

⇒ 建议读路径对 `to > now - liveLag` 的窗口一律回落（先做保守版），
liveLag 取 collector 落盘延迟上界（实测约 60~90s）。这条本文 §6.1 已提，
**是最可能在生产上表现为「最近一小时图表偶发空洞」的地方**，值得单独一条用例。
