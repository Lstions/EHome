# 风险授权删除与「分级 + 确认」简化方案

> 状态：**已实施** · 2026-11-18（同日发布）
> 输入：`docs/分析/风险授权-只读代码分析与简化建议-2026-11-18.md` + 本次核验
> 用户要求：风险授权是多余设计；设备操作简单分等级；风险操作一个干净弹窗确认即可。

## 0. 结论

你的要求可以一句话落地：**只保留「分级」和「弹窗确认」两层，删掉「规则级持久授权」整层。**

但有一个前提必须同时改：删掉授权旁路后，**自动执行路径不能再被确认门拦住**，否则高风险动作的自动执行会 100% 失败（这正是当初 C5 要消除的静默失败）。所以「删授权」和「system 路径直接执行」必须同一版发布。

另外本次核验确认了一个**线上可触发的保存死循环**（编辑风险动作参数必 400、前端无恢复分支），删除授权层会顺带根治它。

## 1. 现有其实是 4 层，不是 1 个开关

| 层 | 回答什么 | 载体 | 处置 |
|---|---|---|---|
| L1 分级 | 这个动作危不危险 | `deviceaction.RiskLevel`（normal/elevated） | **保留**，对外只留 `risk_level` + `risk_reason` |
| L2 弹窗 | 人点下去之前知不知情 | 设备页 `ActionConfirmationDialog`；规则页逐项勾选弹窗 | 设备页**不动**；规则页换成**一次确认** |
| L3 一次性令牌 | 这次点击能否被重放 | `commandexec/confirmation.go`，5 分钟、单次、绑 actor+设备+动作版本+参数哈希 | **建议保留**（用户不可见）；是否也删见 §7 决策 1 |
| **L4 规则级持久授权** | 这条规则「曾经」被谁确认过 | `automation_rules.risk_acknowledged_at` + `risk_acknowledged` 请求字段 + V7 + 执行期旁路 | **整层删除** |

## 2. 删除 L4 后的目标语义（用户能一句话说清）

```text
动作危不危险        → risk_level: normal | elevated      （只影响界面：徽标 / 确认弹窗）
规则触发后要不要先问我 → require_confirmed: false | true   （只影响自动执行方式）
```

### 执行矩阵

| 发起方 | `require_confirmed=false` | `require_confirmed=true` |
|---|---|---|
| 自动（system） | **直接执行**（不再看授权、不要令牌） | `pending_confirm` → 人确认 → 即铸即销令牌 → 执行 |
| 设备页 / 手动触发（user） | 弹窗 → 令牌 → 执行（**不变**） | 同左（**不变**） |
| 确认执行（user） | — | 令牌 → 执行（**不变**） |

一句话：**风险等级只决定「要不要弹窗提示」，`require_confirmed` 才决定「无人时要不要等人」。**

## 4. 必须一起做的三件事（否则会坏）

1. **system 路径不再看授权**：`commandexec` 确认门改成「风险动作且非 system 才要令牌」。漏了这条 ⇒ 自动执行高风险动作永远 `confirmation_required`。
2. **前端提交体删字段**：`risk_acknowledged` 不再发送；后端删字段后即使收到也会被忽略，但契约要一次收干净。
3. **DB 列的下线时序**：见 §7 决策 3（同版 DROP 还是留一版）。

## 5. 顺带修掉的线上缺陷（P0）

现状：编辑含风险动作的规则并改参数 → 前端预检返回风险清单 → 用户勾选后提交 `risk_acknowledged=true` → 后端发现动作集合变了 → 400 `action_changed_requires_reconfirmation` → 前端**没有该错误码分支**（已核验：`grep action_changed frontend-shared/src` 为空）→ 弹窗不关、重试仍 400 ⇒ **该规则无法通过 UI 保存**，而旧动作继续自动执行。

删除 L4 后该错误码与整条冲突判定一起消失，死循环自然根治。**不需要单独的止血版本**（若你想先止血再简化，最小修法是：`ack` 对「本次提交的动作集合」生效，即保存成功后写新时间戳，而不是 400）。

## 7. 需要你拍板的 4 件事

1. **L3 一次性令牌要不要也删？**
   - 保留（推荐）：用户可见的仍然只是一个弹窗；后端多一层防重放/幂等/限流，且 TOCTOU（确认与执行之间参数被改）有哈希兜底。
   - 删：设备操作 API 变成 `POST operations {confirmed: true}`，少一次 `/confirm` 往返；代价是重放防护只剩 idempotency key，且参数 TOCTOU 失去兜底。
2. **`require_confirmed` 保留吗？** 建议保留——它是自动化唯一的「无人值守时要不要先问我」开关；删了就只能二选一（要么全自动、要么全人工）。
3. **`risk_acknowledged_at` 列何时 DROP？**
   - 同版 DROP（干净，符合「不写兼容代码」）：一旦回滚旧镜像，旧代码 SELECT 该列会报错 ⇒ **回滚只能前进修复**。
   - 留一版再 DROP（可回滚）：本次只停止读写，下一版删列；代码零兼容，只是迁移分两步。
   我建议**留一版**：这次改动面已经不小，保留一次可回滚窗口更稳；下一版删列只是一条已写好的迁移。
   
   **最终裁决（2026-11-18 当天）**：用户裁定**同版删除** —— 启动迁移 `MigrateAutomationRuleDropRiskAcknowledged` 随本次发布执行，回滚窗口关闭（旧镜像 SELECT 该列会报错，回滚只能前进修复）。
4. **（可选）保存含风险动作的规则要不要要求 `system_admin`？** 这才是「真正的授权」：当前任何登录用户都能保存一条会自动执行风险动作的规则。单主体部署可忽略；要做就是 1 个分支 + 1 个用例。

## 8. 验收标准

- 新建/编辑含风险动作的规则：**一次弹窗**（列出动作+设备）→ 保存成功，请求体不含 `risk_acknowledged`。
- 修改风险动作参数：能保存（死循环消失）。
- 自动路径 `require_confirmed=false` + 风险动作：真机执行成功，事件 `executed`，**不再出现** `confirmation_required`。
- 自动路径 `require_confirmed=true`：仍落 `pending_confirm`，确认后执行。
- 设备页风险动作：弹窗与令牌链路行为不变（回归用例守住）。
- 动作目录 JSON 只剩 `risk_level` / `requires_confirmation` / `risk_reason`（`risk` 不再下发）。
- 存量 `confirmation_required` 事件仍能在事件表正常显示。

## 9. 诚实的取舍（删了会失去什么）

| 失去 | 影响 | 替代 |
|---|---|---|
| 动作被上调为 elevated 后，旧规则不再被拦 | 历史规则照常自动执行（即使动作刚变危险） | 若在意，做独立的「风险等级变更检测」，而不是让时间戳兼职 |
| 「保存时刻」这条证据 | 规则表不再记录谁在何时确认 | 需要就写 `security_audit_events`（现在保存本就不写审计） |
| 多用户下的「授权」语义 | 任何登录用户都能让规则自动执行风险动作 | 决策 4 的 `system_admin` 校验 |
