# 决策：3.0 链路的 ConfigManifest 应用所有权（2026-10-07，task-35）

## 1. 问题（现象 + 证据）

**3.0 链路收到 ConfigManifest 后，消息到达、被分发，然后什么都不发生。**

证据（两个独立日志、两个判据，均已复核）：
```
  measure2.log  : 3.0 送 6 次 → 6 次全无回响 | MQTT 送 2 次 → 2 次都有回响
  s3p-fixed.log : 3.0 送 4 次 → 4 次全无回响 | MQTT 送 1 次 → 有回响
```
代码侧：`grep handle_config_applied main/device_link_wiring.c` ⇒ **0**。

**为什么比内存门禁更严重**：内存门禁至少会回 `ConfigResult success=0`（服务端看得见、可重试）；
这条是**连失败都收不到**。而 §7.3 P3（MQTT 退役）后，3.0 是**唯一**的路。

## 2. 根因：**同一语义有两份定义**（P4 + P1）

现在"下行消息到达后做什么"被写了两遍：
```
  on_mqtt_msg_cb(data,len,ctx)          on_transport_msg_cb(data,len,ctx)
    is_config_manifest(data,len)          is_config_manifest(data,len)
    msg_handler_process(data,len)         msg_handler_process_with_transport(...)
    if (is_cfg) handle_config_applied()   if (is_cfg) handle_config_applied()

  devlink_on_msg(m, ctx)                ← 3.0 链路
    devlink_rx_handle(..., msg_handler_process, ...)   ← **只有第 2 步**
    （没有 is_config_manifest、没有 handle_config_applied）
```
而 `MSG_CONFIG_MFST` 在 `msg_handler` 分发表里指向的
`handler_config_process_manifest()` **是一句 no-op**（`handler_config.c:28-34` 自己写明）：
> "This function is now a no-op — the actual manifest parse, ConfigResult,
>  and bus rebuild all happen in `handle_config_applied`"

⇒ 于是：**`msg_handler` 的分发表说"我不管"，而真正管的 `handle_config_applied` 只有两个传输回调会调。**
⇒ 3.0 落在两者之间的缝里。**这是 P1（接口表达不了"谁负责应用"）与 P4（同一语义两份定义）的合体。**

## 3. 候选评估

### 候选 A：把"应用"做成 `msg_handler` 的钩子 —— **否掉**
理由：`msg_handler` 是**组件**，而 `handle_config_applied` 在 `main` 且需要 `app_state_t *`
（配置事务、NVS、bus 重建、sync 上报都在 main 侧）。
做成钩子需要把 `app_state` 穿过组件边界 ⇒ 组件依赖 main 的数据结构，
**与既有分层相反**（本仓既有钩子 `ehome_mem_can_start` 是"纯判定"，不持有 main 状态）。
⚠ 而且它**没有**解决 P4：分发表仍会保留一个 no-op 分支，"谁负责应用"依然是隐式的。

### 候选 B：让 3.0 走 `on_transport_msg_cb` —— **否掉**
理由：`on_transport_msg_cb` 是 **debug TCP（`CONFIG_DEBUG_TCP_ENABLED`）** 的路径，
它调 `msg_handler_process_with_transport(data,len,s->tcp_transport)`，
语义是"这条消息**从哪个 transport 来的**，回执走它"。
而 3.0 会话**已经**注册成一条 transport（`session_transport.c:316`），
若再让 devlink 直接调 `on_transport_msg_cb`，**同一条会话会被登记两次**，
且 `s->tcp_transport` 与 3.0 的 session transport **是两个不同对象** ⇒ 回执可能走错路。
⇒ 风险高于收益，且 debug TCP 路径本身不是交付特性。

### 候选 C：把 no-op 的 `handler_config_process_manifest` 真正实现 —— **否掉**
理由：当初搬到 `app_callbacks` 的注释写明是为 **TOCTOU 竞态**
（manifest 解析的 clear+rebuild 与并发 StatusReport 读之间）——
搬回来会**重新引入那个竞态**，而它是本仓已修复的缺陷。

### ✅ 候选 D（采纳）：**抽出唯一入口 `ehome_handle_downlink()`，三条路径都调它**

在 `app_callbacks.c` 里定义一个**具名函数**，它是"下行消息该怎么办"的**唯一**定义：
```c
/* 下行消息的**唯一**处理入口（P4）：三条传输路径都调它，不再各写一遍。
 * 返回是否被当作 ConfigManifest 处理（供调用方决定是否要额外动作）。*/
bool ehome_handle_downlink(const uint8_t *data, size_t len,
                           bool have_transport, transport_t *t);
```
内部三步（**与现有两个回调逐行等价**）：
```
  ① bool is_cfg = is_config_manifest(data, len);
     if (is_cfg) app_state_get()->config_received = true;
  ② have_transport ? msg_handler_process_with_transport(...) : msg_handler_process(...);
  ③ if (is_cfg) handle_config_applied(app_state_get(), data, len);
```
然后：
- `on_mqtt_msg_cb` → 调它（`have_transport=false`）；
- `on_transport_msg_cb` → 调它（`have_transport=true, s->tcp_transport`）；
- **`devlink_on_msg` → 调它**（`have_transport=false`；3.0 自己的回执由 session transport 承担）。

**为什么这是对的**：
1. **P4**：`is_config_manifest`+dispatch+apply 只写一遍，三条路径**不可能再漂移**；
2. **P1**：接口名字就说明"这是下行消息入口"，不再有"分发表说不管、回调偷偷管"的缝；
3. **零新增依赖**：`ehome_handle_downlink` 在 `main`，`devlink_on_msg` 也在 `main`，直接调用；
4. **不碰 `msg_handler` 的 no-op 分支**（保留它，但它不再是"唯一入口"的暗示，注释会写明）。

⚠ **一处必须注意**：`handle_config_applied` 内做配置事务（较重），
而 3.0 的 `devlink_on_msg` **跑在 devlink 任务栈上**（实测峰值 4168 B / 栈 6144）。
⇒ 必须确认配置事务**不会超出该栈**。**证据**：MQTT 路径下它在 mqtt 回调任务里跑，
   而配置事务的实测栈用量未单独测过 ⇒ **这是本决策的唯一硬前提，必须实测**（见 §4）。

## 4. 验收判据（必须是"应用了"，不是"到达了"）

1. **3.0 送达 0x04 后出现 `CALLBACK` 与 `ConfigResult`**（与 MQTT 同款回执）；
   若因内存门禁被拒，也必须出现 `ConfigResult success=0`（那才证明**真的走了应用路径**）；
2. **MQTT 路径回归**：不得被破坏（同样出现 ConfigResult）；
3. `devlink` 栈峰值**实测**不因配置事务而逼近上限（本卡已知：栈 6144、峰值 4168）；
4. 宿主 ctest 全过；新增判据须能咬（附变异自证）。

## 5. 什么条件下该重开这个决定

1. **若配置事务超出 devlink 栈**（判据 3 失败）⇒ 改走"投递到专门任务"的方案，
   即把应用动作**异步化**（本决策**不**默认异步：那会引入新任务与新内存，属更大改动）；
2. 若将来 `msg_handler` 真的需要持有 main 状态（候选 A 的收益变大）⇒ 重新评估钩子方案；
3. 若 debug TCP 路径要变成交付特性 ⇒ 候选 B 需重新评估。

## 6. 与内存卡的关系

本决策**只**解决"应用所有权"。**推理**：门禁能否通过取决于**读数的时刻**（§154）
与 `largest` 是否 ≥ floor（§156 已实证 READY 后为 17408）。
两者独立 ⇒ **修好本卡后，配置才会真正走到门禁那一步**，届时用 §156 的结论判断。
