# ESP32 + 后端 3.0：接口与模块设计（2026-10-06）

> **定位**：本文是 [ESP32-3.0-重构方案](ESP32-3.0-重构方案-2026-10-06.md) 的**设计细化篇**。
> 那份讲"做什么"（TCP+TLS、去 protobuf、消息重组、100 Hz）；
> 本文讲"**怎么组织结构**"——接口怎么定、模块怎么分、内存与效率怎么保证。
>
> **用户要求**："接口设计、类设计不合理的、不规范的都一起重构了，
> 目标是设计良好的同时内存占用也合理，处理高效，**后端也是**"。

---

## 0. 本文的原则：每条都由**真实事故**反推，不是通用最佳实践

项目已有的教训（都可在 git log / docs 中查到）证明这些不是"洁癖"：

| # | 事故 | 根因（设计层） | 由此确立的原则 |
|---|---|---|---|
| 1 | **L-02** 同一帧发布两次（PF/NT=1.998，实测 3,873 条 "Publish failed"） | `transport_ops.send()` 只返回 `esp_err_t`，**无法区分"本地未连接"与"对端失败"**；调用方只好在广播后再"回退重发" | **P1 接口返回值必须能表达调用方的决策分支** |
| 2 | **R1** 超限 Manifest 永远下发失败，而后端只看到"发布成功" | 编码长度与传输上限之间**没有契约检查点** | **P2 端到端契约必须在发出前可验证** |
| 3 | **DataEventBus 静默丢弃**（≥400 报/s 开始丢，实测 500 报/s 丢 1,206） | `Publish()` 满时丢最旧；`DroppedCount()` **存在但从未暴露为指标/告警** | **P3 无静默丢弃：要么背压，要么可观测** |
| 4 | **诊断口径污染**（9 文件用裸 `MALLOC_CAP_8BIT`，s3p 上打 8.25 MB 而门禁看 23 KiB） | 同一语义（"还剩多少内存"）在 9 处**各写一遍**，无单一来源 | **P4 语义只有一处定义** |
| 5 | **PSRAM 门禁恒放行**（`MALLOC_CAP_8BIT` 跨堆取最大） | 判据与实现**各自独立解释**同一个概念 | **P4**（同上） |
| 6 | **内存门禁余量仅 16 B**，下一次提交必然变红 | 阈值是**手抄常量**，与实测值无绑定 | **P5 预算/阈值必须由单一来源派生并可自证** |
| 7 | **IRAM "100% 满"假警报**：工具口径错导致一条不存在的阻塞项 | 判据读的是**工具的二手结论**而非链接器事实 | **P6 判据必须读一手事实** |
| 8 | 我两次把"现场配置"当成"物理上限"（100 Hz / BLE+TLS） | 结论**未标注它依赖的配置前提** | **P7 数字必须带口径与前提** |

**七条原则**（后文所有设计都引用它们）：

- **P1 接口返回值必须能表达调用方的决策分支** —— 调用方不该为了决策再去"查一次状态"。
- **P2 端到端契约必须在发出前可验证** —— 不能靠"发出去了=成功了"。
- **P3 无静默丢弃**：每条丢弃路径必须有 计数器 + 指标 + 告警阈值，三者缺一不可。
- **P4 语义只有一处定义** —— 同一概念在多处各写一遍 ⇒ 必然分叉。
- **P5 预算与阈值由单一来源派生，且可自证**（变异测试能证明它会红）。
- **P6 判据读一手事实**（链接器 map、实测字节数），不读工具的二手中间结论。
- **P7 每个数字带口径与前提** —— "在 X 配置下测得"，不是"系统的极限"。

## 1. ESP32 端接口与模块设计

### 1.1 现状体检（实测数据，非印象）

| 指标 | 现状 | 判断 |
|---|---:|---|
| 固件总行数 | 26,947（components + main） | 规模可控 |
| **全局可变静态 `s_*`** | **282 个** | **严重**：状态无封装、跨模块可直接改、难测试 |
| 其中 `bus_worker` | 55 | 最重 |
| 其中 `main` | 36 | 启动流程与业务混杂 |
| `msg_handler` | 30 | 协议收发与业务处理混杂 |
| 最大实现文件 | `bus_worker.c` **2,285 行** / `bus_dma.c` **2,075 行** / `bus_manager.c` **1,270 行** | **过大**：单一职责被破坏 |
| 最大接口 | `msg_handler_internal.h` **365 行** / `bus_dma.h` 291 行 | **过大**：暴露内部细节 |
| 公开可变结构体 | `transport_t`、`dma_pool` | **严重**：外部可直接改写状态 |

### 1.2 传输层重设计（替换 `transport.h`）

**现状的问题**（`components/transport/include/transport.h`）：

```c
/* 现状 —— 三个设计缺陷 */
typedef struct transport {          /* 缺陷②：公开可变，state 可被外部改写 */
    const transport_ops_t *ops;
    transport_type_t type;
    transport_state_t state;        /* 与真实状态可失步 */
    ...
    void *priv_data;                /* 缺陷③：无类型 void* */
} transport_t;

struct transport_ops {
    esp_err_t (*send)(transport_t *, const uint8_t *, size_t);  /* 缺陷①：语义不足 */
    bool (*is_connected)(transport_t *);   /* 调用方须"先查再发" = TOCTOU */
    ...
};

esp_err_t transport_broadcast(const uint8_t *, size_t);  /* 缺陷④：上行不该广播 */
```

**缺陷①导致的真实后果**：`send()` 返回 `ESP_FAIL` 时，调用方无法知道
"是本地没连上（不该重试）"还是"对端拒了（可重试）"，于是
`msg_handler_publish_checked()` 在 `transport_broadcast()` 已经发过一次之后
**又发一次** ⇒ L-02。

**3.0 设计**（`link.h`，替换 `transport`）：

```c
/* ---- 3.0：单一上行链路，语义自足 ---- */

/* P1：发送结果必须携带调用方决策所需的一切 */
typedef enum {
    LINK_SENT,            /* 已交给链路层并计入账（可能仍在缓冲） */
    LINK_NOT_READY,       /* 链路未就绪：调用方【不应】换路重试，应降级/入队 */
    LINK_BACKPRESSURE,    /* 缓冲满：调用方【应】稍后重试（不是错误） */
    LINK_PAYLOAD_TOO_BIG, /* 超出协商的 MTU/重组上限：调用方【必须】分片或拒绝 */
    LINK_FATAL,           /* 链路已判定不可用：调用方【应】通知上层重建 */
} link_result_t;

typedef struct link link_t;   /* P3：opaque —— 外部【不能】读写字段 */

/* 唯一的上行入口。P1：不做"先查再发"，结果即决策依据。 */
link_result_t link_send(link_t *l, const uint8_t *frame, size_t len);

/* 只读观测（诊断用），不参与决策 */
typedef struct {
    bool     ready;
    uint32_t mtu;             /* 对端可接受的最大单帧（重组上限） */
    uint32_t tx_queued;
    uint32_t tx_dropped;      /* P3：必须可观测 */
    uint32_t reconnects;
} link_stats_t;
void link_get_stats(const link_t *l, link_stats_t *out);
```

**关键设计点（逐条对应原则）**：
1. **`LINK_BACKPRESSURE` 是独立结果，不是错误** —— 让调用方能区分"该退避"与"该报错"（P1）。
2. **`mtu` 由链路层提供**，编码层据此决定是否分片 ⇒ **P2 的契约检查点**（R1 的根治）。
3. **opaque handle**：`link_t` 不暴露字段；状态迁移只发生在 `link.c` 内部（P4）。
4. **取消 `broadcast`**：上行是"选一条路发"。下行（服务端→多个消费者）
   才需要分发，且那是**另一个接口**（`sink_t`，见 1.5）。
5. **无 `void* priv_data`**：`link_t` 内部组合具体实现（见下）。

**实现方式：接口 + 组合，而非继承式 ops 表**：

``c
/* link.c 内部：唯一持有状态的地方 */
struct link {
    const link_driver_t *drv;      /* 具体驱动（tcp_tls / 未来其它） */
    void *drv_ctx;                  /* 类型安全：只在本文件内转换 */
    link_state_t state;             /* 私有：外部看不见 */
    link_stats_t stats;
};

/* 驱动接口保持最小：4 个函数，语义自足 */
typedef struct {
    esp_err_t (*open)(void *ctx);
    void      (*close)(void *ctx);
    link_result_t (*send)(void *ctx, const uint8_t *f, size_t n);  /* 同样返回 link_result_t */
    uint32_t  (*mtu)(void *ctx);
} link_driver_t;
```

隔离了 esp-mqtt / esp-tls 的平台差异，同时**测试可注入假驱动**（P7 可测试性）。

### 1.3 消息层：去 protobuf + 重组

**现状**：`frame_codec.h` 手写 protobuf-wire-style TLV（首字节=类型、无长度前缀、varint）；
`MSG_*` 编号在 `frame_codec.h`，而**各消息的解析逻辑分散在 `msg_handler/` 组件的 8 个 `handler_*.c` 里**
（合计 3,521 行，单个最大 `handler_periph.c` 633 行）。
**问题不是单文件过大，而是「协议知识」被复制到多个文件**：每个 handler 自己拆字段、
自己判 wire type ⇒ 同一字段的宽度/顺序在多处重复定义（违反 P4）。

**设计**：三层分离，每层单一职责

```
wire (字节)  ←→  frame (定界/校验)  ←→  message (语义结构)
```

1. **`wire.h`：定界与重组（P2）**
```c
/* 重组器：唯一负责"把字节流切成帧"的地方 */
typedef struct reassembler reassembler_t;
reassembler_t *reasm_create(uint32_t max_msg_bytes);   /* 上界显式（P5） */
/* 返回值表达进度，调用方无需猜测（P1） */
typedef enum { REASM_NEED_MORE, REASM_FRAME_READY, REASM_ERROR_TOO_LARGE, REASM_ERROR_MALFORMED } reasm_result_t;
reasm_result_t reasm_push(reassembler_t *, const uint8_t *in, size_t n,
                          const uint8_t **frame_out, size_t *frame_len_out);
void reasm_destroy(reassembler_t *);
```
- **`max_msg_bytes` 是构造参数**，不是散落常量 ⇒ P4/P5；
- 超限返回 **`ERROR_TOO_LARGE` 而不是截断**（P3：不静默）；
- 内存上界 = `max_msg_bytes` + 重组器自身，**可静态核算**（P5）。

2. **`msg.h`：消息编解码（纯函数，可脱离硬件测试）**
```c
/* 编解码是纯函数：无全局状态、无硬件依赖 ⇒ 宿主机全量可测（P7） */
size_t msg_encode_data(encoder_t *, const data_msg_t *, uint8_t *out, size_t cap);
/* P1：返回值区分"放不下"与"参数错" */
typedef enum { ENC_OK, ENC_NO_SPACE, ENC_BAD_ARG } enc_result_t;
enc_result_t msg_decode_data(const uint8_t *f, size_t n, data_msg_t *out);
```

3. **`dispatch.h`：分派（表驱动，替代分散在 8 个 `handler_*.c` 里的分派逻辑）**
```c
typedef struct { uint8_t type; handler_fn fn; const char *name; } msg_route_t;
/* 路由表是数据，不是代码 ⇒ 新增消息类型 = 加一行，不改控制流 */
```
后端的 `nodemgr/manager.go:380` 已用**表驱动**（~20 个 `case frame.Msg*`），
这是**正确的做法，应移植到固件侧**；两侧共用同一张类型表 ⇒ 违反 P4 的风险再降一档。
表驱动后**未实现类型可自动生成告警**（P3：不静默）。

### 1.4 消除 282 个全局可变静态（P4）

**现状问题**：`s_xxx` 散在各文件顶层，谁都能改，测试无法隔离，初始化顺序靠隐式约定。

**设计：显式依赖注入 + 单例收敛**

```c
/* 3.0：每个模块只有【一个】实例句柄，由 main 创建并显式传递 */
typedef struct app app_t;                 /* opaque 的顶层组合根 */

/* 模块只暴露 create/destroy + 方法，不暴露静态状态 */
bus_worker_t *bus_worker_create(const bus_worker_cfg_t *cfg);
void          bus_worker_destroy(bus_worker_t *);

/* main.c 变成清晰的装配清单（composition root） */
app_t *app_create(void) {
    app_t *a = calloc(1, sizeof *a);
    a->net   = link_create(&tcp_tls_driver, &net_cfg);
    a->bus   = bus_worker_create(&(bus_worker_cfg_t){ .link = a->net, ... });
    a->cfg   = config_store_create(&cfg_cfg);
    /* …依赖显式可见，不再有隐式初始化顺序 */
    return a;
}
```

**收益**：① 依赖关系在 `app_create()` 一屏可见；② 每个模块可单独建实例做测试（P7）；
③ 生命周期明确（谁 create 谁 destroy）⇒ 消除"双释放/泄漏"类问题。

**代价（诚实）**：需要一次性改造，工作量大；建议**按模块增量迁移**，
先做 `transport`/`msg_handler`（事故最多、收益最大），其余跟随。

### 1.5 内存与效率设计（P5）

**原则**：**每块内存的归属与上界必须单一来源、可静态核算、可门禁验证。**

| 类别 | 现状 | 3.0 设计 |
|---|---|---|
| 栈上大缓冲 | `handler_data.c` 有 3 处 `uint8_t buf[1400]`（是 `report_tx` 栈紧的根因，hw=636 B） | **移出栈**：编码缓冲改为**每链路一份的 scratch**（构造时分配，大小 = `link.mtu`），栈深度可预测 |
| 缓冲上限 | `outbox.limit=4096` 等多处手写常量 | **由 MTU 派生**（P5）：`tx_queue_bytes = link.mtu * N`，N 是唯一可调旋钮 |
| 丢弃 | esp-mqtt 内部静默丢（L-02 根因 B） | **自有队列 + 显式返回 `LINK_BACKPRESSURE`**（P1/P3） |
| PSRAM | 8 MB 仅用 53.8 KiB（实测） | **主动放置策略**：大缓冲/TLS 会话 → PSRAM；必须内部的（BLE 协议栈、DMA、WiFi 驱动）留内部 |
| 静态 vs 堆 | 282 个静态 + 部分堆 | **实例化**（1.4）⇒ 大部分静态转为实例字段，可按需释放 |

**效率的三个具体点**：
1. **编码零拷贝**：`msg_encode_*` 直接写入链路 MTU 大小的常驻 scratch，
   避免"栈上 1400 B + memcpy"；
2. **重组零拷贝**：`reasm_push` 在内部环形缓冲上工作，`frame_out` 指向缓冲内（P2/P5），
   不做二次拷贝；
3. **分派用查表**：`msg_route_t` 数组取代长 switch，O(1) 且可静态校验完整性。

### 1.6 第二批具体缺陷（清单式，均已核实）

除了 transport，另一处高价值目标是 `bus_worker`（2,285 行 + 228 行接口）。

**缺陷 A：setter 式全局单例装配（违反 P4）**

```c
/* 现状：模块是隐式单例，依赖靠 setter 注入，且【没有】返回错误 */
void bus_worker_set_callbacks(write_rsp_cb_t, data_rpt_cb_t);   /* 无返回值 */
void bus_worker_set_channel_cmd_v2_final_cb(channel_cmd_v2_final_cb_t);
void bus_worker_set_data_batch_cb(data_batch_cb_t);
void bus_worker_start(bus_runtime_t *rt);                        /* 无返回值 */
```
问题：① "何时必须调用哪个 setter"是**隐式协议**，漏调一处就是运行期静默失效；
② `start` 无法报告失败（P1）；③ 无法建第二个实例做测试（P7）。

```c
/* 3.0：依赖在构造时显式给定，一次成型 */
typedef struct {
    bus_runtime_t *runtime;
    /* P1：回调合并为一个结构体，避免 8 个位置参数 */
    struct {
        void (*on_write_rsp)(void *ctx, const write_rsp_t *);
        void (*on_data_rpt)(void *ctx, const data_rpt_t *);
        void (*on_batch_ready)(void *ctx, const data_batch_t *);
        void *ctx;
    } cb;
} bus_worker_cfg_t;

/* P1：构造返回值表达失败原因 */
typedef enum { BW_OK, BW_ERR_NO_MEM, BW_ERR_BAD_CFG, BW_ERR_ALREADY_RUNNING } bw_result_t;
bw_result_t bus_worker_create(const bus_worker_cfg_t *cfg, bus_worker_t **out);
bw_result_t bus_worker_start(bus_worker_t *);
bw_result_t bus_worker_suspend(bus_worker_t *);   /* 与 start 同一套返回类型（一致性） */
void        bus_worker_destroy(bus_worker_t *);
```

**缺陷 B：诊断读取器碎片化（违反 P4）**

```c
/* 现状：4 个独立 getter，各自可被并发读取且非原子快照 */
uint32_t bus_worker_get_rx_timeout_count(int channel);
uint32_t bus_worker_get_report_drop_count(void);
uint32_t bus_worker_get_report_queue_high_water(void);
uint32_t bus_worker_get_min_stack_watermark(void);
```
问题：**"通道计数"接口是全局的**（`get_rx_timeout_count(int channel)` 隐含"全局实例"），
与缺陷 A 同源；且 4 次独立读取**不构成一致快照**（读到的是 4 个不同时刻）。

```c
/* 3.0：一次取一致快照 */
typedef struct {
    uint32_t rx_timeout[MAX_CHANNELS];
    uint32_t report_dropped;
    uint32_t report_queue_high_water;
    uint32_t min_stack_watermark;
} bus_worker_stats_t;
void bus_worker_get_stats(const bus_worker_t *, bus_worker_stats_t *out);
```

**缺陷 C：错误约定不一致（违反 P1）**

同一接口里 `start`/`resume`/`stop` 返回 `void`，而 `suspend` 返回 `bool`。
调用方无法形成统一处理路径。3.0 **每个可能失败的接口都返回结果类型**。

**缺陷 D：协议知识分散（违反 P4）**

各消息的字段解析分散在 `msg_handler/` 的 8 个 `handler_*.c`（合计 3,521 行），
每个文件自己拆字段、自己判 wire type ⇒ **同一字段的宽度/顺序在多处重复定义**。
3.0 收敛为 `msg.h` 的编解码纯函数 + `dispatch.h` 的路由表（见 §1.3）。

### 1.7 后端做得对、应当反向移植到固件的一处

`nodemgr/manager.go:380` 的消息分派**已经是表驱动**（`switch msgType` + `frame.MsgTypeName`），
并且 `MsgTypeName` 与固件 `frame_codec.h` 的编号表对应。
**这是正确结构**，3.0 应把它**移植到固件侧**（当前固件是"每个 handler 各自认领"），
并让两侧共用一张类型表 ⇒ 直接把 P4 的风险再降一档。


### 1.8 内存占用设计（用实测数字定预算，不是拍脑袋）

**S3 实测基线**（口径 `MALLOC_CAP_INTERNAL|8BIT`，见配套文档）：

| 项 | 实测值 |
|---|---:|
| 内部堆总量 | 299.0 KiB |
| 启动后（未跑 WiFi） | 184.7 KiB 空闲 |
| WiFi 关联后 | 222.5 → 消耗 **74.4 KiB** |
| 全部业务起来后稳态 | **48.7 KiB 空闲**，largest **23,552 B** |
| **PSRAM** | 8 MiB，**仅用 53.8 KiB** |

**设计结论 1：把"必须内部"的东西锁死，其余全部允许下 PSRAM。**
必须先落内部的（有硬理由，不能只凭"习惯"）：

| 必须内部 | 硬理由 |
|---|---|
| BLE 协议栈（63.3 KiB，实测） | 控制器/DMA 可见性 |
| WiFi 驱动缓冲（74.4 KiB，实测） | DMA |
| 中断/DMA 描述符、ISR 可达代码 | IRAM/内部总线 |
| 任务栈（15 个，共 55.0 KiB 分配） | FreeRTOS 默认内部；**可显式放 PSRAM**，但要评估 |

**可放 PSRAM**：TLS 会话缓冲（`MBEDTLS_EXTERNAL_MEM_ALLOC`）、
大 telemetry 缓冲、日志环形缓冲、非热路径的配置副本。

**设计结论 2：稳态 48.7 KiB 空闲不是"够用"，而是"没有余量"。**
门禁 floor 是 16 KiB（s3p），余量 43.75% 看着安全，但**largest 只有 23,552 B** ——
任何需要 >23 KiB **连续**内部块的分配都会失败（OTA 8 KiB 连续块的历史事故就是这类）。
⇒ 3.0 的设计约束是「**内部 RAM 上不做大块连续分配**」：
需要连续块的（编码 scratch、TLS、OTA）统一走 **PSRAM 或构造期一次性分配**。

**设计结论 3：栈上缓冲必须清零（P5）。**
现状 3 处 `uint8_t buf[1400]` 在 publish 路径上，是 `report_tx` 栈余量只剩 636 B 的直接原因
（`rgb_led` 更紧，584 B）。3.0 改为**每链路一份常驻 scratch**（大小 = `link.mtu`），
栈深度**与 payload 大小无关** ⇒ 可静态核算。

### 1.9 处理效率（实测 24.4 ms/事务的去向，与设计对应）

台架 115200、67 B 往返，实测单事务 **24.4 ms**（⇒ 41.0 Hz）：

| 组成 | 实测 | 归因 | 3.0 对策 |
|---|---:|---|---|
| 纯传输 | **5.8 ms** | 波特率物理 | 提高波特率（≥115200 已满足 100 Hz 的 4.18 ms 余量） |
| **帧静默等待** | **10.0 ms** | `rx_wait_ticks()` 固定付 10 ms | **由重组器按帧长判定完成**，而非固定静默（§1.3） |
| **rx 唤醒** | **~8.6 ms** | 任务唤醒节拍未与 cmd 侧解耦 | 事件驱动/直接唤醒，取消轮询节拍 |
| 合计 | 24.4 ms | | 目标 ≤10 ms/事务（100 Hz） |

**关键洞察**：100 Hz 的障碍 **18.6/24.4 = 76%** 是**软件调度**，不是硬件。
而 §1.3 的 `reassembler`（按帧长定界）**同时**解决"帧静默等待"与 R1 ——
**一个设计改动解决两个问题**，这是 3.0 结构设计的最大收益点。

**效率设计的通用规则**：
1. **热路径零 malloc**：scratch 构造期分配（§1.5）；
2. **零拷贝**：`reasm_push` 直接在内部环形缓冲上工作，`frame_out` 指向缓冲内；
3. **去轮询**：所有"等 X 毫秒"改为"等事件"；
4. **一次快照**：诊断走 `get_stats()` 单次读取（§1.6 缺陷 B），避免 4 次加锁。



### 1.10 规范性问题（用户明确要求处理的"不规范"，此处量化）

#### 1.10.1 同一概念两套命名（实测：**55 个 `_set_*` vs 10 个 `_register_*`**）

同一个语义 —— "把回调接进来" —— 有两套并行命名：

```c
/* 写法 A：set_xxx_cb */
bus_manager_set_write_rsp_cb(...);
log_stream_set_publish_callback(...);       /* 还混了 callback 与 cb 两种后缀 */

/* 写法 B：register_xxx_cb */
mqtt_client_register_msg_cb(...);
mqtt_client_register_owner_wake_cb(...);
mqtt_client_register_ready_cb(...);
mqtt_client_register_state_cb(...);
mem_guard_register_low_cb(...);
```

**为什么这是问题（不是风格洁癖）**：写代码的人**无法从名字推断语义**，
必须去读头文件确认"这个 set 是覆盖还是追加"、"register 能不能注册多个"。
且 `set_publish_callback` 与 `set_publish_cb` 这类差别让**搜索失效**。

**3.0 规范（二选一，全仓统一）**：
```c
/* 约定：单一回调用 set_<what>_cb；可多订阅者用 subscribe，返回句柄 */
void bus_worker_set_data_rpt_cb(bus_worker_t *, data_rpt_cb_t, void *ctx);
int  bus_worker_subscribe_stats(bus_worker_t *, stats_cb_t, void *ctx);
```
**判据**：`grep -c "_register_.*_cb(" ` ⇒ 0（平台 API 的 UART/GPIO 注册除外）。

#### 1.10.2 初始化失败无法上报（实测：**15 个 `void init` vs 6 个 `esp_err_t init`**）

15 个模块的 `init` 返回 `void` ⇒ **初始化失败只能靠内部 log 或直接 abort**，
调用方（`app_main`）无法据此决策（违反 P1）。

```c
/* 3.0：统一结果类型 —— 与 link / bus_worker 一致 */
typedef enum { EH_OK, EH_ERR_NO_MEM, EH_ERR_BAD_CFG, EH_ERR_IO, EH_ERR_STATE } eh_result_t;
eh_result_t config_mgr_init(void);
```
**判据**：`grep -c "^void .*_init(" ` ⇒ 0。

#### 1.10.3 停止/反初始化约定不一致（实测：**4 个返 `esp_err_t`，2 个返 `void`**）

`bus_dma_deinit` / `log_stream_stop` / `pwm_ctrl_stop` 返回错误，
而 `bus_worker_stop` / `msg_handler_deinit` 返回 void
⇒ 调用方**无法统一处理清理失败**。清理失败在嵌入式里通常意味**资源泄漏**，必须可见。

#### 1.10.4 装配是 180 行平铺序列，顺序靠隐式约定

`app_main()` 实测 **180 行**，是一条长调用链，其中：
- **两种注入方式混用**：`config_mgr_init()`（全局）与 `config_mgr_set_dma_pool(s->dma_pool)`（setter）；
- **顺序有隐式依赖**：`config_mgr_init` 必须先于 `msg_handler_init`，
  代码里没有表达，只靠注释与人的记忆；
- **诊断语句与装配交错**（`log_boot_heap()` 12 处）⇒ 真正的依赖关系被淹没。

**3.0**：§1.4 的 `app_create()` 把依赖变成**数据**：
```c
app->cfg    = config_store_create(&cfg_cfg);
app->ingest = ingest_create(&(ingest_cfg_t){ .store = app->cfg });
app->link   = link_create(&tcp_tls_driver, &(link_cfg_t){ .ingest = app->ingest });
/* 诊断作为可选 observer 注入，不再与装配交错 */
```

#### 1.10.5 规范化的收益（为什么值得做）
1. **可搜索**：统一命名后 `grep` 能可靠找到所有装配点；
2. **可检查**：上面每条都给出**可脚本断言的判据** ⇒ 可进 CI，防止回退（P5）；
3. **可测试**：`eh_result_t` + 构造注入 ⇒ 能构造"init 失败"场景做测试
   （现在是 `void`，**结构上无法测试失败路径**）；
4. **降事故**：`void init` 掩盖的失败正是"设备起来了但某子系统没起"这类最难查的问题 ——
   与项目已有的 silent-failure 教训同源。



### 1.11 三个会改排期的发现（审计提出，**我已逐条独立核实**）

> 来源：ESP32 设计审计子任务；**每条我都回源码核对过**，不是转述。

#### 1.11.1 3.0 方案说"transport 抽象已存在，只需加 TLS" —— **不成立**

方案原文（`ESP32-3.0-重构方案-2026-10-06.md:361`）称：
"abstract 层已存在 …… 3.0 只需新增 TLS 实现 + 退役 MQTT 实现，**不改上层广播语义**"。

**实测反驳**：
```c
/* components/msg_handler/msg_handler.c */
:16    #include "ehome_mqtt.h"                      /* ← 分发器直接包含 MQTT 头 */
:103   return mqtt_client_publish_impl(data, len) ? ESP_OK : ESP_FAIL;
       /*     ↑ 存在 MQTT 专用回退分支 */
```
⇒ **退役 MQTT 必须改 `msg_handler`**，不是"只加一个实现"。

**更根本的问题：`transport_ops` 是一份"两个实现都不履行的契约"**：

| 契约项 | MQTT 适配器 | TCP 实现 |
|---|---|---|
| `init` | no-op（`mqtt_transport_adapter.c:21-25`） | — |
| `deinit` | 空函数（`:66-69`） | 空函数（`ehome_tcp.c:153-161`） |

⇒ "新增 TLS 实现"会**继承一个从来没人真正实现过的契约**。这正是 P4（语义只有一处定义）
与 P1（返回值表达决策）要解决的问题 —— 也印证了 §1.2 的 `link.h` 重设计**不是过度设计**。

**方案已据此更正**（见 §1.11.4）。

#### 1.11.2 TCP 传输的启动路径是**死代码** —— 3.0 上线即不可用

```c
/* main/app_callbacks.c:675-693 */
case WIFI_MGR_CONNECTED:
    ...
    ensure_mqtt_supervisor(s);
    break;                      /* ← :683 已经 break 了 */
#ifdef CONFIG_DEBUG_TCP_ENABLED
    if (s->tcp_transport && ...) {          /* :685-691 永不执行 */
        s->tcp_transport->ops->start(...);
    }
#endif
    break;                      /* :692 第二个 break（不可达） */
```

**已核实**：`sdkconfig:1075 CONFIG_DEBUG_TCP_ENABLED=y`（编译进去了），
但代码在 `break` 之后 ⇒ **永远不执行**。
另一处启动点在 `main.c:596-600`，要求"初始化那一刻 WiFi 已连上"——
**正常启动顺序下不成立**。

⇒ **结论：TCP 传输在当前代码里从不启动。** 3.0 以 TCP 为主传输 ⇒ **上线即不可用**。
**建议**：T-3（TCP 双栈）之前**先修此条**，并加一条"启动后必须观察到 TCP 已连接"的
启动期断言（P6：读一手事实，而不是假设代码路径可达）。

#### 1.11.3 TCP 把字节流当完整消息回调；短写记为成功（**接口契约缺失**）

```c
/* components/ehome_tcp.c:447-449 */
if (transport->msg_cb) {
    transport->msg_cb(recv_buf, received, transport->msg_cb_ctx);
    /*  ↑ 一次 recv() 的内容被当作【一条完整消息】 */
}
```
而 `transport.h:35` 的接口**从未声明**"一次回调 = 一条完整消息"这一前提：
- **MQTT 恰好满足**（它有自己的分帧）；
- **TCP 流不满足**（一次 recv 可能半帧，也可能多帧粘连）。

⇒ 这是**典型的"契约只存在于实现者的脑子里"**（P4）。
**3.0 的"消息重组"如果不在接口层定契约，就会被实现成某个 transport 的内部行为** ——
于是换一个实现就复发。

**第二处**：`ehome_tcp.c:293-296` 把 `send() > 0` 记为成功 ⇒ **短写会静默发出半帧**
（P1/P2：应区分"全部写出"与"部分写出"，并让调用方知道）。

**3.0 契约（写进 `link.h`，见 §1.2）**：
```c
/* 链路层【只】提供字节流语义；分帧归 wire.h 的 reassembler */
typedef enum { LINK_SENT_FULL, LINK_SENT_PARTIAL, LINK_BACKPRESSURE, ... } link_result_t;
/* 明确：link_send 不保证对端"按写入边界"收到；定界由上层重组器负责 */
```

#### 1.11.4 对 3.0 方案的三处影响（需同步更正主方案）

| # | 原表述 | 更正为 |
|---|---|---|
| 1 | "transport 抽象已存在，只需加 TLS 实现，不改上层" | `msg_handler` **直接依赖 MQTT**，必须改；且现有 ops 契约**两个实现都未履行** ⇒ 需要 §1.2 的重设计 |
| 2 | 未提及 | **新增前置项**：修 TCP 启动死代码 + 加启动期断言（**T-3 之前必须做**） |
| 3 | "消息重组"作为传输层特性 | **必须在接口层定契约**（`link` 只给字节流语义），否则会退化成单实现细节 |

**方法学**：这三条都是"**代码路径从未被执行过**"造成的 ——
与 §1.10.2 的 `void init`、以及项目已有的 silent-failure 教训同源：
**没有被执行过的路径，等于没有实现。**

### 2.2 后端设计原则（沿用 P1–P7）

| 原则 | 后端的落点 |
|---|---|
| **P1 返回值表达决策** | 领域错误用**类型化错误**（`ErrNotFound` / `ErrConflict` / `ErrBackpressure`），HTTP 层映射为状态码；禁止 `fmt.Errorf` 兜底后再靠字符串判断 |
| **P2 发出前可验证** | 下行帧在 **encode 之后、write 之前**断言 `len <= negotiated_mtu`（R1 的通用形态，不止 Manifest） |
| **P3 无静默丢弃** | `DataEventBus`：`DroppedCount()` **必须接入指标 + 告警阈值**；或改为背压 |
| **P4 语义单一定义** | 设备能力（`features`）、协议版本、MTU **各只有一个来源**（当前 `features` 位在 `handler_hello.go`、版本在 `sender.go`，已接近，需收敛为 `protocol` 包） |
| **P5 预算派生** | `MaxManifestWireBytes` 已具名（好），但 `2011` 是手抄；应**由 (缓冲区大小 − 头部开销 − topic) 计算得出**，并有测试锁住推导 |
| **P6 判据读一手事实** | 设备状态以**设备上报 + 服务端契约校验**为准，不以"我们发过了"为准 |
| **P7 数字带口径** | 所有容量/速率常量带来源注释与实测出处 |

### 2.3 目标分层（`api` 拆分）

```
cmd/server/            装配（composition root，对应 ESP32 的 app_create）
  └ internal/
      protocol/            ① 协议契约：消息编号、能力位、MTU、编解码、重组
                               （现状 `pkg/frame` 已是常量来源，**扩展它而非替换**）
      session/             ② 设备会话生命周期（连接、握手、心跳、能力协商）
      device/              ③ 设备领域：配置事务、指令、状态机（不含 HTTP/DB）
      ingest/              ④ 上行摄入：重组 → 解码 → 背压 → 分发
      store/               ⑤ 持久化接口（repository），实现放 store/postgres
      httpapi/             ⑥ HTTP：只做 解析 → 调 domain → 渲染；【禁止】直接 gorm
      telemetry/           ⑦ 指标/告警（P3 的落点）
```

**拆分判据（可验证，不靠感觉）**：
- `httpapi` 里 **gorm 出现次数必须为 0**（现在是 14 个文件）；
- `device`/`protocol` **不 import `net/http`、不 import gorm**；
- `protocol` 是唯一能定义消息号/能力位的地方 ⇒ 与固件的 `frame_codec.h` **一一对应**。

### 2.4 与 ESP32 端的**对称性**（这是 3.0 的关键结构决策）

3.0 最大的结构机会：**两端用同一套概念名**，消除"同名异物"（项目已有该教训）。

| 概念 | ESP32 端 | 后端 | 必须一致的内容 |
|---|---|---|---|
| 链路 | `link.h` `link_send/link_result_t` | `session` | MTU、背压语义、错误分类 |
| 定界 | `wire.h` `reassembler` | `protocol/reasm` | 帧格式、最大消息、超限行为 |
| 消息 | `msg.h` `msg_encode/decode_*` | `protocol/codec` | 字段编号、类型、宽度 |
| 能力 | `link.mtu` / features | `protocol/features` | 位定义、协商规则 |
| 分派 | `dispatch.h` 路由表 | `ingest` 路由表 | 类型编号表 |

**硬约束**：`protocol` 包与固件的 `wire.h`/`msg.h` **共享一份"契约描述"**
（消息号、字段表、MTU、超限行为），由**双向 golden vector 测试**锁定
（现有项目已有"三方对锚"实践，3.0 应把它制度化）。


### 2.5 后端接口设计（Go，具体到可评审）

#### 2.5.1 领域错误：类型化，不用字符串判断（P1）

**先说现状（避免虚构缺陷）**：实测 `strings.Contains(err.Error(), ...)` 在全仓 **0 处** ——
这一点已经做对了。真正缺的是**错误的分类信息**：
现在多为 `fmt.Errorf("...: %w", err)` + 少量 sentinel，上层要决定 HTTP 状态码/是否重试时
**拿不到结构化的 Kind/Retryable**，只能退化成"大概是 400"。
⇒ 3.0 不是"修 bug"，而是**把已经良好的习惯补齐为类型**。

```go
// 3.0：错误类型自带【决策信息】，而不是让上层解析字符串
type ErrorKind int
const (
    KindInvalid    ErrorKind = iota // 400
    KindNotFound                    // 404
    KindConflict                    // 409
    KindBackpressure                // 429 / 503 + Retry-After
    KindUpstream                    // 502
    KindInternal                    // 500
)

type OpError struct {
    Kind    ErrorKind
    Op      string   // 语义操作名，如 "device.applyConfig"
    Code    string   // 机器可读码，如 "MANIFEST_TOO_LARGE"
    Message string   // 人类可读
    Err     error    // 底层原因（可 errors.Is/As）
    Retryable bool   // P1：调用方据此决定重试，而不是猜
}
func (e *OpError) Error() string { ... }
func (e *OpError) Unwrap() error { return e.Err }
```
**判据**：`httpapi` 层只做 `Kind → 状态码` 的**一张映射表**；
禁止出现 `strings.Contains(err.Error(), ...)`（可脚本断言为 0）。

#### 2.5.2 协议唯一来源（P4）

```go
// pkg/frame —— 【扩展既有包】，不新建 internal/protocol
//
// 现状（重要）：pkg/frame/frame.go 已经是协议常量的单一来源
//   MsgHello=0x01 / MsgDataBatch=0x20 / MsgMemRpt=0x21 …
//   且与固件 frame_codec.h 对应 —— 【这是正确结构，不要另起炉灶】。
// 3.0 要做的是在它之上补齐"契约"：帧长度上限、字段表、发出前校验，
//   即把它从"常量表"升级为"契约包"。
package frame

type MsgType uint8
const (
    MsgHello      MsgType = 0x01
    MsgDataReport MsgType = 0x03
    MsgDataBatch  MsgType = 0x20
    MsgMemReport  MsgType = 0x21
    // …
)

// 帧格式的唯一描述：定界、最大长度、字段表
type FrameSpec struct {
    Type      MsgType
    MaxBytes  uint32     // P2：编码后必须 ≤ 此值，否则拒绝发出
    Fields    []FieldSpec
}
var Specs = map[MsgType]FrameSpec{ /* 单一来源 */ }

// P2：写出前统一断言（R1 的通用形态，不止 Manifest）
func (s FrameSpec) ValidateWire(b []byte) error
```
**约束（可脚本断言）**：`MsgType` / 能力位 / MTU **只能在本包定义**；
`grep -rn "MsgDataBatch\|0x20\|0x21" internal/ --include=*.go | grep -v "pkg/frame"` 必须为空
（现状：常量确已集中在 `pkg/frame`，**需保持**）。

#### 2.5.3 会话接口（对应固件 `link`，语义对称）

package session

type Session interface {

```

#### 2.5.4 摄入管线：背压优先于丢弃（P3）

package ingest

// 现状：DataEventBus.Publish 满时丢最旧，DroppedCount() 从未接指标

type Sink interface {

### 2.6 后端第二批具体缺陷（均已核实，含对我此前一处断言的更正）

#### 2.6.1 HTTP handler 直接依赖具体 DB 类型（实测 **25 处**）

```bash
grep -rhoE "func [a-zA-Z]+\(db \*gorm\.DB" internal/api/*.go | wc -l   # → 36
grep -rhcE "func .*\(db \*gorm\.DB.*\) gin\.HandlerFunc" internal/api/*.go  # → 25
ls internal/store internal/repository 2>/dev/null   # → 无此包
```

**事实**：**25 个 handler 构造函数签名里带 `db *gorm.DB`**，且**全仓没有任何
`store`/`repository` 抽象层**。即：持久化**完全没有接口边界**。

**为什么这是设计问题**（不是"不够优雅"）：
1. handler **结构上无法脱离真实数据库测试** —— 无法用假实现构造
   "DB 返回超时/唯一键冲突"这类分支；
2. 换 ORM / 加读写分离 / 加缓存层**必须改遍所有 handler**；
3. **业务规则与存储细节耦合**：`Where(...)` 的写法泄漏到 HTTP 层，
   同一规则在两个 handler 里可能被写成两种 SQL。

**3.0 设计**：
```go
// internal/device —— 只依赖接口，不知道 SQL
type Repository interface {
    GetNode(ctx context.Context, id string) (*Node, error)
    ApplyConfig(ctx context.Context, id string, m ConfigManifest) error
    // P1：错误用 OpError 分类，调用方据此映射状态码
}
type Service struct{ repo Repository }   // 无 *gorm.DB 字段
```
**判据**：`grep -c "gorm.DB" internal/httpapi/*.go` ⇒ **0**。

#### 2.6.2 真实缺陷前的澄清（**更正我此前一处断言**）

我在 §2.5.5 写过"大量测试用 `sqlmock` 直接断言 SQL" —— **实测是错的**：

| 检查 | 实测 |
|---|---:|
| 使用 `sqlmock` 的测试文件 | **0** |
| 使用 `testify/mock` 或 `gomock` | **0** |
| 使用**内存 sqlite** 的测试文件 | **55** |

**这其实是好消息**：用**真实 DB 引擎**（sqlite 内存库）测，比 mock SQL 更能验证行为。
⇒ **"测试:实现 = 1.42:1"更可能是"测试充分"，而不是"耦合过紧"**。
**更正结论**：3.0 重构时测试**未必需要大量重写**；但 §2.6.1 引入
`Repository` 接口后，**SQL 相关测试应下移到 `store` 实现层**，
handler 测试改为对着接口 + 假实现（更快、更能测失败分支）。

#### 2.6.3 已被做对的两点（记录以免后人误改）

| 项 | 实测 | 说明 |
|---|---:|---|
| 忽略错误 `_ = ...` | **0 处** | 已无"裸忽略错误" |
| 字符串判错 | **0 处** | 已无 `strings.Contains(err.Error())` |
| 协议常量集中 | `pkg/frame` | 已是单一来源（§2.5.2） |

⇒ **3.0 在这些方向上是"保持并制度化"，不是"修复"**。

#### 2.6.4 承载数据的 channel 有 16 处需逐个定性

实测：`make(chan ...)` 共 32 处，其中 **16 处不是 `struct{}`**（即承载数据）。
`struct{}` 的（`stopCh` 等）是信号通道，**无需缓冲**，不是问题。
**待办**：16 处数据通道需逐个判定 **是否有界 + 满时行为是否可观测**（P3）。
其中 `databus/bus.go` 的 `dataChan`(256) 与 `mailbox` 已知会在满时丢弃（§2.5.4）。

#### 2.6.5 panic 的 4 处（需确认仅限启动期）

全部在 `internal/deviceaction/definition.go`（`NewBuiltInRegistry` 及定义构建路径），
**看起来是"启动期定义非法即崩溃"** —— 这在 Go 里是**可接受**的做法
（配置错误应当早失败）。**结论**：**不是缺陷，但需加一条断言**：
确保这些 panic **不可能在请求路径上被触发**（即 Registry 构建只在启动期发生）。

## 3. 迁移路径（不破坏现有可运行系统）

| 阶段 | 内容 | 判据 |
|---|---|---|
| **S0** | 冻结契约（`protocol` 描述文件 + golden vector 机制） | 两端各有一套对锚测试 |
| **S1** | ESP32：`transport` → `link`（先只做 TCP+TLS，MQTT 走同一 `link_driver_t`） | L-02 类缺陷在类型层不可能复现（`link_result_t` 强制分支） |
| **S2** | ESP32：`wire`/`msg`/`dispatch` 三分（去 TLV + 重组） | 宿主机测试覆盖编解码 100%（纯函数） |
| **S3** | 后端：`protocol` 包 + `httpapi` 去 gorm | `httpapi` 里 gorm 计数 = 0（可脚本断言） |
| **S4** | 后端：`DataEventBus` 背压 + 指标 | 丢弃不再静默（有指标/告警） |
| **S5** | 全局状态消解（282 → 实例化） | 每模块可独立建实例测试 |

**注意**：MQTT 退役的**部署层双栈窗口**（见主方案 §5）与本文的**代码结构重构**可以并行，
但**必须先有 S0 契约**，否则重构中两端会各自漂移。
