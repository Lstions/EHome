## 0. 总览（一句话）

生产库 **53 张逻辑表 + 16 个分区子表 = 69 个物理关系**，总大小 **4,142 MB**，236 个索引，**0 个外键约束**（外键在应用层 + 显式 SQL 迁移管理）。

其中 **数据量集中在 3 张时序表**（占 98.9% 体积），其余 50 张是配置/状态/审计/进度类元数据表，**53 张逻辑表里有 26 张当前为空**（功能已实现但生产未启用）。

## 1. 核心概念表（系统骨架）

> 四层模型：**节点 Node**（ESP32 物理板）→ **通道 Channel**（总线端口）→ **设备配置 DeviceConfig**（型号定义）→ **边缘设备 EdgeDevice**（挂载的物理传感器实例）。详见 [概念模型.md](概念模型.md)。

### 1.1 `nodes` — 节点（ESP32 物理设备）

| 项 | 内容 |
|---|---|
| **记录什么** | 一块 ESP32 板（C6/S3/S3P）的身份、型号、固件版本、在线状态、资源快照（free heap / largest internal / uptime / WiFi RSSI）、配置同步状态（config_epoch / manifest / sync_state）、经纬度与时区 |
| **用途** | 节点列表/详情页；在线判定（status + last_seen）；OTA 目标；配置下发的版本基线；日出日落自动化的坐标来源 |
| **主键 / 关键索引** | `id` PK；`node_id` UNIQUE（物理 ID hex，如 `F0F5BD02DD84`）；`deleted_at`、`resource_reported_at` 索引 |
| **生产实况** | **4 行**（3 块 C6 + 1 块 S3P），944 kB。软删（`deleted_at`） |
| **保留期** | 不清理（配置类） |

### 1.2 `channels` — 通道（总线端口）

| 项 | 内容 |
|---|---|
| **记录什么** | 某节点上的一个总线端口：`hardware_type`（UART/SPI/I2C/ADC）、`hardware_id`（如 I2C 地址）、`bus_type`、`bus_config`（JSON：引脚/波特率）、轮询 `interval_ms`、`dma_enabled`、绑定的 `template_ids` |
| **用途** | 采集调度：决定每个通道按什么频率、什么总线参数去轮询挂载的边缘设备 |
| **主键 / 关键索引** | `id` PK；`node_id` 索引；`deleted_at` |
| **生产实况** | **12 行 / 96 kB** |
| **注意** | GPIO/PWM **不是通道**，是独立外设（见 `gpio_configs` / `pwm_configs`） |

### 1.3 `config_templates` — 采集模板（低层命令序列）

| 项 | 内容 |
|---|---|
| **记录什么** | 一条 Modbus/串口读命令的原始描述：`write_data`（hex）、`read_length`、`delay_ms`、归属 `edge_device_id`（可空） |
| **用途** | 通道轮询的实际指令；driver 模板自愈（reconcile）；删除设备时按归属清理 |
| **主键 / 关键索引** | `id` PK；`node_id` 索引；`edge_device_id` 索引 |
| **生产实况** | **14 行 / 96 kB**（DD84 节点 11 条、S3P 2 条、F35C 1 条） |

### 1.4 `device_configs` — 设备配置（型号定义，v2.2 的协议无关描述）

| 项 | 内容 |
|---|---|
| **记录什么** | 设备型号的 JSONB 定义：`connection`（协议/默认参数）、`parser`（解析器 id + options）、`init_flow`（初始化步骤）、`operations`（支持的操作） |
| **用途** | 解析后端选择的依据之一；创建边缘设备时绑定；驱动注册表的模板 |
| **主键 / 关键索引** | `id` PK；`name` / `device_type` / `is_default` / `deleted_at` 索引 |
| **生产实况** | **0 行**（当前完全依赖内置驱动 `drivers.Registry`，未使用配置化设备模板） |
| **注意** | `edge_devices.device_config_id = 0` 表示"无模板，走 driver fallback"——生产 10 台设备**全部**是 0 |

### 1.5 `edge_devices` — 边缘设备（物理传感器/执行器实例）

| 项 | 内容 |
|---|---|
| **记录什么** | 挂在某节点某通道上的一个物理设备：`type`（`jiabaida_bms` / `techfine_inverter` / `sn3001_rain` / `generic_modbus`…）、`name`、`interval_ms`、`status`（pending/active/offline）、`last_data_at`、`last_error`、`error_code`、`init_state/step/total`、`command_intervals`（JSONB 每命令轮询间隔）、`data_purge_requested` / `data_purge_started_at`（彻底删除与恢复的互斥协议） |
| **用途** | **一切历史数据的归属维度**（所有时序表的 `device_id` 就是本表 `id`）；设备列表/详情；在线判定；受控操作目标；数据 purge/restore 竞态控制 |
| **主键 / 关键索引** | `id` PK；`node_id`、`channel_id`、`device_config_id`、`status`、`type`、`deleted_at` 索引 |
| **生产实况** | **10 行 / 240 kB**：`14=bms`(jiabaida_bms, active)、`15=inter`(techfine_inverter, active)、`16=光学雨量计`(sn3001_rain, offline)、7–13 为 S3P 板上的测试设备（offline） |
| **保留期** | 软删保留；勾选"删除数据"时由 `DevicePurger` 分批硬删三张时序表中该设备的数据 |

## 2. 数据源与字段目录（"有哪些字段、单位是什么"）

### 2.1 `data_sources` — 数据源台账（自动派生）

| 项 | 内容 |
|---|---|
| **记录什么** | 每 `(edge_device_id, category)` 一行：`source_type`、`priority`、`is_primary`、`status`（standby/active）、`fail_count`/`max_fail_count`、`last_success`/`last_failure`、`managed_by`（auto/manual）、`derived_at` |
| **用途** | 数据来源页总览（只读投影，不做主备切换）；字段是否曾上报过的事实记录 |
| **生产实况** | **71 行 / 592 kB**，全部 `source_type=edge_device` + `managed_by=auto` |
| **代码** | `backend/internal/models/models.go:332`；唯一约束 `(edge_device_id, category)` |

### 2.2 `data_source_health` / `failover_logs` — 数据源健康与切换日志

| 项 | 内容 |
|---|---|
| **记录什么** | `data_source_health`：某数据源某 category 的健康探测结果（status/message/response_time）。`failover_logs`：主备切换记录（from/to + reason + trigger） |
| **用途** | 健康趋势；切换取证 |
| **生产实况** | 各 **0 行**（主备状态机已于 M3 下线，仅保留来源组一套语义） |
| **保留期** | 无独立清理器（当前为 0 行，非风险点） |

### 2.3 `sensor_field_obs` — 字段观测投影（**单位与"字段是否存在"的权威来源**）

| 项 | 内容 |
|---|---|
| **记录什么** | `(device_id, sensor_name)` 主键：`unit`（最近一次观测到的单位）、`first_seen`、`last_seen`、`samples`（累计条数） |
| **用途** | **① 图表的单位**：`telemetry_frame` 解出的只有 `(name, value)`，**没有 unit 列**，单位靠本表补齐（`api/device_data_sensors_frames.go:274 unitMapForDevice`，本表优先、unified_data 为历史兜底）；② `/latest-values` 与数据源创建时的"该字段是否上报过"校验 |
| **生产实况** | **71 行 / 208 kB**；其中 **16 行 unit 为空串**（未知单位） |
| **写入** | 由 `SchedulerParserConsumer` 的 `latestSink` → `field_resolver.Observe` → projector 每 60s 批量 UPSERT |

### 2.4 `sensor_field_meta` — 字段展示元数据（丰富层）

| 项 | 内容 |
|---|---|
| **记录什么** | 按 `sensor_name`（跨设备共享）：`label_zh`（中文名）、`unit`、`value_type`、`precision`、`status` |
| **用途** | 展示层降级：缺行则前端显示物理名 |
| **生产实况** | **71 行 / 40 kB** |

## 3. 遥测时序表（★ 全部历史数据所在，占 99% 体积）

> 三张表都是 **PG 月分区表**（分区键 = 时间列），保留期统一为 `EHOME_DATA_RETENTION_DAYS=45`（生产）→ 分区整月 DROP + 行级精确 DELETE 两级清理。当前分区：`202609` / `202610` / `202611` + 预建 `202612/202701/202702`。

### 3.1 `telemetry_frame` — L2 帧表（**解析值的唯一完整时序副本**）

| 项 | 内容 |
|---|---|
| **记录什么** | **一帧一行**：`(device_id, ts, seq)` 主键 + `frame_kind`（0=增量帧 / 1=关键帧）+ `slot_id` + `payload`（1B flags + changed_mask + 位打包量化值）+ `raw`（原始总线帧，常规增量帧为 NULL） |
| **payload 实际大小** | 生产实测 **平均 9.3 B/帧**（1 小时 5,937 行 = 0.1 MB） |
| **解析值怎么读出来** | 必须配合 **`telemetry_slot` 字典**：`value = code × step + min`（误差 ≤ step/2）。字段名不在 payload 里 |
| **用途** | ① **短窗历史图表**（≤6h，avg/change 模式）—— `DecodeRangeAnchored` 关键帧锚点 + 增量链推进；② **rollup 的实时尾巴**（最近 2 分钟）；③ 长窗 change 模式的候选分钟精解 |
| **主键 / 索引** | PK `(device_id, ts, seq)`；`(device_id, ts) WHERE frame_kind=1` 部分索引（关键帧锚点查询） |
| **生产实况** | **约 401 万行 / 508 MB**（202610: 约 257 万行/316 MB；202611: 约 145 万行/192 MB）；帧型分布：增量 ≈ 384 万 / 关键 ≈ 17.1 万；`raw` 列仅 **5 行**非空。时间跨度 2026-10-02 → 现在；日增约 **142,000 帧** |
| **写入** | `databus/consumers_heavy.go:472` → `telemetry.DualWriter.Observe`（有界队列 + 128 帧或 2s flush，UPSERT `ON CONFLICT DO NOTHING`）。**无条件启用**，构造失败即拒绝启动（`main.go:622-627`） |
| **保留期** | 45 天，月分区 DROP（`telemetry_frame_lifecycle.go` + `retention_task.go`） |

### 3.2 `telemetry_rollup_1m` — L3 分钟级宽行预聚合（长窗图表的唯一来源）

| 项 | 内容 |
|---|---|
| **记录什么** | **每设备每分钟一行**：`payload` 内是**自描述**编码 —— `1B version + 2B 字段数 + 每字段(1B 名长 + 名字 + 4×8B avg/min/max/last + 4B count)` |
| **payload 实际大小** | 生产实测 **平均 1,816 B/分钟**（29 字段设备） |
| **用途** | **>6h 的 avg 长窗图表**（24h/7d/30d）。按 D1 口径重建（桶内最后值 Last，**不是 avg**），并与帧表实时尾巴拼接 |
| **主键 / 索引** | PK `(device_id, bucket)` —— 天然幂等 UPSERT |
| **生产实况** | **约 7.9 万行 / 103 MB**；dev14/dev15 各约 1,440 行/天，覆盖率接近 100% |
| **写入** | `consumers_heavy.go:481` → `RollupCollector.Observe`（内存累加）→ 60s ticker `FlushCompleted` → `EncodeRollupPayloadV1` → 整分钟桶落库 |
| **保留期** | 45 天，月分区 DROP |
| **已知坑** | ① 长窗能否走 rollup 取决于 **`telemetry_rollup_coverage`** 的每天 state；② 实时尾巴（最近 120s）仍需帧表解码，取不到则整窗回落 |

### 3.3 `device_data` — 原始总线帧留档（**不含解析值**）

| 项 | 内容 |
|---|---|
| **记录什么** | 同一帧写 **两行**（形状不同，**不是重复**）：<br>• `sensor_parser` 行：`{"channel_id":10,"raw_hex":"dd0f...","timestamp":...}`，`device_id` = 真实设备 id<br>• `db_persist` 行：`{"raw":"...","channel":...}`，**`device_id` = 0**（只填 node_id），覆盖 ErrorCode≠0 / 空 raw / 驱动运行期拒收这三类**只有它能留档**的样本 |
| **⚠ 解析值在哪** | **不在本表**。2026-11-07 起写侧**停写 `sensors`**（`consumers_heavy.go:624-642`）；存量老行的 `sensors` 已被默认启用的剥离任务**不可逆删除**（`bytes_before=5.79 GB → bytes_after=0.69 GB`，`rows_stripped=3,469,858`）。生产实测：全表 **0 行**含 `"sensors"` |
| **用途** | ① 数据面板「原始数据」列展示；② 故障取证（原始字节）；③ BMS `hardware_version`/`serial_number` 的 **StringValue 唯一落库处**（`str_values` 键，帧表/unified_data 都没这列） |
| **主键 / 索引** | PK `(id, timestamp)`；`(device_id, created_at DESC)`、`(device_id, timestamp)`、`timestamp` 三条 |
| **⚠ 已知不一致** | 分页接口 `GET /edge-devices/:id/data` 按 **`created_at`** 过滤排序，而模型时间列是 `timestamp`——两列不同源 |
| **生产实况** | **约 868 万行 / 3,486 MB（最大表）**；其中 `device_id=0` 的 raw 行约 **466 万行（54%）**，解析行约 **402 万行**；单行平均 211 B；日增约 302,250 行 |
| **保留期** | 45 天，月分区 DROP |

### 3.4 `telemetry_slot` — slot 字典（帧表解码的必需索引）

| 项 | 内容 |
|---|---|
| **记录什么** | 一个"帧类型" = `slot_id` + `signature`（sha256(command_template_id \| spec_version \| 排序后字段名)）+ `command_template_id` + `spec_version` + `field_count` + `fields_json`（**字段名 + 量化规格快照** `{name,min,step,bits}`） |
| **为什么必需** | `telemetry_frame.payload` **不带字段名**，解码必须靠本表还原"第 i 个字段叫什么、量化规格是什么"。规格是**写入时的快照**（不引用），保证跨进程/重启稳定 |
| **用途** | 帧表解码（`telemetry.DecodeRangeAnchored`）；rollup 回填解码；`/latest-values` 合成 |
| **主键 / 索引** | `slot_id` PK（自增）；`signature` UNIQUE |
| **生产实况** | **约 18,139 行 / 12 MB**，但**只有 553 个 slot 被实际使用**（dev14 494 个、dev15 57 个、dev2/12/13 各 1–2 个） |
| **⚠ 已知异常** | 其中 **18,131 行（99.96%）是 `command_template_id=0` 且 `created_at` 全在 2026-11-07 同一天写入** —— 说明某次批量事件（回填/重放）把"字段集合略有不同的帧"各自派生成了一个新 slot（例：slot 40/41/42 是同一批 `cell_voltage_N` 的不同子集）。属**待治理的膨胀**，不影响正确性（每个 slot 的规格都是自洽的），但会让解码时 slot 命中率下降 |

### 3.5 `telemetry_rollup_coverage` — rollup 覆盖元数据（**长窗图表能否出数的开关**）

| 项 | 内容 |
|---|---|
| **记录什么** | `(device_id, day)` 主键：`buckets`（该日实际数出的分钟桶数）、`state`（`complete` / `missing` / `partial`）、`source`（`unified` / `frames` / `live`）、`updated_at` |
| **用途** | 读路径**唯一的覆盖率判据**：`RollupWindowCovered` 要求窗口跨的**每一天**都有行且 state ∈ {complete, missing}。**`partial` 会让整个窗口回落到帧表解码 → 超过 6h 就直接报错**（就是"SOC/电流加载失败"的直接成因） |
| **生产实况** | **440 行 / 128 kB**；dev14 的 `2026-11-10` 是 **`partial`（buckets=0）**，而同一天 `telemetry_rollup_1m` 实际有 **1,439 个分钟桶** —— 元数据与事实不符 |
| **写入** | 仅回填器写：`MarkRollupCoverage`；`partial` 是**粘性**的（`unitAlreadyDone` 只认 complete/missing） |

### 3.6 `telemetry_backfill_progress` — 帧表回填断点

| 项 | 内容 |
|---|---|
| **记录什么** | 按 `(table_name, part_name)` 记录 unified_data → telemetry_frame 迁移的进度：`state`、`watermark`、`frames_done`、`rows_done`、起止时间、错误 |
| **用途** | 断点续跑；运维可见进度 |
| **生产实况** | **6 行**，全部 `done`（unified_data 各分区已迁移完并可退役） |

### 3.7 `device_data_strip_progress` — device_data sensors 剥离断点

| 项 | 内容 |
|---|---|
| **记录什么** | `task_key=device_data`：`state=done`、`watermark_id`、`rows_selected` / `rows_stripped` / `rows_skipped`、`bytes_before` / `bytes_after` |
| **用途** | 幂等续跑；证明压缩收益 |
| **生产实况** | **1 行**：`rows_stripped=3,469,858`、`bytes_before=5,792,610,535` → `bytes_after=686,671,430`（**释放 5.1 GB**） |

## 4. 告警 / 自动化 / 通知

| 表 | 记录什么 | 用途 | 生产 |
|---|---|---|---|

## 5. 受控操作（命令域）

生命周期：**`command_executions`（真相源）→ `command_outboxes`（事务性外发）→ `command_attempts`（每次尝试）→ `command_inboxes`（设备回报）→ `command_manual_resolutions`（人工裁决）**；高风险动作另有 `command_confirmations`（一次性令牌）。

| 表 | 记录什么 | 用途 | 生产 |
|---|---|---|---|
| `command_executions` | 一次受控操作的全生命周期：`command_id`(PK)、设备/通道/驱动身份、`action_id`+`action_version`+`command_engine_revision`（能力契约冻结）、`idempotency_scope/key`、`params_json`、`status`、`deadline_at`、`final_reason`、`verified_result_json` | 操作真相源 + 幂等 + 审计 | **6 行 / 176 kB** |

| `command_outboxes` | 待发布事件：`event_type`、`payload_json`、`state`、`lease_owner`/`lease_expires_at`/`fencing_token`（租约防并发） | 事务性外发（至少一次） | **0 行** |

## 11. 数据流（一帧数据落到了哪）

```
ESP32 采集 → 帧协议上行 → databus.SensorParserConsumer.Handle
                                   │
                ┌──────────────────┼────────────────────────────────┐
                │                  │                                │
          ① telemetry_frame   ② telemetry_rollup_1m           ③ device_data
           （解析值+量化）       （分钟 avg/min/max/last）      （只有 raw_hex）
                │                  │                                │
                │                  └─ 60s flush → 长窗图表(>6h)       └─ 取证/原始数据列
                ├─ ≤6h 图表（avg/change）
                ├─ rollup 实时尾巴
                └─ latest 缓存回落

      内存 latestValueCache ←→ ④ sensor_field_obs（字段名/单位/首末见）
```

**关键结论（与图表问题直接相关）**：
1. **解析后的数值只存在于 `telemetry_frame` 与 `telemetry_rollup_1m`**；`device_data` 只有 `raw_hex`，且缺 `command_template_id`（无法判定帧属于哪条命令），**不能反向解出数值**。
2. **`telemetry_frame` 不含字段名与单位**：字段名/量化规格来自 `telemetry_slot`，单位来自 `sensor_field_obs`。
3. **>6h 窗口能否出数取决于 `telemetry_rollup_coverage`**：某天 state=`partial` ⇒ 该窗口回落帧表解码 ⇒ 超过 `EHOME_TELEMETRY_FRAME_DECODE_MAX_WINDOW=6h` ⇒ 报"超过帧表单次解码上限"。
