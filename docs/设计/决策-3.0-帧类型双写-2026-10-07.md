# 决策：3.0 帧的"类型双写"如何处理（2026-10-07）

> 状态：**已按现有证据裁决为"保留双写 + 两端强制一致性校验"**。
> 依据不是偏好，而是**当前已经落地的协议向量**与**两端既有实现**。
> 本文把"为什么不是另外两个选项"写清楚，供日后复核。

## 一、问题
3.0 的 12 B 定界头在 **offset 3 有 `type`**；而 payload 的**首字节也是 `type`**（2.x 遗留）。
2.x 时代只有后者（根本没有头），所以**从来没有任何一致性检查**。
现在两者**可以**不一致，失效方式是最坏的一种——**静默**：
路由按 header 走、解析按 payload 走 ⇒ 一帧可能**按 A 类型派发、却按 B 类型解码**。

## 二、三个选项与裁决
| 选项 | 结论 | 理由 |
|---|---|---|
| **A. 保留双写 + 强制一致性校验** | ✅ **采纳** | 见下"为什么" |
| B. 去掉 payload 首字节，type 只留 header | ❌ 否 | 见 §四 |
| C. payload 首字节为权威，header type 仅提示 | ❌ 否 | 见 §四 |

## 三、为什么采纳 A（逐条证据，非偏好）
1. **协议向量已经把它钉死了**：`protocol/vectors/wire_primitives.txt` 里
   `wire 22080112…`（0x22）、`230800120a…`（0x23）、`writecmd` 的 `06…`
   **都以类型字节开头**。这些向量是 **C / Go / Python 三份实现共同校验**的单一来源
   （`check_golden_vectors.py`）。改 B 要**重新生成全部向量**并同步改两端编解码，
   收益是"少一个冗余字节"，代价是**动到全项目最核心的契约**。
2. **两端既有实现都依赖 payload[0]**：
   - 固件 `msg_handler_process`（msg_handler.c:189）就是 `uint8_t msg_type = data[0];` 后 switch；
   - 后端 `manager.go:418` 有 `if payload[0] != msgType { 丢弃 + 计数 }`；
   - 后端 `device_op_wire.go:66-67` 注释明说"payload 的**首字节是消息类型**（2.x 约定，
     也是共享向量所编码的），所以本函数返回**包含它**的完整 payload"。
   ⇒ 选 B 等于同时推翻这三处已落地并已测的实现。
3. **A 的成本已经付了**：后端那条一致性检查**已经在跑**（`FrameTypeMismatchTotal` 指标 + 丢弃）。
   选 A 只需**把同一条规则补到固件侧**，是"补齐对称"，不是新增机制。
4. **与 §7.3 的双栈窗口相容**：P0–P3 期间后端要同时服务 2.8.0 设备（只有 payload[0]）。
   保留 payload[0] 让"同一份消息体"在两条传输上形状一致，避免双栈期出现两套消息体定义（P4）。

## 四、为什么不选 B / C
- **B（去 payload 首字节）**：最"干净"（真正满足 P4 的"一处定义"），但代价最大：
  重生成全部向量 + 同改两端编解码 + 双栈期消息体形状分叉。
  **收益（省 1 字节）与代价（动核心契约）严重不匹配**。
- **C（payload 首字节为权威）**：与"长度前缀定界头"的设计意图相反
  —— 那样 header 的 type 就成了**可忽略字段**，日后必然被误用（有人按 header 路由、有人按 payload 解析，
  又回到同一个二义性）。而且它把"权威"放在**没有长度保护的那一侧**，更差。

## 五、采纳后的**强制要求**（这才是 A 成立的前提）
保留双写**只有配上"不一致就拒绝"才安全**。缺了校验，A 就是"静默错派发"。
因此：

| 端 | 现状 | 要求 |
|---|---|---|
| 后端 | ✅ **已有且有测试**：`manager.go:418` 不一致 ⇒ 丢弃 + `FrameTypeMismatchTotal`；测试见 `nodemgr/router_test.go` 的 `TestHandleFrameAcceptsMatchingType` / `TestHandleFrameDropsTypeMismatch`（后者还断言**指标真的加一**，而不只是"没崩"） | 保持 |
| 固件 | ❌ **缺失**：`devlink_on_msg` 只打日志，`rx_msg_t.type`（header）**完全没被用** | **必须补**：`payload[0] != msg.type` ⇒ 丢弃 + 计数 |

> 固件侧缺失是**真实缺口**：3.0 接收路径把 `rx_msg_t` 的 `type`（header）交给回调，
> 而下游 `msg_handler_process` 只认 `data[0]`（payload 首字节）。
> 两者一旦不一致，**没有任何一层会察觉** —— 正是 §85.2 描述的那个静默失效。

## 六、这条裁决**不**需要用户拍板，为什么
前几轮我把它列为"需设计确认"。复核后认为：**它已经有答案了，只是没被写成一句话**——
(a) 共享向量已把 payload[0] 钉死；(b) 后端已实现 A 的检查；(c) B 的代价远大于收益。
真正的**待确认**其实只剩一个小问题：
**将来（P5 移除 MQTT 之后）要不要把 payload[0] 去掉？** —— 那是**双栈窗口结束后的清理**，
属独立议题，不影响现在。本文把 A 记为**当前有效裁决**，并保留"P5 后可再议"的注记。

## 七、证据边界
- 本文的裁决基于**本仓现状**（向量 + 两端实现 + 双栈窗口约束），未询问用户；
  若用户另有偏好（例如坚持 B），应视为**推翻本裁决**，届时需重生成向量并同改两端。
- 固件侧校验**尚未实现**（本轮登记为待办）。
