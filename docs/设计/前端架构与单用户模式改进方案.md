# 前后端架构与单用户模式改进方案

> 状态：已实现（单用户/单管理员认证已落地，详见 [实现/单用户认证迁移与运维指南.md](../实现/单用户认证迁移与运维指南.md)；本文保留为设计定稿参考）
>
> 适用范围：`frontend-shared`、`backend`、认证数据库迁移、通用/终端 WebSocket 及部署配置
>
> 核心决策：保留 Vue 3 / TypeScript / Pinia / Axios / WebSocket 架构，不重写；收敛为单用户、单管理员认证模式。
>
> 安全原则：**单用户 ≠ 无鉴权**。除明确列入公开白名单的健康检查、登录等端点外，敏感 REST API 与 WebSocket 必须经过有效会话认证。

## 1. 背景与审计基线

项目当前前端已具备完整的工程骨架和主要业务页面，重写无法带来与成本相称的收益，反而会放大 API 回归、实时链路回归和部署风险。因此本方案采用“保留架构、收敛认证、修正契约、补齐质量门禁”的渐进式改进路线。

本方案基于本轮审计时点的已知基线，后续实施必须以相同命令重新留档：

| 检查项 | 审计结果 | 结论 |
| --- | --- | --- |
| TypeScript | `tsc --noEmit` 通过 | 类型工程可持续演进，无需改写技术栈 |
| 单元测试 | 历史审计：40 files；578 passed；1 skipped | 已有回归基础，认证收敛应修改而非抛弃测试；实施前必须重新生成带提交/工作区指纹的当前基线 |
| 生产构建 | build 通过 | Vite 构建链可用 |
| 覆盖率 | lines 38%（2601 / 6844） | 整体偏低，关键认证和核心业务流程需要定向补测 |

注意：这些数字是审计基线，不代表永久门槛；实施合并请求必须记录当次结果，且不得以删除有效测试来维持通过数。

### 1.1 本次后端代码盘点结论

本方案不是仅删除前端用户管理入口。当前后端仍实质支持多用户和多角色，必须同步改造：

- `backend/internal/models/models.go` 的 `User` 含 `Role`、`Enabled`，允许任意多行；业务实体本身没有 `owner_id/user_id/tenant_id`，因此本次无需归并节点、设备、通道、固件等业务数据，主要迁移对象是账户、Token、审计主体和角色授权。
- `backend/internal/api/handler_user.go` 暴露用户列表、详情、创建、编辑、删除、重置他人密码和当前用户改密；其中哈希与数据库错误处理也需一并收紧。
- `backend/internal/api/handler_auth.go` 按用户名查找任意用户，未拒绝 `Enabled=false`，登录返回 role；`SeedAdminUser()` 在空库无条件创建固定 `admin/admin123`。
- `backend/internal/api/middleware.go` 的 JWT 含 `user_id + role`，`JWTAuth()` 不查询账户当前状态，也没有会话版本；修改密码、禁用或删除用户后，旧 Token 直到 24 小时过期前仍可使用。
- 多个敏感 REST 路由使用 `RequireRole("admin")`；删除角色判断时若只移除中间件而未保留外层 `JWTAuth()`，会形成公开接口回归。
- `backend/internal/websocket/websocket.go`、`backend/internal/terminal/ws_handler.go` 和 `backend/cmd/server/main.go` 都依赖 role 做广播/命令授权，不能只改 REST。
- `backend/internal/api/routes.go` 当前公开 `/health`、`/metrics`、认证路由和固件下载；`/ping` 还在路由注册后公开返回驱动列表。公开边界必须在单用户迁移中重新固化。
- `OperationLog` 只有 `UserID/Action/Target`，当前代码未形成覆盖登录、密码修改、设备控制、OTA 和日志清理的统一审计写入链路。
- 现有 SQL 迁移脚本没有账户单主体迁移；生产仍依赖 GORM `AutoMigrate` 加字段，但破坏性删除、唯一主体约束和历史账户归档不能交给 `AutoMigrate` 隐式处理。

## 2. 当前架构与功能边界

### 2.1 保留的前端架构

当前分层合理，应原位演进：

- **视图层**：Vue 3 单文件组件，Element Plus 提供通用交互组件。
- **路由层**：Vue Router 管理登录页、主布局、业务页、错误页及导航守卫。
- **状态层**：Pinia 管理用户、节点、边缘设备、通道、固件、主题和 WebSocket 等状态。
- **访问层**：Axios 统一 API base URL、JWT 注入、响应处理和 401 跳转。
- **实时层**：WebSocket store 负责连接、鉴权、订阅、心跳和指数退避重连。
- **质量层**：TypeScript、Vitest、Vite，以及已有 Playwright E2E。

不引入第二套状态库、HTTP 客户端或实时通信框架；认证模式变化不应侵入各业务页面的数据流。

### 2.2 已覆盖的主要功能

现有页面覆盖登录、仪表盘、节点列表/详情、边缘设备列表/详情、通道、数据面板、固件、配置模板、系统监控、个人设置和用户管理，并包含 BMS、逆变器等设备专用详情组件。

功能边界应区分三类：

1. **保留并继续维护**：设备观测、配置、控制、OTA、监控、日志、实时数据与个人密码修改。
2. **因单用户模式移除**：用户列表、创建/编辑/删除用户、角色选择、他人密码重置、按角色隐藏菜单或按钮。
3. **尚缺业务 UI、不能误报为已完成**：已有 API 模块但缺乏清晰的一等页面入口或完整闭环的能力，例如 `dataSource.ts`、`vendor.ts`、`homeassistant.ts`、`notification.ts` 等对应的数据源管理、厂商/型号管理、Home Assistant 同步和通知中心业务 UI。是否建设这些页面需进入独立产品需求，不与认证清理混做。

### 2.3 公开与敏感边界

建议公开白名单仅包含：

- 登录及必要的首次初始化状态查询/提交；
- `/health`；
- `/metrics` 是否公开由部署边界决定，互联网暴露时必须收紧；
- 固件下载若确需供设备无 JWT 拉取，应采用签名 URL、短时令牌或网络隔离，不能仅因历史实现而视为天然安全。

其余业务读取、修改、控制、日志、监控、OTA、通用 WebSocket、终端 WebSocket均为敏感能力，必须登录。

## 3. 目标与非目标

### 3.1 目标

- 将 `admin / operator / viewer` 三级 RBAC 收敛为**唯一管理员主体**。
- 保留登录、JWT、bcrypt（或等强密码哈希）、登录限流/锁定、Token 过期、401 处理和审计。
- 删除多用户 CRUD、前端 `meta.roles`、`v-permission`、角色 getter/菜单过滤和 `/403` 角色分支等冗余。
- 使用明确、统一、可验证的 API envelope 和 TypeScript 类型，减少 `any` 与重复解包。
- 修复 WebSocket URL 拼接和错误状态可观测性，保持实时事件协议兼容。
- 分阶段实施，每阶段可独立验证和回滚，不覆盖当前未提交工作。

### 3.2 非目标

- 不重写 Vue 应用，不迁移 React，不替换 Pinia、Axios、Vue Router 或 WebSocket。
- 不在本项目内建设组织、租户、团队、细粒度 ACL 或多管理员协作。
- 不因只有一个用户而取消密码、JWT、Token 过期、限流或敏感接口鉴权。
- 不在认证改造中顺带重构全部业务页面、全部 API 或全部 `any`。
- 不承诺本方案提及的缺失业务 UI 自动进入当前版本；应单独排期。
- 不默认实现 refresh token；是否需要长期会话应由威胁模型和部署场景决定。

## 4. 单用户认证模型设计

### 4.1 身份与数据模型

系统在任一时刻只有一个可登录主体，语义名称为 `system_admin`。实现上可暂时复用现有 `users` 表中的一行，以降低迁移风险，但必须建立唯一性约束或应用级不变量：

- 有且仅有一条系统管理员记录；
- 不再接受客户端提交 `role`，历史记录统一归一为 `admin`，新 Token 可逐步移除 role claim；
- 禁止通过通用 CRUD 新增、删除或切换其他用户；
- 管理员 ID 是稳定主体标识，用户名可配置但不作为权限依据；
- 密码只存强哈希，不记录明文、可逆密文或日志片段。

推荐先保留 `role=admin` 数据列和 JWT claim 一个兼容周期，再在后续数据库版本中删除。授权判断从“角色匹配”改为“有效认证主体”，敏感操作仍由统一 `JWTAuth`/`RequireAuthenticated` 中间件保护。

### 4.2 初始化

初始化必须避免固定生产口令：

1. 安装迁移必须显式创建固定 `AuthState=uninitialized`；运行时缺少该行一律视为 `migration_required`，不得根据账户是否存在推导未初始化。
2. 只有 `AuthState=uninitialized` 才生成一次性初始化令牌，并通过本机受信流程设置用户名和强密码。
3. 初始化端点只在 `uninitialized` 状态可用；成功后原子创建唯一管理员并永久关闭该入口。
4. 初始化成功写审计事件，不记录密码和完整一次性令牌。
5. 开发/测试环境如保留 `admin/admin123`，必须显式受环境开关约束，生产模式启动时检测到默认口令应失败或高危告警。

不要让“数据库为空即自动创建已知默认口令”成为生产恢复方式。

### 4.3 登录

- `POST /api/v1/auth/login` 接受用户名和密码，返回统一 envelope：`{ code, message, data: { token, expires_at, user } }`。
- 无论用户名不存在、密码错误、账号禁用，外部统一返回“用户名或密码错误/无法登录”，避免枚举；内部审计保留原因。
- 服务端按来源 IP 与账号标识组合限流，并设置全局保护；前端倒计时只能改善体验，不能替代服务端限流。
- 成功后签发短期 JWT，至少包含 `sub`、`iat`、`exp`、`jti`；若兼容期保留 `role`，固定为 `admin` 且不作为新前端分支依据。
- 客户端“记住我”只决定 localStorage/sessionStorage；应明确 XSS 风险。条件允许时优先迁移到 `HttpOnly + Secure + SameSite` Cookie。
- 登录成功/失败/限流必须进入审计日志；失败日志不得包含密码。

### 4.4 修改密码

保留自助接口，例如 `POST /api/v1/users/me/change-password`，后续可语义化迁移为 `/api/v1/account/password`：

- 必须携带有效会话并校验旧密码；新密码执行长度、弱口令和与旧密码不同等策略。
- 使用 bcrypt/Argon2id 等强哈希；哈希失败必须终止更新，禁止忽略错误。
- 成功后必须在同一数据库事务内更新密码哈希、`password_changed_at` 并原子递增 `session_version`；旧 Token 因版本不匹配立即失效。`password_changed_at` 仅用于审计和显示，不作为 Token 撤销依据；当前会话要求重新登录。
- 写入 `auth.password.changed` 审计事件，不记录旧/新密码。
- 删除“管理员重置其他用户密码”接口和 UI；紧急恢复走受控的本机 CLI/一次性恢复令牌流程，并记录审计。

### 4.5 禁用与恢复策略

单用户系统若允许管理员在 UI 中禁用自己，会造成永久锁死。建议：

- 普通 Web UI 不提供“禁用管理员”开关。
- 运维可通过配置或本机管理命令进入 `disabled` 状态，用于设备移交、安全事件或维护。
- 禁用后拒绝新登录，并通过会话版本使现有 Token 立即失效。
- 恢复只能通过主机本地、受保护的部署密钥或一次性恢复流程执行，不提供匿名远程“恢复”接口。
- 恢复动作必须可审计；若审计存储不可用，恢复流程应输出明确的本地安全日志。

### 4.6 会话模型

- Access Token 必须有明确过期时间；推荐默认 8–24 小时，按部署环境配置，禁止永不过期。
- 前端启动时不能只以“storage 中有字符串”判定已登录；应校验 Token 基本格式/过期时间，并通过 `/api/v1/account`（或兼容的当前用户接口）确认服务端状态。
- 401 时统一清理 token、user 和 WebSocket，保留原目标路由用于重新登录后返回；避免多请求并发触发重复跳转。
- 登出语义定稿为全局撤销：服务端原子递增 `session_version`，同一管理员的全部 REST Token 和两类 WebSocket 立即失效并断开；本项目不引入 per-token denylist。仅返回 200 的无状态 logout 禁止存在。
- 修改密码、禁用、恢复密钥轮换后必须使旧 Token 失效。
- WebSocket 与 REST 共享同一认证语义；连接建立时验证 Token，过期后服务端关闭连接，前端停止无效重连并引导登录。

### 4.7 审计

至少记录：初始化成功/失败、登录成功/失败/限流、登出、密码修改、禁用/恢复、Token 拒绝、重要设备控制、配置变更、OTA 和日志清理。每条包含时间、事件名、主体 ID、来源、结果、关联请求 ID 和必要的目标摘要。

审计日志不得记录密码、完整 JWT、初始化/恢复令牌或敏感请求体。单用户不代表不需要追责：仍需区分“管理员操作”“系统后台动作”“设备动作”。

### 4.8 安全边界

- **单用户 ≠ 无鉴权**：删除 RBAC 只删除角色分叉，不删除身份验证。
- 前端隐藏按钮从来不是安全边界；后端必须保护所有敏感端点。
- `/api/v1` 默认鉴权，公开端点使用显式白名单而不是逐个补保护。
- WebSocket query token 可能进入代理访问日志；优先使用安全 Cookie、短时 WS ticket 或首帧认证，并确保 URL/日志脱敏。
- 限流、CORS、CSRF（Cookie 模式）、安全响应头、TLS 和反向代理配置属于整体边界，不能只靠 Vue 守卫。
- 固件下载、Prometheus metrics 等历史公开端点必须重新做部署级威胁评审。

本项目当前公开路由需要在实施前逐项决策并固化：

- `/health`：保持公开，但只返回存活状态，不返回依赖、驱动、版本或账户状态。
- `/ping`：当前公开并返回版本和驱动列表；应移入 authenticated API 或缩减为与 `/health` 等价，不能继续泄漏能力清单。
- `/metrics`：生产默认不公开；仅允许反向代理内网 allowlist、独立认证或禁用。开发环境显式开放。
- 固件下载：ESP32 无浏览器 JWT 时使用短时签名 URL/设备下载票据，至少绑定 firmware ID、过期时间和签名；不能永久匿名下载任意固件。
- `/api/v1/auth/initialization`、`initialize`、`login`：公开但单独限流；logout 属于 authenticated，不应继续注册在完全公开组。
- 通用 WS 和终端 WS：全部 authenticated；query token 仅兼容，目标使用短时 WS ticket 或安全 Cookie/首帧认证。

跨域边界定稿为生产默认同源：

- REST CORS 仅允许显式 `EHOME_ALLOWED_ORIGINS` allowlist；`AllowCredentials=true` 时禁止 `*` 或任意 Origin 回调。配置为空时生产仅同源，配置含通配符时拒绝启动。
- 通用 WS 与终端 WS 共用同一 Origin 校验器；浏览器请求必须命中 allowlist。缺失 Origin 只适用于携带独立设备/CLI 凭据的非浏览器客户端，不能仅因无 Origin 放行浏览器会话 Token。
- 本次仍使用 Bearer Token 时同步防止跨站 WS 劫持；未来切换 Cookie 必须另行加入 CSRF token、SameSite 和 Origin/Referer 联合校验，不能只改 Token 载体。
- `EHOME_DEV_BYPASS_AUTH` 目标为删除。过渡期若保留，必须同时满足专用开发构建标志、监听地址为 loopback、`GIN_MODE=debug`、`EHOME_ENV=development` 和显式开关；Release/生产任一检测到开关即拒绝启动，而不是仅记录警告。
- 开发自动管理员和鉴权 bypass 是两个独立危险能力，均不得由“GIN_MODE 未设置”隐式开启。

### 4.9 后端唯一主体模型（定稿建议）

后端保留账户表，但它不再表示“用户集合”，而表示唯一系统管理员凭据。推荐兼容期沿用表名 `users`，最终是否改名为 `system_account` 由后续结构清理 ADR 决定，不能在第一阶段同时改表名和认证语义。

兼容期 `User` 模型新增：

- `SubjectKey *string`：活动主体固定为 `system_admin`；兼容期 retired 历史账户为 `NULL`。
- `RetiredAt *time.Time`：历史非保留账户的归档/停用标记；登录永远只查询 `subject_key='system_admin' AND retired_at IS NULL`。
- `SessionVersion int64`：数据库映射正整数 `BIGINT`，初始为 1；修改密码、禁用、恢复、凭据轮换和“登出所有会话”时原子递增。写入/签发前校验 `1 <= value < MaxInt64`，达到上限时拒绝继续签发/递增并进入受控恢复，禁止溢出回绕。
- `PasswordChangedAt *time.Time`、`LastLoginAt *time.Time`：支持会话撤销和安全审计。
- `InitializedAt *time.Time`：记录账户创建时间，但系统是否曾初始化不能只由账户行是否存在决定。

另建固定单行的 `AuthState`（例如主键 `system_auth`），保存 `State`（`uninitialized/initialized/migration_required/disabled`）、初始化完成时间和安全状态版本。该记录一旦进入 `initialized` 不得因账户行被误删而回到 `uninitialized`；账户缺失但 AuthState 已初始化时必须 fail-closed 进入恢复流程。

兼容期保留 `Role` 列但统一写成 `admin`，新代码不再读取它作授权依据；`Enabled` 仍保留为账户状态。业务表没有用户归属字段，本次不新增伪造的 `owner_id`，也不迁移节点/设备等业务数据。

数据库不变量：

1. 数据库增加 `CHECK (subject_key IS NULL OR subject_key='system_admin')`，并增加 `UNIQUE INDEX ... WHERE subject_key='system_admin' AND retired_at IS NULL`，保证最多一个活动主体且不允许第二种主体键；
2. 初始化事务在插入前后都验证当前不存在主体，以数据库唯一冲突作为最终并发闸门；
3. 新部署的安装 migration 显式插入固定主键 `system_auth` 和 `uninitialized`；应用运行时缺少 AuthState 一律进入 `migration_required`，绝不能自行创建或推导 `uninitialized`；
4. `AuthState=initialized` 但活动主体为 0/多于 1、主体键异常、或迁移版本不完整时均进入 `migration_required` 并拒绝登录；
5. 应用数据库角色无权 DELETE 固定 AuthState；数据库触发器/权限阻止删除或修改其固定主键；
6. 状态机只允许：安装 migration→uninitialized；本机令牌初始化事务→initialized；异常检测→migration_required；本机恢复→initialized/disabled。不存在任何 HTTP 或运行时路径回到 uninitialized；
7. 破坏性删除 role/多余账户放在兼容观察期后，由显式 SQL migration 完成，GORM `AutoMigrate` 只负责非破坏性加列。

#### 4.9.1 认证状态机与权威关系

`AuthState` 是系统级认证状态的唯一权威，`User.Enabled` 只表示在 `AuthState=initialized` 前提下该唯一账户是否允许登录，不能独立打开认证能力。所有状态变化由 auth service 在数据库事务内使用行锁/CAS 完成，普通 handler 不得直接更新状态字段。

| AuthState | 活动主体数量 | Enabled | 行为 |
| --- | ---: | ---: | --- |
| `uninitialized` | 0 | — | 仅允许受控初始化；出现任意账户即转 `migration_required` |
| `initialized` | 1 | true | 正常登录和鉴权 |
| `initialized` | 1 | false | 拒绝登录和 Token，进入本机恢复/启用流程 |
| `initialized` | 0 或 >1 | 任意 | fail-closed，转 `migration_required` |
| `migration_required` | 任意 | 任意 | 拒绝登录和远程初始化，只允许只读健康检查与本机迁移/恢复 |
| `disabled` | 1 | 任意 | 拒绝登录和全部既有会话，只允许本机恢复 |
| 缺少固定 AuthState 行 | 任意 | 任意 | 等同 `migration_required`，应用不得补建 |

`GET /auth/initialization` 返回枚举必须包含 `disabled` 和 `migration_required`，但不返回账户数量、用户名或冲突细节。状态变更使用 `SELECT ... FOR UPDATE` 或带版本条件的 CAS；并发状态更新只有一个成功。

### 4.10 JWT 与会话版本（定稿建议）

新 JWT 使用标准 claim：

```text
sub = 唯一管理员稳定 ID
iat = 签发时间
exp = 过期时间
jti = 随机 Token ID
sv  = 签发时 session_version
iss = ehome
aud = ehome-api
```

兼容期可以继续携带 `user_id` 和固定 `role=admin`，但服务端授权不得依赖 role。为保证“即时撤销”，每次 REST 鉴权和每个敏感 WS 入站命令直接读取权威数据库中的唯一主体/AuthState/session_version；本阶段禁止用有 TTL 的正向缓存作为授权依据，并验证：

- 主体存在且 `Enabled=true`；
- Token `sub/user_id` 等于唯一主体；
- Token `sv == user.session_version`；
- 初始化状态为 initialized。

任一不满足统一返回 401。REST 和两类 WebSocket 握手使用同一验证器；WebSocket 建连后至少在敏感入站命令前重新检查会话版本，密码修改/禁用时还应主动关闭该主体的现有连接。这样可以在不维护无限 denylist 的情况下立即撤销全部旧 Token。

多实例撤销定稿为“权威数据库 + 撤销事件加速 + 周期兜底”：撤销事务提交 `session_version` 后写持久化 outbox；各实例消费 outbox/Redis 通知并按主体断开连接。Redis/PubSub 只用于加速，不是授权真相；通知丢失时，WS 在每个敏感入站消息、每次敏感广播发送前、心跳周期以及到达 `exp` 的服务端定时器上回源复核。数据库不可达或无法确认最新版本时，敏感 REST/WS 操作和敏感广播均 fail-closed。

Token 格式和升级策略定稿如下：

- 兼容迁移 A 上线即使所有旧 JWT 失效并要求重新登录；兼容只保留新登录响应里的固定 `role=admin` 字段，不接受缺少 `sub/sv/jti/iat/exp/iss/aud` 的旧 Token。
- 签名算法固定为 `HS256`，验证器必须精确拒绝其他 HMAC、非 HMAC 和 `alg=none`；强制验证 `iss=ehome`、`aud=ehome-api`。
- `sub` 固定为十进制账户 ID 字符串；`jti` 使用密码学安全随机值；允许的时钟偏差必须配置且有上限（建议不超过 60 秒）。
- PostgreSQL `session_version` 使用正整数 `BIGINT`；Go 使用可验证范围的 `int64`。递增必须使用单条 `UPDATE ... SET session_version=session_version+1 ... RETURNING session_version`，禁止读后写导致并发丢失。
- 这是一次计划内全局会话失效，必须进入 release notes 和升级提示；前端收到首次 401 后统一清理并要求重新登录。

`GenerateToken(userID, role)` 先增加新签名函数（例如 `GenerateSessionToken(account)`），旧函数仅保留一个兼容周期并标记 deprecated；最终删除 role 参数和 Claims.Role。

### 4.11 后端账户 API 目标契约

目标 API 只保留单主体操作：

| 方法 | 路径 | 鉴权 | 语义 |
| --- | --- | --- | --- |
| `GET` | `/api/v1/auth/initialization` | public，严格限流 | 返回 `initialized/uninitialized/migration_required/disabled`，不返回用户数量、用户名或冲突细节 |
| `POST` | `/api/v1/auth/initialize` | 仅 uninitialized + 一次性令牌/本机受信通道 | 原子创建唯一管理员 |
| `POST` | `/api/v1/auth/login` | public，IP+账号限流 | 登录唯一管理员，错误统一 |
| `POST` | `/api/v1/auth/logout` | authenticated | 原子递增 session_version，全局撤销全部 Token 并断开两类 WS |
| `GET` | `/api/v1/account` | authenticated | 返回当前唯一账户的可展示字段，不返回 role 分支 |
| `PATCH` | `/api/v1/account` | authenticated | 仅更新用户名/邮箱等允许字段，不允许 role/enabled |
| `POST` | `/api/v1/account/password` | authenticated | 校验旧密码并修改，事务内递增 session_version |
| `POST` | `/api/v1/account/logout-all` | authenticated | 原子递增 session_version，关闭现有 WS |

状态与错误契约：

| 条件 | HTTP | 业务码 |
| --- | ---: | --- |
| 未初始化访问普通认证/业务接口 | 503 | `AUTH_NOT_INITIALIZED` |
| `migration_required` | 503 | `AUTH_MIGRATION_REQUIRED` |
| `disabled` 登录或鉴权 | 401 | 对登录外部仍使用统一凭据错误；内部审计记 `ACCOUNT_DISABLED` |
| Token 缺失、格式错误、过期、旧 sv | 401 | `AUTH_INVALID_SESSION` |
| 旧 users API 无 Token | 401 | 认证优先，不泄漏接口状态 |
| 旧 users API 有效 Token（兼容期） | 410 | `MULTI_USER_API_REMOVED`，附 `Deprecation/Sunset/Link` |

`GET/PATCH /account` 的 DTO 只包含稳定 ID、用户名、邮箱、enabled 展示状态和时间字段；兼容期可返回固定 role，但前端不得分支。PATCH 采用字段白名单、用户名 trim/规范化、唯一冲突 409 和可选 ETag/version 防覆盖，不允许写 subject_key、session_version、role、enabled 或 retired 字段。

兼容期 `/api/v1/users/me/change-password` 可代理到新改密服务并返回弃用头；其余旧接口必须停用：

- `GET/POST /api/v1/users`
- `GET/PUT/DELETE /api/v1/users/:id`
- `POST /api/v1/users/:id/reset-password`

过渡版本固定返回 `410 Gone` 和稳定业务码 `MULTI_USER_API_REMOVED`，不得把旧“修改某用户”语义偷偷映射为修改唯一管理员。观察期结束后再注销路由。

密码服务必须统一检查：bcrypt 生成错误、数据库更新错误、事务提交错误、最低长度/弱口令、与旧密码相同；任一失败不得修改 session version。成功后密码哈希与 `session_version+1` 必须在同一事务提交。

### 4.12 REST 授权去角色化

当前 `/api/v1` 路由组已经统一使用 `JWTAuth()`；目标是保留这一默认鉴权边界，并删除组内重复的 `RequireRole("admin")`，而不是删除认证。执行规则：

- `RequireRole("admin")` 替换为无需额外中间件，或在确需显式表达时使用只断言上下文已有有效主体的 `RequireAuthenticated()`；
- Vendor、DeviceModel、EdgeDevice 写操作、驱动命令、节点日志等原 admin-only 端点继续位于受保护的 `/api/v1` 组内；
- 单独注册的终端 WS 必须继续显式挂载 `JWTAuth()`；
- 新路由默认注册到受保护组；public 路由只能加入集中白名单，并有无 Token 测试；
- 删除 role 后不再存在 403 角色不足分支：未认证/会话失效为 401，已认证后的业务拒绝使用 409/422/423 等业务状态，不能继续伪造角色 403。

### 4.13 WebSocket 去角色化

通用 WS、终端 WS 和日志广播必须整体迁移：

1. `websocket.Client` 保留稳定主体 ID 和会话版本，删除 `Role`；广播消息删除 `targetRole`。
2. `BroadcastEventToRole(..., "admin")` 改为语义明确的 `BroadcastAuthenticatedEvent`（外部仅发给已认证且会话仍有效的客户端）；内部 subscriber 继续独立接收，不能因外部客户端状态提前 return。
3. `terminal.termClient` 删除 role；既然握手已通过唯一主体认证，`send` 命令不再做 admin 字符串判断，但仍需 payload 校验、设备/通道存在性、限流和审计。
4. `backend/cmd/server/main.go` 的通用 WS `send` 回调删除 `client.Role != "admin"`，改为验证 authenticated subject/session；不允许仅凭非空 UserID 长期授权。
5. 密码修改、禁用、session_version 增加时，Hub 按主体断开通用和终端 WS；客户端收到 401/认证关闭码后停止无效重连并回到登录页。
6. 对 role-filter 广播、admin-only send 的旧测试改写为“未认证拒绝、有效唯一主体允许、旧 session version 拒绝、内部 subscriber 不受外部过滤影响”。

两类 WS 共用强类型 `AuthenticatedSubject{SubjectID, SessionVersion, ExpiresAt, JTI}`、同一个 session validator 和跨实例 SessionRegistry。握手注册 subject/version/exp；服务端为每条连接设置到 `exp` 的关闭定时器，并在 session version bump 事件后按主体断连。认证失效统一使用应用关闭码（例如 4401，具体值在协议 ADR 固化）和稳定 reason；前端收到后清会话并停止自动重连，只有重新登录后才能新建连接。

通用 WS `send` 与终端 WS `send` 两条路径必须同时执行：会话版本复核、payload 大小/字段/hex 校验、设备与通道存在性校验、并发/速率限制和安全审计。内部 subscriber 与外部认证客户端使用不同分发分支；外部授权失败不得阻止内部 subscriber 收到事件。

### 4.14 安全初始化与恢复流程

推荐采用“本机 CLI 生成一次性初始化令牌 + HTTP 完成初始化”的明确方案：

- 后端空库启动不再调用 `SeedAdminUser()`，更不能生成 `admin123`；服务可启动，但除 `/health` 和初始化相关端点外，认证业务端点返回初始化状态错误。
- 运维在主机执行管理命令生成随机高熵、短时、单次令牌；数据库只保存令牌哈希、过期时间和使用状态，日志只输出指纹。
- `POST /auth/initialize` 同时提交令牌、用户名和强密码；事务中消费令牌并创建 `subject_key=system_admin`，任一步失败整体回滚。
- 初始化成功后将独立 `AuthState` 原子更新为 initialized，入口永久关闭；删除账户数据不能重新开启初始化，避免远程接管。
- 紧急恢复使用独立本机命令，验证主机权限后重置密码并递增 session_version；不提供匿名网络恢复接口。
- 开发环境若需要自动账号，必须由 `EHOME_DEV_SEED_ADMIN=true` 明确开启，并要求密码来自环境变量；生产/Release 模式检测到此开关或已知默认密码必须拒绝启动。

初始化令牌存储在独立表中，至少包含公开随机 `selector`、secret hash、created_at、expires_at、consumed_at、attempt_count 和创建来源；原始凭据格式为 `selector.secret`，selector 只用于定位记录、不具备认证能力，secret 使用密码学安全随机数且只由本机 CLI 在创建时输出一次。数据库只保存 secret hash。完整凭据不得进入 URL、访问日志、普通日志或审计 metadata。HTTP 只在正文提交凭据；服务端先按 selector 定位，再使用恒定时间比较 secret hash。TTL 建议 10 分钟，单次消费，失败尝试有上限；同一 selector 的失败计入该令牌，无法解析/不存在的 selector 计入独立的 IP+全局初始化限流器，不能任意归到某条令牌记录。

失败尝试计数不属于初始化原子事务：selector 命中但 secret 不匹配、令牌已过期或已消费时，先用独立短事务/单条原子 SQL 持久化该记录的 `attempt_count=attempt_count+1`（必要时锁定/作废令牌），再返回统一失败；selector 缺失、格式错误或不存在时原子递增 IP+全局初始化限流桶。两类计数都不能因后续请求回滚而丢失。只有 selector 命中且 secret 验证成功后，才进入下面的初始化事务。

初始化事务顺序固定为：获取 advisory lock → `SELECT AuthState FOR UPDATE` → 验证 state=uninitialized → 再次验证并锁定已通过预检且未消费的令牌 → 验证无活动主体 → 创建账户 → 消费令牌 → 写关键安全审计 → 更新 AuthState=initialized → commit。此事务内任一步失败，账户创建、令牌消费、关键审计和 AuthState 更新全部回滚；前述独立持久化的失败尝试计数不回滚。`ehomectl auth bootstrap-database` 是唯一可为经人工确认的全新数据库运行安装 migration/创建 uninitialized 状态的入口；生产环境识别使用显式 `EHOME_ENV=production`/构建配置，禁止以 GIN_MODE 未设置推导开发环境。

### 4.15 登录限流与账户状态

服务端登录保护不能依赖前端 `loginLockout.ts`：

- Redis 可用时按 `IP`、规范化用户名及 `IP+用户名` 三个维度计数；Redis 不可用时使用进程内有界 TTL 退化保护，不能完全 fail-open。
- 返回统一凭据错误，不区分用户名不存在、密码错误、禁用或迁移阻塞；限流返回 429 和 `Retry-After`。
- 只有唯一主体且 `Enabled=true`、初始化完成、密码正确时签发 Token；成功登录重置相关失败桶并更新 `LastLoginAt`。
- 记录登录成功、失败类别、限流和 Token 拒绝审计，但对外响应及普通日志不得泄漏是否存在账户。

### 4.16 审计模型完善

安全审计定稿为新增 append-only `security_audit_events`，不对现有 `OperationLog` 做高风险原地重构；旧表保留用于历史兼容。新表至少包含 `actor_type`、nullable `actor_user_id`、`actor_snapshot`、`event_name`、`event_version`、`result`、`request_id`、`source_ip`、`target_type/target_id`、受控 metadata 和 UTC 时间。request ID 由可信服务端中间件生成；只有在显式可信代理 allowlist 下才读取转发来源 IP。

必须审计初始化、登录、限流、登出、改密、全局撤销、恢复、Token 拒绝、设备控制、终端写、配置同步、OTA 和日志清理。审计写入规则分级：

- 初始化、恢复、密码修改和会话撤销：审计写入与状态变更在同一事务，失败则关键操作失败；
- 高频设备数据不进入安全审计；
- 普通控制操作若审计存储暂时失败，至少写结构化安全日志和指标，并明确告警，不能静默吞掉。

登录失败和 Token 拒绝审计必须限频/聚合，避免攻击者制造无界数据库写放大；清理 retired 账户前，先保证相关历史事件已固化 actor snapshot。

安全审计与 ESP32/设备运行日志属于两个独立存储和保留域。节点日志清理、普通日志清理和管理员 UI 均无权删除安全审计。审计表采用 append-only 数据库权限：应用审计写入角色只有 INSERT/SELECT 所需权限，无 UPDATE/DELETE；归档由独立受控运维角色执行。

审计记录固化 `actor_id`、操作时用户名快照、actor type、事件 schema version、request ID、来源、结果和受控 metadata schema。metadata 使用事件白名单，不接收任意请求体。建议在线保留不少于 180 天，之后按部署策略归档到只追加对象存储并保存批次哈希/签名；具体期限允许配置，但不得小于安全基线且必须有容量告警。

审计读取/导出只允许当前有效唯一主体，导出本身也写审计；接口永不返回密码哈希、Token、初始化/恢复令牌或未脱敏请求体。容量耗尽或 append-only 审计写入失败时：初始化、恢复、改密、撤销继续 fail-closed；普通控制操作按前述结构化安全日志降级并触发高优先级告警。增加数据库权限篡改、UPDATE/DELETE 拒绝、容量耗尽、归档恢复和读取越权测试。

## 5. 已发现问题及代码证据

以下为设计输入，不要求在本方案文档提交中修改代码。

### 5.1 WebSocket token URL 拼接存在双路径风险

`frontend-shared/src/stores/websocket.ts` 默认 `VITE_WS_URL || '/api/v1/ws'`；当配置值已经是完整 `ws://` 或 `wss://` URL 时，又执行 `` `${wsUrl}/api/v1/ws` ``。若环境变量已经指向端点（例如 `wss://host/api/v1/ws`），结果会重复为 `/api/v1/ws/api/v1/ws`。

应明确环境变量契约：推荐 `VITE_WS_URL` 表示**完整端点**，完整 URL 原样使用；仅相对路径才基于当前 origin 组装。为 base URL 与 endpoint URL 分别命名也是可选方案。

### 5.2 API envelope 契约不统一

- `frontend-shared/src/api/client.ts` 成功拦截器返回 `response.data`，即业务 envelope。
- `frontend-shared/src/api/auth.ts` 再通过 `post<unknown, any>` 和 `(response as any).data` 解包。
- `edgeDevice.ts`、`driver.ts`、`parser.ts`、`notification.ts` 等存在各自的 envelope 兼容/猜测。
- 后端 `backend/internal/api/envelope_test.go` 的注释和用例显示端点历史上存在 envelope 与 bare array 并存。

这会造成调用方不知道拿到 AxiosResponse、envelope 还是业务 data。应选择一种全局契约：建议 client 统一返回 `ApiEnvelope<T>`，API 模块在单一 helper 中解包为 `T`；错误也使用统一结构。

### 5.3 WebSocket `lastError` 契约缺失

`frontend-shared/src/components/common/NetworkBanner.vue` 读取 `wsStore.lastError`，但当前 `frontend-shared/src/stores/websocket.ts` 未声明/导出该状态，仅在 `onerror` 中写日志并设置 `connected=false`。这会导致错误横幅与 store 契约脱节，也无法区分“未登录”“连接中”“网络错误”“鉴权过期”。

应增加有类型的连接状态和脱敏错误对象，并在成功连接、主动断开、认证失败时按规则清理。

### 5.4 `any` 削弱关键边界类型

已见于：

- `websocket.ts` 的消息 payload、flat data 和 `send(data: any)`；
- `auth.ts` 的登录响应；
- `edgeDevice.ts` 的多个 API 返回值；
- `parser.ts`、`driver.ts` 的 normalize/envelope；
- `channel.ts` store 的响应分支；
- 通用格式化函数及部分异常处理。

不要求“一次清零”，但认证响应、API envelope、WebSocket 事件联合类型应优先改为 `unknown` + 类型收窄，避免服务器契约漂移在运行时才暴露。

### 5.5 lint 与覆盖率门禁不足

`frontend-shared/package.json` 有 typecheck、build、test、coverage、e2e，但没有 lint 脚本；覆盖率汇总 lines 为 38%，且部分关键大型页面/组件覆盖率极低或为 0。单纯追求总体百分比容易被工具函数稀释，应先设置关键文件阈值与增量覆盖率。

建议引入 ESLint（Vue + TypeScript）、禁止新增显式 `any` 的渐进规则、未处理 Promise/无效模板检查；CI 首先“只阻止新增问题”，再分阶段提高门槛。

### 5.6 多角色与多用户冗余遍布前后端

证据包括：

- `frontend-shared/src/stores/user.ts`：`UserRole`、`ROLE_LEVEL`、`isAdmin/isOperator/isViewer/hasRole`；
- `frontend-shared/src/router/index.ts`：`meta.roles` 与 403 分支；
- `frontend-shared/src/directives/permission.ts` 及其测试；
- `frontend-shared/src/views/layout/MainLayout.vue`：菜单角色过滤；
- `frontend-shared/src/views/admin/UserList.vue` 与 `frontend-shared/src/api/user.ts`：多用户 CRUD、重置密码；
- `backend/internal/api/handler_user.go`：列表、创建、编辑、删除、角色字段和重置他人密码；
- `backend/internal/api/middleware.go` 与多个 handler：`RequireRole("admin")`。

清理时必须将 `RequireRole("admin")` 替换/归并为认证要求，而不是直接移除中间件后公开端点。

### 5.7 登录安全能力存在前后端错位

`frontend-shared/src/utils/loginLockout.ts` 提供客户端失败计数/锁定体验，但客户端状态可被清理或绕过；当前登录 handler 展示了密码哈希校验和 JWT 签发，却未从所见代码确认登录端点具备服务端账号/IP 限流，也未在登录流程中看到 `enabled` 拒绝检查。实施前需补充后端证据或按缺口修复。

此外，`backend/internal/api/handler_auth.go` 当前空库会生成固定 `admin123`，且登录响应类型不含前端 `LoginResponse` 声明的 `email`，是初始化安全与契约一致性的直接改进点。

### 5.8 缺失业务 UI

API 模块数量大于清晰的一等业务页面范围。当前视图目录中未见与数据源、厂商/型号、Home Assistant 同步、通知中心一一对应的完整管理页。处理原则：

- 先确认 API 是否仍为受支持产品能力；
- 有需求则单独建立页面、路由、状态、错误/空态和 E2E；
- 无需求则标记内部 API 或废弃，不在导航中制造半成品入口；
- 不以“认证简化”为由删除这些业务 API。

## 6. 优先级

### P0：安全与正确性，进入单用户模式前完成

1. 固化公开白名单与“其余默认鉴权”，验证所有敏感 REST/WS 无 Token 返回 401。
2. 设计安全初始化，生产环境停止自动使用已知默认口令。
3. 服务端登录限流、账号禁用检查、通用错误响应和安全审计。
4. 统一登录/API envelope，修复前后端字段差异与 401 会话清理。
5. 修复 WebSocket 完整 URL 拼接、鉴权过期与 `lastError` 状态。
6. 制定现有多用户数据迁移规则，禁止直接删除导致不可恢复。

### P1：删除冗余并建立质量门禁

1. 移除前端 `meta.roles`、菜单角色过滤、`v-permission`、多角色 getter 及对应测试。
2. 移除用户管理页面/路由和多用户 API 客户端，保留“当前账号/修改密码”。
3. 后端停用多用户 CRUD、角色写入、重置他人密码；将 admin-only 统一为 authenticated-admin 语义。
4. 收紧认证、API envelope 和 WebSocket 的 `any`。
5. 引入 lint 与关键路径覆盖率/增量覆盖率门禁。

### P2：可维护性与产品完整度

1. 评估 Cookie 会话或短时 WS ticket，降低 URL token 与 storage 风险。
2. 按产品优先级补齐数据源、厂商/型号、HA、通知中心等业务 UI。
3. 提升大型低覆盖页面的组件化与交互测试。
4. 清理兼容期 role 列/claim、旧 `/users` 契约和 `/403` 页面。
5. 建立文档版本、ADR、API schema 和 WebSocket topic 治理。

#### 任务 0.3：WebSocket 基线修复

### 阶段 1：后端单主体认证

实施顺序按数据库兼容迁移 → 认证服务 → 路由/WS 去角色 → 旧 API 停用展开；每个任务先写失败测试。建议新增目录：

- `backend/internal/auth/`：唯一主体状态、初始化、密码策略、会话版本和登录限流服务；API handler 不直接拼接这些规则。
- `backend/internal/audit/`：统一审计写入器和敏感字段过滤。
- `backend/scripts/migrations/single_user_*.sql`：显式、可重跑、支持 dry-run/统计/回滚的账户迁移。
- `backend/cmd/ehomectl/`：初始化令牌生成、恢复和状态检查等仅主机运维命令。

不要把业务实体迁移到用户名下；当前节点、设备、通道等表没有用户归属，单主体模式下保持全局资源语义。

#### 任务 1.0：旧库盘点与兼容迁移

- 安装 migration 显式创建固定 `auth_state(system_auth, uninitialized)`；运行时缺失行只报 migration_required，不自动补建。数据库权限/触发器禁止应用删除固定行。
- 新增 nullable `subject_key`、`retired_at`、`session_version/password_changed_at/last_login_at/initialized_at`，以及 subject key CHECK + 活动主体 partial unique index。
- 提供 dry-run 查询：账户总数、每条 ID/用户名/角色/enabled/最近更新时间、OperationLog 引用数量；输出不得包含密码哈希。
- 0 账户的新部署创建 `AuthState=uninitialized`；1 账户的旧部署需要明确迁移确认后将其归一为 `system_admin`；多于 1 账户必须提供 `--keep-user-id`，未指定则退出，不能猜测。
- 未保留账户先导出归档，再设置 `subject_key=NULL/retired_at/disabled`；兼容观察期不硬删除。OperationLog 保留原 UserID 历史，不重写成保留管理员。
- 迁移在事务中执行，使用 advisory lock 防并发；支持重复运行并输出相同统计。
- 回滚只撤销新增约束/状态和 retired 标记，不恢复已签发 Token；回滚后仍需人工确认是否重新开放旧多用户登录。
- 保留主体预检必须验证 ID 存在、未 retired、密码哈希格式受支持；若原账户 disabled，是否重新启用必须由运维显式参数确认，不得自动启用。
- 兼容迁移开始后禁止旧后端与新后端滚动混跑；migration batch/version 是启动门禁。清理迁移 B 后只能通过加密全库备份和匹配的旧应用版本回滚。

#### 任务 1.1：安全初始化

- 增加 initialized 状态查询及受控初始化入口/本机命令。
- 原子创建唯一管理员，密码使用强哈希。

#### 任务 1.2：登录与限流

- 登录时校验管理员状态及凭据，外部错误信息统一。

## 8. 验收标准与建议验证命令

### 8.1 功能与安全验收

- [ ] 系统未初始化时只能通过受控流程创建唯一管理员；重复/并发初始化失败。
- [ ] 生产环境不存在自动可登录的固定默认密码。
- [ ] 正确密码可登录；错误用户、错误密码、禁用状态对外不泄漏差异。
- [ ] 服务端限流可验证，清浏览器 storage 不能绕过。
- [ ] JWT 过期后 REST 返回 401，WS 拒绝或关闭，前端清会话并跳登录。
- [ ] 修改密码要求旧密码；成功后旧 Token 失效并重新登录。
- [ ] 除明确公开白名单外，所有敏感 GET/POST/PUT/DELETE 和 WS 无 Token 均为 401。
- [ ] 前端不存在 `meta.roles`、`v-permission`、admin/operator/viewer 菜单分支和用户 CRUD 入口。
- [ ] 后端不存在可远程创建第二用户、删除唯一管理员或匿名恢复管理员的路径。
- [ ] 审计覆盖初始化、登录、限流、密码修改、禁用/恢复及敏感操作，且无密码/完整 Token。
- [ ] WS 配置为相对路径和完整 URL 时都只生成一个正确 `/api/v1/ws` 端点。
- [ ] API 模块对 envelope 的返回类型和解包方式一致。
- [ ] 数据库最多存在一个 `subject_key=system_admin`；并发初始化只有一个成功。
- [ ] `AuthState` 一旦 initialized，删除账户行也不会重新开放初始化；系统进入 fail-closed 恢复状态。
- [ ] 历史库含多账户时，未提供 `--keep-user-id` 的迁移必须失败且零写入；指定后归档非保留账户并保持 OperationLog 历史主体不变。
- [ ] `Role`、`RequireRole`、Gin context role、通用 WS Client.Role、终端 WS role 和 role-filter 广播在兼容期后均无生产代码依赖。
- [ ] 修改密码、禁用、恢复和 logout-all 后，旧 REST Token 立即 401，已连接的通用/终端 WS 被关闭，旧 session version 不能发送命令。
- [ ] 用户列表/CRUD/重置他人密码在过渡期统一返回 410，最终路由不存在；不能映射为修改唯一账户。
- [ ] 登录拒绝 disabled、migration_required 和旧 session version；外部错误不可区分账户是否存在。
- [ ] 登录限流由服务端执行；Redis 故障时仍有有界降级保护，清浏览器 storage 无法绕过。
- [ ] `/ping`、`/metrics`、固件下载与所有 auth/public 端点均进入公开白名单测试；未列入白名单的路由无 Token 全部 401。
- [ ] 通用/终端 WS 不再以 role 字符串授权，敏感 send 在握手和发送时均验证唯一主体会话。
- [ ] logout 后重放同一 Token 必须立即 401；多实例下撤销通知丢失/Redis 故障时，权威数据库复核和 WS 周期兜底仍阻止旧会话。
- [ ] AuthState 缺失、AuthState 与账户同时缺失、迁移半完成、应用重启均为 migration_required；任何远程路径都不能重建 uninitialized。

- [ ] 生产 REST/两类 WS 拒绝恶意 Origin；凭据 CORS 不允许通配符；开发 bypass 在 Release/非 loopback 环境拒绝启动。

## 9. 数据迁移、兼容与回滚

### 9.1 迁移前盘点

- 备份用户表、会话/撤销表和审计表，并验证恢复。
- 统计用户数量、角色、启用状态、最近登录和与审计记录的关联。
- 由部署负责人明确选定保留主体；若不止一名用户，不能由迁移脚本“取第一条”。
- 检查外部脚本、E2E、反向代理和设备是否依赖 `/users`、role claim、默认账号或 URL token。
- 对生产数据库执行只读 dry-run 并由部署负责人签署保留主体 ID；方案文档不得内置某个具体用户 ID。
- 备份必须包含 `users`、`operation_logs`、新增 `auth_state`/初始化令牌表及数据库 schema；恢复演练后才允许迁移。

### 9.2 建议迁移步骤

1. 先发布兼容后端：支持唯一主体语义，仍读取旧 role，但不再允许创建新用户。
2. 将选定管理员归一为 enabled + admin；其他用户标记 `retired`/禁用并导出存档，不立即硬删除。
3. 发布单用户前端，移除角色和用户 CRUD UI。
4. 观察至少一个发布周期，确认无旧客户端和脚本。
5. 再执行结构迁移：按决定删除多余账号、role 列、旧 API 和兼容测试。

后端实际迁移拆成两次发布：

**兼容迁移 A（可回滚、无破坏）：**

1. 获取 PostgreSQL advisory lock；安装 migration（新库）显式创建固定 AuthState=uninitialized，升级 migration（旧库）若缺少状态则先置 migration_required，完成账户盘点后才切到 initialized。应用运行时绝不创建该行。
2. 创建 nullable subject_key、retired_at 等兼容字段、CHECK、partial unique index，以及 AuthState 固定主键/禁止应用删除约束。
3. 统计账户；新安装 0 账户保持 migration 创建的 uninitialized；旧库 0 账户保持 migration_required 并走本机恢复，不能远程初始化。1 账户在显式确认后写入 subject_key=system_admin/session_version=1，N>1 未指定保留 ID 时整体回滚并退出。
4. 指定保留 ID 后将其归一为 enabled/admin/system_admin；其他账户导出带校验和的脱敏归档并设置 subject_key=NULL、retired_at、disabled，不删除。
5. 写 migration 审计和统计，不改写历史 OperationLog.UserID。
6. 发布可读取旧 role claim、但只接受唯一主体和 session_version 的兼容后端。
7. 部署采用停机/维护窗口或先迁移后整体切换，不允许不理解新字段的旧后端与新后端同时写 users/AuthState；服务启动检查 schema/migration batch 兼容矩阵。

**清理迁移 B（观察期后、破坏性）：**

1. 证明无旧客户端依赖 `/users`、role claim、角色广播和旧改密路径。
2. 删除 retired 账户前再次导出、备份并核对 OperationLog 外键策略；审计应保留 actor 快照，不能因删除账户丢失可读性。
3. 删除 role 列、旧索引/路由和兼容代码；按 ADR 决定是否将 users 重命名为 system_account。
4. 轮换 JWT 签名密钥或递增安全状态版本，确保所有兼容期 Token 失效。
5. 清理 B 是不可由字段级 rollback 安全撤销的边界；回滚必须恢复迁移前加密全库备份，并部署与该 schema 匹配的旧应用。

迁移脚本必须事务化、可重跑，并输出“保留主体 ID、禁用数量、异常数量”；不得输出密码哈希或 Token。

### 9.3 兼容策略

- 登录响应可在一个版本内保留 `role: "admin"`，新前端忽略它。
- 旧 `/api/v1/users/me/change-password` 可代理到新账户接口并返回 deprecation header。
- 多用户 CRUD 在过渡期建议返回 `410 Gone` 或明确的业务错误，而非改成操作唯一账户。
- Token 兼容期后通过签名密钥轮换或 session version 强制旧 Token 失效。
- WebSocket 事件名和业务 payload 不因认证收敛改变。

### 9.4 回滚

- 每阶段独立提交与发布，数据库破坏性迁移放在最后。
- 兼容期回滚前端时，后端仍可返回固定 `role=admin`；旧 UI 的用户 CRUD 应保持服务端禁用，避免安全能力倒退。
- 结构迁移前保留可验证备份；回滚时恢复被禁用用户记录，但是否恢复登录能力需人工明确授权。
- 初始化、密码和 Token 变更不可通过恢复旧明文回滚；应使用受控重置/密钥轮换。
- 若登录、401 或 WS 出现严重回归，优先回滚对应应用版本，不关闭鉴权或延长 Token 为无限期。
- 兼容迁移 A 回滚时恢复 AuthState/兼容字段与 retired 标记，但不自动恢复非保留账户的登录能力；须由人工审批。
- 清理迁移 B 回滚必须使用已验证备份和对应旧应用版本，禁止只恢复 role 列却继续运行新 JWT/session 代码。
- 初始化令牌、密码哈希、session_version 和签名密钥均视为单向安全状态；回滚不得恢复已撤销 Token。

## 10. 文档、版本与 topic 治理

### 10.1 文档治理

- 本文作为总方案；关键安全决策应拆成 ADR：单用户模型、Token 载体、初始化/恢复、公开端点白名单。
- 更新 `docs/设计/认证授权`、总体设计、验收标准和部署文档中三级 RBAC/默认口令描述，避免新旧文档冲突。
- API 契约维护机器可校验的 OpenAPI/schema；前端类型尽量从契约生成或由契约测试约束。
- 每个实施 PR 链接任务、风险、迁移影响、验证结果和回滚点。

### 10.2 版本治理

- 单用户兼容后端发布为过渡版本 N，单用户前端在 N 上线，破坏性清理不早于 N+1。
- `/users` 移除、role claim 移除、初始化行为变化必须写 release notes 和升级指南。
- 数据库迁移使用唯一版本号，禁止依赖 GORM AutoMigrate 隐式删除字段/数据。
- 配置项（Token TTL、限流、初始化模式、WS URL）必须有默认值、环境约束和变更说明。

### 10.3 WebSocket topic 治理

- 建立 topic/事件注册表：事件名、方向、payload schema、敏感级别、引入版本、废弃版本和负责人。
- 事件名继续使用稳定的小写下划线规范；认证改造不重命名业务事件。
- payload 变更优先向后兼容；破坏性变化通过 `schema_version` 或新事件名发布，并设双发/双读窗口。
- 前端使用判别联合类型和集中事件常量，不在组件内散落字符串与 `any`。
- 对未知事件忽略并记录限频诊断；对非法 payload 不应使整个连接处理器崩溃。
- topic 权限当前统一为“已认证唯一管理员”；未来若重新引入多主体权限，必须另立方案，不能复活前端隐藏按钮作为授权机制。

## 11. 推荐实施顺序与决策结论

推荐顺序为：**安全边界与契约测试 → 安全初始化/登录/会话 → WS 正确性 → 后端停用多用户 → 前端删除角色与用户 CRUD → 类型/lint/覆盖率 → 兼容层和数据结构清理 → 独立补业务 UI**。

最终决策保持明确：

1. 当前 Vue 3 / TypeScript / Pinia / Axios / WebSocket 技术架构继续使用，不重写。
2. 产品采用单用户、单管理员认证模式，不维护 admin/operator/viewer 权限矩阵。
3. 登录、JWT、密码哈希、服务端限流、Token 过期、会话失效和审计必须保留并加强。
4. 多用户 CRUD、前端 `meta.roles`、`v-permission` 和角色菜单分支应分阶段删除。
5. 所有敏感接口和 WebSocket 仍必须登录；**单用户绝不等于匿名访问或无鉴权**。
