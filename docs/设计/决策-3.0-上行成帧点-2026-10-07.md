# 决策：3.0 上行的**成帧点**放在传输适配器（2026-10-07）

> 状态：**已裁决**。触发问题是"第二条上行路径 `msg_handler_publish_checked`
> 也不成帧，该在哪一层修"。本文给出裁决与**证据**，并说明为什么不是另外两个候选位置。

## 一、问题
§134 修了 `devlink_send_frame`（Hello 那条）的成帧。但还有第二条上行路径：
```
msg_handler_publish_checked          components/msg_handler/msg_handler.c:55
  -> transport->ops->send            （首选 transport）
  -> transport_broadcast_ex          （回退：**对所有 transport 都发**）
     -> sess_tx_send                 main/session_transport.c:116  ← 3.0 TCP
     -> mqtt_adapter_send            components/ehome_mqtt/mqtt_transport_adapter.c:84
     -> mqtt_tx_send                 main/uplink_mqtt_transport.c:92
```
（HelloAck 回执、device_op 回执、DataBatch、诊断上报都走它。）

## 二、候选位置与裁决

| 候选 | 裁决 | 理由 |
|---|---|---|
| A. `msg_handler_publish_checked`（消息层） | **否** | 见 §三：会把 12 B 头塞进 MQTT 报文 |
| B. `transport_ops.send`（所有 transport 共用的契约点） | **否** | 同上：MQTT 也实现这个契约 |
| **C. `sess_tx_send`（3.0 TCP 适配器）** | **采纳** | 这是"payload → **3.0 TCP 线字节**"的唯一边界 |

## 三、证据（本轮实测，逐条可核验）

### 3.1 `transport_ops.send` 是**传输无关**契约，MQTT 与 TCP 共用
```
main/session_transport.c:173            .send = sess_tx_send        ← 3.0 TCP
components/ehome_mqtt/mqtt_transport_adapter.c:84  .send = mqtt_adapter_send  ← legacy MQTT
main/uplink_mqtt_transport.c:92         .send = mqtt_tx_send         ← 3.0 gated MQTT
```

### 3.2 MQTT 把 `data` **原样当报文载荷**发布
`mqtt_adapter_send` 的实现直接拿 `data`/`len` 去 publish。
⇒ 给它加 12 B 头会**破坏 MQTT**（2.x 设备与 §7.3 P0–P3 双栈窗口的兜底路径）。

### 3.3 回退路径会把同一份字节发给**所有** transport
`msg_handler_publish_checked` 在首选 transport 失败后调 `transport_broadcast_ex`，
后者遍历全部 transport ⇒ **在 publish 层成帧会污染 MQTT 那一份**
（而不是"只是多花 12 字节"）。

### 3.4 结论
**成帧是"3.0 TCP 线协议"的属性，不是"消息语义"的属性。**
把它放在消息层（A）或共用契约层（B），等于把"这条链路是 TCP"这个前提
写进一个**不知道自己在哪条链路**的函数里。

## 四、附带要求：这次不能只"修好"，还要**防它悄悄回来**
§134 之所以能长期存活，是因为出问题的那段代码在
`#ifndef SESSION_TRANSPORT_HOST_TEST` 里 —— **宿主测试结构上看不到它**。
⇒ 本次要求把"**成帧 → 发送（含 progress 循环）**"这段编排抽到**宿主可编段**，
用**发送回调**注入真正的 `session_send`。宿主测试于是能断言：
> 回调收到的字节以 magic `0x45 0x48` 开头、`type == payload[0]`、`payload_len` 等于真实长度。

⇒ **"有人删掉成帧调用"会立刻变红**，而不是又一次静默退化。

## 五、与既有裁决的一致性
本仓已有两次同类裁决（都是"用证据把一个问题定死"）：
- **§120 帧类型双写**：保留双写 + 两端强制一致性校验；
- **§93.4 `request_id`**：保留（有测试证明缺它会把失败报成成功）；
- 本文**成帧点**：放适配器层 + 可测编排。

三次的共同判据：**该语义"属于谁"取决于它描述的是哪一层的事实** ——
`request_id` 属消息语义、帧头属线协议。
