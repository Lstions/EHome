# 证书轮换方案 — 3.0 mTLS 设备侧证书生命周期

> 2026-10-18 真机闭环实测后编写。前置事实全部来自实测，不来自文档推断。

## 0. 先说结论：现在**没有**轮换路径，而且这不是"补一个脚本"能解决的

三个实测事实决定了方案的形状：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 固件**从不**写证书 | `grep nvs_set_blob`（排除 crash 相关）= **0 处** |
| 2 | 3.0 协议**没有**下发证书的消息类型 | `MSG_*` 枚举里无 cert 类；`ConfigManifest` 不承载证书 |
| 3 | 证书在 NVS，且 `nvs_flash_erase()` 会把它一起擦 | `main.c:542`，触发条件是 `NO_FREE_PAGES` / `NEW_VERSION_FOUND` |

事实 1+2 合起来意味着：**证书只能靠"设备外"的通道改变** —— 烧录（USB）或 OTA 之外的带外手段。
事实 3 意味着：**一次意外擦除就会让设备永久失联**，且现场无法恢复（没人能登门接 USB）。

所以轮换方案的核心不是"怎么换"，而是**"怎么在不碰 USB 的前提下换，且失败可回滚"**。

## 1. 现有约束（实测）

```
NVS 命名空间  eh_tls                        (Kconfig CONFIG_EHOME_DEVICE_LINK_NVS_NS)
三个键        ca / cert / key               (device_link_wiring.c:678-680)
单项大小上限  4096 B                        (CONFIG_EHOME_DEVICE_LINK_CERT_BYTES)
实测证书大小  ca=583  cert=591  key=227 B   (RSA-2048)
NVS 分区      0x9000, 0x4000 = 16 KB        (partitions_c6_8m.csv)
```

**容量不是瓶颈**：三件材料实测 1401 B，上限 12 KB，NVS 16 KB。
真正的问题是**没有写入路径**，不是空间。

## 2. 方案：双槽 + 上线自证 + 保留旧材料回滚

### 2.1 数据布局（NVS 里放两套，轮流用）

```
eh_tls/
  ca      / cert      / key        ← 当前生效（slot A，沿用既有键名，零迁移）
  ca_b    / cert_b    / key_b      ← 备选（slot B）
  active_slot    (u8)  = 1|2
  slot_epoch     (u64) = 单调递增，用于判定"这份材料比现役新"
```

为什么沿用 `ca/cert/key` 作为 slot A 而不是三对同等命名：**存量设备已经在用这三个键**，
改键名等于让所有已部署设备在升级后读不到证书 ⇒ 全部失联。兼容性优先。

### 2.2 写入通道：新增 `MSG_CERT_PUSH (0x24)`，但**只在已认证链路上**

这是关键设计取舍。有两个可选通道：

| 通道 | 优点 | 致命问题 |
|---|---|---|
| **OTA 固件里塞证书** | 现有链路 | 证书与固件绑死；换证必须发固件；且 OTA 失败会砖 |
| **协议消息下发** | 换证不动固件 | 需要新增消息类型 + 设备侧写 NVS 的代码（现在为 0） |

选**协议消息**，但必须解决"鸡生蛋"：新证书只能通过**旧证书建立的链路**送达。
这天然安全 —— 能在 mTLS 会话里收到 `CERT_PUSH` 的，一定是已被当前 PKI 信任的对端。

```
MSG_CERT_PUSH = 0x24  (SVR→ESP)
  1 slot_epoch   varint   必须 > 设备当前值，否则拒绝（防重放/降级）
  2 ca_pem       bytes
  3 cert_pem     bytes
  4 key_pem      bytes    ⚠ 私钥走链路是必需的：设备没有别的收法
  5 sha256       bytes    32 B，覆盖 2+3+4 的拼接，设备侧必须校验

MSG_CERT_PUSH_ACK = 0x25  (ESP→SVR)
  1 slot_epoch   varint
  2 accepted     varint   0=拒绝 1=已落 NVS 并**已验证可连**
  3 reason       string
```

### 2.3 设备侧流程（写 NVS 的**唯一**新代码）

```
收到 CERT_PUSH:
  ① 校验 sha256                (失败 → ACK accepted=0，不动 NVS)
  ② 写入**非活动槽**            (失败 → ACK 0；活动槽从未被写，链路不受影响)
  ③ 读回逐字节比对              (同 nvs_certs_gen.py 的 verify 口径)
  ④ 用新槽材料**另开一条 TLS** 试连服务端，成功即证明证书可用
  ⑤ 试连成功 → 写 active_slot + slot_epoch，ACK accepted=1
     试连失败 → 擦掉新槽，ACK accepted=0，**继续用旧证书**
  ⑥ 重启链路任务，让新证书生效
```

第 ④ 步是整套方案的核心：**"能连上"是证书有效的唯一证据**。
不试连就切换，等于用"文件写成功了"冒充"证书能用"—— 而这两件事之间隔着一整个 PKI。

### 2.4 服务端流程

```
① 生成新 CA/证书（离线，私钥只进服务端机）
② 服务端**同时**信任新旧两套 CA  (ClientCAs 可以放多个 CA，这是 mTLS 的标准做法)
③ 逐台下发 CERT_PUSH，收集 ACK
④ 全部 ACK accepted=1 后，才把服务端切到只信任新 CA
⑤ 旧 CA 保留一个观察期（建议 30 天）再删
```

第 ② 步是**灰度必需**：如果不双信任，第一台设备换完证书就连不上，因为服务端还不认新 CA。

### 2.5 失败模式与兜底

| 失败点 | 后果 | 兜底 |
|---|---|---|
| CERT_PUSH 传输中断 | 设备 NVS 未变 | 服务端重发；slot_epoch 幂等 |
| 写 NVS 失败（满） | 活动槽不变 | ACK 0，设备继续用旧证书，可观测 |
| 试连失败 | 擦新槽 | ACK 0，**设备仍在线上**，换证前状态不变 |
| 切换后设备掉线 | 已无旧证书 | ⚠ **这是最危险的窗口** |

最后一行必须防。做法：**切换后不立刻擦旧槽**，保留 `ca/cert/key` 一段时间，
设备侧维持 `BOOT 失败 → 回落旧槽试 3 次` 的逻辑。这样即使新证书有隐蔽问题
（例如 CN 与 host 不匹配），设备仍能靠旧证书回来。

代价：旧私钥在设备上多存 30 天。是否接受取决于威胁模型 —— 对家用 IoT 而言，
"设备变砖要上门接 USB" 比 "旧私钥在已授权的设备上多存 30 天" 严重得多。

## 3. 实施顺序（按性价比，不按完整性）

### 阶段 0 — 立刻能做的（不需改固件）
1. **服务端双 CA 信任**：`ClientCAs` 改为 CA 池。零固件改动，是后续一切的前提。
2. **证书清单工具**：把"每台设备当前用哪套证书"变成可查询状态（现在无从得知）。
3. **NVS 镜像备份**：设备上台前 `read_flash` 留存 NVS（含证书），这是唯一的"恢复出厂"手段。

### 阶段 1 — 补上写入能力（需固件）
4. `CERT_PUSH` / `CERT_PUSH_ACK` 编解码 + 双槽 NVS 布局
5. 上线自证（试连）+ 失败回滚

### 阶段 2 — 运维闭环
6. 批量下发 + ACK 收敛看板
7. 旧 CA 过期提醒（**在过期前 90 天告警**，不是过期后）

## 4. 一个必须同时修掉的隐患

`main.c:541-544` 的 NVS 擦除：

```c
esp_err_t r = nvs_flash_init();
if (r == ESP_ERR_NVS_NO_FREE_PAGES || r == ESP_ERR_NVS_NEW_VERSION_FOUND) {
    ESP_ERROR_CHECK(nvs_flash_erase());   // ← 证书一起没了
    r = nvs_flash_init();
}
```

`ESP_ERR_NVS_NEW_VERSION_FOUND` 发生在 NVS 格式升级时（换 IDF 大版本可能触发）。
也就是说：**一次固件升级就可能静默清空所有设备的证书**，而设备变砖后现场无法恢复。

这不是理论风险 —— 本次实测中我把设备从 IDF 6.0.2 构建切到 6.1 构建，正好踩在这个边界上。
这次没触发（NVS 版本未变），但触发条件完全由 IDF 决定，不由我们控制。

**修法**：擦除前先把 `eh_tls` 三个键读到 RAM，擦完立即写回。约 40 行代码，
但决定了"一次升级会不会让全网设备失联"。建议与阶段 1 一起做。
