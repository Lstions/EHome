## 1. 背景、目标与非目标

### 1.1 需求（用户原话）

> 规则引擎条件的数据来源，现在是怎么管理的？我希望能实现能够直接使用某个边缘设备的数据，或者使用支持主备切换的数据源。比如两个光照传感器，最多有 3 种组合，1 号光照传感器数据、2 号光照传感器数据、1+2 数据组成的光照数据源。

### 1.2 现状（四方独立核实，均为实测）

| 环节 | 现状 | 证据 |
|---|---|---|
| 规则绑来源 | ‵automation_rules.trigger_edge_device_id‵（单 ID）+ ‵trigger_sensor_name‵；告警用 ‵target_type+target_id‵ | ‵models/automation.go:157‵、‵models/alert.go:36-37‵ |
| 求值驱动 | 只有「某台边缘设备上报了一帧」驱动 ‵Evaluate(edgeDeviceID, fields, at)‵ | ‵databus/consumers_heavy.go:405-409‵ |
| 数据源 active | **零消费**：automation/alert/databus 对 datasource 引用 = 0（grep 实测） | 设计 §170 亦自述「接入取值口径列入 v2 候选」 |
| 复合来源 | **零支撑**：‵source_kind‵、‵min_members‵、‵composite‵ 全仓 0 命中 | grep 实测 |
| 主动备组构造 | **产品 API 造不出**：组键 = ‵(LogicalDevice.ID, category)‵，创建同逻辑设备的第二台边缘设备被 409 | ‵handler_edge_device.go:711‵ → ‵handler_edge_device_lifecycle.go:68-86‵ |
| 生产数据 | ‵automation_rules=0 / alert_rules=0 / data_sources=0 / failover_logs=0‵；‵unified_data=179532‵；2 台设备（1=‵sn3001_rain‵ 仅 rainfall，2=‵jiabaida_bms‵ 13 个物理名）；**无 illumination 字段** | PG 实测 2026-10-22 |

### 1.3 目标与可证伪判据

| # | 目标 | 可证伪判据 |
|---|---|---|
| G-1 | 规则可直接用某台边缘设备的数据 | 存量规则（‵source_kind IS NULL‵）行为零变化：现有单测/e2e 全绿且不改断言 |
| G-2 | 规则可用主备数据源，active 变了规则自动跟 | 切换后下一次求值读数来自新 active；同一次触发只落 1 条事件、1 次动作（不双计） |
| G-3 | 支持 1 号 / 2 号 / 1+2 三种组合 | 三条规则分别只读对应来源；1+2 在成员缺席时按**显式**语义处理，绝不静默单边 |
| G-4 | 三种来源失败语义全 fail-closed 且可审计 | 任一路径取不到值 ⇒ 不触发 + 落审计；禁止 fallback 到 0 / 首成员 / 陈旧值 |
| G-5 | 不动已定稿口径与红线 | v3.3 单存活实例约束不变；‵data_sources‵ 行语义与字段不变；固件/协议零改动；解析层不承载业务语义 |

### 1.4 非目标

- 不改 ‵data_sources‵ 行的语义（它仍是「某逻辑设备某类别由某边缘设备提供」的成员台账）—— P-1 裁决。
- 不让 ‵internal/sensorfield‵ 感知 active / 优先级 / 成员拓扑。
- 不做定时轮询驱动求值（会引入第二个采样时钟，与 ‵DurationSec‵ 的「连续满足」定义冲突）。
- 本期不支持 virtual 字段引用来源组。
- 不放开「一逻辑设备多存活实例」（牵动历史聚合与 ‵MAX(id)‵ 保形去重口径）。

## 2. 术语与不变量

### 2.1 术语

| 术语 | 定义 |
|---|---|
| **来源引用 SourceRef** | 规则上「我从哪里取值」的声明：‵edge_device‵（单设备，存量语义）或 ‵source_group‵（来源组） |
| **来源组 SourceGroup** | 一个「数据来源」产品对象，含 ‵kind‵ 与成员集合；**跨逻辑设备**绑定 |
| **成员 Member** | 组内一台边缘设备 + ‵priority‵ + ‵required‵ + 组内运行态 |
| **主备组** ‵kind=primary_backup‵ | 组内同一时刻至多一个**权威成员**，规则读权威成员的值 |
| **复合组** ‵kind=composite‵ | 组内多成员的值按 ‵combine‵ 合成一个值 |
| **权威成员 active** | 主备组内被采纳的成员（‵source_group_members.status='active'‵） |
| **陈旧 stale** | 成员最新值年龄 > ‵staleness_sec‵，视为缺席 |
| **分量结论 ComponentResult** | 单个成员单次求值结果：值 / 是否可判定 / 是否降级 / 原因码 |

### 2.2 不变量

| # | 不变量 | 保证方式 |
|---|---|---|
| I1 | 每个主备组至多一条 ‵status='active'‵ 成员 | PG 部分唯一索引 ‵UNIQUE(group_id) WHERE status='active'‵ + 事务内校验 |
| I2 | ‵kind‵ 与 ‵combine‵ 合法组合：primary_backup ⇒ combine 必须空串；composite ⇒ combine ∈ {‵first_available,avg,max,min,sum‵} 且非空 | 保存期校验（400）+ 门禁 SG-02 |
| I3 | 同组内成员 ‵edge_device_id‵ 不重复 | ‵UNIQUE(group_id, edge_device_id)‵ |
| I4 | 成员必须是 ‵Enabled=true‵ 的边缘设备；被组引用的设备禁止删除 | 保存期校验 + 删除守卫（复用 data_sources 先例） |
| I5 | **composite 组没有 active / 不参与 failover** | 应用层保证（DB 部分唯一索引只兜底不约束）；‵ScanStale‵ 跳过 composite |
| I6 | 被任何规则引用的组禁止删除、禁止 ‵enabled=false‵ | 删除/停用前引用检查（409） |
| I7 | 成员 ‵category‵ 必须等于组 ‵category‵（组只有一个物理名） | 保存期校验（可观测性前置检查，warn/block 分级） |
| I8 | 组 ‵revision‵ 单进程内严格单调递增 | 每次配置/成员/active 变更 +1（不依赖时间戳） |

## 3. 裁决记录

> 分片之间出现的模型冲突在此一次性钉死；后续实施与评审以此为准。

| # | 争议/待决 | 裁决 | 理由 |
|---|---|---|---|
| **D-1** | 成员引用 ‵edge_device_id‵ 还是 ‵data_sources.id‵ | **‵edge_device_id‵** | 组要跨逻辑设备；‵data_sources‵ 行可能不存在（生产 0 行）；‵unified_data.edge_device_id‵ 全 NULL（DS-14）⇒ 全链路统一用 ‵EdgeDevice.ID‵ |
| **D-2** | active 存 ‵source_groups.active_member_id‵ 还是 ‵member.status‵ | **‵member.status‵ 单一真值**，组表不设 active 列 | 双源必然漂移；R1–R11 本来就要在 member 行写运行态；部分唯一索引直接建在 member 表 |
| **D-3** | active 部分唯一索引落 ‵data_sources‵ 还是 ‵source_group_members‵ | **两处都加** | 新表必须有；旧表今天只有非唯一 ‵idx_ds_device_status‵，「至多一条 active」只是应用层假设，一旦被规则消费即变成「规则读到哪条」的不确定性 |
| **D-4** | ‵min_members‵ 与 ‵first_available‵ 的关系 | ‵first_available‵ 时 **‵min_members‵ 强制 1、所有成员 ‵required=false‵**；‵min_members>1‵ 只对聚合类 combine（‵avg/max/min/sum‵）有意义 | ‵first_available‵ 的语义就是「任一台在就够」，再要求 ‵min_members=2‵ 自相矛盾；保存期拒绝该组合 |
| **D-5** | ‵on_degrade‵ 适用范围 | 仅 ‵composite‵ 且存在 ‵required=true‵ 成员时生效；空串归一为 ‵fail_closed‵；‵first_available‵ 归一为 ‵use_available‵ | 缺员处置必须是显式产品选择，不能有隐式默认改变语义 |
| **D-6** | F4 的 staleness 对存量规则是否生效 | **存量（‵source_kind IS NULL‵）不加 staleness 检查，保持现有行为**；仅来源组规则启用 FC-2 | G-1 要求存量零回归；给存量加新拒绝条件属于静默语义变更 |
| **D-7** | 是否新增 result 码 | **新增 4 个**：‵source_member_changed‵、‵source_stale‵、‵source_degraded‵、‵source_resolver_not_configured‵ | 塞进 ‵detail‵ 前缀会让运维无法聚合统计；代价是必须同步 models 常量 + 白名单双向门禁 + 前端枚举 |
| **D-8** | pending_confirm 是否快照来源 | **要快照**（‵source_hash‵ + ‵source_evidence‵），比对不一致 ⇒ ‵ErrConfirmActionChanged‵ | 复用 Y5 ActionHash 的既有安全模型：用户确认的是「他看到的那次决策」 |
| **D-9** | 复合是「合并帧后单计划求值」还是「逐分量求值」 | **逐分量求值再合并**，禁止把多设备帧拼成一个 frame 喂解析层 | 解析层 known-set 是单设备模型（‵resolve.go:64-108‵），合并帧会让同名互补 missing（‵eval.go:168-221‵）⇒ 一设备掉线静默错值 |
| **D-10** | composite 是否需要「隐式去重窗口」防多成员重复触发 | **不引入**。状态机 ‵armed→triggered→冷却‵ 已保证一次触发一次动作；‵cooldown_sec=0‵ 时保存期给 warning | 隐式时间窗去重会与用户显式配置的 ‵cooldown_sec‵ 冲突，且不可解释 |
| **D-11** | 切换钩子丢失怎么办 | 正确性**不依赖**钩子：窗口样本自带来源身份，identity 不匹配即清窗（S3）；钩子只做「尽快」清窗与审计 | 通道溢出/进程重启都不得导致误触发 |

## 4. 数据模型

### 4.1 `source_groups`（新表）

```go
// internal/models/source_group.go
// SourceGroup 是「一个数据来源」的产品对象：主备组或复合组。
//
// 为什么独立于 data_sources（D-1/P-1）：
//   - 组要**跨逻辑设备**（两台光照传感器通常属不同逻辑设备），而 data_sources
//     组键是 (LogicalDevice.ID, category)，跨设备会被拆成多个组；
//   - 主备/复合共用「成员集合」模型，用户的三种组合退化为成员数/combine 不同；
//   - data_sources 行语义（某逻辑设备某类别由某边缘设备提供）保持不变。
type SourceGroup struct {
    ID       uint   `gorm:"primaryKey" json:"id"`
    Name     string `gorm:"size:128;not null" json:"name"`

    // Kind 主备/复合：primary_backup | composite。必填无默认（P-2）。
    Kind     string `gorm:"size:20;not null;index" json:"kind"`
    // Category 组读取的物理名（= unified_data.sensor_name；一期只字面量，
    // 与 data_sources.category 同口径同宽 :64，见 DG-05）。
    Category string `gorm:"size:64;not null;index" json:"category"`

    // Combine 仅 composite 必填：first_available|avg|max|min|sum。
    //   primary_backup 必须为空串（I2，保存期校验）。
    Combine  string `gorm:"size:20;not null;default:''" json:"combine,omitempty"`
    // MinMembers composite 最少可用成员数。0 = service 归一为 1。
    //   first_available 时强制 1（D-4），min_members>1 仅对聚合类 combine 有意义。
    MinMembers int  `gorm:"not null;default:0" json:"min_members"`
    // StalenessSec 成员值年龄上限（秒）。0 = 由成员采集间隔推导
    //   （2×Interval，下限 30s 上限 3600s）；推导在 internal/sourceref。
    StalenessSec int `gorm:"not null;default:0" json:"staleness_sec"`
    // OnDegrade 缺员处置：fail_closed | use_available（仅 composite；空串=fail_closed）。
    OnDegrade string `gorm:"size:16;not null;default:''" json:"on_degrade,omitempty"`

    // Enabled 人工启停。显式 false 不依赖 DB default（models/defaults_gate_test.go 陷阱）。
    Enabled bool `gorm:"not null" json:"enabled"`
    // Revision 配置/成员/active 变更时单调 +1（I8）：供缓存失效与钩子去重，
    //   不依赖时间戳（单进程内严格有序）。
    Revision int64 `gorm:"not null;default:0" json:"revision"`

    Description string    `gorm:"size:255" json:"description"`
    CreatedAt   time.Time `json:"created_at"`
    UpdatedAt   time.Time `json:"updated_at"`
}

func (SourceGroup) TableName() string { return "source_groups" }
```

### 4.2 `source_group_members`（新表，含组内运行态）

```go
// SourceGroupMember 组内成员（一台边缘设备）**及其组内运行态**。
//
// 运行态放这里而不是复用 data_sources 行（P-1）：组键不同，且 data_sources 的
// 唯一索引 (device_id,category,edge_device_id) 会限制跨逻辑设备。
// 代价：R1–R11 需要两个适配器，由公共 helper 保证逻辑只有一份（§5.4）。
type SourceGroupMember struct {
    ID uint `gorm:"primaryKey" json:"id"`

    // GroupID 双挂索引：成员唯一 (u,g) + 每组至多一条 active 的部分唯一索引。
    GroupID      uint `gorm:"not null;index;uniqueIndex:ux_sgm_member,priority:1;uniqueIndex:ux_sgm_one_active,priority:1,where:status = 'active'" json:"group_id"`
    // EdgeDeviceID = EdgeDevice.ID（= unified_data.device_id；禁 edge_device_id，DS-14）。
    EdgeDeviceID uint `gorm:"not null;uniqueIndex:ux_sgm_member,priority:2;index" json:"edge_device_id"`

    // Priority 越大越优先（R3 候选排序 priority DESC, id ASC）。
    Priority int `gorm:"not null;default:0" json:"priority"`
    // Required 仅 composite：缺 required 成员 ⇒ 按 on_degrade 处置。
    Required bool `gorm:"not null" json:"required"`

    // ── 组内运行态（R1–R11 唯一写入口；composite 只维护 last_success 供观测）──
    // Status active | standby | error | disabled（与 DataSource.Status 同词表但语义域不同：
    //   这里 active = 组内权威成员。UI/文档必须写明，防「同名异物」）。
    Status       string     `gorm:"size:20;not null;default:'';index" json:"status"`
    FailCount    int        `gorm:"not null;default:0" json:"fail_count"`
    MaxFailCount int        `gorm:"not null;default:0" json:"max_fail_count"` // 0 = 归一为 3
    LastSuccess  *time.Time `json:"last_success"`
    LastFailure  *time.Time `json:"last_failure"`

    CreatedAt time.Time `json:"created_at"`
    UpdatedAt time.Time `json:"updated_at"`
}

func (SourceGroupMember) TableName() string { return "source_group_members" }
```

> ⚠ 部分唯一索引的 `where:` 只能引用本表列，不能跨表；因此「composite 组无 active」由应用层保证（I5），DB 只兜底。

### 4.3 规则绑定列（存量兼容）

**回落的唯一实现**（禁止各处各写一遍）：

```go
// internal/models/source_ref.go
type SourceKind string
const (
    SourceKindEdgeDevice  SourceKind = "edge_device"
    SourceKindSourceGroup SourceKind = "source_group"
)

// SourceRef 解析「这条规则从哪取值」。唯一实现：evaluator / planner / precheck /
// 前端校验 / 盘点脚本全部调用它，禁止各自判断 source_kind != ''。
func (r AutomationRule) SourceRef() SourceRef {
    if r.SourceKind == string(SourceKindSourceGroup) && r.SourceGroupID != nil {
        return SourceRef{Kind: SourceKindSourceGroup, GroupID: *r.SourceGroupID}
    }
    return SourceRef{Kind: SourceKindEdgeDevice, EdgeDeviceID: r.TriggerEdgeDeviceID}
}
```

**回退安全的铁律（来自回滚推演，§9.2）**：绑来源组的规则**必须同时双写非 0 的 `trigger_edge_device_id`**（= 组主成员）。旧二进制忽略新列后走老路，退化为「只看主成员」而不是「任意设备触发」—— 这是可接受的降级，而不是静默乱触发。

## 5. 求值模型

### 5.1 三层职责（红线）

```
规则（automation / alert）
   │ source_kind + source_group_id   ── 经 models.SourceRef() 唯一解析
   ▼
来源解析 internal/sourceref（唯一实现，热路径零 DB）
   │ 组快照：成员、active、priority、staleness、revision、transitionSeq
   ▼
逐分量求值 internal/sensorfield（单设备 Compile/EvalPredicate，契约不改）
   │ 每个成员独立求值 → ComponentResult{Value, OK, Degraded, Reason, At}
   ▼
合并纯函数 sourceref.Combine（按 kind/combine/on_degrade）
   │ → 一个值，或 unbound/degraded + 原因码
   ▼
规则状态机（DurationSec 窗口 / 冷却 / Y5 确认）
```

**四条红线**：
1. `internal/datasource` 不 import `internal/sensorfield`（领域依赖方向不变）。
2. `internal/sensorfield` 不感知 active / 成员 / 优先级。
3. `internal/databus` 仍只报 `(edge_device_id, fields, at)`，不知道来源组存在。
4. 合并层是**纯函数**：无 DB、无锁、无 IO；同样的输入必得同样输出。

### 5.2 求值驱动：成员帧驱动 + active 过滤 + 切换清窗

**这是本轮最重要的模型裁决**（不做定时轮询）。

| 步骤 | 行为 | 落点 |
|---|---|---|
| 1 | 任一成员设备上报一帧 ⇒ 数据面照旧推 `Evaluate(edgeDeviceID, fields, at)` | `databus/consumers_heavy.go:405-409`（不改） |
| 2 | 规则匹配阶段：解析 SourceRef；`source_group` 规则调 `MatchFrame(edgeDeviceID, ref)` | `automation/evaluator.go:862-887`、`alert/evaluator.go:282-302` |

| 4 | composite 组：成员帧触发一次**整组求值**（逐成员取最新值 → 逐分量求值 → 合并） | `evalCompositeRule`（新增） |

**为什么不做定时轮询**：会引入第二个采样时钟，与 `DurationSec` 的「连续满足」定义冲突（同一物理条件被两个时基各判一次）；且轮询周期与成员上报周期无关，会让冷却/驻留语义不可解释。

### 5.3 逐分量求值 + 合并（禁止合并帧）

**禁止**把多设备帧拼成一个 `[]Reading` 喂解析层（D-9）。原因（解析层实测）：
- `Reading` 无来源标识，`familyPlan` 的 known 是编译期名字快照（`resolve.go:349-373`）；
- `scanMembers` 按帧内出现次数累计 `foundKnown`（`eval.go:205-215`），`missing = len(known) - foundKnown`（`:208-214`）；
- 两设备同名同族（两台光照都报 `illumination_1..4`）⇒ 合并帧 8 条、known 去重 4 个 ⇒ `missing` 被 clamp 到 0 ⇒ **一设备掉线不触发缺员**，`all/avg` 静默按剩余分量算。

**合并语义矩阵**（`combine` × 分量状态）：

| combine | 全部分量 OK | 部分缺席且 `on_degrade=fail_closed` | 部分缺席且 `use_available` | 全部缺席 |
|---|---|---|---|---|
| `first_available` | 按 priority DESC 取第一个 OK | 不适用（D-4：强制 `min_members=1`、全部 `required=false`） | 取第一个 OK，`Degraded=true` | unbound |
| `avg` | 算术平均（等权） | unbound | 按可用成员平均，`Degraded=true` | unbound |
| `max` / `min` | 极值 | unbound | 可用成员极值，`Degraded=true` | unbound |
| `sum` | 求和 | unbound | 可用成员求和，`Degraded=true` | unbound |

> 缺席判定 = ①该成员没有该字段的最新值；②最新值年龄 > `staleness_sec`；③成员状态 `!= active/standby`（主备组）。三者任一 ⇒ 缺席。

### 5.4 R1–R11 接入主备组（防两套状态机漂移）

### 5.5 切换钩子

```go
// ActiveChange 某来源组权威成员变化。Prev/Next 至多一个为 0；Next=0 表示组失去权威（degraded），
// 消费方必须停止用旧 active 过滤（否则会继续用已失效的成员帧求值）。
type ActiveChange struct {
    GroupID     uint      // 组
    Prev        uint      // 原 active member id（0=无）
    Next        uint      // 新 active member id（0=组失去权威）
    Reason      string    // auto | manual_activate | manual_deactivate | reset | degraded
    Trigger     string    // 触发者（stale_scan | mark_failure | api）
    Revision    int64     // 组 revision（单调）
    At          time.Time
}
```

**可靠性纪律**：
- 事务**提交后**发射（避免回滚后误清窗）；
- 有序单 dispatcher goroutine；panic recover；
- channel 溢出 ⇒ 置 `dirty` 标记，消费方**全量重载**快照（**绝不允许「丢事件后继续用旧 active 过滤」**）；
- **正确性不依赖钩子**：窗口样本自带来源身份，identity 不匹配即清窗（§5.6 S3）。

### 5.6 窗口来源身份（P-3①，写死判据 S1–S6）

现状缺陷（实测）：`sample{at, satisfied}` / `sample{at, value, satisfied}` **无来源身份**，`windows` 只按 ruleID 分区（`automation/evaluator.go:46-49,82`；`alert/evaluator.go:39-44,62`）⇒ 主备 A/B 交替上报时 `DurationSec` 的「连续满足」可由两台设备的样本**拼接**成立 ⇒ 单台都不连续也判连续 ⇒ **静默误触发**。

改造：两个引擎的 `sample` 各加来源身份 `sourceIdentity{Kind, GroupID, EdgeDeviceID, TransitionSeq, MembersHash}`。

| # | 判据（写死） | 落点 | 红判据（变异自证） |
|---|---|---|---|
| S1 | 窗口**不得跨 identity 拼接**：写样本前若 `len>0 && last.identity != new.identity` ⇒ 丢弃旧段 | `automation/evaluator.go:948-950`；`alert/evaluator.go:332` | A/B 交替三帧（t0 A、t30 B、t61 A，`DurationSec=60`）⇒ 必须不触发；去掉 identity 检查 ⇒ 必须触发 |
| S2 | 只有 identity 相同的样本才参与 `windowSatisfied` | 同上 + `:1064 windowSatisfied` | 同 identity 连续满足 ⇒ 正常触发（正例） |
| S3 | **切换/重启兜底**：identity 不匹配即清窗，**不依赖钩子** | 同 S1（判据本身） | 关闭钩子跑 A→B 切换 ⇒ 仍不误触发 |
| S4 | 清窗时**保留** `triggered`（冷却锚）；alert 额外关闭陈旧 firing | 钩子 + `alert/evaluator.go:215` | 切换后立即满足但冷却未过 ⇒ `suppressed_cooldown`，零第二次动作 |

### 12.2 关键语义重写（替换 §5.2 / §5.6 的对应段）

#### 12.2.1 按 kind 分流的帧过滤与身份（治理 N-1 / N-4）

| kind | 帧进入求值的条件 | 窗口身份 identity | DurationSec 语义 |
|---|---|---|---|
| `primary_backup` | `IsMember && IsActive`（仅权威成员的帧） | {Kind, GroupID, **GroupRevision**, MembersHash, EdgeDeviceID} | 同成员连续满足（跨成员禁止拼接，S1） |
| `composite` | `IsMember`（任一成员帧触发**整组求值**） | {Kind, GroupID, **GroupRevision**, MembersHash}（**不含**触发成员） | 以「组值」为观测单位连续满足（S7：A/B 交替不得打断） |
| `edge_device`（存量） | 现有逻辑不变 | {EdgeDeviceID, GroupRevision=0} | 现状不变 |

> `GroupRevision` **必须**由 DB 递增（`BumpGroupRevision`），不能由钩子累加 —— 这是 N-13 的核心。

#### 12.2.2 快照所有权与原子发布（治理 N-13）

```
数据源状态机（datasource，事务内）
   ① 写 DB（member.status / fail_count / last_* / group.revision+1）
   ② 事务提交后：sourceref.PublishSnapshot(全新不可变快照, atomic.Pointer 整体替换)
   ③ 事务提交后：emit ActiveChange（只做「清窗加速 + 审计」）
```

- **快照唯一所有者** = `internal/sourceref`；发布者是**状态机本身**（步骤②），**不是钩子**。
- **钩子只做两件事**：加速清窗、写审计。钩子丢失只影响「多快清窗」，不影响「快照是否正确」。
- **进程启动 / dirty 全量重载**：从 DB 全量重建快照并整体替换（`revision` 必须单调）。
- **消费方读快照**：`atomic.Pointer.Load()`，热路径零锁零 DB（SG-18 保证无 IO 依赖）。

> 由此 S3 的正确表述是：**快照正确性不依赖钩子；钩子只影响清窗时延**。「不误触发」由 S1 + S8 保证（见下），「切换后跟随」由快照发布保证。

### 12.3 权威真值表（替换 §7.1 E-5 与 §5.3 矩阵，治理 N-3 / N-10）

#### 12.9.2 权威真值表（v0.3 最终版，替换 §12.3）

**规则**：①`fail_closed`：任一分量缺席 ⇒ unbound（`Required` 不改变结果，仅保存期告警）。②`use_available`：缺 `required=true` ⇒ unbound；仅缺 `required=false` ⇒ 合并 + `Degraded=true`。③`min_members` 只统计 `required=false` 成员的缺席（`fail_closed` 下无意义，强制 1）。

| on_degrade | 缺席成员的 required 情况 | 可用数 vs min_members | 结果 | 审计/标记 |
|---|---|---|---|---|
| `fail_closed` | 任意 | — | **unbound** | `source_degraded` + `members_json` |
| `use_available` | 含 ≥1 个 `required=true` | — | **unbound** | `source_degraded` + `reason=required_missing` |
| `use_available` | 仅 `required=false` 缺席 | 可用 ≥ `min_members` | 按可用合并，**允许触发** | `degraded=true` + `source_degraded` |
| `use_available` | 仅 `required=false` 缺席 | 可用 < `min_members` | **unbound** | `source_degraded` + `reason=below_min_members` |
| `first_available`（归一 use_available，`min_members` 强制 1、全部 `required=false`） | 任意缺席 | 可用 ≥ 1 | 取 `priority DESC, id ASC` 首个可用 | 有缺席 ⇒ `degraded=true` |
| `first_available` | — | 可用 = 0 | **unbound** | `source_degraded` |
| 全部可用 | — | — | 按 combine 合并 | 无降级标记 |

## 13. v0.4 收敛追加（2026-10-22）：砍掉过度设计

> 本节**覆盖**前文与之冲突的条目。前文保留原样，作为决策历史。

### 13.1 为什么要砍

落地完成后做收益-代价评估，发现三个事实：

1. **当前生产收益 = 0**：`automation_rules=0`、`data_sources=0`、`source_groups` 表 0 行，
   且没有任何"同类传感器的第二个实例"（生产只有 1 台雨量计 + 1 台 BMS）。
   这套能力是**0 → 1 的储备**，不是正在痛的病。
2. **代码量超出需求 3 倍以上**：生产 Go 6,148 行 + 测试 8,006 行 + 门禁 1,010 行，
   支撑 2 个新能力，单能力 ≈ 3,000 行。
3. **部分设计引入了新风险而非消除风险**：S8（见 13.2）就是典型 —— 它"保护"窗口，
   却在稀疏上报时静默杀掉存量规则，且没有指标。
