## 2. 严重级缺陷

### S1（严重）`api` 已成上帝包：四个注册函数 = 3,604 行，职责四层混装

**位置**：`internal/api/handler_device.go:286`、`handler_periph.go:540`、`handler_edge_device.go:283`、`handler_node.go:50`

**现状**（函数长度实测，按 `^func` 到下一个 `^func` 计数）：

```
1079  internal/api/handler_device.go:286      func registerDeviceRoutes(v1 *gin.RouterGroup, db *gorm.DB, nodeMgr *nodemgr.Manager, driverRegistry *drivers.Registry) {
1005  internal/api/handler_edge_device.go:283  func registerEdgeDeviceRoutes(v1 *gin.RouterGroup, db *gorm.DB, nodeMgr *nodemgr.Manager, driverRegistry *drivers.Registry) {
 842  internal/api/handler_periph.go:540       func registerPeriphRoutes(v1 *gin.RouterGroup, db *gorm.DB, nodeMgr *nodemgr.Manager) {
 678  internal/api/handler_node.go:50          func registerNodeRoutes(v1 *gin.RouterGroup, db *gorm.DB, nodeMgr *nodemgr.Manager, registries ...*drivers.Registry) {
```

**为什么会这样（机制）**：这四个函数把「路由注册」当成了「模块」。因为每个 `v1.GET/POST/PUT/DELETE` 都内联一个闭包，闭包又直接持有 `db` / `nodeMgr` / `driverRegistry`，所以**任何新端点都只能往这个函数里追加**——函数长度只增不减。以 `handler_periph.go:562-638`（POST GPIO 配置）为例，一个请求里依次出现：路径解析 → 绑定 → 4 类字段校验 → 权威 GPIO 上报校验 → PWM 冲突查询 → DB 事务 → 调 `nodeMgr.SendPeriphCmd` → 写 envelope：

```go
// internal/api/handler_periph.go:593-638（节选）
if err := validateReportedGPIO(db, node, pin); err != nil {
    Error(c, http.StatusUnprocessableEntity, err.Error()); return
}
var pwmConflict int64
if err := db.Model(&models.PWMConfig{}).Where("node_id = ? AND pin = ?", node.NodeID, pin).Count(&pwmConflict).Error; err != nil { ... }
...
if err := nodeMgr.SendPeriphCmd(node.NodeID, PeriphTypeGPIO, uint8(pin), GPIOActionConfig, 0, configBytes); err != nil { ... }
SuccessWithCode(c, http.StatusCreated, cfg)
```

**量化证据（非测试口径）**：

| 指标 | 值 |
|---|---:|
| `internal/api` 非测试文件 / 行 | 38 / 11,707 |
| 其中 import `gorm.io/gorm` 的文件 | **25**（65.8%） |
| import `internal/models` 的文件 | 23 |
| import `internal/nodemgr` 的文件 | 10 |
| `db.<Method>(` 调用点 | **218** |
| `db.WithContext(...)` 调用点 | **7**（3.2%） |
| 唯一四个业务包合计 | nodemgr 7,037 + datalifecycle 5,931 + drivers 4,509 + commandexec 2,513 |

**为什么是设计问题（不是风格）**：
1. **没有服务层，所以"分层"只存在于目录名里**。handler 直接写事务（`handler_node.go:587` 用 `SELECT FOR UPDATE`）、直接写 raw SQL（`handler_data.go:136`）、直接调 `nodemgr`（10 个文件）。业务规则因此**无法被第二个入口复用**（例如 WS 通道、自动化引擎、CLI 想复用"GPIO 配置校验"时无路可走）。
2. **同一规则必然被复制**。`page_size` 解析点共 **11 处**，而"上限"这条规则的落地方式有 **5 种**：
   - ① 同一份 clamp `if pageSize < 1 || pageSize > 200` 被**逐字抄了 6 遍**（`handler_alert.go:311`、`handler_automation.go:465`、`handler_device.go:320,731`、`handler_edge_device.go:307`、`handler_logical_device.go:46`）；
   - ② 1 处用自己的 helper：`handler_notification_channel.go:218,521` → `normalizeNotificationPageSize`（:572-575）；
   - ③ 1 处是**不同上限**的第三份实现：`handler_logstream.go:160`（`size < 1 || size > 1000`）；
   - ④ **2 处完全没有上限**：`handler_vendor.go:37` 与 :99，均为 `db.Offset((page - 1) * pageSize).Limit(pageSize)`，无 clamp 也无 service；
   - ⑤ **1 处正确地把规则交给 service**：`handler_data_source.go:140` → `datasource/service.go:361-372`（`Page<1 归 1；PageSize<=0 归 20，>100 归 100`）—— 全仓唯一"有 service 层"的那处，恰好也是唯一规则只有一份实现的那处，正是本条论点的自我印证。
   可复跑：`grep -rn "Atoi(c.DefaultQuery(.page_size" internal/api | grep -v _test` → 11 处；`grep -rn "pageSize < 1" internal/api | grep -v _test` → 6 处。
3. **可测试性被结构反噬**：33 处测试用 `setupTestRouter` 自建路由（只挂 4 个 register 函数），只有 2 处调用真正的装配根 `SetupRoutes`（见 M10）。端点测试锁的是"注册函数"，不是"生产装配结果"。

**后果（真实）**：
- 分页 clamp 漏做的端点可被 `?page_size=100000000` 拉全表（`handler_vendor.go:41`），响应体与内存随表增长。
- 项目自己记录的负债 I-11「假分页」（`handler_pagination_contract_test.go:334-344` 注释：「两个端点改前都是 `Find` + `Success(c, 裸数组)`，静默丢弃 page/page_size …… el-pagination 纯装饰」）就是这个结构的直接产物：**分页不是能力，是每个 handler 各自的自觉**。
- 2026-09-11 的 `docs/分析/架构与接口评估及优化方案-2026-09-11.md` §6.1 给"分层与依赖方向"打 6/10、§6.6 给"大文件与重复"打 6/10 —— 一个月后本文实测：**结构未变，且新增端点仍在往同样四个函数里加**。

**3.0 改进方向（可执行的切分方案）**：

```
internal/api/                       ← 只保留 HTTP 适配：绑定、鉴权、状态码、envelope
  transport/  routes_*.go           路由注册薄层（每个 register* ≤ 120 行）
  dto/        请求/响应结构 + 绑定   （含统一的 Pagination 解析与 clamp，唯一实现）
internal/<domain>/service.go        ← 新增：业务用例（事务边界在这里）
  node/  edgedevice/  channel/  periph/  config/  ...
internal/repo/ 或 <domain>/repo.go  ← 新增：GORM 访问（handler 不再 import gorm）
```

- **迁移顺序（按风险从低到高）**：① 抽出 `pagination`（唯一实现 + 上限），把 11 个解析点改为调用它 —— 一次改动消掉 5 个无界点；② 抽 `middleware/errors.go` 统一错误映射（见 M4）；③ 逐资源抽 service：先 `periph`（842 行、无跨聚合事务）→ `vendor`（219 行、纯 CRUD）→ `edge_device`（1005 行）→ `device`（1079 行，最后做）；④ 每抽一个，就往 `SetupRoutes` 加一条"路由必须在生产装配下可命中"的测试（见 M10 修法）。
- **验收判据（可证伪）**：`grep -l "gorm.io/gorm" internal/api/*.go | wc -l` 从 **25 收敛到 0**；`registerDeviceRoutes` 长度从 1079 降到 ≤120。

### S2（严重）数据面每样本 8~10 次 DB 往返；`ResolveMergeTarget` 每样本全表扫描

**位置**：`internal/databus/consumers_heavy.go:194,198,200,247,274,294,331`

**现状**（`SensorParserConsumer.Handle`，每个样本都执行）：

```go
// consumers_heavy.go:194
if err := c.db.Preload("Node").Where("id = ? AND node_id = ?", evt.EdgeDeviceID, evt.DeviceID).First(&device).Error; err != nil { return }
// consumers_heavy.go:198（未带 edge_device_id 时的兼容分支，再查一次）
if err := c.db.Preload("Node").Where("channel_id = ? AND node_id = ?", evt.ChannelID, evt.DeviceID).First(&device).Error; err != nil {
    var channels []models.Channel                                  // :200 又一次查询
    if err := c.db.Where("node_id = ?", evt.DeviceID).Order("id ASC").Find(&channels).Error; err != nil { return }
    ...
}
// consumers_heavy.go:331 —— 每个样本都重建整张合并图
target, err := datalifecycle.ResolveMergeTarget(c.db, *device.LogicalDeviceID)
```

且 `ResolveMergeTarget` 的实现是**全表加载**：

```go
// internal/datalifecycle/merge_chain.go:30-41
func LoadMergeGraph(db *gorm.DB) (*MergeGraph, error) {
    var rows []row
    if err := db.Model(&models.LogicalDevice{}).Select("id", "merged_into", "merge_status").Scan(&rows).Error; err != nil { ... }
```

**单样本的 DB 往返账（最坏路径）**：

| 步骤 | 次数 | 位置 |
|---|---:|---|
| `Preload("Node")`（GORM Preload = 2 条 SQL） | 2 | :194 |
| `DeviceConfig`（配置解析路径） | 1 | :247 |
| `CalibrationCache` 或 `ConfigTemplate` | 1 | :274 / :294 |
| `LoadMergeGraph`（全表扫描 `logical_devices`） | 1 | :331 |
| 写 `unified_data`（批量，好） | 1 | :355 |
| 写 `edge_devices` 状态（条件 UPDATE，常常 2 条） | 1~2 | :415,421 |
| 写 `device_data`（解析版） | 1 | :450 |
| **合计** | **8~10** | |

**为什么是设计问题**：
- **物理量与业务量不匹配**：3.0 的目标是"500 样本/s 预算"（3.0 方案 §6.2）与"每设备每通道 100 Hz"（§2）。`Preload("Node")` 这种"每样本重新确立 device↔node 归属"的查询，本质上是把**慢变的拓扑**当**快变的样本**处理。项目在 worker_pool 里已经为同类问题造过 `nodeIDCache`（`worker_pool.go:60-94`，TTL 5 分钟）——**同一条数据链路上，一半做了缓存一半没做**。
- **全表扫描是 O(逻辑设备数) 而不是 O(1)**：`LoadMergeGraph` 把整张表读进内存建两个 map，然后只为一个 ID 做 3~5 跳 walk。合并图是**极低频变更**（人工合并/撤销），却放在最高频路径上。这不是"查询慢"，是**把读扩散从 O(1) 变成 O(N)**。
- 与 S3 叠加后，同一份原始数据还要被写两次（见 S3）。

**后果（可算）**：按 3.0 目标的 8 台边缘设备 × 100 样本/s = 800 样本/s 计，最坏路径 ≈ **6,400~8,000 次 SQL/s**，其中 **800 次是全表扫描**。这不是"以后优化"的量级——它会把 PG 连接池和分区表的 autovacuum 一起拖垮，而现场表现只是"数据有点延迟"，很符合本项目最怕的**无告警劣化**模式。

**3.0 改进方向**：
1. **拓扑/校准/模板三者全部走按 ID 版本化的内存缓存**，命中即零查询；缓存失效用配置事件（`ConfigChangeEvent` 已存在）而不是 TTL。判据：稳态下 `Handle` 的 SQL 数 = **1 次批量 INSERT + 1 次批量 UPDATE**。
2. **合并图改为进程内快照 + 版本号**：`logical_devices.updated_at` 或专门 epoch，变更时重建一次（复用 `LoadMergeGraph`），样本路径只走内存 `Resolve`。合并图本就有 `ResolveMergeTarget` 单入口，改造面很小。
3. **把"节点是否已注销"的判定前移到会话层**（3.0 的 `transport/session` 在建立连接时就知道 node 是否存活），而不是每样本查一次 DB 再 fail-closed。

### S3（严重）同一事件写两行 `device_data`：两个写入者、两种形状、一个"最新一条"读接口

**位置**：`internal/databus/consumers_heavy.go:91`（`DBPersistConsumer`）与 `consumers_heavy.go:450`（`SensorParserConsumer`）

**现状**——两个消费者对**同一个 DataEvent** 各写一行 `device_data`：

```go
// ① consumers_heavy.go:91  DBPersistConsumer.Handle —— 原始 hex
if err := c.db.Session(&gorm.Session{}).Create(&models.DeviceData{
    NodeID:    evt.DeviceID,                       // 字符串节点序列号；DeviceID 字段留 0
    DataJSON:  string(dataJSON),                    // {"raw":hex,"channel":..,"sequence":..}
    Timestamp: evt.ReceivedAt,
}).Error; err != nil { ... }

// ② consumers_heavy.go:450  SensorParserConsumer.Handle —— 解析后的物理量
} else if err := c.db.Session(&gorm.Session{}).Create(&models.DeviceData{
    DeviceID:        device.ID,                     // 数值 edge_device_id
    LogicalDeviceID: logicalTarget,
    NodeID:          evt.DeviceID,
    DataJSON:        string(dataJSON),              // {"raw_hex":..,"sensors":[...]}
    Timestamp:       now,                           // 注意：与 ① 的 ReceivedAt 不同
}).Error; err != nil { ... }
```

而读接口只有一个"最新一条"：

```go
// internal/api/handler_edge_device.go:1220-1223
var data models.DeviceData
cond, args := dataScopeCond(qs)
db.Where(cond, args...).Order("created_at DESC").First(&data)   // ← 取值取决于哪个消费者后写
Success(c, data)
```

```go
// internal/api/handler_node.go:285-287 —— 按 node_id 过滤，两行都会命中
var data []models.DeviceData
db.Where("node_id = ?", node.NodeID).Order("timestamp DESC").Limit(limit).Find(&data)
Success(c, data)
```

**为什么是设计问题**：
- **同一个表 = 两种互不兼容的行契约**。`data_json` 在 ① 里是 `{"raw":...}`、在 ② 里是 `{"raw_hex":...,"sensors":[...]}`；`device_id` 在 ① 里恒为 0。消费者的**任何**下游读取都必须先判断"这行是谁写的"，而没有任何字段能回答这个问题。
- **写入顺序不可判定**：两个消费者注册在不同的 worker 上（`bus.go:224 runConsumer`，每个 consumer 一个 goroutine），① 用 `evt.ReceivedAt`、② 用 `time.Now()`。`/edge-devices/:id/latest-data` 返回哪种形状，取决于调度噪声。这与项目已经修过一次的"缓存冷热改变返回形状"（`latest_value_cache.go:16-23` 注释：「测试一帧 14 个物理量最后只剩 1 个 …… 用户会看到数据『消失』」）是**同一类缺陷，只是搬到了 device_data**。
- **写放大**：每样本多一次 INSERT + 一份 JSON 序列化（`fmt.Sprintf("%x", rawData)` 再 `json.Marshal`）。3.0 目标速率下这等于给最大的表额外加 100% 写入。

**后果**：`GET /nodes/:id/data` 的 `items` 数组里混着两种形状的行；前端任何按 `data_json.sensors` 取值的组件都会在部分行上静默拿到 `undefined`（假绿）。

**3.0 改进方向**：
1. **一张表一个写入者**。原始字节属于**审计/取证**域，应与解析结果分表（或落在 3.0 的 raw+index 存储模型里，见 3.0 方案 §6.4 的 v3mv），并明确"谁读它"。
2. **读接口必须声明形状**：`latest-data` 返回 DTO（`sensors[]`），而不是持久层行；`/nodes/:id/data` 若确需原始字节，改名 `/raw-data` 并返回原始形状。
3. **契约测试**：一条端到端用例 —— 同一设备同一帧入库后，`latest-data` 与列表接口的字段集合必须逐字段相等（当前会红）。

### S4（严重）分页参数解析失败/为负 ⇒ `Limit(-1)` ⇒ GORM **不生成 LIMIT** ⇒ 无界结果集

**位置**：`internal/api/handler_node.go:278-286`、`handler_notification.go:15-17`、`handler_vendor.go:36-41`

**现状**：

```go
// internal/api/handler_node.go:277-286
id := c.Param("id")
limitStr := c.DefaultQuery("limit", "100")
limit, _ := strconv.Atoi(limitStr)          // ← 错误被丢弃
node, err := findNodeByID(db, id)
...
db.Where("node_id = ?", node.NodeID).Order("timestamp DESC").Limit(limit).Find(&data)
```

```go
// internal/api/handler_notification.go:15-17
limit, _ := strconv.Atoi(c.DefaultQuery("limit", "20"))
var notifs []models.Notification
db.Order("created_at DESC").Limit(limit).Find(&notifs)
```

**机制（已核实到库源码）** —— GORM v1.31.2 `clause/limit.go:15-19`：

```go
func (limit Limit) Build(builder Builder) {
    if limit.Limit != nil && *limit.Limit >= 0 {     // ← 负值直接不写 LIMIT
        builder.WriteString("LIMIT ")
        builder.AddVar(builder, *limit.Limit)
    }
```

⇒ `GET /api/v1/nodes/:id/data?limit=-1` **没有任何 LIMIT**，返回该节点全部历史行（`device_data` 是分区大表）；
⇒ `?limit=abc` ⇒ `limit=0` ⇒ `LIMIT 0`，返回空集且**看起来像"没有数据"**。

**为什么是设计问题**：分页参数是**接口语义的一部分**，但这里被当成"随便解析一下的整数"。同一个仓里已经存在正确写法（`handler_node.go:114`：`if err != nil || limit < 1 || limit > 200 { ... }`）——**两种写法并存，说明缺的不是知识而是唯一实现**。这也解释了为什么 S1 的 clamp 会被抄 6 次却仍漏 5 处：规则没有归属。

**后果**：单次请求即可让后端把整表读进内存并序列化（`[]models.DeviceData`，含每行 `DataJSON` 文本）。本项目有 `handler_data.go` 的"分区表上无时间谓词会扫全部子分区"的前车之鉴（`latest_value_cache.go:9-13`），这里是**同一条 SQL 路径上的无界放大**。

**3.0 改进方向**：
1. `internal/api/dto/pagination.go` 提供唯一入口：`ParsePagination(c) (page, size int, err error)`，内部 clamp（1≤page，1≤size≤200）并对非法值**返回 400**（而不是静默回落）。
2. 列表接口一律走该入口；`Limit`/`Offset` 只从该结构取值。
3. **门禁测试**：对每个列表端点参数化跑 `limit=-1 / 0 / abc / 999999`，断言"要么 400，要么返回条数 ≤ 上限"。（当前会红。）
4. 3.0 若有 `transport` 层无界读的风险（TCP 流），同理：**任何"读取对端声明的长度"都必须先比对编译期上界**（3.0 方案 §5.2 已有此原则，把它上提为全局规范）。

### S5（严重）`ConfigEventBus.Publish` 丢事件却返回 `nil`：调用方的错误处理**不可达**，而持久化 outbox 只覆盖一条路径

**位置**：`internal/nodemgr/config_event_bus.go:60-77`；受害调用点 `internal/nodemgr/event_helper.go:43-45`

**现状**：

```go
// internal/nodemgr/config_event_bus.go:58-77
// Publish sends the event to the bus channel.
// If the channel is full, the event is dropped with a warning (non-blocking).
func (b *ConfigEventBus) Publish(evt ConfigChangeEvent) error {
    ...
    select {
    case b.ch <- evt:
        return nil
    default:
        logger.Warnf("ConfigEventBus buffer full, dropping event: type=%s action=%s node=%s entity=%s", ...)
        metrics.EventBusDroppedTotal.Inc()
        return nil // drop silently per design — alarm via metrics in production
    }
}
```

```go
// internal/nodemgr/event_helper.go:43-45 —— 永远进不去的分支
if err := bus.Publish(evt); err != nil {
    logger.Warnf("EmitConfigChange publish failed: %v (type=%s action=%s)", err, t, a)
}
```

**为什么是设计问题**：
1. **签名撒谎**：`error` 返回值是接口契约的"下一步可以做决定"。这里两条路径都 `return nil`，于是调用方**无法**重试、无法落盘、无法把失败透出给 HTTP 响应。注释自己写着 `drop silently per design` —— 这是把"静默丢弃"写成了设计意图，属于审计口径要抓的那类"看起来正常的缺陷"。
2. **丢弃的后果不是丢一条日志，而是丢一次配置下发**。`EmitConfigChange` 是 **5 个 api 文件 / 20 个调用点**共用的配置变更入口（可复跑：`grep -rn "EmitConfigChange(" --include='*.go' internal/api | grep -v _test`；其中 `handler_device.go` 5 处、`handler_edge_device.go` 3 处、`handler_node.go` 5 处、`handler_periph.go` 6 处、`handler_driver_commands.go` 1 处，例：`handler_edge_device.go:724`）。事件丢了 ⇒ SyncGate 不会为该设备生成 `SyncActionFull` ⇒ 设备继续用旧配置，而 API 已经返回 200。
3. **持久化只覆盖一条路径**：兜底的 `ConfigChangeOutbox` 只被 `internal/nodemgr/handler_channel_cmd_v2.go:200,231` 写入（`grep -rn "ConfigChangeOutbox" internal cmd | grep -v _test` 仅此 2 处写入 + `sync_gate.go` 3 处消费）。**CRUD 配置变更路径没有 outbox**。

**后果**：缓冲区 1,024（`manager.go:178`）在批量配置操作（如导入/批量改 100 个通道）或 SyncGate 消费端被一条慢 DB 事务卡住时会被打满；此后每次变更都只留一行 `logger.Warnf`，HTTP 侧全绿。现场表现为"改了配置没生效"，与项目已记录的 `docs/评审/雨量计静默事故-根因与修复方案-2026-09-22.md` §四"设备健康上报假绿"完全同构 —— **同一次事故的两个不同位置**。

**3.0 改进方向**：
1. **`Publish` 改为返回真实结果**：`error`（含 `ErrBusFull`），或返回 `enqueue func() error` 形式的显式重试闭包；**严禁**在失败路径返回 `nil`。
2. **默认必须持久化**：配置变更一律先写 outbox（与 v2 通道命令同一条路），再由 outbox worker 投递。这样 `EmitConfigChange` 的失败语义变成"本次 HTTP 失败/需要重试"而不是"静默丢失"。
3. **丢弃必须可归因**：`metrics.EventBusDroppedTotal` 无 label（`pkg/metrics/metrics.go:180-183`）——加 `type/action` 或至少 `source` label，并配一条"5 分钟内 drop > 0 即告警"的规则。
4. `ConfigEventBus` 注释写"Single subscriber model: only SyncGate subscribes"，但 `Subscribe()` 返回【同一个】channel，第二个订阅者会**偷走**事件。3.0 应改为"显式注册消费者 + 显式拒绝第二个订阅者"。

### S6（严重）`DataEventBus`：拿"丢最旧以保留最新状态"的策略承载**历史样本**，且丢弃无消费者归因、无背压到设备

> **对已知案例的核实结论（先纠正记录）**：用户给的线索是「`nodemgr` 的 `DataEventBus`（`bus.go:85`）实测 ≥400 报/s 开始丢弃，缓冲 256/64，满时静默丢最旧」。
> 实测（2026-10-06）：
> 1. **路径已变**：总线不在 `nodemgr/bus.go`，而在 **`internal/databus/bus.go`**，`bus.go:85` 是 `Publish` 的起始行。
> 2. **常量仍为 256 / 64**：`databus/bus.go:45-48` `dataChanBufferSize = 256`、`consumerMailboxSize = 64`。✅ 线索属实。
> 3. **"静默"已部分修复**：满时现在会 `recordDrop()` → `bus.dropped.Add(1)` + `metrics.DataEventBusDroppedTotal.Inc()`（`bus.go:99-115`）。**所以"静默丢弃"这条旧结论已过期**。
> 4. **但下面三条仍然成立**（这才是 3.0 要解的问题）。

**位置**：`internal/databus/bus.go:45-48`、`83-115`、`187-222`；`pkg/metrics/metrics.go:191-196`

**现状**：

```go
// internal/databus/bus.go:83-110
// Publish is non-blocking and safe after Stop. Under ingress pressure it drops
// an oldest event to retain the latest state.
func (bus *DataEventBus) Publish(evt DataEvent) {
    ...
    select {
    case bus.dataChan <- evt:
        return
    default:
    }
    select {
    case <-bus.dataChan:          // 丢掉最旧的一条
        bus.recordDrop()
    default:
    }
    select {
    case bus.dataChan <- evt:
    case <-bus.stopCh:
    default:
        bus.recordDrop()
    }
}
```

```go
// internal/databus/bus.go:198-220（每个 consumer 的 mailbox 满时同样"丢最旧"）
select {
case worker.mailbox <- evt:
    continue
case <-worker.done:
    continue
default:
}
select {
case <-worker.mailbox:
    bus.recordDrop()          // ← 同样丢的是最旧
case <-worker.done:
    continue
default:
}
```

```go
// pkg/metrics/metrics.go:191-196 —— 无 label，无法归因
DataEventBusDroppedTotal = promauto.NewCounter(prometheus.CounterOpts{
    Name: "ehome_data_event_bus_dropped_total",
    Help: "DataEventBus data reports dropped under backpressure",
})
```

**为什么是设计问题**：

1. **策略与语义错配（最核心）**。"丢最旧以保留最新状态"对**状态型**事件（最近一次读数、在线状态）是正确的；但同一条总线承载的是**时序样本**。对时序历史，正确策略是"丢新的并告知生产者"或"全部保留"，**绝不是丢最旧**——丢最旧恰好丢掉**最先到达、最可能已经解析成功、时间戳最早**的那批。`DataEvent` 里已经有 `Sequence` 字段（`bus.go:17`）可以检测缺口，但全仓无一处做缺口检测（`grep -rn "gap\|Gap" internal/databus internal/nodemgr` 在非测试代码中零业务命中，除注释外）。

   > 同一条总线一次丢弃会同时命中两类负载：`TerminalConsumer`（`consumers_light.go:25`，纯状态/流）、`WSPushConsumer`（:65）、`DBPersistConsumer`（`consumers_heavy.go:74`，历史）、`SensorParserConsumer`（:171，历史+状态）。**一个容量常量服务四种语义**。

2. **丢弃不可归因**：`DroppedCount()`（`bus.go:153`）与 Prometheus counter 都是**全局单值**。运维看到"在丢"却无法回答"是谁慢"。而 `fanout` 里丢的是**某一个** consumer 的 mailbox（`bus.go:205-219`），信息在 `recordDrop` 调用点就丢了。

3. **没有背压，只有丢弃**：`Publish` 的设计目标是"不阻塞 MQTT 回调"（`bus.go:83` 注释）。代价是**设备端永远不知道自己发的数据被丢了** —— MQTT QoS1 的 PUBACK 来自 broker，不是后端；broker 与后端之间是"后端吃了"。3.0 换成 TCP+TLS 之后，这个"假 ACK"会**变得更严重**：TCP 会话层天然可以做到真正的背压（窗口/NAK/重传），但如果沿用"查完就丢、不告知对端"的语义，就白白浪费了 TCP 的能力。

4. **消费端 panic 同样不计入任何指标**：`bus.go:231-238` 的 `recover()` 只 `slog.Error`，**不递增 `recordDrop`**，于是"丢弃"和"消费者崩了"在监控上是不可区分的。

**后果（真实）**：`docs/分析/运行期无界增长表-保留策略设计-2026-09-13.md` 记录过"运行期无界增长表"整类问题；本条的镜像问题是"运行期**静默减少**"——数据库里少了一段历史，而设备、MQTT、HTTP、日志四个面都显示正常。对**能耗/发电量类累计量**（`inverter_techfine`、`jiabaida` 驱动输出的累计 kWh）丢样本是**不可恢复**的：累计量的差值就是用户的收益数据。

**3.0 改进方向**：
1. **按语义分总线**（或给 `DataEvent` 加显式 `LossPolicy`）：`StateOnly`（可丢最旧）vs `History`（不可静默丢）。历史样本的过载处置只有三种合法动作：**阻塞/背压**、**溢出到磁盘/队列**、**显式 NAK + 计数**。禁止第四种（静默丢）。
2. **把丢弃做成"有名字的失败"**：`recordDrop(consumerName, reason)` → `DataEventBusDroppedTotal{consumer,reason}`，并在 `fanout` 里对**每一条**丢弃记采样日志（带 `device_id`/`sequence`）。
3. **利用 3.0 的会话层做真背压**：`transport/session` 持有每节点发送窗口与 seq/ack（3.0 方案 §4.6 已设计 `session.go`），把"后端来不及处理"变成**对端可观测的窗口收缩/暂停**，而不是本地丢弃。
4. **序列缺口检测**：既然 `Sequence` 已经在帧里（`handler_data.go:41`、`handler_data_batch.go:318`），在 ingest 边界维护 `(node_id, channel_id) → last_seq`，缺口即计数 + 事件；这样"丢了多少"从推断变成事实。
5. **容量按最慢消费者定，而不是全局 256/64**：mailbox 大小应是 consumer 的属性（`Register(c DataConsumer)` 时可声明），并在文档里写出"该容量对应多少秒的峰值"。

### S7（严重）"背压"是伪造的：溢出 goroutine 到 50 就阻塞 MQTT 回调，最终仍走会丢数据的 `Publish`

**位置**：`internal/nodemgr/handler_data.go:11-14, 90-116`；配套 `worker_pool.go:29-31, 97-118`

**现状**：

```go
// internal/nodemgr/handler_data.go:11-14
// P1-4: Backpressure — overflow goroutine limit for when worker pool is full
var overflowGoroutines int64
const maxOverflowGoroutines = 50

// internal/nodemgr/handler_data.go:90-116
func (m *Manager) enqueueDataReportJob(deviceID string, job dataReportJob) {
    select {
    case m.dataCh <- job:                       // 8 worker，缓冲 1024
    default:
        metrics.WorkerPoolOverflowTotal.Inc()
        for {
            current := atomic.LoadInt64(&overflowGoroutines)
            if current >= maxOverflowGoroutines {
                // Critical overload — block MQTT callback (better than data loss)
                metrics.WorkerPoolBackpressureBlockTotal.Inc()
                logger.Warnf("[%s] CRITICAL: overflow limit reached (%d), blocking MQTT callback", deviceID, current)
                m.processDataReportJob(job)     // ← 同步执行，直接占住 MQTT 回调
                break
            }
            if atomic.CompareAndSwapInt64(&overflowGoroutines, current, current+1) {
                go func() { defer atomic.AddInt64(&overflowGoroutines, -1); m.processDataReportJob(job) }()
                break
            }
        }
    }
}
```

而 `processDataReportJob` 的终点是 `m.dataBus.Publish(evt)`（`worker_pool.go:145`）——**一个缓冲区满时会丢最旧的函数**（S6）。

**为什么是设计问题**：
1. **注释与行为相反**：`// better than data loss` 是不成立的。这条路最终调用的 `Publish` 在压力下**必然**丢数据（`databus/bus.go:97-108`）。阻塞 MQTT 回调买到的是"这一次没在本函数丢"，但代价是把压力转移给整条 MQTT 读循环，且**丢的行为一分未减**。
2. **阻塞 MQTT 回调会拖垮一切**：`HandleMessage` 由 paho 的消息分发路径调用（`cmd/server/main.go:361 mqttClient.SetHandler(nodeMgr.HandleMessage)`）。在该回调里同步做"解析 + WS + DB 写"（`processDataReportJob` → 消费者）意味着**心跳、ACK、配置回执、OTA 进度全部排在后面**。这正是"控制面被数据面饿死"的经典形态 —— 而 `mqtt.go:94-96` 的注释显示作者已经意识到过同类问题（"a stuck broker must not let high-rate telemetry hold starve command/config publishes"），却在数据面反向做了一次。
3. **批量的放大效应**：`handleDataBatch`（`handler_data_batch.go:308-326`）把一帧 N 个样本**逐个** `enqueueDataReportJob`。一帧 100 样本在溢出状态下会**连续 100 次**同步执行，MQTT 回调被按住的时间 = 100 × 单样本耗时。
4. **`overflowGoroutines` 是包级全局**（`handler_data.go:12`）：进程内多个 `Manager`（测试、未来的多租户/多实例）共享同一个额度；且它不属于任何生命周期对象，`Stop()` 不会等它。
5. **批内不原子**：一批样本可能前一半进 channel、后一半走溢出 goroutine，两组的先后顺序在 `dataChan` 与 goroutine 之间无保证；叠加 S6 的"丢最旧"，用户看到的是**批内随机缺口**。

**后果**：`≥400 报/s 开始丢弃` 这个现场观测（用户口径，测量条件**待确认**，见 §7 U5）与代码路径一致：256 的 ingress + 8×1024 的 worker + 50 溢出，任何一项打满都会导致行为从"排队"跳变到"阻塞回调"或"丢最旧"。叠加 S2 的 8~10 次 SQL/样本，打满的门槛还会进一步下降。

**3.0 改进方向**：
1. **删除"溢出 goroutine"这一层**。它同时引入了无界并发的假象与回调阻塞的真实伤害。替代方案：**固定 worker 数 + 有界队列 + 明确的过载语义（背压或 NAK）**。
2. **把重活移出 MQTT/TCP 回调线程**：回调只做"切帧 + 投递到有界队列"，解析/DB/WS 一律在 worker 侧（现在 `handleDataReport` 已是这个方向，但 `enqueueDataReportJob` 的 `default` 分支把它破坏了——**去掉 default 分支里的同步执行**）。
3. **批为原子单位**：一帧 N 样本作为**一个** job 入队（或整批背压），避免批内撕裂。
4. **过载指标要能回答"哪个节点在制造压力"**：`WorkerPoolOverflowTotal`/`WorkerPoolBackpressureBlockTotal`（`pkg/metrics`）当前无 label，与 S6 同样的问题。

### S8（严重）周边指令"发了就算成功"：`checkManifestWireBytes` 的同类缺口清单

> 用户要求：找出与 `sender.go: checkManifestWireBytes` **同类**的"缺乏端到端契约"处。
> 核实结果：**配置下发路径已有端到端契约**（值得作为模板），**周边/配置指令与若干状态路径没有**。

**先说好消息（作为对照模板）**：配置 manifest 路径的契约是完整的 —— `sender.go:580-685` 在**同一事务**里 reconcile → snapshot → 编码，用 `checkManifestWireBytes(len(payload))`（:665）对**即将上线的同一份字节**做 fail-closed 门禁，失败走 `fail()` 把 `config_sync_state` 置 `failed`；设备侧再用 `config_hash` 回执闭环（`sync_gate.go:52-63` 明确写了"hash 相等只说明设备持有的配置，不说明应用成功"）。这是本项目**最好的一段接口设计**。

**同类缺口（按严重性）**：

**(a) 周边指令：HTTP 200 = 已发送，之后无任何终局**（`handler_periph.go:823-828`）

```go
requestID, err := nodeMgr.SendPeriphCmdWithID(node.NodeID, PeriphTypeGPIO, uint8(pin), action, value, nil)
if err != nil {
    Error(c, http.StatusInternalServerError, err.Error())

```

同步返回 `200 {"message":"command sent"}`，**不等设备回执**。`requestID` 只交给调用方，**不落库**：
- `periphPending` 是内存 map（`manager.go:81`），60 秒 TTL 惰性清理（`sender.go:163-171`），进程重启即丢；
- 没有"待确认/已确认/超时"的持久状态，用户无法回答"那条开闸指令到底生效了吗"；
- 对**控制类**动作（GPIO 置位、PWM 起停、BMS 动作）这是产品级风险：MQTT QoS1 的 PUBACK 只证明 broker 收到，不证明设备执行。

对照：`notify` 包已经把这件事做对了（`notify/dispatcher.go:216-226`：`result.Retryable` 区分可重试/终态、`beginAttempt/finishAttempt` 落 `notification_deliveries` 审计行）——**同一个仓里两种成熟度**。

**(b) 状态/报告类上报无终局**：`handler_resources.go`（907 行）与 `handler_status.go`（637 行）写库后仅广播；未见"设备上报的能力清单与服务器预期不一致"的校验与失败态（**待确认 U1**：本次未逐行读完这两个文件）。

**(c) `EmitConfigChange`**：见 S5 —— 配置变更的"发出成功"没有持久化回执。

**(d) 单样本入库失败**：`consumers_heavy.go:96,356,457` 写入失败只 `metrics.DataConsumerDBWriteFailures.Inc()` + `logger.Warn`，**不重试、不回写、不产生可见状态**。用户看到图表少一个点，与 S6 的丢弃在体验上无法区分。

**3.0 改进方向（统一契约，一次做对）**：
> **"发送"与"生效"必须是两个不同的接口名词，且后者必须落库。**

1. 定义统一命令生命周期：`POST /commands` → `202 {command_id, state:"PENDING"}`，随后 `GET /commands/:id` 返回 `CONFIRMED_SUCCEEDED / CONFIRMED_FAILED / TIMEOUT / ACKNOWLEDGED_UNKNOWN`。`commandexec` 包**已经有这套状态机**（`commandexec/service.go:62-65` `ResolutionConfirmedSucceeded` 等），周边指令应复用它，而不是另开一条"内存 map + 200"的路。
2. 对**所有**下行指令建立与 manifest 相同的三元组：**（α）发送前的上界/合法性门禁（fail-closed）；（β）与发送字节同源的一次性记录；（γ）设备回执驱动的终态**。
3. 给"发出去了但没回执"设**显式超时终态**（3.0 的会话层天然知道连接是否存活，比 MQTT 更可靠）。

### M7（中）SyncGate 单 goroutine 既消费事件又回放 outbox；失败无退避

**位置**：`internal/nodemgr/sync_gate.go:386-449`

```go
// internal/nodemgr/sync_gate.go:387-408
func (g *SyncGate) Start() {
    go func() {
        ch := g.eventBus.Subscribe()
        g.replayConfigChangeOutbox()
        ticker := time.NewTicker(time.Second)
        defer ticker.Stop()
        for {
            select {
            case evt, ok := <-ch:
                if !ok { ... return }
                g.processConfigChange(evt)
            case <-ticker.C:
                g.replayConfigChangeOutbox()      // ← 与事件消费共用同一个 goroutine
            }
        }
    }()
}
```

```go
// internal/nodemgr/sync_gate.go:437-449
func (g *SyncGate) replayConfigChangeOutbox() {
    var pending []models.ConfigChangeOutbox
    if err := g.mgr.db.Where("state = ?", "PENDING").Order("created_at ASC").Limit(100).Find(&pending).Error; err != nil { ...; return }
    for _, row := range pending {
        g.processConfigChange(ConfigChangeEvent{...})
    }
}
```

**为什么是设计问题**：
1. **回放会阻塞事件消费**：`processConfigChange` → `SendConfigManifestWithDecision` 走完整事务 + MQTT 发布（每设备最长 5 秒，见 M8）。一次回放最多 100 行 ⇒ 该 goroutine 可被占用很久，期间 `ch` 里的新事件堆积，**最终触发 S5 的丢弃**。也就是说 S5（事件丢失）与 M7（消费阻塞）是同一个故障的两个方向。
2. **失败无退避、无次数上限**：`processConfigChange` 返回 `false` 时 outbox 行保持 `PENDING`（:424-433），下一个 tick（1 秒后）再试一次 —— 一条永远失败的行会被**每秒重试到进程结束**，并每秒打一行 `logger.Warnf`。没有 attempt 计数、没有指数退避、没有死信。
3. **`Limit(100)` 是静默截断**：超过 100 行待处理时，其余行要等下一轮；本轮没有"还有更多"的日志/指标。

**后果**：与项目自己记录过的「`Limit(500)` 静默截断」是同一形状（`handler_pagination_contract_test.go:8-11`：「用户看到 500 条却以为看到了全部」）。

**3.0 方向**：① 消费与回放分离为两个 goroutine（各自有界）；② outbox 行加 `attempts / next_attempt_at / last_error`，指数退避 + 上限 + 死信态；③ 每轮处理数与剩余数进指标。

### M8（中）`mqtt.publish` 持全局锁跨网络等待；`periphMu` 同样跨 `Publish`

**位置**：`internal/mqtt/mqtt.go`（`publish`：`operationMu` + `waitPublicToken`）；`internal/nodemgr/sender.go:149-221`



**证据**：`publishTimeout = 5 * time.Second`（`mqtt.go:93`）；`waitPublicToken` 在 token 未完成时最多等满该时长（`mqtt.go` 内 select 含 `case <-timer.C`）。

**为什么是设计问题**：
1. **全局锁 + 网络 IO**：所有发布（配置、指令、OTA、HA 发现）串行经过同一个 `operationMu`。broker 卡顿时，一次发布最长占锁 5 秒，其余全部排队。作者在 `mqtt.go:94-96` 的注释里承认了这个风险，但只是给 QoS0 遥测单独降到 1 秒 —— **没有解决锁的作用域**。
2. **二级锁叠加**：`periphMu`（`sender.go:149`）包住 `operationMu`，于是"发一条 GPIO 指令"会把**所有**周边指令排在自己后面最多 5 秒。控制类操作的用户感知是"点了没反应"。
3. 这与 S7 的"阻塞 MQTT 回调"是同一类：**把可变持久状态与网络等待放在同一把锁里**。

**3.0 方向**：`transport/session` 设计成**每节点独立发送队列 + 独立锁**（3.0 方案 §4.6 的 session 已经含"发送窗口"），禁止跨节点全局锁；锁内禁止 IO，等待一律通过 channel/回调在锁外完成。判据：`go test -race` 下注入"broker 挂起 5 秒"，其他节点的指令延迟不受影响。

### M11（中）重组器接口无法表达"不完整"，且静默保留尾部

**位置**：`internal/nodemgr/stream_reassembler.go:51-86`；调用 `internal/databus/consumers_heavy.go:177`

```go
// internal/databus/consumers_heavy.go:27（接口）
type Reassembler interface { ... Append(deviceID string, requestID uint32, data []byte) []byte ... }

// internal/nodemgr/stream_reassembler.go:79-85
buf.data = append(buf.data, data...)
if len(buf.data) > sr.maxBytes {
    // Hard cap: keep tail
    buf.data = buf.data[len(buf.data)-sr.maxBytes:]
    logger.Warnf("[stream] %s requestID=%d buffer capped at %d bytes", deviceID, requestID, sr.maxBytes)
}
return buf.data
```

**为什么是设计问题**：
1. **返回值无法区分"完整帧"与"任意尾部"**：`Append` 只返回 `[]byte`。超过 `maxBytes=2048` 时它把**头部丢掉、保留尾部**并返回 —— 解析器拿到的是**一段没有起点保证的字节流**，却按完整帧解析。项目有一条相关教训（`docs/分析/解析器审计-ReadLength契约-2026-10-02.md`）：解析器契约被违反时会**产出貌似合理的错值**，而不是报错。
2. **接口没有"帧边界"概念**：3.0 的分片（`frag_off/frag_len/total_len/MORE`，方案 §5.1-5.3）是显式的；`Append` 这种"粘字节直到能解析"的接口形状无法承载它，也无法实现方案 §5.3 的 fail-closed 判定（乱序→拒绝整条、长度不符→丢弃、CRC 不符→丢弃）。**3.0 必须换接口，不是改实现**。
3. **requestID 位宽截断**：`DataEvent.RequestID`/`job.requestID` 是 `uint64`，接口是 `uint32`（`uint32(evt.RequestID)`）。当前固件用 32 位，暂无实际碰撞；但这是**类型系统里已经存在的静默截断**，3.0 重新分配消息号时容易踩到。
4. **maxAge 2 秒的 GC 只在 `Append` 里跑**（:59-67）：若某设备最后一次上报后不再有数据，它的缓冲要等**下一个**样本到达才被清理（`pending()` 只读不清理）。单条上限 2 KiB、键数上限 ≈ 设备数 × 并发请求数，量级可控，但"清理依赖后续流量"是应当显式化的生命周期（3.0 的 `session` 关闭时应主动释放）。

**3.0 方向**：`Reassembler` 改成显式状态机，返回结构化结果：

```go
type AppendResult struct {
    Status  ReasmStatus   // NeedMore / Complete / Rejected
    Payload []byte        // 仅 Complete 时有效
    Reason  string        // 仅 Rejected：offset_mismatch / len_mismatch / crc_fail / timeout / cap_exceeded
}
```
并在 `Rejected` 时计数 + 可选 NAK（方案 §5.3 已列出全部拒绝原因，接口照抄即可）。

### M12（中）写放大：每样本两次 `json.Marshal` + 两次 `fmt.Sprintf("%x")`，原始 hex 与解析结果各存一份

**位置**：`internal/databus/consumers_heavy.go:78-90`（① 原始）与 `442-459`（② 解析）

```go
// :78-90
dataJSON, err := json.Marshal(map[string]interface{}{
    "raw": fmt.Sprintf("%x", evt.RawData), ... })
...
// :442-447
dataJSON, err := json.Marshal(map[string]interface{}{
    "raw_hex": fmt.Sprintf("%x", merged), "sensors": sensorData, ... })
```

**为什么是设计问题**：`fmt.Sprintf("%x", ...)` 把字节变成**两倍长度的字符串**再进 JSON，最终进 `TEXT` 列（`models.go:272`：`DataJSON string gorm:"type:text"`）。同一份原始字节在 ① 与 ② 里各转一次（S3 的两行），并以 hex 文本形式**长期占库**。在 3.0 的目标速率下（800 样本/s × 300 B），这是 ~480 KB/s 的纯文本膨胀，且业务读取并不需要它（`device_data` 的读取只有 3 处：`handler_edge_device.go:1220,1245`、`handler_node.go:285`，都是直接返回给前端展示）。

**3.0 方向**：原始字节落 `BYTEA`（或对象存储/分区冷表），JSON 只放解析后的结构；`raw_hex` 这种"给人看的"表示放到**导出/诊断**接口里按需生成，不入库。

### L6（低）`readCounterTotal`：为绕开死锁而起的 goroutine，panic 时会泄漏

```go
// internal/api/handler_metrics.go:177-196
func readCounterTotal(c prometheus.Collector) int64 {
    ch := make(chan prometheus.Metric, 10)
    done := make(chan struct{})
    var total float64
    go func() {
        var m dto.Metric
        for metric := range ch {
            if err := metric.Write(&m); err == nil { if m.Counter != nil { total += m.Counter.GetValue() } }
        }
        close(done)
    }()
    c.Collect(ch)
    close(ch)
    <-done
    return int64(total)
}
```

**为什么是问题**：若 `c.Collect` panic（第三方 collector 完全可能），`close(ch)` 不执行 ⇒ 该 goroutine 永久阻塞在 `range ch` 上；panic 又被 `gin.Recovery` 吞成 500 ⇒ **每次请求泄漏一个 goroutine**。虽然当前只在 summary 端点调用，但"用 goroutine 绕死锁"是应当被记录下来的接口异味：它的根因是 `ch` 缓冲 10 与 label 基数不匹配（注释自己写了）。**3.0 方向**：`defer close(ch)`（配合 `recover`）或改用手写 `prometheus.Gatherer`，并把该逻辑移出请求路径。

## 6. 3.0 应确立的设计原则（从缺陷反推，逐条可执行）

> 每条都注明"反推自哪条缺陷"与"如何证伪"。

**P1 端到端契约三件套（发送前门禁 / 同源记录 / 对端回执）**
反推 S8、S5。任何下行动作必须同时具备：(α) 发送前的上界与合法性校验且 **fail-closed**（`checkManifestWireBytes` 是模板）；(β) 与"即将上线的同一份字节"同源的持久记录；(γ) 由对端回执驱动的终态（`CONFIRMED_*`）。**"发送成功"不得作为 API 的成功语义。**
*证伪*：对每个下行接口构造"设备不回执"的场景，断言其在超时后进入显式失败态且在 UI/API 可见。

**P2 丢弃必须是"有名字的失败"，且默认策略按负载语义选择**
反推 S5、S6、S7。允许 `drop-oldest` 的**只有**状态型事件；历史样本的过载只能背压 / 落盘 / 显式 NAK。所有丢弃点必须带 `{component, consumer, reason}` 标签计数 + 采样日志 + 告警阈值。
*证伪*：`grep -rn "drop" internal/` 每一处都能回答"丢了什么、为什么、谁受影响"。

**P3 `error` 必须携带分类，返回值不得撒谎**
反推 M4、S5、S8。领域错误类型（`NotFound / InvalidArgument / Conflict / Precondition / Retryable / Permanent`）+ `errors.Is/As` 映射到 HTTP；**禁止**在失败路径 `return nil`；**禁止** `Error(c, 404, "")`。
*证伪*：`ErrorWithCode` 覆盖 ≥90% 错误路径；`grep -c 'Error(c, [^,]*, "")'` = 0。

**P4 依赖在装配根一次性构造，且为编译期必填**
反推 M5、L2、L3、M9。`type Deps struct` + `NewXxx(deps)`，缺依赖编译期失败；包级变量只允许常量与指标；请求路径禁止 `panic` 与 `sync.Once` 初始化。
*证伪*：`grep -rn "options ...interface{}" internal/` = 0；请求路径无 `panic(`。

**P5 快变路径不得做慢变的 DB 查询（拓扑/配置/校准必须缓存）**
反推 S2、M1。数据面每样本的 SQL 数应 ≤ 2（1 批量写 + 1 状态更新）；拓扑与配置变更走事件失效而非 TTL 或每样本查询。
*证伪*：基准测试 —— 注入 800 样本/s，统计 `pg_stat_statements` 的 calls 与全表扫描次数。

**P6 一张表一个写入者、一个形状、一个读契约**
反推 S3、M12。"原始 vs 解析"共存必须分表或在同一行里显式区分（且写入者唯一）。读接口返回 DTO，不返回持久层行。
*证伪*：同一事件入库后，所有读取路径的字段集合逐字段一致。

**P7 任何来自外部的数字在使用前必须被限界（含"负值即取消限制"这类库语义）**
反推 S4、M11。分页、`limit`、`total_len`、`frag_len`、`count` 一律先比对编译期上界；解析失败返回 400 而不是静默回落。
*证伪*：参数化模糊测试 `limit ∈ {-1,0,abc,999999}` 全部被拒或受限。

**P8 锁内不做 IO；每节点/每设备的状态不共享全局锁**
反推 M8、S7、M2。发送路径按 3.0 的 `session` 分片；锁只保护内存结构，网络等待在锁外。
*证伪*：`-race` + 注入"单节点 broker 挂起 5s"，其他节点 P99 延迟不受影响。

**P9 消费者与队列的容量是"可声明的属性"，并有对应的过载语义**
反推 S6、S7。`Register(consumer, opts{Capacity, LossPolicy})`；容量必须能换算成"多少秒的峰值"，写进设计文档。
*证伪*：每个 consumer 都能回答"我的容量对应多少秒、满了会怎样"。

**P10 重组/分片必须是显式状态机，且"不完整"是返回值的一部分**
反推 M11、S4。3.0 的 `Reassembler` 返回 `{Status, Payload, Reason}`，拒绝原因与方案 §5.3 表一一对应；禁止"保尾截断后当完整帧解析"。
*证伪*：乱序/缺片/长度不符/CRC 坏/超时 5 类各 3 例，全部 fail-closed 且有独立计数。

**P11 测试只通过装配根构造被测对象**
反推 M10。`NewRouter(Deps)` 是唯一入口；每个路由文件一条"端点存在 + 已挂鉴权"的装配断言；新增测试默认外部测试包。
*证伪*：`grep -c "register.*Routes(" internal/api/*_test.go` = 0；故意注释掉一个 `v1.POST`，装配断言必须变红。

**P12 上下文与取消一路到底**
反推 M3。service/repo 第一参数 `ctx`；`db.WithContext(ctx)` 覆盖率 100%；长任务（OTA、清理、回放）用可取消的 `ctx` 而非裸 `go func`。
*证伪*：lint 规则固化"api 包不得出现裸 `db.`"；断开客户端后 PG 侧查询被取消（`pg_stat_activity` 可观测）。

**P13 监控指标必须带可归因的标签，且"丢弃"与"崩溃"必须可区分**
反推 S6、S5、M5、L1。`DataEventBusDroppedTotal{consumer,reason}`、`ConfigEventBusDroppedTotal{type,action}`、`PanicsRecovered{component}`；告警规则与代码同 PR 提交。
*证伪*：注入"某 consumer 故意变慢"，告警能指出是哪一个。

**P14 "原始字节"只存一次、以二进制形式存、按需呈现**
反推 M12、S3。`BYTEA`/对象存储 + 分区冷表；hex/JSON 表示只在导出接口生成。
*证伪*：单事件存储字节数下降 ≥50%（同一样本集对比）。

**P15 3.0 的传输层改造必须同时承接背压语义，而不只是替换 `Publish`**
反推 S6、S7、3.0 方案 §4.6。方案里 `transport/session` 已有"seq/ack/心跳/发送窗口"——**把后端过载表达为窗口收缩/暂停，而不是本地丢弃**；同时删除 MQTT 时代的 `MaxManifestWireBytes=2011`，换成方案 §5.2 的 16,384 B 重组上界（语义仍是 fail-closed）。
*证伪*：端到端压测 —— 后端降速时，设备侧应观测到发送受限/重传，而不是"发出去了但库里没有"。

**P16 审计/事件类写入不得静默失败**
反推 M6(a)。审计表、outbox、状态位属于"证据"，写入失败必须让调用方可见（HTTP 失败或显式 `PARTIAL` 语义）。
*证伪*：把审计表改成只读/写失败，自动化触发接口必须返回非 2xx 或明确降级标记。
