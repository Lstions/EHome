# 自动化引擎场景仿真验证（Scenario Simulation for the Automation Engine）

- 版本：v2.0
- 日期：2026-09-12
- 状态：已定稿（本文件是自动化域场景的**唯一契约**）
- 关系：基础设施（harness）见 [场景仿真验证框架.md](场景仿真验证框架.md)；本文件是其**自动化专章**，
  并按用户明确要求把「≥50 个场景」的口径收敛到**自动化引擎**。

---

## 1. 口径修正（这是本文件存在的原因）

前一版把「≥50 个场景」理解为全系统覆盖（部署/认证/节点/通道/数据/数据源/指令/OTA/实时/契约），
自动化只有 6 个。用户明确纠正：**50 个场景是针对自动化引擎的**。

因此本文件定义自动化引擎的 **62 个场景**（另加原有 6 个 `SIM-AUTO`，合计 68 个），
覆盖引擎的**每一条语义分支**，而不只是「能跑通」。

## 2. 为什么自动化引擎最需要这一层

自动化是「**条件 → 动作**」的闭环，它的正确性依赖三个真实世界的东西，**单元测试全都给不了**：

1. **真实时序**：`DurationSec` 连续满足、`CooldownSec` 冷却、日熔断跨零点重置、`pending_confirm` 的 24h 过期 ——
   全靠时钟，SQLite 单测里时间是假的。
2. **真实数据流**：触发来自 `SensorParserConsumer` 的解析回调（`SetAutomationSink` 二阶段注入）。
   本仓历史上最贵的缺陷就是「**sink 没注入 → 引擎从未触发，而单测全绿**」。
   自动化只要接错一次线，后果就是**用户家的灯不会亮、BMS 不会被保护**。
3. **真实动作链路**：`device_action` 必须走 `commandexec` 的 9 项 availability gate + 幂等 + 审计。
   gate 全是 fail-closed，任何一项不满足都静默变成 `failed_gate` —— 用户看到的是「策略配了但没执行」。

**结论：自动化的每一条分支都必须以「真实设备上报 → 真实引擎求值 → 真实指令下发/通知落地」来验证。**

> 同包跨文件调用是允许的（框架 §4.1 只约束**声明名**，不约束调用写法），且能避免多写者同时改一个文件。

## 7. 已识别的产品缺陷与缺口

### 7.0 【P0，已派修】全新部署后「未经确认的自动设备动作」静默失效

**现象**：自动化规则为 `device_action` + `require_confirmed=false` + 由传感器数据/时间窗口**自动触发**时，
事件恒为 `result=failed_dispatch` / `detail="invalid command request"`，**指令从未下发**。

**根因链**（逐行核实）：
| # | 位置 | 事实 |
|---|---|---|
| 1 | `cmd/server/main.go:236-244` | 进程**启动时**解析系统主体用户（`subject_key=system_admin`），把 `systemActorID` 冻结后传给 Planner |
| 2 | `internal/auth/initialize.go:67` | 该用户由 `POST /api/v1/auth/initialize` **在进程启动之后**创建 |
| 3 | `internal/automation/planner.go:139` | 自动路径用 `ActorUserID: p.systemActorID`（新装时恒为 0） |
| 4 | `internal/commandexec/service.go:443` | `in.ActorUserID == 0` → 直接拒绝 |

**为什么长期隐藏**：**重启后就读到了该用户**，于是「重启就好了」—— dev 环境反复重启恰好掩盖了它。
准确表述是「**首个进程的整个生命周期内**自动设备动作失效」。

**精确爆炸半径**（这一点很重要，避免误判）：
| 路径 | 受影响 | 原因 |
|---|---|---|
| 自动 + device_action + `require_confirmed=false` | **是** | `executeDeviceAction` 用 `systemActorID` |
| 自动 + device_action + `require_confirmed=true` | 否 | 先 `pending_confirm`，人工确认走 `ConfirmEvent` → **JWT actorID** |
| 手动触发 | 否 | `executeManualDeviceAction` → JWT actorID |
| `notification` 动作 | 否 | 不经过 commandexec |

**为什么是 P0**：自动化的核心价值就是无人值守时自动动作，而**多数用户不会再加一道人工确认**。
静默失效 + 用户以为策略生效 = 用户家的 BMS 没被保护。

**由谁发现**：3 个子代理**独立**报告同一条（CRUD/AUDT 作者、DBLN 作者），经主控逐行复核确认。
这正说明本框架的价值 —— 它把一条「单测永远发现不了（单测里 planner 直接注入 actorID）」的缺陷暴露了出来。

**修法**（已派修）：Planner **惰性解析 + 缓存**系统 actor（不再启动期冻结）；
解析失败时事件 `Detail` 写明真实原因 + 发一条用户可见通知（幂等只发一次）。

### 7.0c 一处引擎语义（**不是缺陷**，但容易被误写为断言）
冷却判定**优先于**满足性判定（`evaluator.go:430-434`）：冷却期内只要这一帧**带了该字段**，
就落一条 `suppressed_cooldown` 审计，**与当前是否满足条件无关**。
因此「天亮那一帧（值已回落）」也会给「天黑开灯」规则留一条抑制审计。
子代理原写「事件总数 == 1」的断言因此失败，改成断言引擎真正承诺的不变量（`notification == 1` + `suppressed ≤ 1`）——
**这是修正错误假设，不是放宽断言**。由此也发现一个待产品裁决的观察：
审计里会出现「值并未越限却记为 cooldown active」的行，若前端把它展示为「险些误触发」会有轻微语义误导。
