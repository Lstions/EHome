## 1. 功能概述

采集 → 上报 → 解析 → 入库 → 实时推送的全链路。包含：周期采集调度、DataEventBus 分片扇出、统一解析器、服务端降采样、数据源健康管理、逻辑设备身份。

## 2. 数据链路全景

```
节点 scheduler（interval_ms）
  → bus_worker（事件驱动 RX，v2.7）
  → DataReport(0x03) → MQTT up
中心端:
  → MQTT consumer（ingest）
  → DataEventBus（分片，heavy/light 消费者分离）
      ├─ SensorParserConsumer：统一解析器 pkg/parser（按 DeviceConfig 规则）
      │     └─ 告警求值回调（v3.4，alertCallback）
      ├─ DBPersistConsumer：unified_data 入库（血缘+归属双列）
      ├─ WSPushConsumer：data_update 事件推送
      ├─ （v3.4 的 RollupConsumer / 1min rollup UPSERT 已于 2026-09-15 退役，见 §6）
      ├─ TerminalConsumer / DataMetricsConsumer / PendingWriteConsumer
      └─（被动数据快速通道：终端/调试数据不经重路径）
```

## 3. unified_data 模型

```sql
CREATE TABLE unified_data (
  id BIGSERIAL,
  edge_device_id BIGINT,      -- 血缘（采集来源实例，永不改写）
  logical_device_id BIGINT,   -- 归属（数据身份，合并时 UPDATE）
  sensor_name VARCHAR(32), value DOUBLE PRECISION, unit VARCHAR(16),
  timestamp TIMESTAMPTZ, created_at TIMESTAMPTZ
);
-- 索引：device_id/timestamp + logical_device_id/timestamp（CONCURRENTLY）
-- v3.4: PG 月分区已落地（分区键 timestamp，主键 (id, timestamp)）；SQLite 不分区间构
```

**不变量**：

- 纯追加时序表，无 GORM 软删（Raw SQL 路径绕过 scope + retention 本就硬删）。
- 大表零 FK 被引用（分区改造安全）。
- rollup 保持 device 维度；logical scope 查询强制 raw（保形去重语义在 raw 上）。**（本项已随 rollup 于 2026-09-15 退役失效，见 §6）**

## 4. 查询链

| 场景 | 路径 |
|------|------|
| 历史趋势（长跨度） | raw + 服务端降采样（max_points LTTB 类 + gzip）；索引 + 分区裁剪，30 天窗口实测 3.6 ms（见 §6） |
| logical scope | 强制 raw + ROW_NUMBER 保形去重（MAX(id) 锚点） |
| 最新值 | latestValueCache（persist 旁路更新 + 启动回填 + miss 回落）（v3.4） |
| 实时数据 | WS data_update 订阅 |
| 导出 CSV | 服务端批查 + 流式导出 |

## 6. retention 与清理（v3.4 已落地）

- 配置：logical_devices.retention_days（默认 90；创建时快照系统级配置，可用环境变量 EHOME_DATA_RETENTION_DAYS 覆盖）。
- v3.3：每日 purge 任务 DELETE 分批。
- **v3.4**：unified_data 到期改整分区 DROP（O(1)，已落地）；device_data 表维持 DELETE。
- raw 默认保留 90 天（系统级默认值，可经 EHOME_DATA_RETENTION_DAYS 覆盖；30 天仅推荐配置示例）。
- **rollup：2026-09-15 裁决为「退役」**（见 `docs/分析/rollup-退役裁决-2026-09-15.md`）。
  - 沿革：2026-09-14 先裁决「停写」（读取侧从未接线：`precisionFor` 零生产调用者，且其 rollup 分支在生产不可达），冻结件保留一个迭代以决定「补读取路径 or 退役」。
  - 退役依据（EXPLAIN 实测复核）：30 天窗口 `unified_data` 查询 **3.64 ms / 1191 buffers**（`/unified-data/historical-batch`，无 LIMIT、全窗口载入后降采样——即 rollup 理论上最该救的那条路径）；带 LIMIT 的 `/devices/:id/history` 为 **0.79 ms / 104 buffers**。各分区上的 `(logical_device_id, "timestamp" DESC)` 与 `("timestamp")` 索引本就存在 ⇒ 长跨度查询本来就索引 + 分区裁剪。
  - 结论：rollup 的收益是「省几毫秒」，代价是第二张无界表（+保留期+清理器+测试）与「必须改数据模型才能接线」（该表无 `logical_device_id` 列，而本仓查询恒带 logical scope）。与 `operation_logs`（死 schema，「没人写」）同案处置，但理由不同：rollup 是「**写了没人读，且读了也不划算**」。
  - 处置：删 `EnsureRollupTable` + main.go 调用点 + `databus/rollup_consumer.go` + `rollupSink` 机制 + `models.UnifiedDataRollup1m`；表本身由 `database.AutoMigrate()` 尾部 `RetireLegacyRollup1m` 幂等 `DROP TABLE IF EXISTS`（存量库 `ehome`/`ehome_test` 由下次启动清除）。门禁（死表不得复活）见 `datalifecycle/rollup_retirement_gate_test.go`。
