# 为什么需要 NTP —— 实测结论与一个反直觉的真相

> 2026-10-18 真机闭环实测。本文档回答"为什么需要 NTP"，结论与直觉相反，先说答案。

## 结论

**当前配置下 NTP 不是"能不能连上"的前提，而是"证书时间语义有没有意义"的前提。**

两个事实同时成立，缺一不可理解：

1. C6 的时钟是 **1970-01-07**（`now=532927`，`time_trusted=0`），因为无 NTP 且掉电后 RTC 归零；
2. 但它**成功建立了 mTLS**，连上了 2026-10-18 才签发的证书。

第 2 条按常理不可能（`notBefore=2026-10-18` > 设备认为的现在 1970）。
原因是本项目 **关闭了 mbedTLS 的日期校验**：

```
esp32-collector/build/c6-n8/sdkconfig:
  CONFIG_MBEDTLS_HAVE_TIME=y
# CONFIG_MBEDTLS_HAVE_TIME_DATE is not set     ← 关键
```

三个 profile（c6-n8 / s3p-n16 / s3-n16）**全是关闭状态**。

## 所以 NTP 到底有什么后果？分两档

### 第一档：连不上（不会有）

日期校验关着 ⇒ 证书过期/未生效都**不会被发现** ⇒ 时钟再错也能握手。
这一档当前不成立。

### 第二档：连上了但**安全语义失效**（正在发生）

这才是真正的问题，而且比"连不上"更隐蔽：

| 后果 | 说明 |
|---|---|
| **证书撤销/过期不生效** | 过期 5 年的证书照样握手成功。轮换时"旧 CA 必须停用"靠的是服务端单边控制 |
| **`tls_guard` 的时间分级是死代码** | 见下节 |
| **服务端日志时间不可信** | `StatusReport` 的时间字段来自设备，1970 年的时间戳会污染时序分析 |

## 为什么 `tls_guard` 的时间分级在现状下永不触发

`tls_guard` 设计了一套很讲究的分级（`components/tls_guard/tls_guard.c:51-83`）：

```
时间不可信 + 证书类失败  →  SYNC_TIME_FIRST  (先校时，可自愈)
时间可信   + 证书类失败  →  FATAL           (证书真有问题，重试无用)
```

判据是 `cert_flags & TLS_CERTFLAG_TIME_RELATED`（EXPIRED | FUTURE）。
但 mbedTLS 只有在 `MBEDTLS_HAVE_TIME_DATE` 打开时才会置这两个位 ——
现在关着 ⇒ **这两个位永远为 0** ⇒ `TLS_FAIL_CERT_EXPIRED` 永不产生 ⇒
`SYNC_TIME_FIRST` 分支**永不执行**。

实测佐证：C6 每次连接失败的日志是

```
tls_esp: 连接失败: last_error=0x8006 code=0 cert_flags=0x0 -> NETWORK
          now=538210 time_trusted=0 -> RETRY_BACKOFF (hard_fatal=0)
```

`cert_flags=0x0` 在所有失败里恒为 0 —— 不是"这次没有时效问题"，而是**这个字段永远不会被填**。

## 那 NTP 应该怎么做？

### 必须同时改两件事，只做一件都是白做

| 只做 | 结果 |
|---|---|
| 只开 NTP，不开日期校验 | 时间对了，但证书过期仍然发现不了 —— **没解决问题** |
| 只开日期校验，不开 NTP | C6 时钟 1970 ⇒ **所有连接失败** ⇒ 全网设备失联 |
| **两个一起开** | 时间可信 + 证书时效生效 = 设计意图兑现 |

顺序有讲究：**先 NTP，后日期校验**。反了会立刻打出全网故障。

### 具体配置

```
CONFIG_EHOME_NTP_SERVER="pool.ntp.org"    # 现在是空 ⇒ SNTP DISABLED
CONFIG_MBEDTLS_HAVE_TIME_DATE=y           # 现在是 not set
```

并且要在**开启日期校验之前**确认：所有在网设备的 NTP 都能成功（即 uptime 几秒内
`time_trusted=1`）。当前 C6 做不到（无 NTP 服务器配置），S3P 做到了
（`now=1792305384 time_trusted=1`）—— 两台设备的差异正好说明"没有 NTP 时时间全靠运气"。

## 一个容易被忽略的副作用：`notBefore` 成为上线硬门槛

一旦开日期校验，**证书签发时间就成了设备能否上线的硬门槛**。这意味着：

1. **设备必须先拿到正确时间，才能验证证书**；
2. **但设备拿到时间的途径只有网络**，而网络连接本身要先过 mTLS。

这是个真实的循环依赖。打破它的方式只有两种：
- **`notBefore` 回退**：签发时把 `notBefore` 设为当前时间**之前**（例如 -1 天），给时钟漂移留余量；
- **首次上线例外**：设备在"从未成功同步过时间"时先放行（`tls_guard` 已有 `time_trusted` 判据，可复用）。

第二种更稳，但需要在服务端侧也配合（服务端不能因为设备证书时间看起来不对就拒绝）。
本项目服务端用 Go 标准库，`tls.RequireAndVerifyClientCert` **会**校验设备证书时间 ——
所以真实约束是：**设备时钟必须对到能让 `notBefore ≤ now ≤ notAfter` 的程度**。

## 建议

| 优先级 | 动作 | 理由 |
|---|---|---|
| P1 | 配置 `CONFIG_EHOME_NTP_SERVER` | 零风险，立刻让 `time_trusted` 从"看运气"变成"确定" |
| P1 | 签发时 `notBefore` 回退 1 天 | 消除时钟漂移导致的启动失败 |
| P2 | 确认全部设备 NTP 成功后，再开 `MBEDTLS_HAVE_TIME_DATE` | 有前置条件，不能直接开 |
| P2 | 开日期校验后，把 `tls_guard` 的 `SYNC_TIME_FIRST` 路径用测试锁死 | 它现在从未被执行过，属于"写了但没验证"的代码 |
