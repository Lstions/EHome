## 1. 功能概述

站内通知统一呈现：合并任务结果、告警（v3.4 起）、数据源健康异常、自动化规则动作、保留期临期提醒。前端铃铛 + 未读计数 + 面板 + 全部已读；点击跳转目标页。

> **注意**：「配置同步失败、节点离线、OTA 结果」为早期设计意图，**当前并未实现**
> （源码无写入点、审计库无记录），详见 §4。

## 2. 数据模型

```sql
CREATE TABLE notifications (
  id, type, title, description, message, source, source_id,
  read, created_at, ...
);
```

- type 语义：info / warning / error / success（前端按 type 映射图标）。
- source 用于回链：如 source="alert_rule"、source_id=ruleID 跳转告警规则页。

## 3. 端点

| 端点 | 用途 |
|------|------|

| /notifications/:id/read | 单条已读 |
| /notifications/read-all | 全部已读 |

## 6. 容错设计

- 通知写入失败不影响主业务路径（旁路写入）。
- 批量合并：同源同内容的连续事件合并计数（防刷屏）。
- 自动清理（D-2 补齐）：由既有每日 retention 任务（`RetentionTask.RunOnce`）顺带执行，
  实现见 `backend/internal/datalifecycle/notification_cleanup.go`，**无新增后台协程**。
  - **已读**通知：超过保留期即删（默认 **90 天**，取 `SystemRetentionDays()`，
    与 `config.DefaultDataRetentionDays` 同源，不新增独立配置项）。
  - **未读**通知：保留期为已读的 **2 倍**（默认 **180 天**）后同样删除。
    只删已读修不掉 D-2——用户从不点开铃铛时未读只增不减，表仍会无限膨胀；
    未读代表用户尚可能想看，故给更长窗口而非等长。
  - 影响面：告警通知的已读态落在 Notification 行上（`handler_alert.go`），
    删掉 180 天前的未读告警通知只会让回链列表重新显示未读；告警本体
    仍完整保留在 `alert_events` 表中，不丢失告警历史。
  - 分批删除：与 purge/retention 同一范式，每批独立事务
    （PG 1 万行 / SQLite 1 千行），批间 sleep 200ms，避免长事务与 WAL 膨胀；
    清理幂等，失败仅 `slog.Warn`，不影响主业务与 retention 主流程。

## 9. 外发通知通道（D-1，2026-09-15 回写）

> **为什么必须在本文件里写这一节**：设计文档此前只描述"站内通知"，
> 于是"通知中心"与"外发通道"被当成了两件事 —— 实际它们是**同一条事实的两个出口**
> （同一条 `notifications` 行，一边落库 + WS 广播，一边按通道配置出站）。
> 不写进来的后果已经发生过：`backend/simulation/catalog/notify.go` 的头注释
> 因此长期声称"全仓没有任何外发通道"，直到 2026-09-15 才被纠正。

### 9.1 数据模型

| 表 | 用途 |
|---|---|
| `notification_channels` | 通道配置（name / type / target_url / secret / template / min_level / enabled / timeout_sec / max_retries / allow_private） |
| `notification_deliveries` | 投递审计，**每次尝试一行**（1 条通知 × N 个通道 × M 次尝试） |

- `secret` 是**只写不读**列（`json:"-"`），列表/详情只回 `secret_hint`（末 4 位）供辨认；
- `target_url` 序列化时**必须脱敏**（企业微信的 key 就在查询串里）——
  这条由 `TestRedactTargetURLMatchesNotify` 守住（守护测试在 `internal/notify` 包，
  因为 `models` 不能反向 import `notify`）。

### 9.2 端点

| 端点 | 用途 |
|---|---|
| `GET /notification-channels` | 通道列表（永不返回 secret） |
| `POST /notification-channels` | 创建 |
| `PUT /notification-channels/:id` | 更新（secret 未传=不改，传空串=清空） |
| `DELETE /notification-channels/:id` | 删除（**deliveries 保留**，删通道不得销毁审计） |
| `POST /notification-channels/:id/test` | 配置自检：**直达该通道**，enabled / min_level 过滤都不参与 |
| `GET /notification-deliveries` | 投递审计（channel_id / state 过滤 + 真分页） |

### 9.3 投递语义（冻结）

1. **fail-open（旁路纪律）**：出站失败**不**回滚业务事务、**不**阻塞采集热路径、
   **不**返回错误码；失败只落到 `notification_deliveries` + 指标 + 日志。
   因此"接收端 500 / 超时 / 连不上"都必须让通知**照样落库**。
2. **审计逐次留痕**：每次尝试先写一行 `pending`（崩溃窗口的唯一证据），
   拿到结论后改写 `delivered`/`failed`；重试**新开一行**（`attempt_no` 递增）。
3. **状态机**：`pending → delivered | failed`；指数退避 1s/2s/4s…上限 30s，
   `max_retries` 上限 5（失败必须能收敛到终态）。
4. **SSRF 闸门**：按**解析出的 IP** 判定（防 DNS rebinding），并且**按该 IP 拨号**；
   loopback/private/link-local/ULA 默认拒绝，仅 `allow_private=true` 的通道可例外
   （家庭内网 OneBot）。
5. **脱敏**：URL 查询串里的 key/token、Authorization 头、Bearer 令牌
   **永不**出现在日志、错误文案或投递审计里。
