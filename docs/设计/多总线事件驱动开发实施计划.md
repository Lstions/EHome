## 2. 核心需求

### 2.1 动态物理接口分配

逻辑 Channel 不固定绑定 UART0、UART1、SPI 或 I2C controller。配置应用时由资源规划器根据以下信息动态选择物理资源：

- 总线类型；
- 引脚和引脚冲突；
- controller 占用状态；
- console/boot 约束；
- DMA 请求和硬件能力；
- 共享总线规则；
- 当前 lease，避免无关配置导致接口随机切换。

### 2.2 UART0/UART1 完全平等

UART0 与 UART1 必须使用同一套：

- runtime 数据结构；
- command worker；
- driver event queue；
- RX event worker；
- 透明接收与自动边界状态机；
- DMA 请求与分配流程；
- 错误和性能统计。

当前实机上 UART0 或 UART1 分别接入什么设备，只是运行时 lease 结果，不进入业务代码。

### 2.3 统一透明接收

UART 对外只有一种透明接收流程，不增加需要用户选择的接收模式。

数据提交边界由运行时状态自动确定：

1. pending command 的明确 `read_size`；
2. 已知协议长度、结束符或 CRC；
3. pending command 的 idle timeout；
4. 无 pending command 时的最大 block 大小或最大等待时间；
5. transaction timeout 或错误事件。

### 2.4 总线处理和网络发送解耦

UART RX、SPI transaction 和 I2C transaction 完成后只投递 report descriptor，不直接执行 MQTT/TCP 发送。

控制结果和普通数据必须使用不同优先级或保留容量，防止高速 UART 数据延迟 ChannelCmdV2 Final、ConfigResult、StatusReport 或 OTA 状态。

### 2.5 DMA 保持可配置

- `dma_enabled=false`：明确不使用 DMA；
- `dma_enabled=true`：要求资源规划器分配兼容 DMA，资源不足时拒绝配置；
- UART0/UART1 平等申请有限 UART DMA 资源；
- SPI DMA 保持 driver 的实际 DMA 开关；
- I2C DMA 开关不得改变 repeated START/STOP 协议语义；
- 不支持 DMA 的硬件不得报告已分配。

## 3. 目标架构

```text
Backend command / Scheduler
             │
             ▼
Channel → Controller Lease Map
             │
     ┌───────┼────────┐
     ▼       ▼        ▼
 UART runtime   SPI runtime   I2C runtime
 control/sample control/sample control/sample
 queues         queues         queues
     │             │             │
 UART TX/RX     SPI transact   I2C transact
 driver event       │             │
     └──────────────┼─────────────┘
                    ▼
          Critical / Telemetry Report Queues
                    │
                    ▼
             Publisher Task
                    │
              MQTT / TCP
```

建议的 controller runtime：

```c
typedef struct {
    uint8_t bus_type;
    uint8_t controller_id;
    bool active;
    uint32_t generation;
    QueueHandle_t control_queue;
    QueueHandle_t sample_queue;
    TaskHandle_t command_task;
    void *lease;
    void *bus_specific_runtime;
} bus_controller_runtime_t;
```

上层仅通过 `channel_id` 查询 lease，不通过 UART 编号决定路由。

## 4. 分阶段实施

## P0：配置与协议契约冻结

### 目标

### 开发内容

- 明确 ResourceReport 中的实际 controller、引脚、DMA request/allocated；
- 固件解析 Channel field 8 `dma_enabled`；
- 保留旧 `bus_config` flags 兼容路径；
- 能区分 field 缺失和显式 false；
- 定义 sequence、overflow、discontinuity 和 queue high-water；
- 定义 C6 UART DMA 冲突以及 I2C DMA 不支持时的拒绝行为。

### 预计影响文件

- Frame/ResourceReport/StatusReport 编解码测试

### 阶段完成标准

- 新旧 manifest host tests 通过；
- backend 与 firmware 对字段含义一致；
- 资源冲突可以在 runtime teardown 前拒绝；
- 本阶段不改变现有实机运行行为。

## P1：资源规划器与动态 lease

### 目标

解除逻辑 Channel 与固定物理 controller 的绑定。

### 开发内容

- 建立 bus resource planner；
- 建立 UART/SPI/I2C controller runtime 数组；
- 根据 Channel 配置计算完整 allocation plan；
- 默认引脚只作为 capability/评分，不作为强绑定；
- 优先复用当前兼容 lease；
- planner 在 teardown 前记录每个兼容 Channel 的实际 controller，并在重新初始化时
  以 preferred controller 强制复用；若 controller 已被占用或配置已不兼容则明确
  失败/重新规划，不静默漂移到另一个 UART/SPI/I2C controller；
- 校验 GPIO、console、controller、DMA 和共享总线冲突；
- plan 全部成功后才执行 teardown/apply；
- ResourceReport 上报最终 lease；
- 失败回滚到原 lease、driver 和 DMA pool。

### 预计影响文件

- `esp32-collector/components/bus_manager/*`
- `esp32-collector/components/bus_dma/*`
- `esp32-collector/components/dma_pool/*`
- `esp32-collector/components/hw_profile/*`
- `esp32-collector/main/app_state.*`
- `esp32-collector/main/config_apply_transaction.*`
- `esp32-collector/main/app_callbacks.c`
- backend ResourceReport 和配置校验

### 阶段完成标准

- 同一逻辑 Channel 可分别租用 UART0 和 UART1；
- 两个 UART 使用相同 worker 入口；
- 命令和 RX 数据按 Channel lease 正确路由；
- 无关 manifest 更新不改变兼容 lease；
- apply 失败后原配置继续工作。

## P2：UART RX 事件驱动行为等价改造

### 目标

移除固定 5 ms 数据轮询，同时暂不改变外部 DataReport 和既有响应语义。

### 开发内容

- UART driver 安装时获取 event queue；
- 每个 UART runtime 创建同构 RX event task；
- 处理 UART_DATA、FIFO overflow、buffer full、frame/parity error；
- RX task 只搬运数据、更新状态和投递 descriptor；
- ChannelCmdV2 批处理响应也由同一 RX event owner 搬运；命令任务只等待有界 hand-off
  和 task notification，不直接读取 driver ring；
- 配置 suspend 使用 lifecycle queue/QueueSet 唤醒阻塞任务；
- driver 删除前必须收到 RX task suspend ACK；
- 保留旧 idle 判帧作为行为等价基线；
- 增加 UART 事件和错误统计。

### 预计影响文件

- `esp32-collector/components/bus_dma/bus_dma.c/.h`
- `esp32-collector/components/bus_worker/bus_worker.c/.h`
- `esp32-collector/main/app_state.*`
- `esp32-collector/main/app_callbacks.c`
- UART host test stubs 和实机脚本

### 阶段完成标准

- UART RX 不依赖 5 ms 数据扫描；
- UART0/UART1 对称回归通过；
- SN-3001 读取、写入、改地址、改波特率和读回通过；
- GB3024/嘉佰达模拟回归通过；
- 配置切换期间无 use-after-delete；
- RX event task 不调用 MQTT。

## P3：统一自动边界与异步上报

状态：已实现（需 P6 实机长稳验收）。

### 目标

用一套状态机处理请求响应和持续输入，并将总线执行与 MQTT/TCP 解耦。

### 开发内容

- 实现统一透明接收状态机；
- pending command 优先使用 `read_size`/协议边界；
- 未知长度响应使用 idle timer；
- 无 pending command 时使用最大 block/最大等待时间；
- 响应完成后的剩余字节继续进入透明接收链路；
- 建立固定 RX block pool；
- 队列只传递小 descriptor，不复制大块 payload；
- 建立 critical report queue 和 telemetry report queue；
- critical queue 额外保留 1 个 emergency block/descriptor，用于关键错误或边界异常
  的有界兜底；池耗尽只计数并丢弃，不从总线任务同步调用 transport 回调；
- 普通 WriteRsp 也进入独立 control-response queue；总线 command task 只复制固定长度
  descriptor，publisher task 才执行响应编码和 transport send；
- 独立 publisher task 执行编码和 transport send；
- 扩展 DataReport 编码容量以承载固定 payload block；
- 启用 per-channel sequence 和 discontinuity；
- 所有队列设置固定内存上限。

### 预计影响文件

- `esp32-collector/components/bus_worker/*`
- `esp32-collector/components/msg_handler/*`
- `esp32-collector/components/frame/*`
- `esp32-collector/components/transport/*`
- `esp32-collector/components/ehome_mqtt/*`
- backend DataReport/DataEventBus/metrics
- frontend 原始数据展示路径（只在必要时限频）

### 阶段完成标准

- SN-3001 短响应不会被半帧完成；
- 持续输入不依赖 idle 也能持续提交；
- 同一 Channel sequence 有序；
- MQTT 短时阻塞不直接阻塞 UART RX；
- critical report 不被 telemetry 挤占；
- 断网不会造成无界内存增长。

## P4：Scheduler 与队列背压隔离

状态：已实现。每个 UART0/UART1/SPI/I2C controller 均有独立 sample/control
队列，worker 使用同构的控制优先、四连发后让渡采样策略。

### 目标

任一总线的拥塞不扩散到其他 controller。

### 开发内容

- scheduler 按目标 controller 检查 queue pressure；
- 修正不同 queue depth 共用 `CMD_QUEUE_DEPTH` 阈值的问题；
- control 与 sample 使用独立队列或明确保留槽位；
- 控制命令优先调度；
- 普通采样允许按本总线压力跳过；
- 每个 controller 统计 depth、high-water、skip、reject 和 timeout；
- 逐步缩小 `bus_cmd_t` queue item，使用 payload pool。

### 预计影响文件

- `esp32-collector/components/scheduler/*`
- `esp32-collector/components/bus_manager/*`
- `esp32-collector/components/bus_worker/*`
- `esp32-collector/main/app_state.*`

### 阶段完成标准

- UART 高负载不会阻止 SPI/I2C/另一 UART 入队；
- sample queue 满时控制命令仍可执行；
- 无控制饥饿；
- 内存和 queue item copy 开销受控。

## P5：DMA、SPI、I2C 语义统一

状态：已实现（需 P6 实机矩阵验收）。

### 目标

保证 DMA 开关只影响传输资源，不改变业务协议。

### 开发内容

- UART DMA 由 planner 和 DMA pool 联合分配；
- C6 两个 UART 同时请求唯一 DMA 时拒绝 manifest；
- SPI DMA 继续使用 `SPI_DMA_CH_AUTO`/`SPI_DMA_DISABLED`；
- 同一物理 SPI bus 的 DMA 属性保持一致；
- I2C write+read 始终保持协议需要的 combined/repeated START；
- C6 I2C DMA 请求按 capability 拒绝；
- 修复 I2C 先检查 bus 数量、后尝试复用的顺序问题；
- 校验实际 driver 行为与 ResourceReport 一致。

### 预计影响文件

- `esp32-collector/components/dma_pool/*`
- `esp32-collector/components/hw_profile/*`
- `esp32-collector/components/bus_dma/*`
- `esp32-collector/components/bus_manager/*`
- backend capability 和 manifest admission

### 阶段完成标准

- UART0/UART1 交换 lease 后 DMA 行为一致；
- SPI/I2C 数据不因 DMA 开关改变；
- 不支持的 DMA 请求不会进入 runtime rebuild；
- DMA apply 失败可恢复原 pool。

### 当前实现记录

- `bus_worker` 使用 UART driver event queue，并用固定 payload block pool 和
  descriptor queue 将 DataReport 发布移到独立 publisher task；critical 与 telemetry
  使用独立保留池，普通 WriteRsp 使用独立 control-response queue，telemetry 丢弃计数和 queue high-water 通过 StatusReport
  runtime performance 字段 6/7 上报。
- DataReport 发布缓冲已扩展到可承载 1024B event-driven block（含 wire/routing
  开销），frame C/Go 编码器同时修复 16 号以上字段的 canonical varint tag，保证
  StatusReport 队列指标字段 18～27 在设备与后端之间可互通。
- UART 自动边界统一为 `read_size`、固定 512B block 和 idle 收尾；无长度 pending
  响应允许连续分块并在 idle gap 关闭 pending descriptor。UART0/UART1 共用同一套
  状态机，SPI/I2C DataReport 也共用该异步上报路径并生成 channel sequence。
- scheduler 按目标 queue 预留 2 个 control 槽位，拥塞只抑制本 controller 的 sample；
  I2C write+read 无论 DMA 开关均使用 combined/repeated-START API。

## P6：性能、长稳和故障验证

### 目标

完成 1 Mbps 对称绑定、全功能回归和异常场景验证。

### 必测组合

```text
A：UART0 连续 1 Mbps，UART1 SN-3001 9600
B：UART1 连续 1 Mbps，UART0 SN-3001 9600
```

两组都要覆盖 DMA 开/关、MQTT 断连、配置切换、SPI/I2C 并行、OTA 和日志任务。

### 阶段完成标准

- 无未解释 sequence gap；
- 无 FIFO/ring/block pool overflow；
- UART 交换绑定后功能结论一致；
- SN-3001 成功率和 p95/p99 达标；
- SPI/I2C 无新增错误；
- heap、栈和 queue 长稳；
- 无 watchdog、panic 或异常重启。

## P7：灰度发布

### 目标

在专用测试节点验证后逐步扩大范围，并保留明确回滚能力。

### 发布步骤

1. host tests 和模拟串口；
2. 专用 C6 节点动态 lease 验证；
3. SN-3001 在 UART0/UART1 间交换；
4. 小范围高速输入；
5. 一个完整业务周期观察；
6. 更新默认固件前完成长稳报告。

### 回滚触发条件

- lease 与 ResourceReport 不一致；
- UART 响应错配；
- ChannelCmdV2 Final 超时或重复；
- SN-3001 成功率下降；
- 无法解释的 sequence gap；
- SPI/I2C 新增错误；
- heap 持续下降或 watchdog 重启；
- 配置回滚无法恢复原 lease。

## 7. 完成定义

全部满足以下条件才算完成：

1. Channel 可动态租用 UART0 或 UART1；
2. UART0/UART1 交换设备后功能与性能结论一致；
3. UART RX 不依赖固定 5 ms 数据轮询；
4. UART 只有统一透明接收流程，不需要用户选择模式；
5. UART 高负载不阻塞控制、另一 UART、SPI 或 I2C；
6. DMA 配置、硬件 capability 和实际 driver 行为一致；
7. SPI/I2C 协议不因 DMA 开关改变；
8. 配置失败能恢复原 lease、DMA 和 driver；
9. 1 Mbps 对称压力、故障和长稳验证通过；
10. 所有丢包、溢出、队列和资源冲突都可观测、可解释。
