> **作用**: 整个系统所有文档、代码、API、数据库 schema、WS 事件、协议字段, 必须使用本文档定义的术语
> **关联**: [00-概念模型.md](00-概念模型.md) | [命名迁移设计.md](../archive/命名迁移设计-v2.2.md)

## 0. 为什么要重定义

v2.0 / v2.1 阶段,"设备" 一词在系统不同位置指代不同事物:
- 物理 ESP32 设备 → 叫"采集器" (Collector)
- 抽象的"传感器型号" → 叫"设备模板" (Device Template)
- 实际接入的传感器 → 叫"设备" (Device)

**问题**: 三层概念混用,新人理解成本高,文档描述不准确,**"通道"和"设备"边界不清**。

v2.2 重定义为**四层模型**,每层只关心自己的职责。

---

## 1. 四层概念模型

```
┌───────────────────────────────────────────────────────┐
│  Layer 4: 平台 (Platform)                              │
│    整个系统 (e.g. "EHomeSystem")                       │
└───────────────────────────────────────────────────────┘
                          ▼
┌───────────────────────────────────────────────────────┐
│  Layer 3: 中心端 (Center)                              │
│    服务端 (Go 后端) + 数据库 + 规则引擎                 │
│    负责: 节点管理 / 设备配置管理 / 数据汇聚              │
└───────────────────────────────────────────────────────┘
                          ▼ MQTT / HTTP
┌───────────────────────────────────────────────────────┐
│  Layer 2: 节点 (Node)         ← 物理边缘设备           │
│    嵌入式 (ESP32-C6 / ESP32-S3)                        │
│    负责: 总线 IO / 协议 / 数据采集 / 数据上报            │
└───────────────────────────────────────────────────────┘
                          ▼ 总线 (UART/I2C/SPI/GPIO/ADC)
┌───────────────────────────────────────────────────────┐
│  Layer 1: 边缘设备 (Edge Device) ← 逻辑上的设备        │
│    节点通过某通道接入的"一个具体传感器/执行器"            │
│    e.g. "Node A 上的 SPI2 上挂的 BMP280"               │
└───────────────────────────────────────────────────────┘
```

> **关键**: 每一层只与它的**直接上下层**对话。节点不直接管理边缘设备的型号定义 (那是中心端的事); 中心端不直接控制节点的硬件 (那是节点自身的事)。

---

## 2. 核心术语 (8 个, 全部加粗记忆)

### 2.1 节点 Node

**定义**: 部署在现场的**物理嵌入式设备**,运行 EHomeSystem 固件 (基于 ESP-IDF),通过 MQTT 与中心端通信。

**特征**:
- 唯一 ID: `node_id` (e.g. `esp32c6_404CCA57B7BC`)
- 有自己的固件版本 (`firmware_version`)
- 通过 WiFi 连接,周期性上报 StatusReport
- 资源 (CPU/Heap/通道数) 有限,嵌入式

**当前实例**: ESP32-C6 / ESP32-S3 (后续支持更多平台)

**易混点**:
- ❌ 不是"采集器" (v2.1 命名, 已废弃)
- ❌ 不是"边缘设备" (节点是物理整机, 边缘设备是节点上挂的具体传感器)
- ✅ 旧名"采集器" / "Collector" 全部替换为"节点" / "Node"

---

### 2.2 通道 Channel

**定义**: 节点上的**物理通信端点** (UART/I2C/SPI/GPIO/ADC),描述如何与外设通信。

**特征**:
- 一个节点有 N 个通道 (1 ≤ N ≤ 32)
- 每条通道绑定一个总线类型 (BusType)
- **只描述物理**: 引脚、速率、模式、I2C 地址范围、SPI CS 引脚
- **不描述**: 上面挂什么型号设备 (那是边缘设备的事)

**示例**:
```yaml
- id: 1
  bus_type: SPI
  bus_config:
    mosi_pin: 11
    miso_pin: 13
    sck_pin: 12
    cs_pin: 10
    clock_hz: 10000000
    mode: 0
- id: 2
  bus_type: I2C
  bus_config:
    sda_pin: 8
    scl_pin: 9
    clock_hz: 400000
```

**易混点**:
- ✅ 通道 = 物理 (引脚/速率/模式)
- ❌ 通道 ≠ "挂着的设备" (那是边缘设备)

---

### 2.3 设备配置 Device Config

**定义**: 一种**设备型号**的协议无关元数据定义,描述"这个型号是什么 / 怎么初始化 / 怎么解析数据"。

**特征**:
- 一个型号一个 DeviceConfig (e.g. "BMP280 型号配置")
- 与具体节点/通道解耦,可在多个节点上复用
- 由中心端管理,中心端统一下发
- 包含三个核心部分:
  1. **设备连接参数** (Connection): 协议/默认参数
  2. **数据解析器** (Parser): 把 raw bytes 解析成物理量
  3. **业务配置流程** (Init Flow): 校准/初始化步骤序列

**示例 (BMP280 设备配置)**:
```yaml
id: 5
name: "BMP280 大气压传感器"
device_type: bmp280
vendor: bosch
# 1. 设备连接参数 (默认)
connection:
  protocol: SPI        # 默认协议
  default_params: { clock_hz: 10000000, mode: 0 }
# 2. 数据解析器
parser:
  id: bosch.bmp280     # 注册的解析器 ID
# 3. 业务配置流程 (5 步)
init_flow:
  steps:
    - { name: reset,        data: \xE0, read_size: 0, timeout: 100ms }
    - { name: read_chip_id, data: \xD0, read_size: 1, timeout: 50ms }
    - { name: read_calib,   data: \x88, read_size: 26, timeout: 100ms }
    - { name: set_config,   data: \xF4\x27, read_size: 0, timeout: 20ms }
    - { name: verify_ready, data: \xF3, read_size: 1, timeout: 50ms }
# 元数据
is_default: true
```

**易混点**:
- ✅ DeviceConfig = "型号" / "配方" / "类型定义"
- ❌ 不是"设备模板" (v2.1 命名, 易与"具体设备"混淆, 改名为"设备配置")
- ❌ 不是"具体设备" (那是边缘设备)
- ❌ 跟节点的 Channel 不绑定 (Channel 是物理, DeviceConfig 是逻辑)

---

### 2.4 边缘设备 Edge Device

**定义**: **节点 + 通道 + 设备配置** 三元组的实例化,表示"在某个节点上,通过某条通道,接入的一个具体设备"。

**特征**:
- 一个 EdgeDevice = 1 个 Node + 1 个 Channel + 1 个 DeviceConfig + 1 个 hardware_id
- 是数据采集的**实际载体** (所有 DataReport 关联到 EdgeDevice)
- 有自己的 `interval_ms` (采集频率)
- 可独立启用/禁用 (`enabled`)

**示例**:
```
边缘设备 ID: 10
├─ 节点:  esp32c6_001 (Node A)
├─ 通道:  Channel 1 (SPI2)
├─ 设备配置: DeviceConfig 5 (BMP280)
├─ hardware_id: 0 (SPI 设备的 CS 索引, 通常为 0)
├─ interval_ms: 1000
└─ enabled: true
```

**I2C 多设备拓扑示例**:
```
节点 esp32c6_001
├─ 通道 Channel 2 (I2C0)
│   ├─ EdgeDevice 10: Channel 2 + DeviceConfig 5 (BMP280) + hardware_id=0x76
│   └─ EdgeDevice 11: Channel 2 + DeviceConfig 5 (BMP280) + hardware_id=0x77
```

**易混点**:
- ✅ EdgeDevice = "实例化" (运行时)
- ❌ 不是"设备" (会跟 DeviceConfig 混淆, 必须用全名"边缘设备")
- ❌ 不是 DeviceConfig (前者是实例, 后者是类型)
- ❌ 不是 Node (Node 是物理整机, EdgeDevice 是其内部的具体设备)

---

### 2.5 数据中心 (Data Center / 中心端)

**定义**: 部署在服务端的 Go 后端,负责节点管理 / 设备配置管理 / 数据汇聚。

**特征**:
- 是 EdgeDevice / DeviceConfig / Channel 的**权威源**
- 通过 ConfigEventBus + SyncGate 推送到节点
- 接收节点的 DataReport / StatusReport
- 不直接控制节点硬件 (通过 MQTT 协议间接)

**易混点**:
- ✅ 中心端 = "云端" / "服务端" / "Server"
- ❌ 跟"节点"是 Layer 3 vs Layer 2 关系,不是"上下级"

---

### 2.6 协议 Protocol

**定义**: 节点与中心端通信的二进制帧协议,本项目使用**自研二进制帧** (非 protobuf)。

**版本**: v2.2 (兼容 v2.1 / v2.0)

**消息**:
- 上行 (ESP→SVR): Hello / StatusReport / DataReport / Pong / ConfigResult / OtaProgress / ScanReport / QueryResponse / ConfigReport
- 下行 (SVR→ESP): HelloAck / ConfigManifest / ConfigPatch / WriteCommand / Ping / OtaCommand / ScanRequest / QueryRequest / ConfigQuery

**详细**: [协议/二进制帧协议.md](../协议/二进制帧协议.md) | [总体设计 §3](../设计/总体设计.md)

---

### 2.7 配置同步 Config Sync

**定义**: 中心端把最新的 DeviceConfig / Channel 配置下发到节点的过程。

**机制** (v2.1+):
- 协议携带 `config_epoch` (全局单调递增)
- 节点发 `Hello` / `StatusReport` 时上报本地 epoch + manifest_id + nvs_has_config
- 中心端通过 `SyncGate` 决策: 需要下发则发 `ConfigManifest`
- 节点应用后回 `ConfigResult` (含 manifest_id + success/error)

**详细**: [同步机制/详细设计.md](../设计/同步机制/详细设计.md)

---

### 2.8 模板 Template (v2.2 引入, Template Pool 概念)

**定义**: 节点的通道上"如何读寄存器"的**二进制命令序列** (e.g. UART 读 8 字节的 hex 命令)。

**特征**:
- 跟 DeviceConfig 不同: Template 是节点的"低层命令" (hex 字节), DeviceConfig 是"高层型号描述" (init flow / parser)
- 多个 EdgeDevice 可共享同一 Template (e.g. 10 个 BMP280 用同一个 read 模板)
- v2.2 计划引入 **Template Pool** (全局共享) + **ConfigPatch** (增量下发)

**详细**: [同步机制/详细设计.md §5.5](../设计/同步机制/详细设计.md) | [v2.2 计划文档](#)

## 3. 术语映射表 (权威)

| 旧命名 (v2.1 及以前) | 新命名 (v2.2+) | 类型 | 备注 |
|---------------------|---------------|------|------|
| 采集器 / Collector | **节点 / Node** | 物理设备 | 整个文档统一 |
| 设备模板 / Device Template | **设备配置 / Device Config** | 型号定义 | 避免与"具体设备"混淆 |
| 设备 / Device | **边缘设备 / Edge Device** | 实例化 | 区分型号 vs 实例 |
| 通道 / Channel | **通道 / Channel** | 物理端点 | 不变 |
| 协议 / Protocol | **协议 / Protocol** | 通信规范 | 不变 |
| 服务端 / Server | **中心端 / Center** | 服务层 | 强调"在中心" |
| Edge / 边缘 | **边缘 (Layer 1 限定)** | 形容词 | 只用于"边缘设备" |
| Template | **模板 / Template** (v2.2) | 命令序列 | 新概念,低层 |

## 4. 必须禁止的命名 (反模式)

以下命名在 v2.2+ 中**禁止使用**:

| ❌ 禁止 | ✅ 替代 | 原因 |
|--------|--------|------|
| 采集器 | 节点 | 跟"采集数据"动词混淆, 不准确 |
| 设备 (单独使用) | 边缘设备 / 设备配置 (具体化) | 二义性 |
| 设备模板 | 设备配置 | 强调"配置"语义, 跟"模板"动词"套用"对应 |
| 设备配方 | 设备配置 | 词汇统一 |
| 设备类型 | 设备型号 (产品) | "类型"是抽象, "型号"是商业概念 |
| 节点ID | node_id / 节点 ID | 不要"节点标识"等冗余表述 |
| 边缘 (单独) | 边缘设备 | "边缘" 单独无意义 |
