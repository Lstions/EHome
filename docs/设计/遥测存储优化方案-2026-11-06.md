## 1. 问题：为什么 1 Hz 的数据会吃掉整块盘

### 1.1 现状实测基线

| 指标 | 实测值 |
|---|---|
| `unified_data` 行数 | **2,811,888 行/天**（device14: 2,503,918 / device15: 307,970） |
| 真实帧数（微秒精度去重） | **142,467 帧/天**（device14: 86,342；device15: 56,125） |
| 每帧解析字段数 | device14 = 29（固定）；device15 = 2–14（7 种帧类型） |
| 现状占用 | **17 GB/月**（unified 12.6 GB + device_data 4.5 GB） |
| 整盘 | 50 GB，可用 20 GB |

### 1.2 PG 实测行成本（临时表真实 payload，含索引）

| 布局 | 每行总成本 |
|---|---|
| 现状 `unified_data`（8 列 + 5 索引） | **178.7 B** |
| 瘦身逐字段（int4 device + int2 sensor + real + timestamptz，单 PK） | 108.0 B |
| 帧级行（int4 + timestamptz + int2 + bytea，PK(device,ts)） | **98.0 B** |
| 帧级行 + 原始 raw(78B) 列 | 174.3 B |
| 1 min rollup（窄表，每字段一行） | 109.1 B |
| 1 min rollup（宽行，每帧一行 232B payload） | 327.3 B |

### 1.3 放大的来源

一帧原始信息量 **约 12–17 B**（29 个量化值打包），现状写入 **29 行 × 178.7 B ≈ 5.2 KB** ⇒ **放大 300–400 倍**。其中：

1. **逐字段展开成行**：29 个值变成 29 行，每行重复 `device_id`/`unit`/`created_at`/`id`/索引键；
2. **5 条索引**：pkey(id,timestamp) + device_id + sensor_name + timestamp + edge_device_id（其中 edge_device_id 全 NULL、sensor_name 无读路径）；
3. **device_data 双写**：同帧写 2 行（raw hex 一份 + raw_hex+sensors 一份）；
4. **无变化抑制**：51.6% 的行与前一条完全相同。

### 1.4 为什么"只调低采样"不是答案

用户明确要求保持 1 Hz。且实测表明：**1 Hz 全量数据本身只有约 1.6 MB/天**（142,467 帧 × 12.1 B），根本不是问题；问题全在存储表示。

## 2. 方案总览

三层结构，逐层可选落地：

```
设备 1Hz 上报（不变）
   │
   ▼
┌──────────────────────────────────────────────┐
│ L1 写入收窄：值不变不入库（60s 心跳）           │  ← 与表示无关，先落地
└──────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────┐
│ L2 帧级增量编码：一帧一行 + 量化位打包          │  ← 核心，收益最大
└──────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────┐
│ L3 读侧：1min rollup + 解码层                  │  ← 保证图表/统计性能
└──────────────────────────────────────────────┘
```

> **L1 与 L2 不是二选一**：L1 决定"写哪些帧"，L2 决定"一帧写成多大"。两者叠加才是最终收益。

## 3. L1：值不变不入库（含 60 s 心跳）

### 3.1 规则

对每台设备、每个字段维护"最后已落库值 + 落库时间"：

- 字段值 **变化** ⇒ 该帧必须写；
- 距上次落库 **≥ 60 s** ⇒ 强制写一帧（心跳，保证时间轴连续、图表不空档）；
- 否则 ⇒ **跳过入库**（但内存缓存、告警、自动化、WS 推送照常更新）。

### 3.2 实测收益（真实一天数据）

| 设备 | 帧数 | 写入行数（帧级） | 跳过 |
|---|---:|---:|---:|
| device14 | 86,342 | 81,788 | 4,554（5.3%） |
| device15 | 56,125 | 35,407 | 20,718（36.9%） |
| **合计** | **142,467** | **117,195** | **25,272（17.7%）** |

**重建校验**：用该规则产出的写入行，重建 1 Hz 全量序列，**2,811,888 个值全部一致，0 丢失**。

> 若改成"逐字段 on-change + 60 s 心跳"（仍是逐字段表），写入 688,153 行/天（24.6%），对应 3.44 GB/月（原 schema）或 2.08 GB/月（瘦身 schema）。

### 3.3 副作用与配套（必须做，否则出错）

| 项 | 要求 |
|---|---|
| 心跳 | 60 s（可配置 `telemetry_heartbeat_seconds`） |
| 读侧语义 | avg 聚合改为"桶内最后值"或时间加权；`change` 模式本身无需改 |
| 行计数类接口 | `/metrics/summary`、`data-reports`、`data_count_today` 语义会变，需改口径或标注 |
| 缓存一致性 | **写库成功才更新缓存**；失败时不得更新，否则变化永久丢失 |
| 进程重启 | 首帧全量写一遍（量小可接受）；可用 `sensor_field_obs` 预热 |
| 多实例 | 缓存为进程内；多副本部署需共享状态（当前单容器，无此问题） |

## 4. L2：帧级增量编码（核心）

### 4.1 表设计

```sql
CREATE TABLE telemetry_frame (
    device_id   integer      NOT NULL,
    ts          timestamptz  NOT NULL,
    seq         smallint     NOT NULL DEFAULT 0,   -- 同一时间戳多帧时区分
    frame_kind  smallint     NOT NULL,             -- 0=增量 1=关键帧
    slot_id     smallint     NOT NULL,             -- 帧类型（字段集合）编号
    payload     bytea        NOT NULL,
    raw         bytea,                             -- 可选：原始总线帧（仅关键帧/错误帧）
    PRIMARY KEY (device_id, ts, seq)
) PARTITION BY RANGE (ts);
```

- **月分区**，沿用现有 `partition_mgr`（`partitionParentDDL` + `partitionParentIndexes` 模板各加一项）；
- **只保留 2 条索引**：主键 `(device_id, ts, seq)` + 可选 `(device_id, ts) WHERE frame_kind=1`（仅关键帧）；
- **不做** `sensor_name` / `edge_device_id` / `node_id` 索引（实测无读路径）。

### 4.2 payload 编码格式

```
+--------+------------------+---------------------------+
| 1B     | ceil(N/8) B      | 剩余                      |
| flags  | changed_mask     | 变化字段的量化值（按位打包）|
+--------+------------------+---------------------------+
```

- `flags`: bit0=关键帧（掩码全 1）
- `changed_mask`: 该 slot 内 N 个字段，第 i 位 = 1 表示本帧该字段变化
- 值与位宽按 slot 定义顺序**LSB-first 位打包**，无对齐填充（实测比按字节切分省 5–8%）

### 4.3 量化规格（按真实数据实测的精度制定，无额外损失）

| 字段 | 量程 | 步长 | 位宽 | 最大误差 |
|---|---|---|---|---|
| `cell_voltage_N` / `_max` / `_min` | 2.0–4.5 V | 1 mV | 12 | 0.5 mV |
| `current` | −200–200 A | 0.01 A | 16 | 5 mA |
| `total_voltage` | 0–200 V | 0.01 V | 15 | 5 mV |
| `remaining_capacity` | 0–200 Ah | 0.01 Ah | 15 | 5 mAh |
| `nominal_capacity` | 0–500 Ah | 0.1 Ah | 13 | 50 mAh |
| `temperature_N` | −40–125 ℃ | 0.01 ℃ | 15 | 5 m℃ |
| `rsoc` | 0–100 % | 1 % | 7 | 0.5 % |
| `cycle_count` / `fet_status` / `protection_status` / `fault_code` | 0–65535 | 1 | 16 | 0.5 |
| `alarm_*` / `fan*_status` | 0–1 | 1 | 1 | 0 |
| `grid_voltage` / `output_voltage` | 0–400 V | 0.1 V | 13 | 0.05 V |
| `bus_voltage` | 0–700 V | 0.1 V | 14 | 0.05 V |
| `battery_voltage` | 0–100 V | 0.1 V | 11 | 0.05 V |

### 4.4 slot 字典（帧类型）

实测帧类型（字段集合）数量：

| 设备 | 帧数 | 帧类型数 | 说明 |
|---|---:|---:|---|
| device14 | 86,342 | **1** | 恒为 29 字段 |
| device15 | 56,125 | **7** | 3 / 14 / 2 / 5 / 5 / 9 / 4 字段，按指令区分 |

`slot` 描述（字段名列表 + 量化规格版本）存 `telemetry_slot` 表，由 `command_template_id` + 解析结果签名生成，读侧 JOIN 一次或启动时全量缓存。

> ⚠ **不能假定固定槽位**：device15 的 7 种帧类型来自 7 条不同指令，硬编码 42 槽会把不同指令的值写串。

## 5. L3：读侧改造

### 5.1 新增解码层

`backend/internal/telemetry/codec`：

```go
// DecodeRange 按时间窗取帧并按 slot 顺序累积状态，产出任意字段序列。
func DecodeRange(ctx, db, deviceID uint, from, to time.Time, fields []string) ([]Point, error)
// LatestSnapshot 取最近一个关键帧 + 其后增量，得到当前全量快照。
func LatestSnapshot(ctx, db, deviceID uint) (map[string]float64, error)
```

实测读成本：

| 窗口 | 帧数 | 压缩后字节 | 解码后内存 |
|---|---:|---:|---:|
| 1 小时（device14） | 3,600 | 43 KB | 0.8 MB |
| 24 小时（device14） | 86,342 | 1.0 MB | 19 MB |
| 30 天（device14） | 2.6 M | 37 MB | 570 MB ⚠ |

⇒ **30 天以上或大范围聚合必须走 rollup**，不能靠解码。

### 5.2 1 min rollup（宽行）

```sql
CREATE TABLE telemetry_rollup_1m (
    device_id integer     NOT NULL,
    bucket    timestamptz NOT NULL,
    payload   bytea       NOT NULL,   -- 每字段 avg/min/max/last 打包
    PRIMARY KEY (device_id, bucket)
) PARTITION BY RANGE (bucket);
```

- 每设备每分钟 **1 行**（不是每字段一行）：实测宽行 327.3 B/行 × 2,880 行/天 = 0.9 MB/天
- 对比窄表（每字段一行）102,240 行/天 × 109.1 B = 10.6 MB/天 ⇒ **宽行省 12 倍**
- 由写入路径旁路聚合（内存累加，分钟切换时落库），无需额外扫描

### 5.3 各读路径的落点

| 读路径 | 改造后数据源 |
|---|---|
| `/unified-data/historical` / `-batch`（图表） | 短窗（≤6 h）解码；长窗查 rollup |
| `/edge-devices/:id/latest-data` | `LatestSnapshot`（最近关键帧 + 增量） |
| `/edge-devices/:id/data-summary` | min/max(ts) 主键索引直取 |
| `/unified-data/categories` | `sensor_field_obs`（已有投影表） |
| `/overview` 与列表富化 | 内存缓存 + `LatestSnapshot` 兜底 |
| 告警/自动化 | **不变**（走内存 sink，不查库） |
| CSV/原始导出 | 解码 + 可选 raw 列 |

### 5.4 关于 rollup 的历史约束

rollup 曾于 2026-09-15 退役（`database/retire_rollup.go` 每次启动 DROP，且有门禁测试禁止复活）——原因是**当时没有任何读路径用它**。本方案的 rollup 有明确消费者（长窗图表），**须同步修改**：

- `database/retire_rollup.go`：只退役旧的 `unified_data_rollup_1m`，不要误伤新表；
- `automigrate_retirement_e2e_test.go` / `retire_rollup_test.go`：门禁名单更新；
- 新增裁决文档一节，说明"死表不得复活"针对的是无消费者的表。

## 7. 实施路线

### 阶段 0：无损项（立即，0 风险）
1. 删 4 条死索引：`unified_data.sensor_name_idx`、`unified_data.edge_device_id_idx`、`device_data.node_id_idx`、`device_data.edge_device_id_idx`

2. 清理日志/镜像/dump（约 5 GB）
3. 保留期 90 → 60 天（不涉及采样率）

> 注意：下一个镜像启动会补建 F-10 复合索引（估算 +2–4 GB），**发版前必须先清盘**。

### 阶段 1：L1 写入收窄（1–2 天）
- `consumers_heavy.go:355-380` 增加"值不变且未到心跳 ⇒ 跳过 INSERT"
- **同时**把 `latestSink` 调用提到 INSERT 之前（现在它在 `Create` 成功的 else 分支里，跳过会冻结缓存）
- 新配置：`EHOME_TELEMETRY_WRITE_ON_CHANGE`（默认 false）、`EHOME_TELEMETRY_HEARTBEAT_SECONDS`（默认 60）
- **影子模式**：先只统计"本可跳过多少行"并打点，跑 1 天核对命中率再开
- 配套：`avg` 聚合改桶内最后值；行计数类接口改口径

### 阶段 2：L2 帧级编码（1–2 周）
1. 新增 `internal/telemetry`（codec + slot 字典），先用重放测试对齐（复用 `replay_real_driver_test.go` 夹具）
2. 建 `telemetry_frame` 表（新表，不动旧表），**双写**
3. 影子校验：双写后逐帧比对"解码结果 == 原 unified_data 值"，误差阈值 = 量化步长/2
4. 双写稳定 1 周后，读路径切换（按 §5.3 逐项）
5. 旧表停写，按保留期自然淘汰分区

### 阶段 3：L3 rollup（与阶段 2 并行/随后）
- 写入侧旁路聚合，宽行落库
- 长窗图表切 rollup，短窗仍解码

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 量化有损 | 电芯电压 1 mV、温度 0.01 ℃、功率 1 W | 已按真实最小步长设计（实测 0 超差）；raw 列可回放；`sensor_field_meta` 可调 |
| device15 多帧类型 | 硬编码槽位会写串 | slot 字典 + `command_template_id` 判别，实测 7 种类型 |
| 秒内多帧 | device15 1.85 帧/秒 | 主键含 `seq smallint`；微秒时间戳不受影响 |
| 增量链断裂 | 丢一帧则后续值错位 | 60 s 关键帧限制最坏窗口；解码遇 `seq` 缺口或版本不符 → 跳到下一个关键帧并打点 |
| 读路径全改 | 回归面大 | 双写期逐项对照；`s3_read_shape_probe_test.go` 扩展为双源等价性测试 |

| PG schema 不在 AutoMigrate | 生产与测试 schema 漂移 | 同改 `partitionParentDDL` / `partitionCopyColumns` / 索引模板 / GORM models 四处 |
| 迁移期空间峰值 | 双写期间翻倍 | 阶段 0 先腾出 ≥6 GB；逐月迁移旧分区 |

## 9. 验收标准

1. **无损性**：任意设备任意 24 h 窗口，解码重建的 1 Hz 序列与旧表逐值对比，误差 ≤ 量化步长/2，缺失值 0
2. **容量**：90 天数据 ≤ 3 GB（当前 55.9 GB）
3. **写入**：行数 ≤ 150k/天；INSERT 行/s ≤ 2
4. **读延迟**：24 h 单字段图表 ≤ 300 ms（现 5.3 s）；30 天 rollup 图表 ≤ 200 ms
5. **回归**：图表/导出/data-summary/latest/categories/告警/自动化全部用例通过
6. **可回滚**：双写期内可切回旧表；停写后仍能从 raw 列回放
