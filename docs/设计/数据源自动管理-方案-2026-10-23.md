## 一、先说一个前置事实（它决定了方案形态）

遍历全部调用链后确认：**`data_sources` 目前没有任何下游消费者**。

| 谁读 `data_sources` | 用途 |
|---|---|
| `internal/api/handler_data_source.go` | 只服务自己的 CRUD 接口 |
| `internal/datasource/service.go` | 只在自身内部读写 |
| **其他模块** | **零引用** |

```
grep 'DataSource' internal/automation/ internal/alert/
  → 只有 2 行注释，零代码引用
```

规则用 `automation_rules.trigger_edge_device_id` 或 `source_group_id`；告警用 `alert_rules.target_id` 或 `source_group_id`；采集用 `edge_devices` + `channels`。

**结论**：即使把 `data_sources` 自动填满，对「规则能不能用上数据」也零影响。因此本方案分两层：先把 `data_sources` 变成**无害的自动投影**（消除困惑），再让真正的自动化落在**来源组 + 规则绑定**上。

### 生产拓扑实测（决定主备/复合是否有真实场景）

| 检查 | 结果 |
|---|---|
| 同一逻辑设备下的边缘设备数 | **全部为 1**（10 个逻辑设备各挂 1 台） |
| 同一 `sensor_name` 出现在几台设备上 | **0 条** |
| 同类设备多台 | `jiabaida_bms` ×2、`techfine_inverter` ×2，但**分属不同逻辑设备** |

⇒ 当前**不存在**主备场景（需「同逻辑设备 + 同类别 + 多设备」），也**不存在**复合场景（需「跨设备同名字段」）。自动派生出来的会是「10 条单成员、永不切换」的记录 —— 那是台账，不是功能。

## 二、设计原则（按你的要求）

### 低耦合：三层，单向依赖

```
观测源（唯一事实来源，已有）
  unified_data（采集） edge_devices（设备）
  logical_devices（归属） sensor_field_obs（字段）
        │ 只读，不反向写
        ▼
派生层 internal/provision（新增：纯函数 + 单次 IO）
  Derive(input) → []DesiredSource
  无 GORM 模型、无业务表引用、可单测零 DB
        │ 声明式期望态
        ▼
收敛器 Reconciler（已有范式可复用）
  期望态 vs 实际态 → upsert / disable
  幂等；失败保留重试；有指标与健康行
```

**这不是我发明的新范式**，本仓已有两处同构实现，我沿用它们：

| 既有 | 派生层 | 收敛方式 |
|---|---|---|
| 字段解析层 | `internal/sensorfield`（纯函数，零 DB） | `Registry.Observe` 内存计数 + `Flush` 每 60s 批量 UPSERT |
| 逻辑设备归属 | `internal/datalifecycle`（纯决策） | `AllocateIdentity` 幂等分配 + ON CONFLICT |

新增的 `internal/provision` 与它们**并列同构**，不引入第四种架构。

### 灵活性：三段可独立开关

| 段 | 开关 | 默认 | 影响面 |
|---|---|---|---|
| S1 `data_sources` 自动投影 | `EHOME_PROVISION_SOURCES` | **on** | 只写台账，无消费方 ⇒ 风险≈0 |
| S2 来源组自动派生 | `EHOME_PROVISION_GROUPS` | **off** | 会创建来源组对象，需产品确认 |
| S3 规则绑定自动推荐 | `EHOME_PROVISION_RULE_HINT` | **off** | 只影响 UI 提示，不改数据 |

**关键**：S2 默认关。三段独立，可分批上线、可单独回滚。

### 可长期维护：三条纪律

1. **派生层零 DB**：`internal/provision` 只接受纯数据、返回纯数据，不 import gorm。可单测覆盖全部判定（与 `sensorfield` 同纪律，现有门禁 SG-18 同款）。
2. **不删除，只 disable**：设备下线/字段消失时把投影行置 `disabled` 保留血缘，绝不 DELETE。
3. **人工配置优先**：投影行带 `managed_by` 列（`auto` / `manual`），收敛器**只碰 `auto` 行**，`manual` 行永不覆盖 —— 这是「自动但可干预」的关键。

### 自动管理：触发时机（全部幂等）

| 时机 | 动作 | 挂载点 |
|---|---|---|
| 启动后一次 | 全量对账 | `main.go` 现有启动序列 |
| 每 60s | 增量对账（复用字段解析层 flush 节奏） | `field_resolver.go` 已有 ticker |
| 采集到新字段 | 只标脏，不即时写库 | 现有 `registry.Observe` 包装点 |
| 设备/逻辑设备归属变更 | 标脏 | `datalifecycle` 已是唯一入口 |

**为什么不在热路径写库**：生产实测每 10 分钟约 19000 行，在 sink 回调写会反压 ingest —— 与「热路径零 DB」红线冲突。

## 三、S1 详细设计：`data_sources` 自动投影（建议先做）

### 数据模型改动

```go
// models.DataSource 新增 2 列
ManagedBy string `gorm:"size:16;not null;default:'manual';index" json:"managed_by"`
//   auto   = 派生器维护（收敛器可改）
//   manual = 人工创建（收敛器永不覆盖，只提示冲突）

DerivedAt *time.Time `json:"derived_at"`   // 最近一次派生命中的时间
```

`data_sources` 生产为 0 行 ⇒ 加列零风险。

### 派生规则（纯函数，`internal/provision/derive.go`）

```go
// DesiredSource 是派生器输出的期望态（纯数据，无 GORM）。
type DesiredSource struct {
    LogicalDeviceID uint
    EdgeDeviceID    uint
    Category        string   // = unified_data.sensor_name
    Name            string   // 自动生成可读名，如「BMS · rsoc」
    DesiredStatus   string   // active（同组唯一） / standby
}

// Derive 从观测事实推导期望态。纯函数：无 DB、无时钟、无随机。
func Derive(in DeriveInput) []DesiredSource
```

`DeriveInput` 由收敛器一次性查库填充：已绑逻辑设备的边缘设备（`edge_devices.logical_device_id NOT NULL`）+ 各设备实际观测到的字段（**用 `sensor_field_obs` 而非 `unified_data`** —— 后者 3000 万行）。

判定逻辑：
```
对每个 (logical_device_id, category)：
  候选 = 该逻辑设备下、观测过该 category 的边缘设备
  按 (edge.enabled DESC, edge.status=='active' DESC, edge.id ASC) 排序
  第一条 → DesiredStatus=active，其余 → standby
```

**注意**：这里**故意不做**「自动主备」的语义承诺 —— 只是排序标 active。真正的主备切换是 `source_groups` 的职责，`data_sources` 只记「谁是当前来源」。

### 收敛器（`internal/datasource/derive.go`，复用现有 Service）

```go
// ReconcileDerived 把期望态收敛到实际态。幂等：可重复调用任意次。
// 只处理 managed_by='auto' 的行；manual 行跳过并计数供 UI 提示。
func (s *Service) ReconcileDerived(ctx context.Context, desired []provision.DesiredSource) (ReconcileResult, error)
```

| 情况 | 动作 |
|---|---|
| 期望有、实际无 | INSERT（`managed_by='auto'`） |
| 期望有、实际有且 `auto` | UPDATE `derived_at`（状态变了才改 status） |
| 期望无、实际有且 `auto` | UPDATE `status='disabled'`（**不删**） |
| 期望有、实际有且 `manual` | **跳过**，返回计数让 UI 提示「人工配置与自动派生重叠」 |

### 前端改动

1. 页面标题下加说明：「本页由设备与采集数据**自动生成**，无需手工维护。需要主备切换请到「来源组」。」
2. 列表加「来源」列：`自动` / `人工` 标签（读 `managed_by`）。
3. 「新增数据源」按钮保留但降级为次要按钮（运维高级操作）。
4. 空状态文案改为：「暂无数据 —— 设备上报数据后会自动出现」。

### 工作量与风险

| 项 | 估算 |
|---|---|
| `internal/provision`（派生纯函数 + 测试） | 0.5 人日 |
| `datasource.ReconcileDerived` + 测试 | 0.5 人日 |
| 模型加 2 列 + 迁移 | 0.2 人日 |
| `main.go` 接线（启动 + ticker） | 0.2 人日 |
| 前端说明/来源列/空状态 | 0.5 人日 |
| 门禁（幂等性 + 不碰 manual 的反向断言） | 0.3 人日 |
| **小计** | **≈ 2.2 人日** |

**风险：低**。`data_sources` 无下游消费者，派生错了只影响一个页面显示，不影响采集/规则/告警。可随时用 `EHOME_PROVISION_SOURCES=off` 关闭。

## 四、S2 设计：来源组自动派生（**建议延后 + 先定产品语义**）

来源组是规则**真正消费**的抽象，自动化价值最高。但有个语义问题必须先定。

### 必须由你决定的问题

**什么时候该自动建来源组？**

| 候选策略 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| A. 检测到多源就建（静默） | 同类别 ≥2 台设备 ⇒ 建主备组 | 全自动 | 用户不知道组从哪来；组名自动生成可能不合意；建了没人用 |
| B. 检测到多源**提示** | 页面显示「检测到 2 个温度来源，可创建来源组」+ 一键创建 | 用户知情；可自定义 | 仍需一次点击 |
| C. 建了但保持 disabled | 自动建 + `enabled=false`，用户启用才生效 | 全自动且不生效 | 一堆 disabled 组造成困惑 |

**我推荐 B**。理由：来源组一旦 `enabled` 就进规则求值链路（`PublishAll` 进快照），静默创建等于让系统在用户不知情时改变了「数据从哪来」的语义 —— 这在自动化里是危险的。「自动**发现** + 一键**确认**」既省了人工查库填 ID，又保留知情权。

### 如果选 B，具体设计

```go
// SuggestGroups 只读：返回「值得建组」的建议，不写库。
func (g *GroupService) SuggestGroups(ctx) ([]GroupSuggestion, error)

type GroupSuggestion struct {
    Kind       string   // primary_backup / composite
    Category   string
    Members    []uint   // 建议的成员设备
    Reason     string   // 为什么建议（给用户看）
    Confidence string   // high / medium
}
```

前端：来源组页面顶部显示建议卡片 → 点击「采用」调用现有 `POST /source-groups`（预填参数）。**S2 不新增写路径**，只是把手工艺流程的填参自动化 —— 耦合度最低。

## 五、S3 设计：规则绑定自动推荐（**最后做**）

现状：用户建规则要填 `trigger_edge_device_id`（裸 ID）或选来源组。目标：用户只说「温度超 60 度告警」，系统自动找到温度数据来源。

```go
// SuggestRuleSource 给定类别，返回建议的来源绑定。只读。
func SuggestRuleSource(ctx, category string) (*SourceSuggestion, error)
//   有唯一来源组 ⇒ 推荐绑组
//   有唯一设备   ⇒ 推荐绑设备
//   多来源无组   ⇒ 推荐「先建来源组」并附建议
```

**为什么放最后**：依赖 S1/S2 的数据基础，且涉及规则编辑器交互改造。先让 S1/S2 跑一段观察建议准确率，再做 S3 更稳。

## 七、我不建议做的事（也请确认）

| 不做 | 理由 |
|---|---|
| 给 `data_sources` 加「自动主备切换」 | 与 `source_groups` 职责重叠 —— 两套主备状态机会漂移。`source_groups` 是超集且已被规则消费，**应当只保留一套** |
| 删掉 `data_sources` 表 | 生产已有该表结构（0 行），删表属破坏性变更；且它有 audit 血缘价值。降级为投影即可 |
| 在采集热路径写库 | 生产每 10 分钟 1.9 万行，会反压 ingest。必须走 60s 批量对账 |
| 静默自动建 `enabled` 来源组 | 会改变「数据从哪来」的语义而不告知用户 |

## 八、请审核的决策点

1. **P1 是否直接开工？**（`data_sources` 自动投影 + 只读化，≈2.2 人日，风险低）
2. **S2 选 A / B / C？** 我推荐 **B（自动发现 + 一键确认）**。
3. **`data_sources` 与 `source_groups` 是否合并为一条路径？** 我倾向**保留两张表、明确分工**：`data_sources` = 自动投影的台账（只读）；`source_groups` = 唯一的主备/复合来源抽象（规则消费它）。若你希望彻底收敛成一张表，那是较大重构，需单独评估。
4. **人工配置还要不要保留？** 我建议保留但降级（`managed_by='manual'` 优先，收敛器不覆盖）。
