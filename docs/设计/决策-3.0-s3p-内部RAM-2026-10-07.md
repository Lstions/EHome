# 决策：3.0 链路的 8 KB 任务栈 + 缓冲，在 s3p 上应该放在哪里

- 日期：2026-10-07
- 触发：真机 §139.4 —— s3p 上 ConfigManifest 被内存门禁**永久拒绝**
- 相关任务：task-34
- 状态：**已决策并实施**（真机复验见 §7）

---

## 1. 现象与精确算术

真机 s3p（30EDA0A9A808）每次配置下发：
```
W CFG_TX: [memgate] phase=A step=preflight need=4096 largest=15872 free=22967 floor=16384
E CALLBACK: Rejecting ConfigManifest before suspend: memory gate
I CFG_H: Sending ConfigResult: v2-3c3b6a56, success=0
```
判据（mem_guard.c:83-88）：`largest >= max(need, floor)`，此处 `required = max(4096, 16384) = 16384`，
而 `largest = 15872` ⇒ **恒拒**（不是偶发）。

Lead 的同源 A/B（同一份源码，只差 `EHOME_DEVICE_LINK_ENABLED`）：

| | internal free | internal largest |
|---|---|---|
| link=n | 49155 | **23552** |
| link=y | 22967 | **15872** |
| 差 | **-26188** | **-7680** |

⇒ **启用 3.0 不是「多花 7.7 KB」，而是「多花 26 KB 内部 RAM，其中只有 7.7 KB 是连续的」。**
s3p 启用前的连续块余量只有 7168 B，缺口 **512 B**。

**我们自己的代码占了多少**：

| 项 | 字节 | 说明 |
|---|---|---|
| dev_link 任务栈 | 8192 | `DEVLINK_TASK_STACK` |
| 读缓冲 rx_buf | 2048 | `CONFIG_EHOME_DEVICE_LINK_RX_BUF` |
| **定界器缓冲** | **4112** | `max_payload(4096) + 12 + 4`，`wire_delim_create` **内部 malloc** |
| 合计 | **14352** | 远超那 7168 B 余量；其中 **6160 B 是纯数据缓冲** ⇒ 可搬走 |

⚠ 另有一大项**不是我们的代码**：`CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN=16384`（+ OUT 4096），
且 `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC` 未开 ⇒ mbedTLS 记录缓冲在**内部 RAM**。
这是 26 KB 里的主要部分。

---

## 2. 判据的真相：floor 是**按 free 论证**的，却按 **largest** 执行

设计文档给 s3p 定 16 KiB floor 的依据是：
> 「实测 WiFi+TLS 后余 **197.0 KiB**，远高于 s3p floor 16 KiB」

那是 **free**。而门禁执行的是 **largest**（mem_guard.c 注释：「判决依据是 largest（连续块），不是 free」）。
**同一句话里的 197 KiB 与 16 KiB 不是一个量**：free 197 KiB 时 largest 完全可能只有 15 KB。
⇒ 这个 floor 从写下那天起就**没有被 largest 口径验证过**，直到 3.0 把 largest 压到 15872 才暴露。

这也是 §139.4 里「2.x largest=8257536 与 3.0 largest=15872 差 8 MB」那个对比**作废**的原因：
两者口径不同（前者含 PSRAM）。**只有 INTERNAL|8BIT 的数字可比较。**

## 3. 候选评估

### A 缩小任务栈 —— **本轮不做（推迟到有实测之后）**

**我一度改成了 4096，随后撤回**：因为我没有真机实测，只是把「大约 1400 B」写进了注释 ——
那正是本卡明令禁止的「估一个数就改」。**记录在此以免后人重蹈**：
凡「收窄栈」的改动，必须有 `uxTaskGetStackHighWaterMark` 的真机读数（OTA 先例：实测 3124 B 才 8K→4K）。

**为什么不需要它**（算术，见 §1）：只把定界器缓冲（4112）+ 读缓冲（2048）搬走，
内部连续块预期 `15872 + 6160 = 22032`，已越过 floor 16384（余量 5648 B）。
⇒ **本卡的缺陷靠候选 B 独立修好**，不依赖任何栈改动。

**为将来的测量做的准备（已落盘）**：把 `dev_link`（以及 `usb_rx`）加进 main.c 的
`uxTaskGetStackHighWaterMark` 采样名单 —— 纯观测、无行为风险。
该名单此前**漏了 dev_link**：它是 3.0 引入的新任务，水位既没被记录也没进 MemReport，
于是「3.0 占了多少栈」在真机上**无法回答**。漏项本身是一类静默缺陷：
采样在跑、看着很全，只是恰好漏掉了要观察的对象。
（`uart0_dl` 有意不加：仅 USB 下载模式创建，正常启动期不存在；已在代码里写明理由。）

### B 定界器 + 读缓冲放 PSRAM —— **采纳（主力）**

省 **4112 + 2048 = 6160 B**，且**不动任何行为**（纯放置）。

**cache 关闭期安全性论证**（本候选唯一真正的风险，逐条回答）：
1. 这两块缓冲**不参与 DMA**：字节由 CPU 从 TLS 读出后，经 `link_rx_adapt_read` →
   `wire_delim_feed` 逐块喂入。没有 DMA 描述符指向它们。
2. `mem_guard.c:34-36` 的「flash 写期间 cache 关闭、访问 PSRAM 会崩」限制，
   针对的是**被 DMA/ISR 访问**的缓冲（任务栈、DMA 环）。
3. **先例（决定性）**：接收方向**同一形态**的缓冲**早就在 PSRAM 里** ——
   `config_mgr.c:91` 的 `collector_mem_alloc_pref_psram(CONFIG_MGR_MANIFEST_BYTES)`
   分配的是「后端下发的配置字节」槽。定界器缓冲与它是**同一类东西**（收到的网络字节），
   自 2.x 起在 PSRAM 上跑过实机，无 cache 相关事故记录。
4. **OTA 期间**：`handler_data_process_ota` 经 msg_handler 分发**在 devlink 任务内**执行。
   届时该任务会**写 flash**（esp_ota_write），期间 cache 关闭 ——
   但那时它**不读 socket**，不会碰这两块缓冲。
5. **不静默降级**：分配失败就**不启动链路**并报错（而非悄悄落回内部）。
   降级会让「以为省下了内部 RAM、其实没有」再次发生，而那正是本卡要修的形态。

### C 任务栈放 PSRAM —— **否掉**
1. s3p 上 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=n`（实测，**不是**开着的；
   Lead 任务书说「已开」，实测为未开，**此处更正**）；
2. 即使打开也**不安全**：devlink 任务会执行 OTA，而 `esp_ota_write` 期间
   flash cache 关闭、PSRAM 不可访问 ⇒ 栈在 PSRAM 上会在 OTA 中崩。
   `ota.c` 的注释对**静态缓冲**写过同样的理由（must stay internal RAM）。
3. ⇒ 栈**必须内部**。「链路不该常驻 8 KB 内部栈」的正确处置不是搬走，
   而是**按实测缩小**（候选 A）。

### D 让 TLS 缓冲动态化（MBEDTLS_DYNAMIC_BUFFER）—— **本轮不采纳，也不否掉其价值**
收益可能最大（16 KB IN + 4 KB OUT 是 26 KB 的主要部分）。不采纳的理由：
1. **不是本卡引入的缺陷**：floor 是按 free 论证、按 largest 执行（§2）；
   先修我们**自己引入**的 14352 B 才是对的顺序；
2. 有**明确代价**：IDF help 明说它改变分配时机（need 时才分配、用完即释放）
   ⇒ 握手/收包路径的**分配点漂移**，而这正是本仓 OTA/配置事务最怕的形态；
3. 它需要**独立**的决策 + 真机验证（含「分配失败会不会变成新的拒绝点」）。
⇒ **记为重开条件（§5.1）**，不静默忽略。

### E 调低 s3p 的 floor —— **否掉（本轮）**
调 16 KiB → 15 KiB 只是让门禁闭嘴，**不解决「内部 RAM 变紧」**。
但 §2 已证明 **floor 的论证口径是错的**（free 论证 / largest 执行）——
那是一个**独立的、真实的**问题，应单独开卡按 largest 口径重新论证三型号 floor，
而**不是**在「为了让配置通过」的语境下顺手改。本轮**不动 floor**，也不动 s3/c6 的任何行为。

## 4. 决策

> 采纳 **B（唯一改动）**：
> 1. 把 3.0 链路的**定界器缓冲（4112 B）与读缓冲（2048 B）放到 PSRAM**（有 PSRAM 时）；
>    无 PSRAM 的 s3/c6 自动落回内部，**与改动前逐字节相同**；
> 2. **不动任务栈**（候选 A 推迟：无实测不做，见 §3A）；
> 3. **不动 floor**，也不动 s3/c6 的放置行为（P8：型号差异只影响放置/大小）。

回收的内部连续块：**6160 B** ⇒ 预期 largest `15872 → 22032`，越过 floor 16384（余量 5648 B）。
⇒ **单一改动即可修好本卡缺陷**，不叠加任何未经测量的收窄。

**判据归一化（P8 不变性）**：三型号走**同一条**判据 `devlink_buf_place(psram_available)`，
差别只在「PSRAM 可用与否」这一个维度。s3/c6 上 `collector_mem` 的桩返回 NULL，
路径与改动前一致 ⇒ **行为不变，只有放置不同**（由宿主用例钉住）。

## 5. 什么条件下该重开这个决定
1. **MBEDTLS_DYNAMIC_BUFFER 被单独论证并采纳**（候选 D）—— 那会改变整个内部 RAM 预算图；
2. 若真机复验后 largest 仍**不足 floor** ⇒ 说明 14352 B 不是主因，必须查那 26 KB 里其余部分
   （每任务栈、lwIP、WiFi 缓冲），而不是继续压缩我们自己的项；
3. 若 s3p 出现「OTA 期间链路异常」⇒ 说明 §3B 第 4 条被推翻，**必须立即改回内部**并重新论证；
4. 若确认 OTA 不经 devlink 任务且允许外部栈，候选 C 可重新评估；
5. 若 floor 按 largest 口径重新论证（独立开卡），本决策的数值需与之对齐。

## 9. ⚠ 真机复验结论：**本决策失败**（2026-10-07，Lead 实测）

### 9.1 实测结果
```
DEV_LINK: 链路缓冲放置=PSRAM（rx=2048 B、delim=4112 B；internal largest 现在=31744）
[memgate] phase=A step=preflight need=4096 largest=15872 free=25575 floor=16384
E CALLBACK: Rejecting ConfigManifest transaction: result=1
```

| 量 | 修复前 | 修复后 |
|---|---|---|
| internal **largest** | 15872 | **15872（一点没变）** |
| internal free | 22967 | 25575（+2608）|
| 门禁 | 拒绝 | **仍拒绝** |

### 9.2 我的算术错在哪（**必须记住**）
我写「回收 6160 B ⇒ 预期 largest 15872 → 22032」。
**那前提是「free 里多出来的字节会变成连续块」—— 真机上不成立。**

`largest` 是**单个最大连续块**，不是「空闲之和」。搬到 PSRAM 的 6160 B
散落在堆里 ⇒ free 涨、largest 不动。

⚠ 这正是我在本文件 §2 指出的那个错误的**镜像版**：
§2 是「floor 用 free 论证、却按 largest 执行」；
§9 是我「用 free 的账回答 largest 的问题」。**同一个病，换了个方向。**
⇒ 判据：**任何关于 largest 的结论，都必须来自 largest 的实测，不能从 free 推。**

### 9.3 真正吃掉那个连续块的是什么（Lead 的算术 + 设备自报）
```
启动时（链路刚建好）largest = 31744
约 1 秒后配置事务时 largest = 15872     ⇒ 运行期吃掉 15872 B 连续内部 RAM
link=n 事务时 largest = 23552
link=y 事务时 largest = 15872             ⇒ 差 7680 B
dev_link 任务栈                          =  8192 B
```
⇒ 7680 ≈ 8192 − 512（堆头/对齐）⇒ 嫌疑指向 **8 KB 任务栈**。

⚠ 但**本卡不下这个结论**：上表只能说明「有一个约 8 KB 的连续分配」，
而同一时点还有一个更大的候选 —— **mbedTLS 的记录缓冲**
（`SSL_IN_CONTENT_LEN=16384` + `OUT=4096`，且 `MBEDTLS_EXTERNAL_MEM_ALLOC` 未开）
—— 它是 3.0 建 TLS 才出现的，**不是我们的代码**。
两者都还没被**直接**测量区分开（见 §10 的判据）。

### 9.4 因此：候选 A（缩栈）与「静态栈」都必须**先测再改**
- 我一度用 `xTaskCreateStatic`（栈进 .bss）的算术算出「可回收 7680」——
  **那个数字同样依赖未验证的前提**（静态化是否真能让 largest 回升），
  且会让 DIRAM +8192、逼近 mem_budget 阈值（余量仅 2420 B）。**本轮不做。**
- 唯一允许的下一步是**测量**（§10）。

## 11. 栈实测 + floor 的证据链（2026-10-07 追加）

### 11.1 栈峰值实测（Lead 真机，两次一致）
`[stack] dev_link high_water=4024 bytes free` ⇒ 栈 8192、**峰值 4168 B**。

⚠ **我此前编造的「~1400 B」差了 3 倍**。若据此改成 4096：`4096 − 4168 = −72`
⇒ **真机缺 72 字节** ⇒ 一个执行 OTA 的任务随机踩踏。
**这是「先测再改」的具体代价：编造的数字会直接变成现场崩溃。**

⇒ **本轮不动栈**（另：缩到 6144 只省 2048，且 §9.2 已证释放空间未必并入连续块，
即使并入也只到约 17408，离 floor 仅 1024；而它执行的是远程救命通道 OTA，风险不对称）。

### 11.2 ⭐ floor 的值**没有操作依据**（全仓声明值）

| 位置 | 声明值 |
|---|---|
| `preflight_need`（app_callbacks.c:324）| **4096** |
| `step_need_apply_buses`（事务最大步）| **4096** |
| `CONFIG_TX_UART_INSTALL_LARGEST_NEED` | 3584 |
| `arena_need` | 1152 |
| OTA 任务栈（ota.c:79）| 4096（**静态 .bss**，不占堆连续块）|

⇒ **全仓没有一处声明需要 16384 连续块；最大声明是 4096**，而门禁要求
`largest >= max(4096, 16384) = 16384` ⇒ 是声明值的 **4 倍**。

**floor 的值从哪来 —— 两处口径不同：**
- 方案 §4.7：「WiFi+TLS 实测后余 **197.0 KiB**，远高于 s3p floor 16 KiB」⇒ **free** 口径；
- `mem_guard.c:42`：「判决依据是 largest（连续块），不是 free」⇒ **largest** 口径。

⇒ **P4/P5 级不一致**：值来自 free 分析、执行在 largest 上。
s3p 实测 free=27355 而 largest=**15360**，两者差得极远。

### 11.3 后果：这是一个**永远无法满足**的门禁
| 场景 | largest | vs floor 16384 |
|---|---|---|
| link=n 事务时点 | 23552 | ✅ |
| link=y 事务时点 | 15872 | ❌ 低 512 |
| **link=y 稳态 61s/121s** | **15360** | ❌ **低 1024（两次一致）** |

⇒ 配置下发失败**不是启动瞬态，是稳态必然** ⇒ 门禁**恒定拒绝**。
这与 **D-25**（判据恒真 ⇒ 永不红）是**同族、方向相反**：那个永远通过，这个**永远不通过**。
本仓对前者有元门禁（`check_mem_budget_thresholds.py` 拒绝恒真阈值），
但**没有机制能发现「运行期 floor 不可达」** —— 这是可开卡的缺口。

### 11.4 ⚠ 但**不能**就此断定「floor 定错了」（两种解释都还活着）
| 解释 | 成立所需的证据 | 对应修法 |
|---|---|---|
| **E1 floor 值错** | link=n **稳态** largest 也 < 16384 ⇒ 从来不可达 | 重定 floor（逐型号）|
| **E2 3.0 撑破预算** | link=n 稳态 ≫ 16384（如 ~23 KB）⇒ 原本可达 | 削减 3.0 的内部连续占用 |

现有数据**不能区分**：link=n 只测了**事务时点**（23552），**稳态从未测**。
⇒ **决定性测量**：刷 link=n + MEM_DIAG 读稳态 largest。两者指向**完全不同**的修法。

### 11.5 若开卡，第一个问题不是「该定多少」
而是 **这个 floor 在守哪个量**：
1. 守 **free**（空闲总量）：16 KiB 可达（实测 27355 ✅）⇒ 应改按 free 判；
2. 守 **largest**（连续块）：值须来自「最需要连续块的操作 + 实测余量」，
   而最大声明需求是 4096 ⇒ 现值是它的 4 倍且不可达；
3. 守「**给 WiFi/lwIP 突发留内部余量**」（意图**未被任何文档写明**）：
   须先写明意图（s3p 有 `SPIRAM_MALLOC_RESERVE_INTERNAL=32768` 这类预留），再按实测定值。

⇒ 三型号取值（s3p 16 K / s3 8 K / c6 12 K）目前**都只有 free 口径来源**，
应**逐型号**按同一口径重新论证，而非单独调低 s3p。

```
I (61373) EHOME: [stack] ---- heap free=49911 largest=23552 (internal) ----
```
该 capture 的**身份核对**：全文**没有**「3.0 链路任务启动 / DEV_LINK / SESS_TX: 3.0 会话已注册」，
且 **0 条 memgate 拒绝** ⇒ **确为 link=n**。

| 场景（均为稳态 61 s） | largest | vs floor 16384 |
|---|---|---|
| **link=n**（本 capture）| **23552** | ✅ **余 7168** |
| link=y（Lead 实测）| 15360 | ❌ 低 1024 |
| 差 | **8192** | |

**差恰好 = 8192 B**，而 3.0 新增的内部 8192 分配**只有一个**：
`dev_link` 任务栈（`xTaskCreate` 走堆；rx_buf/delim 在 task-34 后已进 PSRAM）。
「恰好相等」还说明**那个栈就是从 largest 里切走的**（不是从别的块里挤出来的）。

⇒ **结论翻转：floor 不是错的** —— 3.0 之前它可达且有 7168 B 余量；
是 **3.0 的 8 KB 任务栈**把 largest 压到 15360、跌破了 floor。
（此项亦**修正 §11.4** 原先对 E1 的倾向，以及 Lead §147「缩栈解决不了」的判断。）

### 11.7 ⚠ 本节算术**已被证伪**（缩栈不动 largest）—— 见 §12

> 保留：其中「余量倍数」的论证仍成立（用于说明 6144 的**安全余量**够），
> 但「缩栈能把 largest 抬回 17408」**不成立**。
| 目标栈 | 相对实测峰值 4168 的余量 | largest 预期 | ≥ floor ? |
|---|---|---|---|
| 5120 | 1.23x | 18432 | ✅ |
| **6144** | **1.47x** | **17408** | ✅ |

⚠ Lead §147 算出的「只到 17408（余量仅 1024）」——**17408 ≥ 16384，是能过的**；
真正的保留意见是「**离 floor 只剩 1024，偏薄**」，而不是「过不了」。

**本仓既有先例（都比我提议的更紧）**：
- `status_task` 5120 / 实测 3996 = **1.28x**（main.c:139）；
- `hello_super` 3072 / 实测 2172 = **1.41x**（hello_handshake.c:175）。
⇒ 6144（**1.47x**）比现有已接受的实践**更保守**。

### 11.8 因此：**不要改 floor**，改的是栈（但先补一个测量）
- 改 floor 是**策略变更**（影响三型号、所有重操作），而缺陷根因是一个具体分配；
- 改栈是**修根因**，且不动任何判据；
- ⚠ 但实测峰值**未覆盖 OTA / 大下行帧**（OTA 状态机在该任务上下文里跑）。
⇒ **开卡顺序**：① 测 OTA 期间峰值 → ② 按 1.4x 以上定栈 → ③ 复验 largest ≥ floor。

### 11.9 仍**独立成立**的一项（另一张卡）
§11.2 的 free/largest 口径不一致**依然是真的**：floor 的值来自 free 口径分析、
却被按 largest 执行。本例中它没造成故障（floor 原本可达），
但它是**同类缺陷的温床**（若哪天 largest 常态低于 floor，就会重现本次现象）。
⇒ 仍建议按最大口径重新论证三型号 floor，但**它不该混进本卡**。

## 12. ⚠ §11.6/§11.7 的归因已被真机证伪（缩栈实测，2026-10-07）

### 12.1 实测
| 栈 | largest（事务时）| largest（稳态）| dev_link high_water |
|---|---|---|---|
| 8192 | 15872 | 15360 | 4024 |
| **6144** | **15872** | **15360** | **2056** |

⇒ 缩 2048 B：**largest 一字不变**，门禁照旧拒绝（ConfigResult success=0）。
（两侧 sdkconfig 经 tools/sdkconfig_diff.py 验证差异 0 项，数字可比。）

### 12.2 我的推理错在哪（同类错误第三次发作）
我据「link=n 23552 vs link=y 15360，差**恰好 8192**」断言「就是那个 8 KB 栈」。
**8192 是「第一与第二连续块之差」，不是任何分配的大小。**
⇒ 「数值恰好相等」不是因果证据；要证明某分配是元凶，必须**改它、再看 largest 动不动**。

| # | 错误 | 正确判据 |
|---|---|---|
| §2 | floor 用 free 论证、却按 largest 执行 | 口径必须一致 |
| §9.2 | 用 free 的账回答 largest 的问题 | largest 只能实测 |
| §11.6 | 「恰好 8192」⇒ 因果 | **改它再看**（本轮做了，被推翻）|

### 12.3 修正后的线索（**假设，待测**）
用 [bootheap] 的链路建立前基线（两边同为 31744）重算：

- link=n 稳态 23552 ⇒ 31744 − 23552 = 8192
- link=y 稳态 15360 ⇒ 31744 − 15360 = **16384**

**31744 − 16384 = 15360**（精确），而 16384 正是 CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN。
free 侧自洽：link=y 比 link=n 少 20920 B ≈ IN 16384 + OUT 4096 + SSL 上下文/套接字约 440。

⇒ **假设**：mbedTLS 的 IN 记录缓冲从那个 31744 块里切走，剩余正好 15360。
⚠ 这仍是「数值吻合」，但这次对应一个已知大小的缓冲，且 free 侧也对得上；
**必须由探针确认**，不得据此直接改配置。

### 12.4 已交付的定位手段：[linkheap] 逐步探针（仅 MEM_DIAG）
在 main/device_link_wiring.c 的链路建立各步前后各打一行（口径与门禁一致：INTERNAL | 8BIT）：

    init:enter -> certs:done -> tls_cfg:new -> session:create -> task:create
    -> task:first_poll -> 每次 session 状态跃迁（DOWN -> WAIT_HANDSHAKE -> READY）

⇒ **一次刷机**即可看出哪一步把 largest 从 31744 砍到 15360。
（默认关闭：EHOME_MEM_DIAG=OFF ⇒ 交付态不受影响。）

### 12.5 若 12.3 被证实，候选修法（**独立决策，不在本卡**）
| 候选 | 机制 | 已知代价/风险 |
|---|---|---|
| ① MBEDTLS_DYNAMIC_BUFFER=y | 收发时才分配、用完释放 | 分配点漂移 ⇒ 运行时分配失败成新失败模式 |
| ② MBEDTLS_EXTERNAL_MEM_ALLOC=y | 缓冲进 PSRAM | **flash 写（cache 关闭）期间访问 PSRAM 会崩** —— 真风险 |
| ③ 调小 SSL_IN_CONTENT_LEN | 直接砍那个 16384 | 它与 WIRE_PAYLOAD_MAX=16368「整条消息恰好进一个 TLS 记录」是**一对**，改它必须重算该不变式 |

⇒ 三者都**不许**在未测、未写决策的情况下动手。

### 12.6 本卡最终结论
1. **栈缩到 6144 保留**：依据是**余量**（1.47x，高于本仓已接受的 1.28x/1.41x）与真机 high_water=2056，
   **与 largest 无关** —— 它证明的是「栈不是元凶」；
2. **门禁仍拒绝**：根因未定，最大嫌疑是 mbedTLS 记录缓冲（12.3），待探针确认；
3. **floor 不该动**：link=n 稳态 23552 > 16384 ⇒ floor 在 3.0 之前可达；
   动它是把「未定位的缺陷」换成「放宽的判据」；
4. 11.5 的口径问题仍独立成立（free 论证 / largest 执行），但不混进本卡。

### 12.7 ⚠ §12.3 的 mbedTLS 假设**也已被真机证伪**（Lead 单变量实验，我复核原始日志）
把 CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN 从 16384 降到 8192（其余全同，diff 仅 1 项）：

| 配置 | internal free | internal largest |
|---|---|---|
| IN=16384 | 25327 | 15360 |
| IN=8192 | 25611 | 13824 |

⇒ **方向相反**（若那 16384 是 IN 缓冲，砍半应让 largest 涨到 23552）。**假设证伪。**

### 12.8 我补的第二条独立否定（**比方向更强**）
从原始日志取**同一仪器点**（linkheap WAIT_HANDSHAKE）对比，看**两个池**各释放多少：

| | internal | total | PSRAM(推算) |
|---|---|---|---|
| IN=16384 | 25327 | 8307111 | 8281784 |
| IN=8192 | 25611 | 8307355 | 8281744 |
| Δ | **+284** | +244 | **−40** |

⇒ 砍掉 8192 B 的 IN 上限，**内部只回收 284 B、PSRAM 反而少 40 B**。
**两个池都没收回那 8192** ⇒ 它既不在内部堆、也不在 PSRAM。

⇒ 这同时否定了我 §11.3/§12.3 反复引用的前提「**IN 记录缓冲常驻内部 RAM**」
（device_link_wiring.c:166 的注释也写着这句，并据此写了'并存判据 2'）。
机制解释：MBEDTLS_SSL_IN_CONTENT_LEN 只是**上限**，且本镜像 CONFIG_MBEDTLS_SSL_MAX_FRAGMENT_LENGTH=y
⇒ 实际协商/分配的记录缓冲可远小于该上限 ⇒ 改上限自然不动堆。

### 12.9 ⚠ **第三条**：门禁时点的缺口**与 TLS 无关**（时序）
两次运行的时序一致：

    门禁读数 t≈3.3–3.6 s   <   TLS 连接建立 t≈3.9 s

⇒ 门禁拒绝发生在 TLS **握手之前** ⇒ **门禁时刻的缺口不可能由 TLS 缓冲造成**。
⚠ 这也**修正 Lead 的定位窗口**：
- Lead 报告「下降全在 task:create → WAIT_HANDSHAKE 之间」（我用探针读数核对：属实）；
- 但那个窗口**跨过了 1.6 s 且包含 MQTT 发布、Hello/HelloAck、整笔配置事务**，
  而 uart_install(t=3533) 已见 15872 ⇒ 实际缺口在 **t=2261 之后、t=3533 之前**。
⇒ 「不是 IN 记录缓冲」成立，但「嫌疑集中在 mTLS 连接建立」**不成立**。

### 12.10 结论：停止「算一个数 + 改一个候选」的循环
本卡至此**已被三次'数值吻合'式的归因打空**（§11.6 / §12.3 / Lead 的 IN 实验），
⇒ 建议改用**能把分配归因到调用栈**的工具，而不是继续枚举候选：
- ESP-IDF 自带 `heap_trace_*`（`components/heap/include/esp_heap_trace.h`），
  `heap_trace_record_t` 含 **size + alloced_by[调用栈]** ⇒ 直接指认元凶；
- 现镜像为 CONFIG_HEAP_TRACING_OFF=y，需开 STANDALONE（记录缓冲用静态数组，
  可置于 PSRAM：`CONFIG_HEAP_TRACE_HASH_MAP_IN_EXT_RAM`）。

## 13. ⭐⭐⭐ 重开并**改判**：s3p floor 16 KiB → 8 KiB（2026-10-08，round 144）

### 13.1 为什么现在可以重开
§5 列了 5 个重开条件。本次触发的**不是**它们中的任何一个，而是 §11.5 自己提出的那个前置问题：
```
  §11.5 "若开卡，第一个问题不是「该定多少」，而是 **这个 floor 在守哪个量**"
```
⇒ 本轮把这个问题**用实测回答了**（§185 / §189 / §190），所以可以定值了。

### 13.2 ⭐ 定值判据（按 largest 口径，三条）
| # | 判据 | 说明 |
|---|---|---|
| ① | **可达性** | floor 必须**低于稳态 largest**；否则门禁**永久关闭**，那是**功能缺陷**，不是"保守" |
| ② | **必要性** | 不应远高于调用方最大声明需求（否则纯属空转）|
| ③ | **一致性** | 同芯片型号同一阈值，除非有依据 |

### 13.3 逐条代入实测
**① 可达性 —— 这条直接判了 16 KiB 死刑**：
```
  s3p 稳态 largest（3.0 运行中）实测：**12288 ~ 15360**，最小值 **12288**
  而 16 KiB = 16384 > 12288
  ⇒ floor=16384 **永远无法满足** ⇒ 配置事务恒被拒
  ⇒ §172 实测：memgate 14~21 次、ConfigResult success=0、largest 12288/15360/15872
  ⚠ §11.3 当时就写下了这句："这是一个**永远无法满足**的门禁" —— 本轮把它从"观察"变成"判据"。
```
**② 必要性**：三个调用方的声明需求（2026-10-08 核实，§190）：
```
  配置事务 apply_buses / preflight : 4096
  UART install                     : 3584
  log_stream 启动                  : 2048
  OTA                              : **不调用本门禁**（有意设计，见 §190）
  ⇒ 最大 = **4096**；8 KiB 是它的 **2x**，留了余量。
```
**③ 一致性**：
```
  build_firmware.sh：s3-n16 与 s3p-n16 **都是 esp32s3**（同一颗芯片）
  s3 的 floor 已经是 8 KiB ⇒ s3p 取同一值。
  ⚠ 原 2x 差异无任何文档依据（§178.5）；唯一可能的机制
     （SPIRAM_MALLOC_RESERVE_INTERNAL 占内部 RAM）**只会减少可用连续块** ——
     那更是"门槛必须可达"的理由，而**不是**抬高门槛的理由。
     把门槛设得比平台能给的上限还高，门禁就变成了**恒假的装饰**。
```

### 13.4 ⭐ 实测证据（三条独立）
| 证据 | 内容 |
|---|---|
| §185 | floor=8192，**893 s** 无失败（连接失败 0 / BACKOFF 0 / memgate 拒绝 0 / success=0 0 / 回滚 0 / panic 0）|
| §189 | floor=4096（= 最大 need，此时 floor **已不起作用**），配置事务仍全部成功 |
| §190 | 三个调用方在 floor=8192 下**全部实测通过**（配置事务 ✅ / log_stream 启动 ✅ / UART install ✅）|

### 13.5 决策
```
  s3p floor: 16 KiB → **8 KiB**（与同芯片的 s3 一致）
  s3 floor : **不动**（8 KiB）
  c6 floor : **不动**（12 KiB）—— 可达性已核：C6 稳态 largest 73728 ≫ 12288（§177）
```
⚠ **不动的两项也给了可达性结论**（§11.5 要求"逐型号按同一口径重新论证"）：
```
  · c6：有真机读数（73728），12288 ≪ 73728 ⇒ 可达 ✅
  · s3：**无该硬件**（本仓只有 C6 与 S3P 两块板）⇒ 可达性**未实测**。
    但 s3 与 s3p 同芯片，且 s3 **没有 PSRAM**（无预留池、无外部堆竞争）
    ⇒ 其内部连续块**不应比 s3p 更差** ⇒ 8 KiB 在 s3 上应同样可达。
    ⚠ 如实标注为**推断**，非实测。
```

```
  · §3E "调低 floor 只是让门禁闭嘴，不解决内部 RAM 变紧" ——
```
