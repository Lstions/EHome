## 2. 核心数据流

### 2.1 设备接入流 (Hello 握手, v2.1)

```
ESP32 上电
  ↓
[sync_manager] init
  ↓
[wifi_mgr]  连接 WiFi
  ↓
[msg_handler]  发 Hello (type=0x01) — v2.1 字段:
  - device_id, firmware_version, model, channel_count
  - config_epoch (NEW: 本地 epoch)
  - nvs_has_config (NEW: NVS 是否有 manifest)
  - last_manifest (NEW: NVS 中 manifest_id)
  - protocol_version = "2.1" (NEW)
  ↓ (MQTT up: devices/{id}/up/v2)
[server/mqtt/handler_v2] 收 Hello
  ├─ 解析 + upsert collectors
  ├─ **SyncGate.OnHello()** 决策 (v2.1)
  │     ├─ NVS 空 → 强制下发
  │     ├─ Epoch 落后 → 强制下发
  │     ├─ Hash 不匹配 → 强制下发
  │     └─ 否则 dedup 决定
  ├─ 触发 [HandleHelloOTACompletion] (§6.4.3)
  ├─ 触发 [offline_detector] 重置离线计时
  ├─ HA Discovery (retained)
  └─ 推 collector_status 事件到前端 WebSocket
  ↓
[device/manager] 解析 ConfigManifest (含 epoch + sync_id)
  └─ 写 NVS (含 epoch/manifest_id) + 触发 device init
```

### 2.3 OTA 升级流 (v2.1 HTTPS 安全加固)

```
前端 → POST /api/v1/ota/tasks {collector_id, firmware_id}
  ↓
[server/api/handler_ota] 创建 OTA 记录 + supersede 旧 in-flight
  ↓
[ota/manager] 发 OtaCommand (type=0x0A) — 含 SHA256 checksum
  ↓
[esp32/ota] HTTPS 下载 (v2.1: Mozilla CRT bundle 或 自签 cert)
  ├─ 验证 TLS 证书 (不再 skip)
  ├─ 期间发 OtaProgress (type=0x0B) status=0..3
  └─ 下载完成:
       ├─ esp_partition_get_sha256() 计算固件 SHA256
       ├─ 与 OtaCommand.checksum 比对
       ├─ 不匹配 → reject + 上报 fail
       └─ 匹配 → finish + esp_restart()
  ↓
[设备重启 → 发 Hello (含 firmware_version)]
  ↓
[HandleHelloOTACompletion] §6.4.3
```

### 2.4 配置同步流 (v2.1 多通道)

**所有配置同步入口走 SyncGate 同一管道**:

```
                        ┌─────────────────────────────────┐
                        │     ConfigEventBus (Go chan)    │
                        │     + EpochGenerator            │
                        └────────────────┬────────────────┘
                                         │
   ┌────────────────────┬────────────────┼────────────────┬──────────────┐
   │                    │                │                │              │
   ↓                    ↓                ↓                ↓              ↓
┌─────────┐      ┌─────────────┐  ┌──────────┐   ┌──────────┐  ┌──────────┐
│   CRUD  │      │   Server    │  │  Hello   │   │ Status   │  │ Config   │
│ Handler │      │  Startup   │  │ (设备)   │   │ Report   │  │  Query   │
└────┬────┘      └──────┬──────┘  └─────┬────┘   └─────┬────┘  └─────┬────┘
     │                  │               │              │              │
     └──── EmitChange ──┴──── OnStartup ┴── OnHello ───┴── OnStatus ─┴── OnQuery
                              ↓
                    ┌──────────────────┐
                    │     SyncGate     │
                    │  (统一决策中心)   │
                    └────────┬─────────┘
                             ↓
                    m.SendConfigManifest(deviceID, with sync_id)
                             ↓
                            MQTT
                             ↓
                    ESP32 config_mgr_apply_manifest()
```

**关键不变量**:
- 任何 CRUD 必须 emit ConfigChangeEvent (defer)
- SyncGate 决策带 sync_id
- 5s 内推到所有相关设备
- 任何 sync 失败 30s 后周期 sync 兜底

## 3. 协议规范

### 3.1 协议层定位

EHomeSystem v2.0 **完全废弃** v1.x 的 protobuf 协议, 采用精简**二进制帧**:
- 体积: ~50 字节 vs protobuf ~150 字节 (-67%)
- 解析: 手写 decode (~200ns) vs protobuf 反射 (~10μs) (-50x)
- 可调试: 16 进制 dump 可读
- 缺点: 不向后兼容 (v1.x 不可升级, 必须烧 v2.0 固件)

**v2.1 在 v2.0 基础上扩展 4 个新字段 + 2 个新消息, 向后兼容**。

### 3.2 帧格式 (Frame Format) - 不变


### 4.5 同步机制 v2 (核心新增, 2026-06-04)

> **完整设计**: [同步机制/详细设计.md](同步机制/详细设计.md) (31000+ 字节, 14 章节)
> **验收矩阵**: [同步机制/验收标准.md](同步机制/验收标准.md) (14 章验收)

#### 4.5.1 背景 (为什么升级)

v2.0 "Hello-only 同步" 模式在 2026-06-04 全栈审计中暴露 4 个 P0 GAP + 3 个 P1 缺口:

| GAP | 描述 | 后果 |
|-----|------|------|
| **G1** | 服务端改配置后不主动通知 | 采集器**永远**拿不到新配置 |
| **G2** | 服务端重启后内存态 `hashMgr` 丢失 | 在线设备**永不**重新同步 |
| **G3** | 恢复出厂后 NVS 空 + hash 不变 | 设备**永远**等不到 ConfigManifest |
| **G4** | WS 事件名错位 | 状态变化**永不**实时推到前端 |
| G5 | StatusReport 不触发 config 重发 | offline→online 后 config 不下发 |
| G6 | device init 用 Sleep 等待 | 校准数据可能丢失 |
| G7 | hashMgr.Reset 死代码 | 无法强制重发 |

#### 4.5.2 5 条铁律

| 铁律 | 含义 | 修复 GAP |
|------|------|---------|
| **1. 服务端单一权威源 (SSoT)** | 服务端永远持有 config 权威, NVS 只是 cache | G1, G2 |
| **2. 配置变更 = 事件 (Config-as-Event)** | CRUD 通过 ConfigEventBus 发事件, 订阅者统一推 | G1 |
| **3. 多通道同步 (Multi-Channel)** | Hello/StatusReport/Startup/ConfigChange 走同一 SyncGate | G2, G5 |
| **4. 版本化现实 (Versioned Reality)** | 全局 config_epoch 单调递增, 协议携带, NVS 持久化 | G1, G3 |
| **5. 可观测同步 (Observable Sync)** | 每次同步分配 sync_id, 日志/指标/前端事件都带 | 可观测性 |

#### 4.5.3 协议扩展 (v2.1)

**新增字段** (都是 optional, 向后兼容):

| 消息 | 新字段 | 类型 | 用途 |
|------|--------|------|------|
| Hello (0x01) | config_epoch | varint | 采集器本地 epoch |
| Hello (0x01) | nvs_has_config | bool | NVS 是否有 manifest (修复 G3) |
| Hello (0x01) | last_manifest | string | NVS 中 manifest_id |
| Hello (0x01) | protocol_version | string | "2.1" |
| StatusReport (0x02) | config_epoch | varint | 周期上报 (修复 G5) |
| ConfigManifest (0x04) | config_epoch | varint | 服务端当前 epoch |
| ConfigManifest (0x04) | sync_id | string | 本次同步 UUID |
| ConfigManifest (0x04) | sync_reason | enum | hello/status/change/... |

**新增消息** (修复 G1):
- `0x13 ConfigSyncRequest` (ESP→SVR): 主动请求最新 config
- `0x14 ConfigSyncResponse` (SVR→ESP): 同步请求响应

**三轴决策** (从最严格到最宽松):
```
NVS 状态 (nvs_has_config) > Epoch > Hash
      ↓                         ↓      ↓
  修复 G3                  修复 G1, G2  兼容老固件
```
