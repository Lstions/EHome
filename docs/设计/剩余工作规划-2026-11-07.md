## 2. P0 观察期（建议先做，1~2 天）

**为什么必须先做**：本轮 L1/L2/L3 **写路径**全改过，读路径在**四个数据源**之间切换。
白天验证通过不代表夜间通过 —— 夜间流量低、设备少、帧速率低，是「慢设备/空窗口/低速率」类缺陷的暴露窗口。

**要观察的六项**：

| # | 指标 | 判据 |
|---|---|---|
| 1 | 错误日志 | `docker logs --since 24h \| grep -cE 'ERROR\|FATAL\|panic'` = 0 |
| 2 | 帧表滞后 | `now() - max(ts)` ≤ 3s（2s ticker + 余量） |
| 3 | rollup 覆盖率 | 今日有行的分钟数 ≈ 已过分钟数（允许 collector 漏的次日回填） |
| 4 | 图表抽样 | 1h/6h/24h/7d/30d 各打一次，全部有数据 |
| 5 | 分区自动删除 | 45 天保留是否按期 DROP（12-15 前后 `device_data_202610` 应消失） |
| 6 | 磁盘斜率 | 24 小时增量 / 24 ≈ 487 MB/天（偏差 >20% 要查） |

**建议加一条容量告警**（P4 的一部分，但 P0 期间就该有）：
磁盘可用 < 8 GB 时告警。按当前 487 MB/天，那是最后 16 天。

## 3. P1 退休 `unified_data` 历史部分（最大项）

### 3.1 为什么它是重点

它占日增 **71%**，且稳态会撑到 **15.5 GB**（344 MB/天 × 45 天保留）。

而它**对历史曲线已经没有读者**：
```
≤6h   → 帧表解码（EHOME_TELEMETRY_FRAME_DECODE_MAX_WINDOW=6h）
>6h   → rollup
```

### 3.2 但它还有 6 个读者，全部围绕「最新值」

| 读者 | 位置 | 现状 | 替代方案 |
|---|---|---|---|
| **`/nodes/:id/latest`** | `handler_data.go:134` | **每次请求直查 DB，无缓存，实测 0.863s** | 加缓存 / 改读帧表 |
| `/latest-data` as-of 基线 | `device_data_sensors.go` | 已被帧表合成替代（本轮 b552de95） | ✅ 已完成 |
| 设备列表 latest 兜底 | `handler_edge_device.go:439` | 只对缓存 miss 查 | 保留 |
| overview latest 兜底 | `handler_overview.go:96` | 只对缓存 miss 查 | 保留 |
| 启动 warmup | `main.go:516` | **全表 `DISTINCT ON`，无时间界** | 限定最近 N 小时 |
| 历史回落源 | `history_source.go:136` | rollup/帧表都没覆盖时才走 | 退役后变空页（需确认 coverage 全覆盖） |

### 3.3 执行顺序（四步，每步独立可回滚）

```
第 1 步  /nodes/:id/latest 加缓存
        收益：0.863s → <10ms；同时把「每请求直查」这条依赖切断
        验收：连续 100 次请求，DB 查询次数应 ≈ 1（缓存命中）

第 2 步  warmup 加时间窗（如最近 24h）
        理由：现在是全表 DISTINCT ON，随分区增长线性变慢
        验收：启动 warmup 耗时 < 2s，且缓存内容与全表版逐设备逐字段一致

第 3 步  最新值查询迁到「缓存 + 帧表兜底」
        这一步做完，unified_data 的「最新值」用途就没了
        验收：清空 unified_data 的测试库上，/nodes/:id/latest 仍返回正确值

第 4 步  停写 unified_data 历史（保留最近 7 天做过渡）
        改 L1 写路径：不再 INSERT 历史行，只更新最新值缓存
        验收：7 天后 unified_data 只剩 7 天数据；30 天图表全部正确
```

### 3.4 为什么建议「保留 7 天」而不是立刻全停

```
保底：任何「帧表/rollup 没覆盖」的窗口，还能回落到 7 天内的 unified_data
     （而不是空页）
代价：344 MB × 7 = 2.4 GB 稳态（vs 15.5 GB）
```

### 3.5 收益核算

| | 当前路径（45 天保留） | P1 完成后（7 天保留） |
|---|---:|---:|
| `unified_data` 稳态 | 15.5 GB | 2.4 GB |
| 日增 | 487 MB/天 | **143 MB/天** |
| 稳态后可用空间 | 约 13.6 GB | 约 27 GB |
| **可撑** | **约 1.7 年** | **约 3.6 年** |

## 4. P2 `unified_data` 索引瘦身（P1 的替代方案）

如果 P1 因为风险暂时不做，这里是低风险快赢：

```
unified_data_202611（3,477 MB）索引明细：
  device_id_sensor_name_timestamp_value_idx  1,032 MB   11,599 scans   ← 热，保留
  pkey                                         511 MB        0 scans   ← **零扫描**
  device_id_timestamp_idx                      147 MB      471 scans   ← 保留
  timestamp_idx                                131 MB    2,217 scans   ← 保留
```

`pkey` 511 MB / **0 次扫描**。但它承载 PRIMARY KEY 约束，删除需要评估：
```
选项 A：DROP CONSTRAINT（表变成无主键）
  · 收益：立即 −511 MB（按比例，稳态下约 −2.3 GB）
  · 风险：失去 id 唯一性约束；若有代码依赖 ON CONFLICT (id) 会失败
选项 B：把 PK 改成更窄的（只 (id) 或只 (timestamp, id)）
  · 收益：小一些，但保留约束
建议：先 grep 一遍 ON CONFLICT / 依赖 pkey 的代码，再决定。**优先级低于 P1**。
```

## 5. P3 `device_data` 保留期（**需要你决策**）

`device_data` 存原始总线帧（`raw_hex`），是**唯一不可再生的数据**
（`unified_data` / `telemetry_frame` 都没有原始字节）。用途：解析规则出错时重新解析历史。

| 选项 | 稳态 | 日增 | 代价 |
|---|---:|---:|---|
| **永久保留** | 无限增长 | 121 MB/天 | 1 年后 +44 GB |
| **90 天滚动** | 10.9 GB | 121 MB/天 | 解析规则修正只能重放 90 天 |
| **45 天（当前）** | 5.4 GB | 121 MB/天 | 重放窗口 45 天 |

**我的建议：保持 45 天，或放宽到 90 天。**
理由是磁盘在这个量级上还撑得住（90 天方案稳态后仍有约 22 GB），
而 `raw_hex` 的价值在于「解析规则改错时能重放」——45 天通常够覆盖一次发布周期。

⚠ 但这条**必须你定**，因为它改变的是「数据保留多久」这个业务承诺。

## 7. 建议顺序

```
本周     P0 观察期（挂机 1~2 天）
         + P4-1 容量告警（防事故，成本极低）

P0 通过后  P1 第 1 步 /nodes/:id/latest 加缓存（0.863s 是现成的痛点，先解决）
         P1 第 2 步 warmup 加时间窗
         ↓
         P1 第 3~4 步 退休统一数据历史（最大收益）

并行可做  P3 决策（你定保留期）+ P4-2/3/4 文档

可选      P2 unified_data 索引瘦身（若 P1 暂缓）
```

**判断点**：P1 第 3 步完成前，必须有一次「把 unified_data 藏起来，全接口回归」的演练
—— 就像本轮删 11 GB 前做的那样。那次演练抓到了 2 个会造成永久损失的 bug。
