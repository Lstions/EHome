## 1. 功能概述

对"某个数据类别的取值来源"做主备管理：声明候选来源与优先级、按健康度自动/手动切换权威来源、留痕健康事件与故障切换日志、状态转移进通知中心。

对应需求 FR-G4（数据源健康管理）。**本设计同时修正两处历史债**：

1. 后端 `handler_data_source.go` 原为**骨架**：activate/deactivate/reset 只改状态字符串、`health` 恒返回空数组、`failover-logs` 恒返回空数组，无健康评估、无状态机、无日志表。
2. 前端 `api/dataSource.ts` 与后端 `models.DataSource` **schema 互不兼容**（前端按 device_id/category/is_primary/fail_count 建模，后端只有 name/type/config/priority/status），双方都没有消费方——是一段从未接通的垂直切片。

## 2. 概念与术语

| 术语 | 定义 |
|------|------|
| **数据源 (DataSource)** | 一个候选提供者记录：由**哪台边缘设备**提供**哪个逻辑设备的哪个数据类别** |
| **来源组 (group)** | 键 = `(device_id, category)`。同一组内所有来源互为备份 |
| **权威来源 (active source)** | 组内当前被采纳的来源，`status='active'`；**不变量：每组至多一条 active** |
| **候选来源** | `standby`（健康待命）、`error`（熔断）、`disabled`（人工停用） |
| **来源健康事件** | 一次成功或失败判定，落 `data_source_health` 表 |
| **故障切换 (failover)** | active 从 A 变为 B 的动作（自动或手动），落 `failover_logs` 表 |

**为什么 group 键是 (逻辑设备, 数据类别)**：平台已有"逻辑设备身份 / 合并追溯"（见 [边缘设备数据生命周期.md](边缘设备数据生命周期.md)），`unified_data` 同时保存血缘（edge_device_id）与归属（logical_device_id）。当同一逻辑设备的同一类别可由多台边缘设备提供时，"哪一台是权威"才是真实存在的语义问题，也正是主备的来源。

`device_id` 在本域**指 LogicalDevice.ID**（与 `FailoverLog.device_id` 同义）；提供数据的物理来源是 `edge_device_id`。前端历史客户端把 `device` 当作物理设备是建模错误，v1.0 一并修正。

## 3. 状态机

```
                 MarkSuccess                     MarkFailure × max_fail_count
   error  ───────────────────────►  standby  ─────────────────────────────►  error
     ▲                                 ▲ │                                      ▲
     │ reset                           │ │ 自动/手动切换(成为 active)             │
     │                                 │ ▼                                      │
     └─────────────────────────────  active  ────────────────────────────────────┘
                                       │
                     deactivate(人工)  ▼
                                  disabled  ──activate（且满足组不变量）──► active
```

**转移规则（全部为显式规则，实现须逐条可测）**

| # | 触发 | 前置 | 动作 |
|---|------|------|------|
| R1 | `MarkSuccess(source)` | 来源非 disabled | `last_success=now, fail_count=0`；若 error → standby；**不抢占 active** |
| R2 | `MarkFailure(source, reason)` | 来源为 active 或 standby | `last_failure=now, fail_count++`；写健康事件；`fail_count ≥ max_fail_count` → error |
| R3 | active 变 error | 组内存在健康候选 | 选 `priority DESC, id ASC` 的第一条 → active；写 failover_logs(reason=auto)；通知 |
| R4 | active 变 error | 组内**无**健康候选 | 保持原记录为 error 且**不置空 active 语义**：组进入 `degraded`，写通知"无可用备用来源"（fail-open，不静默） |
| R5 | `deactivate(active)` | 组内有健康候选 | 候选接替（同 R3，reason=manual_deactivate），原来源 disabled |
| R6 | `deactivate(active)` | 组内无候选 | **409 拒绝**，要求先指定接替者 |
| R7 | `activate(id)` | 目标非 disabled | 目标 → active，原 active → standby；写 failover_logs(reason=manual)、通知 |
| R8 | `deactivate(standby/error)` | — | 直接 → disabled |
| R9 | `reset(id)` | 来源为 error | → standby，`fail_count=0`（`last_failure` 保留作证据）；若组内当前无 active，可提升为 active |
| R10 | 防抖 | 同组距上次自动切换 < `cooldown`(默认 300s) | 只记健康事件，**不切换**；写通知（可观测） |
| R11 | 最小驻留 | 来源成为 active 后 < `min_residency`(默认 120s) | 停滞判定不累计 fail_count |

**不自动回切**：恢复健康的来源停留在 standby，直到人工 `activate`。理由：家庭场景抖动（WiFi 重连、边缘设备重启）会造成来回切换，产生日志噪声与口径摇摆；权威来源的稳定性优先于"回到最初声明的主"。

## 4. 健康判定

**不新增探测线程做主动探测**——复用既有可信信号，避免与既有健康语义打架：

| 事件 | 来源 | 语义 |
|------|------|------|
| 成功 | `databus.SensorParserConsumer` 解析成功并持久化后，新增 `sourceHealthSink(edgeDeviceID, category, at)` 回调（与既有 `rollupSink`/`latestSink`/`alertSink` **完全同构**，经 `nodemgr` 二阶段注入，见 §6） | 该来源在该类别上有真实数据入库 |
| 失败（设备级） | `offlinedetector.OnEdgeDeviceOffline(edgeDeviceID)` → datasource hook | 承载来源的边缘设备离线，立即计一次失败 |
| 失败（停滞级） | 内置扫描器（默认 60s 一轮）：`now - last_success > staleness`(默认 300s) 且来源边缘设备在线 | 设备在线但该类别不再产生数据（传感器坏、通道断） |

**成功事件按类别过滤**：回调携带本次解析出的 `sensor_name` 集合（`parser.Field` 已有该信息），只有当来源声明的 `category` 在集合内才标成功——否则"温度来源"会被一次电压上报续命。

**健康记录保留**：`data_source_health` 保留 30 天，由 `datalifecycle` 每日 purge 顺带清理（与 retention 任务同轮，独立 batch DELETE，避免新增长期任务）。

## 5. 数据模型

```go
// DataSource 数据源主备（v1.0 扩展；原骨架仅 name/type/config/priority/status）
type DataSource struct {
    ID            uint       // 主键
    DeviceID      uint       // LogicalDevice.ID —— 来源组键（索引）
    Category      string     // 数据类别（sensor_name 类别）（索引，与 device_id 组复合索引）
    EdgeDeviceID  uint       // 提供数据的边缘设备（血缘来源）（索引）
    SourceType    string     // v1.0 仅 'edge_device'；枚举预留 external/mqtt/ha（校验拒绝）
    Name          string     // 展示名
    Description   string
    Priority      int        // 越大越优先
    IsPrimary     bool       // 声明意图（初始主）；运行期权威看 Status
    MaxFailCount  int        // 熔断阈值，默认 3（1..20 校验）
    FailCount     int        // 连续失败计数（运行态）
    Status        string     // active|standby|error|disabled
    LastSuccess   *time.Time
    LastFailure   *time.Time
    Config        string     // JSON 文本（预留）
    CreatedAt, UpdatedAt time.Time
}

// DataSourceHealth 健康事件（失败与状态转移留痕；成功事件不落库，仅更新来源）
type DataSourceHealth struct {
    ID uint; SourceID uint /*索引*/; DeviceID uint; Category string
    Status string      // failure | transition
    Message string
    ResponseTime int   // ms，停滞判定填停滞时长
    CreatedAt time.Time
}

// FailoverLog 故障切换日志
type FailoverLog struct {
    ID uint; DeviceID uint /*索引*/; Category string
    FromSourceID uint; ToSourceID uint
    Reason string      // auto | manual | manual_deactivate
    Trigger string     // device_offline | stale_data (auto 时必填)
    CreatedAt time.Time
}
```

**迁移**：`data_sources` 生产库实测 **0 行**（2026-09-12 核），故列扩展无存量数据风险；三张表均进 `database.DB.AutoMigrate` 与 `testutil.allModels`（保持两处清单同步，这是本项目既有纪律）。`type` 列保留但不再使用（v2 清理，避免同批做破坏性改名）。

## 6. 实现结构

| 关注点 | 位置 |
|--------|------|
| 领域服务（状态机 + 健康 + 日志） | `backend/internal/datasource/`（新包；纯逻辑与 DB 分离，状态机可表驱动单测） |
| API | `backend/internal/api/handler_data_source.go`（重写）+ `handler_data.go` 的 failover-logs 占位端点移交本域 |
| 接线 | `cmd/server/main.go`：构造 `datasource.Service` → `nodemgr.Manager.SetSourceHealthSink`（与 alert/automation **同一二阶段注入**模式，禁止在 NewManager 前注入）→ `offlinedetector` 离线回调 → 启动停滞扫描器 |
| 前端 | `views/data-source/DataSourceList.vue` + `stores/dataSource.ts` + `api/dataSource.ts`（对齐本契约）+ 路由 `/data-sources` + 侧边栏入口 |
| 通知 | 复用 `models.Notification`（`source='data_source'`） |

> ⚠️ **接线纪律**（踩过坑，见 `main.go` 与 `manager.go:106-130`）：任何 sink 必须在 `nodemgr.NewManager` 之后注入，并同时推送到已构建的 `parserConsumers`；否则引擎"从未触发"而单测全绿。

## 7. API 契约

统一 envelope（`Success/SuccessMsg/Error`），全部路径并入 `/api/v1`。

| 方法 | 路径 | 语义 | 关键校验 |
|------|------|------|---------|
| GET | `/data-sources` | 列表 | `device_id/category/status` 过滤；`page≥1`、`1≤page_size≤100`（clamp 不报错）；返回 `{items,total}` |
| GET | `/data-sources/:id` | 详情 | 404 |
| POST | `/data-sources` | 新建 | 必填 `device_id/category/edge_device_id`；`source_type` 仅 `edge_device`；同组同 edge_device 重复 → **409**；`max_fail_count ∈ [1,20]` → 否则 400；首条自动 active |
| PUT | `/data-sources/:id` | 更新 | 白名单字段 `name/description/priority/is_primary/max_fail_count/config`；**改 .Error 必须检查**（历史吞错误缺陷）；404 |
| DELETE | `/data-sources/:id` | 删除 | 删除 active 且组内有其他来源 → 自动接替（写日志）；组内唯一来源 → 允许删除并通知"该类别失去来源"；404 |
| POST | `/data-sources/:id/activate` | 手动切换 | 目标 disabled → **409**；写 failover_logs(reason=manual) + 通知 |
| POST | `/data-sources/:id/deactivate` | 停用 | active 且无候选 → **409**（R6）；否则按 R5/R8 |
| POST | `/data-sources/:id/reset` | 重置 | 非 error → 400（显式，不静默成功）；按 R9 |
| GET | `/data-sources/:id/health` | 健康记录 | 倒序；`limit` clamp ≤200，默认 50 |
| GET | `/devices/:id/failover-logs` | 切换日志 | 倒序；可选 `category`、`limit` clamp ≤200；返回 **data 为数组**（前端既有契约，勿改形状） |

**契约不变量**：所有数组型 data 在空集时返回 `[]` 而非 `null`（前端直接 `.length`/`.map`）；所有错误返回 envelope 且 `code` == HTTP 状态码。

## 8. 前端设计

- **路由**：`/data-sources` → `views/data-source/DataSourceList.vue`（name: `DataSourceList`，侧边栏"设备"分组下，位于"逻辑设备"之后）。
- **信息架构**（遵循 [前端开发与UIUX设计规范.md](../规范/前端开发与UIUX设计规范.md) §4.1，BMS DNA 模式语言）：
  1. PageHeader（标题 + 说明 + "新建数据源"主操作）
  2. 概览指标条：总来源数 / 权威 / 待命 / 熔断（StatCard，未知显示"—"不伪造）
  3. 筛选：设备选择（逻辑设备）/ 类别 / 状态
  4. 来源表格：设备 · 类别 · 来源边缘设备 · 优先级 · 状态标签 · 连续失败 · 最后成功（相对时间，空显示"—"）· 操作（切换为权威 / 停用 / 重置 / 编辑 / 删除）
  5. 详情抽屉（el-drawer）：基础字段 + 健康记录时间线（分页）+ 该设备的切换日志时间线
- **五态**：加载（骨架/loading）、空（EmptyState + 主操作）、错误（错误态 + 重试）、离线（顶部 NetworkBanner 既有能力）、禁用（按钮 disabled + tooltip 说明原因）。危险操作（删除、停用 active）走 ElMessageBox 二次确认。
- **状态语义色**：active=success、standby=info、error=danger、disabled=info(灰)。文字 + 颜色双重表达（不靠颜色单独承载语义）。
- **测试**（规范 §5.1/§5.2）：store 单测（fetch/CRUD/状态操作/失败分支）+ 页面测试（挂载渲染、空态、状态标签、操作触发 API 调用、错误提示）；**禁止 `?raw` 源码字符串断言**（本项目明令的测试反模式）。

## 9. 已知限制（v1.0 显式声明）

1. **不改读取热路径**：`unified_data` 查询口径不变（血缘全量保留 + 逻辑口径保形去重 MAX(id)）。权威来源当前用于：运维可见性、状态转移、通知、以及详情抽屉中的来源标注。**将"权威来源"接入告警取值/最新值口径列入 v2 候选**，需先有真实抖动数据支撑。
2. 仅支持 `source_type='edge_device'`（外部数据源 external/mqtt/ha 只留枚举）。
3. 无自动回切（§3 裁决）。
4. 停滞扫描为单实例进程内定时器；多实例部署需改为选主（与既有 offlinedetector 同一前提，不是本域新增约束）。
