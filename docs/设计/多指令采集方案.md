# 多指令采集方案 — 详细设计

> **版本**: v2.3
> **日期**: 2026-06-21
> **状态**: 共识方案（4 轮辩论收敛）
> **关联**: [00-术语表.md](00-术语表.md) | [边缘设备/详细设计.md](边缘设备/详细设计.md) | [通道/详细设计.md](通道/详细设计.md)

## 1. 设计动机

### 1.1 四个需求指向同一根因

| 需求 | 根因 |
|------|------|
| TTL-485 多 slave 设备 | Channel 是调度单元，只取 template_ids[0] |
| 边缘设备地址发现/修改 | 无 Modbus 级别扫描协议 |
| 自检/健康检查 | error_count 不上报，只本地退避 |
| 多指令独立频率 | interval_ms 在 Channel 层，所有指令共享 |

**根因**：Channel 同时承担"物理总线"和"采集调度"两个职责。

### 1.2 设计原则

- **不引入新顶层概念**：EdgeDevice 已是正确的抽象
- **最小协议变更**：复用现有消息类型，只扩展字段
- **向后兼容**：版本协商，老固件不受影响
- **以实际代码为准**：方案基于 `esp32-collector/` 和 `backend/` 的实际代码

## 2. 核心方案：EdgeDevice 从「一设备一指令」扩展为「一设备多指令」

### 2.1 概念模型

```
Channel (物理总线)
  └── EdgeDevice (逻辑设备)
        ├── Command 0: template_id=1, interval_ms=1000  (基本信息)
        ├── Command 1: template_id=2, interval_ms=5000  (电池信息)
        └── Command 2: template_id=3, interval_ms=60000 (统计数据)
```

### 2.2 与当前架构对比

| 维度 | v2.2 当前 | v2.3 方案 |
|------|----------|----------|
| 调度单元 | Channel（取 template_ids[0]） | EdgeDevice.commands[] 独立计时 |
| 频率归属 | Channel.IntervalMs | Command.IntervalMs |
| 多设备支持 | 不支持（只取第一个 template） | EdgeDeviceGroup 嵌套结构 |
| 数据路由 | channel_id 猜设备 | edge_device_id + command_index |

## 3. 协议变更

### 3.1 Hello (0x01) — 新增 protocol_version

```
field 7: protocol_version (varint, 默认 1)

老固件：不发送此字段 → 后端按 v1 编码
新固件：protocol_version=2 → 后端按 v2 编码
```

### 3.2 ConfigManifest (0x04) — Channel 子帧新增 field 9

```
ConfigChannel:
  field 1: id              (varint)
  field 2: hardware_id     (varint/string)
  field 3: template_ids    (repeated varint)  — [v1 兼容]
  field 4: interval_ms     (varint)           — [v1 兼容]
  field 5: enabled         (varint)
  field 6: bus_type        (varint)
  field 7: bus_config      (bytes)
  field 9: edge_device_groups (repeated EdgeDeviceGroup)  — [v2 新增]

互斥规则：field 3/4 和 field 9 不同时出现
  - protocol_version=1 → 只写 field 3+4
  - protocol_version=2 → 只写 field 9
```

### 3.3 EdgeDeviceGroup 子消息（新增）

```
EdgeDeviceGroup:
  field 1: edge_device_id  (varint)    — 中心端 PK
  field 2: hardware_id     (varint)    — 总线地址 (Modbus slave / I2C addr)
  field 3: commands        (repeated EdgeDeviceCommand)
```

### 3.4 EdgeDeviceCommand 子消息（新增）

```
EdgeDeviceCommand:
  field 1: template_id     (varint)    — 采集模板 ID
  field 2: interval_ms     (varint)    — 采集间隔，必须非零
  field 3: enabled         (varint)    — 启用/禁用
```

### 3.5 DataReport (0x03) — 新增路由字段

```
field 1: channel_id        (varint)    — 保留
field 2: timestamp         (varint)    — 保留
field 3: sensor_values     (repeated)  — 保留
field 4: edge_device_id    (varint)    — [v2 新增]
field 5: command_index     (varint)    — [v2 新增] 0-based
```

### 3.6 StatusReport (0x02) — 新增健康信息

```
field 1-6: 保留
field 7: channel_health (repeated ChannelHealth)  — [v2 新增]

ChannelHealth:
  field 1: channel_id         (varint)
  field 2: edge_device_health (repeated EdgeDeviceHealth)

EdgeDeviceHealth:
  field 1: edge_device_id     (varint)
  field 2: comm_status        (varint)  — 0=OK, 1=TIMEOUT, 2=CRC_ERROR, 3=FAULT
  field 3: consecutive_errors (varint)
  field 4: total_errors       (varint)
  field 5: last_success_ms    (varint)
```

## 4. 固件数据结构

```c
#define MAX_CHANNELS           8
#define MAX_EDGE_DEVICES_PER_CH 5
#define MAX_COMMANDS_PER_DEVICE 3
#define SCHEDULER_TICK_MS      10
#define FAULT_THRESHOLD        3

// 采集指令运行时
typedef struct {
    uint32_t template_id;
    uint32_t interval_ms;
    uint32_t last_run_ms;
    uint8_t  enabled;
    uint8_t  error_count;
} command_runtime_t;          // 16B

// 边缘设备运行时
typedef struct {
    uint32_t edge_device_id;
    uint32_t hardware_id;
    uint8_t  enabled;
    uint8_t  command_count;
    command_runtime_t commands[MAX_COMMANDS_PER_DEVICE];
} edge_device_runtime_t;      // 58B

// 通道运行时
typedef struct {
    uint32_t channel_id;
    uint8_t  bus_type;
    char     bus_config[64];
    uint8_t  enabled;
    SemaphoreHandle_t bus_mutex;
    uint8_t  edge_device_count;
    edge_device_runtime_t edge_devices[MAX_EDGE_DEVICES_PER_CH];
} channel_runtime_t;          // ~360B

// 全局调度器状态
typedef struct {
    channel_runtime_t channels[MAX_CHANNELS];
    uint8_t channel_count;
} scheduler_state_t;          // ~2900B
```

RAM 预算：scheduler 增量 ~2.9KB，占 ESP32-C6 剩余 240KB 的 1.2%。

## 6. 地址发现/修改（需求 2）

### 6.1 哪些总线需要地址发现

地址发现只存在于**多设备共享物理总线**的场景。按总线类型：

| 总线类型 | 工作模式 | 地址概念 | 地址发现 | 地址修改 |
|---------|---------|---------|---------|---------|
| **UART** | bilateral（点对点） | 无，物理一对一 | ❌ 不需要 | ❌ 不需要 |
| **UART** | rs485（多站） | Modbus slave ID (1-247) | ✅ 需要 | ✅ 需要 |
| **I2C** | 多设备 | 硬件地址 (0x01-0x7F) | ✅ 已有 | ✅ 需要 |
| **SPI** | CS 片选 | CS 引脚编号 | ❌ CS 是硬件引脚 | ✅ 改 CS |
| **GPIO** | 点对点 | 无 | ❌ 不需要 | ❌ 不需要 |
| **ADC** | 点对点 | 无 | ❌ 不需要 | ❌ 不需要 |

**关键设计**：`Channel.bus_config` JSON 中通过 `mode` 字段区分 UART 的工作模式：

```json
// 点对点 UART（默认）
{"baudrate": 9600, "data_bits": 8, "stop_bits": 1, "parity": "none"}

// RS485 多站
{"baudrate": 9600, "data_bits": 8, "stop_bits": 1, "parity": "none", "mode": "rs485"}
```

前端根据 `bus_type + bus_config.mode` 决定是否展示地址发现按钮：
- `I2C` → 显示
- `UART + mode=rs485` → 显示
- 其他 → 隐藏

### 6.2 地址发现：扩展 ScanRequest 协议

当前 `ScanRequest (0x07)` 只有 field 2 (hardware_id)，I2C 扫描够用。RS485 需要范围扫描。

**ScanRequest 扩展**（新增 field 3-5，兼容老字段）：

```
field 1: request_id   (string)  — 保留
field 2: hardware_id  (varint)  — 保留（I2C 路径用）
field 3: scan_type    (varint)  — 新增：1=I2C(默认), 2=MODBUS
field 4: start_addr   (varint)  — 新增：Modbus 起始地址
field 5: end_addr     (varint)  — 新增：Modbus 结束地址
field 6: timeout_ms   (varint)  — 新增：单地址超时
```

ESP32 侧 `on_scan_req_received` 实现：

```
if scan_type == MODBUS:
    for addr in [start_addr, end_addr]:
        send Modbus 03 (read holding register) to addr
        if response within timeout_ms:
            found.append(addr)
    send ScanRpt with found addresses
elif scan_type == I2C (or field 2 present):
    existing I2C scan logic
```

### 6.3 地址修改

**关键约束**：Modbus 地址修改**没有统一标准**。每个 OEM 厂商的地址寄存器、功能码、写值格式都不同——有些用功能码 06 写单个寄存器，有些用功能码 10 写多个寄存器，有些需要特定解锁序列。**系统不能假设一个通用的地址修改命令**。

**设计**：地址修改命令由用户在 **DeviceConfig 中预定义**，作为一个可选的 `change_address_command` 模板。模板中用 `{addr}` 占位符表示目标地址：

```json
// DeviceConfig 中新增字段
{
  "change_address_command": {
    "description": "写 Modbus 从站地址寄存器 (0x0100)",
    "template_hex": "{addr} 06 01 00 {addr_hi} {addr_lo}",
    "read_back": true,
    "verify_register": "0100"
  }
}
```

**占位符规则**：
- `{addr}` — 新地址的完整字节（1 字节，直接替换）
- `{addr_hi}` — 新地址的高字节（用于 16 位寄存器的高位）
- `{addr_lo}` — 新地址的低字节（用于 16 位寄存器的低位）

**后端处理流程**：

```
前端 → POST /api/v1/edge-devices/{id}/change-address { new_address: 5 }
  ↓
后端：
  1. 查 EdgeDevice → 获取 DeviceConfig
  2. 查 DeviceConfig.change_address_command
     → 如果为空 → 返回 400 "该设备型号不支持地址修改"
  3. 取 template_hex，替换占位符：
     "{addr} 06 01 00 {addr_hi} {addr_lo}" + new_address=5
     → "05 06 01 00 00 05"
  4. 追加 CRC（如果设备使用 Modbus RTU）
  5. 用旧地址发送 WriteCommand（在旧地址上执行修改命令）
  ↓
ESP32：bus_dma_write → 等待 ACK → WriteResponse
  ↓
后端：成功 → 更新 edge_devices.hardware_id → EmitConfigChange
```

**前端行为**：
- 只有 DeviceConfig 定义了 `change_address_command` 的设备才显示"修改地址"按钮
- 如果未定义 → 按钮隐藏 + tooltip "该设备型号未配置地址修改指令"

**安全**：
- 操作记录到 OperationLog
- 修改前弹窗确认（显示：旧地址 → 新地址）
- 修改失败（WriteCommand 超时）→ 地址回滚，不更新 DB
