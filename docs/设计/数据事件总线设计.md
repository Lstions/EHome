# 通道数据流事件总线架构 — 设计方案

> **版本**: v2.5 | **状态**: 已实现 | **更新**: 2026-07-14
> **当前开发端口**: 8082 | **历史临时验收端口**: 8090（仅 2026-07-13 的一次性本地验收记录）

## 0. 需求说明

### 0.1 背景与问题

当前通道数据流（DataReport）在后端 `processDataReportJob` 中是同步串行处理，所有数据都经过完整的重型流水线：

```
MQTT handler → dataCh → worker pool → processDataReportJob:
  1. termMgr.RecordRX          (终端记录)
  2. lookupCollectorID         (DB 查询)
  3. db.Create DeviceData      (DB 写入)
  4. parseAndStoreData:        (重量级)
     a. findEdgeDeviceByChannelID  (2次 DB 查询)
     b. DeviceConfig.Parser 查询   (DB 查询)
     c. Driver 解析
     d. unified_data 批量写入      (DB 写入)
     e. edge_device 状态更新       (DB 写入)
     f. HA publish
     g. DataUpdate WS broadcast
  5. findEdgeDeviceByChannelID (又一次 DB 查询)
  6. BroadcastEvent ChannelData (WebSocket 推送)
```

问题：
- 被动数据（request_id=0，通道终端裸字节）也走完整流水线，执行 5+ 次 DB 查询和 3+ 次 DB 写入，但这些操作对终端显示毫无意义
- 传感器解析、DB 存储、HA 推送、WebSocket 推送耦合在一个函数中，无法独立启停或按数据类型跳过
- 高频数据场景下 DB IO 成为瓶颈，拖慢 WebSocket 推送延迟
- 新增消费需求（如数据导出 API、外部 Webhook）需要修改 processDataReportJob，违反开闭原则

### 0.2 功能需求

| 编号 | 需求 | 优先级 | 说明 |
|------|------|--------|------|
| R1 | 生产者消费者解耦 | P0 | MQTT handler 只负责解析帧并投递总线，不关心下游消费方式 |
| R2 | 消费者可插拔 | P0 | 新增消费者不改现有代码（开闭原则） |
| R3 | 消费者独立启停 | P0 | 每个消费者可按数据类型决定是否处理 |
| R4 | 被动数据快速通道 | P0 | request_id=0 的被动数据跳过传感器解析和 DB 存储，只推终端 |
| R5 | 消费者隔离 | P0 | 单个消费者 panic 或慢处理不影响其他消费者 |
| R6 | 背压控制 | P0 | 数据洪峰时丢弃旧数据保留新数据 |
| R7 | 现有功能不变 | P0 | 终端记录、传感器解析、DB 存储、HA 推送、WS 推送等现有行为保持一致 |

### 0.3 约束条件

- 不改变 ESP32 固件协议（DataReport 0x03 帧格式不变）
- 不改变前端 WebSocket 事件格式（channel_data / data_update 事件不变）
- 复用现有 worker pool 机制（dataCh + goroutine），在其内部重构
- 传感器解析依赖 DB 查询（需查 edge_device + device_config），无法完全消除 DB IO，但可对被动数据跳过

## 1. 整体架构

```text
MQTT Handler → dataCh workers → DataEventBus（入口 256）
                                  │
                                  ├─ Terminal worker（mailbox 64，所有事件）
                                  ├─ WS Push worker（64，仅 Passive）
                                  ├─ DataMetrics worker（64，仅 ScheduledSample）
                                  ├─ PendingWrite worker（64，仅 CommandResponse）
                                  ├─ DB Persist worker（64，非 Passive）
                                  └─ Sensor Parser worker（64，可解析的非 Passive）

不同消费者并行；同一消费者内按 mailbox 顺序串行。被动数据只走 Terminal + WS Push，跳过 DB IO。
```

## 2. 核心数据结构

### 2.1 DataEvent

```go
// DataEvent 表示一条从 ESP32 收到的数据报告事件
// 由 MQTT handler 解析帧后创建，投递到 DataEventBus
type DataEvent struct {
    DeviceID          string    // 采集器 node_id
    ChannelID         uint64    // 通道 ID
    Timestamp         uint64    // ESP32 微秒时间戳
    Sequence          uint64    // 序列号
    RawData           []byte    // 原始数据
    ErrorCode         uint64    // 错误码 (0=正常, 0x01=RX超时)
    RequestID         uint64    // 请求 ID (0=被动数据/终端模式)
    EdgeDeviceID      uint64    // 边缘设备 ID (0=未知)
    CommandIndex      uint64    // per-edge-device command array index
    CommandTemplateID uint64    // ConfigTemplate.ID, firmware field 9
    ReceivedAt        time.Time // 后端收到时间
}

// 三类事件分类（基于 RequestID 和 EdgeDeviceID）:

// IsPassive 识别不相关的终端数据 (request_id=0 且 edge_device_id=0)
func (e *DataEvent) IsPassive() bool         { return e.RequestID == 0 && e.EdgeDeviceID == 0 }

// IsCommandResponse 识别调度器命令的响应 (request_id≠0)
func (e *DataEvent) IsCommandResponse() bool { return e.RequestID != 0 }

// IsScheduledSample 识别调度采样 (request_id=0 但 edge_device_id≠0)
func (e *DataEvent) IsScheduledSample() bool { return e.RequestID == 0 && e.EdgeDeviceID != 0 }

// ShouldPersist 被动数据不需要持久化
func (e *DataEvent) ShouldPersist() bool     { return !e.IsPassive() }

// ShouldParse 仅调度数据且无错误才解析
func (e *DataEvent) ShouldParse() bool {
    return e.ShouldPersist() && e.ErrorCode == 0 && len(e.RawData) > 0
}

// IsError 判断是否为错误报告
func (e *DataEvent) IsError() bool { return e.ErrorCode != 0 }
```

### 三类数据事件

| 事件类型 | 判定条件 | 说明 |
|---------|---------|------|
| **被动数据 (Passive)** | `request_id=0 且 edge_device_id=0` | 通道终端裸字节，无对应命令。只走 Terminal + WS Push，跳过 DB IO |
| **命令响应 (CommandResponse)** | `request_id≠0` | Terminal、PendingWrite、DB Persist；有可解析数据时再走 Sensor Parser |
| **调度采样 (ScheduledSample)** | `request_id=0 且 edge_device_id≠0` | 调度器周期采样。需要解析和持久化，但不需 PendingWrite 路由 |

### 2.2 DataConsumer 接口

```go
// DataConsumer 是所有数据消费者的统一接口
type DataConsumer interface {
    Name() string              // 消费者名称（唯一标识）
    ShouldHandle(evt DataEvent) bool  // 判断是否处理该事件
    Handle(evt DataEvent)      // 处理事件
}
```

### 2.3 DataEventBus 中间件

```go
// DataEventBus 解耦 MQTT handler（生产者）和数据消费者。
// 与 LogEventBus 架构一致：通道缓冲 + dispatch goroutine + 消费者隔离。
// 每个消费者拥有独立的 persistent worker goroutine 和 64 容量 mailbox。
type DataEventBus struct {
    mu        sync.RWMutex
    consumers map[string]*consumerWorker
    dataChan  chan DataEvent     // 256 容量有缓冲通道
    wg        sync.WaitGroup
    dropped   atomic.Uint64
    stopCh    chan struct{}
}

// consumerWorker 是一个持久消费者工作单元。
type consumerWorker struct {
    consumer DataConsumer
    mailbox  chan DataEvent  // 64 容量邮箱，背压隔离
    done     chan struct{}   // 单 worker 退出信号
    doneOnce sync.Once       // 防止 Unregister/Stop 重复关闭
}
```

## 3. 消费者设计

### 3.1 Terminal Consumer — 终端记录 + WebSocket 推送

**职责**：记录 RX 数据到终端管理器，推送 terminal 事件到 WebSocket。

**处理条件**：`ShouldHandle` 始终返回 true（所有数据都记录到终端）。

```go
type TerminalConsumer struct {
    termMgr *terminal.Manager
}

func (c *TerminalConsumer) ShouldHandle(evt DataEvent) bool { return true }

func (c *TerminalConsumer) Handle(evt DataEvent) {
    // 1. 记录到终端管理器（已有逻辑，含 terminal WS event）
    c.termMgr.RecordRX(evt.DeviceID, uint(evt.ChannelID), evt.RawData)
}
```

**特点**：最轻量，无 DB 操作。被动数据和命令数据都处理。

### 3.2 WS Push Consumer — 被动 `channel_data` 快速通道

**职责**：仅为未关联的被动/终端 RX 数据构建原始 `channel_data` WebSocket 事件。调度采样和命令响应由 SensorParser Consumer 解析后推送兼容且更丰富的 `channel_data`，避免同一事件重复广播。

**处理条件**：仅 `evt.IsPassive()` 返回 true。

```go
func (c *WSPushConsumer) ShouldHandle(evt DataEvent) bool {
    return evt.IsPassive()
}
```

**特点**：无 DB 操作，纯内存；与 Terminal Consumer 组成被动数据快速通道。

### 3.3 Sensor Parser Consumer — 传感器解析 + 存储 + HA 推送

**职责**：解析传感器数据，写入 unified_data，更新 edge_device 状态，推送 data_update 事件，HA publish。

**处理条件**：`evt.ShouldParse()`，即命令响应或调度采样，只要无错误且包含原始数据就解析。

```go
type SensorParserConsumer struct {
    db    *gorm.DB
    wsHub *websocket.Hub
    ha    *homeassistant.Integration
    // reassembler 需要 Manager 注入或共享
}

func (c *SensorParserConsumer) ShouldHandle(evt DataEvent) bool {
    return evt.ShouldParse()
}

func (c *SensorParserConsumer) Handle(evt DataEvent) {
    // 原 parseAndStoreData 逻辑搬到这里：
    // 1. findEdgeDeviceByChannelID
    // 2. DeviceConfig.Parser / Driver 解析
    // 3. unified_data 批量写入
    // 4. edge_device 状态更新
    // 5. HA publish
    // 6. 兼容 channel_data + data_update WS broadcast
}
```

**特点**：最重量级，包含 DB 查询/写入和协议解析；处理可解析的命令响应与调度采样，被动数据完全跳过。

### 3.4 DB Persist Consumer — 原始数据持久化

**职责**：将原始数据写入 device_data 表（审计/历史记录）。

**处理条件**：`evt.ShouldPersist()`，即命令响应和调度采样；被动数据不持久化。

```go
type DBPersistConsumer struct {
    db *gorm.DB
}

func (c *DBPersistConsumer) ShouldHandle(evt DataEvent) bool {
    return evt.ShouldPersist()
}

func (c *DBPersistConsumer) Handle(evt DataEvent) {
    dataJSON, err := json.Marshal(/* raw report fields */)
    if err != nil {
        logger.Warn(/* structured context */)
        return
    }
    if err := c.db.Create(&models.DeviceData{/* ... */}).Error; err != nil {
        metrics.DataConsumerDBWriteFailures.WithLabelValues(c.Name(), "device_data").Inc()
        logger.Warn(/* structured context */)
    }
}
```

### 3.5 PendingWrite Consumer — 命令响应路由

**职责**：将命令响应路由到 pendingWrite 管理器（用于 WriteCmd 确认和设备初始化）。

**处理条件**：仅处理有 request_id 的数据或错误报告。

```go
type PendingWriteConsumer struct {
    pendingWrite *pendingwrite.Manager
    deviceInit   *deviceinit.Orchestrator
    db           *gorm.DB
}

func (c *PendingWriteConsumer) ShouldHandle(evt DataEvent) bool {
    return evt.RequestID != 0
}

func (c *PendingWriteConsumer) Handle(evt DataEvent) {
    if evt.ErrorCode == 0x01 {
        // RX 超时
        c.pendingWrite.HandleResponse(uint32(evt.RequestID), false, 0x01, "sensor RX timeout")
        return
    }
    c.pendingWrite.HandleDataReportAck(uint32(evt.RequestID), evt.RawData)
    // device init 通知逻辑...
}
```

### 3.6 DataMetrics Consumer — 调度报告计数

**职责**：恢复调度采样结果统计；成功样本递增 `DataReportsProcessed`，错误或空数据递增 `DataReportErrors`。

**处理条件**：仅 `evt.IsScheduledSample()`。命令响应由 pending-write 链路处理，不计入该调度采样指标。

```go
type DataMetricsConsumer struct{}

func (c *DataMetricsConsumer) Name() string { return "data_metrics" }
func (c *DataMetricsConsumer) ShouldHandle(evt DataEvent) bool {
    return evt.IsScheduledSample()
}
func (c *DataMetricsConsumer) Handle(evt DataEvent) {
    if evt.IsError() || len(evt.RawData) == 0 {
        metrics.DataReportErrors.Inc()
        return
    }
    metrics.DataReportsProcessed.Inc()
}
```

**特点**：无 DB 操作，纯计数。统计调度器的采集成功率，供可观测性使用。

## 4. 数据流对比

### 4.1 重构前（串行同步）

```text
DataReport → processDataReportJob
  ├─ Terminal / PendingWrite
  ├─ 节点与边缘设备查询
  ├─ DeviceData / UnifiedData 写入
  ├─ 协议解析与状态更新
  └─ HA / WebSocket 推送
```

重构前，同一 worker 串行执行业务解析和 DB IO；被动数据也可能在重型工作之后排队。

### 4.2 当前架构（隔离消费者）

```text
DataReport → DataEventBus.Publish
  ├─ Terminal Consumer（所有事件）
  ├─ WS Push Consumer（仅被动数据）
  ├─ DataMetrics Consumer（仅调度采样）
  ├─ PendingWrite Consumer（仅命令响应）
  ├─ DB Persist Consumer（命令响应/调度采样）
  └─ Sensor Parser Consumer（可解析的命令响应/调度采样）
```

各消费者由独立 persistent worker 串行消费自己的 mailbox；不同消费者并行，同一消费者内保持事件顺序。被动数据只经过 Terminal 与 WS Push，跳过 DB IO；调度采样与命令响应的兼容 `channel_data`/`data_update` 由 Sensor Parser 在解析后推送。

### 4.3 定性延迟变化

- 被动数据不再等待 DB/解析消费者，Terminal 与 WS Push 可独立推进。
- 调度采样和命令响应仍需协议解析后才产生包含解析结果的兼容 `channel_data`/`data_update`。
- 文档不声明未经同环境基准测试验证的固定微秒值或倍数。

## 5. 与现有 worker pool 的关系

### 5.1 保留 worker pool 做事件转换与投递

现有 `dataCh + 8 workers` 机制保留，但 worker 的职责从“全流程处理”缩减为“把已解码的 `dataReportJob` 转换成 `DataEvent` 并投递总线”：

```go
// 改造前: processDataReportJob 做全部事情
// 改造后: processDataReportJob 只解析帧并投递总线
func (m *Manager) processDataReportJob(job dataReportJob) {
    evt := DataEvent{
        DeviceID:     job.deviceID,
        ChannelID:    job.channelID,
        // ... 其他字段
        ReceivedAt:   time.Now(),
    }
    m.dataBus.Publish(evt)  // 投递后立即返回，worker 可处理下一个
}
```

### 5.2 Worker pool 不再执行重型业务

重构前，worker 会执行协议解析、DB 操作和外部推送，可能长期占用 worker。当前 worker 在 Publish 后即可处理下一个 job；容量收益应由同环境基准测试量化，不在本文声明固定耗时或“不会积压”。

## 6. 消费者注册顺序

注册顺序不影响执行（各消费者并行），但影响日志可读性：

```go
// 在 NewManager 中初始化
m.dataBus = databus.NewDataEventBus()

// 6 个消费者按注册顺序（注册顺序不影响执行，各消费者并行）:
// 1. Terminal — 所有数据
m.dataBus.Register(databus.NewTerminalConsumer(m.termMgr))

// 2. WS Push — 仅被动数据，快速通道
m.dataBus.Register(databus.NewWSPushConsumer(wsHub))

// 3. DataMetrics — 调度报告计数
m.dataBus.Register(databus.NewDataMetricsConsumer())

// 4. PendingWrite — 命令响应路由
m.dataBus.Register(databus.NewPendingWriteConsumer(m.pendingWrite, m.deviceInit, db))

// 5. DB Persist — 原始数据持久化
m.dataBus.Register(databus.NewDBPersistConsumer(db))

// 6. Sensor Parser — 最重量级，最后注册
//    HA 和设备活动回调按运行环境可选注入；SensorParserConsumer 使用 CommandTemplateID
//    查询 ConfigTemplate.WriteData 做逐指令解析
m.dataBus.Register(databus.NewSensorParserConsumer(db, wsHub, ha, m.reassembler, optionalDeviceActivityCallback...))
```

### Register / Unregister

```go
// Register 注册消费者并启动其 persistent worker goroutine。
// 每个消费者获得一个 64 容量的独立 mailbox。
func (bus *DataEventBus) Register(c DataConsumer)

// Unregister 从注册表移除消费者并关闭该 worker 的 done 信号。
// mailbox 不关闭，因为 fanout 可能持有旧快照；worker 观察 done 后退出。
func (bus *DataEventBus) Unregister(name string)
```

## 7. SensorParserConsumer 的 data_update 问题

当前 `processDataReportJob` 在 `parseAndStoreData` 后将解析结果合并到 `channel_data` 事件中。新架构中 WS Push Consumer 和 Sensor Parser Consumer 是并行独立的，无法共享数据。

解决方案：**WS Push Consumer 只负责被动数据；Sensor Parser Consumer 在解析成功后同时推送兼容的 `channel_data` 和 `data_update`。**

当前两个 WS 事件的职责：
- `channel_data` — 被动数据由 WS Push Consumer 立即推原始 hex；调度采样/命令响应由 Sensor Parser Consumer 推原始 hex + 解析结果
- `data_update` — Sensor Parser Consumer 推送解析后的传感器值

因此消费者之间不共享可变解析结果，也不会为同一调度事件产生两次 `channel_data`。

## 8. 背压控制

```go
const dataChanBufferSize = 256  // 数据事件通道缓冲（dispatch 入口）
const consumerMailboxSize = 64  // 每消费者独立 mailbox（背压隔离）

func (bus *DataEventBus) Publish(evt DataEvent) {
    select {
    case bus.dataChan <- evt:
        // 正常入队
    default:
        // 通道满 — 丢弃最旧事件，保留最新
        select {
        case <-bus.dataChan:
        default:
        }
        bus.dropped.Add(1)
        bus.dataChan <- evt
    }
}
```

入口和每个消费者 mailbox 都采用非阻塞“丢旧保新”；具体实现还会检查 `stopCh`/worker `done`，保证 Stop/Unregister 后安全返回。实际 Prometheus 指标为 `ehome_data_event_bus_dropped_total`；内存计数可通过 `DroppedCount()` 读取。

## 9. 资源开销

| 组件 | 开销 |
|------|------|
| DataEventBus dispatch goroutine | 1 个 |
| 通道缓冲 (dataChan) | 256 个 `DataEvent` 槽位 |
| 每消费者 mailbox (6 个) | 每个 64 个 `DataEvent` 槽位 |
| 消费者 persistent worker | 6 个 goroutine（每消费者 1 个） |
| Terminal Consumer | 无额外资源（复用 termMgr） |
| WS Push Consumer | 无额外资源（复用 wsHub） |
| DataMetrics Consumer | 无额外资源（纯计数） |
| PendingWrite Consumer | 无额外资源（复用 pendingWrite） |
| DB Persist Consumer | 无额外资源（复用 db） |
| Sensor Parser Consumer | 无额外资源（复用 db/wsHub/ha） |
| 每事件 fanout | 6 个 mailbox 投递，各消费者独立背压 |

总增量的确定项是 7 个 goroutine（1 dispatch + 6 consumer workers）、256 个入口元素和 6×64 个 mailbox 元素。Go channel、goroutine stack、map/worker 控制对象和 `DataEvent.RawData` 所指向的底层字节不包含在简单的 `sizeof(DataEvent)` 估算内，因此不声明未经实测的固定 KB 总数。

## 10. 关键设计决策

1. **DataEvent 携带完整上下文**：包含 request_id / edge_device_id / error_code 等全部字段，消费者自行判断是否处理。生产者不做任何过滤。

2. **ShouldHandle 在 dispatch 中调用**：dispatch goroutine先判断事件类别，再把事件非阻塞投递到每个匹配消费者的独立 mailbox。每个消费者只有一个持久 worker，因此同一消费者内有序，不会按事件无限创建 goroutine。

3. **被动数据快速通道**：Terminal Consumer 处理所有事件；WS Push Consumer 仅处理 `IsPassive()`。被动数据只走这两个无 DB 操作的轻量消费者。

4. **消费者跨类型隔离、类型内串行**：不同消费者的持久 worker 可并行运行，慢 Sensor Parser 不阻塞被动 WS Push；同一消费者依次处理 mailbox，保持其事件顺序。

5. **保留 worker pool 做投递解耦**：上游 `dataCh` worker 把已解码的 `dataReportJob` 转换为 `DataEvent` 并立即 Publish；业务解析、DB、HA 和 WS 工作全部移到消费者。

6. **与 LogEventBus 架构一致**：相同的接口模式（Name/ShouldHandle/Handle）、相同的背压策略、相同的消费者隔离机制。后端形成统一的事件总线模式，降低维护成本。

7. **不改变 ESP32 协议和前端事件格式**：DataReport 0x03 帧不变，channel_data / data_update WebSocket 事件格式不变。纯后端内部重构。

8. **实现已完成**：当前六个消费者和生命周期/背压测试均已落地；本文不再作为渐进迁移计划。
