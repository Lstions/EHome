> **日期**: 2026-10-23
> **关联**: [概念模型.md](概念模型.md) | [边缘设备.md](边缘设备.md) | [功能需求总览.md](功能需求总览.md) | [术语表.md](术语表.md)

## 1. 需求与最终形态

用户的需求只有一条，原文语义是：**同一物理设备从节点 A 换到节点 B 后，历史数据不丢、连续可查**。

围绕这一条需求，本模块负责三件事：

1. **数据归属维度**：一条数据属于哪台设备（§2）。
2. **历史连续性**：设备换节点/被删/被重建之后，历史仍然查得到（§3）。
3. **数据处置**：保留多久、删除设备时数据怎么办（§4、§5）。

> **v3.5 变更（2026-10-23）**：本模块曾以「逻辑设备（LogicalDevice）身份层」为核心实现，
> 该概念层已**整体移除**（表、列、API、前端页、后台合并任务全部删除）。
> 移除理由与代价测算见 §6，**这是理解本文档其余部分的前提**。
> 决策与实施契约：`.contract/logical-device-removal.md`；
> 评估报告：[../分析/逻辑设备-业务逻辑与需求偏差评估-2026-10-23.md](../分析/逻辑设备-业务逻辑与需求偏差评估-2026-10-23.md)。

## 2. 数据维度：只有边缘设备一个 id 空间

```text
unified_data.device_id  =  edge_devices.id     （解析后的时序数据）
device_data.device_id   =  edge_devices.id     （原始字节审计数据）
```

**只有这一个维度。** 没有第二套 id，没有「血缘列 vs 归属列」的区分，没有列间映射。

关键事实（2026-10-23 起）：

- 写入路径**不做任何身份解析**：`databus` 拿到设备行后直接写 `device.ID`。
  逻辑设备层存在时这里每帧有一次「沿合并链解析最终目标」的 SQL 往返，现已删除。
- 读取路径一律 `WHERE device_id = ?` 等值条件。没有 scope 解析、没有 OR 兜底、
  没有保形去重 —— 三者都是逻辑身份层的产物（§6.3）。
- `unified_data.edge_device_id` 列是 v2.2 遗留的**空列**（写入路径从未填过，
  生产实测全表 NULL，见 DS-14 勘误）。新代码一律使用 `device_id`，禁止使用该列。

### 2.1 为什么不做两套 id

评估报告 §4 的实测给出了直接答案：两套 id 之间来回映射，会让读路径不得不写
「归属 id IN (...) OR (归属 id IS NULL AND 血缘 id IN (...))」这种兜底条件；
PostgreSQL 规划器对这种 OR 形态**无法使用任何前导列索引**，退化为全分区扫。
同一系统、同一需求、只把条件换成等价 UNION ALL，实测从 **26.9–32.3 s** 降到
**0.644–5.6 ms**（同一会话紧随其后各跑一次，报告 §4.2）。

排序最后落在「一个维度」上，不是简化偏好，而是性能与可验证性的直接结果。

## 3. 历史连续性：三条路径

用户真正要的那条需求，在设备维度下有三条**互不重叠**的实现路径。
选择哪条取决于「设备行还是不是同一条」。

### 3.1 路径①：原地换节点（主路径）

```http
PUT /api/v1/edge-devices/:id
{ "node_id": "<新节点>", "channel_id": <新节点下的通道> }
```

**语义**：同一条 `edge_devices` 行改 `node_id` / `channel_id`，**行 id 不变**。
因为 `unified_data.device_id` 指向的正是这个 id，历史**天然连续**——
不需要迁移任何数据，也不需要查询层做特殊处理。

**校验**（与创建路径同一套，见 [边缘设备.md](边缘设备.md) §2.1）：

- 新通道必须属于新节点（`WHERE id = ? AND node_id = ?`，事务内行锁）；
- 传输通道门禁 `validateTransportChannel`：通道 enabled、非 GPIO/PWM 外设、
  `hardware_type == bus_type`；
- `device_config` 与通道硬件类型兼容；驱动声明的 `HardwareTypes()` 必须覆盖通道总线；
- 命令容量门禁 `validateCommandCapacityForDevice`：设备的 `command_intervals` 不得超过
  目标节点申报的每设备轮询上限（否则该节点**整份** ConfigManifest 会被拒发）；
- 三元唯一性守卫 `checkDeviceUniqueness(channel_id, type, hardware_id, excludeID=自身)`
  —— 换绑后不能与同通道同型号同地址的另一台设备冲突；
- 若同时改 `hardware_id` 或 `type`，地址门禁 `validateEdgeDeviceAddress` 生效。

**换绑时的运行时复位**（2026-10-25）：`status=pending`、清 `error_code/last_error`、
`init_state/init_last_step/init_total_steps` 复位、清 `last_data_at` 与 `config_version`，
并清 deviceinit 进程内缓存（缓存以 `edge_devices.id` 为键；不清的话新节点上的
自动初始化会被以「already completed」拒绝，校准流程不执行）。

**这是首选路径**：它一步完成、零数据移动、零幂等负担。
「同一台物理设备换了个插口」在业务上就是这件事。

### 3.2 路径②：恢复已删除设备

适用于「设备行被删了（换线/重装/误删），但物理设备还是那台」的场景。

```http
GET  /api/v1/edge-devices/deleted
POST /api/v1/edge-devices/:id/restore
{ "node_id": "<新节点>", "channel_id": <通道>, "name": "可选", "interval_ms": 可选 }
```

**语义**：清除 `deleted_at` + 改绑节点/通道。因为 `device_id` 不变，
历史数据自动连续 —— 与路径①同样是「复用同一条行」。

**列表端点** `GET /edge-devices/deleted?page=&page_size=` 返回
`{items,total,page,page_size}`，每项字段：
`id / name / type / device_type / hardware_id / node_id / channel_id / last_data_at /
deleted_at / row_estimate / data_purge_requested / purge_in_progress / purge_started_at?`，
按 `deleted_at DESC` 排序，默认 50 条/页（上限 200）。`row_estimate` 是数据量**估算**
（超时或失败时**省略该字段**，不阻塞列表）；整个列表共用一个估算截止时间。

**校验**（2026-10-25 与 create/update 对齐）：

- 目标必须处于软删状态，否则 **409**（避免把「恢复」当成「改绑定」的后门）；
- 节点不存在 → 404；设备已硬删/不存在 → 404；通道不属于该节点 → 409；
- 传输通道门禁（enabled / 非 GPIO-PWM 外设 / `hardware_type==bus_type`）、
  `device_config` 兼容、驱动 `HardwareTypes()` 覆盖通道 → 400；
- 地址门禁：历史行可能带非法地址（如把总线名当从站地址），此时可在请求体带
  `hardware_id` 一并修正；否则 400 并提示；
- 命令容量门禁：`command_intervals` 不得超过目标节点申报的每设备上限；
- 三元唯一性守卫（同上，`excludeID` = 自身）；冲突文案引导「合并历史」；
- **purge 互斥**：`data_purge_started_at` 非空（清理任务已认领）→ 409。清理开始后
  删除不可撤销，恢复不能制造「恢复了但数据已被删一半」的假象；
- 恢复时按驱动**幂等**补齐 ConfigTemplate（`ensureTemplatesFromDriver` 按
  `(node_id, write_data, read_length)` 复用；旧实现无条件新建会导致模板配额泄漏、
  最终整节点 config sync 被拒）。

**复活语义**：清 `data_purge_requested` / `data_purge_started_at`、`status=pending`、
清错误、`init_*` 复位、`enabled=true`、`last_data_at=NULL`、清 `config_version`，
并清 deviceinit 进程内缓存（否则新节点不重新 init/校准）。

## 3.3 路径③：合并历史数据

适用于「历史上有过多次 `edge_devices` 行；旧 id 的数据已没有 API 能查到」的场景。
这是**唯一会移动数据的路径**。

```http
GET  /api/v1/edge-devices/:id/data-summary?source_ids=1,2
POST /api/v1/edge-devices/:id/merge-history
{ "source_ids": [1, 2] }
```

**`data-summary`**（合并前的数据量估算，也可用于删除确认弹窗）：
对 `:id` 与每个 `source_ids` 成员各返回一项
`{source_id, device_name, rows, first_time, last_time}`；
`rows` 是估算（超时则省略），`first_time`/`last_time` 是两表合并后的真实时间范围。
`:id` 允许是已软删设备（用 `Unscoped` 只做存在性判断）。

**`merge-history` 语义**（2026-10-25 修订，权威定义见
[.contract/logical-device-removal.md](../../.contract/logical-device-removal.md) §14.2）：

    -- 对 unified_data 与 device_data 各执行，分批（每批独立事务 + 批间 sleep）
    UPDATE <table> SET device_id = :target
     WHERE id IN (SELECT id FROM <table> WHERE device_id IN (:sources) LIMIT :batch)

- **分批**：PG 每批 10000 行 / 非 PG 1000 行；每批**独立事务** + 批间 sleep，
  避免长事务持锁、放大 WAL（与 retention / purge 同一套大表写入纪律）；
- **幂等**：源设备已无那些行时，第二次调用返回 `rows_migrated = 0`；
- **目标必须存活**：软删设备不能作为合并目标（并进去等于埋掉数据）→ 404；
- **源准入（2026-10-25 产品重做后的核心不变量）：只能合并「已删除 + 与目标同型号」的设备**
  （产品设计：[docs/分析/合并历史-产品设计重做-2026-10-25.md](../分析/合并历史-产品设计重做-2026-10-25.md)）：
  - 源 = 目标 → **400**（不再静默忽略）；
  - 源 id 不存在（无设备行）→ **400**：无法验证型号，「同型号」不变量不可证；
    不再做孤儿数据救援（这类数据只受系统级保留期约束）；
  - 源仍在役 → **409**：在役设备的历史被搬走会变成空壳、之后新数据仍归它自己，
    历史永久分裂。要收尾先删除该设备（保留数据）再合并；只是换位置用路径①；
  - 源型号（`type`）与目标不一致 → **400** 并列出双方型号：不同型号的驱动/字段集合/
    单位/解析语义不同，合并会污染数据语义。**不再有** `allow_live_source` / 自动退役；
- **与 purge 互斥**：源已被 purge 认领 → 409；源只是「请求删数据」尚未认领 → 先撤回
  删除意图（与 restore 同语义）再迁移；
- 迁移四张表：`unified_data`、`device_data`、`sensor_field_obs`、`data_sources`；
  台账按**源逐个**迁移（多源同名不会撞 `(device_id, sensor_name)` 复合主键）；
  `data_sources.managed_by=manual` 行与目标冲突时保留在源设备上并返回 warning；
- 合并后回写目标 `last_data_at`；台账迁移失败 → 200 + `warnings`（可重试补齐）；
- 响应 `{rows_migrated, sources:[{id,state:"deleted",device_type}], warnings?}`；
- `data-summary` 响应拆成 `target` / `sources` / `target_rows` / `source_rows` 四块
  （item 带 `device_type`，供前端同型号校验/展示）；`source_rows` 只含源
  （合并预览的「预计迁移」读它）。旧 `items`/`total_rows` 已删除；
- `GET /edge-devices/deleted` 支持 `device_type` 过滤（合并弹窗只列同型号已删除设备）。

> **注意**：这是「搬走」不是「复制」。合并后源设备侧不再有那些行。
> 若用户只是想换个节点，应当走路径①而不是路径③。

### 3.4 三条路径怎么选

| 场景 | 设备行还在吗 | 用哪条 |
|---|---|---|
| 同一台物理设备换到另一个节点/插口 | 在（同一条行） | **路径①** 原地换节点 |
| 设备行被删了（换线/重装/误删），物理设备仍是那台 | 软删行还在 | **路径②** 恢复 |
| 历史上有多条设备行，旧 id 的数据要并到当前在役行 | 旧行可能已不存在 | **路径③** 合并历史 |

## 4. 保留期：系统级单一窗口

```text
EHOME_DATA_RETENTION_DAYS（config.yaml: data_retention.days）
  默认 90 天；非正值被忽略；运行期快照在 datalifecycle.SystemRetentionDays()
```

**只有一个窗口，全库统一。** 没有 per-device 保留期，没有「按身份配置」，
也没有 30/7 天两档临期通知（三者都随逻辑身份层移除，见 §6.2）。

每日 retention 任务（`datalifecycle.RetentionTask`）的执行顺序：

1. **按月 DROP 分区**（PG 分区表 `unified_data` / `device_data`）：
   只有当一个分区的**最后一天**都已早于 cutoff 时才删（`PartitionManager.DropPartitionsBeforeFor`
   按分区上界判断）。分区 DROP 是整月粒度、不可分割的全局操作。
2. **按 timestamp 精确分批 DELETE**：边界分区里存在「整月未到期但单行已过期」的数据，
   用 `WHERE timestamp < cutoff` 精确删除，每批独立事务 + 批间 sleep。
3. **旁路清理器**：notifications / notification_deliveries / automation_events（分层
   30/400 天）/ 命令域三表（executions、outboxes 30 天、attempts 730 天）/
   security_audit_events（730 天）/ node_events（400 天）。
   它们与本任务**同频、同一调用点**，各自独立失败、失败只告警，
   **绝不影响数据保留期主流程**。

> 分区清扫失败不得中断精确 DELETE（只记指标 + 日志后继续）。
> 非 PG / 未分区时分区清扫整体 no-op，精确 DELETE 是 SQLite 主路径。

## 5. 删除语义

### 5.1 两种删除

```http
DELETE /api/v1/edge-devices/:id?delete_data=false   # 默认：只软删
DELETE /api/v1/edge-devices/:id?delete_data=true    # 软删 + 请求硬删数据
```

- **`delete_data=false`（默认）**：GORM 软删（`deleted_at` 置位），
  **数据全部保留**，受系统级保留期约束（§4）。已删设备的数据仍可通过
  `GET /edge-devices/:id/data`、`GET /unified-data/*` 读到（§5.4）。
- **`delete_data=true`**：软删 + `edge_devices.data_purge_requested = true`。
  数据不在 API 事务内删除，交由后台 `DevicePurger` 异步分批硬删（§5.2）。

历史设备的「彻底删除」走 `POST /edge-devices/deleted/batch-delete`：只接受已软删设备，置
`data_purge_requested=true` 后**立即 Wake DevicePurger**（否则最长等 24h），由后台分批硬删
设备行与四张数据表，**开始后不可恢复**；不提供"只删记录保留数据"。

批量删除 `POST /edge-devices/batch-delete` 逐条复用单删事务（≤100 条），
每项同样可选 `delete_data`，返回 `{ total, succeeded, failed, results[] }`。

### 5.2 后台硬删：DevicePurger

    datalifecycle.DevicePurger
      首次运行：启动后 30s（让刚请求的 purge 不必等满一天）
      之后：每 24h
      扫描：Unscoped WHERE data_purge_requested = TRUE AND data_purge_started_at IS NULL

**与恢复的互斥协议**（2026-10-25 重写；旧实现只按扫描时的内存快照判断「是否复活」，
用户在 purge 运行期间恢复设备时，恢复返回 200 但 purge 仍会把历史与设备行硬删 —— 
不可恢复的数据丢失，runtime 实测复现）：

1. **原子认领**：`UPDATE edge_devices SET data_purge_started_at=now()`，条件为
   「仍软删 + 仍请求删数据 + 尚未认领」；RowsAffected=0 ⇒ 本轮不处理（可能已被恢复）。
2. **restore 行锁互斥**：restore 在事务里对同一行加行锁并检查认领，已认领 ⇒ 409
   （清理开始后删除不可撤销，不允许制造「恢复了但数据被删一半」的假象）。
3. **每轮只清陈旧认领**（早于 1 小时）：避免多实例/滚动发布清掉另一进程在途 claim。
   部署前提：DevicePurger 单实例运行。
4. **分批硬删**两表该设备的全部行（PG 1 万/批、非 PG 1 千/批，
   `DELETE ... WHERE id IN (SELECT id ... LIMIT ?)` 在两方言上都是确定性切片）。
5. **连带清理** `sensor_field_obs` / `data_sources` / `calibration_cache`（数据已清除，
   台账/字段目录/校准都不应再指向已硬删设备）。
6. **条件删除设备行**（`deleted_at IS NOT NULL AND data_purge_started_at IS NOT NULL`）；
   RowsAffected=0 视为 `abandoned_revived`，不谎报成功。
7. 失败路径释放认领并记录 error 日志（下一轮重试）。

每次运行返回逐设备结果 `{edge_device_id, outcome, rows_deleted, error}`，
`outcome` ∈ `purged` / `abandoned_revived` / `failed`。

### 5.3 删除时连带清理 ConfigTemplate

删除设备时 `handleConfigTemplateOnDelete` 处理模板归属：
查 `edge_device_id = :id` 的模板 → 引用检查（同通道仍有存活同型号设备则保留）→
无引用则从 `channel.template_ids` 移除并删除 ConfigTemplate 行。

防的是 ESP32 `maxTemplates = 16` 溢出（累积孤儿模板会导致 ConfigManifest 被节点拒收）。
`edge_device_id IS NULL` 的旧模板（multi-drop 共享池 / 自愈创建）**不在删除时动**，
宁留勿删。

### 5.4 软删设备的数据仍可读

这是产品语义的一部分，不是实现细节：**历史不该因为设备行被软删就消失**。

| 端点类型 | 对已软删设备 |
|---|---|
| `GET /edge-devices/:id/data` | **可读**（按 `device_id` 等值查询，不看 `deleted_at`） |
| `GET /unified-data/*` | **可读** |
| `GET /edge-devices/:id/latest-data`、`/latest-values` | **可读** |
| `GET /edge-devices/:id`（配置类） | **404** |

### 5.5 孤儿数据：`device_data` 里 `device_id = 0` 的行

`DBPersistConsumer`（原始字节审计写入者）历史上只写 `node_id`，不写 `device_id`。
生产实测该表约 168 万行 `device_id = 0`（报告 §4.4 复核）。

这些行**不属于任何设备**，因此：

- 按设备维度查不到它们（这是诚实的：它们本来就没有设备归属）；
- `delete_data=true` 的 purge 也不会删它们（按 `device_id` 匹配，0 不匹配任何设备）；
- 它们只受系统级保留期约束（§4 的精确 DELETE 按 `timestamp`，与 `device_id` 无关）。

## 6. 为什么没有逻辑设备层

### 6.1 原始需求只有一条

用户原话的语义是「同一物理设备从节点 A 换到节点 B 后，历史数据不丢、连续可查」。
**能力层面，路径①（原地换节点）单独就能满足它** —— 评估报告 §5.3 在本机实测过：
`PUT /edge-devices/1 {node_id: 新节点, channel_id: 新节点通道}` → 200，
`node_id` 改变、历史 175,620 点连续可查（首点 2026-09-20T08:18:24Z，末点 2026-10-01T06:56:53Z）。

### 6.2 它被实现成了什么

为了这一条需求，历史上实现了一个完整的概念层：

| 机制 | 说明 |
|---|---|
| 身份层 `logical_devices` 表 | `identity_key = type:hardware_id`（空地址时 uuid v5 派生） |
| 三路径复用策略 | 启动 / 创建新 / 删除补建，各自维护「一逻辑设备至多一个存活实例」 |
| 合并链 `merged_into` | 自引用追溯链，查询时 `followMergeChain`（内存 8 跳 / DB 16 跳两套上限） |
| 合并搬迁 worker | `merge_jobs` + `backfill_jobs` 水位表 + pending 窗口 + 保形去重（重叠时段保留 `MAX(id)`） |
| 三方 id 空间映射 | `edge_devices.logical_device_id`、`unified_data.logical_device_id`、`device_data.logical_device_id` |
| 查询作用域 | `ResolveDataQueryScope` + OR 兜底 + `ApplyShapeDedup` |
| per-identity 保留期 | 每个逻辑设备快照自己的 `retention_days` + 30/7 天两档临期通知 |
| purge 三层守卫 | 按逻辑设备的 purge 标记 + 合并中/已合并/purge 中的 409 门控 |

### 6.3 代价（全部为实测，非估算）

**a) 查询索引失效**。OR 兜底条件让规划器放弃前导列索引：

| 查询形态 | 计划 | 实测 |
|---|---|---|
| 现设计 OR | `Index Scan Backward` + Filter；Rows Removed by Filter 2,931 万–2,937 万；Buffers hit≈102 万 | **26.9–32.3 s**（三次采样 26,932 / 32,087 / 32,260 ms） |
| 等价 UNION ALL | 两分支各走索引 | **0.644 / 4.017 / 5.6 ms** ⇒ 差 3 个数量级 |

**b) 成本与数据量反相关**。「已停写的老设备」最贵 —— 而「换节点后旧实例停写」
恰恰是这条需求要服务的必经状态：

| 逻辑设备 | 行数 | 最后一包数据 | OR 边界查询 |
|---|---|---|---|
| ld=14 | 2,782 万 | 2026-10-23（持续写入） | 0.70–1.38 ms |
| ld=2 | 292 万 | 2026-10-04（已停写） | **36.8 s** |
| ld=13 | 1.4 万 | 2026-10-05（已停写） | **36.3–44.9 s** |

**c) 管理端点不可用**。`GET /api/v1/logical-devices`（当时 16 行数据）生产实测
**94–131 秒**（13 次采样）；前端把超时放宽到 60 s，而 60 s < 94 s ⇒ 兜底本身已失效。

**d) 数据变成孤儿**。生产 16 条逻辑设备里 **13 条没有存活实例**，其中 3 条合计
**314 万行**（ld=2 持 292.3 万 / ld=12 持 20.5 万 / ld=13 持 1.4 万）
**没有任何 API 能读到**，而 retention 仍会按它们的保留期从 2026-12-31 起逐日硬删。

**e) 兜底分支恒不命中**。为一条永不命中的兼容分支，6 条读路径继承了 O(n) 扫描：

| 表 | `logical_device_id IS NULL` | 兜底条件实际命中 |
|---|---|---|
| unified_data | 0 / 3,240 万 | 0 |
| device_data | 1,686,105 / 300 万 | **0**（全是 `device_id = 0`，不属于任何实例） |

### 6.4 结论与执行

**这层身份没有自己的读入口**，也没解决用户的原痛点，只是把它挪到了另一组 id 上。
2026-10-23 按产品裁决**整体移除**，改为设备维度 + 三条路径（§3）。

实际删除范围：

- 表 3 张：`logical_devices` / `merge_jobs` / `backfill_jobs`；
- 4 张表的逻辑身份列：`edge_devices.logical_device_id`、
  `unified_data.logical_device_id`（父表 + 全部分区）、
  `device_data.logical_device_id`（同上）、`data_sources.device_id`；
- `datalifecycle` 10 个文件（identity / merge / merge_chain / preview / purge /
  scope / query_scope / migrate / backfill / indexes）；
- `api` 层 7 个文件：`handler_logical_device.go` / `scope_union.go` /
  `handler_edge_device_candidates.go` 及其 4 个测试文件；
- 前端 1 页（`views/logical-device/`）+ 1 API 模块 + 1 候选组件。

新增能力：原地换节点开放（前端编辑对话框）、`/edge-devices/deleted`、
`/:id/restore`、`/:id/merge-history`、`/:id/data-summary`、`DevicePurger`、
`edge_devices.data_purge_requested` 列。

### 6.5 数据迁移

`ehomectl retire-logical-device`（`database.RetireLogicalDeviceLayer`）：

- **幂等**：所有步骤用 `HasTable` / `HasColumn` / `IF EXISTS` 判定，重跑零副作用；
- **先删索引再删列**：PG 拒绝删除仍被索引引用的列；分区表上索引存在于**每个子分区**
  （必须先 DROP 父索引，子索引随之消失），枚举用 `pg_inherits` 递归；
- **不用 CASCADE**：CASCADE 会连带删除任何对该列有依赖的对象，误伤面不可控，
  且 SQLite 不支持该语法 —— 改为显式枚举 + 逐个 DROP，每步写日志；
- 每步先数行数/非空行数留痕再删。

**验证结果**（在 dev 库副本 `ehome_verify` 上实跑，两遍）：

| 项 | 结果 |
|---|---|
| 第二遍 `rows touched` | **0**（幂等） |
| 迁移后 `logical_device_id` 列 | **0 个** |
| 迁移后三张表 | **0 张** |
| `unified_data` 行数 | 179,532（保留） |
| `device_data` 行数 | 568,617（保留） |
| `edge_devices` 行数 | 2（保留） |

> **生产迁移需要维护窗口**执行 `ehomectl retire-logical-device`（DDL 会取得
> 排他锁）。本模块的自动化验收只覆盖 dev 库副本。

## 7. API 摘要

| 端点 | 方法 | 用途 |
|---|---|---|
| `/edge-devices/:id` | PUT | **换节点/通道**（路径①，主路径） |
| `/edge-devices/deleted` | GET | 已删除设备列表（路径②入口） |
| `/edge-devices/:id/restore` | POST | 恢复已删除设备并改绑（路径②） |
| `/edge-devices/:id/data-summary` | GET | 数据量/时间范围估算（删除确认 + 合并前） |
| `/edge-devices/:id/merge-history` | POST | 合并历史数据（路径③，分批+幂等） |
| `/edge-devices/:id` | DELETE | 删除（`?delete_data=` 可选） |
| `/edge-devices/batch-delete` | POST | 批量删除（≤100） |
| `/edge-devices/batch-update` | POST | 批量启用/停用/设置采集间隔（≤100） |
| `/edge-devices/deleted/batch-delete` | POST | 历史设备彻底删除（入清理队列） |

> 2026-10-25 起：`data-summary` 响应为 `{target,sources,target_rows,source_rows}`
> （item 带 `device_type`）；`deleted` 支持 `page/page_size` 与 `device_type` 过滤，
> 并返回 purge 状态字段；`merge-history` **只接受「已删除 + 与目标同型号」的源**（在役 409 /
> 跨型号 400 / 无设备行 400），响应含 `sources[].state/device_type`、`warnings`
> （详见 [.contract/logical-device-removal.md](../../.contract/logical-device-removal.md) §14.2）。

> **已删除**：`/logical-devices` 全族（含 `/merge`、`/merge/preview`、
> `/merge-jobs/:id`）、`/edge-devices/candidates`、
> `/edge-devices/:id/logical-device-info`。前两者随逻辑身份层移除，
> 后两者（候选发现与逻辑设备信息区）是它的查询面，一并删除。

## 9. 验收标准

### 9.1 效果层（必须全部为实测证据）

- [x] **换节点**：`PUT /edge-devices/2 {node_id, channel_id}` → 200；
      `unified_data` 3,912 行不变；历史端点仍返回数据。
- [x] **合并历史**：`POST /edge-devices/1/merge-history {source_ids:[2]}` →
      `rows_migrated = 4238`，源侧清零；**再调一次 → 0 行**（幂等）。
- [x] **删除 + 恢复**：`DELETE /edge-devices/3` → 200（`data_purge_requested=false`）；
      `GET /edge-devices/deleted` 列出该设备（`row_estimate=20`）；
      `POST /edge-devices/3/restore {node_id, channel_id}` → 200 且 `deleted_at` 清空；
      对存活设备再调 restore → **409**。
- [x] **数据量估算**：`GET /edge-devices/:id/data-summary` 返回
      `source_id/device_name/rows/first_time/last_time`，
      `first_time` ≈ 2026-09-20、`last_time` ≈ 2026-10-01（真实时间范围，非 null）。
- [x] **旧端点消失**：`GET /logical-devices` → **404**。
- [x] **迁移幂等**：dev 库副本跑两遍，第二遍 `rows touched = 0`；
      迁移后逻辑身份列 0 个、三张表 0 张，三张数据表行数全部保留（§6.5）。
- [x] **门禁**：`go build ./...` / `go vet ./...` / `go vet -tags=simulation ./...` 均 0 error；
      `go test ./...` 全绿。

### 9.2 契约层

- [x] `unified_data` / `device_data` 写入不含任何身份解析（无 `ResolveMergeTarget` 往返）。
- [x] 读路径一律 `WHERE device_id = ?`，无 scope 解析 / OR 兜底 / 保形去重。
- [x] 软删设备的数据端点可读、配置端点 404。
- [x] `data_purge_requested` 复活守卫 + **认领协议**（恢复后 purge 撤回；purge 运行期间
      恢复返回 409 或 purge 认领失败后放弃，不再出现「恢复后仍被硬删」）。
- [x] **二审回归（2026-10-25）**：restore 传输通道/驱动总线/容量门禁与状态复位；
      merge 存活源 409、源不存在 400、多源同名台账可迁移、purge 互斥、manual 数据源
      保留；data-summary 目标/源分组；purge 台账清理；离线判定按 `max(created_at, updated_at)` 计时。
- [x] 保留期只有系统级单一窗口，无 per-device 配置、无临期通知。

## 10. 已知限制与债务

| 限制/债务 | 说明 |
|---|---|
| `calibration_cache` 无软删 + 唯一索引 | `idx_calibration_edge_kind` 会阻塞同型号设备重建（配置走 CalibrationAwareDriver 者缺校准即拒收样本）。已知问题，删除确认对话框提示；purge 时会清理该设备的校准行 |
| `config_templates` 孤儿不回收 | 累积超 ESP32 16 模板上限会致 ConfigManifest rejected → 需 SQL 清理（运维手册条目）。删除路径会尽量回收归属明确的模板（§5.3） |
| `device_data.device_id = 0` 的行 | 约 168 万行历史遗留（`DBPersistConsumer` 只写 node_id）。不属于任何设备，按设备维度查不到，不受 purge 影响，只受系统级保留期约束（§5.5）。是否回填归属**未裁决** |
| 合并历史是搬走不是复制 | 若用户想要「两边都留」的语义，当前实现不支持（也不应该：那会产生重复数据）。文档 §3.3 已明示，前端文案需一致 |
| 生产迁移需维护窗口 | DDL 取排他锁；自动化验收只覆盖 dev 库副本（§6.5） |
| merge-history 是同步长请求 | 百万行级合并可能跑数分钟（分批 + 批间 sleep），无进度接口/后台任务；请求上下文可取消（客户端断开即中止，已提交批次幂等可重试）。前端需提示「数据量大时耗时较长」 |
| DevicePurger 单实例前提 | 认领协议使用 `data_purge_started_at` 列 + 每轮清理 >1h 的陈旧认领；多实例并行 purge 需要租约/心跳改造（当前部署形态为单实例） |
| merge 的 manual 数据源冲突 | 源设备人工 data_sources 行与目标同 category 时保留在源设备并返回 warning（不静默删除，也不自动合并人工配置） |
