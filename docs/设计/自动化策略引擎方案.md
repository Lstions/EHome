## 1. 背景与需求

### 1.1 问题陈述

当前系统的数据流是**单向开口**的：

```
ESP32 采集 → 后端解析/入库 → 前端展示/告警通知
```

控制流是**纯人工**的：

```
用户 → DeviceControlPanel → 受控操作 (confirm → create → dispatch → verify)
```

两条链路之间没有自动化粘合层。实际场景需求（均来自真实使用语境）：

| # | 场景 | 触发源 | 期望动作 | 安全等级 |
|---|------|--------|----------|----------|
| S1 | 光照弱（黄昏/阴天）自动开灯 | 光照传感器 `illuminance` | GPIO 输出高电平（继电器） | 低 |
| S2 | 夜间光伏无法发电 | 时间窗口 / `pv1_power` < 阈值持续 N 分钟 | 关闭 BMS 充电 MOS（`set_mos_policy`） | 高 |
| S3 | 电池 SOC 过低 | `soc` < 阈值 | 断开负载 GPIO + 发通知 | 中 |
| S4 | 温度过高 | `temperature` > 阈值 | 停止充电 + 告警 | 高 |
| S5 | 无人值守时段异常 | 时间窗口 + 任意传感器越限 | 仅通知（不动作） | 低 |

这些场景的共同结构是 **触发器（Trigger）→ 条件（Condition）→ 动作（Action）**，即经典的 ECA（Event-Condition-Action）规则模型。

### 1.2 现有设施盘点（源码核实）

| 设施 | 位置 | 能力 | 缺口 |
|------|------|------|------|
| 阈值告警引擎 | `backend/internal/alert/evaluator.go` | 滑动窗口 + 连续满足判定 + firing/resolved 状态机 + 静默抑制 | **只通知，不执行动作**；仅单传感器单阈值比较 |
| 告警规则模型 | `backend/internal/models/alert.go` | `AlertRule{TargetType, SensorName, Comparator, Threshold, DurationSec, SilenceSec, Level, Enabled}` | 无 action 字段，无复合条件，无时间窗口触发 |
| 受控操作目录 | `backend/internal/deviceaction/definition.go` + `commandexec/service.go` | Catalog/Create/VerifyFinal 全链路；bounded_sequence 多步计划；幂等（IdempotencyKey）；9 项 availability gate（dispatch_enabled/action_enabled/current_engine/edge_enabled/edge_status/edge_node_id/node_status/action_channel/reported_action_channel/applied_manifest/current_capabilities/definition_fits_capabilities） | 仅人工触发（`ActorUserID` 为登录用户），无系统 actor |
| GPIO 直控 | `backend/internal/api/handler_periph.go:525` `POST /nodes/:id/gpio/:pin/set` | PeriphCmd 0x1B 即时下发 | 无幂等记录、无审计，不适合策略直接调用裸 handler |
| 数据解析后回调 | `backend/internal/databus/consumers_heavy.go:147` `SetAlertSink` | 解析成功即回调 `alertSink(deviceID, fields, now)`，复用解析结果零重复开销 | 目前仅接 alert.Evaluator，可加挂策略求值器 |
| 通知中心 | `models.Notification` + WS `notification` 事件 | 告警/事件通知落库 + 实时广播 | 可作为策略动作的一种类型 |

**核心结论**：触发求值侧（滑动窗口/状态机）与动作执行侧（Catalog/Confirmation/Dispatcher/Verifier）都已存在且经过 fail-closed 打磨。**缺的是中间的"策略编排层"——把触发事件映射到动作调用，并以系统身份走完整安全门控。**

## 2. 目标与非目标

### 2.1 目标

1. **统一策略模型**：一个 `AutomationRule` 实体覆盖"传感器阈值→动作""时间窗口→动作""复合条件→动作"三类场景，不另起第二套规则引擎。
2. **复用现有求值器**：`alert.Evaluator` 扩展为通用触发求值器（trigger evaluator），告警规则是其"动作=发通知"的特化。
3. **动作一律走受控操作链路**：策略执行设备动作时**必须**复用 `commandexec.Service.Create`，经过全部 9 项 availability gate + 幂等 + 审计 + verify，**禁止**策略引擎直接调 `SendPeriphCmd` 或裸 MQTT 下发。
4. **系统身份可审计**：策略触发的执行在 `command_executions` 中有明确的 `actor` 标识（系统 actor），与人工操作可区分、可归因。
5. **fail-closed 与防抖**：节点离线、能力过期、动作不可用时策略**不执行**（不发半成品命令）；连续触发须有静默/冷却机制防震荡（如光照在阈值附近抖动导致灯频繁开关）。
6. **前端可观测**：策略规则 CRUD、触发历史、执行历史在 UI 可见；策略触发与人工操作在历史列表中可区分。

### 2.2 非目标

1. **不做边缘侧自治**：策略求值在后端进行，不下发到 ESP32。理由：ESP32 资源有限，策略语义在后端可审计可修订；边缘自治（断网兜底）作为后续演进，本期不做。
2. **不做脚本化/任意表达式**：条件仅支持声明式比较（gt/gte/lt/lte/eq/neq + 复合 AND），不支持用户自定义 JS/Lua。与 deviceaction"受限声明式子集"哲学一致。
3. **不做跨设备联动编排**（M:N 场景：多传感器融合决策控制多设备）：本期动作目标为单一设备/引脚；跨设备场景由多条独立规则实现，不引入 workflow 引擎。
4. **不改变告警语义**：`alert_rules` 存量行为不变；策略引擎是增量，不重构告警。
5. **不做定时采样调度**：策略触发是数据到达驱动（event-driven），不引入 cron 式主动轮询（时间窗口触发除外，见 §3.3）。

**关键设计决策**：

- **求值器与告警并列而非合并**：`alert.Evaluator` 语义是"阈值越限→通知"，`AutomationEvaluator` 语义是"条件满足→决策是否执行动作"。两者共享滑动窗口原语（可提取公共 `window` 包）但状态机语义不同——告警有 firing/resolved 双态通知，策略有"触发→执行→冷却"三态。合并会让 alert 规则背上 action 语义包袱。
- **动作执行唯一入口 = `commandexec.Service.Create`**：策略引擎不持有 dispatcher、不持有 MQTT client、不构造物理帧。所有安全门控（能力新鲜度、通道、manifest、节点在线）由既有链路保证，策略层**零绕行**。
- **GPIO 动作不直连 PeriphCmd**：当前 `handler_periph.go` 的 GPIO set 是裸下发（无 CommandExecution 记录）。策略控制 GPIO 时**必须**先为 GPIO 建立 deviceaction 定义（`gpio_set` / `gpio_reset`，Transport=`periph_cmd`），让 GPIO 也走 CommandExecution 链路。这是本方案对既有设施**唯一的前置改造需求**（见 §8 实施记录）。

### 3.2 策略规则模型（ECA 结构）

一条策略规则 = 1 个触发器 + 0..N 个附加条件（AND）+ 1 个动作 + 执行约束。

```go
// models.AutomationRule（示意，最终以实现为准）
type AutomationRule struct {
    ID          uint
    Name        string
    Enabled     bool

    // ── Trigger（恰好一个）──
    TriggerType string // sensor_threshold | time_window | event
    // sensor_threshold: 复用 alert 的滑动窗口语义
    TriggerSensorName  string  // 与 parser.Field.Name 同域, 如 "illuminance" / "pv1_power" / "soc"
    TriggerComparator  string  // gt|gte|lt|lte|eq|neq
    TriggerThreshold   float64
    TriggerDurationSec int     // 连续满足时长, 防抖第一层
    // time_window: 每天 HH:MM 进入/离开窗口, 由 1min ticker 驱动
    TriggerWindowStart string  // "18:30"
    TriggerWindowEnd   string  // "06:30"
    TriggerWindowEdge  string  // enter|exit|inside

    // ── Conditions（全部 AND, 可为空）──
    ConditionsJSON string // []Condition{SourceType(edge_device_self|time|node_status), SensorName, Comparator, Threshold}

    // ── Action（恰好一个）──
    ActionType       string // device_action | notification
    ActionDeviceID   uint   // 目标边缘设备 (device_action)
    ActionID         string // deviceaction.Definition.ID, 如 "set_mos_policy" / "gpio_set"
    ActionParamsJSON string // 动作参数, 如 {"charge_mos":0,"discharge_mos":1}
    ActionLevel      string // notification 级别 (notification)

    // ── 执行约束 ──
    CooldownSec     int  // 冷却期: 上次执行后 N 秒内不再触发 (防抖第二层)
    RequireConfirmed bool // true=策略触发仅生成"待确认"通知, 人工确认后才执行 (高危动作)
    MaxDailyExec    int  // 每日最大执行次数, 0=不限 (熔断)
}
```

**语义约束**：

1. `TriggerType` 三选一，其余触发器字段按类型校验必填/禁用（与 deviceaction Definition 注册校验同风格，fail-closed）。
2. `ActionID` 必须在目标设备的 `deviceaction` Catalog 中存在且 `Enabled=true`；规则保存时校验，执行时仍须过运行期 gate（能力可能变化）。
3. `RequireConfirmed=true` 的策略适用于高风险动作（如 BMS MOS 策略变更）——策略触发**不直接执行**，而是生成一条"建议执行"通知，用户在通知中心一键确认后走 `IssueConfirmation → Create` 链路。这复用了现有 confirmation 设施，避免为策略另造审批流。
4. `CooldownSec` 与告警的 `SilenceSec` 语义对齐但作用于**执行**而非通知。

### 3.3 触发器语义

**① sensor_threshold（数据驱动）**

挂接点与 alert 完全一致：`SensorParserConsumer` 解析成功后回调。求值逻辑复用滑动窗口：连续 `DurationSec` 内所有样本满足比较式才触发。与告警的差异在**出口**——alert 触发后发通知，automation 触发后进入 ActionPlanner。

**② time_window（时钟驱动）**

新增 1 分钟周期的 ticker（独立 goroutine，不挂在数据链路）：每分钟检查所有 `time_window` 规则，当前时刻进入/离开窗口时触发。`TriggerWindowEdge` 语义：
- `enter`：进入窗口瞬间触发一次（如 18:30 触发"关闭充电 MOS"）
- `exit`：离开窗口瞬间触发一次（如 06:30 触发"恢复充电 MOS"）
- `inside`：窗口内每次 tick 都参与求值（受 CooldownSec 抑制，用于"窗口内持续监控"场景）

时间源一律用后端本地时间（`time.Now()`），时区在规则上显式标注（默认 Asia/Shanghai，与部署环境一致）。**注意与 ESP32 uptime 无关**——节点离线时时间窗口规则照常求值，执行阶段被 `node_status` gate fail-closed 拦截。

**③ event（事件驱动，预留）**

节点上线/离线、告警 firing 等系统事件作为触发源。本期仅定义类型占位，不实现（防过度设计：当前场景 S1-S5 均不需要）。

### 3.4 ActionPlanner（防抖与熔断）

触发 ≠ 执行。Planner 在触发后、执行前做四道检查：

1. **冷却检查**：`last_executed_at + CooldownSec > now` → 跳过，记 `automation_events{result: suppressed_cooldown}`。
2. **日熔断**：当日已执行次数 ≥ `MaxDailyExec`（>0 时）→ 跳过，记 `suppressed_daily_limit` 并发一次 warning 通知（防规则配错导致无限循环）。
3. **条件复核**：触发到执行之间状态可能变化（尤其 `DurationSec` 长的规则），执行前用最新值（`api.SetLatestValue` 的最新值缓存）重新求值一次所有 conditions，不满足则记 `condition_changed`。
4. **确认分流**：`RequireConfirmed=true` → 生成建议通知，不执行；`false` → 直接调 `commandexec.Service.Create`。

### 3.5 系统 Actor 与审计

策略执行在 `command_executions` 中的归因方案：

- `ActorUserID` 字段语义是 `uint` 外键（users 表）。系统 actor 方案二选一：
  - **方案 A**：引入内置系统用户行（`users` 表 `id=1, username='system', is_system=true`），`ActorUserID=系统用户ID`。零 schema 变更，外钥完整，历史查询天然兼容。系统用户禁止登录（`password_hash=''` + 登录路径拒绝）。
  - 方案 B：`ActorUserID=0` 约定为系统。无需加用户行但破坏外键语义，历史查询需特判。
  - **实际实现（2026-08-25 对账修订）**：采用单主体模式，复用既有 `system_admin`（`subject_key=system_admin`，main.go:221-226），`ActorUserID=adminUser.ID`。项目 users 表仅单主体，新建第二行 is_system 用户会破坏单主体假设——实现选择务实合理。代价：`command_executions` 按 ActorUserID 无法区分策略/人工，须按 `Reason` 前缀 `automation:` 过滤区分。策略/人工归因依赖 Reason 前缀约定而非外键行区分。
- `Reason` 字段记录策略归因：`automation:<rule_id>:<rule_name>`，操作历史页可直接展示来源。
- 幂等键生成规则：`automation:<rule_id>:<yyyymmdd>:<seq>`（seq 为当日该规则第 N 次触发），保证同一触发不会因重试产生第二次物理执行（复用 `IdempotencyCollision` 机制）。

### 3.6 与告警引擎的关系

| 维度 | alert（告警） | automation（自动化策略） |
|------|--------------|--------------------------|
| 目的 | 人感知异常 | 系统自动处置 |
| 出口 | Notification + WS | ActionPlanner → commandexec / Notification |
| 状态机 | normal→firing→resolved | armed→triggered→cooldown |
| 复合条件 | 不支持 | 支持（AND） |
| 时间触发 | 不支持 | 支持（time_window） |
| 数据模型 | `alert_rules` | `automation_rules` |

两者**并存不合并**。告警规则页保留；策略规则页新增。前端可在告警规则页提供"转为自动化策略"的引导（低优先级）。

## 4. 协议/接口契约

### 4.1 REST API（新增）

```
GET    /api/v1/automation/rules              # 列表（支持 ?enabled=&trigger_type= 过滤）
POST   /api/v1/automation/rules              # 创建（含 trigger/action 组合校验）
GET    /api/v1/automation/rules/:id          # 详情
PUT    /api/v1/automation/rules/:id          # 更新（禁用中规则才可改 trigger/action，防热改歧义）
DELETE /api/v1/automation/rules/:id          # 删除（软删，保留历史归因）
POST   /api/v1/automation/rules/:id/toggle   # 启用/禁用（即时生效, evaluator.Invalidate）
GET    /api/v1/automation/rules/:id/events   # 该规则的触发/执行历史
GET    /api/v1/automation/events             # 全局触发历史（?rule_id=&result=）
```

校验规则（创建/更新时 fail-closed）：
- `trigger_type` 与字段组合一致性（sensor_threshold 必须有 sensor_name+comparator+threshold；time_window 必须有 start/end/edge）
- `action_id` 必须在目标设备 Catalog 中存在（调 `service.Catalog` 验证，但**不**要求当前 available——保存时能力过期不阻塞规则创建，执行时才 gate）
- `cooldown_sec ∈ [0, 86400]`，`max_daily_exec ∈ [0, 1000]`
- `action_params` 必须通过 `deviceaction.CanonicalizeParams` 校验（与人工操作同一参数校验路径）

### 4.2 WS 事件（新增）

```
automation_triggered  { rule_id, rule_name, event_id, result: executed|suppressed_*|pending_confirm, action_id, edge_device_id, value?, at }
```

策略执行产生的 `device_operation_update` 沿用现有事件（执行状态推进：queued→dispatched→succeeded/failed），前端历史页零新增订阅。

### 4.3 数据模型（新增表）

```
automation_rules    -- 见 §3.2（含 created_at/updated_at/deleted_at 软删）
automation_events   -- 触发/执行审计
  id, rule_id (index), triggered_at, trigger_value (触发时传感器值, nullable),
  result (executed|suppressed_cooldown|suppressed_daily_limit|condition_changed|pending_confirm|failed_gate|failed_dispatch),
  command_id (nullable, FK→command_executions, 执行时回填),
  detail (失败/抑制原因),
  created_at
```

`automation_events.command_id` 建立到既有 `command_executions` 的关联——**策略执行历史 = automation_events JOIN command_executions**，不需要第二张执行表。

## 5. 数据模型状态机

### 5.1 规则求值状态机（sensor_threshold）

```
        条件不满足                条件连续满足≥DurationSec
armed ──────────────▶ armed     ──────────────────────▶ triggered
  ▲                                                     │
  │                                                     ▼
  │                                              ActionPlanner 检查
  │                                                     │
  │         ┌───────────────┬───────────────┬──────────┘
  │         ▼               ▼               ▼
  │    cooldown/熔断    pending_confirm   Create() → executed
  │         │               │                    │
  └─────────┴───────冷却期到期/条件复位◀──────────┘
```

- 与告警不同：**不要求"条件先复位再触发"**。armed 的恢复条件是冷却期到期（时间维度），不是条件不满足（值维度）。理由：光照开灯场景，"光照弱"持续整夜，策略只需执行一次"开灯"，之后进入冷却；若等条件复位（天亮）才能再触发，则次日黄昏无法再次开灯。每日重置由 `MaxDailyExec` 的日界提供。
- `pending_confirm` 状态：等待人工确认，确认后进入 Create；超时（如 1h）未确认记 `expired`。

### 5.2 执行结果归因

`command_executions.status` 沿用现有状态集（queued/dispatched/succeeded/failed/unknown/cancelled）。策略层不新增状态，只在 `automation_events.result` 记录策略侧决策结果。

## 6. 场景映射（验证设计完备性）

### S1 光照弱自动开灯

```yaml
trigger: { type: sensor_threshold, sensor: illuminance, comparator: lt, threshold: 50, duration_sec: 120 }
action:  { type: device_action, device: <GPIO继电器对应的逻辑设备>, action_id: gpio_set, params: { pin: 5, level: 1 } }
constraints: { cooldown_sec: 1800, require_confirmed: false, max_daily_exec: 2 }
```

配对规则（关灯）：
```yaml
trigger: { type: sensor_threshold, sensor: illuminance, comparator: gte, threshold: 200, duration_sec: 300 }
action:  { action_id: gpio_set, params: { pin: 5, level: 0 } }
```

**迟滞设计**：开灯阈值（<50）与关灯阈值（≥200）之间留死区，配合 `duration_sec` 与 `cooldown_sec` 三重防抖——这是本模型处理"阈值附近抖动"的标准模式，文档中作为配置最佳实践明确。

**前置依赖**：GPIO 动作需有 `gpio_set` deviceaction 定义（见 §8 前置改造 P0）。

### S2 夜间光伏无法发电 → 关闭 BMS 充电 MOS

两种等价实现，用户可按是否接逆变器选择：

**方案一（时间窗口，不依赖逆变器数据）**：
```yaml
trigger: { type: time_window, window: 19:00-06:00, edge: enter }
condition: [ { sensor: soc, comparator: lt, threshold: 95 } ]   # SOC 高时不必限充
action:  { device: <BMS>, action_id: set_mos_policy, params: { charge_mos: 0, discharge_mos: 1 } }
constraints: { require_confirmed: true }   # 高风险动作, 建议确认制
```

配对规则（清晨恢复）：
```yaml
trigger: { type: time_window, window: 19:00-06:00, edge: exit }
action:  { action_id: set_mos_policy, params: { charge_mos: 1, discharge_mos: 1 } }
constraints: { require_confirmed: true }
```

**方案二（光伏功率驱动，有 techfine 逆变器时更精准）**：
```yaml
trigger: { type: sensor_threshold, sensor: pv1_power, comparator: lt, threshold: 10, duration_sec: 600 }
action: 同方案一
```

`set_mos_policy` 现状（源码核实 `jiabaida.go:52-62`）：`Enabled:true, Semantics:set, ExecutionShape:bounded_sequence(MaxSteps:2), Verification:readback, AtMostOnce:true`——**已实机验证**（2026-08-14 fet_status 0→0x11→0 双向对账），策略可直接调用，全链路已有 readback 对账与 at-most-once 保护。

**为什么高风险动作用 `require_confirmed: true` 而非全自动**：BMS MOS 策略影响电池安全，夜间全自动关闭若遇异常放电场景（如夜间临时用电）可能非预期。确认制下，策略触发生成建议通知，用户一键确认后走 `IssueConfirmation → Create`——既保留自动化便利，又保留人对高风险动作的最终决定权。若用户充分信任后可改为全自动（`require_confirmed: false`）。

### S3 电池 SOC 过低断开负载

```yaml
trigger: { type: sensor_threshold, sensor: soc, comparator: lt, threshold: 15, duration_sec: 60 }
action:  { action_id: gpio_set, params: { pin: <负载继电器>, level: 0 } }
constraints: { cooldown_sec: 3600, require_confirmed: false, max_daily_exec: 1 }
```

同时告警引擎可并行配一条 `soc < 20` 的 warning 通知——**告警（预警）与策略（处置）分层**，预警阈值先于处置阈值，两者互不替代。

### S4 温度过高停止充电

```yaml
trigger: { type: sensor_threshold, sensor: temperature, comparator: gt, threshold: 45, duration_sec: 30 }
action:  { action_id: set_mos_policy, params: { charge_mos: 0, discharge_mos: 1 } }
constraints: { require_confirmed: false, cooldown_sec: 600 }
```

温度是物理惯性量，30s 持续判定 + 10min 冷却足够。恢复规则（<40℃ 恢复充电）建议 `require_confirmed: true`——过热原因未查明前不应自动恢复。

### S5 夜间异常仅通知

```yaml
trigger: { type: sensor_threshold, sensor: <任意>, ... }
condition: [ { type: time, window: 23:00-07:00 } ]
action:  { type: notification, level: warning }
```

动作类型为 `notification` 时退化为"带条件的告警"——这正是策略引擎对告警引擎的**功能超集**体现，但 §3.6 已裁决两者并存（告警更简单，不为策略的复杂度买单）。

## 7. 验收标准（设计层面）

实现后的验收 checklist（供后续实施方案引用）：

- [ ] **后端**：`automation_rules`/`automation_events` 迁移 + CRUD API + 组合校验测试（trigger/action 字段组合 × 非法组合拒绝）
- [ ] **求值器**：sensor_threshold 触发测试（滑动窗口连续满足/抖动不触发/冷却抑制/日熔断）；time_window enter/exit 边界测试（跨零点窗口 19:00-06:00 正确求值）
- [ ] **执行链路**：策略触发 → `command_executions` 行存在 + `actor=system` + `reason=automation:<rule_id>` + 幂等键重试不重复执行
- [ ] **fail-closed**：节点离线时触发产生 `failed_gate` 事件且**无** CommandExecution 行；能力过期（capability_stale）同理
- [ ] **确认制**：`require_confirmed` 规则触发 → 通知生成 + 无执行；确认后 → 执行；1h 超时 → expired
- [ ] **前端**：规则 CRUD 页 + 触发历史页 + 操作历史中策略执行可区分（来源标识）
- [ ] **实机**：S2 场景端到端（时间触发 → 确认 → BMS MOS 关闭 → fet_status readback 对账）

## 8. 前置改造与实施要点

**P0 前置（阻塞策略对 GPIO 的支持）**：

1. **GPIO/PWM 动作纳入 deviceaction**：新增内置定义 `gpio_set`（params: `{pin, level}`）/ `pwm_set_duty`（params: `{hardware_id, duty}`），Transport 需要新增 `periph_cmd` 适配器（当前仅 `channel_cmd_v2`）。这同时解决"GPIO 裸下发无审计"的存量债务。⚠️ 注意与"GPIO 不入通道系统"的裁决不冲突——deviceaction 是动作目录不是通道，PeriphCmd 0x1B 是协议帧。

**实施顺序建议**：

- Phase 1：模型 + CRUD + sensor_threshold 求值器 + ActionPlanner + notification 动作（不含设备动作）——纯新增不触碰现有链路，风险最低

- Phase 3：time_window 触发器 + require_confirmed 确认流 + GPIO deviceaction 前置改造
- Phase 4：实机 S1/S2 场景验收 + 触发历史页

## 9. 风险与开放问题

| # | 风险/问题 | 缓解 |
|---|-----------|------|
| R1 | 策略引擎 bug 导致误触发执行（如光照传感器故障读数恒 0 → 反复开灯） | 三重防抖（duration+cooldown+daily_limit）+ 高风险动作确认制 + 触发历史全审计 |
| R2 | 后端重启丢失内存态窗口/冷却状态 | 窗口状态允许丢失（重启后重新积累 DurationSec，保守不触发）；冷却状态从 `automation_events` 最近一次 executed 重建 |
| R3 | time_window 与节点时区不一致（ESP32 本地时间 vs 后端时间） | 裁决：一切以**后端时间**为准，ESP32 不参与时间语义；文档明示 |
| R4 | 规则动作目标设备被删除/合并 | 执行时 `edge_device` gate fail-closed；规则列表页标注"目标缺失"；逻辑设备合并后规则跟随 `logical_device_id`（复用 alert 的 resolveLogicalID 先例） |
| R5 | 用户期望"光照自动控制"但系统没有光照传感器 | 场景 S1 以 `illuminance` 字段名为契约，实际字段由接入的光照传感器驱动定义（如 bh1750）；规则创建时 sensor_name 校验应对照目标设备驱动的解析字段清单（可借 Catalog 思路做字段目录，Phase 2 再定） |
| R6 | 是否需要边缘自治（断网时 ESP32 本地执行策略） | 本期不做（§2.2）；若未来需要，策略可编译为简化规则下发 ESP32（类似 ConfigTemplate 模式），但需重新设计安全模型 |

## 10. 与既有设计裁决的一致性核对

- ✅ **"功能实现即默认可用"**（2026-08-14 裁决）：策略引擎默认可用，不加功能开关白名单；`DeviceControlV2Enabled` 作为整个 dispatcher 的 kill switch 对策略执行同样生效（fail-closed）。

- ✅ **"GPIO 不入通道系统"**：GPIO 动作走 deviceaction + PeriphCmd，不创建通道。

- ✅ **告警引擎先例**：求值挂接点（解析后回调）、滑动窗口、静默语义、软删规则均沿用 alert 已验证模式。
