### 1.3 存量库的索引回收（方案没写、但必须做的一步）

删模板只影响「之后新建的库」。`ensurePartitionParentIndexes` 的语义是**只补建、不删除**（有意的最小惊讶原则），因此生产库上已存在的 4 条死索引不会自己消失。新增：

- `deadTimeseriesIndexes`：表 → 死索引列清单（当前 4 条）。
- `retireDeadTimeseriesIndexes(db, table)`：按 `pg_get_indexdef` 的**列清单完全相等**判据 DROP（不是按索引名 —— 历史 `<table>_new` 迁移路径建的索引名带 `_new_` 前缀，PG 的 `ALTER TABLE ... RENAME TO` 不改索引名，按名匹配会漏）。
- 挂在 `MigrateTableToPartitioned` 的三个收敛点：原来 `return ensurePartitionParentIndexes(...)` 统一换成 `finalizePartitionParentIndexes(...)`（**先补建活索引、再删死索引**，避免出现「该建的没建、旧的已删」的空窗）。
- **失败只 Warn 不阻断启动**：DROP INDEX 取 ACCESS EXCLUSIVE 锁，长事务占锁时会失败；但「没删掉一条死索引」只是空间没省下来，不能因此让服务起不来（把空间优化变成可用性事故）。
- ⚠ **生产执行前必须先确认 ACCESS EXCLUSIVE 锁的维护窗口**：`DROP INDEX` 会取该表上的 ACCESS EXCLUSIVE 锁并阻塞一切读写，生产 70M 行、5 条父索引 × 每分区子索引的规模下，逐条 DROP 可能持续数十秒。必须在低峰维护窗口升级，或提前人工用 `DROP INDEX CONCURRENTLY` 建好删除路径（PG17+ 对分区表父索引支持 CONCURRENTLY），函数随后按「列清单命中即跳过」自然不再动作。
- **唯一索引/主键一律不参与**：`parseIndexDef` 对 `CREATE UNIQUE INDEX` 直接返回 ok=false。删唯一索引会让重复数据静默可插入（data_sources 的 `uniq_ds_source` 踩过同类事故，见 database/gorm.go 里 RetireLogicalDeviceLayer 的顺序注释）。

## 2. 阶段1（L1）：值不变不入库 + 心跳

### 2.1 规则（方案 §3.1）

对每台设备、每个字段维护「最后**已落库**值 + 落库时间」：

- 字段值**变化** ⇒ 该帧必须写；
- 距上次落库 **≥ 心跳间隔** ⇒ 强制写一帧（心跳，保证时间轴连续、图表不空档）；
- 否则 ⇒ **跳过 INSERT**（内存缓存 / 告警 / 自动化 / WS 推送照常更新）。

### 2.3 三处必须守住的语义（每一处都对应方案 §3.3 的一行副作用）

1. **latestSink 提到 INSERT 之前，且不受写库结果门控。** 改造前它挂在 `Create 成功的 else 分支`上（consumers_heavy.go 原 366-380 行）。一旦开始跳过 INSERT，缓存会冻结在旧值 —— 用户看到「数据不动了」，而 WS 还在推新值。缓存表达的是**设备当前状态**，不是「库里有几行」，所以写库失败时它也要更新。
2. **写库失败不推进状态。** 否则新值被记成「已落库」，后续同值帧全被判成「未变化」而跳过，**该值永久丢失**（方案 §3.3「缓存一致性」）。
3. **首帧全量写。** 状态表是进程内的，重启后为空 ⇒ 每个（设备, 字段）第一次见到都必写（方案 §3.3「进程重启」）。指标里它表现为 `decision="write_first"`，是可观测的正常路径，不是异常。

### 2.4 影子模式（默认）

`write_on_change=false` 时**照常全量写**，只把「本可跳过多少行」打进指标：

```
ehome_telemetry_write_gate_rows_total{mode="shadow"|"enforced", decision="write_first"|"write_changed"|"write_heartbeat"|"skip"}
ehome_telemetry_write_gate_tracked_fields        # 状态表当前跟踪的 (设备, 字段) 数
```

**影子模式的模拟是忠实的**：它按 `wouldWrite`（本应写的集合）推进状态，而不是按「实际全量写」推进。否则心跳条件 `at - prev.at >= heartbeat` 永远不成立，影子统计出的命中率会显著偏离真开时的命中率 —— 影子模式的价值全在「忠实模拟」。

核对方法：`rate(ehome_telemetry_write_gate_rows_total{mode="shadow",decision="skip"}[1d]) / rate(ehome_telemetry_write_gate_rows_total{mode="shadow"}[1d])`，与真实数据回归（`docs/验证/遥测存储-真实数据回归基线-2026-11-06.md` §5.2/§5.3）对账后再开开关。

**回归实测基线（2026-11-04 单日 + 全窗口，已证伪/证实方案的对应数字）**：

| 口径 | 方案 §3.2 | 回归实测 | 结论 |
|---|---:|---:|---|
| device14 跳过率 | 5.3% | **5.27%**（写入 81,788 行，**一位不差**） | ✅ 证实 |
| device15 跳过率 | 36.9% | **36.92%**（差 3 帧 / 0.008%） | ✅ 证实 |
| 合计跳过率（单日） | 17.7% | **17.74%** | ✅ 证实 |
| 合计跳过率（11-01~11-06 全窗口） | — | **18.17%**（726,310 帧；逐日波动 ±1.5pp） | 单日代表合理 |
| 逐字段 on-change 行数 | 688,153（24.6%） | **718,413（25.55%）** | ⚠️ 偏差 −4.2%（见 D2 的口径说明） |

⇒ 影子模式的放行判据用 §3.6 步骤 1 的「10%–30%」区间即可；**device14 与 device15 差异极大（5% vs 37%）是正常现象**，不要因为某台设备跳过率低就以为门控没生效。

### 2.4.1 真实数据回归提出的两条实现约束（**回归证伪/证实的，必须记住**）

出处：`docs/验证/遥测存储-真实数据回归基线-2026-11-06.md` §5.1 / §5.6。

**C1｜L1 必须「逐字段」判定，不能按整帧比较。**
方案 §3.1 写的是「对每台设备、**每个字段**维护最后已落库值 + 落库时间」，而 §3.2 的结果表是**帧级**口径
（一帧写 ⟺ 该帧至少一个字段变化，或该帧距上次落库 ≥ 心跳）。两者是**同一个规则的两层**，实现时不能简化。
回归 SQL 的实测反例：若按「整帧 vs 上一帧」直接比较，device15 的跳过率会从 **39% 掉到 4.22%**、合计从 18.17% 掉到 4.37%
—— 因为 device15 的 7 种帧类型（3/14/2/5/5/9/4 字段）交替出现，**字段集合差异会被误判成「值变化」**。

本实现符合 C1：状态表的键是 `(deviceID, sensorName)`（`telemetryFieldKey`），逐字段独立判定；
整帧「写不写」由 `filter()` 的逐行结果聚合而成 —— 即 `stat.writes() > 0` 时该帧至少写一行。
回归 §5.2 的帧级结果（device14 一位不差、device15 差 3 帧）正是本实现语义的预期输出。

**C2｜60 s 心跳在本批真实数据里从未触发，只能靠单测兜底。**
回归 §5.6 实测：device14 两次写入间最大间隔 **23.1 s**、device15 **33.7 s**，均 < 60 s ⇒ `heartbeat_only = 0` 帧。
两个含义：
1. **好消息**：心跳开销为 0，方案的「跳过率」完全由值变化决定，不会被心跳稀释；
2. **风险**：心跳逻辑**没有任何线上数据覆盖**，不能指望线上跑一年来验证。因此本实现交付了 3 条专门的心跳单测
   （`TestWriteGate_WritesOnHeartbeat` 含 59.999 s / 60 s 边界、`TestWriteGate_SkipsUnchangedValues` 的长时间恒定值路径、
   `TestWriteGate_RestartWritesEverything` 的重启全量写），并用 `heartbeat` 可注入的 gate 直接断言时间语义（不依赖真实时钟）。

### 2.5 多实例与状态表上界

- 状态表是**进程内**的，多副本部署需要共享状态（当前单容器，无此问题，方案 §3.3「多实例」）。
- 按 `(设备, 字段)` 建键，而 bus 的分片保证「同一设备的事件永远进同一个 shard」（shard.go 的 FNV 哈希 + per-device 顺序），因此每个 shard 各持一份状态表不会出现同一设备被两个 shard 交叉判定。
- 上界 `telemetryWriteGateMaxTrackedFields = 200000`。越界时淘汰心跳窗口 10 倍之外的条目；**淘汰只会让该字段下一帧多写一次**（safe direction），绝不漏写。

## 3. 口径影响（**只标注，不擅自改**）

按任务书要求：这些接口的语义在 `write_on_change=true` 之后会变，但本实现**没有修改任何读接口**。

| 接口 / 逻辑 | 现状口径 | 开启 L1 后的变化 | 建议（未实施） |
|---|---|---|---|
| `/unified-data/historical` / `-batch` 的 `agg=avg` | 桶内**所有行**的算术平均（history_points.go:290-300 的 `avg("value")` 分桶） | 跳过的是「未变化」的行，桶内行数变少 ⇒ `avg` 从「时间加权均值」退化为「变化点均值」。**对恒定段无偏差**（同一值重复多少次平均都一样），**对阶跃段有偏差**（变化点密度不均匀时，均值会偏向变化频繁的值）。 | 改「桶内最后值」或时间加权平均（方案 §3.3 原文）。属读侧改造，不在本任务范围。 |

## 3.6 三个开关的灰度顺序建议（可直接当运维 runbook 用）

> 三个开关**互相独立**，但顺序不能随意：每一步都是下一步的**前提证据**。全部默认 `false`；每一步只改**一个**变量并重启（本仓无配置热加载）。前置：完成方案 §7 阶段0（清盘 ≥6 GB、死索引退役已跑过一次启动），否则双写期磁盘会先满。

### 步骤 0（无需开关）：确认基线

```bash
# 死索引退役是否真的执行过（启动日志应有 4 条 dropped dead index）
docker logs <server> 2>&1 | grep 'dropped dead index'
# 建表/迁移是否到位
psql -c '\dt telemetry_*'
```

判据：4 条死索引已不存在；`telemetry_frame` 与 `telemetry_rollup_1m` 两张表存在。

### 步骤 1：L1 影子模式（**默认就是这一步，无需改配置**）

- 开关：`EHOME_TELEMETRY_WRITE_ON_CHANGE=false`（默认）
- 行为：全量写，**零行为变化**；只统计「本可跳过多少行」
- 观察周期：**≥ 24 小时**（覆盖一个完整日周期）

```promql
# 命中率（应接近回归实测的 17.7%~18.2%；device15 应显著高于 device14 —— 37% vs 5% 是正常的）
sum(rate(ehome_telemetry_write_gate_rows_total{mode="shadow",decision="skip"}[1h]))
  / sum(rate(ehome_telemetry_write_gate_rows_total{mode="shadow"}[1h]))
# 分决策构成（write_first 应当只在重启后短暂出现）
sum by (decision) (rate(ehome_telemetry_write_gate_rows_total{mode="shadow"}[1h]))
```

**放行判据**：命中率落在 10%–30%（与方案实测同量级）；`write_first` 只在重启后跳一下；`tracked_fields` 稳定不涨。

### 步骤 2：裁决 D1–D4（**不改任何配置**，纯评审动作）

必须先有 D1（avg 语义）、D2（data_count_today）、D3（points_stored）、D4（preview 分帧）的结论，否则步骤 3 一开就会出现「数字变了但没人知道为什么」。若 D1 决定改「桶内最后值」，那是**读侧代码改动**，应在步骤 3 **之前**合入。

### 步骤 3：L1 真开

- 开关：`EHOME_TELEMETRY_WRITE_ON_CHANGE=true`（心跳保持 `EHOME_TELEMETRY_HEARTBEAT_SECONDS=60`）
- 观察：
  - 写入行数应降到约 1/4–1/5；`unified_data` 分区增长速率同步下降
  - `mode="enforced"` 的 `skip` 计数应与步骤 1 的影子命中率**吻合**（偏差 >5 个百分点说明影子模拟失真，需排查）
  - 抽查任意设备任意 1 小时：库里「最后值」与设备实时值一致（缓存正确性）
- **回滚**：改回 `false` 重启即可，无需数据修复（跳过的是写入，不涉及已有数据）

### 步骤 4：L2 双写（先只写不读）

- 开关：`EHOME_TELEMETRY_DUAL_WRITE=true`（关键帧间隔复用 `EHOME_TELEMETRY_HEARTBEAT_SECONDS`，与 L1 同源）
- 前置：`telemetry_frame` 已建；磁盘余量 ≥ 双写期峰值
- 观察：
  - `DualWriter.Stats()`：`Dropped == 0`（>0 说明落库跟不上采集）、`Failed == 0`（>0 说明编码/写库有问题）
  - payload 平均字节/帧应与方案 §4.5 对账（device14 ≈ 16.7 B、device15 ≈ 4.7 B）
- **回滚**：改回 `false` 重启；已写入的帧表数据可保留（读侧未切换，无影响）

### 步骤 5：L2 影子对拍（**不改开关**，跑验收）

判据（方案 §9 验收 1）：任意设备任意 24h 窗口，解码重建的 1 Hz 序列与 `unified_data` 逐值对比：误差 ≤ 量化步长/2、缺失 0。工具：`internal/telemetry/realdata_roundtrip_test.go`（真实数据往返）+ PG 侧 store 对拍。

**放行判据**：0 超差、0 缺失；`telemetry_frame` 与 `unified_data` 的**帧数**与时间戳分布一致（允许 L1 跳过带来的行数差异，但帧数必须相等）。

### 步骤 6：L3 rollup 写入侧

- 开关：`EHOME_TELEMETRY_ROLLUP_WRITE=true`
- 前置：**D8 已裁决**（读侧切换有排期，否则复刻「写了没人读」）
- 观察：
  - `telemetry_rollup_1m` 每设备每分钟应恰好 1 行（方案 §5.2 宽行主键语义）
  - 分钟桶的字段统计量（avg/min/max/last）应与直接 SQL 聚合 `unified_data` 的结果对得上（注意 L1 开启后原始表行数变少，但恒定段的 avg/min/max 不受影响）
- **回滚**：改回 `false` 重启；已写入的 rollup 行可不清理（读侧未切换）

### 步骤 7：读侧切换（**不在本实现范围**）

- 开关：`EHOME_TELEMETRY_ROLLUP_READ=true`（`internal/api/rollup_read.go`，由 L3 读侧任务实现）
- 切换前必须完成：D1 的 avg 口径改造 + 长窗图表切 rollup + 短窗仍解码（方案 §5.3）
- **回滚**：`rollup_read.go` 是 fail-open 的（表空/坏/不存在 ⇒ 回落原始路径），改回 `false` 即回到旧读法

### 一页速查

| 步骤 | 开关 | 默认 | 放行判据 | 回滚方式 |
|---|---|---|---|---|
| 0 | — | — | 死索引已删、两张新表存在 | — |
| 1 | `WRITE_ON_CHANGE=false`（影子） | false | 影子命中率 10%–30%，持续 24h | 无需回滚（就是默认） |
| 2 | — | — | D1–D4 有结论 | — |

| 4 | `TELEMETRY_DUAL_WRITE=true` | false | Dropped=0、Failed=0、payload 对账 | 改回 false 重启 |

## 3.7 读路径口径改造 D1–D4（2026-11-07 落地）

> 契约：`docs/设计/遥测存储-L1L2无条件启用-契约-2026-11-07.md` §2。
> 触发原因：L1 无条件生效 ⇒ `unified_data` 不再是完整 1 Hz 序列，所有基于
> 「行数 / 行均值」的读路径都会语义漂移。**这四条的共同点是：不改也不会报错，
> 只会让用户看到错的数字。**

### D1｜`agg=avg` 改成「桶内最后值」（**用户可见 bug 的阻断项**）

文件：`backend/internal/api/history_points.go`

| 项 | 内容 |
|---|---|
| 症状 | `avg(value)` 按**行数**平均 ⇒ 恒定段（每 60s 只 1 行）与阶跃段（每帧 1 行）权重相同，平均值被系统性拉向变化频繁的一侧。真实数据回归实测：BMS 电流 24h 均值最大偏差 **0.17 A** |
| 改法 | 桶内**最后值** —— 该桶结束时真实读数。与 L1 严格对应：被跳过的行与前一行值相同，所以「最后一个已落库值」就是「该时刻真实值」 |
| PG | `(array_agg("value" ORDER BY "timestamp" DESC))[1]`（契约 §2.1 原文） |
| SQLite | `ROW_NUMBER() OVER (PARTITION BY <桶号> ORDER BY "timestamp" DESC) = 1` —— SQLite 没有 `array_agg(... ORDER BY ...)` 也没有数组下标 |
| 方言选择 | `historyAvgSQLFor(db, source, W)` 按 `db.Dialector.Name()` 分流；旧名 `historyAvgSQL` **改掉**了（沿用旧名会让读者以为还是 avg 口径） |
| 顺带修的一个坑 | SQLite 分支**不能输出 `datetime(...)` 字符串**：go-sqlite3 只对声明类型为 DATETIME/TIMESTAMP 的列做 string→time.Time 转换，聚合表达式列没有声明类型，`database/sql` 会直接报 `unsupported Scan, storing driver.Value type string into type *time.Time`。因此 SQLite 输出 epoch 秒整数，由 `historyScanRow.toHistoryPoint()` 在 Go 侧转 |
| 硬验收 | 恒定段 avg == 桶内最后值（契约 §6.5）→ `TestD1_ConstantSegment_LastValueEqualsAvg` |
| 鉴别力验收 | 阶跃/稀疏段 avg **必须不等于**桶内最后值 → `TestD1_StepSegment_LastValueDiffersFromAvg`（若实现回退成 avg，这条会红；反过来说，没有这条断言的前者也无法证明改对了） |

### D2｜`/overview` 的 `data_count_today` 改成采样帧数

文件：`backend/internal/api/handler_overview.go`

口径从 `COUNT(*)`（今日行数）改为 `COUNT(*) FROM (SELECT device_id, timestamp ... GROUP BY device_id, timestamp)`（今日**帧数**）。时间边界（`>= 本地零点`）不变 —— 那是 F14-b 已经钉住的语义，本次不动。

**为什么是帧数**：L1 只减少「同一帧里写了几个字段」，不减少「有过几帧」，因此帧数对 L1 天然不敏感。生产实测今日窗口 `count(*)` 235 ms vs 帧数 516 ms，而 `/overview` 有 30 s 缓存，轮询不放大开销 —— 所以这里**只对今日窗口去重**，不做全表去重。

SQL 用「子查询 + GROUP BY」而不是 PG 的 `count(DISTINCT (a,b))` 行构造器：后者是 PG 专有语法，前者 SQLite/PG 都能执行（SQLite 分支由 `TestOverview_DataCountToday_CountsOnlyToday` 覆盖）。

### D3｜`/metrics/summary` 的 `points_stored` 改成采样帧数（**带缓存**）

文件：`backend/internal/api/handler_metrics.go`

**这个和 D2 的代价不一样，必须单独处理**：`points_stored` 是**全表**计数。生产 72.36M 行实测：

| 查询 | 耗时 |
|---|---:|
| `count(*)` | 2.9 s |
| `count(DISTINCT (device_id, timestamp))` 行构造器 | 19.8 s |
| 子查询 + `GROUP BY` | 19.8 s |

而 `Monitor.vue` 以 **10 s** 间隔轮询 `/metrics/summary`（`refreshInterval = ref(10000)`）。不缓存 ⇒ 每 10 s 有一条查询跑 20 s ⇒ 连接池被拖垮。因此新增 `cachedPointsStored(db)`：懒加载 + 60 s TTL + 失败回落上一次值（首次则回落行数），**绝不让 /metrics/summary 返回 5xx**。

### D4｜`/sensor-fields/preview` 的稀疏帧语义（**只标注，不改判定**）

文件：`backend/internal/api/handler_sensor_fields.go`

按 timestamp 分帧的**构造本身仍然正确**（生产端一帧内所有字段用同一个 `now` 写入）。L1 之后变的是**帧的密度**：某字段值未变且未到心跳时它在库里没有行，于是这一帧看起来「缺员」。

例：BMS 一帧 29 个字段，若只有 1 个字段变化 ⇒ 库里只留 1 行 ⇒ `missing_known` 会把它算成缺 28 个。

**处置（有意不做补全）**：
1. 响应新增 `sparse_frames`（bool）与 `frame_semantics`（字符串说明），让调用方知道「帧字段少」是 L1 的**正常结果**，不是设备丢帧；
2. **不补全缺失字段** —— `duration_would_fire` 与 `trace` 都需要「真实写过库的那一帧」的字段集合，补全会给出从未发生过的求值；
3. 既有字段语义零变化（旧前端忽略新字段即可）。

⚠ 正确用法：`missing_known` 现在表达「本帧**未落库**的字段」，不等于「设备没上报」。要判断后者看 `/sensor-fields/obs`（按上报计数，不受 L1 影响）。

### D5｜`agg=change` —— **不动**

变化点检测本来就只要变化点，被跳过的行恰好都是无变化行。契约 §2 的 D5 行明确「无需改」，本次也确实没改。

### 3.7.1 前端文案（由前端同学改，后端只保证字段语义）

| 位置 | 字段 | 现在显示 | 应改成 |
|---|---|---|---|
| `EdgeDeviceList.vue` 「今日数据」卡 | `/overview` → `data_count_today` | 数字（无单位说明） | 「今日采样帧」(单位说明) |

| `backend/internal/datalifecycle/partition_dead_index_test.go`（+6 例） | 4 条死索引模板已删；8 条活索引模板仍在；死索引清单与模板清单不相交；`pg_get_indexdef` 解析（含 `_new_` 前缀、DESC、INCLUDE、唯一索引排除）；列清单**完全相等**判据（前缀不算命中）；非 PG 方言 no-op。 |

### 4.2 为什么 SQLite 足够

L1 收窄是**进程内决策**（值比较 + 时间差），与方言无关；SQLite 只用来断言「到底写了多少行」。死索引的真实 DROP 需要 PG，由 `partition_mgr_*_pg_test.go` 一族的集成测试覆盖（`make test-integration` / `EHOME_TEST_DB=postgres`）；本实现新增的 `retireDeadTimeseriesIndexes` 在 SQLite 上是显式 no-op（有单测钉住）。
