## 一、为什么需要这份规格

逻辑设备层移除后，「历史归属」只剩**一个 id 维度**（`edge_devices.id`），因此用户能做的只有三件事：
换节点（原地）、恢复已删设备、把旧设备历史合并到目标设备。三者都直接改 `device_id`，
**互相之间的状态组合**此前没有定义。本文用真实 API 实测列出全部组合的现状行为与缺口。

## 二、术语与事实基础

| 概念 | 事实（代码/实测） |
|---|---|
| 物理唯一性 | `(channel_id, type, hardware_id)` 三元组。**只在应用层校验**（`checkDeviceUniqueness`），DB 无唯一约束 |
| 软删是否占位 | **不占位**。`checkDeviceUniqueness` 不加 `Unscoped()`，软删设备不计入 ⇒ 同一物理地址可以「新建另一台」 |
| 恢复的目标槽位 | 由请求体 `node_id` + `channel_id` 决定，**可以换到任意空闲位置**，不要求回到原位 |
| 合并的搬运范围 | `unified_data`、`device_data`、`sensor_field_obs`、`data_sources`（2026-10-24 补齐后 4 张） |
| 合并是否删源设备 | **不删**。源设备行保留（若已软删则继续软删；若存活则**变成空壳仍在采集**） |

## 三、现状行为矩阵（全部实测，2026-10-24）

### 3.1 恢复已删设备（`POST /edge-devices/:id/restore`）

| # | 目标槽位 | 结果 | 判定 |
|---|---|---|---|
| R1 | 空闲槽位 | 200，`deleted_at` 清空，按请求改绑 node/channel | ✅ 正确 |
| R2 | 已被**存活**设备占用（同 type+addr） | **409** `channel N already hosts a X device at address Y` | ✅ 正确 |
| R3 | 设备未被删除 | **409** 「设备 #N 未被删除，无需恢复」 | ✅ 正确 |
| R4 | 节点不存在 / 通道不属于该节点 | 404 / 409 | ✅ 正确 |
| R5 | 恢复时该设备仍有 `data_purge_requested=true` | 200 且**清掉该标记**（2026-10-24 P0 修复） | ✅ 正确 |

### 3.2 原地换节点（`PUT /edge-devices/:id`）

| # | 场景 | 结果 | 判定 |
|---|---|---|---|
| M1 | 换到空闲槽位 | 200，`id` 不变 ⇒ 历史天然连续 | ✅ 正确（主路径） |
| M2 | 换到已被占用槽位 | 409 | ✅ 正确 |
| M3 | 只改名不换位置 | 200，地址不动 | ✅ 正确 |

### 3.3 合并历史（`POST /edge-devices/:id/merge-history`）

| # | 源设备状态 | 结果 | 判定 |
|---|---|---|---|
| G1 | 已软删、有历史 | 200，行数与台账都搬到目标，源行保留 | ✅ 正确（主用途） |
| G2 | 同一个源第二次合并 | 200，`rows_migrated=0`（幂等） | ✅ 正确 |
| G3 | 源 = 目标自身 | 200，`sources:[]`，静默忽略 | ⚠ 见缺口 G-1 |
| G4 | 源设备**不存在**（如 9999） | **200** `sources:[9999] rows_migrated:0` | ❌ **缺口 G-2** |
| G5 | 源设备**存活且在采集** | **200**，历史被搬走，源变成空壳但仍在采集 | ❌ **缺口 G-3** |
| G6 | 目标设备已删 | 404 `target edge device not found` | ✅ 正确 |
| G7 | 源数量 > 100 | 400 | ✅ 正确 |

## 四、缺口清单（需要产品裁决）

### G-1【低】源=目标自身：静默忽略
当前返回 200 + 空 `sources`，前端会显示「没有需要迁移的数据」。
**建议**：显式 400「源设备不能是目标设备本身」。静默成功会让人以为操作生效了。

### G-2【中】源设备不存在：假装成功
`POST /edge-devices/1/merge-history {"source_ids":[9999]}` → **200**，`sources:[9999]`。
**危害**：用户拼错 id 或设备早已被硬删时，界面显示成功、实际什么都没发生。
**建议**：源 id 中**任一不存在**返回 400/404，列出无效 id。

### G-3【高】源设备存活：把在用设备变成空壳
当前允许把**正在采集的存活设备**当源。合并后：
- 它的 `unified_data` / `device_data` 全部改挂到目标；
- 但 `edge_devices` 行还在、`status` 还是 active、采集仍在继续；
- 于是它「从现在起」开始积累新历史，而过去的历史已经在别人名下。

**这是最需要裁决的一条**：
- 方案 ①：**禁止**对存活设备合并（只允许源已软删）—— 最安全，但用户若想「把 A 的历史并给 B、然后继续用 A」就做不到；
- 方案 ②：允许，但**必须**在请求里显式传 `allow_live_source:true`，并在响应里标出「源设备已变成空壳，建议删除或改用途」；
- 方案 ③：允许，且合并后**自动把源设备软删**（`data_purge_requested=false`）—— 语义是「这台设备的历史与身份都归目标了」。

### G-4【中】软删设备不占物理位置 ⇒ 可与新设备「同址」
实测：A 在 `(NODE1,ch1,addr=1)` 被软删后，B 可以在**完全相同的物理地址**新建成功。
此时 A 与 B 共享同一物理地址，A 只是已删。

**影响**：
- 恢复 A 时会 409（已正确拦截）；
- 但用户会困惑「我明明删了它，为什么恢复不了」，错误信息没有告诉他「有另一台设备占着这个地址」；
- `merge-history` 把 A 的历史并给 B 是**可行且正确**的出路，但界面没有引导。

**建议**：
- 新建时若同址存在**已软删**设备，返回**警告而非拦截**：「该地址有已删除的设备 A（历史 N 行），是否改为恢复它？」；
- 恢复 409 的文案补一句：「如需把它的历史并入现有设备，请使用『合并历史』」。

### G-5【低】合并后源设备行的收尾无人负责
合并完成后源设备（若存活）变成空壳，系统不做任何处理，也没有「已合并到 #N」的标记。
**建议**：在 `edge_devices` 增加 `merged_into_id`（**仅作展示用，不参与任何查询**），
或在响应里返回明确的后续动作建议。⚠ 若加列，必须写清「这不是第二个 id 空间」，
否则又会长出被我们刚删掉的那种抽象。

## 五、三个动作的选择路径（给用户的引导）

```
用户遇到「设备换位置 / 数据看起来丢了」
  │
  ├─ 设备行还在（未删除）
  │    └─ 用【编辑】改 node/channel ──> id 不变，历史天然连续   ← 主路径
  │
  └─ 设备行已被删除
       ├─ 想继续用这台设备 ──> 【恢复已删除设备】，选一个空闲槽位
       │      └─ 若槽位被占 → 要么换个槽位，要么下面这条
       └─ 想继续用新设备、只想保住旧数据 ──> 【合并历史】，源选旧的已删设备
```

## 六、给产品的问题清单

1. **G-3 最关键**：允许把「仍在采集的存活设备」的历史搬走吗？选①禁止 / ②显式确认 / ③搬完自动软删？
2. **G-2**：源 id 无效时，是报错还是继续静默成功？
3. **G-4**：同址有已删设备时，新建应该**拦截**、**警告**、还是**引导恢复**？
4. **G-5**：合并后要不要在源设备上留「已并入 #N」的痕迹？
5. **通道维度**：合并历史目前只关心「设备」，**不关心通道**。同一通道上先后接入过不同设备时，
   历史该按设备看还是按通道看？（当前：按设备，通道只是连接参数）

> **状态**：本文件最初是「现状实测 + 缺口清单，待产品裁决」。2026-10-25 产品负责人
> 反馈「合并历史数据、恢复已删除设备目前功能逻辑还有大问题！」后，本轮按下列裁决
> **全部实现并加回归**；权威契约见
> [.contract/logical-device-removal.md](../../.contract/logical-device-removal.md) §14。

| 问题（§六） | 裁决 | 落地 |
|---|---|---|
| G-3 允许把仍在采集的存活设备历史搬走吗？ | **完全禁止**（409）：在役设备历史被搬走会变成空壳、历史永久分裂；要收尾先删除（保留数据）再合并，只是换位置用「编辑」换节点。**2026-10-25 晚产品重做新增核心不变量：只能合并「已删除 + 与目标同型号」的设备**（跨型号 400；无设备行孤儿 400）；已删除 `allow_live_source`/自动退役路径 | ✅ |
| G-2 源 id 无效时报错还是静默成功？ | **报错**：源不存在且四张相关表都没有数据 → 400 并列出无效 id；「无设备行但有数据」的孤儿历史仍允许救援 | ✅ |
| G-1 源=目标？ | **400**（不再静默成功） | ✅ |
| G-4 同址有已删设备时新建应拦截/警告/引导？ | 恢复 409 文案已引导「改用合并历史」；**创建向导的同址已删设备提示未实现**（残余，见下） | ⏳ 部分 |
| G-5 合并后要不要在源设备留痕？ | **不加 `merged_into_id` 列**（避免再长出第二个 id 空间）；响应 `sources:[{id,state,device_type}]` + `warnings`；源设备记录本身不删（用户可自行删除/恢复） | ✅ |
| 通道维度：历史按设备看还是按通道看？ | **按设备**（不变；通道只是连接参数） | ✅ 维持 |

> **2026-10-25 晚：合并历史产品设计重做**。首轮实现有一个**根本性错误**：合并没有

> 而不是历史（已删除）设备 —— 产品负责人实测截图指出后要求「从头分析产品功能设计」。

> 前端合并弹窗改为「目标设备 → 同型号已删除历史设备」列表（服务端 `device_type` 过滤），
> 空态给出三条路径引导。设计文档：
> [docs/分析/合并历史-产品设计重做-2026-10-25.md](../分析/合并历史-产品设计重做-2026-10-25.md)。

### 8.1 本轮发现并修复的、不在 G-1..G-5 内的缺陷

三路独立审计（后端 12 条 / 前端 15 条 / 运行时矩阵 13 条，报告见 `.analysis/rr2/`）
另外确认了两个 P0：

1. **purge 与 restore 竞态**：purge 只在扫描时看一次 `deleted_at`，之后按内存快照删到底。
   用户在 purge 运行期间恢复设备 → 恢复返回 200 且 DB 已清标记，purge 仍把历史与设备行
   硬删（不可恢复）。修复：认领列 `data_purge_started_at` + restore 行锁互斥 + 条件删除。
2. **前端「合并历史」三处断路**：手输源 id 是 string（Go `[]uint` 绑定 400）；候选只列
   存活设备（新语义下全部 409）；data-summary 形状变更未同步（预览恒「—」+ 空表）。
   三处独立，只修一处功能仍不可用。

其余 P1：restore 缺 create/update 校验（可恢复到 disabled/GPIO/I2C 通道）、restore 每次
新建 ConfigTemplate 导致节点模板超固件上限（整节点 config sync 被拒）、换节点/恢复缺命令
容量门禁、merge 多源同名台账复合键冲突导致永久半迁移、merge 与 purge 不互斥、
data_sources manual 行被静默删除、data-summary 的 total 把目标自己算进「预计迁移」、
离线判定用 `created_at` 让刚恢复的设备立刻被判离线。

### 8.2 残余（明确未做）

1. **创建向导的同址已删设备提示**（G-4 前半）：新建时若同址存在已删设备，仍不提示
   「有历史 N 行，可恢复」。当前出口是删除/恢复 409 文案与「合并历史」入口。
2. **合并历史后台任务化/进度**：仍是同步长请求（请求上下文可取消、分批幂等），
   百万行级需要前端提示耗时；未做后台任务 + 进度轮询（避免复活 merge_jobs 概念）。
3. **DevicePurger 多实例**：认领协议按单实例部署设计（每轮清 >1h 陈旧认领）。
4. **生产部署**：本轮改动未上生产，需按 runbook 走（新增列 `data_purge_started_at` 由
   AutoMigrate 创建，接受 NULL）。
