## 2. 编码格式（§4.2，含一处必要的扩展）

```
+--------+------------------+----------------------------+
| 1B     | ceil(N/8) B      | 剩余                       |
| flags  | changed_mask     | 变化字段量化值（LSB-first）|
+--------+------------------+----------------------------+
```

- `flags`: bit0=关键帧；**bit1=附加 invalid_mask**（见下）；bit2..7 保留，非 0 一律拒解。
- `changed_mask`: 第 i 位 = 字段 i 本帧变化（bit0 = 字段 0，LSB-first）。
- 位流：仅在 changed 字段上按 slot 顺序写码点，无对齐填充。

### 2.1 对 §4.2 的扩展：invalid_mask（必要性说明）

§4.2 只定义了 changed_mask，隐含假设"每个字段每帧都有值"。真实数据里 NaN 是可能的
（驱动升级、部分解析、位序错位）。若把 NaN 塞进量化，`math.Round(NaN)` 的码点是
实现相关的 —— 那是**静默错值**，比丢字段危险得多。

因此：**正常帧（无 NaN）flags.bit1 = 0，字节布局与 §4.2 完全相同，零额外开销**；
只有出现 NaN/Inf 时才多一段 ceil(N/8) 的掩码。该字段既不进 changed_mask 也不占位宽，
解码侧表现为"本帧该字段无值"（而非塞一个假 0）。

实测：真实数据 24h 里 **0 帧**触发该扩展（见 §4 的往返结果），所以对 §4.5 的体积数字无影响。

### 2.2 量化规则（§4.3）

```
code  = round((v - Min) / Step)   ∈ [0, 2^Bits-1]
value = Min + code * Step
⇒ 最大绝对误差 = Step/2
```

越界值被夹到边界**并计数**（`EncodeStats.ClampedValues`）——夹边界是真实精度损失，
验收要求真实数据上为 0（实测为 0）。

## 3. slot 字典（§4.4）：为什么不能硬编码

签名 = `sha256(command_template_id │ spec_version │ 排序后的字段名列表)[:32]`。

命中三层区分：
1. **command_template_id**（指令级粒度）——实测正好一一对应 device15 的 7 种帧类型；
2. **字段名集合**——最后一道保险，指令模板复用也不会撞；
3. **spec_version**——规格演进后旧 slot 不被新码点污染。

不含设备 ID：同型号多设备共享 slot（实测 device14/device15 各 1 台，若无共享需求也无害）。

**实测验证**（`TestRealDataSlotDictionary`）：

| 设备 | 帧类型数 | 字段数分布 |
|---|---:|---|
| device14 | **1** | [29] |
| device15 | **7** | [2 3 4 5 9 14] |

与方案 §4.4 的表格（device14 = 1；device15 = 7 种，3/14/2/5/5/9/4 字段）**逐项吻合**。

> 硬编码槽位会怎样：device15 的 7 种帧共用一个 slot ⇒ 同一 slot 内字段集合逐帧变化 ⇒
> 变化抑制失效（几乎每帧全变化）**且解码位流错位** ⇒ 值写串。测试里
> `TestSlotSignatureDistinguishesCommandTemplate` 钉住"不同 command_template_id 必须不同签名"。

4. **相对现状放大倍数**：用方案 §1.2 的 178.7 B/行口径估算（device14 2,503,918 行/天 ×

> 行头（PG 24 B/行）+ 主键索引 + 部分索引 + 页填充。

> **本实现不负责也不声称 L1 的跳过收益**（那是 task-2 的范围）。

### 4.4 压缩比分解（为什么 29 字段只花 16 字节）

device14 全天平均只有 **6.77 个字段发生变化**（29 个字段里），所以：
- changed_mask 固定 4 B（29 位）
- 位流 ≈ 6.77 个字段 × 平均 14.9 位 ≈ 12.6 B
- flags 1 B
⇒ 平均 16.15 B。放大倍数的消除来自两件事：**一帧一行**（29×）+ **变化抑制**（在本数据上又省 ~4.3×）。

## 5. 解码层（§5.1）实现与护栏

方案签名 vs 实现的差异（**只有一处**，已在代码注释中说明）：

```go
// 方案：func DecodeRange(ctx, db, deviceID uint, from, to time.Time, fields []string) ([]Point, error)
// 实现：多一个 dict SlotDictionary 参数（slot 字典由调用方注入 —— 本包不 import
//      sensorfield/api/database，数据面零依赖红线）
func DecodeRange(ctx context.Context, db *gorm.DB, dict SlotDictionary, deviceID uint,
                 from, to time.Time, fields []string) ([]Point, DecodeStats, error)
func LatestSnapshot(ctx context.Context, db *gorm.DB, dict SlotDictionary, deviceID uint) (map[string]float64, DecodeStats, error)
```

`DecodeStats` 是方案没有的**可观测性补充**：增量链解错时不会报错，只会产出错位值，
所以把"坏帧数/断链跳过数/无基线字段数"做成显式计数（影子校验要求全为 0）。

### 5.1 硬护栏（防止一次图表请求打爆内存）

| 护栏 | 值 | 依据 |
|---|---|---|
| 单次窗口上限 | `MaxDecodeWindow` = 24 h | 方案 §5.1：30 天解码后 570 MB ⚠ |
| 单次帧数上限 | `MaxDecodeFrames` = 32,768 | ≈ 6 h @1Hz；超限保留最新部分并计入 stats |
| 空窗 / 已取消 ctx | 直接拒绝 | — |

超窗返回 `RangeTooLargeError`（提示调用方走 rollup），而不是静默变慢。

### 5.2 断链处置（§8）

坏 payload ⇒ 该 slot 的链标记失效 ⇒ **丢弃后续增量帧直到下一个关键帧**，并计数。
测试 `TestDecodeBrokenChainSkipsToKeyFrame` 钉住：坏帧后的两个合法增量**不得**产出读数
（否则就是错位数据），且跳到关键帧后值必须完全正确。

## 6. 双写旁路（§7 阶段 2 第 2 步）

**默认关闭**。三条硬约束：

1. `EHOME_TELEMETRY_DUAL_WRITE` 未设置/非真值 ⇒ `NewDualWriterFromEnv` 返回 **nil**，调用方拿到 nil 什么都不做（零成本）。
2. 失败不影响主写入：编码/写库错误全部吞掉并计数，绝不返回给写路径。
3. 不阻塞写路径：`Observe` 只投递到有界队列（默认 4096），满则丢弃 + 计数，**绝不反压**。

启动前置条件（缺一不可）：① 分区母表已建（否则返回 `ErrTablesMissing` ⇒ 安静禁用，不报错）；
② 开关打开；③ 磁盘余量（双写期两份数据）；④ `EHOME_TELEMETRY_HEARTBEAT_SECONDS` 与 L1 同源。

观测：`DualWriter.Stats()` 的 `Encoded / Dropped / Failed / PayloadSum`。
**影子校验要求 Dropped == 0 且 Failed == 0**。

### 8.1 精度偏差明细（必须让评审看到）

按方案 §4.3 标定的规格，与真实数据实测值域/最小步长逐字段核对后，发现 **1 处真实精度损失**：

| `current` | −48.9–34.66 A | 0.01 A | 0.01 | 16 | ✅ 无损 |
| `total_voltage` | 49.01–55.75 V | 0.01 V | 0.01 | 15 | ✅ 无损 |

| `rsoc` | 0–100 | 1 | 1 | 7 | ✅ 无损 |
| `cycle_count` / `fet_status` / `protection_status` | 0–65535 | 1 | 1 | 16 | ✅ 无损 |
| `grid_voltage` / `output_voltage` | 210.3–249.8 V | 0.1 V | 0.1 | 13 | ✅ 无损 |

| **`daily_energy`** | 0–11.004 kWh | **0.001 kWh** | **0.001 kWh** | **19** | ✅ 无损（**已按实测修正方案**，见下） |
| `monthly_energy` / `total_energy` / `yearly_energy` | 0.2–4773.1 kWh | 0.1 kWh | 0.1 kWh | 24 | ✅ 无损 |

**`daily_energy` 的修正依据与代价**：

- 方案 §4.3 把 `*_energy` 统一标为 0–1e6 kWh / 0.1 kWh / 24 位；
- 生产实测（2026-11-04 全天 device15，7,336 个值）逐字段核对**最小差分**：
  - `daily_energy` 0–11.004 kWh，最小差 **0.001 kWh** ⇒ 方案标定的 0.1 **粗了一个数量级**；
  - `monthly_energy` 0.2–35.6 kWh、`total_energy` 4737.7–4773.1、`yearly_energy` 2336.1–2371.5，
    最小差都是 **0.1 kWh** ⇒ 方案标定**正确**。
- 因此只对 `daily_energy` 单独登记 `spec(0, 0.001, 19)`（`exactSpecs` 优先于 pattern 表）：
  - **无损**：与真实分辨率逐位对齐（半步误差 0.5 mWh）；
  - **更省**：19 位 < 方案给的 24 位，该字段每帧省 5 位；
  - 量程 524.287 kWh 足够（实测最大 11.004 kWh，即便户用日发电量翻百倍也不越界；
    越界会被 `ClampedValues` 计数暴露，不是静默截断）。

**修正后实测**：device15 全量 307,970 个值 **0 超差、0 缺失**，最大绝对误差 9.1e-13（浮点噪声）。

> 这是本任务对方案 §4.3 的**唯一一处修正**，且方向是"按实测把标定改准"，
> 不是放宽验收。其余 16 类字段的标定全部经实测复核无误（见上表）。
