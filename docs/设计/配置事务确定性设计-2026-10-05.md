## 0. 结论摘要

| 项 | 设计 | 解决的实测问题 |
|---|---|---|
| 事务 arena | `main/` 内固定 **4 KiB** 单块 bump arena（s3p 用 `collector_mem_alloc_pref_psram`，其余内部静态 `.bss`），事务临时对象承载于它；结束只 reset 游标 | 消除 `tx` 792 B 的堆分配（唯一剩余消费者）；事务成败不再依赖当时堆碎片 |
| 回滚快照 | **不用拷贝、不用帧副本、不写 NVS**：`stage` 只写 inactive，`commit` 是最后一步且失败不翻转，所以 rollback 直接用 `config_mgr_get_manifest()` 的**活指针**；保留 `config_mgr_snapshot_active()` 兼容 API，但事务路径不再调用它 | 事务内 manifest 相关堆峰值 5,400 B → 0；`config_mgr` 不新增 `.bss`，也不占用 arena 固定区 |
| 水位门禁 | 事务 `begin` 前一次性 preflight；每步执行前用 `mem_guard_can_start(need)` 复检（WS-G `main/mem_guard.h`：s3p 16K / s3 8K / c6 12K） | 水位不足时在**变更前**拒绝，返回 `CONFIG_APPLY_FAILED_UNCHANGED`；prepare 之后的步骤拒绝改走 rollback，避免"假 UNCHANGED" |
| UART 驱动复用 | 驱动 install 一次；配置变更只走 `uart_set_pin` / `uart_param_config` / `uart_set_baudrate`；仅"通道删除/控制器变更"或 factory reset/显式 teardown 才真正释放；新增事务前 `preinstall` 步骤 | 消除 apply_buses 中 3 路 UART 的 ~9.3 KiB 反复 install/delete；稳态 apply_buses 目标 ≤ 4 KiB |

## 2. 事务 arena 精确设计

### 2.1 职责与不变量

- **只承载"事务生命周期内"的临时对象**：一期唯一消费者是 `manifest_tx_ctx_t`（792 B）；`periph_config_workspace_t` 与 ResourceReport 缓冲为 phase 1.5（§2.5）。
- **只 reset 游标，不 free**：不产生归还给堆的中间态，因此不存在"释放顺序/碎片"依赖。
- **单写者**：事务由 `app_state_lock_config()` + `periph_owner_transaction_begin()` 串行化；arena 的 bump 区只在锁内使用，不要求线程安全（用 `s_in_tx` 断言防护）。
- **单一 bump 区**：4 KiB 全部为 bump 区，`begin` 归零；没有固定保留区。

### 2.2 大小推导（Lead 裁决：4 KiB）

Lead 复核事务时序后确认：**回滚不需要 old_snapshot 拷贝，也不需要帧副本**（见 §3），因此 arena 的唯一消费者是 `manifest_tx_ctx_t`（792 B）。4 KiB 的推导：

| 组成 | 字节 | 依据 |
|---|---:|---|
| `manifest_tx_ctx_t` | 792 | §1.3 实测 |
| 16 B 对齐/游标开销 | ≤32 | bump 指针本身 |
| 未来向 tx ctx 追加少量快照字段的余量 | ~256 | 例如新增一个 32 通道状态位图/计数器 |
| **实际使用** | **≈1,080** | 792+32+256 |
| **4 KiB 余量倍数** | **3.8×** | 即使 `manifest_tx_ctx_t` 因后续改动翻倍也仍够 |

```c
#define CONFIG_TX_ARENA_BYTES   4096u
_Static_assert(CONFIG_TX_ARENA_BYTES >= 1152u, "tx arena too small for manifest_tx_ctx_t + headroom");
```

**不放进 arena 的东西**（一期明确不做，理由见 §2.5 与 §6.2）：

- `periph_config_workspace_t` 464 B（`periph_config_apply.c`，跨组件边界，phase 1.5）；
- ResourceReport 1024 B 缓冲（`handler_config.c`，同上）；
- 活动帧副本 / NVS blob（Lead 裁决删除：live 结构体即权威，见 §3）；
- `periph_config_workspace_t` 与 ResourceReport 缓冲（phase 1.5，见 §2.5）。

### 2.3 放置（PSRAM / 内部）

| profile | 承载 | 生命周期 |
|---|---|---|
| `COLLECTOR_MEM_PSRAM_ENABLED`（s3p） | `collector_mem_alloc_pref_psram(CONFIG_TX_ARENA_BYTES)`（helper 已存在于 `components/config_mgr/collector_mem.h`：先 `MALLOC_CAP_SPIRAM\|MALLOC_CAP_8BIT`，失败回退 `MALLOC_CAP_INTERNAL`）；再失败则 arena 不可用，事务拒绝并上报 | 首次使用时分配，常驻，不 free（4 KiB） |
| 非 PSRAM（s3/c6） | `static uint8_t s_arena_mem[CONFIG_TX_ARENA_BYTES] __attribute__((aligned(16)))`，`.bss` 静态预留 | 常驻 |

为什么 s3p 采用"首次使用时懒分配"而不是 boot 分配：`main/main.c` 归 task-6（Lead 已裁决），本任务不修改它；配置事务发生在 WiFi 起来之后，PSRAM 池（8 MB）此时无碎片压力。helper 失败只可能是 PSRAM 初始化失败（task-2 的 `SPIRAM_IGNORE_NOTFOUND=y` 降级场景），此时回退内部；两条都失败才拒绝事务——**不把"事务确定性"建立在"启动顺序恰好"上**。

新增 `main/config_tx_arena.h`（纯声明，随 `config_apply_transaction.c` 一起编译，**不需要改 `main/CMakeLists.txt`**），API：

```c
bool config_tx_arena_init(void);          /* 幂等；false = arena 不可用 */
bool config_tx_arena_begin(void);         /* reset bump 游标 + canary；重入返回 false */
void config_tx_arena_end(void);           /* 只 reset 游标；断言 canary 完好 */
void *config_tx_arena_alloc(size_t n);    /* 16B 对齐；越界返回 NULL（不改游标） */
size_t config_tx_arena_high_water(void);
bool config_tx_arena_can_reserve(size_t n);
```

### 2.4 reset 语义与失败安全

1. `config_tx_arena_begin()`：若 `s_in_tx` 已为 true → 返回 false（防重入）；`cursor=0`；写 canary `0xC0FFEE00` 于 bump 区末尾 4 B；`s_in_tx=true`。事务前调用方先 `config_tx_arena_can_reserve(sizeof(manifest_tx_ctx_t)+32)` 做静态预算判定。
2. 每次 `alloc` 前检查 `cursor+aligned(n)+4 <= bump_capacity`；失败返回 NULL，**不改 cursor**（失败可安全重试）。
3. `config_tx_arena_end()`：检查 canary；`cursor=0`；`s_in_tx=false`。**不释放内存**。canary 损坏 → 返回 false 并**latch 不可恢复**（`init()` 不会清除；主机测试用 `config_tx_arena_test_clear_fault()` 模拟重启）。
4. 事务失败（任意 rollback 结果）：`app_callbacks` 在解锁前必调 `config_tx_arena_end()`；因此"失败后 arena 可立即重用"由**同一函数语义**保证，并有单测（§7.2）。
5. 地址断言：
   - s3p：`assert(addr >= SOC_EXTRAM_DATA_LOW && addr < SOC_EXTRAM_DATA_HIGH)`（PSRAM 窗口内）；
   - 非 PSRAM：`assert(!(addr >= SOC_EXTRAM_DATA_LOW && addr < SOC_EXTRAM_DATA_HIGH))`（S3 内部 DRAM 地址**高于** `SOC_EXTRAM_DATA_HIGH`，不能写 `addr < LOW`；task-2 实测踩过）。
6. 首笔事务与后续事务的 arena 需求相同（都是 `manifest_tx_ctx_t`），不再区分有无 old。

| 时点 | 失败 | 行为 |

## 3. 回滚快照设计（Lead 裁决：live 指针，无拷贝 / 无帧副本 / 无 NVS 写入）

> 标题原为"NVS 回滚快照"；经 Lead 复核事务时序，一期实现为**活动 manifest 活指针回滚**。NVS 帧持久化仅作为"未来需要跨重启回滚"的二期候选保留在 §3.4。

### 3.1 事实前提（代码证据，task-3 落盘后行号）

1. `config_mgr_stage_manifest()`（`config_mgr.c:108` 起）只写 **inactive** slot（`inactive_manifest()`），**active 在整个 stage+apply 过程中保持有效**；
2. `config_mgr_commit_staged_manifest()`（`config_mgr.c:146`）在事务链**最后一步**（`config_apply_transaction.c:147-150` 的 `commit_manifest`）才翻转 `s_active_idx`；
3. commit 失败路径（`s_staged_idx < 0 || !manifests_ready()`）**不翻转 active**；
4. commit 之后没有可失败的步骤（`scheduler_activate()` 无失败路径），且 `commit_manifest` 是最后一步，因此**现行步骤序下 rollback 永远发生在 commit 之前**，`config_mgr_get_manifest()` 返回的指针在整个事务内有效、内容从未被写者触碰；
5. 事务期间有 `app_state_lock_config()` 与 `bus_worker_suspend()` 双重串行化，不存在并发 stage/commit；
6. 本仓"NVS 只有同步元数据，不存 manifest 帧，启动不从 NVS 载入配置"（`config_mgr.c` NVS 段、`msg_handler.c` 注释），回滚**不依赖** NVS。

**结论：活动 slot 本身就是事务前配置的权威副本。回滚直接用活指针，不需要任何拷贝、帧副本或 flash 写入。**

### 3.2 `handle_config_applied` 的改动

```c
/* 旧（删除）：
 * config_manifest_t *old_snapshot = calloc(1, sizeof(*old_snapshot));
 * ...
 * bool had_old = config_mgr_snapshot_active(old_snapshot);
 */
/* 新：stage 只写 inactive；commit 最后翻转。因此该指针在 rollback 时
 * 仍指向事务前配置，且无并发写者（config 锁 + worker suspend）。 */
const config_manifest_t *active_cfg = config_mgr_get_manifest();
bool had_old = active_cfg && active_cfg->applied;
...
config_apply_result_t tx_result = config_apply_transaction_execute(
    &s_manifest_tx_ops, tx, had_old ? active_cfg : NULL, staged_cfg);
```

- `manifest_tx_ctx_t` 由 4 KiB arena bump 分配（§2）；
- 事务失败分支（现 L390-412）删除全部 `free(old_snapshot)` / `free(tx)`，统一在退出前 `config_tx_arena_end()`；
- **不新增** `config_mgr_restore_active_frame()` / generation（Lead 裁决简化，避免为不可达场景增加 API 面积）。若将来步骤顺序被重排到"commit 之后仍有可失败步骤"，必须重新评审本前提——在 `config_apply_transaction.h` 的 `commit_manifest` 注释里写明这条约束。

### 3.3 `config_mgr_snapshot_active()` 兼容处理

保留原签名与原实现（host 用例 `config_manifest_pwm_tests.c:124` 仍在用），只把头文件注释改为：

```c
/* Copy active state into caller storage so staged commit cannot invalidate
 * rollback input. Intended for bounded heap transaction workspaces.
 * NOTE(WS-E): the config transaction no longer uses this; rollback uses the
 * live active pointer because stage() only writes the inactive slot and
 * commit_staged_manifest() is the transaction's last step. Kept as a
 * compatibility API for tests/other callers. */
bool config_mgr_snapshot_active(config_manifest_t *out);
```

任务卡要求"`snapshot_active()` 的用法要相应调整（或保留兼容 API 但不再用于事务路径）"——本设计同时满足：用法调整（事务路径删调用）+ 兼容 API 保留。

### 3.4 二期候选：NVS 帧持久化（一期明确不做）

触发条件：只有出现"事务已 commit 成功、但设备在应用运行态建立前掉电，要求重启后回到上一份配置"的需求时才值得做。届时的设计要点（仅记录，不实现）：

- `NVS_KEY_ACTIVE_FRAME "cfg_frame"` blob ≤2048 B（NVS `CHUNK_MAX_SIZE=ENTRY_SIZE*(ENTRY_COUNT-1)=32*125=4000 B`，`nvs_page.hpp:37`；2048 单 chunk 可存）；
- 写入时机：commit 成功后、发布 `ConfigResult(true)` 前（与 `sync_manager_on_config_applied` 同段）；
- 读取时机：boot 时仅在显式"回滚模式"下读入 inactive 再 commit（默认仍 server-is-truth）；
- 代价：每次配置一次 flash 写（2 KB），且需处理掉电半写（blob 长度校验 + CRC）。

### 3.5 为什么这不会退化"事务确定性"

- 回滚路径不再有任何堆分配或 flash 操作：指针 + 幂等重建调用；
- 原先 5,400 B 的 active 拷贝被删除，是**净收益**（事务内 heap 峰值减少 5,400 B）；
- 唯一新前提是"commit 是最后一步"；该前提当前由 `config_apply_transaction.c` 的代码结构保证，并以注释形式固化。

## 4. 水位门禁设计

### 4.1 接口（由 WS-G 提供，本任务只调用）

`main/mem_guard.h`（已落盘）：

```c
size_t mem_guard_largest(void);
size_t mem_guard_free(void);
size_t mem_guard_floor_bytes(void);
bool   mem_guard_can_start(size_t need_bytes); /* largest >= max(need, floor) */
```

floor：**s3p ≥8 KiB** / s3 ≥8 KiB / c6 ≥12 KiB（`main/mem_guard.c`）。⚠ 2026-10-08 重定：s3p 原 16 KiB **不可达**（3.0 稳态 largest min 12288 < 16384）⇒ 门禁永久关闭；按 largest 口径重定为 8 KiB（与同芯片的 s3 一致，实测 893 s 无失败）。详见 `决策-3.0-s3p-内部RAM-2026-10-07.md` §13。本任务**不直接调用** `heap_caps_get_largest_free_block` 做判决。

### 4.2 两阶段门禁（为什么不能中途直接返回 UNCHANGED）

任务卡字面要求"每步前检查，低于阈值直接返回 `CONFIG_APPLY_FAILED_UNCHANGED`"。但代码事实是：

- `tx_prepare`（`app_callbacks.c:92-96`）已经 `scheduler_stop()`；
- 之前步骤可能已 `apply_dma`/`apply_peripherals`/`cleanup_buses`；
- `config_apply_transaction.c:84-87` 的注释明确：prepare 失败必须 `FATAL`，不能 `UNCHANGED`，因为状态已 partial。

因此设计为**两阶段**，既满足"每步检查"，又不产生"谎报 UNCHANGED"：

1. **Phase A（变更前，真正 UNCHANGED）**：`config_apply_transaction_execute` 在 `ops->begin_transaction()` 之前，对**所有步骤的 need 取最大值**做一次 `mem_guard_can_start(max_need)`；失败 →
   ```c
   ESP_LOGW(TAG, "[memgate] preflight step=%s need=%u free=%u largest=%u floor=%u rc=UNCHANGED", ...);
   return CONFIG_APPLY_FAILED_UNCHANGED;
   ```
   调用方（`handle_config_applied`）在调用 execute 前已 `bus_worker_suspend()`——Phase A 失败时按现状 L407-411 解锁并 `bus_worker_resume()`，manifest/runtime 未变。
2. **Phase B（每步执行前，防御性复检）**：在 L102/110/119/128/137/147 每步调用 `ops` 之前 `mem_guard_can_start(step_need)`；失败时**按步骤失败处理**：打结构化日志，然后 `return rollback(...)`：
   ```c
   ESP_LOGW(TAG, "[memgate] step=%s phase=pre need=%u free=%u largest=%u floor=%u rc=ROLLBACK", ...);
   ```
   结果只能是 `FAILED_RESTORED` / `FAILED_SAFE` / `FATAL`，**绝不允许 UNCHANGED**。这是与任务卡字面要求的一处有意修正，理由即上述代码注释中的既有契约；**需 Lead 在评审时确认**。

### 4.3 每步 need（按型号，floor 由 mem_guard 内部选取）

| 步骤 | need | 依据 |
|---|---:|---|
| preflight 汇总 | `CONFIG_TX_MAX_STEP_NEED` = 4096 | apply_buses 稳态最大项（SPI 1,352 + I2C 1,424 ≈ 2,776，取 4 KiB 上界） |
| `apply_dma` | 0 | `dma_pool_*` 无堆分配（`dma_pool.c` 仅数组与 mutex） |
| `apply_peripherals` | 1,024 | gpio/pwm 控制器内部对象；现场该步实测 −372 B（b1896ce） |
| `apply_buses` | 4,096 | SPI2 ~1.35K + I2C0 ~1.42K（arena 方案下 UART 走 preinstall，不再计 12K）；4 KiB 为目标上界 |
| `apply_scheduler` | 0 | `scheduler.c` 任务栈为 `xTaskCreateStatic`（L215/L312），通道数组静态 |
| `apply_log_stream` | 2,048 | log_tx 静态任务（`log_stream.c:112-113`），但 publish/队列路径有 1024B 级报文缓冲 |
| `commit_manifest` | 0 | NVS 持久化不在事务内（§3.4） |
| rollback: `apply_buses(old)` | 4,096 | 同 apply_buses |
| rollback: `restore_peripherals` | 1,024 | 同 apply_peripherals |

型号差异由 `mem_guard_can_start` 的 `max(need, floor)` 自动施加：s3 `max(need,8K)`、c6 `max(need,12K)`、s3p `max(need,16K)`。

### 4.4 冷启动 preinstall 的门禁（UART，§5 前置）

第一笔配置前 UART 尚未 install，install 3 路约 9.3 KiB 是**一次性不可避免成本**。设计把它从 `apply_buses` 里剥离为显式 `preinstall` 步骤（在 suspend 之前），单独门禁：

- 每缺一路 UART，install 前要求：
  - `mem_guard_can_start(CONFIG_TX_UART_INSTALL_LARGEST_NEED = 3584)`（单路 9 个小对象中最大的 ≤512B，3,584 为保守上界）；
  - 且 `mem_guard_free() >= CONFIG_TX_UART_INSTALL_TOTAL_PER_PORT(3200) * remaining_ports + mem_guard_floor_bytes()`（总量约束，`largest` 单指标会漏掉"总量被逐个小分配吃光"）。
- 任一不满足 → 打 `[memgate] step=preinstall ... rc=UNCHANGED`，**在 suspend 之前**返回 `UNCHANGED`，发 `ConfigResult(false)`。
- preinstall 成功后，`apply_buses` 内的 UART 只做 lease 绑定/参数复用，峰值回到 ≤4 KiB。

### 4.5 OTA / log_stream 启动点

- **log_stream**（本任务写范围内，`app_callbacks.c:157-207`）：在 `log_stream_apply_state(enabled=true)` 且当前未运行、准备 `log_stream_start()` 之前调用 `mem_guard_can_start(2048)`；失败 → WARN `[memgate] step=log_stream ... rc=SKIP`，**不启动日志**并继续事务（沿用 L137-154 既有语义：日志是诊断旁路，不能把配置事务拖垮）。关闭日志不需要门禁。
- **OTA**：启动点在 `components/msg_handler/handler_data.c`（当前 L92 `ota_start(cmd)`）。**Lead 2026-10-05 已批准本任务改这一行**（mem-verify 已放弃该文件）：`ota_start()` 前 `mem_guard_can_start(OTA_TASK_STACK_BYTES + 4096)`（OTA 任务栈静态，但 HTTP client 1024/512 连续块 + esp_ota 内部对象；`ota.c:628-633` 已有"largest 只 1024 时 Allocation failed"的实测）。失败走 `reject:` 路径，打 `[memgate] step=ota ... rc=REJECT` 并释放 cmd，不启动 OTA。
- 失败上报：运行时返回 `CONFIG_APPLY_FAILED_UNCHANGED`；对服务端由 `msg_handler_send_config_result(false)` 即时可见；持续水位由 `mem_guard_poll()`（status_task 1 Hz）触发 `MemReport(0x20)`（task-6 已实现）上报 free/largest/floor。本任务不改 StatusReport 字段。

## 5. UART 驱动复用设计

### 5.1 现状调用链（代码引用）

```
handle_config_applied (app_callbacks.c:388)
  -> config_apply_transaction_execute
       -> tx_apply_buses (app_callbacks.c:117-120)
            -> bus_manager_apply_manifest (bus_manager.c:871)
                 -> bus_manager_cleanup_all (L904 -> L815)
                      -> per slot: bus_dma_deinit (bus_dma.c:1711)
                           -> uart_deinit (bus_dma.c:640)  ref_count-- == 0
                                -> uart_driver_delete()          <-- 释放 9 个堆对象
                 -> reg_bus_channel (L922 -> L692)
                      -> bus_dma_init_preferred (bus_dma.c:1605)
                           -> uart_init (bus_dma.c:373)
                                -> uart_find_port() 找不到（entry 已被清）
                                -> uart_param_config + uart_set_pin + uart_driver_install (L537) <-- 重新分配 9 个对象
```

每次配置事务对 3 路 UART 完整 delete+install，实测每路 −3.0~3.1 KiB。

### 5.2 新生命周期契约：install 一次

注册表 `uart_port_entry_t`（bus_dma.c:323-332）新增：

```c
bool installed;   /* 驱动对象已分配；跨 manifest 保留 */
bool leased;      /* 当前有逻辑通道租约 */
/* 已有 port/tx_pin/rx_pin/baud/ref_count/event_queue 保留 */
```

四条不变式：

1. **install-once**：同一 `uart_port_t` 的 `uart_driver_install` 在进程内最多调用一次；之后所有配置变化走 `uart_set_baudrate` / `uart_param_config` / `uart_set_pin`（IDF 6.1 三者均可在 driver installed 后调用：`uart.c:384/1058/862`，均不重新分配 ring buffer）。
2. **lease 与 install 解耦**：`bus_dma_deinit()` 的行为从"释放驱动"改为"归还租约"（`leased=false; ref_count--`），**不** `uart_driver_delete`。
3. **teardown 只发生在两处**（Lead 要求保留显式释放，避免"驱动永不释放"的语义漂移）：
   - 成功 apply 新 manifest 之后，旧 manifest 里存在、而新 manifest 不再租用的 UART 端口（通道删除 / 控制器变更），由 `bus_manager_prune_unused_uarts(rt)` 对每个 `installed && !leased` 端口调用 `bus_dma_uart_teardown(port)`；
   - **factory reset / 未来显式整机 teardown**：`factory_reset` 目前是 `nvs_erase_all → esp_restart()`（`factory_reset.c:195`），重启会重建一切，因此一期**不新增**调用点；但 `bus_dma_uart_teardown()` 作为公开 API 保留，并在头文件注释中说明"整机生命周期结束/控制器移交时调用"。安全状态与 rollback **不** teardown（回滚后旧端口还要用；safe state 保留 idle 驱动，代价是 ~3 KiB/路，换取致命路径不再做堆操作）。
4. **参数变更的失败回滚**：`uart_reconfigure()` 先备份 entry 里的旧 tx/rx/baud，调用序列任一失败则用旧值 `uart_set_pin`/`uart_set_baudrate` 回写，返回错误；上层事务 rollback 随后用 `old_manifest` 再走一遍同样路径（幂等）。

### 5.3 新函数拆分（bus_dma.c）

| 函数 | 职责 |
|---|---|
| `uart_find_installed(uart_port_t)` | 在注册表中按 port 找已 install 的 entry（新增） |
| `uart_port_acquire(ctx, cfg, len)` | 解析/校验 pin+baud；解析目标 controller（沿用 `preferred_controller`/`hw_derive_uart_port` 逻辑，L394-441 原样保留）；处理 pin/controller 冲突；install（仅缺失时）或 reconfigure；`leased=true; ref_count++` |
| `uart_reconfigure(entry, tx, rx, baud, dma)` | 已 install：`uart_wait_tx_done` → `uart_set_pin` → `uart_param_config` → `uart_set_baudrate`；无需 install |
| `uart_deinit(ctx)` | 改名语义为 `uart_release_lease`：ref--、`leased=false`、不改 installed、不 delete |
| `bus_dma_uart_teardown(uart_port_t port)`（新公开 API） | 仅当 `installed && !leased`：`uart_driver_delete` + 清 entry（供 prune 调用） |

预分配 `preinstall` API（新公开）：

```c
/* bus_dma.h */
/* 只为 manifest 中 enabled 的 UART 通道预安装驱动控制器（不绑定通道租约）。
 * 调用方须已通过资源 preflight；成功后可安全地让本次事务只做参数复用。 */
esp_err_t bus_dma_uart_preinstall(uint8_t tx_pin, uint8_t rx_pin, uint32_t baud,
                                  bool dma_enabled, int32_t preferred_controller,
                                  uart_port_t *out_port);
```

> **实现修正（2026-10-05，实机前代码审查发现）**：preinstall **只安装、不重配**。
> 早期版本对已安装但"仍被旧 manifest 租用"的控制器直接 `uart_reconfigure()`，
> 命中租约保护而被拒绝 —— 于是任何"只改波特率"的 manifest 都会在 preinstall
> 阶段整笔失败（旧 manifest 的租约要到 apply_buses 内的 cleanup 才释放）。
> 现语义：preinstall 对已安装控制器一律 no-op（参数变更留给 acquire，在
> cleanup 释放租约之后执行；重配本身不分配堆，不需要提前）。回归测试
> `test_preinstall_does_not_touch_leased_controller` + `test_acquire_reconfigures_unleased_controller` 钉住该语义。

### 5.4 与 `bus_worker_suspend/resume` 的交互

现有契约（`bus_worker.c:1773-1826`）：

- `suspend`：置 `s_suspend_requested` → 等所有 worker 确认 → `destroy_uart_event_set()`（把 event queue 从 queue set 摘除）；
- `resume`：`rebuild_uart_event_set(rt)`，重建前**先 drain** 每个 event queue（L717-742 注释：queue set 不接受非空队列，drain 防自锁）。

驱动常驻后的新交互：

1. suspend 前：UART driver 已安装（preinstall 或历史遗留），ISR 持续把字节写进 driver ring/event queue；
2. suspend 后：worker 不再消费，事件队列可能积压（深度 8）。**不删除驱动、不删 event queue**，所以不存在"worker 引用已删队列"的竞态；
3. apply 期间：`uart_set_pin/param/baud` 在 worker 已停时执行，不与其 `uart_read_bytes` 竞态；
4. resume 时：`rebuild_uart_event_set()` 先 drain 再 `xQueueAddToSet`，积压事件被安全丢弃（对应数据已进 driver ring 或数据本就属于变更窗口，符合"配置变更即重置流边界"）；
5. `bus_worker_suspend` 返回 false（超时）时：不进入 apply，driver 与队列原样保留，语义不变。

**不改 `bus_worker.c`**：新契约只要求它继续在 suspend 摘队列、resume drain 重建；`bus_worker_discard_queued()`（L1837）仍由 `tx_cleanup_buses` 调用。

### 5.5 `bus_manager` 侧改动

- 新增 `bus_manager_preinstall_uarts(bus_runtime_t *rt, const config_manifest_t *m)`（公开）：
  1. `validate_manifest_resources(rt, m, NULL)`（bus_manager.c:378 已有，副作用为 0，会拒绝 pin/controller 冲突）；
  2. 对每个 enabled 且 `bus_type==UART` 的通道，若目标端口未 installed，按 §4.4 门禁逐路 `bus_dma_uart_preinstall()`；任一路失败 → 返回错误（事务在 suspend 前终止，UNCHANGED）。
- `bus_manager_apply_manifest()`（L871）：
  - L904 `bus_manager_cleanup_all()` 现在只是逐 slot 释放租约，不再删驱动；
  - 成功路径 L941 之后调用 `bus_manager_prune_unused_uarts(rt)`：扫描新 manifest 租约集合，对 `installed && !leased` 的 UART 逐个 `bus_dma_uart_teardown()`；
  - 失败路径（L935-938）保持"cleanup_all + 返回错误"，**不 prune**，避免回滚还没做完就把旧端口删掉。
- `bus_manager_cleanup_all()`（L815）：语义改为"释放所有通道租约 + 释放 DMA + 清 slot"，不再删除 UART 驱动对象；SPI/I2C 保持现状（不在本任务目标内，实测合计 2.8 KiB，满足 apply_buses ≤4 KiB）。
- `bus_manager_unreg_channel()`（L948）：释放租约后调用 `prune_unused_uarts`。

### 5.6 回滚路径

- 事务失败 → `rollback()` → `tx_cleanup_buses` → `bus_manager_cleanup_all`（只释放租约）→ `apply_buses(old_manifest)`：旧通道的 UART 若仍 installed，直接 lease 复用；若旧通道用的是另一个 controller（上一次 apply 后被 prune），走 install-once 的冷路径并被 Phase B 门禁保护；
- rollback 后 `prune_unused_uarts` **不调用**（因为 apply_buses(old) 已重新租用旧端口）；
- safe state（`app_callbacks.c:255-267`）：`bus_manager_cleanup_all` 只释放租约，驱动保留；`scheduler_stop`/`dma_pool_reset_runtime`/空 manifest 外设不变。安全状态不再依赖堆分配，符合"致命路径可诊断"。

### 5.7 目标与例外

- **稳态 apply_buses ≤ 4 KiB**：UART preinstall 后，apply 只剩 SPI/I2C 的 driver 重建（1,352+1,424 ≈ 2,776 B）+ 少量 entry/queue，取 4 KiB 上界；
- **例外（必须写进交付说明）**：开机后第一笔配置包含一次冷 install（S3 三路 UART ≈9.3 KiB；C6 两路 ≈6.2 KiB），发生在显式 `preinstall` 步骤，不在 apply_buses 步内，且受 §4.4 门禁保护；`EHOME_MEM_DIAG` 会分别打出 `[heap] uart_preinstall in/out` 与 `[heap] apply_buses in/out`，验收以两步各自的 `[heap]` 差分为准。

## 8. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 非 PSRAM 的 4 KiB 静态 arena 抬高 `.bss` | 稳态 free 永久 -4 KiB | 交付时给 map 前后对比（S3/C6 `idf.py size`）；4 KiB 已在 Lead 裁决中确认对门禁安全 |
| `uart_set_pin/param/baud` 在驱动 installed 后改配置的边界 | 仅下配置瞬间有短暂 pin 重映射；与 worker suspend 配合，无读写竞态 | suspend→reconfigure→resume 顺序；失败回写旧参数；host 单测 + 实机 100Hz 回归 |
| 冷 install 9.3 KiB 一次性成本 | 首笔配置在低堆时被门禁拒绝 | preinstall 显式步骤 + free/largest 双重门禁；失败仅推迟配置，不破坏现有运行 |
| 步骤中途水位拒绝从 UNCHANGED 改为 rollback | 与任务卡字面要求不同 | Lead 2026-10-05 已确认：Phase A（未 suspend）UNCHANGED；Phase B（prepare 后）走 rollback，绝不 UNCHANGED |
| `periph_config_apply` / ResourceReport 的 arena 化 | 一期保留 1.5 KB 级堆分配 | Lead 裁决 phase 1.5；一期由 Phase A/B 门禁保护，无行为回归 |
| task-3 改 `config_mgr.c`（PSRAM 分支/容量） | 同文件可能行号漂移 | static-diet 已回复：事务段（stage/commit/snapshot）不再动；实现前以 `git diff` + 当前文件为准重新对齐 |

### 11.2 与设计的两处实现细节（有意偏离，均有理由）

1. **OTA 门禁经 DIP 弱钩子实现，而非直接 `#include "mem_guard.h"`。**
   `handler_data.c` 属 `components/msg_handler`，不能依赖 `main/` 的头（依赖方向：main REQUIRES msg_handler）。
   实现：`handler_data.c` 声明 `__attribute__((weak)) bool ehome_mem_can_start(size_t)`，`main/app_callbacks.c` 提供强定义
   （`return mem_guard_can_start(need);`）。host 测试与任何未链接 main 的构建自动放行；接口语义与 `mem_guard_can_start` 完全一致。
   这是本仓既有模式（`msg_handler_publish_checked`、`on_query_resources_received` 同为 weak hook）。
2. **Phase B 的 `apply_log_stream` 拒绝 = "跳过日志"而非事务失败。**
   与 `tx_apply_log_stream` 既有语义一致（日志是诊断旁路）。门禁在 `log_stream_apply_state()` 的 start 转换处
   （`mem_guard_can_start(2048)` 失败 → 打 `rc=SKIP` 并返回 ESP_OK）；`config_apply_transaction.c` 的 Phase B 在此步
   仅记录不置错，避免双重拒绝。
