## 1. 功能概述

节点 (Node) 是 EHomeSystem 的**物理边缘设备**抽象。每个 ESP32-C6/S3 物理设备对应一个 Node 记录,承担:
- 状态跟踪 (online/offline)
- 通道管理 (Channel CRUD)
- 心跳管理 (StatusReport, 60s/次 + v2.1 epoch 上报)
- OTA 升级 (HTTPS + SHA256)
- **多通道配置同步 (v2.1, SyncGate)**
- **Config Epoch 持久化 (v2.1)**

> **v2.2 关键变化**: "采集器" → "节点"。原 `Collector` struct → `Node` struct; 原 `collectors` 表 → `nodes` 表。

### 1.2 关键变化 (v2.1 → v2.2)

| 维度 | v2.1 | v2.2 |
|------|------|------|
| 术语 | 采集器 / Collector | **节点 / Node** |
| 表名 | `collectors` | `nodes` |
| 字段名 | `device_id` | `node_id` (协议字段 ID 数值不变) |
| Go struct | `Collector` | `Node` (含 `type Collector = Node` 别名) |
| 关联子表 | channels, devices | channels, edge_devices |
| 协议 topic | `devices/{id}/up\|down` | `nodes/{id}/up\|down` (旧 topic 保留) |
| MQTT topic 旧 | `devices/{id}/up\|down` | (保留 6 个月) |
| 协议字段 1 | `device_id` | `node_id` (v2.2 协议 bump) |
| WS 事件 | `collector_status` | `node_status` (双发) |
| LED 状态 | LED_STATE_RUNNING 等 | 不变 (硬件层) |

## 2. 数据模型

```sql
CREATE TABLE nodes (
  id                    SERIAL PRIMARY KEY,
  node_id               VARCHAR(32) UNIQUE NOT NULL,  -- 物理 ID (e.g. esp32c6_404CCA57B7BC)
  name                  VARCHAR(64) NOT NULL,
  model                 VARCHAR(20),
  firmware_version      VARCHAR(32),  -- size:32 匹配
  protocol_version      VARCHAR(16) DEFAULT '2.2',  -- v2.2 升级
  platform              VARCHAR(16),
  status                VARCHAR(20) DEFAULT 'offline',
  last_seen             TIMESTAMPTZ,
  last_ping_at          TIMESTAMPTZ,
  uptime_seconds        INTEGER DEFAULT 0,
  ping_latency_ms       INTEGER DEFAULT 0,
  mqtt_topic_up         VARCHAR(128),
  mqtt_topic_down       VARCHAR(128),
  wifi_ssid             VARCHAR(64),
  wifi_rssi             INTEGER,
  free_heap_bytes       INTEGER,
  capabilities          JSONB,
  hardware_info         JSONB,
  -- v2.1 同步机制字段
  config_epoch          BIGINT DEFAULT 0,
  last_manifest_id      VARCHAR(64),
  config_sync_state     VARCHAR(20) DEFAULT 'unknown',  -- in_sync/syncing/lag/error
  last_sync_at          TIMESTAMPTZ,
  last_sync_id          VARCHAR(64),
  created_at            TIMESTAMPTZ DEFAULT NOW(),
  updated_at            TIMESTAMPTZ DEFAULT NOW(),
  deleted_at            TIMESTAMPTZ
);

CREATE INDEX idx_nodes_status ON nodes(status);
CREATE INDEX idx_nodes_last_seen ON nodes(last_seen);
CREATE INDEX idx_nodes_config_epoch ON nodes(config_epoch);

-- v2.1 兼容视图 (6 个月)
CREATE VIEW collectors AS SELECT * FROM nodes;
CREATE VIEW devices AS  -- v2.1 兼容 edge_devices
  SELECT id, name, channel_id, ... FROM edge_devices;
```

## 3. 状态机 (v2.2)

### 3.1 节点状态

```
   创建
    ↓
 unknown ──→ online ──→ offline
              │  ↑       │
              │  └───────┘ (心跳恢复)
              ↓
           (网络断开/Hello 重连)
```

| 状态 | 触发 | v2.1 兼容 |
|------|------|----------|
| `unknown` | 创建时默认 | ✓ |
| `online` | 收到 Hello / StatusReport (Redis TTL 15s 内) | ✓ |
| `offline` | 离线检测器判定 (last_seen > 90s) | ✓ |
| `disabled` | 手动禁用 (admin 操作) | ✓ |

### 3.2 离线检测

```
[Redis TTL] 15s 续期
  ↓
若 TTL 过期 (15s 内无新消息):
  - 推 node_status 事件到前端
  - 新增 notification
  - status = offline (3 层: Redis TTL 15s → DB last_seen 90s)
```

### 3.3 同步状态 (v2.1 同步机制, 节点层 + 边缘设备层共享)

| sync_state | 触发 |
|-----------|------|
| `unknown` | 新节点, 等待首次同步 |
| `syncing` | ConfigManifest 已发, 等待 ConfigResult |
| `in_sync` | ConfigResult success |
| `lag` | Epoch 落后, 需要重发 |
| `error` | ConfigResult fail / NVS 写失败 |

## 4. 关键流程 (v2.2)

### 4.1 Hello 握手 (v2.1 同步机制)

```
Node → mqtt.up: {
  node_id, fw_version, model, channel_count,    // v2.2: device_id → node_id (id 数值不变)
  config_epoch, nvs_has_config, last_manifest,   // v2.1 新增
  protocol_version="2.2"                         // v2.2 协议版本
}
  ↓
[server/collector/handler_hello.go]
  1. 解析 v2.2 + v2.1 字段
  2. UPSERT nodes 表 (含 config_epoch)
  3. **SyncGate.OnHello(nodeID, hello)** (v2.1 决策)
  4. 决策结果 → sendConfigManifestWithDecision
  5. 推 node_status 事件 (v2.2: 替代 collector_status)
  6. 推 node_config_synced 事件 (v2.2: 替代 collector_config_synced)
```

### 4.2 心跳 (v2.1 + v2.2)

```
Node → mqtt.up: {
  uptime_sec, status, channel_count,
  config_epoch, sync_state                      // v2.1
}
  ↓ (60s 间隔)
[server/collector/handler_status.go]
  1. 更新 last_ping_at
  2. 更新 config_epoch
  3. **SyncGate.OnStatusReport** (v2.1, 修复 G5)
  4. 推 node_status 事件
  5. **新**: offline→online 时强制 sync (旧只 init, 不 sync)
```

### 4.3 配置下发 (v2.1 多通道)

触发源: Hello / StatusReport / ServerStartup / ConfigChange / ConfigQuery

流程见 [同步机制/详细设计.md §4.3](../同步机制/详细设计.md)

### 4.4 主动 Ping

```
前端 → POST /api/v1/nodes/:node_id/ping
  ↓
[server] 发 Ping (0x08) 到 nodes/{id}/down/v2
  ↓
Node → Pong (0x09) 含 timestamp
  ↓
[server] 收到 Pong → 计算 RTT → 更新 node.ping_latency_ms
  ↓
推 node_status 事件
```

## 6. 容错设计 (v2.2)

| 场景 | 行为 | 修复 GAP |
|------|------|---------|
| 节点重复 node_id | UPSERT (不报错) | - |
| 节点断电 (无离线信号) | Redis TTL 15s + DB last_seen 90s | - |
| ConfigManifest 发送失败 | 退避重试 3 次 | - |
| MQTT 断 | 客户端自动重连, 触发新 Hello | - |
| **服务端重启丢内存态** | **启动 5s 后 push 所有 online 节点** | **G2** |
| **节点恢复出厂 (NVS 空)** | **SyncGate 检测 nvs_has_config=false 强制下发** | **G3** |
| **服务端改配置不通知** | **ConfigEventBus 自动发出事件 → SyncGate 推送** | **G1** |
| **ConfigEventBus 满** | **drop + alarm, 不阻塞 CRUD** | - |
| **同步失败兜底** | **30s 后周期 sync 兜底** | - |
| **OTA 证书不匹配** | **HTTPS TLS 验证失败, 拒绝升级** | - |
| **OTA SHA256 不匹配** | **拒绝刷写, 上报 fail 状态** | - |

## 8. 安全 (v2.2)

- MQTT topic ACL: 节点只能 pub/sub 自己的 topic (`nodes/{own_id}/#`)
- API: admin 才能 POST/PUT/DELETE
- **v2.1**: ConfigEventBus 事件包含 `actor` 字段, 审计"谁改了什么"
- **v2.1**: OTA HTTPS + CRT bundle
- **v2.1**: WS 事件名通过 const 共享, CI 校验

节点的同步机制跟 v2.1 同步机制**完全相同**, 只是术语从"采集器"改为"节点"。详见:
