## 1. 总体架构决策（三主题的统一原则）

**P1：采集域与执行域分离是正确架构，不合并类型，只收敛入口。**
CommandTemplate（轮询帧元数据，进 ConfigManifest）与 ControlAction（受控执行契约，进 Action Catalog）职责不同、生命周期不同、消费方不同。合并会迫使执行域元数据进 manifest 或采集域元数据进 catalog，两头污染。收敛的对象是**入口语义**而非类型。

**P2：元数据最终归宿 = 二选一，废除第三态。**
- 轮询/采集帧 → `CommandTemplate`，且 `Schedulable` 恒为 true；
- 一次性/受控操作 → `ControlAction`（Action Catalog，唯一执行入口 `commandexec.Service.Create`）；
- `CommandTemplate{Schedulable:false}`（"触发指令"）这一组合态**废除**。techfine 的 11 条 query_* 正是该态的最后住户——它们与 11 条 read_* 是同一批物理查询的双入口，正规入口是 Action Catalog（有 verify/历史/幂等/确认制）。这与 b227cc8e 删除 triggerCommands 分组的裁决、以及 `CommandListControlBoundary.spec.ts:54` 与 `sn3001-real.spec.ts:24-28` 的锚定测试完全同向：本方案是那次"有意收敛"的最后一公里。

**P3：风险分级是门禁的唯一权威。**
动作解禁后，它在人工路径的待遇由 `confirmationRequired(Risk)` 决定，在自动化路径的待遇由 `ActorKind×Risk` 矩阵决定。因此**解禁评审必须包含 Risk 分级复核**——防止"解禁了但 Risk 标低导致自动化可无确认执行高风险动作"的漏洞（见主题三 §3.4）。

**P4：解禁是代码审查行为，不是运行时配置行为。**
解禁必须伴随测试断言翻转（guarded 断言→enabled 断言，2026-08-14 已有先例）与文档更新；运行时 `SetEnabled` 只保留为 kill switch/回滚手段。不新增运行时解禁 API。

## 2. 主题一：触发指令元数据的最终归宿

### 2.1 结论

| 元数据 | 归宿 | 状态 |
|--------|------|------|
| 轮询帧（Schedulable=true） | `CommandTemplate` → ConfigManifest / command_intervals | 保留，语义单一化 |
| 一次性受控操作 | `ControlAction` → Action Catalog → commandexec | 保留，唯一执行入口 |
| `CommandTemplate{Schedulable:false}` | **无归宿** | 废除 |
| techfine 11 条 query_* compatibility metadata | 删除（前置审计） | 处置见 2.2 |
| legacyUnsafeCommandTemplates（228 行） | 删除 | 处置见 2.3 |
| template_backfill 的 WriteData 依赖 | 保留机制、解除 techfine 耦合 | 处置见 2.4 |

### 2.2 techfine 11 条 compatibility metadata 的处置：审计先行，然后删除

**为什么删而不是迁移**：11 条 query_* 与 11 条 read_* 是同一批物理查询的双入口。迁移成 catalog 动作 = 制造双份；保留 = 维持第三态。删除后 techfine 的 `GetCommandTemplates()` 返回空，前端 CommandList 对 techfine 设备显示空态文案"该设备没有可配置的轮询指令；一次性读取请使用下方受控操作"（`CommandList.vue:75`）——该文案正是为此设计的。

**删除的硬前提（F6 依赖解除）**：`template_backfill.driverTemplateMatches` 以 `GetCommandTemplates()` 的 WriteData 为匹配源。删除 11 条后，库中任何 WriteData ∈ {HSTS\r, HGRID\r, …, HIMSG1\r}（hex 形式）的 unowned `config_templates` 行将永远无法归属。处置顺序：

1. **审计脚本**（一次性 SQL，不落库）：`SELECT id, node_id, channel_id, write_data FROM config_templates WHERE edge_device_id IS NULL AND upper(write_data) IN (<11 帧 hex 集>);`
2. 结果为空（预期，techfine 从未有 Schedulable=true 模板，理论上不会产生过归属模板）→ 直接删除 11 条 + 更新 `GetCommandTemplates` 为返回空（或删除该方法实现，保留接口兼容）。
3. 结果非空 → 先人工归属（写 `edge_device_id`）或归档，再删。
4. 审计结论写入删除 commit 的 message 与门禁台账。

**删除后的连带**：`GET /drivers/:type/commands` 与 `GET /edge-devices/:id/commands` 对 techfine 返回空数组（配合主题二的后端过滤，语义自洽）；`CreateWizardCommandIntervals.vue` 对 techfine 显示空态。

### 2.3 228 行 legacyUnsafeCommandTemplates：删除

- 纯死代码：`return nil` + 注释块（F4）。注释自述的删除条件"legacy config migration is complete"已满足：数据生命周期方案 v3.3 的 `BackfillConfigTemplateOwnership` 已落地（`template_backfill.go:14-15` 标注"方案 v3.3 §2.4-2"），迁移审查窗口已关闭；且代码完整保留在 git 历史（`git show` 可随时取回），无需再留"source-level migration review"副本。
- 同步删除 `inverter_techfine_test.go:632` 的守卫测试（`legacyUnsafeCommandTemplates() != nil` 断言——函数删除后该测试失去意义，直接删除而非改写）。
- 附带收益：`inverter_techfine.go` 从 1096 行降至 ~868 行，`asciiToHex` 若因此失去全部调用方则一并核查删除（删除前 grep 确认）。

### 2.4 template_backfill 的长期语义

机制本身保留（它是数据生命周期方案的组成部分），但**匹配源语义文档化**：`driverTemplateMatches` 匹配的是"驱动当前声明的轮询帧集"。techfine 无轮询帧 → 其历史模板永远不可归属 → 宁留勿删（现语义正确）。在 `template_backfill.go` 头部注释补一句该语义，防止未来有人"为了 backfill 能匹配"而把 query_* 加回来。

### 2.5 双轨收敛的长期防线

废除第三态后，用**测试而非运行时机制**防回潮（符合"少造机制"哲学）：

- 新增 `drivers_test.go` 用例：遍历 `RegisterBuiltInDrivers` 全部内置驱动，断言 `GetCommandTemplates()` 返回的每条模板 `Schedulable==true`。任何未来驱动想塞一次性操作进模板域，测试当场红。
- `command_template.go:8-11` 注释改写：`Schedulable=false` 标记为 deprecated/过渡态，新驱动禁止使用。

## 3. 主题二：指令配置 API 契约收口

### 3.1 目标不变量

> **I-1：`command_intervals` 的键集 ⊆ 驱动 Schedulable 模板 ID 集。**
> **I-2：GET 端点只返回 Schedulable 模板。**
> **I-3：PUT 与 POST 的校验语义完全对称。**

### 3.2 三处消费语义现状与收口动作

| 消费点 | 现状 | 收口动作 |
|--------|------|----------|
| 创建向导 `drivers/:type/commands` | 后端不过滤，前端 `CreateWizardCommandIntervals.vue:109` 客户端过滤 | 后端过滤（I-2）；前端 filter 保留为防御 |
| 创建路径校验 | `validateAndNormalizeCommandIntervals` 已 enforce I-1 | 提取为共享 helper（见 3.3） |
| GET `edge-devices/:id/commands` | 不过滤，返回含非 schedulable 模板（CommandList 客户端过滤 `:131`） | 后端过滤（I-2） |
| PUT `edge-devices/:id/commands` | merge + 负数归零，无校验（F7） | 复用共享 helper enforce I-1（I-3） |
| ConfigManifest 编码 | `sender_snapshot.go:173-184` 只认 Schedulable+interval>0+模板存在 | 已天然满足 I-1，不改；补一条注释引用不变量 |

### 3.3 文件级改动面

1. **提取共享 helper**：把 `validateAndNormalizeCommandIntervals`（`handler_edge_device.go:66-107`）的"校验+归一化"逻辑与 PUT 的"merge 语义"分离——helper 提供 `ValidateCommandIntervals(driverRegistry, devType, intervals) error`（拒绝未知 ID 与非 schedulable ID）与 `NormalizeCommandIntervals(intervals) map[string]int`（负数归零）。PUT 流程改为：parse 现有 → merge 请求 → **对 merge 后全量 map 校验**（注意：PUT 是部分更新，校验对象是 merge 结果而非请求子集，否则存量脏数据会让校验永远失败——需先做一次存量清洗，见 3.4）→ 归一化 → 落库。
2. **GET 两处过滤**：`handler_driver_commands.go:32` 与 `:56` 在返回前过滤 `t.Schedulable`。前端 `CommandList.vue:131`、`CreateWizardCommandIntervals.vue:109` 的 filter 不动（防御性保留）。
3. **测试**：
   - PUT 拒绝非 schedulable ID / 未知 ID（400，不落库）；
   - GET 两端点不含非 schedulable 模板；
   - `CommandListControlBoundary.spec.ts:54` 与 `sn3001-real.spec.ts:24-28` 锚定测试保持全绿（后端过滤后"触发指令不得出现"依然成立）；
   - 新增一条契约测试：对同一驱动，`GET drivers/:type/commands` 返回集 == `GET edge-devices/:id/commands` 模板集 == `validateAndNormalizeCommandIntervals` 的合法键集 == manifest 编码候选集（四集相等断言，防未来漂移）。

### 3.4 存量数据清洗（PUT 校验的前置）

存量 `edge_devices.command_intervals` JSONB 可能已含非 schedulable 键（PUT 无校验期间写入的）。上线 PUT 校验前跑一次幂等清洗：对每台设备，删除其 `command_intervals` 中不属于驱动 schedulable 集的键，空则置 NULL。清洗脚本作为一次性迁移 commit 的一部分（或 SQL 脚本入 `scripts/`），并在清洗后跑 3.3 的四集相等断言验证。

### 3.5 契约文档化

在 `docs/设计/边缘设备控制.md` §4 API 表补两行语义说明（GET 过滤、PUT 校验），并在 §10 技术债台账引用本方案的不变量 I-1/I-2/I-3。避免"契约只在代码里"导致下次漂移。

## 4. 主题三：动作门禁的制度化

### 4.1 现状与问题

"Enabled:false 等待硬件证据"的动作分两类（F12、F13）：

- **A 类（AvailabilityCode 冻结）**：BMS 15 个 `protocol_unverified`（AvailabilityReason 已是结构化中文证据注释）、`clear_rainfall_write`（`hardware_evidence_required`）；
- **B 类（Enabled:false 冻结）**：GB3024 11 条 `read_*`（无 AvailabilityCode，纯 `Enabled:false`，注释"until the target GB3024 hardware evidence gate is met"）。

问题：解禁路径目前是**代码改动 + 部署**的隐性流程，无证据登记、无评审记录、无回归闭环。SN-3001 三项（2026-08-14 双串口实机闭环）与 BMS `set_mos_policy`（fet_status 0→0x11→0 双向闭环）已经走完解禁，但证据散落在 skill 参考文档与对话记录里，仓库内无登记。

### 4.2 制度设计：一张表 + 一条命名规范 + 一个 PR 模板（不新造系统）

**载体 1：动作门禁台账**（新建 `docs/分析/动作门禁台账.md`，与 `控制域技术债台账.md` 并列，`边缘设备控制.md` §7 表升级引用它）。每动作一行：

| 字段 | 说明 |
|------|------|
| 动作 ID / 设备类型 | 唯一标识 |
| Risk / Semantics / ExecutionShape | 门禁权威（P3） |
| 冻结原因 | `protocol_unverified` / `hardware_evidence_required` / `Enabled:false` + AvailabilityReason 原文 |
| 解禁条件 | 从 AvailabilityReason 提炼的**可验证判据**（如"F2 写帧 CRC 覆盖范围 + 真机读回黄金向量冻结"） |
| 证据路径 | `docs/验证/证据/<设备>-<动作>-<日期>.<ext>` 相对路径 |
| 评审 PR / 启用 commit | 可追溯 |
| 回归结果 | 实机验证矩阵结论 + 日期 |
| 状态 | frozen / evidence_collected / reviewed / enabled / reverted |

**载体 2：证据命名与存放规范**：`docs/验证/证据/<设备类型>-<动作ID>-<YYYYMMDD>.<ext>`（沿用既有先例 `SN3001-前端实机读取-20260719.png`）。证据类型：截图、串口/日志摘录、黄金向量（帧 hex + 期望响应）、readback 对账记录、观察事件（PeriphRsp/offline window）记录。证据文件本身进 git（图片/文本均可，仓库已有先例）。

**载体 3：解禁 PR 模板**（写入台账文档，作为评审清单）：
1. 证据链接（必须指向 `docs/验证/证据/`）；
2. 证据覆盖声明：动作的每个物理步骤（写帧/读回/finally）都有对应证据；
3. 代码改动声明：删 AvailabilityCode 或 Enabled:true + **同步翻转的测试断言清单**（guarded→enabled，2026-08-14 先例）；
4. Risk 分级复核（P3）：确认 Risk 与 confirmation 语义一致（见 4.4）；
5. 台账行更新 diff。

**流程四步**：证据登记（PR 1，纯文档+证据文件）→ 评审（按清单，通过才合并）→ 启用（PR 2，代码改动+断言翻转+台账状态更新）→ 回归（实机验证矩阵，参照 2026-08-14 双串口闭环模式；结果写回台账；失败则 revert PR 2 恢复 AvailabilityCode）。两步 PR 分离的理由：证据评审与代码解禁是不同性质的审查，且证据 PR 可先行合并、长期有效。

### 4.3 存量迁移与样板

- **补登记（不重新评审）**：SN-3001 三项已闭环（`set_rain_sensitivity`/`set_device_address`/`set_baud_rate`）与 BMS `set_mos_policy` 已实机闭环——在台账中登记为 `enabled`，证据路径指向既有 skill 参考文档与验收报告，并补录关键证据文件（如 fet_status 对账记录）进 `docs/验证/证据/`。这是"制度先例"的建立。
- **首个全流程样板**：从 BMS 15 个冻结动作中选一个证据门槛最低的走完整四步（建议 `read_protection_parameters` F2 读——只读、有明确判据"工厂模式步骤与实机响应冻结"），作为流程样板，验证制度可执行性后再推广。
- **GB3024 11 条 read_***：解禁条件 = 实机证据（目标硬件 + 响应解析验证）。注意其冻结形态是 B 类（无 AvailabilityCode），解禁 PR 需同时给动作补 AvailabilityCode 历史记录（台账行）或直接 Enabled:true——台账行必须记录"原冻结形态"。

### 4.4 与自动化引擎的统一收口

**厘清两条确认策略的关系**（F10）：

- `confirmationRequired`（medium 起须 token）是**人工路径**的底线——参数化写从 medium 起必须确认，比"high/critical 最低要求"更严格，这是有意设计；
- `ActorKind=system` 豁免 medium/low 是**自动化路径**的授权——授权发生在规则创建时（用户配置规则 = 表达意图），而非执行时；
- 两者不冲突，但有一个**收口缺口**：规则编辑器目前不展示动作 Risk 分级，用户配置"medium 动作自动执行"时不知情。收口动作：规则编辑器展示动作 Risk + medium 动作保存时提示"该动作将自动执行，无需逐次确认"（前端改动，`automation` 规则页）。

**统一原则（P3 落地）**：解禁评审清单第 4 项"Risk 分级复核"强制检查——解禁动作的 Risk 决定它在两条路径的待遇。具体规则：
- medium 动作解禁后：人工路径须确认，自动化路径可自动执行（system 豁免）——评审须确认该动作被自动化自动执行是可接受的；
- high/critical 动作解禁后：两条路径都须 token（system 不豁免）——自动化规则引用它必须 `require_confirmed=true`，否则 planner 落 pending_confirm 等人工确认（现有语义，`planner.go:91`）；
- 评审发现 Risk 标低 → 解禁 PR 拒绝，先改 Risk。

**PeriphCmd 的统一**（F11）：gpio_set/pwm_set_duty 是 medium、`Enabled:true`、observation 确认、节点级不走 channel 锁。三件事要文档化而非改代码：
1. PeriphCmd 不走 channel 锁是**设计豁免**（节点级资源无 channel 归属，并发安全由 0x1B 帧的值幂等性保证）——写入台账/设计文档，防止未来被当漏洞"修复"；
2. PeriphCmd 的确认 = PeriphRsp 观察事件，与 channel 动作的 readback verifier 是两种证据形态——解禁评审清单对 PeriphCmd 动作的"证据覆盖声明"应要求观察事件记录；
3. 自动化 S1（光照自动开灯）已验证 system+medium+PeriphCmd 全链路——作为台账中 PeriphCmd 动作的回归样板登记。
