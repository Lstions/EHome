## 1. 一屏结论

- 检出 **28 条**接口/模块设计缺陷：**严重 11 / 中 14 / 低 3**。
- **最贵的三条**（相互独立，都可单独排期）：
  1. **D-01**：`transport_ops.send()` 的三态信息在抽象层被压回二态，去重被降级成调用方的"查表"——这就是 L-02 的结构成因，且**修完仍在**。
  2. **D-03**：TCP 传输的 WiFi-触发启动路径是 `break;` 之后的死代码，**3.0 主通道首日不可用**。
  3. **D-06**：`msg_handler_send_data_batch` 被 `bus_worker.c` 以**弱符号重复定义**，"哪个实现生效"由链接器决定；一旦 `handler_data.o` 不再被拉入，100 Hz 聚合会**静默退化**且无测试会红。
- **对 3.0 方案的直接更正**：方案 §4.1（`docs/设计/ESP32-3.0-重构方案-2026-10-06.md:361`）称传输抽象层"3.0 只需新增 TLS 实现 + 退役 MQTT 实现，不改上层广播语义"。**该判断不成立**，见 D-01 / D-02 / D-09 / D-10 / D-21 与 §5。
- **静默失败四族全部命中**（对照表见 §6）：不可达 3 条、假绿 4 条、静默丢弃 2 条、静默改写 5 条。
- **可测试性**：33/49 个生产 .c（71% 行数）被宿主测试编译；**17 个文件 / 6,309 行（29%）从未被任何宿主测试编译**，其中包含 `msg_handler.c`、`ehome_tcp.c`、`mqtt_transport_adapter.c`（见 D-08、D-24）。

## 2. 严重缺陷（严重，11 条）

### D-01　`transport_ops.send()` 无法表达"未连接 / 对端失败"，分类信息在抽象边界被主动丢弃

**证据**

`components/transport/include/transport.h:53-60` —— 接口只给 `esp_err_t`：
```c
struct transport_ops {
    esp_err_t (*init)(transport_t *transport, const void *config);
    esp_err_t (*start)(transport_t *transport);
    esp_err_t (*stop)(transport_t *transport);
    esp_err_t (*send)(transport_t *transport, const uint8_t *data, size_t len);
    bool (*is_connected)(transport_t *transport);
    void (*deinit)(transport_t *transport);
};
```

`components/ehome_mqtt/ehome_mqtt.h:98-110` —— 底层**已经有**三态，且注释写明了它为什么必须存在：
```c
typedef enum {
    MQTT_PUBLISH_OK = 0,
    MQTT_PUBLISH_NOT_CONNECTED = 1,   /* 本地未连接，调用方**不应**重试其它 MQTT 路径 */
    MQTT_PUBLISH_FAILED = 2,          /* 对端/队列问题（含 outbox 满 -2），可上报失败 */
} mqtt_publish_result_t;
```

`components/ehome_mqtt/mqtt_transport_adapter.c:51-58` —— **三态在适配器里被压回二态**，注释自陈是刻意的：
```c
    switch (mqtt_client_publish_ex(data, len)) {
    case MQTT_PUBLISH_OK:
        return ESP_OK;
    case MQTT_PUBLISH_NOT_CONNECTED:
    case MQTT_PUBLISH_FAILED:
    default:
        return ESP_FAIL;
    }
```
> 该文件 :42-50 的注释：*"为什么这里仍然把两者都映射为 ESP_FAIL：transport_broadcast() 用返回码统计 sent_count，改动它会连带改变'广播是否成功'的判定，超出本次最小修复的范围。去重由调用方的注册表查询完成。"*

`components/msg_handler/msg_handler.c:74-103` —— 调用方只能靠**查注册表**这一代理判据去重：
```c
    esp_err_t ret = transport_broadcast(data, len);
    if (ret == ESP_OK) { ... return ESP_OK; }
    /* ... L-02 根因（2026-10-06，参数化闭环）... */
    if (transport_registry_has_type(TRANSPORT_TYPE_MQTT)) {
        ESP_LOGW(TAG, "Broadcast failed; MQTT already attempted inside broadcast, not re-publishing");
        return ret;
    }
    ESP_LOGW(TAG, "Broadcast failed, falling back to MQTT");
    return mqtt_client_publish_impl(data, len) ? ESP_OK : ESP_FAIL;
```

**为什么这是设计问题（不是风格问题）**

1. 抽象层的 `send()` **无法表达调用方做决策所必需的信息**——这正是任务书要求抓的那一类。三态枚举之所以要存在，恰恰是因为二态不够；但它在 `transport_ops` 边界上被丢掉，于是**信息只能绕路**：底层造三态 → 适配器压平 → 调用方另外发明一个查询 API 把信息猜回来。
2. `transport_registry_has_type()` 回答的是 **"MQTT 是否在注册表里"**，而调用方需要问的是 **"我上一次 broadcast 有没有尝试过 MQTT"**。二者不等价：`transport_broadcast()` 只在 `t->ops->is_connected(t)` 为真时才调用 `send`（`transport.c:93-99`）。因此当 MQTT 已注册但**未连接**时，广播根本没碰它，而 `msg_handler.c:98` 的日志却断言 *"MQTT already attempted inside broadcast"*——**日志在说谎**。当前行为恰好是安全的（未连接时本来也发不出去），即"**碰巧正确**"，不是设计正确。
3. 接口的全部缺陷被"最小修复范围"这一**流程理由**固定下来。这不是实现者的疏忽，而是接口语义不足导致的必然绕路。

**后果（真实事故）**

L-02：100 Hz 台架实测 **PF/NT = 1.998**（`MQTT: Publish failed` 3,873 行 / `No transport connected` 1,938 行，120.12 s），即**每帧 2 条失败日志**——广播内已发一次失败，调用点又重发一次。转引 `docs/分析/遗留问题复核与修复方案-2026-10-06.md` §2.2 与提交 `b8410352`。修复后 PF/NT→1.004，但验收判据（`Publish failed ≤ 10`）实测 1,826，**未达成**。

**3.0 改进方向**

- `send()` 的返回类型改为可表达决策的结构：
  ```c
  typedef enum { TX_OK, TX_NOT_CONNECTED, TX_PEER_REJECTED, TX_QUEUE_FULL, TX_TIMEOUT } tx_result_t;
  ```
- `transport_broadcast()` 返回**逐通路结果**而不是一个 esp_err_t：
  ```c
  typedef struct { uint8_t attempted, succeeded; tx_result_t first_error; uint8_t failed_mask; } tx_report_t;
  ```
- 删除 `msg_handler` 里的 MQTT 回退分支（见 D-02）；删除 `transport_registry_has_type()`（它只为绕路而存在）。

### D-02　消息分发器直接依赖 MQTT 组件，并保留 MQTT 专用回退路径

**证据**

`components/msg_handler/msg_handler.c:16` 与 `:103`：
```c
#include "ehome_mqtt.h"
...
    return mqtt_client_publish_impl(data, len) ? ESP_OK : ESP_FAIL;
```
`components/msg_handler/CMakeLists.txt`：
```
REQUIRES frame ehome_mqtt config_mgr ota sync_manager hw_profile transport scheduler bus_worker gpio_ctrl pwm_ctrl periph_owner wifi_mgr
```
`components/sync_manager/CMakeLists.txt`：`REQUIRES config_mgr ehome_mqtt nvs_flash rgb_led`

**为什么这是设计问题**

分发器（`msg_handler_process`，`msg_handler.c:173-247`）是**协议无关**的路由层——它按 `data[0]` 把帧分给 handler，这层不该知道"帧最终走 MQTT 还是 TCP"。但它在 `:103` 硬编码了具体传输实现。传输的**选择**被写在两个地方：抽象层（`transport_broadcast`）与分发层（回退分支）。一个职责两个 owner，两者就会互相污染——L-02 正是这个结构长出来的。

**后果**

3.0 退役 MQTT 时，需要改动的是 `msg_handler.c`（以及 `sync_manager`）而不只是传输层。方案 §4.1 的"退役 MQTT 实现"在依赖图上不成立。另外 `msg_handler` REQUIRES **12 个组件**，是宿主测试无法编译它（D-08）的直接原因。

**3.0 改进方向**

- `msg_handler.c` 只依赖 `transport.h`；出站一律经 `transport_send_via(session, ...)`。
- 给组件依赖加一条不变量：**分发层不得 REQUIRES 任何具体传输实现**，并加脚本门禁（见 §7 原则 P7）。

### D-03　TCP 传输的 WiFi 触发启动路径是死代码（`break;` 之后的 `#ifdef` 块）

**证据**

`main/app_callbacks.c:674-692`（逐字）：
```c
    switch (state) {
    case WIFI_MGR_CONNECTED:
        rgb_led_set_state(LED_STATE_MQTT_CONNECTING);
        /* Pending OTA images are confirmed only by status_task after MQTT is
         * connected and the first StatusReport has been sent. */
        /* WiFi callbacks never own MQTT lifecycle operations. They only wake
         * the long-lived supervisor, which serializes recovery and teardown. */
        ESP_LOGI(TAG, "WiFi connected, waking MQTT supervisor");
        ensure_mqtt_supervisor(s);
        break;                                    /* ← 683：本 case 到此结束 */

#ifdef CONFIG_DEBUG_TCP_ENABLED
        if (s->tcp_transport && s->tcp_transport->state != TRANSPORT_CONNECTED
            && s->tcp_transport->ops->start) {
            ESP_LOGI(TAG, "Starting TCP transport");
            s->tcp_transport->ops->start(s->tcp_transport);
        }
#endif
        break;                                    /* ← 692：同样不可达 */
```

仅有的另一处启动点在 `main/main.c:587-601`：
```c
    s->tcp_transport = tcp_transport_create(&tcp_cfg);
    if (s->tcp_transport) {
        ...
        transport_register(s->tcp_transport);
        if (wifi_mgr_get_state() == WIFI_MGR_CONNECTED      /* ← 要求"此刻"已连上 */
            && s->tcp_transport->state != TRANSPORT_CONNECTED
            && s->tcp_transport->ops->start) {
            s->tcp_transport->ops->start(s->tcp_transport);
        }
    }
```
配置项：`sdkconfig.defaults:237 CONFIG_DEBUG_TCP_ENABLED=n`，但工作树 `sdkconfig:1075 CONFIG_DEBUG_TCP_ENABLED=y`（即**当前调试构建已开启**）。

**为什么这是设计问题**

这不是笔误问题，而是**传输生命周期没有单一 owner** 的必然后果：TCP 的"何时启动"被同时写在两处（`main` 的 init 与 `app_callbacks` 的 WiFi 回调），两处各自重复判断"是否已连接"，而回调那处被 `break;` 挡死。只要"网络状态变化"这件事有两个响应点，它们就会分叉；`break;` 只是让分叉以最隐蔽的方式（不可达）出现。

**后果**

正常启动顺序（WiFi 后连）下 **TCP 永不启动**。这是 3.0 主通道的**首日 blocker**：T-3（"TCP 传输（先明文，双栈并存）"）跑不起来，而且失效方式是"连接被拒绝"而非"固件报错"，排查会先怀疑后端端口/防火墙。另：`main.c:594` 的 `transport_register(s->tcp_transport)` **返回值被丢弃**（`MAX_TRANSPORTS=4`，`transport.c:12`），注册表满时 TCP 会静默不注册。

**3.0 改进方向**

- 传输生命周期收归**唯一 owner**：`transport_manager` 提供 `transport_on_network_state(wifi_state_t)`，由它决定 start/stop/重连；任何模块不得直接調 `->ops->start`。
- 把"注册即可用"作为不变量：`transport_register()` 在已注册且网络可用时自行启动，调用方无需知道时机。
- `transport_register` 的返回必须被处理（`ESP_ERROR_CHECK` 或显式上报）；`MAX_TRANSPORTS` 固定数组改为按需注册（见 D-26）。

### D-04　`transport_t` 是公开可变结构体，`state` 与 `is_connected()` 构成双真值源，且两实现语义不同

**证据**

`components/transport/include/transport.h:41-50`：
```c
typedef struct transport {
    const transport_ops_t *ops;
    transport_type_t type;
    transport_state_t state;      /* ← 任何人可写 */
    transport_msg_cb_t msg_cb;
    void *msg_cb_ctx;
    transport_state_cb_t state_cb;
    void *state_cb_ctx;
    void *priv_data;  // 各 transport 的私有数据   /* ← 无类型 */
} transport_t;
```

MQTT 实现：`transport->state` 只是镜像，`is_connected` **不读它** ——
`components/ehome_mqtt/mqtt_transport_adapter.c:113` 写；`:61-64` 读的是别的东西：
```c
static bool mqtt_adapter_is_connected(transport_t *transport)
{
    return mqtt_client_is_connected_impl();
}
```

TCP 实现：`state` 是谓词的一部分，且在**尚无任何客户端时**就被置为 CONNECTED ——
`components/ehome_tcp/ehome_tcp.c:205`：`transport->state = TRANSPORT_CONNECTED;`（`start()` 里，bind/listen 成功之后、accept 之前）
`components/ehome_tcp/ehome_tcp.c:313-321`：
```c
static bool tcp_is_connected(transport_t *transport)
{
    if (!transport) return false;
    tcp_transport_priv_t *priv = transport->priv_data;
    return (transport->state == TRANSPORT_CONNECTED && priv->client_count > 0);
}
```

外部直接读者（绕过 `is_connected`）：
`main/main.c:596-597`、`main/app_callbacks.c:686`、`main/app_callbacks.c:686` 所在的 D-03 死代码块。

**为什么这是设计问题**

同一个公开字段在两种实现下**含义不同**：MQTT 下它是"事件回调顺手写的缓存"（可能与真值不一致），TCP 下它是"服务器在监听"。任何直接读 `.state` 的外部代码，在切换实现时语义就变了——而它在类型系统里完全看不出来。这正是本仓已有一份专门文档在讨论的缺陷类（`docs/设计/契约评审-同名异物与双值状态-2026-09-23.md`）。同时 `ops` 是可写指针、`priv_data` 是无类型 `void*`，封装在这个类型上等于不存在。

**后果**

- TCP 下 `state == CONNECTED` ≠ "有对端"。`main.c:596` 与 `app_callbacks.c:686` 用它决定"要不要 start"，语义是"服务器是否已在监听"；而 `transport_any_connected()`/`is_connected()` 决定"能否发送"。两套谓词一旦被同一个人混用，就会得到"看起来连上了但发不出去"，或反之。**D-03 的分叉就是这样长出来的。**
- MQTT 适配器的 `state` 可能与真实连接状态不一致（它是事件驱动的缓存），而它同时被 `ops->state_cb` 携带出去。

**3.0 改进方向**

- `transport_t` **不透明化**：对外只暴露 `typedef struct transport transport_t;`（或句柄 `transport_handle_t`），字段全部进 `.c`。
- 状态只经**快照查询**获得，且单一真值源：
  ```c
  typedef struct { bool usable; bool link_up; tx_result_t last_error; int64_t since_us; } transport_status_t;
  esp_err_t transport_get_status(transport_handle_t h, transport_status_t *out);
  ```
- `priv_data` 改为 `struct transport_impl;` 前向声明指针，或在 `ops` 里带 `size_t priv_size` 由 manager 分配（避免两处各自 calloc）。

### D-05　`bus_worker_start()` 返回 `void`，且忽略 6 个 `xTaskCreate` 的返回值

**证据**

`components/bus_worker/bus_worker.c:2129-2158`：
```c
void bus_worker_start(bus_runtime_t *rt)
{
 ensure_suspend_events();
 s_runtime = rt;
 if (s_data_batch_cb == NULL) s_data_batch_cb = msg_handler_send_data_batch;
 report_path_init();
 if (!s_report_path_started) {
  /* report_path_init() failed (or was never able to build its pool).  Starting
   * the RX/cmd tasks here would let rx_task write into a NULL stream buffer. */
  ESP_LOGE("BUS_WORKER", "report path unavailable; not starting bus workers");
  return;                                    /* ← 唯一信号是一条日志 */
 }
 rebuild_cmd_queue_sets(rt);
 rebuild_uart_event_set(rt);
 xTaskCreate(rx_task, "rx_task", RX_STACK, (void *)rt, RX_PRIO, &s_rx_task_h);
 xTaskCreate(cmd_task_uart0, "cmd_u0", UART_STACK, (void *)rt, CMD_PRIO, &s_cmd_u0_h);
 ... /* 共 6 个 xTaskCreate，返回值全部未检查 */
}
```
调用点 `main/main.c:578`：`bus_worker_start(&s->bus_runtime);` —— 返回值无从检查。

**为什么这是设计问题**

启动是一个**可失败**的操作（内存不足、队列创建失败、任务创建失败），接口却按"不可失败"建模（`void`）。于是失败只能退化成日志，调用方无从分支。这与本仓 2026-10-04 的两次栈溢出教训同形：**代价不在失败本身，而在失败后系统仍以为一切正常**。

**后果**

采集/上报全链路可以**完全不存在**而系统"启动成功"：`report_path_init()` 失败（PSRAM 分配失败 / 队列创建失败 / `report_tx` 任务创建失败，`bus_worker.c:862-903`）后，设备照常连 WiFi、照常回 HelloAck、照常应答配置——但一个样本都不会上报。服务端看到的现象是"节点在线但无数据"，与 2026-09-30 那次"静默传感器消失 7 天"（`handler_data.c:190-195` 注释自陈）属同一可见性等级。

**3.0 改进方向**

- 签名改为 `esp_err_t bus_worker_start(bus_runtime_t *rt)`，失败必须让启动流程 fail-closed（或进入显式的 degraded 状态并上报）。
- 6 个 `xTaskCreate` 逐个检查；任何一个失败都要回滚已创建的任务并返回错误。
- 把"已启动的任务清单"作为不变量暴露给诊断通道（现在的 `bus_worker_get_min_stack_watermark()`「Zero means workers are not running yet」是一种事后探测，不替代启动期检查）。

### D-06　跨组件弱符号：`msg_handler_send_data_batch` 被 `bus_worker.c` 重复定义，"谁生效"由链接器决定

**证据**

`components/bus_worker/bus_worker.c:2081-2136`：
```c
/* 前向声明：让 bus_worker_start() 能在定义之前引用编码器。这里刻意**不带**
 * weak 属性 —— 它只是声明；真正的弱定义在下面，宿主测试可用编译定义关掉。 */
bool msg_handler_send_data_batch(uint32_t channel_id, uint32_t first_sequence, ...);

/* ... 为什么需要它：bus_worker 已经 REQUIRES msg_handler（handler_data.c 读

 * bus_worker_set_data_batch_cb()。task-1 的写范围明确冻结 main/，因此
```

真实实现：`components/msg_handler/handler_data.c:346`。已有的显式注入点：`components/bus_worker/include/bus_worker.h:188-190`：

生产代码中 `bus_worker_set_data_batch_cb` **零调用**（`grep` 只命中定义与声明）。

**为什么这是设计问题**

三层问题，逐层加重：

1. **同一公开符号在两个组件里各有一份定义**，"运行时调用哪个实现"由静态库被拉取/解析的顺序决定，而不是由代码决定。注释自陈的机制是"链接器解析 `__idf_msg_handler.a` 时会把强定义拉进最终镜像"——而归档成员**只在解析到未定义符号时才被拉入**。也就是说，强定义的生效依赖**另一个无关引用**（`main` 引用了 `handler_data.o` 里的 `msg_handler_send_data_report`/`msg_handler_send_status`）把该 `.o` 拽进来。这是**巧合正确**。
2. **已有的注入 API 被绕过**，理由写在注释里：*"task-1 的写范围明确冻结 main/"*。也就是**开发流程的临时约束被固化成了架构**。注入点（`bus_worker_set_data_batch_cb`）从此成为死代码，而它才是设计上正确的连接方式。
3. **宿主测试编译的是另一套符号表**：`EHOME_HOST_TEST_REAL_DATA_BATCH_ENCODER`（`:2112`）让测试禁用弱定义。因此"弱符号是否被正确覆盖"这一**唯一重要的链接期风险，结构上不可测**。

**后果（失效路径，非已发生事故）**

若将来 `handler_data.o` 因任何原因不再被拉入——例如重构后不再引用 `msg_handler_send_data_report`、或构建策略改为 `--gc-sections` 更激进、或把两个 `send_*` 移走——弱定义就会生效，`s_data_batch_cb()` **永远返回 false**，于是：
- `report_try_data_batch()` 每次都走"编码失败→回填队列"分支（`bus_worker.c:631-641`），
- 每帧打一条 `DataBatch encode failed …; falling back to 0x03`（`:569-572`），
- 100 Hz 的聚合优化**静默消失**，退化为逐样本 0x03，恰好是 3.0 想消除的开销。
- **没有任何测试会变红**：宿主测试走的是 `EHOME_HOST_TEST_REAL_DATA_BATCH_ENCODER` 分支。

**3.0 改进方向**

- **删除弱定义**；在 `main` 的初始化里加一行 `bus_worker_set_data_batch_cb(msg_handler_send_data_batch);`（这正是该 API 存在的意义）。
- 若"main 不该知道编码器"是硬约束，则把编码器**下沉为独立组件**（`components/msg_handler/data_batch_codec.c` 已是独立文件，只因目录归属才绑定消息处理器）——依赖环随之消失（见 D-14）。
- 加一条门禁：**生产代码中不得出现 `__attribute__((weak))` 的跨组件函数定义**（现有的弱符号用法都是 DIP 回调默认值，属于另一类，需区分）。

### D-07　"本机队列满"被累加进 `error_count`，而该字段是上报给服务端的**唯一**设备健康量

**证据**

`components/scheduler/scheduler.c:676-690`（背压分支）：
```c
            /* Keep a small per-bus reserve for on-demand control commands.
             * A congested SPI queue must not suppress UART0/UART1 sampling. */
            if (!scheduler_queue_is_present(target_q) ||
                uxQueueSpacesAvailable(target_q) <= SCHED_CONTROL_QUEUE_RESERVE ||
                xQueueSend(target_q, &bcmd, 0) != pdTRUE) {
                if (metric_index >= 0) {
                    if (!scheduler_queue_is_present(target_q) ||
                        uxQueueSpacesAvailable(target_q) <= SCHED_CONTROL_QUEUE_RESERVE)
                        s_queue_metrics.sample_skipped[metric_index]++;
                    else
                        s_queue_metrics.sample_rejected[metric_index]++;
                }
                (*queue_full_count)++;
                scmd->error_count++;                 /* ← 本机背压 → 设备错误计数 */
                if (scmd->error_count > 100) scmd->error_count = 100;
            }
```
`components/scheduler/scheduler.h:146-171` 定义了该字段的**唯一**对外语义：
> *"StatusReport's EdgeDeviceHealth sub-frame is built from `sched_command_t.error_count` … 它是服务端能观察到的**唯一**字段。… `success false -> increment it`"*

消费点 `components/msg_handler/handler_data.c:196-212`：
```c
                    if (!cmd->enabled || cmd->error_count == 0) continue;
                    ...
                    // comm_status: 0=OK, 1=TIMEOUT, 2=CRC_ERROR, 3=FAULT
                    uint64_t comm_st = cmd->error_count >= 3 ? 3 :
                                       (cmd->error_count > 0  ? 1 : 0);
```

**为什么这是设计问题**

一个计数器承担了两个**互不相关**的语义：
- 语义 A（对端）：从机没应答 / 超时 / 校验错 —— 由 `scheduler_notify_command_outcome(success=false)` 写入（`bus_worker.c:1755/1775/1985`）。
- 语义 B（本机）：调度器的队列满，样本**根本没发出去** —— 上面那行 `scmd->error_count++`。

两者被同一个数字承载，且**没有任何第二个字段可以区分**。接口层面：`scheduler_notify_command_outcome()` 返回 `bool`（"是否匹配到槽位"，`scheduler.h:170-178`），也无法表达"我为什么记了一次错"。

**后果**

100 Hz 下队列压力是必然量（转引 `docs/分析/遗留问题复核与修复方案-2026-10-06.md` §2.1 L-01c：实测 `full=577~589 / min_free=2`）。届时：

- 服务端会把**本机过载**读成**现场传感器故障**（`comm_st=1 TIMEOUT`，连续 3 次→`3 FAULT`），触发告警/工单；
- 真正的从机超时被淹没在同一种信号里，无法区分"该修总线"还是"该加内存/降速"；
- 这是**静默改写**（写进去的值与真实原因不同），且写进的是运维唯一依据。

本仓已有一次同形事故的注脚：`handler_data.c:190-195` 注释记录 `error_count` 曾被错误清零导致"静默传感器消失 7 天"。字段语义一旦不纯，下一次误用就还是它。

**3.0 改进方向**

- 拆字段：`comm_error_count`（只由对端结果驱动，语义=通信健康）与 `local_drop_count`（背压/丢弃，语义=本机容量），两者都在 StatusReport 上报，`comm_status` **只**由前者派生。
- `scheduler_notify_command_outcome()` 的入参改为带原因：`sched_outcome_t { OK, PEER_TIMEOUT, PEER_CRC, LOCAL_DROPPED, BUS_ERROR }`。
- 现有 `scheduler_queue_metrics_t.sample_skipped/sample_rejected`（`scheduler.h:190-196`）已经有正确口径的计数——把上报接到它上面即可，不需要新增结构。

### D-09　TCP 把流式字节块当作完整消息交给消息回调；接口未声明定帧契约

**证据**

`components/ehome_tcp/ehome_tcp.c:431-449`：
```c
    while (client->active) {
        ssize_t received = recv(client->socket, recv_buf, TCP_RECV_BUF_SIZE, 0);
        if (received < 0) { ... break; }
        else if (received == 0) { ESP_LOGI(TAG, "Client disconnected"); break; }
        priv->bytes_received += received;
        ESP_LOGD(TAG, "Received %d bytes", (int)received);
        // 调用消息回调
        if (transport->msg_cb) {
            transport->msg_cb(recv_buf, received, transport->msg_cb_ctx);
        }
    }
```
接口侧 `components/transport/include/transport.h:34-35` 只有：
```c
/* === 消息回调 === */
typedef void (*transport_msg_cb_t)(const uint8_t *data, size_t len, void *ctx);
```
消费侧 `components/msg_handler/msg_handler.c:173-190`：
```c
void msg_handler_process(const uint8_t *data, size_t len)
{
    if (len < 1) { ESP_LOGW(TAG, "Empty frame"); return; }
    uint8_t msg_type = data[0];
    frame_decoder_t dec;
    frame_err_t err = frame_decoder_init(&dec, data, len);
    ...
```

**为什么这是设计问题**

`transport_msg_cb_t` 的**隐含前置条件**是"一次回调交付一条完整消息"。这个条件在 MQTT 下**恰好成立**（esp-mqtt 按 MQTT 报文投递，一次一条），在 TCP 下**必然不成立**（字节流：两个帧可能粘在一次 `recv`，一个帧可能跨两次 `recv`）。契约没有被写下来，于是它靠实现的巧合成立——而 3.0 正要换掉那个碰巧满足它的实现。

后果是双向的，而且都不报错：
- **粘包**：`data[0]` 是第一条帧的类型，`frame_decoder_next` 会把第二条帧的字节当成第一条帧的字段继续解析（只要 tag/wire_type 合法就一路读下去），得到**字段值错误**的一帧；不合法才返回 `FRAME_ERR_INVALID_TAG`。
- **拆包**：`frame_decoder_next` 返回 `FRAME_ERR_UNDERFLOW`（`frame_codec.c:123-129`），`msg_handler_process` 在 `:183-186` 打一行 `Decoder init failed` 就 `return`，**半帧被丢弃且没有重组缓冲**。

**后果**

3.0 计划含"消息重组"（方案 §5）。但如果在 `transport.h` 不把定帧契约写进接口，重组会被实现成"TCP 适配器的内部行为"，而其它实现继续按各自的理解违约；下一次换传输（BLE，方案 T-9）会重复同一个坑。这与 2026-10-03 的事故同形——转引 `docs/分析/遗留问题复核与修复方案-2026-10-06.md` §2.1：*"定帧错误 ⇒ **产出错误数值**（不是报错）——2026-10-03 已发生一次（Techfine 截断帧被采信）"*。

**3.0 改进方向**

- 在 `transport.h` 明确并**同时提供**两种契约之一：
  - `on_message(ctx, const uint8_t *msg, size_t len)` —— 要求传输实现自己保证"完整消息"；或
  - `on_bytes(ctx, const uint8_t *buf, size_t len)` —— 明确是字节流，由**共享的 `stream_framer` 组件**（长度前缀 + 魔数 + CRC，即方案 §5.1 的分帧格式）负责定帧。
- 无论选哪种，**定帧器必须是共享组件而不是某个 transport 的私有实现**，且要有"半帧 / 粘包 / 丢片"的宿主测试。

### D-10　TCP `send()` 把"部分写"当作成功，截断帧会静默上线

**证据**

`components/ehome_tcp/ehome_tcp.c:290-311`：
```c
    if (xSemaphoreTake(priv->clients_mutex, pdMS_TO_TICKS(100)) == pdTRUE) {
        for (int i = 0; i < priv->config.max_clients; i++) {
            if (priv->clients[i].active && priv->clients[i].socket >= 0) {
                ssize_t sent = send(priv->clients[i].socket, data, len, 0);
                if (sent > 0) {
                    sent_count++;
                    priv->bytes_sent += sent;
                } else {
                    ESP_LOGW(TAG, "Failed to send to client %d", i);
                }
            }
        }
        xSemaphoreGive(priv->clients_mutex);
    }
```

**为什么这是设计问题**

流式 `send()` 返回的是"已接受字节数"，**允许小于 `len`**（发送缓冲满、被信号打断后部分写出）。接口把 `sent > 0` 等同于"这一帧发出去了"，于是"发出了 300 / 1400 字节"与"完整发出"在上层完全不可区分。这不是实现细节，而是 `transport_ops.send` 契约里缺了"要么全发要么报错"这条**原子性**约定——正因为契约没写，TCP 实现按最省事的方式理解了它。

**后果**

半帧上线，后端拿到一条无法解析的残缺帧。由于 TCP 流上没有长度定帧（D-09），后端**无法**把它当作"半帧等待后续"来处理，只能丢弃或误解析——与 D-09 叠加后，"静默产出错误数值"的路径被打开。另：`send()` 在阻塞套接字上无超时，且持锁发送（`:290`），一个慢客户端会阻塞整个广播路径。

**3.0 改进方向**

- `send` 契约写死：**返回 `TX_OK` 当且仅当 `len` 字节全部进入内核缓冲**。
- 实现用写循环 + 短超时（`SO_SNDTIMEO`）+ 出错即关连接并回报；绝不"部分算成功"。
- 广播路径不得在持锁状态下做阻塞 I/O：把每客户端的发送卸载到其自有发送队列/任务。

### D-11　`tcp_stop()` 拿不到锁就**整块跳过清理**，随后销毁该锁

**证据**

`components/ehome_tcp/ehome_tcp.c:248-273`：
```c
    // 关闭所有客户端
    if (xSemaphoreTake(priv->clients_mutex, pdMS_TO_TICKS(1000)) == pdTRUE) {
        for (int i = 0; i < priv->config.max_clients; i++) {
            if (priv->clients[i].active) {
                if (priv->clients[i].task_handle != NULL) {
                    vTaskDelete(priv->clients[i].task_handle);
                    priv->clients[i].task_handle = NULL;
                }
                if (priv->clients[i].socket >= 0) { close(priv->clients[i].socket); priv->clients[i].socket = -1; }
                priv->clients[i].active = false;
            }
        }
        priv->client_count = 0;
        xSemaphoreGive(priv->clients_mutex);
    }                                    /* ← pdFALSE 时以上全部被跳过，且无任何日志/返回码 */
    transport->state = TRANSPORT_DISCONNECTED;
    ESP_LOGI(TAG, "TCP server stopped");
    return ESP_OK;                       /* ← 永远返回 OK */
```
销毁路径 `components/ehome_tcp/ehome_tcp.c:127-151`：
```c
void tcp_transport_destroy(transport_t *transport)
{
    if (transport->ops && transport->ops->deinit) transport->ops->deinit(transport);  /* → tcp_stop */
    tcp_transport_priv_t *priv = transport->priv_data;
    if (priv) {
        if (priv->clients_mutex) vSemaphoreDelete(priv->clients_mutex);   /* 可能仍被 client task 持有 */
        if (priv->clients) free(priv->clients);
        free(priv);
    }
    free(transport);
}
```
同类：`components/ehome_tcp/ehome_tcp.c:458-461` —— `client_count--` 同样在 `if (xSemaphoreTake(...) == pdTRUE)` 内，拿不到锁就**永不递减**。

**为什么这是设计问题**

清理是**必须执行**的动作，却被写成一个"尽力而为"的条件块，且函数的返回类型（`esp_err_t`）不能表达"我没清干净"。同时用 `vTaskDelete` 强杀可能持有互斥量的任务，再删除该互斥量——这是把"线程安全的收尾"交给未定义行为。FreeRTOS 对删除被持有的互斥量没有保护。

**后果**

- `tcp_stop()` 在压力下跳过清理 → socket 泄漏、`client_count` 不归零 → `tcp_is_connected()`（`:320`）**永久返回假真** → 上层以为有对端可用。
- `vSemaphoreDelete` 一个仍被 `tcp_client_task` 持有/阻塞等待的锁 → 句柄悬空，后续 `xSemaphoreGive`/`Take` 命中已释放内存 ⇒ 断言或踩踏。
- 当前 `tcp_transport_destroy` 零调用（见 D-12），所以是**潜伏**缺陷；但 3.0 的"双栈并存 → 退役 MQTT"与重连策略一定要走销毁路径。

**3.0 改进方向**

- 清理无条件执行，并把失败**返回**：`esp_err_t tcp_stop(transport_t *t)`；拿不到锁就报错而不是跳过。
- 用"停止标志 + 协作退出（任务自删并置 `task_handle = NULL`）+ 有界 join"替代 `vTaskDelete` + 删锁；锁的销毁必须在**确认无持有者**之后。
- `client_count` 改为由"活跃槽位数"派生（遍历统计），避免两个写入点各自维护一个计数。

### D-15　编码器溢出只体现在返回值里，无"粘滞错误"，最自然的调用形态会静默丢字段

**证据**

```c
{
```

以及 `handler_data.c:290-291`、`:303-304`：
```c

        ...
        (void)frame_encode_bytes(&enc, STATUS_RPT_F_CONTROL_STATS, ...);
```
另一处口径不一致（同文件 `:40`）：`frame_encode_varint` 为 varint **多预留 10 字节**（`frame_codec.c:40` `encoder_ensure_space(enc, tag_size + 10)`），而调用方若按 `frame_varint_size()`（`frame_codec.h:163`）估算容量，会得到**不同**的"装得下吗"答案。本仓已有过一次同形缺陷（提交 `06e7a2f0`："修复配置因'模板容量'被拒 —— 校验口径与编码器不一致"）。

**为什么这是设计问题**

**3.0 改进方向**

- `frame_encoder_t` 增加 `bool overflow;`（粘滞）；`frame_encoder_size()` 在 overflow 时返回 0；`publish` 前统一 fail-closed。
- 或者让 `frame_encode_*` 返回 `void`，在消息结束时提供一次 `frame_encoder_ok(&enc)` 检查——让"忘记检查"变成**编译期**可见（函数不存在就无法忽略）。
- 容量算术只保留一处：把 `frame_varint_size` 与编码器的预留规则统一（或让调用方通过 `frame_encoder_remaining()` 询问）。

### D-16　`ESP_ERR_INVALID_STATE` 一码两义（"未初始化"与"没有任何通路成功"）

**证据**

`components/transport/transport.c:78-110`：
```c

{
    if (!s_initialized) { return ESP_ERR_INVALID_STATE; }     /* 语义 A：子系统未就绪 */
    if (!data || len == 0) { return ESP_ERR_INVALID_ARG; }
    int sent_count = 0;
    for (...) { if (t->ops->is_connected(t)) { if (t->ops->send(...) == ESP_OK) sent_count++; } }
```

```c
static size_t db_field_varint_size(uint8_t field_num, uint64_t value) { ... }
```

消费点 `components/bus_worker/bus_worker.c:606-616`：

```c
  ...
  size_t projected = data_batch_frame_size(desc->channel_id, desc->timestamp_us, ...);
  if (projected > DATA_BATCH_BUF_SIZE) break;      /* 降 n */
```

契约（`components/bus_worker/include/bus_worker.h:124-132`）只给 `bool (*data_batch_cb_t)(...)`——**无法回答"这 n 个样本装得下吗"**。

- 若必须保留预言（为了不链接编码器），则把它做成**唯一的**实现并让编码器**调用它**（而不是各写一份）。

### D-19　`frame_field_get_string()` 静默截断并返回成功

**证据**

`components/frame/frame_codec.h:181-189`：
```c
static inline frame_err_t frame_field_get_string(const frame_field_t *f, char *buf, size_t sz) {
    if (!f || !buf || sz == 0) return FRAME_ERR_INVALID_TAG;
    if (f->wire_type != WIRE_LENGTH_DELIMITED) return FRAME_ERR_INVALID_TAG;
    if (!f->value.bytes.ptr) { buf[0] = '\0'; return FRAME_OK; }
    size_t n = f->value.bytes.len < sz - 1 ? f->value.bytes.len : sz - 1;
    memcpy(buf, f->value.bytes.ptr, n);      /* ← 超长即截断 */
    buf[n] = '\0';
    return FRAME_OK;                          /* ← 仍然报告成功 */
}
```

**为什么这是设计问题**

"取到了"与"取到了但被截短"是两种不同的事实，接口把它们合并成一次 `FRAME_OK`。调用方若未在调用前自己做长度前置检查，就会把**前缀**当完整值使用——这是静默改写（族 4），而契约没有任何提示。

**后果**

标识类字段（`ota_id` / `manifest_id` / `request_id` / `sync_id`）被截断后，服务端与设备**各持一个不同的 ID**：表现为"配置下发成功但设备说没收到"、"OTA 进度上报对不上"这类无错误码的错配。当前多处调用点确实做了前置长度检查（例如 `handler_data.c:81-91` 检查 `field.value.bytes.len >= sizeof(...)` 才调用），所以是**潜伏**缺陷；但接口默认行为是危险的。

**3.0 改进方向**

- 返回 `FRAME_ERR_OVERFLOW`（或增加 `bool *truncated` 出参），让"截断"成为**调用方必须显式选择**的行为；提供 `frame_field_get_string_exact()` 作为安全默认。

**证据**

`components/ehome_mqtt/mqtt_transport_adapter.c:21-25`：
```c

{

}
```
`components/ehome_mqtt/mqtt_transport_adapter.c:66-69`：

```c
static void mqtt_adapter_deinit(transport_t *transport)
{
    // ehome_mqtt 没有 deinit API
}
```
`components/ehome_tcp/ehome_tcp.c:153-161`：

**为什么这是设计问题**

**后果（use-after-free 路径）**

`components/ehome_mqtt/mqtt_transport_adapter.c:157-168`：
```c

{
    if (!s_adapter) return;
    transport_unregister(&s_adapter->transport);
    free(s_adapter);                  /* ← transport 结构被释放 */
    s_adapter = NULL;
}
```
但 MQTT 事件回调仍持有指向它的上下文（`:141-142`）：
```c

    mqtt_client_register_state_cb(mqtt_adapter_state_cb, &s_adapter->transport);
```
`mqtt_adapter_msg_cb` 会解引用 `transport->msg_cb`（`:82-89`）、`mqtt_adapter_state_cb` 会写 `transport->state`（`:113`）——**释放后再来一条 MQTT 事件即为 use-after-free**。该函数当前零调用（D-12），属潜伏；3.0 切换传输时必然经过注销路径。

**3.0 改进方向**

- 要么删掉 `init/deinit`（让接口诚实），要么让它们真正承担生命周期：`init` 做全部资源分配并返回错误，`deinit` 做全部释放。
- 注销**必须**先反注册回调（`mqtt_client_register_msg_cb(NULL, NULL)`），再 deregister/释放；顺序写进接口注释并加用例。

### D-25　三个 `uint8_t buf[1400]` 放在栈上；池大小与栈预算靠注释耦合，跨组件的 1024↔1400 是隐式契约

**证据**

同一文件里三个 1400 字节栈帧（`components/msg_handler/handler_data.c`）：
```c
:150    uint8_t buf[1400];      /* msg_handler_send_status      —— 由 status_task 调用 */
:327    uint8_t buf[1400];      /* msg_handler_send_data_report —— 由 report_tx 调用 */
:363    uint8_t buf[1400];      /* msg_handler_send_data_batch  —— 由 report_tx 调用 */
```
`send_status` 里还**嵌套**了三个子编码缓冲（同一栈帧内累计）：
```c
:174    uint8_t ch_buf[512];      /* ChannelHealth 子帧 */
:199    uint8_t ed_buf[64];       /* 每个 EdgeDeviceHealth 子帧（循环内） */
:239    uint8_t perf_buf[192];
:296    uint8_t control_buf[48];
```
调用方栈预算与它绑定（注释自陈，非我实测）：
- `components/bus_worker/bus_worker.c:101-115`：*"report_tx 的栈。4096 在 2026-10-04 的排查中被判定**不安全**…… send_data_report 有 2416 字节的栈帧（`handler_data.c:254`，其中 `uint8_t buf[1400]` 是必需的）…… **⚠ 根因未消除：send_data_report 仍把 2416 字节放在栈上。**"*
- `main/main.c:115-143`：`STATUS_TASK_STACK` 从 6144 → 8192 → 5120 的调整理由全部围绕这个 1400 字节帧。
- `components/msg_handler/CMakeLists.txt` 与 `components/bus_worker/CMakeLists.txt` 分别设 `-Wframe-larger-than=3072` 与 `=1024`。

跨组件的常量耦合（**隐式契约**）：
- `components/bus_worker/bus_worker.c:82`：`#define REPORT_PAYLOAD_BLOCK_SIZE 1024`
- `components/bus_worker/bus_worker.c:143-146`：`#define DATA_BATCH_BUF_SIZE 1400`（注释：*"真正的 buf[1400] 在 msg_handler 的批量编码器里"*）
- `components/msg_handler/handler_data.c:149`：*"DataReport payloads are produced by the bus-worker fixed block pool (currently 1024 bytes)……"*

**为什么这是设计问题**

1. **缓冲尺寸是跨模块契约，却写在两个组件的注释里。** `bus_worker` 的池块是 1024，`msg_handler` 的编码缓冲是 1400，两者必须满足"1400 ≥ 1024 + 报头开销"。这个约束**没有任何编译期检查**，只有注释与"如果超了就 `FRAME_ERR_OVERFLOW` → 打日志 → 丢帧"的运行时后果。3.0 若要改块大小（100 Hz 下很可能会），改动点分散在两个组件。
2. **`1400` 这个数字的来源是一个已调参过的经验值**（"512 字节栈缓冲装不下一个完整块"），第 4 个 `buf[N]` 出现时没人会重新算总账。
3. **栈是"空间换确定性"的正确选择，但前提是尺寸可证明。** 现在的保证方式是 `-Wframe-larger-than` + 任务栈手算 + 注释警告。这种保证在"再加一个缓冲"时立即失效（2026-10-04 的两次栈溢出正是这么发生的：门禁当时只覆盖一个文件）。
4. `send_status` 的**嵌套**子编码器（512+64+192+48 与 1400 同帧）使真实峰值远大于单个 `buf[1400]`，而 `-Wframe-larger-than=3072` 是按"整帧"判的——需要确认编译器是否把嵌套数组算进同一帧（通常会）。

**后果**

- 栈溢出 = 随机踩踏/复位，历史上已发生两次（`log_tx` 1536→4096、`status_task` PANIC，转引 `CMakeLists.txt` 头部与 `bus_worker.c:101-131` 注释）。
- 池块与编码缓冲不一致时，表现为"大 payload 的帧被静默丢弃"（`report_enqueue` 打一行 WARN 后按 critical 与否决定计数或降级，`bus_worker.c:787-799`）——即 **100 Hz 下最不该丢的数据以最不显眼的方式丢失**。

**3.0 改进方向**

- **编码缓冲上移为调用方提供的参数**（`frame_encoder_init(&enc, buf, cap, type)` 已经是这个形状）：由 `report_tx` 任务持有一块**任务自有的**编码缓冲，或从既有的 1024 池块**原地编码**（省掉整块拷贝），`msg_handler` 侧不再有 1400 字节栈帧。
- 池块大小、编码预算、任务栈三者**集中定义在一个头文件**并加 `_Static_assert(ENCODE_BUF >= POOL_BLOCK + HEADROOM)`——把隐式契约变成编译期错误。
- 保留并强化 `-Wframe-larger-than` 门禁；给"新增栈缓冲"设一个人工评审项（提 PR 模板即可，不需要新工具）。

## 7. 3.0 应确立的设计原则（从缺陷反推，可执行）

> 每条原则后面标注它治的是哪几条缺陷。原则只谈**结构与接口**，不改变任何产品行为。

- **P1　接口的返回值必须能表达调用方的每一个决策分支。**
  若调用方需要区分"N 种情况"，返回值就必须能表示 N 种；不允许把分类信息在抽象边界压平，再由调用方"另发明一个查询把信息猜回来"。
  具体判据：把返回值换成 `void`，调用方是否还能写出正确策略？若能，说明返回值是装饰；若不能，说明它是必需的，必须完整。→ 治 **D-01 / D-16 / D-17 / D-20**
- **P2　"可失败的操作"不得返回 `void`；启动路径必须 fail-closed。**
  启动/初始化/注册/停止/销毁五类操作的返回值必须被处理；忽略即视为缺陷。→ 治 **D-05 / D-12 / D-21 / D-26**
- **P3　公开结构体不透明化：跨模块不得直接读写他人字段。**
  对外只暴露句柄或前向声明；状态只经"快照查询"获得，且**单一真值源**（不得有"字段 vs 函数"两个答案）。→ 治 **D-04 / D-13**
- **P4　一个计数器只承载一个语义。**
  面向运维的字段（健康/错误/丢弃）必须能区分"对端问题"与"本机问题"；不得用同一个数字表达两种成因。→ 治 **D-07 / D-15**
- **P5　契约里没写的前置条件，等于不存在。**
  接口必须写明：一次回调交付的边界（完整消息 or 字节块）、发送的原子性（是否允许部分写）、所有权的转移时机（成功时/失败时/始终）。→ 治 **D-09 / D-10 / D-19 / D-21**
- **P6　门禁必须打到生产代码上。**
  测试目标里没有生产 `.c` 的用例，不得计入覆盖率；不得用"复刻决策结构"的用例声称锁住了某个修复。核心策略（如"每帧只发一次"）应下沉到可宿主编译的层去测。→ 治 **D-08 / D-24**
- **P7　组件依赖图无环；单组件依赖数有上限；宽度超标须写明理由。**
  `msg_handler` REQUIRES 12 个组件、与 `bus_worker` 成环，是"分发层被业务污染"的直接结果；被双方需要的窄接口应**下沉为独立组件**，而不是靠链接顺序容忍。→ 治 **D-14 / D-02 / D-06**
- **P8　禁止用链接期技巧替代显式注入。**
  生产代码里不得出现跨组件的 `__attribute__((weak))` 函数定义、不得依赖静态库解析顺序；已有注入点存在时，必须使用它。→ 治 **D-06**
- **P9　线格式只有一份实现。**
  编码器与"尺寸预言"不得各写一份算术；调用方若需要知道"装不装得下"，契约必须直接回答。→ 治 **D-18**
- **P10　大缓冲不得放在栈上；缓冲尺寸是接口的一部分。**
  编码缓冲改由调用方提供（`enc(buf, cap, msg_type)` 已经是这个形状，继续沿用并明确"谁拥有、能多大"）；跨模块的"1024/1400"这类耦合常量必须集中定义并有 `_Static_assert` 守卫。→ 治 **D-25**（见下）与现有 `-Wframe-larger-than` 门禁的延续
- **P11　死代码与死 API 一律删除，而不是留着。**
  "零调用"的公开函数要么补调用方，要么删声明；`break;` 之后的不可达块视为缺陷而非风格问题（它在 `-Wall -Wextra` 下不报）。加一条静态检查：`-Wunreachable-code` 不可用时用脚本扫描"case 内 break 之后的语句"。→ 治 **D-03 / D-12**
- **P12　有状态模块必须有对称的 create/destroy（或 reset）。**
  静态存储期的状态不得作为唯一形态；资源"只申请不归还"的接口（`dma_pool_release`、`tcp_transport_destroy` 零调用）必须在 3.0 前补齐调用方或删除。→ 治 **D-12 / D-22 / D-11**

## 8. 已经做得好、**不要动**的部分

只列问题会让改动失去边界。以下设计在本次审计中是加分项，3.0 重构应保留：

1. **解码侧的严格性**（`frame_codec.c:131-162`）：`decoder_read_varint` 检查 `shift == 63 && byte > 1`、拒绝非规范编码（`byte == 0` 且长度 > 1）、`len > SIZE_MAX` 检查。这套 fail-closed 的解析纪律是 3.0 新编码应当继承的。
2. **`-Wframe-larger-than` 组件级门禁 + 逐条注明根因**（`components/*/CMakeLists.txt`）：2026-10-04 的两次栈溢出后，门禁从"只看一个文件"扩到所有编译型组件，且每家都写明了阈值理由。**这是本仓最有效的防回退机制之一。**
3. **上报池三级分级 + "绝不丢样本"的回填**（`bus_worker.c:178-201`、`:631-641`）：critical / emergency / telemetry 三段隔离，遥测压力不能吃掉关键响应；批量编码失败时逆序回填队列头。这个思路在 3.0 应当保留。
4. **`_Static_assert` 派生关键上界**（`scheduler.h:42-46`：`SCHED_MAX_CHANNELS` 派生自 `config_mgr MAX_CHANNELS`，并断言 ≥4 的物理下限）：用一个编译期断言消灭了一整类"两个数组长度不一致导致静默截断"的缺陷。
5. **诊断口径的防回退扫描**（`host_tests/diag_heap_metric_scan.py`，转引自 `main/main.c:84-85` 注释）：断言"8BIT 必须与 INTERNAL 同语句出现"，防止内存口径退回。
6. **注释文化**：大量注释记录了**为什么**、实测数字与事故编号（`handler_data.c:187-195` 的 7 天停摆、`ota.c:907-915` 的 90 秒误判、`bus_worker.c:101-131` 的栈账）。这是我能在不上机的情况下做出可引用审计的前提，也是 3.0 最该保留的工程习惯。
