## 3. 三个核心层 — 不变量

### 3.1 节点层 (Node Layer)

**不变量**:
- 节点是物理设备,有自己的 `node_id` (MAC 派生)
- 节点只跟中心端通过 MQTT 通信
- 节点**不知道** EdgeDevice / DeviceConfig 概念 (在中心端)
- 节点的 ConfigMgr 只存"通道配置" (bus_type + bus_config) + "模板池版本"
- 节点的 Scheduler 接到"通道配置"后,跟本地 parser 配合,产出 DataReport

### 3.2 通道层 (Channel Layer)

**不变量**:
- 一个通道 = 一个物理总线实例 (e.g. I2C0, SPI2)
- 通道只描述**怎么通信** (引脚/速率/模式),不描述**跟谁通信**
- 通道的"物理参数"是**节点层**的事,跟 DeviceConfig 无关
- 通道的"逻辑设备"是**EdgeDevice**层的事,通过 `edge_devices.channel_id` 关联

### 3.3 边缘设备层 (EdgeDevice Layer)

**不变量**:
- EdgeDevice = 中心端的逻辑抽象
- 一个 EdgeDevice = Node + Channel + DeviceConfig 三元组实例化
- EdgeDevice 是数据采集的**实际载体** (DataReport 关联到 EdgeDevice.id)
- EdgeDevice 的"型号" (device_config_id) 决定了解析器和初始化流程
- EdgeDevice 的"采集参数" (interval_ms) 在 EdgeDevice 上,不在 DeviceConfig 上

## 4. 拓扑示例

### 4.1 简单 1:1 (SPI)

```
节点: esp32c6_001
├─ 通道 1: SPI2 (mosi=11, miso=13, sck=12, cs=10, 10MHz)
│   └─ 边缘设备 10:
│       ├─ 设备配置 5: BMP280 (SPI 默认)
│       ├─ hardware_id: 0
│       ├─ interval_ms: 1000
│       └─ 启用
├─ 通道 2: I2C0 (sda=8, scl=9, 400kHz)
```

### 4.2 共享总线 (I2C 多设备)

```
节点: esp32c6_001
├─ 通道 2: I2C0 (sda=8, scl=9, 400kHz)
│   ├─ 边缘设备 11:
│   │   ├─ 设备配置 5: BMP280
│   │   ├─ hardware_id: 0x76  ← I2C 地址
│   │   ├─ interval_ms: 1000
│   │   └─ 启用
│   └─ 边缘设备 12:
│       ├─ 设备配置 6: SHT30 (I2C 协议)
│       ├─ hardware_id: 0x44  ← I2C 地址
│       ├─ interval_ms: 2000
│       └─ 启用
```

### 4.3 UART + GPIO 混合

```
节点: esp32c6_001
├─ 通道 3: UART1 (tx=20, rx=21, 9600,8,N,1)
│   └─ 边缘设备 13:
│       ├─ 设备配置 7: SN3000 风速风向
│       ├─ hardware_id: 0  (UART 通常无地址)
│       ├─ interval_ms: 500
│       └─ 启用
├─ 通道 4: GPIO (pin=18, output)
│   └─ 边缘设备 14:
│       ├─ 设备配置 8: relay_switch
│       ├─ hardware_id: 0
│       ├─ interval_ms: 0  (事件触发, 不轮询)
│       └─ 启用
```

### 4.4 跨节点共享 DeviceConfig

```
设备配置 5: BMP280 (BMP280 型号定义)
│  ├─ connection: { protocol: SPI, default_params: ... }
│  ├─ parser: bosch.bmp280
│  └─ init_flow: 5 步
│
├─ 边缘设备 10: Node A, SPI2, hw=0  ← 复用 BMP280
├─ 边缘设备 20: Node B, SPI2, hw=0  ← 复用 BMP280 (不同节点)
├─ 边缘设备 30: Node C, I2C0, hw=0x76  ← 复用 BMP280 (不同协议/地址)
└─ 边缘设备 31: Node C, I2C0, hw=0x77  ← 复用 BMP280 (同节点不同地址)
```

> **关键洞察**: DeviceConfig 是**协议无关**的,可在 SPI / I2C / 任何总线上实例化;而"该设备用什么通信"由 Channel + EdgeDevice.hardware_id 决定

## 5. 与 v2.1 现状对比

### 5.1 数据库 schema 对比

| 概念 | v2.1 表 | v2.2 改名 | v2.2 字段变化 |
|------|---------|----------|--------------|
| 节点 | `collectors` | → `nodes` | 表名变 |
| 通道 | `channels` | 不变 | `node_id` → `node_id` |
| 设备 | `devices` | → `edge_devices` | 加 `device_config_id` (FK) |
| 设备模板 | `device_configs` | 不变 (改语义) | 强化 `connection` / `parser` / `init_flow` 字段 |
| 模板 | `config_templates` | 不变 | v2.2 加 Template Pool 表 |
| 配置版本 | (无) | 新增 `config_meta` | v2.1 同步机制已加 |

### 5.2 关键变化

**v2.1** 的 `Device` 表:
```go
type Device struct {
    ID        uint
    Name      string       // "BMP280 in site A"
    Type      string       // "bmp280"  ← 跟 DeviceConfig.DeviceType 重复
    ParserID  string       // ← 也跟 DeviceConfig.ParserID 重复
    ChannelID uint
    Status    string
    // 缺: device_config_id
}
```

**v2.2** 的 `EdgeDevice` 表 (建议):
```go
type EdgeDevice struct {
    ID              uint
    Name            string        // "BMP280 现场 A" (业务名, 冗余但运维需要)
    NodeID          uint          // 物理节点 (FK)
    ChannelID       uint          // 物理通道 (FK)
    DeviceConfigID  uint          // 型号定义 (FK) ← 关键变化
    HardwareID      uint          // 通道上的地址 (I2C 0x76 / SPI 0 / GPIO pin)
    IntervalMs      int           // 采集频率
    Enabled         bool
    Status          string        // active/error/disabled
    // 删除: Type, ParserID (都从 DeviceConfig 读)
}
```

### 5.3 关键解耦

| v2.1 问题 | v2.2 解耦 |
|----------|----------|
| `Device.Type` 和 `DeviceConfig.DeviceType` 重复 | EdgeDevice 不存 type, 通过 device_config_id 查 |
| `Device.ParserID` 和 `DeviceConfig.ParserID` 重复 | 同上, 从 DeviceConfig 读 |
| 改 DeviceConfig 时 Device 不更新 | EdgeDevice 用 device_config_id 引用, 实时一致 |
| 节点不知道 EdgeDevice (但又被下发 channel 引用 template) | 节点只接收 channel 配置, 不接收 EdgeDevice |
| Init sequence 在哪? 在 Device 还是 DeviceConfig? | 在 DeviceConfig.init_flow, 边缘设备初始化时按此执行 |

## 6. 协议层 (Node ↔ Center)

### 6.1 协议不下发"EdgeDevice" 概念

**原因**: 节点不知道 EdgeDevice, EdgeDevice 是中心端的逻辑抽象

**节点接收的**:
- Channel 配置 (bus_type, bus_config, template_refs)
- Template Pool (二进制命令模板)
- Parser (从 DeviceConfig 推导, 但以"注册过的 parser id"形式下发)

**节点不接收的**:
- EdgeDevice.id (中心端 PK)
- EdgeDevice.name (业务名)
- EdgeDevice.device_config_id (中心端 FK)

### 6.2 协议字段命名 (v2.2)

| 概念 | 协议字段 (建议) | 备注 |
|------|----------------|------|
| 节点 | `node_id` (string) | 替代 `device_id` (v2.1) |
| 通道 | `channel_id` (uint32) | 不变 |
| 设备配置 | `device_config_id` (uint32) | v2.2 引用下发 |
| 模板 | `template_id` (uint32) | v2.2 引入 |
| 边缘设备 | (不下发, 中心端内部) | — |

**兼容性**: v2.2 协议用 `node_id` 替代 `device_id`,需协议版本 bump (v2.1 → v2.2)

---

## 7. 总结: v2.2 三层概念模型 vs v2.1 混淆模型

| 维度 | v2.1 (混淆) | v2.2 (清晰) |
|------|------------|------------|
| 物理设备叫啥 | "采集器" | **节点** |
| 型号定义叫啥 | "设备模板" | **设备配置** |
| 实例化叫啥 | "设备" (易混) | **边缘设备** |
| "设备" 一词 | 5 个地方指 4 个不同事物 | 永远只指具体事物 + 明确限定 |
| 物理-逻辑边界 | Channel / Device 混在一起 | 节点层 vs 边缘层清晰 |
| 协议层 | 下发 Device (过载) | 只下发 Channel + Template |
