## 🔴 致命问题（推翻方案 C）

### F1. 方案 C **破坏原子性**——这是原设计要解决的核心问题

**证据链**：
```
① 原设计的原子性来自「一个命令内同步执行完整序列」:
   bus_worker.c:1338  static bool execute_uart_batch(int ch_idx, bus_dma_ctx_t *ctx,
                                             const bus_cmd_t *cmd, ...)
   ⇒ 整个 plan 由**一个** bus_cmd_t 携带，worker 在一次调用里跑完全部步骤。
      期间该 channel 的 worker 被独占 ⇒ 不存在"步骤间插入"。

② 方案 C 把序列拆成 N 条独立命令:
   步骤 i 执行完 -> 固件 ACK -> 后端再发步骤 i+1
   ⇒ 两次之间 worker **空闲**，会去取样本命令（100Hz 调度）。

③ 更致命的：后端崩溃/网络断 ⇒ 后续步骤**永远不会下发**。
   例: reset_rainfall（read→clear→readback），若在 clear 之后崩溃，
       readback **永不执行** —— 这正是原注释要防的
       "destructive action silently losing readback/finally semantics"
       （definition.go:263-265）
```

**结论**：方案 C 不是"把复杂度从固件搬到后端"，而是**降低了安全保证**。

### F2. 方案 C 的"事务锁"未定义且不可行

```
我的设计写「事务期间锁定该 channel」，但核查发现:

① 槽位是**池式分配**，不是按 channel 索引:
   handler_channel_cmd_v2.c:164-196  reserve_slot()
     遍历 s_slots[]，取"第一个 FREE"或"最旧 FINAL"槽
     ⇒ slot 是池索引，与 channel_id **无关**

② 因此「按 channel 索引的事务表」与现有槽位机制**不一致**。
   要加锁必须另外建立 channel_id -> 事务 的映射，且要处理:
     · 同一 channel 的两个事务竞争
     · 锁与槽位分配的顺序（避免死锁）
     · 锁的超时释放

③ 而样本命令走**另一个队列**（*_cmd_queue），锁不到 ——
   要真正锁定必须改 worker 的取命令逻辑（receive_prioritized_command_raw）。
   ⇒ 改动面远超"新增事务表"
```

### F3. 我在设计中写错的数字

```
文档写「net 14.1 KiB」，独立核算:
  元素 188 B（不是 190）=> 3 队列省 12,384 B = 12.1 KiB（不是 12.0）
  msg_handler 侧省 2,560 B = 2.5 KiB
  事务表：若带 final_raw[128] => 760 B；若复用 s_slots 的 final_raw => 60 B
  ⇒ 净收益 ≈ 12.1 + 2.5 - 0.06 = **14.5 KiB**（数字大致对，但过程与文档不符）
```

### F4. 协议版本升级的解析顺序问题（我未在设计里说明）

```
handler_channel_cmd_v2.c:311-314 的解析 switch:
  case 3: cmd.attempt=...; ... case 14: if(v!=V2_PROTOCOL) goto malformed;
  default: goto malformed;

⇒ 字段 14 **在 switch 里校验**，但新增字段 16/17/18 也会进 switch。
   若 V2_PROTOCOL=1 的命令带了 16，switch 到 case 16 时**还不知道**版本
   （版本在 case 14 才校验，但字段顺序不保证 14 先到）。
   Modbus 风格 wire 的字段是**流式**的，14 可能出现在 16 之后。
⇒ 设计必须改为"两遍解析"或"记录 pending 后置校验"。
   我在设计 8.7 节只写了"实现细节"，**低估了**。
```

## ✅ 自审发现：一个**更好的方案 D**（保留原子性）

### D 的核心洞察

```
原子性的真正来源是「一个命令内执行完整序列」——
那就不该拆命令，而应该【让命令元素不再内联 512 B 的 plan】。

现有机制恰好提供了零成本的落点:
  ① msg_handler 的槽位 s_slots[slot] 已经持有 channel_cmd_v2_t（含 plan_data[512]）
  ② 槽位在 QUEUED 期间**独占**（reserve_slot 只复用 FREE/最旧 FINAL）
  ③ QUEUED 状态**跨越整个执行期**（worker 完成后才 complete_slot -> FINAL）
  ⇒ 槽位的 plan_data 在命令执行期间**天然有效且稳定**
  ⇒ 命令元素只需存**指针**，不需要自己的 512 B 副本
```

### D 的改动点（实测确认，每处都有依据）

| # | 位置 | 改动 | 依据 |
|---|---|---|---|
| 1 | `cmd_queue.h` `bus_cmd_t` | `plan_data[512]` → `const uint8_t *plan_ptr; size_t plan_len; uint8_t plan_step_count;` | 元素 700 → 192 B |
| 2 | `handler_channel_cmd_v2.c:352` | `on_channel_cmd_v2_received(&cmd, slot)` → 传 `&s_slots[slot].cmd` | 现传的是**栈局部** `&cmd`，指针会悬垂 |
| 3 | `bus_manager.c:1359` | 删除 `memcpy(cmd.plan_data, ...)` → `cmd.plan_ptr = plan_data;` | 消除 512 B 拷贝 |
| 4 | `bus_worker.c:1358,1362` | `cmd->plan_data[cursor]` → `cmd->plan_ptr[cursor]` | 读取端 |
| 5 | `bus_worker.c:473-478` `scrub_plan_tail` | 尾部从 520 B 缩到 12 B（指针字段） | ⚠ **指针悬垂风险**：scrub 更必要 |
| 6 | `same_identity` (`handler_...c:136-137`) | 仍比 `plan_data`（槽位自己的副本，未改） | 幂等比较不变 |
| 7 | host_tests | `bus_cmd_t` 的 plan 字段访问需同步改 | 编译期暴露 |

### D 的收益（独立核算）

```
  元素: 700 -> 192 B   （180 公共前缀 + ptr 4 + size_t 4 + step_count 1 + 对齐 3）
  ✅ 符合 ≤256 B 约束（192 < 256）

  3 个 control 队列: 3 x (8 x 700 + 104) = 17,112 B
               -> 3 x (8 x 192 + 104) =  4,920 B
  省: 12,192 B = **11.9 KiB**（堆）

  新增静态开销: **0**（复用槽位已有缓冲，无新分配）
  协议变更:      **无**（wire 不变）
  后端变更:      **无**（仍是一次下发）
  原子性:        **保留**（仍是一个命令执行完整序列）
```

### D 的风险与缓解

| 风险 | 缓解 | 验证状态 |
|---|---|---|
| **悬垂指针**（槽位被提前复用）| `reserve_slot` 只复用 FREE/最旧 FINAL；QUEUED 不可复用 | ✅ 已读代码确认（:164-196）|
| 命令被丢弃时指针悬垂 | `discard_command_queue:2389` 会 `complete_control` 置 FINAL；worker 不再读 | ✅ 已确认 |
| 桥接失败时槽位泄漏 | handler 桥接失败路径直接置 FINAL（:353-360）| ✅ 已确认 |
| `scrub_plan_tail` 尾部残留 | 尾部缩到 12 B，scrub 覆盖全部指针字段 | ⚠ 需改，已列入改动点 5 |
| 跨组件耦合（bus_dma 指向 msg_handler 缓冲）| **已有先例**：`control_slot` 就是这个耦合 | ✅ |
| host 测试失效 | 编译期暴露，逐处修 | ⚠ 待评估影响面 |

## 结论

```
方案 C: ❌ **不可实施**
  致命问题 F1（破坏原子性）+ F2（事务锁不可行）
  ⇒ 它用「降低安全保证」换「内存收益」，方向错了。

方案 D: ✅ **推荐**（保留原子性 + 无协议变更 + 无后端变更 + 省 11.9 KiB）
  仍需评审：scrub 改动、host 测试影响面、跨组件耦合的可接受性。
```

## ⚠ 附录：本报告的 2 处修正（经独立评审指出，2026-10-10）

### 修正 1：改动点 2 的表述有误（**现状无 bug**）
```
原写: 「handler_channel_cmd_v2.c:352 现传栈局部 &cmd => 指针会悬垂」

评审指出（并经我复核确认）:
  · 传的确实是栈局部 &cmd（channel_cmd_v2_t cmd 定义于
    handler_channel_cmd_v2.c:283，调用在 :352）
  · **但 plan 在 bus_manager.c:1359 被 memcpy 进队列元素**，
    栈指针并未逃逸 ⇒ **今天不存在悬垂**

⇒ 正确表述: 「改传 &s_slots[slot].cmd」是**方案 D 的前置条件**，
   不是方案 C 的缺陷。**现状无 bug**。
   原文把它写在"改动清单"里是对的，但语气让人误读。
```

### 修正 2：方案 D 升级为 D-prime（消除裸指针）
```
评审提出的最大风险:
  所有权倒置且**无强制手段** —— bus_dma 队列元素长期持有 msg_handler
  静态槽内缓冲的裸指针，无引用计数、无断言、无状态钩子；
  "FINAL 可复用 != reader 已释放引用"只靠当前执行顺序成立。
  一旦完成发布提前（完成回调走 s_control_final_q **异步队列**，
  bus_worker.c:837-850）或新增取消/重发路径，立即 use-after-free。

⇒ 我的回应: 当前顺序是**严格有序**的（读 plan 与发布 FINAL 在同一任务内
   串行，读在前），但**未来风险成立**，且没有任何机制会报警。

⇒ 设计改为 **D-prime**（带校验的访问器，见方案 D 设计文档 §8.4）:
   · 队列元素只带 control_slot（**已有字段**），连指针都不需要
   · worker 通过 channel_cmd_v2_borrow_plan(slot, ...) 取 plan
   · 访问器内部校验 state==QUEUED，不满足则**打印错误并拒绝执行**
   ⇒ 把隐式不变量变成**显式运行时强制**

   收益还更好: 元素 192 -> 180 B，省 12,384 B = 12.1 KiB（vs D 的 11.9）
```
