# 命名迁移设计 (v2.1 → v2.2)

> **版本**: v2.2 (2026-06-04)
> **状态**: 草案 (Phase 1 部分完成, Phase 2-3 未开始)
> **关联**: [00-术语表.md](00-术语表.md) | [00-概念模型.md](00-概念模型.md)

---

## 1. 迁移目标

将 v2.1 的"采集器 / 设备模板 / 设备" 三层混淆命名,**统一**为 v2.2 的"**节点 / 设备配置 / 边缘设备**" 三层清晰命名。

**核心原则**:
- ✅ **协议层 (wire format)**: 必须 bump 版本 (v2.1 → v2.2), 因为协议字段是 hard-coded 在 firmware 里的,改不了
- ✅ **API 路径 + WS 事件**: 保留旧路径, 加新路径, 灰度切换
- ✅ **数据库**: 保留旧表, 加新表 + 视图 + 同步触发器, 灰度迁移
- ✅ **文档 + 代码变量名**: 一次性改完 (不破坏外部接口)

---

## 2. 命名映射 (权威)

| 概念 | v2.1 (旧) | v2.2 (新) | 兼容性策略 |
|------|----------|----------|----------|
| 物理设备 | Collector / 采集器 | **Node / 节点** | API 路径兼容, DB 表重命名, 协议 bump |
| 型号定义 | DeviceConfig / 设备模板 | **DeviceConfig / 设备配置** | API 路径保持, 文档改, 强化字段 |
| 实例化 | Device / 设备 | **EdgeDevice / 边缘设备** | DB 表重命名, API 路径加 /edge-devices |
| 物理端点 | Channel / 通道 | **Channel / 通道** | 不变 |
| 服务端 | Server / 服务端 | **Center / 中心端** | 文档改, 代码注释改 |

## 3. 分层迁移策略

### 3.1 协议层 (必须改, 需版本 bump)

| 协议字段 | v2.1 | v2.2 | 备注 |
|---------|------|------|------|
| Hello field 1 | `device_id` | `node_id` | ⚠️ v2.2 固件 + v2.2 服务端 |
| Hello field 8 | `protocol_version` | 同 | "2.2" |
| ConfigManifest field | `node_id` | `node_id` | 协议字段 ID 数值不变 |
| MQTT topic | `devices/{id}/up` | `nodes/{id}/up` ⚠️ | 重大变化, 需 broker ACL 重配 |

**v2.2 兼容性矩阵**:

| Server \ Device | v2.1 (旧) | v2.2 (新) |
|----------------|-----------|----------|
| v2.1 (旧) | ✅ 完整 | ⚠️ 设备名 "device_id" 字段, 服务端按 v2.1 解 |
| v2.2 (新) | ⚠️ 服务端识别 v2.1 字段, 映射到 v2.2 schema | ✅ 完整 |

**实施**:
- v2.2 固件 + v2.2 服务端: 同时支持两种 field 名字 (用 frame field number 1 解码, 字段值就是 node_id, 无变化)
- MQTT topic 改变 → 灰度: 旧节点用旧 topic, 新节点用新 topic
- 协议版本号: bump 到 2.2, 老固件上报 2.0/2.1, 新固件上报 2.2

### 3.2 数据库层 (平滑迁移)

**当前表 (v2.1)**:
- `collectors` (节点)
- `channels` (通道)
- `devices` (边缘设备)
- `device_configs` (设备配置)
- `config_templates` (模板)

**v2.2 目标表**:
- `nodes` (节点, 从 `collectors` 迁移)
- `channels` (通道, 不变, 改 FK)
- `edge_devices` (边缘设备, 从 `devices` 迁移)
- `device_configs` (设备配置, 强化字段)
- `config_templates` (模板, 不变)

**迁移策略**:

```sql
-- 步骤 1: 创建新表 + 视图 (v2.2 部署时)
CREATE TABLE nodes (
  id SERIAL PRIMARY KEY,
  node_id VARCHAR(32) UNIQUE NOT NULL,  -- 物理 ID (e.g. esp32c6_XXX)
  model VARCHAR(20),
  -- ... 其他字段同 collectors
);

-- 步骤 2: 数据迁移
INSERT INTO nodes (id, node_id, model, ...)
  SELECT id, device_id, model, ... FROM collectors;

-- 步骤 3: 视图兼容 (旧代码继续读 collectors 名)
CREATE VIEW collectors AS SELECT * FROM nodes;
-- 注: GORM 也支持 gorm:"tableName:collectors" 兼容

-- 步骤 4: 修改 channels FK
ALTER TABLE channels RENAME COLUMN node_id TO node_id;

-- 步骤 5: 同理 edge_devices
CREATE TABLE edge_devices (...);
INSERT INTO edge_devices SELECT * FROM devices;
ALTER TABLE devices RENAME TO devices_deprecated;
```

**兼容期**: 6 个月,期间 `collectors` 视图 = `nodes` 表, 代码可双写

**实施工期**: 1 天 (SQL 迁移脚本) + 0.5 天 (后端代码改 GORM 表名)

### 3.3 API 路径层 (双路径, 灰度切换)

| v2.1 路径 | v2.2 路径 | 兼容策略 |
|----------|----------|---------|
| `GET /api/v1/nodes` | `GET /api/v1/nodes` | 双路径, 都返回 nodes 数据 |
| `GET /api/v1/nodes/:id` | `GET /api/v1/nodes/:id` | 双路径 |
| `POST /api/v1/nodes` | `POST /api/v1/nodes` | 双路径 |
| `GET /api/v1/devices` | `GET /api/v1/edge-devices` | 双路径 |
| `GET /api/v1/devices/:id` | `GET /api/v1/edge-devices/:id` | 双路径 |
| `GET /api/v1/device-configs` | (保持) `/api/v1/device-configs` | 路径不变 (语义改) |

**实施**: gin 路由用 `HandleContext`,两个路径都注册到同一个 handler

**前端**: 旧路径用 1-2 个月, 切到新路径, 然后清理

**工期**: 1 天 (后端 + 前端)

### 3.4 WebSocket 事件层 (双事件名, 灰度)

| v2.1 事件 | v2.2 事件 | 兼容策略 |
|----------|----------|---------|
| `node_status` | `node_status` | 推送两个, 订阅两个, 二选一 |
| `data_update` | (保持) | 名字不变, payload 加 `edge_device_id` 字段 |
| `device_status` | `edge_device_status` | 推送两个, 订阅两个 |

**v2.2 事件名规范**: `<resource>_<verb>`, 见 [同步机制 §7](../设计/同步机制/详细设计.md)

**工期**: 0.5 天

## 5. 风险评估

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 协议 bump 后老固件不识别 | 高 | 高 | 协议版本号协商 + 字段兼容解码 |
| MQTT topic 改变 broker ACL 失效 | 中 | 高 | 灰度: 旧 topic 保留 6 个月, ACL 双重配置 |
| DB 迁移丢数据 | 低 | 致命 | 全量备份 + 迁移前 dry-run |
| 前端组件重命名漏 import | 中 | 中 | TypeScript strict mode + 全量 typecheck |
| 文档改动漏改某处 | 高 | 低 | grep 检查 + CI 校验 "采集器" 出现次数 |
| 团队成员习惯旧名 | 高 | 低 | 文档 + PR review 强制新名 |

---

## 6. 不变性保证 (Invariants)

迁移过程中,这些**绝对不能改**:

1. **二进制协议 wire format (除了 v2.2 bump)**: frame format 0xEB + length + type + payload **不变**
2. **MQTT broker topic 至少 6 个月保留旧名**
3. **API 路径至少 6 个月保留旧名**
4. **数据库表/列名至少 6 个月保留** (通过 view 兼容)
5. **WS 事件名至少 6 个月保留**
6. **所有用户/客户已部署的设备能继续工作** (v2.1 节点 + v2.2 中心端, 降级路径)
