## 四、功能回归 — HA 集成（15 分钟）

前提：HomeAssistant 已订阅 EMQX（或用 `mosquitto_sub -t 'homeassistant/#' -v` 替代观察）。

| 用例 | 操作 | 预期 |
|------|------|------|
| H1 状态推送 | 设备正常上报 | `homeassistant/sensor/<node>_<field>/state` 持续收到最新值 JSON；**允许丢帧**（QoS0），但最终值必须与 unified_data 最新值一致 |
| H2 发现配置 | 新建设备/重启节点 | `homeassistant/sensor/<node>_<field>/config` 仍为 retained 消息（`mosquitto_sub -t '...' -r` 可重读） |
| H3 HA 宕机隔离 | 停掉 HA 订阅端（或断开 broker 到 HA 链路），设备持续上报 ≥2 分钟 | 后端日志无刷屏（队列满 WARN 限频在 1024 设备内不触发）；恢复 HA 后状态自愈为最新值；**期间 unified_data 入库不中断** |
| H4 命令面不受影响 | broker 短暂不可达时下发设备命令 | 命令仍走 QoS1 重试语义，恢复后送达（对比旧版会被 HA 发布阻塞） |

**验收点 G3**：HA 链路故障不影响核心数据入库与命令下发（这是 P0-3 的核心目标）。

## 六、性能复测（对照原压测，60 分钟）

复用留档工具：`/tmp/ehload/`（压测器）、`scripts/bench/prepare_bench_data.sh`（数据准备）。

```bash
# 1. 准备 1000 模拟节点
bash scripts/bench/prepare_bench_data.sh 1000

# 2. 资源采样（后台）
python3 /tmp/ehload/sampler.py /tmp/ehload/sample_after.csv 360 &

# 3. 逐档压测（与原报告相同档位）
cd /tmp/ehload && ./ehload --nodes 200 --rate 2 --duration 60 --qos 1 --device-base 3    # S1 400/s
./ehload --nodes 500 --rate 4 --duration 60 --qos 1 --device-base 3                      # S2 2000/s
./ehload --nodes 1000 --rate 5 --duration 60 --qos 1 --device-base 3                     # S3 5000/s
./ehload --nodes 1000 --rate 10 --duration 60 --qos 1 --device-base 3                    # S4 10000/s

# 4. 每档对账（精确丢率）
docker exec ehome-postgres psql -U ehome -d ehome -t -A -c \
  "SELECT count(*) FROM unified_data WHERE device_id BETWEEN 3 AND 1002;"

# 5. 清理
docker exec ehome-postgres psql -U ehome -d ehome -q -c \
  "DELETE FROM edge_devices WHERE node_id LIKE 'SIM%'; DELETE FROM nodes WHERE node_id LIKE 'SIM%';"
```

**对照表（修复前 → 修复后预期）**：

| 档位 | 输入 msg/s | 修复前 parser 处理 | 修复前丢弃率 | 修复后预期处理 | 修复后预期丢弃率 |
|------|-----------|------------------|-------------|---------------|-----------------|
| S1 | 400 | 3,842 (16%) | 84.0% | ≥21,600 (90%) | ≤10% |
| S2 | 2,000 | 3,807 (3.2%) | 96.8% | ≥60,000 (50%) | ≤50% |
| S3 | 5,000 | 2,056 (0.7%) | 99.3% | 显著提升 | 待实测 |
| S4 | 10,000 | 2,145 (0.4%) | 99.6% | 显著提升 | 待实测 |

判定口径：
- S1 预期最好（8 分片 × 64 evt/s = 512 evt/s > 400 输入，理论近零丢）
- S2（2000/s）超过 512 理论上限，预期仍有丢弃但处理量应 ≈500×60=30,000+（8 倍于旧值）
- 若 S1 丢弃率仍 >20%，判定未达标，回报数据

**同时观察**：
- 日志行速率（sampler CSV）：修复前 S4 峰值 28k 行/s → 预期 <1.5k 行/s
- 5 分钟日志体积：修复前 193MB → 预期 <10MB
- 后端 RSS：应仍稳定在 <100MB（新增分片 worker 预期 +10~20MB）
- CPU：S1-S2 段应明显高于修复前同档（并行干活了），但 S4 不应超过 ~3 核

**验收点 G5**：S1 丢弃率 ≤10%、日志量降一个数量级、S2 处理量 ≥8×基线。
