## 判定

- **S1 ≤10% 丢弃**：✅ 0% 丢弃（24000 输入全处理）。8 分片 × 64 evt/s = 512 evt/s 理论 > 400 输入，验证通过
- **S2 处理量 ≥8× 基线**：⚠️ 6.7×（25,411 vs 30,456=8×）。受 512 evt/s 理论上限约束（=30,720 最大），
  实测达理论值的 83%。方案"≈30,000+"口径基本达成
- **日志降一个数量级**：⚠️ 部分达成。P0-2 三处热路径日志 info 级下 0 输出（DataReport/Received/Parsed
  全部为 0 行），S1 档日志 181 行/s（原 1,267）。但 **Terminal WS channel full WARN 刷屏**（死代码
  路径，见下）使 S4 档峰值仍达 ~9,058 行/s（原 28,046，降 3 倍）
- **CPU ≤3 核**：✅ 峰值 2.34 核（S4）
- **RSS <100MB**：✅ 峰值 52MB（基线 40MB，+12MB 符合分片 worker 预期）
- **PG 写入**：✅ 峰值 3,744 插入/s（原 ~450/s，8.3×，DB 写入瓶颈解除）

## 发现：P1 — Terminal WS 死代码 WARN 刷屏

- 位置：`backend/internal/terminal/terminal.go:164-168`（record() 内 select default）
- 根因：`m.wsCh`（chan TerminalEvent, 缓冲 256）**无生产消费者**——`Events()` 仅 terminal_test.go
  使用；真实终端事件走 websocket hub 的 channel_data 广播（ws_handler.go:90 Subscribe→dispatchEvent）。
  通道 256 填满后无人消费，每事件触发 default 分支打一条 WARN
- 影响：压测期间 26 万行 WARN（S1 档 4,597 条），是 P0-2 降噪后最大日志源；生产环境低速率下量小
  但同样是纯浪费
- 建议：① 删除 wsCh/record() 中 WS 广播段（确认无消费者后死代码清理）；② 或把 WARN 降为
  Debugf/限频。属 P0-2 同族日志降噪遗漏，非本次修复引入（原压测同路径存在）
