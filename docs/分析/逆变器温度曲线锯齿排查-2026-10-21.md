# 逆变器温度曲线锯齿 — 深入排查报告（2026-10-21）

用户反馈「温度曲线有锯齿」。本报告给出**完整证据链**与结论，结论推翻了我第一轮的判断。

---

## 一、结论先行

**锯齿是真实数据，不是渲染 bug，也不是降采样伪影。**
根因在**数据面**：逆变器驱动的 `HTEMP` 温度读取存在**周期性升温→回落的采集假象**，
表现为 5 路温度同步以约 **22~27 分钟**为周期，先缓慢爬升 3~8℃，再快速回落，形成锯齿。

前端渲染参数（`smooth` / `sampling:lttb` / 多序列 / Y 轴范围）**均已逐一排除**。

---

## 二、排除过程（每一步都有对照实验）

### 2.1 排除「前端画错了」

| 实验 | 做法 | 结果 |
|---|---|---|
| 同一份数据在空白容器重画 | 取真实图表的 `getOption()` 原样喂给新 `echarts.init` | **锯齿完全复现** ⇒ 与容器/时序无关 |
| 只画 1 条序列 | `series` 截断到第 1 条 | 锯齿仍在（幅度略小） ⇒ 非多序列叠加问题 |
| 去掉 `smooth: true` | 逐条设 `smooth:false` | 齿数 **完全不变**（53→53） |
| 去掉 `sampling: 'lttb'` | `sampling: null` | 齿数 **完全不变**（53→53） |
| 去掉 `areaStyle` | 删除渐变填充 | 齿数不变 |
| 固定 Y 轴 0~60℃ | 压缩纵向放大倍数 | 齿形**依然清晰可见** ⇒ 不是「Y 轴范围过窄把噪声放大」 |

### 2.2 排除「API 返回的数据和图表拿到的不是一份」

从运行中的图表实例 `getOption()` 取出 577 个点，与同一时刻的 API 响应逐个比对：**时间戳完全重合、值完全一致**。
用同一套「齿」判定口径（局部极值 + 相邻极值差 ≥2℃）分别计算：

| 传感器 | API 数据（577 点） | 图表渲染数据 |
|---|---|---|
| pv_temp | 34 齿 | 31 齿 |
| inverter_temp | 55 齿 | 53 齿 |
| boost_temp | 55 齿 | 57 齿 |
| transformer_temp | 52 齿 | 51 齿 |
| max_temp | 63 齿 | 59 齿 |

（微小差异来自采样窗口起止不同）⇒ **前端忠实渲染了 API 给的数据**。
### 2.3 关键对照：`max_points` 降采样有没有引入锯齿？

同一时间窗口（24h）、同一传感器（inverter_temp），只改 `max_points` 参数：

| 请求 | 返回点数 | 齿数 | 取值范围 |
|---|---|---|---|
| `max_points=0`（原始 30s 全量） | 2880 | **3** | 34..45℃ |
| `max_points=500`（前端默认） | 577 | **55** | 34..45℃ |

**看起来像降采样引入了 52 个假齿**——但逐点核对后推翻了这个结论：

- 降采样的 577 个点，**时间戳与原始点完全重合**（`all(timestamp in raw) = True`），值也完全相等；
- 即降采样只是**稀疏抽样**（avg 分桶后取代表点），没有制造新值；
- 「齿数变多」是**抽样率效应**：原始 2880 点里，一个 30 分钟的缓慢升温段有 60 个点，
  齿被「长平台」淹没；抽样到 577 点后每 2.5 分钟一个点，升温段的每个台阶都成了可见的齿。

结论：**降采样放大了视觉效果，但锯齿的物理来源是原始数据本身**。

## 三、锯齿的真实形态（原始数据，无降采样）

取 `max_points=0` 的 30s 原始序列，22:15~23:10 一个完整周期：

```
22:15:26  35      ← 平台
22:18:26  35
22:19:27  36      ← 开始爬升
22:21:27  38
22:24:27  40
22:25:57  41      ← 峰值
22:28:27  40      ← 开始回落
22:31:27  38
22:34:27  36
22:37:27  35      ← 回到平台
… 平台持续约 5 分钟 …
22:44:27  34      ← 再次触底
```

特征：

1. **周期 22~27 分钟**（峰间隔中位数 22.5 min）；
2. **幅度 3~8℃**（inverter 34→41，boost 28→38）；
3. **5 路温度高度同步**：`max_temp` 与其余 4 路的最大值**逐点完全一致（3600/3600）**，
   且存在 5 路同时跳 +1℃ 的时刻（实测 5 次全部上跳、11 次全部下跳）；
   不同物理部位（PV 板、逆变桥、升压、变压器）热惯性差异极大，**不可能同步跳变**；
4. **值域是整数**：3600 个点**没有一个小数**。而 `HTEMP` 真机帧的 7 个温度位就是整数
   （`(027 037 031 033 037 030 030 11…`），所以这是驱动的原始解析值，不是 avg 平均出来的。

## 四、机制推断（数据面，需固件/厂商侧确认）

### 4.1 已排除的解释

| 解释 | 为什么排除 |
|---|---|
| 真实散热波动 | 5 路不同热惯性部件同步跳变，物理上不成立；且夜间无功率输入（pv1_power=1W）时仍在振荡 |
| 与功率相关 | 相关性检查：夜间 pv1_power=0~1W 时温度照常振荡；白天 2261W 时反而平稳 |
| 位序解析错位 | `max_temp` 与其余 4 路最大值逐点一致（3600/3600），位序映射是对的 |
| 脏传感器（如 pv2_temp 的 30/50/100） | 那两路是**离散枚举式**跳变；这 5 路是**连续小步爬升**，形态完全不同 |

### 4.2 最可能的机制

**「HTEMP 应答与上一帧的错位复用」或「轮询周期与设备内部温度更新周期拍频」。**

支持证据：

- 周期 22~27 分钟，而 `HTEMP` 是**轮询链中的第 7 条命令**（HSTS→HGRID→HOP→HBAT→HPV→HPVB→**HTEMP**→HGEN→HBMS1），
  通道 `interval_ms=5000`、9 条命令，理论一整轮 45 秒 —— 与 22 分钟不构成整数比，**拍频可能来自设备侧**；
- 5 路同步爬升、同步回落，符合「同一条 HTEMP 应答里的 7 个温度位被整体缓存/延迟刷新」的特征；
- 幅度只有 1℃ 的台阶（456/460 次变化都是 ±1），符合设备内部温度寄存器按 1℃ 量化后**分批提交**。

### 4.3 未验证的部分（诚实标注）

- **没有抓到原始 `HTEMP` 应答帧与温度值的对应关系**：库里只存解析后的传感器值，`raw_hex` 只随最新一帧保存，
  且当前 `latest-data` 里只有 PV1 那一路（`HPV` 应答），没有 `HTEMP` 的 `raw_hex`；
- 因此「帧错位」是**基于数据特征的推断，不是直接观测**；要坐实需要：
  ① 让固件/后端把 `HTEMP` 的 `raw_hex` 也落库（或临时抓串口日志）；
  ② 对比「同一 30 秒内 HTEMP 帧内容」与「落库值」是否一致；
  ③ 若一致，则问题在设备侧（厂商协议/固件）；若不一致，则问题在本仓库的解析/入库链路。

## 五、前端本轮做了什么

结论是「数据本身如此」⇒ 前端的正确做法是**如实呈现 + 不放大噪声**，而不是伪造平滑曲线。

### 5.1 已做的（本轮）

1. **移除不可靠的 `pv2_temp` / `dc_rectifier_temp`**（上一节已述：只有 30/50/100 三档，非温度量）；
2. **温度分级修正**：原 `>40℃ 就黄色警告` 把正常工作温度（41~46℃）全涂黄，改为 `≤60 / 60~75 / >75`；
3. **图表图例错位修复**：`bottom:'auto'` + 去掉 `undefined` 键（本文件第三节已述，与本锯齿无关但同屏出现）。

### 5.2 明确**不做**的（避免用视觉掩盖数据问题）

| 方案 | 为什么不采用 |
|---|---|
| 给温度曲线加移动平均（w=5~7） | 实测能把齿数从 55 降到 37~52，但那是**把设备采集缺陷伪装成平滑曲线**，用户会以为温度真的平稳；且会掩盖真实的温度突升（安全相关） |
| 加大 `smooth` 系数 | 只改变视觉连接方式，不改变数据；且在 30 分钟短窗口下会把峰值削平 |
| 扩大 Y 轴范围 | 实测齿形仍清晰（0~60℃ 固定范围下依旧明显），无效且降低可读性 |
