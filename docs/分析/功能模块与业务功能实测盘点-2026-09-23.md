### 1.2 端点提取方法（可复跑）

注册全景的唯一权威入口是 `SetupRoutes`（`backend/internal/api/routes.go:31`），其显式调用的 `register*` 见 `routes.go:100,116-168,188-194`，另有 `main.go:449` 注入 `commandService/alertEvaluator/automationPlanner/datasourceSvc/notifyDispatcher/ControlPolicy`。本次盘点用脚本遍历 `backend/internal/api/*.go`（排除 `_test.go`）中每个 `func register*` 的函数体，按 `x := root.Group("/prefix")` 解析组前缀，再统计全部 `.GET/.POST/.PUT/.PATCH/.DELETE(` 字面量，最后把 `SetupRoutes` 调用图内的注册函数拼成完整路径。复跑命令（输出见 §9 证据）:

```bash
grep -rnE '\.(GET|POST|PUT|PATCH|DELETE)\(' backend/internal/api --include='*.go' | grep -v _test.go | wc -l   # 187（含 routes.go 的 6 条与 handler_ota.go:322 的公开下载）
grep -rnE '^\s*register[A-Za-z]+\(v1' backend/internal/api/routes.go | wc -l                                  # 24（v1 组内显式注册调用；含 registerFailoverLogRoutes）
grep -rn 'func register' backend/internal/api --include='*.go' | grep -v _test.go | wc -l                     # 29 个 register* 函数定义
```

**实测端点总数 = 178**（唯一 method+path，无重复注册）。其中 `/api/v1` 组内 175 条，公开无版本 3 条；按方法：GET 81 / POST 57 / PUT 22 / DELETE 15 / PATCH 3；按鉴权：JWT v1 组 170 / 登录限流公开 3 / query-param JWT 1 / 签名票据公开 1 / 完全公开 3。

> **算式（复核 2026-09-23 要求补出，避免 187→178 的扣减过程被误读）**：
> 上述第一条 grep 得 **187** 条注册语句，其中同时统计到**真实分支与 unavailable 分支**——
> `registerDataSourceUnavailable` / `registerFailoverLogUnavailable` 共 **10 条 503 占位**（`routes.go:160-161`；
> 当 `datasourceSvc` 不可用时注册，与 163-164 的可用分支**互斥**，同一时刻只有一套生效）；
> 再补 `main.go:457` 的 `/ping`（**1 条**，不在 `backend/internal/api` grep 范围内）。
> 即：**187 − 10（互为互斥的占位分支）+ 1（/ping）= 178**。
> 直接做 `187 − 6 − 3` 是错的口径（6/3 不是扣减项）。
> 复跑：`grep -rnE '\.(GET|POST|PUT|PATCH|DELETE)\(' backend/internal/api --include='*.go' | grep -v _test.go | wc -l` → 187；
> `grep -rn 'func register.*Unavailable' backend/internal/api/*.go | grep -v _test` 与 `backend/internal/api/routes.go:160-161` 可见占位分支。

### 4.2 生命周期主链路（实测）

1. **设备创建**：`POST /edge-devices` 事务内 `validateInheritanceTarget`→去重（`handler_edge_device.go:93` `checkDeviceUniqueness`，唯一键为 `(channel_id,type[,hardware_id])`）→建 `ConfigTemplate`→`EnsureLogicalDevice`（`handler_edge_device_lifecycle.go:88`）→回写 `logical_device_id`；事务外 `EmitConfigChange`（`handler_edge_device.go:688`）→ SyncGate 下发。
2. **删除**：软删实例 + `handleConfigTemplateOnDelete` +（可选）`purge_requested=true`；数据硬删由 `datalifecycle.Purger` 后台任务完成（`main.go:148-149`）。
3. **保留**：`RetentionTask` 每 24h，首发延迟 40s（`retention_task.go:124` 默认值），先临期通知（30/7 天，`:24-25`），再按 scope 分批硬删（`:488`），最后对 PG 分区表做整月 `DROP`（`:321`）；全局 cutoff 取所有逻辑设备中最长 `retention_days`（`:357-372`）。
4. **启动补建**：`BackfillLogicalDevices` 对 `logical_device_id IS NULL` 的 EdgeDevice（含软删）补建（`identity.go:74-99`）。

## 6. 重叠与边界模糊事实

> 本节只列事实，不给方案。

### 6.1 数据源 / 逻辑设备 / 边缘设备 / 通道 / 节点

1. **`DataSource.DeviceID` 实际指向 `LogicalDevice.ID`**，而非 EdgeDevice（`models/models.go:279` 字段注释 `// LogicalDevice.ID`）；`EdgeDeviceID` 才是实例。同表还有 `SourceType` 固定只支持 `edge_device`（`datasource/service.go:31,171-172`）。
2. **逻辑身份与物理实例一对多**：`LogicalDevice` 是一个身份锚点，`EdgeDevice` 是通过 `logical_device_id` 挂载的历史/当前实例（`models/models.go:120-126`）。但 API 取名混用：`GET /data-sources` 的 `device_id` 指逻辑身份，`GET /devices/:id/failover-logs`、`GET /devices/:id/sensor-data`、`GET /devices/:id/history` 的 `:id` 按 handler 各自注释又指 EdgeDevice 物理 id（`handler_data_source.go:62` vs `handler_data.go:64,165`；后两者实际未被消费）。
3. **通道的 `HardwareID` 与边缘设备的 `HardwareID` 语义冲突**：`Channel.HardwareID` 注释为「总线上的硬件地址 (e.g. I2C 0x76)」（`models/models.go:160`），而 `EdgeDevice.HardwareID` 是「物理设备地址 (Modbus unit id / I2C address)」（`handler_edge_device.go:126-129`）；`checkDeviceUniqueness` 只查 EdgeDevice 的 `(channel_id,type,hardware_id)`，不查 Channel 的 `HardwareID`。
4. **`Channel.BusType` 与 `HardwareType` 双列并存**，要求二者非空且大小写不敏感相等（`handler_device.go:61-68`）；`Config` 与 `BusConfig` 也是双列（`models/models.go:163,164`），`Config` 注释为「兼容旧字段」。
5. **节点同域两条并行读路径**：`GET /nodes/:id/channels`（`handler_node.go:263`）与 `GET /channels?node_id=`（`handler_device.go:637`）返回同类数据；后者有活跃前端消费，前者无。

### 6.2 设备配置模板 / 驱动 / 型号 / 固件

6. **三套「设备类型定义」并存**：`DeviceConfig`（协议无关定义 + `Operations` JSON，`models/models.go:206`）、内置驱动 Registry（`drivers/registry.go`）、`DeviceModel`+`Vendor`（`models/models.go:401,409`，仅 CRUD，前端零消费）。同一 `device_type` 字符串被三者同时使用；`EdgeDevice.Type` 注释自认 deprecated、建议用 `DeviceConfig.DeviceType`（`models/models.go:84`），但 `checkDeviceUniqueness` 等仍写 `type` 列。
7. **`ConfigTemplate` 与驱动 `CommandTemplate` 双重来源**：`ConfigTemplate`（DB 行，`models/models.go:179`）由驱动 `GetCommandTemplates()`（`drivers/command_template.go`）在建设备时生成（`handler_edge_device.go:665`），发送时还有 `sender.reconcileDriverTemplates` 自愈路径再建模板（`handler_edge_device.go:179-186` 注释）。
8. **`Parser` 的前端来源也双源**：`parserApi.getList`（`api/parser.ts:134`）同时拉 `GET /device-configs?status=active` 与 `GET /device-configs/tree` 后合并去重（`api/parser.ts:140,128,96-122`）；`GET /device-configs/:id` 的 `parserApi.getById` 无消费者。
9. **固件「URL」与「下载票据」双语义**：上传时 `Firmware.URL` 存 30 分钟 HMAC 签名票据（`handler_ota.go:193,204`），而 `storag e_path` 才是磁盘路径（`:296-315`）；前端又用自己的 token 拼 URL（`api/firmware.ts:46-50`），双方 URL 都不含后端签名的 `expires/signature`，只有前端 token 会被下载 handler 拒绝（`handler_ota.go:324`）。前端下载链接与后端票据是**两条不互通的鉴权路径**。
10. **`Firmware` 无 `deleted_at`**，DELETE 直接硬删模型 + 磁盘文件（`handler_ota.go:277-291`）；`OTATask` 保留期无清理器（对比 G6 对 `UnifiedData` 有完整清理，见 §4.1）。

### 6.3 受控操作 / 通道终端 / 直控

11. **受控操作与通道终端共享物理写路径但门禁不同**：受控操作走 `ChannelCmdV2` + confirmation + Channel 行锁（`commandexec/dispatcher.go:114-133`）；通道终端 REST 写入直接 `nodeMgr.SendWriteCommand`（`handler_terminal.go:68`），仅统一受 `RawDiagnosticsEnabled` 总开关（默认关，`control_policy.go:9-18`）约束。两者都写物理总线，但审计/幂等能力不对等。
12. **GPIO/PWM 的「CRUD 配置表」与「PeriphCmd 直控」分离**：`GPIOConfig`/`PWMConfig` 行经 REST CRUD 落到资源定义；实际电平变更走独立帧类型 0x1B/0x1C（`frame/frame.go:75-76`），不经 Channel 行（`commandexec/dispatcher.go:113-116` 明确 periph_cmd `channel_id=0` 跳过 channel 锁），却仍在 `CommandExecution` 统一审计。
13. **终端有两个不完全等价的入口**：`GET /channels/:id/terminal`（REST 历史，`handler_terminal.go:32`）与 `GET /api/v1/ws/terminal`（WS 订阅含历史回放，`routes.go:194`、`terminal/ws_handler.go:193-222`）。前端只消费前者对应的 REST 写入和全局 WS 的 `channel_data`，终端 WS 零连接（§5.2）。

### 6.4 数据管线

14. **`UnifiedData` 与 `DeviceData` 双写**：`databus/SensorParserConsumer.Handle` 成功解析后同时写两张表（`consumers_heavy.go:91` 附近写 UnifiedData、`:434` 写 DeviceData），保留期/分区卸载由同一 `RetentionTask` 对两表统一处理（`retention_task.go:323`）。
15. **`GET /nodes/:id/latest` 与 `GET /edge-devices/:id/latest-data` 双实现**：前者直接 SQL 关联 `unified_data`+`edge_devices`（`handler_data.go:136-150`），后者走 API 内 latest 缓存（`handler_edge_device.go:1143`）；两者前端分别有死包装 (`dataApi.getNodeDevicesData`) 与活包装 (`edgeDeviceApi.getLatestData`)。
16. **告警/自动化求值挂点相同但保留策略不同**：两者都挂 `SensorParserConsumer` 的解析后回调（`nodemgr/manager.go:261,266`），AlertEvent 无清理器而 AutomationEvent 有 30/400 天分层清理（§4.1）。

### 6.5 前端信息架构

17. **主导航实为 14 项，文档 FR-N1 称 9 项**：`MainLayout.vue:397-412` 14 个菜单路径，`router/index.ts` 23 个 named route、26 个 path 字面量（含 redirect/兜底/dev）。其中 `profile` 为 `hiddenInMenu` 但可从用户菜单到达（§5.3 第 6 条）。
18. **`NodeDetail.vue`/`NodeOverview.vue` 双页骨架，路由只保留一个**：两文件都实现「节点详情 + 总线配置 + 日志 + 终端 + OTA」，路由两条都指向 `NodeOverview.vue`（`router/index.ts:49,55`），`NodeDetail.vue` 成为同主题的不可达副本；`components/node/ChannelPanel.vue` 的代码注释（`:5-16`）已自认此事实。
19. **`Configuration` 视图消费三源**：`DeviceConfigList.vue` 同时消费 `deviceConfigApi`、`parserApi`（经 `stores/parser.ts`）与 `driver.ts` 的 `getDriverTree`，三者的数据源在 §6.2 第 6-8 条已重叠。

## 8. 不确定性与方法边界

1. **端点总数对「注册函数是否在生产调用图内」的判定基于 `routes.go` 静态读**：`registerDataSourceUnavailable`/`registerFailoverLogUnavailable`（`routes.go:160-161`）与真实分支（`:163-164`）互斥，生产 `main.go:301,449` 注入了 `datasourceSvc`，故按真实分支计入 9+1 条；若测试环境未注入，则同一路径返回 503（路径集合不变，端点数不变）。
2. **`registerLogStreamRoutes`（`handler_node.go:665`）与 `registerEdgeDeviceCandidateRoutes`（`handler_edge_device.go:417`）由父注册函数内嵌调用**，不是 `routes.go` 顶层调用；已计入。
3. **「消费」按静态调用图可达性判定**：`router/index.ts` 的 `import.meta.env.DEV` 分支在开发模式可达（`/dev/mock-bms`、`/dev/bms-demo`）；标记为「生产不可达/开发直连」。生产构建会静态消除。
4. **`NodeOverview.vue` 中的 `<ChannelManager>`/`<LogPanel>`/`<ChannelTerminal>` 通过 template 使用**，脚本 import 可见（`:812-814`），计为可达；若 Vue 编译器对某模板分支做了 dead-branch 消除，计数会偏乐观（未观察到相关构建产物的证据）。
5. **`utils/constants.ts`/`downsample.ts`/`validate.ts`** 用 `grep -rn` 在生产 `.ts/.vue` 零命中，但 `downsample` 在测试中被 mock；不排除它们被测试间接受益但在生产确为死代码。
6. **`GET /api/v1/firmwares/:filename/download` 计入「手动 URL 消费」**：`firmwareApi.getDownloadUrl`（`api/firmware.ts:46`）被 `FirmwareManage.vue:314,338` 调用并拼出该 URL，但用的是前端 token 参数而非后端签名票据；按「代码里确有构造与使用该 URL 的路径」计入消费，但请求是否 401 存疑（未实际发请求验证，任务禁止网络请求）。
7. **指标族计数只数 `promauto.New` 调用点（46）**，未去重 label/向量维度；「族」口径可能使实际注册 Series 数不同，但满足「15+」判定。
8. **模型 46 个 struct 数**为 `grep '^type ... struct'` 统计，未排除内嵌结构用途；生命周期表的「归档/删除」列中未找到清理器的表（OTATask、AlertEvent、DataSourceHealth、FailoverLog、MergeJob、BackfillJob）只能说明「截至本 commit 无清理代码」，不能断言未来不会由数据库运维删除。
