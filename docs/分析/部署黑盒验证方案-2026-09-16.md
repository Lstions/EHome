# 部署黑盒验证方案（Black-Box Deployment Verification）

> 制定时间：2026-09-16 | 制定人：主控 | 状态：待执行
> 目标：**用真实容器部署**验证系统，而非只用本地二进制/单测——补上当前唯一缺失的验证层。

---

## 1. 为什么需要这一层（先说清缺口，再说做法）

### 1.1 现状：验证层有 5 层，唯独缺「真容器」

| 层 | 手段 | 被测对象 | 覆盖 |
|---|---|---|---|
| L1 单测 | `go test ./...` | 函数/包（内存 SQLite 或隔离 schema PG） | ✅ |
| L2 集成 | `EHOME_TEST_DB=postgres` | 真实 PG（隔离 schema） | ✅ |
| L3 仿真 | `-tags=simulation`（138 场景） | **本地二进制** + 真实 PG/EMQX + 真 MQTT/HTTP | ✅ |
| L4 浏览器 e2e | Playwright（23×2） | 真浏览器 + **本地** 8082 | ✅ |
| **L5 真容器部署** | **docker compose / 镜像** | **Dockerfile + compose + 镜像内的产物** | ❌ **缺失** |

**已实测确认的缺口**：
```bash
grep -nE 'docker (build|compose|run)' Makefile          # 无 docker build/run
grep -rn 'docker build' --include=*.go --include=*.sh .  # 无
# 仿真 harness 启的是本地二进制：
sed -n '914p' backend/simulation/harness/env.go
#   exec.CommandContext(ctx, goTool(), "build", "-buildvcs=false", "-o", out, "./cmd/server")
```
⇒ **L1–L4 全都绕过了 Dockerfile 与 compose**。这意味着：Dockerfile 写错、compose env 漏配、
镜像内静态资源缺失、多阶段构建产物不对——**现有 5 层验证一个都抓不到**。

### 1.2 已被证实的风险（不是假设）

本轮已实测：`docker build` **成功**（90.4MB 镜像，`EXIT=0`），镜像内 `/app` 只有
`ehome-server` + `static/` + `firmwares/`，**无 `.env` 泄漏**。
但这是**人工冒烟**，不是**可重复的门禁**——下次改 Dockerfile 没人会重跑。

### 1.3 本方案要回答的问题（黑盒视角）

真容器部署后才成立、本地二进制验证**天然覆盖不到**的命题：

| # | 命题 | 为什么本地验证覆盖不到 |
|---|---|---|
| Q1 | 镜像能构建且**产物完整**（含 SPA 静态资源） | 本地跑的是 `go build` + 已有 `dist`，不经过多阶段构建 |
| Q2 | compose 的 **env 契约**正确（必填项缺失时明确报错） | 本地用 `.env`/环境变量直连，不走 compose 的 `${VAR:?err}` 校验 |
| Q3 | 容器**冷启动**全序列成功（AutoMigrate / 退役 DDL / 初始化凭据） | 仿真 harness 虽启二进制，但**不验证容器 entrypoint 与挂载** |
| Q4 | 容器内**健康探针**可达（`/health` / `/metrics`） | 本地 8082 是手工起的，探针语义未被部署视角验证 |
| Q5 | 首次部署的**一次性凭据**流程（未初始化 → 设置 → 登录） | SIM-DEP-001..004 已覆盖逻辑，但**未在容器内**验证 |
| Q6 | **跨容器**连通性（web→PG、web→EMQX 用服务名） | 本地用 `127.0.0.1`，容器内必须用 compose 服务名 |
| Q7 | 镜像**可重复构建**（同 commit 两次构建行为一致） | 无此验证 |

## 2. 关键约束（不可违反）

| 约束 | 说明 |
|---|---|
| **不碰现有服务** | `:3080`(DSH GUI)、`:8082`(审计后端)、`nginx`(80 已占用)、共享 `ehome-postgres`/`ehome-emqx` 全部保持不动 |
| **不碰共享数据** | **禁止**对 `ehome` / `ehome_test` / `ehome_uiux` 库做任何写操作；黑盒验证一律用**独立库** |
| **端口隔离** | 黑盒栈使用 `HOME_PORT=18080`（避开 80/3080/8082） |
| **容器隔离** | 用独立 compose project 名（`-p ehome-bb`），容器名 `ehome-bb-*`，**不与 `ehome-web` 冲突** |
| **可清理** | 验证结束必须 `-p ehome-bb down -v`，且核对无残留容器/卷/网络 |
| **PG/EMQX 复用** | 复用现有 `ehome-postgres`/`ehome-emqx` 容器，**不新起**（省资源、避免端口冲突）——通过 compose override 指向外部网络 |

## 3. 执行设计

### 3.1 目录与产物

```
deploy/blackbox/
├── README.md              # 怎么跑、怎么读结果
├── compose.bb.yml         # 独立 project 的 compose（复用外部 PG/EMQX）
├── run.sh                 # 编排：构建→起栈→探针→黑盒断言→清理
├── probes/
│   ├── 01-image-contract.sh    # Q1 镜像产物完整性
│   ├── 02-env-contract.sh      # Q2 compose 必填 env 校验
│   ├── 03-coldstart.sh         # Q3 冷启动全序列 + 日志断言
│   ├── 04-health.sh            # Q4 探针可达
│   ├── 05-first-boot.sh        # Q5 一次性凭据全流程
│   ├── 06-wiring.sh            # Q6 跨容器连通（服务名）
│   └── 07-reproducible.sh      # Q7 可重复构建
└── evidence/              # 每次运行的证据（时间戳目录）
```

### 3.2 黑盒纪律（与 §5 一致，不可放松）

1. **只经公开接口**：HTTP / MQTT / docker inspect / 日志——**不读容器内私有文件**、不直连其 DB 改数据
2. **断言可证伪**：每条断言必须能在「故意破坏」时变红（每条都要有变异自证）
3. **分母守卫**：脚本必须断言「真的扫到了东西」（如镜像内文件数 ≥ N、探针 ≥ N 条）
4. **失败要能诊断**：断言失败时打印原始响应/日志片段，不是只说「失败」
5. **证据留痕**：每步输出写入 `evidence/<run_id>/`，含时间戳与可复现命令
6. **如实声明边界**：写明「本方案不覆盖什么」（见 §6）

### 3.3 复用而非重造

| 已有资产 | 复用方式 |
|---|---|
| `docker-compose.yml` | 用 `-f` 叠加 override，不修改原文件 |
| `backend/simulation/catalog/dep.go`（SIM-DEP-001..006） | Q5 断言逻辑对齐其不变量，但**在容器上重做**（黑盒） |
| `frontend-shared/e2e/` Playwright | Q4/Q5 可用其 helper 打真浏览器（若成本可控） |
| `scripts/check_e2e.py` 等 | 参考其断言风格 |

## 4. 子代理分工（4 个，可并行）

> 分配原则：**按「独立可验证的产物」切分**，避免多人改同一文件。
> 每个子代理必须：先跑通自己的命令 → 出证据 → 变异自证 → 如实报告未做项。

### 子代理 A：镜像与构建契约（Q1 + Q7）

**产出**：`probes/01-image-contract.sh`、`probes/07-reproducible.sh`、`evidence/A-*/`

**任务**：
1. 构建镜像，断言：镜像存在、体积在合理区间（参考实测 90.4MB）、`/app/ehome-server` 可执行、
   `/app/static/dist/index.html` **存在**（SPA 入口）、`/app/firmwares` 存在
2. 断言镜像内**无 `.env` / 无密钥**（`docker run --entrypoint sh ... find / -name '.env*'`）
3. **静态资源完整性**：断言 `dist/index.html` 引用的 assets 在镜像内**均存在**（不是只看目录在）
4. Q7：同一 commit 连续构建两次，断言关键产物（index.html 引用的文件名集合）一致；
   若不一致⇒说明构建不确定，**如实报告**而非放宽断言
5. **变异自证**：故意破坏 Dockerfile（如删掉 `COPY --from=frontend-builder`）⇒ 断言必红

**边界**：不做网络连通性、不氧化到运行时行为。

### 子代理 B：compose 与冷启动契约（Q2 + Q3 + Q6）

**产出**：`compose.bb.yml`、`probes/02-env-contract.sh`、`probes/03-coldstart.sh`、`probes/06-wiring.sh`、`evidence/B-*/`

**任务**：
1. 写 `deploy/blackbox/compose.bb.yml`：project 名 `ehome-bb`，`HOME_PORT=18080`，
   复用外部 `ehome-postgres`/`ehome-emqx`（external network 或 host 网络声明，**实测哪种可行**）
2. Q2：断言**必填 env 缺失时 compose 明确报错**（`EHOME_EXTERNAL_HOST` / `EHOME_JWT_SECRET`）；
   提供时不报错。这是 compose 契约的黑盒验证
3. Q3：冷启动全序列 —— 断言容器 `Up`、日志出现 AutoMigrate 完成、
   **不是** `CrashLoopBackOff`；用**独立库**（`ehome_bb_<runid>`）避免碰共享库
4. Q6：断言 web 容器能解析 `postgres`/`emqx` 服务名并连通（如通过容器内探针或日志中的成功连接）
5. **变异自证**：把 `EHOME_DB_HOST` 改成不存在的名字 ⇒ 启动必须失败（而非静默起个空壳）

**边界**：不改 Dockerfile（属 A）、不做业务断言（属 C/D）。

### 子代理 C：部署后的功能黑盒（Q4 + 本会话已修缺陷的容器复验）

**产出**：`probes/04-health.sh`、`probes/05-first-boot.sh`、`evidence/C-*/`

**任务**：
1. Q4：断言 `/health`（或等价）与 `/metrics` **未鉴权可达**（对齐 SIM-DEP-005 的不变量）
2. Q5：**一次性凭据全流程**（黑盒）：
   - 起全新库的栈 → 读容器日志取一次性凭据 → `POST /auth/initialize` 建管理员 → 登录成功
   - 断言：错误凭据被拒、重复初始化被拒、**凭据不可重放**（对齐 SIM-DEP-001..004）
   - **凭据是秘密，不写入证据文件**（只记「出现过」与长度特征）
3. **本会话修复的容器级复验**（关键——这是黑盒层对修复的独立确认）：
   - `latest_data` 在**冷启动**（无 warmup）下形状正确（多物理量，非只 1 个）
   - `reconfigure` 端点：**真的改 bus_config**（活服务已验，容器内复验）
   - 告警规则 `enabled:false` **落库为 false**
4. **变异自证**：至少 1 条（如把健康检查断言改成要求鉴权，应红）

**边界**：不做镜像构建（属 A）、不做 compose env 契约（属 B）。

### 子代理 D：编排、清理与总报告

**产出**：`run.sh`、`README.md`、`evidence/D-*/`、最终报告

**任务**：
1. 写 `run.sh` 编排 A/B/C 的探针（按依赖顺序），支持 `--only <probe>`
2. **清理是硬要求**：`trap` 保证异常也执行 `-p ehome-bb down -v`；
   结束后核对**零残留**（容器/卷/网络/独立库）
3. 汇总报告：每条命题的 结论 + 证据路径 + 复现命令 + **未覆盖项**
4. 与主控一起做**端到端演练**：干净环境跑一次完整 `run.sh`

**边界**：D 不写断言逻辑，只编排与如实汇总。

## 5. 验收标准（主控亲自核）

| # | 标准 | 判据 |
|---|---|---|
| 1 | `run.sh` 从零可跑通 | 干净环境下一条命令，退出码 0 |
| 2 | 每条命题都有**独立证据** | `evidence/` 下有对应输出，非「据说」 |
| 3 | 每条断言都有**变异自证** | 破坏后必红，且报出可诊断信息 |
| 4 | **零残留** | `docker ps -a`/`volume ls`/`network ls` 无 `ehome-bb` 痕迹；独立库已 DROP |
| 5 | **共享资源未被触碰** | `:3080`/`:8082` 仍健康；`ehome`/`ehome_test`/`ehome_uiux` 行数/Schema 未变 |
| 6 | 报告**如实** | 明确写出未做的、不确定的、与预期不符的 |

---

## 6. 本方案**不覆盖**什么（诚实声明）

- **不做真实 ESP32 硬件验证**（需实机，见 `docs/操作/ESP32刷机指南.md`）
- **不做生产环境验证**（本方案在开发机上用独立 project；生产域名/证书/反代不在范围）
- **不做压力/容量测试**（`scripts/bench` 是另一条线）
- **不做镜像安全扫描**（CVE/漏洞扫描需额外工具，本方案只查「无密钥泄漏」）
- **不覆盖 `nginx` 反代路径**（80 端口被占用，本方案不经 nginx）

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 复用外部 PG/EMQX 时网络配置不可行 | 子代理 B **先实测**，不可行则退化为「起独立 PG/EMQX 容器」（端口 15432/11883），并如实记录 |
| 独立库残留 | 清理脚本显式 `DROP DATABASE IF EXISTS ehome_bb_*`，并纳入验收标准 4 |
| 构建耗时（首次 ~2min） | 探针允许复用已构建镜像（`--skip-build`），但**至少跑一次全量构建** |
| 子代理并行改同一文件 | 已按产物切分：A 只碰 `probes/01,07`，B 只碰 `probes/02,03,06`+compose，C 只碰 `probes/04,05`，D 只碰 `run.sh/README` |
