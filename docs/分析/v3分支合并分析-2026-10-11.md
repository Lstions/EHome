## 六、方案选项

### 方案 A（推荐）：先推分支让 CI 说话，再 ff-only 合并

```
1. 删 main 工作树的 psBig.txt / psS.txt
2. git push origin feat/v3-refactor        # 让 CI 先跑这 3 个提交
3. 等 CI 六个 job 结果（重点：backend-scenarios 的 EMQX 依赖）
4. 绿了 → git checkout main && git merge --ff-only feat/v3-refactor
5. git push origin main
```

理由：零冲突风险已数学确认；唯一不确定性是 CI 从未在此分支跑过。
**推分支让 CI 先说话**比直接合 main 安全。

### 方案 B（保守）：`--no-ff` 留合并点

`git merge --no-ff` 保留一个合并提交，便于整体 `git revert -m 1`。
代价：历史多一个空合并节点。若担心 MQTT 移除需一键回退，选此。

### 方案 C（不推荐）：直接 `git push origin feat/v3-refactor:main`

绕过本地校验，丢失本地可回退性。

### CI EMQX 处置要点（实测依据）

移除前先测出两件事，都推翻了「CI 是绿的」这一默认假设：

1. **该 job 从来就是红的**：
   `--- FAIL: TestScenarios (31.71s)` / `等待服务端 MQTT 就绪失败: …服务端尚未消费 MQTT 上行`。
   后端 2026-10-08 移除 MQTT 后，harness 的探针链路就不存在了。
2. **它有连带伤害**：`TestMain` 的 `Preflight` 要求 MQTT 可连，
   实测 MQTT 指向死端口时，连不碰 MQTT 的 `TestCatalogGate`（纯结构门禁）也被一并 FAIL。

处置：删 EMQX 容器 + 1883 轮询 + `MQTT_BROKER`；`Preflight` 去掉 MQTT 要求；
`TestScenarios` 改为**显式 Skip**（并写明恢复路径）。本地复现新 job 命令：**ok 1.0s**。

### ⚠ 生产路径有意保留（实测依据）

生产当前镜像 tag = `sha-56516fd`，该 commit 在 main 上，且仍含
`backend/internal/mqtt/`、`main.go:201` 仍 `mqtt.New(...)`、不含 `internal/transport/`。
