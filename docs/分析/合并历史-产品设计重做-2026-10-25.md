# 合并历史：产品设计重做（2026-10-25）

> **状态**：设计已定稿并实施中
> **触发**：产品负责人实测截图指出「目标 #14 bms，源候选却是 #15 逆变器 / #16 光学雨量计」——
> 合并历史的**功能设计根本错误**，要求「从头分析产品功能设计」。
> **结论**：此前把「换节点后历史不丢」的收尾问题，错误地做成了**任意两条设备记录之间的
> 数据搬运工具**。本文件重新定义三条路径的职责、合并功能的准入条件与交互，并给出
> 可证伪的验收判据。

---

## 一、错误复盘（为什么会做出截图里那个东西）

| # | 错误 | 后果 |
|---|---|---|
| E-1 | **合并没有设备型号约束** | 目标 bms 可以合并逆变器/雨量计的历史。不同型号的 `type` 对应不同驱动、不同传感器字段集合与单位；合并后 `unified_data.sensor_name` 会把 A 型号的物理量挂到 B 型号名下，`sensor_field_obs` 台账、历史图表、告警/自动化按字段名取值全部被污染。**这是数据语义错误，不是体验问题。** |
| E-2 | **源候选选自"当前页存活设备"** | 真正要清理的「旧记录」是**已删除设备**，却不在列表里；列表里全是在役的不同型号设备（截图证据）。信息架构完全反了：合并是「历史设备 → 当前设备」的收尾，不是「当前设备 → 当前设备」。 |
| E-3 | 为掩盖 E-2 的存活源空壳问题，引入了 `allow_live_source` + 自动退役 + 孤儿 id 救援 | 把简单问题做复杂：在役设备根本不该出现在合并里；无设备行的孤儿无法验证型号，与「必须同型号」冲突。 |
| E-4 | 缺少「同型号」的领域概念与门禁 | 类型校验只在前端向导里按解析器筛选过（创建设备时），合并路径从未继承该不变量。 |

**根因**：需求原文是「同一物理设备换节点后历史不丢」。它的主解是 **①原地换节点** 与
**②恢复已删除设备**；**③合并历史只是第②条走不通时的收尾**（旧记录已删、不想恢复）。
此前把第③条当成了通用数据搬运能力，才长出跨型号、选现役设备这些错误设计。

---

## 二、需求再确认

1. 同一台物理设备换节点/插口后，历史数据不丢、连续可查（主需求）。
2. **合并历史要求「同一种设备」**（产品负责人明确裁决）。
3. 合并的源必须是**历史设备**（已删除的旧记录），界面必须把它们列出来。

## 三、三条路径的职责（重新划定）

| # | 场景 | 设备行状态 | 路径 | 数据是否移动 |
|---|---|---|---|---|
| ① | 同一台物理设备换节点/通道 | 存活（同一条行） | **PUT 原地换节点**（主路径） | 否（id 不变，历史天然连续） |
| ② | 设备行被删除，物理设备还要继续用 | 软删（同一条行） | **恢复已删除设备**（改绑节点/通道） | 否（id 不变） |
| ③ | 旧设备行已删除且不想/不能恢复，只想要回历史 | 旧行**软删**、新行存活 | **合并历史**（收尾工具） | 是（四张表改挂） |

**路径③的准入边界（本次重做的核心）**：

- 目标：必须**存活**。
- 源：必须是 `edge_devices` 行存在、**已软删**、且 `type` **与目标完全相同**的设备。
- 源在役 → **不允许**合并（不是"确认后允许"）：在役设备的历史被搬走会变成空壳，之后新数据
  仍归它自己，历史永久分裂。要收尾就先把旧设备删除（数据保留）再合并；只是换位置就用路径①。
- 源无设备行（历史遗留孤儿 id）→ **不允许**合并：无法验证型号，「同型号」不变量不可证。
  这类数据只受系统级保留期约束（是否做专项救援另行立项，不在本功能内）。
- 源被 purge 认领（后台正在硬删数据）→ 409，等清理结束（或赶在认领前用恢复撤回）。
- 源=目标（不可能，目标存活）、重复 id、>100 个 → 400。

**不允许的设计（明确删除）**：

- ❌ 跨型号合并（任何形式提示/确认后放行都不行）。
- ❌ 在役设备作为源；`allow_live_source` 参数与"自动停用退役"整段删除。
- ❌ 无设备行的孤儿 id 救援。
- ❌ 合并前"自动把源设备软删"。

## 四、数据语义（同型号约束下的搬运规则）

同 `type` ⇒ 同一驱动 ⇒ 同一 `sensor_name` 集合与单位语义，四张表可以安全改挂：

1. `unified_data` / `device_data`：`device_id` 改挂（分批、幂等）。
2. `sensor_field_obs`：按字段名合并统计量（first=MIN、last=MAX、samples=SUM），按源逐个处理
   避免多源同名撞复合主键。
3. `data_sources`：组键 `(edge_device_id, category)` 改挂；冲突的 `managed_by=manual` 行
   保留在源设备上并返回 warning（人工配置永不静默删除）。
4. 合并后回写目标 `last_data_at`；台账失败降级 warning（时序数据已迁移且幂等，可重试）。

## 五、交互设计（重做）

### 5.1 入口

- 设备列表行/卡片「合并历史」（目标 = 当前在役设备）。

### 5.2 弹窗流程

    ┌ 合并历史 ─────────────────────────────────────────────────────┐
    │ 说明：把「同型号」的已删除设备的历史并入当前设备。              │
    │       不同类型的设备数据字段/单位不同，不能合并。               │
    │                                                               │
    │ 目标设备： [#14 bms]（只读，显示型号中文名）                    │
    │ 源设备（历史设备）：                                            │
    │   [ 多选，仅列同型号、已删除、且还有数据的设备 ]                │
    │     · #12 bms-旧    · 约 123,000 行 · 最后数据 10-02 08:00      │
    │     · #09 bms-更早  · 约 2,431 行   · 最后数据 09-18 21:30      │
    │   （也可手输同型号已删除设备 ID，防分页遗漏）                   │
    │                                                               │
    │ 数据量：目标现有 3,512 行；预计迁移 125,431 行（仅源合计）      │
    │ [明细表：源 / #id 名称 / 行数 / 最早 / 最新]                    │
    │                                                               │
    │ 空态：没有可合并的同型号历史设备。                              │
    │   · 旧设备记录还活着 → 请用「编辑」换节点（历史天然连续）       │
    │   · 旧设备已删除     → 可在「恢复已删除设备」中找回             │
    └───────────────────────────────────────────────────────────────┘

### 5.3 关键交互

- 源列表**只来自** `GET /edge-devices/deleted?device_type=<目标 type>`（服务端过滤，分页/上限内
  全量展示），并过滤掉行数估算为 0 的记录（已合并过/无数据，展示它们只会让用户白点）。
- 手输 ID 允许（超 200 台时），但**提交前**用 data-summary 拿 `device_type` 校验：不一致直接
  红字阻断并说明原因，不发请求。
- 选中源后展示类型徽标与名称；**不出现**"使用中设备"分组、风险勾选、"停用源设备"等概念。
- **同型号 ≠ 同一台**：型号只是必要条件。界面展示每条历史设备的名称/#id/最后数据时间，
  由用户确认它就是当前设备的前身；不做自动物理身份推断（地址/节点都可能因换位置而变，
  用它们判身份会产生误判）。文案明确提示「请确认这些记录是这台设备的前身」。
- 提交按钮：危险操作样式 + 二次确认语义（文案"合并后源设备侧不再有这些行"）。
- 结果：迁移行数；warnings（人工数据源冲突等）原样展示；不再有"已停用设备"提示。
- 错误文案示例：跨型号 → 「源设备 #15 是 逆变器（inverter_techfine），与目标设备 #14 的型号
  bms（jiabaida_bms）不一致，只能合并同型号设备」；在役 → 「源设备 #x 仍在役…」。

## 六、API 变更（相对 2026-10-25 上午版本）

| 端点 | 变更 |
|---|---|
| `POST /edge-devices/:id/merge-history` | 请求体删 `allow_live_source`；源校验改为「存在 + 已软删 + 同 type + 未 purge 认领」；响应删 `retired_sources`，`sources[].state` 只可能是 `deleted`、`sources[].device_type` 返回源型号；其余（分批/幂等/台账/warnings/last_data_at）不变 |
| `GET /edge-devices/:id/data-summary` | 每个 item 增加 `device_type`（target 与 sources 都有），供前端同型号校验/展示 |
| `GET /edge-devices/deleted` | 新增可选筛选 `device_type`（精确匹配），供合并弹窗服务端过滤 |

## 七、非目标 / 暂不做

- 无设备行的孤儿历史数据救援（另行立项：需要独立的数据归属审计工具）。
- 合并后台任务化/进度接口（当前同步长请求：可取消、分批幂等、可重试）。
- 跨型号「字段级映射合并」（明确不做：语义无法保证）。
- 从「恢复已删除设备」弹窗一键转「合并到同型号在役设备」（后续体验优化，接口已具备）。

## 八、验收判据（可失败）

### 8.1 后端（真实 HTTP + DB 前后状态）

1. 跨型号：目标 bms + 源（已删逆变器）→ **400**，错误信息含双方类型；四表**一行不动**。
2. 在役同型号源 → **409**（即使旧客户端传 `allow_live_source: true` 也一样）。
3. 无设备行孤儿（有数据）→ **400**。
4. 同型号已删源 → 200：四表迁移、幂等重放 0 行、目标 last_data_at 回写、manual 冲突保留+warning。
5. purge 认领源 → 409；仅 `data_purge_requested=true` → 撤回后 200。
6. data-summary 返回 `device_type`；deleted 列表 `device_type` 过滤生效。
7. 换节点/恢复路径的既有门禁不回归。

### 8.2 前端

1. 打开合并弹窗只看到「与目标同型号的已删除设备」；不同型号设备**不出现**。
2. 手输不同型号 ID → 阻断并给出类型说明，不发提交请求。
3. 无同型号历史设备 → 空态文案（含三条路径引导），不显示现役设备。
4. 不再出现 allow_live_source / 风险勾选 / "停用源设备"文案；结果无 retired 提示。
5. 门禁：`pnpm test:run` / `pnpm typecheck` / `pnpm build` 全绿。
