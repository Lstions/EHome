## 1. 我错在哪（实测证据）

### 1.1 PG 已经在压缩 `device_data`

```sql
SELECT pg_size_pretty(sum(octet_length(data_json))),   -- 原始字节
       pg_size_pretty(sum(pg_column_size(data_json))), -- 实际存储
FROM device_data GROUP BY (data_json LIKE '%"sensors"%');
```

| 类型 | 行数 | 原始 | 实际存储 | 压缩比 |
|---|---:|---:|---:|---:|
| A（带 sensors） | 3,462,696 | 5,514 MB | **1,981 MB** | **2.78x** |
| B（仅 raw） | 4,037,700 | 871 MB | 885 MB | 0.98x（低于 TOAST 2 KB 阈值，不压） |

逐行样本：`raw=2215 B → stored=638 B (3.47x)`、`raw=465 B → stored=469 B (0.99x)`。

**所以 `device_data` 的 4.4 GB 是压缩后的体积，不是 5.5 GB 原始体积。**

### 1.2 9.2x 是怎么来的（两个错误叠加）

| 错误 | 事实 |
|---|---|
| 拿**批量**压缩比当单行比 | 实测 1 行 4.5x、20 行 9.9x、50 行 11x。单行中位数 **4.5x** |
| 拿**原始 JSON 字节**当磁盘占用 | PG 已压过，正确基线是 1,981 MB 而不是 5,514 MB |

⇒ 应用层 gzip 的真实边际只有 **210 MB**；deflate+预设字典能到 870 MB，但要永久冻结字典 + 版本前缀共存。

## 2. 更好的做法：剥离而非压缩

实测（2,000 行真实样本，`jsonb - 'sensors'`）：

```
现在存储       1,278 kB
剥离 sensors     468 kB     (2.73x)
```

| 方案 | 一次性释放 | 新增永久复杂性 |
|---|---:|---|
| GZ1（base64+gzip） | 210 MB | 格式前缀 |
| ZD1（deflate+预设字典） | 870 MB | **冻结字典 + 版本前缀共存** |
| **剥离 sensors** | **1,255 MB** | **零** |

**理由不只是更省**：`sensors` 与 `unified_data`/`telemetry_frame` 是同一份物理量的副本。
压缩 = 给不该存在的副本减肥；剥离 = 切除副本。剂量相同，方向相反。

## 4. 与用户需求的对齐

用户要求「**所有数据要长期保留**」。需要澄清「数据」指什么：

| 内容 | 在哪 | 保留多久 |
|---|---|---|
| **物理量**（电压/电流/温度/电量…） | `telemetry_frame` | **永久**（无损，已验证 142,467 帧 0 缺失 0 超差） |
| 原始总线帧（寄存器原文） | `device_data` | 90 天（超期后仍可从帧表还原物理量） |
| 帧元数据（channel/error_code） | `device_data` | 90 天 |

⇒ 「长期保留」在**物理量层面完全成立**；原始总线字节是排障素材，滚动 90 天是工程上合理的。
