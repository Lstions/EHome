# 本机生产同构服务联调验证报告（ESP32-S3 + BMS）

- 日期：2026-10-16
- 范围：本机部署生产同构服务 → 热点接入 ESP32-S3 → mTLS 上线 → 通道/边缘设备配置下发 → BMS 数据上行 → 前端托管 → 受控操作（含风险二次确认）
- 结论：**端到端链路打通并实测通过**；过程中发现并修复 1 个模拟器协议缺陷，定位 1 个残余间歇失败根因。

## 1. 部署形态

| 组件 | 实现 | 端口/地址 |
|---|---|---|
| PostgreSQL | docker `ehome-postgres`（postgres:18-alpine） | 127.0.0.1:5432 |
| EHome 后端 | systemd --user `ehome-backend.service`（Restart=always） | API :18090，mTLS 设备链路 :8443 |
| 前端 | 后端托管 `frontend-shared/dist`（`EHOME_STATIC_DIR`，SPA 回退 + /assets immutable） | http://10.42.0.1:18090 |
| BMS 模拟器 | systemd --user `ehome-simulator.service` | /dev/ttyUSB0 (CH340) 9600 8N1 |

设备接入：本机 Wi-Fi 热点 `Hotspot-1`（10.42.0.1/24，**channel 6**）。

## 2. 实测证据链

1. **设备上线**：`node_id=ACA704222198`（= 设备证书 CN）`status=online`，`fw=2.8.0`，`proto=2.6`，`wifi_rssi=-24`，`heap=125492`。
2. **配置下发**：建 UART0 通道（`bus_config=2B2C0000258000` = TX43/RX44/9600/无DMA）+ `jiabaida_bms` 边缘设备；设备回 `ConfigResult success=true`，`config_status=applied`、`sync_state` 收敛。
3. **数据上行**：模拟器收到并应答 `0x03` 轮询；后端 `DataReport err=0` → `Parsed 14 sensors using Driver(jiabaida_bms)`。
   最新值：`voltage=51.2V current=3.5A soc=78% fet_status=0x03`。
   累计：`unified_data` 35910 行 / `device_data` 8650 行。
4. **前端**：`GET /` 200（index.html）、`/assets/*.js` 200（20617B）、深链 `/automation` 200（SPA 回退）。
5. **受控操作（普通）**：`read_basic_info`（risk=normal）→ `status=SUCCEEDED final_reason=final_succeeded`。
6. **受控操作（风险）**：
   - 直接下发 → `409 valid confirmation is required`（确认门生效）；
   - `POST /edge-devices/1/actions/set_mos_policy/confirm` 取得一次性凭据；
   - 带凭据 + reason 下发 → `202 queued` → 设备收到 `0xE1` 写帧并读回对账 → **SUCCEEDED**。

## 3. 风险两级模型实测

26 个动作全部返回 `risk_level` + `requires_confirmation`，与驱动方言一致：

- `normal` / `requires_confirmation=false`：`read_basic_info`、`read_cell_voltage`、`read_test_mos_status`、`find_car` 等
- `elevated` / `requires_confirmation=true`：`set_mos_policy`、`test_charge_mos`、`test_discharge_mos`、`bms_restart`、`write_sn`、`force_balance`、`write_protection_parameters` 等

## 4. 发现与修复

### 4.1 模拟器 `fet_status` 极性反转（已修复）

**现象**：`set_mos_policy(readback)` 恒 `FAILED`：
`readback mismatch: fet_status=0x00 charge bit=0 want 1 discharge bit=0 want 1`

**根因**：E1 写字节与 `fet_status` **极性相反**（依据 `jiabaida_control.go:710`）：

| | 语义 |
|---|---|
| E1 写字节 | `1 = 软件关闭` |
| `0x03.fet_status` | bit0=充电MOS、bit1=放电MOS，`1 = 导通` |

模拟器把 E1 写字节原样存入并当 `fet_status` 上报，于是"请求双开"读回 `0x00`（双关）。

**修复**：`scripts/uart0_bms_rain_simulator.py` 构造 `0x03` 时取反低两位：`fet_status = (~args.mos) & 0x03`。

**意义**：这是**后端读回对账正确拦下一个假成功**的实证 —— 若无该 verifier，界面会显示成功而设备实际状态相反。

### 4.2 残余间歇失败（已定位，未修复）

**现象**：修复极性后 `set_mos_policy` 成功率约 **80%**（无轮询时 6/7；有轮询 4/5）。

**两种失败签名**：

| 签名 | 含义 |
|---|---|
| `readback: jiabaida: [3]` | `ErrChecksumMismatch` —— 60B 读回窗口内容错位 |
| `ACK: expected ACK for cmd 0xE1, got DDE10400000077` | ACK 的 status 字节被读成 `0x04`（应为 `0x00`） |

**根因（2026-10-15 已定案）**：**串口选错口导致物理层电平争用**。

本台架有两个 USB 串口适配器，**两者的 TX 都接到了 S3 的 UART0 RX(GPIO44)**：

| 设备 | ID | 实际角色 |
|---|---|---|
| `/dev/ttyUSB0` | `1a86:7523` CH340 | 曾被当作模拟器口，**非独占** |
| `/dev/ttyACM0` | `1a86:55d3` USB Single Serial | S3 UART0 的正确接入口 |

两个驱动同时驱动同一根 RX 线 ⇒ 电平争用 ⇒ 帧内出现**单 bit 翻转**（实测一帧 60B 中有 8 个字节各翻 1 位，XOR 全为 2 的幂）。

**A/B 对照（决定性证据）**：

| 模拟器端口 | 解析成功率 |
|---|---|
| `/dev/ttyUSB0` | **0/5、100% 失败** |
| `/dev/ttyACM0` | **90s 18/18、60s 12/12，失败率 0%** |

**同一根因的三种表现**：
1. 轮询帧校验和错（99~100%）→ 解析失败 → `last_data_at` 不刷新 → 超 60s 阈值判**边缘设备离线**；
2. `set_mos_policy` 读回间歇失败（~20%，即本节前述两种签名）；
3. 界面"离线但仍有读数"——`DataReport` 确实在到，只是解析不过。

**已修复**：`ehome-simulator.service` 端口由 `ttyUSB0` 改为 `ttyACM0`（文件内注明原因与禁止改回）。修复后设备回到 `active`、`err=0`、最新读数持续刷新。

> 结论修正：本节原先归因于"固定 `read_size` 窗口错位"**不成立** —— 真因在物理层。`read_size` 语义本身无缺陷，无需改动协议。

## 5. 环境坑（值得记录）

0. **串口必须选 `/dev/ttyACM0`（`1a86:55d3`），不能用 `/dev/ttyUSB0`（CH340）** —— 见 §4.2，选错口会造成帧内单 bit 翻转，表现为"有数据但显示离线"。这是本轮最耗时的一个坑，判据：先换串口做 A/B，别先怀疑协议。
1. **固件默认控制台走 USB-Serial-JTAG**，只有 CH340 接 UART0 时串口全黑、看起来像"没启动"。本次一度把控制台改到 UART0 以诊断，**但这会让固件 `bus_dma.c:424` 跳过 UART0**，BMS 数据链路随之失效 —— 控制台与 UART0 数据口**互斥**，已回退。
2. **热点默认 channel 13** 会导致 ESP32 关联失败（`reason=205`/`2`），改 **channel 6** 后正常。
3. **能力窗口 15 分钟**（`MaxCapabilityAge = 10min + 5min`）：`ResourceReport` 仅在启动/配置变更时上报，超窗后所有控制动作被 `capability_stale` 门禁拦下。需 `POST /nodes/:id/query-resources` 主动刷新。
4. **确认凭据限流**：5 次/分钟/动作（`maxConfirmationsPerWindow=5`）。
5. **`POST /edge-devices/:id/operations` 三个必填项**：`Idempotency-Key` 头、风险动作的 `reason`、以及 `params`（**不是** `parameters`）。
6. **Docker 构建不可用**：构建容器访问 `proxy.golang.org` 超时，改为本机构建后端二进制 + 前端 dist。
7. **8080 被 SearXNG 占用**，后端改用 18090。

## 6. 复现命令

```bash
# 服务
systemctl --user status ehome-backend ehome-simulator
# 热点（需 sudo：radio 软件关闭时必须先开 radio）
sudo nmcli radio wifi on
sudo nmcli device wifi hotspot ifname wlp0s20f3 ssid EHome-Test password ehome12345
sudo nmcli connection modify Hotspot-1 802-11-wireless.band bg 802-11-wireless.channel 6
# 设备
python3 -m esptool --chip esp32s3 --port /dev/ttyACM0 write_flash \
  0x0 .run/fwbuild/s3-n16/bootloader/bootloader.bin \
  0x8000 .run/fwbuild/s3-n16/partition_table/partition-table.bin \
  0xd000 .run/fwbuild/s3-n16/ota_data_initial.bin \
  0x10000 .run/fwbuild/s3-n16/ehome_collector.bin
python3 -m esptool --chip esp32s3 --port /dev/ttyACM0 write_flash 0x9000 .run/eh_tls_nvs.bin
# 能力刷新（控制动作前必做，窗口 15 分钟）
curl -X POST -H "Authorization: Bearer $TOKEN" http://127.0.0.1:18090/api/v1/nodes/1/query-resources
```
