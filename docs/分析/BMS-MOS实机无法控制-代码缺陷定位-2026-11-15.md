# 嘉佰达 BMS「MOS 开关实机不受控」代码缺陷定位

> **状态**: 分析完成（P0 缺陷已用真实固件代码路径复现）
> **日期**: 2026-11-15
> **触发**: 实机验证 `set_mos_policy`（充电/放电 MOS 软件开关）无法成功
> **关联**: [嘉佰达BMS协议与门禁](../协议/嘉佰达BMS协议与门禁.md) | [日出日落BMS-MOS-自动化验证记录-2026-11-13](../验证/日出日落BMS-MOS-自动化验证记录-2026-11-13.md) | [本机生产同构联调验证-2026-10-16](./本机生产同构联调验证-2026-10-16.md)

## 0. 结论

**代码有问题，且是必然失败的结构性缺陷，与实机接线/波特率无关。**

| 编号 | 结论 | 等级 |
|---|---|---|
| **D1** | `set_mos_policy` 有界计划的**读回步声明 `ReadSize: 60`**，而真实 0x03 帧长 = `30 + 2×NTC`（典型 38 B）。固件把 `read_size` 当"收满下界"，短帧永远收不满 ⇒ 静默窗口一到即判失败 ⇒ **整条动作 FAILED（错误码 0x1401）** | **确认缺陷（P0）** |
| D2 | 写步 7 B ACK 与读回步互相独立：**写大概率已生效，但系统报失败**（用户看到"失败"，电池侧 MOS 其实动了） | 确认（D1 的后果） |
| D3 | 0xE1 优先级锁陷阱：运营优先级(0xAA)关闭后，用户优先级(0x00)无法解除，BMS 仍回 ACK，读回不一致 ⇒ 也表现为"失败" | 高可疑（需实机确认） |
| D4 | `error_code`（哪一步、什么错）只进 `command_inboxes.payload_json`，不进 `final_reason`/UI ⇒ 现场无法区分"没 ACK"与"读回短帧" | 可诊断性缺陷（P1） |
| D5 | 单步读动作（`read_basic_info` 等）同样声明 `ReadSize: 60/50/`… sim 值；单步 V2 有短读豁免所以不致命，但埋雷 | 潜在（P2） |
| D6 | 迟到的轮询 0x03 帧可能被写步当成 ACK 收下：batch 路径**完全不校验 ACK 内容**；`s_plan_active` 期间任何字节都进 batch 缓冲，而 drain 发生在 `s_plan_active=true` **之前**、fence 只等 pending 队列空不等线路空闲 ⇒ 仍可能被抢。只有服务端 verifier 能抓到 | 低-中（P3） |
| D7 | 写步 `ReadSize: 7` 是**截断式**的（固件 `len >= expected` 只交前 7 B）。若真机对 0xE1 回显 9 B（`DD E1 00 02 YY XX CHK CHK 77`），会被截成 7 B ⇒ 报 "ACK: expected ACK for cmd 0xE1, got DDE100020001FF"，现场极易误判成"ACK 不对" | 中（与 D1 同族，P0 一并治） |
| D8 | 读回失败时状态机落 `FAILED` 而非 `UNKNOWN`，且不区分"step0 已成功" ⇒ 写帧已物理发出、MOS 可能已变化，界面却引导操作员重试 | 中（P1） |

**根因一句话**：`ReadSize` 在固件里是"必须收满的长度下界"，而驱动把它当"建议窗口"填了模拟器时代的 60 —— 仓库自己在 2026-10-02 为**轮询模板**修过同一缺陷（`ReadLength` 必须为 0，见 `jiabaida_control.go:1226-1248`），但**控制计划没同步修**。

## 1. 缺陷 D1 的代码证据

### 1.1 计划声明（后端）

`backend/internal/drivers/jiabaida_control.go:459-465`：

```go
return CompiledControlPlan{
    AtMostOnce: true,
    Steps: []CompiledControlPlanStep{
        {ID: "write_mos", Kind: "write", TXData: writeStep.TXData, ReadSize: 7, RXTimeoutMS: 1500, PostTXDelayMS: 100},
        {ID: "readback_fet", Kind: "readback", TXData: jiabaidaReadFrame(0x03), ReadSize: 60, ...},
    },
}
```

同一文件 `1235-1238` 记录了实机事实（2026-10-02 修复轮询时的取证）：

> `Every real 0x03/0x04/0x05/0x0F/0xAA reply is shorter than the values that used to sit here`
> 帧长 = `DD CMD STATUS LEN DATA.. CHK_H CHK_L 77`，`LEN = 23 + 2*NTC for 0x03`。

即 NTC=4 时总帧 = 4 + 31 + 3 = **38 B ≪ 60 B**。

### 1.2 固件把 read_size 当"下界"（`esp32-collector/components/bus_worker/bus_worker.c`）

`uart_collect_response()`（:1381-1394）：

```c
if (expected > 0 && len >= expected) { /* 快速路径：收满才返回 */ }
if (len > 0 && ...10ms 静默...) { memcpy(...); *out_len = len;
    return expected == 0 || len >= expected; }   // ← 38 < 60 ⇒ 返回 false
if (elapsed_ms > timeout_ms) return false;       // ← 最终 1500ms 超时
```

`execute_uart_batch()`（:1463-1467）：`uart_collect_response(...)` 失败 ⇒ `*error_code = 0x1400 + i`（i 为 0-based 步序号）⇒ 整条计划失败。

**失败时机要分清**（现场抓日志别按 1.5 s 找）：

| 设备行为 | 返回时机 | error_code |
|---|---|---|
| 回了帧但比声明短（本次） | **约 10 ms**（静默窗口一到即判 false） | 0x1401 |
| 完全没回帧 | 约 1500 ms（`rx_timeout_ms`） | 0x1400 / 0x1401 |
| 回了足够长但被 >10 ms 间隔切段 | 约 10 ms 判短 | 0x1401（与 read_size 无关的分帧敏感） |

### 1.3 仓库内部自相矛盾（不用上实机就能发现）

后端单测的读回 fixture 造的是 **38 B** 真实形状帧
（`backend/internal/drivers/jiabaida_test.go:1055-1063`：`DD 03 00 1F` + 31 B + CRC + `77`），
而**同一份代码编译出的计划声明 60 B**。单测把 38 B 直接喂给 `VerifyControlAction`，
**绕过了固件的长度门**，于是"38 B 合法"和"要求 60 B"两个事实长期共存而没有测试红。

独立复核（后端只读审计，复刻固件判据 + 后端 `decodeBatchPlanEnvelope`/`VerifyControlAction` 实跑）：
**34 / 38 / 46 / 60 B 的 0x03 帧，后端 verifier 全部通过**；只有固件在 `read_size=60` 时把 38 B 判 0x1401。
⇒ 问题**只在"声明长度"这一层**，不在校验层，也不在 gating/幂等/capability 任何一层。
修复有现成先例：`read_sn` 的读回步就是 `ReadSize: 0`（`jiabaida_control.go:699`）。

在 `__scratch_mos_audit/`（临时，已删）用仓库 host-test harness（`bus_worker_batch_tests.c`

[PROBE C] readback read_size=0 (idle framing), real reply 38B -> ok=1 error_code=0x0000

## 3. 为什么 2026-11-13 的"通过"没发现

| 环节 | 当时的形状 | 是否经过固件长度门 | 后果 |
|---|---|---|---|
| `scripts/esp32_simulator.py`（2026-08-26 S1S2） | **直答后端协议**的 Python 模拟器 | ❌ 完全不经过固件 | 其 envelope 里 0x03 只有 `02 26 00` = **38 B**（`自动化引擎S1S2验收报告:162`），照样 SUCCEEDED —— 因为没走 `uart_collect_response` |
| `backend/__scratch_simnode`（2026-11-13 日出日落） | Go 节点模拟器，mTLS 直连后端 | ❌ 不经过固件 | 按驱动假设回 60 B（`验证记录 §2.2`），读回步"刚好"收满 |
| 2026-10-16 本机同构联调（唯一有真 S3 的） | 真固件 + `uart0_bms_rain_simulator.py` | ✅ 经过 | 但模拟器回 **60 B**，正好等于声明值 ⇒ 缺陷不可见 |
| 后端单测 | 38 B fixture 直连 verifier | ❌ 绕过 | "38 B 合法"与"要 60 B"长期共存 |
| 固件 host 测试（`bus_worker_batch_tests.c`） | 只 stage **恰好 `read_size`** 字节 | ✅ | 无一条用例送短帧 |

**结论**：`execute_uart_batch` 的 `read_size` 语义**从未被任何端到端验证覆盖过**——
要么模拟器不经过固件，要么经过固件的那个模拟器恰好回 60 B。
这就是"模拟器按代码写、测试按模拟器写"的循环验证：链条每一环都自洽，唯一不自洽的是真实设备。

## 4. 修复方案

### P0（必须，1 行）

`jiabaida_control.go` 中**所有 0x03 读回步** `ReadSize: 60` → `0`：

```go
{ID: "readback_fet", Kind: "readback", TXData: jiabaidaReadFrame(0x03), ReadSize: 0, ...}
```

- 合法性：`validateChannelCmdV2Step` 只拒绝 `> MaxRX`，0 合法；`read_sn` 步早已用 `ReadSize: 0`。
- 语义：0 = 交给 `bus_rx_boundary` 的"行空闲定帧"（`bus_worker.c` `expected==0` 分支），与轮询模板同一策略，对任意 NTC/串数都成立。
- **写步也一起改 0**（D7）：`ReadSize: 7` 会把长于 7 B 的回包截断成 7 B，真假 ACK 无法区分；`0` 让固件交回设备实际发的字节，由后端 `jiabaidaExpectZeroAck` 做内容裁决（它本来就会校验 CMD/LEN/状态/校验和/0x77）。
- 同类待审：`readback_test_status`(9B)、`readback_custom`(13B)、`readback_resistance`(67B)、`readback_sn`(39B) —— 都是 sim 值，同一缺陷族。
- 逐条对照（`grep 'ReadSize: [1-9]' jiabaida_control.go` 的结果必须只剩非嘉佰达帧的确定长度场景）。

### P1（配套回归，防止再漂移）

1. **跨层契约用例**（Go）：编译出的 plan 里，任何 `readback` 步若 `ReadSize > 0`，则必须 ≤ 该命令"最小合法响应帧长"；对 0x03 直接要求 `== 0`。
2. **host 用例入库**（`bus_worker_batch_tests.c`）：把本文件 PROBE C/E 固化 —— "声明 0 的读回步在短帧下成功"、"声明长度大于实回是失败不是成功"。
3. **fixture 自洽断言**：`jiabaidaMOSEnvelope` 造 38 B，就必须断言同 action 的 plan `ReadSize == 0`（或 ≤ 38），二者同源。

### P2（可诊断性）

`nodemgr/handler_channel_cmd_v2.go:47-64` 丢掉 `response.ErrorCode`：最终 `final_reason` 只有 `final_failed`，UI 显示"设备未接受或回读校验不一致"。
建议 `final_reason = fmt.Sprintf("final_failed(0x%04X)", ErrorCode)`，UI 映射：

| error_code | 含义 |
|---|---|
| 0x1400+i | 第 i 步无响应/超时（设备没回帧） |
| 0x1401 | 第 2 步（读回）长度不足或超时 —— **本次最可能** |
| 0x1100+i | 计划/步骤解码失败 |
| 0x1200+i | UART 写失败 |
| 0x1300+i | 响应缓冲溢出（>256 B） |

### P2.5（语义）

读回步失败时，写步多半已经生效。建议：`verified_result` 或 `failure_detail` 标出"已发出的步序号"，
状态在"step0 成功 + step1 失败"时优先落 `UNKNOWN`（"结果未知，请先核对当前 MOS 状态"），
而不是 `FAILED` —— 现在的 UI 文案"设备未接受或回读校验不一致"会引导用户**重复下发**，在 MOS 场景里是危险的。

### P3（实机确认项）

- **优先级锁（D3）**：`YY=AA` 运营锁不能被 `YY=00` 解除（协议 §0xE1）。UI 的 MOS 开关固定发 `priority: "user"`（`useBmsMosControl.ts:124`），而 2026-11-13 的规则用例发的是 `operator`。若同一台设备被 operator 锁过，**"打开"指令会被 BMS 忽略但 ACK 成功** ⇒ 读回不一致 ⇒ FAILED。需实机确认，并决定"谁能解锁"的产品策略。
- **0xE1 是否回 ACK**：部分嘉佰达固件对 `5A` 写帧不回 7 B ACK（则表现为 0x1400）。用串口工具直发 `DD 5A E1 02 00 00 FF 00 77` 观察原始回包即可判定。

## 5. 现场取证（30 秒定位到哪一步失败）

```sql
-- 最近一条 MOS 命令走到了哪一步（error_code 是关键）
SELECT c.command_id, c.status, c.final_reason, c.created_at,
       i.event_type, i.payload_json
FROM command_executions c
LEFT JOIN command_inboxes i ON i.command_id = c.command_id
WHERE c.created_at > now() - interval '1 hour'
ORDER BY c.created_at DESC LIMIT 10;
```

- `payload_json.error_code = 5633`（0x1401）⇒ 写步已过、**读回步长度不符**（即 D1）。
- `payload_json.error_code = 5632`（0x1400）⇒ 写步没有收到 ACK（BMS 不回写 / 接线 / 优先级/固件不支持 0xE1）。
- `status=SUCCEEDED` 但界面显示失败 ⇒ 前端状态机问题（本轮未发现）。

## 5.1 操作层注意（修复上线前，别用"重试"验证）

- 同一次执行**重试只会重放那条 FINAL**（`CommandID` 跨 attempt 不变，固件 `same_identity()` 排除 attempt），不会再发一次物理写；要重来必须**新建执行**（新 commandID）。
- 新执行若计划字节变了（例如 ReadSize 改 0）而 commandID 撞到旧槽位，会得 `V2_ERR_COLLISION 1003`，需重启节点或等槽位被顶掉。
- 前端每次点击都生成新幂等键 UUID，所以"连点两次"会真的下发两次（对 MOS 是危险操作）。

## 6. 本轮未验证（需要实机）

1. 真实 BMS 对 `DD 5A E1 02 ..` 的原始回包（长度/状态字节/校验）。
2. 设备当前是否处于 operator 锁。
3. 修掉 D1 后 `fet_status` 位是否真按 `0x01/0x02` 语义翻转（协议原文 vs 固件实现差异）。
