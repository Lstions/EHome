## 0. 一句话结论

新表 `telemetry_rollup_1m`（宽行、月分区、有消费者、有保留期）**不是** 2026-09-15 退役的
`unified_data_rollup_1m` 的复活；两者名字同构但**不是同一条命**。退役步骤只 DROP 旧表，

## 1. 「死表不得复活」针对的是**无消费者**的表，不是所有预聚合

2026-09-15 的退役裁决（`docs/分析/rollup-退役裁决-2026-09-15.md`）给出的理由只有三条，
逐条对照新表：

| 退役理由（原文摘要） | 旧表 `unified_data_rollup_1m` | 新表 `telemetry_rollup_1m` |
|---|---|---|
| 无界增长的第二张表（需另配保留期+清理器+测试） | 是：无保留期、无分区、无清理路径 | **否**：月分区 + 复用 `DropPartitionsBeforeFor`（O(1) 整分区 DROP）+ 挂统一窗口 `SystemRetentionDays()` |
| 必须改数据模型才能接线（表无 `logical_device_id` 列 ⇒ 生产不可达） | 是（当时查询恒带 logical scope） | **否**：逻辑设备层已整体移除（`bb19ee30`），本仓查询协议就是 `device_id = ?`，新表列即 `device_id` |
| 收益是"省几毫秒"，没有读路径用它 | 是：实测 30 天窗口 3.6 ms / 1191 buffers | **否**：消费者是长窗图表（方案 §5.3），且**短窗仍走原路径**，只有 > 6h 窗口才切 |

⇒ 裁决里"死表"的判据是 **「写了没人读 + 读了不划算 + 无界」**，不是"表名带 rollup"。
新表三条都不成立，因此建表**不违反**该裁决；而"不得复活旧表"这一条仍然有效，
由 `datalifecycle/rollup_retirement_gate_test.go` 守住。

> 这条区分是本次补进裁决体系的**新增一节**（原裁决文档 §8 的原文是「若未来确需 rollup 类
> 预聚合，正确入口是**重新裁决**（含：加列、改冲突键、重聚合回填、保留期与清理器），而不是
> 复活本表」）。本次即按该入口执行：重新裁决 = 本文档 + 新表的保留期与清理路径。

### 2.1 建表模板（四处一致性，方案 §4.1/§8 最后一条的同款要求）

|---|---|---|

| `partitionParentIndexes` | `backend/internal/datalifecycle/partition_mgr.go:700-718` | **空切片登记**（不是不登记！见下） |
| `partitionCopyColumns` | 未登记（有意） | 本表无 `id`/`sensor_name` 列，通用搬迁路径不适用；误登记会被 `TestTelemetryRollupRegisteredInPartitionTemplates` 判红 |

**为什么 `partitionParentIndexes` 必须登记一个空切片**：`createPartitionedParent`
（partition_mgr.go:749-779）对**未登记表**会回退到 `unified_data` 的 DDL 与索引清单
（`:648-651` 的 `ddlTable = partitionedTable` 回退）。若本表不登记索引项，会被套上

edge_device_id` 在本表**不存在** ⇒ 建表 DDL 直接报错。空切片才是"已登记且无二级索引"。

### 2.2 分区与保留期

| 函数 | 文件:行号 | 语义 |
|---|---|---|
| `EnsureTelemetryRollup1mPartitions` | `datalifecycle/telemetry_rollup.go` | 复用 `EnsurePartitionsFor`（`<table>_<YYYYMM>` 命名，与 unified_data 同款） |
| `MigrateTelemetryRollup1mToPartitioned` | 同上 | 空库直接建分区母表；**平表守卫**见 §2.4 |
| `DropTelemetryRollup1mPartitionsBefore` | 同上 | 复用 `DropPartitionsBeforeFor`（按分区名 `YYYYMM` 后缀识别，整月早于 cutoff 才删） |
| 启动接线 | `backend/cmd/server/main.go:100-111`（迁移）、`:115-124`（加入 `ensurePartitions` 表清单） | 迁移**失败仅 Warn**，不挡启动 |
| 保留期接线 | `backend/cmd/server/main.go:126-152`（定义+首跑）、`:163-166`（挂既有 24h ticker） | `reapRollupPartitions()` |

**分界/保留期取值（Lead 点名项）**：

- cutoff 用 **`datalifecycle.SystemRetentionDays()`**，即 `EHOME_DATA_RETENTION_DAYS`
  （`config.DefaultDataRetentionDays = 90`，见 `internal/config/config.go:253`）。
  **没有**使用设备级 `retention_days` —— 该字段已随逻辑设备层（`bb19ee30`）删除，
  本仓现在是系统级单一窗口（`internal/datalifecycle/retention_task.go:17-25` 的注记）。
- 方案 §7 阶段0 建议把保留期 90 → 60；本任务**不擅自改默认值**，只按现有配置读。
  即：运维把 `EHOME_DATA_RETENTION_DAYS` 设成 60，rollup 分区随之 60 天回收，无需改码。
- **口径一致性证据**：`reapRollupPartitions` 与 `RetentionTask.dropExpiredPartitionsOnce`
  读的是同一个 `SystemRetentionDays()`，cutoff 计算式也相同（`now - days*24h`）。

### 2.3 为什么不把新表加进生产 AutoMigrate（Lead 要求落一句裁决）

与 `UnifiedData` / `DeviceData` 完全同范式（`internal/database/gorm.go:89-96` 的注记）：
PG 生产库的分区母表由 `partition_mgr` 用裸 DDL 建，`AutoMigrate` **无法建分区表，且会把
已存在的分区母表降级改写**成普通表 —— 一旦降级，`DropPartitionsBeforeFor` 找不到
`<table>_YYYYMM` 分区，保留期机制**静默失效**（不报错、不删数据 = 又变回"无界表"，
正好踩回旧 rollup 的退役理由）。

⇒ **裁决：`telemetry_rollup_1m` 不登记 `database.AutoMigrate()` 清单，也不登记
`testutil.allModels`。** 模型文件存在只为两件事：(a) 给 SQLite 测试建表；
(b) 让表名/列名的 GORM 可推导性可读。生产唯一建表入口是 `partitionParentDDL`。

### 2.4 平表守卫（本表独有）

`MigrateTelemetryRollup1mToPartitioned` 在 PG 上若发现库里已有一张**平表**
`telemetry_rollup_1m`，**直接报错**而不是走通用搬迁路径。理由：通用路径的
`copyMonthBatched` 用 `partitionCopyColumns[src]`，未登记的表会回退到 `unified_data` 的
8 列清单（`partition_mgr.go:733-736` 定义、`:807` 回退），而本表只有三列 ⇒ `INSERT ... SELECT` 报列不存在，
留下半成品 `_new` 母表，每次启动重试都失败。

哪种情况才会出现平表：有人把模型加进生产 AutoMigrate（正是 §2.3 禁止的做法）。
fail-loud 比静默半迁移好；错误消息里直接给出处置指令（`DROP TABLE telemetry_rollup_1m`，
派生数据丢了可重建）。

## 3. 诚实声明：v1 payload 编码**不是**方案 §5.2 的目标形态

方案 §5.2 的 232 B/行 是建立在 §4.3 逐字段量化表 + §4.4 slot 字典之上的（payload 不带
字段名，只带 slot_id 与量化位宽打包）。两者都由 `internal/telemetry`（L2，task-3）交付，
本任务按任务书要求**不依赖**它，因此先落 v1 自描述编码：

```
v1 = 1B version | 2B BE 字段数 | N × { 1B 名字长度, 名字, 8B avg, 8B min, 8B max, 8B last, 4B count }
```

| 项 | v1（本任务） | 方案 §5.2 目标（v2，待 L2） |
|---|---|---|
| 每行字节（29 字段） | ≈ 1.5 KB | ≈ 232 B |
| 每设备每天 | 1440 行 × 1.5 KB ≈ 2.2 MB | 1440 × 232 B ≈ 0.33 MB |
| 是否依赖外部字典 | 否（自描述，可独立回放） | 是（slot 字典） |

**影响**：在 v2 落地前，本表的实际占用是目标值的约 6.4 倍。
⇒ **容量结论（90 天 ≤ 3 GB）不能用 v1 的实测值去论证**；`docs/验证/` 的回归基准
若引用 rollup 占用，必须标注编码版本。解码已按 `payload[0]` 版本分派
（`DecodeRollupPayload`），v2 落地后新写入用 v2、旧行照 v1 解，**无需数据迁移**。

## 4. 读路径分派（§5.3）的落地边界

| 端点 | 本任务是否已接 | 说明 |
|---|---|---|
| `/unified-data/historical` | ✅ 已接（`backend/internal/api/handler_data.go:279-297`） | 长窗 avg 先试 rollup，未命中/未启用回落原路径 |
| `/unified-data/historical-batch` | ✅ 已接（`handler_data.go:388-404`） | 同上，每 category 独立判定；并发 goroutine 用 `db.Session(&gorm.Session{})` 隔离 Statement |
| `/edge-devices/:id/latest-values`、`/overview` | ❌ 未接 | 走既有 `latestValueCache`（内存），rollup 的分钟粒度对"最新值"没有意义 |
| `/edge-devices/:id/data-summary` | ❌ 未接 | min/max(ts) 走主键索引直取，已是 O(log n)，rollup 帮不上 |
| `/unified-data/categories` | ❌ 未接 | 方案说读 `sensor_field_obs`；那是字段解析层的投影表，与 L3 无关，属另一任务的接线 |
| 告警/自动化 | 不动 | 走内存 sink，不查库（既有语义） |

**默认关闭**（`EHOME_TELEMETRY_ROLLUP_READ=false`）。关闭时 `shouldUseRollup` 恒 false，
**旧路径一个字节的行为都不变**（这是硬约束，有单测）。开启后仍 fail-open：
表空/坏行/表不存在 ⇒ 回落原路径，不返回空点集（空图比慢更糟）。

`change` 模式（状态翻转序列）**绝不走 rollup**：payload 里没有翻转信息，用
avg/min/max/last 重建 0→1 跃变会算错（与 `history_points.go:174-180` 的
`maxChangePoints` 同款理由：错数据比报错更坏）。

## 5. 门禁（§5.4 硬要求）

`backend/internal/datalifecycle/rollup_retirement_gate_test.go` 是本任务**重建**的门禁
（原版随 `bb19ee30` 整文件删除，490 行 → 0，见 `git show --stat bb19ee30`）。
重建后比原版多守三条：

| 断言 | 守什么 |
|---|---|
| (1)(2) 旧表名/旧符号零生产引用 | 原版能力，保留 |
| (3) 退役步骤仍是幂等 DROP 且被 AutoMigrate 调用 | 原版能力，保留 |
| **(4) 退役文件里不得出现新表的可执行用法** | 新增：退役 DROP 是启动时无条件执行，误伤新表后**没有任何运行时现象**会暴露（表空、无消费者），只有源码门禁能拦 |
| **(5) 退役 DROP 不得用通配（LIKE / %）** | 新增：`unified_data_rollup_1m%` 会连带删掉 `telemetry_rollup_1m` 与 `telemetry_rollup_1m_YYYYMM`（名字同构） |
| **(6) 新表必须真的登记在建表清单里** | 新增：防止另一种假绿 —— 有人把新表从 `partitionParentDDL` 删掉，"没误伤"依然全绿（没什么可误伤） |
| **(7) 写入侧 sink 的命名契约** | 新增：黑名单是**连续子串**匹配，旧名 `SetRollupSink` / `rollupSink` 会连带禁掉 L3 的接线符号（含**局部变量名**）。自检里有正反两条用例：用 `TelemetryRollup` 词根 ⇒ 不红；误用旧名 ⇒ 红。目的是让接线者「照文档接线是绿的」，而不是被门禁拦下后去改门禁 |

行为侧证据（不是源码扫描）：
- `backend/internal/database/retire_rollup_test.go`：
  `TestRetireLegacyRollup1mDoesNotTouchTelemetryRollup` —— 两表同时存在 + 各自有数据，
  退役后旧表没了、新表行数与 payload 字节**原样**；
  `TestRetireLegacyRollup1mDoesNotUseWildcardDrop` —— 钉死退役文件不得出现通配形态。
- `backend/internal/datalifecycle/telemetry_rollup_pg_test.go`（PG 真库）：
  建分区母表 → ensure 建出 `telemetry_rollup_1m_YYYYMM` → 写一行 → reaper 按 cutoff
  删掉**那一个**分区、母表与本月份分区保留 → 二次调用幂等；
  另一条：同库放着名字同构的旧表 `unified_data_rollup_1m`，reaper 跑完它原样在（行数不变）。

### 8.2 无损性证据（L3 的真实数据验收）

`backend/internal/datalifecycle/telemetry_rollup_realdata_test.go` 直接用生产导出的
`.tmp-telemetry/realdata/unified_data_202611.csv.gz`：

```
EHOME_ROLLUP_REALDATA_CSV=/ws/.tmp-telemetry/realdata/unified_data_202611.csv.gz \
  go test -run TestRollupRealData -v ./internal/datalifecycle/

读取真实数据 300000 行（每设备上限 150000）
原始行入库 300000 行，耗时 ~0.5s
rollup 落库 788 行（每设备每分钟一行 / 2 设备）
✅ 逐桶逐字段比对通过: 31965 条 (设备数=2, 分钟桶数=788)；
   count/min/max/last **严格相等**；avg 最大相对误差 6.943e-16 (<=1e-12)
```

判据的精确含义（不许含糊）：
- `count / min / max / last` —— **严格相等，误差 0**。前三个是整数/选择，`last` 是"该分钟最后一行"
  （CSV 顺序 = 入库顺序，rowid 单调）。
- `avg` —— 相对误差 ≤ 1e-12。原因是**求和路径不同**（Go 侧增量均值 vs SQL 侧 sum/count
  + SQLite 的 Kahan 补偿求和），属浮点舍入顺序差异，不是语义差异；同时断言
  `avg ∈ [min, max]` 才是真正防"算错"的判据。

> ⚠ 该用例必须 **`SetBucketTTL` 关掉内存桶过期**：TTL 是生产保护（DB 长时间不可用时丢
> 预聚合防 OOM），不是统计语义；一次性重放跨天数据时若不关，跨度 > 6h 的桶会被当"过期"丢弃
> —— 实测踩到（device 15 整段桶消失，15078 vs 31965）。这一点已写进用例注释。
