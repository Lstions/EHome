# 自动化策略：sun_event 补发机制与「冷却吞掉手动触发」（2026-11-17）

- 触发场景：生产实测，规则「关闭BMS充电」（日落 · 正点）
- 涉及代码：`backend/internal/automation/evaluator.go`（`evalSunEventRule` / `LoadRules`）、`planner.go`（`TriggerRule`）
- 关联：`docs/设计/自动化策略引擎-日出日落与多动作-方案.md` §3.1.4 / §6.2、`docs/分析/自动化策略-下次执行时间-可行性与实施方案-2026-11-17.md`

---

## 1. 现象

触发历史里两条记录（截图 2026-11-17 22:15）：

| 时间 | 来源 | 结果 | 事件时刻 | 命令 ID | 详情 |
|---|---|---|---|---|---|
| 22:15:12 | 手动 | 冷却抑制 | - | - | `cooldown active (15s remaining)` |
| 22:14:57 | 自动 | 已执行 | 17:41:54 | `1dd6-42a7-864b-e35` | - |

用户的操作只有一次：点「触发」（手动）。观察到的"三个不对"：时间不对、来源不对、多了一条冷却抑制。

## 2. 时间线复原

- **17:41:54**：该规则坐标的当日日落（`event_at` 的口径 = `fireAt = 日落 + 偏移`）。
- **22:14:57**：求值器在 1 分钟 tick 上把这次 4.5 小时前的日落**补发**了一次，真实下发 `set_mos_policy`；同事务写冷却锚点 `last_triggered_at = 22:14:57`。
- **22:15:12**：用户点「触发」。手动路径读锚点判定冷却：距锚点 15s < 30s ⇒ 拦截，落 `suppressed_cooldown`，`detail` 写 `cooldown active (15s remaining)`。

算术自洽：`22:14:57 + 30s = 22:15:27`，`22:15:12` 时剩 15s。**两条记录都是真的，出错的是 22:14:57 那次自动执行本身。**

## 3. 根因：电平判定 + 纯内存的"本日已触发"

`evalSunEventRule` 旧判定：

```
now >= fireAt && sunStates[rule.ID] != 本地日期  → 触发
```

- 这是**电平**判定：不要求"本次 tick 真的跨过了 fireAt"；
- `sunStates` 是**纯内存** Map（rule ID → 本地日期），下列任一情况都会让它为空/被清：
  1. 进程重启；
  2. 规则在事件之后**新建**（新 ID 无状态）；
  3. **停用后重新启用**，或保存了 `sameWindowStateFields` 白名单字段（`enabled` / `trigger_type` / 窗口 / `sun_kind` / `offset` / 经纬度 / 时区）⇒ `LoadRules` 删除该项。

旧实现只对第 1 种做了保护（`firstSunTick` 首 tick 保守跳过，A-3 门禁）。第 2、3 种在下一个 tick 就满足了"电平"条件，于是把几小时前的事件重放一次并真实下发设备动作。

## 4. 证据

1. **触发历史"共 2 条"**：若这条规则在 17:41 时已在生效集合里，必然留下一条 executed；没有 ⇒ 它在 17:41 之后才进入求值器。
2. **沙箱复现**（同一套求值器，`go test ./internal/automation`，2026-11-17）：

| 场景 | 旧实现 | 新实现 |
|---|---|---|
| 事件后保存规则（改偏移） | 补发 1 次 | 0 |
| 事件后新建规则 | 补发 1 次 | 0 |
| 停用 → 重新启用 | 补发 1 次 | 0 |
| 事件前生效、跨过事件 | 1 次 | 1 次（未误杀） |
| 进程重启 | 0 次 | 0 次 |

## 5. 裁决与改动（2026-11-17 用户）

> 不做这种"创建了还操作之前的"补发机制，用户完全可以自己手动触发一次。

实现要点：

- `Evaluator` 新增 `lastClockTick`（上一轮时钟 tick 的时刻，零值 = 进程还没 tick 过）；
  `evalTimeWindows` 在同一个写锁里读取并推进它。
- `evalSunEventRule` 的触发条件改为 **`prevTick < fireAt <= now`**；
  `fireAt <= prevTick`（错过 / 规则在事件之后才进入集合）⇒ 登记"本日已处理"、**不提交、不下发**，并打一条 INFO：
  `automation: sun_event 跳过已过事件(不补发) rule_id=... event=... prev_tick=... now=...`。
- 新增 `configChanged[ruleID]`：`LoadRules` 在"规则新进入缓存 / `sameWindowStateFields` 白名单字段变化"时置位；事件未到达时清除，事件已过时登记"本日已处理"并跳过。**仅靠 prevTick 不够**：编辑把 `fireAt` 往后挪（`offset` 0→+1）时 `prevTick < fireAt` 仍成立，只有这个标记能拦住。
- `firstSunTick` 字段删除（被 `prevTick.IsZero()` 的同一分支吸收，A-3 语义不变）。
- `nextrun.go`：`ruleNextRunState` 增加 `clockTick` 快照；"即将触发"分支从"事件过了 ≤2 tick"改为
  **`lastClockTick < fireAt`**（只有事件正好落在上一轮 tick 与现在之间才真会触发），其余一律报次日。
- 门禁：新增 `backend/internal/automation/sun_no_backfill_test.go`（新建 / 停用→启用 / 编辑三类"不得补发" + 事件前生效必须照常触发 + 次日恢复）；A-3 保留。

## 6. 有意接受的边界

- 在事件前**不足一个 tick** 内才新建/修改的规则，当天也不再自动触发——无法判定新配置是否赶在事件之前生效，取保守方向；需要时手动触发。这与"不做补发"是同一条裁决的两个方向。
- `time_window` 的 `enter` 仍是"未知状态即触发"（`evalWindowRule`：`inside && (!exists || !wasInside)`），**本次未改**；它与 sun_event 的语义相反，需要单独裁决。
- 手动触发仍受 `cooldown` 抑制（有意的防连点设计，见 `docs/设计/自动化引擎场景仿真验证.md` SIM-MANU-002）。若规则刚被自动触发过，手动点击仍会被吞——建议前端在确认框前置提示"冷却中，剩余 Ns"。

## 7. 现场复验方法

- 创建/编辑一条"事件时刻已过"的日落规则后，等一个 tick：触发历史**不应**出现新的 executed，日志应有 `跳过已过事件(不补发)`。
- 负向：在日落前 1 分钟建规则，跨过日落的那一轮 tick 必须正常执行一次。
- 正向回归：同一条规则次日日落必须照常触发（跳过不是永久失效）。
