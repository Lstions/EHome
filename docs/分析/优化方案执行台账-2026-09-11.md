### 2026-09-12 第五轮：真实数据上暴露的分区迁移丢数据缺陷（P0）

> 触发：第四轮收尾时，主代理在本机开发库上**真跑一次迁移**做验收（而非只信 ehome_test 的绿灯），
> 服务日志立刻暴露：

```
ERROR unified_data partition migration failed (continuing with flat table):
      row count mismatch after migration: src=87487 dst=10000 (aborting, tables intact)
```

**根因（主代理实测取证，我最初的判断是错的，已自我更正）**

我最初根据"恰好 10000 行 = 一个批大小"猜测是 `ON CONFLICT DO NOTHING` 使 `RowsAffected` 偏小、
导致批次提前退出。**取证推翻了该判断**：

- 平表 87487 行**全部落在同一月 2026-08**，id 从 1 到 2094379（**id 稀疏、大量空洞**）；
- `count(*)=87487` 且 `count(distinct id)=87487` —— **无任何重复 id，根本不会触发 ON CONFLICT**。

真实根因在 `copyMonthBatched` 的**水位推进**：推进水位的查询
`SELECT COALESCE(max(id),?) FROM src WHERE id > ? AND timestamp ∈ 本月` **没有 LIMIT**，
求的是"本月剩余所有行的 max(id)"而非"本批搬走的 max(id)"。于是第 1 批搬走 id 最小的 10000 行后，
水位被直接推到**月末最大 id**，第 2 批 `id > 2094379` 无行 → `RowsAffected=0 < 10000` →
**误判"本月搬完"并 return nil**，整月只搬 10000 行。

**两点值得记下**
