### 2026-09-12 第五轮：真实数据上暴露的分区迁移丢数据缺陷（P0）

> 触发：第四轮收尾时，主代理在本机开发库上**真跑一次迁移**做验收（而非只信 ehome_test 的绿灯），
> 服务日志立刻暴露：

```
ERROR unified_data partition migration failed (continuing with flat table):
      row count mismatch after migration: src=87487 dst=10000 (aborting, tables intact)
```

**根因（主代理实测取证，我最初的判断是错的，已自我更正）**

我最初根据"恰好 10000 行 = 一个批大小"猜测是 `ON CONFLICT DO NOTHING` 使 `RowsAffected` 偏小、
导致批次提前退出。**取证推翻了该判断**：

- 平表 87487 行**全部落在同一月 2026-08**，id 从 1 到 2094379（**id 稀疏、大量空洞**）；
- `count(*)=87487` 且 `count(distinct id)=87487` —— **无任何重复 id，根本不会触发 ON CONFLICT**。

真实根因在 `copyMonthBatched` 的**水位推进**：推进水位的查询
`SELECT COALESCE(max(id),?) FROM src WHERE id > ? AND timestamp ∈ 本月` **没有 LIMIT**，
求的是"本月剩余所有行的 max(id)"而非"本批搬走的 max(id)"。于是第 1 批搬走 id 最小的 10000 行后，
水位被直接推到**月末最大 id**，第 2 批 `id > 2094379` 无行 → `RowsAffected=0 < 10000` →
**误判"本月搬完"并 return nil**，整月只搬 10000 行。

**两点值得记下**

### 关键教训（供后续复用）
1. **契约不冻结到字段/取值级别，就等于没冻结**：Domain 取值、包级命名、节点命名、URL scheme —— 四处都是「我以为写清楚了，其实留下并行的解释空间」，且**全部在并行实现时爆炸**。
2. **hot file 不能当稳定事实取证**：我用 rt.go 的文件快照断定 RT-003 是缓存问题，子代理用诊断实验证伪，并指出我引用的报错文案与该文件当前文本不一致 → 我读到的是**写入中的中间版本**。对活跃写者的文件取证前先确认 mtime 稳定。
3. **同一包内绝不允许两个写者**：据此拒绝了「另一个子代理顺手改 rt.go」的合理请求（它分析完全正确），改由该文件唯一写者执行。上一轮正因双写者覆盖，把已修好的文件恢复回原状。
4. **门禁从「文件名」推导规则时，命名方案必须先反向对齐门禁**，否则规则与目录结构打架（见设计缺陷 7）。
5. **抑制类逻辑必须验证可观测性**：suppressed_cooldown 因节流只落首条；断言「每次越限都有记录」会假红，断言「从不记录」会漏缺陷 —— 场景要断言**恰好 1 条**。
6. **夹具必须自带自检**：ProvisionSimpleDevice 搭建后先做哨兵上报并等落库，失败时分步诊断，使后续 60 个场景的失败能归因到「场景断言」而非「夹具没配好」。
7. **子代理的实测证据优先于我的推断**：本轮我两次被证伪（RT-003 归因、EDGE-004 语义的口径），两次都是子代理拿源码/实验说话。

### 2. 根因比最初判断更细：**不是单纯的特异性**

窄屏块与粗指针块用 `.el-select__wrapper`（0,1,0）把输入控件抬到 44px，压不住两条更窄的规则：

### 3. 三次尝试（前两次均被实测否决，记录以免后人重走）

| # | 尝试 | 实测结果 |
|---|---|---|
| 1 | 写进 674 起的窄屏块内（同特异性靠后出现） | **仍为 36px** —— 该块在第 4 条**之前**，同特异性更早出现 ⇒ 被压掉 |
| 2 | 把第 4 条整体移进 `@media (min-width:769px)` | **掉到 24px（更糟）** —— 移走后窄屏只剩 (0,1,0)，直接输给 EP 自带的 (0,3,0) 24px |
| 3 ✅ | 写进第 4 条**之后**的既有窄屏块（904 起）+ 新粗指针块 | 44 / 44 / 36（桌面不变），门禁全绿 |

**额外约束**：**不能新增 `@media (max-width:768px)` 块** —— F6/F27 的 spec 按块数（≤3）与锚点定位，
新增会顶开它们（实测打红 F6 的 2 条 + F27 的 4 条 + F6 粗指针块的 1 条）。最终方案**并入**既有块，块数保持 3。

> **教训更正**：前几轮把这类问题归为「特异性倒挂」，**不够准确**。
> 真正决定胜负的是**三个因素**：特异性、**源码顺序**、以及**是否在媒体查询内**。
> 本次两次失败尝试分别错在「顺序」与「移除后特异性不足」。
> 本轮实际用的排查法（可复用）：
> ① 用几何实测确认**症状**（哪个变体、哪几档不达标）；
> ② 用 `page.addStyleTag` **逐条注入候选选择器**判定「谁能赢」（本轮据此快速定位到顺序问题）；
> ③ 从**服务端 CSS 文本**逐条列出命中该元素且含目标属性的规则（含媒体条件），而非只读源码。
