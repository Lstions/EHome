### ⚠️ 修正：`failover-logs` 与 `dataSourceApi` 是「有后端无 UI」的完整垂直切片，属产品决策

初版报告建议「产品未发布可直删路由」，**经源码核实该建议不成立**：

- 前端**确实在调用**该端点：`src/api/dataSource.ts:108` 的 `getFailoverLogs(deviceId, limit)` →
  `client.get('/api/v1/devices/${deviceId}/failover-logs')`，且 `src/api/__tests__/api-wrappers.spec.ts:310` 有用例。
- 但该 wrapper **无视图级消费者**；进一步追查发现整个 `dataSourceApi`（`src/api/dataSource.ts`，113 行 / 10 方法 + 4 个 interface）
  **除自身测试外零消费者**（`grep -rn 'dataSourceApi' src --include=*.vue --include=*.ts` 仅命中 `api/__tests__/`）。
- 后端侧对应 `handler_data_source.go` 的 9 条 `/api/v1/data-sources*` 路由（CRUD + activate/deactivate/reset/health）
  与 `failover-logs` 占位端点，同样无前端 UI 消费。

即：这是与 vendor 体系同类的**「后端已建成、前端只有 API 客户端、没有页面」的半成品功能**（主备数据源/failover 设计）。
**正确处置是产品决策，不是单方面删代码**：要么补 UI 接入（让功能可见），要么整体下线（后端路由 + 模型 + 前端客户端 + 测试一次性清理）。
在决策前**保留现状**——避免后续批次误删导致前端 wrapper 变悬空。

## 三、接口契约（5.5）

### 3.1 响应方言实测分类（**修正 §一 的粗计数**：355 处按形态细分）
> 本节数据由主 Agent 用括号配平解析器逐处分类（非正则行匹配），口径比 §一 的粗略计数更准确。

| 形态 | 处数 | 与 envelope 的关系 | 改动性质 |
|---|---|---|---|
| **A. code 为数字**（`{code:N,...}`） | **230** | envelope 会补 `data`/`message` 字段 | **纯 additive，可机械替换**（JSON 消费者安全：多出字段不影响读取） |
| **B. code 为字符串**（`{"code":"AUTH_UNAVAILABLE"}`） | **3** | ⚠️ **与 `envelope.Code int` 不兼容**（类型冲突，机械替换会编译失败或丢语义） | 必须改用 `ErrorWithCode`（数字 code + `error_code` 字符串），见 `handler_auth.go:42/49/68` |
| **C1. `{"error": msg}`** | **81** | 字段名不同（`error` vs `message`）；envelope 还会补 `data:null` | **形状变更，需前端同批** |
| **C2. 裸对象无 envelope**（如 `c.JSON(201, node)`） | **35** | 完全不在 envelope 体系内 | **契约变更，必须前端同批**（前端当前直接读对象） |
| 合计 | 355 | （`envelope.go` 自身的 6 处已排除） | |

⚠️ **重要修正**：先前评估报告 §一 写的"238 处手搓 `{code,message}` 与 envelope 字节兼容，可零风险机械替换"是**不准确的**：正确的可机械替换范围是 **230 处数字 code**，且严格说是 *additive 兼容*（envelope 恒输出 `data` 与 `message`，而手搓方言常省略其一），并非字节相同。此外还有 **3 处字符串 code**（类型层面就装不进 `envelope.Code`）与 **116 处无 code 字段**（81 个 `{"error"}` + 35 个裸对象）需要前端协同。

→ P1.1 应按此分三批推进：**批次1** 230 处机械替换（后端单侧可完成）→ **批次2** 3 处字符串 code 改 `ErrorWithCode` → **批次3** 81+35 处与前端同批发布（需先确认前端对这 116 个端点的读取方式）。

## 六、架构设计（7.5）

### 6.1 分层与依赖方向（6/10）
- **无循环依赖**，且跨切面接线一律用函数/窄接口注入刻意避免成环：`main.go:212` `SetLatestSinkFn(api.SetLatestValue)`、`:236` `SetLatestValueFn(api.LatestValue)` 切断 nodemgr/automation→api 的反向依赖；`manager.go:106-130` setter 显式注释动机。**这一纪律是项目最被低估的资产。**
- **api 包三合一**：36 个非测试文件中 **25 个**直接持有 `*gorm.DB`，共 186 处 `db.*` 调用，绕过任何 service 层。对照 `commandexec`（Service 结构体 + 注入 db + `now` 函数字段）与 `datalifecycle` 的正确 service 形态。
- **`SetupRoutes` 用 variadic `interface{}` + 类型开关做 DI**（`routes.go:27-63`），源码注释自认"若用接口 case 会按序首个匹配，automation 永不到达"、"`commandService==nil` 时静默自建" —— 装配脆弱且失败静默。

### 6.2 并发与事务（7/10）
- **教科书级（勿动）**：`commandexec/service.go:448-530` Create 单事务写 execution+outbox+audit，幂等唯一索引兜底（`models/command_execution.go:25-26`），replay-before-gates 保证重试永不发第二条物理指令，Cancel 用 `FOR UPDATE`+RowsAffected CAS。
- **历史竞态已根治（亲验）**：`sender.go:408` `SendConfigManifestWithDecision` 的 "reconcile→快照→哈希→编码" 全流程在同一 REPEATABLE READ 事务内，MQTT publish 在 commit 之后，失败持久化带 `last_sync_id` 守卫。**上一轮路线图记录的"事务外 6 次 Find"在当前源码已不存在。**
- **遗留**：外设启停补偿写在事务外（`handler_periph.go:851-860`：先落 `enabled=false` → 停止命令失败 → 补偿写回 `true`；补偿再失败则 DB 与硬件状态相反）；batch-delete 逐条独立小事务且 HTTP 恒 200、无 `partial` 标志。
