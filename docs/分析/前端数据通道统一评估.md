# 前端数据通道统一性评估(F9)

> 对应《边缘设备修复优化方案-v2.md》F9 节(P2,仅设计不实现)。
> 评估基准:当前 main 分支源码(git f9cd79d 之后工作区)。
> 本文件为评估结论,不含任何代码改动。

## 1. 结论摘要

| 评估项 | 结论 |
|---|---|
| 三详情页数据链路收敛 | ✅ 已收敛(useDeviceData → edgeDeviceApi + useRealtimeData),无 setInterval 轮询 |
| `unifiedDataApi` 生产调用方 | ❌ **生产零调用**;且路径缺前缀、3/5 方法路由不存在,属**双重死代码**(未被用 + 用到也 404) |
| `channel_data` / `data_update` 双事件 | ⚠️ **载荷级重复**:后端同一条已解析采样同时广播两个事件,`data` 字段是同一个 map;前端默认双订阅导致同帧在 dataItems 重复计 2 条、messageCount 翻倍 |
| 建议动作 | 见 §6(全部为后续设计输入,本期不实现) |

## 2. REST 首屏链路盘点

### 2.1 三详情页实际使用的通道(现状,已验证)

- `GenericDeviceDetail.vue:78`、`BmsDetailPage.vue:208`、`InverterDetailPage.vue:186` 均经共享 composable `useDeviceData`(src/composables/useDeviceData.ts)。
- REST 首屏:
  - `useDeviceData.ts:82` → `edgeDeviceStore.fetchDetail(id, true)`(设备详情,含 `last_data`)
  - `useDeviceData.ts:109` → `edgeDeviceApi.getLatestData(id)` → `GET /api/v1/edge-devices/:id/latest-data`(edgeDevice.ts:202)
  - `:87-93` 合并 `device.last_data` 进 `latestData`,且不覆盖 WS 实时值("REST 首屏 + WS 增量合并防覆盖"实现存在)。
- WS 增量:经 `useRealtimeData`(`useDeviceData.ts:66`),默认订阅 `data_update` + `channel_data`。
- **三详情页均无 `setInterval` 轮询**(useDeviceData.ts 全文无计时器;仅 Dashboard.vue:578 的 30s trendRefreshTimer 属趋势图 REST 刷新,非详情页)。

### 2.2 `unifiedDataApi` 调用方盘点(grep 全 frontend-shared/src)

| 位置 | 性质 |
|---|---|
| `src/api/unifiedData.ts:47` | 定义本身 |
| `src/api/__tests__/api-wrappers.spec.ts:1079-1120` | 仅测试(5 个方法的包装级测试) |
| **生产代码(.ts/.vue)** | **零引用** |

即:F9 v2 修订中"grep 全 src 仅 api 定义与测试"的陈述**再次验证属实**。

### 2.3 `unifiedDataApi` 可达性检查(关键发现)

`unifiedData.ts` 的 5 个方法:路径全部缺 `/api/v1` 前缀,而后端路由全部挂在 v1 group;同源部署(`VITE_API_BASE_URL=''`,frontend-shared/.env:1)下请求将打向 `/unified-data/...` → 404。

| 方法 | 请求路径 | 后端路由(handler_data.go) | 响应形状一致性 |
|---|---|---|---|
| `query` | `/unified-data` | ❌ 无 | — |
| `getLatest` | `/unified-data/latest` | ❌ 无(仅 `/nodes/:id/latest` :74) | — |
| `getHistorical` | `/unified-data/historical` | ✅ :216 | ❌ 后端返回裸数组,前端期待 `{data:[]}` |
| `getAggregated` | `/unified-data/aggregated` | ❌ 无 | — |
| `getCategories` | `/unified-data/categories` | ✅ :187 | ❌ 后端返回裸数组 `[{code,unit}]`,前端期待 `{data:DataCategory[]}` |

另外 `UnifiedData` 接口字段(id/device_pk/source_id/category/value/unit/quality)与后端实际 JSON(sensor_name/device_id/timestamp/…)也不一致。

**结论:unifiedDataApi 是"未被使用 + 一旦使用必 404/解析错"的双重死代码。**

### 2.4 与 `edgeDeviceApi` 的关系

- `edgeDeviceApi.getLatestData` 是详情页真实 REST 首屏通道;
- `unifiedDataApi` 与 `edgeDeviceApi` **语义不同**:后者按 edge-device 主键取最新一帧,前者按 `device_pk` 查询历史分页/聚合。二者不是同一接口的两份实现,`unifiedDataApi` 不应"收敛到 edgeDeviceApi",而是应被"真实存在的历史数据通道"收编或删除(见 §6)。

## 3. 历史数据查询通道(与 F9 正交,顺带盘点)

生产代码中 `/unified-data/historical*` 的**真实调用方**全部是 inline `client.get('/api/v1/...')`,未走任何 API 封装:

| 位置 | 用途 |
|---|---|
| `src/composables/useHistoryData.ts:81,103` | 详情页历史图表(HistoryChartSection 依赖) |
| `src/views/dashboard/Dashboard.vue:368` | 首页趋势图 |
| `src/views/data/DataPanel.vue:380,401,519,554,746` | 数据面板历史/分类查询 |

这 7 处共享同一后端资源,但各自手写 `client.get` + 各自定义返回类型(MeasurementPoint/MeasurementBatch 等)——是**同一通道的 7 份重复客户端代码**,与详情页实时链路正交(历史≠实时)。这是比 unifiedDataApi 死代码更实际的双路径残留。

## 4. WS 双事件重复度评估

### 4.1 后端发布端(consumers_heavy.go,同一条已解析采样)

`SensorParserConsumer.Handle` 对**同一条解析结果**连续广播两个事件,且 `data` 字段是同一个 `dataMap`(consumers_heavy.go:333 与 :354):

- **channel_data**(consumers_heavy.go:318-337):`device_id / node_id / channel_id / raw_hex / timestamp(unix秒) / error_code / request_id / edge_device_id / command_index / data / sensor_device_id / sensor_device_name / sensor_type`
- **data_update**(consumers_heavy.go:343-355):`device_id / edge_device_id / device_name / collector_id / collector_name / node_id / channel_id / data(同一个 map) / collected_at(RFC3339)`

另有 consumers_light.go 的 `WSPushConsumer` 只发 `channel_data`(被动/未关联原始帧,无 data 解析),与上述不同源。

### 4.2 前端订阅端

| 订阅点 | 事件 | 入口 |
|---|---|---|
| `useRealtimeData.ts:155` 默认 `[DATA_UPDATE, CHANNEL_DATA]` | 双订阅 | 三详情页(经 useDeviceData) |
| `Dashboard.vue:567` | 仅 DATA_UPDATE | 手动订阅 |
| `DataPanel.vue:695` | 仅 DATA_UPDATE | 手动订阅 |
| `ChannelTerminal.vue:505` | 仅 CHANNEL_DATA | 手动订阅(终端,需要 raw_hex) |

### 4.3 重复度量化

- 详情页(含 `includeChannelData` 默认 true):同一条后端解析采样 → 前端收到 **2 条事件 → `handleMessage` 各生成 1 条 DataItem → dataItems 同帧重复 2 条,messageCount 每次 +2**。
- `handleMessage`(useRealtimeData.ts:119-150)对两类事件处理逻辑**完全相同**,仅 timestamp 来源略有差异:
  - channel_data 用 `p.timestamp`(unix 秒,须 ×1000 转 ISO);
  - data_update 用 `p.collected_at`(已是 RFC3339,且 `p.timestamp` 可能缺省 → 回退 `new Date().toISOString()`)。
- `latestData` 合并是幂等的(同字段覆盖),所以**指标卡不受影响**;受影响的是实时流列表(RealtimeDataList:同帧两条)、messageCount(统计翻倍)、以及前端 WS 带宽(每帧发 2 条)。

### 4.4 两事件信息量差(真正需要保留什么)

| 能力 | data_update | channel_data |
|---|---|---|
| 解析后的 `data` map | ✅ | ✅(同一份) |
| 服务端采集时间(RFC3339) | ✅ collected_at | ❌ 仅 unix 秒 |
| raw_hex / error_code / command_index / request_id | ❌ | ✅ |
| 设备/节点名 | ✅ | ✅(channel_data 也有 sensor_device_name/type) |

- 详情页实时数据流**只消费 `data` + 时间戳**(GenericDeviceDetail.vue:90 按 data 过滤;Bms/InverterDetail 图表与列表用 item.data),不消费 raw_hex/error_code/command_index。
- raw_hex/error_code 的真实消费方是 **ChannelTerminal.vue:505**(独立订阅,不经过 useRealtimeData)与 DataPanel 的错误码展示。

**结论:详情页通道中 channel_data 与 data_update 信息重复度 ≈ 100%(仅时间戳编码与附带元字段差异,而附带字段详情页并不消费)。双订阅在详情页是纯冗余。**

## 6. 结论与后续设计输入(本期不实现)

### 6.1 应删除:`unifiedDataApi`(src/api/unifiedData.ts 全文件)

依据:
- 生产零调用(§2.2);
- 实现即错:路径缺 `/api/v1` 前缀(同源 404),3/5 方法对应路由不存在,2/5 方法响应形状与后端不符(§2.3);
- 同步删除 `api-wrappers.spec.ts` 中对应 describe 块(1079-1120)。

风险:无(无生产引用,删后 `pnpm test:run` 过 + `grep unifiedDataApi` 为空即闭环)。

### 6.2 应保留并可选收编:历史数据通道(inline `client.get('/api/v1/unified-data/historical*')`)

- 7 处调用(§3)是真实消费者,**不能删**;
- 若要统一,正确做法不是"收到 edgeDeviceApi"(语义不同),而是**新建/复用一份 API 封装**(建议以真实存在的后端路由为准重写,如 `unifiedDataApi` 改名重写为带 `/api/v1` 前缀 + 只暴露 historical / historical-batch / categories 三方法,并让 useHistoryData / Dashboard / DataPanel 改用它),消掉 7 份重复的 client.get + 返回类型定义。
- 收益:单一客户端契约、测试可覆盖;成本:一处封装 + 7 处调用点替换。属 P3 清理项,与 F10 死代码清理同批。

### 6.3 应收敛:详情页双事件订阅(useRealtimeData 的 includeChannelData)

- 详情页(`useDeviceData` 调用处)应设 `includeChannelData: false`,只订阅 data_update——消除同帧重复 DataItem 与 messageCount 翻倍,前端每帧少收 1 条 WS;
- `channel_data` 保留给真实消费方(ChannelTerminal 的 raw_hex;如 DataPanel 需要错误码可继续独立订阅,或后端在 data_update 中补齐 error_code 后前端单订阅);
- 后端侧另一种收敛:consumers_heavy.go 合并为单事件(保留全部字段),则前端天然单订阅——**但这是后端协议行为变化,波及 Dashboard/DataPanel/ChannelTerminal 的既有字段解析,须单独评估**,本评估仅记录倾向:前端侧收敛(行为不变)优先,后端合并作为 P3 后续候选。

### 6.4 不建议动

- Dashboard.vue:567 / DataPanel.vue:695 的手动 `subscribe(DATA_UPDATE)`:各自有独立业务(趋势图 upsert、实时开关控制),强行收敛到 useRealtimeData 会引入开关语义损失,收益小,维持现状。

### 6.5 验收口径(若后续实施)

1. `grep -rn unifiedDataApi frontend-shared/src` 生产代码零命中;
2. 详情页经 CDP 观察 WS:每帧采样只收到 1 条 data_update,messageCount 与帧数一致;
3. `pnpm test:run` 全绿 + `pnpm typecheck` 零新增错误(删 unifiedDataApi 后同步删测试);
4. 历史图表(Dashboard 趋势 / 详情页历史 / DataPanel)回归无变化(§6.2 兜底项)。
