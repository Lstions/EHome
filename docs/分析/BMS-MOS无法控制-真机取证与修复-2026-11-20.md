## 0. 结论

| 编号 | 结论 | 等级 |
|---|---|---|
| **D1** | `set_mos_policy` 的读回在**写入后 100 ms** 就采样，而这台 BMS 收到 `0xE1` 软件关断后约 **1 s 内自行把 `fet_status` 恢复成 `0x03`**。于是命令被判 `SUCCEEDED`（假成功），用户却在页面上看到 MOS 仍然导通 ——「手动触发显示执行成功，但实际没有效果」的根因 | **P0 已修** |
| **D2** | 自动化事件在命令**刚提交**时就落 `result=executed`，此后命令进入终态（`FAILED`）**没有任何回填**，触发历史恒显示「已执行」，失败没有提示 | **P0 已修** |
| **D3** | 设备回退时会把 `protection_status` 的 bit12（`0x1000`）置位并保留；原失败文案只写「检查 protection_status 是否有硬件保护覆盖」，把人引向不存在的硬件保护 | **P1 已修** |
| **D4** | BMS 固件**有时会**在写入后约 1 s 自行恢复（13:10 充电中 +1.41A、14:02 各一次），**有时能保持**（14:16 空闲 I=0 时关闭成功并保持 ≥1 min）。分界条件尚未确证，最可能是「写入瞬间是否正在充电」；本仓能保证的是「成功即真实生效、失败即真实回退」，不再出现假成功 | **已如实化** |
| **D5** | 后端容器重启后，节点的能力快照（`resource_reported_at` / `command_engine_revision`）在 `Hello` 时被清空，只有收到 `ResourceReport` 才恢复；期间所有 bounded 动作都报 `action unavailable`，需要手动 `POST /api/v1/nodes/:id/query-resources`（自动化路径有自愈，手动路径没有） | 观察项 |

## 1. 证据链（真机原始字节，非推断）

### 1.1 一次「成功」的关闭命令实际上 1 秒后就回退

| 时刻(Z) | 事实 | 来源 |
|---|---|---|
| 13:10:05.98 | 下发 `set_mos_policy{charge_software_closed:true,priority:user}` | `command_executions` |
| 13:10:06.88 | 命令 `SUCCEEDED`，`verified_result.fet_status=2`、`protection_status=4096` | `command_executions.verified_result_json` |
| 13:10:06.986 | 周期 0x0F 帧 `fet_status=2` | 节点 `DataReport raw`（DEBUG 日志） |
| 13:10:07.942 | 同一帧结构 `fet_status=3`（**已自行恢复**） | 同上 |
| 13:10:49 起 | 之后每次关闭都 `readback mismatch: fet_status=0x03 charge bit=1 want 0` | 后端 WARN 日志 |

原始 `0x0F` 帧（ch10，13:30:44）：

```
dd0f0047 0013c5fd ae060274 268e1000 0c660c56 00000000 014d0303
0b530b45 0b59100c 5c0c5e0c 5f0c590c 5c0c590c 5c0c560c 5b0c560c
590c590c 5d0c5d0c 660c5f00 00000000 000000f3 3177
```

解码（与 `parse0x0F` 完全一致，说明解析偏移无误）：`total_voltage=5061(50.61V)`、`current=-594(-5.94A)`、`rsoc=6%`、`protection_status=0x1000`、`fet_status=data[22]=0x03`、`ntc=3`、`cell_count=0x10(16)`、16 节单体电压 `0x0C5C..0x0C5F`。

### 1.2 `protection_status` 的 0x1000 不是硬件保护

- 12 位保护位（bit0~bit11）在全程都是 0；`0x1000` 只在**软件关断请求**之后出现，`0xE1 XX=00`（释放）后立即消失（13:39:05 实测 `0x1000 → 0x0000`）。
- 对照：11-19 04:35~07:35 的 `fet_status=2` 是 BMS **自身单体过压保护**（`protection_status=0x0001`、充电电流 25A → 0A），与软件关断是两回事。

### 1.3 软件关断只改了标志位，充电电流没有停

13:10:06.986 同一帧里 `fet_status=2`（关断）与 `current=+1.41A`（仍在充电）同时成立 → 该固件把 `0xE1` 当作**瞬时动作**（JBDTools 手册原文亦称「此功能用来快速测试 MOS 管开关」），不是可保持的开关。

## 2. 修复

| # | 文件 | 改动 |
|---|---|---|
| 1 | `backend/internal/drivers/jiabaida_control.go` | `set_mos_policy` 计划：写入步 `PostTXDelayMS 100ms → 1200ms`（**稳定窗**），读回采的是 1.2 s 后的真实状态；回读不再可能把「1 s 后回退」判成成功 |
| 2 | 同上（verifier） | 失败文案重写：带 `fet_status`/两个 bit/`protection_status`，并明确区分「设备回退（0x1000 是软件锁定标志位）」与「可能有硬件/保护覆盖」 |
| 3 | `backend/internal/commandexec/automation_backfill.go`（新增） | 命令进入终态时回填 `automation_events`：`FAILED/UNKNOWN/CANCELLED → result=failed` + `detail` 带 `final_reason`；`SUCCEEDED → executed` + 成功说明；并广播 WS 事件 |
| 4 | `backend/internal/automation/planner.go`、`models/automation.go`、`simulation/catalog/audit.go` | 新增结果常量与白名单/映射同步 |
| 5 | `frontend-shared/src/views/automation/automationFormat.ts`、`AutomationRules.vue` | 「执行失败」中文标签 + 标签色 + 详情列展示失败原因 |

### 2.1 为什么稳定窗取 1200 ms

实测回退发生在写入后 **约 960 ms**（13:10:07.942 那一帧）；再叠加一个 0x0F 周期（1 s）与串口静默定帧（10 ms）的余量。取 1.2 s 后：真实生效的命令仍会在 ~1.4 s 内成功返回，回退的命令必然被判失败。

## 4. 仍未解决 / 建议

1. **设备会自行恢复软件关断**（D4，概率与触发条件待定）。当前对策是稳定窗 + 如实上报：规则执行失败会在触发历史显示「执行失败」并产生一条 error 级通知。若要提高「日落关充电」的成功率，建议在**充电电流为 0 的间隙**下发（例如把规则触发改为「日落 + 电池电流 ≤ 0」），或向嘉佰达确认该型号（软件版本 0x81）`0xE1` 的保持语义与是否需要「工厂模式」。
2. **手动路径缺少能力快照自愈**（D5）：建议把自动化 planner 的 `SendQueryResources` 自愈同样接到 `commandexec.Create/IssueConfirmation` 的 `ErrCapabilityStale` 分支，否则每次后端重启后第一次手动操作都会报 `action unavailable`。
3. 前端失败文案仍是通用句（后端详细原因目前只进日志）。若要页面直接显示「设备回退」这类原因，需要把 verifier 错误码落库（`command_executions.final_reason` 或 inbox payload）并在 UI 展开。
