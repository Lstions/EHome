# 创建规则四个问题的根因分析与解决方案（2026-11-14）

> **状态**: 已实施（2026-11-14，P0/P1/P2）
> **范围**: 自动化策略 → 创建规则向导（步骤状态、动作目录、BMS MOS、动作语义）
> **证据**: 运行中后端/前端实测 + 源码定位

## 一、结论摘要

| # | 现象 | 根因 | 解决方向 |
|---|---|---|---|
| 1 | 跳过第 1 步，第 1 步仍显示绿色 ✓ | 步骤完成态只按“当前步骤序号 > 步骤号”计算，与校验结果无关 | 步骤三态：完成/未完成（黄）/未开始；按校验结果与“是否到过”计算 |
| 2 | 动作全部显示“当前不可用”、风险原因不对 | 目录的 available 把“运行期可执行”当成“配置期可选”；UI 丢掉 reason；read 动作被驱动标成 medium → 触发确认，但没有 risk_reason | 拆分 configurable / runtime；设备级横幅代替逐项“不可用”；补 risk_reason；读动作移出自动化目录 |
| 3 | BMS 设置 MOS 交互复杂、要设优先级 | set_mos_policy 是底层双位写入，参数含 protocol priority；参数编辑还要再开一层弹窗 | 新增单 MOS 语义动作（关闭/打开充电 MOS、放电 MOS），读改写+读回；priority 默认/隐藏；布尔参数内联 |
| 4 | 动作列表里读取/写入没有意义 | 动作目录把驱动全部 28 个 ControlAction 都当自动化动作；没有“用途/暴露面”元数据 | 增加 Exposure（automation/diagnostic/configuration），自动化只取 method 动作 |

## 二、问题 1：跳过第一步却显示绿色

### 现象

创建规则后不填名称，直接点左侧第 2 步；第 1 步显示绿色 ✓，第 2 步高亮。此时名称必填未满足，第 1 步实际未完成。

### 根因（源码）

- 步骤栏完成态只由位置决定：
  - 类名：is-done = wizardStep > step.id
  - 图标：wizardStep > step.id ? '✓' : step.id
- goStep 允许跳到任意步骤，不记录“跳过了未完成的步骤”；
- 真正校验只在 goNext 与保存时发生，且没有回写步骤状态。

因此“是否完成”被错误地等同于“是否在当前步骤之前”，与表单有效性完全解耦。

### 方案

把步骤状态从二态（当前/完成）改为三态：

~~~text
active   当前步骤（蓝）
done     已完成：校验通过，且用户已离开过该步
warning  未完成：到过/被跳过且校验失败（黄 + !）
todo     未开始：未到过且无错误（灰 + 数字）
~~~

算法：

~~~ts
const stepErrors = computed(() => ({
  1: validateBasic(),
  2: validateTriggerType() ?? validateConditions(),
  3: validateActions() ?? validatePolicy(),
  4: null,
}))
const attempted = ref(new Set<number>())

function markSkipped(target: number) {
  for (let s = 1; s < target; s++) {
    if (stepErrors.value[s]) attempted.value.add(s)
  }
}
function goStep(target: number) {
  markSkipped(target)
  wizardStep.value = clamp(target)
}
function goNext() {
  const msg = validateStep(wizardStep.value)
  if (msg) { attempted.value.add(wizardStep.value); toast(msg); return }
  wizardStep.value++
}
~~~

- 绿色只在“该步校验通过且已离开”时出现；
- 第 1 步名称为空被跳过后显示黄色 !，补齐名称立即变绿；
- 保存仍走 firstInvalidStep 跳回；保存前把所有错误步骤标为 warning；
- 移动端进度条继续表示“当前位置”，但顶部文字可显示“步骤 2/4 · 第 1 步未完成”；
- 给步骤按钮补 aria-label（已完成/未完成/未开始）。

### 验收

- 空名称跳到第 2 步：第 1 步黄色 !；
- 补名称：变绿 ✓；
- 空动作跳到第 4 步：第 3 步黄色；
- 保存时自动跳到第一个黄色步骤；
- 既有 138 条自动化测试与新增 3~4 条步骤状态测试全绿。

## 三、问题 2：动作全部不可用、风险原因不对

### 2.1 “全部当前不可用”

实测：当前 BMS 节点在线时，GET /api/v1/edge-devices/1/actions 返回 28 个动作，available 全部为 true；截图状态与“节点离线时抓取目录”一致。

根因有两层：

1. Catalog 的 available 是“此刻能否执行”，门禁包含 node.Status == online、capability 新鲜度、manifest、channel 上报等运行期条件。节点离线 ⇒ 所有动作 available=false。
2. UI 把运行期不可用逐项写成“当前不可用”，且丢掉 reason；用户看到 28 条相同后缀，既不知道为什么，也无法配置规则。

这混淆了两个问题：

~~~text
配置期可选（这个动作是否属于该设备/是否启用/引擎是否支持）
运行期可执行（设备此刻在线、能力上报新鲜、指令通道可用）
~~~

规则创建属于配置期，不应因为设备临时离线而否定动作存在。

### 方案

后端 CatalogItem 增加三个字段（Create 仍用全门禁 fail-closed）：

~~~go
type CatalogItem struct {
  Definition   deviceaction.Definition
  Available    bool   // 运行期可执行（保持兼容）
  Reason       string
  ReasonCode   string
  Configurable bool   // 新增：配置期可选
  RuntimeReason string // 新增：运行期不可执行原因
  RuntimeReasonCode string
}
~~~

门禁分两类：

| 类别 | 门禁 |
|---|---|
| 配置期 | dispatchEnabled、actionEnabled、currentEngine、edgeEnabled、edgeStatus、edgeNodeID、actionChannel |
| 运行期 | nodeStatus、reportedActionChannel、appliedManifest、currentCapabilities、definitionFitsCapabilities |

- Configurable = 配置期门禁全部通过；
- Available = 全部通过（兼容旧调用）；
- 配置期失败：逐项标“不可用 + 具体原因”；
- 仅运行期失败：动作照常列出、可选中、可保存；页面顶部一条设备级横幅：
  “设备当前离线 / 能力上报过期：规则可以保存，执行时由后端做最终判定”；
- 选项后缀只用于配置期失败（如“驱动未启用”），运行期失败不再逐项重复。

前端改动：

- actionOptions 返回 configurable / runtimeReason；
- catalogAllUnavailable 改为“配置期全部不可用”；
- 新增 catalogRuntimeUnavailable(action) → 渲染一条横幅；
- 选项文案：不可用时追加“· 原因”，而不是固定“当前不可用”。

### 2.2 风险原因不对

实测同一份目录：

- read_basic_info / read_cell_voltage：requires_confirmation=false；
- read_sn / read_protection_parameters / read_system_parameters：risk=medium → RiskLevel=elevated → requires_confirmation=true；
- 所有风险动作都没有 risk_reason；前端只能显示“⚠ 风险”。

根因：

- 驱动的 Risk 是 4 级方言（low/medium/high/critical），medium 被归一化为 elevated（需要确认）；
- 对“只读但会进工厂模式”的动作，medium 在语义上可以成立，但没有给出原因；
- 前端 ActionCards 的注释也承认“后端 risk_reason 尚未实现”，只能显示光秃秃的“风险”。

### 方案

1. ControlAction / Definition 增加 risk_reason（必填校验：risk 为 high/critical 时必须提供）；
2. 为 BMS 方法动作补原因：
   - set_mos_policy / 单 MOS：直接控制充放电回路，误操作会断电或过流；
   - bms_restart：设备会重启并短暂离线；
   - clear_alarm：清除告警历史状态；
   - test_*_mos：强制切换 MOS，需负载配合；
   - 工厂模式读：会短暂进入工厂模式，采集可能中断。
3. 前端选项与卡片展示“⚠ 风险：<原因>”；风险确认弹窗也用同一文案；
4. 读动作移出自动化目录（见问题 4）后，普通读取不再出现在规则里；设备详情页仍可看到，并显示原因。

## 四、问题 3：BMS 设置 MOS 太复杂

### 根因

set_mos_policy 是底层协议动作：

~~~go
Parameters: charge_software_closed(bool), discharge_software_closed(bool), priority(enum user/operator)
~~~

- 两个位必须同时提交，用户很难理解“我只想关充电 MOS，放电怎么办”；
- priority 是协议层 user/operator，不是业务概念；
- 参数编辑还要从动作卡片再开“编辑参数”弹窗（二层交互），表单里三个字段都要填。

### 方案（推荐）

新增两个单 MOS 语义动作，把复杂度收回后端：

| 动作 ID | 参数 | 物理执行 |
|---|---|---|
| set_charge_mos | closed: boolean | 读 fet_status → 保留放电位、只改充电位 → 写 E1 → 读回对账 |
| set_discharge_mos | closed: boolean | 同上，只改放电位 |

- 驱动实现 read-modify-write（bounded_sequence，3 步），优先级固定 user（或后端内部处理），UI 不出现 priority；
- 自动化目录只暴露这两个方法动作；set_mos_policy 降级为“高级/手动”动作（设备详情页可继续用）；
- 动作卡片对单布尔参数内联渲染开关/两个按钮（关闭充电 MOS / 打开充电 MOS），不再开参数弹窗；
- 风险高，risk_reason 明确；
- 既有规则若已使用 set_mos_policy：编辑时保留原动作并提示“高级动作”，不静默迁移；新规则不展示。

若暂不做驱动 RMW，退而求其次的短期方案：

- 仍用 set_mos_policy，但表单默认 priority=user 并隐藏，只显示两个布尔；
- 明确提示“两个位会一起写入”，避免用户误以为只改一个；
- 该方案不能解决“只想改一个 MOS”的语义问题，不建议长期保留。

## 五、问题 4：动作列表混入读取/写入

### 根因

- ControlAction 没有“用途/暴露面”字段；
- Catalog 返回驱动声明的全部动作（BMS 28 条），自动化前端全部展示；
- read_*、write_* 是诊断/参数配置能力，不是可编排的方法。

### 方案

增加动作暴露面元数据（后端为权威，前端不靠 ID 前缀猜）：

~~~go
type Exposure string // automation | diagnostic | configuration

type ControlAction struct {
  ...
  Exposure Exposure
}
~~~

- 自动化接口：GET /edge-devices/:id/actions?purpose=automation
  - 只返回 Exposure=automation；
- 设备详情/手动控制：默认返回全部（或 purpose=manual）；
- BMS 分类建议：

| Exposure | 动作 |
|---|---|
| automation | set_mos_policy（或新单 MOS）、test_charge_mos、test_discharge_mos、bms_restart、force_balance、find_car、clear_alarm、auto_test_edv、set_charge_time_window、set_discharge_time_limit、set_report_interval、set_static_correction_time |
| diagnostic | read_basic_info、read_cell_voltage、read_hardware_version、read_comprehensive、read_protection_count、read_protection_parameters、read_system_parameters、read_sn、read_test_mos_status、read_custom_attributes、read_internal_resistance |
| configuration | write_custom_attributes、write_internal_resistance、write_protection_parameters、write_system_parameters、write_sn |

- 缺省规则：read_* → diagnostic，write_* → configuration，其余 → automation（仅作为兼容兜底，驱动应显式声明）；
- 既有规则引用了非 automation 动作时：编辑页保留原值 + 黄字“该动作已不在自动化目录，保存时由后端校验”，不静默清空。

### 验收

- BMS 新建规则的动作下拉只剩方法动作（约 8~12 条），无 read_*/write_*；
- 设备详情页仍能看到并执行诊断/配置动作（权限允许时）；
- 既有规则不丢动作。

## 六、统一动作元数据（一次改，四处受益）

建议一次性补齐以下字段，避免每个问题各自打补丁：

| 字段 | 所属 | 用途 |
|---|---|---|
| Exposure | ControlAction / Definition | 自动化 vs 诊断 vs 配置 |
| RiskReason | ControlAction / Definition | 风险原因，替代光秃秃的“风险” |
| Configurable | CatalogItem | 配置期可选 |
| RuntimeReason / Code | CatalogItem | 运行期不可执行原因（设备离线等） |
| Presets（可选） | Definition | 单 MOS 这类一键预设，前端渲染按钮 |

前端只消费元数据，不再写死 BMS 动作 ID 或“读取/写入”正则。

## 七、分阶段实施计划

### P0（1~2 天，前端为主）

1. 步骤三态 + 跳过标记（问题 1）；
2. 动作下拉显示具体 reason；运行期不可用改为设备级横幅（问题 2.1 的 UI 部分）；
3. 风险徽标/选项显示 risk_reason；后端补字段前先用动作名映射兜底（问题 2.2 的 UI 部分）；
4. 自动化目录前端过滤 read_*/write_*（临时规则，P1 换后端权威过滤）。

### P1（2~3 天，后端元数据）

1. ControlAction/Definition 增加 Exposure、RiskReason；
2. CatalogItem 增加 Configurable、RuntimeReason/Code，拆分门禁；
3. /actions?purpose=automation 过滤；
4. BMS 驱动补 Exposure 与 RiskReason，补单测/快照；
5. 前端切换到后端元数据，去掉临时过滤。

### P2（3~5 天，MOS 语义）

1. 驱动实现 set_charge_mos / set_discharge_mos（RMW + 读回）；
2. 自动化目录隐藏 set_mos_policy（保留手动/高级）；
3. 动作卡片布尔参数内联，隐藏 priority；
4. 既有规则兼容提示；
5. 仿真/集成测试：MOS 关闭→读回、打开→读回、只改一个位不影响另一个位。

### P3（1 天）

1. 更新设计文档、验证记录、动作目录说明；
2. 回归：创建/编辑规则、预检、风险确认、执行事件；
3. Playwright 双端走完整流程（含离线设备配置）。

## 九、需要产品确认的两个点

1. **自动化动作边界**：是否同意“只暴露方法动作”，把诊断/参数配置留在设备详情页？
2. **MOS 单 bit 语义**：是否接受后端做 read-modify-write（推荐），还是短期接受“两个位一起写”的显式提示？

## 十、实施结果（2026-11-14）

### 10.1 步骤状态

- AutomationRules.vue 增加 attemptedSteps 与 stepValidity，步骤四态：active/done/warning/todo；
- 跳过未完成步骤显示黄色 !，补齐后立即转绿；保存前标记所有错误步骤并跳回第一个；
- 新增 2 条单测（跳过第 1 步、跳过第 3 步）。

### 10.2 动作元数据与目录

- ControlAction / Definition 增加 Exposure、RiskReason、Presets；
- deviceaction.Register 缺省推导 Exposure：read → diagnostic、write_* → configuration、其余 → automation；
- commandexec.Catalog 增加 Configurable / RuntimeReason / RuntimeReasonCode：
  - 配置期门禁：dispatch/actionEnabled/currentEngine/edgeEnabled/edgeStatus/edgeNodeID/actionChannel；
  - 运行期门禁：nodeStatus/reportedActionChannel/appliedManifest/currentCapabilities/definitionFits；
  - 设备离线时 Configurable=true、Available=false、RuntimeReasonCode=node_offline；
- GET /edge-devices/:id/actions 增加 purpose 过滤（automation/diagnostic/configuration）；
- 规则向导只请求 purpose=automation；BMS 28 个动作过滤后剩 10 个方法动作，read_*/write_* 不再出现；0x0C 产测命令 test_charge_mos/test_discharge_mos 归为 diagnostic（只留设备详情/手动控制）；
- 选项标签显示 risk_reason，不再只有"⚠ 风险"；运行期不可用改为设备级横幅。

### 10.3 BMS MOS

- set_mos_policy 增加 4 个 Presets（充电/放电 × 开/关），params 固定 priority=user；
- 规则向导选中带预设的动作不再自动弹参数表单；预设按钮内联在动作卡片；
- 预设写入普通 action_params_json，落库形态不变；
- 保留 set_mos_policy 的"编辑参数"高级入口（仍含 priority），但默认路径不再要求用户面对协议字段。

### 10.4 兼容与边界

- 旧后端无 Configurable 时前端按 Available 兜底，避免把"全部不可用"误判成"可配置"；
- 既有规则使用的动作即使不在 automation 目录中，编辑时也不清空，保存交给后端校验；
- MOS 预设仍是"协议一次写两位"的显式语义：标签写明同时将另一 MOS 置为导通；
  未实现单 bit read-modify-write（需要驱动新增 read→write→readback 的动态计划，列为后续项）。
