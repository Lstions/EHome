## 0. 结论摘要

1. **可行，但不是"所有规则都能给出一个时间"** —— 必须按触发器分类回答，否则就会给出骗人的数字：

   | 触发器 | 能否给出"下次执行时间" | 依据 | 精度 |
   |---|---|---|---|
   | `sun_event` | **能**，确定性计算 | 同一份 `sun.SunEvent` 纯函数 + 规则时区 | 秒级（实测与事件表差 4 秒） |
   | `time_window` | **能**（enter / exit / inside） | 窗口边界是固定钟面时刻 | 秒级，但基准是**后端进程时区** |
   | `sensor_threshold` | **不能** | 由设备上报数据决定，无时间语义 | 只能显示"等待数据满足条件" |
   | `event` | 不能 | 本期未实现（`models/automation.go:22` 占位） | — |

2. **推荐做法：后端在 `GET /automation-rules`（及详情）响应里现算并附加只读字段 `next_run`** —— 不落库、不新增 ticker、不做写放大。成本是 O(规则数) 次纯函数 + 1 条 `GROUP BY` 查询。
3. **本方案最大的风险不是算法，而是"预测与执行的状态必须同源"**：求值器有 3 份内存态（`sunStates` / `windowStates` / `triggered`），其中 `sunStates` 会在**规则字段被编辑时被清空**（`evaluator.go:387-391`）。若用数据库列反推，必然出现"页面说今天还会执行，实际今天已被判为错过"这类反向错误（2026-11-17 起 `sun_event` 不再补发，见 §2 补充事实第 3 条）。
4. **前端不要加第 8 列**：现有桌面表 7 列最小宽度合计已 970px（`RuleListSection.vue:18-87`），再加 130px 会把固定在右侧的「操作」列挤出可视区。应把时间放在「触发器」单元格第二行 + 窄屏卡片新增一行。

## 1. 需求边界：什么叫"下次执行时间"

必须先钉死语义，否则实现会各说各话。本文采用的定义：

> **该规则下一次"可能真正触发"的绝对时刻**（不含此时刻是否会被 gate 拦截的执行结果）。

三个必须排除的干扰项：

- **不是"下次评估时刻"**：求值器每 30s / 60s 都在评估，那没有产品意义。
- **不是"下次一定执行"**：`require_confirmed=true` 的规则触发后只是落 `pending_confirm`（`planner.go:204-213`），真正下发要人工确认。界面文案应标「需确认」。
- **要包含阻塞顺延**：冷却（`cooldown_sec`）与日熔断（`max_daily_exec`）会把"计划时刻"推到更晚。例如事件表里那条 `2026/11/17 22:15:12 关闭BMS充电 / 冷却抑制 / cooldown active (15s remaining)` 就是冷却顺延的真实表现。

## 2. 现状盘点：时间从哪来、状态在哪

| 触发器 | 求值入口 | tick 周期 | 时间基准 | 关键状态载体 | 可预测 |
|---|---|---|---|---|---|
| `sensor_threshold` | `evaluator.go:883` `Evaluate()` | 帧驱动（设备上报即评估） | 帧时间戳 | `windows`（滑动窗口）、`triggered`（冷却） | ❌ |
| `time_window` | `evaluator.go:785` `evalWindowRule()` | 1 min（`evaluator.go:558`） | `time.Now()` → **进程时区** | `windowStates`、`triggered` | ✅ |
| `sun_event` | `evaluator.go:642` `evalSunEventRule()` | 1 min（复用同一个 ticker） | 规则时区（`rule.timezone`） | `sunStates`（本地日期）、`triggered`、`sunCache` | ✅ |
| `event` | — | — | — | — | ❌ 未实现 |

补充事实（决定实现方式）：

- **`sun_event` 的触发时刻是纯函数**：`fireAt = SunEvent(lat, lon, tz, 本地日, kind) + offset_min`（`evaluator.go:657-675`）。`sun.Cache.Lookup` 未命中时会**顺带预计算次日**（`sun/cache.go:109-128`），所以"今天/明天两个候选"天然是热的。
- **每规则每日只触发一次**：由 `sunStates[ruleID] = 本地日期` 保证（`evaluator.go:690, 722`）。
- **不补发（边沿判定）**：触发条件是 `prevTick < fireAt <= now`（`evaluator.go` 的 `lastClockTick` + `evalSunEventRule`）。事件早被上一轮 tick 越过就**不触发**、只把该日标记为已处理——这条覆盖**进程重启 / 规则新建 / 停用后重新启用 / 编辑白名单字段**四种状态丢失（2026-11-17 用户裁决）。它直接决定"事件已过但今天还没触发"的预测该给明天还是"马上"。
- **编辑会清状态**：`sunStates` / `windowStates` 在 `sameWindowStateFields` 不相等时被删除（`evaluator.go:381-391, 475-486`），字段白名单含 `trigger_sun_kind` / `trigger_sun_offset_min` / `latitude` / `longitude` / `timezone` / `enabled`。
- **冷却锚点已持久化**：`automation_rules.last_triggered_at`（`models/automation.go:311`），自动路径（`planner.go:559`）、手动路径（`planner.go:1376-1377`）、确认路径（`planner.go:1522-1523`）都写；启动时由 `rebuildCooldowns` 回填内存（`evaluator.go:223-233`）。
- **日熔断按进程时区的 00:00 切日**：`planner.go:189` `dayStart := time.Date(at.Year(), at.Month(), at.Day(), 0,0,0,0, at.Location())`，统计口径是 `result='executed'` 的当日行数（`planner.go:187-202`）。

## 3. 实测证据：下一时刻可以从同一纯函数直接算出

截图的触发历史里有一条：`关闭BMS充电`（日落 · 正点）在 **`2026/11/17 22:14:57`** 落 `executed`，`event_at = 2026/11/17 17:41:54`（该列口径就是 `fireAt`，见 `planner.go:869` 与 `planner_event_at_test.go`）。**这两个时刻不相等本身就是缺陷证据**：规则在事件之后才进入求值集合，旧实现按电平判定把 4.5 小时前的日落补发了一次（详见 `docs/分析/自动化策略-补发机制与冷却吞触发-2026-11-17.md`），2026-11-17 已改为边沿判定、不再补发。

用仓库内 `backend/internal/sun` 的实现，对多个候选城市在 `Asia/Shanghai` 下实算 2026-11-17 日落：

| 城市 | 坐标 | 日落 |
|---|---|---|
| 上海 | 31.2304, 121.4737 | 16:54:57 |
| 北京 | 39.9042, 116.4074 | 16:57:02 |
| 武汉 | 30.5928, 114.3055 | 17:24:48 |
| 西安 | 34.3416, 108.9398 | 17:39:01 |
| **广州** | **23.1291, 113.2644** | **17:41:50** |
| 深圳 | 22.5431, 114.0579 | 17:39:36 |
| 成都 | 30.5728, 104.0668 | 18:05:47 |

广州实算 `17:41:50` 与库里 `17:41:54` 相差 4 秒（差异来自落库坐标的取点精度，不是算法误差）。广州同月相邻日：

```
2026-11-17  日出 06:41:33  日落 17:41:50
2026-11-18  日出 06:42:13  日落 17:41:35   ← 次日
2026-11-19  日出 06:42:53  日落 17:41:21
2027-06-21  日出 05:41:52  日落 19:15:25
```

极昼/极夜分支也已验证可显式区分，不会返回零值冒充结果：

```
Tromso(69.65N, Asia/Shanghai tz) 2026-12-21 sunrise → status=always_down, time=零值
Tromso(69.65N, Asia/Shanghai tz) 2026-06-21 sunset  → status=always_up,   time=零值
```

**结论**：不需要"观测历史再外推"，下次执行时间是可确定复现的计算结果。截图里那两条规则在 2026-11-17 22:19 这个时刻的正确显示应该是：

| 规则 | 触发器 | 下次执行 |
|---|---|---|
| 关闭BMS充电 | 日落 正点 | `2026-11-18 17:41`（今日已过） |
| 打开BMS充电 | 日出 正点 | `2026-11-18 06:42`（今日已过） |

## 4. 三个必须先裁决的问题

### 4.1 状态同源：不能用数据库列反推

天真的实现是"读 `last_triggered_at`，同日即视为今日已触发"。它在下面三个场景全错：

1. **刚新建 / 刚改过规则**：`sunStates` 被 `sameWindowStateFields` 清空（`evaluator.go:387-391`）。2026-11-17 起不补发 ⇒ 求值器今天已经不会再触发；但库里要么没有锚点（新规则）、要么锚点就是今天（编辑前已触发），两者都无法表达"本日已被判为错过"。只有内存态知道，预测必须读它才能给出"次日"。
2. **频繁重启**：`sunStates` 重启清空 + 首个 tick 不补发（`prevTick` 为空）⇒ 反推得到"今天还会触发"，实际今天已被标记处理。
3. **手动触发**：`TriggerRule` 只写 `last_triggered_at`（`planner.go:1376`），**不更新** `evaluator.triggered` 内存态 ⇒ 反推说"冷却中"，求值器却认为已 armed。

**裁决建议**：预测函数放进 `automation` 包、以 `*Evaluator` 方法形式实现，直接读同一把锁下的内存态；`last_triggered_at` 只作为"重启后内存态尚未建立"时的兜底，取两者中更晚者（`max`）。这与 `rebuildCooldowns` 的既有设计一致。

### 4.2 `time_window` 的时区口径（本次显示会立刻暴露的既有缺陷）

- `isInWindow` 构造边界用 `now.Location()`（`evaluator.go:859-861`），即**后端进程时区**；
- `time_window` 规则在三列坐标/时区上是**允许为空**的（只有 `sun_event` 强制，见 `handler_automation.go:1143-1187`），表单里时间窗口也没有时区选择（`TriggerFields.vue:143-184`）；
- 但 `docker-compose.yml` / `Dockerfile` **都没有设置 `TZ`**，运行镜像是 alpine（`Dockerfile:51` 只装了 tzdata）⇒ 容器内 `time.Local` 默认是 **UTC**，与设计文档写的"默认 Asia/Shanghai，与部署环境一致"（`docs/设计/自动化策略引擎方案.md:179`）不一致。

**后果**：一条 `08:00-18:00` 的时间窗口规则，在东八区用户看来的实际生效区间可能是 16:00–次日 02:00。**这是既有缺陷，只要把"下次 08:00"显示出来就会被用户第一时间发现。**

**裁决建议（二选一）**：
- **A（推荐，先做）**：预测严格与执行同口径（进程时区），并在 `next_run.timezone` 里回传进程时区名，前端按该时区格式化。行为零变更，先让数字正确可信。
- **B（另立一项）**：把 `time_window` 改成用规则时区（三列对 `time_window` 变必填 + 存量规则迁移 + 表单补位置选择器）。属行为变更，不应塞进本次显示需求里。

### 4.3 `sensor_threshold` 不能给时间

数据驱动触发器没有时间语义。可选的两条错误做法都不能做：

- 编一个"预估时间"（伪科学）；
- 显示求值器 tick 间隔（"30 秒后"）—— 那是评估时刻，不是执行时刻。

**正确做法**：状态 `waiting_data`，文案「等待数据满足条件」；若当前正处于冷却期，附带 `cooldown_until` 供提示「冷却中，最早 HH:MM 可再次触发」。

## 5. 方案设计

### 5.1 总体

```
请求 GET /api/v1/automation-rules
   │
   ├─ handler: db.Find(&rules) + database.AttachRuleActions   （既有）
   │
   └─ automation.(*Evaluator).NextRuns(rules, now)            （新增，只读）
          ├─ 1 次 GROUP BY 查当日 executed 计数（日熔断）
          ├─ 每规则：按 trigger_type 分派 → 纯计算
          │     sun_event    → sun.Cache.Lookup(今日/次日) + offset
          │     time_window  → 窗口边界推算（进程时区）
          │     sensor_thr.  → waiting_data
          └─ 读内存态：sunStates / windowStates / triggered（同一把 RLock）
   │
   └─ 响应每条规则附加 next_run
```

不落库、不加列、不加 ticker。理由见 §7 备选对比。

### 5.2 数据契约

```json
{
  "id": 2,
  "name": "关闭BMS充电",
  "trigger_type": "sun_event",
  "trigger_sun_kind": "sunset",
  "next_run": {
    "status": "scheduled",
    "at": "2026-11-18T17:41:35+08:00",
    "timezone": "Asia/Shanghai",
    "basis": "sun",
    "detail": "日落 17:41 + 0 分",
    "computed_at": "2026-11-17T22:19:23+08:00"
  }
}
```

`status` 枚举（与前端 union 三向同步，参照既有 `AutomationEventResult` 的 F-8 门禁做法）：

| status | 含义 | `at` |
|---|---|---|
| `scheduled` | 有确定的下次时刻 | 非空 |
| `waiting_data` | 数据驱动，无法预测 | 可空（仅冷却期有值） |
| `no_event` | 极昼/极夜，本日无该事件 | 空 |
| `disabled` | 规则停用 | 空 |
| `unsupported` | `event` 类型（未实现） | 空 |
| `unavailable` | 坐标/时区解析失败或配置非法 | 空 |

`basis` ∈ `sun | window | cooldown | daily_limit`，用于前端区分"计划时刻"与"被顺延"。当发生顺延时，`at` 取顺延后的时刻并把原因写进 `detail`（例：`"冷却中，顺延 25s"`）。

契约要点：
- `at` 一律 RFC3339 **带偏移**，禁止返回无时区的裸时间；
- `computed_at` 必带 —— 前端据此判断陈旧（页面停留期间 `at` 会过去）；
- `status` 为 `scheduled` 时才允许 `at` 非空，其余状态 `at` 为空（避免出现"停用规则也有下次时间"的荒谬展示）。

### 5.3 各类型算法

**公共前置**：

```
if !rule.Enabled                 → disabled
if trigger_type == "event"       → unsupported
cooldownUntil = lastTriggeredAt + cooldown_sec      （cooldown_sec < 0 视为 0）
dailyBlocked  = max_daily_exec > 0 && 当日 executed 计数 >= max_daily_exec
dailyResetAt  = 次日 00:00（进程时区）
blockedUntil  = max(cooldownUntil, dailyResetAt if dailyBlocked)
```

**A. `sun_event`**

```
loc, err = LoadLocation(rule.timezone)          → err: unavailable
eventToday, st = sun.Lookup(lat, lon, loc, now, kind)
if st != ok                                     → no_event
fireToday = eventToday + offset_min
if sunStates[rule.ID] == 今日本地日             → 候选 = 次日 fireAt
else if now < fireToday                         → 候选 = fireToday
else                                            → 候选 = 次日 fireAt   // 已过且未触发 = 不补发（2026-11-17 裁决）
at = max(候选, blockedUntil)
```

> 注：`now >= fireToday` 且当日未触发时，**只有**事件正好落在上一轮 tick 与现在之间（`lastClockTick < fireToday`，即规则刚进入缓存）时，下一个 tick 才会真的把它当作跨越触发；此时返回 `scheduled` + `at = now + 1min`。其余情况一律次日——2026-11-17 起不补发，"已过且未触发"不再是"马上会执行"。实现见 `nextrun.go` 的 `case !st.clockTick.IsZero() && fireToday.After(st.clockTick)`。

**B. `time_window`**（`start==end` 视为全天窗口，`evaluator.go:863-866`）

| edge | 候选时刻 |
|---|---|
| `enter` | 严格晚于 `now` 的下一个 `start` 钟面时刻（今日未到取今日，否则明日） |
| `exit` | 严格晚于 `now` 的下一个 `end` 钟面时刻 |
| `inside` | 当前在窗内：`now + max(cooldown_sec, tick=60s)`；不在窗内：下一个 `start` |
| `start==end` | `enter`/`exit` 不再发生 → `at` 空 + `detail="全天窗口"`；`inside` 按冷却周期 |

跨零点窗口（`start > end`）不需要特殊处理：上面"下一个边界"的自然语言定义本身已覆盖（如 22:00–06:00 在 03:00 时，下一个 `start` = 今日 22:00，下一个 `end` = 今日 06:00）。

**C. `sensor_threshold`**

```
status = waiting_data
at     = blockedUntil（仅当 now < blockedUntil，否则空）
detail = "等待数据满足条件"（冷却中追加剩余时间）
```

### 5.4 计算位置与并发

- 放在 `backend/internal/automation/nextrun.go`，方法签名 `func (e *Evaluator) NextRuns(rules []models.AutomationRule, now time.Time) map[uint]models.NextRun`。
- 读内存态统一在一把 `RLock` 内**快照**后释放，再算（`sun.Cache` 自身有锁，纯函数无 I/O，不要在锁内做 DB）。
- `api` 侧用**可选接口断言**接入，避免改动既有 `automationEvaluator` 接口而牵连 `fakeEvaluator` 等测试替身：

```go
type automationNextRunner interface {
    NextRuns([]models.AutomationRule, time.Time) map[uint]models.NextRun
}
if nr, ok := evaluator.(automationNextRunner); ok && nr != nil {
    for i := range items {
        if v, hit := m[items[i].ID]; hit { items[i].NextRun = &v }
    }
}
```

- `models` 侧新增字段（与 `Actions` 同一模式，见 `models/automation.go:313-319`），**不得落库**：

```go
NextRun *NextRun `gorm:"-" json:"next_run,omitempty"`
```

### 5.5 成本

| 项 | 量级 |
|---|---|
| 天文计算 | 每 (lat,lon,tz,日期,kind) 组合 1 次，`sun.Cache` 命中后 0 次；典型部署 < 10 次纯函数 |
| 窗口推算 | 每规则 O(1)，无 I/O |
| 日熔断 | **1 条** `GROUP BY rule_id` 查询（不是 N+1） |
| 内存 | `sun.Cache` 保留 today+tomorrow（`cache.go:148-152`），不因本功能增长 |

列表接口本身无分页（`handler_automation.go:206` `Order("id DESC").Find`），规则量在百级以内，实测应在毫秒级。

## 6. 前端改动

### 6.1 展示位置：不加第 8 列

现有桌面表 7 列最小宽度：140 + 180 + 180 + 120 + 90 + 80 + 180 = **970px**，而截图视口下表格实际渲染宽度约 1230px；再加一列 130px 会触发表格横向滚动，并让 `fixed="right"` 的「操作」列压住相邻列（`RuleListSection.vue:67-78` 记录过同类事故）。

**推荐**：放在「触发器」单元格第二行（桌面）+ 窄屏卡片 `<dl class="rule-card__meta">` 新增一项「下次执行」。

```html
<!-- RuleListSection.vue 触发器列内 -->
<div class="trigger-cell">
  <el-tag size="small">{{ triggerTypeText(row.trigger_type) }}</el-tag>
  <span class="mono trigger-summary">{{ triggerSummary(asRule(row)) }}</span>
  <span class="next-run" data-test="rule-next-run">{{ nextRunText(asRule(row), now) }}</span>
</div>
```

### 6.2 纯函数（`automationFormat.ts`，与 `triggerSummary` 同处）

```ts
export function nextRunText(rule: AutomationRule, now: number): { text: string; tone: 'ok'|'muted'|'warn' }
```

- `scheduled` 且 `at - now > 0`：`"今天 17:41"` / `"明天 06:42"` / `"11-20 17:41"`；`require_confirmed` 追加 `"（需确认）"`。
- `scheduled` 且 `at <= now`（页面停留导致过期）：`"即将触发"` + 触发一次 `fetchRules` 刷新。
- `waiting_data` / `no_event` / `disabled` / `unsupported` / `unavailable`：对应灰字文案，**不显示时间**。

### 6.3 时效性

不要在页面上持续轮询列表。做法：

1. 页面持有 `now` ref，`setInterval` 30s 更新（页面隐藏时暂停，`document.visibilitychange`）；
2. 文本由 `now` 驱动重算；
3. 检测到任一 `at <= now` 时，延时 90s 触发一次 `fetchRules`（给求值器一个 tick 落事件的时间）。

### 6.4 契约同步

`frontend-shared/src/api/automation.ts` 增加 `NextRunStatus` union + `NextRun` interface + `AutomationRule.next_run?`。按既有 `AutomationEventResult` 的 F-8 门禁（`automationFormat.ts:53-61`）思路补测试：**后端常量、前端 union、文案映射三处必须同时齐全**。

## 7. 备选方案对比

| 方案 | 做法 | 优点 | 致命缺点 | 结论 |
|---|---|---|---|---|
| **A（推荐）** | 列表/详情接口现算附加 | 永远新鲜、零写放大、状态同源、易回滚 | 每次请求一点 CPU（毫秒级） | ✅ |
| B | 新增 `automation_rules.next_run_at` 列，ticker 每分钟刷新 | 查询零成本 | **写放大**（每分钟写全部规则，`UpdatedAt` 抖动会打穿 `LoadRules` 的字段比对设计，见 `evaluator.go:366-368` 的 A-17 教训）；且两次 tick 之间仍是过期值 | ❌ |
| C | 前端自己算 | 后端零改动 | 需在浏览器复刻 NOAA 算法 + IANA 时区 + 冷却/熔断状态；与现实必然漂移 | ❌ |
| D | 展示"上次执行 + 周期"让用户自己推 | 极简 | 日出日落时刻每天变（实测相邻日差 15 秒，季节差 2 小时），用户推不出来 | ❌ |

方案 B 的隐藏坑值得单独记一句：它会让每条规则每分钟 `UPDATE` 一次，而 `LoadRules` 每 30s 重载规则并做字段比对（`evaluator.go:369-391`），`UpdatedAt` 的抖动会把"干净重载"变成"每 30s 清一次边沿状态"，正是 A-17 记录过的事故形态。

## 9. 风险与开放问题（需裁决）

1. **【需裁决】`time_window` 时区口径**（§4.2）。建议本次选 A（与执行同口径），另立一项修 B。若选 A，界面上应明示「时间窗口按服务器时间（UTC+0）」——否则用户会按本地时间配置。
2. **【需裁决】`require_confirmed` 规则的文案**：显示「下次触发」还是「下次执行（需确认）」？建议后者，避免用户误以为会自动下发。
3. **风险：预测与执行的漂移**。缓解手段只有一条硬约束——**预测函数与求值函数必须同包、同状态、同夹具测试**。跨包重写一份判定逻辑是本方案唯一的不可接受实现。
4. **风险：页面长期停留**。已由 `computed_at` + 30s ticker + 过期刷新覆盖；若用户开着页面跨过触发时刻，最多 90 秒后收敛。
5. **已知不精确（可接受）**：手动触发不更新 `evaluator.triggered` 内存态，导致"冷却中"提示可能与自动路径的实际判定有偏差；该偏差属于既有 D-5 家族问题，本方案用 `max(内存, 持久锚点)` 收敛，不引入新偏差。
6. **不做的事**：不给 `sensor_threshold` 造时间；不做"下次一定执行"的承诺（gate/确认制仍可能拦截）；不把该字段写进数据库。

#### 真机操作抓到的两个缺陷（单测没覆盖到）

1. **`timezone` 下发成了字面量 `"Local"`**（已修）。`time.Local.String()` 在未显式
   设 TZ 时返回的就是 `"Local"`，**不是合法 IANA 名**；前端 `Intl.DateTimeFormat({timeZone:"Local"})`
   抛 RangeError，只能退回浏览器时区。单测只断言了 sun 规则的时区，恰好没覆盖窗口规则。
   修法：新增 `localZoneName()`（TZ 环境变量 → `/etc/localtime` 软链的 zoneinfo 段 → 空串），
   并在 `TestNextRunWindowEnter` 里钉死"不得为 `Local`、非空时必须是可 LoadLocation 的名字"。
   修复后实测下发 `"Asia/Shanghai"`。

2. **纯通知规则不写 `last_triggered_at`**（**未修，属既有行为，记录在此**）。尽管
   `planner.go` 的注释写着"通知规则开始写冷却锚点"，实测规则触发后该列仍为 NULL。
   对本功能的影响有限：预测走 `max(内存态, 持久锚点)`，服务运行期间正确；但**重启后**
   纯通知规则的冷却锚点会丢——这与求值器自身的内存态丢失同源，属既有债，不在本次范围。

**两个踩过的环境坑（供下次复用）：**

1. **Go 会忽略位于 `$TMPDIR` 根部的 `go.mod`**：sandbox.sh 把 CWD 设为 `/tmp/work` 且 `TMPDIR=/tmp/work`，Go 于是报 `ignoring go.mod in system temp root` 并当成"无模块"。修法：`--env TMPDIR=/tmp/gotmp`。
2. **`node:24-alpine` 不能复用宿主装好的 `node_modules`**：宿主是 glibc，`rolldown`/`esbuild` 装的是 `*-linux-x64-gnu`；alpine 是 musl，`vitest` 启动即报 `Cannot find native binding @rolldown/binding-wasm32-wasi`。`vue-tsc` 是纯 JS，所以能在同一容器里通过。修法：容器内 `rm -rf node_modules` 后按 lockfile 重装（这也正是 Dockerfile 的构建路径）。

### 落地时相对方案的两处收敛

1. **`sensor_threshold` 的冷却期给时刻**：方案写的是"可空（仅冷却期有值）"，实现里首次写出时漏了这条分支（`cand.at` 为零值直接返回），被 `TestNextRunSensorWaitingData` 抓住并修正 —— 说明该用例确实可失败。
2. **`sun_event` 的"即将触发"分支要跟求值语义一起变**：初版按"事件刚过 ≤2 个 tick ⇒ 即将触发"判断。同日另一处改造把 `sun_event` 从**电平**改为**边沿 + 不补发**（只有 `prevTick < fireAt <= now` 才触发；重启 / 规则事后新建 / 编辑判定字段一律不补发），于是该分支必须改为读取求值器的 `lastClockTick` 与"判定字段刚变更"标记：
   - `configChanged=false` 且 `fireAt > 上一轮 tick` ⇒ 事件确实落在本次求值区间内 ⇒ 「即将触发（下一个 tick）」；
   - `configChanged=true`（刚建/刚改）或事件早已过 ⇒ 本日不触发 ⇒ 给次日。
   
   这条是**跨改造的一致性约束**：预测与执行必须同源，任何一方改边界语义都要同步另一边。
