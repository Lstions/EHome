# Test CI 长期红灯排查与修复（2026-10-21）

> 背景：推送到 main 后 `Build and Publish Docker Image` 一直是绿的，但 `Test CI` 长期失败。
> 失败的是 `Firmware (host tests)`、`Backend (PostgreSQL integration)`、`Backend (simulation gates)`
> 三个 job，**与驱动改动无关**（其上多个提交同样红）。
> 本文记录三处根因、修复方式与验证证据。

## 一、Firmware (host tests)：3 个用例 SEGFAULT

| 项 | 内容 |
|---|---|
| 失败用例 | `scheduler_route_tests`、`handler_data_tests`、`rx_health_e2e_tests` |
| 现象 | ctest 报 `***Exception: SegFault`（只给退出状态，不给栈） |
| 复现 | 本机用仓库自带 `.tools/cmake-3.30.5` 构建 host_tests，ctest 复现同样 3 个 SEGFAULT；gdb 定位到具体行 |
| 根因 | 2026-10-15 把 `config_edge_device_t.commands` / `sched_edge_device_t.commands` 从**内联数组**改成**按需分配指针**（RAM 优化），但三个夹具仍直接写 `commands[0]` 而**没有分配** ⇒ 空指针写 |
| 证据 | gdb：`ch = {... commands = 0x0 ...}`，崩在写入行（例 scheduler_route_tests.c:441） |
| 修复 | 夹具给静态存储并把指针指过去（`static config_command_t fixture_cmds[1]` / `sched_command_t`），夹具生命周期覆盖 scheduler_add_channel 调用即可 |
| 验证 | 本机 ctest：**99/99 通过**（唯一"失败"的 `golden_vectors_go` 是沙箱内 `~/.cache/go-build` 只读导致；置 GOCACHE 到可写路径后 exit=0，CI 上一直通过） |

## 二、Backend (PostgreSQL integration)：时间戳精度比较

| 项 | 内容 |
|---|---|
| 失败用例 | `internal/automation.TestConfirmEventExecutesAllActionsInOrder` |
| 现象 | `冷却锚点=2026-10-21 13:25:15.204153 +0000 UTC want 2026-10-21 13:25:15.204153196 +0000 UTC` |
| 根因 | 断言用 `time.Time.Equal` 比较「从 PostgreSQL 读回的 timestamptz（**微秒**精度）」与「time.Now() 产生的事件时刻（**纳秒**精度）」⇒ 同一时刻被判不等，**恒红**，与并发无关 |
| 修复 | 两边都 `Truncate(time.Microsecond)` 后再比（DB 能表达的最大精度），并在注释里写清口径 |
| 验证 | 本机 `go test -tags=integration ./internal/automation/` → ok（49.5s） |

## 三、Backend (simulation gates)：3 个场景

| 场景 | 现象 | 根因 | 修复 |
|---|---|---|---|
| **SIM-ACTN-004**（幂等键序号） | 同日两次执行的序号是 **1、3**，期望 1、2 | **产品 bug**：`nextTriggerSeq` 统计当日**全部** `automation_events` 行数，而冷却期内的求值 tick 会落 `suppressed_cooldown` 事件 ⇒ 被抑制的 tick 把序号顶高 | 只统计**真实触发**：排除 `suppressed_cooldown` / `suppressed_daily_limit` / `suppressed_no_solar_event`；其余结果（executed / partial_failure / failed_* / notification / confirmation_required / pending_confirm / condition_changed）全部计入，否则两次真实触发会共用 trigger_seq 而命中幂等重放（A-6 反例） |
| **SIM-ACTN-004** 附带 | 幂等键形态断言按 4 段写（`automation:<rule_id>:<yyyymmdd>:<seq>`） | 代码自多动作起就是 **5 段**（多 `action_seq`，见 docs/分析/B2多动作评审缺陷台账-2026-10-14.md:17）⇒ 断言过期 | 正则与错误文案改为 5 段 |
| **SIM-COND-005**（执行前复核） | 创建规则时 HTTP 400 `risk_action_requires_confirmation` | O-2 规则级授权契约加入后，风险动作自动执行需 `risk_acknowledged=true`；场景未带 ⇒ 400，未到复核环节 | 场景补 `risk_acknowledged: true`（本场景要验证的是 F4 复核，不是授权门） |
| **SIM-WIND-002**（离开时间窗边沿） | 17s 内 0 条 notification | 场景用 PUT 把窗口挪走再等 exit 事件，但 **A-17** 规定"影响窗口判定的字段变化 ⇒ 清除 windowStates"（`evaluator.go:sameWindowStateFields`）⇒ 引擎不再知道"上次在窗口内"，exit 边沿永不触发 | 改为**真实语义**：窗口在整分钟边界自然结束，等下一个 tick 触发离开边沿；并断言触发时刻晚于窗口结束时刻（归因） |
