# 节点同步卡死自愈 与 time_window 边沿不补发（2026-11-18）

承接 `docs/分析/自动化动作-能力快照过期与手动确认门-2026-11-18.md`（同一晚的两条自动化失败事件）。本文记录当天确认并修复的另外两处。

## 一、节点同步卡死（固件 `sync_state` 长期非 idle）

### 现场证据（生产 192.168.20.6:18090）

| 观测 | 值 |
|---|---|
| 节点 | `F0F5BD02DD84`（C6，fw 2.8.0），uptime 连续增长，MQTT/3.0 链路在线 |
| StatusReport（每秒一条） | `sync_state=1(syncing)`、`epoch=0`、`hash=v2-2b1a1a5a`，**11 小时未变** |
| Hello | 12 小时内只有 **1 次**（后端重启后的重连），其后 `Hello skip: reason=hash_match` |
| 服务端 | 同一时段 0 条 `sent` / 0 条 `rejected` —— 双方都没做错动作 |

### 死锁链条

1. 设备 `sync_manager_request_sync()` → 置 `SYNCING` → 发 Hello，等一条能让状态回 `IDLE` 的下行帧；
2. 服务端 `SyncGate.OnHello` 判 `hash_match` ⇒ `SyncActionNone`，**什么都不发**；
3. 设备永远停在 `SYNCING`，服务端永远认为"同步没问题"。

这与 2026-10-05 `config_status=failed` 那次是**同一形状**的死锁（见 `sync_gate.go` 的 `hash_match_but_config_failed` 注释），只是打破对称的证据从「服务端判 failed」换成了「设备自述卡死」。

### 修复

`internal/nodemgr/sync_gate.go`：`OnStatusReport` 在 hash 比较**之前**调用 `reconcileStuckSync`——

- 设备自报 `sync_state` ≠ `idle` 持续超过 `stuckSyncGrace = 3min`（正常一次同步是秒级）；
- 且距上次为卡死重下发超过 `stuckSyncRepushInterval = 5min`（卡死是**稳态**，每 1s 心跳都推全量会把"配置卡死"放大成"总线过载"）；
- ⇒ 强制 `SyncActionFull`，`Reason = hash_match_but_sync_stuck`；设备回到 `idle` 即清除观测。

单测：`sync_gate_sync_stuck_test.go`（强制重下发 / 节流 / idle 重置计时）。变异自证：删掉 `reconcileStuckSync` 分支 ⇒ 首条用例退回 `hash_match/none`。

**边界**：这是后端侧的兜底修复，不能替代固件修复（周期 Hello 没发出去仍是固件问题）。若设备连 Hello 都不再发，本机制只能靠 StatusReport 自述触发，仍会每 5 分钟重推一次 manifest。

## 二、`time_window` enter 边沿补发（未知即触发）

### 证据（改前先写红测复现）

`evalWindowRule` 旧实现：`shouldTrigger = inside && (!exists || !wasInside)`。
`!exists` 表示"求值器没有这条规则的窗口历史"，被当成"刚刚进入"⇒ 三种情况会**凭空执行一次设备动作**：

1. 进程重启后首个 tick 恰好落在窗口内；
2. 规则在窗口内才被创建/启用；
3. 规则被编辑（`windowStates` 被清）时正处窗口内。

红测输出（改前）：

```
--- FAIL: TestWindowEnterDoesNotBackfill       重启后首个 tick 落在窗口内时补发了 1 次
--- FAIL: TestWindowRuleCreatedInsideWindowDoesNotBackfill   规则在窗口内新建时补发了 1 次
```

### 修复

`shouldTrigger = inside && exists && !wasInside`（与 2026-11-17 sun_event 同一裁决：不做补发，要立刻执行用手动触发）。exit 分支本就要求 `exists && wasInside`，未动。

### 受影响的既有用例（已按新语义更新）

| 用例 | 旧断言 | 新断言 |
|---|---|---|
| `TestTimeWindowCooldownSuppression` | 首个 tick 在窗口内即触发 | 先窗口外 tick 建立 `wasInside=false`，再跨入触发 |
| `TestTimeWindowRestartConservative` → `TestTimeWindowRestartDoesNotBackfill` | 重启后首 tick 在窗口内"保守触发" | 重启后不补发；次日真边沿仍触发 |
| `TestA17WindowStatesClearedOnContentChange` | 首个 tick 在窗口内触发 | 窗口外→窗口内触发后再验证白名单清理 |

设计文档 `docs/设计/自动化策略引擎-日出日落与多动作-方案.md:217` 的「重启后首 tick 的边沿语义」一行已同步更新。

## 三、`confirmation_required` 实为**不可达态**（用户 2026-11-18 裁定后修正结论）

### 用户的判断（正确）

> 「未完成风险授权」不存在也不合理：能创建成功就一定是完成了授权。

核对代码后确认成立：

| 入口 | 校验 | 结论 |
|---|---|---|
| `POST /automation-rules` | `validateActionsCatalog` → `validateRiskActionAuthorization`（V7） | 风险动作 + `require_confirmed=false` + 未授权 ⇒ **400 拒绝** |
| `PUT /automation-rules/:id` | 同上；动作集合变化时 `acknowledged` 先置 false 再校验 | 变更动作后必须**重新授权**，否则 400 |
| 其它入口 | 只有 `PATCH /enabled`、`DELETE`、`POST /trigger`、`POST /precheck` | 都不能改动作/授权 |

生产库实测：2 条规则，`risk_acknowledged_at` 均非空。

### 因此它是数据异常态

剩余可能来源只有三类：① V7 上线前的存量规则；② 动作定义的风险等级后来被升级；③ 绕过 API 直接写库/导入。

### 旧文案是**双重错误**

1. 标签「需确认（未授权）」把一个不应出现的状态描述成正常的等待确认；
2. WS 提示让用户「到触发历史里对相应事件执行确认」—— **做不到**：`Planner.ConfirmEvent` 对非 `pending_confirm` 事件直接返回 `ErrConfirmNotPending`（`planner.go:1579-1581`），该类事件没有确认入口。

### 本次修复

| 位置 | 改动 |
|---|---|
| `frontend-shared/.../automationFormat.ts` | 两处标签：`需确认（未授权）` → **`规则未授权`** |
| `AutomationRules.vue` | WS 提示改为「缺少规则级授权（不应出现的数据状态）：请编辑该规则并勾选风险确认后重新保存」 |
| `frontend-shared/src/api/automation.ts` | 枚举注释同步真实语义 |
| `automation/planner.go` | 新增 `describeDeviceActionError`：未授权时 detail 写明原因+处置；已授权却被拦时判为「确认令牌无效（内部错误）」 |
| `api/handler_automation.go` | V7 收口 **fail-closed**：目录查询失败/动作不在目录中不再 `continue`，改为拒绝保存（旧行为等于"无法判定风险等级 ⇒ 当作不是风险动作 ⇒ 放行"） |

单测：`planner_confirmation_detail_test.go`（三分支）、`TestHandleTriggerAutoRiskActionWithoutAuthorizationIsNotDispatched` 增补 detail 断言；前端 `AutomationRules.spec.ts` 的 F-8 断言同步（119 例全绿）。
