# 自动规则「显示失败但实际已生效」取证与修复方案（2026-11-25）

> 现场：生产 100.64.0.7，镜像 `ghcr.io/lstions/ehome:latest` = `14d5ad1d`（11-20 终态回填 + 11-24 能力自愈均已上线）。
> 方式：**只读**拉取生产库与 `/api/v1/devices/14/history`，未下发任何命令、未改库。

## 1. 现象

「自动化策略」页把 `set_mos_policy` 的失败记为 `failed_execution`（红色「执行失败」），并推送
「策略执行失败」通知；但设备的实际状态表明策略**已经生效**（关断锁存位置位、充电被阻断，
打开时充电电流立即恢复）。

## 2. 取证

### 2.1 审计面：失败的都是同一条动作

`automation_events` 全表 26 行，非 executed 的结果只有 5 条 `failed_execution`，且都是
`set_mos_policy`：

| event | 规则 | 动作 | 命令终态 | final_reason |
|---|---|---|---|---|
| 19 | 2 关闭BMS充电 | charge=true | FAILED | final_failed |
| 21 | 2 关闭BMS充电 | charge=true | FAILED | final_failed |
| 23 | 2 关闭BMS充电 | charge=true | FAILED | final_failed |
| 24 | 1 打开BMS充电 | charge=false | FAILED | final_failed |
| 25 | 2 关闭BMS充电 | charge=true | FAILED | final_failed |

审计行与命令行**一致**（不存在回填错位）：5/5 的 `command_executions.status` 都是 FAILED。

### 2.2 命令面：设备侧计划是成功的

`command_inboxes` 对每条命令只有两条事件，`final_failed` 的 payload 是：

```json
{"error_code":0,"final":true,"raw_response_len":59,"replayed":false}
```

`error_code=0` = 节点执行整条 bounded plan 没有报错（写 ACK 收到、回读帧收到）。
`verified_result_json` 为 `[]`：**服务端 verifier 没产出证据**。

`backend/internal/nodemgr/handler_channel_cmd_v2.go:51-63`：节点报 `final=true & success` 之后，
服务端再跑 `VerifyFinal`；只要 verifier 返回 error，就把事件改写成 `final_failed`。
所以失败点在**服务端回读判定**，不在设备执行。

### 2.3 设备面：策略其实生效了（遥测为证）

`/api/v1/devices/14/history`（fet_status / protection_status / current，1 Hz）与命令时刻对齐：

| 时刻(UTC) | 事件 | 写入后 fet_status | protection_status | 之后的事实 |
|---|---|---|---|---|
| 11-20 15:26:04 | 手动 close（OK） | 15:26:07 → **2** | 0→**4096** | 空载，FET 立即切换 ⇒ verifier 通过 |
| 11-21 09:41:03 | close（FAILED） | 09:41:05 → 3 | 0→**4096** | 锁存置位，charger 全程无正向电流 |
| 11-22 09:40:53 | close（FAILED） | 09:40:55 → 3 | 0→**4096** | 锁存保持到 22:45 打开 |
| 11-23 09:40:46 | close（FAILED） | 09:40:47 → 3 | 0→**4096** | 锁存保持到 22:46 打开 |
| 11-23 22:46:19 | open（FAILED） | 22:46:21 → **3** | **4096→0** | 22:46:21 电流 0→**+1.45 A**，随后整夜 +13~29 A 充电 |
| 11-24 09:40:39 | close（FAILED） | 09:40:41 → 3 | 0→**4096** | 锁存保持到 22:47 打开，07:00 本地充电恢复 |

关键对比：**11-20 15:26 空载时 close 成功（fet=2）**，而 11-21~24 的 close 全部发生在
`current≈-4~-5 A`（带载放电）时 —— 同一个动作、同一份代码，只有「是否带载」不同。

## 3. 根因

### 3.1 判定标准与这台 BMS 的真实语义不符（主因）

`VerifyControlAction`（`backend/internal/drivers/jiabaida_control.go:832-847`）用 `fet_status` 的
charge/discharge 位**必须立刻等于请求值**作为成功判据。实际语义是：

- `0xE1` 是**策略锁存**：写入后 `protection_status` bit12（`0x1000`）立即置位/清零；
- `fet_status` 是**物理 FET 状态**，带载放电时 BMS 不切换充电 MOS（保持 `0x03`），等负载空闲
  才切换（11-23 15:24 才看到 `fet=2`）；
- 因此「关断策略已生效」与「fet 位立刻变化」不是同一件事。

### 3.2 回读帧选错：读的是 0x03，看不到 0x1000

计划第 2 步读 `0x03`（基本信息，23+2×NTC 字节），**该帧没有 protection_status 字段**。
verifier 里的 `hasProtection` 分支因此恒为假，报错文案永远落到「设备在稳定窗内回退了软件策略」
——这也解释了为什么现场看到的失败原因总是同一条，且与事实相反。

### 3.3 单次 1.2 s 回读对「打开」也会踩窗口

11-23 22:46 的 open：设备在 22:46:21 已经 `0x1000→0` 且充电 +1.45 A（物理生效），但 verifier
在约 1.2 s 时读到的仍是旧状态（`fet=2`），判失败。回读只做一次、没有重试，慢一拍就永久记失败。

### 3.4 文案把「服务端判定失败」说成「设备上报失败」

`automationTerminalCauseText(final_failed)` 返回「设备上报最终执行失败，或最终回传未通过服务端校验」，
通知正文再叠加一层「已下发，但设备未确认执行成功」。实际这次设备**上报的是成功**（`error_code=0`），
是服务端 verifier 不认。用户看到的就是「失败」，而设备已经做了。

## 4. 修复方案

### 4.1 计划：先读基线，再写，再读两次（4 步）

```
step1 read  0x0F            settle 100ms    // 基线：fet_status + protection_status
step2 write 0xE1            settle 1200ms   // 策略写入
step3 read  0x0F            settle 400ms    // 第一次回读（快）
step4 read  0x0F                            // 第二次回读（慢一拍兜底）
```

`MaxSteps: 2 → 4`（bounded plan 上限 8，富余）。

### 4.2 判定矩阵（verifier）

| 请求 | 成功条件（step3 或 step4 任一满足） | 说明 |
|---|---|---|
| close | `prot&0x1000 != 0` **或** `fet.charge == 0` | 锁存位=策略已接受；FET 位=物理已切换 |
| open | `prot&0x1000 == 0` **且** `fet.charge == 1` | 必须两者都满足，避免「看起来打开了」 |
| 任一 | `fet.discharge` 必须等于请求值 | 与现状一致 |

基线（step1）**只进诊断文案，不参与判据**：幂等重复关断时锁存位本来就在，仍应判成功；
判据本身对「本次写入是否改变了状态」不做要求（关闭请求命中已关闭状态就是成功）。

### 4.3 把 verifier 的原因落库

`handler_channel_cmd_v2.go` 现在只 `logger.Warnf` 丢弃 verifier 错误。改为：

- inbox payload 增加 `verify_error`（原始错误串）；
- 自动化回填 detail 直接引用它，而不是泛化文案；
- 通知文案区分「设备未执行」与「设备已执行但回读未通过」。

### 4.4 兼容与回归

- 其它厂商/其它 action 的 verifier 不动；
- `jiabaida_test.go` 金标：步数 2→4、step2 settle ≥ 1000ms、step3/4 读 0x0F；
- 仿真 catalog 的 `MaxSteps`/步序断言同步更新；
- 真机验证矩阵：空载 close、带载 close、open、幂等重复 close。

## 5. 影响面与风险

- 收益：`set_mos_policy` 的误报失败归零；失败时能给出「哪一次回读、看到什么」；
- 风险：`0x1000` 判据只对确认过语义的机型启用（有基线差分兜底，误判为成功的窗口很小）；
- 回滚：单文件 verifier + 计划，无 schema 变更（`verify_error` 只写 payload_json）。

## 6. 待确认

- `0x1000` 在其它嘉佰达固件（非 0x81）上是否同义 —— 用基线差分 + 真机复测覆盖；
- 是否要把「设备执行成功、回读证据不足」单列为 `unverified`（黄色「未确认」），
  而不是继续算 `failed_execution`（红色「失败」）。

### 7.2 判定矩阵（实现）

| 请求 | 成功条件（单帧 0x0F 回读） |
|---|---|
| close | `fet.charge == 0` **或** `protection & 0x1000 != 0` |
| open | `fet.charge == 1` **且** `protection & 0x1000 == 0` |
| 任一 | `fet.discharge` 等于请求值 |

**步数硬约束**：节点固件最终响应上限 128 B（`handler_channel_cmd_v2.c` 的 `V2_MAX_RX`），
一帧 0x0F（16 串 4 NTC）约 78 B，加上写 ACK 与步头已 94 B；再加第二帧就必然 1005。
回归护栏：`TestJiabaidaMOSPlanFitsNodeFinalPayload`。

### 7.4 线上生效后的预期

- 日落关断：设备回 `fet=0x03 + protection=0x1000` ⇒ 判成功，不再产生 `failed_execution`；
- 日出打开：`protection 0x1000→0` 且 `fet.charge=1` ⇒ 判成功；
- 真失败（设备没接受）：`fet` 位未变且锁存位未置位 ⇒ 仍判失败，且 detail 里能看到两次回读的原始位；
- 设备/协议异常（帧解析失败、ACK 校验错）：照旧失败，原因进 `verify_error`。

## 9. 事故复盘：2026-11-27 生产「全部失败」

### 9.1 现象

生产升级到 `678ef186`（4 步计划）后，**每一条** set_mos_policy 都失败：

| 时间(UTC) | 动作 | error_code | raw_response_len |
|---|---|---|---|
| 11-25 09:40 | close | **1007** | 0 |
| 11-25 22:47 | open | **1005** | 0 |
| 11-26 09:40 | close | **1007** | 0 |
| 11-26 22:48 | open | **1005** | 0 |

审计 detail 全是「未记录判定原因」——因为 `success=false`，服务端 verifier 根本没跑。

### 9.2 根因

1. **1005 = `V2_ERR_FINAL_OVERFLOW`（主因）**：节点把整条计划的最终响应存进
   `V2_MAX_RX = 128 B` 的槽位（`handler_channel_cmd_v2.c:222`），超过即整条命令失败。
   4 步计划 = 1 + (3+7) + 3×(3+78) ≈ 254 B ⇒ 必超。写入本身已经执行（步骤先跑完，
   只在完成时判定），所以设备状态其实变了，只是命令被判失败。
2. **1007 = 命令执行期间被 suspend 打断（次因）**：当日 09:40:32 服务端因
   「节点 sync_state=syncing 超过 3 分钟」强制重下发 manifest，节点应用 manifest 时
   调用 `bus_worker_suspend()`，正在执行的批次被中断并报 1007。

### 9.3 修复

- 计划回到 **2 步**（写 + 单帧 0x0F），响应最坏信封 94 B < 128 B；
- 稳定窗 1200ms → **1800ms**（实测设备 0.8~1.4s 完成锁存/清锁存，单帧必须落在刷新后）；
- 新增 `TestJiabaidaMOSPlanFitsNodeFinalPayload` 把「信封 ≤ 128 B」钉成回归护栏，
  以后谁再往计划里加读步，单测直接红。

### 9.4 遗留风险（未修）

- **配置同步会打断在途命令**：manifest 下发 → `bus_worker_suspend()` → 批次 abort(1007)。
  这是固件既有设计，与本次改动无关；缓解方向（择一）：
  1. 服务端在「有在途命令」时推迟 manifest 下发；
  2. 命令收到 1007 时自动重试一次（set_mos_policy 幂等）；
  3. 固件在批次执行期间拒绝 suspend（等批次结束再切配置）。
- 「sync_state=syncing 超过 3 分钟」本身也值得单独排查（何时进入 syncing、为何没回 idle）。
