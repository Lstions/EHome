## 9. 设计约束推论 (由上述事实直接推出)

1. **外发必须是旁路, 且必须挂在"所有通知写入点"的共同下游, 而不是某一个调用者。**
   依据 §1/§2: 10 个构造点分布在 automation / alert / datasource / datalifecycle 四个包, 没有共用写入函数; 各点写入失败一律吞掉 (`planner.go:337-340`, `evaluator.go:307-310`, `service.go:857-872`, `migrate.go:411-417`, `retention_task.go:338-342`)。若外发只挂在 alert 或 automation 一家, datasource/datalifecycle 的通知将永远不外发。
2. **外发失败不得改变主流程返回码, 也不得阻塞调用方 (尤其是事务内与数据采集热路径)。**
   依据 §1/§2: datasource 的通知在 **事务提交后** 才投递 (`service.go:857` "事务提交后投递"; `emitAll` 在 `Transaction` 返回之后调用, 如 `service.go:323-327`); 部分写入点在采集/解析热路径上 (alert evaluator 由 parser 回调驱动)。
3. **通知通道配置需要一张新的可配置表 + 完整五段式接线, 且必须复用 DTO 白名单与"写路径回刷"范式; 敏感凭据不能照抄现有存储方式。**
   依据 §4 (模板: `models/alert.go:34-50` / `handler_alert.go:62-77` / `routes.go:132` / `api/alert.ts` / `stores/alert.ts` / `AlertRules.vue` / `router/index.ts:112-117`) 与 §6: 全仓无应用层加密 (`DataSource.Config` 明文 `models.go:304`), MQTT/DB/JWT 凭据一律走环境变量且**不可回读** (`config.go:156-169`, `mqtt.go:266-267`)。因此"用户可配置 + 可回读"的 webhook 密钥在本仓**无先例**, 必须在设计中显式裁决 (加密存储 / 只写不读 / 不落库)。
4. **前端不能依赖现有 WS `notification` 事件做实时刷新。**
   依据 §5: `events.Notification` 已存在且 alert 会广播 (`evaluator.go:311-325`), 但前端**没有任何 `WS_EVENT.NOTIFICATION` 订阅者**, 铃铛只在 mounted 时拉一次 (`MainLayout.vue:306-322`) 且 automation 的 3 条通知**根本不广播** (`planner.go:431-451` 无 broadcast)。外发通道若要在 UI 上可见, 需要同时补 WS 订阅/广播与"外发状态"字段。
5. **外发投递的可观测性必须新建, 不能复用现有指标口径。**
   依据 §2: 现有唯一指标 `DataConsumerDBWriteFailures{consumer,table}` (`metrics.go:185-186`) 只统计**库写入失败**, 且 datasource 与 datalifecycle 两条路径**根本没打指标**; 若外发失败只写日志, 用户与运维都无法发现"告警没发出去"。
6. **出站 HTTP 客户端、超时、重试/退避、SSRF/内网地址限制全部从零建; 且可测试性依赖新范式。**
   依据 §3: 运行时后端零出站 HTTP 调用、无可复用封装 (唯一可参考的 `http.Client` 在 `simulation` 构建标签内: `harness/http.go:53`, `catalog/rt.go:480`); §8: 现有 `httptest.NewServer` 全是入站方向, **没有"被测代码外发到 mock 接收端"的范式**。可复用的只有 §7.1 文档裁决与 `notify.go` 的 SIM-NTFY 断言口径 (`docs/设计/自动化引擎场景仿真验证.md:271-277`)。
7. **外发动作的配置面若加在 automation 上, 必须补 `action_level` 式白名单校验的缺口。**
   依据 §7: `action_level` 只判空不校验取值 (`handler_automation.go:611-614`), 非法级别在 `NotificationType` 里静默降级为 `info` (`models/alert.go:71-79`); 与之对比 alert 有 `validLevels` 白名单 (`handler_alert.go:21-23,376-378`)。新增通道字段若照抄 notification 分支, 会重复"脏值静默降级"。
