## 0. 一句话结论

上一轮的"停写 + 保留冻结件"是在等一个决策输入；本轮把那个输入测出来了：
**长跨度查询本来就索引 + 分区裁剪，rollup 能省的只是几毫秒**，而它要求一张无界表、
一套保留期/清理器/测试，以及一次**数据模型改造**（该表无 `logical_device_id` 列，
而本仓查询恒带 logical scope）。⇒ 收益与代价不成比例，退役。

---

## 1. 证据复核（EXPLAIN ANALYZE，本轮实测）

复跑命令（与任务书一致）：

```bash
export DOCKER_CONFIG=/tmp/dockercfg
docker exec ehome-postgres psql -U ehome -d ehome_uiux -c "
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)
SELECT timestamp, value FROM unified_data
WHERE device_id=7053 AND sensor_name='total_voltage'
  AND timestamp BETWEEN now() - interval '30 days' AND now()
ORDER BY timestamp ASC;"
```

**实测结果（与任务书的量级一致，但有两个数字需要更正）**：

| 查询 | 计划 | 实测 | 任务书写的 | 差异 |
|---|---|---|---|---|
| 无 LIMIT（`/unified-data/historical-batch` 形态） | `Sort` ← `Append` ← `Bitmap Heap Scan` on `unified_data_202608`（`sensor_name` 索引 + 过滤 device/timestamp），`Subplans Removed: 3`（分区裁剪） | `Execution Time: 3.644 ms`，执行期 `Buffers: shared hit=1191` | 3.6 ms / 820 buffers | 时间一致；**buffers 实际是 1191** |
| 带 `LIMIT 500`（`/devices/:id/history` 形态，本轮补测） | `Limit` ← `Index Scan using unified_data_202608_timestamp_idx`，读满 500 行即停，202609 分区 `never executed` | `Execution Time: 0.791 ms`，`shared hit=104` | 0.24 ms / 609 buffers | **本轮实测 0.79 ms / 104 buffers** |

> **关于 820 的更正（如实说明）**：`820` 是该 EXPLAIN 的 **Planning Buffers**（`Planning: Buffers: shared hit=820`），
> 不是执行期 buffers；同一份计划里执行期是 `Buffers: shared hit=1191`。
> 结论方向不受影响（仍是**毫秒级**），但本文档按实测值记录。

**索引确实存在**（各月分区上）：`unified_data_<月份>_logical_device_id_timestamp_idx (logical_device_id, "timestamp" DESC)`
与 `unified_data_<月份>_timestamp_idx ("timestamp")` ⇒ 长跨度查询本来就索引 + 分区裁剪，
`LIMIT` 让它**从不扫描整个窗口**。

**结论**：rollup 的收益是"省几毫秒"。这个量级不足以支撑以下三项代价：

1. 无界增长的第二张表（需另配保留期 + 清理器 + 测试）；
2. **必须改数据模型才能接线**：rollup 表无 `logical_device_id` 列，而本仓查询恒带 logical scope
   ⇒ 上一轮已论证"接线在生产不可达"，除非加列 + 改冲突键 + 重聚合回填；
3. 冻结件**现在就有成本**：`cmd/server/main.go` 每次启动仍调 `EnsureRollupTable`（建表 DDL），
   外加 consumer/测试/门禁永久占用维护面。

## 3. 代码级变更要点（两处值得单独标注）

### 3.1 建表路径必须先于退役 DDL 摘除

`AutoMigrate()` 尾部的 `RetireLegacyRollup1m` 只负责把**存量库**的表清掉。
只要 `EnsureRollupTable` 还在 `main.go` 里被调用，就会出现"启动先建表、随后 DROP"的
往返（同 `operation_logs` 的注释所述）。本轮处置顺序：**先删调用点与建表函数，再加退役 DDL**，
由 `TestRollupTableNotCreated_Postgres` 钉死"走完启动路径后表不存在"。

### 3.2 退役暴露出一个隐藏耦合（已解耦，非范围外改动）

原持久化成功分支是：

```go
} else if c.rollupSink != nil {     // ← 未注入 rollup ⇒ 整段跳过
    c.rollupSink(records)
    if c.latestSink != nil { ... }  // ← latestSink 被 rollupSink 门控
}
```

即 **`latestSink` 的生效条件被 `rollupSink` 门控**（一个 sink 的存在性决定另一个 sink 是否执行）。
rollup 退役后若照搬原结构，`latestValueCache` 会在 `c.rollupSink != nil` 这个**永假**条件下永不更新
（`/overview`、`/edge-devices/:id` 的最新值将永远 miss 并回落原 SQL —— 功能退化且无测试能发现）。

处置：把 `latestSink` 提为独立条件（`} else if c.latestSink != nil { ... }`），语义等价甚至更正确。
这是**退役本身暴露的耦合**，已在该处代码注释中写明。

## 4. 门禁改写：从"条件式 INV-7"到"死表不得复活"

**旧门禁**（`rollup_wiring_gate_test.go`）看守的是：*若*接线则必须有保留期。
退役后这个**条件的本体不存在了** —— 它只能看守空气。**新门禁**
（`datalifecycle/rollup_retirement_gate_test.go`）与 `database/operation_logs_gate_test.go`（INV-8）
**同范式**，断言：

1. 生产代码（`internal/` + `cmd/` + `testutil`，跳过 `_test.go`）中，表名不得出现在
   建表 / AutoMigrate / SELECT / INSERT 等任何语义里（幂等 DROP 除外）；
2. 已退役符号 `EnsureRollupTable` / `SetRollupSink` / `rollupSink` / `RollupConsumer` / `UnifiedDataRollup1m` 零生产引用；
3. 退役步骤本身仍在（`retire_rollup.go`，幂等 `DROP TABLE IF EXISTS`）且被 `AutoMigrate` 生产路径调用；
4. `gorm.go` 与 `testutil/db.go` 的模型清单不含该模型/表名（子串陷阱：只看清单区块，不看全文件）。

**扫描器自检（必须）**：`TestRollupGate_ClassifierSelfCheck` 是**变异重放**，把退役前**真实存在过**
的写法硬编码喂给扫描器，要求逐条判红（13 条），另有 11 条允许项要求不红。自检用例**不依赖被检清单
自身** —— 若有人把某个符号从 `rollupRetiredSymbols` 里删掉（把门禁改窄），自检第一步就失败。

> 自检第一版有两条用例本身写错了（把"行尾注释里的符号"当成代码引用；把归档文档当扫描面），
> 已按实测修正并在用例里写明理由：**非 `.go` 源（docs/** 含 archive）不扫**。
