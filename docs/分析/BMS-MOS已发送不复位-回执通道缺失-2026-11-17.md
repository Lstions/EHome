## 0. 结论

**不是设备问题，也不是上一轮 read_size 修复的回归：是前端根本没接回执。**

上一轮修好 read_size 后，后端已能真正把 MOS 写下去并回读校验成功（所以"实际已经打开了"）；
但**执行状态与写后回读值这两样东西，前端一件都收不到** —— 页面只在挂载和手点「刷新数据」时
用 REST 拉一次历史，而历史里那条记录永远是 POST 返回的 `QUEUED`。

| 编号 | 结论 | 等级 |
|---|---|---|
| **D1** | BMS 详情页**没有订阅** WS `device_operation_update`，也**没有任何轮询**；两个状态域（`useBmsOperations` / `useBmsMosControl`）都只读 `store.histories` ⇒ 终端状态与 `verified_result` 永远到不了页面 ⇒「已发送…」永不复位、开关期间一直 `disabled`，只能手点「刷新数据」自救 | **确认缺陷（P0）** |
| **D2** | D1 的连带后果：写后回读的**权威值**（`verified_result.fet_status`）永远不生效 ⇒ 开关只能追周期帧；写之前采集、写之后才到的那一帧会把它打回旧值，下一帧再跳回 —— 即用户看到的「跳一下打开、再跳回关闭」 | **确认（D1 的后果 + D3 语义不足）** |
| **D3** | `verifiedFet` 桥接只按「实时值恰好等于回读值」撤销：① 更旧的帧照样能覆盖它（抖动的直接成因）；② 若设备此后不再回该位（例如被硬件保护覆盖），桥接会**永久**钉住显示值 —— 保护关断也看不见 | **确认缺陷（P1）** |
| **D4** | 回执链路一旦断掉，在途态**没有任何超时**：`mosPhase` 挂着「已发送」⇒ 开关 `:disabled="!!m.phase"` 永久禁用。用户没有任何页面内自救入口 | **确认缺陷（P1）** |
| **D5** | `scripts/check_ws_event_names.sh` **长期失败**（union 缺 `device_operation_update`/`node_resources_updated`、豁免名单不全、还扫到了测试文件）⇒「WS 事件名单一来源」形同虚设。这正是 D1 能长期存在而没人发现的结构原因 | 确认缺陷（P2） |

**根因一句话**：后端在每次状态变化时都广播 `device_operation_update`（5 处），前端常量表里却连这个名字都没有 —— 于是只有 `DeviceControlPanel` 一个组件用裸字符串订阅了它，BMS 页从来没人订阅。

## 1. 证据链（为什么"必须点刷新"）

### 1.1 页面侧：状态只有一个入口，而那个入口不更新

| 位置 | 事实 |
|---|---|
| `useBmsOperations.ts:55` | `const opStore = useDeviceOperationStore()`，历史来自 `opStore.histories.get(deviceId)` |
| `useBmsOperations.ts:161-168` | `watch(historyOps, ...)` 只在 **store 变了** 时把回执映射到 UI —— store 不变就什么都不会发生 |
| `useBmsMosControl.ts:94-101` | 同一份 `store.histories`，成功时用 `verified_result` 桥接显示 |
| `BmsDetailPage.vue`（改前 `onMounted`/`refreshAll`） | `loadOperations()` 只在**挂载**和**手点刷新**时调用 |

### 1.2 store 侧：那条记录只可能是 `QUEUED`

`stores/deviceOperation.ts` 里 `apply()` 是唯一写入口，调用方只有三处：
`create()`（POST 返回值 = `QUEUED`）、`refresh()`（REST 列表）、`resolve()`。
**没有任何 WS 订阅**（改前全仓 `subscribe(` 调用点里，操作域只有 `DeviceControlPanel.vue:231` 一处）。

⇒ 用户在 BMS 页点开关后：store 里多一条 `QUEUED`；后端推进到 `SUCCEEDED` 时广播，
**但本页没有订阅者**；页面于是永远停在 `QUEUED` → 文案「已发送」。

### 1.3 后端侧：广播一直都有

`backend/internal/events/events.go:15` 定义 `DeviceOperationUpdate`，
`handler_device_operation.go:73/151/174`、`cmd/server/main.go:1430`、`nodemgr/handler_channel_cmd_v2.go:113` 共 5 处广播。
**不是后端没发，是前端没接。**

### 1.4 为什么"跳一下"

```
T0  周期帧（fet_status=0x03 导通）→ latestData=3 → 开关显示「导通」
T1  用户点关断 → 写 0xE1 → 设备执行 → 回读 0x03 得 0x02 → 服务端 SUCCEEDED
T2  页面：没有回执 ⇒ verifiedFet 不设置 ⇒ 开关**仍按 latestData 显示导通**
T3  一帧 T0 之前采集、T1 之后才送达的旧帧（0x03）→ 开关"跳一下打开"
T4  下一帧 0x02 → 开关"跳回关闭"
```

D3 让 T3 无解：桥接既没被设置（D1），撤销条件又只看"值相等"，
所以旧帧永远能把显示打回旧值。

## 4. 残留（需真机确认，不在本次代码修复范围）

1. **真机复验**：MOS 开关操作后卡片应在 ~1s 内从「已发送」走到「成功/失败」，且开关只动一次。
2. **`fet_status` 双源风险**：`0x03`（偏移 20）与 `0x0F`（偏移 22）都会解出 `fet_status`。
   若该设备同时启用了这两条轮询，而真机 `0x0F` 布局与协议文档不符，则 `fet_status` 会在两个值之间
   每周期翻一次 —— 那会是**另一种**抖动源，本次修复只能保证"旧帧不覆盖权威回读"，不能纠正解析偏移。
   现场判据：页头「轮询已启用 N 条」与指令清单里 `read_comprehensive` 是否启用；`latest-values` 里
   `fet_status` 是否呈两值交替。
3. **`automation_*` 三条事件**仍由 `automation/planner.go` 直发裸字符串，未进 `events.go` 常量表
   （已在门禁里显式豁免并注明，属独立任务）。
4. `BmsMosStatus.vue` 已是**死代码**（只被自己的 spec 引用），其 `before-change` 实现与新卡片的
   `:model-value + @change` 实现并存，属技术债（不影响本缺陷）。
