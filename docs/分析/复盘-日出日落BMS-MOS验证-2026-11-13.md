## 1. 结论摘要

1. **用户需求本身成立**：模拟节点 + 嘉佰达 BMS → 日落关充电 MOS（`fet_status 0x03→0x02`）→ 日出开充电 MOS（`0x02→0x03`），两条事件均 `executed`、两条命令均 `SUCCEEDED`，且回读校验通过；同日本地日不重复触发。证据见验证记录 §4/§5。
2. **但「日出/日落规则」在界面上原本存不进去**：规则级坐标三项全填仍被前端判成「部分填写」并拒绝保存，POST 根本不会发出；而节点级坐标**没有任何写入路径**（无 API、无 UI）。两条路径都断 ⇒ **sun_event 规则在修复前无法通过产品界面创建**。已做最小修复并验证（前端 130 个自动化单测全绿）。
3. **新库上有持续报错噪声**：解析后的传感器数据每帧尝试写已退役的 `unified_data`，该表在新库不存在 ⇒ 每 3 秒一条 ERROR。数据本身经 L2 帧表正常落库（实测 `telemetry_frame` 505 行）且 UI 正常，但日志会误导排障。生产口径是 `EHOME_TELEMETRY_UNIFIED_WRITE=false`，而 `docker-compose.yml` / `.env.example` 都没有这个开关。
4. **成功触发链路没有 INFO 日志**：两次成功触发在日志中只有第一次的「惰性解析系统主体用户」一行，第二次完全静默；事件/命令只能靠 DB 或 UI 才知道。排障与验收的可观测性不足。
5. **部署文档与编排已漂移**：README 仍描述 MQTT/EMQX 与 8080 单体容器，实际是 mTLS 直连 + 本机 Go/Vite；`.env` 缺失、设备监听默认关闭、`EHOME_WINDOW_TICK_INTERVAL` 这类运行参数没有任何部署模板承载 —— 「部署服务」必须先读代码。

## 4. 关键问题详解

### 4.1 P0-1：规则级坐标被前端自己的校验拦下（已修复）

**复现**：`/automation → 创建规则`，触发器选「日落」，纬度 39.9、经度 116.4、时区 Asia/Shanghai，动作 `set_mos_policy`。点击保存 →

- 表单顶部出现提示「纬度、经度、时区必须同时填写，或全部留空以继承节点」；
- 「坐标与时区」状态行在填完经纬度后仍显示「留空 = 继承节点…」，选完时区后变成「必须同时填写」；
- Network 面板 **没有任何 POST**（前端校验直接 return）。

**代码路径**（`frontend-shared/src/views/automation/`）：

```text
AutomationRules.onSave()
  └─ validate()                               // useRuleForm.ts:372
       └─ sunLocationState(form) === 'partial' -> return '纬度、经度、时区必须同时填写…'   // :394
  └─ buildPayload()                           // 只有到这里才执行 syncCoordinates()
       └─ syncCoordinates(): form.latitude = parseCoordinate(sunLatitudeText)  // :260 / :468
```

即：**判据读的是 `form` 字段，写入却发生在判据之后**。文本层 `sunLatitudeText/sunLongitudeText`（页面持有）与 `form.latitude/longitude` 脱钩，只在提交体组装时同步一次。

**影响面**：`sun_event` 是唯一需要坐标的触发器；节点级坐标又没有写入路径（P0-2），所以这不是「某条分支不好用」，而是**整类规则无法创建**。对照实验同样失败：三项全空 → `validate()` 通过（判为继承）→ 后端按 O-7 fail-closed 返回 400。

**为什么既有测试没抓到**：`sunEvent.spec.ts` 只测纯函数 `sunLocationState()`；`AutomationRules.spec.ts` 覆盖保存/风险/预检，但没有一条用例走「填写经纬度文本 → 保存」的真实路径。纯函数绿 + 页面用例绿，中间那层绑定没人测。

**修复**（未提交，随验证记录留档）：

```ts
// useRuleForm.ts
import { computed, reactive, ref, watch } from 'vue'
...
watch([sunLatitudeText, sunLongitudeText], syncCoordinates, { immediate: true })
```

选择 `watch` 而不是「在 `validate()` 开头调一次 `syncCoordinates()`」：后者只让保存通过，界面的「坐标与时区」状态文案仍会长期显示「继承/必须同时填写」，用户看到的因果与实际提交内容不一致。

**验证**：状态行变为「本规则使用规则级坐标与时区，不继承节点」；POST 体含 `latitude/longitude/timezone`；precheck 返回风险动作；勾选确认后规则落库且 `risk_acknowledged_at` 非空；`pnpm vitest run src/views/automation` → **130 passed**（补用例后 131）。

**回归用例（2026-11-13 已补，变异自证）**：`AutomationRules.spec.ts` 新增「规则级坐标三项填满时必须可保存，且 payload 携带三项」——填 lat 39.9 / lon 116.4 / tz Asia/Shanghai → 断言 `sun-location-state[data-state]=override` 且 `createRule` 收到三项。把 `watch` 注释掉重跑：**该用例红**（状态退回 partial、createRule 未被调用），恢复后绿。

**建议验收判据**（防回归）：新增一条页面级用例 —— 打开创建规则 → 选日出/日落 → 填 lat/lon/tz → 断言「坐标与时区」状态为 `override` 且保存时 `buildPayload()` 含三项；把 `watch` 删掉应使该用例变红。

### 4.2 P0-2：节点级坐标根本没有写入路径

- `models.Node` 定义了 `Latitude/Longitude/Timezone`（`models.go:86`），但全仓**没有**任何 handler 写这三列（`grep 'Latitude' backend/internal/api` 只命中自动化规则）；
- 节点详情页明确裁掉了位置卡（`NodeOverview.vue:4` 注释：「位置/备注/时区/搜索/通知卡已裁剪（后端模型无对应字段）」——该注释本身也已过时，模型其实有字段）；
- 设计文档 O-7 的语义是「规则级覆盖，留空继承节点；节点也没有则拒绝保存」，但节点值永远为空 ⇒ **留空必然 400**，只能填规则级坐标 ⇒ 又撞上 P0-1。

**建议**：二选一。① 补 `PUT /api/v1/nodes/:id/location` + 节点编辑 UI（与 O-3 的「节点级权威」一致）；② 明确废除节点级坐标（产品裁决），把规则编辑器的坐标改为必填并更新设计文档与错误文案。

### 4.3 P1-1：新库上 `unified_data` 写失败（噪声 + 浪费）

**证据**：后端日志每 3 秒一条：

```text
INSERT INTO "unified_data" (...) RETURNING "id"
ERROR: relation "unified_data" does not exist (SQLSTATE 42P01)
WARN databus: failed to persist parsed sensor data {consumer: sensor_parser, edge_device_id: 1, ...}
```

**但数据没丢**：解析后的帧照常进 L2 帧表（`select count(*) from telemetry_frame` → 505），BMS 页/最新值/自动化全部正常。也就是说这是**纯副作用失败**，代价是每设备每帧一次无效 INSERT + 一条 ERROR，并且会让排障者误判「BMS 数据没有入库」。

**根因**：2026-11-08 的硬切换把读取切到 L2 帧表，并规定生产用 `EHOME_TELEMETRY_UNIFIED_WRITE=false` 停写；但代码默认值仍是「写」，且新库不再创建该表。`docker-compose.yml`、`docker-compose.example.yml`、`.env.example` 都没有这个变量（`grep` 仅命中 docs 与 .tmp-* 演练脚本）。

**建议**：
1. 缺表即跳过（启动时探测一次 `to_regclass('unified_data')`，缺失则置 `unifiedWriteEnabled=false` 并打一条 INFO 说明）；
2. 或把默认值改为 false（与文档裁决一致），并在 compose/.env.example 显式列出；
3. 日志降级为一次性 WARN + 计数指标，而不是每帧 ERROR。

**处置记录（2026-11-13，用户裁决「直接 false」）**：

- 代码：`databus/telemetry_write_gate.go` 的 `resolveUnifiedWriteEnabled(db)` 改为
  「未设置/解析失败 ⇒ false；显式 true ⇒ 表存在才 true，否则 WARN + false」；
  调用点传入 `db`。停写分支的位置不变（仍在 latestSink / L2 帧表 / L3 rollup **之后**），
  因此 `/latest-data`、图表、告警、自动化都不受影响。
- 测试：新增 `databus/unified_write_default_test.go`（7 条表驱动，含「显式 true 但表不存在 ⇒ 仍停写」）；
  已有的 L1 门禁/软删节点用例在测试夹具里**显式打开**该历史写路径（它们测的是写路径本身，
  不应依赖生产默认值），`go test ./internal/databus/` 全绿。
- 模板：`.env.example` 增补遥测段（含本开关与心跳间隔说明）；`docker-compose.yml` 显式写
  `EHOME_TELEMETRY_UNIFIED_WRITE: "false"`，避免「默认值改了没人知道」。
  **（同日稍后随全量退役一并删除 —— 代码已无写入路径，变量不再被读取。）**
- **全量退役（同日，用户「完成 unified_data 废除」）**：删除 L1 写入门禁与 INSERT、
  `internal/backfill` 整包、`/api/v1/system/backfill` 与前端进度卡、两处读回落；
  新增 `ehomectl retire-unified-data`（默认只读，`--yes` 才 DROP）。
  实施记录：[unified_data整表退役-实施记录-2026-11-13.md](unified_data整表退役-实施记录-2026-11-13.md)。
- 运行期复核：重启本机后端 + 模拟节点后，`42P01` 计数 = 0，`telemetry_frame` 持续增长
  （见验证记录 §6 环境复核）。

### 4.4 P2-1：成功触发无 INFO 日志

两次事件在 DB 各有 `executed` 行，但后端日志中 `rule_id` 只出现 1 次（23:02:33 的首 tick 保守跳过），两次真实触发只在 23:08:13 打出「automation: resolved system actor lazily」。日出触发（23:12:13）**零日志**。

**影响**：现场「规则到底有没有求值/为什么没动作」只能查库；对验收也是负担（本次靠 DB + 模拟器日志才能对齐到毫秒）。

**建议**：事件落库处补一条结构化 INFO：`rule_id, trigger_type, sun_kind, event_at, result, command_id, elapsed_ms`，并在失败分支保留原因码。

### 4.5 P2-2：触发历史「触发值」为空

UI 触发历史表的「触发值」列显示 `-`（`automation_events.trigger_value` 为空串）。对传感器规则它应是数值，对 sun_event 语义上应是「哪一次日出/日落」。当前只能靠时间反推，无法自证「用的是 17:08:12 那次日落」。

**建议**：sun_event 事件写入 `trigger_value`（如 `2026-11-13T17:08:12+02:00`）或至少在 `detail` 里带 `event_at` 与偏移。

### 4.6 P2-3：新库 BMS 页长窗图表报错

首次打开 BMS 详情页即可见两处红字：

- 「保护历史加载失败：change 长窗读路径不可用（rollup 覆盖未验证…），且窗口 720h 超过纯帧分段解码上限 8 天」；
- 「温度趋势/SOC 与电流加载失败：查询窗口 24h 超过帧表单次解码上限 1h，且该窗口尚未被分钟聚合覆盖」。

这与本任务无关，但**新部署的首屏就有 3 处红色错误**，与「验证成功」的观感直接冲突。根因是新库 rollup 尚未回填（回填是后台任务，且长窗需要覆盖验证）。建议：覆盖未就绪时把默认窗口降到 1h 并给出「聚合回填中」的提示，而不是报错。

### 4.7 P3-1：部署文档与编排漂移

- README 架构图仍是 EMQX/MQTT + 「ehome-web 容器（8080）」，实际 3.0 是设备 mTLS 直连（8443），`docker-compose.yml` 里没有 EMQX；
- 本机部署需要自己拼 `EHOME_DEVICE_ENABLED/ADDR/CERT_FILE/KEY_FILE/CLIENT_CA_FILE`、`EHOME_WINDOW_TICK_INTERVAL` 等参数，`.env.example` 无一项；
- `.env` 不存在，`docker compose` 的必填变量（POSTGRES_PASSWORD 等）只能从 Makefile 默认值或历史环境推断；
- 设备监听默认关闭（`EHOME_DEVICE_ENABLED` 未设 = false），部署者若只跑 compose，会得到「节点永远离线」的静默失败。

**建议**：补一份「本机独立部署（含模拟节点）」操作文档 + `.env.example` 增补设备/遥测/自动化相关变量；README 架构图与端口表按 3.0 更新。

## 5. 做得对的地方（可复用）

1. **传输层仿真复用真实实现**：模拟器直接依赖 `pkg/frame` / `pkg/protoframe`，与固件同一份编解码；一旦协议改字节，模拟器立刻编译失败或握手失败，不会「仿真通过、真机失败」。
2. **安全红线**：node_id 强制 `sim-` 前缀（仓库既有约束），避免误连同网段真机。
3. **前端可测性**：规则表单大量 `data-test` 属性，Playwright 无需依赖文案/层级即可稳定定位（本次仅 2 处绕行：Element Plus 的 tab 需点 `.el-tabs__item`；风险确认是原生 `input[type=checkbox]`）。
4. **风险动作门禁成链**：目录风险标签 → precheck `risk_actions` → 逐项勾选 → 规则级 `risk_acknowledged_at` → 自动路径放行；本次完整走通，未出现「确认了但仍被拒」。
5. **回读校验**：`set_mos_policy` 的 bounded 写+读回 `fet_status` 对账，使「命令 SUCCEEDED」等价于「设备状态确实变了」，而不是「帧发出去了」。这是本次能给出 `0x03→0x02→0x03` 位级证据的前提。
6. **证据三角**：UI 截图（人可见）+ DB 行（权威）+ 设备侧日志（wire 字节），三者时间戳可对齐到毫秒。

## 7. 未验证项与风险

- **回读失败负对照未跑**：本次只验证了成功路径。建议补一条「BMS 回读 `fet_status` 与请求不一致 → 命令 `FAILED` 且 UI 显示原因」的负对照（模拟器加一个 `-ignore-mos` 开关即可）。
- **未验证真实硬件**：模拟器不覆盖串口时序、电气保护、BMS 固件错误帧。
- **冷却与日熔断**：本次两规则各只触发一次，未验证「同日再次满足条件时被 `max_daily_exec`/`cooldown` 抑制」的分支（事件表 `suppressed_*` 结果码）。
- **重启语义**：未单独验证「事件已过后重启，首 tick 保守跳过；下一 tick 是否补触发」的完整边沿（日志里已见到首 tick 跳过行，但没有针对同一事件的重启演练）。
- **时间注入**：`EvaluateClockRulesAt` 仅测试可用，生产验证必须等真实天文时刻；本次通过「规则级坐标」把事件挪进验证窗口，属于配置手段而非时钟伪造。

## 8. 流程复盘（耗时与卡点）

| 阶段 | 耗时（约） | 卡点 |
|------|-----------|------|
| 勘察代码/协议 | 25 min | 传输从 MQTT 改成 mTLS，需重读 frame/protoframe 与 commandexec 门禁；`scripts/esp32_simulator.py`（MQTT）已失效 |
| 部署（DB/PKI/后端/前端） | 15 min | `.env` 缺失、设备监听默认关闭、tick 参数无文档；需要自己生成 PKI |
| 写模拟器 | 30 min | ChannelCmdV2 的 Ack/Final 身份字段（command_id/digest/attempt/boot_id）必须逐一回显；有界批次信封格式只在固件 C 代码里 |
| 前端设备创建 | 20 min | Element Plus 下拉/标签页的点击目标不是文字节点 |
| 规则创建 | **50 min（返工 3 次）** | P0-1 让保存静默失败；先怀疑选择器，后用 Network 面板确认「0 请求」才定位到 `validate()` |
| 事件等待与取证 | 15 min | 事件时刻固定，必须按天文时间安排；长等待曾撞上工具 120s 超时导致进程被杀一次 |

**可自动化的点**：PKI 生成、后端环境变量拼装、模拟器启动、规则创建（本次的 `ruleform.cjs`）均可脚本化；建议把「模拟节点 + 日出日落规则」做成本仓库的 `make` 目标或 `backend/simulation` 的一个场景（后者已具备 mTLS 与设备证书能力）。
