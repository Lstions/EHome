## 1. 先厘清：现在其实叠了 4 层东西

「风险」这个词在代码里被用在了四个不同层次上，混在一起讨论就会得出「全删」或「全留」两个极端结论。分开看：

| 层 | 它回答的问题 | 载体/落点 | 是否多余 | 建议 |
|---|---|---|---|---|
| L1 风险分级 | 这个动作危不危险 | `deviceaction.RiskLevel`（normal/elevated），`risk.go:12-49`，注册期由 4 级驱动方言归一化（`definition.go:118-123`） | 不多余，但对外漏了三份字段 | 保留，收敛成 1 个对外字段 |
| L2 确认弹窗 | 人点下去之前知不知情 | 设备页 `ActionConfirmationDialog.vue:1-17`、BMS `BmsMosStatus.vue:76-89` | 不多余，已经足够干净 | 原样保留 |
| L3 一次性令牌 | 这次点击能不能被重放/伪造 | `commandexec/confirmation.go:31-40/137-189`，5 分钟、单次、绑定 actor+设备+动作版本+参数哈希 | 不多余（用户不可见） | 保留；自动化系统路径不需要它 |
| **L4 规则级持久授权** | 这条自动化规则「曾经」被谁在保存时确认过 | `automation_rules.risk_acknowledged_at` + 请求字段 `risk_acknowledged` + V7 校验 + 执行期 `RiskAcknowledged` 旁路 | **多余** | **建议整层删除** |

用户说的「多余」= L4。下面只论证 L4；L1–L3 保留。

## 3. 为什么说 L4 是多余设计（8 条论证）

### 3.1 原始需求只要求「保存时弹窗」，没要求持久授权

[任务书-日出日落与多动作改造-2026-10-14.md:16-20](./任务书-日出日落与多动作改造-2026-10-14.md) 的原话是：风险操作要「展示风险颜色或提示，**保存时弹窗列出风险操作并二次确认**」。
没有任何一句要求把「确认过」落成一列、在动作变化时失效、在执行期作为旁路、还要配 503 与监控。现在的实现是在需求之上自建了一套状态机。

### 3.2 它不构成新的授权边界

- 规则写接口只要求 JWT：`routes.go:130-133` 整个 `/api/v1` 组只挂了 `JWTAuthWithDB`，`automation-rules` 没有额外的角色/管理员校验。
- 而手动确认令牌的铸造要求 `system_admin` 主体：`confirmation.go:146-148`。
- 也就是说：**能保存规则的人**和**被允许点确认的人**本来就不是同一个集合，而 V7 让前者通过勾选 `risk_acknowledged` 直接替后者做了决定。
- 单主体自托管部署下两者恰好等价，所以今天看不出问题；但这说明该字段不是「授权」，只是「某人勾过一个框」。真要做授权，应该在保存入口校验主体（与确认门同一条件），而不是存一个时间戳。

### 3.3 它声称的审计价值没有落地

`models/automation.go:285` 的理由是「审计需要回答何时被授权的」。实际上：

```text
$ grep -n 'audit' backend/internal/api/handler_automation.go
(无输出)
```

规则创建/更新不写 `security_audit_events`；`risk_acknowledged_at` 只在规则 JSON 里回传，前端没有任何一处渲染它（`grep risk_acknowledged_at frontend-shared/src` 只命中 API 类型注释）。
结论：这列在运行时只服务于确认门，不服务于审计；它记录的信息（保存时刻）本来就能从规则的更新时间推断。

### 3.4 「动作变化即失效」是持久化自己制造出来的问题

因为把「确认过」存成了状态，才需要回答「状态什么时候过期」。于是有了：逐 seq 比较、参数原文比较、清空规则、同请求冲突 400、存量数据三类来源的口径说明（`docs/分析/节点同步卡死与窗口补发-2026-11-18.md:72-90`）。
如果不存状态，「用户点了保存」就是这一次的授权，天然只对被保存的那份内容有效——没有失效，也没有失效漏判。

### 3.5 它制造了一个真实的功能缺陷：编辑风险动作会进入 400 死循环

这是本次分析最值得先修的一条，与「是否简化」无关。完整链路：

1. 用户编辑一条含风险动作、`require_confirmed=false`、`risk_acknowledged_at` 非空的规则，改了动作参数（例如 MOS 的充放电位）。
2. 前端提交体始终包含完整 `actions`：`useRuleForm.ts:524`。
3. `onSave` 预检返回风险动作 ⇒ 弹逐项勾选弹窗：`AutomationRules.vue:1025-1031`。
4. 用户勾选后确认，`confirmRiskSave` 固定加 `risk_acknowledged: true`：`:1101`。
5. 后端比较库中动作与传入动作，**比较项包含参数原文**（`handler_automation_actions.go:181-201`）⇒ `changed=true`。
6. `changed && risk_acknowledged=true` ⇒ 400 `action_changed_requires_reconfirmation`（`handler_automation.go:649-653`）。
7. 前端**没有**这个错误码的分支（全仓 `grep action_changed` 只命中后端与后端测试），`confirmRiskSave` 只 `catch { feedback.error('保存失败') }`：`:1105-1106`。
8. 弹窗不关、输入不变、再点一次——仍然是 `changed=true + ack=true` ⇒ 再 400。**无法通过 UI 保存**。

更糟的是：被拒的请求整体不落库（后端测试 `handler_automation_actions_test.go:253-289` 明确断言这一点），所以**旧规则继续按旧动作自动执行**。用户以为把「开」改成了「关」，实际设备仍按旧参数动作——这是自动执行场景里最危险的一种「静默不生效」。

> 注：只改名称/触发器、不动动作时 `changed=false`，不会 400；但只要动到风险动作的参数/目标/顺序，就必然卡死。也不存在「先保存一次再确认」的可行路径——第一次保存不带 ack 会被 V7 以 `risk_action_requires_confirmation` 拒绝（`handler_automation.go:1179-1182`）。
>
> 证据性质：本条是**静态代码路径推演**（本机无 Go 工具链，未跑后端测试）。后端 400 分支本身已被测试钉住（`handler_automation_actions_test.go:253-289`）；缺的是前端对该错误码的恢复分支——`grep -rn action_changed frontend-shared/src` 为空。

### 3.6 它把「每次保存」都变成了逐项勾选，包括不需要确认的场景

- 规则已经开启 `require_confirmed=true`（触发时还要人工确认一次）时，保存仍然弹逐项清单。此时保存时的授权对执行没有任何影响，纯粹是重复确认。
- 只改规则名称、冷却时间也会弹（只要动作集合里含风险动作）。
- 风险动作 3 个以上时，逐项勾选会退化成闭眼连点（设计稿自己也承认这一点：`designs/automation-sunrise-mos/README.md:211-214`）。

### 3.7 它带来了第二套判定路径与第三套文案

| 问题 | 证据 |
|---|---|
| 同一件事两个来源：卡片的徽标读本地动作目录，保存的放行读预检端点 | `useRuleActions.ts:168-178` 注释自己写了「二者分工明确」，代价是两套缓存/两种失败模式 |
| 风险原因有三层回落：预检的 `risk_reason`（后端未下发）→ 本地目录的 `risk_reason` → 「后端未下发风险原因…」占位文案 | `AutomationRules.vue:895-900`、`useRuleActions.ts:189-205`；而 `useRuleActions.ts:192` 的注释说「后端没有 risk_reason」已经过时（`jiabaida_control.go:188-208` 实际有） |
| 预检端点复制了保存端点的整条硬校验链 | `handler_automation.go:1395-1434` 与 create/update 重复 |
| 降级路径要自己拼风险清单，还要处理「目录未加载」 | `AutomationRules.vue:1035-1085` |

这些复杂度都不是「风险分级」本身的成本，而是「保存期必须判定授权、授权又必须有唯一事实源」派生出来的。

### 3.8 它把「能保存成功 = 已完成授权」从定义变成了需要证明的不变式

这句话本来可以是一句废话（保存就是授权）。现在它需要：两条目录查询、一个 fail-closed 的 503 分支（`handler_automation.go:1160-1189`）、一个专门的测试文件（`handler_automation_risk_catalog_failclosed_test.go`）、一条监控告警，以及一段解释「这个结果码正常不可达」的运维文案。
所有这些都是在维护一个不必要的不变式。

## 4. 你的目标形态：可行，但有两处必须一起改

### 4.1 分级：对外收敛成一个字段（可行）

现在同一个概念对外发了三份：`risk`（4 级驱动方言）、`risk_level`（2 级）、`requires_confirmation`（派生布尔）：`definition.go:73-84`。
前端只用后两个（`DeviceControlPanel.vue:184-196`），`risk` 字段在 `frontend-shared/src` 已无业务读取（只有类型声明与门禁测试的负例）。

建议：
- 对外**只保留** `risk_level`（normal/elevated）+ `risk_reason`，删掉 `risk` 的 JSON 输出；4 级字面量退回驱动包内部（`CurrentEngineAllows` 的 `Risk == low`、`AtMostOnce` 要求 high/critical 是引擎/能力约束，不是确认语义，不要顺手改成 2 级）。
- `requires_confirmation` 可以保留（前端直接消费，避免自己写判定），也可以删（`risk_level == elevated` 即可）。建议**保留**：它是后端唯判定点的显式派生，删了会让前端多一份比较。

### 4.2 保存：一个弹窗、一次确认（可行，且更贴近任务书）

目标弹窗（替换现在 `AutomationRules.vue:373-436` 的逐项清单）：

```text
标题：确认保存
正文：本规则包含 N 个风险操作，触发后将自动执行：
      · 设置充放电 MOS 软件策略 — BMS-01
      （只列动作名 + 目标设备，最多 5 条，之后折叠为「等 N 个」）
说明（可选一行）：开启「需人工确认」时，执行前仍会二次确认。
footer：取消（默认焦点） / 确认保存（danger）
```

理由：需求要的是「列出风险操作并二次确认」，不是「逐项签署」。一次确认 + 可读清单已满足知情要求；逐项勾选在 1 个动作时无差别，在多个动作时反而训练用户盲勾。

### 4.3 执行：`require_confirmed` 成为唯一策略（这是删 L4 的必要配套）

删掉 `RiskAcknowledged` 之后，系统路径（`ActorKind=system`）不能再被确认门拦住，否则风险动作的自动执行会永远失败（这正是当初 C5 缺陷的成因）。所以必须一起改：

- `require_confirmed=true`：planner 仍只落 `pending_confirm`，人工确认后即铸即销令牌执行——**不变**。
- `require_confirmed=false`：planner 以 system 身份直接 `Create`，**不再需要令牌**。
- 人工路径（设备页、手动触发、确认执行）：**不变**，仍走弹窗 + 一次性令牌。

语义变成了用户能一句话说清的两个开关：
> 这个动作危不危险（决定 UI 提示）；这条规则触发后要不要先问我（决定执行方式）。

### 4.4 设备页/手动路径不需要动

`ActionConfirmationDialog.vue` 现在已经是「取消 / 确认」两键 + 一行风险说明；`BmsMosStatus.vue:76` 的注释也记录了用户此前「不要在确认里加理由」的裁决。这部分已经是你想要的样子，不在此次简化范围内。

## 5. 建议的目标契约

### 5.1 动作目录（`GET /edge-devices/:id/actions`）

```text
{ id, name, description, risk_level: normal|elevated, risk_reason?, requires_confirmation, ... }
```
- 删：`risk`（4 级）。
- 保留：`risk_level` / `requires_confirmation` / `risk_reason`。

### 5.2 规则写接口

```text
POST/PUT /automation-rules  { ... , require_confirmed: bool }   // 删 risk_acknowledged
```
- 删：`risk_acknowledged` 请求字段、V7 校验、`risk_acknowledged_at` 的读写、授权失效、`action_changed_requires_reconfirmation`、`risk_catalog_unavailable` 的 503 分支。
- 留：`validateActionsCatalog`（目录存在性/参数规范化）——它与授权无关，是保存正确性的一部分。
- 留：`precheck` 端点的 `blocking_errors` / `warnings`（选择器诊断），只把 `risk_actions` 的用途从「授权凭证」降级为「弹窗清单数据」。

### 5.3 执行

```text
system + require_confirmed=false  → 直接执行（无令牌）
system + require_confirmed=true   → pending_confirm → 人工确认 → 即铸即销令牌 → 执行
user                              → 弹窗确认 → 即铸即销令牌 → 执行（不变）
```

### 5.4 删除/保留清单

| 对象 | 处置 | 备注 |
|---|---|---|
| `deviceaction.RiskLevel` 与映射 | 保留 | 唯一判定点，设计正确 |
| `Definition.Risk` 对外 JSON | 删 | 内部严重度保留 |
| `automation_rules.risk_acknowledged_at` | 停止读写；下一发布周期 DROP COLUMN | GORM AutoMigrate 不删列，需要一条 SQL 迁移 |
| `CreateInput.RiskAcknowledged` | 删 | 连同三条安全边界注释 |
| `commandexec` 确认门 | 改：system 不再看 `RiskAcknowledged` | 仅此一处行为变更 |
| `confirmation_required` 结果码 | 保留枚举、停止新产生 | 存量事件仍要能显示；`describeDeviceActionError` 的三个分支可删两个 |
| 监控告警 `EhomeAutomationConfirmationRequired` | 降级为「存量数据排查」或删除 | 不再有生产路径 |
| 规则页逐项勾选弹窗 | 替换为简单确认弹窗 | 保留风险徽标/原因展示 |
| 规则页 `ack-hint` 提示 | 删除 | 无授权语义后不再需要 |
| 事件「规则未授权」文案 | 保留为存量标签，删除新事件引导 | 存量事件可能还有 |

## 7. 取舍与风险（诚实说清楚）

### 7.1 会改变的一个真实行为：动作被升级为风险后，旧规则不再被拦

现状：某动作被驱动从 normal 上调为 elevated 后，历史规则的 `risk_acknowledged_at` 仍为空 ⇒ 自动执行被确认门拦住（落 `confirmation_required`），直到有人编辑规则重新勾选。
简化后：历史规则照常自动执行（因为规则本身没变）。

这个差异要接受或显式处理：
- **接受**：风险等级是「提示/展示」属性，不是运行期的 kill switch；动作被调用本身是用户当初的意图。产品方向（2026-11-15 简化确认、`BmsMosStatus` 极简弹窗）也支持这个取舍。
- **不接受**：那应该做一个独立的「风险等级变更检测」能力（保存/启动时对比目录与规则快照，通知或禁用受影响规则），而不是让时间戳兼职做它。注意现在的实现其实也做不到「升级即重新授权」：已授权的规则升级后不会失效，只有从未授权过的规则会被拦。

### 7.2 会失去「保存时刻」这条证据

如果确实需要，正确做法是给规则保存写一条审计事件（现在没有），而不是把时间戳塞在业务表里。审计事件还能回答「谁、从哪个 IP、改了哪些字段」。

### 7.3 多用户场景下的授权语义

当前实现下任何登录用户都能勾选授权并让规则自动执行风险动作；手动确认却要求 `system_admin`。这是不一致的。
简化后若要保持「只有管理员能让规则自动执行风险动作」，应在保存入口加主体校验（与 `confirmation.go:146-148` 同条件），这是一个**真正的授权**，成本约 1 个中间件/分支，比时间戳便宜且语义正确。单主体部署可以不做，但要在文档里写明。

### 7.4 存量数据

- 已存在的 `confirmation_required` 事件仍要能显示（保留枚举与前端标签）。
- 已存在的 `risk_acknowledged_at` 值在停止读取后无副作用；建议保留一列一个发布周期再 DROP，便于回滚。

| 阶段 | 内容 | 为什么这个顺序 |

| P0（止血，独立于简化） | 修 400 死循环：把「changed + ack」从 400 改为「ack 对传入的这份动作集合生效」，即保存成功后写新时间戳；或前端在收到该错误码后重试一次不带 ack 的保存（但需同时放宽 V7，否则第二跳仍 400） | 这是线上可触发的功能缺陷，与是否删除 L4 无关 |
