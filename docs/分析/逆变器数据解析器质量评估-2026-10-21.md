## 零、一句话结论与评分

**接口骨架是这个仓库里最讲究的部分（命令上下文、形状绑定、物理闸门、fail-closed 都有），但"讲究"只覆盖了受控动作（ControlAction）这一条路；轮询/摄入主路径仍靠形状嗅探，并在生产上真实写出过 2501 条污染数据。** 同时字段语义有 1 处实锤错误（把风扇转速标成温度），测试还把该错误当契约锁死。

| 维度 | 评分 | 一句话理由 |
|---|---|---|
| 接口设计 | **7/10** | `CommandAwareDriver`/`VerifyControlAction` 的分层与"形状绑定"思路正确且领先同仓其它驱动；扣分在**同一张命令表被复制 4 份**、`ParseData` 仍以形状嗅探为兜底。 |
| 逻辑设计 | **4/10** | fail-closed 与 fail-open 并存且边界随手写（`parseFloat` 遍地 0 兜底）；8 字段帧的分派路径根本走不到 `parseHTEMP`。 |
| 实现质量 | **5/10** | 注释极其详尽（罕见的优点），但存在**不可达动作**、**幽灵传感器**、**测试保护缺陷**三类硬伤，且无一条测试能发现"温度帧被读成电池帧"。 |
| 契约/可运维性 | **4/10** | 入库时间戳用 `time.Now()` 而非设备时间（设备帧里**有**时间却被丢弃），导致重放/延迟不可观测；`raw_hex` 已全量落库却无人使用。 |

> **修复后（§七，2026-10-21 晚）**：接口设计 **7→8.5**、逻辑设计 **4→8**、实现质量 **5→8**、契约/可运维性 **4→4**（唯一未修项受固件阻塞，见 §7.4）。
> 主要变化：命令表单一真相源、ParseData fail-closed、HTEMP 位序修正、静默 0 兜底清零、7 条不变式用例 + 生产帧回放防线。
> 评分仍不打满分的原因：11 字段旧形状与 HBMS1/HEEP1 缺真机样本（§7.6），契约层的设备时间依赖固件。

## 一、接口设计

### 1.1 分层是清晰的（这是优点，给证据）

驱动能力被拆成 4 个**可选**接口，解析型驱动不会被迫暴露控制面：

| 接口 | 位置 | 职责 |
|---|---|---|
| `Driver` | `drivers/registry.go:17-32` | 最小契约：`ParseData` + 元数据 + `GetSensorDefinitions` |
| `CommandAwareDriver` | `registry.go:87-93` | 同形应答靠命令上下文消歧（HPV/HPVB） |
| `ControlActionProvider` | `action.go:60-62` | 声明式只读动作目录 |
| `ControlActionVerifier` | `action.go:133-135` | 动作级权威校验（与 `ParseData` **故意分离**） |
| `CompiledControlPlan` 系列 | `action.go:95-123` | 只为 bounded_sequence 预留，浏览器不能注入脚本 |

`action.go:125-129` 那句注释写得对：*"a setter's ACK or readback is not a sensor sample"* —— 把"校验"和"取数"分开是正确判断。

### 1.2 但 `ParseData(raw []byte)` 本身是**没有类型信息的接口**

`ParseData` 签名里没有任何命令/长度/方向信息，驱动只能靠"字段数 + 字段长相"反推这是哪条命令（`inverter_techfine.go:362-372` 的注释直接承认了）。这带来两个必然后果：

1. **分支顺序即语义**：任何一次顺序调整都会改变解析结果，而分支表只能靠注释维护；
2. **同形状必冲突**：8 字段的 HTEMP 应答与 7 字段的 HBAT 判断仅差一个 `len>=7`，见 §2.1。

`CommandAwareDriver` 是对这个缺陷的**补丁式修正**（`ParseDataWithCommand` + `techfineParserFor` 精确分派，`inverter_techfine.go:489-566`），方向完全正确，但**它只覆盖了"有命令上下文"的调用方**：

```go
// backend/internal/databus/consumers_heavy.go:315-335
} else if commandAware, ok := drv.(drivers.CommandAwareDriver); ok {
    if evt.CommandTemplateID == 0 {
        // 早退：无上下文就不采信（正确）
        return
    }
    var template models.ConfigTemplate
    if lookupErr := c.db.Where("id = ? AND node_id = ?", ...).First(&template).Error; lookupErr != nil {
        return   // 查不到模板也早退（正确）
    }
    drvData, err = commandAware.ParseDataWithCommand(merged, template.WriteData)
} else {
    drvData, err = drv.ParseData(merged)   // ← 形状猜测兜底仍在
}
```

**正确性依赖的是"上游永远给得出 template"**，而不是驱动自身。`registry.go:85-86` 还专门写了 *"Callers must not fall back to Driver.ParseData"* —— 这条纪律没有任何机制强制，只有注释。**接口设计上缺一个"没有上下文就必须显式失败"的类型级保证**（例如把 `ParseData` 从 `Driver` 里挪走，只留 `ParseDataWithCommand`）。

### 1.3 同一张命令表被复制了 **4 份**

| # | 位置 | 形态 |
|---|---|---|
| 1 | `ControlActions()` `inverter_techfine.go:95-109` | `techfineReadAction(id,name,cmd,desc)` × 11 |
| 2 | `VerifyControlAction()` `129-134` | 内联 `map[string]string` × 11 |
| 3 | `techfineParserFor()` `543-566` | `switch` × 9（缺 HPV/HPVB，靠前置 if） |
| 4 | `GetCommandTemplates()` `1393-1405` | `[]pollCmd` × 11 |

`GetCommandTemplates` 的注释（`1384-1385`）自称 *"与 ControlActions()/VerifyControlAction() 使用同一张命令表，避免两处各自维护一份 ASCII 命令而产生漂移"* —— **这句话与事实不符**：它只复用了 `asciiToHex` 这个编码函数，命令字面量仍是第 4 份拷贝。真正共享的只有一个 `asciiToHex`。

**已发生的漂移（T，实测）**：`read_eeprom` 在动作目录里 `Enabled: true`（`114`），`techfineActionMinSensors["read_eeprom"] = 15`（`219`），但 `parseHEEP1` 无论帧多完整都**只产出 4 个字段**（`1272-1277`）。

```
read_eeprom len=73 -> n=0 err=techfine read_eeprom: response yielded only 4 sensor values, expected at least 15
read_eeprom len=73 -> n=0 err=... （换 3 种完整帧，全部同一个错）
同一帧走 ParseData -> n=4 err=<nil>  eeprom_model_source/eeprom_max_charge_current/eeprom_output_voltage/eeprom_output_frequency
```
⇒ **`read_eeprom` 是一个永远不可能成功的已启用动作**，用户点它必然失败，且报错说的是"帧被截断"（误导方向）。

### 1.4 传感器定义与实际产出不一致（幽灵传感器）

`GetSensorDefinitions()` `273-353` 声明 60 个 sensor。生产 2 天实测 device_id=15 只出现 **59** 个，其中：

```
fan1_speed/fan2_speed 行数 = 0   （声明了，8 字段路径永不产出，只有 11 字段旧形状才有）
```
`software_version`/`software_date`/`protocol_type` 同理：来自 HIMSG1/QPRTL，而 `GetCommandTemplates` 给它们的 `IntervalMs` 默认 0（`1404`），且 `MaxCommandsPerEdgeDevice` 限制同时最多 3~6 条——生产 `command_intervals` 实际启用了 6 条，都不含这两条。**声明面 ≠ 产出面，没有任何一致性校验**。

## 二、逻辑设计

### 2.1 【P0 已实证】8 字段 HTEMP 帧在无上下文路径下被读成电池数据

`ParseData` 的分支顺序（`374-482`）：

```go
if len(fields) >= 10 && len(fields[1]) >= 8 && isAllBinary(fields[1]) { return d.parseHBMS1(fields) }  // 419
if len(fields) >= 6 && strings.Contains(fields[1], ":")              { return d.parseHGEN(fields) }    // 425
if len(fields) >= 15 && len(fields[0]) == 1 && ...                   { return d.parseHEEP1(fields) }   // 431
if len(fields) >= 11                                                  { return d.parseHTEMP(fields) }   // 438  ← 8 字段落不到这里
if len(fields) >= 6 && strings.Contains(fields[0], ".")               { return d.parseHGRID/parseHOP}   // 447
if len(fields) >= 7                                                   { return d.parseHBAT(fields) }    // 457  ← 8 字段落在这里
```

真机 HTEMP 是 **8 字段**（`(041 037 032 033 041 100 100 11...`），`len>=11` 不命中 ⇒ 落到 `len>=7` 的 `parseHBAT`。

**实测（docker golang:1.26.5 跑真机帧）**：

```
[A: 8-field real HTEMP via ParseData (no cmd ctx)]
  battery_voltage            = 37 V      ← 实际是 inverter_temp
  battery_capacity           = 31 %      ← 实际是 boost_temp
  battery_charge_current     = 33 A      ← 实际是 transformer_temp
  battery_discharge_current  = 37 A      ← 实际是 max_temp
  bus_voltage                = 30 V      ← 实际是 pv2_temp 位
  err = <nil>                            ← 无任何报错
```

**这不是纸面推演，生产上真的发生了（T）**：

```sql
-- battery_voltage 正常应在 48~58V（48V 系统）
select count(*) total, count(*) filter (where value<45) polluted,
       count(*) filter (where value>1000) absurd
from unified_data where device_id=15 and sensor_name='battery_voltage';
--  26847 | 2501 | 5
```

污染窗口 `2026-10-18 14:46 → 2026-10-19 11:43 UTC`。抓该时刻原始帧：

```
2026-10-18 22:06:22 | raw_hex=2830323720303339...  → "(027 039 033 035 039 030 030 1100...00\r"
                    | sensors = battery_voltage=39, battery_capacity=33,
                                battery_charge_current=35, battery_discharge_current=39, bus_voltage=30
```
**raw_hex 是温度帧，投影出来的却是电池字段。** 逐小时统计显示污染是"每 30s 一条"叠加在真 HBAT（每 10s 一条）之上，比率恒为 120:360/小时 —— 与 `read_temperature=30000ms`、`read_battery=10000ms` 精确吻合。

**修复边界与代码提交精确对齐（T）**：
- 污染最后一条：`2026-10-19 11:43:00.887844 UTC`
- `git log -S 'techfineParserFor'` → `eaf7888d` **2026-10-19 19:44 +08:00 = 11:44 UTC**

⇒ 该缺陷由 `eaf7888d`（"命令上下文拿到了却没用"）修复并上线，数据边界与提交时间差 1 分钟。这是本仓库少有的**"缺陷-修复-数据"三方对齐**证据。

**结论**：该 P0 已修，但修法是在**调用侧**加了精确分派表，`ParseData` 的 `len>=7 → parseHBAT` 兜底分支**原样保留**。任何一次"命令上下文丢失"（固件不回填 field 9、模板被 prisma 清掉、回放脚本、新接入路径）都会让同样的污染重演。`inverter_techfine_regression_test.go` 只锁了"HGRID 形状不被当 HBAT"，**没有一条测试锁"HTEMP 形状不被当 HBAT"**。

### 2.2 【P1 已实证】两个字段语义错误：风扇转速被当成温度

`parseHTEMPCompact` 把 8 字段帧的 `[0..6]` 全部当温度（`1036-1043`）：

```go
{Name: "pv2_temp",          Value: temps[5]},   // ← 实际是 fan1_speed(%)
{Name: "dc_rectifier_temp", Value: temps[6]},   // ← 实际是 fan2_speed(%)
```

5545 帧真机数据（T）给出三重否证：

| 判据 | 观测 | 结论 |
|---|---|---|
| 取值基数 | `field[5]`/`field[6]` 只有 3 个取值 `{30, 50, 100}`；其余 5 位各有 11~24 个取值 | 是档位百分比，不是温度 |
| 两路关系 | `field[5]==field[6]`：**5545/5545 = 100%** | 双风扇同步调速 |
| 与风扇位串联动 | 位串前 2 位 `00` 时 f5≡30（756 帧）；`11` 时 f5∈{30,50,100}（3754/365/670 帧） | 风扇不转=30%，转起来升到 50/100 |

⇒ 这两个字段**就是 `fan1_speed`/`fan2_speed`**。

**第四条旁证（硬件事实）**：本机是 **PV1-only** 机型（用户确认；协议 V0.5 把 HPVB 列为可选的独立一节）。
一台没有第二路 PV 的机器不可能上报"PV2 温度"；而协议 V0.5 的 HTEMP 摘要只列
「PV/逆变/升压/变压器温度、风扇状态」，压根没有 `pv2_temp`/`dc_rectifier_temp` 这两个名字。
它们是 11 字段布局里第 9/10 位的候选语义，本机 8 字段应答根本不含这两位。驱动把它们标成 `°C` 写库，前端因此看到"100℃ 温度"（`第三轮UI修复-2026-10-21.md` §2.2 记录的"只有 30/50/100 三档、不是温度"现象，此处给出完整机理）。

驱动的注释 `1002` 写"7 个温度 + 1 个 20 位状态串"，`942-943` 的示意图也标"7 个温度值" —— **两处都错**：真机帧是 **5 温度 + 2 风扇转速 + 1 状态位串**。

### 2.3 fail-closed 与 fail-open 并存，边界随手写

驱动里有两套完全相反的错值策略：

**fail-closed（好）**：`checkRange` `608`、`hbatMaxPlausibleVoltage` `626`、HTEMP `[-40,150]` `1023`、HSTS 13 字符 `657`、PV 功率宽度 `>=4` `903`、HBMS1 温度哨兵 `1177`。
**HBMS1 温度哨兵是设计亮点**：`tempRaw==0` 时**不产出** `bms_temp` 而不是写 -273.15℃（`1177-1201`）。生产核实：设备未接 BMS，`bms_temp` 行数 **0**，`bms_soc` 有 478 行 —— 哨兵按设计生效。

**fail-open（坏）**：`parseFloat` `1287-1290` 解析失败返回 0，被当作真实值写库。使用者：

| 位置 | 字段 |
|---|---|
| `parseHOP:763-765` | apparent_power / active_power / load_percent |
| `parseHBAT:844-847` | capacity / charge_current / discharge_current / bus_voltage |
| `parseHGEN:1086-1089` | daily/monthly/yearly/total_energy（**4 个全用**） |
| `parseHBMS1:1162-1168` | 7 个 BMS 字段（含 soc） |
| `parseHEEP1:1266-1276` | 4 个 EEPROM 字段 |
| `parseHIMSG1:1225,1234` | version / date |

`parseHEEP1` 与 `parseHIMSG1` **完全不校验字段内容**，任意垃圾串都"成功"产出 0 值。这与同文件里 `parsePV` 大段论证"截断帧不能读成 0W"（`883-906`）形成直接矛盾 —— **同一个作者、同一份文件、两套哲学**。

**另一处 fail-open**：`parseHBMS1:1135` `if len(status1) >= 8` —— 长度不足时 8 个告警标志全部保持 0，即"一切正常"。这正是 `parseHSTS` 在 `657` 明确拒绝的失败模式（注释 `652-656` 称之为"最危险的一类"），但 HBMS1 没跟上。

### 2.4 时间戳：设备时间被解析后丢弃

`parseHGEN` 读到 `fields[0]=YYYYMM`、`fields[1]=HH:MM`（协议注释 `1074-1075`），但**只取 4 个电量值，时间字段直接不读**（`1086-1096`）。

入库侧，`consumers_heavy.go:370,379`：

```go
now := time.Now()                       // 入库时刻，不是采集时刻
records = append(records, models.UnifiedData{ ..., Timestamp: now })
```

`DataEvent.Timestamp` 字段存在（`databus/bus.go:16`）但**全仓无消费者**。后果：
- MQTT/worker 排队延迟直接进时间轴（温度序列出现 3s/150s 等非 30s 间隔，实测 42 种不同间隔）；
- 无法用设备时间做帧重放/陈旧帧检测 —— 而这正是锯齿排查所缺的能力；
- 同一批 12 个 sensor 共享一个 `now`，这一点是正确的（实测 device_id=2 单帧 12 字段时间戳完全相同）。

### 2.5 单位与量纲

单位是驱动**自报字符串**原样透传（`SensorData.Unit`），没有量纲校验。于是：
- `pv2_temp` 单位写 `°C` 但值是 `%`（§2.2）；
- `fan1_status`/`fan2_status` 单位空串，值 0/1，但 `work_mode` 也是空串值 0~6 —— **两者在前端无法靠单位区分**；
- `software_version` 用 float64 存 `0000.03 → 0.0003`（`1221-1231`），`software_date` 用 float64 存 `20230220`（`1234`）。数值化版本号/日期是反模式，且入库时被再转一次（生产实测 `software_version=32`，是浮点残留）。
- **命名与协议不符**：`eeprom_model_source` 实为协议里的「工作模式」（0 UTI / 1 SUB / 2 SBU）；
  `pv2_temp`/`dc_rectifier_temp` 则是「把风扇转速位硬取一个温度名」。这类「名字比事实更持久」的错误，
  正是前端三轮修复都在绕它走的根因（详见 §2.2）。

## 三、实现质量

### 3.1 做得好的（客观列出）

1. **注释密度与诚实度罕见**。`1008-1010` 明写"其余位置只能按厂商位序约定归属，实测期间恒定不变，无法用数据自证"；`4.3` 节外的 `1171-1176` 记录了 BMS 绝对零度缺陷的真实发现过程。这种"标注不确定"的纪律值得推广。
2. **每个 fail-closed 判据都配了反向验证说明**，例如 `inverter_htemp_real_test.go:23`"把 8 字段分支去掉，本用例立即变红"。这是本仓库最好的测试写法。
3. **HBMS1 温度哨兵**（§2.3）是正确设计且生产已验证。
4. **`expectActionSensors` 双判据**（族前缀 + 最小字段数，`231-252`）思路正确，能同时拦"喂错形状"和"同族截断"。
5. 测试覆盖了 **48 个** Techfine/Inverter 用例（源文件共 48 个 `func Test`），全部通过（`go test ./internal/drivers/ -run 'Techfine|Inverter'` → `ok`，实跑 `--- PASS` 48 条）。

### 3.2 测试保护了缺陷（最严重的一条）

`inverter_htemp_real_test.go:33-43`：

```go
temps := []string{"pv_temp","inverter_temp","boost_temp","transformer_temp",
                  "max_temp","pv2_temp","dc_rectifier_temp"}
for _, name := range temps {
    ... if s.Value < -40 || s.Value > 150 { t.Fatalf(...) }
}
```

`field[5]=100`、`field[6]=100` 恰好落在 `[-40,150]` 内 ⇒ 断言通过。**这条用例把"风扇转速被标成温度"当成契约锁死了**，任何想修正字段语义的人会先看到它变红，从而被劝退。

同类问题：`inverter_bms_temp_test.go`、`inverter_dispatch_test.go` 都只测"某形状不被误判成另一形状"，**没有任何用例断言"HTEMP 8 字段帧经 ParseData 必须失败"**（而它确实会 succeed 并返回 battery_*）。补上这条用例，`ParseData` 的 `len>=7` 兜底就能被钉死。

### 3.3 `disabled`/`enabled` 状态与实际能力不符

`ControlActions` 注释 `28-45` 用 47 行论证"11 个动作全部 Enabled=true 是安全的，因为它们都是纯只读查询，错帧只会超时不会损坏状态"。这个论证**只对"写"成立**，忽略了读动作的**数据污染风险**：错帧不会损坏逆变器，但会往库里写假数据。生产 2501 条污染正是这条"读动作无副作用"假设的反例。且 `read_eeprom` 永远失败（§1.3）。

### 3.4 无效的 `ReadSize` 语义

`techfineReadAction` 一律 `ReadSize: 256`（`118`），注释 `70-93` 用 24 行解释"256 是节点上界而非真实行长"。但同一驱动的 `GetCommandTemplates` 用 `ReadLength: 0`（`1413`）走"行空闲定帧"。**同一条命令在两条路径用两套定帧语义**（`ReadSize=256` 硬上界 vs `ReadLength=0` 软边界），行为差异只能靠人记。

## 五、改进建议（可执行，按收益排序）

**P0-a｜把 `ParseData` 的兜底改成 fail-closed**
删掉 `len(fields)>=7 → parseHBAT` 的隐式兜底，改为：先按形状判定候选集合，**候选数≠1 就报错**（`inverter_techfine.go:374` 起）。8 字段帧的候选集合是 `{HTEMP(8), HBAT(>=7)}`，必须要求命令上下文才能消歧。配套用例：*"8 字段温度帧经 `ParseData` 必须返回 error"* —— 该用例在现状下会红，正好证明缺口。

**P0-b｜合并命令表为单一真相源**

**P1-a｜修正 `field[5]/field[6]` 语义**
`parseHTEMPCompact` 改为产出 `fan1_speed`/`fan2_speed`（单位 `%`），不再产出 `pv2_temp`/`dc_rectifier_temp`。同步改 `GetSensorDefinitions`、`techfineActionSensorFamily["read_temperature"]`、`inverter_htemp_real_test.go`。历史 5558 条 `pv2_temp` 脏数据保留（可加注说明），前端可立即恢复"风扇转速"展示。

**P1-b｜`parseFloat` 收口**
把 0 兜底限定在"确认可缺省"的字段；其余改为返回 error。建议直接删除 `parseFloat`，全部改 `strconv.ParseFloat` + 显式错误（与 `parsePV`/`parseHGRID` 现有写法一致）。

**P2｜补三类缺失用例**

### 7.4 为什么时间戳缺陷没修（根因在固件，附证据）

§2.4 说「设备帧里有时间却被丢弃」。本轮查清了更根本的事实：

- `parseHGEN` 读到的 `YYYYMM`/`HH:MM` 只在 HGEN 应答里，11 条命令中仅此一条带时间；
- 协议层已有 `DataBatch.base_timestamp_us + delta_us`（`nodemgr/handler_data_batch.go:317`），
  也一路传到了 `DataEvent.Timestamp`（`nodemgr/worker_pool.go:133`）；
- **但固件侧该字段的来源是 `esp_timer_get_time()` = 开机以来微秒，不是墙上时间**
  （`esp32-collector/components/bus_worker/bus_worker.c:1690,1708`；
  同类注释见 `tls_guard.h:14`：「即开机以来的秒数，不是墙上时间」）。

⇒ 后端拿到的是「设备启动后第 N 微秒」，**无法换算成绝对时刻**。正确修法在固件侧（二选一）：
① 在 DataBatch 里加一次 `boot_epoch_ms`（节点在 HELLO 时已收到服务器时间，见 `handler_hello.c:135`，可据此锚定）；
② 各命令应答若含时间则透传。二者都要改固件 + 协议，超出本次范围。
**没有采用「硬把 uptime 当 epoch 写库」的做法** —— 那会把一个可见的缺陷变成不可见的错误时间轴。

### 7.5 解耦设计说明（对应「接口/数据依赖不要强耦合」）

1. **一张表 + 四个派生入口**：命令字面量、解析器、形状族、最小字段数、默认轮询周期只在一处声明。
   旧代码里这 5 类信息分散在 4 处，已经产生 `read_eeprom` 这类真实漂移。
2. **注册表在 `init` 期自校验**：ID/wire 重复、缺 Parser、`MinSensors<=0`、wire 不以 CR 结尾 —— 任一不满足直接 panic。
   「配置错误在启动时炸」比「运行时静默走错分支」便宜得多。
3. **解析器保持纯函数**：不碰 DB、不碰时钟、不读全局可变状态；输入 `[]byte`，输出 `[]SensorData`。
   唯一包级状态是只读注册表与不可变前缀表。
4. **零每帧分配的表查找**：`map[wireHex]*techfineCommand` 与 `map[ID]*techfineCommand` 在 init 建好；
   解析路径只有「查表 + 解析」，不再构造 map 字面量、不再 `&Driver{}` 新建接收者。
5. **形状判定与解析分离**：`techfineShapeRules` 只回答「这帧是什么」，parser 只回答「怎么取值」；
   两层各自可单测。`ParseData` 不猜，`ParseDataWithCommand` 精确分派。
6. **未动摄入层**：`databus/consumers_heavy.go` 与 API 一行未改 —— 驱动行为变化（更严格、更正确）
   对上层兼容（错误路径本来就 `return`，不落库）。

#### 7.7.2 交叉命令矩阵（替代原先「只覆盖 6 对」的用例）

原来的 `TestTechfineCrossCommandFramesAreRejected` 只挑了 6 个组合，注释却写「命令上下文给错也必须失败」——**过度承诺**。

| 命令 | 允许形状 | 命令 | 允许形状 |
|---|---|---|---|
| read_status | HSTS | read_temperature | HTEMP8 / HTEMP11 |
| read_grid | HGRID | read_energy | HGEN |
| read_output | HOP | read_bms | HBMS1 |
| read_battery | HBAT | read_eeprom | HEEP1 |

#### 7.7.4 第二轮变异自证（8 个实验）

| 变异 | 期望 | 实际 | 抓到的用例 |
|---|---|---|---|
| M-A `parseHGEN` 去掉 HH:MM 校验 | 变红 | ✅ | CrossCommandMatrix |
| M-B `parseHOP` 去掉形状校验 | 变红 | ✅ | CrossCommandMatrix |
| M-C `parsePV` 去掉形状校验 | 变红 | ✅ | CrossCommandMatrix |
| M-D HBMS1 短状态守卫 `<8`→`<1` | 变红 | ✅ | CrossCommandMatrix（panic）+ HBMS1ShortStatus |
| M-E HTEMP 短状态位 `<2`→`<1` | 变红 | ✅ | HTEMPShortStatusIsRejected |
| M-F `parseHOP` apparent_power 改静默 0 | 变红 | ⚠ 存活，**但属纵深防御** | 见下 |
| M-F2 `parseHOP` load_percent 改静默 0（该位不被形状谓词覆盖） | 变红 | ✅ | MalformedNumericFieldIsRejected |
| M-F3 `parseHBAT` bus_voltage 改静默 0 | 变红 | ✅ | MalformedNumericFieldIsRejected |
| M-G `parseHIMSG1` 去掉 `!isAllBinary` | 变红 | ✅ | CrossCommandMatrix |

**M-F 为什么「存活」却不是缺口**：`looksLikeHOP` 谓词要求 `fields[2]` 是全数字，所以把该位改成 "XX" 时
**形状绑定先于数值解析**把它拦住——静默 0 根本没机会发生。这正是「形状绑定 + 数值校验」两层防御的价值。
为避免该结论只靠推理，补了 M-F2/M-F3：选两个**不被形状谓词覆盖**的数值位（load_percent、bus_voltage）
做同样的静默 0 退化，两条都如实变红。

恢复自证：8 次实验后 `md5sum` 与工作区一致（`782a5741…` / `9c648056…`），基线重新全绿。

### 7.6 未修 / 风险提示（诚实标注）

1. **时间戳**：见 §7.4，受固件阻塞。
2. **`parseHEEP1` 形状未经真机验证**：生产 `read_eeprom` 轮询间隔为 0，30 小时 0 帧。
   现在至少「动作可达」（4 字段），但 23 字段完整语义仍只有协议文档支撑。
3. **11 字段旧 HTEMP 形状**同样无真机样本，保留兼容但未被生产验证；已收紧为「恰好 11 字段 + 全数字 + 风扇状态 0/1」。
4. **HBMS1（read_bms）**生产未轮询，仅用文档帧 + 历史污染帧验证。
5. **`fan1_status`/`fan2_status` 语义**来自设备自述的状态位前两位（与温度变化因果一致性极强，但无独立观测）。
6. **PG avg 聚合上线后的行为变化**（锯齿分支文档 §8.5）未在本轮处理：一旦部署，温度锯齿会被抹平且 `max_temp` 恒等式失效。
7. **`software_version` 语义变更未回填历史**（复核 R6）：新值 0.03 vs 历史 0.0003，同一时间序列会看到 100× 台阶。
   要么做一次性迁移，要么接受该传感器仅供诊断、不入趋势图。float 存版本号本身仍有损，根本解是补 `StringValue` 持久化链路。
8. **`/test-parser` 诊断端点体验变差**（复核 R7）：该端点无命令上下文，PV 现在只能报"形状歧义"；
   建议给它加一个可选 `command` 参数（或直接固定按命令 ID 分派）。
9. **风扇状态位语义已由协议确认，但"00 + 转速 30"的组合仍待厂商解释**：协议 V0.5 §5.8 明确
   风扇1/2状态 0=关、1=开，且风扇1/2转速单位是 %。3,600 帧里有 **474 帧状态位为 `00` 但转速仍是 30/30**，
   最可能是 `00` = 未使能而 30% 是设定档位（协议只写了"0：关，1：开"，没有定义"未使能"）。
   §8.10 的极限环结论只依赖"状态位切换与温度反向"这一可观测相关性，不依赖该细节。
   若 `00` = 停转，则"停转时仍报 30%"自相矛盾；更可能的解释是 `00` = "运行确认/未使能"、30 = 设定档位。
   该语义需要厂商确认（§8.10 的极限环结论不依赖它，只依赖"状态位切换与温度反向"这一可观测相关性）。
10. ~~PV 命名未验证~~ → **已澄清（用户确认 + 协议 + 生产数据三方一致）**：
    本机硬件**只有一路 PV**。协议 V0.5 把 `HPVB` 列为独立命令（可选硬件，第 51 行），
    生产侧证据：`read_pv2` 曾于 2026-10-18 15:29 ~ 10-19 12:54 轮询，7,708 条应答**全为 0**
    （电压/电流/功率三者 min=max=0），随后该命令 interval 被设为 0；
    而同期 `pv1_*` 有 53,348 条真实值（0~269.4V / 0~13.2A / 0~2,668W）。
    **设备对 HPVB 有应答（不是超时）⇒ 命令本身有效**，只是没有第二路 PV。
    因此 `read_pv2` 的前缀映射属"能力已实现、本机无硬件可验"，不算缺陷；
    `pv2_temp`/`dc_rectifier_temp` 为何不该由 8 字段温度帧产出，也由此多了一条旁证。
11. **历史「污染 2,501 条」不在当前 30h 语料内**：本轮回放语料（10-20~10-21）的 `battery_voltage` 最小 51.1V，
