- **代价**：每队列 +0.4~0.8 KiB（需先量 `sizeof(bus_cmd_t)`）；`error_count` 语义要重定义（现 `>100` 封顶）。
- **风险**：`min_free=2` 说明队列在 10 ms 事务期间持续被填，**加深只是推迟打满**。
  ⇒ 本条的定位应是"**把静默丢样本变成可观测延迟**"，不是 100 Hz 的解法。
- **验收判据**：同台架 120 s，`missing_reports` 由 1,762 → **0**、`seq_gaps = 0`；
  `samples ≥ 12,000`（允许 `full` 非 0，因为它现在代表延迟）。
- **优先级 P1**　**前置依赖**：无　**证据强度**：实测

**L-01a/b（需专门设计）**
- 红线：**不改"现场 `read_length` 保持 0"**（否则重现 2026-10-02 的 **100% 静默丢弃**）。
  替代：**帧尾校验 + 最短帧长下界**的定帧器（按厂商协议各一），并把 `bus_worker.c:2017` 的 idle 截止
  改为由期望长度/下界驱动。
- **代价**：落在 `bus_worker.c` 的 RX 状态机（**本仓事故高发区**）。
- **风险**：定帧错误 ⇒ **产出错误数值**（不是报错）——2026-10-03 已发生一次（Techfine 截断帧被采信）。
- **验收判据**：每路真实从机的**逐字节截断探针 0/N 被采信**；100 Hz 台架 `error_reports=0`。

### 2.2 L-02 —— 100 Hz 下持续发布失败（**根因已定位：两个叠加根因**）

**现状**：✅ 现象成立。**2026-10-06 实测闭环定位**：根因由两部分叠加，
**(A) 同一帧被发布两次**（已修，最小改动）；**(B) outbox 因吞吐上限而长期饱和**
（已定量，需契约/架构决策）。**验收判据未达成**，见本节末。

#### 2.2.1 定位方法（为什么这次能定下来）

上一轮只给了三个"待证实假设"，因为**只看返回码无法区分失败原因**。
本轮做了两件事：

1. **参数化闭环** —— 把调用链摊开，预测"每个失败帧应产生几条什么日志"，
   再与实测逐项比对（见 2.2.2 的 A）；
2. **加一行可机读诊断** —— 在 `mqtt_client_publish_impl` 失败分支打印
   `enqueue` 返回码 / `valid` / outbox 当前字节 / limit / qos / len。
   关键：`esp_mqtt_client_enqueue` 在 **−2 路径上没有任何日志**
   （`mqtt_client.c:2723-2727` 直接 `return -2`），所以
   "日志里没有 outbox 字样"**不能**证明"没饱和" —— 必须把数打出来。

#### 2.2.2 根因 A：同一帧被发布两次（**已修**）

**机制**：`main.c:526` 的 `mqtt_transport_register()` 无条件把 MQTT 适配器
注册进 transport manager。因此 `transport_broadcast()` **已经对 MQTT 发过一次**
（适配器 `is_connected()` 为真 ⇒ 进入 `ops->send()`），
广播失败后又执行"回退到 MQTT" `mqtt_client_publish_impl()` —— **同一帧第二次发布**。

**闭环预测 vs 实测**（分母 = `step2-ch8-115200-100hz-console.log`）：

| 量 | 预测 | 实测 |
|---|---:|---:|
| `Publish failed` | 2 × 帧 | **3,873** |
| `No transport connected` | 1 × 帧 | **1,938** |
| `Broadcast failed, falling back` | 1 × 帧 | **1,937** |
| `Failed to send via current transport` | 0（`s_current_transport` 生产恒为 NULL） | **0** |
| **PF / NT** | **2.0** | **1.998** |

**修复**（最小改动）：
- `msg_handler_publish_checked()`：广播失败后，若注册表里已有 MQTT 适配器，
  **不再重复发布**（新增 `transport_registry_has_type(TRANSPORT_TYPE_MQTT)`）；
- 该判据用**注册表查询**而非硬编码，使宿主测试（不注册适配器）仍走原路径，
  不改变既有测试契约；
- `ehome_mqtt`：新增三态 `mqtt_publish_result_t` + `mqtt_client_publish_ex()`
  （让"没连上"可判），对外语义保持不变。

**验证（可复跑）**：`scripts/l02_publish_forensics.py <log>`。
同台架 120 s、同 ch8 + 115200/10ms：

| 量 | 修复前 | 修复后 |
|---|---:|---:|
| `Publish failed` | 3,873 | **1,826** |
| `No transport connected` | 1,938 | 1,818 |
| **PF / NT** | **1.998** | **1.004** |
| ch8 实测 Hz | 26.13 | 26.26 |
| `CMD_U0` 事务 | 409/10s | 405–415/10s |

⇒ **重复发布被消除**（PF/NT 由 2.0 降到 1.0）。失败数已少于成功数
（1,826 < 3,253），"失败多于成功"这一异常特征消失。

#### 2.2.3 根因 B：outbox 长期饱和（**已定量，未修**）

诊断读数（1,826 条失败行，**100% 命中**）：

| 观测 | 值 | 含义 |
|---|---|---|
| `enqueue` 返回码 | **−2 × 1,826（100%）** | 全部是"超出 `outbox.limit`"这一条纯容量算术判定 |
| `valid` | 1 × 1,826（100%） | 操作期间 client **没有**被换代 |
| outbox 当前字节 | min 3,663 / **avg 4,082** / max 4,119（limit 4,096） | 长期贴着上限；100% 的样本 > 3,000 |
| `Memory exhausted` / `No mem` | **0** | 没走到任何分配失败 |
| `Poll read error` / disconnect / abort / TWDT | **0** | 没有断连、没有超时判死 |

**为什么必然饱和（算术）**：饱和稳态下"接收率 = 排出率"。
本台架排出率 ≈ 27/s（= 3,253 成功 / 120 s），而**供给 ≈ 41/s**
（`CMD_U0` 事务 405–415/10s）。**供给 > 排出 ⇒ 任何有限缓冲都会溢出** ——
这就是"加大 `outbox.limit` 治不了本"的原因。

**排出率为什么只有 27/s**：esp-mqtt 的任务循环**每轮只发一条**排队报文
（`mqtt_client.c:2080` 单次 `outbox_dequeue`，非循环），随后 `poll_read`
（`mqtt_client.c:2178`）等 PIGGYBACK/PUBACK；QoS1 未确认报文必须留在 outbox。
⇒ 单条在途 + 等 ACK ⇒ 吞吐受 **ACK 往返**限制，与带宽无关
（27 帧/s × ≈80 B ≈ 2.2 KB/s）。

#### 2.2.4 四个候选假设逐一裁决（本轮实测）

| 假设 | 裁决 | 依据（可复跑） |
|---|---|---|
| **内存不足** | ❌ **排除** | `enqueue=−2` 占 100%。该判定在 `mqtt_client.c:2723-2727` 是**纯 `outbox_get_size()` 算术**，**在任何分配之前**返回；全日志 `Memory exhausted`/`No mem` **0 次**。**历史结论"tcp_write errno=11 实为内存不足"在本条链路上不再适用** —— 本轮根本没有 errno=11，也没有走分配路径 |
| **队列满** | ✅ **成立（残存根因 B）** | outbox avg 4,082/4,096、100% 样本 >3,000、−2 占 100% |
| **Broker 限流** | ⚠️ **部分排除** | 排除"主动限流/断连"：broker `disconnects=0`、持续 27/s 成功、失败发生在**本地 enqueue**（报文根本没发到 broker）。但**不能**排除"ACK 往返延迟偏高"—— 那正是排出率只有 27/s 的直接含义，需 broker 侧 RTT 取证（本轮未做） |
| **超时判定过激** | ❌ **排除** | `network.timeout_ms=3000` 只作用于 esp-mqtt 自身的读写；**不参与** `enqueue` 的 −2 判定。日志 `Poll read error` **0 次**、abort/disconnect **0 次** |

#### 2.2.5 验收判据（**未达成，诚实报告**）

判据：同台架 120 s，`Publish failed` 3,873 → **≤10**。
**实测：1,826 —— 未达成。**

原因：判据是在"根因只有一个"的假设下写的；实测根因有两个。
(A) 修好后，每个失败帧由 2 次尝试降为 1 次，**失败数恰好减半**（3,873→1,826），
但 (B) 供给(41/s) > 排出(27/s) 的饱和仍在，**必须消除饱和才能到 ≤10**。

**为什么本轮不修 (B)——诚实二选一中的"不修"**：

| 候选 | 为什么本轮不落地 |
|---|---|
| 加大 `outbox.limit` | **治不了本**：供给 > 排出时任何有限缓冲都会满（2.2.3 的算术）。仅把失败推后，并增加内部 RAM 与队列时延 |
| 遥测改 QoS0 | **改投递契约**：`mqtt_client.c:45-55` 明确把 0x03 作为"关键样本路径"保留 QoS1；改动需契约方决策 |
| 启用 **DataBatch(0x20)** | **这是设计好的解法**：n=4 时 41/s → ≈10/s，低于 27/s 排出上限。但 `bus_worker.c:591` 有门控 `hello_get_server_caps() & CAP_DATA_BATCH_V1`，**本台架未生效**（旁证：`data_reports` 3,253 ≈ 事务数，均值 60 B 的单帧；无 0x20 批帧）。能力位由**服务端**决定 ⇒ 跨到后端/下阶段 |

- **优先级 P1**　**前置依赖**：DataBatch 方案需服务端能力位（后端侧；不属本任务）
- **风险（不修 B 的代价）**：100 Hz 下仍有 ≈37% 上行帧被拒；**任何 100 Hz 数字
  仍受此上限约束**（实测 Hz 被钉在 ≈27/s）。但已不再是"失败多于成功"的不可信状态
- **证据强度**：现象＝实测；根因 (A)(B)＝**实测闭环**；
  排出率 27/s 的上游（ACK RTT / broker）＝**推断，未直接取证**

> ⚠️ **本条仍应先于 100 Hz 的任何数字验收** —— 因为 Hz 上限的成因 (B) 已定量，
> 但消除它需要 DataBatch 能力位或 QoS 契约决策。

### 2.4 L-04 —— IRAM 100% 占用 → **假警报，已证伪并修复**（2026-10-06 更正）

> **本节原结论（"IRAM 窗 100% 满，新增 ISR/IRAM 代码会链接失败"）是错的。**
> 保留原判定供追溯，实际结论以下方"更正"为准。

**原判定**：`mem_budget_check.py` 报 `IRAM used=16384 total=16384 remain=0` ⇒ 判为合并阻塞项。

**更正后的结论：❌ 不成立（假警报）**。真正的问题是**门禁工具的 IRAM 口径错**，不是 IRAM 段满。

#### 根因（已核实到机制）
`esp_idf_size` 报的 IRAM "total" **不是 IRAM 段的容量**，而是它按
`chip_info/esp32s3.yaml` 的内存类型窗切分 `iram0_0_seg` 后、落在 "IRAM" 窗内的**那一段**：

```
yaml IRAM 窗  0x40370000 .. 0x40378000   (len 0x8000 = 32 KiB)
链接器段      0x40374000 .. 0x403CB700   (len 0x57700 = 358,144 B)
交集          0x40374000 .. 0x40378000   = 16,384 B   ← 正是那个"total"
```

⇒ 无论实际用了多少 IRAM，该栏都**恒为 total=used=16384 / free=0**；
放在该窗**之后**的 IRAM 代码全部被计入 **DIRAM 类**（341,760 B 那部分）。

> 说明：本节初版曾把机制写成"iram0_0_seg 与 dram0_0_seg 长度之差"。
> 数值上同为 16,384（两者都源于 0x4000），但**机制描述是错的**，
> 已按 `esp32s3.yaml` + map 实测更正。记为一次"数值巧合掩盖机制"的教训。

#### 决定性实验（含一次失败的实验）
往 IRAM 放 **32 KiB** 静态块，并**让它被引用**（`l04_probe.c` + `app_main` 调用）：

| | `_iram_end` | 真实已用 | 构建 |

| 基线 | `0x40389800` | 88,064 B | ok |
| +32 KiB IRAM | `0x40391800` | 120,832 B | **成功（RC=0）** |

**⚠ 第一次实验是个假阴性**：探针写好了、也加进了 `SRCS`、`.obj` 确实编出来了，

### 2.6 L-06 —— BLE 不达标（**需用户决策；含根因级分析**）

**现状**：✅ 成立，且**比原判断更严重**，但**根因已定位到 WiFi 的量级**。

#### 2.6.1 预算的来历（先证伪"预算偏保守"）

`sdkconfig.defaults:145` 与 `tools/net_network_sizing.md` §5 写"**Budget: 48–64 KiB internal RAM**"。

```
BLEMEAS after nvs                internal_free=347959
BLEMEAS after nimble_port_init   internal_free=287687 largest=212992   Δ 60,272
BLEMEAS after host task +3s      internal_free=282555 largest=208896   Δ  5,132
⇒ BLE 净占 65,404 B = 63.9 KiB；largest 降 44.0 KiB
```
⇒ **"预算偏保守、实测会更小"被证伪**：实测 **63.9 KiB**，落在 48–64 KiB 的**最上沿且略超上限**。
**48 KiB 下限不可达。** 正确门槛 = 63.9 + 8 = **71.9 KiB 内部空闲**。
（转引 Lead 实测；串口已释放，我未独立复跑。）

**方法学要点（值得记录）**：① **独立最小工程**隔离被测物，避免"WiFi/其它子系统同时变化"污染差分；
② **用门禁同口径** `MALLOC_CAP_INTERNAL|MALLOC_CAP_8BIT`（若用裸 `MALLOC_CAP_8BIT`，
在 s3p 上会被 PSRAM 稀释到看不出变化 —— 正是 `1224b15a` 修的那类缺陷）；
③ 踩过的坑：漏 `nvs_flash_init()` → `phy_init: NVS has not been initialized` → abort；
手工 `esp_bt_controller_init()+enable()` 又调 `nimble_port_init()` → **double-init abort**
（IDF 6.1 的 `nimble_port_init()` **内部含控制器初始化**）。两次都是"测试代码错"而非"被测物错"。
④ **未覆盖**：BLE 运行期随连接/吞吐的动态分配、BLE OTA 的额外缓冲 ⇒ 63.9 KiB 应视为**静态+初始化下限**。

| 型号 | 内部堆总量 | 当前空闲 | 门槛 | 结论 |
|---|---:|---:|---:|---|
| **S3（s3p-n16）** | 299.4 KiB | **48.7 KiB** | 71.9 KiB | **缺口 23.2 KiB** |

⇒ **BLE 不是"全部不可行"，而是"C6 可行 / S3 不可行"**。用户原话是"RAM 够则做"——
**事实是 s3p 不够、C6 够**。

#### 2.6.3 根因量级：WiFi 独占 79.3 KiB 内部 RAM（**本轮最重要的定量发现**）

Lead 用 `1224b15a` 的双口径 `[bootheap]` 在 S3 上逐阶段测量：
```
[bootheap] after app_state   int free=184735 largest=110592
           after config_mgr  int free=184647
           after msg_handler int free=184559
           after periph      int free=174235   ← periph 吃 10,324
           after ota+sched   int free=174235
           after mqtt_init   int free=174023
           before wifi       int free=167843   total free=8543083  largest=8257536
           after wifi_start  int free= 86651   total free=8390987  largest=8257536
[stack heap] int free=49911 largest=23552
```
| 口径 | before wifi | after wifi | Δ |
|---|---:|---:|---:|
| **内部** | 167,843 | 86,651 | **−81,192 B（79.3 KiB）** |
| **合计** | 8,543,083 | 8,390,987 | −152,096 B（148.5 KiB） |

⇒ `SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` **部分生效**：PSRAM 承担 **70,904 B（占 47%）**，
内部承担 **79.3 KiB（占 53%）**。

> **Lead 已自我更正**：先前"PSRAM 几乎没被用"的结论**是错的** —— 那是从"largest 全程恒定 8,257,536"
> 反推机制，而 **largest 恒定只能说明没有大到能改变最大连续块的分配，不能说明 PSRAM 未被使用**。
> 本文按**更正后版本**采信。**教训**：从一个数字反推机制，正是本项目反复强调要避免的跳跃。

**定位那 79.3 KiB 内部残余的成因（我查证 IDF 源码后的结论）**：

| 候选解释 | 查证结果 | 判定 |
|---|---|---|
| `SPIRAM_MALLOC_ALWAYSINTERNAL=4096` 把 ≤4 KiB 的分配钉在内部 | **不适用于 WiFi/LWIP** —— WiFi 走 `wifi_malloc/calloc` → `heap_caps_malloc_prefer(size,2,DEFAULT|SPIRAM,DEFAULT|INTERNAL)`（`esp_wifi/esp32s3/esp_adapter.c:69-100`），lwIP 同理（`lwipopts.h:1743-1749`）；`ALWAYSINTERNAL` 只作用于**普通 `malloc()`**（`heap_caps.c:107-124`）。<br>**但**：`MALLOC_CAP_DEFAULT|MALLOC_CAP_SPIRAM` 的 caps 过滤**不含** `MALLOC_CAP_8BIT`，而 PSRAM 堆区 caps 含它 ⇒ 实际仍匹配（`heap_caps_base.c:152` 的 `(all_caps & caps) == caps`；`get_all_caps` 对多优先级 OR，`heap_private.h:59`）⇒ **机制上二者都可用，不会强制内部** | ❌ **不是主因** |
| 部分 WiFi 结构**只能**在内部（DMA 可见 / 中断上下文 / 有内部 caps 硬要求） | 未逐项查证（需 `heap_caps_print_heap_info` 的实机输出） | ⚠️ **待查（最可能的主因）** |
| `SPIRAM_MALLOC_RESERVE_INTERNAL=32768` 的影响 | 见 2.6.4：它是**分配偏好池**，不改变量级 | ❌ 非主因 |
| PSRAM 碎片导致小分配回退内部 | 逻辑自洽但**与 largest 恒定矛盾**（碎片大则 largest 会降） | ⚠️ 待查 |

**⇒ 结论（诚实版）**：**"去修一个不存在的缺陷"（WiFi 没进 PSRAM）是不对的**；
正确的问法是"**这 79.3 KiB 里哪些必须先落内部**"——这一点**目前只有假设，没有证据**，
需要一次 `heap_caps_print_heap_info(MALLOC_CAP_INTERNAL)` + WiFi 前后差分的实机取证（记作 **B0**）。

#### 2.6.4 `SPIRAM_MALLOC_RESERVE_INTERNAL=32768` 到底能不能动（查清后回答）

**IDF 实现（逐行读过，不是猜）**：
```
esp_psram/system_layer/esp_psram.c:647  esp_psram_extram_reserve_dma_pool(size)
  → heap_caps_malloc(next_size, MALLOC_CAP_DMA | MALLOC_CAP_INTERNAL)   ← 从常规内部堆取出
  → heap_caps_add_region_with_caps(caps, ...)
      caps[] = {0, MALLOC_CAP_DMA|MALLOC_CAP_INTERNAL,
                   MALLOC_CAP_DEFAULT|MALLOC_CAP_8BIT|MALLOC_CAP_32BIT}
调用点：freertos/app_startup.c:165-170（main_task 内，PSRAM 初始化后）
```
**三条结论**：
1. 它是**从常规内部堆切出的独立堆区**，**不是"已用内存"** —— Lead 的这个判断**正确**；
2. 因为它带 `MALLOC_CAP_DEFAULT|MALLOC_CAP_8BIT`，且 `get_all_caps` 对多优先级 **OR**
   （`heap_private.h:59`），`heap_caps_get_free_size(INTERNAL|8BIT)` 仍会算上它
   ⇒ **调小它不会增加门禁/BLE 口径的读数**；
3. 它的作用是**DMA/内部专用安全网**（Kconfig 原文：*"reserves a pool specifically for requests like
   that; a normal malloc() can fall back to the pool only after all other internal are exhausted"*）
   ⇒ **调小＝移除保护**，而 WiFi 缓冲的 PSRAM 优先分配**失败时会回退内部**，这个池正是那类回退的落点。

- **可证伪的验证（如果用户仍想看数据）**：把 32768 临时改 8192，在 S3 上读 `[intdiag] internal free/largest`。
  **我的预测**：`free` 读数**基本不变（±2 KiB）**，而 `largest` 可能**下降**
  （因为 32 KiB 的池本身就是可用的连续块之一）。
  **若实测 free 大幅上升，则说明第 2 条推导有误，本节必须重写。**
- **判定**：**不是 BLE 的杠杆**；调它属于风险 > 收益。**优先级 P3**

**杠杆 2：`SPIRAM_MALLOC_RESERVE_INTERNAL`** —— 见 2.6.4：**收益 ≈ 0，不是杠杆。**

**杠杆 3：WiFi/LWIP 缓冲 —— 必须先量化；在未量化前**不得**建议**

- 现状（`build/s3p-n16/sdkconfig` 实测）：`STATIC_RX=16`、`DYNAMIC_RX=32`、`STATIC_TX=16`、
  `CACHE_TX=32`、`RX_BA_WIN=16`、`AMPDU_TX/RX=y`。
- **约束（代码事实）**：`SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` 时 IDF 把 `RX_BA_WIN` 抬到 16
  （`esp_wifi/Kconfig:204-205`），而 `wifi_init.c:55` 要求 `RX_BA_WIN ≤ 2*STATIC_RX`
  ⇒ **`STATIC_RX ≥ 8` 是编译期硬下界**。
- **为什么不能凭估算建议**：`STATIC_RX` 由 6→16 时的修改者已实测"**内部 RAM 增量为 0**"
  （因为 PSRAM 优先），所以**"调小 STATIC_RX 能省多少内部 RAM"必须先实测** —— 按 2.6.3 的机制，它主要吃 PSRAM。
  **我的预测**：调小 `STATIC_RX` 对 **内部** 水位影响很小，主要影响**吞吐/丢包**。
  这是一个**可证伪的预测**，一次 A/B（16 vs 8）即可判定。
- **代价/风险**：降缓冲＝用丢包/时延换 RAM，**用户已明确不要**（"性价比中间值"）。
- **如果要做，必须同时给出**：① 实测内部节省字节；② 吞吐代价（丢包率 / p99）；③ 验收判据（丢包率仍 < 0.1%）。
  **否则视为不合格建议。**
- **优先级 P2（需用户决策）；不作为默认建议**

**杠杆 4：再往 PSRAM 搬 —— 剩余 < 2 KiB**
已搬：`s_telemetry_payload` / `s_streams` / `s_manifests` / `s_channels` / 事务 arena（s3p）。
**不可搬**：任务栈（IDF 强制内部；flash 写期间 cache 关闭会崩）、DMA 描述符、ISR 路径
（`collector_mem.h` 文件头已写清）。
**剩余候选**：`handler_data.c` 的 3 处 `buf[1400]`（CPU-only）——**但 OTA flash 写窗口内访问 PSRAM 会崩**，
而发布路径可能在 OTA 期间运行 ⇒ **判定不可搬**。⇒ **杠杆 4 不足以影响 BLE 决策。**

**杠杆 5：编码缓冲改共享静态（1,400 B）—— 净 ≈ 1.7 KiB，但**主要价值是安全** **

- 事实：`handler_data.c` 有 **3 处** `uint8_t buf[1400]`（`:150` `send_status`、`:327` `send_data_report`、`:363` `send_data_batch`）。
- 改用一个**共享静态缓冲 + 互斥锁**：栈侧 `status` 5,120→3,072（**2,048**）+ `report_tx` 4,096→3,072（**1,024**）= 3,072；
  `.bss` 付出 **1,400** ⇒ **净 ≈ 1,672 B（约 1.7 KiB）**。
- **风险（数据损坏级）**：共享缓冲无互斥 ⇒ `status_task` 与 `report_tx` 并发**串帧**。
  必须用互斥（净收益 1,672 B）或按任务分离两个缓冲（+2,800 B，**净收益归零**）。
- **验收判据**：并发压测（status 1 Hz + DataReport 100 Hz × 120 s）下**每帧内容自校验通过、0 串帧**；
  两任务 `hw ≥ 1,024 B`。
- **优先级 P2**　**前置依赖**：L-07/L-08

**杠杆 6：重新审视 48 KiB —— 已由实测回答**：**预算不是偏保守，而是偏乐观**（见 2.6.1）。**不要再把 48 KiB 当门槛。**

**杠杆 7（本轮新增）：BLE 只在"配网窗口"启用（面向 S3）**
- 观察：S3 **启动瞬态**水位显著更高 —— `largest=31,744 / free=81,423 / min_ever=49,340`
  （`实机缺陷-PSRAM…` §9.4），而稳态 `free≈48.7 KiB`。**81.4 KiB ≥ 71.9 KiB，余 ~9.5 KiB。**
- 逻辑：配网期**系统负载最低**（无 MQTT 流量、无 100 Hz 轮询、无 log stream），而 BLE 的用途正是"无凭据时配网"。
- **必须先验证三点**：① 该瞬态是否**稳定**到足以容纳 63.9 KiB；② **拿到凭据后能否把内存还给系统**
  （`esp_bt_controller_disable` + `nimble_port_deinit` 的回收语义需查证）；③ WiFi 与 BLE **共存的 coex 开销**未测。
- **收益**：S3 也能获得 BLE 配网，无需大改。
- **代价/风险**：BLE 只在启动早期可用；**若回收语义不成立，运行期将永久少 63.9 KiB**。
- **验收判据**：S3 上 ① 启动后 `internal free ≥ 71.9 KiB` 时可成功 `nimble_port_init`；
  ② 配网完成后 `internal free` 回到 **±2 KiB** 于基线；③ 100 Hz 负载下 BLE 关闭时 MQTT 不掉线。
- **优先级 P1（需用户决策）**　**证据强度**：瞬态数字＝实测；可行性＝**推断，待实测**

**杠杆 8（评估 Lead 提到的 periph 10,324 B）**
- 相关事实：`PERIPH_CMD_QUEUE_DEPTH=8`、`PERIPH_RSP_QUEUE_DEPTH=8`、
  `periph_worker`/`periph_rsp` 各 3072 B 栈（堆分配，已含在栈合计里）。
- **判断：不值得单独追**。量级上 10,324 B 相对 23.2 KiB 缺口不足一半，且它对应**用户明示要求的
  DMA/PWM 能力**；追它属于"用产品能力换内存"。**建议不列入 BLE 杠杆**。
- **优先级 P3**

#### 2.6.6 L-06 的结论

> **栈右尺寸化（≤8.9 KiB）+ 编码缓冲静态化（1.7 KiB）+ PSRAM 搬迁（<2 KiB）
> 三者合计上界 ≈ 10.6 KiB ≪ 缺口 23.2 KiB。**
> ⇒ **"靠省内存让 S3 跑 BLE"在当前架构下不成立**（除非动 WiFi —— 用户已否决，或重构任务模型 —— 风险高）。
> **但**：BLE 缺口的**根因量级**是 **WiFi 占 79.3 KiB 内部**，而这 79.3 KiB 里"哪些必须先落内部"
> **尚无证据** —— 这是一个**尚未证伪的、可能的突破口**，应在做"放弃 S3 BLE"的决定**之前**
> 用一次实机 heap info 取证（**B0**）。

**给用户的选项**（详见 §4 D-1）：
- **B0（追加，成本最低）**：先做一次 **WiFi 79.3 KiB 内部的成分取证**，**再**决定 A/B/C —— 不改代码，只花一次刷机；
- **A（推荐，立即可得）**：**BLE 只在 C6 实现**（余 48.2 KiB），S3/s3p 不提供 BLE 配网；
- **B**：**S3 走"配网窗口 BLE"**（杠杆 7），先实测开关前后的内存回收；
- **C**：**暂缓 BLE**，先把 100 Hz（L-01~L-03）做完。

### 2.7 L-07 —— `report_tx` 栈余量 636 B（**复核后：不是本轮引入**）

**现状**：✅ 余量确实很薄，但"是本轮引入"被**证伪**。`bus_worker.c:131` 附近注释原文：

> `/* 报告任务栈。**由 6144 降到 4096（2026-10-05，实测依据）**。
> 依据：uxTaskGetStackHighWaterMark() 实测该任务峰值只用 3464 字节（未用余量 2680）。
> 取 4096 保留约 630 字节余量，相对峰值约 1.18 倍。 */`

- 2026-10-05 测：峰值 **3,464 B**（6144 分配，hw=2,680）
- 2026-10-06 测：**used = 3,460 B**（4096 分配，hw=636）
⇒ **两次峰值差 4 B** ⇒ **DataBatch 的 1,400 B 栈缓冲没有叠加**（与源码注释"批路径与单样本路径互斥"一致），
**当前的 636 B 余量就是 10-05 自己选择的 630 B 余量**。

- **方案**：见杠杆 5（编码缓冲改共享静态 + 互斥）——**唯一能同时解决 L-07 且不牺牲其他东西**的改法。
- **代价/风险**：互斥锁引入发布路径锁竞争（`report_tx` 与 `status` 并发）；锁粒度必须是"编码阶段"而非整个 publish。
- **验收判据**：改后 `report_tx` `hw ≥ 1,024 B`；并发压测 0 串帧。
- **优先级 P2**　**证据强度**：实测（两次独立采样）+ 源码注释交叉验证

### 2.8 L-08 —— `rgb_led` 栈余量 584 B（**且分配值有误**）

**现状**：✅ 成立，且**分母需更正**。`components/rgb_led/rgb_led.c:322-327`：
```
BaseType_t ret = xTaskCreate(
    rgb_led_task,
    "rgb_led",
    2048,          // ← 源码是 2048，不是 3072
    NULL, 3, &s_task_handle);
```
- 若按 3072 算：used = 2,488（81%）；**按源码 2048 算：used = 1,464（71.5%）**，余量仍 **584 B**。
- 影响：① 结论方向不变（`rgb_led` 仍是**绝对余量最小**的任务）；
  ② **堆分配栈合计从 56,320 更正为 55,296 B**。

- **方案**：`rgb_led` **不是裁减对象**，反而应**增加到 3,072 B**（+1,024 B）：
  584 B 余量对调用 IDF 驱动（RMT/LED strip）的任务太薄，而其栈溢出的后果（随机踩踏）远大于 1 KiB 内存。
- **代价**：−1,024 B 内部 RAM（与 L-06 缺口方向相反，是**净支出**）。
- **验收判据**：`rgb_led` `hw ≥ 1,024 B`。
- **优先级 P2（建议在 L-06 决策前先做）**　**证据强度**：源码（本轮）+ 实测 hw（Lead）

### 2.9 L-09 —— 后端 USB `bus_config` 无长度校验

**现状**：✅ 成立，且是**显式不做**（有注释）。`backend/internal/nodemgr/manifest_codec.go:92-100`：
```
// USB carries no GPIO route: a CDC/JTAG data bus has no tx/rx pins and no
// baudrate, so there is nothing for the pin-authority check to claim.
// bus_config may therefore be empty OR any length — a host-side length gate
// here would only reject manifests the collector accepts (config_mgr's
// channel_uses_pin returns false for unknown bus types, and
// bus_config_get_dma_enabled defaults to true). Non-hex text is still
// rejected by the decode above, exactly as for every other bus type.
case "USB":
    return nil, nil
```
**固件侧是真的 fail-closed**（`components/config_mgr/config_mgr.c:342-346`）：
```
case 7: /* bus_config */
    if (cf.wire_type != WIRE_LENGTH_DELIMITED || !cf.value.bytes.ptr ||
        cf.value.bytes.len > sizeof(cur_channel->bus_config)) return false;   // 64 B
```
⇒ 后端可下发 >64 B 的 USB `bus_config`，**固件整份 manifest fail-closed 拒绝**

### 3.3 最该先做的三条（理由）

1. **L-02 定位上行发布失败**（P1，无依赖，一次刷机 + 120 s）。
   它是当前**唯一**能解释"Hz 上不去"且**尚未定位**的缺陷；在它关闭前，任何 100 Hz 数字都不可信
   —— 因为**失败（3,873）比成功（3,227）还多**。
2. **B0 WiFi 79.3 KiB 内部成分取证 + D-1 BLE 分型决策**（P1，一次刷机，不改代码）。
   实测已把问题从"能不能做"变成"**在哪个型号做**"，而断言的根因量级是 **WiFi 占 79.3 KiB 内部**；
   花一次刷机就能判定"这 79.3 KiB 里是否真有可搬的部分" —— **先证伪再放弃**，
   否则"BLE 不可行"这个结论本身也是未经验证的。
3. **L-01c scheduler 队列背压**（P1，可独立开工，与 L-02 并行写代码）。
   它是当前唯一能在**不碰事故高发的 RX 状态机**的前提下改善 100 Hz 的改动，
   且把"静默丢样本"变成"可观测延迟"（`missing_reports` 从 1,762 → 0）。
   即使 Hz 不提升，也让后续测量可信。
