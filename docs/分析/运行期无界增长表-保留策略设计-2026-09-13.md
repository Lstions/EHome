## 0. 本文档的裁决口径（先说清楚什么算「做了分析」）

本仓刚发生过一次清理策略论据被证伪的事件（`未发布产品负债盘点` §3.17）：投递审计清理子代理
声称「成功投递记录是冗余的、可以只留一半时间」，被可跑测试推翻 —— `notification_deliveries`
是「这条通知**当时送达没有**」的**唯一**证据，`models.Notification` 根本没有投递状态字段。
教训不是「审计不能删」，而是：**「冗余 / 等价 / 重复」是事实断言，必须能被一次观测证伪**。

因此本文档对每张表强制回答四个问题，缺一即视为未做分析：

1. **谁写、什么频率**（读写入点代码，判断是「每次采集一行」还是「每次操作一行」）
2. **谁读**（有无 API/UI 消费者；**无消费者本身就是结论**）
3. **这一行唯一承载了什么事实？这个事实还有没有第二处记录？**（证据唯一性）
4. **删了它，哪个问题就再也答不出来了？**（代价，不是收益）

**被本文档明确拒绝的三种结论**（写给未来的复核者）：

- ❌「建议统一保留 90 天」—— 不区分表性质 = 没做分析
- ❌「审计表不能删」—— 等于没有策略，且与 §3.17 已确立的「审计保留期应写**允许的目标**而非只写禁令」冲突
- ❌「建议加清理任务」而不写清清理**哪一档**、**按什么字段**、**边界值多少天**

## 2. 逐表取证与裁决

### 2.1 `automation_events`

**表结构**（`backend/internal/models/automation.go:156-168`）

```go
type AutomationEvent struct {
    ID            uint      `gorm:"primaryKey"`
    RuleID        uint      `gorm:"not null;index"`
    TriggeredAt   time.Time `gorm:"not null;index"`
    TriggerValue  *float64
    TriggerSource string    `gorm:"size:8;not null;default:auto;index"` // auto|manual
    Result        string    `gorm:"size:32;not null;index"`
    CommandID     string    `gorm:"size:36;index"`                     // FK→command_executions (无 DB 外键，见下)
    Detail        string    `gorm:"size:512"`
    CreatedAt     time.Time
}
```
索引（PG 实测）：`pkey(id)`、`idx_automation_events_rule_id`、`idx_automation_events_triggered_at`、
`idx_automation_events_result`、`idx_automation_events_trigger_source`、`idx_automation_events_command_id`。
**`command_id` 上无真实 FK 约束**（`pg_constraint` 对全部目标表查询 `contype='f'` 返回空集）——
删除 `command_executions` 不会级联，也不会报错，只会**静默留下悬空的 command_id**。这是本批所有表的共同性质，
是「证据之间靠约定而非约束关联」的结构性风险，写入 §7 不变式 INV-3。

**谁写、什么频率**（`automation/planner.go`、`automation/evaluator.go`）

| 写入点 | 触发条件 | 频率性质 |
|---|---|---|
| `planner.go:283 recordRet` / `:294 Create` | 每次触发决策落一行 | **每次决策一行** |
| `evaluator.go:484` | 冷却窗内每帧越阈 | **每次采集一行的风险——已被同窗节流抑制**（`evaluator.go:475-481`，设计注记明写「1s 上报 × 1h 冷却 = 3600 行/窗」，故同窗只落首条） |
| `planner.go:542/569/586/599/619/646/657` | 手动触发各分支 | 每次人工点击一行 |
| `planner.go:797 sweepExpiredPending` | 每 5 分钟（`planner.go:493 cleanupInterval`）`UPDATE`（非 INSERT） | 把 24h 前的 `pending_confirm` 改写成 `expired` |

**上界 = 规则数 × 传感器数 × (86400 / max(cooldown, 1)) + 决策数**。
实测 ≈1405 行/天 ≈ 单规则 × 单传感器 × 1s 上报、冷却 60s 的结构上界（1440）。
**这是一个稳态可长期维持的速率**，不是一次性导入——即它确实在无界增长。

**谁读——关键发现：它不是只读审计，它是「热状态」的持久层**

| 读取点 | 用途 | 读什么 |
|---|---|---|
| `planner.go:93-97` | **日熔断计数**（`max_daily_exec`） | 当日 `result='executed'` 行数 |
| `planner.go:175-178` | **幂等键序号** `automation:<rule>:<yyyymmdd>:<seq>` | 当日 `executed` 计数 |
| `planner.go:530-533` / `:626-629` | 手动触发日熔断 / 幂等序号 | 同上（手动加 `trigger_source='manual'`） |
| `planner.go:553-557` | 手动触发冷却判定（DB 兜底） | **最近一条** `executed`/`pending_confirm` 的 `triggered_at` |
| `planner.go:797-802` | 清扫 `pending_confirm` | 24h 前的行 |
| `evaluator.go:110-121 rebuildCooldowns` | **进程启动时重建内存冷却表** | 每 rule `MAX(triggered_at) WHERE result='executed'` |
| `api/handler_automation.go:458-489` | `GET /api/v1/automation-events` 真分页 | UI 事件列表 |
| `frontend-shared/src/api/automation.ts:223` | 前端消费上述端点 | — |

⇒ **`automation_events` 同时是审计证据和一份没人备份的运行状态**。删除其中 `executed` 行会产生
**功能性后果**（不是审计后果）：`rebuildCooldowns` 的回填锚点是「每 rule 最新一条 executed」，
一旦该行被删，重启后该 rule 的冷却窗**提前解除**，条件仍满足时会立即多触发一次——
这是一个**真实的设备动作多执行**风险，不是报表少一行。

**增长速率量级**：≈1.4×10³ 行/天（仿真上界形态）；稳态下由规则数线性放大。
**证据唯一性：Y（混合）**

- `executed` 行的「该 rule 当时是否处于冷却窗内」→ `command_executions` 有对应行，
  但**「什么时候被抑制的、为什么」只有本表有**。`suppressed_cooldown` / `suppressed_daily_limit` /
  `condition_changed` / `failed_gate` 四种结果**在其它任何表都没有第二处记录**
  ——「自动化为什么没动作」这个问题的唯一证据。
- `TriggerSource`（auto/manual）**全仓唯一**。

**裁决：分层保留。**（⚠️ **本节已于 2026-09-14 修订**，两处原裁决被更晚的证据推翻，见下方「修订记录」）

| 档位 | 字段 | 边界值 | 理由 |
|---|---|---|---|
| A：**白名单** 7 种纯遥测 result（`suppressed_cooldown`/`suppressed_daily_limit`/`condition_changed`/`failed_gate`/`failed_dispatch`/`notification`/`expired`） | `triggered_at` | **30 天**（硬下界 2 天） | 纯遥测/可观测性：被抑制、条件失效、门禁拒绝的瞬时判断，30 天后无人追问 |
| B：`result = 'executed'`（**仅此一种**） | `triggered_at` | **400 天** | 承载设备动作归因与幂等序号历史；必须覆盖规则的生命期 |
| — | `pending_confirm` | **永不删** | 它是**待人工确认的待办**，不是遥测也不是历史：`ConfirmEvent` 依赖该行存在（行不存在 → `ErrConfirmEventNotFound`），删掉 = 用清理器代替人结案。同型于命令域「未处置 UNKNOWN」 |

> **400 天的来源**：`ValidateAutomationRuleConstraints`（`handler_automation.go:652`）把
> `cooldown_sec` 上界钉在 `86400`（1 天）。因此「重启回填是否正确」只依赖**最近 1 天**的 executed 行。
> 400 天不是为冷却算的，是为「这条规则上个月为什么开了一次阀门」这类事后追责留的窗口；
> 若产品认定 1 年足够，取 1 年同样满足技术下界。**下界由 `cooldown_sec` 上界决定，不由偏好决定。**

**⚠️ 前置缺陷 —— 已修复（2026-09-14），修法与原方案相反，勿再回退**

原描述是对的：若某规则连续 >30 天无 `executed`，其 executed 行会落入窗口，而"冷却窗从哪一刻起算"
依赖这些行 ⇒ 删了会**冷却提前解除、设备动作多发**。

**但原修正方式（清理器同事务补写 `base_cooldown` 哨兵行）已被否决** ——
理由：它把正确性寄托在**尚未实现的清理器**上（漏写一次 / 事务边界写错 / 未来有人 TRUNCATE 表，
缺陷立刻复现）。而前置条件的意义恰恰是"**不依赖清理器实现正确**"。

**已落地的正确修法**：冷却锚点**物理解耦**到规则行 `automation_rules.last_triggered_at`
（三个 executed 写入点同事务写锚点；`rebuildCooldowns` 改读该列；仅"锚点为空"的规则做一次性回填）。
⇒ 删事件行**在物理上不可能**影响冷却。因此清理器**不需要也绝不应该**补写任何哨兵行，
并且它**绝不碰 `automation_rules`**（有测试钉住删完事件行后锚点原值不变）。
完整裁决与验证见 `docs/分析/清理前置条件-冷却锚点与监控基线-2026-09-14.md`，台账 §3.24。

**代价**：档位 A 删除后无法回答「这 3 次被冷却压制具体压在哪个窗口」；档位 B 删除后
「这条规则上一次真正动设备是什么时候」只能去 `command_executions` 反查（依赖 `command_id` 未被一并删除）。

### 2.2 `node_events`

**表结构**（`backend/internal/models/models.go:443-451`）

```go
type NodeEvent struct {
    ID        uint      `gorm:"primaryKey"`
    NodeID    string    `gorm:"column:node_id;type:varchar(32);index;not null"`
    EventType string    `gorm:"size:20;not null"`
    OldStatus string    `gorm:"size:20"`
    NewStatus string    `gorm:"size:20"`
    CreatedAt time.Time
}
```
索引（PG 实测）：`pkey(id)`、`idx_node_events_node_id`。**注意：`created_at` 上无索引**
（与 model tag 一致，也没有复合索引），而两个读取点都按 `created_at DESC` 排序——
这是本表未来的查询性能隐患，见 §7 INV-5。

**谁写**（3 个写入者，均为**状态转换时一行**，非每帧一行）

| 写入点 | 条件 | 频率性质 |
|---|---|---|
| `offlinedetector/offlinedetector.go:121 markOffline` | `status='online'` 且 `last_seen` 超 90s（`checkDBLastSeen`，`:94-107`） | 每次离线判定一行 |
| `nodemgr/handler_status.go:344` | `oldStatus != status` | 每次状态变化一行 |
| `nodemgr/handler_hello.go:300 / :355` | 首次注册 / `oldStatus != 'online'` 的复苏 | 每次握手转换一行 |

**关键观察（实测数据揭示）**：`node_events` 里 `offline` 占 99.6%（6073/6098）。
原因不是采集频率，而是 **offlinedetector 的无条件重复写入**：`checkDBLastSeen` 只扫
`status='online'` 的节点，理论上不会对已离线的节点重复落行；但实测 6073 条 offline 对应
**1002 个不同的 node_id，其中只有 2 个存在于 `nodes` 表**（`SELECT count(DISTINCT n.node_id), count(DISTINCT nd.node_id) FROM node_events n LEFT JOIN nodes nd ...` = `1002|2`，
而 `nodes` 现有 47 行、全部 `offline`）。即：**本表保存的是 1000 个仿真节点的完整离线时间线，
这些节点行早已被清掉**。这既解释了速率，也说明了一个重要事实：
**`node_events` 是本系统里唯一保留了「已不存在的节点」历史的表**——它是一份真正的历史账本，不只是当前拓扑的附属。

> 该发现同时暴露一个独立缺陷（**不在本任务范围，仅记录**）：`nodes` 已无对应行时，
> `markOffline` 的 `First(&nodeRecord)` 会失败并**静默丢弃**事件（`:120 if err == nil`），
> 即「设备离线」这件事在某些路径上根本没有记录。这与「本表是唯一证据」叠加会更危险。

**谁读**（2 个 API，均有前端消费者）

| 读取点 | 端点 | 前端 |
|---|---|---|
| `api/handler_node.go:103-124` | `GET /api/v1/nodes/status-history?limit=50`（默认 50，硬上限 200） | `views/dashboard/Dashboard.vue:517`（运维时间线） |
| `api/handler_node.go:147-168` | `GET /api/v1/nodes/:id/status-history?limit=50` | `views/node/NodeOverview.vue:1348`（最近事件卡） |

**无第二处记录的事实**：`nodes.last_online_time` / `last_seen`（`models.go:30,51`）只保存
**最新一次**，不保存历史。删除 `node_events` 行 = 该节点的上下线时间线**不可重建**。

**增长速率量级**：≈1.9×10² 行/天（含 1000 个仿真节点的离线风暴）。
**真实单节点稳态**：`online` 仅 6 条 / 31.8 天 ⇒ 每节点约 **0.2 次状态转换/天**；
若生产有 100 节点，量级 ≈20 行/天，**是本文档八张表里增长最慢的**。

**证据唯一性：Y**

**裁决：统一保留 400 天，按 `created_at` 删，**不设分层档位**。**

理由（可反驳）：
1. 本表无法像 `automation_events` 那样分层——99.6% 是 `offline`，而 `offline` 恰恰是
   运维时间线的主内容，按 `event_type` 分层等于删掉时间线本身。
2. 增长速率是全批最低（≈20 行/天/100 节点），**删它省不下空间**：400 天 × 100 节点 × 2 行/天 ≈ 8×10⁴ 行，
   约 5 MB。**为 5 MB 牺牲唯一时间线不划算**——这是「代价 vs 收益」的直接权衡，不是「审计不能删」。
3. 400 天与 `automation_events` 档位 B 对齐，减少一条需要单独解释的口径。

**代价**：删除后「某节点在 2027 年的某次离线」不可追溯；若未来要做节点可用率 SLA 报表，历史窗口就只有 400 天。

**⚠️ 若产品坚持更短（例如 90 天，把本表定性为「运行遥测」），必须先满足 INV-5**：
把两个消费端的展示上限（当前 50/200）写进不变式，否则会出现
「保留期缩到 90 天 → 1000 节点 × 1 次离线/天 = 9 万行，页面上仍只显示最近 47 条」，用户无感但历史已丢。

```go
    Metadata      string    `gorm:"type:text"`

```
7 个索引，是本文档索引最密的表。模型注释自述：`"append-only security event"`。

**谁写**：唯一写入口 `audit.Writer.Write`（`internal/audit/audit.go:39-71`）——`db.Create`，无 Update、无 Delete。
调用方 5 处（`commandexec/service.go:526,622,663`、`commandexec/confirmation.go:166`、
`auth/initialize.go:90`、`auth/account.go:60,107,136`），全部传入**事务 `tx`**——
即审计行与业务行同事务，要么都成，要么都不成，**不存在「业务成功但审计丢失」的窗口**（这是本表最强的性质）。
`Write` 还会拒绝含敏感键（password/token/authorization/secret）的 Metadata（`audit.go:73-86`）。

**频率**：每次受控动作一行（`device_action.created` 3776 行 = 每次创建设备动作一行）。
实测 ≈116 行/天。

**谁读——重要发现：运行期零读取者**

全仓搜索 `SecurityAuditEvent` / `security_audit_events`：生产代码只有三处
（`audit.go:56` 写、`database/gorm.go:93` 注册、`pkg/metrics/metrics.go:255` 写失败计数器）。
**没有 HTTP 端点、没有前端页面、没有任何查询服务**。
唯一读它的是仿真目录的只读投影（`simulation/catalog/cmd.go:310-330`，`FROM security_audit_events WHERE request_id = $1`）。

⇒ 这是「审计证据」的教科书形态：**写下来就是为了将来在争议中回答「当时是谁、从哪个 IP、
对哪个目标做了什么」，且当前没有任何自动化消费者**。也正因如此，它的保留期**只能由
产品/合规决策，不能由工程师按「没人查」来定**——「当前没人查」与「将来要不要查」是两件事。

**增长速率量级**：≈1.2×10² 行/天（仿真）。稳态 ≈ 每受控动作 1 行，随操作量线性。
按每动作 1 行、日均 1 万次操作估，约 3.6×10⁶ 行/年 ≈ 数百 MB —— **是本文档里唯一可能真的有体量的表**。

**证据唯一性：Y（但需分档核查，见下）**

实测：`device_action.created` 3776 行，与 `command_executions` 3776 行
**通过 `request_id = command_id` 100% 一一对应**（join 计数 = 3776 = 两侧总数）。
因此**对命令创建这一类事件，本表不是唯一证据**——`command_executions` 有同样的 `command_id`、
`actor_user_id`、`created_at`，metadata 里的 `action_id`/`action_version`/`request_hash` 也在执行行的
`ActionID`/`ActionVersion`/`RequestHash` 列上。

但**本表唯一承载的字段仍然只有它有**：`SourceIP`、`ActorSnapshot`、`RequestID`（跨事件的请求关联）、
`ActorType`（区分 user/system/admin）。且 `auth.password.reset`(2) / `auth.initialized`(1) /
`device_action.confirmation_issued`(18) 这三类事件**在别处完全没有记录**。

**裁决：统一保留 730 天（2 年），按 `created_at` 删。**

1. **谁决定**：保留期必须由产品/合规拍板，工程默认值取 **730 天**并作为**可配置常量**（非法值 fail-closed 回落到该值，
   不允许 0/负数表示「永久」——那会重新打开无界增长）。
2. **为什么不是 90 天**：本表的消费者是「未来的争议调查」，不是「当前的排障」。
   一个「上季度某次密码重置是不是管理员本人做的」问题，90 天后就答不出来，
   而这类问题**恰好总是在 90 天后才被提出**。这是 §0 拒绝的「只写禁令」的反面：
   给一个**明确允许删的窗口**，而不是「永久保留」。
3. **为什么不是「永久」**：附录中的既有原则是「审计保留期应写**允许的目标**而非只写禁令」
   （`未发布产品负债盘点` §3.17 教训 4）。永久保留 = 无界增长重新抬头，且没有任何一条业务规则需要 2 年以上。
4. **可实现性**：`created_at` 有独立索引，`DELETE ... WHERE created_at < ?` 可索引扫描，无需新增索引。

**⚠️ 强前置依赖（见 INV-6）**：本表的 `request_id` 指向 `command_executions.command_id`。
若 `command_executions` 按 400 天清理而本表按 730 天，则 **401~730 天之间的审计行会变成
「指向一条已不存在的命令」的孤证**——审计还在，但被审计对象没了，「当时到底做了什么操作」答不出来。
因此本表的保留期**不得长于** `command_executions`，或者两者取齐。本文档取齐为 730 天（建议），
理由：命令执行行本身也是审计级证据，400 天与 730 天相比省不下有意义的空间。

**代价**：删除后无法回答 2 年前的认证事件；若将来引入等保/审计合规要求（常见 6 个月~3 年），
需要重新评估。**这是一条需要人来拍板的线，不是技术推导的结果，本文档只给出默认值与下界。**

### 2.4 `command_executions`

**表结构**（`backend/internal/models/command_execution.go:10-40`）

**谁读**

| 读取点 | 用途 |
|---|---|
| `api/handler_metrics.go:112-122` | 监控面板 7 个计数：`operations_total / active / queued / succeeded / failed / unknown / unresolved_unknown / cancelled` —— **前端 `Monitor.vue:127-160` 逐项渲染** |

**⚠️ 本表最重要的一条性质（可直接证伪「整表按窗口删」的直觉）**：

```sql
SELECT count(*) FROM command_executions WHERE status='UNKNOWN' AND completed_at IS NULL;  -- 0
SELECT status, count(*) FROM command_executions GROUP BY 1;                             -- UNKNOWN 3759
```
面板上的 **`failed`(9)、`succeeded`(8)、`cancelled`、`operations_total`、`unknown`、`unresolved_unknown`
全部是「对当前表做 `COUNT(*)`」**（`handler_metrics.go:112-122` 逐行 `db.Model(...).Count()`），
**没有任何计数器表或持久化聚合**。因此：**按时间窗删除终态行 → 这些数字会随着删除同步变小。**
「操作失败」从 9 变成 0，不是因为故障恢复了，而是因为证据被删了。
「未处置 UNKNOWN」是前端唯一的告警高亮（`Monitor.vue:141` `attention` 类）——删掉旧 UNKNOWN 行
会让一个从未被人处置过的悬案**从面板上消失**。

⇒ **任何对本表的清理都必须同时钉住 INV-2（监控计数不得被清理改写）**，
最小实现是在表上增加一个「已计入监控口径」的判定列/水位（例如 `metrics_counted_at` 或
一张 `control_metrics_baseline` 单行表），让面板读「存活行 + 已归档基线」而不是纯 `COUNT(*)`。
**在 INV-2 落地之前，本表不得启用任何删除。**

**增长速率量级**：≈2.2×10² 行/天（仿真），每次受控设备动作一行。稳态随操作量线性。

**证据唯一性：Y（是命令控制域的真相源）**
`IdempotencyScope+IdempotencyKey` 唯一索引是幂等语义的唯一实现；`VerifiedResultJSON` 是
「设备到底返回了什么被服务端认可的结果」的唯一记录（原始控制字节按设计不入库）；
`CommandEngineRevision` 是「当时按哪版能力契约准入」的唯一记录。

**裁决：保留 730 天，按 `COALESCE(completed_at, created_at)` 删，且必须先实现 INV-2。**

- **只删终态行**：`Status IN ('SUCCEEDED','FAILED','UNKNOWN','CANCELLED')` 且
  `COALESCE(completed_at, created_at) < now() - 730d`。非终态行**永不删**（INV-4）。
- **730 天而非 400**：为了与 §2.3 的审计保留期取齐（INV-6），避免产生孤证审计行。
- **`unresolved_unknown`（未处置的悬案）单独排除**：若一条 UNKNOWN 从未被
  `command_manual_resolutions` 处置，**不参与时间窗删除**（`WHERE command_id NOT IN (SELECT command_id FROM command_manual_resolutions)`
  的否定形式），直到有人写下结论。理由：悬案的价值恰恰在于「还没人管」，按时间把它删掉
  等于**用清理器代替人做了结案**。这一条把无界增长的风险限制在「人为不处置」的极小集合上。

**代价**：删除后无法回答「这条命令当时的参数与幂等键」；`automation_events.command_id` 的关联会悬空（无 FK，见 §2.1）；
监控口径的实现复杂度上升（需要基线机制）。

### 2.5 `command_outboxes` —— 投递机制的副产物

**表结构**（`models/command_execution.go:84-96`）
`ID`、`CommandID uniqueIndex`、`EventType`、`PayloadJSON`（**即该命令的规范化参数**）、
`State`（`PENDING/LEASED/PROCESSED/CANCELLED`）、`LeaseOwner`、`LeaseExpiresAt`、
`FencingToken`、`ProcessedAt`、`CreatedAt/UpdatedAt`。

**谁写**：`service.go:522 Create`（`PENDING`，与 execution 同事务）；
`dispatcher.go:140-142` 租约（`LEASED`+fencing+1）；
`dispatcher.go:179-181` 取消（`CANCELLED`）；`dispatcher.go:229-231` 发布完成（`PROCESSED`）；
`inbox.go:162` 租约回收；`inbox.go:177` 超期取消。

**谁读**：**只有 dispatcher 自己**（`ProcessOnce` 选 `PENDING` 行、检查同 node+channel 是否已有 `LEASED`），
以及 `handler_metrics.go:123-124` 的两个计数（`outbox_pending`/`outbox_leased`，前端 `Monitor.vue` 渲染）。
**没有任何 API 暴露单条 outbox**。

**与 `command_executions` 的关系（本任务的核心裁决点）**：

```
Create(tx):  INSERT command_executions (QUEUED)  +  INSERT command_outboxes (PENDING)  +  INSERT audit   ← 原子
dispatcher:  outbox LEASED → 建 attempt → 发布 → outbox PROCESSED + execution QUEUED→DISPATCHED   ← 原子
inbox:       设备事件 → execution 状态推进 + attempt 状态推进                                       ← 原子
```

- **真相源（source of truth）= `command_executions`**。它承载「这条命令是什么、参数是什么、
  谁下的、当前处于什么状态、最终结果是什么」。`Status` + 状态机 `validateTransition` 是唯一权威。
- **`command_outboxes` 是投递机制的中间态**：它的存在只为回答「这条已持久化的命令**还没被交给传输层**」。
  它借用 `state` + `lease_owner` + `fencing_token` 实现「多 worker 不重复发布」（`dispatcher.go:95-102` 的
  `NOT EXISTS (… LEASED …)` 与 channel 行锁），这些字段**在终态之后对系统没有任何作用**。
- 实测印证：`command_outboxes` 3776 行 = `command_executions` 3776 行，
  `command_id` 上无孤儿（`LEFT JOIN` 两侧均为 0）。**一对一**，因为 `dispatcher` 硬编码 `AttemptNo: 1`
  且 outbox 的 `CommandID` 是 uniqueIndex —— **当前不存在「一次命令多条 outbox」**。

**但「机制副产物」不等于「零证据」——它唯一承载的事实是**：
`payload_json`（该命令入队时的参数快照）+ `processed_at`（**发布发生的时刻**）+ `created_at`（入队时刻）。
`command_executions` 有 `created_at` 但没有「发布时刻」；`command_attempts.published_at` 也有发布时刻
——**所以发布时刻有第二处记录**；而 `payload_json` 与 execution 的 `params_json` 是同一份内容
（`service.go:522` 直接复用了 `string(params)`）。

**「冗余」是事实断言，因此本文档把它跑了一遍（而不是只在论证里声称）**：

```sql
-- 断言 A：outbox.payload_json 与 execution.params_json 是否逐字节相同
SELECT count(*) FROM command_outboxes o JOIN command_executions e ON e.command_id=o.command_id
WHERE o.payload_json IS DISTINCT FROM e.params_json;                                  -- 实测 0 / 3776

-- 断言 B：outbox.processed_at 与 attempt.published_at 是否相同
SELECT count(*), count(*) FILTER (WHERE o.processed_at = a.published_at),
       max(abs(extract(epoch from (o.processed_at - a.published_at))))
FROM command_attempts a JOIN command_outboxes o ON o.command_id=a.command_id;
-- 实测: 3773 | 精确相等 11 | 最大差 0.000093 秒 (93 微秒)
```

**结论（含一处必须如实记录的自我修正）**：
- **断言 A 成立**：3776/3776 逐字节相同，`payload_json` 是 `params_json` 的**真冗余拷贝**。
- **断言 B 以「精确相等」形式不成立**：只有 11/3773 精确相等，其余最大差 **93 微秒**。
  根因是同一事务内两次独立的 `time.Now()`——`dispatcher.go:211 now := d.now()`（写入 `processed_at`）
  与传输层 `DispatchResult.PublishedAt`（`channel_cmd_v2_transport.go:183 t.now()`）。
  **语义上仍是同一时刻**（同事务、同一次发布的同一条事实，差值恒 < 0.1 ms，且无一条
  `processed_at < published_at`），但**它不是可断言为 `==` 的等价关系**。
  ⇒ 这条不变式必须写成**容差断言**（见 INV-9），而不是等号；写成等号会立刻变红，
  从而把一个「本质上冗余」的表误判为「不冗余」，反向阻止清理。

⇒ **终态之后，outbox 行是冗余拷贝，且这一次「冗余」经过了实跑验证**：删它不丢失任何
`command_executions` 与 `command_attempts` 都不能回答的问题（`created_at` 除外，见下方裁决档位）。

**增长速率量级**：≈2.2×10² 行/天，与 execution 严格 1:1。

**证据唯一性：N（终态后）** —— 前提是上面两条断言成立（A 实测成立；B 需按容差形式成立）。
**这是本文档唯一判定为「可删」的表**，且判定依据是一次**已经跑过**的等价性测试，不是修辞。
⚠️ 这个判定有明确的**失效条件**：一旦 `dispatcher.go:190` 的 `AttemptNo: 1` 不再硬编码
（即一次命令可产生多条 outbox/attempt），一对多的映射会让 `processed_at` 不再与唯一 attempt 对应，
本判定必须立即重新评估。

**裁决：终态 + 冷却期后立即删（比任何审计表都短）**

| 档位 | 条件 | 边界值 |
|---|---|---|
| 删除 | `state IN ('PROCESSED','CANCELLED')` **且** 对应 execution 为终态 **且** `COALESCE(processed_at, created_at) < now() - 30d` | **30 天** |
| 保留 | 其余（`PENDING`/`LEASED`，或对应 execution 非终态） | 永不删 |

**为什么是 30 天而不是「立即」**：`dispatcher.go:194-200` 的注释明写了一个必须被覆盖的崩溃窗口——
「MQTT 可能已接受报文而本事务随后回滚」，此时下一次租约会重新发布**字节相同**的命令。
租约本身 30s（`dispatcher.go:139`）、execution 死线 2 分钟（`service.go:517`）。
30 天是「事后调查一次重复发布」的宽松窗口，与 execution 的 730 天相比已缩短 24 倍。
**不建议更短**：小于 execution 死线（2 分钟）的窗口会让「这条命令为什么没发出去」变得不可查。

**代价**：30 天后无法回答「这条命令是何时被交给传输层的」——但 `command_attempts.published_at` 仍可回答，
故**实际能力损失接近于零**（这正是判 N 的含义）。

### 2.6 `command_attempts` —— 不是副产物，是**防伪锚点**

**表结构**（`models/command_execution.go:67-79`）
`ID`、`CommandID`+`AttemptNo`（uniqueIndex `idx_command_attempt`）、`Status`、
`EnvelopeID`（uniqueIndex）、**`WireDigest`**、`BootID`、`FencingToken`、
`CreatedAt`、`PublishedAt`、`CompletedAt`。

**谁写**：`dispatcher.go:190-200`（建 attempt，`Status=DISPATCHED`，写 `EnvelopeID`、`stableWireDigest`）；
`dispatcher.go:215-219`（回填 `boot_id`/`published_at`/传输层 digest）；
`inbox.go:112-114`（随设备事件推进状态）；
`inbox.go:203`（`RecoverExpired` 置 UNKNOWN）。

**谁读——决定性证据**：`nodemgr/handler_channel_cmd_v2.go:42`
```go
if attempt.BootID == "" || attempt.BootID != response.BootID || !matchesAttemptDigest(attempt.WireDigest, response.Payload...)
```
即：**设备上报的响应帧，必须与 `command_attempts` 里那一行的 `boot_id` 和 `wire_digest` 逐字节匹配**
（`matchesAttemptDigest` 用 `subtle.ConstantTimeCompare` 前 16 字节）。
`dispatcher.go:245-252` 的注释解释了 digest 的设计意图：
「lease/fencing token 只保护数据库所有权，**绝不能**参与线路身份：MQTT 可能已接受报文而事务回滚，
崩溃窗口后下一次租约必须发出**字节完全相同**的命令身份，否则 ESP32 会正确地上报 command-id/digest 冲突」。

⇒ **`command_attempts` 是「这条物理命令当时确实以这个字节序列发出去了」的唯一证据**，
也是拒绝伪造/重放响应的唯一凭据。它**不是** outbox 那样的机制副产物：
删掉它，`wire_digest` 与 `envelope_id` 无法从任何其它表重建
（`stableWireDigest` 是 `sha256(commandID|actionID|actionVersion|requestHash|attemptNo)`，
可由 execution 重算 `stable_wire_digest`；但**传输层实际写入的 `WireDigest` 是 `channelCmdV2WireDigest`
/ `periphWireDigest`，含 `bootID`/`channelID`/`deadline`/`payload`，且覆盖写入了 attempt 行**
——即「**当时实际用的**是哪一个」不可重算）。

**增长速率量级**：≈2.2×10² 行/天，与 execution 1:1（`AttemptNo` 硬编码为 1）。
实测 3773 vs execution 3776：差 3 条 = 3 条 `CANCELLED` 的 outbox 从未进入 `dispatch`，
因此**从未创建 attempt**——即 attempt 只记录「真正被传输层接受过的尝试」（模型注释 `:65-66` 自述此设计）。

**证据唯一性：Y**
- `boot_id`/`wire_digest` 的「当时实际值」唯一；
- 「这条命令是否真的被发出过」的唯一物理证据（execution 的 `DISPATCHED` 状态可由 `RecoverExpired` 事后改写为 UNKNOWN，
  但 attempt 的 `published_at` 一旦写下就不再变）。

**裁决：保留 730 天，按 `created_at` 删，与 `command_executions` 同寿命；且不得短于 execution（INV-6）。**

**为什么绝不可以像 outbox 一样短（这是本任务给「另一个子代理」的反例警示）**：
若按「attempt 是 execution 的副产物」把它归入 30 天档，则第 31 天起
「这条命令当时是否真的发出去了」只剩 execution 的 `DISPATCHED` 标记——
而 `RecoverExpired`（`inbox.go:188-205`）会把超期未收到 final 的 execution 改写成 `UNKNOWN`，
**这个改写会抹掉「曾经 DISPATCHED」这一事实**（`updates` 覆盖 `status`）。
于是 attempt 行就成了唯一的见证。**删 attempt = 抹掉「设备到底有没有收到这条命令」的唯一答案**，
而这正是本系统最核心的安全问题（一个自动化规则开了一次阀门，事后责任归属取决于它）。

**代价**：保留 730 天意味着约 730 × 223 ≈ 1.6×10⁵ 行（仿真速率）；生产按操作量线性放大。
这是本批表里**最贵的保留决定**，也是**最不该省的一笔**。

#### 2.8.3 三个问题的正面回答

**问题 1：留 365 天 / 30 天 / 干脆停写，哪个对？**

在「无读取者」这一事实下，**「保留 365 天」不是正确裁决**——它是在为一个不存在的消费者付存储与维护成本，
且保留期越长，**越会掩盖「读取路径从未接线」这件事**（表里有数据，看起来功能是好的）。
三个选项的裁决如下：

| 选项 | 评价 | 理由 |
|---|---|---|
| 留 365 天（原裁决） | ❌ **撤回** | 保护空气：没有任何查询会因这 365 天而受益；且与「删除即不可恢复」的成本不对称 |
| 留 30 天 | ⚠️ 仅在**明确要补读取路径**时可用 | 一旦读取路径落地，30 天数据足以验证正确性（对比 raw 与 rollup 的口径），且不长期占成本 |
| **停写 + 清理 + 保留积压判定** | ✅ **推荐** | 停写直接消除增长源（4.9×10³ 行/天）；已写入的 26586 行**暂不删**，等读取路径决策后一次性处置 |

**推荐裁决（分两步，先停增长、再谈保留）**：
1. **立即停写**：把 `SensorParserConsumer.SetRollupSink`（`nodemgr/manager.go:255`）置空，
   或让 `RollupConsumer.Upsert` 在读取路径未接线前直接 return。
   **收益**：增长源消失（≈4.9×10³ 行/天 → 0），且**不丢失任何当前能力**（无消费者）。
   **代价**：**零**——当前没有任何查询依赖它。这是本文档中**唯一一条代价为零的处置**。
2. **已写入的 26586 行暂留**（不设自动清理），作为「读取路径是否值得做」的决策输入：
   若决定补读取路径，这批数据可用于离线验证聚合口径正确性；若决定不做，则与 `operation_logs` 同案**退役**（DROP + 删模型）。
3. **`models.go:268` 的注释必须修正**（当前与代码不符，属文档债）。

> 为什么不停写又清理、而是先停写：**清理是治标，停写是治本**。
> 对一张没有读取者的表，按天清理等于「持续生产垃圾 + 定期清扫垃圾」两个成本一起付。

**问题 2：INV-7 还成立吗？**

**不成立，撤回。** INV-7（「rollup 保留期 ≥ max(`logical_devices.retention_days`)」）
的前提是「存在一个会用 rollup 的长跨度趋势消费者」。该消费者**不存在**（`precisionFor` 零调用者），
因此这条不变式**在保护空气**——它会对一个没有人问的问题施加约束，并在有人把 rollup 窗口调短时
报出一个没有实际意义的红。

**改写形式（保留其真实内核）**：原不变式真正想守的是
「**不能出现"raw 已删、聚合也没了"的数据空洞**」。它只在读取路径存在时才有意义，故改为**条件式不变式**：

> **INV-7（修正版，条件式）**：*若且仅若* 生产代码中存在一个会对 `unified_data_rollup_1m` 发起 SELECT 的消费者
> （即 `precisionFor` 被接线、或历史端点查询该表），则必须同时满足：
> `rollup_retention ≥ MAX(logical_devices.retention_days)`，**且**该消费者在结果被截断时必须显式提示。

**测试（关键：它必须能因"读取路径落地但不变式没跟上"而变红）**：
一条门禁测试断言「**存在 rollup 消费者** ⟺ **rollup 清理器已配置且窗口 ≥ max(retention_days)**」。
即：有人接线了读取路径却没配保留期 → 红；有人把保留期配得比 raw 短 → 红；
**两者都没有时不红**（不会因为「一个还没做的功能」而产生噪声）。
这条测试的形态本身就是对 §3.17 教训的应用：不变式应当约束**真实存在的因果链**，而不是想象中的消费者。

**问题 3：它该进汇总表吗？算哪一类？**

**该进**（它确实无界增长），但**分类要改**：
**不是「运行遥测」，而是「未接线的产出物 / 读取侧欠账」**——与 `notification_channels`（写入侧欠账）对称。
「只写不读」不是一种数据性质，而是一种**实现状态**；把实现状态误当成数据性质，
就会推出「可按遥测窗口短留」这种错误结论（短留会销毁将来验证读取路径的唯一素材）。

**处置建议：停写 + 清理（暂缓）+ 限期裁决**，并进汇总表：

| 表 | 性质分类 | 建议策略 | 保留期 | 理由 | 证据唯一性 |
|---|---|---|---|---|---|
| `unified_data_rollup_1m` | **未接线的产出物（读取侧欠账，与 `notification_channels` 对称）** | **立即停写**；积压 26586 行**暂不清理**，限期（如一个迭代）决定「补读取路径」还是「退役」 | **暂缓** | 零读取者 ⇒ 留 365 天是在保护空气；但删掉会销毁验证读取实现的唯一素材 | **Y（弱，见 §4）** |

> 若最终决定**退役**：处置与 `operation_logs` 完全同案——删模型（`models.go:267-284`）、
> 删建表（`partition_mgr.go:175-210 EnsureRollupTable` 及其在 `cmd/server/main.go:120` 的调用）、
> 删 sink 接线（`nodemgr/manager.go:233,255`）、删 `RollupConsumer` 及其 PG 测试、
> 修正 `models.go:268` 与 `docs/设计/数据采集与数据链路.md:54,72,97` 的文档描述。
> **本轮不动手，仅列出影响面。**

## 3. `command_outboxes` / `command_attempts` / `command_executions` 三者关系（专项）

| 维度 | `command_executions` | `command_attempts` | `command_outboxes` |
|---|---|---|---|
| 角色 | **真相源**（业务事实） | **物理证据**（线路事实） | **机制状态**（投递队列） |
| 承载的唯一事实 | 命令是什么/参数/谁下/最终状态与原因 | **实际发出的字节身份**（`wire_digest`+`boot_id`）、发布时刻 | 「尚未交给传输层」的待办、发布发生的时刻 |
| 生命周期 | 创建 → 终态，之后只读 | 传输层接受时才创建 → 终态 | 入队 → 终态，之后**无用** |
| 终态后是否有作用 | 有（审计、幂等重放、结果查询、监控） | 有（响应防伪校验、发布事实） | **无** |
| 与其它表的关系 | 1 : 1 : 1（实测无孤儿、无一对多） | 依附 execution | 依附 execution |
| 删除后果 | 抹掉「做了什么、结果如何」 | 抹掉「是否真的发出去、发的是什么字节」 | 抹掉「何时入队」（发布时刻另有 attempt 记录） |
| 证据唯一性 | Y | **Y** | **N（终态后）** |
| 建议保留 | 730 天（终态；未处置 UNKNOWN 除外） | 730 天 | **30 天** |

**一句话裁决**：**`command_executions` 是真相源；`command_attempts` 是防伪锚点（同寿命）；
`command_outboxes` 才是「投递机制的副产物」（终态后冗余，可短）。**
把三者混为一谈（「都是命令域的表，统一保留 N 天」）会造成两个方向相反的错误：

- 把 outbox 当审计 → 为一个已无作用的队列行付 730 天的存储与合规解释成本；
- 把 attempt 当副产物 → **抹掉设备动作责任归属的唯一物理证据**，重演 §3.17 那次「论据被证伪」。

## 6. 不变式（必须永远成立的性质 + 用测试钉住的方式）

> 每条都写成「**什么样的改动会让它变红**」，让它成为**约束**而不是当前取值的快照（§3.17 教训）。

### INV-1 冷却基线锚点（`automation_events`）
**性质**：清理器删除 `result='executed'` 行后，对任意 rule，`MAX(triggered_at) WHERE result='executed'`
**不得比清理前更新**；若被删集合包含原 MAX，则必须存在一条 `base_cooldown` 行，
其 `triggered_at` ≥ 被删集合的 `MAX(triggered_at)`。
**测试**：构造 rule=R 的 3 条 executed（T-400d、T-30d、T-1h）→ 用 `now=T` 跑清理 →
断言存活行中 `MAX(triggered_at) ≥ T-30d`（若 30d 行被删则必须有 `base_cooldown ≥ T-30d`）。
**变红条件**：有人把档位 B 缩到 30 天以内、或删掉 `base_cooldown` 补写逻辑、或把补写放在不同事务里。

### INV-2 监控计数不被清理改写（`command_executions`）
**性质**：对任意时刻，`GET /api/v1/metrics` 的 `control.failed` / `succeeded` / `cancelled` /
`operations_total` / `unknown` / `unresolved_unknown` **不得因清理而减少**。
**测试**：写 1 条 `FAILED`（`completed_at = now-800d`）+ 1 条 `FAILED`（now）→ 跑清理 →
断言 `failed ≥ 2` 且 `operations_total ≥ 2`。
**变红条件**：有人把保留期改短、或实现里漏掉基线补偿、或把 `unresolved_unknown` 也一起删。

### INV-3 无副作用删除（全部表）
**性质**：清理 `command_attempts` 不得改变 `command_executions` 行数；清理 `command_outboxes`
不得改变前两者行数；清理 `node_events` 不得改变 `nodes`。
**测试**：三表各造 1 条过期终态行 → 记录三表行数 → 逐表单独跑清理 → 断言另外两表行数不变。
**变红条件**：有人加了 `ON DELETE CASCADE`、或写了跨表 DELETE、或 `command_executions` 的删除
牵连 `automation_events.command_id` 的清理。

### INV-4 在途行永不删（命令域三表）
**性质**：任何非终态行（`QUEUED/DISPATCHED/DEVICE_ACCEPTED/VERIFYING`、`PENDING/LEASED`）
无论时间多老都不得被清理。
**测试**：构造 `status='QUEUED'` 且 `created_at = now-1000d` 的执行行 + 对应 `PENDING` outbox →
跑清理 → 断言两行仍在。
**变红条件**：有人只按时间过滤而忘了状态白名单（这是清理器最经典的写法错误）。

### INV-5 保留期可承载展示窗口（`node_events`）
**性质**：`node_events` 的保留期必须严格大于两个消费端的展示需求：在保留窗口内，
`GET /nodes/status-history?limit=200` 必须仍能取满 200 条（在事件量足够的前提下）。
**测试**：造 300 条分布在「保留期第 1 天」到「保留期末日」的事件 → 跑清理 → 断言
按 `created_at DESC LIMIT 200` 仍返回 200 条且最老一条的年龄 ≥ 保留期 × 0.9。
**变红条件**：有人把保留期从 400 天降到 90 天而节点/事件量没变（本仓有 1000 节点仿真，
恰好会触发——这正是 §2.2 的隐患）。

### INV-6 证据保留期不得短于被审计对象的保留期（本仓已因反例被证伪过一次）
**性质**：任何「关于另一张表的证据」的保留期 ≥ 被引用对象的保留期。
本批实例：`command_attempts.retention ≥ command_executions.retention`；
`security_audit_events.retention ≥ command_executions.retention`（因 `request_id → command_id`）。
**测试**：构造 `command_executions` 行 E（`completed_at = now-700d`，仍在 730 天窗口内）
及其 `command_attempts` 行 / `security_audit_events` 行（`request_id = E.command_id`）→
跑全部清理器 → 断言 **E 存活 ⇒ attempt 与 audit 行必须存活**。
**变红条件**：有人把 attempt 或 audit 的窗口调到短于 execution（**这正是 `notification_deliveries`
那条被推翻的 45 天策略的同构错误**，见 §3.17）。

### INV-7（修正版，**条件式**）rollup 保留期只在有消费者时才受约束（`unified_data_rollup_1m`）
**性质**：***若且仅若*** 生产代码中存在对 `unified_data_rollup_1m` 发起 SELECT 的消费者
（判据：`precisionFor` 被接线，或某历史端点查询该表），则必须同时满足：
`rollup_retention ≥ MAX(logical_devices.retention_days)`，且该消费者在结果被保留期截断时必须显式提示。

**测试**（双向，缺一不可）：
1. **消费者存在** ⇒ 断言 rollup 清理器已配置且窗口 ≥ `MAX(logical_devices.retention_days)`。
   构造：注册一个（测试用的）rollup 消费者 + 一台 `retention_days=900` 的逻辑设备 ⇒ 断言清理窗口 ≥ 900 天。
2. **消费者不存在** ⇒ 断言**不产生**「窗口配置错误」的红（避免为不存在的功能报噪声）。

**变红条件**：
- 有人接线了 `precisionFor` / 新增了查 rollup 的端点，却**没有**同步配置保留期 ⇒ **红**（这是本条真正要防的）；
- 有人把保留期配得比 `MAX(retention_days)` 短 ⇒ **红**；
- 两者都没做 ⇒ **不红**（原版 INV-7 会在这里无意义地约束，已撤回）。

> **为什么改成条件式**：原 INV-7 假设「存在一个用 rollup 的长跨度消费者」，而该消费者不存在
> （`precisionFor` 生产零调用者，实测）。**保护一个不存在的消费者 = 保护空气**，
> 并且会让「rollup 该不该留」这个真正的问题被一条看似严谨的不变式掩盖过去。
> 不变式应当约束**真实存在的因果链**——这是 §3.17「复核要打前提，不要打措辞」的又一次应用。

### INV-8 死 schema 不得复活（`operation_logs`）
**性质**：迁移完成后，运行库中不存在 `operation_logs` 表，且生产代码不引用 `models.OperationLog`。
**测试**：`db.Migrator().HasTable("operation_logs")` 断言为 `false`；
再加一条仓库级门禁断言 `grep -rn "models\.OperationLog" backend/internal backend/cmd` 在非 `_test.go` 中零命中。
**变红条件**：有人把 `&models.OperationLog{}` 加回 `gorm.go` 的 AutoMigrate 列表。

### INV-9 outbox 冗余性必须用容差断言（`command_outboxes`）
**性质**：`command_outboxes` 被判为「终态后冗余」的全部依据，是下面两条**同时**成立：
- A：`payload_json == command_executions.params_json`（**逐字节相等**，可直接写等号）
- B：`|processed_at - command_attempts.published_at| < 1 ms`（**容差**，不得写等号）

**测试**：造终态命令（PROCESSED outbox + DISPATCHED attempt + QUEUED→终态 execution）→ 断言 A 等号成立、
B 差值 < 1ms；再跑清理 → 断言 execution 的 `params_json` 与 attempt 的 `published_at` **都仍在**。
**变红条件**（两条，方向相反，都必须能变红）：
1. 有人把 `payload_json` 改成与 `params_json` 不同的内容（例如只存命令 ID）⇒ A 变红 ⇒ **禁止清理**；
2. 有人把 B 写成 `o.processed_at == a.published_at` ⇒ **立刻变红**（实测仅 11/3773 精确相等）
   —— 这是「不变式写得太紧」的反向故障：它会阻止一个本来正确的清理。
> 第 2 条是本轮实测暴露的真实陷阱：本文档初稿正是把 B 写成了等号，
> 若直接落为测试就会永久变红。**「不变式过紧」与「过松」同样是有害的**，两者都要能被观测到。

## 7. 风险与代价（逐条，不只写收益）

| 策略 | 丢失的能力 | 新增的风险 | 缓解 |
|---|---|---|---|
| 1a `automation_events` 非执行档 30 天 | 「这条规则昨天为什么被冷却压制」超过 30 天不可答 | 低 | 档位 A 只含被抑制/失败事件，不含设备动作 |
| 1b `automation_events` 执行档 400 天 | 400 天前的规则执行史 | **若基线锚点未实现 → 冷却提前解除 → 设备动作多发** | 强制 INV-1 先行；`command_executions` 保留更久可交叉验证 |
| 2 `node_events` 400 天 | 节点可用率的长期历史 | 展示端 LIMIT 截断导致「用户以为还有历史」 | INV-5；必要时给前端加分页与「更早记录已清理」提示 |
| 3 `security_audit_events` 730 天 | 2 年前的认证/授权追溯 | **合规要求可能长于 730 天（等保常见 6 个月~3 年）** | 保留期做成可配置常量 + fail-closed 下界；由产品书面确认 |
| 4 `command_executions` 730 天 **+ 监控基线改造** | 700 天前的命令明细 | **基线机制本身可能算错，导致监控数字偏大或偏小** | 基线与存活行之和的口径写成单测；改动 metrics 端点需回归 |
| 5 `command_outboxes` 30 天 | 「何时入队」超过 30 天不可答 | 若等价性断言其实不总成立（例如未来支持多 outbox/重试），删的就是证据 | 等价性测试先行；一旦 `AttemptNo` 不再硬编码为 1，**必须暂停本策略并重评** |
| 6 `command_attempts` 730 天 | 730 天前的发布字节证据 | 存储成本（本批最大单项） | 接受：这是设备动作责任归属的唯一物理证据 |
| 7 `operation_logs` 退役 | 无（0 行、无读写者） | 若未来有外部系统直连该表读取 → 破坏兼容 | 未发布产品，无外部消费者；迁移前导出（0 行，空导出）留档 |
| 8 `rollup` **停写**（积压暂留） | **零**——当前没有任何查询依赖它 | 若将来补读取路径，历史窗口只有停写前的那 5 天数据（26586 行 = 单设备 5 天） | 把「是否补读取路径」提为一个**限期决策**；已停写的积压数据保留到决策日 |

**跨表风险（无 DB 外键带来的静默悬空）**：`automation_events.command_id`、
`security_audit_events.request_id`、`command_attempts.command_id` 均**无 FK 约束**（实测 `pg_constraint` 空集）。
删 `command_executions` **不会报错也不会级联**，只会留下指向不存在命令的引用。
⇒ 这是 INV-6 必须用测试钉住、而不能靠数据库保证的根本原因。

| 表 | 性质分类 | 建议策略 | 保留期 | 理由（一句话） | 证据唯一性 |
|---|---|---|---|---|---|
| `automation_events` | 审计证据 **+ 热状态** | 分层：非执行档按时间删；执行档长留 + 基线锚点 | **30 天 / 400 天** | 它同时是冷却窗的持久层，删之前必须先补基线锚点 | **Y** |
| `node_events` | 审计证据（运维时间线） | 单档按时间删 | **400 天** | 节点上下线的唯一时间线，且增长率全批最低（省不下空间） | **Y** |
| `security_audit_events` | 审计证据（安全/合规） | 单档按时间删，保留期可配置 | **730 天** | 运行期零读取者 ⇒ 消费者是「未来的争议调查」，窗口由产品拍板 | **Y** |

## 9. 未决事项（需要人裁决，不是工程能定的）

1. **`security_audit_events` 的 730 天**：是否满足产品的合规预期？（等保/审计常见要求 6 个月~3 年）
   —— 本文档只给默认值与下界，不给最终值。
2. **`node_events` 是否接受 90 天**：若产品把节点时间线定性为「运行遥测」而非「审计证据」，
   可按 90 天清理，但必须先满足 INV-5 并给前端加「更早记录已清理」的显式提示。
3. **`automation_events` 档位 B 的 400 天**：技术下界是「`cooldown_sec` 上界 1 天 + 余量」，
   400 天是审计口径的建议值，可下调至 90 天，但**不得低于 30 天**（否则 INV-1 的锚点会频繁触发）。
4. **`command_outboxes` 是否直接降到「终态后立即删」**：本文档取 30 天是为了保留一次重复发布调查窗口；
   若产品接受「调查靠 attempt 记录即可」，可以降到 7 天。
5. **⭐ `unified_data_rollup_1m`：补读取路径，还是退役？**（本文档 §2.8 最高优先级的待决项）
   事实：写入侧已完整实现（建表 + 监控 + PG 测试），**读取侧从未接线**（`precisionFor` 生产零调用者），
   已累积 26586 行且以 ≈4.9×10³ 行/天继续增长。两条路都自洽：
   - **补读取路径**：接线 `precisionFor` → 历史端点支持 `precision=rollup` → 长跨度趋势不再全量扫 raw。
     代价：一个功能的实现成本；收益：raw 分区 DROP 后仍能看长期趋势。
   - **退役**：与 `operation_logs` 同案（删模型/建表/sink/消费者/测试 + 修 4 处文档）。
     代价：放弃 v3.4 已投入的设计；收益：消除一个只写不读的表与一条死代码路径。
   **建议先停写**（零代价），把决策成本留到有人真正需要长跨度趋势时再付。
