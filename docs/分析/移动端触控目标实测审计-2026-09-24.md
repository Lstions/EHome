## 1. 结论摘要

**是，这是一类问题，但不是「全站普遍不达标」那一种。**

在 23 条路由 / 423 个真实可点控件中，**180 个（42.6%）**至少一个维度 <44px。但按 §4.4.5 逐条归类后：

| 类 | 含义 | 数量 |
|---|---|---|
| **A 真缺陷** | 规范字面点名的图标按钮/Switch <44px（A1），或任何控件连 §4.4.5 最低档 36px 都没到（A2） | **50** |
| **B 规范例外** | 表格行内/横滚容器内高密度工具条，≥36px，§4.4.5 明确允许 | 24 |
| **C 待定** | 非表格 36–43px 需裁决（C2）；**或 dev 环境 CSS 注入顺序所致、生产环境实测 44px（C1）** | 106 |

两个关键限定，不写清就会误判：

1. **180 这个数字有 46 个是 dev 环境的 CSS 注入顺序假象**。开发服务器下 Element Plus 样式晚于 `theme.css` 注入，压掉了既有 44px 规则；用 `dist/index.html` 的真实顺序复现则全部为 44px。**生产不受影响**（§8）。
2. **A 类 50 个里 30 个集中在 `/node/:id/overview` 一条路由**，且其中 19 个是自研控件（`.ph-edit` / `.copy-icon` / `.mini-edit` / `.link-btn` / `.btn-sm`）。**这不是全站问题，是节点详情页的问题**。

**对 Lead 既有结论的复核**：`.link-btn.chan-del` / `.chan-edit` **复现不到 42×20** —— 实测已是 **44×44**（M2 修复已落地）。桌面端仍是 42×20 且**应保持**（§4.2.3 有意紧凑密度）。详见 §3.1。

## 3. Lead 既有结论复核

### 3.1 `.link-btn.chan-del` / `.chan-edit`：**复现不到 42×20，实测 44×44**

测量时刻 `2026-09-25 09:35 CST`，`NodeOverview.vue` md5 `f363e7b83d04ebbc717d3f399fa3bf2e`：

| 视口 | `.chan-edit` | `.chan-del` | `.chan-row` | `minW/minH` |
|---|---|---|---|---|
| **390×844**（`hasTouch:true`, `pointer:coarse`） | **44×44** | **44×44** | 302×44 | `44px / 44px` |
| 1440×900 桌面 | 42×20 | 42×20 | 1152×44 | `auto / auto` |

**差异原因**：我这次实测期间，M2 修复（`NodeOverview.vue:2671-2682`，`@media (max-width:768px)` 内 `.chan-row .link-btn.chan-edit,.chan-del{min-width:44px;min-height:44px}`）**已经落地**。CDP `CSS.getMatchedStylesForNode` 确认命中该规则，且三个连续 run 稳定为 44×44。

**但 42×20 这个数字是对的 —— 它在桌面端仍然成立**，且**应当保持**：该修复被刻意限定在 `@media (max-width:768px)` 内，注释写明「桌面 1440px 实测同样是 42x20，但那是 §4.2.3 有意保留的紧凑密度（鼠标精度高），故桌面必须保持原样，规则不得外溢到 1440 块」。我在 1440×900 复核确认桌面仍为 42×20，**规则未外溢**，符合设计意图。

> **结论**：Lead 的 42×20 是**修复前的实测值**（描述准确），但已不是当前值。**以本报告 44×44 为当前事实**；桌面 42×20 不是缺陷。
> ⚠️ 另注：测量期间 `NodeOverview.vue` 被并发编辑（md5 从 `7454d6b0` → `b1954042` → `38971353` → `f363e7b8`），且一度出现**两个** M2 规则块（`:2658` 与 `:2671` 附近的 `:2678`）。截至本报告定稿，390 下实测稳定 44×44。

## 8. 关键发现：dev 与 prod 的 CSS 注入顺序不同（C1 类根因）

### 8.1 现象

`theme.css` 明确写了窄屏/粗指针要把输入控件抬到 44px（`theme.css:736`、`:763`、`:821`、`:949`、`:958`），且我实测 `pointer:coarse=true`、`max-width:768px=true`，**但 `.el-select__wrapper` 实算 32px，分页变量实算 32px**：

```
/data .el-select__wrapper  rect=200x32   ← 期望 44px
/firmware .el-pager li     rect=32x32    ← 期望 44px（coarse 分支写的是 44px）
```

### 8.2 根因（CDP `CSS.getMatchedStylesForNode`，输出为低→高优先级）

```
### /data .el-select__wrapper  rect=200x32
  [3] spec=0,1,0 (max-width:768px)  .el-input__wrapper,.el-select__wrapper,.el-textarea__inner  min-height:44px
  [4] spec=0,1,0 (pointer:coarse)   .el-input__wrapper,.el-select__wrapper,.el-textarea__inner  min-height:44px
  [6] spec=0,1,0 (none)             .el-select__wrapper                                          min-height:32px   ← 压掉上面

### /firmware .el-pagination  rect=300x76
  [3] spec=0,1,0 (none)             .el-pagination  --el-pagination-button-width:36px ...
  [4] spec=0,1,0 (pointer:coarse)   .el-pagination  --el-pagination-button-width:44px ...
  [7] spec=0,1,0 (none)             .el-pagination  --el-pagination-button-width:32px ...   ← 压掉上面
```

`[6]` / `[7]` 是 **Element Plus 自带样式**。三者**特异性完全相同（0,1,0）**，胜负**只由源码顺序**决定 —— 而 EP 的样式**排在 `theme.css` 之后**。

`theme.css` 自己在 F30 注释里**已经识别过这个坑**（`theme.css:934-951`）：小号 select 被 `.el-select--small .el-select__wrapper`（0,3,0）压制，解法是「写在第 4 条之后，同特异性 + 后出现 ⇒ 覆盖成功」。
**F30 只修了 `.el-select--small`（0,3,0）这一路，没有修裸 `.el-select__wrapper`（0,1,0）这一路** —— 后者被 EP 的**同特异性但更晚**的规则压掉。

### 8.3 决定性验证：这是 dev-only 假象

用 `dist/index.html` 真实加载顺序（`element-*.css` 在前、`index-*.css` 在后）与 dev server 实际顺序（EP 由 JS 动态注入，晚于 `theme.css`）分别复现，同一真机移动媒体特性：

| 顺序 | `.el-select__wrapper` | `.el-select--small` | `--el-pagination-button-width` |
|---|---|---|---|
| **prod 顺序**（element → index） | **44px** | **44px** | **44px** |
| **dev 顺序**（index → element） | 32px | 24px | 32px |

`dist/index.html` 实测：`element-GfQPuZdl.css`(offset 1446) 在 `index-DugQjQfc.css`(offset 1522) **之前**；`vite.config.ts:36` 用 `ElementPlusResolver({importStyle:'css'})`，而 `main.ts:6` 的 `./styles/theme.css` 在 dev 下由 JS 注入、**晚于** EP 按需注入的样式。

> **结论**：C1 的 46 个在**生产构建里不是缺陷**（实测全是 44px）。它是**仅存在于 dev server 的 CSS 级联假象**。
> **但它有一个真实的次生影响**：任何**在 dev server 上做的移动端触控验收**（包括本仓既有 UI/UX 门禁若跑 dev）都会读到 32px/24px 并可能据此「修」一个生产不存在的问题，或**漏掉**生产才暴露的问题。**建议触控尺寸验收一律跑 `dist` 构建产物**（与 `UIUX审计契约` §3「前端：后端直接托管 `frontend-shared/dist` 构建产物」的既有做法一致）。
