## 1. 现象与排查路径

### 1.1 用户看到什么

```
SOC / 电流加载失败：查询窗口 24h0m0s 超过帧表单次解码上限 6h0m0s，
且该窗口尚未被分钟聚合覆盖；请缩小到 6h0m0s 以内（例如先看近 1 小时），
或等待分钟聚合回填推进到该窗口

温度趋势加载失败：同上

保护历史加载失败：change 长窗读路径不可用（rollup 覆盖未验证或读取失败），
且窗口 720h0m0s 超过纯帧分段解码上限 8 天；请缩小窗口到 8 天以内
```

而 **≤6h 的图表全部正常**（1h 450 点、6h 477 点）。

### 1.2 读路径的判定逻辑

```
窗口 ≤ 6h（frameDecodeMaxWindow） → 帧表解码          ✅ 一直正常
窗口 > 6h                        → 走 rollup
                                    ↓
                             RollupCoverageVerified(device, day)
                                    ↓
                             只认 complete / missing
                                    ↓
                             dev14 2026-11-10 是 partial
                                    ↓
                             判定「覆盖未验证」→ 报错  ❌
```

关键：`partial` 是一个**粘性**状态 —— 只有回填能改写它，而回填每次都被同一个原因打断。

### 1.3 数据其实是齐的（决定性证据）

```sql
SELECT day, state, buckets FROM telemetry_rollup_coverage WHERE device_id=14 ORDER BY day DESC;
-- 2026-11-10 | partial | 0        ← 元数据说「没跑完」

SELECT count(*) FROM telemetry_rollup_1m
WHERE device_id=14 AND bucket >= '2026-11-10' AND bucket < '2026-11-11';
-- 1439                            ← 实际有 1439 个分钟桶（一天 1440 分钟）
```

**元数据与数据矛盾** ⇒ 问题在回填的「记账」，不在数据本身。

## 2. 根因

### 2.1 两个常量的语义差异

`internal/telemetry/store.go`：

| 常量 | 值 | 语义 | @1Hz 覆盖 |
|---|---:|---|---|
| `MaxDecodeFrames` | 32,768 | **一次性解码**（DecodeRange 单批）上限 | 9h06m |
| `MaxScanFrames` | 262,144 | **扫描预算**（从锚点起最多扫多少帧） | 72h49m |

### 2.2 传错的地方

`cmd/server/main.go` 的 rollup 回填解码器：

```go
// ❌ 修复前
pts, stats, err := telemetry.DecodeRangeAnchoredBounded(
    ctx, db, telemetryDict, deviceID, from, to, nil,
    window*2, telemetry.MaxDecodeFrames)   // ← 扫描预算传成了单批上限
```

```go
// ✅ 修复后
    window*2, telemetry.MaxScanFrames)
```

### 2.3 为什么恰好是 11-10 这一天

`DecodeRangeAnchoredBounded` 要先从**上一个关键帧**开始预热解码链（增量编码必须有锚点）：

```
dev14 的关键帧分布（生产实测）：
  2026-11-08 15:57:58  ← 关键帧
  ...（32 小时没有关键帧）...
  2026-11-10 05:21:20  ← 下一个关键帧

回填 2026-11-10 00:00~01:00 这一段：
  锚点 = 11-08 15:57  ⇒  预热跨度 32h05m  ⇒  ≈ 118,922 帧
  预算 32,768 ⇒ 只扫到前 27% ⇒ FramesTruncated = 86,154 ⇒ 本段报错
  ⇒ 整个单元回填失败 ⇒ MarkRollupCoverage(partial, buckets=0)
```

而 11-10 的 06:00 及之后各段，锚点已经近了（≤ 6 小时），旧预算够用 ⇒ 那些段是成功的。
**这解释了「为什么只有某一天坏、且那一天的数据其实是齐的」。**

## 4. 修复与验证

### 4.1 代码改动

1. `internal/telemetry/store.go`：导出 `MaxScanFrames`（包内别名保留），注释写明两个常量的语义差异。
2. `cmd/server/main.go`：改用 `telemetry.MaxScanFrames`，**并修正原注释** —— 原文写「段宽 1h × 1fps = 3,600 帧，远低于上限，这个分支在生产不会触发」，这是**错的**：它只算了段内帧数，没算锚点预热段的帧数。触发条件是「关键帧间隔 × 采样率 > 预算」，1 Hz 设备 9.1 小时没有关键帧就会撞上。

## 6. 教训

### 6.1 「参数语义」比「参数类型」危险

`DecodeRangeAnchoredBounded(..., maxWindow time.Duration, maxFrames int)` —— 两个参数都是数值，
编译器不会区分「单批上限」和「扫描预算」。**同名前缀的两个常量**（`MaxDecodeFrames` /
`MaxScanFrames`）只差一个词，review 时几乎看不出选错。

### 6.2 「看起来像资源不足」的错误可能是「配置太小」

报错文案「超过帧表单次解码上限」让人第一反应是「数据太多，该用 rollup」——
而实际上 rollup 数据就在那里，是回填的**记账**坏了。**症状指向的方向可能与根因相反。**

### 6.3 粘性状态 + 静默失败 = 长期不可见

`partial` 状态只会被回填改写，而回填每次都因同一原因失败 ⇒ **自愈不可能**。
这类「一旦进入就永不复原」的状态，进入条件必须极其保守（宁可标 missing 也不要标 partial），
或者必须有**带告警的持续重试**。

### 6.4 注释里的「不会发生」需要证据

原注释断言「生产不会触发这个分支」，理由是「段宽 1h × 1fps = 3,600 帧」。
这个算术**漏了锚点预热段** —— 而锚点跨度才是扫描预算的实际消耗方。
写「不会发生」时，要写清楚「在什么假设下不会发生」，否则注释会掩盖 bug 而不是防住它。
