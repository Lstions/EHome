## 1. 结论（先给判断）

**当前设计不合理。** 但不是"实现有 bug"层面的不合理，而是**需求被重新定义**层面的不合理：

1. **用户原始需求只有一条**：同一个物理设备从 1 号节点搬到 2 号节点后，历史数据不要丢。用户给了两个可接受解法 ——「合并旧数据」或「直接复用」。用户**明确否认**需要"逻辑设备"这个概念。
2. **该需求在能力层已被满足，而且不依赖逻辑设备**：`PUT /api/v1/edge-devices/:id` 同时改 `node_id` + `channel_id` 即可，身份与历史天然连续。本机实测（T）：改节点后 `logical_device_id` 不变、`node_id` 改变、**175,620 条历史点连续可查**（§5.3）。
3. **这条 30 行的路在 UI 上不存在**：编辑对话框里"所属节点"被显式隐藏（`EdgeDeviceList.vue:433` 的 `v-show="!editingDeviceId && createStep === 2"`），提示语写着"设备型号与通道绑定不可在编辑中变更"（`:541`）。用户唯一可走的路径是**删除 → 重新创建 → 在"历史数据继承"步骤里挑一个内部实体**。
4. **于是为一个已被满足的需求，新建了一层实体**：3 张表 / 4 张表现有表加列 / 3 条身份生成路径 / 6 个端点 / 3 个后台 worker / 96 种状态组合 / **4,088 行功能代码 + 8,964 行测试**（测试比实现多 119%）。
5. **这层实体的运行时代价已经发生**：生产 `GET /api/v1/logical-devices`（16 行数据）实测 **94–131 秒**，前端被迫把该请求超时放宽到 60 s 兜底 —— 而 60 s 仍小于 94 s，**兜底本身已经失效**（§4）。
6. **这层实体没有解决用户的原痛点，只是把它挪了个位置**：生产 16 条逻辑设备里 13 条没有存活实例；其中 3 条合计 **314 万行**历史（ld=2 持 292.3 万、ld=12 持 20.5 万、ld=13 持 1.4 万）**没有任何 API 能读到**（`GET /edge-devices/:id` 与 `:id/data` 对软删实例返回 404，ld=2 连实例行都没有），而 retention 仍会按逻辑设备的保留期继续删它们（T+C）。

## 2. 最初需求回溯（两层需求必须分开）

### 2.1 L0 用户原始需求（最强证据）

> 「逻辑设备我不知道谁抽象出来的，这根本不正确！根本不需要什么逻辑设备概念！我当初只是需要合并旧数据而已，比如一个边缘设备在1号节点，我重新连接到2号节点，数据就会丢失，所以需要历史边缘设备合并或者直接复用！但是后面不知道谁过度设计，曲解了我的意图。」

拆成一条需求 + 两个可接受解法：

| 编号 | 内容 | 来源 |
|---|---|---|
| **R0** | 同一物理设备从节点 A 换到节点 B 后，历史数据不丢、连续可查 | 产品负责人口述（T） |
| R0-解法① | 历史边缘设备合并 | 同上 |
| R0-解法② | 直接复用（把实例重新挂到新节点） | 同上 |

**用户没有提出**：逻辑身份层、跨实例身份锚点、N:1 多源合并、追溯链、保形去重、保留期按身份配置。

### 2.2 L1 方案自述需求（文档层）

`docs/archive/v4.0-重建前归档/设计/边缘设备数据生命周期管理方案.md`（650 行，v3.3 定稿）第 15–19 行写：

> 需求约束（**用户已确认**）：① 删除后默认保留数据 ② 继承/合并是可选、用户显式触发 ③ 保存时间可配置、默认 1 年 ④ 跨节点也能继承/合并、多源用户可选

**问题**：该文档标注"用户已确认"，但用户口述显示他只提了 R0。仓内可复核面（提交 / review / issue）**没有任何需求确认记录**；该方案以单次提交 `81300a2b`（2026-08-03）一次性加入 609 行，v1→v3.3 的 5 轮评审在仓内没有对应提交。

⇒ **L1 是方案作者对 R0 的展开与再定义**。以 L1 为基准评估"合理性"会循环自证 —— 这是本次评估最重要的口径校正。

## 3. 业务逻辑梳理（现状到底在做什么）

### 3.1 实体与不变量

```
edge_devices（物理实例：node + channel + hardware_id）
     │ N:1（一逻辑设备至多一个存活实例）
     ▼
logical_devices（数据身份：identity_key / merged_into / merge_status / purge_requested / retention_days）
     │ 1:N（unified_data / device_data 的 logical_device_id 归属；device_id 保留血缘）
     ▼
unified_data / device_data（月分区时序表）
```

设计不变量（C）：

| # | 不变量 | 位置 |
|---|---|---|
| I1 | `identity_key` 唯一；规则 `type:hardware_id`，hardware_id 空则 `uuid5(edge:<id>)` | identity.go:47-63 |
| I2 | 一逻辑设备至多一个**存活**实例 | handler_edge_device_lifecycle.go:68-86 |
| I3 | 合并要求源**无存活实例** + `purge_requested=false` + 未被来源组引用 | merge.go:134-162 |
| I4 | 每条数据 `device_id`（血缘）永不改写，只改 `logical_device_id`（归属） | 概念模型.md:5 |
| I5 | 大表不引入软删；retention 与 purge 均为硬删 | 边缘设备数据生命周期.md |

### 3.2 三条身份生成路径（复杂度核心）

| 路径 | 触发 | 撞 key 时的行为 |
|---|---|---|
| `PathStartup` | 启动 backfill | 无存活实例才复用，否则 `#2`/`#3` 序号 |
| `PathCreateNew` | 创建向导"作为新设备创建"（**默认**） | **永不复用**，直接序号 |
| `PathDelete` | 删除时补建 | 可复用，但跟随 merged_into 链、purge 中禁止复用 |

⇒ 三条路径 × 256 次重试 + ON CONFLICT 并发兜底（identity.go:115-165）。

### 3.3 状态机

| 字段 | 取值 | 谁写 |
|---|---|---|
| `merge_status` | NULL / pending / done | 合并事务置 pending；Migrator 置 done；失败复位 |
| `merged_into` | NULL / 目标 id | 合并事务；purge 时解除入边 |
| `purge_requested` | true / false | 删除设备勾选"同时删数据"；purge 放弃时清回 |
| `retention_days` | 90（默认，2026-09-12 由 365 下调） | 创建时快照系统配置；可经 PUT 改 |

**不闭合处（C，未实测）**：合并失败路径复位 `merged_into/merge_status`，但**不回滚已提交的搬迁批次**（每批独立事务，migrate.go:324-337）⇒ 数据被劈成两半且无补偿路径。审计报告已将该条标为"未取到实测"。

### 3.4 查询协议（性能问题源头）

所有按设备取数的入口都先 `ResolveDataQueryScope(edge_device_id)` → `ResolveScope(logical_id)` → SQL 条件：

```
(logical_device_id IN (?) OR (logical_device_id IS NULL AND device_id IN (?)))
```
（datalifecycle/scope.go:49-52，注释称"permanent"，为兼容 backfill 前 NULL 行）

这个 OR 就是 §4 的全部性能根因。**同一个仓库里已经有正确写法**：`api/scope_union.go` 把同一语义拆成两段 UNION ALL，仅给 history/latest-data 用，**列表富化没采用**。

### 3.5 列表富化的每次往返（放大 11 倍的地方）

`GET /logical-devices` 对当前页的**每一条**记录串行执行（handler_logical_device.go:80-98）：

| 步骤 | DB 往返 | 备注 |
|---|---|---|
| `CountInstances` | 1 | |
| `EstimateRowCount` → `ResolveScope` | 1 | 与 handler 自己已做过的 scope 解析**重复** |
| `EstimateRowCount` → `EXPLAIN` × 2 表 | 2 | 每表单次 EXPLAIN 在分区父表上再扇出 5 个分区 |
| `ScopeTimeRange` → `ResolveScope` | 1 | **第三次重复解析** |
| `ScopeTimeRange` → 边界查询 × 2 表 × 2 方向 | **4** | 每项最贵的就是这 4 条（§4.2） |
| **合计** | **≈ 11 次/项（实测）** | 其中 ≥2 次是重复计算 |

⇒ 端到端 = 16 项 × 11 次串行往返，而其中 3 项的 4 条边界查询各要 35–45 s。**模型算 81–104 s，实测 92.5–131 s，不需要任何未知开销解释。**

### 4.1 端点计时

| page_size | 实测耗时 | 返回条数 |
|---|---|---|
| 1 | 0.007–0.041 s | 1 |
| 4 | 0.022–0.040 s | 4 |
| 8 | 0.042–0.069 s | 8 |
| **12** | **37.3 s** | 12 |
| 16 | 74.4–123.7 s | 16 |
| **20（前端默认）** | **92.5 / 93.2 / 93.7 / 94.2 / 97.5 / 104.2 / 105.7 / 109.8 / 110.3 / 115.7 / 119.0 / 128.2 / 130.8 s（13 次）** | 16 |
| 200 | 118.9–121.5 s | 16 |

**这是阈值突变**：1→8 全程 <0.07 s，8→12 跳 1000 倍。

### 4.2 根因（EXPLAIN ANALYZE + 等价重写，同一会话）

| 查询形态 | 计划 | 耗时 |
|---|---|---|
| 现设计 OR，ld=12/13 | `Index Scan Backward using unified_data_202610_timestamp_idx` + Filter；**Rows Removed by Filter: 29,310,548–29,367,450**；Buffers hit≈102 万 / read≈42 万 | **26,932–32,087 ms**（三次独立采样：26,932 / 32,087 / 32,260） |
| 等价 UNION ALL 重写（同一会话，紧随其后） | 两分支各走 `logical_device_id` 索引 | **0.644 / 4.017 / 5.6 ms** ⇒ **41,820× – 6,500×** |
| 仅 logical 分支 | `Index Only Scan` + Index Cond | **0.720–1.040 ms** |
| OR，ld=14（数据最新） | 同上计划，但 Filter 第一行即命中 | 0.697–1.38 ms |

⇒ **同一系统的同一需求，两种写法差 3 个数量级（32 s vs 4 ms）**。这不是数据量问题，是实现选择问题。

### 4.3 成本的真实驱动量（"数据量越大越慢"是错的）

逐设备隔离实测（三位执行者独立采样，量级一致）：

| 逻辑设备 | unified_data 行数 | 最后一包数据 | OR 边界查询耗时 |
|---|---|---|---|
| ld=14 | **27,821,154**（占全库 86%） | 2026-10-23（持续写入） | **0.70–1.38 ms** |
| ld=15 | 1,566,530 | 2026-10-23（持续写入） | 0.70–7.44 ms |
| ld=2 | 2,923,306 | 2026-10-04（已停写） | **36.8 s** |
| ld=13 | 14,224 | 2026-10-05（已停写） | **36.3–44.9 s** |
| ld=12 | 205,073 | 2026-10-06（已停写） | **35.0–42.4 s** |

⇒ 成本 ≈ **该设备最后一包数据之后还有多少行**（= 停更时长 × 全局写入速率）。
**与数据量反相关**：2,782 万行的设备 1 ms，1.4 万行的设备 45 s。
**恰恰"已停写的老设备"最贵，而"换节点后旧实例停写"正是 R0 的必经状态** —— 也就是说这套设计对**它要服务的那类设备**恰好最慢。

### 4.4 那个 OR 兜底分支的真实命中情况（我复核并修正了一条）

| 表 | `logical_device_id IS NULL` 行数 | 兜底分支条件 | 实际命中 |
|---|---|---|---|
| unified_data | **0** / 32.4M | `device_id IN (实例集)` | 0 |
| device_data | **1,686,105** / 3.0M | 同上 | **0**（这 168 万行全部 `device_id=0`，见 consumers_heavy.go:120-124 只写 NodeID） |

⇒ 兜底分支在**两张表上都恒 0 命中**（第二张表虽有 168 万 NULL 行，但它们不属于任何实例，条件不匹配）。为一条永不命中的兼容分支，6 条读路径继承了 O(n) 扫描。

### 4.5 前端兜底已失效

`LogicalDeviceList.vue:356` 把该请求超时放宽到 60 s，注释写"生产实测 42.4s"；`api/logicalDevice.ts:99-102` 同样注释"后端提速后此参数可删"。**实测 92–131 s > 60 s ⇒ 页面在默认参数下依旧必然超时**，仍渲染错误态。数据来源页的逻辑设备下拉是同一段代码的第二份拷贝（`DataSourceList.vue:553-569`）。

⚠️ **错误归因已进入用户可见文案**：`LogicalDeviceList.vue:395` 直接对用户显示「请求超时：逻辑设备列表接口响应较慢（**生产实测约 42 秒**），请稍后重试。」——数字（42 vs 92–131）与解释（"响应较慢"而非"某条查询退化为全表扫描"）双错。这也是把实现缺陷呈现成"偶发慢"的根因。

另：生产 HTTP server **未设 ReadTimeout/WriteTimeout**（main.go:698-701），除 `EstimateRowCount` 有 3 s 兜底外，4 条 boundary 查询与 `CountInstances` **均无超时**⇒ 单个慢请求会持续占用连接直到查完。

## 5. 设计合理性评估（逐维度）

### 5.1 需求覆盖度：R0 被解决了吗？

| 判定 | 证据 |
|---|---|
| **能力层：已解决** | 本机实测 `PUT /edge-devices/1 {node_id: 新节点, channel_id: 新节点通道}` → 200；`node_id` 改变、`logical_device_id` **不变**、历史 175,620 点连续可查（T，§5.3） |
| **交互层：不可达** | 编辑对话框隐藏"所属节点"（`EdgeDeviceList.vue:433`/`:541`）；提交体不含 `channel_id`（`:1638-1645`）。用户只能删除→重建 |
| **默认路径：反着走** | 创建向导默认 `inheritMode='new'`（`:817`）⇒ `PathCreateNew` 永不复用 ⇒ 新实例新身份 ⇒ 历史断裂。需要连续时用户必须显式进入"历史数据继承"步骤挑内部实体 |
| **语义层：与物理现实相反** | 迁移有过渡期（新设备验好才删旧的）⇒ 必然短暂双实例；而设计把双实例当非法态（409 + `#N` 序号切碎历史） |

⇒ **R0 在"用户实际能走的路径"上没有解决，反而被替换成一条需要理解内部模型的六步流程。**

### 5.2 复杂度与收益之比

| 身份生成路径 | 3 × 256 重试 | identity.go |

| 后台 worker | 3（retention / purge / migrator）+ backfill | datalifecycle |
| 状态组合 | 96（审计口径：merge_status × merged_into × purge × retention） | backend-audit §6 |
| 功能代码 | **4,088 行** = datalifecycle 逻辑设备专有 3,130 行（identity/merge/merge_chain/preview/purge/retention/scope/query_scope/migrate/backfill/indexes + retention_task）+ 相关 handler 958 行（logical_device/lifecycle/candidates/scope_union） | `wc -l` 实测（整个 datalifecycle 包非测试共 6,007 行，其余为 8 个与本需求无关的表清理器） |

### 5.3 关键反证：直接复用确实可行（本机实测，已复原）

```
PUT /edge-devices/1 {"node_id":"30EDA0A9A808","channel_id":3}
=> http=200；node_id 30EDA0A9A808 / channel_id 3 / logical_device_id 仍为 1
GET /unified-data/historical?device_pk=1&category=rainfall&...
=> 200，175,620 点，首点 2026-09-20T08:18:24Z，末点 2026-10-01T06:56:53Z
（随后已把设备移回原节点并删除临时通道，dev 库已复原）
```

**结论**：满足 R0 不需要任何逻辑设备概念。这一条把"是否过度设计"从判断题变成事实题。

### 5.5 未被覆盖的副作用（比性能更严重）

| # | 现象 | 证据 |
|---|---|---|
| D1 | 生产 **13/16** 逻辑设备没有存活实例；其中 3 条合计 **314 万行**（ld=2: 2,923,306 / ld=12: 205,073 / ld=13: 14,224）⇒ **这些历史无任何 API 可读**，而 retention 仍会按保留期逐日硬删 | T+C |
| D2 | 数据读入口只有 `/edge-devices/:id/...`；一旦实例软删，GET `:id` 与 `:id/data` 均 404 | T（`GET /edge-devices/12` → 404） |
| D3 | 生产 `merge_jobs=0` / `notifications=0` / `updated_at<>created_at=0/16` ⇒ 合并与改保留期**零使用痕迹** | T（注：不能单独当删除依据，可能是 110 s 劝退。幸存者偏差） |
| D4 | 13/16 逻辑设备无存活实例 ⇒ 在 `/edge-device` 页不可达，只能从本页看见（而本页 110 s） | T |
| D5 | 合并失败不回滚已提交批次（状态机不闭合）；`logical_devices/edge_devices` 上 FK 约束实测 **0 条**，引用完整性全靠应用层 | C+T（未做失败注入实证） |

### 5.6 最根本的一条：这层身份**没有自己的读入口**

这是比"列表 110 秒"更根本的设计不一致（T+C）：

- 全仓所有数据读取端点都是 `/edge-devices/:id/...` —— 必须**先有一个 edge_devices 行**才能读。
- 唯一按逻辑设备取数的入口是 `GET /data-sources/overview?logical_device_id=`（**14.8 ms，实测 200**），但它只是 `data_sources` 台账的投影：生产该表 71 行、`distinct device_id = 2` ⇒ **只覆盖 2/16 个逻辑设备**，且只给最新值、无历史。
- ⇒ 生产 3 条"无存活实例但有数据"的 ld（314 万行）**物理上不可通过任何 API 读到**；而 retention 仍在按它们的 `retention_days=90` 计算到期日，从 2026-12-31 起逐日硬删。
- ⇒ **验收宣称的"历史连续可查"对这类身份从未成立**；而这正是用户"换个节点数据就丢了"的痛点，只是从"删了就丢"变成"90 天后静默删且看不见"。

**这与 §5.4 的过度设计形成最尖锐的对照**：为承载历史造了一层身份，这层身份却不提供读取历史的能力。

## 6. 结论：不合理在哪一层

| 层 | 判定 | 理由 |
|---|---|---|
| **需求层** | ❌ **被重新定义** | L1 把 L0 的"换节点后历史连续"放大成"独立身份实体 + N:1 合并框架 + 双层保留期"；方案文档标注的"用户已确认"无证据 |
| **方案层** | ❌ **过度设计** | 为一条 30 行可解的需求引入 4,088 行功能代码 + 8,964 行测试 + 3 表 + 3 worker；且把用户给的"或"（合并 **或** 直接复用）收窄成唯一正规路径 |
| **不变量层** | ⚠ **与物理现实冲突** | "一身份一存活实例"否定迁移过渡期的双实例；而双实例正是真实迁移必经状态 |
| **实现层** | ⚠ **有可修缺陷** | OR 条件让索引失效（32 s → 4 ms 可修）；合并失败不回滚；无可达读入口 |
| **产品层** | ❌ **名不副实** | 副标题承诺"统一视图"，但页面看不到任何测点值、无详情页；真实能力只有合并 + 改保留期，且两者零使用 |

**一句话**：这不是"逻辑设备做得不好"，而是"**为一个已能满足的需求造了一层概念**，然后为了消化这层概念不断补规则（保形去重、合并链、purge 守卫、两档通知、分区清扫），最终让一个 16 行的管理页需要 110 秒才能打开。

### 7.1 用户裁决（原文要点）

产品负责人对 §7.3 的 A/B/C 三选项明确选择 **C（撤除概念层）**，并给出三点口径：

1. **「根本不需要什么逻辑设备概念」** —— 不是"收缩承诺"（A）也不是"降级为可选"（B），而是整层删除。
2. **真正的需求只有一条**：「同一物理设备从节点 A 换到节点 B 后，历史数据不丢、连续可查」。

### 7.7 一句话结论

用户的原始需求（换节点后历史不丢）**在能力层早就成立**，且**不需要这层概念**；
本次移除把"为一个已满足的需求造的概念层"连同它的全部自造机制（合并链、保形去重、
查询 OR 兜底、per-identity 保留期、合并搬迁 worker）一次性删除，
并用三条**设备维度**的路径（原地换节点 / 恢复已删除设备 / 合并历史数据）直接满足需求。
§4 那些实测出来的性能悬崖与孤儿数据，是这层概念的**代价**，随它一起消失。
