# 生产镜像事故与部署校验（2026-10-21）

## 一、事故：部署了「不是从 main 构建」的镜像，回退了已修复的解析器语义

| 时间（UTC） | 事件 |
|---|---|
| 13:00:09 | 我用 `dea94e4d` 的干净树构建 `ehome-new:inverter-fix1` 并部署；8 字段温度帧开始正确产出 `fan1_speed/fan2_speed` |
| 13:05:21 | 另一个会话推送 UI 提交（`5230eece`） |
| 13:06:29 | 另一个会话部署 `ehome-new:ui-fix13`（**由旧代码树构建**，不含解析器修正）|
| 13:06:49 起 | 生产**回退**：`pv2_temp`/`dc_rectifier_temp` 重新出现（风扇转速再次被写成温度），持续到 14:37 |
| 14:37 | 我从 `b2936a9e`（当时 main）重建 `ehome-new:inverter-fix2` 并部署，语义恢复 |

**影响面**：设备 15 在 13:06–14:37（约 91 分钟）写入了 `pv2_temp`/`dc_rectifier_temp` 两个"假温度"字段，共约 **174 行/字段**。
未出现电池污染（`battery_voltage` 同期 524 行、52.4–52.9 V 全部正常），因为生产摄入链路带了命令上下文，不走 `ParseData` 的兜底猜测路径。

**根因**：不是代码缺陷，而是**部署产物来源不可追溯** —— 镜像没有构建来源标识，谁也无法在部署时判断它是否包含 main 上的修复。

## 二、立即修复

1. 从 `b2936a9e` 用 `git archive` 导出干净树重新构建（不用工作树，避免卷入未提交改动），得到 `ehome-new:inverter-fix2`。
2. 传输 → 生产 `docker load` → `.env` 改 `EHOME_IMAGE` → `docker compose up -d ehome`（仅重建 web）。
3. 验证：容器 healthy、`/health` 200、二进制含 5 个代码标记、按分钟统计 `pv2_temp=0 / fan1_speed>0`。

## 三、防复发：部署前镜像校验脚本

新增 `tools/deploy/verify_image.sh`，在镜像内用 `strings` 检查一组**与已修复缺陷一一对应**的代码标记：

| 标记 | 对应的已修复缺陷 |
|---|---|
| `techfineCommandByWire` | 命令注册表（单一真相源 + fail-closed） |
| `or exactly 10 (` | HTEMP 协议 V0.5 §5.8 的 10 字段形状 |
| `non-binary char` | HBMS1 状态串必须是 0/1 |
| `bms_temp_high` | HBMS1 `c7` = BMS 温度过高 |
| `leadingFixedDigits` | HTEMP 里 `KKK` 与 `O` 粘连的定宽解析 |

用法：

    tools/deploy/verify_image.sh ehome-new:inverter-fix2
    tools/deploy/verify_image.sh ehome-new:xxx --remote 192.168.20.6
    tools/deploy/verify_image.sh ehome-new:xxx --require some-new-marker

实测：正确镜像 exit 0（5/5 标记）；旧树镜像（`ehome-new:v8`）exit 1 并逐条列出缺失标记。

## 四、建议后续（未做）

1. **镜像内烙上构建来源**：Dockerfile 用 `ARG GIT_COMMIT` + `--label org.opencontainers.image.revision`，并把 commit 注入二进制（`-ldflags -X`），让 `/health` 直接回显。这样"部署的到底是哪份代码"变成可查询事实，而不是靠 `strings` 推断。
2. **部署前置门禁**：把 `verify_image.sh` 串进部署脚本，缺标记直接拒绝部署。
3. **多会话协作约定**：谁部署谁说明 commit；同一时间只允许一个会话改生产镜像（本轮事故就是并发部署 + 旧树构建叠加）。
