# 节点「型号」语义待评估（记录，未动代码）

> **状态**: 记录 / 待评估（不影响 2.10.0 发布）
> **日期**: 2026-11-19
> **触发**: 真机验证时 UI 节点详情「型号」显示 `esp32c6`，看起来不像产品型号。

---

## 1. 现象

节点详情页「型号」一栏显示 `esp32c6`（S3P 板则会显示 `esp32s3p`），与同一页的「平台/芯片」重复。

## 2. 值从哪来（三跳，已核实）

| 环节 | 位置 | 行为 |
|---|---|---|
| 生成 | `esp32-collector/main/app_state.c:45,110-126` | `s_model_name` 初值 = `CONFIG_IDF_TARGET`；若 `CONFIG_COLLECTOR_PSRAM` 且检测到 PSRAM，则追加 `p`（`esp32s3p`） |
| 上报 | `main/device_link_wiring.c:1006` | 作为 Hello 第 3 个字段 `model` 发出 |
| 入库 | `backend/internal/nodemgr/handler_hello.go:97,381` | `hello.Model` → `nodes.model` |
| 展示 | `frontend-shared/src/views/node/NodeOverview.vue:107` | 标签「型号」直接渲染 `nodes.model` |

也就是说：**「型号」= 芯片族名**，不是产品型号。设备端从来就没上报过产品型号。

## 3. 与 `nodes.platform` 的关系

`platform`（值为 `ESP32C6`）**不是 Hello 写的**，而是 `dbschema.BackfillNodeHardware` 调 `firmwareid.ParseNodeHardware(platform, model)` 解析出来的：

```go
// model 比 platform 信息多（带 p 位），优先它；platform 兜底芯片。
for _, raw := range []string{model, platform} { ... }
```

⇒ 两个字段的数据同源，且 **`model` 承担了硬件档案解析源**（PSRAM 的 `p` 位只存在于 model 里）。

## 4. 为什么不能直接改

把 `model` 改成产品型号会切断三处依赖：

1. `ParseNodeHardware` 的 PSRAM `p` 位来源 → OTA 闸门 `hw_psram` 会退化成 `""` → 所有 PSRAM 板子被判 `OTA_GATE_HARDWARE_UNKNOWN`；
2. `BackfillNodeHardware` 的 `platform` 规范化；
3. 前端 `NodeList.vue` 的「型号筛选」facet（当前按 model 去重）。

## 5. 可选方向（未决策）

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 只改文案 | UI 把「型号」改成「芯片」，另加「产品型号」占位（显示 —） | 最小，1 文件；但产品型号仍然无处存 |
| B. 新增独立字段 | `nodes.product_model`（出厂配置上报或人工录入），`model` 保持芯片族名 | 加列 + Hello 带字段 + UI 一栏；中等 |
| C. 重定义 model | Hello field 3 改产品型号，硬件档案改由新字段携带 | 协议不兼容，需两端同版本灰度；最大 |

**建议**：先做 A（立刻消除误解），把 B 排进下个迭代；C 只在确实需要「一型号多芯片」时再考虑。

## 6. 本次发布怎么处理

不改代码，只在 2.10.0 发布说明与本文记录该语义，避免后续把 `esp32c6p` 误当产品型号做运营统计。
