### 1.2 计数口径（所有步数可复算）

| 量 | 口径 |
|---|---|
| 1 步 | 一次离散的**用户交互**：点击/触碰、选择一个下拉项或卡片、录入一个字段、翻一页、在确认框作出一次选择。页面自动加载/渲染不算步 |

### 1.3 评级定义

| 评级 | 判据 |
|---|---|
| 合理 | 入口可达且唯一/一致，步骤与任务心智模型匹配，危险操作有相称保护，失败可恢复 |
| 可优化 | 主路径可完成，但存在入口重复、额外步骤、语义不一致、失败反馈缺失等可裁剪项 |
| 不合理 | 主路径不可达、关键步骤缺失、同一任务被拆成互相矛盾的多条路径，或存在无保护的实质风险 |

## 3. 流程明细

### 3.1 流程 1：首次初始化与登录（`/initialize` → `/login` 引导、失败锁定与恢复）

**触发入口**
- 首次访问深链 `/initialize`：**不存在该路由**——`router/index.ts:21-26` 只注册 `/login`；未知路径落到 `router/index.ts:168-173` 的 404 兜底 `NotFound`。这与任务书写的“`/initialize` → `/login` 引导”不符：真实引导是**登录页内部按认证状态切换表单**。
- 正常入口：任一受保护深链被守卫拦截 → `router/index.ts:198-202` 重定向 `/login?redirect=<fullPath>`。
- 已登录用户访问 `/login` → `router/index.ts:204-206` 弹回 `/dashboard`。
- 键盘路径：用户名/密码输入框 Enter 提交（`components/forms/LoginForm.vue:17,31`）。

**前置条件**
- 后端可访问；`GET /api/v1/auth/initialization` 返回 `uninitialized|initialized|migration_required|disabled`（`api/auth.ts:21-27`；后端 `handler_auth.go:39-56`）。
- 未初始化时，操作者持有 `make up` 输出的一次性初始化凭据（有效期 10 分钟，界面在 `InitializeAdminForm.vue:29-31` 自述）。

**步骤序列（首次初始化，桌面）**

| 步 | 动作 | 控件 | 锚点 |
|---|---|---|---|
| 1 | 打开部署地址 → 登录页挂载，读认证状态 | 页面自动 | `views/auth/Login.vue:130-136` |
| 2 | 状态 `uninitialized` → 渲染初始化表单 | `InitializeAdminForm` 条件渲染 | `Login.vue:56-59` |
| 3 | 粘贴初始化凭据 | `el-input` | `components/forms/InitializeAdminForm.vue:15-27` |
| 4 | 输入管理员用户名 | `el-input` | `InitializeAdminForm.vue:28-38` |
| 5 | 输入管理员密码 | `el-input`（≥8 位） | `InitializeAdminForm.vue:40-53` |
| 6 | 再次输入确认密码 | `el-input` | `InitializeAdminForm.vue:54-67` |
| 7 | （可选）邮箱 | `el-input` | `InitializeAdminForm.vue:69-79` |
| 8 | 提交“创建管理员并继续” | `el-button` | `InitializeAdminForm.vue:81-93` → `Login.vue:252-265` |
| （成功后） | 用新账号重新登录：用户名、密码、点「登录」 | 3 控件 | `Login.vue:260-262`；`LoginForm.vue:9-56` |

- 表中第 1/2 行为自动过程（不计步），第 7 行邮箱为可选步骤（不计入基线）。
- **步数 8** / 点击数 2 / 必填决策 4：凭据、管理员用户名、管理员密码、确认密码、点「创建管理员并继续」（5 个交互步）＋重新登录的用户名、密码、点「登录」（3 个交互步）；输入文本不计点击，故点击数只有 2 次按钮激活（“创建”和“登录”）。
- 纯登录路径（已初始化）：步数 3（用户名、密码、点「登录」）；点击 1；必填决策 2（“记住我”为可选，不计）。

**反馈与失败恢复**
- loading：提交时按钮文案 `创建中...`（`InitializeAdminForm.vue:89`）；登录按钮 `登录中...`（`LoginForm.vue:54-56`）。
- 成功：`管理员账号创建成功，请使用新账号登录。`（`Login.vue:259-260`），表单不自动登录，需重新输入账号密码。
- 失败：初始化失败写 `errorMsg`（`Login.vue:262-263`）；登录失败按状态分支（`Login.vue:193-221`）：
  - 429：提示“登录尝试过于频繁”（`Login.vue:196-205`）；
  - 非 401（网络/超时/5xx）：`getLoginErrorMessage` 区分网络、超时、服务器（`Login.vue:230-242`）；
  - 401：前端本地计失败数（5 次锁 5 分钟，`utils/loginLockout.ts:27-28,65-81`），提示“还剩 N 次机会”或锁定分钟数（`Login.vue:212-221`）。
- 锁定恢复：`lockSeconds` 每秒刷新，为 0 时解锁（`Login.vue:113-120`）；锁定期间按钮禁用（`LoginForm.vue:52`）。
- **UI 实现缺陷（U6）**：`Retry-After` 头（后端 `handler_auth.go:91-93`）没有被 `api/client.ts:85-90` 映射到 `retryAfterSeconds`，但 `Login.vue:199` 读取该字段——实际 429 永远只显示“稍后重试”，拿不到具体秒数。另前端 5 分钟锁定与后端 15 分钟窗口（`handler_auth.go:33`）不一致：本地解锁后再次尝试仍会被服务端 429 继续拦截，用户会看到“刚解锁又失败”。

**危险操作保护**
- 初始化凭据一次性使用、10 分钟有效；后端 `VerifyInitializationCredential` 对失败/锁定有独立错误（`backend/internal/auth/initialization_token.go:18-19,43-44`）。
- 登录页无“退出/清除”类破坏性动作；忘记密码只给运维命令提示（`LoginForm.vue:59-67`）。

**可发现性**
- 初始化入口依赖“登录页自动切换”，没有任何 `/initialize` 直链或运维文档内链接；知道 `/initialize` 的用户会直接落 404（U2）。
- 状态文案对 `migration_required/disabled` 只提示“通过本机运维流程恢复”/“联系管理员”（`Login.vue:122-127`），无进一步入口。

**重复入口/断裂点/认知负担**
- 断裂点 1：初始化成功后必须**重新登录**，凭据状态机与登录表单在同一页切换，用户刚输入的密码要再输一次（无预填）。
- 断裂点 2：`/initialize` 深链 404（结构性入口缺失 + 404 缺陷类别）。
- 认知负担：两套锁定窗口（前端 5 分钟、服务端 15 分钟）与两处计时（页头倒计时 + 429 文案）互相矛盾。

**评级：可优化（理由）**
- 主路径（首次访问 → 初始化 → 重新登录）完整可走通，状态分支与错误文案覆盖度高于同类页面；但深链不可达、双锁定窗口语义冲突属于入口设计与状态机协同问题，而非单纯 UI 缺陷。

**精简/合并候选**
1. **初始化成功自动进入登录态**（或直接签发 token 跳 `/dashboard`）：省 3 步（重新输用户名、密码、点登录）+ 2 次输入；风险：需后端在 `/initialize` 返回 token 或前端临时取一次登录；依赖：`handler_auth.go:59-75` 契约变更。预计节省 **3 步**。
2. **合并锁定源为服务端单一真值**：前端把 429 的 `Retry-After` 作为唯一倒计时源，删除本地 5 分钟锁定；节省 0 步但消除“刚解锁又失败”的往返；风险：离线场景失去前端保护（可保留为纯提示）；依赖：`api/client.ts` 透出 header 字段。
3. **增加 `/initialize` 显式路由/重定向到 `/login`**：消除 1 个断裂入口；风险：低；依赖：`router/index.ts` 增补一条 `redirect`。

### 3.5 流程 5：设备控制（驱动动作选择 → 参数 → dry-run 预览 → 确认执行 → 结果反馈）

**触发入口**

- 键盘路径：动作项支持 Enter/Space（`DeviceControlPanel.vue:35` `@keydown.enter.space.prevent`）。

**前置条件**
- 设备存在且已绑定节点；动作目录由 `GET /edge-devices/:id/actions` 拉取（`api/deviceOperation.ts:25`）。
- 可用性受资源快照新鲜度影响；不可用时给“立即恢复”或冻结说明（`DeviceControlPanel.vue:11-28,64-88`）。
- 中/高风险动作要求操作理由，且可能要求 10 分钟内重新验证密码（`DeviceControlPanel.vue:53-58,148,155-157`）。

**步骤序列（桌面，以“带参数的中风险动作”计）**

| 步 | 动作 | 控件 | 锚点 |
|---|---|---|---|
| 1 | 菜单「边缘设备」 | 菜单项 | `MainLayout.vue:400` |
| 2 | 点设备「详情」 | `el-button` | `EdgeDeviceList.vue:256` |

**反馈与失败恢复**
- loading：动作卡 `busy`、`submitting` 状态；确认按钮无独立 loading（`ActionConfirmationDialog.vue:6`），靠外层 `submitting`。

- 失败：
  - 有响应的 API 错误 → `feedback.handleError(error,'操作未能提交')`，409 时自动重拉目录（`:154`）；
  - 网络级不确定 → `ElMessage.warning('操作结果未确认，已刷新状态；请勿重复提交')`（`:154`）；幂等键保证不产生第二次物理操作（`api/deviceOperation.ts:36-44`）。
- 幂等/重试：同 `Idempotency-Key` 对无响应请求自动重试一次（`deviceOperation.ts:38-43`），是本仓最完整的失败恢复设计之一。
- 结果未知（UNKNOWN）提供“人工处置”对话框，要求结论 + 理由（`DeviceControlPanel.vue:51,159-160`）。

**危险操作保护**
- 中/高/严重风险必须填操作理由并进确认对话框（`DeviceControlPanel.vue:148`；`ActionConfirmationDialog.vue:3-6`）。
- 高风险动作可能要求重新输入密码（`DeviceControlPanel.vue:53-58,155-157`）。
- 不可用原因按“为什么/怎么办”分类聚合，冻结类明确“无需操作”（`DeviceControlPanel.vue:8-28`）。

**可发现性**
- 「受控操作」卡位于详情页主体中段，无独立菜单；BMS/逆变器/通用详情页均有，位置一致。
- **dry-run 预览缺失**：全仓 grep `dry-run|dryRun|dry_run` 在业务源码中无任何实现（仅 `frontend-shared/node_modules` 与 backend 迁移脚本），`ActionConfirmationDialog` 只显示动作名 + 风险等级 + 一句“将向设备发送参数变更”（`ActionConfirmationDialog.vue:3-4`）。任务书期望的“dry-run 预览 → 确认执行”中，**预览环节不存在**；对 26 个 BMS 动作（commit `7a3522b1` 全量启用的上下文）尤其缺少“参数将产生什么影响”的可用性预览，用户只能依赖动作描述。
- 「暂不可用操作」是折叠项（`DeviceControlPanel.vue:46`），可发现性尚可。

**重复入口/断裂点/认知负担**
- 重复入口：自动化规则也可调用同一批 `gpio_set/pwm_set_duty` 动作（`AutomationRules.vue:248`；后端 `deviceaction/periph.go:16-23`），但那是另一个域，属合理重复。
- 断裂点：操作提交成功后页面无“跳转到该 command 详情/结果”的入口（时间线里也没有 command_id 链接）；用户只能盯历史时间线。
- 认知负担：理由字段在确认对话框里必填（`ActionConfirmationDialog.vue:5-6`），但《操作理由》在低风险路径中完全消失，同一动作风险分级不同导致交互差异大。

**评级：可优化（理由）**
- 提交流程本身的分级确认、幂等、失败恢复明显强于同仓其他写路径；但缺少预览环节与提交后的结果闭环，且“结果未确认”与真实失败共用一句刷新提示，用户难以判断下一步。

**精简/合并候选**
1. **补齐 dry-run 预览**：在确认对话框渲染“目标设备 + 动作 + 参数表 + 预期验证方式（observation/readback）”；预计 +1 步但把“参数填错”类失败前移；风险：需后端提供参数解析后语义（现有 `input_schema` 可直接渲染，`api/deviceOperation.ts:7-10`）；依赖：`ActionConfirmationDialog` 增加 props。
2. **提交后定位最近一条操作**：排队成功后在历史时间线顶部高亮并自动滚动，或给 `command_id` 加详情对话框；预计节省 1-2 个观察步（找结果）；风险：低；依赖：`DeviceControlPanel.vue:48-51` 增加高亮。
3. **统一低风险动作语义**：低风险动作至少给“已排队 + 结果查看位置”的常驻提示（当前只有 4 秒 toast），或也走一次轻量确认；预计 +1 步换可追溯性；风险：低。

**评级：可优化（理由）**
- 建通道→测试→审计的主链路可达，错误/脱敏/语义诚实度都很高；问题集中在测试后无闭环跳转与审计无刷新/重试，属可补齐的流程断点。

**精简/合并候选**
1. **测试成功后按 `deliveries_url` 跳转或就地展开审计**：预计测试→结果确认从 **3 步降到 2 步**（测试后自动跳到该通道的审计过滤视图，省掉手动切菜单与选通道）；风险：低；依赖：前端使用后端已返回的 `deliveries_url`（`api/notificationChannel.ts:115`）。
2. **审计页自动刷新 + 手动重投**：页面在存在 `pending` 行时 5 秒轮询（或可见性变化刷新），失败行提供“重新投递”；预计为“反复切菜单/刷新确认结果”节省 1-2 步；风险：中（需后端支持投递重试端点，目前无）；依赖：后端新增 `POST /notification-deliveries/:id/retry`。
3. **投递审计从通道行深链**：通道行加“查看投递记录”链接到 `/notification-deliveries?channel=<id>`，审计页消费该 query 预填过滤；预计节省 1 步（免手动切菜单+选通道过滤）；风险：低。

**危险操作保护**
- 停用权威来源：`confirmDanger('组内候选将自动接替')`（`DataSourceList.vue:577-587`）。
- 删除数据源：`confirmDanger`（`:608-615`）。
- 切换为权威/重置：无确认（`:564-612`），但影响可逆（可再切换）。
- 合并：预览弹窗展示时间轴、重叠提示、数据量合计、新目标保留天数 + 目标名称必填（`LogicalDeviceList.vue:123-217`），属本仓最完整的破坏性操作预览之一；但合并**没有第二次 `confirmDanger`**，预览弹窗的“确认合并”即最终确认（`:208-217`），按钮为 primary 而非 danger——风险披露充分但按钮语义不足。

**可发现性**
- 数据源页把“权威/待命/熔断/停用”状态与健康度、连续失败、最后成功都放在列上（`DataSourceList.vue:124-152`），切换按钮的 disabled+title 解释了不可用原因（如“该来源已是权威”，`:158-163`）——可发现性较好。
- 逻辑设备合并入口常驻工具栏并有 disabled 原因提示（`LogicalDeviceList.vue:25-44`）。
- 但“合并后我的数据去哪了”的追溯只在列表行标签（`已合并 → #id`，`:60-62`）与进度弹窗；没有专门的合并历史页。

**重复入口/断裂点/认知负担**
- 断裂点 1：新建来源要求**手输**逻辑设备 ID 与来源边缘设备 ID（`DataSourceList.vue:245-282`），无选择器；ID 写错只会得到后端校验错误（无前端存在性校验）。
- 断裂点 2：逻辑设备合并的勾选是**当前页**的；分页下无法跨页选择 2 个同类型设备（`LogicalDeviceList.vue:50-53,111-120`，`el-table` selection 不带 `reserve-selection`）。当设备散落在不同页时任务不可完成。
- 断裂点 3：retention 深链只查当前页且失败静默（`:616-630`）。
- 认知负担：来源配置（`/data-sources`）与逻辑设备（`/logical-device`）分属两个菜单，但“主备/合并”是同一套逻辑设备生命周期的两个阶段；用户在两个页面之间来回切换才能完成“建来源→看健康→合并”。

**评级：可优化（理由）**
- 主路径完整、预览/冲突/进度反馈质量高；主要问题集中在 ID 手输、跨页选择不可行、深链命中率三处可运维性缺陷。

**精简/合并候选**
1. **来源表单改为设备选择器**：逻辑设备与边缘设备用 `filterable` 下拉（复用 `DataSourceList.vue:62-68` 的 `deviceOptions` 与 `edgeDeviceApi`）；步数不变（选择替代输入），但把“输错 ID”从提交后错误前移为选择事件；风险：低；依赖：新增边缘设备选项加载（`:755` 只加载逻辑设备）。
2. **合并选择支持跨页/服务端筛选**：`el-table` 加 `reserve-selection` + 前端维护选中 ID 集合，或提供“按类型合并全部”；预计让跨页场景从不可完成变为 **4 步**；风险：中（需在预览与提交时校验全部选中项）；依赖：`LogicalDeviceList.vue:50-56`。
3. **retention 深链改为按 id 直查**：`GET /logical-devices/:id` 或带 `id` 查询；未命中给出显式“通知引用的逻辑设备不存在/已合并”提示；预计消除 1 个静默断裂；风险：低。
4. **合并确认键改 danger + 二次确认**：预览弹窗的“确认合并”改为 danger，并在数据量超过阈值时要求输入目标名称确认；风险：低；依赖：`LogicalDeviceList.vue:208-217`。

## 6. 结论

1. **12 条核心流程中没有一条达到“合理”**：入口重复（数据查看 3+、边缘设备创建 2、通道 3）、深链失效（4 处）、功能不可达（节点接入、外设直控、OTA 回滚/任务列表）是主要结构问题；删除类确认、幂等、轮询、错误条等“实现质量”普遍较好，说明问题集中在**编排层**而非控件层。
2. 必须区分：
   - **流程结构性不合理**：节点接入无 UI、外设直控不可达、数据查看三入口口径不一、告警事件无处置/筛选、OTA 第二入口断裂/回滚缺失、来源-合并跨页不可行；
   - **UI 实现缺陷类别（已知即可，不展开修法）**：U1 静默 catch、U2 未消费 query、U3 死按钮、U4 导出范围失真、U5 移动端固定列、U6 锁定窗口/`Retry-After`、U7 死组件、U8 后端能力未接线、U9 请求形状错误。
3. 建议的落地顺序：先修 C1/C2/C3 三个“不可达→可达”，再修 C4-C8 的步骤收益，最后统一 C9/C10/C12 的语义与保护；所有候选均**不改变后端契约**（除 C11）即可推进，符合本仓“单主体、最小改动”的现状。
