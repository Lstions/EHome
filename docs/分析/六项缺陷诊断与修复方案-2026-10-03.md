# EHomeSystem 六项缺陷诊断（2026-10-03）

> 证据口径：本机工作树 commit `0ad5975`（main == origin/main）；本机实库 ehome-postgres；
> 截图来源 2026-10-03 08:44–08:49 生产 192.168.20.6:18090（只读探活 200）。
> 每条缺陷给出：现象 → 代码/数据证据 → 根因 → 判据（可复跑）。

## 缺陷 1：11 个操作「action is not enabled for rollout」，用户无法使用

**证据**：
- UI 原文 `action is not enabled for rollout` 逐字来自
  `backend/internal/commandexec/service.go:422`（`reasonForGate(gateActionEnabled)`）。
- 该 gate 判据：`appendResult(gateActionEnabled, definition.Enabled, ...)`（service.go:182）。
- `techfine_inverter` 共 11 个动作，全部 `Enabled: false`
  （`inverter_techfine.go:52` 的 `techfineReadAction` 工厂函数统一写死）。
- 数量吻合：UI 报「有 11 个操作暂不可用」，驱动恰好 11 个动作。
- 截图列举的「读取电池信息 / 读取 BMS 信息 / 读取 EEPROM 设置 / 读取发电量 /
  读取市电信息 / 读取输出信息 / 读取 PV1 信息」全部是 techfine 的动作名
  （`inverter_techfine.go:35-45`），**逐条对上**。

**根因**：`techfineReadAction` 里硬编码 `Enabled: false`。注释理由是「未获得 GB3024
实机证据」—— 这是**开发期 rollout 开关被当成了永久禁用**，且没有任何配置入口能打开。
用户看得见、点不动 = 禁用面 100%。

**修复方向**：这 11 个都是 `Semantics:"read"`（无副作用读查询），把它们改为
`Enabled: true`。同时 `TestTechfineReadActionsExcludeUnverifiedWrites` 里
`definition.Enabled` 必须为 false 的断言要同步改（它锁的是「禁用」这一现状，
不是安全属性 —— 安全属性是「不能有未验证的写」，继续保留）。

## 缺陷 2：采集器断电后数十秒才显示离线（要求 ≤5s）

**证据链**（三段时间常数互相叠加）：
| 环节 | 当前值 | 位置 |
|---|---|---|
| 固件 StatusReport 周期 | **5s** | `esp32-collector/main/main.c:68` `vTaskDelay(pdMS_TO_TICKS(5000))` |
| 服务端离线判定阈值 | **90s** | `offlinedetector.go:103` `now.Sub(*col.LastSeen) > 90*time.Second` |
| 边缘设备判定阈值 | **60s** | `offlinedetector.go:205` `time.Now().Add(-60 * time.Second)` |
| 检测循环 ticker | 5s | `offlinedetector.go:47` |

**根因**：阈值 90s = 「18 个 5s 心跳周期」（offlinedetector.go:102 注释自证），
这是为容忍丢包而设的宽松值，但用户要的是**断电后 5s 内可见**。90s 是主因，
不是 ticker。最坏可见时延 = 90s(阈值) + 5s(ticker) = 95s，与「数十秒」现象吻合。

**修复方向**：心跳周期 5s→1s、阈值 90s→3s、ticker 5s→1s。
但**必须先确认**：MQTT keepalive=30s（ehome_mqtt.c:920）+ LWT 未启用 ⇒
SO 网络断需要更久。断电是 TCP 硬断，理由要充分。

## 缺陷 3：命名混乱（UART0 / UART UART0 / UART / 串行 / 总线类型）

**证据（同一实体在本仓有 ≥5 种写法）**：
| 位置 | 值 | 来源 |
|---|---|---|
| ChannelList 表头 | 「硬件类型」+「总线类型」**两列** | ChannelList.vue:149/158 |
| ChannelList 总线类型列 | `uart→'串行'`、`i2c→'I²C'`、`gpio→'数字IO'`、`adc→'模拟'` | ChannelList.vue:417-422 |
| hardwareTag.ts（共享单一源） | `uart→'UART'` | hardwareTag.ts:23-28 |
| ChannelTerminal | `uart→'串口 (UART)'` | ChannelTerminal.vue:290 |
| NodeOverview 通道名 | `${hardware_type} ${hardware_id}` → `"UART UART0"` | NodeOverview.vue:1323 |

**根因**：`getBusTypeLabel`（ChannelList 私有）与 `getHardwareLabel`（共享）
**是同义的两份真相**，且取值不同（串行 vs UART）。同一个通道在列表页写「UART/串行」，
在共享组件写「UART」，在终端写「串口 (UART)」。
`channelName` 用 `hardware_type + hardware_id` 拼接，而 hardware_id 本身就是
「UART0」⇒ 渲染出 `UART UART0` 这种重复。

**修复方向**：收敛到 `utils/hardwareTag.ts` 单一标签源；删除 ChannelList 私有 map；
ChannelList 合并「硬件类型/总线类型」两列为单列（两者同源，重复列本身是缺陷）；
`channelName` 检测 hardware_id 已含总线名时不重复前缀。

## 缺陷 4：新建通道后改波特率报「bus_config 为空」+ 总线配置页波特率对不上

**证据**：
- 报错原文 `通道 bus_config 为空，无法重配波特率（请先配置该 UART 通道）` 来自
  `backend/internal/api/channel_reconfigure.go:31`。
- 触发条件：`ch.BusConfig == ""`。截图里 UART1 通道 `bus_config` 为空的直接来源是
  `handler_edge_device.go:548-550`：设备向导的内联建通道路径 **只在 caller 显式传
  bus_config 时才写入**，`dto.Channel.BusConfig` 为 nil 时落库空串（:463-469 注释自证）。
- 本地实库实测：`channels` 表 id=2 的 USB0 通道 `bus_config` 为空（该行合法），
  而新建 UART 通道若走向导内联路径同样为空 —— 但 UART 的波特率**必须有** bus_config 承载。
- 波特率「对不上」：`NodeOverview.resourceParameters` 显示
  `Number(resource.baud_rate || resource.max_baud)` —— 而 ResourceReport 的 uartEntry
  **只有 `max_baud`（能力上限），没有 `baud_rate`（当前值）**（handler_resources.go:25-33）。
  于是资源表显示的 5000000（max_baud）被当成「当前波特率」，与通道里真实的 4800/9600 冲突。

**根因**：两处独立 —— ① 建通道路径允许 UART 落空 bus_config；② 资源表把
**能力上限**当作**当前值**显示。第二个是纯粹的显示口径错误。

**修复方向**：① UART 通道创建时 bus_config 为空则按资源默认引脚 + 默认波特率补齐
（后端兜底，前端保持下发）；② 资源表「波特率」标签改为「最高 5000000 baud」，
当前值只从通道 bus_config 解（已有 `baudCurrentRate`）。

## 缺陷 5：新建边缘设备无数据却显示「在线」

**证据**：
- `models.EdgeDevice.Status` 的 gorm tag 是 `default:active`（models.go:93）。
- 本地实库实测：`模拟BMS` `last_data_at = 2026-09-23`（9 天前）、
  `status = offline` —— 已是 offline，说明离线检测**最终**会纠正。
- 但创建瞬间 status=active ⇒ 前端 `statusLabel('active') → '在线'`
  （EdgeDeviceList.vue:1354）。
- 更关键：`checkEdgeDevicesOffline`（offlinedetector.go:204-215）**只处理 cache 中
  `!lastData.IsZero()` 的条目**；`OnEdgeDeviceCreated` 写入的是
  `time.Time{}`（零值，:197）⇒ 零值被显式跳过 ⇒ **新建且从未上报数据的设备
  永远不会被这条路径判离线**。它会一直显示「在线」。

**根因**：三处叠加 —— ① 模型默认值 active；② 前端把 active 直接渲染为「在线」；
③ 离线检测跳过零值 last_data_at（本意是防误判，实际造成永久在线）。

**修复方向**：① 新建设备 status 初始化为 `pending`（或 `inactive`），收到首条数据才 active；
② 前端把 pending/inactive 渲染为「等待数据」而非「在线」;
③ 离线检测显式处理「cache 中有 ID 但 last_data_at 为零且创建已超阈值」的设备。

## 缺陷 1（11 个操作无法使用）：已修，且发现真正的根因在固件而非开关

**分两层，缺任一层都不算修好：**

1. 开关层：11 个动作 `Enabled: true`（`inverter_techfine.go` 的 `techfineReadAction`）。
   同步翻转测试断言（`definition_test.go`、`inverter_techfine_test.go`）——
   依据 `docs/设计/设备指令与操作体系演进方案.md` §4.2 第 3 项「解禁必须同步翻转断言」。
   新增 `TestAvailabilityCodeActionsStayDisabled` 钉住 fail-closed 未被放宽。
2. **传输层（真正的根因）**：单步 ChannelCmdV2 在节点侧一律映射为 `CMD_WRITE`
   （`bus_manager.c:1064`），于是
   - `read_size > 0` 且回复更短 ⇒ `complete_idle_response()` 判 **error 0x03**；
   - `read_size == 0` ⇒ `bus_worker.c:985` 成功但**零字节**。
   GB3024 回复是一行 15~40 字节 ASCII、长度不可预知 ⇒ **两种取值都必然失败**。
   ⇒ 只改开关**不会**让这 11 个操作可用。
   修复：节点对 V2 改为「行空闲即帧边界」，短回复原样投递，由服务端
   `VerifyFinal`→`VerifyControlAction` 做权威校验；**遗留写响应的短读仍判 error**（规则未放宽）。

**凭什么信它**：
- 帧字节被逐字节钉死在测试里（11 条命令 `HSTS\r` … `HIMSG1\r`）。
- 固件新增 `test_v2_short_read_delivers_partial_payload`，并保留
  `test_short_read_reports_command_error` / `test_idle_short_read_legacy_is_failure` 钉住遗留路径。
- **变异自证**：去掉 V2 豁免 ⇒ 新旧两条用例共 5 条 CHECK 红；把豁免扩大到所有路径
  ⇒ 遗留路径用例红。两个方向都被抓住，且改回后文件 md5 与改前一致。
- 服务端「校验失败 ⇒ final_failed」有代码路径佐证（`handler_channel_cmd_v2.go:54-56`）。

### ⚠ 主控自查发现的 P0 回归（已修，记录在案）

上面那句「服务端 verifier 是权威校验」**当时只对了一半**，而我把它当成了完整的安全前提。
固件改动落地后，我写了一个截断探针去验证这个前提，结果发现：

- **Techfine 的 verifier 当时并不校验帧结尾**（`ParseData` 用 `TrimRight` + `strings.Fields`）。
- 于是节点投递上来的**截断 ASCII 行会通过校验并产出错误数值**：
  实测 `"(220.5 08.0 0"` 被解析成 `pv2_power=0`（真实值 **960**）。
- 后果比"读取失败"更糟：**"失败"退化成了"静默的假数据"**，用户看到一个看似正常但错误的功率读数。
  这正是本仓历史上反复出现的那类缺陷（silent failure），而**是我这次改动引入的**。

修复：`VerifyControlAction` 增加 CR 结尾校验（GB3024 每条响应都以 CR 结尾）。
判据放在 verifier 而不是 `ParseData`：后者也被轮询路径（`CMD_SAMPLE`）调用，
那条路径的定帧由节点侧负责，收紧它会影响既有轮询行为。

**验证**：新增 2 条用例，逐字节截断穷举（18 个前缀，修复前 **5 个被采信**，修复后 **0 个**），
并用**具体数值后果**钉住危害（不得产出 `pv2_power=0`）。变异自证：删掉 CR 校验 ⇒ 2 条用例红，
且报错信息逐条列出被采信的前缀与错误数值。

**教训**：「下游有权威校验」这类论证必须**去读那个校验到底校验了什么**，
不能因为"有个 verifier 存在"就假定它覆盖了新引入的输入形态。

**没验证**：**无 GB3024 实机**（本机 `/dev/ttyUSB*`、`/dev/serial/by-id/` 均不存在）。
未做真机读回；台账 `证据路径` 字段如实留空，状态记 `enabled` 而非 `reviewed`。

## 缺陷 2（离线可见时延 → ≤5s）：已修，预算 1+3+1=5s

| 环节 | 改前 | 改后 | 位置 |
|---|---|---|---|
| 固件 StatusReport 周期 | 5000ms | **1000ms** | `esp32-collector/main/main.c`（宏 `STATUS_REPORT_PERIOD_MS`） |
| 节点离线阈值 | 90s | **3s** | `offlinedetector.go`（`NodeOfflineThreshold`） |
| 检测 ticker | 5s | **1s** | `offlinedetector.go`（`OfflineCheckInterval`） |
| 边缘设备阈值 | 60s | 60s（**有意不动**） | `offlinedetector.go`（`EdgeDeviceOfflineThreshold`） |

边缘设备阈值不跟着收到 3s：它按各自 `interval_ms` 轮询（BMS 实测 5000ms），
阈值小于轮询周期会让正常轮询间隙被误判离线，设备永久停在 offline。

**顺带修掉的真问题**：`nodemgr/handler_status.go` 原有一段论证「重启只要几秒，
远小于 90s 阈值，因此不会产生 offline→online 跳变」。阈值收到 3s 后**该前提不成立**
（几秒的重启与 3s 同量级），注释已如实改写：uptime 回退检测从「冗余保险」
变成「真实需要的路径」。**逻辑未改，只改注释**——但这是「改小一个常数会让别处论证失效」的实例。

**凭什么信它**：`TestOfflineLatencyBudget` 钉住预算=5s；边界语义（`>` 而非 `>=`）有专测；
三条常数任一改回都会让用例红（变异自证：阈值回 90s ⇒ 红；`>` 改 `>=` ⇒ 红）。
`backend/simulation` 的 90s 硬编码断言已改为引用生产常量。

**没验证**：固件只做源码级修改，**未编译进 ESP32 固件、未做断电实测**；
1s 周期对 MQTT/看门狗/带宽的实机影响未测。

## 缺陷 3（禁用全给我去掉）：已修，且给出了分母

改前 disabled 动作：`techfine_inverter` 11 个 + `prs3001/read_rainfall` 共 12 个。
改后 disabled 动作：**2 个**，且都是**写**操作并带 `AvailabilityCode`：

| 动作 | 类型 | 冻结原因 | 状态 |

## 缺陷 4（新建通道后改不了波特率 + 波特率参数对不上）：已修

两个独立缺陷：

(a) **空 bus_config**：波特率**只**存在 bus_config 里（`withUARTBaudrate` 改它的字节 2..5），
空串 ⇒ 该通道永远改不了波特率。前端在资源能力未上报时 `&& hw` 不成立就静默留空串并提交。
修复：① 服务端 `ensureUARTBusConfig` 按节点**已上报**的 UART 资源补齐（查不到则明确 400，
不静默落空串）；② 前端资源缺失时**拒绝提交**并给出可操作提示（覆盖 uart/i2c/spi）；
③ 布局收敛为单一实现（`buildUARTBusConfig` + `setUARTBaudrateBytes`），
新建与改写共用，杜绝第三个字节偏移实现。

(b) **波特率对不上**：`NodeOverview.vue` 写 `resource.baud_rate || resource.max_baud`，
而 ResourceReport 的 uartEntry **只有 `max_baud`（能力上限）没有 `baud_rate`**，
于是永远走回退分支、把上限当当前值显示。实测现场 `max_baud=5000000`，
界面显示「5000000 baud」，而通道里真实生效的是 4800（`bus_config=1415000012C008010000`）。
修复：上限明确标注「最高 5000000 baud」，当前值只从通道 bus_config 解，无通道时如实说未配置。

默认波特率 `115200` → `9600`：本仓真实设备是 2400/4800/9600，没有一台用 115200。
拿设备不支持的速率当默认值，等于「建完还得先改波特率」。

**凭什么信它**：`ChannelManagerBusConfigGuard.spec.ts` 断言「能力缺失时不得提交」
（变异自证：把守卫去掉 ⇒ 用例红）；后端 `channel_create_uart_busconfig_test.go` 断言
补齐后的 hex 能被 `withUARTBaudrate` 解析/改写，即「建完就能改波特率」这个用户可见效果。

**(c) 更新路径的残留缺口（复核时由子代理如实上报，已补）**：`PUT /channels/:id` 原先
把 `bus_config` 原样写回，包括空串 —— 创建路径守住了不变量，更新路径没守，
**一次 PUT 就能把已有通道打回「改不了波特率」**。不变量只守一半等于没守。
修复：更新路径同样走 `ensureUARTBusConfig`；非法非空值报 400 且**不落库**
（静默改写会让用户以为自己的引脚被采纳了，比明确拒绝更危险）。
新增 3 条用例（含 I2C 对照组，防「修一个坏一个」），**变异自证**：
去掉更新路径的兜底 ⇒ 2 条用例红。

> 同时修正一处**文档与代码漂移**：`ensureUARTBusConfig` 的注释原写「空或非法 ⇒ 按能力补齐」，
> 但实现是「空 ⇒ 补齐；非法非空 ⇒ 报错不改写」。已按实现改正 —— 这类漂移会让下一个人
> 依据注释做出错误判断。

## 缺陷 5（新建边缘设备明明没数据却显示在线）：已修，共三处缺口

用户看到的是「在线」，实际有三个叠加的缺口：

1. 模型默认 `status = "active"`（`models.go:93`），前端把 `active` 渲染成「在线」⇒
   创建即在线。改为默认 `pending`，前端渲染为「**等待数据**」（warning 色，不是 success）。
2. 数据到达时只从 `offline` 提升（`status = "offline"` 条件）⇒ pending 设备即使一直
   正常采数也永远停在 pending。改为 `status <> "active"`（任何非在线状态都被真实数据纠正）。
3. **最隐蔽的一处**：离线检测用 `!lastData.IsZero()` 跳过零值，而新建设备的
   `last_data_at` 恰好是零值 ⇒ **永远不会被判离线**。改为对「从未上报」的设备
   用 `created_at` 判超时。

**还有第四处（复核时发现）**：设备缓存只在 `Start()` 装载一次，
而 `OnEdgeDeviceCreated` 在生产代码里**没有任何调用点**（全仓 grep 为 0）⇒
运行期新建的设备根本不进缓存，永远不会被离线判定看到。改为每个检测 tick 重新同步
DB 中尚未离线的设备（add-only，不覆盖 `OnEdgeDeviceData` 刚写入的新鲜时间戳）。

口径同步修掉：`handler_metrics.go` 与 `handler_overview.go` 原来用 `status <> active`
兜底计 offline ⇒ 新建的 pending 设备会被算成「离线」（与原缺陷方向相反的同类错误）。
改为三态分开计数，监控页新增「等待数据」一行。

**凭什么信它**：新增 6 条用例覆盖「默认值是 pending」「从未上报超时判离线」
「刚创建不立即判离线」「pending 也进缓存」「运行期新建的设备能进判定视野」
「每 tick 重载不覆盖新鲜时间戳」。**变异自证 6 个方向全部被抓住**
（默认值改回 active / 零值分支绕过 created_at / 恢复零值守卫 / 只载 active /
去掉每 tick 重载 / 无条件覆盖），且每次改回后文件 md5 与改前一致。

**没验证**：无端到端实测（未真建一台设备观察它 60s 后转离线）。

## 缺陷 6（文案乱七八糟，全部统一）：已修，并找到重复前缀的成因

用户原话「一会 uart0，一会又 uart uart0，一会 UART，串行」对应**四个独立成因**：

1. 多个私有 label map：`ChannelList.vue` 私有 `getBusTypeLabel`（`uart: "串行"`）、
   `ChannelTerminal.vue` 私有 `typeLabels`（`uart: "串口 (UART)"`）、各处裸 `toUpperCase()`。
   ⇒ 收敛到 `utils/hardwareTag.ts` 单一来源，删除私有 map 与私有 tag 颜色函数。
2. **「UART UART0」的成因**：模板里手工拼 `${hardware_type.toUpperCase()} ${hardware_id}`，
   而现场的 `hardware_id` 本身就是 `UART0`/`UART1`/`I2C0` ⇒ 同一个词出现两遍。
   新增共享 `getHardwareDisplay(type, hardwareId)` + `hardwareIdIncludesBusName()`：
   自带总线名就只显示 `hardware_id`，纯数字/地址才补前缀。
3. 同一事实两列同源：`ChannelList.vue` 同时显示「硬件类型」与「总线类型」两列（值都来自
   `hardware_type`），一列走 `toUpperCase`、一列走私有 map ⇒ 同一行两个不同写法。收敛为一列。
4. 中英混排与兜底不一：统一由 `getHardwareLabel`（英文标签）/`getHardwareTitle`（中文）
   提供，未知类型返回归一后大写原文而非空串。

**凭什么信它**：`hardwareTag.spec.ts` 11 条用例 + 源码级反向断言

而非 `UART UART0`，`("uart","1")` 返回 `UART 1`。

# 第二轮审查（固件/传输层）与整改（2026-10-03 14:37–15:05）

固件审查者回报了一条**推翻我安全前提**的 P0。这是本次全部工作里最重要的一次纠正。

## P0：CR 结尾校验不足以防「错配/截断帧」（我引入）

我原先的论证是：「V2 短读交给服务端 verifier 做权威校验，故安全」。
审查者指出并实测证明：**该前提只部分成立**。我的 CR 结尾校验只挡住「行中截断」，
而**CR 结尾但形状错误**的帧会通过校验、被解析成**别的传感器**，并记为 `final_succeeded`。

我独立复现（全部为实测，非推断）：

| 请求的动作 | 喂入的帧 | 修复前返回 | 危害 |
|---|---|---|---|
| read_battery | HGRID 形状 | `grid_voltage`/`grid_frequency` | 电池读数变成市电读数 |
| read_output | 市电形状 | `grid_voltage`/`grid_frequency` | 输出读数变成市电读数 |
| read_status | 截短 HSTS `(00 P0000` | 12 个 `alarm_*` **全为 0** | **fail-open**：设备可能在报警，界面显示「无告警」 |
| read_temperature | HBAT 形状 | `battery_*` 字段 | 温度读数变成电池读数 |
| read_pv2 | 截断功率 `(220.5 08.0 0` | `pv2_power=0` | 960W 被读成 0W，像是停止发电 |

根因有两层，都修了：

1. **verifier 未绑定动作形状**（`inverter_techfine.go`）：`ParseData` 是按字段数/格式
   「嗅探」分支的，不绑定所请求的动作。新增两道判据：
   - `techfineActionSensorFamily`：返回字段必须**全部**属于该动作期望的族（拦错配）；
   - `techfineActionMinSensors`：字段数不得少于该动作的完整形状（拦截短）。
   未登记的动作**不静默放行**（新增动作必须同时声明形状，否则防线会静默缩水）。
2. **解析器自身的 fail-open**：`parseHSTS` 在状态串短于 13 字符时把缺失告警位默认成 0；
   `parsePV` 用 `parseFloat` 的「解析失败返回 0」兜底。两者都改为显式报错。

**验证**：新增 3 条用例（5 个坏帧逐个钉死 + 合法帧反向对照 + HSTS fail-open 的后果），
**变异自证 3 个方向全部被抓住**（去掉形状绑定 / 恢复 HSTS fail-open / 恢复 PV 0 兜底）。
同时确认 JBD(0/8)、PRS3001(0/9) 经截断探针本来就安全。

**教训（比缺陷本身更重要）**：「下游有权威校验」这类论证，必须**去读那个校验到底校验了什么**。
我第一次只确认了「有 verifier」，就把它当成了完整的安全前提 —— 而它当时既不校验帧完整性、
也不校验形状归属。这是同一个错误在本次会话里的第二次出现（第一次是 read_size 语义）。

## P1：1s 心跳放大 manifest 推送频率（我引入）

审查者指出：`OnStatusReport` 的 `hash_mismatch` 分支**每次心跳都推送全量 manifest**，
没有冷却窗口；心跳 5s→1s 后，持续失配的节点推送频率 ×5。

我复核时发现一个更根本的事实：`SyncActionDefer` 的常量注释写着
「Defer — within dedup window」，但**全仓没有任何代码产生它** ——
**去重窗口从未实现**。此前无人在意，因为心跳是 5s。

修法：把窗口真正实现出来（而不是新造第二套机制），只作用于**周期心跳**路径，
窗口取 **5s = 收紧前的心跳周期** ⇒ 持续失配节点的推送频率**不高于改动之前**。
显式配置变更（`OnConfigChange` / `OnHello` / `nvs_empty`）**不受**窗口限制 ——
否则用户改完配置要等冷却期，那比推送频繁严重得多。

**验证**：2 条用例（窗口内降级为 Defer / 窗口外恢复推送 / 按设备维度隔离 /
显式变更绕过窗口）；**变异自证**：去掉窗口 ⇒ 红；窗口设为无限 ⇒ 红。
