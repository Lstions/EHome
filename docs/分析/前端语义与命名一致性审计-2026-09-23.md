### 1.1 T1-T11 补充说明

- T1 的“采集器”残留不在可见文案，但 `NodeList.vue` 的 `.collector-*` 类名与 `NodeOverview.vue` 的 `fetchCollectorDetail` 仍是同物异名；若未来做 CSS/日志检索会持续噪声。

- T7 的“告警/自动化”后端资源分属 `alert` 与 `automation`，UI 用同一张“规则”卡片，建议卡片标题加领域定语，避免同屏歧义。

- T11 的 `state` 在通知投递域是有意设计（每次尝试一行），但页面筛选标签只写“状态”；建议 UI 写“尝试状态”，与实体状态区分。

- 14 项全部平铺在同一个 `el-menu` 中，没有 `el-sub-menu`/分组标题：`MainLayout.vue:16-37`；移动端同样平铺：`:67-90`。其中既有资源管理（节点/边缘设备/逻辑设备/通道/配置模板/数据源），也有运行观测（数据面板/系统监控/仪表盘），还有策略与通道（告警/自动化/通知通道/投递审计），以及运维（固件）。用户无法从位置推断“我在管资源还是在看运行”。
- 面包屑与菜单标题也不同源：`breadcrumbs` 把 `/node` 写作“节点管理”、`/edge-device` 写作“边缘设备管理”：`MainLayout.vue:708-713`；而菜单与路由 meta 是“节点”“边缘设备”（`:399-400`）。这使列表页（无 PageHeader）只剩面包屑的“节点管理/边缘设备管理”一个标题，与菜单导航词不一致。
- 详情页的 `meta.title` 与页面标题不同源：`router/index.ts:51-75` 有“节点详情/节点总览/边缘设备详情”，但 `NodeDetail.vue:572`、`NodeOverview.vue:996`、`GenericDeviceDetail.vue:84` 都用实体名覆盖；详情页不可只用 `meta.title` 判断标题。
- 空态文案暴露层级：节点列表空态按钮是“添加节点”（`NodeList.vue:272`），边缘设备空态却引导“进入节点详情页，点击‘创建边缘设备’按钮开始添加”（`EdgeDeviceList.vue:268`）；同一动作在不同页叫“添加/创建”，且边缘设备空态必须借道节点详情，层级关系靠文字而非菜单结构表达。
- `BmsDemoPage.vue:423` 也硬编码了一组菜单（含“配置模板”），与 `MainLayout.vue:397-412` 形成第二份菜单清单；这是 DEV 预览页，但也说明菜单项没有单一数据源。
- 结论建议：菜单按三组组织——① 运行（仪表盘/数据面板/系统监控）；② 资源（节点/边缘设备/逻辑设备/通道/数据源/配置模板/固件）；③ 策略与通知（告警规则/自动化策略/通知通道/投递审计）；列表页补齐 PageHeader（title 与菜单/路由 meta 三处同源）。分组仅是 UI 提案，不涉及后端。

## 6. 结论与建议优先级

### 6.1 Top 5 先做

1. **冻结 `active` 与 `online` 的契约**（F1）：边缘设备列表当前同时接受两值，筛选只发 `active`；先让契约回答“后端到底存哪个值”，再决定前端是否保留双值兼容。
2. **解决 `hardware_id` 同名异物**（F6 / T10）：Channel.hardware_id 与 EdgeDevice.hardware_id 语义相反，已有生产事故记录；建议为 Channel 侧引入 `bus_name`（或至少契约注释冻结），其他代码禁止跨资源回退。
3. **统一“设备配置”术语**（T4 / T8）：菜单/路由/页头当前“配置模板”，权威词是“设备配置”；保留 `device-configs` 路径与 `device_type` 字段，UI 词表与代码注释收敛。
4. **补齐 `/node`、`/edge-device` 页面标题并统一“通知通道”页头**（第 2 节）：列表页缺 PageHeader 是当前唯一一类“菜单可见但页面无标题”的不一致；`通知通道` vs `外发通知通道` 二选一，建议菜单和页头都用“外发通知通道”或都用“通知通道”。
5. **动作词冻结**（第 3 节）：主按钮统一“新建/编辑/删除/保存”；“添加/新增”只保留在 `新增外设配置` 这一场景；“触发/测试/同步配置”保持领域词。

### 6.2 不建议现在做的

- 不批量替换 `collector-*` CSS 类名和 `collectorId` prop：它们是前端内部命名，改名的收益低于回归风险；可在新增代码中停止使用，存量等页面重构时顺带。
- 不把 `device_type` 字段改名为 `device_model`：后端列/JSON 已冻结，UI 文案改“设备型号”即可，字段契约变更需独立评审。
- 不把 `state` 改为 `status`：投递审计是一次尝试一行的状态机，和实体生命周期不应混用；需要做的是在 UI 标签写“尝试状态”并在类型注释中说明。
- 不因 `UNKNOWN` 英文常量而改协议：`UNKNOWN` 在 `api/deviceOperation.ts:3` 是后端协议结果枚举，用户可见统一显示 `—`（`utils/format.ts:11`）即可。

### 6.3 不确定性

- 本次计数用 `rg` 扫 `.vue` 并排除 `__tests__`，可能包含注释/变量名；可见标签列已单独给出，但 `quick-actions`、`confirmText` 等动态文案仍可能被低估。
- 术语表没有为“通知通道/投递审计”“数据源/候选来源”“告警规则/自动化策略”提供专条中文名，因此本文对这些组按领域设计文档判定，属于提案而非既有权威裁决。
- 第 5 节只记录“字段不一致事实”，未验证后端所有 handler 的实际响应形状（本次要求不跑测试/网络）；实际修复前需用真实 API 响应或 handler 代码抽样复核。

### 9.3 本报告可直接引用的核心结论

- 术语冲突合计 **12** 项（T1-T6、T8、S2、S3、S5、M2、M3），其中 T4、T9、T10、F1、F6 需要契约或产品裁决。
