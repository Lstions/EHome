# 固件型号与节点匹配：误刷风险审计

> **状态**: 提案
> **版本**: v1.0
> **日期**: 2026-11-18
> **关联**: [版本与更新机制-自更新设计可复用性分析](版本与更新机制-自更新设计可复用性分析-2026-11-18.md) | [固件OTA](../设计/固件OTA.md) | [ESP32刷机指南](../操作/ESP32刷机指南.md) | [部署3.0到生产服务器](../操作/部署3.0到生产服务器-2026-10-18.md)

> 触发：用户指出「节点固件型号不规范、固件上传与管理和固件-节点关联性存在问题、可能误刷误升级」。
> 本文只做审计与方案，不含代码改动；所有结论可按下表文件与行号复核，测试命令见 §10。

## 1. 结论摘要

### 1.1 一句话

本系统里「型号」不是一个**能力声明**，而是一段**描述性文本**：设备上报的是 `CONFIG_IDF_TARGET`（`esp32c6` / `esp32s3` / 运行时加 `p`），
服务端只是把它抄进 `nodes.model` 并在每次 Hello 时覆盖，**全仓没有任何一行代码用它做过判断**；
固件与节点之间也**不存在关联模型** —— 建 OTA 任务时只接收 `node_id` 与 `firmware_id` 两个裸 ID，中间没有任何兼容性校验。

因此用户担心的「误刷」不是偶发操作失误，而是**结构性可达**：

| 错配 | 设备端会拦下吗 | 后果 |
|---|---|---|
| C6 镜像 → S3 节点（或反向） | 会（`esp_ota_end` 校验 chip_id） | 干净失败，不切分区，可重试 |
| s3 镜像与 s3p 节点互刷 | **不会**（同 chip_id、同 flash，镜像头无法区分） | **刷入成功**；构建假设与硬件不符，可能崩溃且无法自愈 |
| n8 与 n16 镜像互刷 | 不会（设备不校验 flash 字段） | 当前分区仅容量不同，多为记录失真；一旦引入容量相关数据分区即成真故障 |
| 同版本重刷 | 不会（设备只按 `ota_id` 去重，不比版本） | 重复下载与刷写；成功判定可被版本字符串骗过（§4.4） |

### 1.2 三个根因

| # | 根因 | 具体表现 |
|---|---|---|
| R1 | **型号语义错位** | 型号 = IDF 编译目标 + 运行时 PSRAM 探测，不是构建产物身份。6 个构建档位只产生 3 个型号值，Flash 容量（n8/n16）在型号里完全不可见 |
| R2 | **关联层缺失** | `Firmware.target_model` 只写不读；`CreateTask` 连节点都不查；`OtaCmd` 载荷无任何硬件身份字段（且不能加，见 §4.3） |
| R3 | **版本号不可区分** | 四个真实产物版本号都是 `2.8.0`；`Version` 无唯一约束；成功判定只比版本字符串 |

### 1.3 风险分级

- **P0（可导致远程设备失联且无法自愈）**：s3 与 s3p 互刷。回滚链路未武装（见主文档 §3.5-C），`boot_guard` 只能进安全模式、不能换回旧镜像。
- **P1（可导致升级失败或账实不符）**：跨芯片错配（干净失败但被误读为网络问题）；同版本重刷被报成功；删除固件打断在途升级。
- **P2（可维护性）**：型号文风混乱、界面标签错误、列表无过滤。

## 2. 型号当前到底是什么

### 2.1 设备侧：编译目标 + 运行时探测

```c
// esp32-collector/main/app_state.c:45
static char s_model_name[16] = CONFIG_IDF_TARGET;
```

`generate_model_name()`（`app_state.c:110-126`）：若构建期 `CONFIG_COLLECTOR_PSRAM=y` 且运行时 `heap_caps_get_total_size(MALLOC_CAP_SPIRAM) > 0`，
则输出 `<target>p`（如 `esp32s3p`），否则输出 `<target>`（如 `esp32s3`）。

两个后果：

1. **同一个二进制在不同板子上会报不同型号**（PSRAM 探测结果不同）；
2. **型号里没有 Flash 容量**，而这恰恰是 6 个构建档位的主要差异（§2.2）。

### 2.2 六个构建档位只产生三个型号值

| 档位（`build_firmware.sh:100-105`） | IDF target | Flash | PSRAM 构建开关 | 设备上报型号 |
|---|---|---|---|---|
| `c6-n8` | esp32c6 | 8MB | 关 | `esp32c6` |
| `c6-n16` | esp32c6 | 16MB | 关 | `esp32c6` |
| `s3-n8` | esp32s3 | 8MB | 关 | `esp32s3` |
| `s3-n16` | esp32s3 | 16MB | 关 | `esp32s3` |
| `s3p-n8` | esp32s3 | 8MB | 开 | `esp32s3p`（有 PSRAM 时） |
| `s3p-n16` | esp32s3 | 16MB | 开 | `esp32s3p`（有 PSRAM 时） |

即 `c6-n8` 与 `c6-n16` 的设备在服务端完全无法区分；`s3` 与 `s3p` 只能靠运行时探测区分，而探测可能因硬件或时序失败而退化。

### 2.3 服务端：每次 Hello 覆盖，纯展示

- `backend/internal/nodemgr/handler_hello.go:342`（首次注册）与 `:381`（重复注册）都是 `node.Model = hello.Model`，无校验、无历史、无告警。
- 全仓 `Node.Model` 的读写点只有这两处；没有任何查询、过滤或决策依赖它。
- 列宽 `size:20`（`backend/internal/models/models.go:23-24`），而固件侧 `TargetModel` 是 `size:64`（`:428`），两侧对型号宽度预期不一致。

### 2.4 前端：映射表只覆盖 S3/S2/C3，`collectorModel` 从未使用

- `frontend-shared/src/components/forms/OTAForm.vue:220-224` 的 `MODEL_NAMES` 只映射 `ESP32-S3` / `ESP32-S2` / `ESP32-C3`；设备实际上报的 `esp32c6` / `esp32s3` / `esp32s3p` 全部落在 fallback，原样显示。
- 同文件 `:160-170` 定义了 `collectorModel` 属性（默认值写死 `ESP32-S3`），`NodeOverview.vue:500` 也确实传了 `:collector-model="node?.model"`，但该属性在组件内**没有任何读取点**，属于死参数。
- 结论：界面既不知道节点型号，也不拿它做判断；默认值 `ESP32-S3` 还会给人「已经识别了」的错觉。

### 2.5 型号文风本身也没有规范

代码与测试里同时存在 `ESP32S3`（`nodemgr/datapipe_test.go:196`）、`ESP32-C6`、`ESP32`、`RPi4`，而运行时值是小写无连字符的 `esp32c6`。
任何按字符串相等做的匹配今天都会失败，这也是「先规范化、再做匹配」必须先行的原因（否则加了闸门只会误伤正确固件）。

## 3. 固件上传与管理：三处信人不信二进制

### 3.1 上传只验扩展名与 Content-Type

`backend/internal/api/handler_ota.go:130-164` 的上传校验只有三条：

1. `version` 表单字段非空；
2. 文件名以 `.bin` 结尾；
3. `Content-Type` 在白名单内（含空）。

**完全没有解析镜像内容**：把任意 4MB 以内的二进制改名 `.bin` 都能入库。版本号、型号全部来自表单手填。

### 3.2 版本号无唯一约束，四个真实产物同名

`Firmware.Version`（`models.go:419-433`）是普通字符串，**没有唯一索引**；`AutoMigrate` 也不补（`backend/internal/database/gorm.go:100-101` 只做建表）。

用本机真实构建产物实测（解析方法见 §6）：

| 产物 | 大小 | chip_id | flash 字段 | 镜像内 version | 镜像内 IDF |
|---|---|---|---|---|---|
| `build/c6-n8/ehome_collector.bin` | 1.36 MiB | 0x000D (C6) | 3 = 8MB | **2.8.0** | v6.0.2 |
| `build/c6-n16/ehome_collector.bin` | 1.31 MiB | 0x000D (C6) | 4 = 16MB | **2.8.0** | v6.1 |
| `build/s3-n16/ehome_collector.bin` | 1.19 MiB | 0x0009 (S3) | 4 = 16MB | **2.8.0** | v6.0.2 |
| `build/s3p-n16/ehome_collector.bin` | 1.15 MiB | 0x0009 (S3) | 4 = 16MB | **2.8.0** | v6.1 |

四个不同二进制共享同一个版本号，连构建用的 IDF 版本都不一致（v6.0.2 / v6.1）。数据库允许它们并存，前端下拉框只会显示成四条几乎一样的「2.8.0 - xxx.bin」。

### 3.3 元数据三件套全部零消费

| 字段 | 写入点 | 读取点（非测试） |
|---|---|---|
| `target_model` | `handler_ota.go:206`（上传）、`:246-248`（编辑） | **无** |
| `min_from_version` | `handler_ota.go:229-232`、`:249-251` | **无** |
| `stable` | `handler_ota.go:231`、`:252-254` | **无** |

三个字段目前只是能被填进数据库的标签，不参与任何筛选、匹配或拦截。

### 3.4 列表接口没有过滤，前端传的参数被丢弃

- 后端：`handler_ota.go:123-127` 就是 `db.Find(&firmwares)`，无 where、无分页。
- 前端：`stores/firmware.ts` 声明了 `FirmwareListParams { model?, status? }`，但后端从不读取；`total` 也只是 `list.length`。
- 管理页 `FirmwareManage.vue` 没有任何筛选控件（只有表格与上传/编辑弹窗），连「按型号看一眼」都做不到。

### 3.5 删除固件不检查在途任务

`handler_ota.go:262-292` 先删磁盘二进制、再删 DB 行，**不查询是否有活跃 OTA 任务引用它**，`OTATask.FirmwareID` 也无外键约束。
后果：删掉正在被下载的固件，设备侧只会看到 404 或 401，而任务记录停在 `downloading` 直到 30 分钟超时。
（主文档 §3.5 已单列，此处只做交叉引用。）

### 3.6 界面把 SHA256 标成 MD5

`OTAForm.vue:52` 的详情面板写的是 `label="MD5"`，但 `Firmware.Checksum` 是 64 位十六进制 SHA256（`handler_ota.go:177`）。
这会让排障者在「校验不一致」时去比对错误的算法。

## 4. 关联层：目前根本不存在

### 4.1 建任务只接收两个裸 ID

```json
POST /api/v1/ota/tasks
{ "node_id": "...", "firmware_id": 42 }
```

`handler_ota.go:58-71` 只做 `binding:"required"`，没有任何语义校验；随后直接 `CreateTask` 并 `SendOtaCommand`。

### 4.2 `CreateTask` 连节点都不查

`backend/internal/ota/ota.go:374-409` 的全过程：按 `firmwareID` 查固件 → 把同节点在途任务置 failed（supersede）→ 建任务。
**没有 `nodes` 查询**，因此即使节点 `model` 与固件 `target_model` 完全无关，也照建不误。
（`SendOtaCommand` 里那次 `nodes` 查询只是为了拿 `node_id` 拼下行地址，不做校验。）

### 4.3 `OtaCmd` 没有硬件身份字段，而且不能加

`ota.go:526-535` 的载荷只有 6 个字段：`ota_id` / `url` / `checksum` / `size` / `version` / `sequence`。设备端自然无从自检「这个镜像是不是给我的」。

更关键的是协议不允许顺手加字段。`esp32-collector/components/msg_handler/handler_data.c:77` 对未知字段号是 fail-closed（`OTA_CMD_F_SEQUENCE = 6`，见 `msg_handler_internal.h:166`）：

```c
if (field.field_num < OTA_CMD_F_OTA_ID || field.field_num > OTA_CMD_F_SEQUENCE ||
    (seen & (1U << field.field_num))) goto reject;
```

即 `field_num > 6` 会被整条拒绝。这与主文档中 `HelloAck` 的结论同构：**已有消息加字段等于破坏旧固件**，唯一安全的方向是「新增消息号」或「服务端先拦」。

### 4.4 成功判定只比版本字符串

`ota.go:684-727` 的 `HandleHelloOTACompletion` 判据是：

```go
if task.ToVersion != "" && task.ToVersion == firmwareVersion { /* 标记 success */ }
```

问题有二：

1. **无法区分「刚刚真的升级了」与「本来就是这个版本」**。同版本重刷时，只要任务期间发生一次 Hello（例如设备重启），任务就会被判成功，即使下载或写入其实失败了；
2. **判据粒度是版本号**，而四个档位版本号相同（§3.2），理论上「刷了同版本的另一档位」也会被判成功。

### 4.5 操作现场：一个版本号加一个文件名

`OTAForm.vue:12-30` 的下拉框：

- 数据源是 `firmwareStore.fetchList({ status: "active" })`（`:240-244`），后端忽略该参数，**返回全量**；
- 选项标题是 `version - filename`，右侧附带 `getModelName(fw.target_model)`；
- `target_model` 为空时 `getModelName` 直接返回空串，也就是「通用固件」在界面上**什么都不显示**，而不是显示「通用」；
- `target_model` 非空时原样显示（因为 `MODEL_NAMES` 覆盖不到真实值）。

于是操作员看到的是「2.8.0 - ehome_collector.bin」乘以 N，唯一区分线索是文件名；节点自身的型号既不显示也不参与。

## 5. 误刷后果矩阵

| 错配类型 | 镜像头能否判别 | 服务端是否拦 | 设备端实际结果 | 能否自愈 |
|---|---|---|---|---|
| C6 镜像 → S3 节点 | 能（chip_id 0x0D 对 0x09） | 否 | `esp_ota_end` 经 `bootloader_common_check_chip_validity` 返回 `ESP_ERR_IMAGE_INVALID`，不切分区 | 能（仍跑旧分区） |
| S3 镜像 → C6 节点 | 能 | 否 | 同上 | 能 |
| **s3 镜像 → s3p 板** | **不能**（同 chip 0x0009、同 flash 字段） | 否 | 写入与校验通过，切换分区并重启；新镜像按无 PSRAM 构建，PSRAM 未被使用 | **不能**（回滚关闭） |
| **s3p 镜像 → s3 板** | **不能** | 否 | 写入与校验通过，切换分区并重启；新镜像按有 PSRAM 构建，`heap_caps_get_total_size(SPIRAM)` 为 0，配置事务或 OTA 任务等大分配可能失败 | **不能**（`boot_guard` 只进安全模式，不换镜像） |
| n16 镜像 → n8 板 | 能（spi_size 4 对 3） | 否 | 镜像不超过 3.5MB 时写入成功（当前产物约 1.2 到 1.4MB）；超过时写到一半失败 | 视情况 |
| n8 镜像 → n16 板 | 能（3 对 4） | 否 | 写入成功；仅容量浪费 | 不适用 |
| 同版本重刷 | 无需判别 | 否 | 设备无版本比较（`ota_classify_cmd` 只按 `ota_id` 去重），照常下载刷写；结果可能被 Hello 判成功 | 不适用 |

**为什么 s3 与 s3p 互刷是唯一真正危险的组合**：它是唯一「镜像头看不出、设备端校验会通过、失败后又没有回滚」的三重叠加。
其余组合要么在设备端被明确拒绝（可重试），要么在当前分区布局下无可观测影响。

## 6. 二进制其实自带身份（实测可解析）

### 6.1 布局（ESP-IDF 6.1）

| 偏移 | 内容 | 用途 |
|---|---|---|
| 0x00 | `magic = 0xE9` | 拒绝非固件文件 |
| 0x01 | segment_count | 健全性检查 |
| 0x03 | 高 4 位 = `spi_size`（0 到 3 分别为 1/2/4/8MB，4 = 16MB） | **Flash 容量假设** |
| 0x0C | `chip_id`（u16：C6 = 0x000D，S3 = 0x0009） | **芯片型号** |
| 0x18 | 首个 segment header（8 字节） | 不适用 |
| 0x20 | `esp_app_desc_t`（256 字节，magic `0xABCD5432`） | 应用身份 |
| 0x30 | `version[32]` | **镜像自带版本** |
| 0x50 | `project_name[32]`（`ehome_collector`） | 拒绝非本项目镜像 |
| 0x70 / 0x80 | 编译时间 / 日期 | 溯源 |
| 0x90 | `idf_ver[32]` | 溯源 |
| 0xB0 | `app_elf_sha256[32]` | **镜像指纹**（同版本不同构建的唯一区分） |

结构定义见 `components/bootloader_support/include/esp_app_format.h`（镜像头 24 字节、packed）与 `components/esp_app_format/include/esp_app_desc.h`（描述符 256 字节）。

### 6.2 实测结果

见 §3.2 表：四份产物的 `chip_id`、`spi_size`、`version`、`idf_ver` 全部可离线解析，无需设备参与。
这直接说明：**上传时的「版本」与「型号」原本不需要人手填**。

### 6.3 能拿到什么、拿不到什么

- 能：芯片、Flash 容量假设、版本号、项目名、编译时间、IDF 版本、ELF SHA256；
- 不能：**PSRAM 是否启用**（`CONFIG_COLLECTOR_PSRAM` 不写入镜像头），也无法知道目标板是否真有 PSRAM。

即 PSRAM 维度必须由构建系统额外提供（sidecar 元数据），或后续由设备上报（§7.3）。

## 7. 改造方案

### 7.1 P0：让上传以二进制为准

在 `POST /firmwares/upload` 落盘后、入库前解析前 0x100 字节：

1. `magic != 0xE9` → 400，拒绝非 ESP 应用镜像；
2. `project_name != "ehome_collector"` → 400，拒绝把别的项目的 bin 传进来；
3. `chip_id` 不在白名单（0x000D / 0x0009）→ 400；
4. `version` **以镜像内为准**，表单 `version` 只做一致性校验（不一致即 400），不再作为真源；
5. 落库新增 `chip` / `flash_mb` / `elf_sha256` / `built_at` / `idf_ver`，并派生 `model_key`（如 `esp32c6-n8`）；
6. 用 `(model_key, version)` 建唯一索引，重复上传直接拒绝。

收益：即使前端完全不动，也能挡住「C6 镜像当 S3 用」和「同版本重复入库」，并且让固件列表第一次能按芯片与容量显示。

### 7.2 P0：把「通用」显性化、把 MD5 改对

- `getModelName("")` 返回「通用」而不是空串；
- 详情面板 `MD5` 改为 `SHA256`；
- 列表与下拉框增加 `chip` / `flash` / `profile` 列（数据来自 §7.1）。

### 7.3 P1：节点硬件身份（需要固件改动）

目标：把「型号」升级成可判定的 `(chip, flash_mb, psram_required)`。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A（推荐） | 构建期注入 `EHOME_HW_PROFILE`，型号字符串改为 `esp32c6-n8` / `esp32s3p-n16` | 复用现有 Hello 字段 3，无协议变更；12 字符小于现有 16 字节缓冲 | 需改 `build_firmware.sh` 与 `app_state.c`；旧固件仍报短名，需兼容解析 |
| B | 新增一条上行消息上报 profile | 语义干净 | 需新增消息号并双端发版；旧后端会遇到未知消息 |
| C | 依赖运维填写 `nodes.model` | 零固件改动 | 不可信，且设备每次 Hello 会覆盖 |

选 A 时要注意 `app_state.c:45` 的 `char s_model_name[16]`：`esp32s3p-n16` 为 12 字符，够用但已接近上限，建议同步扩到 32 并加编译期断言。

兼容策略：服务端解析 `([a-z0-9]+)(?:-n(8|16))?(p)?`；解析失败的一律记为 `unknown`，并**禁止一键升级**（只允许人工确认并留审计）。

### 7.4 P1：三道闸门

| 闸门 | 位置 | 规则 | 失败返回 |
|---|---|---|---|
| A 上传 | `POST /firmwares/upload` | 二进制自证（§7.1） | 400 加具体原因 |
| B 建任务 | `POST /ota/tasks` 或 `CreateTask` | `chip` 必须相等；`flash` 相等，或节点未知时降级为「需人工确认」；`psram_required=true` 的镜像只能给 `psram_present=true` 的节点；`compareVersion(target, current) > 0`（同版本或降级需 `force=true` 并写审计） | **409** 加机器码（`MODEL_MISMATCH` / `FLASH_UNKNOWN` / `PSRAM_REQUIRED` / `NOT_AN_UPGRADE`） |
| C 下发 | 服务端（可选） | 若将来新增 `MSG_OTA_CMD_V2`，才可在帧内携带 `chip` / `flash` / `psram` 让设备自检；现有的 `0x0A` 不可加字段 | 不适用 |

注意 `compareVersion`（`ota.go:113`）已经写好但全仓零调用，闸门 B 是它的第一个正当使用者。

### 7.5 P1：成功判定加固

- `HandleHelloOTACompletion` 增加前置条件：任务必须已经有过 `downloading` 或 `installing` 进度（排除「从未开始却被 Hello 判成功」）；
- 同版本重刷默认拒绝（§7.4 B），从源头消除「本来就是这个版本」的歧义；
- 中期：设备在 Hello 中追加运行镜像的 `elf_sha256` 前 8 字节（需新消息号或 features 位协商），服务端与 `firmware.elf_sha256` 比对，做到「验明正身」而不是「版本对得上」。

### 7.6 P2：版本语义与投放

- 版本号与构建档位解耦：`version` 仍可 `2.8.0`，但唯一性由 `(model_key, version, elf_sha256)` 保证；
- 落地主文档 §4.3-C1 的 `channel`（stable / beta / internal）与 `min_from_version` 强制；
- 删除固件前检查活跃任务（§3.5），或改为「软删，任务清空后由清理任务物理删」。

## 8. 决策与分期

| 编号 | 问题 | 推荐 | 理由 |
|---|---|---|---|
| D7 | 型号标识格式 | `esp32c6-n8` / `esp32s3p-n16` | 复用现有字段，不破坏协议；可解析、可比较 |
| D8 | PSRAM 如何表达 | 构建期注入加运行时探测交叉校验（不一致记 `psram_mismatch` 并禁止自动升级） | 探测会退化，不能单独作准 |
| D9 | 节点硬件信息缺失时 | fail-closed：禁止一键升级，只允许人工确认加审计 | 误刷代价远高于多点一次手工确认 |
| D10 | 同版本重刷 | 默认 409，`force=true` 才允许并记录审计 | 消除 Hello 判成功的歧义 |

| 阶段 | 内容 | 判据 |
|---|---|---|
| **P0**（1 到 2 人日） | 上传解析（§7.1）加文案修正（§7.2） | 上传 C6 镜像记录 `chip=esp32c6`；上传非 ESP 镜像被拒；重复 `(model_key, version)` 被拒 |
| **P1a**（2 到 3 人日） | 建任务闸门 B（§7.4）加前端按节点型号置灰与提示 | 给 `esp32s3` 节点选 `esp32c6` 固件得到 409；选 `esp32s3p` 固件得到 409 |

| **P2**（3 到 5 人日，需实机） | 固件上报 profile（§7.3）加设备验明正身 | 真实 s3p 设备 Hello 报 `esp32s3p-n16`；错配任务在服务端即被拒 |

## 9. 验收判据（可证伪）

1. 上传 `build/c6-n8/ehome_collector.bin`，记录 `chip=esp32c6, flash_mb=8, version=2.8.0, elf_sha256` 非空；
2. 上传同一个文件两次，第二次被拒；
3. 上传任意非 ESP 二进制（改名 `.bin`）被拒；
4. 对 `model=esp32s3` 的节点建 `chip=esp32c6` 的任务，得到 409 `MODEL_MISMATCH`；
5. 对 `model=esp32s3`（无 PSRAM）的节点建 `psram_required=true` 的任务，得到 409 `PSRAM_REQUIRED`；
6. 对当前版本 `2.8.0` 的节点建同版本任务，得到 409 `NOT_AN_UPGRADE`（`force=true` 时允许并写审计）；
7. 制造「任务 pending、设备不下载、Hello 版本恰好相等」场景，任务**不得**被判 success；
8. 删除被活跃任务引用的固件，得到 400，而不是删完再让设备 404。
