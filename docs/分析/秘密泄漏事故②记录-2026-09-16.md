## 2. 两条独立根因（都必须修，缺一不可）

### 根因 A：`.gitignore` 只写了一半

`.gitignore` 第 51-58 行有一段以「2026-09-16 真实事故」开头的注释，明确说明
证据目录不该入库 —— 但它**只忽略了 `deploy/ghcr/evidence/`**，
`deploy/blackbox/evidence/` **从未被忽略**。

⇒ 注释里写着「黑盒那批文件已在历史中，此处只防新增」，
  而黑盒的「新增」一直在被跟踪。**规则只写了一半，却以为写全了。**

整改：补上 `deploy/blackbox/evidence/`，并在注释里写明「两份证据目录必须成对出现」。

### 根因 B：判据漏掉的那一类，等于不存在

`deploy/blackbox/probes/_redact.sh` 的脱敏与扫描**只认一种形状**：
`<selector>.<secret>`（base64url 一次性凭据，事故① 的形态）。

而事故② 的泄漏形态是 **JSON 键值对**：
```json
"EHOME_JWT_SECRET": "ehome_jwt_secret_key_..."
```

规则① 对它**一个字符都扫不到**，于是 `bb_scan_credentials` 在事故现场返回 0 ——
**门禁全绿，秘密就在眼前**。这正是本仓反复记载的「假绿」家族。

整改：脱敏与扫描各增加两条规则（JSON 键值对 / KEY=value），
并**共用同一份敏感键名**与**同一个文件集**（见 §4 第三条）。

### 3.3 脱敏器的变异自证（这是最关键的一条）

在**同一份输入**上对比新旧判据：

```
scan BEFORE (新判据): 3
```

并且做了一次**注入回归**：把真实值塞回一个 in-scope 文件 ⇒ 扫描重新报警（1）；
脱敏后回到 0。⇒ 判据不是「永远绿」，它真的能发现该发现的东西。

## 4. 三次踩同一个坑（这是本文最该记住的部分）

| # | 形态 | 表现 |
|---|---|---|
| ① | 脱敏只做在 `05-first-boot` 一处 | 另外两个 dump 日志的探针裸奔 |
| ② | 扫描只认 `<selector>.<secret>` 一种形状 | 键值对型秘密全绿通过 |
| ③ | **扫描的目录范围比脱敏宽** | 扫描扫到 `.sh` 里的 `secret_len=$SEC_LEN`（长度变量），**永远报 4、永远不可能变绿** |

③ 是本次写整改时**自己引入又自己抓到**的：一个永远红的门禁，
最终一定会被收窄到失效 —— 本仓已记载该失败模式。

⇒ 纪律：**判据的作用域必须与实现的作用域逐字相同**（现由 `bb_text_files` 统一提供），
  并且判据必须能被「注入已知坏样本 ⇒ 变红」自证。

## 5. 残留风险与未做的事（如实）

1. **已推送的历史无法撤回**：`abe3a7b0` 已包含该 secret，GitHub 上仍可检出。
   ⇒ **必须轮换密钥**（改 `.env` 的 `EHOME_JWT_SECRET` / 数据库口令），这不在代码仓库内，**需要人来做**。
   仅靠后续提交抹掉文件**不等于**消除泄漏。
2. 本次只处理了 `deploy/blackbox/evidence/` 与 `.gitignore`；
   其它 `*-evidence` 目录若将来新增，**没有自动守卫**（现在靠注释提醒）。
3. `_redact.sh` 的规则仍是**黑名单**：换一种键名写法（如 `jwt` 不带 `secret` 字样）会漏。
   没有做成「白名单 + 其余全红」，因为那会破坏证据的可读性。
4. 未做：CI 侧的秘密扫描（如 gitleaks）；未做 pre-commit hook。
   ⇒ 当前守卫仍依赖「有人记得跑 `make blackbox`」，**不是自动的**。

## 7. 密钥可利用性评估（主控实测，2026-09-16）

> 这一节存在的理由：说「必须轮换密钥」很容易，但没说清**为什么现在就必须**。
> 以下是实测，不是推测。

| 判据 | 实测 | 命令 |
|---|---|---|
| 泄漏值是否仍是**当前生效**值 | **是**。`.env` 里 `EHOME_JWT_SECRET` 命中 1 次，即本机服务正在用的就是泄漏出去的那个 | `grep -c EHOME_JWT_SECRET .env` |
| 数据库口令是否仍有效 | **是**。用 `ehome<redacted>` 能成功连上 PostgreSQL | `docker exec ehome-postgres psql -U ehome -d postgres -c 'SELECT 1'` |
| 泄漏文件是否仍在远端可检出 | **是**。本地历史 `abe3a7b0` 仍含该文件，而该提交已推送 | `git cat-file -e abe3a7b0:deploy/blackbox/evidence/D-20260916-105359/00-compose-config-layered.json` |

⇒ 结论：**这不是「已过期的一次性凭据」**（事故① 是），而是**长期有效的生产配置密钥**，
且此刻仍有效。任何能读到 GitHub 仓库的人都能拿到它。
⇒ **轮换优先级 = 立即**，不是「下次部署时顺手做」。

### 7.1 轮换清单（需要人执行，不在本仓库内）

1. `EHOME_JWT_SECRET` —— 换新值后**所有已签发的 JWT 会失效**（用户需重新登录）。这是可接受的代价。
2. PostgreSQL 口令（`ehome<redacted>`）—— 注意 `docker-compose.yml` / `.env` / CI 里多处引用，需一并改。
3. 轮换后本机验证：起服务 + 登录一次（确认新密钥可用）+ 确认旧 token 被拒。

### 7.2 为什么「删掉文件」不够（写给未来的人）

`git rm` 只能让**新提交**不含该文件。已经推送的 `abe3a7b0` 仍在远端对象库里，
`git log -p` / GitHub API / 任何 clone 都能取回。**历史是不可变的**（除非 force-push 重写 + 平台 GC）。
所以对**已泄漏**的密钥，唯一有效的补救是「让它失效」= 轮换。

## 8. 我在本次整改中自己犯的两个错（如实登记）

1. **事故记录文档本身含完整密钥**：我写的 `秘密泄漏事故②记录-2026-09-16.md` 第 63 行
   把完整真值写进了 `grep -rFl '<完整真值>' …` 这条示例命令里，并提交进了 `64d356b0`（未推送）。
   推送前自查时发现 ⇒ 已改为不可复原的前缀模式 `ehome_jwt_secret_key_2026_<redacted>`。
   **教训**：写「如何检出这个秘密」的文档时，**示例命令本身**就是泄漏载体。
   这与根因 B 同源 —— 我以为我在「记录泄漏」，其实我在「复制泄漏」。
2. **一次假绿**：跑后端契约测试时我写 `go test … | tail -10; echo "EXIT=$?"`，
   `$?` 取的是 `tail` 的退出码而非 `go` 的；当时 `go: command not found` 却打出 `EXIT=0`。
   改用 `${PIPESTATUS[0]}` 才是真结果。本仓反复记载「管道吞掉退出码」这类假绿，我自己犯了。
