## 二、根因（读码）

### 2.1 崩溃现象与解码

```
E esp-tls-mbedtls: write error :-0x6C00      ← MBEDTLS_ERR_SSL_INTERNAL_ERROR
E esp-tls-mbedtls: read error :-0x004C
assert failed: tlsf_free tlsf.c:630 (!block_is_free(block) && "block already marked as free")
Rebooting...
```

backtrace 解码（`fence_s3p-n16` ELF，SHA256 与设备一致）：

```
tlsf_free                              heap/tlsf/tlsf.c:630
multi_heap_free_impl                   heap/multi_heap.c:240
heap_caps_free                         heap/heap_caps_base.c:86
free                                   esp_libc/src/heap.c:34
esp_tls_internal_event_tracker_destroy esp-tls/esp_tls_error_capture.c:50   ← 二次 free
esp_tls_conn_destroy                   esp-tls/esp_tls.c:188
tls_esp_close                          components/tls_esp/tls_esp.c:253
tcp_release_handle                     components/link_tcp/link_tcp.c:170
```

⚠ **口径**：IDF Backtrace 是**栈扫描**，不是精确调用链，栈上残留地址也会打印。
因此不能据此断言帧间调用关系。可靠的只有一条：**崩溃点是 `esp_tls_internal_event_tracker_destroy()`
对同一个 `error_handle` 二次 `free()`**。"两个任务并发释放"的依据是下面的代码事实。

### 2.2 代码事实：handle 有两个并发使用者，且无锁

```c
// link_tcp.c:166（修复前）—— 唯一的释放点
static void tcp_release_handle(link_tcp_ctx_t *c)
{
    if (c == NULL || c->handle == NULL) return;   // ← 非原子检查
    if (c->cfg.io != NULL && c->cfg.io->close != NULL) {
        c->cfg.io->close(c->handle);              // → tls_esp_close → esp_tls_conn_destroy
    }
    c->handle = NULL;                             // ← 太迟：别人已经通过了上面的检查
}
```

| 任务 | 调用链 |
|---|---|
| `dev_link`（prio 5） | `session_poll`（device_link_wiring.c:1039）→ `rx_pump_step` → `link_rx_adapt_read` → `link_tcp_read`（:50/:82） |
| `report_tx` | `msg_handler_send_data_report` → `msg_handler_publish` → `transport->ops->send` → `sess_tx_send` → `session_send` → `tcp_send`（:235） |

两条路径都会在"连接不可用"时调 `tcp_release_handle()`，而 `c->handle` **没有任何锁**
（`link_tcp.c` / `session.c` / `link.c` / `rx_pump.c` / `link_rx_adapt.c` 里
`grep mutex|Semaphore|lock` = **0 命中**）。

⇒ 两者同时读到 `handle != NULL` ⇒ 都调 `io->close()` ⇒
`esp_tls_conn_destroy()` 对同一 `error_handle` 二次 `free()` ⇒ tlsf 断言。

### 2.3 为什么既有测试全绿却漏了它

`test_close_is_idempotent` 是**单线程**幂等（连一次、关一次、再关一次），
覆盖不到"两个线程同时关闭"。⇒ 这是典型的"测了行为，没测并发"盲区。

### 2.4 触发条件（A/B 实测，同机同固件）

| 场景 | 时长 | 崩溃 |
|---|---|---|
| 空闲（无配置活动） | 70s | **0** |
| 被动配置 + 无负载 | 80s | **0** |
| 主动轮询 + 从机**不应答** | 60s | **0** |
| 被动 5 fps | 58s | **0** |
| **主动轮询 + 从机应答 47.85 req/s** | 60s | **9** |
| **被动 100 fps** | 78s | **9~10** |

⇒ **与上行负载量正相关**，与被动/主动无关。每次重启前设备 uptime 实测 4293~9362 ms。

## 三、修法（已实施）

### 3.1 为什么不能"持锁跨越 I/O"

`io->read` 最坏阻塞 `EHOME_DEVICE_LINK_TIMEOUT_MS = 10000 ms`
（`esp_tls_cfg_t.timeout_ms` → `setsockopt(SO_RCVTIMEO)`，IDF `esp_tls.c:311`）。
若把锁持到 I/O 返回，`report_tx` 会被一次下行静默挡住最多 10s —— 吞吐直接归零。
⇒ **锁绝不能跨越 I/O**。

### 3.2 采用的机制：I/O 租约 + 延迟关闭

核心思路：**用"在飞计数"代替"持锁调用"**。

```c
// 取租约：连接有效时 ++inflight 并返回句柄，否则 NULL
static void *tcp_io_acquire(link_tcp_ctx_t *c)   // link_tcp.c:55
{
    xSemaphoreTake(c->lock, portMAX_DELAY);
    if (c->handle != NULL) { c->inflight++; h = c->handle; }
    xSemaphoreGive(c->lock);
    return h;
}

// 归还租约：最后一个归还者负责真正 close
static void tcp_io_release(link_tcp_ctx_t *c)     // link_tcp.c:75
{
    xSemaphoreTake(c->lock, portMAX_DELAY);
    if (c->inflight > 0) c->inflight--;
    if (c->retiring != NULL && c->inflight == 0) { h = c->retiring; c->retiring = NULL; }
    xSemaphoreGive(c->lock);
    if (h != NULL) c->cfg.io->close(h);           // ⚠ close 在锁外
}
```

`tcp_release_handle()` 只做"认领"（锁内摘句柄，锁外决定关不关）：

```c
static void tcp_release_handle(link_tcp_ctx_t *c) // link_tcp.c:287
{
    xSemaphoreTake(c->lock, portMAX_DELAY);
    c->handshaked = false;
    if (c->handle != NULL) {
        void *claimed = c->handle;
        c->handle = NULL;              // 新 I/O 立刻取不到它
        if (c->inflight == 0) to_close = claimed;   // 无人使用 ⇒ 当场关
        else                  c->retiring = claimed; // 有人用 ⇒ 交给最后一个归还者
    }
    xSemaphoreGive(c->lock);
    if (to_close != NULL) c->cfg.io->close(to_close);
}
```

### 3.3 关键不变量

```
① 一个句柄只会被 close 一次（消除 double-free）
② 只在 inflight == 0 时才 close（消除 use-after-free）
③ 同一时刻至多只有一个未关闭的 handle
```

③ 由 `tcp_open()` 强制：`retiring` 非空时**不允许建新连接**（返回 `LINK_NOT_READY` 稍后重试）。
没有它，`inflight` 这个**跨代**计数就无法分辨租约属于哪一代，归还时可能关错那一个。

### 3.4 其余改动

| 位置 | 改动 | 理由 |
|---|---|---|
| `link_tcp_new()` | 建锁；失败则 `free` 并返回 NULL | 不返回半成品（P1）；lock==NULL 会让链路静默不可用 |
| `link_tcp_free()` | 先 `tcp_release_handle` 再删锁 | 调用方没先 close 就 free（session.c 的失败路径）时补一次关闭，避免 §216 的 socket 泄漏 |
| `tcp_is_ready()` / `link_tcp_is_connected()` | 读 handle 走锁 | 避免读到释放瞬间的中间态（**只读观测**，不进决策） |
| `link_tcp_read()` / `tcp_send()` | 改用租约 | 消除原 TOCTOU（注释里原先写"不存在被外部改变的窗口"，**那是错的**，已更正） |

## 四、验证

### 4.1 host 测试：新增确定性并发用例

`host_tests/link_tcp_tests.c` 新增 `test_concurrent_release_closes_once()`：
用 `pthread_barrier` 让**读线程**与**写线程同时**处在 I/O 调用中，
随后各自返回"连接不可用"（读 → `LINK_TCP_IO_CLOSED`，写 → 硬错），
⇒ 两条释放路径**并发**到达 `tcp_release_handle`。
**确定性复现，不靠概率。**

断言：
```
① close 恰好一次（close_calls == 1）—— double-free 的直接判据
② 不得在 read 持有句柄期间 close —— use-after-free 的判据
③ 释放后新 I/O 返回 NOT_READY
④ 反向用例：无并发时释放必须立刻 close（否则"永不 close"也能让①通过）
```

⚠ **信号量桩必须是真的**：新增 `host_tests/stubs/freertos_sem_stub.c` 用 `pthread_mutex` 实现，
**不是** `return (SemaphoreHandle_t)1` 那种空桩 —— 空桩会让并发断言在单线程下照样全绿，
等于没测（本仓反复记的"假绿"）。

### 4.2 变异自证（改坏必须变红）


**这是"变异自证"直接改进测试设计的一个实例。**

## 六、遗留 —— 三条已全部闭环（2026-10-11 续）

### 1. 126.49 req/s 不是上限 —— ✅ 已实测（详见 [吞吐上限与被动路径-2026-10-11.md](../验证/吞吐上限与被动路径-2026-10-11.md)）

| 波特率 | 从机 | 吞吐 |
|---|---|---|
| 115200 | slave_fast2 | 126.49 req/s |
| 921600 | slave_fast2 | 156.23 req/s |
| 115200 | slave_imm（定长立即回） | **152.9 req/s** |
| 921600 | slave_imm | **190.1~195.6 req/s** |

⇒ 上限远高于 126.49。且**测量工具本身贡献 >20%**：
仅把从机的静默分帧换成定长立即回，同波特率就从 126.49 → 152.9 req/s。
剩余约 4.9ms 地板与波特率无关（读码推算 = 2ms 空闲阈值 + 1ms 调度 tick + fence），
**未逐项 A/B**，不冒充已定位。

### 2. 被动路径未走 DataBatch —— ✅ 已评估：优先级低，暂不做

实测被动路径在 **200fps 零丢失**（7498/7498）、300fps 仅 0.96% 合并。
这已远高于任何当前真实传感器速率 ⇒ DataBatch 省的是设备侧 CPU/包数，
**不是当前已观测到的瓶颈**。

⚠ 附带发现：500fps 的「丢失」其实是**合并**（261B = 29×9B），
98% 的字节都到了，因为发送间隔 2.1ms 小于 `UART_IDLE_THRESHOLD_US=2000`。

### 3. `io->write` 并发是否安全 —— ✅ 已确认**不安全**，并已修复（commit `07cee645`）

**两个独立缺陷**：

1. **成帧缓冲是共享静态的**：`session_transport.c:190` 的 `s_tx_scratch` 是**单个**数组，
   被 `report_tx` / `log_tx_task` / `status_task` / `crash_diag` / `dev_link` 共用。
   `stx_send_frame` 是「整帧编码进 scratch」→「循环 write(scratch)」，
   并发时后者的编码**覆盖**前者未写完的缓冲 ⇒ 线上出现半条帧 + 另一条帧的头。
   host 双线程复现实测：一种消息**凭空消失**、另一种**重复**（0x23=0 / 0x31=2）。
2. **TLS 上下文不线程安全**：`esp_tls.c` / `esp_tls_mbedtls.c` 里 `xSemaphore|mutex` = 0 命中；
   `MBEDTLS_THREADING_C` 只保护 `ssl_cache` / `ssl_ticket` / `x509_crt`，
   **不含 `ssl_tls.c`**（读写路径）。

**修法**：`sess_tx_send` 整段「成帧 + 写出」用 `tx_lock` 串行化；
背压的 `vTaskDelay(1)` 移到**锁外**；锁建不出来时不静默降级（如实报 NOT_READY）。
为什么这里锁可以跨越 I/O（与 §258 的租约修法不同）：本临界区**本来就该串行** ——
两条上行不可能同时写同一条 TCP 流而保持帧边界，串行化是语义要求；
且写路径最坏是毫秒级 TLS record 写。

**真机验证（最大化并发：打开 log_stream，使三个发布者同时活跃）**：
240s 高负载 30045 req / 125.19 req/s / **0 崩溃** / `crc_bad=0` / `report_drop=0`。

**意外收获**：`tx_lock` 还消除了被动路径的 **72% 帧丢失**与 **2.8s TLS 重连风暴**：

| | 仅 link_tcp 修复 | + tx_lock |
|---|---|---|
| 被动 100fps 收到 | 1336 / 4835（**丢 72%**） | **3870 / 3870（0%）** |
| TLS 重连 / 47s | 14 | **1** |

⚠ 诚实边界：这是**相关性**证据（同负载、仅固件不同），
不是「已定位到具体哪一次内存写导致 TLS 报错」。根因链最后一环未闭合。
