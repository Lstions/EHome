## F2 manifest 快照化 + reconcile 原子化 + hash 一致性(P0)

### 问题
`SendConfigManifestWithDecision`(sender.go:418+)在事务外 ~6 次独立 Find(:435 node、:445 templates、:457 reload、:461 channels、:465 gpio、:469 pwm),外加 :581 每 channel 的 edges 查询及 validateManifestScheduleCapacity 内 :924 重复 edges 查询(v2 新增:同一数据查两遍)。并发 CRUD 期间可编码半新半旧 manifest。reconcile(sender.go:969-1048)的 Create(:1035)与 Update(:1041)两条独立语句,且 Create 失败仅 Warnf+continue(:1036-1037)——孤儿模板+半截 template_ids 风险。

### v2 修订 1(审查最严重发现,主 Agent 复核属实):hash/manifest 一致性联动
SyncGate.decide 先调 `CalcConfigHashForDevice`(sync_gate.go:101/113)得出 manifestID,之后 SendConfigManifestWithDecision 才 reconcile 新增模板——**编码出的 manifest 内容 ≠ manifestID 对应的 hash 输入**,设备回 config_hash 与服务端永不匹配 → 每轮 Hello 重推死循环。
**设计:reconcile 必须在 hash 计算之前完成。将「reconcile → 快照读 → hash 计算 → manifest 编码」收进同一事务**,使 manifestID 的 hash 输入与编码字节流来自同一快照。

### v2 修订 2:消除 v1 自相矛盾
v1 不变量声明"事务只读"但设计又把 reconcile(写)移入事务。v2 明确选择:**(b) reconcile 写 + 全部编码读 + hash 计算同一事务,接受 fail-closed 语义**——单个模板 Create 失败从 warn+continue 降级路径变为整个 manifest 发送失败(fail(:453) 持久化 failed 状态)。**行为变化声明:这是有意的,fail-closed 优于发不一致 manifest;sync_state 自愈下轮重试。**

### 修复设计
1. `db.Transaction` 内:reconcileDriverTemplates(写)→ 快照读(node/templates/channels/**edge_devices/device_configs/dma_configs**/gpio/pwm——以 buildHashData 实际参数为准,manager.go:438 的 hash 输入含 edge_devices/device_configs/dma_configs,快照清单必须与 hash 输入同源,否则 hash 与编码仍不同源)→ CalcConfigHashForDevice(改为读快照)→ 编码。MQTT 发布在事务提交后(避免长事务持锁)。
2. 编码函数签名改为接收快照实体集合(依赖注入),便于单测。
3. GORM 写法沿用 manager.go:382-386 + SetTransactionIsolation(manager.go:510-513/testutil/db.go:187-193)先例。死锁风险低(按 node_id 小集合;API 侧 updateNodeConfig 的 clause.Locking{UPDATE} handler_node.go:885 只锁 channel/edge 行,与 reconcile 的 template 写不同行)。
4. 顺带合并 :581 与 :924 的重复 edges 查询(快照内只查一次)。

### v2 修订 3:并发验收测试必须 PG(审查专项,主 Agent 确认)
SQLite 事务是 SERIALIZABLE(强于 PG REPEATABLE READ),且 nodemgr 包全部测试用 sqlite :memory:,SetTransactionIsolation 在 SQLite no-op(testutil/db.go:187-193)。**SQLite 全绿不代表 PG 下无竞态**。并发验收测试必须用 testutil 包 + PG(`EHOME_TEST_DB=postgres`,testutil/db.go:92-94),纳入 `make test-integration` 并 CI 强制。

### v2 修订 4:生产重复模板数据(dev PG 实测)
dev PG 实测:config_templates 8 行 write_data 全部相同(010300000001840A),channels 1-4 的 template_ids 逐条引用(1,2,3,4,5,6 / 7,8 / 9-14 / 15-19),**且 channel 3 引用模板 9-14 不存在**(全表仅 8 行)。reconcile 的 write_data 去重不清理既有重复。**F2 落地前需数据修复评估**:重复模板挤占 maxManifestTemplates=16(sender.go:32) 容量;悬空引用见 F3。

### 验收
- PG 并发测试:后台 goroutine 并发更新 channel/template 时,编码 manifest 内部自洽(所有 channel 引用的 template_id 在同一快照内)。
- reconcile 中途失败不留孤儿模板;manifestID 的 hash 输入与编码字节同源(测试断言)。
- make test + make test-integration(PG)全绿;dev 一次完整 config sync 回归。

## F8 固件简化:RESERVED 态删除 + report_task 前置层收敛(P2)

### F8.1 RESERVED 态删除 — v2 重写(审查 FATAL,主 Agent 复核源码属实)

**v1 的"RESERVED 实际不可达"论断事实错误,重写理由与影响分析:**

实读 reserve_slot(handler_channel_cmd_v2.c:140-191):`s_reservation_lock` 自旋锁只互斥并发 reserve 调用者,**不互斥 handler_channel_cmd_v2_complete**。complete 在 bus worker 任务运行,reserve 在 MQTT 投递任务运行,双核/抢占式调度下可真正并发。锁内时序:CAS 置 RESERVED(:172/181)→ prepare_slot(:174/183 非原子多字段写)→ store QUEUED(:175/184)。complete 此期间读 state(CAS 期望 QUEUED :209-211)会**观测到 RESERVED** 并 return——RESERVED 对 complete 路径可达,锁管不着。

**删除的真实安全性论证(替代"不可达"):**
- 锁内 RESERVED 窗口里 complete 的 CAS(期望 QUEUED)失败 return——该 race 在删除前后都存在(删后窗口内 state=FREE/FINAL,CAS 同样失败 return),**删除不改变可观察行为**。
- bus 侧 V2 命令单 worker 串行执行,complete 必然发生在 ack 之后,ack 在 reserve 返回后才发(:308-337),故该窗口实际不可命中。
- 真正需要锁保证的是扫描-占用原子性(same_identity 扫描与 CAS 占用之间不能有第二个 reserve 插入),锁覆盖 :143-190 全程(审查 VERIFIED 五条出口 :158/162/176/185/188 全部释放)。

**连带改动(v1 未列):** 删枚举值后 :155 的 skip 分支、:172/:181 的 CAS 目标态都要改(CAS 改直接 store 或保留 CAS 目标 QUEUED)。complete 读半初始化 final 字段由 QUEUED→COMPLETING CAS(:210)保证,不受影响。

### F8.2 report_task 前置层收敛 — v2 修订(审查发现方案低估真实语义)

实读 bus_worker.c:314-383:前置扫描是**三层**不只是 critical/emergency——:324-337 先非阻塞扫 `s_control_final_q` + `s_write_rsp_q`(控制面最高优先),:342-345 才扫 critical/critical_emergency,:351-366 最后 QueueSet 等待。v1 漏述 control_final/write_rsp 两层。

**v2 决策(采纳审查的保守替代):保留 control_final/write_rsp 前置(控制面延迟敏感),只删 :342-345 的 critical/emergency 扫描。**
- 删除影响声明:critical/emergency 与 telemetry 同就绪时,xQueueSelectFromSet 按队列加入 set 的顺序选择(FreeRTOS 语义),不再保证 critical 严格优先。critical 承载 error_code!=0 OR request_id!=0 的报告(report_is_critical,bus_worker.c:134),延迟敏感。
- 缓解:将 critical 队列在 xQueueAddToSet 中排在 telemetry/emergency 之前(bus_worker.c:521-525 中 control_final/write_rsp 因前置扫描保留仍在最前,语义自洽)并注明依赖 FreeRTOS 选择顺序语义。
- QueueSet 等待 1000ms 上限(:352)与 esp_task_wdt_reset(:323,328,335)的 WDT 语义不受删扫描影响。

### 验收(v2 增强)
- host_tests 全绿;**新增为 report_task 队列选择顺序补 host 用例(同就绪时的服务顺序),或显式声明接受实机回归为唯一验证**。
- F8 落地前 F5 的 collision/replay/CAS 用例必须先绿(回归网);F8 删态后**同步更新 F5 受影响用例**(目标态集合变化)。
