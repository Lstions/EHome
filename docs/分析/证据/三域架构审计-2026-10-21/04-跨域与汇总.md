## 1. 结论摘要

**一句话**：这是一个"工程纪律远高于行业平均、但业务语义尚未在数据面闭环"的模块化单体。三层模型、二进制帧契约、显式状态机、注入式解耦、证据驱动文档都属**优秀**；真正的问题不在代码质量，而在**同一份"数据"被三个互不引用的子系统各自解释**（数据源/告警/自动化），以及**权威契约文档与门禁落后于代码**。

| 维度 | 评分 | 一句话理由 |
|---|---:|---|
| 产品功能定义 | **7.0/10** | FR-A~O 共 15 域、58 篇设计文档、术语表/概念模型边界清晰；扣分：数据源"权威来源"不接数据面且组语义与"单存活实例"冲突（01 报告 P0×2）、HA 接口假成功、MQTT 权威文档整体过期、三域身份口径三套 |
| 数据流转 | **7.5/10** | 上行 8 跳、下行 9 跳逐跳可追，背压/丢弃/幂等都有显式落点；扣分：帧 seq/CRC 语义未实现、固件断链丢帧无账、数据源停滞扫描与离线钩子可能双计、自动化"执行结果不回写规则层"、调度器全系统 ≈1 命令/秒 |
| 接口依赖 | **6.5/10** | HTTP（190 条/26 文件）、WS（17 常量）、DB（45 模型）、协议（32 类型）四层都有契约；扣分：协议文档/字段门禁落后代码、**前后端 WS 事件名错位**（前端订阅的名字后端 0 生产者）、两阶段 setter 注入只能靠源码 grep 门禁、MTU 上界三处漂移 |

### 2.2 三域的角色与相互引用（关键结论）

| 域 | 业务角色 | 数据面角色 | 对其它域的编译期依赖 |
|---|---|---|---|
| **边缘设备** | 唯一物理数据生产者 + 自动化执行器 | 上行：DataReport/DataBatch；下行：ChannelCmdV2/WriteCmd/PeriphCmd/DeviceOp/OTA/Config | 无（固件只认帧类型） |
| **数据源** | 逻辑设备×类别的"候选来源/权威来源"声明 | **管理面**：不参与摄入、不参与查询、不参与告警/自动化取值 | `datasource -> models, notify`（最孤立） |
| **自动化** | ECA 规则：触发→条件→动作 | 控制面：读 parser 回调、写 commandexec | `automation -> commandexec, datalifecycle, deviceaction, notify, sun` |

**实证（本报告最关键的一条否定性断言）**：
```bash
# 分母：backend/internal/{alert,automation,databus,datasource} 的非测试 Go 文件
grep -rn 'datasource\|DataSource' --include=*.go internal/alert internal/automation internal/databus | grep -v _test   # → 0
grep -rn 'automation' --include=*.go internal/datasource | grep -v _test                                            # → 0
grep -rn 'internal/alert' --include=*.go internal/automation | grep -v _test                                        # → 0
```
即：**"哪个来源是权威"这件事，只有人能看到，数据面没有任何消费者**。数据源切换不会改变入库、不会改变最新值、不会改变告警阈值判定、不会改变自动化触发。

### 2.3 三套身份口径（同一批数据，三种主语）

| 消费方 | 作用对象 | 证据 |
|---|---|---|
| 数据源 | `(logical_device_id, category)` 组 + 提供者 `edge_device_id` | docs/设计/数据源主备与故障转移.md:23,28-30；models.DataSource |
| 阈值告警 | `target_type = edge_device \| logical_device` 二选一 | backend/internal/models/alert.go:11-12,36 |
| 自动化 | **只有** `trigger_edge_device_id` / `action_device_id`，无逻辑设备作用域 | backend/internal/models/automation.go:157,190 |

后果：① 换设备/逻辑设备合并后，自动化规则仍绑在旧 edge_device 上，不会跟随身份迁移；② 告警可以按逻辑设备配，自动化不行，前端要用户理解两套口径；③ 数据源按逻辑设备组管理，但触发/动作按边缘设备执行——**"权威"与"执行"不在同一主语上**。这是比"功能缺失"更本质的产品定义问题。

## 3. 端到端数据流转（逐跳 + 失败/背压点）

### 3.1 上行（采集 → 入库 → 三个消费者）

| # | 位置 | 动作 | 失败/背压 |
|---|---|---|---|
| 1 | 固件 scheduler | 按 interval 生成 sample_cmd_t（180B）投 per-bus 队列 | 队列满计数跳过 |
| 2 | 固件 bus_worker | TX→事件 RX→错误码 | RX 超时/CRC → 带 error_code 上报 |
| 3 | 固件 report 池/队列 | critical/emergency/telemetry 三档 + 有界队列 | 池/队列满 → drop+计数 |
| 4 | 固件 msg_handler → session_transport → mbedTLS | 唯一成帧点、tx_lock 串行 | 发送返回 esp_err_t，但调用方多为 void → **断链期静默丢帧**（03-edge.md §5 缺陷 4） |
| 5 | 后端 transport.readLoop | magic 重同步、长度校验、type==payload[0] 强校验 | payload 超界/CRC 错 → 断连 |
| 6 | nodemgr.HandleFrame → enqueueDataReportJob | dataCh 满 → overflow goroutine → 再满阻塞 OnFrame | 阻塞会反压到该节点读循环（设计选择） |
| 7 | databus.DataEventBus（分片） | fan-out 到 parser/persist/WS/metrics/pendingwrite | 丢弃有 metrics，但 consumer 维度弱 |
| 8 | SensorParserConsumer | 解析 → persist → 四个 sink：latest / alert / automation / sourceHealth | sink 为 nil 时**静默跳过**（见 §7.2） |

关键事实：三个业务消费者（alert / automation / datasource）**并列挂在同一个解析回调点**（manager.go:270-279），共享一个 `parser.Field`，但各自维护自己的状态与冷却/去重，**互不仲裁**。

### 3.2 下行（规则/人工 → 物理执行 → 回执）

| # | 位置 | 动作 | 语义要点 |
|---|---|---|---|
| 1 | automation.Evaluator | 规则 armed→triggered（sensor_threshold 滑窗 / time_window / sun_event） | 冷却锚点持久化到 `last_triggered_at`（models/automation.go:227-245） |
| 2 | automation.Planner.HandleTrigger | 日熔断 → require_confirmed 分流 → 多动作串行 | 幂等键 `automation:<rule>:<day>:<trigger_seq>:<action_seq>`（planner.go:340-341） |
| 3 | commandexec.Service.Create | 9 项 availability gate + CanonicalizeParams + 幂等 scope 去重 + Outbox 持久化 | 拒绝返回哨兵错误（fail-closed） |
| 4 | commandexec.Dispatcher → ChannelCmdV2Transport | 目标可用性/清单已应用/能力位/deadline 校验 → 编译 bounded plan | 超能力位拒绝发布（channel_cmd_v2_transport.go:174-199） |
| 5 | downlink.Bridge.Publish | 包装 12B 帧 → Registry.SendToNode | 无 session = **ERROR**（MQTT 已删，无兜底） |
| 6 | 固件 devlink → msg_handler | type 与 payload 一致性校验 → 唯一下行入口 → switch | 未知类型 WARN；handler 返回 void，拒绝对派发层不可见 |
| 7 | 固件 bus_manager → control queue → bus_worker | 与 sample 队列物理隔离；多步 plan 借 control_slot 原子执行 | 队列满 → 立即回失败回执 |
| 8 | 固件回执（0x16 ACK / 0x17 FINAL / 0x07 WriteRsp） | final 队列满 → **丢弃 final**（日志+计数） | 后端只能等 deadline → UNKNOWN → 人工处置 |
| 9 | 后端 nodemgr → VerifyFinal → command_executions 终态 | 终态包含 UNKNOWN + ManualResolution | automation_events 只记"已提交"（result=executed），终态需 join command_executions（前端已提供跳转） |

**下行最值得肯定的设计**：把"提交"与"成功"分成两件事——automation_events.result=executed 的注释明确写"已提交 commandexec 执行"（models/automation.go:51），最终状态在 command_executions 里，前端用 command_id 跳转（AutomationRules.vue:198/1516-1520）。这是诚实语义，避免了"审计说成功、设备其实没动"。

### 3.3 自动化域的三个"承重墙"细节（02 报告实证，Lead 已复核）

1. **plan step ≠ 自动化动作**（重要概念澄清）：自动化 1 个动作 = 1 条 CommandExecution = 1 个 ChannelCmdV2 信封；"一个信封内多步"只发生在设备动作执行形状为 `bounded_sequence` 时（channel_cmd_v2_transport.go:174-206）。多动作规则（N 个动作）产生 **N 条命令、N 个信封**，彼此不共享事务。
2. **"失败中止剩余"只覆盖入队失败**：`planner.executeActions` 的循环只在 `commandexec.Service.Create` 返回错误时中止（planner.go:324-362），而 Create 的同步边界是"QUEUED + outbox PENDING"（commandexec/service.go:560-573）；设备侧 final_failed/UNKNOWN 发生在 Create 返回之后，**不会中止后续动作，也不会落 partial_failure**。唯一 partial 测试用 `no_such_action` 造的是入队失败（planner_multi_action_test.go:426-451）。→ 设计文档承诺的"第 k 个动作失败 ⇒ 中止剩余动作"在物理层面不成立。
3. **全系统命令调度吞吐 ≈ 1 条/秒**：`runCommandDispatcher` 每 1s 调一次 `ProcessOnce`（main.go:593-601），而 `ProcessOnce` 每次只取 1 条 outbox（dispatcher.go:76-100，`Limit(1)` + 同 node/channel 互斥）。多条自动化命令/多设备并发时会排队；叠加"executed 在 Create 返回即写"，审计上会先看到 executed，再看到命令排队/超期。

## 6. 产品功能定义完整性

### 6.1 做得好的
- **术语与边界**：三层模型（中心端/节点/边缘设备）+ 血缘/身份分离（edge_device_id / logical_device_id）在术语表与概念模型里是权威定义，且代码模型与之一致（models.go、unified_data 双列）。
- **需求清单**：FR-A~O 15 域 + FR-P 协议 4 项 + 非功能 4 类；每项给"依据文件"（功能需求总览.md）。
- **设计文档体系**：58 篇设计 + 61 篇分析 + 275 篇 md/9.1MB，含验收标准、已知限制、裁决记录。
- **受控操作体系**：9 项门禁、幂等 scope、Outbox、UNKNOWN+人工处置、风险动作确认制——这是三域里定义最完整的部分。

### 6.2 关键缺口（按用户可感知度）
1. **数据源是"看起来能用、实际不影响数据"的功能**：设计文档 §1 定义它"对取值来源做主备管理"，§9.1 又声明"不改读取热路径，权威来源当前用于运维可见性/通知/标注"。→ **产品承诺与交付语义不一致**，前端用户切换"权威来源"后数据/告警/自动化都不变，只有状态标签变化。
2. **数据源创建表单要求用户手填内部 ID**：`device_id`（逻辑设备"ID"）、`edge_device_id`（"ID"）、`category`（自由文本）都是裸输入（DataSourceList.vue:245-262），且后端只校验非零，**不校验对象存在、不校验 category 是真实传感器名**（service.go:157-231）。拼错 category → 永不 MarkSuccess → 5 分钟后判停滞 → 熔断，用户拿到的错误文案与实际原因相隔很远。
3. **HA 集成假成功**（§5.5）：比"没做"更糟——用户以为同步了。
4. **自动化无逻辑设备作用域**（§2.3）：设备替换/合并后规则失效且无提示。
5. **数据源页无实时事件**：切换/熔断只经通知中心，页面本身不订阅 WS（前端无 data_source 事件常量；后端 events 包也无）。
6. **固件 I2C 扫描未实现但不回执**（03-edge.md 缺陷 7）、**证书铺开未实现（私钥明文）**（03-edge.md §0/§2）——属功能完备度缺口。

## 7. 架构评价

### 7.1 优秀之处（with evidence）
1. **三层模型 + 中心端权威 + 节点无业务逻辑**：全系统最重要的抽象，概念模型 §4 裁决正确；代码层面固件只认帧类型、后端持有全部状态（nodemgr/transport 与 link_tcp 的分工）。
2. **双协议单一契约 + golden vectors**：Go/C 共享 `protocol/vectors` 与语义头，帧编解码有跨语言变异证明（tools/manifest_crosslang_mutation_proof.py 等）。
3. **显式状态机 + 幂等**：command_executions 8 态与转移表（commandexec/state.go:3-32）、automation 幂等键含 trigger_seq+action_seq（planner.go:285-294）、ChannelCmdV2 的 command_id/digest/attempt/boot_id 四元组去重。
4. **分片数据总线 + 轻重消费者分离**：ingest→persist→push 单进程扇出，避免了网络 MQ；背压/丢弃有指标（databus/bus.go、consumers_heavy.go）。
5. **解耦手法**：用函数值/接口注入打断反向依赖（api→nodemgr 的 latest sink、automation→api 的 latestValueFn、databus→api），并在 main.go:365/374 明确记录"为什么"。
6. **测试纪律**：后端 Go 162,309 行（测试 83,485 行，51.4%；2,122 个 Test/Benchmark）；固件 host_tests 37,788 行 / 95 个 ctest 用例 / 76 个测试文件；大量"变异自证"测试（mutation self-check）。
7. **文档治理**：58+61 篇文档、设计-实现-验收三合一、明确记录"已知限制"与"裁决"。
8. **资源约束当作设计输入**：S3/S3P/C6 的 IRAM/DRAM 取舍、方案 D（bus_cmd_t 700→180B、3 队列省 16.8KiB）、放置判定、可见失败——固件质量明显高于一般 ESP32 项目。

### 7.2 结构性缺陷（按严重度）
1. **P0 三域数据面不闭环**：权威来源不参与任何取值（§2.2 实证）。这使"数据源"成为"带状态机的通讯录"，且它与告警/自动化的身份口径（edge vs logical）无法对齐。
   - 可证伪判据：`grep datasource alert automation databus` 零引用；`docs/设计/数据源主备与故障转移.md:170` 自陈。
1-bis. **P0 自动化闭环在物理执行层断裂**：规则层只有"已提交"（executed），设备终态（SUCCEEDED/FAILED/UNKNOWN）只落在 command_executions，**没有任何回写规则事件的消费者**；多动作的真实失败不中止剩余动作、不落 partial_failure；前端订阅的 2 个"可感知"事件名后端 0 生产者。→ 用户看到的"自动化成功"只是"命令已入队"。
   - 可证伪判据：让设备对第 1 个动作回 final_failed，观察第 2 个动作是否仍被下发、automation_events.result 是否仍为 executed（02 报告判定：是）。
   - 关联：调度器 ≈1 命令/秒（main.go:593-601 + dispatcher.go:76-100）。
2. **P1 两阶段 sink 注入 = 编译期不可检查的接线**：`Manager` 先构造、sink 后注入；漏注入时引擎"从未触发"而所有单测全绿（manager.go:225-228、main.go:341-343）。缓解手段是**扫描 main.go 源码字符串**的门禁（cmd/server/notify_wiring_gate_test.go:59-70），并带变异自检——工程上已尽力，但依然是"文字匹配代替类型系统"的脆弱契约。
3. **P1 协议契约治理失效**：权威协议文档漏 6 个消息类型、字段门禁脚本期望表停在 0x18 且未进 CI（§5.2）。对"接口依赖"是根本性问题：**唯一契约文档不是真值源**。
4. **P1 handler 层仍厚**：5 个 handler >1000 行（periph 1467 / edge_device 1435 / device 1450 / node 1356 / automation 1120），与"≤300 行"目标背道而驰；业务逻辑与传输层混杂会放大改动面。
5. **P2 同一语义多处实现**：MTU 上界三处漂移（wire 16368 / link_tcp 8192 / backend 8192+8176）、TLS 记录长度 `sdkconfig` 16384 vs `sdkconfig.defaults` 8192（03-edge.md 缺陷 2）、category 大小写/命名跨边界（本仓有专门缺陷类文档：跨边界枚举大小写缺陷类-2026-09-16.md）。
6. **P2 失败可观测性不对称**：固件上行发送失败多为 void（无丢弃计数）、下行 final 队列满直接丢、seq 恒 0/CRC 无校验；后端则有 metrics/UNKNOWN/人工处置。→ "设备侧发生了什么"不可对账，排障只能靠现象。
7. **P2 部署残留**：本机仍在运行 `ehome-emqx` 容器（3 天），但 compose 已无 emqx、后端已无消费者（docker ps 观测）。属环境残留，不是代码缺陷，但会误导"MQTT 还在用"的判断。
8. **P3 数据源引用完整性缺失**：3 张表无 FK、Create 不校验 device/edge_device 存在（§6.2-2），可产生永远静默的数据源。

### 7.3 独立复核（05-verify.md）补充的两条系统性风险（四份报告共同盲区）

- **R1 单实例部署假设未显式化**：所有周期任务（datasource ScanStale 60s、automation window ticker 1min/dispatcher 1s、datalifecycle retention/purge、offlinedetector）都是进程内定时器，**没有选主/租约**（唯一 advisory lock 用于 seed 开发播种）。双副本会双触发、双通知、双切换。当前"单机单实例"是值得写进部署契约的**硬约束**，而不是隐含前提。
- **R2 全局调度容量 × deadline × 多动作的合成后果**：dispatcher ≈1 命令/秒（§3.3-3），命令 deadline 默认 2 分钟 ⇒ 突发超过 ~120 条时，尾部命令在派发前就已超期（被判 FAILED）；多动作规则的 N 条命令共享同一个 2 分钟 deadline；自动化/人工/OTA/配置下行共用**无优先级 FIFO**。单看任何一域都不算 bug，合起来是"自动化在高负载下先失败、且失败原因看起来像设备失败"。
