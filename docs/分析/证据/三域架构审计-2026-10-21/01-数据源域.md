## 1. 一句话结论 + 评分

**一句话结论：数据源主备是一套"工程质量不差、产品闭环不成立"的运维台账——R1–R11 状态机、健康留痕、通知与 9+1 条 API 基本按 v1.0 设计落地且有测试（T），但 `status=active` 从未被摄入/查询/告警/自动化任何热路径消费（C，设计 §9.1 自认），其组键语义又与"同一逻辑身份至多一个存活实例"不变量正面冲突（C），因此在真实数据链上它既不能影响取值、也难以被正常构造出来；生产库 `data_sources` 0 行（T），属"已交付、未使用"。**

| 维度 | 评分 | 一句理由 |
|---|---|---|
| 功能定义 | **5/10** | 11 条转移规则、术语与边界写得比多数模块清楚，也显式声明了"v1.0 不改读取热路径"；但产品页/仿真场景标题宣称"由主来源负责取值"（view:3、ds.go:37），代码里 active 只是台账；`is_primary` 声明后零消费；category 不封闭。 |
| 数据流转 | **5/10** | 成功/离线/停滞三路信号真实接通并有单测（consumers_heavy.go:410-426、offlinedetector.go:259-283、service.go:689-777）；代价是每成功帧在解析热路径同步做 1 次 SELECT+N 次 UPDATE，且失败只 Warn（fail-open）；流转终点仍是"台账+通知"，不回流数据链。 |
| 接口依赖 | **6/10** | 9+1 路由统一 envelope/JWT/分页 clamp/错误哨兵映射/空集 `[]`，前端 DTO 与后端逐字段一致（40 条前端用例通过）；但 `device_id` 与 `unified_data.device_id`（=edge_device_id）同名异义、`/devices/:id` 前缀两种 ID 语义、无 FK/无存在性校验、删设备不清理来源。 |
| 架构设计 | **5/10** | 领域服务/HTTP 分层、事务边界、通知 fail-open、二阶段 sink 注入与接线门禁测试都是好范式；但"至多一条 active"无 DB 约束、冷却抑制后组永久无权威、候选不校验健康、UpdatedAt 被复用为"成为 active 时刻"造成语义糊化。 |

**给 Lead 的三句话**：① 数据源不是拓扑实体，是横切在"逻辑设备（归属）× 数据类别（sensor_name）"与"边缘设备（提供者）"之间的**权威声明台账**；② 它当前对数据流转**零影响**（唯一作用是运维可见性/通知/留痕），与逻辑设备合并去重功能在价值上重叠；③ 它最大的问题不是 bug，而是**概念前提与逻辑身份不变量冲突**，导致"主备"在正常创建流程下不可构造。

### 2.1 产品概念关系（必答 a 的完整版，Lead 汇总直接引用）

**证据链**：
- **概念模型/术语表没有"数据源"这一实体**（C+D）。`docs/设计/术语表.md:12-33` 的四层模型只列 中心端/节点/通道/设备配置/边缘设备/逻辑设备/数据；`概念模型.md:43-58` 的 E-R 摘要同样没有 data_sources。全仓 `grep -rn '数据源' docs/设计/*.md`（排除本域文档）只命中"数据源主备""通知中心"等引用，无第二处定义（附录 A-3）。
- **代码事实是三元组 + 权威状态**：`DataSource{DeviceID=LogicalDevice.ID, Category=sensor_name, EdgeDeviceID=EdgeDevice.ID, Status}`（models.go:340-359；设计:21,30）。**没有 node_id / channel_id / device_config_id 字段**，也没有任何指向 Node/Channel 的查询（C）。
- **引用关系是软引用**：生产 PG 上 `data_sources` 只有 not-null 与 pkey 约束，**无外键**（T，附录 A-7）；`Create` 只校验 `device_id/edge_device_id != 0`（service.go:158-166），不查实体是否存在。

**结论（可直接引用）**：

1. **数据源 ≠ 节点 ≠ 通道 ≠ 边缘设备 ≠ 逻辑设备**，它是**第 5 类、控制面/台账类**对象：把"某个逻辑设备的某个数据类别"指派给"某台边缘设备"作为候选提供者，并维护"谁是权威"的角色位。物理拓扑（节点/通道/设备配置/边缘设备）与数据身份（逻辑设备）都没有它的位置。
2. **与"逻辑设备合并去重"功能域重叠**：设备更换/多源同量的真实问题，已由逻辑身份合并 + 查询侧保形去重（`边缘设备数据生命周期.md:60-71`）解决；数据源主备在数据层没有提供合并机制之外的新能力——这正是它"不改读取热路径"仍能成立的根因（设计 §9.1）。
3. **与"逻辑身份单存活实例"不变量正面冲突**：`handler_edge_device_lifecycle.go:64-86` 规定"同一 logical_device 同时只允许一个存活实例"（D+C）。因此"同一逻辑设备同一类别由两台存活边缘设备提供"在正常创建流程下**不可构造**；唯一可能是先合并两个逻辑身份（merge 链）再利用追溯，但那是"故障后归档"而非"在线主备"。SIM-DS 夹具直接绕过了这一前提：它让两台设备各持自己的逻辑身份，只把组键统一取主设备的逻辑身份（`simulation/catalog/ds.go:111-117`），因此**备来源的数据从不落在组键对应的逻辑设备上**——仿真只验证了状态字段，从未验证"切换后取值来自备用"。
4. **与设备在线状态同名异义**：`EdgeDevice.status='active'`=启用/在线（models.go:177），`DataSource.status='active'`=主用（service.go:24），仓库自己的 `契约评审-同名异物与双值状态-2026-09-23.md:57-77` 已把这一条登记为危害（D）。
5. **术语违规**：failover-logs 路由用 `/devices/:id`（handler_data_source.go:63），但 `术语表.md:125-134` 明令"设备（单独使用，有歧义）"禁止、且同前缀的 `/devices/:id/history`、`/devices/:id/sensor-data` 用的是**边缘设备 ID**（handler_data.go:56-78, 164-229）——同一路径参数两种 ID 命名空间（C）。
6. **product 层面一句话**：页面副标题"为逻辑设备的数据类别声明主备来源，按健康度自动切换权威来源"（view:3）在"声明/切换权威"上成立，在"由主来源负责取值"（SIM-DS-001 标题，ds.go:37）上**不成立**——后者是 v2 才可能有的能力（设计 §9.1）。

## 4. 数据流转（生产→传输→摄入→落库→查询/触发→下行）

### 4.0 流转全景（文本时序）

```
节点采集 ──mTLS──► databus.SensorParserConsumer ──解析成功──┐
                                                    │      ├─► unified_data 落库 ─► latestSink（与 active 无关）
                                                    │      └─► sourceHealthSink(edgeDeviceID, sensorNames, at)
                                                    │                │
                                                    ▼                ▼
offlinedetector(1s 扫描,60s 阈值) ──离线钩子──► datasource.Service.MarkFailure   MarkSuccess
                                                    │  fail_count++ / health(failure)     │ last_success, fail_count=0, error→standby
                                                    ▼                                     │
                                    fail_count ≥ max_fail_count? ──否──► 结束             │
                                                    │是                                   │
                                                    ▼                                     │
                                    maybeFailover(冷却? 有 active? 有 standby?)            │
                                      │ 是切换                                              │
                                      ▼                                                     │
              data_sources 状态迁移 + failover_logs + data_source_health + notifications ◄──┘
                                      │
                                      ▼
              notify.Dispatcher（落库 notifications + Deliver 外发）
```

（注：图仅为阅读辅助；逐跳函数/行号见 §4.1。）

### 4.1 逐跳路径

1. **生产/传输**（不属本域，仅给上下文）：ESP32 节点 UART/SPI 采集 BMS(嘉佰达)/逆变器(techfine) → mTLS TCP 3.0 上行 DataReport → `databus` 分片消费。
2. **解析成功 → 健康成功**（T：解析路径有既有测试）：
   `SensorParserConsumer` 解析成功、持久化 unified_data 后，同一函数内同步调用注入的 sink：
   `sourceHealthSink(device.ID, sensorNames, now)`（consumers_heavy.go:410-426；sensorNames=[parser.Field.Name...]，含 panic recover）。
   → `main.go:349-351` → `Service.MarkSuccess`（service.go:599-634）：
   `SELECT data_sources WHERE edge_device_id=? AND status<>'disabled'`，对 `Category ∈ sensorNames` 的来源 `UPDATE last_success=at, fail_count=0`，`error → standby`。**不抢占 active**（R1）。
3. **设备离线 → 健康失败**：`offlinedetector` 每 1s 扫描、阈值 `EdgeDeviceOfflineThreshold=60s`（offlinedetector.go:37-41, 310-357），把"曾上报超时"与"新建从未上报"两类设备置 offline → `OnEdgeDeviceOffline` → **独立 goroutine** 调 hook（:259-283）→ `Service.MarkFailure(edgeDeviceID, "device_offline")`（service.go:638-684）：该设备名下所有 active|standby 来源 `fail_count++`、写一条 failure 健康事件；达 `max_fail_count` → `error` 并进入 `maybeFailover`。
4. **数据停滞 → 健康失败**：`Service.Start` 每 `ScanInterval=60s`（main.go:355-357）→ `ScanStale`（service.go:689-710）只扫 status=active：`at-UpdatedAt < MinResidency(120s)` 跳过；`LastSuccess` 新鲜（≤ Staleness 300s）跳过；否则 `failStaleSource`（:713-761）计一次失败 + health(failure, response_time=停滞ms) → 达阈值 → error → `maybeFailover(trigger="stale_data")`。
5. **切换决策** `maybeFailover`（service.go:779-836，必须在调用方事务内）：组内已有 active→no-op（防两条 active）；`now-最近 failover_log < Cooldown(5m)`→**只记 transition+通知、不切换**；否则选 `status=standby ORDER BY priority DESC, id ASC` 第一条 → active，写 `failover_logs(reason=auto, trigger)`、`data_source_health(transition)`、通知。无候选→写 warning 通知（degraded），不改状态（R4）。
6. **落库**：`data_sources`（运行态）、`data_source_health`（failure|transition，成功事件不落库）、`failover_logs`（from/to/reason/trigger）；通知落 `notifications(source='data_source')` 并同步 `Deliver` 外发（notify/dispatcher.go:109-126）。
7. **查询**：REST 三组——列表（过滤+分页）、单条、健康时间线、`/devices/:id/failover-logs`（device_id=**逻辑设备**）。**无 WS 事件**（附录 A-9），前端靠页面加载/操作后回查。
8. **下行**：**无**。本域不依赖 `commandexec`/downlink，不下发任何指令；这也是"台账"定位的必然结果。

### 4.2 失败与背压点（按影响排序）

| 点 | 事实（C/T） | 影响 |
|---|---|---|
| B1 解析热路径写放大 | 每个成功帧同步 1 次 `SELECT data_sources` + 每个命中来源 1 次 UPDATE（service.go:607-630 在 consumer goroutine 内，无 batch/异步） | 解析器饱和上限 ~500 evt/s（数据采集与数据链路:99）时额外 ~500 QPS 落在 data_sources；且每次 UPDATE 会 bump updated_at，间接影响 R11 判定（见 D4） |
| B2 健康失败静默 | MarkSuccess 查询/更新失败只 `logger.Warn`（service.go:608-610, 631-633）；sink panic 只 Warn（consumers_heavy.go:418-423） | 健康信号丢失时无指标、无通知，前端表现为"来源一直健康/或一直停滞"，不可观测 |
| B3 通知同步外发 | `emit` 在事务提交后同步调用 `Dispatcher.Create`（service.go:896-899），Create 内同步 `Deliver`（dispatcher.go:120-125，外发 HTTP） | 切换发生在 ScanStale 循环/离线 hook goroutine 中，慢通道会拉长该轮扫描；频次低，风险有限 |
| B4 无界表 | `data_source_health`/`failover_logs` 无清理任务（附录 A-8，设计 §4 承诺 30 天） | 长期运行无界增长；停滞扫描每轮为每个 stale active 写 1 行，理论上可积累 |
| B5 扫描 O(active) | `ScanStale` 每次全表取 active（service.go:690-693），逐条开事务 | 家庭规模可忽略；台账条目多时是 N 次事务/分钟 |
| B6 通知路径双写风险 | 生产同时注入 dispatcher 与旧回调（main.go:338/344），优先级 dispatcher（service.go:896-902） | 不会双写（旧回调被短路），但属冗余接线（D10） |

### 6.2 缺陷（含影响面与可证伪判据）

> 判据写法：**按判据做一次操作/查询，若结果与"影响"描述不符，则本条被证伪**。D1/D2 为 P0，D3–D5 为 P1，其余 P2/P3。

**D1（P0）active 权威是纯台账，产品承诺与实现不符** — 证据：非测试 `models.DataSource` 引用仅 migrate/testutil/领域包（附录 A-4）；无任何摄入/查询/告警/自动化读 `status=active`；设计 §9.1 自认（数据源主备:168-170）；SIM-DS-001 标题"由主来源负责取值"（ds.go:37）但断言只查 `status`（ds.go:325-341）。影响面：所有数据页/告警/自动化取值、以及用户对"主备"的产品预期；数据源页副标题（view:3）同样承诺了未交付语义。**判据**：把某组 active 置 error 并切到 standby 后，`GET /unified-data/historical`、`/overview` 的 latest_data、告警求值结果与切换前逐字节相同——这正是设计 §9.1 的预期，说明"切换"对数据无影响。

**D2（P0）组语义与"逻辑身份单存活实例"不变量冲突，主备在正常流程下不可构造** — 证据：`checkLivingInstanceUniqueness` 明确 409（handler_edge_device_lifecycle.go:64-86）；数据源组键 = LogicalDevice.ID（models.go:343；设计:21,30）；SIM 夹具绕行说明（ds.go:111-117）。影响面：功能可验收性——即便 D1 被修复，也无法在生产里搭出"两个存活提供者"的合法组；现有唯一可能形态是"先合并再追溯"，但合并后 unified_data 已按 MAX(id) 保形去重，切换无事可做。**判据**：按产品流程创建第二台边缘设备并选择"继承同一逻辑设备"→ 返回 409；或查 merge 后两设备各自的 unified_data.logical_device_id 已相同（此时主备声明已无意义）。

**D3（P1）冷却抑制后组永久无权威来源（状态机无活性）** — 证据：`maybeFailover` 冷却分支只写 health/通知即 return（service.go:792-806）；`ScanStale` 只扫 active（service.go:689-693），error 源不会被再次评估；`MarkSuccess` 只把 error 降为 standby、不升 active（service.go:622-623）；`Create` 判定"首条 active"用的是 `groupCount==0` 而非"组内无 active"（service.go:197-206），所以 degraded 组新增健康来源也只会是 standby；`TestR10` 把"抑制后 active=0"写成断言且无后续恢复用例（service_test.go:589-635）。影响面：一次冷却期内的二次故障会让该组永久停在"无权威"，只能人工 activate；且与 R4 的"degraded"状态叠加后不可自愈。**判据**：构造 A=error、B 在 cooldown 内故障→组 active=0；把时钟推进 >cooldown 后再跑 `ScanStale`/等待，DB 中该组仍无 active、无新 failover_log。

**D4（P1）候选不校验健康与新鲜度；`LastSuccess==nil` 即判超期** — 证据：候选查询只按 `status=standby` + priority（service.go:809-811），不看 `last_success`、不看承载设备是否离线；`ScanStale` 对 `LastSuccess==nil` 直接视为超期（service.go:697-701，测试 TestScanStaleNilLastSuccessIsStale:700-719）；`MinResidency` 用 `UpdatedAt` 近似"成为 active 时刻"（注释 service.go:687），但 MarkSuccess 的 `Updates`、Save、Activate 都会刷新 updated_at（service.go:618-625, 582, 463-468）。影响面：① 自动切换可能选中"从未成功过/已离线很久"的 standby，切换后 3 轮扫描再熔断，等于把故障延后 3–5 分钟；② 新配置且设备尚未上线的来源在 2 分钟驻留后即被计失败，默认 3 次扫描（受 R11 节流实际约 4–6 分钟）后误熔断并产生"数据源切换/降级"通知。**判据**：造一个 `last_success=NULL` 的 standby（设备离线），让 active 故障 → 观察它被提升为 active（不校验新鲜度）；或新建来源后不产生任何数据，等待 ~6 分钟 → 出现 failure 健康事件与 error 状态。

**D5（P1）数据模型无引用完整性、无生命周期清理** — 证据：产线 PG `pg_constraint` 只有 not-null/pkey，无外键（附录 A-7）；`Create` 不校验 device_id/edge_device_id 存在（service.go:158-166）；全仓无"删除边缘设备/逻辑设备时清理 data_sources"的代码（附录 A-4）；`data_source_health`/`failover_logs` 无 retention（附录 A-8，设计 §4:78 承诺 30 天）。影响面：孤儿来源（指向已删除的逻辑设备/边缘设备）会继续参与停滞扫描并产生通知；健康表无界增长；前端显示裸 ID 时用户无法识别孤儿。**判据**：直接 `DELETE FROM edge_devices WHERE id=<有来源的设备>`（或用 API 删设备）后查 `data_sources`，行仍在且下一次 ScanStale 仍会为它写健康事件。

**D6（P2）摄入热路径写放大与同步依赖** — 证据：sink 在 consumer goroutine 内同步执行（consumers_heavy.go:410-426），`MarkSuccess` 每次 1 SELECT + N UPDATE（service.go:607-630）。影响面：解析器吞吐上限（~500 evt/s）下额外 ~500 QPS；data_sources 行被高频写（updated_at 每帧变），也是 D4 的诱因之一。**判据**：同一压测下对比注入/不注入 `SetSourceHealthSink` 的吞吐与 DB QPS（本次未做，见 U5）。

**D7（P2）ID/路径/状态三重"同名异物"** — 证据：`DataSource.device_id`=LogicalDevice.ID vs `UnifiedData.device_id`=EdgeDevice.ID（models.go:320,343）；`/devices/:id/history|sensor-data` 用边缘设备、`/devices/:id/failover-logs` 用逻辑设备（handler_data.go:56-78,164-229 vs handler_data_source.go:63）；`active` 双义（models.go:177 vs service.go:24），仓库自己的契约评审已登记（契约评审:57-77）。影响面：前端/第三方必然误用；跨域排障时 ID 语义需要查注释。**判据**：把同一数字分别作为 :id 调 history 与 failover-logs，返回的数据主体不同（一个是边缘设备的时序，一个是逻辑设备的切换记录）。

**D8（P2）category 非封闭枚举 + 4 层字符串隐式耦合** — 证据：`varchar(32)` + 无校验（models.go:344；service.go:161-163 只查非空）；前端文本框（view:253-259）；`/unified-data/categories` 已有词表但未用于本页（handler_data.go:231-266）；真实取值 `rsoc/temperature_1/...`（附录 A-7）。影响面：类别拼错→永不 MarkSuccess→被停滞扫描误熔断（连锁 D4②）；设备型号更换/parser 改名会让来源静默失效。**判据**：创建 category="temp"（真实为 "temperature_1"），设备正常上报 10 分钟 → 该来源 last_success 始终 NULL 且最终 error。

**D9（P2）"至多一条 active"无数据库约束，并发下可破** — 证据：产线唯一索引仅 `uniq_ds_source(device_id,category,edge_device_id)`，`idx_ds_device_status` 非唯一（附录 A-7）；仓库已有 partial unique index 先例（migrate_device_config_default.go:49）但本域未用；并发 Create 空组可各自 `groupCount=0`→各自 active；并发重复 Create 命中唯一键→gorm 非哨兵→**500**（handler:118-121）。影响面：多实例部署（设计 §9.4 承认需选主）或重试风暴下不变量被破；API 契约 409 在并发路径缺失。**判据**：PG 上并发 10 个 POST 同一空组（不同 edge_device_id）→ 查 `select device_id,category,count(*) ... having count(*)>1` 可能 >1；并发 2 个相同 body → 部分返回 500。

**D10（P3）通知接线冗余** — 证据：main.go:338 注入 dispatcher 后 344 又注入旧回调；`emit` 优先级使旧回调在生产永不执行（service.go:891-908）。影响面：维护者误以为两条路径都生效；测试与生产的通知路径不同（测试用旧回调）。**判据**：在 `SetNotifier` 回调里加 panic，生产故障切换不会触发它（被 notifySink 短路）。

**D11（P3）前端只显示/要求裸数字 ID，未复用已加载实体** — 证据：表格/抽屉显示 `device_id`/`edge_device_id` 原值（view:110-124, 301-303）；表单为 `el-input-number`（view:244-269）；已加载的逻辑设备下拉仅用于筛选（view:60, 547-569）。影响面：用户必须先去别处查 ID；无法识别孤儿；与页面"为逻辑设备…"的产品叙述不匹配。**判据**：打开新建对话框，无任何实体选择器（只能输数字）；填入不存在的 ID 也能创建成功（后端不校验）。

**D12（P3）文档-代码漂移（D≠C）** — ① 设计头部"待实现"（数据源主备:3）vs 已实现（代码+T 测试+产线路由 401 探测）；② §4 的 30 天保留未实现（附录 A-8）；③ §5"type 列保留但不再使用"（:122）vs 产线表无 `type` 列、只有 `source_type`；④ 契约评审引用 `models.go:289` 已过期（现 340）；⑤ CI 注释称 TestScenarios 已 Skip（test.yml:170）vs 代码已恢复（simulation_test.go:57-89）。影响面：以文档为验收依据会误判；建议 Lead 汇总时统一按 C/T。**判据**：逐条按上表行号核对。

**D13（P3）Health/FailoverLogs 无对象存在性语义** — 证据：handler:290-318 直接返回数组；不存在来源返回 `[]`。影响面：前端无法区分"无记录"与"来源已删除"，配合 D5 的孤儿更隐蔽。**判据**：`GET /data-sources/999999/health` → 200 + `[]`（而 `GET /data-sources/999999` → 404），同一资源两种语义。
