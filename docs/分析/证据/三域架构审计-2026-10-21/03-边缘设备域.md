## 1. 一句话结论 + 评分

**结论**：边缘侧已经完成"2.x 消息语义 + 3.0 12B 定界帧 + mTLS 长连接"的三层落地，且把「多个生产者 → 一条 TLS 流」的并发正确性收敛到 `session_transport` 的一把 tx_lock 上；「数据源提供者(provider)」与「自动化执行器(actuator)」在固件里**共享同一套 bus_worker/消息表/上行发布出口**，只在帧类型字节处分叉——业务边界清晰、物理执行边界有队列隔离，但**发布出口与下行任务都是单点，异常/背压路径的可观测性弱于协议声明**（seq/CRC/ACK 字段两端均未实现）。

| 维度 | 评分 | 一句话理由 |
|---|---:|---|
| 功能定义 | **8/10** | 上行遥测/批量/状态/资源/日志/崩溃、下行写命令/通道命令/外设/运维/OTA/配置全部有类型与落点；扣分因 ScanReq 明确未实现、证书铺开未实现、seq/ACK 语义只写在文档 |
| 数据流转 | **7/10** | 逐跳可追（scheduler→bus→report→publish→link→backend→databus；下行对称），控制/采样队列分离是亮点；扣分因"发布失败静默"与 seq=0 使断链丢帧不可对账 |
| 接口依赖 | **6/10** | 类型表两端有一致性门禁、MTU/能力位有协商；但 MTU 上界三处漂移（16368/8192/8176）、`sdkconfig` 与 `sdkconfig.defaults` 的 TLS 记录长度不一致、seq 字段事实失配 |
| 架构设计（含资源约束） | **7/10** | 分层/opaque/返回码/宿主可测/资源放置判定都按"资源约束是设计输入"来做；扣分因下行单任务头阻塞、IDF 胶水段不可宿主测试、文档-代码漂移 |

### 3.3 必答(a)：两条链路在固件里的模块归属、分叉点、共享状态

**分叉点只有一个：帧类型字节。** 协议里没有显式方向位；方向由"类型白名单"隐式表达：
- 上行：`payload[0]=type ∈ {0x01,0x02,0x03,0x05,0x07,0x09,0x0B,0x0C,0x0F,0x11,0x13,0x16,0x17,0x19,0x1C,0x1D,0x1E,0x21,0x23}`，由 `msg_handler.c:54/185` 的发布面与 `manager.go:421-473` 的 switch 承接；
- 下行：`{0x04,0x06,0x08,0x0A,0x0D,0x0E,0x10,0x12,0x14,0x15,0x1A,0x1B,0x1F,0x22}`，由 `ehome_handle_downlink`（`app_callbacks.c:695`）→ `msg_handler_process` 的 case 承接。
- 两端的上行=采集（provider）、下行=执行（actuator）；**后端侧则是 `manager.HandleFrame`（上行摄入）与 `downlink.Bridge`（下行发送）两个包**，方向边界比固件更显式。

### 4.1 传输抽象的两层遗留（3.0 没有"替换掉" transport，而是"包了一层"）

- 现状：`msg_handler.c:15` 仍 `#include "transport.h"`，`publish_checked` 走 `transport_ops_t->send`（`msg_handler.c:54-116`）；3.0 的 `session` 通过 `main/session_transport.c` **适配回 transport_ops_t**（`session_transport.c:333-379`），再由 `transport_broadcast_ex` 调进 `link_send`。也就是说：**`transport_ops` 与 `link` 两套上行抽象同时存在**，P1 的七值结果在适配器边界被压回 `esp_err_t`（`stx_to_esp_err`，`session_transport.c:91-101`）。
- 代价：① `msg_handler` 层再次失去"该退避 vs 该报错"的分辨力（返回值最终被 void 调用方忽略，缺陷4）；② `transport_broadcast` 的"发全部已注册 transport"语义与"3.0 只有一条上行"的注释结论冲突（`msg_handler.c:105-114`）——**若 debug TCP 被注册（见下）就真的不止一条**；③ 组件数与心智负担：`transport` / `ehome_tcp` / `link` / `link_tcp` / `tls_link_adapt` / `link_rx_adapt` / `rx_pump` 七个组件描述两条链路。
- 这是**可理解的迁移中间态**（不破坏 2.x 回执路径），但它把"两套结果语义"留在了生产路径上；建议在 2.x 写响应迁到 V2/或旧 type 退役时一并删除 transport 抽象。

## 5. 架构评价

### 5.1 优点（带证据）

1. **接口把"决策信息"放进返回值，而不是让调用方再查一次**：`link_result_t` 七值（`link.h:24-40`）区分 PARTIAL/NOT_READY/BACKPRESSURE/TOO_BIG；`link_send` 显式 `progress` 出入参，附带 D-30 的"部分写出必须续写、重发整帧会静默污染 TCP 流"说明（`link.h:41-135`）。后端 `Session.Send` 对称实现了超时续写 + 硬失败关连接（`session.go:196-247`）——**同一缺陷类型两端都有防线**，这是本仓最成熟的设计手法。
2. **"字节流定界"从实现者脑子里搬到接口层**：`wire.h:127-186` 定界器只做定界不做重组（删除分片的依据与实测在头文件里），超上界"立即拒绝、不缓冲"；后端 `server.go:422-506` 有对应的"坏头逐字节重同步、尾字节未解析即报错"。
3. **单写者收敛**：`session_transport.c:177-206/240-258` 用 tx_lock 串行化成帧+写，理由列出两条真实机制（共享 scratch 覆盖、mbedTLS 写路径无锁）；后端 `session.go:104-109` 同样用 writeMu 并说明不加锁会插帧。
4. **两条业务链路在队列层解耦**：control queue 与 sample queue 分离且 sample 侧保留控制余量（`bus_manager.c:1295-1326`；`scheduler.c:751-758`）；命令回执在 report_tx 内严格优先（`bus_worker.c:808-821`）。
5. **幂等/原子性有可指认的实现**：ChannelCmdV2 槽位状态机（`handler_channel_cmd_v2.c:154-248`）+ plan 借用访问器（`:380-402`，把隐式 use-after-free 不变量变成显式校验）；device_op "ACK 先于重启、擦除失败不重启"（`device_op.h:1-50`）。
6. **资源约束被当作设计输入**：`variant_caps`/placement 判定（`device_link_wiring.c:147/1320-1340`，放不下就**可见地拒绝启动**而非悄悄缩小）；PSRAM 放置与 `delim_buf` 外置（`wire.h:150-165`）；`mem_budget.json` 六 profile 门禁 + 假绿修复记录（`:44-46`）；默认 payload 4096、链路 MTU 8192。
7. **弱符号/隐式单例被系统性收敛**：`msg_handler_hooks.h:1-40` 把 9 个"弱默认=静默无操作"钩子改为普通 extern（漏实现=链接错误）；D-06 的 weak DataBatch 编码器已改成 `main.c:675` 显式注入；D-14 用 `report_stats` 破 `msg_handler ↔ bus_worker` 环（`main.c:677-695`）。
8. **可测试性（本轮已实测）**：`host_tests/` 84 个 C 文件 / 28,624 行，`CMakeLists.txt` 78 个可执行目标；用仓库自带 cmake 在 **Debug** 下全量构建成功，`ctest` **96/99 通过**（总耗时 453.81 s），核心层（link/wire/msgcodec/dispatch/session/rx_pump/link_tcp/device_op/config_apply_transaction/bus_worker）用例均可跑。3 个红例**不是生产缺陷**而是测试 fixture 未随 2026-10-15 的"commands 指针化"同步（§5.2 缺陷13 / §6 #16）——这反而证明该套件确实在测东西，只要有人跑它。
9. **"反假绿"门禁已成体系**：`protocol/vectors/frame_header.txt` 与 `wire_primitives.txt` 是两端共享向量（`pkg/protoframe/frame.go:23-28` 直接读它）；`host_tests/golden_vectors_tests.c`、`device_op_shared_vectors_tests.c`、`diag_heap_metric_scan.py`、`mutation_proof_defect2.py`、`mutation_proof_transport_registry.py` 把"判据会红"变成可复跑资产；`tools/check_message_types.py` 按固件 `frame_codec.h` 扫两端消息号（`device_op.h:41` 引）。这类门禁在本仓是评分加分项，而不是可有可无的脚本。

### 5.2 缺陷（严重度降序；每条给"影响面 + 可证伪判据"）

**缺陷1｜seq/flags/ACK/CRC 是"写在规范里、没在实现里"的字段（两端一致地缺）｜严重度：高（协议诚实性）**
- 事实：`wire.h:20-30` 声称 `seq` 是"每方向单调递增（重放检测 + ACK 关联）"；但固件两处成帧都硬编码 **seq=0、flags=0**：`session_transport.c:257` `stx_send_frame(&tx, data, len, 0)`；`device_link_wiring.c:1070-1073` `devlink_encode_frame(..., /* seq */ 0u, ...)`（`:1058-1063` 注释自陈 flags=0 不置 CRC 位）。后端下行同样 `downlink.go:125` `Seq: 0, // per-node sequencing is not implemented yet`；接收侧 `server.go`/`manager.go` 只读 header.Type，从不校验 seq/flags；固件 `devlink_on_msg` 只打印 `m->seq`（`device_link_wiring.c:609`）。
- 影响：① 重连后无法检测丢失/重复帧（当前唯一幂等靠 ChannelCmdV2 的 command_id+boot_id；legacy 0x06 无幂等）；② ACK_REQ/IS_ACK/NAK 三条 flag 无任何消费者，"请求确认"能力不存在；③ CRC 不启用 ⇒ 传输错误只能靠 TLS 记录层，应用层无校验和（TLS 下可接受，但"flags 位存在"会被误读为可用）。
- 可证伪：`grep -rn "seq" esp32-collector/main/*.c backend/internal/nodemgr/manager.go` 若发现真实递增/校验即推翻；或让固件在 `:1072` 传非 0 seq 后跑 `host_tests/frame_header_tests` / golden vector 观察是否有用例失败。

**缺陷2｜"一条消息恰好一个 TLS 记录"的 MTU 论证已过期，且上界在四处各写一份｜严重度：中高（契约漂移，历史事故同族）**
- 事实：`wire.h:66-76` 仍写"16368 = IN_CONTENT_LEN(16384)−12−4"、`WIRE_PAYLOAD_MAX=16368`；但 `link_tcp.h:52-53` `LINK_TCP_MTU_BYTES 8192`、后端 `protoframe/frame.go:58-61` `MaxFrameBytes=8192/PayloadMax=8176`；`sdkconfig.defaults:214` `MBEDTLS_SSL_IN_CONTENT_LEN=8192` 而**已提交的 `sdkconfig:3007` 仍是 16384**；Kconfig `MAX_PAYLOAD` `range 256 8176`（`main/Kconfig.projbuild:194-210`）但 help 文案仍写 "Ceiling 16368 comes from WIRE_PAYLOAD_MAX"。
- 影响：① 若按 `sdkconfig`（16384）构建而 MTU 报 8192，只是"记录比帧大"，不会坏；但若有人把 `MAX_PAYLOAD` 配回 16368 侧（旧 range 允许），会出现"帧跨记录、后端按 8176 拒收"——正是 Kconfig 注释要防的"配置项说谎"；② 三个数字谁是真源不清，违反 P5/P4；③ `wire.h` 的核心论证（单记录）在当前默认构建下**不成立**（16384≠8192 的配置事实），文档可信度受损。
- 可证伪：三处常量应互为派生关系（如 `WIRE_PAYLOAD_MAX = LINK_TCP_MTU_BYTES - 16`），用一条脚本断言 `wire.h == link_tcp.h == protoframe == sdkconfig.defaults`；跑 `host_tests/frame_header_tests` + 后端 `pkg/protoframe` golden vector 对照即可暴露。

**缺陷3｜下行是单任务串行，且"重活"（ConfigManifest 事务）与命令分发在同一条 6144 B 栈上｜严重度：中高（命令延迟/过期与栈风险）**
- 事实：`device_link_wiring.c:602-605` `devlink_downlink_dispatch → ehome_handle_downlink`，`:693` 与 `app_callbacks.c:693-694` 都注明"本函数做**配置事务**（较重），跑在 devlink 任务栈 6144 B"；`DEVLINK_TASK_STACK 6144`（`:525`）依据的是**握手峰值 4168 B**（`:470-495`），**未含配置事务峰值**（`app_callbacks.c:693-694` 自陈"决策文档 §4 判据 3 要求实测其栈影响"）。下行命令的 admission 在 `handler_channel_cmd_v2.c:325-331` 检查 `deadline_unix_ms`；若 manifest 事务正在该任务里跑，后续 V2 命令只能排队等到事务结束——排队时间不被 deadline 考虑之前就已消耗。
- 影响：① manifest 下发（配置变更/OTA 后恢复）期间，自动化命令/设备运维可能被延迟到超过后端 deadline，被设备以 `V2_ERR_EXPIRED` 拒绝——表现为"刚改完配置，自动化偶发不执行"；② 若配置事务峰值确实超过 6144−余量，栈溢出会以 panic 形式出现（`main.c:118-134` 记录过 status_task 6144 溢出史）。
- 可证伪：在 EHOME_MEM_DIAG 构建下由后端连续下发 Manifest 与 V2 命令，读 `uxTaskGetStackHighWaterMark(dev_link)` 与 V2 拒绝码；或把"配置应用"移出 devlink 任务（专用任务）后对比 V2 `EXPIRED` 计数。若实测峰值 < 5000 且 EXPIRED=0，本缺陷降级。

**缺陷4｜上行发布失败在消息层被静默吞掉，断链期遥测丢帧无账可查｜严重度：中（P3 违反）**
- 事实：`msg_handler.c:54-116` `publish_checked` 有返回值，但 3.0 唯一上行链路上层多为 `void`：`msg_handler_send_data_report`（`handler_data.c:327`）直接调 `msg_handler_publish`（`msg_handler.c:118-121` 丢掉返回值）、`msg_handler_send_data_batch` 的 false 只在 bus_worker 决定退回逐样本（`bus_worker.c:859-863`）；`session_transport.c:257-273` 失败只 `ESP_LOGW`，tx 统计（`stx_tx_t.stats`）是**局部变量**、不进入任何上报帧。断链（LINK_NOT_READY）时 `report_task` 仍从队列取走样本并调用回调 ⇒ 样本**被丢弃且不计入 `report_stats_note_drop()`**（该计数只覆盖队列满/池耗尽，`bus_worker.c:957-989`）。
- 影响：seq=0（缺陷1）使后端也无法通过序号缺口发现丢失；运维只能看到"数据变少"，不能归因"链路抖 vs 设备采不到"。
- 可证伪：`grep -n "stx_tx_t.stats\|tx_sent_full\|link_get_stats" esp32-collector/main/*.c` 若发现把 stats 读进 StatusReport 即证伪；或断网 30 s 后对比设备侧 `report_drop` 与后端 databus 增量，差值大于 0 即证实静默丢弃。

**缺陷5｜legacy WriteCmd(0x06) 没有幂等，而后端有重试 ⇒ 存在重复物理写入风险｜严重度：中**
- 事实：固件 `bus_manager_on_write_cmd`（`bus_manager.c:1260-1326`）只校验参数并投 control queue，**不记录/比较 request_id**；后端 `pendingwrite.SendWriteCommand` 先发布再等超时（`pendingwrite.go:94-165`），并有 `RetryFailed(maxRetries)`（`:272`）重发同一帧。重发时固件会把同一字节序列**再写一次总线**（对 BMS/逆变器这类"写寄存器/写参数"命令可能改变状态）。
- 影响：写命令是自动化域执行器的低层能力，重复写可能造成参数抖动/倍率错误；当前自动化主链已迁到 ChannelCmdV2（有 command_id 幂等），但 0x06 仍由 `pendingwrite` 与通道调试路径在用（`routes.go` 未逐一核）。
- 可证伪：`grep -n "request_id" esp32-collector/components/bus_manager/bus_manager.c` 若出现"已见 request_id 集合/去重"即推翻；或后端注入 `RetryFailed` 后观察总线抓包出现两次相同 TX。

**缺陷6｜"两套编解码"并存：`msgcodec`（新）与 `frame_codec`（生产）语义相同、实现不同｜严重度：中低（长期腐化风险）**

### 5.3 架构是否"优秀与完善"的总判断（可直接引用给 Lead）

- **优秀的部分**：协议分层（wire/frame/msg）、单写者、返回码语义、幂等槽位、资源放置判定、弱符号清除——这些是本仓反复用真实事故换来的，且都带"为什么"注释与可证伪判据，质量高于一般嵌入式固件。
- **不完善的部分**（按对业务影响排序）：① 断链丢帧无账（缺陷4）+ seq 未实现（缺陷1）使"数据完整性"无法自证；② 下行单任务 + 配置事务头阻塞（缺陷3）影响"改完配置就执行"的自动化体验；③ 上界常量漂移（缺陷2）是下一次"配置对、跑不通"事故的温床；④ legacy 写命令幂等（缺陷5）与扫描死功能（缺陷7）是功能完善度缺口。
- **资源约束视角**：设计没有用服务器思维（没有"加线程/加内存"），而是用"放置判定 + 可见失败 + 门禁"处理 S3/S3P/C6 差异；默认 4096 payload、7 个任务每 4096 B 栈、TLS IN 8192 都是实测倒逼的取舍（`main.c:710-724` 记录顺序敏感与 largest 塌陷）。这一层**按约束打分应给 7.5–8/10**；扣分全部来自"没有把已实测的数字固化成单一推导源"。
