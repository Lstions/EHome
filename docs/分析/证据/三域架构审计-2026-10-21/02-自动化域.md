## 1. 一句话结论与评分

**一句话**：自动化引擎的"评估→编排→受控执行"分层是本仓最成熟的一块——触发模型边界清晰、动作执行唯一入口收口到 `commandexec.Create`、风险判定单一事实源、幂等/审计/冷却锚点设计可辩护；但它只把"动作**提交**"做成状态机，没有把"动作**生效**"接回规则级语义，因此"多动作失败中止剩余""partial_failure""前端可感知"三条关键闭环在**物理执行层是断的**，且 2 个新 WS 事件名在前后端之间没有生产者（前端订阅/测试全绿但线上永不触发）。

| 维度 | 分 | 一句话理由（可复核锚点） |
|---|---|---|
| 功能定义 | **8/10** | 4 类触发、多动作、确认制、风险授权、日熔断/冷却、手动触发均有代码落点且注释给出裁决依据；扣分在 `event` 触发器可存不可跑、`actions[].enabled` 是死字段、precheck 端点被裁决取消但前端仍调用。 |
| 数据流转 | **7/10** | 逐跳可追踪且幂等键含 `trigger_seq`+`action_seq` 修复了 P1-A；扣分在执行结果不回写规则事件（`executed` 永久=已受理）、WS 新事件无生产者、databus sink 同步阻塞且无 recover。 |
| 接口依赖 | **6/10** | 窄接口注入（`automationEvaluator/Planner/Trigger/Catalog`、`notify.Notifier`、`downlink.Publisher`）方向干净；扣分在 3 处前后端契约漂移（precheck 404、`automation_confirmation_required`/`automation_partial_failure` 无生产、`enabled` 写入无消费者）与 periph 动作在规则校验侧不可达。 |
| 架构设计 | **8/10** | 风险 2 级单一事实源（`RiskLevel.RequiresConfirmation`）、冷却锚点与事件表物理解耦、Catalog/Create 门禁同源（F4）、确认令牌即铸即销均可作为同类系统范本；扣分在"规则状态机 vs 命令状态机"两套状态未缝合、冷却态内存/锚点双写、多动作不隔离。 |

**最值得 Lead 直接引用的 5 条判据**：
1. 多动作"失败中止剩余"只在**入队失败**成立；设备侧失败（final_failed / UNKNOWN / 读回不一致）不会中止剩余动作，也不会落 `partial_failure`（planner.go:324-362，测试 planner_multi_action_test.go:426-451 用 `no_such_action` 造的是入队失败）。
2. 前端订阅的 `automation_confirmation_required` / `automation_partial_failure` 在 backend **0 生产者**（`grep -rn` 两串均 0）；planner 只用 `automation_event` 广播，而该事件名前端 0 订阅 —— C5"前端无感知"并未真正消除。
3. `automation_events.result=executed` 的语义是"已提交 commandexec（queued）"，命令后续 FAILED/UNKNOWN 不会回写规则事件（接口设计 §2.3 自述；全仓无 command→automation 回写点）。
4. 方案 D-prime（队列元素只带 `control_slot`、worker 用 `borrow_plan` 借）**已落地**（commit `5edb8bc0`）：`bus_cmd_t` 与 `sample_cmd_t` 同尺寸 180B(target)/192B(host)，`plan_data[512]` 已删除，控制槽访问器带 QUEUED/COMPLETING 状态守卫（cmd_queue.h:109-151；handler_channel_cmd_v2.c:380-405）。
5. 冷却态存在"内存 triggered vs 持久锚点"双写分裂：部分失败后自动路径仍被内存冷却压住，手动路径（读锚点）可立即重试，重启后又都可重试 —— 同一配置三种行为（evaluator.go:817-845 vs planner.go:900-920）。

### 2.3 现状尺寸与队列内存（把"若未落地"的风险量化，供对照）
- 改建前：`bus_cmd_t=700B`（内联 `plan_data[512]+plan_len+plan_step_count`，见 `5edb8bc0^:cmd_queue.h:114-117` 与 commit message "3 个 control 队列共 ~16.8 KiB 堆"）。
- ⚠ 注释漂移（Lead 交叉确认 + 本次复核）：`esp32-collector/main/app_state.c:177-186` 仍写 "The CONTROL queues keep the full bus_cmd_t (700 B)"，但 D-prime 后 `bus_cmd_t` 已与 `sample_cmd_t` 同尺寸（cmd_queue.h:148-151 的 `_Static_assert`），control 队列实际按 180B 分配 —— **注释过期，代码正确**，属 D-8 类文档债。
- 现状：元素 180B(target)；control 队列 3 条 UART × depth 8（`esp32-collector/main/app_state.c:193-195`）= 24 × 180 = **4,320 B**，改建前 24 × 700 = **16,800 B** ⇒ 省 **12,480 B（≈12.2 KiB）**；sample 队列另用 `sizeof(sample_cmd_t)`(:183-187)，同尺寸。
- 结论：**"记录（plan）只有一份、队列元素只带句柄（control_slot）"这一记录/缓存分离已经在固件落地**；队列内存风险不再是 700B×24 的形态。

### 2.4 残余风险（不推翻结论）
1. 真机验证未闭环：方案 §12.1 状态表 P9"真机验证 ⏳ 进行中"，P7/P8（host 99/99 绿、三型号构建 PASS）为文档声明（D）。**本次未跑固件 host tests**，故"函数级行为"只有 C，没有 T。
2. 借用约束是**同任务串行**的运行时约定，非编译期保证：若将来把"发布 FINAL"移出同一任务，状态守卫会报错拒绝（比裸指针 UAF 好），但错误路径是"命令执行失败"而非"编译失败"。
3. `plan_data` 仍存在于 msg_handler 槽位（`handler_channel_cmd_v2.c` 的 `v2_control_slot_t.cmd`），只是不再进队列；"记录"与"缓存"的边界是**每节点 MAX_CHANNELS 个槽位**（msg_handler_internal.h:251；方案按 5 槽记），不是全局单例 —— 分析时不要误读为"plan 全局只有一份"。

## 3. 必查项 B：「已生效但未验证」状态 + 重试/补偿语义

### 3.1 设备指令状态机（C）：确有"已生效但未验证"
`backend/internal/commandexec/state.go:6-13` 定义 8 态：`QUEUED → DISPATCHED → DEVICE_ACCEPTED → VERIFYING → SUCCEEDED/FAILED`，另有 `UNKNOWN/CANCELLED`。迁移表（:24-37）中 `VERIFYING` 只允许去 `SUCCEEDED/FAILED/UNKNOWN`。

| 状态 | 物理语义 | 证据 |
|---|---|---|
| `VERIFYING` | 设备已受理、正在读回校核（写动作`Verification=readback`） | inbox.go:70-71 `"verifying"`→`StatusVerifying`；通道响应处理器 nodemgr/handler_channel_cmd_v2.go:47-64 |
| `UNKNOWN` | **可能已生效但无终局证据**：已发布且过 deadline 无 FINAL，或设备显式 unknown | inbox.go:298-325 `RecoverExpired`：`DISPATCHED/DEVICE_ACCEPTED/VERIFYING` 超 deadline → `UNKNOWN` + reason "deadline expired without final evidence"；:76-77 `"unknown"` 事件 |
| `FAILED`（读回不一致） | **可能已生效但被判失败**：写已下发、读回不匹配 → VerifyFinal 失败→final_failed | handler_channel_cmd_v2.go:54-62；service.go:603-621 `VerifyFinal` 用冻结动作版本+driver verifier |

**"已生效但未验证"的判定结论**：存在，且是**命令域**的合法终态/中间态（`VERIFYING`/`UNKNOWN`），不是缺陷；`UNKNOWN` 只能由人工结论收尾（`Service.ResolveUnknown`，service.go:632-689，追加 `CommandManualResolution` 且不改写物理结果，`ErrAlreadyResolved` 防二次结论）。

### 3.2 但"已生效但未验证"**没有向上传播**——规则级审计会失真
- `automation_events.result=executed` 在 `commandexec.Create` 返回后立即写入（planner.go:386-388 → 452-494），Create 的同步边界只到 `command_executions(QUEUED)+command_outbox(PENDING)`（service.go:560-573）。
- 全仓对 `automation_events` 的 UPDATE 只有确认制路径（pending→executed/failed/partial，planner.go:1170-1185/1264-1270）与 24h 过期清扫（:1298-1313）。**没有任何代码在命令终态时回写规则事件**（搜索：`grep -rn 'AutomationEvent{}' backend/internal backend/cmd | grep -v _test`，仅 evaluator/planner 的写入点，无订阅命令终态的消费者）。
- 前端展示边界（精确化）：规则页**不**在事件行/列表中展示命令终态，也不自动刷新；但提供了就地查询回链 —— 点 `command_id` 打开只读弹窗，`goCommand` 调 `GET /api/v1/device-operations/:command_id` 并映射终态中文（含 `VERIFYING→核验中`、`UNKNOWN→结果未知`、`FAILED→失败` + `final_reason`）（AutomationRules.vue:1505-1560/650-690）。
- 产品后果：终态**可查但不自明** —— 用户必须在每条事件上手点一次才知道设备到底有没有动；无人值守/批量规则下等于不可运营，且 `UNKNOWN`（可能已生效）不会在规则维度提示人工处置。
- 设计文档自己也承认 `executed = 已受理（queued）非物理执行`（`docs/设计/自动化策略引擎接口设计.md` §2.3 对账段），但这只是**文档级免责**，没有代码闭环。

### 3.3 PARTIAL_FAILED 是否仍 0 命中？——**大写 0 命中；等价能力用 `partial_failure` 实现在规则层**
- `grep -rn PARTIAL_FAILED backend --include=*.go | wc -l` = **0**（13:10）。
- 全仓大写形态只在 docs：`docs/archive/边缘设备控制架构设计.md:1005/1369/2114/2512`、`docs/archive/v4.0-重建前归档/设计/边缘设备控制与Driver注册统一方案.md:928/1437`（6 处，均为归档，不代表实现）。
- 现行等价物：`models.AutomationResultPartialFailure = "partial_failure"`（models/automation.go:72），落点 `recordActionFailure`（planner.go:400-429，`executed>0` 时改码并写 `action_seq`）、`recordManualActionFailure`（:1075-1100）、`recordConfirmFailure`（:1255-1278）。
- 命令域**没有** partial 状态：一条 `CommandExecution` 要么成功/失败/未知，多动作的"部分"只在规则层聚合。因此"设备已被改了一半"的事实只能从**事件行 + 多条 command_executions**推断，没有原子事务记录。

### 3.4 重试/补偿语义（逐层）
| 层 | 有重试吗 | 证据 | 语义 |
|---|---|---|---|
| 发布（outbox→transport） | **有**，且是 at-least-once | dispatcher.go:139-149 租约 30s；失败不标 PROCESSED，租约过期回 PENDING 重投（:85-89），wire digest 稳定不含 fencing（:303-308） | 同一物理命令可能重复到达；设备侧按 command_id+BootID+digest 去重（nodemgr/handler_channel_cmd_v2.go:42-45 身份校验） |

### 4.5 触发模型语义与边界（必答 a：边沿/电平、recheck、冷却锚点、去重）

| 触发类型 | 触发语义 | 状态/边沿 | 冷却与去重 | 证据 |

## 5. 数据流转（逐跳 + 失败/背压点）

```
ESP32 采集(UART/SPI) → 3.0 mTLS 上行 → nodemgr.HandleFrame → databus 解析
  → SensorParserConsumer.consume（consumers_heavy.go:341-409）
      ├─ 落 unified_data
      ├─ latestSink（最新值缓存）
      ├─ alertSink
      └─ automationSink(device.ID, sensorData, now)   ← :407-408
           → automation.Evaluator.Evaluate(:740) → evalRule(:795)
                → armed→triggered → Planner.HandleTrigger(:122)
                     → 日熔断(:130) → require_confirmed(:147) → F4 复核(:162)
                     → executeActions(:295) → commandexec.Service.Create(:481)
                          → 目录/Canonicalize/幂等预查/门禁谓词集(通道域 12 项)/确认门
                          → 同事务写 command_executions(QUEUED) + command_outboxes(PENDING) + audit
           → dispatcher.ProcessOnce(:76，1s tick，main.go:597)
                → 租约 outbox + channel 行锁 + 建 CommandAttempt
                → ChannelCmdV2Transport.dispatch(:117)
                     → 冻结动作版本/能力新鲜度/执行形状
                     → single: CompileForAddress；bounded_sequence: CompilePlanForAddress → frame.Plan[]
                     → downlink.Bridge.Publish(:83) → transport.SendToNode（无会话=错误，MQTT 已移除）
           → ESP32 msg_handler 槽位 → bus_worker 借 plan → 逐步 UART → FINAL/ACK 上行
                → nodemgr.handleChannelCmdV2Response(:24) → VerifyFinal(:603)
                     → RecordInbox → SUCCEEDED/FAILED/UNKNOWN
```

关键映射与失败点：
1. **plan step ≠ 自动化动作**：自动化 1 个动作 = 1 条 `CommandExecution` = 1 个 ChannelCmdV2 信封；设备执行形状为 `bounded_sequence` 时，一个信封内才含多个 `frame.ChannelCmdV2Step`（channel_cmd_v2_transport.go:174-206）。多动作规则（N 个动作）= N 条命令、N 个信封。**两者不要混为一谈**。
2. **背压点 1（同步入摄取路径）**：`automationSink` 在解析 consumer 的事件处理函数里**同步**调用（consumers_heavy.go:405-409），Planner 内部会做多次 SQL（`ruleActions`、`nextTriggerSeq`、`Create` 事务、事件写入），最坏把一次上报处理拉长到数个 DB RTT；同批 `sourceHealthSink` 有 `recover` 包裹（:412-420），alert/automation sink **未见 recover**（:400-409）——panic 将沿 consumer 协程上抛，是否能被上层拦截取决于 consumer 框架，本次未验证。
3. **背压点 2（1s 单条调度）**：`runCommandDispatcher` 每 tick 只 `ProcessOnce` 一条（main.go:597-620），全系统吞吐上限约 1 命令/秒；多动作规则会放大占用。
4. **背压点 3（无会话即失败）**：MQTT 移除后 `downlink.Publish` 无会话直接返回 error（downlink.go:56-105），dispatcher 记录"dispatch rejected"原因、租约到期重试至 deadline（dispatcher.go:156-185, 243-264）。
5. **无上行反馈闭环**：设备终态只更新 `command_executions/command_attempts`，不回写 `automation_events`；规则层与命令层是两条只读 JOIN 关系，不是状态同步关系（§3.2）。

### 7.2 缺陷（含影响面与可证伪判据）

**D-1（高）多动作"失败中止剩余"只覆盖入队失败，物理失败不中止、不落 partial_failure，也不等前序完成**
- **原子性边界（与 Lead 判断一致，已核实）**：原子性只到**单条命令内的 bounded plan**（`bounded_sequence` 的多 step 被 worker 在一次函数调用里跑完，见 cmd_queue.h:119-130 的 `execute_uart_batch` 论证）；**跨动作（跨 CommandExecution/信封）不原子、也不隔离**。
- 现象：`executeActions` 对每个动作只做 `Create`（同步到 outbox PENDING 为止）并立即进入下一个；`Create` 返回后设备侧失败（final_failed/UNKNOWN/读回不一致）不会回到 planner。
- 证据：planner.go:324-362（循环内只判 `err`）+ 方案 §3.2.4 "任一动作完成后才开始下一个"（D）vs service.go:560-573（Create 只落 QUEUED+outbox）；唯一"部分失败"测试用 `no_such_action` 造**入队**失败（planner_multi_action_test.go:426-451）。
- 影响：2 动作规则"关充电 MOS 成功、关放电 MOS 设备侧失败"时，第 3 个动作仍会被提交；规则事件=executed；"设备已被改了一半"没有任何自动信号。
- 可证伪判据：构造 2 动作规则，把动作 1 的目标动作设为 readback 必不一致（或用仿真让设备回 final_failed），观察动作 2 是否仍产生 command_executions 且事件 result=executed —— 若出现 partial_failure/动作 2 未提交，则本缺陷不成立。

**D-2（高）C5 的"前端可感知"闭环未闭合：2 个新 WS 事件名无生产者**
- 现象：方案 §3.2.5 第 3 步/§4.3 要求新增并广播 `automation_confirmation_required`/`automation_partial_failure`；实现只在 `automation_event` 载荷里带 result（planner.go:639-656），而前端只订阅新名字（AutomationRules.vue:1764-1770）。
- 证据：`grep -rn automation_confirmation_required backend | wc -l` = **0**；`automation_partial_failure` = **0**（13:09）；前端 F-9 单测对 mock WS 断言"订阅存在"（AutomationRules.spec.ts:1160-1185），60/60 通过（T）→ 典型"测试绿但契约无生产"。
- 影响：自动路径被确认门拦住时，用户不会收到实时提示（只能事后翻事件表）；多动作部分失败同理。
- 可证伪判据：见 §3.2；或在真实 WS 上触发一条未授权风险动作规则，抓 WS 帧 —— 若收到 `automation_confirmation_required` 则本缺陷不成立。

**D-3（高）规则结果与命令结果未缝合："executed"是已受理而非已生效**
- 现象：`executed` 在 Create 返回即写，命令后续 FAILED/UNKNOWN 不回写；自动化页只能通过 command_id 手工跳转核对。
- 证据：planner.go:386-388/452-494；接口设计 §2.3 自述；无命令终态→automation 的消费者（§3.2 搜索结论）。
- 影响：无人值守价值主张（"设备真的按规则动作了"）无法从规则审计证明；UNKNOWN（可能已生效）在规则维度不可见。
- 可证伪判据：把一条 command_execution 人为置 FAILED/UNKNOWN 后查 automation_events —— 若 result 被更新则本缺陷不成立。

**D-4（中）冷却态双写分裂：内存 triggered 与持久锚点在不同层、不同时机写入**
- 现象：evaluator 在触发瞬间写内存 `triggered[rule]=at`（evaluator.go:840-845），planner 仅"全部动作成功"才写锚点（recordExecuted，partial failure 明确不写）。部分失败后：自动路径被内存冷却压住 → 落 suppressed_cooldown；手动路径读锚点（为空）→ 允许立即重试；进程重启后内存清空 → 自动路径也可重试。同一配置三种行为。
- 证据：evaluator.go:817-845；planner.go:900-920/961-974；方案 §3.2.4「部分失败的锚点」（D：声称"用户可在窗口内重试恢复"）。
- 影响：P2-C 裁决的可恢复性只在手动路径成立；自动路径在冷却窗内静默抑制（有审计但无提示）。
- 可证伪判据：造 2 动作规则使动作 2 入队失败（partial_failure）→ 条件仍满足时让 evaluator 再触发：若自动路径未被抑制（无 suppressed_cooldown 行）则缺陷不成立；再对比手动触发是否允许。

**D-5（中）前端依赖未实现的 precheck 端点：每次保存发起 1 个 404 请求**
- 现象：`onSave` 先 `precheckRule`（AutomationRules.vue:1311-1316），后端无路由；方案 §4.1.2 明确"未实现——2026-10-14 裁决取消"（:452）。
- 证据：backend `grep -i precheck --include=*.go` 仅 `systemActorPrecheckID`（main.go:322-360）；前端 automation.ts:341-347。
- 影响：每次保存多一跳失败请求与一条 catch 日志；风险清单依赖"动作目录降级"（前端已诚实实现 fail-closed 降级与测试，故不是安全漏洞，但是接口债与可观测噪声）。
- 可证伪判据：`curl -X POST /api/v1/automation-rules/precheck` → 404；若返回 200 则本缺陷不成立。

**D-6（中）`actions[].enabled` 是"写而不读"的死字段；periph 动作在规则校验侧不可达**
- 现象 1：模型/API 持久化 `enabled`，planner/evaluator 无任何读取（`grep 'act.Enabled' internal/automation` = 0，13:10）；前端类型也定义（automation.ts:220-225）但不提交（actionList.ts SequencedAction 无 enabled）。禁用动作仍会执行。
- 现象 2：`validateDeviceActionCatalog`→`commandexec.Catalog` 只查 `edge_devices`（service.go:382-386），而 `Create` 对 periph 动作把 `EdgeDeviceID` 解释为 `nodes.id`（service.go:327-340）。故含 `gpio_set/pwm_set_duty` 的规则在保存时 Catalog 失败 → 400；同一动作手工路径却可执行。
- 影响：产品语义不一致（UI/API 暴露的开关无效；periph 自动化不可配）；潜在"用户以为禁用了"的物理风险。
- 可证伪判据：① HTTP 提交 `actions:[{seq:1,enabled:false,action_id:"gpio_set"...},{seq:2,...}]` 后触发规则，若动作 1 未执行则本缺陷不成立；② POST 含 `gpio_set` + 节点 ID 的规则，若 201 则现象 2 不成立。

**D-7（中）"串行"不含隔离：多动作提交之间可插入其他命令**
- 现象：多动作是 N 次独立 `Create`（各自事务/各自 outbox），dispatcher 只按 outbox id 全局 FIFO + 单条/秒；两条动作的提交间隙里，用户/其他规则的命令可插入其 outbox 序号之间，设备侧执行顺序=outbox 顺序，规则内动作不再连续。
- 证据：planner.go:324-362（逐个 Create）；dispatcher.go:90-103（按 outbox.id 选单条）；main.go:597-620（1s 一条）。
- 影响：BMS 类"关充电→关放电"序列可能被无关命令打断；文档"同一 Channel 串行"只保证不并发，不保证不交错。
- 可证伪判据：规则 2 动作 + 在两动作之间插入一条用户命令（或在第一动作 Create 后阻塞），抓 command_executions.created_at/outbox id 序列 —— 若用户命令落在两动作之间即成立。
