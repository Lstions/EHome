# 数据源自动纳入 —— 只读可行性验证记录（2026-10-21）

> **状态**: 提案（证据留档）
> **日期**: 2026-10-21
> **关联**: [需求分析-数据源自动纳入-2026-10-21](../需求分析-数据源自动纳入-2026-10-21.md) | [架构审计台账](../架构审计-数据源与自动化与边缘设备-缺陷与改进台账-2026-10-21.md)

## 1. 目的

在动手写代码前，用**只读查询**回答三个问题：
1. "自动纳入"如果今天上线，会在 `data_sources` 里创建多少行？
2. 提供者列到底该用哪一个（`device_id` 还是 `edge_device_id`）？
3. 现有数据能不能撑起"在线且有数据"这个判据？

**所有命令只读，未修改任何数据，未启停容器。** 采集时刻 2026-10-21 18:05–18:20 (+08:00)。

## 2. 结论摘要

| 问题 | 结论 | 关键证据 |
|---|---|---|
| 会创建多少行 | **13 行**（当前 2 台设备）；BMS 开启单体电压命令后单台可达 ~39 行 | §3.1 |
| 提供者列 | **必须用 `device_id`**；`edge_device_id` 全表为 NULL | §3.2 |
| "有数据"判据 | **可支撑**，但数据已停更 20 天 ⇒ 时间窗必须可配 | §3.3 |

## 3. 证据

### 3.1 规模（分母：生产库 `ehome`，2026-10-21）

```bash
docker exec ehome-postgres psql -U ehome -d ehome -Atc \
  "SELECT count(*) FROM (SELECT DISTINCT logical_device_id, sensor_name, device_id FROM unified_data) t"
# → 13
```

按逻辑设备拆分：

| logical_device_id | 设备 | 类别数 | 明细 |
|---:|---|---:|---|
| 1 | sn3001_rain（雨量） | 1 | `rainfall`（326 行数据） |
| 2 | jiabaida_bms | 12 | `total_voltage / current / rsoc / remaining_capacity / nominal_capacity / cycle_count / protection_status / fet_status / cell_count / software_version / temperature_1 / temperature_2`（各 326 行） |

**推算上限**（代码路径 `jiabaida_parse.go:296-315`、`:386-395`）：启用 0x04/0x0F 单体电压命令后，追加 `cell_voltage_1..16` + `cell_voltage_max/min/avg` + `cell_resistance_1..8` ⇒ 单台 BMS **≈ 39 行**。

**结论**：字段级（方案 A）在"2 台设备"规模下完全可接受（13 行），但一旦接入 3–5 台 BMS 就会到 100–200 行 —— 这正是为什么推荐 **方案 C（混合：索引类字段归并）**。

### 3.2 提供者列：`edge_device_id` 全表为空（新发现的缺陷）

```bash
docker exec ehome-postgres psql -U ehome -d ehome -Atc \
  "SELECT count(*) FILTER (WHERE edge_device_id IS NULL) AS null_rows, count(*) AS total FROM unified_data"
# → 179532 | 179532      （100% 为空）

docker exec ehome-postgres psql -U ehome -d ehome -Atc \
  "SELECT count(DISTINCT device_id) FROM unified_data"
# → 2                     （= edge_devices.id 的数量，语义正确）
```

抽样（按时间倒序 5 行）：

```
   id   | device_id | edge_device_id | logical_device_id | sensor_name
--------+-----------+----------------+-------------------+-------------
 179532 |         1 |                |                 1 | rainfall
 179531 |         1 |                |                 1 | rainfall
```

**根因（C 级）**：写入点 `internal/databus/consumers_heavy.go:373-380`

```go
records = append(records, models.UnifiedData{
    DeviceID:        device.ID,          // ← 实际承载血缘
    LogicalDeviceID: logicalTarget,
    SensorName:      sd.Name,
    Value:           sd.Value,
    Unit:            sd.Unit,
    Timestamp:       now,
})                                        // ← 没有 EdgeDeviceID 字段
```

而 `models.UnifiedData.DeviceID` 的注释写着 `// v2.2: 改为 EdgeDeviceID`，另外 5 处设计文档（总体设计.md:72、概念模型.md:50、术语表.md:74、数据采集与数据链路.md:35、数据源主备与故障转移.md:28）都称 `edge_device_id` 是血缘列。

**连带影响**：`internal/datalifecycle/purge.go:246` 的 `Where("edge_device_id IN ?", scope.InstanceIDs)` 也恒命中 0 行（calibration_cache 清理从未真正生效）。这条未被本次审计的其他域发现，已登记为台账 **DS-14**。

### 3.3 "在线且有数据"判据能否成立

```bash
docker exec ehome-postgres psql -U ehome -d ehome -Atc \
  "SELECT min(timestamp), max(timestamp), now() FROM unified_data"
# → 2026-09-20 08:18 | 2026-10-01 06:56 | 2026-10-21 10:05   （数据停更 20 天）
```

- 设备侧判据（`EdgeDevice.Status`/`LastDataAt`）是**权威且现成**的：首个成功数据帧把 `pending → active` 并写 `last_data_at`（consumers_heavy.go:443-460）。
- 但**数据本身已停更 20 天**，所以任何"近 7 天有数据"的清单在本机会返回 **0 行**。

**教训（证据纪律）**：空结果既可能是"功能没生效"，也可能是"窗口内确实没有数据"。因此 B1 必须做到：
1. 时间窗参数可配（默认 **30 天**，而非 7 天）；
2. 空态文案区分 **"近 N 天无数据"** 与 **"无来源"**；
3. 集成测试用**有分辨力的输入**（一台在窗口内、一台在窗口外），避免"空库上跑清理器"式假绿。

## 4. 只读 SQL（可直接用于 B1 的 catalog 实现）

```sql
SELECT ud.logical_device_id AS device_id,
       ud.sensor_name       AS category,
       ud.device_id         AS provider_edge_device_id,
       MAX(ud.timestamp)    AS last_data_at,
       MAX(ud.unit)         AS unit,
       (ds.id IS NOT NULL)  AS adopted
FROM unified_data ud
LEFT JOIN data_sources ds
       ON ds.device_id      = ud.logical_device_id
      AND ds.category       = ud.sensor_name
      AND ds.edge_device_id = ud.device_id
WHERE ud.logical_device_id IS NOT NULL
  AND ud.timestamp >= now() - ($1 || ' days')::interval
GROUP BY 1,2,3, ds.id
ORDER BY 1,2,3;
```

**实测（全量窗口，即 `$1 = 100000`）**：返回 13 行，`adopted` 全为 `f`。

## 5. 生产设备配置事实（影响方案形态）

```bash
docker exec ehome-postgres psql -U ehome -d ehome -c \
  "SELECT id, node_id, channel_id, type, device_config_id, interval_ms FROM edge_devices"
```

| id | node_id | channel | type | device_config_id | interval_ms |
|---:|---|---:|---|---:|---:|
| 2 | F0F5BD02F35C | 2 | jiabaida_bms | **0** | 5000 |
| 1 | F0F5BD02F35C | 1 | sn3001_rain | **0** | 5000 |

**`device_config_id = 0` ⇒ 走驱动回退（`drv.ParseData`），`device_configs.parser` 为空**。
所以：类别词表不能来自 DeviceConfig；只能是"实际入库过的 sensor_name"。这正是"观测驱动"方案的依据。
