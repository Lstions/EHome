# 边缘设备：批量管理 + 历史设备视图（2026-10-25）

> **需求原文**：边缘设备要支持批量管理、显示历史边缘设备，能够批量删除。
> **范围**：边缘设备列表页（在役/历史双视图）、批量操作、历史设备彻底删除。
> **语义基线**：沿用 2026-10-25 已落地的路径职责（原地换节点 / 恢复已删除设备 / 合并历史）与
> 删除语义（软删默认保留数据；delete_data=true 才后台清理数据）。

## 一、现状与缺口

| 能力 | 现状 | 缺口 |
|---|---|---|
| 多选 | 仅**表格视图**有勾选列 | 卡片视图无法多选 |
| 批量操作 | 仅「批量删除」「批量导出 CSV」 | 缺批量启用/停用/设置采集间隔（"批量管理"） |
| 历史设备 | 只在「恢复已删除设备」弹窗里出现；合并弹窗只列同型号历史设备 | **没有独立的列表视图**；无法搜索/分页浏览；看不到数据量/删除时间/清理状态 |
| 历史设备批量清理 | 无入口 | 无法批量彻底删除（记录+历史数据） |
| 删除语义区分 | 在役删除=软删（可恢复）；勾选数据=后台清理 | 用户容易把"删除"与"彻底删除"混淆，历史设备也不该有"软删"动作 |

## 二、概念与不变量（先定义再实现）

1. **在役设备**：`edge_devices.deleted_at IS NULL`。可采集、可改绑定、可停用。
2. **历史设备**：`edge_devices.deleted_at IS NOT NULL`（软删）。数据仍在（受系统保留期约束），
   可**恢复**（改绑节点/通道后重新在役），不能被采集、不能编辑、不能停用。
3. **清理中**：`data_purge_requested=true`（已提交彻底删除）或 `data_purge_started_at` 非空
   （DevicePurger 正在删）。此时**不可恢复**（restore 409），历史列表必须显示状态。
4. **两种删除，语义必须分开**：
   - 在役设备「删除」= **软删**：记录进历史列表、数据默认保留、可恢复；可选"同时删除数据"
     （后台清理，开始后不可恢复）。
   - 历史设备「彻底删除」= **删除记录 + 全部历史数据**：提交给 DevicePurger 后台分批执行，
     不可恢复。**不提供"只删记录保留数据"**（会制造无主孤儿数据）。
5. **守卫不变**：被来源组/规则引用的在役设备禁止停用/删除（沿用现有 409 语义）；
   批量操作对每条设备独立判定，逐条返回结果（不做"一条不合规整批回滚"，与现有批量删除一致）。
6. **历史设备不可"批量恢复"**：恢复必须为每台选择节点/通道，批量预填原槽位会与占用冲突，
   属于另一个交互（后续可做"批量恢复到原位置"单独立项）。

## 三、功能设计

### 3.1 双视图（列表页顶部 Tab）

    ┌ 边缘设备 ────────────────────────────────────────────────┐
    │ [ 在役设备 ]  [ 历史设备 ]                                │
    │ 搜索 ____  类型 ▾   硬件 ▾   节点 ▾        [卡片|表格] ★ │
    ├──────────────────────────────────────────────────────────┤
    │ （在役）统计卡 / 批量操作条 / 列表                         │
    │ （历史）历史概览：共 N 台已删除（其中 M 台清理中）          │
    └──────────────────────────────────────────────────────────┘

- 两个视图共用搜索框与类型筛选；历史列表逐行展示清理状态（本轮不做"清理状态"筛选，
  避免一个对分页不友好的客户端过滤；如需要再加服务端参数）。
- 历史视图固定为表格（信息密度高：数据量/删除时间/状态/操作），不提供卡片视图（明确不做）。
- Tab 切换不丢筛选（各自维护分页），从"恢复已删除设备"弹窗恢复成功后刷新两个视图。

### 3.2 批量管理（在役视图）

- **表格视图**：勾选列（已有）→ 批量操作条。
- **卡片视图**：工具栏新增「批量管理」开关；开启后卡片头部出现复选框、点击卡片切换选中，
  批量操作条出现（含"全选本页 / 取消选择"）。关闭开关清空选择。
- 批量操作条（在役）：

  | 操作 | 语义 | 后端 |
  |---|---|---|
  | 批量启用 | `enabled=true` | `POST /edge-devices/batch-update` |
  | 批量停用 | `enabled=false`（来源组规则引用 → 该条失败并给出原因） | 同上 |
  | 设置采集间隔 | 统一 `interval_ms`（0–3600000，0=不调度） | 同上 |
  | 批量删除 | 软删（默认保留数据）；对话框可勾选"同时删除历史数据"（后台清理，不可恢复） | 复用 `POST /edge-devices/batch-delete` |
  | 导出 CSV | 导出选中行 | 前端本地生成 |

- 执行后：成功数/失败数 toast；**有失败时弹明细表**（设备 #id / 原因），刷新列表并清空选择。
- 批量操作互斥：请求进行中禁用整个操作条，防连点。

### 3.3 历史设备视图

- 列：ID / 名称 / 型号 / 原节点·通道 / 数据量（约，估算）/ 最后采集 / 删除时间 / 清理状态 / 操作。
- 清理状态三值：`可恢复` / `已提交清理` / `清理中（不可恢复）`。
- 行操作：
  - **恢复**：打开现有「恢复已删除设备」弹窗并定位到该设备（弹窗需支持 initialDeviceId 预展开）。
  - **彻底删除**：二次确认（文案明确"记录与全部历史数据将被后台删除，开始后不可恢复"）→
    调批量接口（单条）→ 该行状态变"已提交清理"。
- 批量操作条（历史）：已选 N → **批量彻底删除**（同一确认弹窗）、导出 CSV；提供全选本页。
- 顶部提示条：「历史设备=已删除但数据仍保留的设备；恢复可重新投入使用；彻底删除会清理数据且不可恢复。」
- 空态：无历史设备时显示说明 + 引导（在役列表删除后进入这里；恢复入口）。

### 3.4 彻底删除的异步语义

- 接口只**提交清理队列**（`data_purge_requested=true`）并**立即唤醒 DevicePurger**（新增 Wake），
  由后台分批硬删（复用现有 purge 认领/台账清理/硬删设备行逻辑）。
- 响应含义：`queued`（已入队）；已在清理中的设备重复提交幂等成功。
- 历史列表展示 `data_purge_requested` / `purge_in_progress`；清理完成后设备行消失（下次刷新）。
- 注意：清理一旦被 purger 认领，restore 返回 409（现有语义）——界面上"清理中"的设备禁用恢复按钮。

## 四、API 契约变更

| 端点 | 变更 |
|---|---|
| `GET /edge-devices/deleted` | 新增 `search`（名称/型号模糊，大小写不敏感）；保留 `device_type` / `page` / `page_size`；响应不变 `{items,total,page,page_size}` |
| `POST /edge-devices/batch-update` **新增** | body `{ids: number[], enabled?: boolean, interval_ms?: number}`（至少一个字段；ids 1..100，去重）；逐条结果 `{total,succeeded,failed,results:[{id,success,error?,enabled?,interval_ms?}]}` |
| `POST /edge-devices/deleted/batch-delete` **新增** | body `{ids: number[]}`（1..100，去重）；仅接受已软删设备；逐条置 `data_purge_requested=true` 并唤醒 purger；逐条结果同上（`queued` 标记）；未删除/不存在 → 该条失败 |
| `POST /edge-devices/batch-delete` | 不变（在役软删，`delete_data` 可选） |

补充：
- 批量停用沿用「来源组规则引用」守卫（与单台 PUT 停用一致，逐条失败并给原文）。
- 批量设置间隔不校验驱动命令容量（间隔是设备默认轮询周期，命令容量由 command_intervals 决定）。
- 所有批量接口逐条独立事务，返回部分成功结果（前端展示失败明细）。

## 五、明确不做（避免范围膨胀）

- 批量恢复（需逐台选槽位；后续可做"批量恢复到原位置"）。
- 历史设备详情页/数据图表（历史数据可读，但详情页依赖配置端点 404；如需要另做只读页）。
- 批量修改节点/通道（换绑定需逐台校验，与换节点交互一致）。
- 历史设备"只删记录保留数据"（会制造孤儿数据，明确禁止）。
- 卡片视图的历史设备展示（表格足够，做卡片无增益）。

## 六、验收判据（可失败）

### 6.1 后端（真实 HTTP + DB 前后状态）

1. `POST /edge-devices/batch-update`
   - `{ids:[1,2], enabled:false}` → 200，两台 `enabled=false`；返回逐条成功；
   - 来源组规则引用的设备停用 → 该条失败（error 含组名/规则名），其余设备仍成功；
   - 已删除/不存在 id → 该条失败（不误改其它）；
   - `{ids:[], ...}` / ids>100 / 未提供任何字段 / `interval_ms<0 或 >3600000` → 400；
   - 间隔批量设置后 `interval_ms` 落库正确。
2. `GET /edge-devices/deleted?search=xxx`：按名称/型号大小写不敏感模糊命中；与
   `device_type` / 分页组合正确；total 与 items 一致。
3. `POST /edge-devices/deleted/batch-delete`
   - 软删设备 → 逐条成功（`queued:true`），DB `data_purge_requested=true`；
   - 在役/不存在 id → 该条失败且不改动；
   - 重复提交（已请求清理）→ 幂等成功；
   - 调用后 DevicePurger 被唤醒并实际清理：设备行与 unified_data/device_data/sensor_field_obs/
     data_sources 全部消失（`WaitGroup`/轮询断言）；
   - 清理认领中的设备提交 → 成功但状态显示清理中（不重置认领）。
4. 回归：单台删除/恢复/合并/列表分页/查询功能不变。

### 6.2 前端

1. 列表页顶部「在役设备 / 历史设备」双 Tab：历史 Tab 加载 `GET /deleted`（分页、搜索、
   类型筛选）；显示数据量估算/最后采集/删除时间/清理状态；清理中禁用恢复。
2. 在役表格：多选后批量条包含 启用 / 停用 / 设置采集间隔 / 删除 / 导出；执行后刷新并清空选择；
   有失败时展示失败明细（#id + 原因）。
3. 卡片视图：「批量管理」开关开启后出现复选框与批量条，支持全选本页/取消；关闭清空选择。
4. 历史视图：行操作 恢复（弹窗预选该设备）/ 彻底删除（二次确认、文案明确不可恢复）；
   批量彻底删除 + 导出 CSV。
5. 门禁：`pnpm test:run` / `pnpm typecheck` / `pnpm build` 全绿；后端
   `go build/vet/test` 全绿。

## 八、风险与边界

| 风险 | 处理 |
|---|---|
| 历史设备"彻底删除"不可恢复，误操作 | 二次确认 + 明确文案 + 逐条结果；不提供"只删记录" |
| 批量停用触发来源组规则失效 | 沿用现有守卫逐条拦截，失败原因透出 |
| 批量接口部分成功 | 逐条独立事务 + 结果明细（与现有 batch-delete 一致），前端必须展示失败明细 |
| purger 24h 周期导致"删除不生效" | 彻底删除后立即 Wake purger；列表显示"已提交清理" |
| 卡片批量模式与点击卡片进入详情冲突 | 批量模式下点击卡片只切换选中；需在 UI 上明确提示 |
| 历史设备数据量估算噪声 | 显示为"约 N 行"；0 行用 EXISTS 钉死（与现有 data-summary 口径一致） |
