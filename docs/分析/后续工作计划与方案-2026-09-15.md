### 1.4 ⚠️ 本文档自身的一处失真（**开工纪律执行的直接产物，2026-09-15 实测**）

> 本节存在的理由：§6 要求"开工前先重跑现状证据"，主控照做了，于是**发现本文档 §1.1 是错的**。
> 把它写回本文档（而不是只写在报告里），是因为**下一轮的执行者会读这份文档**。

**§1.1 原写**：`make test-scenarios` ⇒「**133 场景**已注册」。

**实测（2026-09-15）**：133 这个数字**只是"注册数"**（`grep -rhoE '"SIM-[A-Z]+-[0-9]+"' backend/simulation/ | sort -u | wc -l`），
**不是"通过数"**。实际**运行**仿真套件时，**多个既有场景是红的**。

**根因已确诊**：提交 `a96afda5`（`feat(pagination): 真分页 + 消除 Limit(500) 静默截断`）
把一批端点从**裸数组**改成 **`{items,total,page,page_size}`**，但**没有同步更新
`backend/simulation/catalog/` 里的解析代码**：

```bash
git show a96afda5 --stat | grep simulation   # ⇒ 零命中：该提交没有碰仿真套件
```

于是 helper 仍按裸数组反序列化，报同一类错误：
```
解析策略事件失败: json: cannot unmarshal object into Go value of type []catalog.autoEventRow
（data={"items":[...]...}）
```

**已复现的红场景（既有、非本轮新增）**：`SIM-AUTO-002`、`SIM-AUTO-003`、`SIM-AUDT-001`、`SIM-CNFM-001`
（以及 `SIM-NTFY-001/002/003`）。`autoListEvents` 是被 `cnfm/audit/manu/scene/trig/cond` 等**多个域共用**的
helper，因此影响面远大于这 4 个场景。

**这条事实的三重含义**（比缺陷本身更重要）：

| # | 含义 |
|---|---|
| 1 | **"已注册"不等于"通过"** —— 两个分母必须分开写，本文档 §1.1 混用了它们（与 §0 批评旧清单的是同一个错误） |
| 2 | **改契约不搜调用方** ⇒ 静默破坏下游。这与"静默失败"家族同源：解析失败被吞成"等待超时"，现场只剩"条件未满足" |
| 3 | **本文档 §1.1 的门禁结果有保质期**（§7.4 已自我声明），但 §1.1 的场景数**压根不是一次运行的结果** —— 那是把"目录里有 133 个 ID"当成了"133 个都跑过" |

⇒ 因此**任何"仿真套件全绿"的说法，必须附一次完整运行的时间戳与通过/失败数**，
不得只报注册数。

**根因的两个层次（都已在同一轮修掉）**：

| # | 缺陷 | 层次 | 修法 |
|---|---|---|---|
| 1 | 端点契约变了、仿真解析没跟着变 | **解析漂移** | `catalog.go` 新增只接受 `{items,...}` 的 `sim*` 助手；**裸数组显式失败**（不兼容、不兜底），其余裸数组端点在调用点写明依据 |
| 2 | `windFindCrossWindow` 的整点搜索**覆盖不到** 11:00–11:59 与 23:00–23:59 | **可满足性缺陷**（与分页无关） | 改为**构造式**（不再搜索）；`wind_satisfiability_test.go` 穷举 1440 分钟、并用**独立真值**（全枚举 1440×1439/2 个跨零点窗口）钉死"唯一无解分钟是 23:59" |

> 第 2 条是本轮最有价值的发现之一：它是一个**按小时周期性**的假红 ——
> 每天 11:00–11:59 与 23:00–23:59 必然变红，其余时刻全绿。
> **抽样测试永远抓不到它**（2026-09-15 11:11 那次全量恰好踩在无解小时里才暴露）。
> 这也解释了为什么"昨天还是绿的"不能作为"今天也是绿的"的证据。

#### (8) 第 7 轮续：错误提示可区分性（`handleError` 歧义收敛）

**开工纪律第一步（先重跑分母）**：按「同一文件内是否出现**完全相同**的错误文案」扫描，
得到 **9 个文件**存在同操作域内重复文案；其中 `LogPanel.vue` 是最明确的形态：
**三处不同操作全部报同一句话 `操作失败`**。

```bash
cd frontend-shared
grep -n -B8 'handleError' src/components/node/LogPanel.vue | grep -E 'async function|await |handleError'
#   198  await nodeApi.updateLogConfig(collectorId, { stream_enabled: on })   → :205 handleError(e,'操作失败')
#   216  await nodeApi.updateLogConfig(collectorId, { level: value })         → :222 handleError(e,'操作失败')
#   234  await nodeApi.updateLogPersist(collectorId, on)                      → :241 handleError(e,'操作失败')
```

**为什么这是真缺陷而不是文案洁癖**：`handleError` 的第二参数是**兜底而非前缀**
（`extractErrorMessage` 优先级 `response.data.message || … || fallback`），后端又**总是**带 message，
⇒ 用户实际只看到服务端那句话（如 `invalid level`），**既不知道是哪个控件失败、也不知道失败的是哪件事**。
决定性证据：**同一文件的三条成功路径各自不同**（`日志流已开启` / `日志级别已更新` / `持久化已开启`）——
作者显然知道这是三件事，**只有失败路径被抹平了**。

**修法**：三处改用 `handleErrorWithContext`，文案含宾语与开关方向：
`开启/关闭日志流失败`、`更新日志级别失败`、`开启/关闭日志持久化失败`。

**新增门禁**：`frontend-shared/src/utils/__tests__/errorContextDistinctnessGate.spec.ts`（3 用例）——
每个文件内 `handleError` / `handleErrorWithContext` 的文案字面量**不得重复**；
含分类器自检（同文件重复必报 / 跨文件与单次必不报 / 注释里的不算）与分母守卫（`scanned > 30`、命中文件 ≥ 10）。
**变异自证**：把两处退回 `'操作失败'` ⇒ 红并报
`LogPanel.vue 文案「操作失败」出现在行 208, 225 —— 同一组件内不同操作报同一句话，用户无法判断是哪个操作失败`；
恢复后 md5 `241df6f5…` 一致。
**边界（写进文件头）**：只拦「一模一样」这一种明确形态；不判断文案是否**有信息量**
（改成「失败 A/B/C」仍会通过），也不覆盖 `ElMessage.error` 直调与动态拼接。

> **本轮最有价值的一条连带发现：改进一个出口，暴露了守卫的假阴性。**
> 把 3 处 `handleError` 改成 `handleErrorWithContext` 后，既有守卫
> `i1ErrorConvergenceGuard` 的分母从 **110 掉到 108** 而变红。追查发现其正则是
> `/feedback\.(handleError|error)\(/g` —— **匹配不到 `handleErrorWithContext(`**
> （`handleError` 后面跟的是 `W` 不是 `(`）。
> 后果很隐蔽：**做正确的改进会让「收敛度」看似下降**，若当时选择放宽阈值（110 → 105），
> 就会把这个假阴性永久固化，且**真正的收敛退化再也测不出来**。
> 处置：**修正则并加分类器自检**（三种出口形态必须都命中；`ElMessage.error`/`console.error` 必须不命中），
> **阈值保持 110 不动**。**变异自证**：把正则退回旧形态 ⇒ 自检红并报
> `出口正则必须匹配: feedback.handleErrorWithContext(e, 'x'): expected false to be true`，
> 同时分母守卫报 `expected 108 to be greater than or equal to 110`。
>
**续做（同一判据的推广）**：门禁建立后按同一口径继续收敛另外两处 ——
  · `DeviceConfigList.vue` 的「启用/禁用」动作报 `'操作失败'`（同文件其余动作都带宾语：克隆/设置默认/导入）⇒ 改 `启用失败` / `禁用失败`；
  · `ChannelPanel.vue` 的「删除通道」报 `'删除失败'`（同文件另两处删除已写明对象：`删除 GPIO 失败` / `删除 PWM 失败`）⇒ 改 `删除通道失败`。
  · **这两处不是门禁红出来的**（它们是「同文件内唯一」，门禁只拦重复），而是**按同一口径主动扩查**出来的；
    这说明门禁的判据只覆盖了最明确的一半形态（见上文边界第 1 条），**不能把「门禁全绿」当成「文案都已裁决」**。
  · 修 `DeviceConfigList` 时 `vue-tsc` 报了 `TS2552: Cannot find name 'newStatus'` —— 目标状态原本声明在 `try` 内，
    而 `catch` 里要用它拼文案。这是**真实的作用域错误**（不是误报），已把声明提到 `try` 外并包成块作用域。
    ⇒ 又一次说明：**改错误文案不是纯文本替换**，它会把「catch 能不能看到某个变量」这类约束暴露出来。

#### (12) 第 9 轮：落地一处「已建议但未实施」的仓库级改进（陈旧 PG schema 兜底回收）

**怎么找到的**：由 §1.7 (11) 的同类扫描延伸 —— 全仓搜「写 PG 库名却没连 PG」与「残留检查查错对象」，

> 「给 `testutil.openPostgres` 增加启动时的陈旧 `test_*` schema 兜底回收」

**为什么它值得做（不是洁癖）**：`openPostgres` 的清理挂在 `t.Cleanup` 上，而 `t.Cleanup` **只在进程正常退出时执行**。
`go test … | head` 会触发 SIGPIPE、`kill`/OOM 会 SIGKILL —— 这些情况下清理钩子**根本不跑**，schema 永久残留。
本仓的日常操作（包括本轮我自己）大量使用 `| head` / `| tail`，所以这不是边角场景。

**先复现，再修（拒绝「读代码觉得有风险」就动手）**：

```bash
# 跑 PG 测试，轮询到 schema 出现后立刻 kill -9
EHOME_TEST_DB=postgres EHOME_DB_NAME=ehome_sim_pg go test -count=1 ./internal/api/ &
# … 观察到 800ms 时 schema 出现 …
pkill -9 -f api.test
# ⇒ ehome_sim_pg 残留 test_3861920_1789489580224261933
```

**实现**（`backend/testutil/db.go`）：新增 `reapStaleSchemas(base)`，在 `CREATE SCHEMA` **之前**调用。
安全规则用 `syscall.Kill(pid, 0)` 判断 schema 名里的 pid 是否仍存活，**存活则不动** ——
因为本仓常并行跑多个测试进程，无条件 DROP 会误删别人正在用的 schema。
回收决策抽成纯函数 `shouldReapSchema(name, alive)`，以便用**行为**而非文本断言来验证。

**三组实测证据**：

| 场景 | 结果 |
|---|---|
| 复原残留后跑任一 `OpenTestDB` 用例 | 残留 **1 → 0**（回收生效） |
| 用**当前 shell 的活 pid** 伪造 `test_<pid>_…` 再跑同一用例 | **未被回收**（安全规则生效，未误删） |
| 名字格式不符（`public` / `test_` / `test_abc_1`） | **一律不碰**（fail-closed：宁可漏收不误删） |

**新增回归测试**：`backend/testutil/reap_test.go`（4 用例）—— 命名解析、存活判定、接线顺序、回收决策与安全规则。

**变异自证 3 组**：删掉接线调用 ⇒ 红；忽略格式校验 ⇒ 红；**把存活判定架空（`!(alive(pid) && false)`）⇒ 红**（见下）。
恢复后 md5 `9b5cfe31…` 一致。

> **本门禁第一版又踩了与 §1.7 (11) 同一个坑（值得连记）**：安全规则的判据写成
> `strings.Contains(body, "processAlive(pid)")`。变异把决策改成 `if processAlive(pid) && false {…}` ——
> **字符串仍在、逻辑已死，门禁全绿放行**。这与 (11) 里 `os.Getenv("EHOME_TEST_DB")` 出现 3 次是**同一类错误**：
> **用「字符串存在」代替「行为正确」**。修法不是再换个正则，而是**把决策抽成纯函数、用行为断言**：
> `shouldReapSchema("test_1234_1", alwaysAlive)` 必须为 false、与 `alwaysDead` 的结果必须**不同**。
> 复测同一变异 ⇒ 红，报「存活判定的结果未影响决策 —— 安全规则已被架空」。
>
> ⇒ **纪律补充（第 10 次失真，与第 9 次同源）**：**能写成行为断言的就不要写文本断言。**
> 文本断言只适用于「根本无法在测试里执行」的对象（如纯文档）；**凡是被测代码里的逻辑，一律抽函数后喂输入断言输出**。

#### (17) 第 13 轮：把「GORM 写路径形态」也做成门禁（上次是「模型默认值」，这次是「写调用」）

**触发**：§1.7 (16) 建了「非零 default」门禁后，按同一条线索往下问一句 ——
**零值陷阱不只在模型 tag 上，也在写调用的形态上**：
GORM 的 `Updates(struct)` 会**跳过结构体里的零值字段**（与 `default:` tag 是同一个坑的另一半），

**先量分母（按 §1.7 (16) 的教训：先用最朴素的模式扫）**：
```bash

grep -rn "Updates(" --include=*.go internal/ cmd/ | grep -v _test   # 66
grep -rn "\.Save("  --include=*.go internal/ cmd/ | grep -v _test   # 13
```
逐文件核对变量声明后确认：
  · **66 处 `Updates()` 全部是 `map[string]interface{}` 形态**（39 处直接字面量 + 27 处经变量）；
  · **13 处 `.Save()` 全部是「先读后写」** —— 对**已加载的完整结构体**保存，

⇒ **两类形态在现行代码里都正确**；本门禁的作用是**把纪律固定下来**，防止将来有人写成

**门禁自身的三个缺陷（全部被自己的守卫/自检当场抓出）**：

  ⇒ 三条合起来说明：**门禁的判据本身要有守卫，且守卫要能区分「类型正确」与「名字像」**。

## 2. 战略判断：这个项目现在最缺什么

在排期之前先明确**方向**，否则会陷入"修完 UI 修后端"的无序循环。基于 16 轮实测，主控的判断是：

### 2.1 已解决的问题类型
- **"能力缺失"**（D-1 外发通道、清理器）——已基本补齐；
- **"UI 缺陷"**（F 系列的绝大多数）——已修复过半；
- **"无界增长"**（10 张表）——已全部有处置。

### 2.2 **仍然系统性薄弱的环节（本计划的重点）**

| 薄弱环节 | 证据 | 为什么重要 |
|---|---|---|
| **① 新能力的验证覆盖滞后** | 外发通道 6 端点 + 引擎**零仿真场景**（133 个场景里无一个覆盖它） | 本仓的核心资产是"133 场景的仿真套件"；**新能力不进套件 = 不受套件保护** |
| **② 文档与实现的漂移** | 本轮实测 3 处（G-1/G-2/G-3）；历史上已反复出现（D-2/D-3/D-5 均因文档或记录失真而误判） | 漂移会让**后续所有排期基于错误前提**（本计划 §0 就是被漂移坑到的一例） |
| **③ 契约层的一致性缺陷** | `models.RedactTargetURL` 输出 `%2A%2A%2A` 而 `notify.RedactURL` 输出 `***`；且注释声称的守护测试 `TestRedactTargetURLMatchesNotify` **全仓不存在** | 这是"**注释声称有测试、实际没有**"——比缺测试更危险 |
| **④ 少量残留的"静默失败"** | F2：**4 处** `ShouldBindJSON` **返回值被丢弃** ⇒ 畸形 JSON 静默按零值处理（其中 `handler_vendor.go:183` 会把字段**静默清空**） | 属"伪装成正常"家族，且在后端（**无 UI 提示可依赖**） |

### 2.3 ⇒ 战略结论

> **从"补能力 / 修缺陷"转向"固化已有成果"**：
> 项目已积累了大量正确实现与 133 个场景，**当前最高价值不是再加功能，
> 而是让"已经对了的东西"被持续保护起来，并消灭会误导后续判断的漂移。**
>
> 具体三件事：**① 把新能力纳入仿真套件（G-1 + D-1 步骤 7）；② 系统性清除文档/注释漂移；
> ③ 补齐"声称有但实际没有"的守护测试。**
> 之后才是继续修剩余的 UI/UX 低频项。

### P0-A：清除"注释声称有测试但实际没有"的契约漂移（**最小、最高杠杆**）

**现状证据**：
```bash
grep -rn "RedactTargetURL" backend/internal/models/*.go
# 注释称"由 TestRedactTargetURLMatchesNotify 守住两者一致"
grep -rn "TestRedactTargetURLMatchesNotify" backend/   # ⇒ 零命中（该测试不存在）
```
且两者行为**确实不同**（主控实测复现，非推断）：
```
models.RedactTargetURL = …/webhook/send?key=%2A%2A%2A&x=1
notify.RedactURL       = …/webhook/send?key=***&x=1
EQUAL=false
```
复跑方式（**注意不能从 `models` 侧写**——`models` 不能 import `notify`，会在 setup 阶段就失败）：
```bash
cd backend
cat > internal/notify/zz_probe_test.go <<'EOF'
package notify
import ("testing"; "ehome/backend/internal/models")
func TestZZRedactDivergence(t *testing.T) {
  const in = "https://x/y?key=SECRET&x=1"
  t.Logf("EQUAL=%v", models.RedactTargetURL(in) == RedactURL(in))
}
EOF
go test -buildvcs=false -count=1 -run TestZZRedactDivergence -v ./internal/notify/
rm -f internal/notify/zz_probe_test.go   # 探针必须删除, 不留残留
```
**这同时暴露了一个连带事实**：`models` 与 `notify` 之间**不可能通过 `models` 侧的单测**来做一致性断言
（会构成 import cycle）⇒ 那个"缺失的守护测试"**只能放在 `notify` 包**（或独立的第三包）。
**这一约束应当写进修复方案**，否则实施者会在 `models` 里写出一个编译不过的测试。

**目标**：统一占位符为 `***`，并**补上那个缺失的守护测试**（让注释不再说谎）。

**验收判据**：
1. 两个函数对同一输入的输出**逐字符相同**；
2. 新增 `TestRedactTargetURLMatchesNotify`（一个表驱动用例，覆盖：有 key / 无 key / 带特殊字符 / 空值）；
3. **变异自证**：把任一处的占位符改回 `%2A%2A%2A` ⇒ 该测试**变红**；恢复后 md5 一致。

**风险与对策**：`models` 包被 `gorm` 引用面广，改函数体需确认无调用方依赖旧格式
（实测调用点有限，且旧格式是**转义后的星号**，无消费者会依赖它）。

**成本**：≈0.5 小时。
