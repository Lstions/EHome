## 2. 战略判断：这个项目现在最缺什么

在排期之前先明确**方向**，否则会陷入"修完 UI 修后端"的无序循环。基于 16 轮实测，主控的判断是：

### 2.1 已解决的问题类型
- **"能力缺失"**（D-1 外发通道、清理器）——已基本补齐；
- **"UI 缺陷"**（F 系列的绝大多数）——已修复过半；
- **"无界增长"**（10 张表）——已全部有处置。

### 2.2 **仍然系统性薄弱的环节（本计划的重点）**

| 薄弱环节 | 证据 | 为什么重要 |
|---|---|---|
| **① 新能力的验证覆盖滞后** | 外发通道 6 端点 + 引擎**零仿真场景**（133 个场景里无一个覆盖它） | 本仓的核心资产是"133 场景的仿真套件"；**新能力不进套件 = 不受套件保护** |
| **② 文档与实现的漂移** | 本轮实测 3 处（G-1/G-2/G-3）；历史上已反复出现（D-2/D-3/D-5 均因文档或记录失真而误判） | 漂移会让**后续所有排期基于错误前提**（本计划 §0 就是被漂移坑到的一例） |
| **③ 契约层的一致性缺陷** | `models.RedactTargetURL` 输出 `%2A%2A%2A` 而 `notify.RedactURL` 输出 `***`；且注释声称的守护测试 `TestRedactTargetURLMatchesNotify` **全仓不存在** | 这是"**注释声称有测试、实际没有**"——比缺测试更危险 |
| **④ 少量残留的"静默失败"** | F2：**4 处** `ShouldBindJSON` **返回值被丢弃** ⇒ 畸形 JSON 静默按零值处理（其中 `handler_vendor.go:183` 会把字段**静默清空**） | 属"伪装成正常"家族，且在后端（**无 UI 提示可依赖**） |

### 2.3 ⇒ 战略结论

> **从"补能力 / 修缺陷"转向"固化已有成果"**：
> 项目已积累了大量正确实现与 133 个场景，**当前最高价值不是再加功能，
> 而是让"已经对了的东西"被持续保护起来，并消灭会误导后续判断的漂移。**
>
> 具体三件事：**① 把新能力纳入仿真套件（G-1 + D-1 步骤 7）；② 系统性清除文档/注释漂移；
> ③ 补齐"声称有但实际没有"的守护测试。**
> 之后才是继续修剩余的 UI/UX 低频项。

### P0-A：清除"注释声称有测试但实际没有"的契约漂移（**最小、最高杠杆**）

**现状证据**：
```bash
grep -rn "RedactTargetURL" backend/internal/models/*.go
# 注释称"由 TestRedactTargetURLMatchesNotify 守住两者一致"
grep -rn "TestRedactTargetURLMatchesNotify" backend/   # ⇒ 零命中（该测试不存在）
```
且两者行为**确实不同**（主控实测复现，非推断）：
```
models.RedactTargetURL = …/webhook/send?key=%2A%2A%2A&x=1
notify.RedactURL       = …/webhook/send?key=***&x=1
EQUAL=false
```
复跑方式（**注意不能从 `models` 侧写**——`models` 不能 import `notify`，会在 setup 阶段就失败）：
```bash
cd backend
cat > internal/notify/zz_probe_test.go <<'EOF'
package notify
import ("testing"; "ehome/backend/internal/models")
func TestZZRedactDivergence(t *testing.T) {
  const in = "https://x/y?key=SECRET&x=1"
  t.Logf("EQUAL=%v", models.RedactTargetURL(in) == RedactURL(in))
}
EOF
go test -buildvcs=false -count=1 -run TestZZRedactDivergence -v ./internal/notify/
rm -f internal/notify/zz_probe_test.go   # 探针必须删除, 不留残留
```
**这同时暴露了一个连带事实**：`models` 与 `notify` 之间**不可能通过 `models` 侧的单测**来做一致性断言
（会构成 import cycle）⇒ 那个"缺失的守护测试"**只能放在 `notify` 包**（或独立的第三包）。
**这一约束应当写进修复方案**，否则实施者会在 `models` 里写出一个编译不过的测试。

**目标**：统一占位符为 `***`，并**补上那个缺失的守护测试**（让注释不再说谎）。

**验收判据**：
1. 两个函数对同一输入的输出**逐字符相同**；
2. 新增 `TestRedactTargetURLMatchesNotify`（一个表驱动用例，覆盖：有 key / 无 key / 带特殊字符 / 空值）；
3. **变异自证**：把任一处的占位符改回 `%2A%2A%2A` ⇒ 该测试**变红**；恢复后 md5 一致。

**风险与对策**：`models` 包被 `gorm` 引用面广，改函数体需确认无调用方依赖旧格式
（实测调用点有限，且旧格式是**转义后的星号**，无消费者会依赖它）。

**成本**：≈0.5 小时。

### P1-B：修补残留的"静默失败"（F2 与同类）

**现状证据**（实测 **4 处**，返回值被丢弃）：
```bash
grep -rn "c.ShouldBindJSON(&req)$" backend/internal/api/*.go
# internal/api/handler_device.go:513
# internal/api/handler_device.go:966
# internal/api/handler_node.go:317
# internal/api/handler_vendor.go:183      ← 计划初稿只数了 3 处, 复核时补上
```
⇒ 畸形 JSON ⇒ `req` 保持零值 ⇒ 请求"成功"但**行为与用户意图不符**。
其中 `handler_vendor.go:183` 最危险：它把 `req.Fields` **直接写库**（`Update("fields", req.Fields)`），
畸形输入会**静默清空该字段**。

**目标**：四处改为「绑定失败 ⇒ 400 + 明确错误消息」，并**补测试**（发送畸形 JSON，断言 400 而非 200）。

**验收判据**：
- **4 处**均返回 400；每个新增至少 1 条测试；
- **变异自证**：把某处改回丢弃错误 ⇒ 对应用例变红；
- 全量 `go test ./...` 0 FAIL（注意：**可能有既有测试依赖"畸形 JSON 也返回 200"**，
  若有，需逐个判断那是"测试固化了缺陷"还是"有意行为"——**不要直接改测试让它绿**）。

**风险与对策**：改 API 行为可能影响前端调用方（前端可能依赖"宽松"）。
对策：先 grep 前端这三个端点的调用点确认都发合法 JSON。**这是行为变更，需在提交信息里写明。**

**成本**：≈2 小时。

**主控的采集命令**（复核时请原样重跑，与本文档不符以实测为准）：
```bash
cd frontend-shared
# I-4: 总 hex 数 + 按文件分布（注意 dev/ 页应剔除）
grep -rnE "#[0-9a-fA-F]{6}\b" src --include=*.vue | grep -v __tests__ | wc -l          # 199
grep -cE "#[0-9a-fA-F]{6}\b" src/dev/BmsDemoPage.vue                                  # 115（dev 页）
# I-9: 交互元素与显式 tabindex 的对比分母
grep -rn "cursor: pointer" src --include=*.vue | grep -v __tests__ | wc -l             # 62
grep -rn "tabindex" src --include=*.vue | grep -v __tests__ | wc -l                    # 20
# F8: 仍缺 mobile-table-wrapper 的页面（应只剩 2 个非列表页）
for f in $(find src/views -name "*.vue" | grep -v __tests__); do
  grep -q "el-table" "$f" && ! grep -q "mobile-table-wrapper" "$f" && echo "$f"
done
```
**注意**：I-4 的 199 与 115 **不是同一层级的分母**（前者是"所有 .vue 里的 hex 行数"，
后者是"单个 dev 文件的 hex 行数"）—— 混用会得出"dev 页占 58%"这种误导性结论。
**必须先定义"业务代码"的边界，再统计。**

**目标**：按"**先拆分母、再定范围**"的顺序处理，**不做全量机械替换**。

**验收判据**：
- 每项**先给出实测分母与采集命令**（例如 I-4 要区分 dev 页与业务页）；
- 修复项有回归测试或门禁；**无法修复的（如 F8）明确写"不修及理由"**。
