> **日期**: 2026-10-21

## 1. 需求陈述与结论

**真实需求**：边缘设备接入并产生数据后，自动化引擎应能**直接使用这些数据**做规划。举例：
1. BMS 接入 → 规则里可直接选「BMS 当前电量（`rsoc`）」作为触发/条件；
2. 日出/日落作为触发；
3. 动作 = 控制 MOS（充放电开关）。

**结论：这条链路今天「能用」，但由**三个手工填字符串**串起来，其中两个是静默失败陷阱；一个关键复核环节对多字段设备（BMS）会必然拒绝执行。也就是说：功能上不缺，产品上不可用。**

| 环节 | 现状 | 判定 |
|---|---|---|
| BMS 数据进入引擎 | **已通**：解析成功即同步调 `automationSink(edgeDeviceID, fields, now)` | ✅ 可用 |
| 规则能否选中 `rsoc` | 能，但**必须手打字符串 `rsoc`**（前端是文本框，无字段目录） | ⚠ 可配不可发现 |
| 日出日落触发 | **已实现**（sun_event + 偏移），但**坐标必须先在节点页配**，否则保存直接 400 | ⚠ 前置条件未引导 |
| MOS 动作 | **已实现**（`set_mos_policy`，风险 high→elevated，需确认或规则级授权） | ✅ 可用 |
| **触发→执行间的条件复核（F4）** | **对多字段设备必然拒绝执行**（详见 §2.1） | ❌ **阻断** |
| 附加条件的 JSON 写法 | 前端 placeholder 教错字段名（`sensor` vs `sensor_name`）⇒ 条件被静默跳过 | ❌ **静默失效** |

## 2. 三个必须修的实现缺陷（都是本轮实测复现，不是推断）

### 2.1 【阻断】F4 条件复核对多字段设备必然拒绝执行

**机制**（四段静态事实拼起来的）：

| # | 事实 | 证据 |
|---|---|---|
| 1 | databus 对一帧解析出的 **N 个物理量逐条**调 latestSink | `consumers_heavy.go:373-397`（`for i := range records { c.latestSink(records[i]) }`） |
| 2 | `SetLatestValue` 的 `last[deviceID] = rec` 是**覆盖写**（只保留最后写入的那一条） | `latest_value_cache.go:41-58` |
| 3 | `LatestValue` **只返回最后写入的那条**（单值语义，注释明说"自动化 F4 依赖它"） | `latest_value_cache.go:61-68` |
| 4 | BMS 0x03 帧的**末位**是 `temperature_2`（标量 10 项之后追加温度） | `jiabaida_parse.go:250-274` |

**结论**：对 BMS 设备，`LatestValue(dev)` **恒为 `temperature_2`**（生产库实测：`SELECT sensor_name ... ORDER BY id DESC LIMIT 1` → `temperature_2`）。

**而 F4 复核的语义是 fail-closed**（`planner.go:527-536`）：缓存里的传感器名 ≠ 规则传感器名 ⇒ **判"条件不再满足"并拒绝执行**，reason 写 `trigger sensor "rsoc" not in latest-value cache (cache holds "temperature_2")`。

**本轮实测**（临时探针测试，已删除，不污染仓库）：

```
sensor=rsoc             ok=false  reason="trigger sensor "rsoc" not in latest-value cache (cache holds "temperature_2")"
sensor=total_voltage    ok=false  reason="... (cache holds "temperature_2")"
sensor=temperature_2    ok=true   （按数值正常复核）
```

**业务后果**：用户配一条「`rsoc < 30` → 关 MOS」的规则，**触发能成立（Evaluate 用的是整帧 fields，正确），但执行前复核必然拒绝**，事件落 `condition_changed`，MOS 永远不动。这是**最隐蔽的失败**：规则保存成功、触发日志出现、没有任何错误提示。

> 修法（三选一，建议 A+B）：
> - **A**：`LatestValue` 改为"按传感器名取"（用已有的 `entries[deviceID][sensorName]` 多槽缓存，而不是 `last`），F4 复核按 `rule.TriggerSensorName` 精确取。**这是最小且正确的修法**：多槽缓存 2026-09-16 就已存在，只是 F4 仍走单值通道。
> - **B**：F4 复核拿不到该传感器时**降级为"跳过复核"而非拒绝**（需同步改注释与测试，属语义变更，须裁决）。
> - C：缓存 `last` 改为"每传感器各一条"，但仍是覆盖面问题，不彻底。

### 2.2 【静默失效】附加条件的 JSON 字段名前后端不一致

- 前端 placeholder：`[{"sensor":"humidity","comparator":"lt","threshold":30}]`（`AutomationRules.vue:411`）
- 后端结构：`SensorName string \`json:"sensor_name"\``（`models/automation.go:97`）
- 后端**不校验** `conditions_json` 的结构（`handler_automation.go:307/582` 都是原样存字符串）

**实测**（本轮探针）：

```
按前端 placeholder 写: [{SensorName: Comparator:lt Threshold:30}]     ← SensorName 为空
按后端 tag 写:        [{SensorName:rsoc Comparator:lt Threshold:30}]
```

引擎侧（`evaluator.go:806-810`）：`cv, ok := matchField(fields, c.SensorName)`；`c.SensorName == ""` ⇒ `ok=false` ⇒ `return`（**整条规则不触发**）。

**业务后果**：用户照 placeholder 写附加条件（例如「夜间 + rsoc<30」）⇒ 规则**永不触发**，且没有任何校验错误。

> 修法：① 前端改 placeholder 为 `sensor_name`（一行）；② 后端保存时**解析并校验** conditions_json（fail-closed 400）；③ 前端把附加条件做成字段选择器而非 JSON 文本框（见 §4）。

### 2.3 【不可发现】传感器名只能手打，用户无法知道 BMS 有哪些字段

- 触发传感器是自由文本输入框（`AutomationRules.vue:332`，placeholder `如：temperature`）。
- 而 BMS 真实字段名是 `rsoc / total_voltage / temperature_1 / cell_voltage_1` 这类**代码内部标识**。
- 后端已有现成词表接口：`GET /api/v1/unified-data/categories?device_pk=` → `[{code, unit}]`（`handler_data.go:231-266`），前端也有封装（`api/unifiedData.ts:85`），但**自动化页未使用**。
- 更糟：`sensor_name` 与 `category` 是同一个字符串域，数据源页（DS-08）也有同类问题。

**业务后果**：用户不可能凭记忆写出 `rsoc`；写错（如 `soc`）⇒ `matchField` 找不到 ⇒ 规则**永不触发**，无任何提示。

### 2.4 附带发现：日出日落规则的"坐标未配置"是保存期硬失败

- 校验链 `validateSunEventRule`（`handler_automation.go:1078-1085`）在**保存时**就要求能解析出坐标/时区（规则值 → 节点值 → 失败即 400）。
- 生产库实测：`nodes` 表 **727 行里 latitude 非空 = 0 行**（两台真实节点 `F0F5BD02F35C`/`30EDA0A9A808` 的 lat/lon/timezone 全为 NULL）。
- 前端已做了引导文案（`sun-location__state`，`AutomationRules.vue:390-400`），但用户仍需**先跳到节点页配坐标**才能保存日出规则。
- 这不是缺陷（fail-closed 是对的），但**是新用户路径上的第一个失败点**：需求里"日出日落 + MOS 开关"这类规则，用户第一次保存就会 400。

## 4. 推荐方案：把"能配"变成"可发现、可验证"

### B1（P0，最小修复，约 1 天）
1. **F4 复核改按传感器名取值**（§2.1 修法 A）：`Planner.SetLatestValueFn` 改为接收 `(deviceID uint, sensorName string)`，实现侧走多槽 `entries`。**验收**：BMS 设备上 `rsoc` 规则能通过复核并执行；`temperature_2` 规则仍正常（防"一律放行"退化）。
2. **conditions_json 前后端对齐 + 后端校验**（§2.2）：改 placeholder、保存期解析校验、非法结构 400。
3. **触发传感器改字段选择器**（§2.3）：选设备后调 `/unified-data/categories?device_pk=`，下拉展示 `rsoc（%）` 这类"内部名 + 单位"。**验收**：新建规则时无需手打任何字符串。

### B2（P1，产品闭环，约 2–3 天）
4. **规则编辑器给出"当前可用数据"预览**：选设备后展示最近一次上报的字段与值（复用 `/edge-devices/:id/latest-values`），让用户在保存前就看见 `rsoc = 82%`。
5. **保存期校验触发传感器存在性**：`trigger_sensor_name` 必须出现在该设备的 `unified_data` 历史字段集（或最近上报）里，否则 400 并提示"该设备从未上报 `soc`，可用字段：rsoc/total_voltage/…"。
6. **日出规则前置引导**：保存日出规则且坐标缺失时，返回可行动的错误（含跳转节点页的链接/提示），或提供"在规则里直接填坐标"的内联入口（已有字段，只是未突出）。

### B3（P2，闭环到"生效"，约 3–5 天）
7. **命令终态回写规则事件**（台账 AU-02 / P0-4）：规则事件时间线显示 `queued → dispatched → succeeded/failed/unknown`。
8. **多动作物理失败中止 + partial_failure**（台账 AU-01）。

## 6. 与其它需求的依赖

- **与「数据源自动纳入」的关系**：本需求**不依赖**数据源主备。自动化读的是 `unified_data` / 实时字段，与 `data_sources` 表无关（证据：`grep datasource internal/automation` = 0）。所以「数据源自动纳入」不是本需求的前置；但**如果**要做"多来源选权威"（同一逻辑设备两台提供者时用哪台的值），那时才需要数据源域介入。
- **与台账 P0-4 的关系**：本需求的 B3 就是台账 P0-4（自动化闭环）。建议合并排期。
- **与 IS/F4 的关系**：§2.1 是本需求**独占**的阻断项（台账未登记），必须优先修。
