# 日出日落跨本地午夜、启动补发与多副本去重

> 日期：2026-11-18 ｜ 状态：已实施 ｜ 范围：`backend/internal/automation`、`backend/internal/sun`、`backend/internal/api`、`frontend-shared`
> 前置：`docs/分析/日出日落天文计算选型-2026-10-14.md`、`docs/分析/日出日落与多动作-实施计划-2026-10-14.md`

## 1. 结论

| 问题 | 旧行为（实测） | 现行为 |
|---|---|---|
| 偏移把 fireAt 推过本地午夜 | 规则**一次都不触发**（0 次） | 按 D-1/D/D+1 三日候选触发；同一场事件只触发一次 |
| 进程停机/重启跨过事件 | 静默跳过，事件表无任何记录 | 首 tick ≤10 分钟补发一次；超窗落 `missed_solar_event` 审计 |
| 配置晚于事件（事件后新建/编辑/启用） | 不补发 | **不变**，仍不补发（2026-11-17 裁决） |
| 表单看不到今天几点日出/日落 | 只有「日落前 30 分钟」这句相对文案 | 预览今天日出/日落；偏移跨午夜显式提示「次日 00:46 触发」 |
| 触发最多晚 59 秒 | 固定 1 分钟 tick | 最近的 sun fireAt 提前唤醒（≤1 秒），1 分钟 tick 兜底 |
| 滚动发布两个容器并存 | 同一场事件各下发一次设备动作 | `automation_sun_fires` 唯一键认领，全局只执行一次 |

## 2. 问题与实测

### 2.1 P0：偏移跨本地午夜时永远不触发

复现（北京 39.9042,116.4074 / Asia/Shanghai，2026-06-21）：

| 规则 | 事件时刻 | fireAt | 旧实现触发次数 |
|---|---|---|---|
| 日出，偏移 -600 分钟 | 2026-06-21 04:45:55 | 2026-06-20 18:45:55 | **0** |
| 日落，偏移 +300 分钟 | 2026-06-21 19:46:19 | 2026-06-22 00:46:19 | **0** |

根因：求值器只取「`now` 所在本地日的那一场」事件计算 fireAt，再按 `prevTick < fireAt <= now` 判边沿。
偏移把 fireAt 推到相邻本地日后，到真正 fireAt 时 `now` 已属于新的一天，算出来的是**再下一场**事件，
于是 `now < fireAt` 恒成立——永远等不到。

影响面：`|offset|` 大于「事件时刻到本地午夜的距离」时命中。中国境内日常 ±60 分钟基本碰不到，但：

- UI 允许 ±720 分钟（`handler_automation.go` 的 `sunMaxOffsetMinutes`），没有任何跨午夜提示；
- 高纬夏季日落 23:30+ 配 `+60`、日出 03:30 配 `-300` 就会跨日；
- `next_run` 用同一份逻辑，界面也会把"下一次"报到错误的日期。

### 2.2 P1：停机跨过事件时静默跳过

2026-11-17 的"不补发"裁决（A-3）本意是拦住两类错误：

1. 进程重启后把几小时前的日出/日落**重放**一次并真实下发设备动作；
2. 规则在事件之后才新建/编辑/启用，却按新配置补执行旧事件。

但它同时把"服务不可用导致的错过"也变成了静默跳过：部署窗口、崩溃重启撞上事件时刻，
当天规则就是不动，事件表里连一行都没有——用户只能看到"规则今天没生效"，无法区分是配置错还是停机。

## 3. 方案

### 3.1 候选事件集（P0）

`sunCandidatesAround`（`backend/internal/automation/sunwindow.go`）一次求值取三日候选：

```text
eventDate ∈ {D-1, D, D+1}  （D = now 在规则时区下的本地日）
eventAt   = 该日日出/日落
fireAt    = eventAt + offset
```

求值器按两种方式选"本 tick 该处理的那一场"：

- 正常 tick：`prevTick < fireAt <= now`（真正跨过事件时刻的那一轮）；
- 首 tick（`prevTick` 为空）：取"最近一场已发生的事件"，交给补发窗口判定。

`sunStates[ruleID]` 从"tick 的本地日"改为"**事件所属本地日**（eventDate）"。跨午夜时二者不同；
用 tick 日期会让同一场事件在次日再处理一次，或用相邻日的事件顶替本场。

`next_run` 用同一候选集：先找"本次 tick 区间内即将触发"的候选，再找"下一个未来 fireAt"；
跨午夜时 detail 会写触发日（如 `日落 19:46（06-22 00:46 触发）`），避免用户误以为规则配错。

### 3.2 启动补发窗口与 missed 审计（P1）

首 tick 的判定（`evalSunEventFirstTick`）：

| 条件 | 行为 |
|---|---|
| `UpdatedAt >= fireAt`（配置晚于事件） | 跳过，不补发、不审计 |
| 事件已过 ≤ 10 分钟，且库侧无该事件审计行 | 补发一次，`EventAt` = fireAt |
| 事件已过 > 10 分钟，且库侧无记录 | 落 `missed_solar_event` 审计，不执行 |
| 库侧已有记录（任意 result） | 跳过（防重复设备动作） |

安全细节：

- **库侧去重按 `event_at ±2 分钟` 查，不只看 `executed`**。上一次可能落的是 `failed_gate` / `pending_confirm` /
  `missed_solar_event`，它们都证明系统已为这场事件做过决策；补发会重复下发设备动作。
- **查询失败按"已记录"处理**（fail-safe）：重复动作的代价高于漏一次补发。
- 只有首 tick 走补发窗口；进程运行期间的 tick 迟滞（GC/时钟跳变）不触发补发。
- `missed_solar_event` 只表示"事件存在但没执行"，与"今日没有该事件"（`suppressed_no_solar_event`）分开；
  前者没有任何动作进入执行路径，与 `failed_*` 也不同。

为什么没有新增 `fired_late` 结果码：`result` 表达的是**执行结果**（补发仍可能是 executed / pending_confirm /
failed_gate），把"迟到"塞进去会覆盖真实结果。迟到由审计行的 `event_at` 与 `triggered_at` 差值 + 日志可见。

### 3.3 缓存淘汰窗口（配套）

求值器现在每 tick 查三日事件，而 `sun.Cache.pruneLocked` 原先只保留 `{前一日, 当日, 次日}`。
三日查询会互相淘汰（查次日挤掉前一日，下一 tick 查前一日又挤掉次日），实测 A-18 出现 `2 → 4` 次重算，
缓存形同虚设。淘汰窗口改为 `{today-2 … today+2}`（5 日 × 2 事件），仍是常数级，且覆盖三日候选 + 次日预热。

### 3.4 表单预览（P3）

新增只读端点 `GET /api/v1/automation-rules/sun-times`（注册在 `/:id` 之前）：

```text
GET ?latitude=39.9042&longitude=116.4074&timezone=Asia/Shanghai
    &date=2026-11-18&kind=sunset&offset_min=300
→ { timezone, date, sunrise:{at,status}, sunset:{at,status},
    selected:{kind,offset_min,event_at,fire_at,crosses_midnight,status} }
```

- 判据全部在后端（`sun.SunEvent` + 同一套归日/极昼极夜语义），前端不复刻；
- `status != ok` 时 `at` 必须缺席（极昼/极夜不得用零值时间冒充）；
- `crosses_midnight` = `fire_at` 与 `event_at` 不在同一规则本地日；
- 规则表单在位置/偏移变化后 300ms 防抖请求，显示「今天（11-18）：日出 07:02 ｜ 日落 16:56」
  与「本规则：日落 19:46，后 300 分钟 → 次日 00:46 触发」；跨午夜/极昼极夜用 warning 色。

### 3.5 精确唤醒（P2）

`StartWindowTicker` 从固定 1 分钟 ticker 改为**单 goroutine**循环：

```text
wait = min(1 分钟, 最近 sun fireAt - now + 1s)
```

- 事件到点后 ≤1 秒唤醒，`time_window` 仍按 1 分钟兜底；
- 必须单 goroutine：tick 与提前唤醒若各起一个 goroutine 并发调用 `evalTimeWindows`，
  两次求值会交错使用对方的"上一轮时刻"，边沿判定可能漏触发/重复；
- 早醒不改变判定：`prevTick < fireAt <= now` 没跨过就什么都不做（冷却/配置变更同样拦住）；
- `nextSunWakeAt` 只返回"未来"的 fireAt，事件后自动指向次日。

### 3.6 跨进程认领（P2）

`automation_sun_fires` 表：唯一键 `(rule_id, event_date, kind)`，触发前先
`INSERT ... ON CONFLICT DO NOTHING`；`RowsAffected == 1` 的进程才交给 Planner。

- `event_date` 是**事件所属本地日**，不是 fireAt 的日期（跨午夜时二者不同）；
- 认领在 `fireSunEvent` 内部、交给 Planner 之前完成；认领失败不写冷却锚点；
- 认领是 at-most-once：抢到后崩溃则本场不执行，靠 `missed_solar_event`/`executed` 缺失可见；
- 写库失败按"未抢到"处理（fail-safe）：重复下发设备动作的代价高于漏一次；
- 认领表每日清理 14 天前数据（每规则每天 2 行，规模有界）。

这层保护也覆盖**滚动发布**：旧容器尚未退出、新容器已启动的几秒里，两个进程都可能
判定"跨过了事件"，唯一键保证只有一次真实设备动作。但 `time_window` / `sensor_threshold`
没有这层保护，`deploy/prod/TOPOLOGY.md` §7 的单副本约束**没有放宽**。

## 5. 语义边界与安全

- **不补发**：窗口外、配置晚于事件、库侧已有记录、库查询/认领失败。
- **单副本约束**：`windowStates` / `triggered` / `configChanged` 仍在进程内存；
  日出日落有认领表保护，`time_window` / `sensor_threshold` 没有，扩容仍需分布式互斥。
- **触发精度**：日出日落 ≤1 秒；`time_window` 仍 1 分钟。
- **事件日期口径**：`eventDate` 取规则时区下的本地日，与 `SunEvent` 的归日口径一致；
  `sunStates` / 认领键都用它，跨日不需要额外清理任务。

## 8. 回滚

回滚本次改动即恢复旧行为：

- `evalSunEventRule` / `nextSunEvent` 退回单日事件（跨午夜规则重新变成不触发）；
- 首 tick 补发分支与认领表删除（重启后静默跳过、滚动发布可能重复）；
- `missed_solar_event` 常量与三向白名单可保留（旧代码不会写入）；
- `automation_sun_fires` 表可保留（旧代码不读；删表也不影响其他功能）。

数据兼容：`automation_events` 不需要迁移；`automation_sun_fires` 是新增表，回滚后只是闲置。
