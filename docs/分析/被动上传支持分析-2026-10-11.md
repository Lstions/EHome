# 被动上传究竟要怎么支持 —— 分析 + 真机实测（2026-10-11）

> 用户提问（Round 258）：**「就不能优化支持一下被动上传吗？被动收到数据时就放在一个
> 缓冲区里，如果是读取固定长度的数据同时检查一下是否达到要读取的长度，达到了就直接上传。
> 否则让调度器上传，调度器不是会定时检查嘛。分析一下，究竟要怎么支持」**
>
> 本文先逐条对照用户的三点方案，给**已实现 / 需新增**的结论；再给真机实测证据；
> 最后报告实测过程中**发现的、比被动上传更严重的缺陷**。

口径：**实测** = 本机真机 S3P 测得；**读码** = 源码/IDF 源码确认；**推算** = 由前两者推导。

---

## 一、结论先说

| 用户的方案 | 状态 | 依据 |
|---|---|---|
| ① 被动收到数据就放进缓冲区 | **已实现** | `rx_append_from_event()` bus_worker.c:1907 |
| ② 定长命令达到 `read_size` 就直接上传 | **已实现** | `bus_rx_boundary_length()` bus_rx_boundary.h:47-49 |
| ③ 否则由调度器定时检查上传 | **已实现**（落点不是 scheduler_task，是 rx_task） | `expire_uart_state()` :2261 → `complete_idle_response()` :2086；deadline 由 `rx_wait_ticks()` :2326 算出 |

**⇒ 被动上传早就支持了。三点没有一条需要"新增"。**

**但实测中撞到一个 BLOCKER 级缺陷：**
**在正常负载下设备会以 ~9 次/60s 的频率因堆 double-free 崩溃重启**
（`assert failed: tlsf_free tlsf.c:630 (!block_is_free(block) && "block already marked as free")`）。
这就是压测报告里**一直没定位的「~4.8s 周期性停顿」的真因** —— 那不是停顿，是**重启**。

## 二、逐条对照用户的三点方案

### ① 被动收到数据就放进缓冲区 —— 已实现

```c
// bus_worker.c:1907  rx_append_from_event()
static void rx_append_from_event(bus_runtime_t *rt, int idx, uint8_t *rx, size_t rx_cap)
{
 stream_rx_t *s = &s_streams[idx];
 for (;;) {
  size_t n = bus_dma_read(&rt->bus_ctx[idx], rx, rx_cap);
  if (n == 0) break;
  s_last_rx_us[idx] = esp_timer_get_time();     // ← 记"最后收到字节的时刻"
  ...
  memcpy(s->buffer + s->len, rx, n);            // ← 入缓冲区
  s->len += n;
  emit_ready_stream_chunks(rt, idx, s_last_rx_us[idx]);
  if (n < rx_cap) break;
 }
}
```

缓冲区**归属**：`s_streams[idx]`，每通道一份，`buffer[512]` + `len` + `overflow`
（`bus_worker.h:172-179`，`STREAM_RX_BUF_SIZE = 512`）。
RX 路径**已是中断驱动**：硬件中断 → IDF 事件队列 → 队列集 → `rx_task` 阻塞等待
（`bus_dma.c:667 uart_set_rx_timeout(port, 4)` + `uart_driver_install`）。
不需要"实现中断回调"——它已经存在（§224.1 已记录）。

### ② 定长 `read_size` 达到就直传 —— 已实现

```c
// bus_rx_boundary.h:43-50
static inline size_t bus_rx_boundary_length(size_t buffered, bool pending,
                                             bool channel_cmd_v2, uint32_t read_size)
{
    if (buffered == 0 || (pending && channel_cmd_v2 && read_size == 0)) return 0;
    size_t target = read_size > 0 ? (size_t)read_size : BUS_RX_FIXED_BLOCK_SIZE;
    return buffered >= target ? target : 0;
}
```

`read_size > 0` ⇒ `buffered >= read_size` 即返回 `read_size` ⇒ 立即上传。**"达到就直接上传"就是现状。**

⚠ **但真被动路径拿不到 `read_size`**：调用点 `bus_worker.c:1820` 是
`pending ? pcmd.read_size : 0` —— **没有 pending 命令时恒传 0**。
所以"无 pending（真被动）+ 定长"这一组合，**当前只能靠 512 B 固定块或静默兜底**，
走不到"达到 N 字节即上传"这条快路。

⇒ **这是三点里唯一可以真正优化的一项**（见第四节建议 1）。

另注：`pending && channel_cmd_v2 && read_size == 0` 时返回 0（不上传）。
这不是遗漏，是 2026-10-03 的**有意设计**：V2 的 `read_size` 是节点 RX *窗口*（≤256），
不是厂商帧长承诺（`bus_worker.c:2004-2013` 有完整推理）。
V2 的权威帧边界是**行静默**。

### ③ 否则由"定时检查"上传 —— 已实现，但落点不是 scheduler_task

用户说"调度器不是会定时检查嘛"。**方向对，落点不同**：

- **不是** `scheduler_task`（`scheduler.c:824`，1ms/10ms 节拍）——它只管**下发**命令，
  不碰 RX 完成；`scheduler.c:796` 注释明确 `"rx_task handles passive"`。
- **是** `rx_task`（`bus_worker.c:2352`）：

```c
while (1) {
  member = xQueueSelectFromSet(s_uart_event_set, rx_wait_ticks(rt));  // ← 超时由 deadline 算出
  if (member) { ...handle_uart_event... }
  completions += expire_uart_state(rt);      // ← "定时检查"就在这里
  ...
}
```

`rx_wait_ticks()`（`:2326`）对**每个有数据的通道**取
`deadline = s_last_rx_us[i] + UART_IDLE_THRESHOLD_US` 的最小值，
`xQueueSelectFromSet` 就在那个时刻超时返回 ⇒ `expire_uart_state()` →
`complete_idle_response()`（`:2086`：`now_us - s_last_rx_us[idx] < UART_IDLE_THRESHOLD_US` 则返回 false）
→ `emit_buffered_frame()`（`:1958`，**唯一写者**）。

**这是事件驱动 + 一次性 deadline，不是轮询**（§228.2 任务审计已确认；
`RX_WAKE_PERIOD_MS = 250` 只是生命周期兜底）。

**两条完成路径互斥且不重复**（`:1946-1957` 注释）：
两者都 funnel 进 `emit_buffered_frame()`，谁先赢谁清 `s_last_rx_us`，另一个看到 0 立即返回。

## 三、真机实测：被动路径确实能上传

### 3.1 实验设计（如何造出"真被动"通道）

|---|---|---|
| 设备 | S3P `30EDA0A9A808` / `/dev/ttyACM1` | 16MB，烧 `b8fdde6d`（idle=2ms） |
| 对端 | `/dev/ttyUSB1` = **CH340**（`1a86:7523`）→ UART1 GPIO4/5 | `udevadm info` 实测 |
| 通道 | `channels.id = 104`（UART1） | 115200，`dma_enabled=false` |
| **造被动** | 把 ch104 的 5 个 `edge_devices` 全 `enabled=false` ⇒ 重新下发 manifest | |
| 装置 | `__scratch_v3/bin/passive_sender.py` | **只写不读**，无请求-响应 |

**manifest 侧验证**（设备日志实测）：

⇒ **无 pending 命令、无 `read_size`** = 真正的被动通道。

上报侧验证：所有事件都是 `request_id=0, edge_device_id=0` ⇒
`DataEvent.IsPassive()` 为真（`databus/bus.go:29`）⇒ 走 `WSPushConsumer`
（`consumers_light.go:63`）广播 `channel_data`。

### 3.2 实测结果

| 实验 | 打的帧 | 上报 | 每秒分布 |
|---|---|---|---|
| A（10ms 间隔 15s） | 1450 | **763** | s03=96, s04=97, s05=97 / s08=**12** / s09=97, s10=97 / s15=75, s16=97, s17=95 |

**帧内容完整**：`raw_hex = 01030400010000abf3`（9 B，含 CRC），`seq` 单调递增，
**一帧一条上报，无合并、无截断**。

**结论（实测）**：
1. **被动上传通路完全可用** —— 不需要任何新代码。
2. **干净窗口内的持续速率 ≈ 97 帧/s**（连续 3 秒 96/97/97）。
3. 但存在**多秒级空窗**（s06/s07 全空、s11~s14 几乎全空），把均值拖到 51/s。

## 四、⚠ 实测中发现的 BLOCKER：堆 double-free 导致重启

### 4.1 现象

**在完全没有改动代码的情况下**，只要链路有负载，设备就崩溃重启：

```
E (7257) esp-tls-mbedtls: write error :-0x6C00        ← MBEDTLS_ERR_SSL_INTERNAL_ERROR
E (7258) esp-tls-mbedtls: read error :-0x004C
assert failed: tlsf_free tlsf.c:630 (!block_is_free(block) && "block already marked as free")
...Backtrace...
ELF file SHA256: 0f162113d
Rebooting...
```

### 4.2 Backtrace 解码（`fence_s3p-n16` ELF，SHA256 与设备一致）

```
tlsf_free                       heap/tlsf/tlsf.c:630        ← 断言点
multi_heap_free_impl            heap/multi_heap.c:240
heap_caps_free                  heap/heap_caps_base.c:86
free                            esp_libc/src/heap.c:34
esp_tls_internal_event_tracker_destroy   esp-tls/esp_tls_error_capture.c:50   ← 二次 free
esp_tls_conn_destroy            esp-tls/esp_tls.c:188
tls_esp_close                   components/tls_esp/tls_esp.c:253
tcp_release_handle              components/link_tcp/link_tcp.c:170
tcp_send                        components/link_tcp/link_tcp.c:235          ← 发送路径
link_tcp_read                   components/link_tcp/link_tcp.c:82           ← 接收路径
link_rx_adapt_read / rx_pump_step / session_poll
devlink_task                    main/device_link_wiring.c:1039
```

**关键：同一份 backtrace 里同时出现 `tcp_send`（:235）与 `link_tcp_read`（:82）两条路径的
`tcp_release_handle` 调用点。**

⚠ **口径说明（不夸大证据）**：ESP-IDF 的 Backtrace 是**栈扫描**，不是精确的调用链，
栈上残留的返回地址也会被打印出来，而 `tcp_send` 并不调用 `link_tcp_read`
⇒ **不能**据此断言"这两帧构成调用链"。可靠的只有一条：
**崩溃点是 `esp_tls_internal_event_tracker_destroy()` 对同一个 `error_handle` 二次 `free()`**。
"两个任务并发释放"的**真正依据是 4.3 的代码事实**（`c->handle` 无锁 + 两个任务都能走到关闭），
不是这段栈。

### 4.3 根因（读码）

```c
// link_tcp.c:166  —— 唯一的释放点
static void tcp_release_handle(link_tcp_ctx_t *c)
{
    if (c == NULL || c->handle == NULL) return;   // ← 非原子检查
    if (c->cfg.io != NULL && c->cfg.io->close != NULL) {
        c->cfg.io->close(c->handle);              // → tls_esp_close → esp_tls_conn_destroy
    }
    c->handle = NULL;                             // ← 太迟
}
```

`c->handle` **没有任何锁保护**（全仓 `grep mutex|Semaphore|lock` 在
`link_tcp.c` / `session.c` / `link.c` / `rx_pump.c` / `link_rx_adapt.c` = **0 命中**），
而它有**两个并发调用方**：

| 任务 | 调用链 |
|---|---|
| `dev_link`（prio 5） | `session_poll`（`device_link_wiring.c:1039`）→ `rx_pump_step` → `link_tcp_read`（`:50`/`:82`） |
| `report_tx` | `msg_handler_send_data_report` → `msg_handler_publish` → `transport->ops->send` → `sess_tx_send` → `session_send` → `tcp_send`（`:235`） |

两个任务同时读到 `c->handle != NULL` ⇒ **都调 `io->close()`** ⇒
`esp_tls_conn_destroy()` 对同一个 `tls->error_handle` 调两次
`esp_tls_internal_event_tracker_destroy()`（IDF 源码 `esp_tls.c:188`）
⇒ `free()` 同一块 ⇒ **tlsf 断言**。

（`9cc045be` §216 引入 `tcp_release_handle` 时修的是"socket 泄漏"，
只考虑了"必须释放"，**没有考虑"两个任务都会走到这里"**。仓库里
`docs/设计/3.0-实施设计-骨架与增量-2026-10-06.md:393` 已预警过 transport
生命周期 double-free 风险，但那是 `deinit/destroy` 的语义问题，不是并发问题。）

### 4.4 频率与触发条件（A/B 实测，同一台设备）

| 场景 | 时长 | tlsf 崩溃 | 重启 |
|---|---|---|---|
| 空闲（无配置活动） | 70s | **0** | 0 |
| 被动配置 + 无负载 | 80s | **0** | 0 |
| 主动轮询 + **从机不应答** | 60s | **0** | 0 |
| 被动 5 fps | 58s | **0** | 0 |
| **主动轮询 + 从机应答（47.85 req/s）** | 60s | **9** | 9 |
| **被动 100 fps** | 78s | **9** | 10 |
| **被动 100 fps（复现）** | 78s | **9** | 10 |

⇒ **与上行负载量正相关**，与是被动还是主动无关。
每次重启前设备 uptime 实测：6274 / 9361 / 7408 / 4293 / 4341 / 7351 / 4341 / 9342 / 6418 ms。

### 4.5 ⭐ 这就是「~4.8s 周期性停顿」的真因

`docs/验证/峰值性能压测-2026-10-10.md` 长期挂着一条未定位项：

> 「1. **定位 ~4.8s 的周期性停顿**（吞吐波动 30~56 req/s 的主因；中位延迟已稳定在 7.44ms）」

本次实测同机同工具：`slave_fast2.py` 60s 跑出
`req_per_s=47.85, median=7.47ms, max=**4205.79ms**`，同一时段设备重启 **9 次**，
两次重启间隔 4293~9361 ms。

**⇒ 「停顿」不是调度或协议问题，是设备在重启**（bootloader + WiFi + TLS 握手 ≈ 4.3~9.4s，
期间从机收到的是 TCP 断连后的重发/丢弃）。
这解释了：(a) 为什么中位延迟高度稳定（7.43~7.47ms）而均值被拉到 17.8~31.9ms；
(b) 为什么吞吐在 30~56 req/s 之间随机波动（取决于时间窗内撞上几次重启）；
(c) 为什么"与波特率无关"。

## 五、怎么改（按收益排序）

### 建议 1（BLOCKER，必须先做）：给 `link_tcp` 的 handle 生命周期加互斥

**最小改法**：把 `c->handle` 的**检查+释放+置 NULL** 放进一个互斥区，
或用一个 `SemaphoreHandle_t` / `portMUX`。要点：

```c
static void tcp_release_handle(link_tcp_ctx_t *c)
{
    if (c == NULL) return;
    void *h = NULL;
    xSemaphoreTake(c->lock, portMAX_DELAY);
    h = c->handle; c->handle = NULL; c->handshaked = false;   // ← 先摘指针
    xSemaphoreGive(c->lock);
    if (h != NULL && c->cfg.io && c->cfg.io->close) c->cfg.io->close(h);  // ← 出锁后再关
}
```

"先摘指针再出锁关闭"是关键：保证**只有一个**调用方拿到非 NULL 的 `h`。
⚠ 必须同时审计 `tcp_send` / `link_tcp_read` 里 `c->handle` 的**读取**也走同一把锁
（否则 TOCTOU 仍在：读到旧值后句柄已被释放 ⇒ use-after-free）。
`tcp_send` 的 `c->cfg.io->write(c->handle, ...)` 是在锁外还是锁内，是一个**要单独决策**
的正确性/延迟权衡（锁内会让 TLS 写序列化，直接限制吞吐）。

**验收**：`host_tests/link_tcp_tests.c` 补一条"并发 close 只调一次 `io->close`"的用例
（现有 `test_close_is_idempotent` 是**单线程**幂等，覆盖不到这个竞态）。
真机验收：主动轮询 60s，`tlsf_free` 计数 = 0，`slave_fast2.py` `max` 从 4205ms 回落。

### 建议 2：真被动 + 定长 ⇒ 让 `read_size` 也能生效

**现状**：`bus_worker.c:1820` 无 pending 时传 `read_size = 0` ⇒ 只能攒 512 B 或等静默。
**改法**：在**通道级**存一个"期望帧长"（来自 `ch->config` 或 manifest 新字段），
无 pending 时用它代替 0：

```c
size_t target = bus_rx_boundary_length(s->len, pending,
                                       pending && pcmd.channel_cmd_v2,
                                       pending ? pcmd.read_size : s_passive_read_size[idx]);
```

**代价/风险**：
- 需要 manifest 新增"被动通道期望帧长"字段 ⇒ 后端 + 固件 + 界面三处改动，**属于新特性**。
- 只有在"被动 + 定长协议"场景才有收益；**当前 97 帧/s 的上限不是它决定的**
  （见下），而崩溃才是主要损失。⇒ **优先级低于建议 1**。

### 建议 3（要澄清的量级问题）：97 帧/s 上限来自哪

实测干净窗口 ~97 帧/s。**推算**：被动每帧走
`report_enqueue`（1 块/帧，`REPORT_TELEMETRY_BLOCKS = 8`）→ `report_tx` 任务
→ **每帧一次 TLS record 写**（`msg_handler_send_data_report` → `msg_handler_publish`
→ transport send，**同步**）。`DataBatch`（`msg_handler_send_data_batch`）虽然已接线
（`main.c:675`），但**被动路径没有调用它**。

⇒ 97 帧/s ≈ 每帧 ~10ms 的 TLS 写开销。
**若要让被动高频真正跑起来**，出口是**批量上报**（被动数据按窗口聚合成 `DataBatch`），
而不是改判帧。**这一点需要单独确认后再动手**（先量一帧 TLS 写的时间，
以及 `SupportsBoundedBatch` 是否真的上报给了后端 —— 后者在待办清单里仍标"疑似从不上报"）。

### 不要做的

- **不要把"无 pending 就有字节就交出"当作被动优化**。
  2026-10-10 试过，**host 测试当场抓到会破坏半帧**
  （`test_emit_partial_block_no_emission` 期望 300 B 时不发射），已回退。
  根因：`emit_ready_stream_chunks` 在**每批字节到达后立即**被调用
  （`rx_append_from_event` 内），不是只在静默后调用
  ⇒ **"缓冲区有字节" ≠ "一帧已收完"**。
- **不要删软件静默兜底**：IDF 不保证 FIFO 溢出时发 TOUT 事件。
