## 1. 结论摘要

### 1.1 一句话结论

样例解决的是「**一个可执行文件如何替换自己**」，本仓库面对的是「**一台设备、一个镜像、一份 SPA 如何各自被替换**」。
把 `version.json` + `Updater.exe` 照搬过来是错的；真正值得抄的是三件方法论：

1. **版本必须是构建期注入的单一事实**（样例：CI 传 MSBuild 属性 → `MP_*` 宏）；
2. **投放顺序纪律**（样例：先上传资产、后提交清单）；
3. **状态机在服务层、视图只做投影**（样例：`UpdateService` 不引用任何 UI 类型）。

而本仓库真正缺的不是「执行层」，是**决策层**：
「谁该升级到哪个版本」目前 100% 靠人手点选，且没有任何单调版本比较参与决策 ——
`ota.go:113` 定义了 `compareVersion`，**全仓零调用**。

### 1.2 三条更新链路的分级结论

| 链路 | 现状 | 与样例的差距 | 优先级 | 主要成本 |
|---|---|---|---|---|
| **Web 前端（SPA）** | 静态资源已可安全替换（`index.html` no-cache / `assets` immutable+hash），但客户端不知道换了 | 缺「构建身份 + 检查 + 提示」三件套 | **P0** | 小：1 个端点 + 1 个横幅组件 |
| **服务端镜像** | 有 `/health` 回显 commit，无版本、无清单、无投放顺序 | 缺「发布清单 + 部署前后对账」 | **P1** | 中：清单文件 + 脚本 + `ehomectl` 子命令 |
| **设备固件** | 推送式 OTA 已成熟（ack 重试 / 超时扫描 / Hello 对账 / supersede），**强于样例** | 缺决策层、渠道、撤回；且回滚与下载凭据有**实缺** | **P1/P2** | 大：含实机故障注入 |

### 1.3 五个与直觉相反的判断

1. **设备侧最不该照抄样例**。样例的「客户端拉静态 JSON」在本仓库是能力倒退：本仓库的 `OtaCmd → OtaProg → Hello 补完成` 闭环已经解决「帧丢了怎么办」，静态清单反而把状态一致性丢回给客户端。
2. **版本号不该强行统一**。三件制品发布节奏不同；该统一的是「身份字段集合」，不是数字本身（见 §4.0）。
3. **设备侧不需要「1 天一次检查更新」**。服务端本来就在 `Node.FirmwareVersion` 里掌握每个节点的版本，节流应落在**服务端策略扫描间隔**，而不是让设备发请求（见 §4.3 C2）。
4. **样例的「先资产后清单」在本仓库的等价物不是 `version.json`**，而是「固定镜像 digest + 部署后 `/health` 对账」（见 §4.2）。
5. **最危险的不是「不会更新」，而是更新链路里已经埋了会 100% 失败、或根本无法回滚的路径** —— §3.5 列出三处，其中两处可直接静态证明。

## 2. 样例机制拆解：哪些可迁移，哪些不可

### 2.1 逐项对照

| # | 机制 | 样例实现 | 迁移判定 | 本仓库对应物 |
|---|---|---|---|---|
| 1 | 版本注入链 | CI → MSBuild 属性 → `MP_*` 宏 | ★ **必抄** | 固件有 `PROJECT_VER`；后端只有 commit；前端是 `.env` 常量 |
| 2 | 数字版本与展示标签分离 | 三元组比较 / `tag` 展示 | ◐ 改造后抄 | `Firmware.Version` 是自由文本，比较函数零调用 |
| 3 | 编译期版本常量 | `MAGPIE_VERSION` | ★ 必抄 | 固件等价物已存在；后端应改为构建期常量 |
| 4 | 静态 JSON 清单 | `version.json` + raw 地址 | ✗ 设备侧不抄；◐ 平台侧改造 | 设备：DB `firmwares` 表即清单（更强）；平台：无 |
| 5 | 双通道（稳定/预览） | `main` / `dev` 两分支 | ◐ 抄语义 | `Firmware.Stable` 字段存在，**零消费** |
| 6 | 启动检查 + 1 天节流 | `ThreadPoolTimer` + 墙钟 | ✗ 设备侧；◐ 前端 | 设备无需自检；前端需要节流（§4.1） |
| 7 | 8 态状态机 | 枚举偏序 + 单写入点 | ◐ 已有且更严谨 | `ota.go:24-33` 8 态；DB 为源 + 条件更新 |
| 8 | 服务层单源 + 视图投影 | `Event<>` + 派生布尔属性 | ★ **必抄** | 后端已广播 `ota_progress`；前端有 2 份映射表：一份有「解析后端源码」的门禁，一份仍是手抄（§4.4） |
| 9 | 首页横幅 vs 详情页 | 横幅轻提醒 + 关于页完整信息 | ★ 抄结构 | `App.vue:24` 已有 `NetworkBanner` 挂载点 |
| 10 | 完整性校验 | MD5（弱） | ◐ 已在更好层级 | 设备下载 SHA256 + HTTPS；缺签名 |
| 11 | 外部 Updater 交接 | 搬交接器 → 等退出 → 清陈旧文件 | ✗ 不适用 | 设备用 A/B 分区；服务端用容器替换 |
| 12 | 发布顺序纪律 | 先传资产、后提交清单 | ★ **必抄**（换载体） | 部署手册「不要用 GHCR 旧镜像」是同类纪律的口头版 |
| 13 | 设置持久化 | `settings.json` | ◐ | 前端 `sessionStorage` 足够 |

### 2.2 去掉外壳后的四层结构

样例的实现可以抽象成四层，这四层是本仓库分级补齐的骨架：

| 层 | 问题 | 样例答案 | 本仓库现状 |
|---|---|---|---|
| **L1 身份** | 我是谁？ | 编译期版本常量 + `MP_COMMIT_ID` | 固件强（`PROJECT_VER`）、后端弱（只有 commit）、前端几乎无（`.env` 常量） |
| **L2 决策** | 该不该升？ | 三元组单调比较（相等即不升） | **缺失**：全仓无人用版本号做判断 |
| **L3 执行** | 怎么升、失败了怎么办？ | 下载 → MD5 → 解压 → 交接 Updater → 重启 | **强**：SHA256 + A/B + ack 重试 + Hello 对账（优于样例） |
| **L4 呈现** | 怎么让人知道？ | 服务层状态机 → 两个 ViewModel 投影 | 半成品：后端有 WS 广播，前端三份映射表 |

⇒ 本仓库应**跳过 L3**（已经更好），集中补 L1/L2，收敛 L4。

## 3. 本仓库现状（证据化盘点）

### 3.1 版本事实：同一个系统至少四个版本，互不相等

| 制品 | 事实来源 | 当前值 | 运行时可查 | 问题 |
|---|---|---|---|---|
| 设备固件 | `esp32-collector/CMakeLists.txt:13` `PROJECT_VER` → `main/app_state.c:32` | `2.8.0` | Hello `fw_version`；`Node.FirmwareVersion` | 独立演进，本身合理 |
| 后端 | `backend/cmd/server/main.go:57` `buildCommit`（ldflags 注入） | `unknown` → sha | `/health.commit` | **没有版本号** |
| 后端对外声明 | `backend/cmd/server/main.go:1023-1026`、`backend/internal/api/maintenance.go:171-173` | 字面量 `2.0.0` | `/ping.version` | **硬编码两次**，与任何制品无关 |
| 前端 | `frontend-shared/.env.production:26` | `2.0.0` | 侧栏/登录页 | 构建期常量；三处 fallback 不一致（`MainLayout.vue:378` 是 `2.2.0`） |
| 前端包声明 | `frontend-shared/package.json:4` | `0.0.0` | — | 与展示值无关联 |
| 文档 | `docs/README.md:3` / `docs/设计/固件OTA.md` 头部 | `v3.4` / `v3.6` | — | 与代码版本无映射关系 |

**判断**：`/ping` 是唯一对外承诺「服务在跑 + 版本」的端点，却返回字面量。
因此任何「检查更新」能力都必须**先补身份层**（§4.0），否则新端点只会变成第五个版本。

### 3.2 设备固件 OTA：已具备的能力（这部分不该动）

| 能力 | 实现位置 | 说明 |
|---|---|---|
| 8 态状态机 | `backend/internal/ota/ota.go:24-33` | DB 为唯一事实源；含 `needs_retry`（当前无写入点） |
| 命令 ack 重试 | `ota.go:411-523` | 30s × 3 次，指数退避 |
| 超时扫描 | `ota.go:209-262` | 60s tick / 30min 阈值，条件更新防竞态 |
| 抢占 supersede | `ota.go:380-393` | 同节点新任务把旧任务置 failed |
| Hello 补完成 | `ota.go:684-727` | 终帧丢失时靠重启后的 Hello 对账 |
| 取消闸门 | `ota.go:739-792` | 仅 `pending`/`downloading` 可取消，否则 409 |
| 完整性校验 | 设备侧 SHA256 + 下载票据 HMAC | 优于样例的 MD5 |
| A/B 双分区 | `esp32-collector/partitions/ota_8m.csv` | 无 factory 分区（这放大了 §3.5-C 的后果） |

结论：**L3 执行层不需要任何来自样例的改造**。

### 3.3 Web 前端：产物可安全替换，但没人知道替换了

- `backend/cmd/server/static.go:9-14`：`/assets/*` 带内容 hash ⇒ `immutable, max-age=1y`；SPA 入口 `index.html` ⇒ `no-cache`。
  这套策略本身已经**为「发布即生效」准备好了**：只要有一个可比较的构建身份，前端就能自行发现新版本。
- 但当前没有任何「构建身份」端点：`/ping` 是字面量，`/health` 只有 commit，前端自身版本来自 `.env` 常量。
- 后果：部署新版本后，已打开的标签页继续运行旧 chunk；用户下次刷新才拿到新版。
  更糟的情形见 §7.2 风险表：若镜像重建时删掉旧 `assets`，旧标签页的懒加载 chunk 会 404。

### 3.4 服务端：只有 commit，没有版本与清单

- `.github/workflows/docker-publish.yml` 会产出 `ghcr.io/…:v*` / `:sha-*` 镜像，并把 `GIT_COMMIT` 显式传入 build-arg（注释记录了一次「镜像 label 有 commit 但 `/health` 是 unknown」的事故）。
- 但部署手册明确写着「**不要用 GHCR 的 main/latest**，实测是旧镜像」，生产实际走本机 `docker build -t ehome-new:v2`。
- 于是「部署的是哪份代码」只剩 `/health.commit` 一条线索，**没有版本号、没有镜像 digest、没有上一版是哪个**。

### 3.5 三个已定位的缺口（按严重度排序）

#### A. 固件下载票据 30 分钟，短于任务寿命（严重度：高）

- **现象**：上传固件 30 分钟后再发起 OTA，设备大概率拿不到固件。
- **证据链**：
  - `backend/internal/api/handler_ota.go:193`：上传时用 `30*time.Minute` 生成签名票据，**并存进 `Firmware.URL`**；
  - `backend/internal/ota/ota.go:529`：`SendOtaCommand` 把 `firmware.URL` 原样编进 `OtaCmd`；
  - `backend/internal/api/firmware_download_ticket.go:16-24`：`expiresUnix <= now` 直接判假 ⇒ 下载端点 401；
  - 全仓**没有**任何「按发送时刻重新签发」的路径。
- **影响**：这是「昨天上传的固件，今天点升级」这一最正常的工作流。设备侧表现只是 `3=failed`，日志会被误读为网络问题。
- **修法方向**：票据在 `SendOtaCommand` 时刻按需签发（`Firmware.URL` 只保存**稳定定位**，不保存凭据）；或 OTA 下载改走设备 mTLS 口，票据仅用于人工下载。
- **验收**：上传 → 等待 >30min → 建任务 → 设备日志出现 200 下载而非 401。

#### B. 前端「下载固件」恒 401（严重度：中）

- **现象**：固件管理页点「下载」，后端返回 401。
- **证据**：`frontend-shared/src/api/firmware.ts:46-50` 拼的是 `?token=<jwt>`；而 `backend/internal/api/handler_ota.go:322-335` 只校验 `expires` + `signature` 两个 query 参数，`token` 不参与校验。
- **影响**：一个真实失败的用户路径，且现有前端单测只断言「URL 里带 token」（`api/__tests__/api-wrappers.spec.ts:1173`），把错误契约锁成了「预期行为」。
- **修法方向**：`GET /firmwares` 返回服务端新签的 `download_url`（短 TTL），前端只做展示；不要在浏览器侧拼签名。

#### C. 设备回滚链路未武装，与设计文档矛盾（严重度：高）

- **现象**：`docs/设计/固件OTA.md` §1/§7 声称「A/B 分区 + 30s mark-valid：新镜像启动后验证，失败自动回滚旧分区」，但配置与代码路径表明该链路**不会被执行**。
- **证据链**：
  - `esp32-collector/sdkconfig.defaults:220`：`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=n`；
  - `esp32-collector/main/main.c:555-562`：只有分区状态为 `ESP_OTA_IMG_PENDING_VERIFY` 才置 `s_ota_pending_verify`；该状态**只在 bootloader 回滚开启时**由引导器写入；
  - `main.c:331-332`：`ota_need_confirm` 为假 ⇒ `ota_confirm_valid()`（`components/ota/ota.c:364`）永远不会被调用；
  - `ota.c:385` 的 `ota_mark_invalid_rollback()` **全仓无调用点**；
  - `partitions/ota_8m.csv` 无 `factory` 分区 ⇒ 回滚目标只有另一 OTA 槽。
- **影响**：坏镜像上线后不会自动退回，只能人工刷机（`docs/操作/ESP32刷机指南.md`）。这直接决定「能否开放自动升级」。
- **修法方向**：开启 bootloader 回滚 + 明确「30s 判据到底以什么为准」（当前实现以**首次 StatusReport 成功**为准，不是 30s）+ 实机故障注入；或**显式承认无回滚**，把自动升级永久关闭并在 UI 标注。
- **附带动作**：本仓库已有 `make docs-audit`（声称-实现对账）。本条应作为该门禁的输入样本登记，避免「文档写了 = 已实现」再次发生。

## 4. 方案：三条链路怎么补

### 4.0 共同底座：构建身份（L1）

先补身份，否则后面所有比较都没有意义。

| 制品 | 注入方式 | 字段 |
|---|---|---|
| 后端 | Dockerfile `--build-arg` → `-ldflags -X`（沿用现有 `buildCommit` 通道） | `version` / `commit` / `build_time` |
| 前端 | Dockerfile `ARG VITE_APP_VERSION` / `VITE_BUILD_ID` → `ENV`（Vite 自动读 `import.meta.env`） | `version` / `build_id` / `build_time` |
| 固件 | 现有 `PROJECT_VER`；可选追加 `git describe` | `fw_version` |

新增只读端点（免鉴权，与 `/ping` 同级白名单；**不要**复用 `/health`，后者语义是「进程活着」）。请求：`GET /api/v1/system/version`，响应体：

```json
{
  "version": "2.9.0",
  "build_id": "a1b2c3d",
  "commit": "a1b2c3d9e8f7...",
  "build_time": "2026-11-18T06:12:00Z",
  "api_schema": 3,
  "assets_manifest": "sha256:5f2c..."
}
```

要点：

1. `build_id` 用于**等值比较**，`build_time` 用于**方向判断**（防止回滚后被误判为「有新版本」，见 §4.1）。
2. `assets_manifest` 比 commit 更强：同一 commit 重建产物也能区分（前端 chunk 变化）。
3. `/ping` 的 `version` 改为读该值，删掉两处字面量（`main.go:1023`、`maintenance.go:171`）。
4. 版本策略建议：**制品独立 semver + 平台组合版本**（如 `2026.1118.1`），清单里记录矩阵；不追求「三端同一个数字」。

### 4.1 链路 A：Web 前端「有新版本」提示（P0，最贴近样例）

**为什么可行**：`index.html` 已是 `no-cache`、`assets` 已是 hash+immutable。缺的只是一个可比较的身份与一次提示。

**状态机**（按 Web 语义从样例 8 态收缩为 6 态）：

| 状态 | 进入条件 | UI 表现 |
|---|---|---|
| `idle` | 初始 | 无 |
| `checking` | 发起 `/system/version` | 无（静默，不占位） |
| `current` | `build_id` 相同 | 无 |
| `stale` | `build_id` 不同 **且** 服务端 `build_time` 更新 | 顶部横幅：「系统已更新，刷新以使用新版本」+ [立即刷新] [稍后] |
| `dismissed` | 用户点「稍后」 | 无；本 build 生命周期内不再提示 |
| `error` | 网络/解析失败 | 无（静默，避免和 `NetworkBanner` 的断线提示打架） |

**触发点**（对齐样例「启动即检 + 节流」，但换成浏览器语义）：

1. 首屏挂载后 1 次；
2. **WebSocket 重连成功**后 1 次（部署必然导致 WS 断开重连，这是最自然的信号）；
3. `visibilitychange` 回到前台（≥30 分钟未检查才发）；
4. 30 分钟定时兜底。

**节流与去重**：最少 5 分钟一次请求；「稍后」把 `build_id` 写入 `sessionStorage`，本次会话不再提示同一 build。
**不做自动强刷**：用户可能在填表单；刷新动作必须由点击触发（样例的「以后再提醒我」同理）。

**落点**：`frontend-shared/src/App.vue:24` 的 `NetworkBanner` 同层新增一个 `UpdateBanner`，复用现有视觉（浅底 + 基色文字，满足两主题 4.5:1 对比度）。

### 4.2 链路 B：平台发布清单（P1，样例「先资产后清单」的等价物）

**关键差异先说清**：样例的清单**给客户端读**；本仓库的平台清单**给 CI / 运维读**。消费者不同 ⇒ 不该把清单塞进浏览器端点。
浏览器只需要 §4.0 的轻量 `version`；完整清单是部署物料。

**载体比选**：

| 载体 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 仓库静态 `deploy/release.json` | 可 review / 可 diff / 零运行时依赖 | 需 CI 提交，可能与实际部署脱节 | ★ **推荐**（用部署后对账补足） |
| 镜像 OCI label | 与制品同生共死 | 需 pull 才能读，不便评审 | 辅助 |
| 数据库表 | 可查询 | 部署前数据库可能不可用（鸡生蛋） | ✗ |
| GHCR tag/API | 零维护 | 依赖外部服务与 token | 辅助 |

**建议字段**：

```json
{
  "platform_version": "2026.1118.1",
  "image": { "ref": "ghcr.io/lstions/ehome", "tag": "v2.9.0", "digest": "sha256:..." },
  "build": { "commit": "...", "build_time": "...", "go": "1.27.3", "node": "24" },
  "compat": { "min_firmware": "2.6.0", "api_schema": 3 },
  "rollback": { "previous_digest": "sha256:...", "db_migration": "forward-only" }
}
```

**投放顺序纪律**（这条是样例最值钱的部分，顺序不能换）：

1. 构建镜像并推送；
2. **读回 digest**（不是只看 tag）；
3. 写 `deploy/release.json` 并提交（此时才「挂牌」）；
4. 部署（`docker compose up -d` 用 digest 固定）；
5. 部署后对账：`/health.commit` 与清单一致、`/api/v1/system/version` 与清单一致；
6. 任一不符 ⇒ 用清单里的 `previous_digest` 回滚，并把清单改回。

样例注释写的是「此步应在发布版本之后，因为程序使用 version.json 检查更新」；本仓库的等价约束是「**清单可见时，镜像必须已可拉取**」。

**工具落点**：新增只读子命令 `ehomectl release check`（读清单 + 打 `/health`、`/system/version` 比对），不影响现有启动流程。

### 4.3 链路 C：设备固件能力补齐（P1/P2）

#### C1 台账收紧：让已有字段真正参与决策

> 型号语义、上传校验、固件与节点的关联缺失、以及误刷会不会被设备端拦住，已单独取证为 [固件型号与节点匹配-误刷风险审计](固件型号与节点匹配-误刷风险审计-2026-11-18.md)。本节只保留结论，实施细节以该文 §7.1 与 §7.4 为准。

| 字段 | 现状 | 建议 |
|---|---|---|
| `version` | 自由文本，无唯一约束（`models.go:419-433`） | 校验 semver + 唯一索引 `(target_model, channel, version)` |
| `target_model` | 写入但**零消费**；`Node.Model` 宽度 20 vs `target_model` 64 | 归一化 + 明确「空 = 通用」语义 |
| `min_from_version` | 写入但**零消费** | 决策层使用：低于门槛时拒绝或提示先升中间版本 |
| `stable` | 写入但**零消费** | 改为 `channel`（stable/beta/internal），默认只选 stable |
| 撤回 | **不存在**：`DELETE /firmwares/:id` 直接删二进制再删行（`handler_ota.go:262-292`），不检查在途任务 | 增 `withdrawn` 软删态；有活跃任务时禁止物理删 |

> 最后一行是现存运维陷阱：删掉正在被下载的固件，设备侧只会看到 404/401，而服务端记录仍是 `downloading`。

#### C2 不引入「设备主动检查」（论证）

- 设备版本在每次 Hello/StatusReport 已上报，服务端 `Node.FirmwareVersion` 始终是最新的；
- 让设备「查一下有没有新版」不产生任何服务端不知道的信息，只增加协议面、唤醒与功耗；
- 因此自动升级 = **服务端定时策略扫描**（每节点每天一次，等价于样例的 1 天节流），命中后复用既有 `CreateTask + SendOtaCommand`；
- 设备唯一的配合是「忙时拒绝」：现有 `ota_classify_cmd` 的 BUSY 语义已经覆盖，服务端按 ack 失败重排即可。

#### C3 协议扩展规则（**这是硬约束，先于任何实现**）

| 扩展方式 | 旧固件行为 | 结论 |
|---|---|---|
| 新增消息号 | `components/msg_handler/msg_handler.c:262` `default` 仅 WARN 丢弃 | ✅ 安全 |
| 在已有消息里加字段 | `components/msg_handler/handler_hello.c:115` 未知字段 ⇒ **整条 HelloAck 被拒**，握手作废 | ❌ 破坏性 |
| 复用 `HelloAck.features` 位图（field 2） | 旧固件只读整数，未知位无副作用 | ✅ **唯一安全的语义扩展点** |
| 在 Hello（上行）加字段 | 需逐字段核对旧后端严格校验（`proto_ver` 相等检查） | ⚠ 需单独评估 |

⇒ 结论：**短期不加任何帧字段**。自动升级完全由服务端发起，复用现有 `OtaCmd`；
若将来要下发「有新版本」提示，只允许用 `features` 新位 + 新消息号，绝不给 `HelloAck` 加字段。

#### C4 回滚：先修 §3.5-C，再谈自动化

顺序不能反：**自动升级会把「无回滚」的后果放大到全部设备**。

1. 打开 `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`，确认 `esp_ota_get_state_partition` 在实机上能读到 `PENDING_VERIFY`；
2. 明确「有效」判据：当前实现是「首次 StatusReport 成功」（`main.c:331`），需在文档里写死，不要含糊成「30s」；
3. 在判据失败路径上接入 `ota_mark_invalid_rollback()`（当前无调用点）；
4. 实机故障注入：故意发布一个启动即崩的镜像，验证自动退回；
5. 以上全部通过后，才允许把自动升级从「默认关」改为可开启。

#### C5 下载凭据随任务签发

改法见 §3.5-A：`Firmware.URL` 只存稳定定位（文件名/相对路径），`SendOtaCommand` 时现签短票。
附带收益：`DELETE /firmwares/:id` 不再需要从 URL 反解文件名（`handler_ota.go:295-317` 那段注释描述的历史坑也随之消失）。

### 4.4 链路 D：前端状态投影收敛（P1，低成本高收益）

现状比「三处重复」更整齐，也更值得保护：

- `views/node/components/NodeOtaHistoryCard.vue:77-92` 是**存活的唯一** OTA 状态真源；
- 门禁 `views/node/__tests__/OtaStatusTruthSource.spec.ts` **直接解析后端 `ota.go`** 的 `Status*` 常量做双向相等断言（不得多、不得少）；
- 该门禁的注释本身就是两条历史教训：`NodeDetail.vue` 因「重复真源」被删除（删除前已逐键核实等价），映射曾只覆盖 5 态导致中文界面显示英文状态名。

仍存在的两个漂移点：

1. `components/forms/OTAForm.vue:135-157` 另有一份手抄表，且多出 `flashing`/`completed` 两个后端枚举里不存在的键；其覆盖门禁 `OTAFormStatusCoverage.spec.ts` 也把「8 个字面量」手抄了一遍 —— 后端新增状态**不会**让它变红，正是门禁注释里描述过的缺陷形态。
2. `docs/设计/固件OTA.md` §5 仍引用已删除的 `NodeDetail.vue`（`views/node/` 下已无该文件），属文档债。

建议：**不要**新建「大而全」的 `utils/otaStatus.ts` —— `NodeOtaHistoryCard.vue:54-56` 已明确写明「刻意留在这里」的理由（门禁按文件定位；抽走会让门禁失去定位能力）。
正确做法是让 `OTAForm` 的手抄表接入同一真源断言，或直接复用卡片内映射；若确实要抽公共模块，**必须先改门禁**，否则门禁会静默失去覆盖面。

另：`events.OTACompleted`（`events.go:22` 已定义但**从未广播**）要么接上，要么删除，避免事件名成为第二份真相。

## 7. 不建议照搬，以及风险

### 7.1 不建议照搬的五点

1. **设备端拉静态 JSON**：会把已经解决的「帧丢失/状态对账」问题重新引入。
2. **MD5 校验**：本仓库已是 SHA256 + HTTPS，退回去没有理由。
3. **自替换 Updater 模式**：设备有 A/B 分区、服务端有容器，均不需要「外部进程搬文件」；样例的 `PackageFiles` 版本清单表（990 行）在本仓库没有对应负担。
4. **「发现更新」状态易失**：样例把 `Available` 重置为 `Pending` 并叠加 1 天节流，导致重启后可能看不到更新；本仓库有 DB 真相，**不要**模仿这种内存态设计。
5. **单一渠道**：样例靠 `main`/`dev` 两个分支区分，本仓库应在数据层表达渠道（§4.3-C1）。

### 7.2 风险清单

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| 旧标签页 chunk 404 | 镜像重建删除了上一版 `assets`，旧 `index.html` 仍引用旧 hash | 保留上一版静态产物一个发布周期，或**只做增量目录**；发布说明写清 |
| 多副本导致横幅抖动 | 灰度/多实例新旧版本并存，检查请求落到不同实例 | 要求**连续两次**检查一致才提示；或由负载均衡 sticky |
| 回滚被误判为「有新版本」 | 只比较 `build_id` 不等 | 同时比较 `build_time` 方向（§4.1），只在服务端更新时提示 |
| 自动升级放大无回滚 | 在 C4 完成前开放自动升级 | D6 默认关；P2 验收通过后才可开 |
| 清单与实际部署脱节 | 手工改清单、跳过 CI | `ehomectl release check` 进部署脚本，不一致即中止 |
| 版本号再次分叉 | 新端点未取代旧来源 | P0 顺手删除 `/ping` 两处字面量；CI 比对 `/system/version` 与镜像 label |
