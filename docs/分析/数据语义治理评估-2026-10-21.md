# 数据语义治理评估：边缘设备数据 ↔ 规则引擎 ↔ 数据源 有没有统一规范？

> **状态**: 提案
> **版本**: v1.0
> **日期**: 2026-10-21
> **关联**: [术语表](../设计/术语表.md) | [概念模型](../设计/概念模型.md) | [数据采集与数据链路](../设计/数据采集与数据链路.md) | [数据源主备与故障转移](../设计/数据源主备与故障转移.md) | [自动化策略引擎方案](../设计/自动化策略引擎方案.md) | [架构审计-缺陷与改进台账](架构审计-数据源与自动化与边缘设备-缺陷与改进台账-2026-10-21.md)

## 1. 结论

**分层回答：实体层有统一规范且质量不错；数据语义层（字段名 / 单位 / 值类型）没有任何统一规范 —— 是"四套命名空间 + 三套标签/单位来源 + 零校验门禁"。**

| 层 | 是否有统一规范 | 证据 |
|---|---|---|
| **实体层**（节点/通道/边缘设备/逻辑设备） | ✅ **有且执行得不错** | 术语表 8 个术语权威定义 + 概念模型不变量 + 禁用命名表；DB 表名/Go struct/API 路径/前端组件名四处一致 |
| **协议层**（帧格式/消息类型） | ✅ 有（但文档落后，见台账 XC-01） | C/Go 共享 golden vectors；`protocol/vectors/` |
| **事件层**（WS 事件名） | ◐ 部分 | `internal/events` 包是单一定义源，但 automation 6 个事件名绕过它（XC-09） |
| **数据语义层**（`sensor_name` / `category` / `unit` / 值类型） | ❌ **没有任何统一规范** | 见 §2~§7，本轮全部实测 |

**一句话**：设备数据、规则引擎、数据源三者都在用 `sensor_name` 这一根字符串当"数据身份证"，但这根字符串**没有注册表、没有词表、没有校验、没有单一事实源**——它只是「驱动代码里手写的字面量」和「数据库里出现过的值」。规则引擎写错一个字母不会报错，数据源写错一个类别不会报错。

## 2. 现状：同一根字符串在 5 个地方各写一遍

| # | 位置 | 形态 | 约束 | 证据 |
|---|---|---|---|---|
| 1 | 驱动代码（产出方） | Go 字符串字面量，**169 个不同字段名** | 无 | `grep -rhoE 'Name:\s*"[a-z_0-9]+"' backend/internal/drivers/*.go \| sort -u \| wc -l` → **169** |
| 2 | `unified_data.sensor_name` | `varchar(32)` | 仅 NOT NULL | 生产库 information_schema |
| 3 | `alert_rules.sensor_name` | `varchar(64)` | 仅非空 | `handler_alert.go:397` |
| 4 | `automation_rules.trigger_sensor_name` + `conditions_json` | `varchar(64)` + JSON 文本 | 仅非空；JSON 里 key 还是 `sensor` | `handler_automation.go:850`；`models/automation.go:97` |
| 5 | `data_sources.category`（+ `data_source_health.category`、`failover_logs.category`） | `varchar(32)` | 仅非空 | `service.go:161` |
| 6 | 前端展示词表 | `sensorNameMap`/`sensorUnitMap` **89 条** + `EXTRA_LABELS`/`EXTRA_UNITS` **6+4 条** + 正则族 | 无 | `frontend-shared/src/utils/sensor.ts`、`deviceReadings.ts:21-36` |

**没有任何一处声明"这是唯一事实源"**：
```bash
grep -rn '= "rsoc"\|= "total_voltage"\|Sensor[A-Za-z]* = "' --include=*.go backend/internal | grep -v _test
# → 空（字段名没有任何共享常量，全部是内联字面量）
```

### 2.1 五个字面量最多的消费点（都靠"记得写对"）

- 驱动解析产出：`internal/drivers/*.go`（169 个名字）
- 规则引擎匹配：`matchField(fields, rule.TriggerSensorName)`（`evaluator.go:884-891`）
- 告警匹配：同域
- 数据源健康匹配：`if _, ok := want[src.Category]; !ok { continue }`（`service.go:615`）
- 前端渲染：`sensorNameMap[code] || code`（8 处 fallback，`DataPanel.vue:177/665/926/975/1106/1129`、`Dashboard.vue:360/480`）

## 3. 词表本身：四个候选"权威来源"，没有一个能用

| 候选 | 设计意图 | 生产实际 | 结论 |
|---|---|---|---|
| `driver.GetSensorDefinitions()`（驱动接口方法，注释写"for HA Discovery"） | 驱动自报传感器定义 = 天然词表 | **生产零调用者**；唯一消费者 HA Discovery 已随 MQTT 删除（2026-10-08） | **孤儿 API**（`grep '\.GetSensorDefinitions()' \| grep -v _test` → 空） |
| `device_models` 表 + `/device-models/:id/fields` | 型号级字段定义 | **生产 0 行**；`/device-categories` 只是对空表做 `DISTINCT type` | **空表** |
| `device_configs.parser.fields[]` | 解析器声明的字段名 | **生产 0 行 device_configs**；两台真实设备 `device_config_id=0`，走驱动回退 | **空** |
| `GET /unified-data/categories` | 返回"可用类别" | `SELECT DISTINCT sensor_name FROM unified_data`——**是观测结果不是词表**；受 retention 分区 DROP 影响（字段从词表消失） | **不是词表** |

> 这四条里，前三条本来都可以当"声明式词表"（declaration），实际全是空的；第四条是"事后观测"（observation）。
> 结果：**系统里唯一存在的"字段名清单"是「历史上恰好入库过的字符串」**。设备没上报过的字段，规则引擎就配不出来——而用户也不知道它存在。

## 4. 标签 / 单位：前后端双源，覆盖率 46%

### 4.1 后端有字面量、前端无标签 = 88/163（54%）

```bash
# 后端静态字段名（169，去掉 6 个 ack 回读伪量 → 163）
grep -rhoE 'Name:\s*"[a-z_0-9]+"' backend/internal/drivers/*.go | sed -E 's/.*"([a-z_0-9]+)"/\1/' | sort -u
# 前端有效词表（sensorNameMap 89 + EXTRA_LABELS 6 = 94）
# 差集 → 88 个字段没有中文标签，UI 直接显示原始 key
```

前端有 `sensorNameMap[key] || key` 的 8 处 fallback，所以**不会报错，只会把 `cell_ov_protect` 原样显示给用户**。

### 4.2 "僵尸条目" 19 个

前端有、后端静态字面量里没有：`soc / soh / co2 / pm25 / uv / uv_index / light / noise / energy / power / frequency / voltage / wind_speed / rain_accum / rain_intensity / temperature_1..3 / balancing`。
其中 `temperature_N` 由正则族生成（合法），其余多为历史/未来预留——**没有门禁能告诉你哪些是死的**。

### 4.3 生产库 13 个字段里 4 个不在主 map

`cell_count / cycle_count / nominal_capacity / software_version` 不在 `sensorNameMap`，靠 `deviceReadings.ts` 里的 `EXTRA_LABELS`/`EXTRA_UNITS` 补丁表（**另一个文件的第二套词表**）才能显示中文。

### 4.4 单位是无约束字符串，且语义被重载

后端 `Unit:` 字面量分布（`internal/drivers/*.go`）：

| 值 | 次数 | 问题 |
|---|---:|---|
| `""`（空） | 49 | 无量纲/未标注混在一起 |
| `°C` / `V` / `A` / `%` / `Ah` / `kWh` / `W` / `Hz` | … | 正常 |
| `ack` | 12 | **不是单位，是"回执"这种值类型** |
| `bitmask` | 8 | **不是单位，是值编码方式** |
| `raw` | 5 | **不是单位，是"未解释"** |
| `state` | 2 | **不是单位，是枚举** |
| `%RH` vs `%` | 3 vs 16 | 同一物理量两种写法 |
| `Lux` vs `lux` | 4 vs — | 大小写不统一 |
| `S` / `mV` / `mΩ` / `VA` / `bit/s` / `hPa` / `°` / `次` / `串` | … | 混用 SI 与非 SI |

**单位是承重的**：图表分轴按 `a.unit === unit` 字符串相等判断（`LineChart.vue:133/164`）⇒ `%RH` 与 `%` 会被切成两根 Y 轴；`bitmask` 被当单位后，图例显示 `(bitmask)`。

**前端还有第二套单位源**：`DataPanel.vue:666/732` 写 `unit: category.unit || sensorUnitMap[category.code] || ''` —— 后端已经给了 `unit`，前端再用自己的 map 兜底/覆盖，两者可分歧。

## 5. 校验与门禁：零

### 5.1 写入侧只查空字符串

```go
// handler_alert.go:397
if sensorName == "" { return "sensor_name 不能为空" }
// handler_automation.go:850
if req.TriggerSensorName == "" { ... }
// datasource/service.go:161
if strings.TrimSpace(in.Category) == "" { ... }
```

**没有**：存在性校验（该设备是否上报过这个字段）、字符集校验、长度校验、词表校验。

### 5.2 列宽不一致，且超长是 DB 硬报错

| 表.列 | 宽度 |
|---|---:|
| `unified_data.sensor_name` | **32** |
| `data_sources.category` / `data_source_health.category` / `failover_logs.category` | **32** |
| `alert_rules.sensor_name` | **64** |
| `automation_rules.trigger_sensor_name` | **64** |
| `unified_data.unit` | 16 |

实测（事务内回滚，未留痕）：`INSERT ... varchar(32)` 放 33 字符 → `ERROR: value too long for type character varying(32)`。

⇒ 一个 33–64 字符的字段名**可以在告警/自动化里配置成功，但永远匹配不到数据**（数据侧写不进去）。当前静态最长 27、动态族最长 ~18，属**潜在**而非现行缺陷，但**没有任何机制阻止它发生**。

### 5.3 CI 5 个 job，没有一个查字段语义

`.github/workflows/test.yml`：Backend lint+test / Backend PG integration / Backend simulation / Frontend lint+test / Firmware host tests。
`grep -rn 'sensor' .github/workflows/test.yml` → **空**。

## 6. 一个被静默丢掉的数据维度：字符串型传感器

- `parser.Field` 与 `drivers.SensorData` 都有 `StringValue`（注释：hardware version / serial number）
- 嘉佰达驱动确实产出：`hardware_version`、`serial_number`（`jiabaida_parse.go:437/499`，`Value=0` + `StringValue=...`）
- 但 `models.UnifiedData` **没有 StringValue 列**，落库循环（`consumers_heavy.go:371-381`）只拷 `Name/Value/Unit` ⇒ **字符串值恒丢失**，入库只剩 `value=0`
- 生产实测：`software_version` 存的是 `32`（把版本字节当 float），真字符串无法表达

⇒ 数据模型实际是 `(name, float64, unit)`，**不是通用的"传感器读数"模型**；这也是"单位/值类型混用"的结构性根因。

## 8. 治理方案（5 层，按杠杆排序）

### L1 · 词表 = **三源投影**，不是"权威表"

> ⚠ 关键设计修正（回答"是否会导致边缘设备数据强耦合"，见 §11）：
> catalog 必须是**只读投影 + 可选丰富层**，**不是**数据写入的前置条件。

```sql
-- 丰富层（唯一需要人维护的部分）：只放"描述性元数据"，不放任何业务语义
CREATE TABLE sensor_catalog (
  name        VARCHAR(64) PRIMARY KEY,          -- 同一根字符串
  label_zh    VARCHAR(32),                      -- 中文标签（可空 = 未标注，降级显示原名）
  unit        VARCHAR(16),                      -- 受控词表（见 L4）
  value_type  VARCHAR(16),                      -- number|boolean|enum|bitmask|string|raw
  precision   SMALLINT,
  status      VARCHAR(16) DEFAULT 'active',     -- active | deprecated
  created_at, updated_at
);
-- 注意：**没有** source/device_types 静态列、**没有** 被 unified_data 引用的 FK
```

**三源投影（API 返回的合并视图，不落库）**：

| 源 | 产生方式 | 作用 |
|---|---|---|
| **① 声明**（declaration） | 启动时读 `drivers.Registry` 的 `GetSensorDefinitions()`（8 个驱动已实现）+ `device_configs.parser.fields[]` | 新设备**未上报前**规则编辑器就能看到字段 |
| **② 观测**（observation） | `SELECT sensor_name, max(timestamp) FROM unified_data GROUP BY 1`（窗口可配） | 覆盖"声明漏了但实际在产出"的字段；**只读派生，零写入** |
| **③ 丰富**（enrichment） | `sensor_catalog` 人工/脚本补 label/unit/precision | 展示质量；缺失即降级显示原名 |

`GET /api/v1/sensor-catalog` 返回 ① ∪ ② 左连接 ③，每项标注 `sources: [driver|config|observed]` 与 `labeled: bool`。
**设备类型不静态存**：由观测派生（哪台 edge_device 报过这个字段），避免"静态映射腐烂"。

### L2 · 写入侧：声明在启动期，观测靠查询 —— **热路径零依赖**

1. **声明（启动期，内存）**：`GetSensorDefinitions()` 从"孤儿 API"变成**注册期校验项**（与现有 `Register` 同处），结果存进 registry 的内存快照。**不写 DB、不在每帧做任何事**。
2. **观测（查询期，零写入）**：`GET /sensor-catalog` 时对 `unified_data` 做一次 `GROUP BY sensor_name`（带时间窗 + 索引），**不在 ingest 路径写任何表**。
   - 若担心查询成本：可加一个 5 分钟粒度的物化投影，但仍是**后台任务**，不是数据面依赖。
3. **未标注字段**：不自动建行。API 直接返回 `labeled=false`，前端降级显示原名；后台任务可按需把"观测到但未标注"的字段列出来供人补标签（**不阻塞任何数据）**。
4. **已消失字段**：不删，由 `status=deprecated` 人工标记；数据仍可解释。

### L3 · 消费侧：全部改查 catalog

| 消费方 | 现状 | 改为 |
|---|---|---|
| 告警规则 | 自由字符串 | 校验 `name ∈ sensor_catalog`，否则 400 |
| 自动化规则 | 自由字符串 | 同上 |
| 数据源 category | 自由字符串 | 同上 |
| 前端标签 | `sensorNameMap`+EXTRA | **删掉两套 map**，用 `GET /api/v1/sensor-catalog` |
| 前端单位 | `sensorUnitMap` 兜底 | 只用 catalog.unit（后端已是权威） |
| 图表分轴 | `a.unit === unit` | 用 catalog.unit（受控） + value_type |
| 精度/小数位 | `deviceReadings.ts` 按 key 硬编码 | catalog.precision |

### L4 · 单位受控词表 + value_type 分离

- `unit` 只允许 SI/标准写法（`°C V A % Ah kWh W Hz mm mΩ hPa VA bit/s ° 次 串`），`%RH` 归一为 `%`（湿度靠 value_type/name 区分），`Lux`→`lx`。
- `ack / raw / bitmask / state` **移出 unit**，改由 `value_type` 表达（`boolean/enum/bitmask/raw/string`）。
- 后端已有 49 处空 unit —— 空值合法（无量纲），但要区分"无量纲"与"未填"。

### L5 · 门禁（CI）

1. **声明自洽**：`169 个驱动字面量 ⊆ 声明集合`（**只查代码，不查 DB**，无需数据库即可跑）。
2. **标签完整性（警告级）**：未标注字段数 `> N` 时 CI 警告而非失败——**标签是展示质量，不是数据正确性**，不应阻塞任何提交。
3. **列宽一致性**：全部 64（当前 32/64 混用）。
4. **数据面零依赖（新增，最重要）**：`go list -deps ./internal/databus ./internal/automation ./internal/datasource | grep sensorcatalog` 必须为空；且 `models.UnifiedData` 不得有指向 catalog 的 FK。
5. **单位词表**：`unit` 值 ∈ 白名单（DB CHECK 或 CI 扫描）。
6. **降级可用性**：catalog 表为空 / 不存在时，摄入与规则求值仍必须正常工作（单测覆盖）。

## 11. 耦合影响评估：这个方案会不会把边缘设备数据"强耦合"？

> 本节回答一个必须回答的质疑。结论：**现状已经是"隐式强耦合"（比显式契约更糟）；方案本身有耦合，但方向从"隐式 / 多份 / 无主"变为"显式 / 单份 / 单向"。前提是把 catalog 设计成投影而不是权威——§L1/L2 已按此修正。**

### 11.1 先分清两种"耦合"

| 类型 | 定义 | 现状 | 方案后 |
|---|---|---|---|
| **契约性耦合**（必要） | 生产方与消费方必须对"字段含义"有一致理解 | 有，但**以 5 份手写字符串副本的形式存在**（驱动/告警/自动化/数据源/前端）——改一处不报错，错一处静默失效 | 有，但**只有 1 份显式契约**（catalog），且可校验、可枚举 |
| **实现性耦合**（应避免） | 运行时强依赖、编译期反向依赖、数据写入被元数据阻塞 | 无（因为根本没有元数据层） | **必须用红线禁止**（见 §11.3） |

**关键判断**：一个多生产者、多消费者的数据维度，**不可能没有契约**。今天不是"没有耦合"，而是"耦合藏起来了"——`sensor_name` 这根裸字符串就是隐式契约，只是它没有主人、没有版本、没有校验。DS-08 / AU-13 / DG-03 三个缺陷都是同一个根因：**契约缺失导致的口径漂移**。

### 11.2 依赖边对照（before / after）

| 依赖边 | 现在 | 方案后 | 判定 |
|---|---|---|---|
| 驱动 → 字段名 | 内联字面量（169 个） | 驱动 → `GetSensorDefinitions()`（**同包接口，已在**，无新 import） | 不变 |
| 规则引擎 → 字段名 | 用户手写字符串（无校验） | **保存时**校验 catalog（控制面） | 由隐式变显式 |
| **规则求值 → 字段名** | `matchField(parser.Field, name)` | **不变**（数据面零改动） | ✅ 不耦合 |
| 数据源 → category | 用户手写字符串（无校验） | **保存时**校验；`MarkSuccess` 仍按字符串匹配 | ✅ 数据面不变 |
| 前端 → 字段名 | 2 套 map（`sensorNameMap`/`sensorUnitMap` + EXTRA） | 1 个 API | 单调依赖 |
| `unified_data` → catalog | 无 | **无 FK**，仅读时 JOIN | ✅ 不耦合 |
| **ingest → catalog** | 无 | **零同步读写**（观测靠查询派生） | ✅ 不耦合 |
| 固件/协议 → catalog | 无 | **无**（协议零变更） | ✅ 不耦合 |
| catalog 包 → 其他业务包 | — | 只依赖 `models` + `drivers`（读声明），**不被数据面包依赖** | 单向 |

包依赖方向（与仓库现有 `api → domain`、`nodemgr → databus` 一致）：

```
drivers（声明，叶子包）
      ↓ (启动期读取)
sensorcatalog（合并三源 + 提供 API）
      ↑ (仅控制面查询：保存校验、UI)
api / frontend

数据面：parser → databus → evaluator/matchField → datasource
        ↑ 与 catalog 无任何依赖（红线）
```

### 11.3 六条反耦合红线（实现时必须逐条守）

1. **固件零感知**：不向节点下发字段词表、不在协议里加字段字典。设备始终是透明管道（符合概念模型 §4 "节点不感知 EdgeDevice/DeviceConfig" 的既有裁决）。
2. **数据面零依赖**：`parser` / `databus` / `nodemgr`(ingest) / `automation.Evaluator` / `datasource.MarkSuccess` **禁止 import `sensorcatalog`、禁止查 catalog**。只允许"未标注字段"计数指标（异步）。
3. **`unified_data` 不加 FK**：字段名是数据的一部分，不是引用；加 FK 会让"元数据缺失 = 数据写不进去"，是最危险的耦合。
4. **catalog 不承载业务语义**：只放 `name/label_zh/unit/value_type/precision/status`。阈值、告警级别、优先级、动作映射一律不得进 catalog（否则它会变成"上帝表"，任何业务改动都要动它）。
5. **校验口径 = 声明 ∪ 观测**：规则保存校验不能只认"已观测到"——新设备今天没数据、明天才有；只认观测会让新设备**配不出规则**。声明源保证"装好驱动即可配"。
6. **新增设备/字段不改中心端代码**：除驱动本身外，新增字段应自动出现在 API（声明或观测），标签缺失只降级展示、不阻塞。这条是"防止强耦合"的总验收：**给一个新 BMS 型号加 5 个字段，中心端零改动**。

### 11.4 什么情况下我才会说"这会强耦合"（反例）

如果实现成下面任一种，**你的担心就成立，应当否决**：

| 反模式 | 后果 |
|---|---|
| ingest 里同步 `INSERT/UPSERT sensor_catalog` | 数据面被元数据表阻塞；catalog 故障 = 数据丢失 |
| `unified_data.sensor_name` 加 FK 到 catalog | 同上，且历史数据迁移会卡死 |
| 规则求值热路径查 catalog | 每帧一次额外查询；元数据变更直接影响触发行为 |
| 新字段必须先由人建 catalog 行才能入库 | 设备上线依赖人工流程，这是真正的强耦合 |
| catalog 放进 `automation` 或 `datasource` 包 | 数据语义被某个业务域"拥有"，其他域反向依赖它 |

### 11.5 如果仍然想要"零新增中心制品"：方案 A（更轻，但能力更弱）

| 方案 | 做法 | 新增耦合 | 能力 |
|---|---|---|---|
| **A 最小** | 不建表：保存期用 `GET /unified-data/categories`（DISTINCT 观测）校验；前端删两套 map 改用该 API | 规则配置 → `unified_data` 查询（控制面只读） | 能防"填错字段名"，但**新设备无数据时配不出规则**；无中文标签/精度 |
| **B 推荐**（本文 L1–L5） | 三源投影 + 可选丰富层 | 规则配置 → catalog API（控制面只读）；数据面零依赖 | 声明让新设备"装好即可配"；标签/单位/精度统一；可枚举可门禁 |
| **C 反模式** | catalog 作为权威表 + ingest 写入 + FK | **数据面强耦合** | 不推荐 |

**结论**：按 B 实现，耦合是**单向的、控制面的、可降级的**——比现状（5 份无主副本）耦合**更少**，且新增的每一条边都能用 §11.3 的门禁守住。

## 12. 更灵活、动态的方案：字段解析层（Field Resolution Layer）

> 本节回答"有没有灵活、动态的优秀方案"。结论：**有，而且比上一版更好** —— 把"词表（名词表）"升级为"解析层（选择器 + 别名 + 派生 + 自动发现）"。数据本身已经是自描述的，缺的从来不是 schema，而是**索引与解析**。

### 12.1 为什么"词表"不够灵活（上一版 B 方案的局限）

| 场景 | 词表方案的问题 |
|---|
| 动态索引字段 | cell_voltage_1..N 的 N 由固件上报的 cell_count 决定（jiabaida_parse.go:248/289，每台设备不同）⇒ **无法穷举登记**，只能登记一个"族"再写死前缀规则 |
| 同义字段 | 厂商 A 的 soc、厂商 B 的 rsoc、厂商 C 的 battery_capacity 是同一物理量 ⇒ 词表只能登记三个名字，规则要写三次 |
| 换设备/换厂商 | 规则绑定的是**物理字段名**，换 BMS 型号就得改规则（而规则是用户资产） |
| 新增字段 | 必须先有人登记才能用，登记是人工流程 ⇒ 设备上线仍然依赖中心端 |

**关键事实**：数据其实**已经是自描述的** —— `drivers.SensorData{Name, Value, Unit, StringValue}` 每条读数都自带名字与单位（`registry.go:9-14`）。所以缺的不是 schema，是 **对已存在名字集合的索引 + 解析能力**。

### 12.2 方案 D：四层解耦（数据面零改动）

```
① 物理/数据面   unified_data(name, value, unit)          ← 完全不变，零依赖
                 parser → databus → evaluator.matchField → datasource

② 解析层（内存） FieldResolver                            ← 新增；不参与写入
                 ├─ 声明：driver.GetSensorDefinitions() / device_configs.parser.fields[]
                 ├─ 观测：首次入库自动学习（异步投影，热路径零写）
                 ├─ 别名：vendor_field → semantic_name（配置，热加载）
                 └─ 派生：virtual_name = expr(其他字段)

③ 契约层       Selector：name | prefix_* | virtual:name | role:xxx
                 （规则/数据源只存 selector，不存物理名）

④ 消费面       规则编辑器 / 规则求值 / 数据源 / UI
                 求值：内存缓存（零 DB）；保存：软校验 + 候选列表
```

### 12.3 四个"动态"机制（这是灵活性的来源）

**① 自动发现（把"人工登记"变成"首次观测自动入库"）**
- 设备第一帧数据到达 → 解析层学习到 `name/unit` → 异步写入"观测索引"（不是热路径写）
- 新设备接入：**中心端零代码、零配置**即可在规则编辑器里看到字段（带 `observed` 标记）
- 与仓库既有裁决同构：概念模型 §4「资源全部来自 ResourceReport 上报，中心端零硬编码型号资源」——本方案把同一原则从"硬件资源"扩展到"数据字段"

**② 通配选择器（解决动态索引字段）**
- 规则写 `temperature_*` / `cell_voltage_*`，解析层展开为该设备**实际存在**的字段集合
- 16 串 BMS 只登记一个族，不需要 16 行；`cell_count` 变化时规则**自动跟随**
- 语义：`prefix_*` 求值为"该前缀下全部字段"；比较符对多值字段按 min/max/any 求值（需定义，见 §12.7 O-1）

**③ 别名归一（解决厂商差异）**
- 配置表：`semantic: soc ← [rsoc, soc, battery_capacity, battery_soc]`，`semantic: power ← [output_active_power, pv1_power]`
- 规则绑定 `soc`，不绑定 `rsoc` ⇒ **换 BMS 厂商不用改规则**
- 别名是"多对一"映射，冲突时按设备类型/discovery 优先级解析（可观测：记录命中哪个物理名）

**④ 派生/虚拟字段（解决"规则想用但设备不给"）**
- `virtual:power = total_voltage * current`；`virtual:max_temp = max(temperature_*)`；`virtual:cell_delta = cell_voltage_max - cell_voltage_min`
- 只在读时计算（或 ingest 时物化成普通读数，二选一，见 §12.7 O-2）
- 这让"数据源/规则引擎"可以表达**业务语义**，而不被设备字段表绑架

### 12.4 动态方案最大的风险：错字从"保存期 400"变成"运行期静默"

动态/柔性校验必然放松保存期约束。必须配四个**反静默**机制（否则比现状更糟）：

| # | 机制 | 作用 | 对应现有缺陷 |
|---|---|---|---|
| 1 | **软校验**：保存时未知 selector → WARN + 候选列表 + 允许存为 pending_discovery（不 400） | 不阻断"先配规则、后上设备"的流程 | 替代 B 的硬校验 |
| 2 | **规则试算（dry-run）**：对最近 N 条真实数据试跑，展示命中/未命中/值 | 保存前就能看见"这条规则永远不会触发" | 复用仓库既有 dry-run 范式（设备动作 CompilePlan 预览、parser 在线测试） |
| 3 | **never-matched 指标**：每条规则累计"匹配到字段的次数"，30 天为 0 → UI 红标 + 通知 | 直接消灭"规则永不触发却无报错" | **AU-12 / AU-13 这类静默失效的通用解** |
| 4 | **执行期未命中审计**：selector 解析不到时落 unresolved_selector 事件（不是静默 return） | 动态解析失败可追溯 | 替代"fail-closed 拒绝执行"的不可见性 |

### 12.5 与上一版 B 方案对比

| 维度 | B：词表 + 保存硬校验 | **D：解析层（推荐）** |
|---|---|---|
| 新增字段 | 必须有人登记 | **自动发现**（声明或首次观测） |
| 动态索引字段（cell_voltage_N） | 登记族 + 前缀规则写死 | **通配选择器**，随设备自适应 |
| 换厂商/换型号 | 规则绑物理名 → 要改规则 | **别名归一**，规则不动 |
| 业务语义（功率/温差） | 不支持 | **派生字段** |
| 保存期安全 | 强（400） | 软校验 + 试算 + 未命中指标（弱约束、强观测） |
| 数据面耦合 | 零 | **零** |
| 实现量 | G1+G3 约 3–5 人日 | **D1–D5 约 6–8 人日** |
| 登记维护成本 | 持续人工 | **趋零** |

### 12.6 落地批次（在 B 的 G0 文档决策之后）

| 批次 | 内容 | 工期 | 验收判据 |
|---|---|---|---|
| **D1** | 内存 registry（声明 ∪ 观测）+ 自动补全 + 软校验 + never-matched 指标 | 1–2d | 新设备首帧后规则编辑器可见其字段（零中心端配置）；错字保存只 WARN 不 400 |
| **D2** | 别名归一（配置热加载） | 1d | 规则绑定 soc，BMS 报 rsoc、逆变器报 battery_capacity 均能匹配 |
| **D3** | 派生字段（max/min/sum/ratio/算术） | 1–2d | virtual:power 与设备自报 output_active_power 误差 <1%（同源校验） |
| **D4** | 通配选择器（规则 + 数据源 category） | 2d | temperature_* 规则在 4/16 串两台 BMS 上都能触发；数据源 category 可用语义名 |
| **D5** | 规则试算 + 未命中告警 + 执行期 unresolved 审计 | 1–2d | 永不命中的规则 24h 内被标记；试算面板展示命中字段与值 |

**总 6–8 人日**（与 B 相当），但**长期维护成本趋零**，且直接消灭 AU-12/AU-13 这类"静默失效"根因。

### 12.7 D 方案新增待裁决

| ID | 问题 | 选项 | 建议 |
|---|---|---|---|
| O-1 | 通配选择器对多值字段的求值语义 | any / all / min / max / avg | **默认 min（最保守，适合"温度过高"类保护规则）+ 规则级可指定** |
| O-2 | 派生字段在读时算还是写时物化 | 读时计算 / ingest 物化为普通读数 | **读时计算**（零写入、可回滚） |
| O-3 | 别名的权威来源 | 配置文件 / 数据库表 / 代码常量 | **配置（热加载）+ 代码内置默认**（可回滚、可审计） |
| O-4 | 未命中选择器在保存时 | 硬 400 / 软 WARN + pending | **软 WARN + pending**（否则"先配规则后上设备"不可行） |
| O-5 | 解析层缓存失效策略 | TTL / 事件驱动 / 每请求 | **事件驱动（配置变更）+ TTL 兜底** |

### 12.8 红线不变（D 方案继承 §11.3 六条，另加两条）

7. **解析层只在内存/控制面**：求值路径零 DB 查询（缓存 miss 时按"未命中"处理并落审计，不回查 DB）。
8. **允许"未知 selector"存在，但不允许"执行期依赖解析成功"**：解析不到 = 不触发 + 落 unresolved_selector 审计（可观测），**不报错、不猜测、不 fallback**。

### 12.9 为什么这个方案符合本仓哲学

- **同一原则复用**：概念模型 §4「资源全部来自 ResourceReport 上报，中心端零硬编码型号资源」——D 方案把"声明来自生产方"从硬件资源扩展到数据字段
- **数据已自描述**：不新造协议、不改固件、不改 unified_data
- **少造机制**：不引入 DSL、不引入新服务、不引入消息队列；只在内存里加一层解析 + 配置化别名
- **可观测优先**：动态带来的不确定性用指标/试算/审计覆盖（本仓一贯的"可见失败"哲学）
