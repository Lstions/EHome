## 1. 需求陈述与结论

**需求**：边缘设备创建后，在"在线且有数据"时，能否**自动**把它的相关数据纳入数据源管理？

**结论：技术上可以，且约 70% 的基础设施已经就位；但直接做"全自动写入"会把当前数据源域的既有缺陷放大，建议按"先可见 → 再一键纳入 → 最后可选全自动"三段推进，并先拍板 3 个决策。**

| # | 已经就位的东西（无需新建） | 证据 |
|---|---|---|
| 1 | **幂等键天然存在**：`uniq_ds_source(device_id, category, edge_device_id)` 唯一索引，自动 upsert 只需 `ON CONFLICT DO NOTHING` | 生产库 `pg_indexes`：`CREATE UNIQUE INDEX uniq_ds_source ON data_sources (device_id, category, edge_device_id)` |
| 2 | **"有数据"信号已现成**：解析成功回调 `sourceHealthSink(edgeDeviceID, sensorNames[], at)` 每次成功解析都带本次真实出现的 sensor_name 集合 | backend/internal/databus/consumers_heavy.go:413-427 |
| 3 | **在线状态有权威定义**：首选数据帧即把 `pending → active`（不是"创建即在线"），并写 `last_data_at` | consumers_heavy.go:443-460；models.go:126-136 |
| 4 | **逻辑身份已挂载**：`edge_devices.logical_device_id` + merge 链解析 `ResolveMergeTarget` | consumers_heavy.go:353-368；datalifecycle/merge.go |
| 5 | **健康跟踪已接线**：`MarkSuccess`/`MarkFailure`（解析成功/离线/停滞三路）已生产运行 | main.go:344-357；service.go:599-684 |
| 6 | **类别词表可查**：`GET /api/v1/unified-data/categories?device_pk=` 返回 `{code, unit}`（前端已有 `api/unifiedData.ts:85` 封装，但数据源页未使用） | handler_data.go:231-266；frontend-shared/src/api/unifiedData.ts:85 |

**结论一句话**：能自动纳入，但"纳入"当前只买到**可见性与健康留痕**；要买到"主备切换/取值分派"，必须先完成台账 P0-1 的裁决（给 `active` 一个真实消费者）。

### 1.1 一个必须先修的数据缺陷：`unified_data.edge_device_id` 全表为空（新发现，T 级）

本需求的核心是"哪个**边缘设备**提供了哪个类别"，所以必须从 `unified_data` 反查提供者。实测：

```bash
docker exec ehome-postgres psql -U ehome -d ehome -Atc "SELECT count(*) FROM unified_data WHERE edge_device_id IS NULL"   # → 179532 = 全表
docker exec ehome-postgres psql -U ehome -d ehome -Atc "SELECT count(DISTINCT device_id) FROM unified_data"                # → 2（= EdgeDevice.ID）
```

- **写入路径不写该列**：`DBPersistConsumer` 构造 `models.UnifiedData{DeviceID, LogicalDeviceID, SensorName, Value, Unit, Timestamp}`（consumers_heavy.go:373-380），**没有 `EdgeDeviceID`**。
- **实际血缘寄居在 `device_id` 列**：`models.UnifiedData.DeviceID` 的注释是 `// v2.2: 改为 EdgeDeviceID`（models.go），取值确实等于 `edge_devices.id`。
- **但四份设计文档都声称 `edge_device_id` 是血缘列**：总体设计.md:72、概念模型.md:50、术语表.md:74、数据采集与数据链路.md:35、数据源主备与故障转移.md:28。
- **影响**：任何按 `edge_device_id` 过滤/分组的新功能（包括本需求的 catalog、以及 `Purger` 的 `calibration_cache` 清理 `Where("edge_device_id IN ?")`）都拿不到数据。查询侧因为用 `device_id`/`logical_device_id` 的 `Scope.Cond()`（scope.go:32-53）而**不受影响**，所以这个缺陷至今没被暴露。

**结论**：自动纳入的 B1 必须**用 `device_id` 作为提供者列**（或先补 `EdgeDeviceID` 写入 + 一次性回填 `UPDATE unified_data SET edge_device_id = device_id`）。这是一条独立于本需求的 P1 缺陷，建议单独立项（台账新增 DS-14）。

## 2. 三个必须先拍板的决策（阻塞实施）

### D-1 纳入粒度：字段级 vs 语义类别级 ⭐关键

`DataSource.category` 的取值就是 `unified_data.sensor_name`，而 sensor_name 是**动态生成的**：

| 设备 | sensor_name 形态 | 一条设备可能产生的行数（实测/推算） |
|---|---|---|
| SN3001 雨量 | `rainfall` | **1**（实测） |
| 嘉佰达 BMS **当前生产配置** | `total_voltage/current/rsoc/remaining_capacity/nominal_capacity/cycle_count/protection_status/fet_status/cell_count/software_version/temperature_1/temperature_2` | **12**（生产库实测：每个字段各 326 行） |
| 嘉佰达 BMS **启用单体电压命令后** | 追加 `cell_voltage_1..N` + `max/min/avg` + `cell_resistance_1..8` | 12 + 16 + 3 + 8 ≈ **39**（推算，代码路径见 jiabaida_parse.go:296-315/386-395） |
| Techfine 逆变器 | 131 处 `Name:` 字面量（含 `..._1` 类索引字段） | 数十行（推算，未实测） |

**实测基数（2026-10-21 只读）**：生产库 2 台边缘设备、2 个逻辑设备、**13 个 sensor_name**（雨量 1 + BMS 12），`(logical, sensor, provider)` 三元组 = **13**。

> ⚠ **两台生产设备的 `device_config_id` 都是 0**（走驱动回退，没有 DeviceConfig 解析器配置）。
> 这意味着 **"类别词表"不能从 `DeviceConfig.parser.fields` 取**——生产里它是空的。
> 唯一可靠的词表来源是 **实际入库的 `unified_data.sensor_name`（DISTINCT）** 或驱动代码里的 `SensorData.Name` 字面量。
> 本方案的 B1（S0 只读清单）天然满足这一点（直接 `SELECT DISTINCT sensor_name`）。

- **A. 字段级**（每个 sensor_name 一行）：与现有模型 1:1，语义最准，告警/自动化按 sensor_name 对齐零改造；**代价是行数随硬件通道数膨胀**（一台 16 串 BMS ≈ 35-40 行，10 台设备 ≈ 300+ 行，DataSourceList 直接不可用）。
- **B. 语义类别级**（把索引后缀归并：`cell_voltage_* → cell_voltage`、`temperature_* → temperature`）：行数约 **12-15/台**，页面可读；代价是 category 与 `unified_data.sensor_name` **不再字面相等**，而 `MarkSuccess` 的匹配逻辑是**字面比较**（`want[src.Category]`），必须同步引入"类别 → sensor_name 集合"的映射，否则健康信号永远不命中（→ 源源不断误熔断）。
- **C. 混合**：标量走字段级，索引类字段归并为一个"族"类别（如 `cell_voltage` 一个来源行代表 16 个测点）。

**⚠ 一个与实现强相关的实测事实**：生产库两台设备的 `device_config_id` 都是 **0**（走驱动回退路径 `drv.ParseData`，没有 DeviceConfig 解析器）。因此：

- **不能用 `device_configs.parser.fields[].name` 作为类别词表**（生产里为空）；
- **也不能靠"创建边缘设备时配置了哪些字段"来预生成数据源**（那时还不知道设备实际输出什么）；
- **唯一可靠的来源是"实际入库过的 `unified_data.sensor_name`"**（或驱动代码里的 `SensorData.Name` 字面量）。

这直接决定了方案的形态：**必须是"观测驱动"（先有数据 → 再纳入），而不是"配置驱动"（先配置 → 再声明）** —— 这也正好回答用户的问题："创建后、在线且有数据"才纳入，而不是"创建即纳入"。

> **建议选 C**，并把"类别 ↔ sensor_name 集合"的映射做成唯一事实源（建议放 `pkg/parser` 或 `datasource` 包的一个纯函数 + 单测），
> 因为它同时被 **MarkSuccess 匹配**、**UI 分组展示**、**告警/自动化对齐**三处消费（单一事实源原则，见台账 XC-09 同类问题）。
> 若短期只想最小改动，先做 A 并把默认纳入范围限制为"标量字段"（忽略 `*_\d+`），把索引类字段留到二期。

### D-2 active 语义：自动纳入的"权威来源"是否要接数据面（依赖台账 P0-1）

- 台账 **DS-01** 已实证：`status=active` 当前**不参与任何**数据面消费（`grep datasource alert automation databus` = 0），生产库三表均 0 行。
- 因此"自动纳入"现在买到的是：**设备→类别→提供者 的清单 + 健康状态 + 最后成功时间 + 失败计数 + 切换日志留痕**；**买不到**：取值分派、告警取值、自动化触发源选择。
- **若 P0-1 选 A（让 active 生效）**：自动纳入必须同时定义"新来源如何取得 active"的规则，否则会把任意一台刚上线的设备变成权威来源（可能是接线错误/量程不对的设备）。
  - 建议规则：首条来源 `active`，但其后需要**最近 N 次解析成功**（建议 N=3）且 `min_residency` 之后才允许被 `MarkSuccess` 用于"权威性"判定；新来源默认 `standby`，由人工或规则提升。
- **若 P0-1 选 B（降级为只读目录/可见性）**：自动纳入反而成为**该目录的主要生产者**，需求与实现完全对齐，且不引入任何数据面风险 —— 这是**成本最低且当前最自洽**的路径。

### D-3 生命周期：设备删除 / 逻辑设备合并 / 设备替换时怎么办

| 场景 | 现状 | 自动纳入后必须补的规则 |
|---|---|---|
| 删除边缘设备 | `DELETE /edge-devices/:id` 完全不碰 `data_sources`（`grep data_sources handler_edge_device*` = 0） | auto 行同步置 `disabled`（保留历史换机器可追溯），manual 行**不动**（用户资产） |
| 逻辑设备合并（merge） | `datalifecycle` 零引用 `data_sources` | 源逻辑设备的 auto 行迁移到目标逻辑设备（改 `device_id`），冲突则置 disabled 并留健康事件 |
| 设备替换（同型号换机） | 旧设备删除、新设备创建，新逻辑身份（`attachNewLogicalDevice`） | 旧 auto 行 disabled + 新 auto 行 active，形成"同一物理位置的两代提供者"留痕 |
| 设备长期离线 | `MarkFailure` 计失败 → 熔断 → `error` | 无变化（沿用现有状态机） |

**结论：自动纳入必须自带 `origin` 列**（`auto` / `manual`），否则清理流程会误删用户手工创建的来源 —— 这是不可逆的数据破坏，必须在第一版就有。

## 3. 方案对比

| 方案 | 做法 | 写入 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|---|
| **S0 只读观测清单** | 新增 `GET /api/v1/data-sources/catalog`，从 `unified_data` 实时派生 `DISTINCT (logical_device_id, sensor_name, edge_device_id)` + `max(timestamp)` + 设备状态；前端在数据源页顶部展示"可纳入的来源" | **零写入** | 零 schema 变更、零写入放大、零生命周期债；先用真实数据回答"纳入后会是什么样" | 无 per-source 策略（优先级/熔断阈值/停用）、无切换历史 | ✅ **第一步必做** |
| **S1 一键纳入** | 用户在 S0 清单里勾选/全选 → `POST /data-sources/adopt`（批量，幂等 upsert，`origin=auto`） | 按需 | 完全可控、可回滚、把"自动"的决策权留给用户 | 需要一次点击 | ✅ **第二步** |
| **S2 全自动纳入** | 解析成功回调里自动 upsert（有界 worker，不阻塞热路径） | 每台设备每类别 1 次 | 零操作 | 行数膨胀、误纳入无法撤销、写入放大 | ⚠ 需 S0/S1 验证后 + 开关默认关 |
| **S3 什么都不做，只改文案** | 明说"数据源仅用于运维可见性" | 零 | 最省 | 不满足需求 | 备选（若 P0-1 选 B 且用户接受） |

**S0 的派生 SQL（已在本机生产库只读验证通过）**：

> ⚠ 提供者列必须用 `device_id`（= EdgeDevice.ID），**不能用 `edge_device_id`** —— 后者全表为 NULL（见 §1.1）。

```sql
-- 分母：已成功入库过的 (逻辑设备, 类别, 提供者) 三元组
SELECT ud.logical_device_id AS device_id,          -- 归属（来源组键）
       ud.sensor_name       AS category,
       ud.device_id         AS provider_edge_device_id,   -- 血缘（= edge_devices.id）
       MAX(ud.timestamp)    AS last_data_at,
       MAX(ud.unit)         AS unit,
       (ds.id IS NOT NULL)  AS adopted
FROM unified_data ud
LEFT JOIN data_sources ds
       ON ds.device_id      = ud.logical_device_id
      AND ds.category       = ud.sensor_name
      AND ds.edge_device_id = ud.device_id
WHERE ud.logical_device_id IS NOT NULL
  AND ud.timestamp >= now() - interval '7 days'    -- 只列仍然活跃的数据（可选窗口）
GROUP BY 1,2,3, ds.id
ORDER BY 1,2,3;
```

**本机实测结果（2026-10-21 只读）**：
- 全量数据 **179,532 行 / 时间范围 2026-09-20 ~ 2026-10-01**（数据已停止上报 20 天，故 7 天窗口返回 **0 行**——这正是"用有分辨力的输入"的重要性：窗口参数必须可配，默认建议 30 天）。
- 全量口径下返回 **13 行**：逻辑设备 1 的 `rainfall`（provider=edge 1），逻辑设备 2 的 12 个 BMS 字段（provider=edge 2），全部 `adopted=false`。
- 与 `unified_data` 的 `device_id` 语义一致（distinct=2，对应 2 台 edge_devices）。

## 4. 推荐实施路线（4 批，每批独立可验证）

### B0 · 决策与前置（无代码）
- 拍板 D-1（粒度）、D-2（active 语义，依赖台账 P0-1）、D-3（生命周期规则）。
- 若 D-2 选 A，必须先做台账 P0-1 与 **DS-03/DS-04**（否则自动纳入的行会被"停滞扫描误熔断"和"冷却后无自愈"两处缺陷反复打中）。

### B1 · 只读观测清单（S0，约 1 天）
- 后端：`GET /api/v1/data-sources/catalog?device_id=&days=7`（只读 SQL，见 §3），返回 `{items:[{device_id, category, edge_device_id, unit, last_data_at, adopted: bool}], total}`。
- 前端：数据源页新增"可纳入来源"区块（或 drawer tab），列：逻辑设备 / 类别 / 提供设备 / 单位 / 最近数据 / 状态。
- **验收**：新建边缘设备 → 首帧数据后刷新页面 → 清单出现该行且 `adopted=false`；把设备离线 7 天以上 → 清单不再出现（窗口外）。

### B2 · 一键纳入（S1，约 1–2 天）
- 迁移：`data_sources` 增列 `origin varchar(8) not null default 'manual'`、`adopted_at timestamptz`；存量行回填 `manual`（现状 0 行，风险为零）。
- 后端：`POST /api/v1/data-sources/adopt`（body: `[{device_id, category, edge_device_id}]`）→ 事务内 **GORM `clause.OnConflict{Columns: uniq_ds_source, DoNothing: true}`** 批量插入；`origin='auto'`、`priority=0`、`is_primary=false`、`status` 按"组内是否已有 active"决定；写审计行。
- 幂等保证：唯一索引 + DoNothing；重复调用行数不变。
- **验收**：同一批 POST 两次 → `SELECT count(*) FROM data_sources` 不变；`origin` 全为 auto；已手工存在的同键行**原样保留**（不被覆盖）。

### B3 · 可选全自动（S2，约 2–3 天，默认关闭）
- 新增独立 sink（**不要挂在 sourceHealthSink 里**，避免混入健康语义）：
  ```go
  // databus.SensorParserConsumer
  autoProvisionSink func(edgeDeviceID, logicalDeviceID uint, sensorNames []string, at time.Time)
  ```
  在解析成功后**只投递到有界 channel**（容量建议 256，满则丢弃并计数），由独立 worker 做去抖（同一设备 30s 内只处理一次）+ 内存缓存（`map[edgeDeviceID]map[string]struct{}`，命中直接返回）。
- 配置：`datasource.auto_provision.enabled`（默认 `false`）+ 环境变量覆盖，沿用 `config.go` 既有 env 读取模式；开启时启动日志显式声明（对齐 `device.enabled` 的"响亮失败"风格）。
- 门槛（防止误纳入）：`EdgeDevice.Status == active` 且 `LastDataAt` 在 `staleness` 内 且 该 sensor_name **连续出现 ≥ N 次**（建议 N=2）。
- **验收**：
  1. 开关开 → 新设备首帧后 30s 内出现 auto 行；开关关 → 不出现（**用有分辨力的输入**：同一设备分别在两种开关下建两台）。
  2. 解析吞吐：开启前后同压测对比丢率/延迟，差异 < 5%（对照 `ehome_data_received_total` 与 `datasusbus drop` 指标）。
  3. 断链期不产生垃圾行（无解析成功 = 无调用 = 无写入）。

### B4 · 生命周期 hook（约 1 天）
- `DELETE /edge-devices/:id`：`UPDATE data_sources SET status='disabled' WHERE edge_device_id=? AND origin='auto'`（manual 不动）。
- merge worker：迁移 `device_id`，冲突则 disabled + 健康事件。
- **验收**：删除设备后自动行变 disabled 且 `ScanStale` 不再为它写健康事件；手工行保持原状。

## 5. 风险登记

| # | 风险 | 触发条件 | 缓解 |
|---|---|---|---|
| R1 | **行数膨胀** | 选了 D-1-A 且接入多台 16 串 BMS | 默认 D-1-C 归并索引字段；S2 需带"忽略列表"配置 |
| R2 | **误纳入垃圾来源** | 接线错误/量程异常设备上报了 1 帧 | 连续 N 次成功 + 开关默认关 + S0 先给用户看 |
| R3 | **放大既有缺陷** | DS-03（无自愈）/DS-04（nil 即超期）未修就上线 → 自动行反复熔断并产生大量通知 | **B0 前必须先修 DS-04**（或创建行时把 `last_success` 初始化为首帧时间） |
| R4 | **覆盖用户配置** | 用户手工改过优先级/阈值，自动流程再次 upsert | `ON CONFLICT DO NOTHING`（**只插不改**）+ `origin` 区分 |
| R5 | **热路径阻塞** | 在 consumer goroutine 里同步 upsert | 有界 channel + 独立 worker + 去抖（B3 设计） |
| R6 | **不可逆** | 自动写入的表行无法区分"系统生成"与"人工资产" | 第一版就加 `origin` 列（B2） |
| R7 | **语义混乱** | category 与 sensor_name 不再字面相等 | 类别映射单函数 + 单测；文档同步更新术语表（category 定义） |
| R8 | **血缘列全空导致取错列** | 照设计文档写 `WHERE edge_device_id` → 永远 0 行（静默空结果，最难发现） | B1 一律用 `device_id`；同时立 DS-14 修写入+回填；给 catalog 加"返回行数 > 0"的集成测试（有分辨力输入） |
| R9 | **数据已停更 20 天** | 默认 7 天窗口看不到任何数据 → 用户以为"功能没生效" | 窗口可配（默认 30 天）；空态文案明示"近 N 天无数据"而非"无来源" |

## 6. 与现有台账的依赖关系（顺序不能颠倒）

```
台账 P0-1（active 语义裁决）
   ├─ 选 B（只读目录）→ 本需求 S0/S1 直接落地，S2 可选
   └─ 选 A（接数据面）→ 必须先修 DS-03 + DS-04，再谈自动 active 提升

本需求 B1（S0 只读）—— 无依赖，可立即做
本需求 B2（S1 一键）—— 依赖 D-1 粒度决策
本需求 B3（S2 自动）—— 依赖 B1/B2 + DS-04 修复 + 开关
本需求 B4（生命周期）—— 依赖 B2 的 origin 列
```

**若只能做一件事**：做 **B1（S0 只读观测清单）**。它零写入、零 schema 变更、当天可交付，能立刻回答用户"自动纳入后会看到什么"，并且不制造任何需要回滚的数据。
