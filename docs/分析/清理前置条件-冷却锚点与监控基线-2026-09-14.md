# 清理前置条件 — 冷却锚点与监控基线

> 状态：**v1 初稿（正在实施，本文档随实现同步更新）**
> 日期：2026-09-14
> 范围：只做两件事 —— ①`automation_events` 冷却锚点 ②命令域监控基线。**不含任何清理器**。
> 上游裁决：`docs/分析/运行期无界增长表-保留策略设计-2026-09-13.md`（INV-1 / INV-2）
> 取证口径：所有行号均为本文档写作时对工作树的**实测**（`read` 工具逐行核对），非转述。

## 0. 本文档要钉住的两条不变式（先写结论）

| 编号 | 不变式（必须永远成立） | 不成立时的后果 |
|---|---|---|
| **A-INV** | 删除 `automation_events` 中任意 `result='executed'` 行后，对任意规则，**冷却窗不得提前解除** | 条件仍满足的规则在重启后**立即重触发** → **真实设备动作多发**。这是改变系统行为，不是丢审计 |
| **B-INV** | 删除 `command_executions` 中任意历史行后，`GET /api/v1/metrics/summary` 的 `control.*` 累计计数**不得减少** | 面板"操作失败 9"变"0"、告警高亮消失 → **看起来像故障自愈，实际是证据被删** |

两条不变式的共同性质：**它们都不是"数据保真"问题，而是"删数据会改行为"问题。**
所以判据不能是"删完之后表还在不在"，只能是"删完之后**行为/回答**是否相同"。

## 1. 现状证据（实测）

### 1.1 前置条件 A：`automation_events` 是冷却状态的唯一持久锚点

**证据 1 — 冷却态是纯内存，重启即失**

`backend/internal/automation/evaluator.go:80-81`
```go
// triggered 规则当前是否处于 triggered 态 (冷却中)。
triggered map[uint]time.Time // rule ID → 触发时刻
```
`evaluator.go:97` 初始化该 map，`evaluator.go:102-103` 在构造时调用 `LoadRules()` + `rebuildCooldowns()`。

**证据 2 — 回填的唯一数据源就是事件表**（`evaluator.go:107-139`）

```go
func (e *Evaluator) rebuildCooldowns() {
    ... e.db.Model(&models.AutomationEvent{}).
        Select("rule_id, MAX(triggered_at) AS max_at").
        Where("result = ?", models.AutomationResultExecuted).
        Group("rule_id").Scan(&rows) ...
    e.triggered[r.RuleID] = at
}
```
⇒ **删掉 executed 行 = 删掉重启后唯一能恢复冷却的东西。** `len(rows) == 0` 时直接 return，`triggered` 保持为空 —— 所有规则被视为"从未触发"（armed）。

**证据 3 — 规则表上没有任何"上次触发"字段**
逐行核对 `backend/internal/models/automation.go:102-149` 的全部字段：
`ID / Name / Enabled / TriggerType / TriggerSensorName / TriggerComparator / TriggerThreshold /
TriggerDurationSec / TriggerWindowStart / TriggerWindowEnd / TriggerWindowEdge / TriggerEdgeDeviceID /
ConditionsJSON / ActionType / ActionDeviceID / ActionID / ActionParamsJSON / ActionLevel /
CooldownSec / RequireConfirmed / MaxDailyExec / CreatedAt / UpdatedAt / DeletedAt` —— **无 last_triggered 类字段**。
全仓 grep `last_triggered|LastTriggered` = **0 命中**（实测）。

**证据 4 — 同一张表还承载另外 6 处业务判定（不是只读审计）**

| # | 位置 | 用途 | 口径 |
|---|---|---|---|
| 1 | `evaluator.go:115-121` | 启动重建冷却 | `MAX(triggered_at) WHERE result='executed'` GROUP BY rule_id |
| 2 | `planner.go:93-97` | 日熔断（自动路径） | 当日 `executed` 计数 |
| 3 | `planner.go:175-179` | 幂等键序号（自动路径） | 当日 `executed` 计数 → `automation:<id>:<yyyymmdd>:<seq+1>` |
| 4 | `planner.go:530-533` | 日熔断（手动触发） | 同日同口径 |
| 5 | `planner.go:553-557` | **手动触发的冷却抑制** | 最近一条 `executed/pending_confirm` 的 `triggered_at` |
| 6 | `planner.go:626-629` | 幂等键序号（手动） | 当日 `executed AND trigger_source='manual'` 计数 |

**⚠️ 与任务书背景的一处出入（以实测为准）**：任务书写"planner.go:93/175/530/553/626 另有 5 处"。
实测这 5 个位置确实存在，但**对应 6 个不同口径**（`:175` 与 `:626` 分别是自动/手动两条幂等序号）；
并且**任务书漏掉了第 7 处**：`planner.go:795-802 sweepExpiredPending`（每 5 分钟把 24h 前的 `pending_confirm` 改写成 `expired`）。
该处是 UPDATE 而非按时间 DELETE，不影响本次前置条件的结论，但清理器实现者必须知道。
**结论方向与任务书一致，差别只在数目与一处遗漏。**

**证据 5 — executed 行有 3 个生产写入点（任务书只点名了 2 个）**

| # | 位置 | 场景 | 是否落 `executed` |
|---|---|---|---|
| ① | `planner.go:210 executeDeviceAction` → `planner.go:281-310 recordRet` | 自动触发执行成功 | 是 |
| ② | `planner.go:657-665 executeManualDeviceAction` | 手动触发执行成功 | 是 |
| ③ | **`planner.go:757-766 ConfirmEvent`** | 人工确认把原 `pending_confirm` 行**条件 UPDATE 成 `executed`** | 是（不是 INSERT） |

⇒ ③ 意味着：**如果只在 `recordRet` 里写锚点，确认制规则（`require_confirmed=true`）的冷却锚点永远不会被写**，
重启后同样解除冷却。这是本次实测发现的、任务书未覆盖的第三个必须修补的点。

**结论**：`automation_events.result='executed'` 行**不是审计**，是运行状态的持久层。
删除它 = 冷却锚点丢失 = 重启后冷却窗提前解除。

## 2. 方案对比

### 2.1 前置条件 A：冷却锚点

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A1（选中）规则表加列 `last_triggered_at *time.Time`** | 在 `automation_rules` 加可空时间列；触发并落 `executed` 时**同事务**写该列；`rebuildCooldowns` 改读该列；启动时若锚点为空且事件表有历史则回填一次 | ✅ 锚点与事件表**物理解耦**，删事件行不影响冷却<br>✅ 语义显式（列名即事实）<br>✅ 与 `CooldownSec`/`MaxDailyExec` 同族（都在规则行上）<br>✅ 无需新表、无孤儿行<br>❌ 规则行变成"配置 + 状态"混合体（唯一需要辩护的点） |
| A2 独立锚点表 `automation_cooldown_anchors(rule_id PK, last_triggered_at)` | 状态完全外置 | ✅ 职责最干净<br>❌ 多一张表 + 多一次 upsert + 多一个 AutoMigrate 入口，**对本次目标无增量收益**<br> 规则删除后残留孤儿行需要另加清理 —— **反而制造新的无界增长表** |
| A3 在事件表里补写 `base_cooldown` 哨兵行（上游 §2.1 原始建议） | 清理器删 executed 行时同事务补一行锚点 | ❌ **锚点仍与事件表生命周期绑定**：清理器漏写一次/事务边界写错/未来有人 TRUNCATE 表，缺陷立刻复现<br> 把正确性寄托在**尚未实现的清理器**上 —— 而前置条件的意义恰恰是"不依赖清理器实现正确"<br>✅ 唯一优点：不需要 schema 变更 |
| A4 冷却窗改为纯内存、不重建 | 承认重启后冷却丢失 | ❌ 直接保留缺陷 |
| A5 启动时扫 `command_executions` 反推 | 不用事件表 | ❌ 关联是弱关联（无 FK，且 `notification`/`failed_gate` 类根本没有 command 行）<br>❌ **命令表自己也要被清理** —— 等于把锚点从一个会被删的表搬到另一个会被删的表 |

**裁决：A1。** 一句话理由：**要让"删事件行"在物理上不可能影响冷却，锚点就必须不在事件表里**；
A3 只是把"必现缺陷"改成"取决于清理器实现质量"，本任务的存在意义就是不接受这种依赖。

**字段名与类型的辩护（任务书要求说明）**
- 名用 `last_triggered_at` 而非 `cooldown_base` / `last_executed_at`：
  它记录的是**触发**而非**执行成功** —— 冷却窗起点是 evaluator 决定 `armed→triggered` 的那一刻
  （`evaluator.go:460` `e.triggered[rule.ID] = at`），不是命令真正下发成功的时刻。
  旧 `rebuildCooldowns` 用 `executed` 行**近似**它（因为只有 executed 才落行），新列把"近似"变成"就是这个值"。
  名字若与语义不一致，下一个读代码的人必然用错。
- 类型 `*time.Time`（可空）：**必须能表达"从未触发"**。用零值 `time.Time` 会让
  "从未触发"与"1970 年触发过"不可区分，且 `now.Sub(zero)` 是巨大正数，
  一旦有人写 `if now.Sub(rule.LastTriggeredAt) < cooldown` 就会把新规则静默永久冷却。
- **不加** `gorm:"default:..."`（同 `CooldownSec`/`Enabled` 的既有教训）：默认值会吞掉显式零值语义。

### 2.2 前置条件 B：监控基线

| 方案 | 做法 | 取舍 |
|---|---|---|
| B1 改成 Prometheus counter | `control.failed` 等读 `readCounterTotal(...)` | ✅ 天然不受清理影响<br>✅ 与已有的 HTTP/MQTT 3 个字段同范式（`handler_metrics.go:82-88`）<br>❌ **进程重启归零** —— 面板数字照样"跳回 0"，只是换了触发条件<br>❌ 现成的 `DeviceActionTransitionsTotal` 是 counter，counter 不是"当前状态数"，拿它当 `active/queued` 是语义错位<br>❌ `unresolved_unknown` 本质是**集合状态**，不是事件计数 |
| B2 加时间窗 | `WHERE created_at >= now-Nd` | ❌ **改变产品语义**：面板从"累计"变成"最近 N 天"；前端文案"操作总数"未变，用户无从知道口径变了<br>❌ **且不解决问题**：窗口内被删的行照样让数字变小 |
| **B3（选中）计数快照表** | 清理器删除前，在**同一事务**内把即将删除的行按状态累加进快照；面板读 = 存活行 `COUNT(*)` + 快照 | ✅ 语义**完全不变**（仍是"累计"，与面板文案、前端契约、既有测试断言逐字一致）<br>✅ 与 A1 同构：**把易失事实搬到清理器碰不到的地方**<br>✅ 单行 upsert，写放大 O(1)，表不可能增长<br>✅ 清理器未实现时本改动**可独立上线且行为零变化**（基线恒为 0）<br>❌ 需要清理器配合（**本任务只交付读侧 + 累加 API + 可用性证明，不交付调用方**）<br>❌ 快照写错无法自愈（对策：单调性不变式 B-INV-3） |
| B4 新建行时双写计数器 | 每次 Create 时 `counter + 1` | ✅ 同样不受清理影响<br> 仍需一次性历史回填（与 A1 回填同型）<br>❌ 把写放大压到控制域最不能慢的热路径 `Create` 上<br> 本质与 B3 相同但多一次热路径写 |

**裁决：B3。** 一句话理由：**"累计"这个语义必须原样保住**（B2 改语义、B1 退化成"本次进程内累计"），
而保住累计的唯一办法是让被删掉的那部分计数有一个清理器不会碰的落点。

**明确否证的一个直觉**（写给复核者）：`command_manual_resolutions` + `security_audit_events`
**不能**充当基线 —— 前者只覆盖"被人工处置的 UNKNOWN"，后者自己有保留期（上游 INV-6）。
**两个都会被时间削掉的表不能互为基线。**

### 2.3 为什么不选"先实现清理器再谈基线"

前置条件的定义就是**"不做就会造成功能可见损坏"**。A/B 两条都满足"清理器一旦上线且未做前置条件 → 损坏必现且静默"。
因此顺序只能是：**A1 + B3 落地 → 再写清理器**。

## 3. 不变式（写成测试，且必须能变红）

> 每条都写成「**什么样的改动会让它变红**」，让它成为约束而不是当前取值的快照。

### A-INV-1 冷却窗不因删除 executed 行而提前解除（本仓当前**应为红**）
**性质**：造规则 R（`cooldown_sec = 3600`），制造"1 小时前触发过"的事实并落一条 `executed` 行；
**删除该行**（模拟清理）；新建 Evaluator（模拟重启）；在同一时刻再次求值 ⇒ **不得触发**（冷却未到期）。
**测试**：`backend/internal/automation/cooldown_anchor_test.go`
**变红条件**：`rebuildCooldowns` 回退成依赖 `automation_events`；锚点列被移除；触发路径不再写锚点；**或确认制路径（③）忘了写锚点**。

### A-INV-2 锚点写入与 executed 事件同事务（崩溃窗口不得存在）
**性质**：让 `executed` 事件的落库失败（例如规则行被同步删除导致外键/约束失败，或注入了失败的 DB 句柄），
断言**事件行与锚点列一起不存在** —— 不允许"事件落了锚点没落"或反之。
**测试**：`cooldown_anchor_test.go` 的 `TestCooldownAnchorAndExecutedEventAreAtomic`。
**变红条件**：有人把锚点更新挪到事务外（这正是任务书点名的崩溃窗口）。

### A-INV-3 一次性回填只填"锚点为空"的规则，绝不覆盖已有锚点
**性质**：若某规则已有锚点 T0，而事件表 MAX = T1 > T0，回填**不得**把它改写为 T1（锚点自持）。
**变红条件**：有人把回填写成无条件 `UPDATE ... = (SELECT MAX(...))` —— 那会让事件表的清理再次影响冷却。

### B-INV-1 清理后累计计数不减少
**性质**：造 3 条 `FAILED`（1 条 now、2 条 800 天前）+ 2 条 `UNKNOWN`（其中 1 条已人工处置）+
1 条 `SUCCEEDED` ⇒ 记录面板值 ⇒ **删除历史行并在同一事务累加基线** ⇒ 面板值**逐字段不得减少**，
且 `unresolved_unknown` 不得从 1 变 0。
**测试**：`backend/internal/api/command_metrics_baseline_test.go`（走真实 `GET /api/v1/metrics/summary` HTTP 链路）
**变红条件**：基线补偿被漏掉；或有人把 `unresolved_unknown` 也写成"只数存活行 + 基线"。

### B-INV-2 清理前后 control 字段名与语义不变（前端零改动）
**性质**：`MetricsResponse.Control` 的 12 个 JSON 字段名与今天**逐字一致**。
**测试**：对响应体做**原始 JSON 键集合**断言（不是反序列化到结构体 —— 那会掩盖字段缺失/改名）。
**变红条件**：有人把字段改名成 `failed_total` 之类，或把某个计数从 int 改成对象。

### B-INV-3 基线只增不减（单调性）
**性质**：连续累加，各字段单调不减；在**无新命令**时 `基线 + 存活行` 恒定。
**变红条件**：有人把 upsert 写成覆盖而不是累加（第二次清理会抹掉第一次的 `failed`）。

## 4. 代价（丢失了什么能力）

| 改动 | 丢失的能力 | 是否可接受 |
|---|---|---|
| A1 加锚点列 | 锚点只保留**最后一次**触发时刻；删掉 executed 行后，"之前那些触发分别是什么时候"不可答 | ✅ 可接受：冷却只需最近一次（`cooldown_sec` 上界 86400 = 1 天，实测数据跨度 5.36 天）；逐次历史仍在事件表（清理前） |
| A1 一次性回填 | 回填**依赖事件表仍存在**。若在回填代码上线前有人先删了事件行，锚点永久为空 | ️ **这正是"锚点必须先于清理器上线"的原因**；本任务把该顺序固化 |
| A1 加列 | 规则行变成"既是配置又是状态"，规则导出/导入需忽略该列 | ✅ 可接受：`json` 只读暴露，文档标注 |
| B3 基线表 | **"被清理掉的那部分计数发生在哪一天"永久不可答**（只剩总数） | ✅ 可接受：面板今天也只显示总数，没有时间维度 |
| B3 基线表 | 基线一旦写错（重复累加/漏累加）**没有第二个数据源可对账** | ⚠️ 用 B-INV-3 单调性 + 清理器"删除行数 == 累加行数同事务"断言兜住 |
| B3 读侧 | `operations_total` 不再等于"表里行数"，DBA 直接 `count(*)` 会与面板不一致 | ✅ 可接受且**必须如此**：这正是"删数据不改行为"的定义；需在面板/文档注明口径 |

**明确不接受的代价**：❌ 重启后面板归零（B1）；❌ 面板只显示最近 N 天（B2）；❌ 冷却锚点由清理器补写维护（A3）。

**`unresolved_unknown` 的特殊裁决（必须写清楚）**：它 = "UNKNOWN 且**从未被人处置**"。
这个集合**语义上就不该按时间清理**（上游 §2.4 已裁决"悬案不参与时间窗删除"）。因此：
- 清理器遵守上游裁决 ⇒ 这些行永不被删 ⇒ 基线对它恒为 0，**不需要累加**；
- 若有人违规删了它 ⇒ 基线也救不了（"这条悬案存在过"在删除瞬间就没了）。
⇒ 本条**不改** `unresolved_unknown` 的计算方式，但把它写成 B-INV-1 的显式断言：
**清理器删除的任何 `UNKNOWN` 行，必须是已被 `command_manual_resolutions` 处置过的**（与上游 INV-4/§2.4 一致）。
