### 1.2 聚合逻辑（只对 PostgreSQL 生效）

仅在 `db.Dialector.Name() == "postgres"` **且** `maxPoints > 0` **且** 时间窗 > 0 时启用新路径；SQLite / maxPoints<=0 / 非法参数**完全保持现有行为**（现有单测不得改动语义）。

新增可选 query 参数 `agg`：`auto`（默认）| `avg` | `raw` | `change`。
- `auto`：category ∈ {protection_status, fet_status} → `change`；其余 → `avg`。
- `raw`：旧行为（全量行 + Go 侧 downsample）。
- 非法值：回落 auto（不返回 400，保持兼容）。

**avg 模式（连续量）**：桶宽 `W = max(1, ceil(windowSeconds / maxPoints))` 秒。

```sql
SELECT to_timestamp(floor(extract(epoch FROM "timestamp") / $W) * $W) AS bucket_ts,
       avg("value") AS value
FROM unified_data
WHERE (<dataScopeCond 条件>)
  AND "sensor_name" = $cat
  AND "timestamp" BETWEEN $start AND $end
GROUP BY 1 ORDER BY 1
```

返回点数 ≤ maxPoints + 1。

**change 模式（状态位/掩码）**——返回**变更点序列**（首点 + 每次值变化，含 1→0）。前端 `bitTransitions` 在变更点序列上计数 0→1 跃变与时长的语义与全量序列等价：

```sql
SELECT s."timestamp", s."value" FROM (
  SELECT "timestamp", "value",
         lag("value") OVER (ORDER BY "timestamp") AS prev
  FROM unified_data
  WHERE (<dataScopeCond 条件>)
    AND "sensor_name" = $cat
    AND "timestamp" BETWEEN $start AND $end
) s
WHERE s.prev IS DISTINCT FROM s."value"
ORDER BY s."timestamp"
```

（注意：不得用仅非零过滤，否则 1→0 的结束点丢失、触发时长变错。）

**响应 item 形状**（PG 新路径）：`{"timestamp":"<RFC3339>","value":<number>}`（不再返回 id/device_id/unit/created_at 等冗余字段）。
批次响应外层不变：`{"category":"...","data":[...]}`。
**SQLite 旧路径保持 `models.UnifiedData` 全字段**（现有测试 `handler_data_lifecycle_test.go` 断言了该类型，不得破坏）。

## 一·补充（2026-10-20 22:57，verifier 实测发现，必须实施）

### 1.6 UNION ALL 重写：让复合索引真正生效

【问题】PG 实测 EXPLAIN 显示 `idx_unified_logical_sensor_ts` 与 `idx_devdata_logical_created` **没有被使用**：dataScopeCond 生成的 OR 条件 `(logical_device_id IN (...) OR (logical_device_id IS NULL AND device_id IN (...)))` 出现在前导列上，PG 无法把复合索引当访问路径 ⇒ 24h 单测点仍然 `Index Scan timestamp_idx` 扫 2.5M 行（Rows Removed by Filter 806,400/worker），latest-data 仍然 Parallel Seq Scan 2M 行。

【修法】聚合路径（avg/change）与 latest-data 的 PG 查询改为 **UNION ALL 两个分支**，各自可用索引：
```sql
-- 分支 A（逻辑身份）
SELECT * FROM unified_data WHERE logical_device_id IN (?) [AND sensor_name=? AND timestamp BETWEEN ? AND ?]
UNION ALL
-- 分支 B（backfill 前 NULL 逻辑行）
SELECT * FROM unified_data WHERE logical_device_id IS NULL AND device_id IN (?) [AND 同样的过滤]
```
- 聚合：在 `(A UNION ALL B) AS u` 上做 avg 分桶 / lag 变更点；DedupNeeded 时在 union 外层加 ROW_NUMBER 去重（见下）再聚合。
- latest-data：`SELECT * FROM ( (A ORDER BY created_at DESC LIMIT 1) UNION ALL (B ORDER BY created_at DESC LIMIT 1) ) t ORDER BY created_at DESC LIMIT 1`。
- 只有一种 scope（仅 LogicalIDs 或仅 InstanceIDs）时用单分支，不拼 UNION。
- SQLite 路径保持旧实现（测试契约）；新路径仅 PG。
- 建议用 `ToSQL()` 取两个分支的 SQL+args 后拼 UNION 的 raw SQL（bucket 表达式里的桶宽直接内联整数，避免占位符顺序问题），并在 **PG integration 测试里断言 `EXPLAIN (COSTS OFF)` 出现 `idx_unified_logical_sensor_ts` / `idx_devdata_logical_created`**（这是本修复的关键回归门禁）。
- 验收：bench 上 EXPLAIN 单测点 24h 扫描行数 ≈86,400（而非 2.5M）；protection 30d change 走索引有序扫描（无大排序/无 bitmap recheck）；latest-data 走 index scan；5 个请求 after 总耗时相对当前 after（3.07s）应再显著下降（目标 <1.5s）。

### 1.7 部署影响
新索引只有在上述重写后才有收益；**两者必须一起上线**，否则索引只是占空间。
