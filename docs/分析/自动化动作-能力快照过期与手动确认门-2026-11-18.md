- 现场：生产实例 `192.168.20.6:18090`（容器 `ehome-prod-web`，镜像 `ghcr.io/lstions/ehome:latest`，commit `9f77db7b`）
- 现象事件：`2026/11/18 06:42:57 打开BMS充电 / 门禁失败 / action is unavailable for this device`、`2026/11/18 07:15:58 打开BMS充电 / 需确认（未授权） / confirmation is required`
- 关联：`docs/分析/自动化策略-补发机制与冷却吞触发-2026-11-17.md`（同一批规则的前一次事故）

## 2. 根因一：能力快照只有"人打开设备页"才会刷新

`current_capabilities` 门禁用 `MaxCapabilityAge = 10min + 5min = 15min` 卡快照；而快照只由
Hello / 清单提交 / **服务端 QueryResources** 三处刷新。生产的 `QueryResources` 只在两处发出：

1. `POST /api/v1/nodes/:id/query-resources`（唯一调用方 = 前端 `deviceOperation` store，检测到目录 `capability_stale` 时补一次）；
2. 后端没有周期刷新。

节点侧：12 小时内只有 1 次 Hello（后端重启后重连），此后每秒一条 StatusReport，
`sync_state=1(syncing)`、`epoch=0` 从连上到现在**从未变化** —— 固件周期同步没生效（`sync_manager_periodic_task` + `sync_manager.c:295-310` 记录过同类"永久钉在 SYNCING"缺陷）。

于是时间线与事件严丝合缝：

| 时刻(CST) | QueryResources | 结果 |
|---|---|---|
| 22:14:43 | 有（页面打开） | 22:14:57 关闭动作 executed |
| 22:38:09 | 有 | 快照只活 15 分钟 |
| 22:38 → 06:42 | **无（8 小时）** | 06:42:57 日出触发 → `capability_stale` → failed_gate |
| 07:15:34 | 有（用户打开设备页排查） | 07:15:58 手动触发**过门禁** → 撞确认门 |

## 3. 根因二：手动触发从不携带确认令牌

`executeManualDeviceAction` 调 `Create` 时只传 `ActorUserID`：既没有 `ConfirmationToken`，
也没有 `ActorKind=system` / `RiskAcknowledged`。而 `set_mos_policy` 是 `risk=high`、
`requires_confirmation=true` ⇒ 必然 `ErrConfirmationRequired`。
**与规则是否授权无关**（两条规则的 `risk_acknowledged_at` 都非空，UI 的"未授权"标签是误导）。

## 4. 修复（3 处）

| 位置 | 改动 |
|---|---|
| `commandexec/service.go` | 新增 `ErrCapabilityStale`（`ErrActionUnavailable` 的子类）；门禁拒绝改为 门禁拒绝包装为 `fmt.Errorf("%w: gate=<name> reason=<code>", ErrActionUnavailable)`；`current_capabilities` 且 **reason=capability_stale** 时再追加 `ErrCapabilityStale`（双 `%w`）。事件 detail 从通稿变成 `action is unavailable for this device: gate=current_capabilities reason=capability_stale ...` |
| `automation/planner.go` | 新增 `CapabilityRefresher` 注入（生产 = `nodemgr.Manager`）；`ensureNodeCapabilityFresh()` 在**执行前**检查快照，过期就发 `QueryResources` 并等落库（2s/100ms，可注入）；自动 / 手动 / 确认三条路径都先自愈 |
| `automation/planner.go` | 手动触发与 `ConfirmEvent` 同族：为该动作**即铸即销**一次性确认令牌（低风险动作为 `ErrConfirmationNotNeeded`，按无令牌执行） |
| `cmd/server/main.go` | `automationPlanner.SetCapabilityRefresher(nodeMgr)` |

设计取舍：

- 自愈只在快照**已过期**时才打扰节点（不是每次动作都发一帧）；
- 刷新失败不吞错：继续走 `Create`，由门禁给出带名字的精确拒绝（可见地失败）；
- 手动路径对 `IssueConfirmation` 的 `ErrActionUnavailable` 放行到 `Create` —— 令牌铸造自带一套**内联**可用性检查且不带门禁名，若在那终结会让 detail 退回通稿；
- 系统/自动路径的授权边界不变（仍靠规则级 `risk_acknowledged_at`），手动路径拿到的是**与设备操作页同一套**的一次性令牌机制。
