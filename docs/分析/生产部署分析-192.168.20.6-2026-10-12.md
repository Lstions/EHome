# 生产服务器（192.168.20.6）部署分析

日期：2026-10-12　性质：**只读分析，未接触生产**

## 0. 一句话结论

**现在不能部署。** 直接部署 `main` 会在几十秒内让**全部现场设备失联**，
且**无法远程恢复** —— 因为 main 已彻底删除 MQTT，而现场固件只会 MQTT。
设计文档早就写了这条风险（§7.2 / X4 / K3），但它给出的 5 阶段迁移方案
（P0 双栈 → P5 移除 EMQX）的**前提在当前 main 上已不存在**（见 §3）。

## 3. ⚠ 核心矛盾：设计文档的迁移方案前提已失效

设计文档 §7.3 规定的唯一可行顺序（**物理锁死**，不是选择）：

```
P0  后端同时启用 MQTT + TCP（双栈）   ← 此时 2.8.0 设备行为逐字节不变
P1  通过 MQTT 推送 3.0 固件 OTA（A/B 分区）
P2  观察期：TCP 上跑通 Hello/ConfigManifest/采集/OTA 完整闭环
P3  关掉固件 MQTT 回退分支
P4  后端关闭 MQTT 监听          ← 回滚窗口在此**永久关闭**
P5  移除 EMQX 容器/端口/ACL/看板
```

**矛盾点**：

- P0 要求后端**同时**提供 MQTT 与 TCP；
- 但 main 已在 2026-10-08（`91fd7856`）**把 MQTT 删干净**，且之后又有 111 个提交；
- ⇒ **当前 main 无法执行 P0**，也就无法执行第 753 行所说的"设备只能通过它当前懂的通道
  （MQTT 下行 OtaCmd 0x0A）拿到新固件"这一步。

⇒ 现实是：我们直接跳到了 P4/P5 的代码状态，但设备还在 P0 之前。

## 4. 三条可选路径

### 路径 A：恢复双栈（对齐设计文档 P0-P5）——**推荐**

做法：以 `91fd7856^`（删 MQTT 之前的那版）为基底，**摘取** MQTT 监听能力，
与当前 3.0 传输共存，部署为一个"双栈"镜像。然后按 P0→P5 走。

**可行性已核实（好消息）**：`91fd7856^` = **`ec6424e6`** 这个提交上，
**MQTT 与 3.0 transport 是并存的** ——

```
ec6424e6:
  backend/internal/mqtt/      → 2 个文件（在）
  backend/internal/transport/ → 9 个文件（也在）
```

⇒ **双栈状态在本仓历史上真实存在过**，不是要从零实现。
路径 A 因此是"取回一个已存在的状态"，而非"开发新能力"。

优点：与设计文档一致；每一步可回滚；设备不会失联。
代价：需要把 `ec6424e6` 的 MQTT 接线重新摘到当前 main 上（中间隔了 111+ 个提交，
      其中 `91fd7856` 一次就动了 60 个文件、-2935 行），需要重新验证共存无冲突。
工作量：**中等** —— 代码可取回，但重新接线 + 双栈测试是主要成本。

### 路径 B：现场人工刷机（绕过 P1 的 OTA 依赖）

做法：**先不部署新后端**。带设备到现场（或用 USB/串口），逐台刷 3.0 固件，
刷完再部署纯 TCP 后端。

优点：不需要恢复 MQTT 代码。
代价：必须**现场可达**（O-4 决策点）；设备分布未知（O-3）；
      刷机期间设备离线；且刷完到后端切换之间设备一直连不上（旧后端只会 MQTT）。
      实际上仍需"双栈期"或"接受一段离线"。

### 路径 C：直接部署 + 接受现场失联 —— **不可接受**

部署 main → 现场设备立刻失联 → 且带外只有 BOOT 长按（只恢复出厂设置，
**不能把固件换回 MQTT**）⇒ **无法远程恢复**。
设计文档 §7.2 原文："后端移除 EMQX / MQTT 监听，现场设备无任何通道可以通信
（连 OTA 都下发不了）"。

### 4.5.3 ⚠ 新发现：OTA 曾因内存不足失败（改变 P1 风险评估）

生产 OTA 历史有一条**失败**记录：

```
node_id    : 30EDA0A9A808（S3P）
status     : failed        progress: 0
error_msg  : "Insufficient heap to start OTA task"
to_version : 2.7.0
completed  : 2026-10-04T07:23:08Z
```

时间线：**2026-10-04 失败 → 2026-10-10 内存优化落地**（堆 +17 KiB / largest +20 KiB）。
⇒ 很可能是同一根因，而内存优化**正是为了**让 OTA 能起来。

**但必须诚实标注**：该 OTA 是 2.7.0（非 3.0），且内存优化**尚未在真机复测 OTA**
（只验证了堆指标）⇒ **"3.0 固件能否 OTA 成功"是未验证项**，
而它是整个迁移路径 P1 的**单点依赖**。

⇒ **这改变了 P1 的风险判断**：P1 并非"照文档做就行"，
   它依赖一个**历史上刚失败过、且修复未经验证**的能力。

## 6. 回滚预案（关键不变量）

> 设计文档 §7.4：**能回滚与 MQTT 是否还在是同一件事。**

| 阶段 | 回滚能力 |
|---|---|
| 后端仍监听 MQTT | ✅ 任何时刻可把设备刷回 2.8.0 并恢复通信 |
| 后端关闭 MQTT（P4 之后） | ❌ **回滚窗口永久关闭**，只能带外 USB/串口恢复 |

⇒ **在 P4 之前，务必先演练一次"带外刷回 2.8.0"**（设计文档 U5 已列为待办）。
