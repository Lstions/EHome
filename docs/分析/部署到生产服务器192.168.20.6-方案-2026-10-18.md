# 部署到生产服务器 192.168.20.6 —— 可行性分析

日期：2026-10-18　性质：**只读分析，未接触生产**

## 0. 一句话结论

**现在不能直接部署。** 有一个物理性的死锁：

> 3.0 后端**只认 mTLS**（MQTT 已从代码里删除），而现场设备的固件**只认 MQTT**。
> 两者的共同语言是零。而且**无法通过 SSH 进入服务器**，连"先备份再试"都做不到。

要部署，必须先解决**三件事按此顺序**：拿到 SSH → 打通双栈过渡 → 逐台换固件。
下面每一节都给出实测证据，不引用推断。

## 1. 实测到的生产现状

### 1.1 网络与服务（本次实测）

| 项 | 值 | 证据 |
|---|---|---|
| 主机可达 | ✅ ping 0.25ms | `ping -c2` |
| **Web 端口** | **18090** | `/health` → `{"status":"ok"}` (application/json) |
| **MQTT** | **1883 OPEN，是真 broker** | MQTT CONNECT → 回 `CONNACK 20020000` |
| EMQX WebSocket | 8083 | open |
| **设备端口 8443** | **CLOSED** | `/dev/tcp` 探测 |
| SSH 22 | 可连，**凭据无效** | `Permission denied (publickey,password)` |
| 数据库 5432 | closed | 未对宿主暴露（合规做法） |

⚠ **同一网段的 8080 不是 EHome**：它是另一个应用 `Sub2API - AI API Gateway`。
任何"8080 是 EHome"的假设都会把命令打到别人的服务上。

### 1.2 世代的决定性判据

我最初想用 `/api/v1/mqtt/status` 是否 200 来判断世代 —— **这个方法无效**：
该路径在两代都返回 200，因为 SPA fallback 对未匹配路由返回 index.html（`text/html`）。

真正可判定的两个信号：

```
① 生产 8443 CLOSED          ⇒ 3.0 后端不可能在运行（它启动即监听 8443）
② 生产 1883 回 CONNACK      ⇒ 有一个活的 MQTT broker 在服务现场设备
```

对照本机（已部署 3.0）：

```
本机  8080(Web) + 8443(mTLS 监听) + 1883(EMQX 残留容器，但新后端不连它)
生产  18090(Web) + 8443 CLOSED    + 1883(EMQX，生产后端的设备通道)
```

### 1.3 代码侧（实测）

```
backend/internal/mqtt/         → 目录不存在（已删）
backend/internal/transport/    → 9 个文件（3.0 mTLS）
新镜像 ehome-new:v2 里 "mqtt" 字符串 → 仅剩 9 处，全是 DB 字段名/指标名遗留
                                        （mqtt_topic_up / ehome_mqtt_publish_failures_total）
```

⇒ 3.0 后端**没有任何 MQTT 监听能力**，不是"关掉了"，是代码里没有。

## 2. 核心死锁

```
        现场设备（fw 2.8.0）          生产后端（MQTT 世代）
        只会 MQTT  ────────────────►  只会 MQTT        ✅ 现在是通的

        现场设备（fw 2.8.0）          3.0 后端
        只会 MQTT  ────── ✗ ──────►  只会 mTLS        ❌ 零共同语言
```

把 3.0 后端推上去，等于当场切断唯一设备通道。而设备**不会自己升级**：
固件升级靠后端下发 `OtaCmd`，而新后端连不上设备 ⇒ 下发不了 ⇒ **永久失联**。

设计文档 §7.3 早就写了唯一可行的顺序（P0 双栈 → P5 移除 EMQX），
但**当前 main 已无法执行 P0**（没有 MQTT 代码可开）。这与 10-12 的分析结论一致。

## 3. 部署前必须解决的阻断项

### 阻断 A：SSH 不可达（**最硬的一条**）

实测：`sun@192.168.20.6: Permission denied (publickey,password)`。
也没有 Portainer / Docker API / 其他管理端口。

**后果**：
- 无法确认容器状态、镜像 tag、`.env` 实际内容、`data/` 目录大小；
- 无法备份数据库（5432 未暴露，只能进容器）；
- 无法执行任何部署、无法回滚、无法看日志。

⇒ **这一条不解决，后面全是纸上谈兵。**

### 阻断 B：固件 host 是**编译期常量**

```c
// esp32-collector/main/device_link_wiring.c:1289
tcfg.host = CONFIG_EHOME_DEVICE_LINK_HOST;   // 编译期宏，不是运行期配置
```

`ConfigManifest` **不下发** host（已 grep 确认）。默认值是 `192.0.2.1`（RFC 5737 占位符）。

⇒ 换服务器地址 = **必须重编固件 + 重新 OTA/刷机**。
这不是"改个配置"，是每个设备都要重新过一遍烧录流程。

这一点决定了迁移的**最小代价**：如果 20.6 就是长期生产机，那就在编译时把 host 设为 `192.168.20.6`；
如果只是临时迁移，代价会重复支付。**先确认 20.6 是不是最终归宿。**

### 阻断 C：mTLS 证书还没有生产形态

3.0 需要三个文件：`server.crt` / `server.key` / `client_ca.pem`。现状：

| 项 | 状态 |
|---|---|
| `deploy/prod/docker-compose.prod.yml` | **完全没有** `certs` 挂载和 `EHOME_DEVICE_*` 环境变量 |
| 生产宿主机证书 | 未知（无 SSH） |
| 当前唯一可用证书 | 我 10-18 生成的**测试 PKI**，私钥在 `.logs/closedloop/certs/`（gitignored） |

⚠ 测试 CA 的私钥放在工作区，不是密钥管理。**正式上线必须重新签发**。

### 阻断 D：prod compose 仍是 MQTT 世代

`deploy/prod/docker-compose.prod.yml`（工作区与 `.worktrees/v3` 内容相同）现状：

```yaml
services:
  postgres    # OK
  emqx:       # MQTT broker，3.0 不需要
  ehome:
    image: ghcr.io/lstions/ehome:${EHOME_IMAGE_TAG:-latest}
    environment:
      MQTT_BROKER: tcp://emqx:1883      # ← 新镜像会忽略，无害但误导
      EHOME_MQTT_CLIENT_ID: ehome-server # ← 同上
      # ❌ 缺 EHOME_DEVICE_ENABLED / ADDR / CERT_FILE / KEY_FILE / CLIENT_CA_FILE
      # ❌ 缺 8443 端口映射
      # ❌ 缺 certs 卷挂载
```

⇒ **用现有 compose 起新镜像，8443 根本不监听**，设备永远连不上，
而 Web 界面一切正常 —— 又一个"看起来成功"的静默失败。

### 阻断 E：OTA 是单点依赖，且历史上刚失败过

10-12 的分析记录了一条**失败**的 OTA：

```
node   : 30EDA0A9A808 (S3P)
status : failed   progress: 0
error  : "Insufficient heap to start OTA task"
target : 2.7.0    at 2026-10-04
```

之后 2026-10-10 做了内存优化（堆 +17 KiB / largest +20 KiB），但：
**只验证了堆指标，没有真机复测 OTA 能否成功**。

⇒ 3.0 固件能否 OTA 成功 = **未验证项**，而它是整个迁移路径的单点依赖。
好消息：本机有真机台架，**这个可以先在本机验证，不碰生产**。

### 阻断 F：回滚窗口

| 阶段 | 回滚能力 |
|---|---|
| 后端仍监听 MQTT | ✅ 可把设备刷回 2.8.0 恢复 |
| 后端关闭 MQTT 之后 | ❌ **永久关闭**，只能带外 USB 恢复 |

现场设备的物理可达性**至今未知**（无 SSH 无法确认，也没有现场清单）。
⇒ 在关闭 MQTT 之前，**必须先演练一次"带外刷回 2.8.0"**。

## 4. 建议路径

### 阶段 0：解锁（不做这一步，后面全免谈）

| # | 动作 | 产出 |
|---|---|---|
| 0.1 | **提供 20.6 的 SSH 凭据** | 能进机器 |
| 0.2 | 进机器后盘点：`docker ps`、`.env`、`data/` 大小、`df -h` | 真实基线 |
| 0.3 | 全量备份 `data/`（postgres 目录）+ `.env` | 可回滚 |
| 0.4 | 确认 20.6 是否是长期生产机 | 决定 host 编译值 |

### 阶段 1：本机台架验证（**不碰生产**）

| # | 动作 | 为什么 |
|---|---|---|
| 1.1 | 复测"内存优化后 OTA 能否成功" | 阻断 E 的单点依赖 |
| 1.2 | 演练"带外刷回 2.8.0" | 阻断 F 的回滚手段 |
| 1.3 | 本机已跑通完整 3.0 闭环（✅ 10-18 已完成） | 证明软件侧就绪 |

### 阶段 2：双栈过渡（唯一不流血的路）

要同时服务两种设备，需要后端能听懂两种语言。有两条实现路：

**2A. 恢复 MQTT 代码（对齐设计文档 P0）**
- 基底：`ec6424e6`（MQTT 删除前的最后一个提交）上 MQTT 与 3.0 **并存过**，是真实存在过的状态；
- 代价：从 `ec6424e6` 摘出 MQTT 接到当前 main（中间隔 111+ 提交，其中 `91fd7856` 动了 60 文件 -2935 行）；
- 工作量：中等，需要重新验证共存无冲突。

**2B. 边车桥接（另写一个 MQTT→3.0 适配进程）**
- 不动主后端，用一个独立容器订阅 EMQX、转成 3.0 协议写库；
- 优点：主代码零改动、可独立回滚；
- 缺点：多一个要维护的组件，且要处理 Hello/ConfigManifest 的语义映射。

**我倾向 2A**：设计文档已论证过，且双栈状态在历史上真实存在，
2B 的协议语义映射复杂度被低估了。

### 阶段 3：逐台换固件

```
P1  OTA 推 3.0 固件（host 已编译为 192.168.20.6）
P2  观察期：TCP 上跑通 Hello/ConfigManifest/采集 完整闭环
P3  关固件 MQTT 回退分支
P4  后端关闭 MQTT 监听          ← 回滚窗口在此永久关闭
P5  移除 EMQX 容器/端口/看板
```

⇒ 数据迁移是**已设计好的**，不是新问题。关键是 `data/postgres` 的属主（镜像内 uid=70）。

## 6. 一个必须提前说清的风险

**服务器 IP 变更 = 全网设备重新编译 + 重新烧录。**

因为 `EHOME_DEVICE_LINK_HOST` 是编译期常量、manifest 不下发 host。
如果 20.6 只是过渡，而将来还要换，这个成本要再付一次。

**建议（低成本、一次解决）**：把 host 改成可运行期覆盖 ——
优先级：NVS 存储 > 编译期默认。约 30 行代码，能彻底消除"换 IP = 全部重刷"的诅咒。
这件事值得在第一次 OTA 之前做掉，因为**第一次 OTA 是唯一免费的机会**。

| 3.0 软件 | ✅ 本机真机闭环已跑通（mTLS→Hello→配置→轮询→入库） |
| 部署资产 | ⚠ prod compose 仍是 MQTT 世代，需改写 |
| 服务器访问 | ❌ **SSH 不可达，这是第一道门** |
| 设备升级路径 | ❌ 双栈未实现 → OTA 下发不了 |
| 回滚手段 | ⚠ 未演练 |

## 8. 需要你决策的三件事

1. **20.6 的 SSH 凭据**（或改用其他可操作方式）—— 不解决则无法推进；
2. **20.6 是不是最终生产机**—— 决定固件 host 编译值，也决定要不要先做"host 运行期可配"；
3. **双栈走 2A（恢复 MQTT 代码）还是 2B（边车桥接）**—— 我建议 2A。
