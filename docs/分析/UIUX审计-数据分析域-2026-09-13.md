### [D3-01] 仪表盘 | 全视口 | light+dark | D3 人机反馈

**现象**: `/api/v1/overview` 返回 500 时，四个 KPI 全部渲染为 **0**，异常摘要卡显示**绿色对勾 + 「运行正常」+「节点与设备均在线，暂无采集错误。」**，与事实相反。

**证据DOM**:
```
# 拦截 /api/v1/overview → HTTP 500 后：
overviewFail.kpi = [{"v":"0","l":"节点总数"},{"v":"0","l":"在线节点"},{"v":"0","l":"设备总数"},{"v":"0","l":"在线设备"}]
overviewFail.alertText = "异常摘要运行正常节点与设备均在线，暂无采集错误。"
overviewFail.alertTag  = "运行正常"   (el-tag type=success)
overviewFail.alertIconColor = rgb(103, 194, 58)   # success 绿
overviewFail.messages  = ["获取概览数据失败"]      # 仅瞬态 ElMessage，转瞬即逝
overviewFail.elResult  = 0                        # 无错误态组件
overviewFail.skeletons = 0                        # 无骨架屏
overviewFail.trendHeader = "最近 24 小时趋势1小时24小时7天温度"
```

**证据截图**: `/tmp/uiux-d1/dashboard-overview-fail.png`（1440x944，真实存在；画面即上表所述：四个 0 + 绿色「运行正常」）

**证据代码**:
- `frontend-shared/src/views/dashboard/Dashboard.vue:18` — `<p class="stat-value">{{ overview.nodes?.total || 0 }}</p>`（:30、:42、:54 同型）
- `frontend-shared/src/views/dashboard/Dashboard.vue:98-101` — `<div v-else class="alert-ok"><el-icon color="var(--el-color-success)" :size="20"><CircleCheck /></el-icon><span>节点与设备均在线，暂无采集错误。</span>`
- `frontend-shared/src/views/dashboard/Dashboard.vue:470-480` — `fetchOverview` 失败只 `ElMessage.error`，`overview` 保持初始全 0 对象（:269-273）
- `frontend-shared/src/views/dashboard/Dashboard.vue:339` — `hasAlerts` 为 `false`（0>0 为假）→ 走 `v-else` 成功分支

**为什么导致该现象**: `overview` 初值是 `{nodes:{total:0,online:0,...}}`；请求失败时不区分「加载失败」与「真实为 0」，
`hasAlerts` 因全 0 而为 `false`，模板遂渲染成功语义。用户看到的是「系统一切正常」，而实际是一次失败。

**规范条款**: §1.2.1（"不能用模拟数据、猜测状态或前端默认值伪造设备事实；未知应明确显示'未知'或'—'"）、§3.4.2（"空状态不是错误状态的替代品"）、§3.2.5（"不得以本地默认值伪造'正常'"）、§4.3.3.3

**严重度**: **阻断**（用户会基于「运行正常」做出错误判断，且这是首屏第一信息）

**建议**: 在 `fetchOverview` 的 catch 中置 `loadError=true`；模板按 `v-if="loadError"` 渲染错误态（`EmptyState kind="error"` + 重试按钮）；KPI 区改用 `—` 而非 `0`，并**抑制**「运行正常」卡片。
**验收方法**: 拦截 overview 返回 500，断言 `document.querySelector('.alert-ok') === null` 且 `.stat-value` 文本为 `—`。

### [D5-01] 数据面板 | 全视口 | light+dark | D5 业务完整交互流程

**现象**: 翻到第 3 页后**更换设备**或**更换时间范围**，分页不重置，新查询直接以 `page=3` 发出。

**证据DOM / 网络原文**:
```

reqPage3      = /edge-devices/7053/data?start_time=2026-09-12T04:50:04Z&end_time=2026-09-13T04:50:04Z&page=3&page_size=20
a3 (改时间范围→最近30天)    page="3"          <-- 未重置
a4 (点查询)                page="3"
reqAfterRange = /edge-devices/7053/data?start_time=2026-08-14T04:50:08Z&end_time=2026-09-13T04:50:08Z&page=3&page_size=20   <-- page 仍为 3
a5 (改设备→"测试雨量计")
a6 (点查询)                page="3"
reqAfterDevice= /edge-devices/2/data?start_time=2026-08-14T04:50:12Z&end_time=2026-09-13T04:50:12Z&page=3&page_size=20      <-- page 仍为 3
```

**证据截图**: `/tmp/uiux-d1/data-after-light-1440.png`（真实存在）

**证据代码**:
- `frontend-shared/src/views/data/DataPanel.vue:462-467` — `page: currentPage.value, page_size: pageSize.value`
- `frontend-shared/src/views/data/DataPanel.vue:372-376` — `queryForm` 变更**没有** watch 重置 `currentPage`
- `frontend-shared/src/views/data/DataPanel.vue:228-237` — 只有 `el-pagination` 的 `@current-change`/`@size-change` 才调 `fetchData`
- `frontend-shared/src/views/data/DataPanel.vue:837-848` — 现存的 3 个 watch 只覆盖 `compareDevices` 与 `compareCategory`，不含查询范围条件

**为什么导致该现象**: `currentPage` 是独立 ref，只有分页组件自己会改它；筛选控件（设备/时间范围）变更时不失效派生状态，
查询按钮直接复用旧页码。当新范围总条数 ≤ 20 时（例如切到「最近1小时」的雨量计）会请求一个不存在的页，用户看到空表却以为没有数据。

**规范条款**: §3.2.6（MUST "对会改变查询范围的输入（节点、设备、型号、时间范围、筛选）重置或失效其派生状态：选中项、分页、异步结果、表单合法选项和缓存"）、§3.3.5

**严重度**: **高**（违反 MUST，且在常用视口下可导致「看起来无数据」的错误结论）

**建议**: 在 `queryForm.deviceId` 与 `queryForm.timeRange` 的 watch 中执行 `currentPage.value = 1`。
**验收方法**: 复跑上述 6 步，断言 `reqAfterRange` 与 `reqAfterDevice` 的 `page=1`。

### [D2-02] 系统监控 | 全视口 | dark | D2 配色与主题

**现象**: 暗色主题下**图表系列绿**与**DOM 绿色**解析为两个不同值，同页不同区域「成功/在线」色不一致。

**证据DOM**:
```
dark  tokens: { "--color-success": "#85ce61", "--el-color-success": "#67c23a" }
# 同时 dark 下实测：
el-progress inline style = "width: 0%; animation-duration: 3s; background-color: rgb(103, 194, 58);"   <-- #67c23a (亮色值)
canvas 系列色 top   = #85ce61, #79bbff, #f78989, #ce93d8, #ebb563                                    <-- 已随暗色
dark 下 .control-metric.attention strong 实测 color = rgb(245, 108, 108)   <-- 也是亮色的 #f56c6c
```

> 即：同页 `.stat-value .online`（走 `var(--el-color-success)`）与 `.el-progress`（走 JS 常量）分叉，
> 且暗色下 `--el-color-danger` 仍是 `#f56c6c` 而 `--color-danger` 已是 `#f78989`。

**证据截图**: `/tmp/uiux-evidence/desktop-1440-dark-monitor.png`（真实存在）

**证据代码**:
- `frontend-shared/src/views/monitor/Monitor.vue:196` — `:color="THEME_COLORS.success"`
- `frontend-shared/src/views/monitor/Monitor.vue:206` — `:color="THEME_COLORS.danger"`
- `frontend-shared/src/views/monitor/Monitor.vue:229` / `:239` — 节点状态两条进度条同型
- `frontend-shared/src/views/monitor/Monitor.vue:305` — `import { THEME_COLORS } from '@/utils/theme'`
- `frontend-shared/src/utils/theme.ts:17-23` — `THEME_COLORS` 是模块级静态 `as const` 常量，**不随主题变化**（注释自述 "for JS-only contexts"）
- `frontend-shared/src/styles/theme.css:113-142` — 暗色块只覆盖 `--color-*`，**未覆盖** `--el-color-*`，故 `--el-color-success` 暗色仍为 `#67c23a`

**为什么导致该现象**: `THEME_COLORS` 在模块加载时求值一次，对主题切换无响应；
同页的 CSS 变量路径会随 `html.dark` 变化，JS 常量路径不会。

**规范条款**: §3.6.2（MUST "新增图表颜色通过 getThemeColors()/getThemeSurfaceColors() 或等价 token 解析，以支持亮暗主题；禁止组件内写独立亮色调色盘"）、§3.6.1、§3.6.5

**严重度**: **中**（一致性缺陷；不阻断任务，但同页同语义两色，且暗色下偏亮刺眼）

**建议**: `Monitor.vue` 的四处 `:color` 改为计算属性取 `getThemeColors().success/danger`（该函数每次调用重新读取 CSS 变量），并在 theme store 变化时触发重算；
或在 `theme.css` 暗色块补齐 `--el-color-success/danger/warning/info` 桥接。
**验收方法**: 暗色下断言 `.el-progress-bar__inner` 的 computed backgroundColor === `--color-success` 解析值（`#85ce61`）。
