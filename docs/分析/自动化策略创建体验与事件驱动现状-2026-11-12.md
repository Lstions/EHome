## 0. 结论摘要

1. **后端已经把"能选的东西"全准备好了，前端一个都没接。** 字段目录（`GET /sensor-fields`）、词表（`/schema`）、试算（`POST /sensor-fields/preview`）、保存前 selector 诊断（`POST /automation-rules/precheck` 的 `warnings`）、动作目录（`GET /edge-devices/:id/actions`）、参数表单（`input_schema` + 现成 `ActionForm.vue`）都在生产可用；前端 `grep "sensor-fields"` 命中 **0**（只有一份 README 说明和一条 e2e mock）。
2. 创建对话框 **26 个表单项（含按触发器类型条件显示的子项）里有 9 项纯手打**，其中 **6 项**的权威候选就在系统内（字段目录 ×2、动作目录、参数 schema、IANA 时区、时间控件）。
3. 最严重的一处是"传感器"：它其实不是名字，而是**字段选择器契约**（字面量 / 字段族 + 6 种聚合 / 语义别名 / 派生量），UI 却是一个 placeholder 写着"如：temperature"的文本框。写错一个字母 → 保存成功、永不触发、无任何界面反馈。
4. **25.4% 的字段是"选中即死"的陷阱**：71 个字段里 `boolean` 14 个、`enum` 2 个、`bitmask` 2 个。这些字段能选中、能保存，但比较永远返回 `non_numeric` ⇒ 规则永不触发。
5. **后端算好了"这条规则可能永不触发"，前端把它丢了**：`precheck.warnings` 在 `AutomationRules.vue` 里 0 引用；`blocking_errors` 也只弹第一条（`ElMessage.warning(blocking[0])`）。
6. 时间窗口两个输入是无校验文本（`placeholder="HH:MM，如 08:00"`）：填 `8:00`（不补零）能被保存，运行期 `time.Parse("15:04")` 失败 → 只写一条服务端 warn 日志，**不落审计、界面无痕**。
7. **事件驱动不是"没做完"，而是"语义未冻结"**：模型常量占位、无字段、无求值分支、创建被 400 拒绝、前端是 disabled 项。存量 event 规则（若有）既不执行也不审计——比"不支持"更糟。

> 改造窗口正好：生产 `automation_rules` = 0 行，没有任何存量规则要兼容。

## 3. 传感器阈值触发：四层缺陷

### 3.1 一根裸字符串背后的真实契约

`trigger_sensor_name` 的类型是 `varchar(64)`，但它的语义是"字段选择器"，四类文法互斥（`sensorfield/doc.go:5-13`、`selector.go:46-51`）：

| 形态 | 例子 | 用途 |
|---|---|---|
| 字面量 | `temperature_1` | 精确字段 |
| 字段族 + 聚合 | `cell_voltage_*:max` | "16 节电芯里最高的那节"，聚合 ∈ `any/all/min/max/avg/sum` |
| 语义别名 | `@soc` | 跨厂商同义字段（需 `field_aliases.yaml`） |
| 派生量 | `virtual:cell_delta` | 多字段计算（需 `virtual_fields.yaml`） |

现状 UI（`AutomationRules.vue:352-359`）是一个 placeholder 写着 `如：temperature` 的文本框。后果是**用户永远发现不了后三类能力**，而写错字面量又没有任何界面反馈——这正是 `sensorfield` 包存在的理由（`doc.go:5-8`："规则里写错一个字母，保存成功、永不触发、没有任何报错"）。

### 3.2 非数值字段是陷阱（25.4%）

机制链（已核对代码）：

    sensor_field_meta.value_type = boolean|enum|bitmask|string|raw
      → resolve.go:55-60 fieldNumeric() = false
      → eval.go:297-305 判定 numeric=false ⇒ Verdict{OK:false, Reason:"non_numeric"}
      → 规则永不触发，每次求值落一条 unresolved_selector 审计（5 分钟节流）

与设计文档一致（`数据字段解析层-方案 §12.1`："非数值 value_type 参与比较 ⇒ 视为缺失 + 指标，fail-closed"）。但这个 fail-closed 对用户是**完全静默**的：下拉里 `protection_status` 和 `temperature_1` 长得一模一样。

> 这里不需要改后端：门禁应该做在**候选列表**上（默认只列 `value_type=number` 或未知类型），而不是让用户先选中、再在运行期失败。

### 3.3 保存前诊断已经产出，前端把它丢了

后端 `collectSelectorDiagnostics`（`handler_automation.go:1380-1435`）对每条规则做：

- 语法/未知语义/未知派生 ⇒ 进 `blocking_errors`（前端会拦，但**只显示第一条**）；
- 语法合法但当前解析不到 ⇒ 进 `warnings`，原文：

      选择器 "temperatuer" 当前解析不到（resolution_unbound），保存后可能永不触发

前端 `onSave`（`AutomationRules.vue:1408-1423`）只读 `blocking_errors` 与 `risk_actions`，**`warnings` 全页 0 引用**。于是最有价值的那句提示（"你可能写错了字段名"）根本没有到达用户。

顺带两个同类问题：

- `ElMessage.warning(blocking[0])`：多个错误只显示第一个，用户改一条、再保存、再看第二条（往返 N 次）；
- 校验失败提示是 `ElMessage`（3 秒消失），没有字段级红字，用户回去找不到是哪一项。

### 3.4 结果码没同步：英文原串直出到界面

后端在运行期会写两个结果码（`sensorfield/selector.go:44-45`）：`unresolved_selector`、`field_resolver_disabled`。前端：

| 位置 | 缺什么 | 后果 |
|---|---|---|
| `api/automation.ts:45-64` `AutomationEventResult` 联合类型 | 缺 2 个码 | 类型层面不承认这两个值 |
| `AutomationRules.vue:793-806` `resultOptions` | 缺 2 个筛选项 | 无法按"选择器解析不到"筛选 |
| `:1737-1756` `resultText` | 缺映射，`return map[r] ?? r` | 结果列直接显示 `unresolved_selector` |
| `:1757-1764` `resultTagType` | 落到 `'info'` | 一个"配置错了"的状态被画成中性灰 |

设计文档本来就要求前端同步（`数据字段解析层-方案:637`："前端枚举 `AutomationEventResult` 必须同步新增两个值"），这条没落地。

### 3.5 同一类问题的第二个实例：时间窗口

- 前端只校验非空（`validate()`，`:1183-1184`），placeholder 说 `HH:MM，如 08:00`；
- 后端保存期同样只校验非空（`handler_automation.go:935-937`）；
- 运行期 `parseHHMM` = `time.Parse("15:04")`（`evaluator.go:921-924`），`8:00` 解析失败；
- 失败路径：`logger.Warn(...) + return`（`evaluator.go:830-836`）—— **不落审计、不产生事件、界面无任何痕迹**。

一个时间选择器就能把这一类"文本无校验 → 静默死规则"整类消灭。

## 4. 优化设计

### 4.1 核心：字段选择器（P0）

**数据源**（唯一新增请求，1 次/设备，可缓存）：

    GET /api/v1/sensor-fields?edge_device_id=<id>
    → { edge_device_id, device_type, truncated,
        fields: [{ name, unit, label_zh, value_type, precision,
                   sources:["decl","obs"], semantics:[], first_seen, last_seen,
                   samples, deprecated }] }

**降级链**（任何一层拿不到都不阻塞建规则）：

1. `/sensor-fields`（中文名 + 单位 + 类型 + 最近上报）；
2. `/unified-data/categories?device_pk=`（只有 code + unit，无类型、无中文名）；
3. 纯手输（`allow-create`），但**保存前必须过 resolve 校验**（§4.1 末）。

**交互**（两行，默认收在"数值字段"上）：

    字段   [ 数值 53 | 全部 71 ]   ← 分段控件，默认"数值"（53 = value_type:number）
           ┌─────────────────────────────────────────────────────────┐
           │ 电池电流          current               A     2s 前     │
           │ 温度探头 1        temperature_1         °C    2s 前     │
           │ 电芯电压族(16)    cell_voltage_*        V     —         │  ← 族伪条目
           │ 单体最高电压      cell_voltage_max      V     2s 前     │
           └─────────────────────────────────────────────────────────┘
    已选   temperature_*:max  ⌄聚合   · 3 个探头取最大值 · °C

- 列表项文案 = `label_zh` + 物理名 + 单位 + `last_seen` 相对时间（"2s 前" / "3h 前" / "从未上报"）。`last_seen` 是关键信息：它区分"字段存在但设备现在不发了"和"字段根本不存在"。
- 搜索匹配 name 与 label_zh（中文搜"温度"能命中 `temperature_1`）。
- `deprecated:true` 的字段灰显 + 标注（后端已下发）。
- 选中后在下方显示一行**解析摘要**：中文名、单位、当前值（取 `/edge-devices/:id/latest-values`）、解析成员数。用户不需要记住物理名。

**类型门禁**（消除 25.4% 陷阱）：

- 默认只列 `value_type ∈ {number, 未知}`；
- 切到"全部"时，非数值字段带灰色标记 `非数值，阈值比较不生效`，**不可选中**（而不是选中后运行期失败）；
- 若未来要支持 `boolean`（"为真/为假"）或 `bitmask`（"第 N 位为 1"），那是后端语义扩展（新增比较符/谓词），不在本次范围——**不要用 `= 1` 假装支持**，因为 `fieldNumeric` 会直接判 unbound。

**字段族 + 聚合**（把最强能力暴露出来）：

- 客户端从同一份列表按 `^([a-z][a-z0-9_]*)_\d+$` 聚出族（≥2 个成员才成"族"），族条目里直接给出成员数与聚合下拉；
- 聚合词表**必须**从 `GET /sensor-fields/schema` 的 `aggregates` 读（设计文档 §8.4 明令"禁止在代码里另存一份"），默认值读 `aggregate_default`（= `any`）；
- 每个聚合旁给一句人话 + 缺员语义（这是最容易配错的地方）：

| 聚合 | 人话 | 缺员（本帧少一个探头） |
|---|---|---|
| `any` | 任意一个满足 | 不影响 |
| `all` | 全部满足 | unbound（不触发） |
| `max` / `min` | 最高 / 最低那个 | 按现有成员求值，标 degraded |
| `avg` / `sum` | 平均 / 合计 | unbound（不触发） |

**语义别名**（`@soc`）：

- 候选来自 `/schema.aliases`；列表为空（未配 `field_aliases.yaml`）时**整块隐藏**——不要展示一个选不出东西的模式；
- 命中多候选时展示"已归一为 `rsoc`（首候选）"。

**保存前校验**（把后端能力用起来）：

- 失焦或防抖 400ms 调 `GET /sensor-fields/resolve?edge_device_id=&selector=`；
- `status=unbound` ⇒ 行内黄条："当前解析不到，保存后可能永不触发"（**允许保存**，与后端软校验口径一致）；
- 400 + `error_code`（`invalid_selector_syntax` / `unknown_semantic` / `unsupported_aggregate` …）⇒ 行内红字 + 逐码人话（错误码表从 `/schema.error_codes` 读，不硬编码）。

**为什么不是"一个普通下拉就够了"**：普通下拉只能产出字面量，等于把"字段族极值 / 语义别名"这两个已经实现、且是 BMS/逆变器场景最常用的能力永久藏起来。§3.1 那张表就是差距本身。

### 4.2 阈值控件（P0）

- 数字框后缀显示单位（来自字段目录；未知时不显示）；
- 小数位优先 `precision`（当前生产 71 行全为空 ⇒ 回落 3 位，与现状一致）；
- 比较符保留符号并加中文语义：`高于 >`、`不低于 ≥`、`低于 <`、`不高于 ≤`、`等于 =`、`不等于 ≠`；
- 阈值旁给一条**可达性提示**（P2，见 §4.4）："用近 24h 数据试算：满足 3 次"。

### 4.3 附加条件结构化（P1）

把 `conditions_json` 文本域换成"条件行"：

    附加条件（全部满足）                                   + 添加条件
    [温度探头 2 ⌄]  [高于 > ⌄]  [45] °C    ✕
    [剩余电量 ⌄]    [低于 < ⌄]  [20] %      ✕

- 与传感器选择器**复用同一组件**（后端条件走的也是同一个 selector 契约：`conditionsSatisfied → evalSelector`，`evaluator.go:1018-1033`）；
- 序列化键与后端 `models.AutomationCondition` 一致：`sensor_name / comparator / threshold`；
- 保留"JSON 源码"折叠面板（迁移期与排障用），但默认不展示。

收益：`conditions_json` 目前是唯一需要用户懂 JSON 的地方，而它恰好是"复合条件"这种高级能力的入口——手写 JSON 把使用门槛抬到了只有开发者能用的高度。

### 4.4 试算：保存前预演可达性（P2，但价值最高的一项）

`POST /api/v1/sensor-fields/preview` 已经实现了完整语义（逐帧重放 + 连续满足判定 + 缺员标注），请求体正好是表单里已有的字段：

    { edge_device_id, selector, comparator, threshold, window_hours, duration_sec }
    → { samples_considered, frames[], duration_would_fire, reduced,
        missing_known[], aggregation_trace[], sparse_frames, data_source }

UI 一行话：

    近 24h 试算：满足 37 帧；最长连续满足 4m10s（持续时长 60s → 会触发）。

或：

    近 24h 满足 0 次。阈值 45°C 从未达到（该字段最高 42.8°C）→ 规则保存后不会触发。

这是**唯一能在保存前回答"这条规则会不会永远不响"的功能**，比任何文案都有效。实现成本：1 个按钮 + 1 个请求 + 1 行结论（`duration_would_fire` 已是后端算好的布尔值）。

## 5. 事件驱动：设计与实现状况

### 5.1 设计意图（原文）

    ③ event（事件驱动，预留）
    节点上线/离线、告警 firing 等系统事件作为触发源。本期仅定义类型占位，不实现

模型注释同口径（`models/automation.go:22`："本期仅占位, 未实现"）。所以"预留"是**主动裁决**，不是遗漏。

### 5.3 "语义未冻结"具体冻结的是什么

现在的 4 个字段（sensor/comparator/threshold/window）没有一个能表达"哪个事件"。要做，必须先冻结四件事：

1. **事件词表**：`event_kind` 的取值域 + 每个 kind 携带的参数（如 `alert_firing` 要 `alert_rule_id`、`device_offline` 要 `edge_device_id`）。
2. **触发证据**：`automation_events.trigger_value` 是 `float64`（`models/automation.go` 事件表），承载不了"哪个事件实例"。现状代码已有 `value != 0 || trigger_type == sensor_threshold` 的特判（`evaluator.go:1107`、`planner.go:499/548/879/910`），说明"非传感器规则没有数值"这一点已经处理；缺的是**可查询的证据**（建议 `source_event_kind` + `source_event_id` 两列，或 JSON 列，而不是塞进 `detail` 文本——文本不可筛选、不可去重）。
3. **时间语义**：瞬时事件错过是否补触发？`sun_event` 已给出先例——**首 tick 保守不触发、绝不补触发**（`evaluator.go:651-656`）。事件驱动必须沿用同一条裁决，否则进程重启后"把积压的 N 条离线事件一次性全部执行"会直接打到设备上。
4. **去重/幂等**：同一事件可能重复投递（WS 重连、重试、状态抖动）。需要 `(rule_id, event_key)` 唯一性或内存指纹 + 冷却，否则一次抖动触发两次动作。

其余机制**全部可复用**：冷却、日熔断、确认制、风险授权、多动作串行、审计。不需要新造。

### 5.4 候选事件源与接线点

| 事件 | 现有可挂接点 | 接线代价 | 价值 |
|---|---|---|---|
| 告警 firing / resolved | `alert/evaluator.go:544-566`（写 `alert_events` + `Notification` + WS） | 小（单点，且有 rule_id/level 可过滤） | **高**（"告警时联动关断/开窗"） |
| 设备离线 / 上线 | `internal/offlinedetector`（状态翻转 + `edge_device_status` 广播） | 小 | **高**（"离线关阀、上线恢复"） |
| 命令执行终态 | `commandexec` 状态机终态写入 | 中（状态多、要区分失败原因） | 中 |
| OTA 完成 / 失败 | `ota_completed` 广播点 | 小 | 低 |
| 节点上下线 | `node_status` | 中 | 中 |

> 现状没有事件总线：`internal/events` 只有 WS 事件**名字常量**，广播是各处回调（`hub.broadcast`）。所以"事件驱动"落地时**不要**顺手造一个通用 event bus（那是另一件事），直接在两个写入点调用求值器即可。

### 5.5 建议的最小 v1（先冻结、再实现）

契约（对现有 API 是纯加法，不破坏任何字段）：

    trigger_type = "event"
    trigger_event_kind ∈ { alert_firing | alert_resolved | device_offline | device_online }
    trigger_event_filter_json = {"edge_device_ids":[14]} | {"alert_rule_ids":[3]} | {"min_level":"warning"}

- 求值：事件写入点调用 `Evaluator.HandleSystemEvent(ev)` → 按 kind + filter 匹配 → 走**既有** `applyTrigger/Planner` 路径（冷却/日熔断/确认制全复用）；
- 分派：`evalRule` 入口必须**按 `trigger_type` 分派**（今天不看类型，`event` 规则会被数据路径误求值——这是 event 必须禁创建的根本原因之一，不能只靠前端不生成）；
- 证据：`automation_events` 增 `source_event_kind` / `source_event_id`（可空，仅 event 规则填），`trigger_value` 置 0；
- 语义：**瞬时事件，不补触发**（与 sun_event 同裁决），前端明写这句话；
- 灰度：创建端仍保留 400 开关，等语义冻结评审通过再放开；
- 门禁：新增 kind 需同时改 `models` 常量 / 校验白名单 / 前端联合 / 仿真白名单（与 §3.4 那两个漏掉的码同一条纪律——这次别只改一处）。

工作量：后端 2–3d（两个接线点 + 幂等 + 单测），前端 0.5–1d（事件类型下拉 + 过滤选择器 + 说明文案），**前置是一份语义冻结稿**（1 页）。

### 5.6 明确不做

- 通用事件总线 / 事件 DSL（当前只有 2 个真实事件源，抽象没有第二个用户）；
- 事件回调链（A 触发 B 触发 C）：环路检测、深度上限、爆炸半径全都要新机制；
- 把 `event` 当成"任意条件"的逃生门（它会绕过确认制与风险授权的语义）。
