# CI 仿真 job 偶发红：根因与处置（2026-09-17）

> `Backend (scenario simulation)` 曾**连续两次**在 CI 失败，而本地同一棵树多轮全绿。
> 本文记录根因、证据链与防复发措施。**根因不是环境噪声，是一个 6.25% 概率的测试缺陷。**

## 1. 现象

| 运行 | 提交 | 结果 | 失败场景 | 特征 |
|---|---|---|---|---|
| run 35051586582 | `abe3a7b0` | ❌ | `SIM-CMD-002` | `Eventually` 30s 超时，`config_status=pending / config_sync_state=syncing` |
| run 35114984093 | `c7742ef1` | ❌ | `SIM-AUTH-007` | **0.00s** 瞬时断言失败 |
| run 35177843739 | `d34d8c68` | ✅ **success** | — | 138 场景完整跑完（16m48s），`FAIL` 计数 0 |

本地在**同一棵树**上跑 138/138 全绿（`sim-20260917-d5a4`，`GO_EXIT=0`）——
这正是最难办的一类：**「本地绿」无法证伪**。

## 2. 为什么一开始定位不了（诊断能力的教训）

- CI 的失败 annotation 只有 `Process completed with exit code 1.` —— **不含场景名**
- 完整细节在 `simulation-evidence` artifact 里，而 **artifact 需要认证**（匿名下载 401）
- job 日志同样需要认证（403）

⇒ 装上 `gh` 并登录后，一条命令就拿到了根因：

```bash
gh api "repos/Lstions/EHome/actions/jobs/<job_id>/logs" | grep -E 'FAIL: TestScenarios/|auth.go:[0-9]+:'
```

**这条应当写进 README**：CI 红的诊断入口是 `gh`，不是网页。

## 3. 根因：`SIM-AUTH-007` 的「篡改令牌」有时**根本没篡改成功**

失败信息（CI 与本地历史**逐字相同**）：
```
auth.go:331: 篡改令牌应返回 401，实际 200: {"code":200,"data":{"items":[],"page":1,"page_size":20,"total":0},"message":"ok"}
```

### 机制

```
HS256 签名 = 32 字节
base64url(无填充) 编码 = ceil(32*8/6) = 43 字符
43 × 6 = 258 位，而有效载荷只有 256 位
⇒ 末字符仅**低 2 位**参与解码，高 4 位被丢弃
```

旧实现 `authFlipLastChar` 把**末字符**改成 `'A'`（若已是 `'A'` 则改 `'B'`）。
canonical 编码的末字符只可能是 16 种：`AEIMQUYcgkosw048`。
当它本来就是 `'A'`（index 0）时，`'A'` → `'B'`（index 1）**低 2 位相同**
⇒ **解码后签名逐字节不变** ⇒ 令牌没被篡改 ⇒ 服务端返回 200 ⇒ 用例断言 401 **假红**。

**概率 = 1/16 = 6.25%**（实测 3000 次随机签名：5.67% 不改变解码结果，与理论吻合）。

### 三个独立佐证
1. 两条记录（2026-09-15 本地 `sim-20260915-0acc`、2026-09-16 CI）失败消息**逐字相同**
2. 两次都是**瞬时**（`duration_ms: 1` / `0.00s`），不是超时
3. `SIM-AUTH-007` 在本地全量历史中失败 **1/14** 次 ≈ 7%，与 6.25% 同量级

## 4. 修法（两处）

1. `authFlipLastChar` → **`authTamperSegment`**：改**首字符**。
   base64url 首字符 6 位**全部有效**，改它必然改变解码结果（实测 3000 次：改变率 100%）。
2. **语义修正**：原调用点改的是**整串末字符** —— 那落在 **header 段**上，
   根本不叫「签名被篡改」。已改为明确篡改**签名段**（第 3 段）。

## 5. 防复发：把概率问题变成**确定性**判据

⚠️ 光修代码不够：6.25% 的偶发率下，**「再跑几轮绿」不是证据**。
必须用穷举把不变量钉死。

新增 `backend/simulation/catalog/auth_tamper_invariant_test.go`（`go test` 秒级，无需起服务）：

| 用例 | 判据 |
|---|---|
| `TestAuthTamperSegmentAlwaysChangesDecodedBytes` | **穷举** 64 个 base64url 字符分别作首/末字符，断言**解码后的字节**必须改变（只断言字符串变了不够 —— 旧实现字符串确实变了、解码没变） |
| `TestAuthTamperSegmentLastCharIsUnsafe` | 反向守卫：断言「末字符方案确实存在不生效的取值」，记录**为什么不能用末字符** |

**变异自证**：退回末字符逻辑 ⇒ 红，报
`first 字符 'A'：篡改后**解码字节未变**（长度 32）—— 「篡改」没生效，这会让 SIM-AUTH-007 变成假红`；
恢复后绿。端到端 `SIM-AUTH-007` 连跑 3 次全绿 + SIM-AUTH 全域绿。

## 6. 另一处**未修**的独立问题

`abe3a7b0` 那次失败的 `SIM-CMD-002`（`Eventually` 30s 超时，节点停在
`config_status=pending / config_sync_state=syncing`）**与本次不是同一个问题**：

- 它在**本地 14 次全量运行中 0 次失败**，只在 CI 出现 ⇒ 环境相关
- 怀疑与「CI 冷启动容器 vs 本地复用已运行 9 天的共享 PG/EMQX」的时序差异有关，**未证实**

⇒ 处置建议：**先加可诊断性**（失败场景名进 job summary / step summary），
再观察是否复现；不要在没有证据的情况下改断言（那是拆门禁）。

## 7. 纪律产出

1. **偶发率低的缺陷，用「跑几轮绿」证伪是不可能的** —— 必须穷举输入或把判据降到不变量层。
2. **测试的构造代码本身也要被测试**：本例缺陷不在被测系统（服务端正确拒绝了真篡改），
   而在**构造篡改的辅助函数**。它此前没有任何单元测试。
3. **假红的危害等同假绿**：它让团队对红色信号脱敏，最终导致真红被忽略。
4. **CI 日志的可达性 = 可诊断性**：artifact 需认证、annotation 无细节，等于把根因藏起来。
   装 `gh` 之前，我只能在「环境差异」的猜测上打转。
