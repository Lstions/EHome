## 0. 一句话结论

路线 A 不是"接线"，而是"改数据模型 + 改响应契约 + 改前端口径"三件事的合并；
而它要服务的查询**在生产代码里恒不走 rollup**（`precisionFor` 自己的规则 + §1.1 的实测使然）。
⇒ A 的投入是真金白银，产出是一条**当前不可达**的路径。B 的代价是本轮已实测确认的**零能力损失**。

## 1. 问题 1：接线的工作量到底多大？

### 1.1 关键发现：`precisionFor` 的 rollup 分支在生产**不可达**

`precisionFor`（`backend/internal/api/latest_value_cache.go:73-88`）的规则是
"**跨度 > 48h 且 logical scope 为空**才走 rollup"。那么"logical scope 为空"何时发生？

| 证据 | 位置 | 含义 |
|---|---|---|
| `if dev.LogicalDeviceID == nil || *dev.LogicalDeviceID == 0 { return qs, nil }` | `datalifecycle/query_scope.go:59` | `LogicalID == 0` ⟺ 实例的 `logical_device_id` 为 NULL |
| `BackfillLogicalDevices`：`Where("logical_device_id IS NULL")` → 逐条建逻辑设备并回写 | `datalifecycle/identity.go:74-96`（启动调用） | **启动时全量回填**，正常实例不会停留在 NULL |
| 新实例创建即赋逻辑身份 | `api/handler_edge_device_lifecycle.go:96`、`handler_edge_device.go:499` | 运行期新实例同样不会停留在 NULL |

⇒ 生产环境下 `hasLogicalScope` **几乎恒为 true** ⇒ `precisionFor` 恒返回 `"raw"`。
即便把三个历史端点全部接上 `precision` 参数，**auto 与显式 `rollup` 都会落回 raw**，
唯一的例外是"实例不存在 / 回填前旧数据"这条**兜底**路径——那正是 handler 当前用 `device_id = ?` 查 NULL-logical 旧行的路径。

> 这不是实现瑕疵，而是**语义自洽的结果**：读取侧协议（§六）以**逻辑身份**为口径，
> 而 rollup 表以**物理实例**为口径。两者在"合并设备"这个核心场景上不可能同时成立。

### 1.2 scope 语义与 rollup 表结构：**对不上**（明确结论）

| | `unified_data`（handler 现在查） | `unified_data_rollup_1m` |
|---|---|---|
| 逻辑列 | `logical_device_id`（普通列，可预测） | **不存在**（DDL 实测：`partition_mgr.go:194-205` 仅 device_id/sensor_name/bucket/min_v/max_v/avg_v/last_v/last_id/cnt；模型 `models.go:271-281` 同） |
| scope 条件 | `Scope.Cond()` → `logical_device_id IN ?` / `(logical_device_id IN ? OR (logical_device_id IS NULL AND device_id IN ?))`（`datalifecycle/scope.go:32-53`） | **列不存在 ⇒ 该条件无法落到该表** |
| 兜底条件 | `"device_id = ?"`（`handler_data.go:25-30`） | 语法上可用，但**语义不等价**（见下） |
| 行粒度 | 每样本一行 | 每 (device, sensor, 分钟) 一行（`rollup_consumer.go:42-58` 的 UPSERT 冲突键） |

**"不等价"的具体形态（这是比"精度变粗"更严重的一档）**：
`device_id = ?` 这条兜底条件在 raw 上之所以正确，是因为回填前的数据行 `logical_device_id IS NULL`，
而回填**只回填实例、不回填历史行**（`identity.go` 只 `Update` `edge_devices`）。
反观 rollup 表，其行**没有逻辑列可筛**，一个 device_id 的**全部历史分钟桶**（含回填后带逻辑身份的时段）
都会被同一条 `device_id = ?` 返回 —— 即：**读出了 raw 路径刻意隐藏的、逻辑上属于另一 scope 的数据**。

⇒ **结论：scope 语义落不到 rollup 表上。** 路线 A 若要保住 §六 口径，必须
**(a)** 给 rollup 表加 `logical_device_id` 列 → 改 DDL + 改 UPSERT 冲突键（`(device_id,sensor,bucket)` → 需含逻辑列）
+ 历史数据重聚合回填；或 **(b)** 接受 device_id-only 的**错误 scope**。
(a) 是数据模型变更，(b) 是正确性回归。**两者都不是"接线"。**

### 1.3 工作量清单（若强行走 A）

| # | 改动 | 性质 |
|---|---|---|
| 1 | 三个端点（`handler_data.go:165 / :271 / :333`）解析 `precision`、算 span、调 `precisionFor` | 真正的"接线"（小） |
| 2 | rollup 分支：`SELECT device_id,sensor_name,bucket,last_v,... FROM unified_data_rollup_1m` + 重建 scope 条件 | 需要新的 scope 方案（大，见 1.2） |
| 3 | **响应适配器**：`[]models.UnifiedData`（id/unit/created_at/edge_device_id/logical_device_id）在 rollup 上没有对应列（**rollup 无 unit、无 id**），必须合成 | 中；引入"合成行"这一新契约 |
| 4 | 选择 min/max/avg/last 中的哪一个作为 `value` | 语义裁决（画图口径变化） |
| 5 | `max_points` 降采样（`downsampleUnifiedData`，`handler_data.go:35-50`）与分钟桶叠加 | 双重降采样口径 |
| 6 | 前端不必改（`frontend-shared/src` 实测**零 `precision` 参数**；`useHistoryData.ts:81-89` 只发 device_pk/categories/start_time/end_time/max_points） | **无前端配合**——但也意味着 auto 规则是唯一入口，而它恒 raw |

### 1.4 附带发现（支持 B 的一个新证据）

`rollup_consumer.go:55-56`：`last_v = EXCLUDED.last_v`（**按写入顺序**取最后写入者）
而 `last_id = GREATEST(表内 last_id, EXCLUDED.last_id)`（**按 id 最大值**取）。
两者口径不一致：**乱序写入 / 回填写入**会让 `last_v` 与 `last_id` 指向不同样本，
即"保形去重语义锚点"本身在非顺序写入下会漂移。当前**零读取者**，所以这个缺陷从未被任何查询暴露；
一旦路线 A 上线并依赖 `last_v`，这将是一个静默的正确性缺陷（需先修写入侧顺序语义）。

## 2. 问题 2：rollup 的聚合语义够不够用？

**结论：不足以支撑现有契约；只能支撑一个"单实例、分钟分辨率、取值=每分钟最后样本"的窄场景。**

| 前端需要 | rollup 能提供 | 判定 |
|---|---|---|
| 时间序列点 `{time, value}`（`useHistoryData.ts:53-55 `mapItem`：`created_at || timestamp` + `value`） | 每 (device,sensor,分钟) 一行的 `bucket` + 4 个候选值 | ⚠️ **需要裁决 value 取哪个聚合列**（avg 会"发明"未发生过的读数） |
| `unit`（tooltip/图例） | **无该列** | ❌ 需另查或硬编码 |
| `id`（行标识） | 无（`last_id` 只是每分钟最新样本的 raw id） | ❌ 需合成 |
| **保形去重**后的序列（§六：per (sensor_name, timestamp) 保留 MAX(id)，跨物理设备） | `last_id = MAX(id)` 只在**分钟桶内、单 device** 有定义；跨设备去重无对应结构 | ❌ 语义对不上 |
| 精确值 / 单点回读 | 只有 min/max/avg/last/cnt | ❌ |

**`last_id` 能否支撑"去重后的序列"？**
能支撑**一个更弱的命题**：对**单个 device_id**，"每分钟保留最新样本" 可由
`(bucket, last_v)` 近似还原（前提：写入顺序 = 时间顺序，见 §1.4 的反例，该前提并不成立）。
不能支撑 §六 的去重语义，因为后者的分区键是 `(sensor_name, timestamp)` 且**跨实例**，
而 rollup 的键是 `(device_id, sensor_name, bucket)` —— 停机/合并切换期间两个实例同分钟写入时，
rollup 会给出**两行**，去重后的序列应给出**一行**。**键不同，无法在 rollup 上复现去重。**

## 4. 为什么不是 A（对"半成品该收口"判据的正面回应）

判据（*半成品该收口，而不是继续留一半*）**成立**，但"收口"不等于"必须把消费者接上"。
收口 = **让仓库的状态与它的宣称一致**。两个方向都能收口：

- 接上消费者（A）：需要 §1.3 的 6 项改动，其中 2 项是数据模型/契约变更，而收益是一条
  **生产不可达**的路径（§1.1）——即"收口"的代价是真金白银，收益是零。
- 停写 + 删孤儿读取件（B）：**一行接线切断增长源**；同时删掉 `precisionFor`，
  使"读取侧从未接线"这一事实**在代码里可 grep 到**，而不是靠文档记账。

**⇒ 选 B。A 不是被"懒得做"否决的，是被 §1.1 + §1.2 否决的：它要服务的那条分支在当前协议下恒不可达，
而唯一可达的分支 scope 语义是错的。** 若将来产品确实要"长跨度趋势"，正确做法是**重开一张卡**：
先裁决 rollup 的 scope 口径（加逻辑列 or 明确 device-only），再谈接线 —— 那时 `precisionFor` 也需要重写，
所以本轮删除它不损失任何未来工作。

## 5. 不变式与门禁（INV-7 修正版的落地）

INV-7（修正版）要求"**存在消费者 ⟺ 清理器已配置且窗口 ≥ max(retention_days)**"，且
"两者都没做 ⇒ 不红"。本轮把这条不变式做成**可执行的门禁测试**
（`datalifecycle/rollup_wiring_gate_test.go`，源码扫描，不含 PG 依赖）：

1. **写侧接线**（`nodemgr/manager.go` 出现 `SetRollupSink(`）⇒ 必须同时存在
   **读侧消费者**与**保留期配置**；二者缺一 ⇒ **红**。
2. **读侧消费者**（生产代码出现对 `unified_data_rollup_1m` 的 SELECT）⇒ 必须存在保留期配置 ⇒ 否则 **红**。
3. **两者皆无**（本轮停写后的状态）⇒ **绿**（条件式不变式的本义：不约束一个不存在的功能）。

这条门禁同时是**回归锁**：任何人把 `SetRollupSink` 接回去而不带读取路径/保留期，测试立刻变红——
精确地防止本卡修复的"半成品"再次出现。本轮已做**变异自证**（见 §6）。
