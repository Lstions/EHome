**U-1 与 U-2 的共同模式值得单独记**：两者都是**"失败被静默伪装成正常"**——
U-1 是运行时（接口失败 → 界面说正常），U-2 是测试时（断言太弱 → 缺陷说通过）。
这与仿真层要解决的「单测全绿但引擎从未触发」是**同一类失败**。

**本轮已累积该家族的 4 个实例**（模式一致、载体不同）：

| # | 实例 | "伪装"形式 | 发现方式 |
|---|---|---|---|
| 1 | 接口失败 → /dashboard 显示绿色对勾「运行正常」 | 运行时状态 | D1 域审计 + 主控复现 |
| 2 | 固件编辑返回 200 但数据未变 | 运行时结果 | D3 域审计 + **主控真实 API 闭环** |
| 3 | `toContain` 对缺陷 URL 恒真 → P0 存活数月 | 测试断言 | D4 域审计 + **主控真实 vitest** |
| 4 | **假分页**：前端有分页器、后端忽略 page 参数 | 交互语义 | 任务 D **施工前核实任务书前提**时发现 |

> **共同点**：四者都让"看起来在工作"与"实际在工作"分离，且都能通过常规检查。
> **防御手段**：① 真实闭环（API/浏览器）而非只看返回值；② 断言必须能对缺陷变红；
> ③ **施工前核实任务书前提**（第 4 例正是这样发现的）。

**第 5 个实例（构建期静默丢弃）**：任务 C 在写触控热区时发现，
`theme.css` 里新增的 `.el-pagination .el-button { min-width: 36px }` 被 Vite 的 CSS 压缩器
（esbuild）**误判为 keyframes 名并整条丢弃**（警告文案：`the keyframes name 'el-pagination .el-button' is invalid`），
触发条件是同一文件里存在 `@keyframes`。
**症状**：源码里规则明明写了，"构建成功、无报错"，但**产物里没有这条规则**，样式不生效。

其处理正确：删除被误判的规则（分页器有独立样式，不受影响），
并把 `::after` 的 `min-width` 改为 `max(100%, 36px)` 语义（单向放大，避免窄化宽按钮热区）。

> **教训**：CSS 写对了不等于生效 —— **构建期可能静默丢弃**。
> 凡是"断言源码里有这条规则"的测试都抓不到它；只有**读构建产物的 CSS** 或**浏览器实测计算样式**
> 才能发现。这与 U-2（断言太弱）同源：**验证必须落在真正的效果层，而不是中间表示层。**

**第 7 个实例（门禁读了未就绪的页面 — 本轮新增，且是本轮最严重的一例）**：

| 项 | 内容 |
|---|---|
| 载体 | 新建的 UI/UX 回归门禁 `frontend-shared/e2e/uiux-regression.spec.ts` 的横向溢出用例 |
| 伪装形式 | **门禁在页面尚未渲染数据时测量，把「还没来得及出问题」当成「没有问题」** |
| 发现方式 | 主控对刚提交的门禁做**变异自证**：删掉 `LogicalDeviceList.vue` 的 `.ld-pagination :deep(.el-pagination){flex-wrap:wrap}` 并重新构建 |
| 关键事实 | 产物 CSS 里该规则**确实消失**（`grep` 证实，见 `bash-313`），但 `npx playwright test --project=uiux-gate-fine -g "360px 无视口横向溢出"` **仍然 1 passed** |
| 真实缺陷 | 主控独立探针在同一份产物上测得 **clips=12、最大裁切 365px、`.btn-prev` x=-118（视口外，`elementFromPoint` 返回 null）** |

**根因（逐帧实测，360x800，亮色，`/logical-device`）**：

```
t+   0ms  scanned=149  nclips=0   rows=0   pag=0  loadingMask=1  bodyLen=154   <- 门禁在这里判定通过
t+ 300ms  scanned=705  nclips=12  rows=20  pag=1  loadingMask=1  bodyLen=1144
t+ 500ms  scanned=701  nclips=12  rows=20  pag=1  loadingMask=0  bodyLen=1144  <- 稳定态
```

`pollUntil` 的就绪谓词是 **`scanned > 50`** —— 一个**结构性分母**，由应用外壳（侧栏+工具栏+表头）
在 t+0 就满足（149）。此刻表格 0 行、`bodyLen=154`、**loadmask 仍挂着**，即「数据请求还没回来」。
门禁于是在这个瞬间取数并判为合规；300ms 后真实裁切才出现。

> **与第 3、5 例的关系**：三者同属「验证落在中间表示层」——
> 第 3 例断言太弱（`toContain` 对缺陷恒真），第 5 例构建期静默丢弃（源码有、产物无），
> 本例则是**测量时机太早**（度量原语本身正确，但被喂了一份尚未就绪的 DOM）。
> 新增教训：**「分母非 0」只保证探针扫到了东西，不保证扫的是终态** ——
> 就绪判据必须依赖**该路由的数据承载信号**（行数 / 空态 / 错误态）与**布局稳定**（连续两次测量一致），
> 而不是元素总数。

> **同时证明了变异自证的不可替代性**：这条门禁 19/19 全绿，且断言写得很严（`clips` 必须为空数组、
> 还带分母守卫），**只看代码与绿灯完全无法发现它是假绿**。

**F19 专项说明（本轮最有价值的取证）**

危险确认（`feedback.confirmDanger`）的安全侧焦点，先前靠 `autofocus: false` + EP `el-focus-trap` 的兜底行为实现。
F5 执行者读 EP 2.14.3 源码后**正确指出**：这只是**偶然**结果 —— 若对对话框根节点的聚焦**成功**，
焦点就停在根节点，Tab 序列从根开始，**第一次 Tab 直达「删除」**。

执行者据此改为「用回调 ref 拿到真实 DOM，显式把焦点交给取消键」。但该实现用了
`root.querySelector('button:not([disabled])')` —— 一个**DOM 位置假设**。主控双重取证证伪：

**取证 1（Node 侧读 EP 渲染函数）**：`element-plus/es/components/message-box/src/index.mjs:66` 在标题栏里先渲染
一个 `headerbtn` 关闭按钮，排在 `.el-message-box__btns` **之前**；且 `showClose` 默认 `true`
（`index.vue_vue_type_script_lang.mjs:43-46`），confirmDanger 未关闭它。

**取证 2（真实 Chromium 实测）**：登录后点节点列表「删除」，读 `.el-message-box` 内全部 button：

```
buttonCount: 3
[0] class="el-message-box__headerbtn"        aria="关闭此对话框"  text=""
[1] class="el-button"                        text="取消"
[2] class="el-button el-button--danger ..."  text="删除"
activeElement: DIV.el-message-box is-draggable   <- 停在根节点，显式聚焦未生效
```

即 `querySelector('button')` 拿到的是**关闭按钮**，兜底失效。

> **教训**：用 DOM **位置**（第 N 个、第一个）表达语义**契约**是脆弱的 —— 上游多渲染一个装饰性元素就静默失效。
> 本仓的探针契约 §2 已记录过同类问题（选择器太窄导致假阴性、判据太宽导致假阳性）；
> 本例是第三种：**选择器命中了一个语义完全不同的元素**，而且它「不报错、不抛异常」，只是静静地聚焦错了地方。
> 正确做法是用**语义选择器**（限定 `.el-message-box__btns` 或排除 `__headerbtn`）。

**主控后续复核（同轮次，修正上文一处夸大）**

上文的「第一次 Tab 直达『删除』」**不准确**，且这个不准确来自执行者的注释、由主控原样转抄进本文档。
主控用同一份探针（`frontend-shared/tools/f5-focus-probe.mjs`）在真实 Chromium 上补测了
**焦点停在对话框根节点时连续 Tab 的落点序列**，实测：

```
[0] div.el-message-box            <- 起点（根节点）
[1] button.el-message-box__headerbtn   <- 关闭按钮
[2] button.el-button              <- 取消
[3] button.el-button              <- 删除
```

即：从根节点出发，**第一次 Tab 落在「关闭」按钮，第二次才是「取消」，第三次才是「删除」**。
所以准确表述是「**需要 2–3 次 Tab 才可能到达破坏性按钮**」，而不是「第一次 Tab 直达」。

> **但这个夸大不影响修复的正确性**：
> ① `.el-message-box__headerbtn` 存在，确证 `querySelector('button')` 是**错的定位方式**（拿到关闭键）；
> ② 根节点聚焦**成功**（实测 `activeElement` 停在 `div.el-message-box`），
>    说明执行者注释里描述的那个分支**真的发生了**，而非理论担忧；
> ③ 真正的危险不在 Tab 计数，而在**回车键**：EP 给 confirm 按钮绑定了 `onKeydown` Enter → 触发确认。
>    若焦点停在根节点，用户按回车**不会**误删（根节点没有该绑定）；
>    但焦点语义不确定本身即是缺陷 —— 修复把焦点**确定地**放到取消键，实测注入后 `activeElement` 为
>    `button.el-button|取消`（见探针 part B 的 `result: focused-cancel`），这才是契约。

> **教训（写给后来者）**：执行者在源码注释里写下了一个**未经实测的因果推断**
>（「第一次 Tab 直达删除」），主控在**没有独立验证**的情况下把它转抄进了本盘点文档。
> 本仓反复强调「不采信子代理自报」，但这条恰恰是**主控自己违反了**：
> 转抄等于背书。正确做法是——**任何进入文档的具体坐标/序列断言，都必须由主控亲手测一次**。

### 3.5 F19 的完整结论（经真实浏览器 A/B 与 C 段实测）

**真正成立的危害不是「第一次 Tab 直达删除」，而是 EP 默认档**。两个档位的实测对比：

| 档位 | 实测 `activeElement` | 危害 |
|---|---|---|
| EP 默认（`autofocus: true`） | `button.el-button--primary`「确定」 | **成立**：焦点就在破坏性按钮上，回车即删除 |
| `autofocus: false`（修复前的「半吊子安全档」） | `div.el-message-box`（根节点，随环境漂移） | 焦点既不在危险键也不在安全键 |
| 显式定焦（修复后） | `button.el-button`「取消」 | 安全侧，且第二次宏任务后仍稳定 |

**两个必须写进契约的反直觉事实**（均经真实浏览器 + jsdom 双向复现）：

1. **不能用「第一个 button」定位取消键** —— EP 在标题栏先渲染 `.el-message-box__headerbtn`（关闭键），
   它排在按钮区之前。第一版修复正是踩此坑。
2. **用 `nextTick` 定焦无效** —— EP 的聚焦链路全是微任务
   （visible watcher → focus-trap onMounted → `startTrap()` 内 `await nextTick()` → 再 `nextTick(tryFocus(rootRef))`）。
   实测第 1 个 `nextTick` 时定焦生效，**第 2 个 `nextTick` 就被 EP 自己的 `tryFocus(根)` 覆盖**。
   必须用 `setTimeout(0)` 宏任务排到其后（并对返回值有限次重试，不依赖 EP 内部微任务层数，版本升级不会失配）。

> 这条解释了主控在真实 Chromium 上看到 `activeElement` 停在根节点的现象 ——
> 执行者**用 jsdom 复现出了主控在真实浏览器观察到的结果**，两侧互证。

**另一处「伪装成正常」的活样本（第 8 例）**：变异自证时发现，
把安全侧定焦整个注释掉后，「`activeElement` 不是危险按钮」这条断言**依然通过** ——
因为焦点只是退回了根节点而不是危险键。也就是说：**只断言「不在危险侧」是不够的，
必须断言「确定地在安全侧」**（`expect(document.activeElement).toBe(cancel)`）。
执行者自己发现并记录了这一点，属正确处置。

### 3.13 F30（新发现，真缺陷）：CSS 特异性倒挂让「小号 select」永久停在 36px

**发现者**：F27 执行者在做口径校正时发现，并在「不动它、交主控裁决」的方式下正确处理（未擅改 F6 已有规则）。

**主控独立复现（源码 + 三档实测）**：

`theme.css:744` 是**无媒体查询的全局规则**：

```css
.el-select--small .el-select__wrapper { min-height: 36px; }   /* 特异性 (0,3,0) */
```

而窄屏块里的对应规则是 `.el-select__wrapper { min-height: 44px }`（特异性 **(0,1,0)**）。
**低特异性永远赢不了** ⇒ 小号 select 在 fine-390 与 coarse-390 都被钉在 36px：

| 视口 | /node 普通 select | /dashboard 小号 select |
|---|---|---|
| fine-390 | 300x**44** | 300x**36** ← 应为 44 |
| coarse-390 | 300x**44** | 300x**36** ← 应为 44 |
| fine-1440 | 160x32 | 140x36 |

**定性**：不是「fine 漏档」，而是「**全局 36 压过 44**」。

**主控口径裁决**：按 §4.4.5，「输入控件」在移动端应为 **44px**；36px 是给「极高密度、非主要任务的工具栏」的例外档。
`/dashboard` 那个 small select 是**时间范围选择器**，属主要交互控件而非高密度工具栏 ⇒ **应按 44px**。
故这是**真缺陷**，影响面 4 处（dashboard 1 + node 3）。

> **本条的独立价值**：它是「口径倒挂」这一类的**首个 CSS 特异性实例** ——
> 此前本仓记录的倒挂都是「fine 档比 coarse 档松」（F6 的 `.el-switch` 漏档）或「断言比实现松」（U-2 的 `toContain`）。
> 本条是**层叠顺序**造成的：两条规则各自都对，但**相遇时高特异性那条永远赢**，
> 且**在全部三档下都赢**（所以它连「窄屏生效、桌面不生效」这种可察觉的破绽都没有，看起来像「设计就这样」）。
> 记录教训：**`theme.css` 里的尺寸规则必须审视特异性**，
> 通配越窄的选择器（如 `--small` 变体）如果写在**无媒体查询**的位置，会静默压过所有媒体查询里的宽泛规则。

**F30 状态**：已登记，**未修**（需独立验证，且修它会让窄屏表单整体变高，须重新核对密度）。

### 3.15 门禁残余盲区的复核与分级（2026-09-14，第十四轮）

前一轮把 3 条盲区记为「待处理」，但**未区分「有害盲区」与「无害特性」**。主控本轮逐条实测复核，
结论：**只有 1 条是真盲区（且已派发修复），另 2 条是「页面本身在等用户交互」的正常特性。**

**复核方法**：用 `page.route('**/api/v1/**', () => new Promise(() => {}))` 挂起**全部** API，
然后按 `readyBlockers()` 的同源判据逐项检查（root / signal / masks / skeletons / settle）。

| 路由 | 挂起全部 API 后 | 判定 |
|---|---|---|
| **/monitor** | `blockers=[]`（10s 仍无 blocker），取数时 `scanned=181`，真实数据渲染后 `scanned=295` | **真盲区** —— 门禁在**只有骨架的 DOM** 上做裁切判定 |
| /data | `blockers=[]`，signal=1 | **无害** —— 该「信号」是**界面初始提示**「选择设备后查看数据…」 |
| /profile | `blockers=[]`，signal=1 | **无害** —— 该页**无列表接口**，用户名来自 store，不依赖后端取数 |

**/monitor 的根因（两条，互相独立）**：

1. **骨架判定认不出本仓自研组件**：F28 给 `/monitor` 用的加载骨架是本仓 `SkeletonCard.vue`，
   它渲染 `.skeleton-card` / `.skeleton-value` 等**自有 class**，而 `readyBlockers()` 只检查 `.el-skeleton`，
   所以**看不见它**（实测挂起 10s 后 `skeletons=0`、`blockers=[]`）。
2. **probe 定义漏了错误态**：`/monitor` 的 `visible`/`settle` 只有 `.stat-value`，
   而同文件里 `/dashboard` 的范式是 `'.el-table__row, .empty-state, [data-test="dashboard-error"]'` ——
   **把错误态也算作「确定结论」**。按契约，确定态有三种：有数据 / 空态 / **错误态**。

**/data 与 /profile 为何无害**：

- `/data` 的「信号」实测是 `.empty-state.default.initial`，文案「选择设备后查看数据…」——
  即**该页在用户选择设备前根本不会发起查询**。「还没查询」与「查询失败」在语义上不同：
  门禁此时测的是一份**静态表单页**，它确实已进入确定态（不需要更多数据）。
  若要更严，可把该 probe 的 `dataShaped` 改为 `false` 并注明「需交互后才取数」，但**不构成缺陷**。
- `/profile` 的 probe 注释**自己就写明了**：「唯一不依赖后端取数的受审路由：它没有列表接口。
  以『用户名已从 store 渲染』作为数据承载信号」。这是**有意的设计**，不是遗漏。

> **教训**：上一轮把 3 条盲区并列记为「待处理」，是**未加区分**的记账 ——
> 其中 2 条是页面设计使然（一个等交互、一个不取数），把它们与真盲区并列会误导后续投入。
> **正确做法**：盲区清单必须标注「**是否有真实危害**」及其判据（本例：挂起 API 后取到的 DOM 是否代表终态），
> 而不是只列出「判据不适用」的路由。

### 3.17 清理策略的论据必须是**可证伪**的：一例被推翻（2026-09-14，第十五轮）

**背景**：D-1 裁决 3 要求"保留投递审计"，并写明代价是"需要一条清理策略"。执行子代理交出了
`notification_delivery_cleanup.go`，其**核心论证**（文件头 §30-60）是：

> "delivered 是**幂等冗余**的 —— 一条 delivered 行早于 notifications 行存在，且 notifications 表自己按
> 90/180 天窗口清理 —— delivered 行只是同一事实的**第二份拷贝**。因此 delivered 留 45 天（基准的一半）。"

论证结构完整、措辞严谨、还引用了 D-1 原文，**单看无可挑剔**。

**主控的复核方式**：不读论证，而是把它转成**可证伪断言** ——"若 delivered 真冗余，则删掉 delivered 后，
'这条通知当时送达没有'仍应可答（notifications 里还有）"，然后**跑**它
（`backend/internal/datalifecycle/leadproof/proof_test.go`，临时验证件，结论已并入正式测试）：

```
SystemRetentionDays=90
notification cleanup deleted={ReadDeleted:0 UnreadDeleted:0}
delivery cleanup    deleted={DeliveredDeleted:1 FailedDeleted:0 PendingDeleted:0}
60 天前的未读通知: 本体存活=1 投递证据存活=0
notifications 的列 = [id type message title description source source_id read created_at]
```

**结论：论据被证伪。** 60 天前的**未读**通知按 180 天窗口**本体仍在**（用户在通知中心仍能看到、
仍能追问），但它的投递证据在第 45 天就被删了。而 `models.Notification`（`models.go:376-386`）
**没有任何投递状态字段**，全仓也搜不到第二处读 `notification_deliveries`（只有 dispatcher 写、
gorm 注册）。所以 delivered 行和 failed 行**同样是唯一证据**，不是冗余拷贝。

后果是**具体的**：read 窗 90 天 / unread 窗 180 天，而 delivered 窗 45 天 ⇒ **第 45～180 天之间，
追问对象还在、证据已消失** —— 恰好违背 D-1 要保护的那条价值。

**要求的修正（已下发）**：把策略钉在一条**不变式**上，而不是钉在天数上：

> **投递证据的保留期，不得短于被审计对象（通知本体）的最长保留期。**

因为"追问窗口"的长度由**被审计对象**决定，证据必须**活得比问题久**。
该不变式要求写成**回归测试**（构造"通知本体仍在、投递行按短窗已到期"的数据，断言清理后证据**必须仍在**），
且这条测试必须能因为"有人把窗口调回 45 天"而**变红** —— 即它是**约束**，不是当前取值的快照。

**可复用的教训（本轮新增，写入方法论）**：

1. **"冗余/等价/重复" 是事实断言，不是论证修辞**，必须能被一次观测证伪。
   凡是清理/合并/去重类策略，都要回答"删了它，哪个问题就再也答不出来了？"
2. **区分"诊断价值"与"审计价值"**：执行者的原话是"成功是预期路径，不承载**诊断**信息"——
   但审计要证明的恰恰是预期路径（"我说发了，证据呢"）。用诊断价值的尺子量审计证据 = 系统性低估。
3. **单看论证质量无法分辨对错**。本例的论证比正确版本更"像样"（有引用、有分档、有逐条理由），
   唯一的破绽在**一处未经验证的事实前提**上。⇒ 复核要打**前提**，不要打**措辞**。
4. 审计表保留期应写**允许的目标**（可删什么、留多久）而非只写禁令（"审计不能删"）——
   后者无法执行，实践中会被执行者自行降级或违反。

## 7. 主控自主裁决（原待裁决项，已按"自主决策、不提问"要求裁定）

### 裁决 1：D-4 vendor 体系 —— **删前端 api 客户端，保留后端端点**

**证据链**（主控第 8 轮核实）：
| 证据 | 位置 | 说明 |
|---|---|---|
| `DeviceModelID *uint` **全仓零读写** | `models.go:223` | 只有类型定义本身命中，无任何写入/读取 |
| `DeviceConfig` 注释写「v2.1 老字段保留作 legacy」 | `models.go:205` | 真正在用的是 v2.2 的 4 个 JSONB 字段（Connection/Parser/InitFlow/Operations） |
| `Vendor` / `DeviceModel` 注释直接写「**(保留)**」 | `models.go:424/431` | 模型自身被标注为遗留 |
| 前端 api 客户端 175 行**零消费** | `api/vendor.ts` | 三个 API 对象无任何调用点 |
| `EdgeDeviceList.vue:376` 的 `parser.vendor` | | 是**解析器自带字段**，不依赖这套 API |

**裁决理由**：前提是「当作未发布产品开发，不需要那么多兼容」。
把遗留体系补上一套 UI = **为死代码投资**，且会固化一个已被 v2.2 取代的模型。
**保留后端端点**（有测试、无副作用、将来若真需要型号库可复用），
**删除前端零消费的 api 客户端**（消除"有 api 无页面"的误导性半成品状态）。

### 裁决 2：T-2 SIM-CNFM-005/006 —— **标注"靠单测覆盖"结案**

**理由**：两条场景黑盒不可达的根因是**产品缺少「时间注入」或「多操作者」能力**
（近认证门读**用户级** `last_login_at`，而产品是单主体、无用户创建 API）。
为它给产品加测试专用通道 = **为测试改产品设计**，代价与收益不成比例。
而这两条语义**已被单测覆盖**（`commandexec/confirmation_test.go` 有 stale/nil last_login_at 的用例）。
故：在设计文档标注为「靠单测覆盖，场景仿真不可达及原因」，**不再列为待办**。

### 裁决 3：D-1 删除通道时是否保留投递审计 —— **保留**

**理由**：`notification_deliveries` 是**审计记录**，其价值在于事后追溯"某条通知当时是否送达"。
删除通道时连带删除投递历史 = 抹掉审计证据，与"审计不可删"的既有原则冲突
（本仓 audit 表同理）。且实现上保留更简单（`ON DELETE` 不级联）。
**代价**：需要一条清理策略（按时间/条数），与 `notifications` 表的清理需求同批处理。
