## F1 删除 handler_data.go 旧解析双实现(P0)

### 问题
`backend/internal/nodemgr/handler_data.go` 的 `parseAndStoreData`(:173)与 `findEdgeDeviceByChannelID`(:126)是 v2.5 databus 迁移前的旧实现。生产路径只剩测试引用(datapipe_test.go:68/100/123/264-301),与 `databus/consumers_heavy.go:129-158` 的解析+寻址逻辑完全重复。改解析行为只改一处时另一处悄悄失效——双实现漂移。

### 现状复核(2026-08-03 主 Agent 已验)
- `handleDataReport`(:25)仍是生产入口(MQTT 回调),但其内部已走 worker pool → DataEventBus → SensorParserConsumer;`parseAndStoreData` 不再被 `handleDataReport` 调用,仅被 datapipe_test.go 直接调用。
- `findEdgeDeviceByChannelID` 同样仅测试引用。

### 修复设计
1. 将 datapipe_test.go 中直接调用 `parseAndStoreData`/`findEdgeDeviceByChannelID` 的用例迁移为构造 DataEventBus + SensorParserConsumer 的等价测试(复用消费者公开入口),断言同一可观察结果(UnifiedData/DeviceData 落库 + WS 推送)。
2. 删除 handler_data.go 中两个私有函数及其独占辅助;`handleDataReport` 保留(它是生产入口)。
3. 若迁移后发现消费者覆盖了 datapipe_test.go 的全部断言维度,则整文件删除旧函数而非保留兼容壳。

### 验收
- `grep -rn "parseAndStoreData\|findEdgeDeviceByChannelID" backend/` 仅余历史文档引用。
- `make test` 全绿;迁移后的测试对 SensorParserConsumer 的覆盖不低于原 datapipe_test.go 的断言点(逐条对照表)。

### 风险
- 测试迁移可能丢失 channel_id 双编码(0-based vs channels.id)的边界用例。缓解:迁移时逐条对照原 264-301 行的寻址用例(channel 命中/edgeDeviceID 命中/不存在),确保全部保留。

## F2 manifest 编码读操作快照化 + reconcile 原子化(P0)

### 问题
`SendConfigManifestWithDecision`(sender.go:418+)在事务外做 ~6 次独立 Find(:445-471 templates、:461-470 channels/gpio/pwm),并发 CRUD 期间可能编码出半新半旧的 manifest。当前靠下一轮 Hello 的 hash 比对自愈,属侥幸正确而非结构正确。`reconcileDriverTemplates`(sender.go:969-1048)的模板创建+template_ids 追加是两条独立语句,中途失败留孤儿模板。

### 修复设计
1. 将 SendConfigManifestWithDecision 的全部读操作(node/templates/channels/gpio/pwm/devices)收进单个 `db.Transaction`(PG REPEATABLE READ;SQLite 测试环境下 SetTransactionIsolation 被静默忽略——可接受,因为生产是 PG),事务内只做读+编码,不做 MQTT 发布(发布移到事务提交后,避免长事务持锁)。
2. reconcileDriverTemplates 改为同事务内:缺失模板创建 + Channel.template_ids 追加 + reload,任一失败整体回滚。reconcile 移入上述同一事务,避免"reconcile 提交了但后续编码读的是旧快照"。
3. 编码函数的签名从"内部自查库"改为"接收已快照的实体集合"(依赖注入数据而非 db handle),便于单测构造快照。

### 不变量
- 事务只读,不引入写锁竞争;manifest 编码是纯函数。
- MQTT 发布在事务外,失败走既有 sync_state 自愈(下轮 Hello 重推),不改变既有恢复语义。
- hash 计算输入 = 快照数据,与设备自报 config_hash 的比对逻辑不变。

### 验收
- 新增并发测试:后台 goroutine 并发更新 channel/template 时,编码产出的 manifest 内部自洽(所有 channel 引用的 template_id 在同一快照的 templates 集合内)。
- reconcile 中途失败(注入 DB 错误)不留孤儿模板。
- make test 全绿;实机/dev 环境一次完整 config sync 回归。

### 风险
- 长事务:编码涉及多次查询但均为按 node_id 的小集合,PG REPEATABLE READ 快照开销可控;若实测慢,改为单连接显式 snapshot(START TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY)。
- sender.go 签名变更波及调用方(SyncGate/Hello 路径)。缓解:保持导出函数签名不变,仅内部重组。

## F3 findTemplateID 移除 fallback=1(P1)

### 问题
sender.go:407-416 `findTemplateID` 在 Channel.TemplateIDs 为空时静默 fallback 到模板 1。模板 1 被删除后,编码会引用不存在的模板而不报错,设备采错寄存器。

### 修复设计
1. `findTemplateID` 无匹配时返回 0(不再返回 1)。
2. 调用方(sender.go:632)对返回值 0 显式跳过该命令编码 + `logger.Warn` + 指标计数,不静默编码。
3. 审查 0 是否会被 frame 编码成合法值:若 varint 0 在 wire 上合法但语义无效,则在编码前 guard 跳过,确保 0 永不上线。

### 验收
- 测试:TemplateIDs 为空 → 该命令不编码 + warn 日志;模板 1 删除后全量 manifest 不含悬空 template_id。
- make test 全绿。

### 风险
- 依赖"template_ids 为空也能正常采集"的现存部署会变为不编码(行为变化)。缓解:先 grep 生产/dev 数据库确认是否存在 TemplateIDs 为空的 Channel;若存在,先在 F2 的 reconcile 中补齐再启用本项。

## F4 Catalog 谓词与 Create 门控抽共享函数(P1)

### 问题
Catalog 可用性 9 项检查(service.go:98)与 Create 门控(:192-219)几乎逐项重复,靠人工保持同步;新增门控条件时必然漏一处。Catalog 是 advisory(给 UI reason code),Create 是 authoritative,双份实现有必要但应共享谓词。

### 修复设计
1. 抽取 `admissionGates(def, edge, node, caps) (blocked bool, reasonCode string, reason string)` 纯函数,承载全部 9 项谓词,返回结构化 reason code(供 UI 的 capability_stale 等)。
2. Catalog 调用它填充 EffectiveAction.ReasonCode;Create 调用它做准入拒绝。两处共享同一份谓词列表,消除人工同步。
3. 保持两层调用语义不变:Catalog 不拒绝只标注,Create 拒绝。

### 验收
- 9 项谓词逐项单测(每项 blocked=true/false 一例)。
- 故意制造一处谓词变更,验证 Catalog 与 Create 同步生效(回归测试)。
- make test 全绿。

### 风险
- reason code 字符串是 UI 契约,抽取时不得改变既有 code 值。缓解:抽取前后对同一输入快照比对 reason code 集合。

## F5 固件 V2 状态机 + execute_uart_batch host 测试(P1)

### 问题
V2 槽位状态机核心路径无独立 host 测试:reserve_slot 的 collision(-2/V2_ERR_COLLISION)、FINAL 重放重发、CAS 拒绝非 QUEUED complete。execute_uart_batch(TX→turnaround→collect 循环)只有组件级覆盖,无端到端。

### 修复设计
1. 复用 host-test .c 直接包含模式(见 skill host-test-c-inclusion-pattern)包含 handler_channel_cmd_v2.c,构造:
   - 同 command_id 不同 payload_digest → 期望 collision(-2);
   - 已完成槽位收到相同 identity 重放 → 期望重发 FINAL 且不改变 completed_order;
   - 非 QUEUED 槽位调 complete → 期望 CAS 拒绝。
2. execute_uart_batch 注入 fake RX 字节流(stub uart_collect_response),断言 envelope `[count][kind+len_le+data]` 逐字节正确、单步失败时 error_code 分段(0x1100/0x1200/0x1400 + step index)正确。
3. 接入现有 ctest,host_tests 30 → 30+N 全绿。

### 验收
- 新增测试覆盖上述分支;ctest 全绿;不引入新的 stub 全局状态泄漏(file-static 重置模式)。

### 风险
- file-static 变量(s_slots/s_reservation_lock)跨用例污染。缓解:每个用例前 memset 重置(host-test-c-inclusion-pattern 已沉淀的模式)。

## F6 数据落库失败补偿(P2)

### 问题
UnifiedData/DeviceData 插入失败仅日志+指标(consumers_heavy.go:259-262、304-307),DB 抖动期采样静默丢失,无补偿。

### 修复设计
1. 不引入重试队列(避免新基础设施),先做"可观测性补偿":写失败按 (node_id, error_class) 聚合计数,超阈值(如 1min 内 >10)发一条 WARN 聚合日志 + metrics 暴露,供告警接入。
2. 评估是否需要轻量重试:采样数据是时序流,丢失少量点通常可接受;若业务要求不丢,二期再做有界内存重试环形缓冲(容量上限 + 满则丢最旧 + 指标)。
3. handler_data.go:258 旧路径的 `db.Create` 不查 error 随 F1 一并消除。

### 验收
- 注入 DB 错误,断言聚合计数与 WARN 日志;make test 全绿。

### 风险
- 聚合告警本身成为日志风暴。缓解:按 (node_id, error_class) 维度 1min 窗口去重。

## F7 nodeIDCache TTL 自失效(P2)

### 问题
worker_pool.go:37 `nodeIDCache sync.Map` 依赖显式 InvalidateNodeIDCache 调用(:41),遗漏即陈旧主键(节点删除/重建后映射错误)。

### 修复设计
1. cache entry 带写入时间戳,读取时超 TTL(建议 5min,与 MaxCapabilityAge 一致)自动失效并重查。
2. 保留显式 InvalidateNodeIDCache 作为快路径,双保险。
3. 或更彻底:挂到节点删除/更新的统一事件钩子(ConfigEventBus 或 nodemgr 事件),删除时主动失效。二选一,倾向 TTL(改动小、无新耦合)。

### 验收
- 测试:TTL 内命中缓存;TTL 后重查;显式失效立即生效。make test 全绿。

## F8 固件简化:RESERVED 态删除 + report_task 单路径(P2)

### 问题
- V2 槽位 5 态中 RESERVED 仅为 CAS 窗口服务,与全局 s_reservation_lock 自旋锁功能重叠——lock 已串行化整个 reserve 过程,RESERVED 实际不可达。
- report_task 双路径消费(bus_worker.c:338-367 先非阻塞扫 critical/emergency 再 QueueSet 等待)冗余,QueueSet 已含全部 5 队列,前置扫描在 1ms tick 粒度下无实际意义。

### 修复设计
1. 删除 V2_SLOT_RESERVED 态,reserve 路径简化为 lock 内直接 FREE→QUEUED CAS;或反向删 lock 保留 CAS 态——二选一,倾向删 RESERVED 态(保留 lock,因 lock 还保护扫描-占用原子性)。
2. report_task 删除前置非阻塞扫描,统一走 QueueSet 单路径。
3. 每项独立 commit,便于回退。

### 验收
- host_tests 30/30 全绿;实机一次 config 切换 + 控制命令回归无异常。

### 风险
- RESERVED 态删除改变状态机,若 F5 测试先行落地可作为回归网。建议 F8 排在 F5 之后。
