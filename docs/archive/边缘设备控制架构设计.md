# 边缘设备控制架构设计

> **文档性质**：完整设计方案，仅定义架构、协议、模型、接口、状态机、前端交互、实施阶段与验收标准，不代表授权实现。
>
> **适用项目**：EHomeSystem
>
> **适用范围**：通过 ESP32 节点的 UART、I2C、SPI 等 Channel 接入的下游协议设备，例如雨量计、BMS、逆变器、仪表和其他支持读写协议帧的边缘设备。
>
> **设计基线**：`/home/sun/workspace/EHomeSystem-gpio` 当前工作树（包含审查时已有的 tracked 与 untracked 改动）。
>
> **核心约束**：GPIO/PWM 是节点本地无协议外设，继续使用独立的 `PeriphCmd/PeriphRsp`；雨量计、BMS、逆变器等有协议帧的下游设备必须使用 Channel，不得扩展为新的 `periph_type`。

# 1. 背景与问题

当前 EHomeSystem 的边缘设备前端主要用于展示采集数据。系统已经可以通过 ESP32 节点与下游设备进行字节级通信，也已经存在部分操作定义和前端按钮，但尚未形成一个可靠、通用、可审计的设备控制面。

需要支持的代表性能力包括：

- 雨量计累计值重置；
- BMS 重启；
- BMS 充电 MOS、放电 MOS 控制；
- BMS 保护参数和运行参数设置；
- 逆变器开机、关机、复位；
- 逆变器工作模式、输出电压、输出频率、充电电流、电池类型等设置；
- 其他设备的瞬时命令、目标状态控制、数值设置、枚举设置和多步骤配置。

这些能力表面上是“增加几个按钮”，实际包含完整的分布式控制问题：

1. 浏览器、后端、MQTT、ESP32、总线和目标设备之间存在多层异步边界；
2. MQTT 发布成功不等于 ESP32 接受；
3. ESP32 总线发送成功不等于目标设备接受；
4. 目标设备 ACK 成功也不一定等于设置已持久化或运行状态已改变；
5. 超时后命令可能已执行，也可能未执行；
6. 非幂等命令盲目重试可能产生二次破坏；
7. 控制命令可能与周期采集、初始化、终端命令交错；
8. 高风险操作需要权限、确认、审计和可追溯结果；
9. 不同设备协议差异很大，但前后端控制架构必须通用。

因此，本设计的目标不是继续堆叠设备专用 API，而是建立统一的设备动作目录、持久化操作生命周期和透明 Channel 事务执行能力。

# 2. 设计目标与非目标

## 2.1 设计目标

### G1：统一能力模型

以一个版本化的设备动作定义描述：

- 动作是什么；
- 接受哪些参数；
- 风险等级；
- 幂等性质；
- 前置条件；
- 如何编译为设备协议帧；
- 如何解析 ACK；
- 如何验证最终状态；
- 前端应使用什么受控组件展示。

### G2：端到端可靠状态

把一次操作建模为持久化实体，明确区分：

- 请求已创建；
- 后端已接受；
- 已排队；
- MQTT 已分发；
- ESP32 已接受；
- 总线事务已执行；
- 目标协议已确认；
- 最终业务状态已验证；
- 明确失败；
- 结果未知。

### G3：通用而非设备硬编码

新增设备型号时：

- 不新增设备专用 REST 控制接口；
- 不新增设备专用 MQTT 消息类型；
- 不在通用前端增加型号分支；
- 只增加动作定义、必要的协议编译器/解析器和设备专用可视化。

### G4：安全可控

- 后端执行权威参数校验；
- 高风险操作强确认；
- 支持操作理由、近期登录或密码再确认；
- 记录 append-only 审计；
- 不允许浏览器提交任意原始命令帧。

### G5：设备端幂等和重放保护

- 相同命令 ID 和相同 payload 不重复执行；
- 相同命令 ID 和不同 payload 拒绝 collision；
- 过期命令不执行；
- 对高风险、at-most-once 命令保留跨重启的重放证据。

### G6：保持现有正确边界

- Channel 处理有协议帧的下游设备；
- GPIO/PWM 继续使用独立 PeriphCmd；
- ResourceReport 是节点实际硬件和执行引擎能力的唯一事实源；
- Driver 只负责设备协议知识，不负责 MQTT、权限、持久化和业务状态机。

## 2.2 非目标

本设计不做以下事情：

1. 不把设备厂商协议解析下沉到 ESP32；
2. 不让 ESP32 理解“BMS”“雨量计”“逆变器”等业务概念；
3. 不把 GPIO/PWM 重新并入 Channel；
4. 不承诺分布式系统中的绝对 exactly-once；
5. 不用 QoS2 代替业务幂等和设备端去重；
6. 不允许后端下发 HTML、JavaScript、Vue 模板或任意动态组件路径；
7. 不为设备型号硬编码 ESP32 硬件资源；
8. 不在本设计阶段实现代码。

## 3.2 当前主要缺口

### 3.2.1 Driver 命令与 DeviceConfig Operations 双轨

Driver 的 `CommandTemplate` 描述底层协议命令：

- `backend/internal/drivers/command_template.go:3-26`

但 `/execute` 只读取 `DeviceConfig.Operations`：

- `backend/internal/api/handler_edge_device.go:608-625`

Driver 中 `Schedulable=false` 的 BMS/逆变器控制命令虽然可列出，但没有统一执行桥：

- `backend/internal/api/handler_driver_commands.go:21-76`
- `frontend-shared/src/components/device/CommandList.vue:34-49`

### 3.2.2 写操作是 fire-and-forget

当前 write 分支调用 `SendWriteCommand(..., readSize=0)` 后立即继续：

- `backend/internal/api/handler_edge_device.go:684-700`

随后返回 `status=sent` 并计为 success：

- `backend/internal/api/handler_edge_device.go:749-759`

这只能证明后端尝试发布，不能证明目标设备已执行。

### 3.2.3 verify 失败仍返回成功

当前 `verify_operation` 的配置错误、发送失败、NACK 或解析失败只记录 warning：

- `backend/internal/api/handler_edge_device.go:702-747`

最终仍返回 success。因此当前验证不是权威闭环。

### 3.2.4 参数校验主要存在于前端

前端类型定义了：

- 参数类型；
- min/max/step；
- enum options；
- confirm。

证据：

- `frontend-shared/src/api/deviceConfig.ts:9-26`

后端 `OperationConfig` 不包含对等参数 schema：

- `backend/pkg/parser/template.go:24-49`

浏览器限制可以被直接调用 API 绕过。

### 3.2.5 没有业务操作状态机和真实历史

`PendingWriteRecord` 只保存底层写帧：

- `backend/internal/models/models.go:359-374`

缺少业务动作、actor、风险、状态、验证和步骤结果。

操作历史接口固定返回空数组：

- `backend/internal/api/handler_edge_device.go:560-567`

### 3.2.6 前端状态反馈不可靠

写操作只提示“命令已发送”：

- `frontend-shared/src/views/edge-device/shared/OperationButtons.vue:217-229`

详情页没有持久化操作 store，也没有在刷新/重连后恢复 pending 操作。

### 3.2.7 在线判断不权威

前端根据 EdgeDevice 快照判断离线：

- `frontend-shared/src/views/edge-device/shared/OperationButtons.vue:113-116`

后端执行前只检查 EdgeDevice enabled 和 Channel 有效，没有强制检查 Node 当前在线：

- `backend/internal/api/handler_edge_device.go:599-605`

### 3.2.8 协议文档与实现漂移

`docs/协议/二进制帧协议.md:137-159` 描述的 WriteCmd/WriteRsp 字段与当前 Go/C 实现不一致。任何控制协议扩展前必须先冻结真实 Wire Spec。

### 3.2.9 WriteCmd 缺少固件端幂等重放保护

PeriphCmd 已有 payload-aware replay/collision 机制；WriteCmd 直接解析和投递：

- `esp32-collector/components/msg_handler/handler_writecmd.c:38-66`

MQTT 重投、服务重启或调用方重试可能重复执行危险命令。

### 3.2.10 BMS MOS 需要多步骤事务

MOS 命令要求工厂模式：

- `backend/internal/drivers/jiabaida.go:622-637`

进入/退出工厂模式 helper 已存在：

- `backend/internal/drivers/jiabaida.go:553-568`

但当前没有一个排他的原子 workflow 将进入工厂模式、MOS 控制、退出工厂模式和状态验证串联起来。

# 4. 架构边界与不变量

## 4.1 责任边界

| 组件 | 责任 | 不负责 |
|---|---|---|
| Node | 物理 ESP32 节点身份、在线状态、配置代际 | 下游设备业务动作定义 |
| ResourceReport | 实际硬件资源和命令执行引擎能力的唯一事实源 | 某型号 BMS/逆变器业务知识 |
| Channel | 总线端点、队列、排他、字节事务 | GPIO/PWM、本地业务权限 |
| EdgeDevice | 具体下游设备实例、地址、实例状态 | 型号级协议实现 |
| DeviceConfig | 型号配置、现场覆盖、动作策略 | 任意不受信任原始命令执行 |
| Driver | 协议知识、动作编译、ACK/响应解析 | MQTT、DB 生命周期、权限、审计 |
| PeriphCmd | Node 本机 GPIO/PWM | 雨量计、BMS、逆变器 |
| CommandExecution | 操作生命周期、幂等、步骤、验证、审计 | 厂商协议硬编码 |
| 前端 | 展示能力、收集参数、显示状态 | 决定最终权限、提交任意帧 |

## 4.2 必须保持的不变量

### I1：GPIO/PWM 与 Channel 分离

- GPIO/PWM 继续使用 `PeriphCmd/PeriphRsp`；
- 只有有协议帧的外部设备使用 Channel；
- 不新增 `periph_type=BMS/INVERTER/RAIN_GAUGE`。

### I2：硬件和执行能力来自 ResourceReport

- 后端不得按 ESP32-C6/S3 型号推测能力；
- 节点未上报时返回空能力或不可执行；
- ResourceReport 过期时高风险控制 fail-closed。

### I3：Driver 是可信协议编译器

浏览器只提交：

```text
action_id + structured params
```

不能提交：

- write_data；
- command_template；
- CRC 算法；
- 任意寄存器地址；
- 任意脚本。

### I4：期望值与确认值分离

- desired value 表示用户意图；
- confirmed value 表示设备已验证状态；
- MQTT publish 或总线 TX 成功不得提升 confirmed value；
- 无法确认时保留最后 confirmed value，并将操作标为 UNKNOWN。

### I5：型号级配置与实例级状态分离

不得将单个设备的：

- 地址；
- 波特率；
- MOS 状态；
- 逆变器设置；
- 运行目标值

写回共享 `DeviceConfig`。

### I6：所有控制路径共享 Channel 串行化边界

以下操作必须共享 `node_id + channel_id` 的调度边界：

- 周期采集；
- 用户 read；
- 用户 write；
- 写后 verify；
- 初始化；
- 多步骤事务；
- 调试终端写入。

# 6. 统一设备动作模型

## 6.1 DeviceOperationDefinition

建议使用版本化定义：

```text
DeviceOperationDefinition
├── identity
├── semantics
├── input_schema
├── preconditions
├── execution_plan
├── verification_plan
├── safety_policy
├── availability_requirements
└── presentation
```

### 6.1.1 Identity

```json
{
  "id": "bms.set_discharge_mos",
  "version": 1,
  "label": "放电 MOS",
  "description": "设置放电 MOS 的绝对目标状态",
  "category": "control"
}
```

要求：

- ID 稳定且不可复用为不同语义；
- 协议步骤变化或验证语义变化时增加 version；
- Execution 持久化时保存实际使用版本。

### 6.1.2 Semantics

```json
{
  "kind": "set",
  "idempotency_class": "set_absolute",
  "concurrency_policy": "serialize",
  "exclusive_scope": "channel"
}
```

`kind`：

- `query`：只读查询；
- `set`：设置绝对目标值；
- `action`：瞬时动作；
- `reset`：清零或恢复操作；
- `reboot`：重启并通过重连验证；
- `workflow`：多步骤事务；
- `batch`：批量设置。

`idempotency_class`：

- `read_only`；
- `set_absolute`；
- `reconcilable`；
- `at_most_once`。

### 6.1.3 Input schema

示例：

```json
{
  "type": "object",
  "required": ["enabled"],
  "properties": {
    "enabled": {
      "type": "boolean",
      "label": "目标状态"
    }
  },
  "additional_properties": false
}
```

数值设置示例：

```json
{
  "type": "object",
  "required": ["current_a"],
  "properties": {
    "current_a": {
      "type": "integer",
      "minimum": 10,

      "label": "总充电电流"

```

后端必须校验：

- required；
- 类型；
- 整数与浮点区分；
- min/max；
- step/multiple_of；
- enum；
- 字符串长度和字符集；
- 禁止未知字段；
- 跨字段约束；
- 编码后的数值范围；
- 业务前置条件。

### 6.1.4 Preconditions

示例：

```json
{
  "all": [
    { "type": "node_online" },
    { "type": "channel_enabled" },
    { "type": "edge_device_enabled" },

```

前置条件必须由后端执行。前端可用于解释和预先禁用，但不是安全边界。

### 6.1.5 Execution plan

Driver 将语义动作编译为一个或多个步骤：

```text
CompiledOperationPlan
- operation definition identity
- canonical normalized params
- required engine features
- exclusive scope
- repeated steps
- finally steps
- verification plan
```

步骤示例：

```json
{
  "step_id": "set_mos",
  "tx_data": "<server-only bytes>",
  "read_policy": "idle_gap",
  "max_read_size": 64,
  "rx_timeout_ms": 1500,
  "post_tx_delay_ms": 100,
  "response_parser": "jiabaida.ack",
  "success_predicate": "ack_success"
}
```

原始 `tx_data` 不暴露给普通前端。

### 6.1.6 Verification plan

策略：

- `none`：仅适用于无状态、低风险且协议 ACK 已足够的操作；
- `protocol_response`：同一事务响应即为最终确认；
- `readback`：执行另一查询并比较；
- `telemetry`：等待后续主动数据满足条件；
- `reconnect`：等待设备重新响应；
- `boot_change`：要求 boot ID、uptime 或运行代际变化；
- `composite`：组合多个条件。

示例：

```json
{
  "strategy": "readback",
  "read_operation": "bms.read_basic_info",
  "value_path": "fet_status.discharge",
  "compare": "equals_input",
  "initial_delay_ms": 200,
  "deadline_ms": 5000
}
```

### 6.1.7 Safety policy

```json
{
  "risk_level": "high",
  "confirmation": "show_current_and_target",
  "reason_required": true,
  "recent_auth_required": false,
  "cooldown_ms": 3000,
  "rate_limit": {
    "count": 3,
    "window_ms": 60000
  }
}
```

风险级别：

| 级别 | 典型操作 | 确认策略 |
|---|---|---|
| low | 查询状态 | 直接执行 |
| medium | 可恢复的普通设置 | 普通确认或不确认 |
| high | MOS、输出电压、雨量清零 | 显示当前值和目标值，二次确认，通常要求理由 |
| critical | 重启、系统复位、危险保护参数 | 输入设备名/确认短语，必要时近期登录或密码再确认 |

### 6.1.8 Presentation

前端受控组件 token：

- `button`
- `switch`
- `enum`
- `number`
- `slider`
- `form`
- `settings_group`

后端不得下发：

- HTML；
- JavaScript；
- Vue 模板；
- 任意组件文件路径；
- 任意 CSS；
- 可执行表达式。

有限条件展示只允许声明式操作符：

- equals；
- not_equals；
- in；
- exists；
- numeric_range。

## 6.2 能力来源合并

建议建立规范化 `DeviceActionRegistry`：

```text
Built-in Device Descriptor / Driver
            │ 协议权威
            ▼
DeviceConfig site overlay
            │ 标签、范围收窄、启停、现场策略
            ▼
EdgeDevice instance
            │ 地址、实例状态
            ▼
Channel + ResourceReport + protocol version
            │ 运行可行性
            ▼
Current user policy
            │ 权限
            ▼
EffectiveActionCatalog
```

合并规则：

1. Driver/Descriptor 提供可信命令编译和解析；
2. DeviceConfig 可收窄范围、修改标签、禁用动作，但不能扩大 Driver 不支持的协议能力；
3. DeviceConfig 不得注入未经注册的危险 raw command；
4. EdgeDevice 提供实例地址和 confirmed state；
5. ResourceReport 决定节点能否执行对应事务；
6. API 返回最终有效动作和 unavailable reason。

# 8. 命令执行状态机

## 8.1 后端权威状态机

```text
CREATED
   │
   ▼
VALIDATING ───────────────→ REJECTED
   │
   ▼
QUEUED ───── cancel ─────→ CANCELLED
   │
   ▼
DISPATCHED
   │
   ▼
DEVICE_ACCEPTED
   │
   ▼
RUNNING
   │
   ├──────────────→ FAILED
   │
   ├──────────────→ TIMED_OUT
   │
   ├──────────────→ UNKNOWN
   │
   ▼
VERIFYING
   │
   ├──────────────→ FAILED
   │
   ├──────────────→ UNKNOWN
   │
   ▼
SUCCEEDED
```

附加状态：

- `EXPIRED`：排队或到达设备时已超过 max age；
- `CANCEL_REQUESTED`：只适用于已分发且执行引擎支持取消的操作；
- `SUPERSEDED`：同一 setting 的较新目标意图取代尚未执行的旧 queued 操作；
- `PARTIAL_FAILED`：批量/多步骤操作部分成功且无法原子回滚。

## 8.2 状态语义

| 状态 | 语义 |
|---|---|
| CREATED | 已创建未校验 |
| VALIDATING | 校验权限、参数、能力、前置条件 |
| QUEUED | 已持久化，等待 Channel 调度 |
| DISPATCHED | MQTT 发布已接受 |
| DEVICE_ACCEPTED | ESP32 已校验身份、hash、deadline 和资源并接受 |
| RUNNING | ESP32 正在执行一个或多个总线步骤 |
| VERIFYING | 后端或设备端正在做读回/遥测/重连验证 |
| SUCCEEDED | 最终业务状态已按策略验证 |
| REJECTED | 执行前明确拒绝，设备未执行 |
| FAILED | 已明确失败，且失败语义可确定 |
| TIMED_OUT | 某一阶段超过期限，且策略可确定为失败 |
| UNKNOWN | 命令可能已执行，但无法证明最终结果 |
| CANCELLED | 确认尚未执行且已取消 |
| EXPIRED | 到达执行边界时已过期，未执行 |

## 8.3 状态转换 CAS

所有状态转换必须：

- 使用 expected current state；
- 检查 `RowsAffected == 1`；
- 使用 command ID、attempt、boot ID、generation 作为身份；
- stale ACK 影响零行；
- 不能根据数据库已经处于某状态推断本次响应完成了转换。

## 8.4 HTTP 生命周期与操作生命周期分离

长操作创建接口返回：

```text
HTTP 202 Accepted
```

而不是等待整个设备操作。

浏览器通过：

- REST 查询权威状态；
- WebSocket 接收实时更新。

WebSocket 断线不改变操作生命周期。

# 9. 成功语义、错误模型与超时

## 9.1 五层成功语义

必须区分：

1. `MQTT_DISPATCHED`：MQTT publish 已接受；
2. `DEVICE_ACCEPTED`：ESP32 已严格解码、去重并接受；

# 10. 幂等、重放与结果不确定性

## 10.1 后端幂等

客户端通过 `Idempotency-Key` 提交操作。

唯一范围建议：

```text
(actor, edge_device_id, operation_id, idempotency_key)
```

规则：

- 相同 key + 相同 canonical payload hash：返回已有 Execution；
- 相同 key + 不同 hash：HTTP 409 collision；
- Execution 必须先持久化，再 publish；
- 重试复用 command ID，只增加 attempt；
- 不能使用时间戳作为业务幂等身份。

## 10.2 Canonical payload hash

hash 输入至少包含：

- command ID；
- operation ID/version；
- EdgeDevice/Channel 身份；
- 规范化参数；
- 编译后步骤身份；
- deadline policy；
- required boot/config generation。

不能只 hash 原始 JSON 字符串，因为字段顺序和数值表示可能不同。

## 10.3 ESP32 重放分类

设备端分类：

- `NEW`
- `EXACT_REPLAY`
- `COLLISION`
- `BUSY`
- `EXPIRED`

规则：

- 同 command ID、同 payload hash：禁止重执行，重放原 authoritative 状态/终态；
- 同 command ID、不同 payload hash：fail-closed collision；
- in-flight entry 不可被缓存淘汰；
- response 缓存必须保存合法零值；
- publisher/queue admission 失败不能销毁重放证据；
- high/critical、at-most-once 命令按策略持久化到 NVS；
- 控制 NVS 写放大，只为必要风险类别持久化。

## 10.4 幂等类别策略

### read_only

- 可安全重试；
- exact replay 可返回缓存结果或重新读，取决于 freshness policy。

### set_absolute

- 例如 `set_discharge_mos(false)`；
- 不使用 toggle；
- 可通过读回收敛；
- stale 结果不得覆盖较新目标值。

### reconcilable

- 例如参数绝对值设置；
- 可根据 confirmed value 决定是否再次执行；
- 需要 expected revision 或 expected old value 以避免覆盖并发更新。

### at_most_once

- 例如雨量累计清零、BMS/逆变器重启；
- 一旦可能已执行，超时进入 UNKNOWN；
- 禁止自动重试；
- 只能通过对账、读回、重连或人工确认恢复。

## 10.5 UNKNOWN 的必要性

以下场景不能直接标 FAILED：

- MQTT 已发布但未收到设备 accept；
- ESP32 已开始执行但连接断开；
- 总线写成功但设备 ACK 丢失；
- 重启命令执行后设备来不及回复；
- 后端重启导致内存 waiter 丢失，但设备可能已执行。

UNKNOWN UI 必须：

- 保留最后 confirmed value；
- 显示目标值和未知原因；
- 优先提供“重新读取当前状态”；
- 禁止默认显示“重试危险操作”。

# 11. Channel 调度、排他与多步骤事务

## 11.1 统一调度范围

排他 key：

```text
node_id + channel_id
```

同一 Channel 上所有命令进入统一调度器。

建议优先级：

1. 安全停止/紧急操作；
2. finally cleanup；
3. 当前事务验证；
4. 高风险用户控制；
5. 普通用户控制；
6. 手动查询；
7. 初始化；
8. 周期采集。

紧急优先级不能绕过设备端幂等、权限和严格解码。

## 11.2 与 scheduler 协调

单步事务：

- 用户控制进入 Channel 队列；
- scheduler 不再直接与控制路径竞争底层队列；
- 控制步骤执行完成后恢复周期采集。

多步骤事务：

- 事务获得 Channel 排他权；
- 暂停该 Channel 的新采集 admission；
- 等待已在执行的总线操作完成；
- 按顺序执行 steps；
- 执行 finally steps；
- 释放排他权；
- 恢复采集。

不得停止整个节点的其他独立 Channel。

## 11.3 多步骤事务语义

事务定义：

```text
- atomic admission
- ordered steps
- stop_on_error
- finally steps
- per-step result
- overall result
```

“atomic”只表示：

- 同一 Channel 上不会插入其他事务；
- steps admission 和身份是整体的。

不代表目标设备具有数据库式硬件回滚。

## 11.4 finally step

适用于：

- 退出 BMS 工厂模式；
- 恢复临时通信模式；
- 释放设备锁；
- 恢复原页/寄存器 bank。

finally 失败时：

- 主动作不得简单显示 success；
- 状态至少为 FAILED 或 UNKNOWN；
- 记录 `cleanup_failed`；
- 触发高优先级告警；
- 可按动作定义限制该设备后续控制，直到人工确认或恢复成功。

## 11.5 批量配置

设备协议若没有原子 batch：

```text
VALIDATE ALL
→ read current snapshot
→ step 1 + verify
→ step 2 + verify
→ ...
→ SUCCEEDED / PARTIAL_FAILED
```

要求：

- 提交前显示 diff；
- 每项有独立状态；
- 明确顺序；
- 只在协议支持时承诺回滚；
- 不允许一个 toast 掩盖部分失败。

# 12. 协议设计

## 12.1 Phase 0：冻结现有协议事实

在扩展前必须修正权威协议文档，使其与 Go/C 一致：

### 当前 WriteCmd

```text
Type: 0x06
field 1: request_id (uint32, required, nonzero)
field 2: channel_id (uint32, required)
field 3: data (bytes, required, bounded)
field 4: read_size (uint32, optional)
```

### 当前 WriteRsp

```text

field 2: success
field 3: error_code

```

### DataReport correlation

非零 `request_id` 表示对应命令读回。

## 12.2 单步可靠命令方案

简单 read 或单步 set 可以在兼容版本中硬化 WriteCmd，增加：

```text
command_id / generation
payload_hash
deadline/max_age
boot_id
manifest/config generation
rx_timeout_ms
flags
```

如果旧消息字段空间和兼容性不足，使用新消息类型，不能以“允许未知字段但旧固件静默忽略”冒充支持。

## 12.3 多步骤 ChannelTxnCmd

建议新增独立消息族，而不是无限扩展 WriteCmd。

### ChannelTxnCmd

顶层建议字段：

```text
field 1: command_id          bytes/string, required
field 2: payload_hash        bytes, required
field 3: attempt_no          varint, required
field 4: boot_id             bytes/string, required by policy
field 5: edge_device_id      varint, required
field 6: channel_id          varint, required
field 7: deadline_ms         varint, required
field 8: manifest_id         string, required by policy
field 9: atomic              canonical bool
field 10: stop_on_error      canonical bool
field 11: steps              repeated nested bytes
field 12: flags              varint
field 13: risk_class         enum
```

### ChannelTxnStep

```text
field 1: step_index          varint, required
field 2: tx_data             bytes, required
field 3: read_policy         enum, required
field 4: read_size           varint
field 5: max_read_size       varint
field 6: rx_timeout_ms       varint, required
field 7: post_tx_delay_ms    varint
field 8: min_response_size   varint
field 9: finally_step        canonical bool
field 10: redaction_class    enum
```

ESP32 不解析厂商 ACK，只返回原始响应和 transport 状态。协议 ACK 解析仍由后端 Driver 完成。

## 12.4 ChannelTxnEvent

事件类型：

- `ACCEPTED`
- `REJECTED`
- `STARTED`
- `STEP_COMPLETED`
- `STEP_FAILED`
- `COMPLETED`
- `REPLAY`
- `COLLISION`
- `EXPIRED`

字段至少包含：

- command ID；
- payload hash 摘要；
- attempt；
- boot ID；
- state；
- 当前 step；
- transport error；
- raw response；
- started/finished timestamp；
- cached/replayed 标记。

## 12.5 严格解码要求

所有控制消息必须检查：

- allowed field number；
- wire type；
- duplicate singular field；
- required presence；
- canonical bool 只接受 0/1；
- clean EOF；
- 数值范围；
- bytes 长度；
- command ID 非空；
- deadline 有效；
- Channel 存在且类型有效；
- payload 不得静默截断；
- 非法 bus type 不得 fallback 到 UART0。

## 12.6 ACK-before-HTTP 与早到事件

后端必须先：

1. 持久化 Execution；
2. 注册 command identity；
3. 再 publish。

否则设备快速 ACK 可能在 HTTP 返回前到达且找不到 owner。

前端仍需处理 WebSocket 事件早于 HTTP `202` 的情况：

- 按 edge device + command ID 做 bounded early-result buffer；
- HTTP 返回后注册 owner 并立即消费；
- 如果已消费终态，HTTP continuation 不得覆盖为 pending/unknown。

# 13. 能力声明与 ResourceReport

## 13.1 两类能力必须分开

### 节点执行引擎能力

来自 ResourceReport：

- 节点是否支持新命令协议；
- 是否支持单步/多步骤；
- 最大步骤数；
- 最大 TX/RX；
- 最大超时；
- 是否支持 Channel 排他；
- 是否支持 finally；
- 去重缓存能力；
- boot ID。

### 下游设备业务能力

来自 Driver/DeviceConfig：

- 雨量清零；
- MOS 控制；
- BMS 重启；
- 逆变器模式和参数；
- ACK/读回解析。

ResourceReport 不包含某型号 BMS/逆变器业务知识。

## 13.2 ResourceReport 建议扩展

```json
{
  "command_engine": {
    "protocol_version": 1,
    "boot_id": "...",
    "supports_single_step": true,
    "supports_multi_step": true,
    "supports_channel_exclusive": true,
    "supports_finally_step": true,
    "supports_fixed_length_rx": true,
    "supports_idle_gap_rx": true,
    "max_steps": 8,
    "max_tx_bytes": 256,
    "max_rx_bytes": 512,
    "max_step_timeout_ms": 30000,
    "max_transaction_timeout_ms": 120000,
    "dedup_cache_size": 16,
    "dedup_persistent": true
  }
}
```

上例只是 schema 形状，不代表任何 ESP32 型号的硬编码能力。实际值必须由固件基于编译目标和运行资源上报。

## 13.3 能力新鲜度

后端保存：

- report revision；
- reported_at；
- boot ID；
- protocol version。

执行操作前校验：

- report 存在；
- report 属于当前 boot；
- report 未过 freshness TTL；
- 所需 feature 均存在；
- Channel 仍存在且 enabled。

高风险操作遇到缺失或 stale report 时 fail-closed。

## 14.1 建议模块划分

```text
backend/internal/deviceaction/
├── definition.go          # DeviceOperationDefinition
├── registry.go            # 统一动作注册和有效能力合并
├── schema.go              # 参数 schema 与校验
├── compiler.go            # Driver 编译接口
├── availability.go        # Node/Channel/ResourceReport/权限交集
├── risk.go                # 风险与确认策略
└── errors.go

backend/internal/commandexec/
├── service.go             # 创建、状态转换、取消、验证
├── repository.go          # Execution/Attempt/Step 持久化
├── idempotency.go         # key/hash/collision
├── scheduler.go           # node+channel 调度
├── dispatcher.go          # MQTT publish
├── response.go            # ESP32 事件关联
├── verifier.go            # readback/telemetry/reconnect
├── recovery.go            # 重启恢复、超时扫描
├── audit.go
└── metrics.go
```

## 14.2 Driver 编译接口

建议职责接口：

```text
ListOperationDefinitions()
CompileOperation(operation_id, normalized_params, instance_context)
ParseStepResponse(operation_id, step_id, raw)
EvaluateProtocolSuccess(...)
BuildVerificationPlan(...)
EvaluateVerification(...)
```

Driver 不应：

- publish MQTT；
- 操作 DB 状态机；
- 决定当前用户权限；
- 直接写审计；
- 返回前端 HTML；
- 自行绕过 Channel scheduler。

## 14.3 DeviceConfig overlay

DeviceConfig 可配置：

- 动作启用/禁用；
- 标签和帮助文本；
- 参数范围收窄；
- 默认值；
- 现场确认策略加强；
- cooldown/rate limit 加强；
- 现场前置条件。

DeviceConfig 不可：

- 扩大 Driver 安全范围；
- 替换为未注册 encoder/parser；
- 注入 raw command；
- 降低 Driver 定义的最低风险等级；
- 取消协议强制验证。

## 14.4 Availability Service

返回：

```text
available: true/false
reason_code
reason_message
retryable
current_boot_id
capability_revision
```

判定输入：

- 当前用户；
- Node 在线；
- EdgeDevice enabled；
- Channel enabled 和兼容类型；
- ResourceReport 新鲜度；
- 协议版本；
- 当前冲突操作；
- 当前 confirmed state；
- 前置条件。

## 14.5 Dispatcher

职责：

1. 获取 Channel 调度权；
2. 创建 Attempt；
3. 持久化 identity 和 payload hash；
4. publish；
5. 状态转 DISPATCHED；
6. 接收设备 accept/result；
7. 解析每步响应；
8. 进入 VERIFYING；
9. 完成终态；
10. 释放 Channel 调度权。

## 14.6 Recovery

后端启动时：

- 加载非终态 Execution；
- 根据状态、deadline、idempotency class、boot ID 决定：
  - 查询设备缓存结果；
  - 继续等待；
  - 进入 VERIFYING；
  - 标 UNKNOWN；
  - 对安全 read_only 重试；
- 禁止对 at-most-once UNKNOWN 自动重发。

当前 `PendingWriteRecord` 的“恢复后等待清理”不能作为最终业务恢复机制。

## 14.7 post_action 重构

任何实例状态变更必须：

- 在设备验证成功后执行；
- 写入 EdgeDevice 或 EdgeDeviceSettingState；
- 不修改共享 DeviceConfig；
- 使用 execution identity 和 revision CAS；
- 失败时不能吞 warning 后返回 success。

## 15.8 HTTP 状态建议

| HTTP | 场景 |
|---|---|
| 202 | 操作已持久化并接受 |
| 400 | JSON/参数格式错误 |
| 401 | 未认证 |
| 403 | 无权限或确认不足 |
| 404 | 设备或动作不存在 |
| 409 | idempotency collision、revision conflict、冲突操作 |
| 412 | 前置条件失败 |
| 422 | 参数领域校验或能力不匹配 |
| 429 | cooldown/rate limit |
| 503 | Node 离线、执行引擎不可用 |

设备执行后的 FAILED/UNKNOWN 不通过延迟 HTTP 500 表达，而记录在 Execution 状态中。

# 17. 安全、权限与审计

## 17.1 权限模型

虽然系统目标是单用户/单管理员，仍需区分操作能力，而不是重新引入多用户 RBAC。

建议权限能力：

- `device.read`
- `device.control.low`
- `device.control.high`
- `device.control.critical`
- `device.configure`
- `device.diagnostics.raw`
- `device.audit.read`

单一管理员主体默认可拥有全部能力，但服务端仍按动作风险做明确检查，便于：

- 会话状态验证；
- 二次确认；
- API token 能力收敛；
- 未来自动化主体隔离。

## 17.2 风险确认

### low

- 当前有效 JWT；
- 无额外确认。

### medium

- 普通确认；
- 显示目标和影响。

### high

- 显示 current → target；
- 二次确认；
- 操作理由；
- 短期 confirmation token。

### critical

- 输入设备名称或确认短语；
- 操作理由；
- 近期登录或密码再认证；
- token 绑定 payload hash；
- 更严格 cooldown；
- 审计写入失败 fail-closed。

## 17.3 MQTT 安全

控制面至少需要：

- 每节点 topic ACL；
- 节点级凭据或 mTLS；
- 禁止任意节点订阅其他节点 control topic；
- broker 到 ESP32 的身份可信；
- TLS；
- 凭据轮换。

消息 deadline、command ID 和 payload hash 不能替代传输认证，但可以防重放和过期执行。

## 17.4 审计内容

不得记录：

- 密码；
- JWT；
- authorization header；
- secret；
- 未脱敏私密参数。

建议记录：

```text
actor
source_ip
execution_id
edge_device_id
node_id/channel_id
action_id/version
risk_level
params_summary
payload_hash
reason
state transition
error domain/code
verification result
timestamps
```

## 17.5 raw command 访问

普通动作 API 不返回 raw command。

诊断权限下可提供：

- TX/RX digest；
- 长度；
- 截断脱敏 preview；
- 模板版本；
- parser 名称。

完整帧只能在明确诊断模式下受控查看，并纳入审计。

# 18. 典型设备场景

## 18.1 雨量计累计值重置

### 动作定义

```text
operation_id: rainfall.reset_accumulator
kind: reset
risk: high
idempotency: at_most_once
exclusive_scope: channel
verification: readback
```

### 执行计划

1. 可选读取当前累计值并记录；
2. 发送厂商重置帧；
3. 等待协议 ACK；
4. 等待设备处理；
5. 读取累计值；
6. 验证值为 0 或符合协议定义的 reset baseline；
7. 更新 confirmed state。

### 特殊风险

第一次重置成功但 ACK 丢失时，盲目第二次重置会删除第一次重置后新增的雨量。因此：

- 发送后结果不确定必须 UNKNOWN；
- 禁止自动重试；
- 优先 readback；
- 厂商命令字节必须来自权威设备协议，不在通用层猜测。

## 18.2 BMS 充电/放电 MOS

### 动作定义

```text
bms.set_charge_mos(enabled)
bms.set_discharge_mos(enabled)
```

使用绝对目标状态，不提供 toggle。

### 执行计划

```text
1. 获取 Channel 排他权
2. 校验 BMS 数据新鲜、当前电流和保护状态
3. enter factory mode
4. parse ACK
5. set MOS absolute state
6. parse ACK
7. finally: exit factory mode
8. read basic info
9. verify fet_status bit
10. 释放 Channel 排他权
```

### 结果

- MOS ACK 失败：FAILED；
- exit factory 失败：FAILED/UNKNOWN + maintenance alert；
- ACK 成功但 readback 不一致：FAILED；
- 已发送后断线无法验证：UNKNOWN；
- confirmed value 只在 fet_status 验证成功后更新。

## 18.3 BMS 重启

### 动作定义

```text
operation_id: bms.reboot
kind: reboot
risk: critical
idempotency: at_most_once
verification: reconnect/composite
```

### 验证

- 命令发出后通信暂时中断；
- deadline 内重新收到 BMS 合法响应；
- 若协议提供 uptime/restart_count/version，验证代际变化；
- 不以同连接 WriteRsp 作为成功依据。

未重新响应：

- 若明确收到设备拒绝：FAILED；
- 若命令可能已执行：UNKNOWN。

必须与 ESP32 Node 自身重启区分。

## 18.4 逆变器开关机

推荐动作：

```text
inverter.set_power_state(on/off)
```

如果某型号只支持开机、不支持关机：

- capability 只暴露支持的目标状态；
- 不用另一个型号命令推测；
- availability 明确说明 unsupported。

验证：

- 解析设备 ACK；
- query status；
- 验证工作状态；
- 状态切换可能有合理延迟，使用 verification deadline。

## 18.5 逆变器参数设置

将当前每个枚举值一条命令：

```text
set_voltage_220
set_voltage_230
set_voltage_240
```

规范化为：

```text
inverter.set_output_voltage({ voltage: 220|230|240 })
```

其他动作：

- `set_output_frequency`
- `set_battery_type`
- `set_grid_range`
- `set_work_mode`
- `set_total_charge_current`
- `set_mains_charge_current`

执行：

1. 读取当前值和 revision；
2. 校验范围；
3. 编译协议帧和 CRC；
4. 写入；
5. 解析 ACK/ERR；
6. query EEPROM 或状态；
7. 比较目标值；
8. 更新 confirmed value。

不同逆变器型号的合法范围由对应 Driver 声明，不能通用硬编码。

## 18.6 逆变器复位

- critical；
- at-most-once；
- 需要设备名确认、理由和近期认证；
- 验证重连和状态恢复；
- 结果不确定时 UNKNOWN，不自动重试。

## 18.7 批量参数设置

UI 显示：

```text
工作模式: UTI → SBU
输出电压: 220V → 230V
总充电电流: 20A → 40A
```

后端：

- 一次校验所有参数；
- 生成有序计划；
- 每步写后读回；
- 不支持原子回滚时明确 `best_effort_ordered`；
- 第 2 步失败后停止第 3 步；
- 返回第 1 步已成功、第 2 步失败；
- 状态为 PARTIAL_FAILED；
- 重新读取全部设置，展示最终真实状态。

# 20. 兼容与迁移策略

## 20.1 不破坏现有采集

初期保留：

- 当前 ConfigManifest 周期采集；
- 当前 Driver parser；
- 当前 DataReport 数据链路；
- 当前 PeriphCmd GPIO/PWM。

新控制域旁路接入，不先删除旧代码。

## 20.2 旧 `/execute` 迁移

阶段性策略：

1. 对 read 操作内部转到 CommandExecution，但可暂时保留同步兼容响应；
2. write 操作改为返回 202 和 execution ID；
3. 旧客户端若需要兼容，可提供明确 deprecation header；
4. 禁止继续把 `status=sent` 映射为 success；
5. 最终移除直接 fire-and-forget 写路径。

## 20.3 Driver CommandTemplate 迁移

- Schedulable read command 继续服务周期采集；
- one-shot command 转换为 DeviceOperationDefinition；
- 相同底层命令可被采集和控制引用，但业务动作定义独立；
- 不把 raw command 列表作为前端公共控制契约；
- 为 Driver 与 DeviceConfig 建立一致性 lint。

## 20.4 DeviceConfig Operations 迁移

现有未版本化 JSONB：

1. 读取并验证；
2. 能映射到已注册 Driver action 的转为 overlay；
3. 只含 raw template 且无可信 Driver 的标记 `migration_required`；
4. 危险 raw operation 不自动启用；
5. 无法确认语义时 fail-closed，不猜测。

## 20.5 数据库迁移

新增表：

- command_executions；
- command_attempts；
- command_step_results；
- edge_device_setting_states。

旧 `PendingWriteRecord` 可在过渡期继续服务底层 read，但不能作为业务历史。

迁移必须：

- 向前增表，不破坏现有数据；
- 建立唯一幂等索引；
- 支持 rollback 到不使用新控制面的版本；
- 不为旧记录伪造“成功”历史。

## 20.6 前端迁移

1. 新建统一 DeviceControlPanel；
2. 专用页面嵌入同一控制面；
3. OperationButtons 标记 deprecated；
4. CommandList 只保留轮询频率管理，不展示可执行 raw command；
5. 操作历史接真实 API；
6. 移除 `config.operations` fallback，只有后端有效动作端点是权威来源。

# 24. 风险、开放决策与禁止事项

## 24.1 当前 BLOCKER

### B1：协议文档漂移

在修正 Wire Spec 前不得扩展控制协议。

### B2：缺少持久化 CommandExecution

当前 pendingwrite 不能表示业务操作生命周期。

### B3：写操作假成功

当前 `sent` 不能对用户呈现为设备执行成功。

### B4：verify 失败仍成功

必须改成 FAILED/UNKNOWN。

### B5：固件端 WriteCmd 无重放保护

危险操作上线前必须具备 exact replay/collision。

### B6：BMS MOS 缺少排他多步骤事务

直接开放现有单帧 MOS 命令不安全。

### B7：后端无权威参数 schema

前端校验不能作为安全边界。

### B8：无真实操作历史和审计闭环

破坏性控制上线前必须可追溯。

## 24.2 高风险问题

1. ESP32 RX timeout 与后端不一致；
2. payload 可能截断；
3. 非法 bus 可能 fallback；
4. Node offline 未在后端执行前 fail-closed；
5. 实例状态可能被写回共享 DeviceConfig；
6. DeviceConfig/Driver 双轨漂移；
7. 参数化 write 绕过确认；
8. 前端在线状态快照过期；
9. raw command 暴露给前端；
10. MQTT 使用全局凭据时缺少节点隔离。

## 24.3 开放决策

### D1：单步命令扩展 WriteCmd 还是新消息类型

决策条件：

- 旧固件兼容；
- required 字段能否严格协商；
- unknown field 行为；
- command ID/hash/deadline 是否可完整表达。

多步骤事务建议独立 `ChannelTxnCmd/Event`。

### D2：设备端高风险 replay 持久化策略

需要权衡：

- NVS 写放大；
- 命令风险；
- 缓存容量；
- 跨重启时长；
- boot ID 语义。

### D3：验证放在 ESP32 还是后端

建议：

- ESP32 执行透明 steps；
- 后端 Driver 解析协议 ACK 和业务值；
- 需要 Channel 原子性的 readback 可作为事务 step；
- 最终业务 predicate 由后端判断。

### D4：旧 `/execute` 兼容周期

需要根据现有调用方确定，但不能继续保留误导成功语义。

### D5：自动化主体权限

未来若加入自动化规则，必须使用独立 capability scope 和审计 actor，不能共享浏览器管理员语义。

## 24.4 明确禁止

- 禁止为每种设备新增专用 MQTT 消息；
- 禁止把 BMS MOS 当作 ESP32 GPIO；
- 禁止让浏览器提交任意 hex；
- 禁止以后端 publish 成功宣告设备成功；
- 禁止 verify 失败只记 warning；
- 禁止 at-most-once UNKNOWN 自动重试；
- 禁止用 toggle 代替绝对目标状态；
- 禁止将实例设置写入共享 DeviceConfig；
- 禁止按芯片型号硬编码命令引擎能力；
- 禁止非法 Channel fallback 到默认 UART；
- 禁止 payload 静默截断；
- 禁止后端下发可执行 UI 脚本；
- 禁止只凭单元测试宣告控制闭环完成；
- 禁止在开发验证中触碰生产 `/opt/EHomeSystem` 或 `ehome-*`。

# 最终结论

EHomeSystem 已经具备实现通用边缘设备控制所需的大部分基础设施：Channel 透明传输、request_id、PendingWrite、DeviceConfig.Operations、Driver 命令、WebSocket，以及 GPIO/PWM 已验证的请求关联模式。

正确的演进方向不是为雨量计、BMS 和逆变器分别增加一套控制代码，而是将现有能力收敛为：

```text
统一动作定义
→ 后端权威校验和风险策略
→ 持久化 CommandExecution
→ Channel 统一调度和排他
→ ESP32 严格解码、去重和事务执行
→ 目标设备协议 ACK
→ 读回/遥测/重连验证
→ confirmed state
→ WebSocket 通知
→ 操作历史和安全审计
```

在完成协议文档冻结、业务状态机、设备端重放保护和 BMS 原子 workflow 之前，不应正式开放雨量清零、BMS MOS/重启或逆变器复位等破坏性控制。
