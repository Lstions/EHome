## 传输层

- 接口：RS-232C；2400 bps、8 数据位、1 停止位、无校验。
- DB9 交叉连接：上位机 RX ↔ 逆变器 TX（Pin 2）；上位机 TX ↔ 逆变器 RX（Pin 3）；GND ↔ GND（Pin 5）。
- 所有指令为 ASCII，以回车 `\r` 结束。
- 上位机发命令后，逆变器应在 500 ms 内响应。
- 状态/查询类命令示例不带 CRC；设置类命令格式为 `<command><crc16>\r`。

### CRC 实现门禁（阻断写操作）

原件只写出占位符 `<crc16>`，**没有**说明多项式、初值、反射方式、异或值、覆盖范围、两个 CRC 字节的顺序，或 ASCII/二进制编码方式，也没有可校验的完整报文 golden vector。

因此不得复用或假定 Modbus CRC16。任何 GB3024 写操作在取得以下任一证据前必须保持未注册/不可用：

1. 厂商给出的 CRC 算法和至少一个完整请求/响应样例；或
2. 对真实 GB3024 设备的串口抓包，包含请求、ACK/NAK 和 CRC；并以该样例写入固件/后端测试向量。

### HSTS 模式值

| 值 | 含义 |
| --- | --- |
| `P` | 初始上电 |
| `S` | 待机 |

### HEEP1 响应与写后核对字段

响应形状（原件空格整理后）：

```text
(A BBB CCC D E F G HHH I J K L M N P QQQ RRR SSS TTT UUU.U VVV.V XXX.X O...\r
```

| 字段 | 含义 / 枚举 |
| --- | --- |
| `A` | 工作模式：`0` UTI、`1` SUB、`2` SBU |
| `BBB` / `CCC` | 最大总充电电流 / 市电最大充电电流（A） |
| `D` | 市电输入范围：`0` APL、`1` UPS |
| `E` | 电池类型：`0` AGM、`1` FLD、`2` USER |
| `F` / `G` | 过载重启 / 过温重启：`0` 关、`1` 开 |
| `HHH` / `I` | 输出设定电压（V）/ 频率：`0` 50 Hz、`1` 60 Hz |
| `J` | 充电优先：`0` CUT、`1` CSO、`2` SNU、`3` OSO |
| `K`～`N` | 蜂鸣器、LCD 背光、过载转旁路、输出模式 |
| `P` | BMS 通信控制：`0` 关、`1` 开 |
| `QQQ`～`TTT` | BMS 低电、回市电、回电池、低电自动开机 SOC（%） |
| `UUU.U` / `VVV.V` / `XXX.X` | 强充电压 / 浮充电压 / 低电锁机电压（V） |

### 原件中的语义冲突

`POP` 表格将 `00/01/02` 分别列为 UTI（市电优先）/ SUB（太阳能优先）/ SBU（电池优先），但紧随其后的 `POP01` 示例又写成“市电优先”。两处互相矛盾。该动作必须在真实设备上逐项读回与观察模式变化后，才可注册为可执行动作。

## 接入统一控制方案的约束

首次可实现的写动作应满足以下闭环，缺一不可：

1. Driver 只公开有明确枚举、量纲与范围的一个低影响设置（优先考虑 `PGR`，但仍需现场确认语义）。
2. 命令编码使用经黄金向量验证的 GB3024 CRC，绝不使用猜测值。
3. 写前要求 ResourceReport 证明实际通道存在，并走中风险以上的确认令牌与原因审计。
4. 接收 ACK 后不能直接视为成功；必须执行 `HEEP1`，由该动作的可信 verifier 用冻结参数比对对应字段，才写入最终成功结果。
5. 在真实 GB3024 设备上完成“设置 → ACK → HEEP1 回读 → 还原 → 再回读”的现场证据后，才扩展下一个动作。

当前连接到 ESP32-C6 UART1 的是 SN-3001 雨量计，并非 GB3024 逆变器；因此本文不授权向现有 C6 发送任何 GB3024 写帧。

### 当前只读接入

实现已将 `HSTS`、`HGRID`、`HOP`、`HBAT`、`HPV`、`HPVB`、`HTEMP`、`HGEN`、`HBMS1`、`HEEP1`、`HIMSG1`
注册为 11 个 `read/low` Action。它们默认禁用，接收上限为 256 bytes、超时为 1 s；UART 固件按线路
空闲收集完整响应。`HPV`/`HPVB` 由 action-specific verifier 携带原始请求上下文解析，避免相同响应形状
被错误归属。

这只是协议/软件单元验证，**不是**实机准入证据。只有在真实 GB3024 上得到每条命令的成功响应、并核对
解析结果后，才能在 `enabled_device_actions` 中灰度启用相应动作。

### C6 模拟传输证据（非 GB3024 实机）

2026-07-19 的第一轮 C6 UART0/GPIO16/17、2400 8N1 模拟仅接受 `HSTS\r`，并返回
`(00 P000000000000\r`。在 ResourceReport 确认临时通道已实际应用后，API
创建 `read_status` 操作 `7cbab934-64b0-42ff-a612-021804f4963f`；Outbox、V2 Ack/Final、
action-aware 解析和 verified result 均成功，发布至 Final 为 `215.713 ms`。C6 统计随之从
`accepted=40/completed=40` 增至 `accepted=41/completed=41`，无 rejected/replayed。

同日第二轮扩展为完整 11 条只读 Action。临时 EdgeDevice 使用 channel 1（UART0/GPIO16/17、
2400 8N1、无调度模板），C6 ConfigResult 成功且 ResourceReport 实报 channel 1 enabled 后，
`/dev/ttyUSB0` 模拟器依次接收 `HSTS`、`HGRID`、`HOP`、`HBAT`、`HPV`、`HPVB`、`HTEMP`、
`HGEN`、`HBMS1`、`HEEP1`、`HIMSG1`，并只对这 11 条查询回复预设 CR 终止 ASCII 行。11 条
Operation 均为 `SUCCEEDED`、各有一次 Attempt 和非空 Driver `verified_result`；发布至 Final 为
211--452 ms。PV1/PV2 分别持久化为各自字段，证明 command-aware verifier 没有混淆相同帧形状。

该验证证明统一控制链能承载全部当前 Catalog 的 CR 终止 ASCII **模拟响应**；它不证明真实 GB3024
的电气连接、型号兼容性、实际固件返回格式或任何 CRC 写操作。临时设备/配置已软删除、UART0 已恢复
禁用，C6 已收到恢复 Manifest 的 `success=true` 回执并实报仅剩 SN-3001 channel 3；模拟器已停止，
C6 保持开发 MQTT 配置。

### Manifest 容量能力证据

为防止 Driver 的轮询模板把配置推过 ESP32 固定数组上限，C6 ResourceReport 现在上报
`manifest_capacity`。本次专用 C6 实机回传：`max_templates=16`、`max_channels=8`、
`max_template_ids=8`。后端以该值预拒绝超限 Manifest：隔离开发库从 5 条临时增至 17 条模板时，
服务端在 MQTT 发布前以 16 条上限拒绝，C6 保持原 Manifest；清理后恢复 5 条模板并收到
`ConfigResult success=true`。未上报该字段的旧固件使用同一保守默认。
