## 1. 背景与目标

评估报告（分析/架构设计评估与重设计设想.md）确认当前架构为"良好解"，7 处偏离最优。本方案将其中可独立落地、收益明确的 4 项细化为可实施任务：

| 任务 | 内容 | 对应评估 § |
|------|------|-----------|
| A | unified_data 时序化：月分区 + rollup + retention 改 drop partition | §3.1 |
| B | Redis 退役：心跳/限流/去重进程内化 | §3.2 |
| C | 阈值告警引擎：规则 CRUD + DataEventBus 求值 consumer + 前端规则页 | §3.6 |
| D | 文档一致性修正（EMQX/Mosquitto 矛盾）+ broker 选型决策留档 | §3.3 |

**非目标**：微服务化、更换协议、更换前端栈、多租户、handler 全面下沉、驱动表驱动化。

## 2. 全局约束

1. 测试基线不回退：`make test`（后端 SQLite 单测 + 前端 vitest）全绿；涉及 PG 特性的部分走 `make test-integration`。
2. 方言兼容：单测跑 SQLite，PG-only DDL 必须以 `db.Dialector.Name() != "postgres"` 分支（现有模式见 datalifecycle/purge.go:300、backfill.go:178）。
3. API 兼容：/api/v1 既有响应形状不变；新增字段只增不改。
4. 每任务独立提交序列，A/B 可并行（文件集不重叠），C 依赖 A 的 rollup 表存在与否需在实现前确认接口边界（§5 任务 C 已解耦）。
5. 凭据/密钥不入文档不入代码。

## 3. 任务 A — unified_data 时序化

### 3.1 现状事实（已核实，含第一轮审查实证）

- 模型 `models.UnifiedData`（models.go:250）：ID/SensorName(32)/Value/Unit/Timestamp/CreatedAt/EdgeDeviceID/LogicalDeviceID，b-tree 索引 4 个。
- **全仓零外键引用 unified_data.id**（第一轮审查 grep 实证：`REFERENCES unified_data` 零命中）→ 主键改复合不破坏任何 FK。
- **persist consumer 显式设 `Timestamp: now`**（consumers_heavy.go 写入路径实证）→ 分区键恒有值，无 NULL 时间戳风险。
- **merge 是 `UPDATE logical_device_id` 原地改写**（migrate.go 实证），非 INSERT 搬迁 → 搬迁不产生新行，rollup 无需合并后重算全量（但 logical_device_id 变化要求 rollup 键含逻辑维度，见 3.2.2）。
- **遗漏查询面（v0.2 补）**：handler_overview.go 与 handler_edge_device.go 用 `DISTINCT ON (device_id) ... ORDER BY created_at DESC` 取各设备最新值——无时间谓词，会扫全部分区。须为该查询路径建专用覆盖或改造（见 3.2.4）。
- retention：`retention_task.go deleteExpired()`（:261）对 unified_data/device_data 两表按 Scope 条件分批 DELETE（LIMIT 子查询 + batchSleep），每日任务。
- purge（手动删除逻辑设备）：purge.go 同样 DELETE 式（方言分支 purge.go:300）。
- 降采样：handler_data.go 读时 downsampleUnifiedData()（内存 LTTB 类），max_points 参数。
- AutoMigrate 统一建表（gorm.go:57），真实 FK 走 SQL 迁移；**testutil/db.go:40 也 AutoMigrate UnifiedData**（测试基建同步改）。

### 3.2 设计

#### 3.2.1 分区策略

- unified_data 改为 PG 声明式 RANGE 分区，**分区键 (timestamp)**，月粒度，表名不变：
  - 主键从 `(id)` 改为 `(id, timestamp)`（PG 分区表约束：分区键必须进主键/唯一约束）。
  - ID 序列保持全局（bigserial 语义），业务代码零感知——所有既有查询按 id 排序仍正确（id 单调）。
  - 既有 4 个索引保留在分区级（GORM AutoMigrate 不支持分区，DDL 全部走手写 SQL 迁移，AutoMigrate 列表中移除 UnifiedData 并加注释防回归）。
- SQLite（测试环境）：不分区，模型/查询路径完全一致（方言分支），索引由 GORM 建。
- 分区管理器 `datalifecycle/partition_mgr.go`：
  - 启动时确保未来 3 个月分区存在（CREATE TABLE ... PARTITION OF，IF NOT EXISTS 语义用 pg_class 查询判断）；
  - 每日任务检查滚动创建下月分区；
  - retention 到期 → `DROP TABLE unified_data_YYYYMM`（替代该表的批量 DELETE）；device_data 表维持现状 DELETE（量小，不动）。
- 迁移（一次性，启动时执行 + 手动脚本双通道）：
  1. CREATE TABLE unified_data_new（分区母表 + 索引）；
  2. INSERT INTO ... SELECT 按月分批搬迁（复用 backfill 的水位断点续跑模式，每批 10K 行 + batchSleep）；
  3. RENAME 原表 → unified_data_legacy，new → unified_data；
  4. 观察一个 retention 周期后归档 legacy（本期只 RENAME 不 DROP，降险）。

#### 3.2.2 Rollup 表

```sql
CREATE TABLE unified_data_rollup_1m (
    device_id      BIGINT       NOT NULL,
    sensor_name    VARCHAR(32)  NOT NULL,
    bucket         TIMESTAMP    NOT NULL,   -- 分钟对齐
    min_v, max_v, avg_v         DOUBLE PRECISION,
    last_v                      DOUBLE PRECISION,
    last_id                     BIGINT,     -- 保形去重语义锚点(MAX(id))
    cnt            INTEGER,
    PRIMARY KEY (device_id, sensor_name, bucket)
);
```
- 写入：新 databus heavy consumer `RollupConsumer`（挂在 persist 之后），UPSERT ON CONFLICT DO UPDATE；仅 PG 启用（SQLite 跳过，测试不受影响）。
- **写放大防护（v0.2）**：RollupConsumer 独立邮箱 + fail-open（bus 既有语义），且 UPSERT 按事件逐条执行不阻塞；若单机压测中 rollup consumer 邮箱丢率 >0.1% 则降级为内存微批（500ms/批多行 UPSERT），实现留开关 `rollup.batch_ms`（默认 0=逐条）。
- **逻辑维度（v0.2 修正）**：merge 为原地 UPDATE logical_device_id，rollup 行不含该列则合并后历史归属无法在 rollup 层体现。裁决：rollup 保持 device 维度（物理写入源不变，无需重算）；logical 维度查询一律走 raw 路径（保形去重语义本就定义在 raw 上）。前端长跨度趋势按设备展示，与现状一致——不引入第三种口径。
- 读取：GET /unified-data/historical 与 historical-batch 增加 `precision=rollup|raw` 参数（默认 auto：跨度 > 48h 强制 rollup，≤ 48h 用 raw），响应形状不变（value 字段映射 avg_v，附 min/max 可选字段）。**仅当查询含 device 过滤时允许 rollup 路径**；logical scope 查询强制 raw（见上）。
- retention：rollup 保留 365 天（量小用 DELETE）；原始数据默认保留 30 天（可配 `retention.raw_days`，**默认值裁决 v0.3：保持 365 天与现状一致，30 天仅作为推荐配置写入 .env.example 注释——不静默缩短用户数据寿命；rollup 的收益在查询侧已兑现，存储收益留给用户主动选择**）。
- **保形去重交互**：query_scope.go 的 ROW_NUMBER() OVER (PARTITION BY ...) 去重在 raw 路径保留原样；rollup 天然无重复问题。

#### 3.2.4 最新值查询面改造（v0.2 新增）

handler_overview.go / handler_edge_device.go 的 `DISTINCT ON (device_id) ... ORDER BY created_at DESC` 无时间谓词，分区表下会扫全部子分区。改法：
- 该"每设备最新值"语义迁到**内存缓存**：nodemgr 已有 worker_pool_cache 先例，新增 `latestValueCache`（map[deviceID]UnifiedData，persist consumer 写入时旁路更新，启动时从各分区最新 1 页回填）；
- overview/latest-data 类 API 改读缓存，miss 回落原 SQL（保留正确性兜底）；
- 收益：该查询面彻底脱离 unified_data 表结构演进，且延迟更低。

## 4. 任务 B — Redis 退役

### 4.1 现状事实（已核实，含主Agent自查）

Redis 消费方全量盘点（grep 实证，共 6 处接线 + 1 个包）：

### 4.2 设计

原则：**删除依赖而非替换服务**。三处分别进程内化：

1. **ping 防伪造 + 配对**（sender + handler_response）：防伪造校验并入 PingTracker——Track(deviceID, ts) 时已存时间戳，handler_response 的 Pong 处理改为从 pingTracker 取 pending 记录比对 timestamp（mismatch 拒绝并 WARN），Complete 语义即一次性消费（等价 Redis Del）。PingTracker 已有 10s 超时清理，TTL 语义保留。
2. **心跳/在线判定**：offlinedetector 删除 checkRedisHeartbeats 分支，统一走 checkDBLastSeen。**v0.3 修正（第二路审查发现 nil-panic 面 + 主Agent复核确认）**：现 checkDBLastSeen:118 有 `if redis.IsOnline(col.NodeID) { continue }`——redis.Client 为 nil 时 IsOnline 会 panic（redis.go:47 直接 Client.TTL 无 nil 检查），当前靠 checkRedisHeartbeats 先行 return 掩盖。退役改法：删除该 continue 行与整个 checkRedisHeartbeats 函数，checkDBLastSeen 成为唯一路径；**LastSeen==nil 的节点跳过判定（保持 :129 现状语义）**。StatusReport 周期实测固件 status_task 5s（main.c:65），90s 阈值 = 18 个心跳周期，检测上界不变。
3. **登录限流**：LoginLimiter 删除 redis 字段与分支，固定 memory 实现（单主体场景内存桶足够；重启清零可接受——锁定窗口仅 5 分钟）。构造点 3 处（routes.go/handler_auth/handler_account）签名同步。

配套：
- cmd/server/main.go 移除 redis.Connect（:135，non-fatal 连接失败分支一并删）；config.yaml 删 redis 段；config.go 删 Redis 字段/RedisAddr()/REDIS_ADDR env 解析（:179）；go.mod 去 go-redis + miniredis。
- **部署面同步清理（v0.3 补，第二路审查实证）**：docker-compose.yml 删 redis 服务(:22)/卷(ehome-redisdata)/ehome.depends_on.redis(:89)/REDIS_ADDR env(:73)；Makefile infra 目标 `up -d --wait postgres redis emqx` 去 redis（:86 附近）；.env.example 删 REDIS_PORT/REDIS_ADDR 注释段（:11-13, :41-42）；Makefile 头部注释 4 处 redis 字样。
- README 架构图同步。
- **保留升级路径**：offlinedetector 的 Detector 接口不变，未来多实例时在 detector 内加分布式心跳实现即可。

## 5. 任务 C — 阈值告警引擎

### 5.1 设计

#### 5.1.1 数据模型（新增 2 表）

```go
// AlertRule 阈值规则
type AlertRule struct {
    ID             uint
    TargetType     string // edge_device | logical_device
    TargetID       uint
    SensorName     string    // 与 UnifiedData.SensorName 同域
    Comparator     string    // gt|gte|lt|lte|eq|neq
    Threshold      float64
    DurationSec    int       // 连续满足时长, 0=立即
    SilenceSec     int       // 告警恢复后静默窗口, 默认 300
    Level          string    // info|warning|critical
    Enabled        bool
    Name           string
    CreatedAt/UpdatedAt
}
// AlertEvent 告警事件（含恢复）
type AlertEvent struct {
    ID, RuleID uint
    State      string    // firing | resolved
    Value      float64   // 触发/恢复时值
    FiredAt, ResolvedAt *time.Time
    NotifiedAt *time.Time
}
```

#### 5.1.2 求值引擎（v0.4 修正挂接点：解析后回调，非独立 consumer）

**挂接点裁决（Phase 2 预核实实证）**：DataEvent 携带的是 RawData 原始字节，物理量由 SensorParserConsumer 内部解析为 `[]parser.Field{Name,Value,Unit}`（consumers_heavy.go:164-241）。若按 v0.1 的"独立 DataConsumer"挂 bus，每个事件要重复解析一遍 RawData，按 10000 events/s 基线 CPU 翻倍，不可接受。

改法（复用既有回调先例 deviceActivity）：SensorParserConsumer 增加 `alertCallback func(edgeDeviceID uint, fields []parser.Field, at time.Time)`，在 records 构建处（:269）调用；nodemgr/manager.go 构造时注入 alert.Evaluator 回调。分片模式下回调随分片并发，天然并行求值。语义与 v0.1 ShouldHandle 等价（只对解析成功的物理量求值）。

- `alert/evaluator.go`：规则缓存（**CRUD 写路径直接失效+重载缓存，30s 兜底刷新仅作保险**）+ 每规则滑动窗口（[]timestampedValue，DurationSec=0 直通）。
- 状态机：normal → firing（条件连续满足 DurationSec）→ resolved（任一不满足值出现）。firing/resolved 各生成 AlertEvent + 复用 Notification 表 + WS BroadcastEvent。**Notification 接入实证：events.Notification 常量已定义但全仓无生产者、前端按 type 映射图标（warning/success/info）——告警通知 type 用 "warning"/"critical"（critical→前端 fallback 图标），Notification.Source="alert_rule"、SourceID=ruleID 用于回链，不改通知中心组件**。
- 抑制：同规则 firing 未 resolved 不再发新事件；SilenceSec 内不重复通知但更新 AlertEvent。
- 超载保护：评估器内 ring buffer 上限 1000 规则×窗口，超出丢弃并计数（对齐 databus fail-open 风格），暴露 metrics。

#### 5.1.3 API（/api/v1/alert-rules, /api/v1/alert-events）

- rules: GET list / POST / PUT /:id / DELETE /:id / PATCH /:id/enabled；events: GET list（rule_id/state/时间过滤）+ POST /events/read。
- envelope 对齐既有 Success/Error 模式；**权限对齐现状（v0.3 修正）：单主体模式下系统无 role 中间件强制（JWT claims 带 role 但 handler 未消费），告警规则写操作与边缘设备写操作同策略——登录即可，不引入新的权限面**。
- AlertRule 模型字段 Level 取值 info|warning|critical，映射 Notification.Type（critical→"error"，warning→"warning"，info→"info"，对齐前端图标映射）。

#### 5.1.4 前端

- 新页 `/alerts`（导航"告警规则"，MainLayout allMenuItems 追加）：规则表格 + 创建/编辑对话框（目标设备选择器复用 LogicalDeviceCandidateSelect 模式——已实证组件存在）+ 事件时间线（复用 Dashboard 状态变化时间线样式）。
- api/alert.ts + stores/alert.ts；Dashboard 增加未处理告警计数卡（可选，P2）。

## 7. 实施顺序与并行性

```
Phase 1（并行）:
  Task A 数据层（分区+rollup+retention改drop）   ← 最大风险先行
  Task B Redis 退役                              ← 文件集与 A 零重叠
Phase 2（A 合入后）:
  Task C 告警引擎（后端 consumer/API → 前端页面）
Task D 文档修正（随 Phase 1 收尾一并提交）
```

依赖说明：C 的求值输入是 DataEvent（物理量），不依赖 rollup 表；但 C 的"历史告警上下文图表"若要长跨度展示则受益于 A，故排 Phase 2。B 与 A 无交集可并行。
