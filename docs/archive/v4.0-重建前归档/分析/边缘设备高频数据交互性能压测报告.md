# 边缘设备高频数据交互 — 后端资源占用与性能压测报告

- 日期：2026-08-15
- 环境：AMD Ryzen 5 5600 (12 核) / Linux 7.0 / 后端 ehome-server v2.0 (本机进程) / EMQX (docker) / PostgreSQL (docker, 统一基础设施) / Redis (docker)
- 目标：模拟边缘设备高频数据上报，量化后端资源占用（CPU/内存/DB/日志）与有效处理吞吐，定位容量瓶颈

---

## 1. 测试方法

### 1.1 模拟器架构（MQTT 级，非串口级）

真实链路为 **ESP32 → MQTT(EMQX) → 后端 HandleMessage → worker pool → databus 6 消费者**。
本压测在 MQTT 层注入与固件帧格式完全一致的 DataReport (0x03) 帧（`/tmp/ehload/main.go`，复用 `pkg/frame` 编码规则）：

- 每节点 1 个独立 MQTT 连接（模拟真实设备连接形态），topic `nodes/<node_id>/up`，QoS1
- 帧字段：f1=channelID f2=timestamp(ms) f3=sequence f4=raw(4B lk_th01 温湿度) f5=errorCode=0 f7=edgeDeviceID（scheduled sample 语义 → 走 sensor_parser 全链路）
- 微抖动随机相位，避免所有节点同拍

### 1.2 负载模型

| 档位 | 节点数 | 每节点速率 | 总输入 (msg/s) | 60s 发送总数 |
|------|--------|-----------|---------------|-------------|
| S1   | 200    | 2 Hz      | 400           | 24,000      |
| S2   | 500    | 4 Hz      | 2,000         | 120,000     |
| S3   | 1000   | 5 Hz      | 5,000         | 300,000     |
| S4   | 1000   | 10 Hz     | 10,000        | 600,000     |

压测数据：`nodes` 表插入 SIM0001-SIM1000 共 1000 节点（status=online），`edge_devices` 表每节点 1 个 `lk_th01` 设备（device id 3..1002，driver-backed，无 DeviceConfig）。

### 1.3 度量与对账

- **对账法（精确丢率）**：每档前后对 `unified_data`（device_id 3..1002）与 `device_data`（node_id LIKE 'SIM%'）做 count 快照，增量换算处理事件数：
  - sensor_parser 处理数 = unified_data 增量 / 2（每事件写 2 个传感器字段行）
  - db_persist 处理数 = device_data 增量 − unified_data 增量（parser 也写 device_data 1 行/事件）
- **资源采样**：2s 间隔采样后端进程 CPU（/proc utime+stime，CLK_TCK 换算）/RSS/线程、PG 写吞吐（pg_stat_database 差分）、表行数、后端日志行速率
- 发布侧：压测器统计发送/失败/QoS1 ack 延迟

| 档位 | 输入 msg/s | 发送总数 | parser 处理 | db_persist 处理 | **总体丢弃率** | 后端 CPU | RSS | PG 插入/s | 后端日志/s |
|------|-----------|---------|------------|----------------|--------------|---------|-----|----------|-----------|
| S1   | 400       | 24,000  | 3,842 (16%) | 11,289 (47%)  | **84.0%**     | ~0.27 核 | 40 MB | ~450 | 1,267 |
| S2   | 2,000     | 120,000 | 3,807 (3.2%)| 11,261 (9.4%) | **96.8%**     | ~0.55 核 | 43 MB | ~450 | 6,048 |
| S3   | 5,000     | 300,000 | 2,056 (0.7%)| 5,568 (1.9%) | **99.3%**     | ~0.9 核  | 44 MB | ~450 | 14,000 |
| S4   | 10,000    | 600,000 | 2,145 (0.4%)| 6,624 (1.1%) | **99.6%**     | ~1.5 核  | 44 MB | ~450 | 28,000 |

补充数据：
- 发布侧：S1/S2 零失败，ack 平均 0.26/0.39 ms；S3 有 4,887 条失败（3.5%），平均延迟 35.8 ms、最大 4.4 s；S4 失败 2,023 条（0.5%），平均 11.5 ms、最大 4.9 s

- databus overflow goroutine：0 次（worker pool 未溢出）；sensor_parser 解析失败：0 次（被处理的事件全部成功）
- 压测期间 PG 连接数 16（上限 25），无连接耗尽

## 3. 核心发现（按严重度）

### F1（CRITICAL）sensor_parser 单消费者串行吞吐 ≈ 64 evt/s —— 系统有效容量天花板

sensor_parser 是唯一做「解析+落库+状态更新+HA 发布+WS 广播」的消费者，**单 worker 串行**（`databus.runConsumer`，每消费者 1 个 mailbox worker）。实测饱和吞吐：

- S1/S2（低负载段）：**64 evt/s**（unified 增量 3,842/3,807 ÷ 60s）
- 每事件成本 ≈ **15.6 ms**：3 次 DB 查询（EdgeDevice Preload Node → DeviceConfig/模板查找）+ 3 次 DB 写入（unified_data ×2 行、device_data 1 行、edge_devices.last_data_at update）+ 2 次同步 MQTT QoS1 发布（HA PublishState 每传感器 1 topic）+ 2 次 WS 广播
- 输入 400 msg/s 时即饱和 → 84% 的事件在 fanout 阶段被丢弃，**前端实时数据在 >100 msg/s 输入下只能看到被处理的 ~16%**

### F2（CRITICAL）db_persist 独立饱和 ≈ 188 evt/s

db_persist（1 次 JSON marshal + 1 次 INSERT device_data）饱和吞吐 ≈ 188 evt/s（5.3 ms/事件）。与 parser 独立饱和——同一事件 parser 丢、db_persist 可收（fanout 对每个消费者独立判定），故两者处理数不同。

### F3（HIGH）databus fanout 静默丢弃，无日志

`bus.go fanout()`：消费者 mailbox 容量 64，满时**丢弃新事件**（`recordDrop` → prometheus `ehome_data_event_bus_dropped_total`），**无任何日志输出**。压测全程 backend.log 无一条 drop 记录。生产环境数据丢失完全静默，仅靠 Prometheus 指标可观测。

### F4（HIGH）日志爆炸：每消息 ≥2 行 Info 日志，S4 峰值 28k 行/s

`HandleMessage` 每消息固定 2 行 Info（`Received msg type 0x03` + `DataReport: ...`），解析成功再加 1 行 `Parsed`。S4 时 28,046 行/s、5 分钟 193 MB。slog 同步写文件成为压测中 **CPU 消耗第一大项**（输入 10k/s 时后端总 CPU 仅 1.5 核，其中日志占大头）。生产长时间运行会：磁盘膨胀、IO 抢占、日志检索瘫痪。

### F5（HIGH）HA 发布同步阻塞 + 失败放大 —— 高负载下 parser 吞吐二次崩塌

`consumers_heavy.go` 中 `c.ha.PublishState()` 是**同步 QoS1 发布**（每事件 2 次，每次最长阻塞 5s timeout）。S3/S4 段 EMQX 压力上升后出现 518 次发布失败——**每次失败在 sensor_parser 消费者内阻塞至超时**，期间 mailbox 迅速堆满丢弃新事件。证据：S3/S4 的 parser 吞吐从 64/s 掉到 **34-36/s**（输入越大，HA 越慢，parser 越慢，负反馈）。**单点慢依赖（HA/EMQX）直接拖垮核心数据链路**。

### F6（MEDIUM）MQTT 回调侧每消息同步 Redis SET

`HandleMessage` 每消息同步 `offlineDetector.UpdateHeartbeat` → Redis `SETEX`（15s TTL）。10k msg/s 即 10k SET/s——本地 Redis 尚可承受，但这是 MQTT 回调热路径上的同步 IO，输入再高或 Redis 抖动会直接阻塞消息接收。

### F7（MEDIUM）EMQX 在 5k msg/s 输入下 QoS1 ack 开始超时

S3 起发布失败率 3.5%、ack 平均延迟从 0.4 ms 恶化到 35.8 ms（最大 4.4 s）。EMQX 单实例在此负载下（5k 入 + 10k HA 出）开始退化，进一步放大 F5。

### F8（LOW）后端 CPU/内存本身远未到瓶颈

修正后的 CPU：400/s→0.27 核、2000/s→0.55 核、5000/s→0.9 核、10000/s→1.5 核。RSS 稳定 40-45 MB（Go 无泄漏迹象），线程 17-20 恒定。**瓶颈 100% 在串行消费者 + 同步 IO 链，不在算力/内存**。这也是为什么「加机器」解决不了问题——单消费者只吃单核。

## 4. 真实场景换算（容量预算）

系统有效容量（当前架构）：

| 场景 | 输入 | parser 可处理 | 丢数据 |
|------|------|-------------|--------|
| 1 节点 × 10 设备 × 1 Hz | 10 msg/s | 100% | 无 |
| 10 节点 × 10 设备 × 1 Hz | 100 msg/s | 64% | **36%** |
| 50 节点 × 10 设备 × 1 Hz | 500 msg/s | 12.8% | **87%** |
| 100 节点 × 10 设备 × 1 Hz | 1000 msg/s | 6.4% | **93.6%** |

（假设每设备 1 秒 1 条上报；若 5s 间隔则容量 ×5，100 节点 × 10 设备 = 200 msg/s 时仍丢 68%。）

**结论：当前架构的安全线约为 60-80 msg/s（≈ 8 台设备 × 10 设备 × 1 Hz），超过即静默丢数据。**

## 5. 优化建议（分级）

### P0-1：sensor_parser 消费者并行化（分片多 worker）
按 `deviceID` hash 分片到 N 个独立消费者（如 8-16），保持单设备内有序。吞吐理论 ×8-16 → 突破 64 evt/s 天花板至 ~500-1000 evt/s。这是**唯一能从根上解决容量问题的改动**。databus 已有 Register/Unregister 机制，改造为「每片一个 consumerWorker」即可，无需动 bus 核心。

### P0-2：日志降噪（成本最低收益最大）
- `HandleMessage` 的 `Received msg type` / `DataReport` 每消息 Info 日志降为 Debug 或按节点抽样（如每节点每 10s 1 条）
- `Parsed` 成功日志同降级
- 压测证明：日志是 CPU 第一大项、磁盘 193MB/5min 的元凶，且信息量极低（压测日志 97% 是重复帧头）

### P0-3：HA PublishState 异步化 + 失败隔离
- 改为非阻塞：独立 goroutine/队列 + QoS0（HA 场景可接受），失败只记 metric 不阻塞 parser
- 或至少把 publish timeout 从 5s 降到 500ms-1s
- 消除「EMQX 慢 → 核心数据链路雪崩」的负反馈环（F5）

### P1-1：DB 批量写
sensor_parser 每事件 3 次写入（unified ×2 + device_data + last_data_at update）改为：
- unified_data 跨事件批量 INSERT（消费者内攒批，如 50ms 窗口或 50 行）
- `edge_devices` 状态更新节流（last_data_at 每设备 ≥1s 才写一次）
- db_persist 与 parser 的 device_data 双写合并（同一事件写 2 次 device_data = 浪费 1 次 INSERT）

### P1-2：Redis 心跳节流
每节点 15s TTL 窗口内仅首次消息执行 SETEX（内存记上次时间），10k msg/s → ≤1000 SET/s。

### P1-3：丢弃可观测性
- databus drop 增加周期日志摘要（如每 10s 汇总 dropped 计数）
- Prometheus 告警规则：`ehome_data_event_bus_dropped_total` 增长 > 0 即告警

### P2-1：EMQX 侧
- 压测接入数上限评估（连接数 × 速率预算）
- 高负载时 QoS0 降级开关

### P2-2：WS 广播合并
高频 `channel_data` 事件按 100ms 窗口合并（前端实时性要求通常 ≤500ms 即可）。

## 6. 复现步骤

```bash
# 0. 环境: docker 基础设施(ehome-postgres/ehome-emqx/ehome-redis) + make backend

# 1. 准备压测数据 (1000 节点 + 1000 lk_th01 设备, 幂等)
bash scripts/bench/prepare_bench_data.sh 1000

# 2. 构建压测器 (帧格式与固件一致)
cd /tmp/ehload && GOPROXY='https://goproxy.cn,direct' go mod tidy && go build -o ehload .

# 3. 资源采样 (后台)
python3 /tmp/ehload/sampler.py /tmp/ehload/sample.csv 360 &

# 4. 单档压测: 500 节点 × 4Hz = 2000 msg/s, 60s
./ehload --nodes 500 --rate 4 --duration 60 --qos 1 --device-base 3

# 5. 对账 (精确丢率)
docker exec ehome-postgres psql -U ehome -d ehome -t -A -c \
  "SELECT count(*) FROM unified_data WHERE device_id BETWEEN 3 AND 1002;"

# 6. 清理
docker exec ehome-postgres psql -U ehome -d ehome -q -c \
  "DELETE FROM edge_devices WHERE node_id LIKE 'SIM%'; DELETE FROM nodes WHERE node_id LIKE 'SIM%';"
```

压测文件位置（留档可复现）：
- 压测器：`/tmp/ehload/main.go`（go.mod module ehload）
- 采样器：`/tmp/ehload/sampler.py`
- 编排脚本：`/tmp/ehload/run_bench.sh`（4 档全自动）
- 数据准备：`scripts/bench/prepare_bench_data.sh`
- 原始数据：`/tmp/ehload/bench_run.log`、`/tmp/ehload/bench_sample.csv`、`/tmp/ehload/smoke_sample.csv`
