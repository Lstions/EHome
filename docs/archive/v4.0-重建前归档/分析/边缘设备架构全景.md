# 边缘设备架构与接口设计全景（2026-08-16 源码取证版）

> 范围：中心端 Go 后端（backend/）+ ESP32 固件（esp32-collector/）+ 前端接口面。
> 本文以当前工作区源码为准（行号/文件为实读取证），设计文档（docs/设计/）为对照。
> 协议版本现状：二进制帧 v2.2 命名 + ChannelCmdV2(0x15-0x17) + PeriphCmd(0x1B/0x1C) + LogStream(0x1D)。

---

## 1. 三层物理模型（docs/设计/总体设计.md v2.2）

```
平台层 Platform
  └─ 中心端 Center：Go/Gin/GORM/PG/Redis/Mosquitto
      ▲ MQTT (nodes/{id}/up|down|control) + HTTP
  └─ 节点 Node：ESP32-S3/C6，ESP-IDF + FreeRTOS，23 个 component
      ▲ 5 种总线：UART/I2C/SPI/GPIO/ADC（GPIO/PWM 不走通道系统）
  └─ 边缘设备 EdgeDevice：物理传感器/执行器
```

核心概念区分（术语表约定）：
- **节点 Node** = 物理整机（ESP32）
- **通道 Channel** = 节点上的物理通信端点（总线号+引脚+波特率+模式）
- **设备配置 DeviceConfig** = 一种型号的协议无关定义（init_flow/parser/默认间隔）
- **边缘设备 EdgeDevice** = (node_id, channel_id, device_config_id) 三元组实例化
  - 唯一性：`(channel_id, hardware_id, type)` 三元组去重（hardware_id=从机地址；空地址降级为 (channel, type)）
  - 应用层校验而非 DB 唯一索引（空地址语义）

## 2. 通信面：MQTT 主题与二进制帧协议

### 2.1 MQTT 主题（backend/internal/mqtt/mqtt.go:537-546）

| 主题 | 方向 | QoS | 用途 |
|---|---|---|---|
| `nodes/{id}/up` | 节点→中心 | 0/1 | 遥测上报（DataReport 等常规流） |
| `nodes/{id}/down` | 中心→节点 | 1 | 下行（WriteCmd 等） |
| `nodes/{id}/control` | 中心→节点 | 1 | **可靠主题**：manifest + 控制命令（ChannelCmdV2） |

### 2.2 二进制帧（esp32-collector/components/frame/frame_codec.h）

protobuf 兼容 wire type，消息类型 0x01-0x1D：

| 类型 | 代码 | 方向 | 语义 |
|---|---|---|---|
| Hello | 0x01 | ↑ | 上电握手（node_id/fw/model/config_hash/nvs_has_config） |
| StatusReport | 0x02 | ↑ | 节点状态（uptime/config 摘要） |
| DataReport | 0x03 | ↑ | 传感器数据上报（含 report_type 轮询/写回） |
| ConfigManifest | 0x04 | ↓ | 配置下发（channel+template+parser） |
| ConfigResult | 0x05 | ↑ | manifest 应用结果 |
| WriteCmd / WriteRsp | 0x06/0x07 | ↓/↑ | 旧式单步读写（现仅透明管道/终端场景） |
| Ping/Pong | 0x08/0x09 | 双向 | 心跳与延迟测距（ping_result WS 事件） |
| OTA Cmd/Prog | 0x0A/0x0B | ↓ | OTA 固件分发 |
| Scan Rpt/Req | 0x0C/0x0D | ↑/↓ | I2C 总线扫描 |
| Query Rsp/Req | 0x0E/0x0F | ↑/↓ | 资源能力查询（旧） |
| ConfigQuery/Report | 0x10/0x11 | ↑/↓ | 节点请求配置+上报（10min 周期） |
| HelloAck | 0x12 | ↓ | Hello 应答 |
| ConfigSyncReq/Rsp | 0x13/0x14 | 双向 | v2.1 同步 |
| **ChannelCmdV2** | 0x15 | ↓ | **有界物理事务信封**（身份+计划步骤） |
| **ChannelCmdV2 ACK / FINAL** | 0x16/0x17 | ↑ | 设备接受回执 / 最终结果（含逐步响应） |
| ResourceReport | 0x19 | ↑ | 硬件资源上报（DMA 通道/GPIO/PWM/UART 档位） |
| QueryResources | 0x1A | ↓ | 中心请求刷新资源 |
| **PeriphCmd / PeriphRsp** | 0x1B/0x1C | ↓/↑ | GPIO/PWM 引脚直控（不经通道系统） |
| LogStream | 0x1D | ↑ | 固件日志流（分页+level 过滤+persist） |

协议核心契约（backend/pkg/frame/channel_cmd_v2.go:32）：

```
ChannelCmdV2 { CommandID[16B] PayloadDigest[16B] Attempt BootID EdgeDeviceID
               ChannelID DeadlineUnixMS TXData ReadSize RXTimeoutMS PostTXDelayMS
               RiskClass Flags Plan[≤8 steps] }
ChannelCmdV2Response { CommandID PayloadDigest Attempt BootID Success
                       ErrorCode RawResponse[信封] }
```

- 身份四元组（CommandID+PayloadDigest+Attempt+BootID）用于 ACK/FINAL 归属
- Plan 步骤 kind：read=0 / write=1 / readback=2 / finally=3（transport.go:263 planStepKindCode）
- 批量响应信封（固件 bus_worker.c:806-848 编码；backend drivers/batch_envelope.go 解码）：
  `raw[0]=N(1..8); 每步 kind(1B)+len_le(2B)+resp`

## 3. 中心端分层与核心组件（backend/internal/）

### 3.1 包结构与职责

```
api/            REST 路由+信封（envelope.go Success/Error）
nodemgr/        Manager：MQTT 消息分发入口 → handler_{hello,config,data,resources,status,logstream,channel_cmd_v2,response}
mqtt/           MQTT 客户端（监督式断线重连 backoff，Ready 通道）
databus/        DataEventBus + 分片消费者（2026-08-15 性能修复：P0-1 分片+R1 复合键）
deviceaction/   动作目录（声明→schema→编译→验证 装配，默认启用推导）
commandexec/    执行域：创建/确认/dispatch/状态机/终局验证
drivers/        驱动注册表 + 可选能力接口 + 协议解析器（jiabaida/techfine/generic_modbus/generic_i2c/bmp280）
deviceinit/     初始化编排器（InitSequenceProvider 三层解析）
pendingwrite/   WriteRsp 关联与重试（旧式单步写路径）
sync_gate.go    Hello/config 同步决策（NVS空/epoch落后/hash不匹配→强制下发）
manifest_codec  ConfigManifest 编解码（field 1-9，case 覆盖完整性是审查点）
offlinedetector 离线检测（Redis 心跳 TTL）
datalifecycle/  软删设备的合并/保留/清理（logical_device 方案 v3.2）
homeassistant/  HA Discovery（retained）
logstream/      日志总线（DB 持久 + WS 推送 + 72h 清理）
```

### 3.2 数据流（上行）

```
ESP32 DataReport(0x03) ──MQTT up──► Manager.HandleMessage（manager.go:237）
  ├─ offlineDetector.UpdateHeartbeat（Redis TTL 续期）
  └─ DataEventBus.Dispatch（按 deviceID 分片路由）
       ├─ StreamReassembler（流式分帧重组，parserShards 个分片）
       ├─ SensorParserConsumer（driverRegistry.Get → ParseData/Calibration/CommandAware 三级）
       │    └─ 解析失败 → PendingWriteConsumer（写命令的读回数据救回路径）
       ├─ DBPersistConsumer（unified_data 批量写入，消费模式为 parallel）
       ├─ WSPushConsumer（WS data_update/channel_data 推送）
       ├─ TerminalConsumer / DataMetricsConsumer
       └─ HA Integration（entity 状态发布）
```

### 3.3 同步流（配置 SSoT）

```
Hello ─► SyncGate.decide（sync_gate.go:92）
           NVS 空 / hash 不匹配 / epoch 落后 → 强制下发 ConfigManifest
           └─ ConfigEventBus（1024 缓冲，配置变更秒级推送）
                └─ sender_snapshot 快照上传（manifest field 编码）
ConfigManifest ─► 固件 config_mgr 解析 → 应用事务（成功/失败回执）
  失败 → sync_state 自愈重发；hash 全程不匹配 → 诊断证据链
设备初始化：InitSequence 三层解析 = Driver InitSequenceProvider > DeviceConfig.InitFlow JSONB > 硬编码
```

## 4. 设备控制域（本轮 BMS 评审的核心，最新形态）

### 4.1 分层：驱动声明 → 目录装配 → 执行域

```
drivers.Driver（7 方法基础接口：ParseData/DeviceType/DeviceName/OEM/Category/HardwareTypes/GetSensorDefinitions）
  + 可选能力接口（渐进装配，parsing-only 驱动永不暴露控制面）：
    ControlActionProvider      声明动作目录（纯声明，无 DB/传输/字节注入）
    ControlActionCompiler      参数化动作→单步帧（服务端可信代码）
    ControlActionPlanCompiler  bounded_sequence→计划（写+读回+finally）
    ControlActionAddressCompiler / PlanCompilerForAddress   地址绑定（防多从机总线误广播）
    ControlActionVerifier / AddressVerifier  终局验证（ACK+读回对账，与 ParseData 分离）
    CalibrationAwareDriver / CommandAwareDriver / CommandTemplateProvider / InitSequenceProvider

deviceaction.NewBuiltInRegistry（definition.go:445）
  ├─ schemaFromDriver：参数标量 schema（string/boolean/integer/number，Required/Min/Max/Enum）
  ├─ 注册期 fail-closed 校验：set 必须有 verifier；参数化必须有 compiler；
  │   bounded 必须有 plan 源；AtMostOnce⇒high/critical；MaxSteps≤8；Verification 枚举
  ├─ 默认启用推导（definition.go:543-549）：set/reset 且 verifier≠nil 且 Verification≠""
  │   且 AvailabilityCode=="" ⇒ enabled=true（驱动出厂 Enabled 只是默认值非权威）
  └─ AvailabilityCode：protocol_unverified 动作目录可见但不可执行（15 个 BMS 写动作现状）

commandexec.Service
  ├─ Catalog()：9 项可用性检查（动作存在/启用/引擎 gate/设备状态/节点能力/确认要求…）
  ├─ Create()：Idempotency-Key 幂等 + Confirmation（medium+ 风险需 5min token，限流 5/min）
  │   + RecentAuth 要求 + Reason 审计
  ├─ Dispatcher：CompilePlanForAddress → 节点能力核对（MaxBatchSteps/MaxTX/RX/超时档位）
  │   → WireDigest（绑定 bootID/channel/deadline/实际 step 字节）→ MQTT control 主题
  ├─ 状态机（state.go）：QUEUED→DISPATCHED→DEVICE_ACCEPTED(0x16)→VERIFYING(0x17)→
  │   SUCCEEDED/FAILED/UNKNOWN/CANCELLED；非终态可 Cancel，UNKNOWN 可人工 Resolve
  └─ VerifyFinal（service.go:403）：五元组身份冻结（edge.node/channel/config/type）+ action 版本冻结
      + CanonicalizeParams 逐字节复验 → 驱动 Verifier 对账后落 verified_result
```

### 4.2 REST/WS 接口面（handler_device_operation.go:21-216）

| 端点 | 语义 | 关键契约 |
|---|---|---|
| GET `/api/v1/edge-devices/:id/actions` | 动作目录（含可用性） | Catalog 9 项检查结果 |
| POST `/api/v1/edge-devices/:id/operations` | 创建执行 | `Idempotency-Key` 头必填；`confirmation_token`；`reason`；202 Accepted |
| POST `/api/v1/edge-devices/:id/actions/:action_id/confirm` | 高风险写前确认 | 5min 有效、5/分钟限流（confirmation.go:31-34） |
| GET `/api/v1/edge-devices/:id/operations` | 操作历史 | 按设备 |
| GET `/api/v1/device-operations/:execution_id` | 单次执行详情 | 三路 GORM 错误分支 |
| POST `/api/v1/device-operations/:execution_id/cancel` | 取消（非终态） | |
| POST `/api/v1/device-operations/:execution_id/resolve` | UNKNOWN 人工裁决 | success/failure + reason ≤512 |

WS 事件（events/events.go 常量单一来源）：`device_operation_update` 推送执行状态变化；
GPIO/PWM 走 `periph_result`/`periph_state`。

### 4.3 固件执行侧

```
ChannelCmdV2(0x15) ─► msg_handler → handler_channel_cmd_v2_process
  ├─ 槽位状态机（RAM 槽位，at-most-once；幂等身份比较）
  ├─ bus_worker execute_uart_batch：逐步 TX→turnaround→collect→[kind|len_le|resp] 编码
```

## 5. 接口设计模式（跨层提取）

1. **可选能力接口 + 类型断言装配**：Driver 基础接口最小化，控制/校准/命令上下文/初始化全部走可选接口。优点：旧驱动零迁移成本、控制面天然 fail-closed。代价：接口清单已 10+（见 BMS 评审 §5.2），装配链 60 行断言。
2. **声明与执行分离**：ControlAction 是数据，Compiler/Verifier 是可信服务端代码。浏览器输入到 wire bytes 之间隔着 schema 校验+CanonicalizeParams+编译重放+WireDigest 四道。
3. **身份/版本冻结**：VerifyFinal 同时校验 edge 五元组冻结与 action 版本冻结，杜绝 stale 响应串仓与降级重放。
4. **地址绑定族**：共享多从机总线（Modbus/I2C）的动作在编译与验证两入口都绑定 EdgeDevice.hardware_id，杜绝错地址广播（2026-08-14 实测修复：reset_rainfall 写死 0x01 事故）。
5. **证据门禁分层**：目录注册期构造校验 → AvailabilityCode 协议冻结门禁 → 运行时 9 项可用性 → 5min 确认窗口 → at-most-once 禁重传 → 读回/观测对账。每层独立可测。
6. **信封与语义分离**：ChannelCmdV2 只承载身份+有界步骤，业务语义全部在 RawResponse 交给驱动服务端解析——设备侧永不解释业务字节。
7. **事件总线 + 分片消费**：上行数据经 DataEventBus 按 device 分片并行消费（解析/持久化/WS/HA/终端五类消费者正交），2026-08-15 压测后 S1 丢率 0%。
8. **配置 SSoT + 多信号同步**：Hello/ConfigQuery/ConfigEventBus 三条信号收敛到同一 SyncGate decide，中心端为唯一权威源。

## 6. 接口设计的已知债务（诚实清单）

| # | 债 | 位置 | 影响 |
|---|---|---|---|
| 1 | 信封解码器在 drivers 包内小写共享（deviceaction 反向 import 成环） | drivers/batch_envelope.go | 第二 bounded 驱动可直接用；环问题需未来拆包解决 |
| 2 | 参数 schema 标量-only，数组用 resistance_1..30 hack | deviceaction/schema.go | Modbus 块写需要 array 类型（action Version 字段已预留） |
| 3 | CommandAwareDriver 依赖 WriteData hex 字符串匹配模板 | registry.go:100-116 | 大小写敏感靠消费方全局 ToUpper 归一，脆弱 |
| 4 | F2/F3 表驱动后 spans/schema/parse 已统一，但 0x0F trailer 等解析缺口仍在 | jiabaida.go | parse0x0F 声明 runtime/humidity 但未投影 |
| 5 | 旧式 WriteCmd(0x06/0x07)+pendingwrite 与新 ChannelCmdV2 双轨并存 | pendingwrite/ | 透明管道/终端场景依赖旧路径，合并需谨慎 |
| 6 | Catalog 9 项可用性检查人工维护 | deviceaction vs REST 层 | 双份同步风险（此前评审已提） |
| 7 | 协议文档分层：设计文档 v2.2 与代码现状存在命名漂移（collector 包名/deviceID 参数名） | docs/设计/同步机制 | 文档自身已声明，读码以代码为准 |

## 7. 演进方向评估（承接 BMS 评审）

- **能支撑长远开发的骨架**：三层模型、SSoT 同步、声明式动作目录、有界事务信封、身份冻结——五个支柱都已落地且有测试锁。
- **当前最值得投入的三件事**：(a) schema array 类型（第二批驱动的硬门槛）；(b) deviceaction 包拆分解决 import 环（信封/状态机/验证归位）；(c) 旧 WriteCmd 轨道的退役时间表（唯一还在用"无可信验证的裸写"路径）。
- **BMS 站点的现状**：read 全目录可用（5 读操作）、set_mos_policy 实机双向验证已启用、15 个写/工厂动作 protocol_unverified 冻结等待真机证据——目录完整、门禁严格，正是骨架设计意图的体现。
