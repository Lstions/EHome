## 1. 评估基线与结论

### 1.1 证据基线（2026-08-21，commit cc40e3c6 + 工作区）

| 维度 | 事实 |
|------|------|
| 后端 | 34,757 行 Go（非测试）+ 36,236 行测试（测试:代码 > 1:1） |
| 固件 | 20,524 行 C，21 个 component |
| 前端 | 39,627 行 TS/Vue，40 组件 + 36 视图 |
| 部署 | docker-compose 4 服务：postgres + redis + emqx + ehome（单容器多阶段构建） |
| 协议 | 二进制帧 v2.5，20 种消息类型，MQTT 双 topic 灰度 |
| 数据 | unified_data 单表 + b-tree 索引（CONCURRENTLY 建），无分区；读时降采样；DELETE 式 retention |

### 1.2 总结论

**当前架构是这套需求的"良好解"，不是"最优解"；但偏离最优的部分是局部的、可增量修正的，重写不成立。**

判断依据：需求是"家庭规模、单主体、多协议、长稳运行"，当前架构在正确性关键路径（配置同步自愈、OTA 可靠性、fail-open 容错）上的设计质量高于同类系统平均水平，这些恰恰是最难改的部分，已经做对了。偏离最优的是部署重量、数据层时序化、代码分层三处，均可渐进改造。

## 2. 当前架构做对了什么（不应动的部分）

| # | 设计决策 | 为什么对 |
|---|---------|---------|
| 1 | **三层模型（中心端/节点/边缘设备）** | 节点无业务逻辑、中心端持有全部状态 → 节点可替换、协议演进可控。这是全系统最重要的抽象，与"方案必须通用"的原则一致 |
| 2 | **二进制帧协议而非 protobuf** | 实测 ~50B vs ~150B（-67%）、~200ns vs ~10μs（-50x）、十六进制可调试。对 ESP32 + MQTT QoS1 场景是正确的取舍，且共用 C/Go 语义头文件避免了双端 schema 漂移 |
| 3 | **SyncGate + Epoch + ConfigHash 配置同步** | Hello 决策（NVS 空/Epoch 落后/Hash 不匹配强制下发）+ 中心端重启 push 兜底 + 节点 60s 周期 sync 兜底。配置最终一致是 IoT 系统最常见的翻车点，这里做了三重兜底，是系统里质量最高的设计 |
| 4 | **资源全部来自 ResourceReport 上报** | 中心端零硬编码 ESP32 型号资源 → 新硬件型号零后端改动。通用性原则的最好落实 |
| 5 | **Driver Registry + ConfigTemplate + 逐指令 Manifest** | 新设备 = 配置 + parser + 动作定义，多数情况不改代码。扩展方向正确 |
| 6 | **进程内 DataEventBus（分片 + 轻重消费者分离）** | 单二进制内解决 ingest→persist→push 扇出，复测丢率 84%→0%、PG 写入 8.3×。没有引入网络 MQ 是正确的克制 |
| 7 | **OTA：HTTPS 下载 + SHA256 + A/B + mark-valid 回滚** | 比帧分块传输简单可靠，失败路径（帧丢失→Hello 补完成、并发→supersede）都覆盖了 |
| 8 | **测试纪律与文档治理** | 测试:代码 > 1:1、固件 host_tests ~6000 行、docs/ 规范强制。这是长期演进的真正本钱 |

## 3. 偏离最优的点（按影响排序）

### 3.1 数据层缺时序化设计（影响最大）

**现状**：unified_data 单表 + b-tree；retention 靠 DELETE + 每日 purge；降采样在读取时做（max_points + gzip）。

**问题**：
- DELETE 删行产生死元组，需要 vacuum，表越大 purge 越慢——retention 成本随数据量线性上涨。
- 高频场景（BMS 综合数据 + 16 串单体电压，秒级间隔）年数据量可达 10⁷~10⁸ 行，b-tree 索引写入放大与查询退化会重现（性能复测已经撞过一次 84% 丢率的墙）。
- 读时降采样每次查询都重算，原始数据一条不少地存 365 天，存储成本高。

**改法**（增量，不动表结构语义）：
1. unified_data 按月原生分区（PG declarative partitioning），retention = drop partition（O(1)），purge 任务退化为分区管理。
2. 写时聚合 1min rollup 表（保留 30 天原始 + 365 天 rollup），前端趋势图查 rollup，详情才下钻原始。
3. 不引入 TimescaleDB——原生分区 + 一张 rollup 表已覆盖家庭规模需求，扩展依赖不值得。

### 3.2 Redis 是近乎冗余的服务（部署重量）

**现状**：Redis 仅 4 处消费方——心跳 TTL（nodemgr/sender、offlinedetector）、写响应去重（handler_response）、登录限流（auth/login_limiter）。

**问题**：多一个服务 = 多一份内存、多一条故障路径、多一份备份/监控负担。而：
- 心跳：节点周期发 StatusReport，后端重启后一个心跳周期内自愈，DB last_seen 本就可兜底；
- 登录限流：单进程 + 单主体，进程内计数器完全够；
- 响应去重：单进程内存 map + TTL 即可（当前单实例部署没有共享状态需求）。

**改法**：Redis 降级为可选组件（默认不启），上述三处改进程内实现 + DB 兜底。compose 从 4 服务降到 3。若未来真做分布式多实例（设计 §5.2 的 ≥10 节点路径），再引回来，届时它才有存在理由。

### 3.3 EMQX 对家庭规模过重（且文档不一致）

**现状**：README 架构图 = EMQX 5.7；总体设计 §5.1 部署架构 = Mosquitto 2.x；compose 实际 = EMQX。文档与实现互相矛盾。

**问题**：EMQX 是为百万连接设计的分布式 broker，10-100 节点场景用到的能力（集群、管理 dashboard）用不上，内存占用是 Mosquitto 的一个数量级以上。ACL（节点只能 pub/sub 自己 topic）Mosquitto 同样支持。

**改法**：切 Mosquitto（配置文件声明 ACL，无 dashboard 依赖），或至少先修正文档不一致。此项收益纯是资源与运维面。

### 3.4 API 层业务逻辑下沉不彻底（分层债）

**现状**：设计规定 handler 只做参数校验 + 调 service，实际 handler_edge_device.go 1,666 行、handler_device.go 1,096 行、handler_node.go 1,078 行，业务逻辑沉淀在 handler 内。对照：commandexec/、datalifecycle/ 是正确的 service 形态。

**问题**：handler 内逻辑无法被复用（如未来 MCP/API 扩展）与单测直测，只能走 HTTP 集成测试；三个千行文件是改动冲突热点。

**改法**：不一次性重构。按"下次改哪个域就顺手下沉哪个域"的规则渐进：edge-device 域优先（最大且最活跃）。新代码强制 service 层。

### 3.5 驱动实现是命令式大文件（扩展成本）

**现状**：jiabaida.go 1,929 行、inverter_techfine.go 1,096 行、builtin.go 894 行。驱动接口（Registry + action schema）是对的，但每个驱动内部把帧编解码、寄存器定义、动作编排、解析全部平铺。

**问题**：每加一个厂商协议 ≈ 新增 1-2K 行。嘉佰达已有 17+ 动作且还在加（4ebbefa4），线性膨胀中。BMS/逆变器/通用 Modbus 三类驱动 80% 结构同构：读寄存器组 → 字段解码表 → 动作 = 写寄存器 + 校验。

**改法**：寄存器表数据化——驱动 = 声明式 register map（YAML/Go 结构）+ 一个通用帧引擎，厂商差异收敛为数据。**但注意时机**：只有 2-3 个厂商时手写是合理的，第 4-5 个厂商出现时再做不迟（避免为未验证场景增复杂度）。当前最务实的动作是：新动作一律写进现有驱动时保持"表驱动"风格（定义与逻辑分离），为将来抽取留好缝。

### 3.6 产品功能缺口：无阈值告警引擎

**现状**：通知中心只承载事件类通知（配置失败、节点离线）。BMS 单体过压、逆变器过温这类"数据越限"没有告警路径，只能靠人盯屏或 HA 侧。

**问题**：对"家庭能源/环境监控"这个定位，阈值告警是核心闭环而非锦上添花；设计文档也只把它列在 P2/P3（边缘设备级告警历史）。

**改法**：规则 = (数据点选择器, 比较符, 阈值, 持续时间, 通知渠道) 的 CRUD + 数据入库路径上的规则求值（DataEventBus 已有消费者挂点，加一个 alert consumer 即可，架构上零阻力）。这是"重新设计"清单里唯一真正缺的功能件。

### 3.7 前端体量与响应式维护成本

**现状**：39.6K 行服务 9 个页面；移动端断点适配历史包袱重（rebase 增量丢失事故的根因就是响应式 CSS 多版本并行）。

**问题**：不算失衡（BMS/逆变器详情页的 shared/ 抽取方向是对的），但响应式实现分散在组件级 @media，缺统一的断点 token，回归成本高。

**改法**：断点 token 收敛到 theme 变量 + 布局组件统一消费；不重写。

## 4. 如果基于需求重新设计（绿地方案）

> 前提：同样的需求（FR-A~N）与约束（家庭规模、ESP32 硬件、单主体、单人+AI 维护）。结论先行：**骨架 80% 会做成一样**——三层模型、二进制帧、MQTT、SyncGate 式同步、驱动注册表、资源上报、OTA 设计全部保留。差异在下面六处。

### 4.1 部署形态：2 容器，进程内化一切

```
┌─ 宿主机 ──────────────────────────────┐
│  ehome (单 Go 二进制)                  │
│   ├─ HTTP API + WebSocket + Swagger   │
│   ├─ MQTT 客户端                       │
│   ├─ DataEventBus（分片，已有）        │
│   ├─ 告警规则求值器（新增）            │
│   └─ 内存态：心跳/限流/去重（替代 Redis）│
├───────────────────────────────────────┤
│  postgres:16（含分区 DDL 迁移）        │
│  mosquitto:2（ACL 文件声明）           │
└───────────────────────────────────────┘
```

- Redis 删除（§3.2 论证）；EMQX → Mosquitto（§3.3）。
- 单二进制内已含 broker 客户端、事件总线、WS hub——家庭规模下"一切进程内"是复杂度最低解。
- 保留升级路径：多实例时 Redis（心跳共享）与 broker 集群再回来，接口不变。

### 4.2 数据层：分区 + rollup 从第一天就有

- unified_data 建表即按月 RANGE 分区，retention = drop partition；
- 同事务写 1min rollup（device_id, sensor_name, min/max/avg/last/count），原始 30d + rollup 365d；
- 降采样 API 优先查 rollup，下钻才碰原始分区；
- 逻辑设备合并（v3.3）不变——它解决的是身份问题，与分区正交。

### 4.3 分层：handler=transport 强制，service 为业务家

```
api/      只做绑定/校验/envelope（目标 <300 行/文件）
service/  edge_device / node / channel / config / ota / alert / dashboard
          —— 状态机与事务边界都在这层，可直接单测
repo/     GORM 封装
```
现状的 commandexec、datalifecycle 就是这个形态，推广到全部域。集成测试保住端到端，service 单测保住分支覆盖。

### 4.4 驱动：接口不变，实现表驱动

```go
type RegisterMap struct {   // 厂商差异收敛为数据
    Blocks   []RegisterBlock          // 地址/长度/解码字段
    Actions  map[string]WriteAction   // 动作→寄存器写 + 校验规则
    Parsers  map[string]DecodeRule
}
```
- 通用帧引擎（Modbus RTU / 嘉佰达 DD A5.. / Techfine ASCII 三种传输壳）+ 每厂商一份 RegisterMap；
- 预期把 jiabaida 1,929 行压到 ~400 行数据 + 共享引擎；
- **绿地第一天就这么做**（因为引擎反正要写）；对现库则按 §3.5 的时机判断渐进。

### 4.5 告警引擎作为一等公民

- 规则模型挂边缘设备/逻辑设备，求值挂在 DataEventBus 的 alert consumer（入库同路径，零额外链路）；
- 告警 → 通知中心（已有）→ WS 推送（已有），只补"规则 CRUD + 求值 + 抑制/恢复"三件事；
- 这是绿地方案里唯一新增的运行时常驻件，也是产品完整度最大补齐。

### 4.6 协议与固件：原样保留，一处小改

- 二进制帧、20 种消息、双 topic、OTA 流程、DMA/事件驱动总线全部照搬——这些是被性能复测和实机验证过的资产；
- 小改：Hello 握手时节点直接上报"协议能力位图"（支持哪些消息类型），替代当前按版本号推断，降低灰度期的兼容矩阵复杂度。

### 4.7 前端：同栈，三处纪律

- Vue3 + Element Plus + Pinia 不变（换栈无收益）；
- 断点/间距/字号 token 化，组件只消费 token（§3.7）；
- 详情页一律"shared 组合 + 类型特化卡"模式（BMS/逆变器已验证），禁止页面级复制。

### 4.8 绿地方案明确不做的

| 不做 | 理由 |
|------|------|
| 微服务/服务网格 | 单进程足够，网络边界只会加延迟与运维面 |
| protobuf/gRPC | 实测体积与解析成本都劣于手写帧（总体设计 §3.1） |
| TimescaleDB/InfluxDB 双写 | 原生分区 + rollup 覆盖家庭规模，少一个数据库 |
| NATS/Kafka | DataEventBus 进程内已达标（10000 events/s 设计值） |
| 多租户/OAuth/RBAC 界面 | 单主体是产品决策 |
| Kubernetes | docker-compose 足够，K8s 运维成本 > 收益 |

## 5. 落地路径（增量，非重写）

重写不成立：95K 行已验证资产、测试:代码 > 1:1、关键路径（同步/OTA/容错）质量高。按投入产出排序的改造序列：

| 步骤 | 内容 | 规模 | 收益 |
|------|------|------|------|
| 1 | unified_data 月分区 + rollup 表 + retention 改 drop | 中 | 消除最大的未来性能/存储风险 |
| 2 | 告警规则引擎（consumer + CRUD + 前端规则页） | 中 | 补齐产品功能缺口 |
| 3 | Redis 退役（心跳/限流/去重进程内化） | 小 | 部署 -1 服务 |
| 4 | EMQX → Mosquitto + 文档一致性修正 | 小 | 资源占用、消除文档矛盾 |
| 5 | edge-device handler → service 下沉（随下次改该域顺手做） | 中 | 分层债渐进偿还 |
| 6 | 驱动 RegisterMap 抽取（第 4 个厂商出现时启动） | 大 | 扩展成本线性→常数 |

每步独立可验证、可回滚，互不阻塞；步骤 1/2 收益最大优先。

## 6. 评审点（需少爷拍板的语义决策）

1. **Redis 是否值得保留**：若近期有 ≥2 后端实例计划则留，否则退役。
2. **告警引擎优先级**：是否认可"数据越限告警"为 v3.4 级功能（当前 P2/P3）。
3. **驱动表驱动化的时机**：认可"第 4 个厂商触发"还是"现在就做"。
4. **EMQX → Mosquitto**：是否依赖 EMQX dashboard/规则引擎等未在需求清单中的能力。
