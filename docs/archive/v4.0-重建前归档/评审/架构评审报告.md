### Component 体系

```
main.c (319 行, 薄入口)
  ├─ frame_codec    — 二进制帧编解码 (共享protocol定义)
  ├─ wifi_mgr       — WiFi 连接状态机
  ├─ ehome_mqtt     — MQTT 客户端+断线重连+auto-resubscribe
  ├─ msg_handler    — 消息分发 (switch-case, 10种下行消息)
  ├─ config_mgr     — ConfigManifest 解析+NVS持久化
  ├─ scheduler      — 周期性采集调度器 (FreeRTOS task)
  ├─ bus            — 硬件总线抽象层 (UART/I2C/SPI统一接口)
  ├─ sync_manager   — 配置同步客户端
  ├─ ota            — HTTPS OTA固件升级
  ├─ rgb_led        — 状态指示
  └─ factory_reset  — 恢复出厂
```

### 亮点

**1. MQTT 死锁理解深刻**

`main.c:173` 将 Hello handshake 从 MQTT 回调线程中提取到独立 FreeRTOS task，避免了等待 HelloAck 时阻塞 MQTT 消息分发导致死锁。

```c
/* The MQTT state callback runs on the MQTT event task, which is also
 * responsible for dispatching incoming MQTT_EVENT_DATA. If we block
 * here waiting for HelloAck, the event task cannot deliver the very
 * message we are waiting for */
xTaskCreate(hello_handshake_task, "hello", 3072, NULL, 5, NULL);
```

**2. NVS 配置持久化完整**

`config_mgr` 支持 save/load + CRC32 校验 + hash 比对，断网重启后能自动恢复上次配置。

**3. bus 抽象层接口设计统一**

```c
bus_handle_t bus_open(uint8_t bus_type, const uint8_t *config, size_t config_len);
void bus_set_tx(bus_handle_t handle, const uint8_t *tx_data, size_t tx_len, uint32_t read_length);
bus_error_t bus_transact(bus_handle_t handle, uint8_t *rx_buf, size_t rx_buf_size, size_t *rx_len);
```

三总线（UART/I2C/SPI）共用同一套接口，scheduler 不需要关心底层协议。

**4. msg_handler 回调解耦**

用 `__attribute__((weak))` 暴露 `on_write_cmd_received` / `on_scan_req_received` 给 main.c 覆盖，msg_handler 不依赖上层。

### 硬伤

| # | 问题 | 位置 | 严重度 | 说明 |
|---|------|------|--------|------|
| 1 | **SPI 总线未实现** | `bus.c:263-265` | 高 | 返回 BUS_OK 但 `*rx_len=0`，上层误以为成功 |
| 2 | **bus_config 解析无版本号** | `bus.c:76-83` | 高 | 硬编码字节偏移，后端格式变化固件无法感知 |
| 3 | **scheduler 不处理模板** | `scheduler.c:158` | 高 | 只做 `bus_set_tx(NULL,0,0)` 即只读不写，DeviceConfig 下发的 write_data 模板未使用 |
| 4 | **无硬件看门狗** | `main.c:53` | 中 | WiFi断开或MQTT卡死时设备不会自动重启 |
| 5 | **静态缓冲区限制** | 多处 | 中 | `tx_buf[64]`, `rx_buf[256]`, `MAX_CHANNELS=8` 写死 |
| 6 | **bus_config_len 无上限校验** | `config_mgr.c:337` | 中 | 直接拷贝到 `bus_config[128]`，超长会溢出 |
| 7 | **业务层零测试** | 全部 component | 中 | 仅 frame_codec 有测试 |

### 亮点

**1. SyncGate 是三端中最精彩的设计**

```
决策入口: OnHello / OnStatusReport / OnConfigChange / OnServerStartup / OnConfigQuery
决策逻辑: NVS为空? → Epoch落后? → Hash不匹配? → Dedup过期?
                                ↓ 任一命中
                           SyncActionFull
                                ↓
                    SendConfigManifestWithDecision
```

每个决策都有独立的 `SyncReason` + `SyncID` (UUID) 用于全链路追踪，decisions 通过 Prometheus counter 暴露。

**2. manager.go 依赖注入干净**

```go
type Manager struct {
    db              *gorm.DB
    mqtt            *mqtt.Client
    wsHub           *websocket.Hub
    ha              *homeassistant.Integration
    otaMgr          *ota.Manager
    hashMgr         *ConfigHashManager
    pendingWrite    *pendingwrite.Manager
    deviceInit      *deviceinit.Orchestrator
    termMgr         *terminal.Manager
    offlineDetector *offlinedetector.Detector
    dataCh          chan dataReportJob
    eventBus        *ConfigEventBus
    syncGate        *SyncGate
}
```

每个依赖都是接口或具体类型，main.go 里装配，没有全局变量（除了 database 和 redis 包）。

**3. DataReport 处理管道**

```
MQTT消息 → handleDataReport (快速解码)
  → dataCh (worker pool, 非阻塞)
    → processDataReportJob
      → parseAndStoreData (driver解析)
        → DB写入 (UnifiedData + DeviceData)
        → HA MQTT发布
        → WebSocket广播
```

Worker pool 满时 fallback 到同步处理，不丢数据。

**4. 事件系统一致性**

前后端事件名通过 `check_ws_event_names.sh` CI script 校验一致性。events.ts 和 events.go 必须一一对应。

**5. v2.2 命名迁移彻底**

models.go 里 Node/EdgeDevice/DeviceConfig/Channel 四张表，命名完全对齐术语表。

### 硬伤

| # | 问题 | 位置 | 严重度 | 说明 |
|---|------|------|--------|------|
| 1 | **API 响应格式不一致** | `handler_edge_device.go` | 中 | 有时用 `Success()` 帮助函数，有时手写 JSON；错误有时用 `message`，有时用 `error` |
| 2 | **DataReport 每次都查 DB** | `handler_data.go:63` | 中 | 高频场景下 `deviceID → collectorID` 映射应缓存 |
| 3 | **v2.1 命名残留** | `handler_hello.go` | 低 | 函数名叫 `handleHello` 但参数叫 `deviceID` |
| 4 | **无请求超时** | 全部 API handler | 中 | DB 操作没有 context timeout，慢查询会挂起请求 |
| 5 | **GORM AutoMigrate 禁用了外键** | `database/gorm.go:31` | 中 | SQL 迁移需手动执行，首次启动 DB 缺 FK |
| 6 | **无集成测试** | 全部 | 高 | 端到端链路只靠手工验证 |

### 目录结构

```
src/
├── api/          — HTTP API 封装 (12 个模块)
├── stores/       — Pinia 状态管理 (8 个 store)
├── views/        — 页面组件 (12 个页面)
├── components/   — 通用组件 (forms/charts/common/channel/node/parser)
├── router/       — Vue Router 配置
├── events/       — WebSocket 事件名常量
├── composables/  — 组合式函数
├── directives/   — 自定义指令
├── utils/        — 工具函数
├── locales/      — i18n (中/英)
└── styles/       — 全局样式
```

### 亮点

**1. WebSocket store 设计完整**

- 发布-订阅模式，按事件类型分发
- 自动重连（5秒退避）
- 应用层心跳（30秒 ping）
- token query param 认证
- 支持 `'*'` 通配订阅
- 返回 unsubscribe 函数（避免内存泄漏）

**2. 事件名共享（Single Source of Truth）**

`events.ts` 定义了所有 WS 事件名常量，与后端 `events.go` 通过 CI script 校验一致性。

**3. API 层封装**

`client.ts` 统一处理 JWT token 注入、401 自动跳转、业务错误码拦截。

**4. 路由设计合理**

- lazy load (`() => import(...)`)
- meta 字段丰富(`requiresAuth`, `title`, `icon`, `roles`, `hidden`, `hiddenInMenu`)
- 认证+角色双重守卫
- 403/404 专用页面

**5. 生产部署 server.js 考虑了 WebSocket 代理**

正确处理了 HTTP Upgrade 请求转发，支持前端容器直接代理 WS 到后端。

### 硬伤

| # | 问题 | 位置 | 严重度 | 说明 |
|---|------|------|--------|------|
| 1 | **测试几乎为零** | 全部 store/view | 高 | 仅 6 个测试文件，API handler/WS store/router guards 全无测试 |
| 2 | **TypeScript 大量 any** | `stores/node.ts:6` 等 | 中 | `nodes: [] as any[]`, `data?: any` |

**Go 后端 > ESP32 > Vue3 前端**

### 三端共同短板

| 短板 | 严重程度 | 影响 |
|------|---------|------|
| 集成测试为零 | 高 | 端到端链路只靠手工验证，回归风险大 |
| SPI 总线未实现 + 模板不生效 | 高 | 数据采集核心链路断裂（ESP32端） |
| 前端测试覆盖 4/10 | 中 | 重构风险大，类型安全弱 |
| 配置/协议版本号缺失 | 中 | bus_config 格式一改就挂，无向前兼容 |

### 一句话总结

**Go 后端的 SyncGate 设计是亮点，但前后端串联测试缺失让质量评估缺少底气。ESP32 固件模块化好但核心功能（模板驱动采集）链没打通。前端工程化不错但测试覆盖太少。**
