# 节点（ESP32）— 实现与中心端交互

> **固件协议版本：** Hello `proto_version = "2.6"`
> **事实来源：** `esp32-collector` 当前实现（`main/`、`components/`）
> **本文范围：** 节点固件实际提供的业务能力，以及中心端与节点之间的 MQTT 二进制协议契约。后端应以本文的“中心端要求”实现收发、状态处理与配置下发。

## 1. 节点职责

ESP32 节点是“现场总线和外设的受管执行端”，而不是配置的最终来源：中心端是配置单一事实来源。节点启动后建立网络连接、声明自身身份和硬件能力，接收中心端配置后驱动现场总线采集或执行控制，并持续回传运行状态、原始数据和命令结果。

| 业务域 | 节点实际能力 | 中心端要求 |
|---|---|---|
| 网络接入 | STA 自动重连；无凭据时启动 SoftAP + HTTP 配网页；凭据存于 NVS | 不参与配网页协议；等待节点 MQTT 上线 |
| 身份 | 优先使用 eFuse Wi-Fi MAC 生成 12 位大写十六进制 `node_id`；MAC 读取失败才回退到 `CONFIG_COLLECTOR_NODE_ID` | 以 Hello 中的 `node_id` 和 MQTT topic 作为节点身份；不要假定 Kconfig 默认值是实际 ID |
| 配置 | 接收并校验配置清单，事务化重建 DMA、GPIO/PWM、总线、调度器和日志流 | 下发完整 `ConfigManifest`，以 `manifest_id + sync_id` 关联结果；仅在成功 `ConfigResult` 后认定已生效 |
| 现场采集 | UART、I2C、SPI、ADC 通道；每通道可挂多个边缘设备，每设备最多 3 个独立周期命令 | 解析 `DataReport` 的通道、边缘设备、命令索引和原始字节；业务解析在中心端完成 |
| 现场控制 | 兼容旧 `WriteCmd`；支持具幂等/重放语义的 `ChannelCmdV2`；支持 GPIO/PWM 外设控制 | 选择对应控制协议并处理 ACK 与最终结果；超时、重试和幂等键必须遵守 V2 协议 |
| 可观测性 | 5 秒状态心跳、资源清单、通道健康、内存/队列指标、日志流 | 更新节点在线状态和能力快照；按需消费日志流 |
| 运维 | OTA 下载、校验、进度回传、待验证镜像回滚；长按 BOOT 5 秒清除 NVS 并重启 | 下发 OTA 后根据 `OtaProg` 跟踪；工厂重置后按新节点会话重新配置 |

## 2. 连接与会话流程

```text
ESP32                         MQTT / 中心端
  | Wi-Fi 就绪                      |
  |-- connect / subscribe --------->| nodes/{id}/down (QoS 0)
  |                                 | nodes/{id}/control (QoS 1)
  |-- Hello (0x01, nonce) --------->|
  |<--------- HelloAck (0x12, 同 nonce)
  |-- ResourceReport (0x19) ------->|
  |<--------- ConfigManifest (0x04) | 需要配置或配置变更时
  |-- ConfigResult (0x05) --------->| 仅完整应用成功后 success=1
  |-- ResourceReport (0x19) ------->| 成功配置后刷新运行时能力
  |-- StatusReport (0x02, 每 5 秒)->|
```

MQTT broker URL 来自 `CONFIG_COLLECTOR_MQTT_BROKER_URL`；当前默认配置为 `mqtt://192.168.20.3:1883`，部署时应通过 sdkconfig 或对应 defaults 覆盖。会话 client ID 为 `node_id`，keepalive 为 30 秒，节点自行管理重连：指数退避、最多 3 次 reconnect 后销毁并重建客户端；订阅 ACK 超时同样触发重建。

| Topic | 方向 | QoS | 用途 |
|---|---:|---:|---|
| `nodes/{node_id}/up` | 节点 → 中心端 | 1，日志流为 0 | 所有上行二进制帧 |
| `nodes/{node_id}/down` | 中心端 → 节点 | 0 | 常规下行：配置、采集控制、OTA、查询等 |
| `nodes/{node_id}/control` | 中心端 → 节点 | 1 | 可靠控制入口；与 `down` 一同订阅 |

只有 MQTT 连接且两个 topic 已完成订阅后，节点才认为链路 ready 并发送 Hello。HelloAck 必须回显当前会话 nonce；缺少字段、重复字段、未知字段或 nonce 过期都会被拒绝。连接代际变化后旧 ACK 不得用于确认新会话。

## 3. 编码约定

每个 MQTT payload 是一个无外层长度前缀的二进制帧：第 1 字节为消息类型，随后为 protobuf 兼容的 `tag + value` 字段编码（varint 或 length-delimited）。字段未出现表示未提供；中心端必须能忽略未知的可扩展字段，节点对部分安全敏感的下行帧会执行严格字段校验。

## 4. 上行消息（节点 → 中心端）

| 类型 | 名称 | 发送时机 | 中心端处理重点 |
|---:|---|---|---|
| `0x01` | Hello | 每次 ready、主动同步请求或重连后 | 绑定身份、对比 epoch / manifest、回复同 nonce 的 HelloAck |
| `0x02` | StatusReport | 已连通时每 5 秒 | 刷新在线状态、同步状态、健康和性能指标 |
| `0x03` | DataReport | 定时采集或读命令完成 | 用边缘设备和命令索引路由原始数据 |
| `0x05` | ConfigResult | 配置事务完成 | 使用 `manifest_id + sync_id` 去重、确认或标记失败 |
| `0x07` | WriteRsp | 旧 WriteCmd 完成 | 关联 `request_id` |
| `0x09` | Pong | 收到 Ping | 用回显时间戳计算链路延迟 |
| `0x0B` | OtaProg | OTA 下载/校验/失败 | 按 `ota_id` 更新进度和终态 |
| `0x0C` | ScanRpt | Modbus 扫描完成 | 接收发现地址列表 |
| `0x0F` | QueryRsp | 查询请求完成 | 关联 `request_id` |
| `0x11` | ConfigReport | 收到 ConfigQuery | 返回当前 manifest、模板及通道数量 |
| `0x16` / `0x17` | ChannelCmdV2Ack / Final | V2 命令被接受及最终完成 | 用命令身份四元组和 `event_sequence` 去重；Final 才是执行终态 |
| `0x19` | ResourceReport | Hello 成功、配置成功或收到 QueryResources | 保存硬件和当前可用通道能力；它是 V2 命令准入依据 |
| `0x1C` | PeriphRsp | GPIO/PWM 操作完成 | 关联 `request_id`，读取错误码、返回值和 PWM running 状态 |
| `0x1D` | LogStream | 配置开启后批量发送 | 仅用于诊断；以 QoS 0 发送，不能作为可靠审计数据 |

### 4.1 Hello（0x01）与 HelloAck（0x12）

Hello 字段：`1 node_id`、`2 firmware_version`、`3 model`、`4 active_channel_count`、`5 epoch`、`6 has_active_manifest`、`7 last_known_manifest_id`（可选）、`8 proto_version="2.6"`、`9 handshake_nonce`。

字段 6 只反映当前内存中已应用的配置，不等同于 NVS 中保存的上一次 manifest；节点重启后应视作尚未具有活动配置。中心端应结合 epoch、manifest ID 与此字段决定是否立即推送完整清单。

HelloAck 必须包含：`1 server_time_ms`、`2 features`、`3 handshake_nonce`。节点用 server time 建立当前服务器时间估算，供 V2 命令 deadline 校验；nonce 不匹配时节点不进入已握手状态。

### 4.2 StatusReport（0x02）

基础字段为：`1 uptime_sec`、`2 status`（当前实现固定为 `online`）、`3 active_channel_count`、`4 epoch`、`5 sync_state`（0 idle / 1 syncing / 2 error）、`6 manifest_id`、`8 sync_id`。

扩展字段：`7 channel_health` 为有通信错误的通道/边缘设备/命令嵌套记录；`9 runtime_perf` 包含堆内存、栈余量及总线队列聚合指标；`10 control_stats` 包含 ChannelCmdV2 的 accepted、rejected、completed、replayed 计数。中心端应将字段 7–10 作为可选观测数据，缺失不能视为协议错误。

### 4.3 DataReport（0x03）

字段为：`1 channel_id`、`2 timestamp_us`、`3 sequence`、`4 raw_data`、`5 error_code`（可选）、`6 request_id`（可选）、`7 edge_device_id`（可选）、`8 command_index`（可选）、`9 command_template_id`（当前编码实现会携带）。`raw_data` 是现场总线原始响应，不是业务 JSON；中心端按实际设备协议解析，并把错误码和空数据作为一次采集结果保存。

### 4.4 ResourceReport（0x19）

包含平台字符串、资源总数、静态总线/引脚能力、当前启用通道、DMA 分配状态，以及 ChannelCmdV2 引擎能力（包括 `boot_id`、最大批量步骤、最大 TX/读取/超时和重放缓存上限）与配置容量上限。中心端在下发配置前应依据该报告裁剪资源使用；在发送 V2 命令前必须以最新报告确认目标通道已启用且本次 `boot_id` 一致。

## 5. 下行消息（中心端 → 节点）

| 类型 | 名称 | 必填/关键字段 | 节点行为 |
|---:|---|---|---|
| `0x04` | ConfigManifest | `manifest_id`、模板、通道、`sync_id` | 解析、校验、事务化应用，回 `ConfigResult` |
| `0x06` | WriteCmd | `request_id`、`channel_id`、`data`、可选读长/超时/边缘设备 | 写入现场总线并回 `WriteRsp`，兼容路径 |
| `0x08` | Ping | timestamp | 回 Pong |
| `0x0A` | OtaCmd | `ota_id`、URL、checksum、size、version、sequence | 去重/冲突判定后启动 OTA，持续回 OtaProg |
| `0x0D` | ScanReq | request、硬件 ID、地址范围、超时 | 在第一个 UART 通道以 Modbus 03 扫描 1–247，回 ScanRpt |
| `0x0E` | QueryReq | `request_id`、query_type | 执行查询并回 QueryRsp |
| `0x10` | ConfigQuery | `request_id` | 回 ConfigReport |
| `0x12` | HelloAck | server time、features、当前 nonce | 完成当前握手 |
| `0x15` | ChannelCmdV2 | 身份、目标、deadline、TX/RX 参数，可含批步骤 | 严格校验、去重，先 ACK 后 Final |
| `0x1A` | QueryResources | `request_id` | 立即回 ResourceReport |
| `0x1B` | PeriphCmd | request、类型、资源、动作、值/配置 | 异步执行 GPIO/PWM，回 PeriphRsp |

### 5.1 ConfigManifest（0x04）

清单至少必须有非空 `field 1 manifest_id` 和非空 `field 8 sync_id`。节点支持的顶层字段如下：

| 字段 | 内容 |
|---:|---|
| 1 | `manifest_id` |
| 3 | 重复模板：`id`、写入字节、读取长度、延时 |
| 4 | 重复通道：ID、hardware ID、模板 ID、周期、启用状态、bus 类型、bus 配置、DMA 偏好、边缘设备组 |
| 5 | DMA 通道：ID、启用、绑定目标 |
| 8 | `sync_id`，用于本次配置关联与去重 |
| 10 | 日志流配置：enabled、level |
| 11 | GPIO 配置：pin、direction、initial_level |
| 12 | PWM 配置：LEDC channel、pin、frequency、duty（0–10000）、resolution、auto_start |

通道 `bus_type`：1 UART、2 I2C、3 SPI、5 ADC；legacy GPIO 总线类型 4 不接受。固件容量上限为 16 模板、8 通道、每通道 5 个边缘设备、每边缘设备 3 条命令、8 个 DMA 配置、12 个 GPIO 和 8 个 PWM。不要下发超过 ResourceReport/这些上限的清单。

应用顺序是：挂起总线 worker → 暂存和校验新清单 → 停止旧调度 → 快照 → 应用 DMA、外设、总线、调度器、日志流 → 提交活动清单 → 激活调度器。任一步失败将恢复旧运行时；若无法恢复，节点进入安全状态并重启。因而：

- 中心端收到 `success=1` 前不得把清单标为已部署。
- `success=0` 表示节点拒绝或应用失败；保留原配置并根据错误上下文重试或修正。
- 成功结果在同步元数据持久化之后发出，随后节点刷新 ResourceReport。

### 5.2 ChannelCmdV2（0x15）

这是面向可靠现场控制的首选协议。命令身份为 `command_id(16 bytes)`、`payload_digest(16 bytes)`、`attempt`、`boot_id`；目标为 `edge_device_id`、`channel_id`，并携带 `deadline_unix_ms`、`tx_data`、`read_size`、`rx_timeout_ms`、`post_tx_delay_ms`、risk/flags/protocol version 与可选批步骤。

中心端发送前应先完成 Hello（获取服务器时间基准）并收到本次启动的 ResourceReport。节点会对 deadline、目标资源、命令结构和重放记录进行校验，接受后发送 `0x16 ACK`，执行完成后发送唯一的 `0x17 Final`。重投相同身份的命令可能返回已记录的最终结果，`replayed=1`；中心端必须按身份四元组而非仅按 MQTT 投递次数去重。

### 5.3 GPIO/PWM（0x1B）

`PeriphCmd` 的字段为：`1 request_id`、`2 periph_type`（1 GPIO、2 PWM）、`3 resource_id`、`4 action`、`5 value`、`6 config`。操作异步执行，`PeriphRsp` 返回 success、value、error_code、资源与动作；PWM 额外返回 running。中心端应先通过 ConfigManifest 声明可用 GPIO/PWM，并处理“未配置、引脚冲突、资源耗尽、参数错误、硬件错误”等返回码。

## 6. 同步、可靠性与运维约束

- 节点周期性（默认 10 分钟）或在无配置、epoch 落后、manifest 不匹配、用户触发、状态可疑等情形请求同步；同步通过重新发起 Hello 驱动，而不是从 NVS 恢复完整配置。
- NVS 只保存配置同步元数据（epoch、上次 manifest ID），不在启动时恢复活动硬件配置。因此每次重启后中心端都应依据 Hello 推送可运行的完整 ConfigManifest。
- OTA 使用双 OTA 分区。新镜像处于 pending verify 时，必须完成 Wi-Fi、MQTT 和首次 StatusReport 后才确认；连续失败会回滚。中心端应把 `OtaProg` status 0 downloading / 1 completed / 2 verifying / 3 failed 作为状态机输入。
- 物理 BOOT 键长按 5 秒会擦除 NVS 并重启（S3 GPIO0，C6 GPIO9）。清除后 Wi-Fi 凭据和同步元数据丢失，中心端不应依赖旧的活动配置。
- 调试 TCP transport 仅在 `CONFIG_DEBUG_TCP_ENABLED` 时并行开放（默认端口 8088），不是生产后端协议入口；生产交互以 MQTT 为准。
