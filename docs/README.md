### 2026-11-18（**固件型号与节点匹配审计** —— 误刷在哪些组合下会被设备端放过）

- **新增文档**：[分析/固件型号与节点匹配-误刷风险审计-2026-11-18.md](分析/固件型号与节点匹配-误刷风险审计-2026-11-18.md)：用户指出「型号不规范、固件与节点关联有问题、可能误刷」。审计结论是**结构性可达**，不是偶发操作失误。
- **型号真实语义**：设备上报的是 `CONFIG_IDF_TARGET`（`esp32c6`/`esp32s3`，PSRAM 探测成功才加 `p`），6 个构建档位只产生 3 个型号值，**Flash 容量在型号里不可见**；服务端每次 Hello 直接覆盖 `nodes.model`，全仓**零消费**；前端 `MODEL_NAMES` 只覆盖 S3/S2/C3，`collectorModel` 是死参数。
- **关联层缺失**：建任务只收 `node_id` 与 `firmware_id`；`CreateTask` 连节点都不查；`OtaCmd` 仅 6 字段、无任何硬件身份，且设备端对未知字段 fail-closed ⇒ **不能加字段**。
- **误刷后果分级**：跨芯片（C6↔S3）会被 `esp_ota_end` 的 chip_id 校验干净拒绝；**s3 与 s3p 互刷镜像头无法区分**（同 0x0009、同 flash），会刷入成功，叠加「回滚未武装」后**不可自愈** —— 这是唯一 P0 组合。
- **可立即修复的抓手**：镜像头自带身份（0x00 magic、0x03 高 4 位 flash、0x0C chip_id、0x20 起 app descriptor 含 version/project_name/elf_sha256），四份真实产物实测全部可离线解析；上传时解析即可消除「人手填版本与型号」。
- **分期**：P0 上传解析 + 唯一约束（1–2 人日）；P1 建任务闸门 + 前端置灰 + 成功判定加固；P2 固件上报硬件 profile 后开放自动升级。

### 2026-11-18（**版本与更新机制分析** —— 三条更新链路的可复用性判定，仅分析不实现）

- **新增文档**：[分析/版本与更新机制-自更新设计可复用性分析-2026-11-18.md](分析/版本与更新机制-自更新设计可复用性分析-2026-11-18.md)：以外部样例（Windows 桌面自更新）为参照，判定哪些机制可迁移到本仓库的**三条替换链路**（设备固件 / 服务端镜像 / Web 前端）。

### 2026-11-11（**长窗图表全坏事故修复** —— rollup 回填帧预算选错常量）

- **新增文档**：[分析/长窗图表全坏事故分析-2026-11-11.md](分析/长窗图表全坏事故分析-2026-11-11.md)
- **现象**：BMS 详情页 3 条图表报错（24h SOC/电流、24h 温度趋势、30d 保护历史），影响所有设备所有 >6h 窗口 —— 用户**完全看不到历史趋势**。
- **根因**：`cmd/server/main.go` 的 rollup 回填把 `DecodeRangeAnchoredBounded` 第 8 个参数（**扫描预算**）传成了 `MaxDecodeFrames`（32,768，语义是「一次性解码单批上限」），而不是 `MaxScanFrames`（262,144）。生产 dev14 在 2026-11-08 15:57 ~ 11-10 05:21 之间**没有关键帧**，回填 11-10 每段都要从 32 小时前的锚点预热 ≈ 118,922 帧 ⇒ 超预算 ⇒ `FramesTruncated>0` ⇒ 该单元标 `partial` ⇒ 读路径判定「覆盖未验证」⇒ 图表报错。**而底层 rollup 数据是齐的**（1439 个分钟桶）。
- **为什么难发现**：报错文案是「超过帧表单次解码上限」，指向「数据太多」，实际是「预算太小」。且 `partial` 是**粘性**状态 —— 只有回填能改写它，而回填每次都被同一原因打断，**自愈不可能**。
- **修复**：导出 `telemetry.MaxScanFrames` 并改用它；**修正原注释**（原文断言「段宽 1h × 1fps = 3,600 帧，远低于上限，这个分支在生产不会触发」—— 错，漏算了锚点预热段）。生产只读验证：同一段旧预算 `points=0 truncated=86154`，新预算 `points=104400 truncated=0`。
- **上线结果**：常规滚动升级（无数据迁移），停机约 40 秒。回填只重跑 1 个单元（dev14/2026-11-10，其余 439 个已 complete），写 1440 个分钟桶，`errors=[]`。coverage `partial`→`complete/1440`，全局 `partial=0`。
- **验证**：dev14 图表 1h/6h/**24h**/**168h**/**720h** 全部 200（24h 497 点、7d 500 点、30d 403 点）；change 模式长窗 30d 1199 点；BMS 页失败提示 **0 条**（修复前 3 条），9 个 canvas 全部渲染，保护历史显示「86 次触发」。
- **防复发**：新增 `internal/telemetry/scan_budget_gate_test.go`（3 条用例）—— ① `MaxScanFrames` 必须覆盖最坏锚点跨度（37h+6h @1Hz = 154,800 帧）；② 反向断言 `MaxDecodeFrames` **覆盖不了**该跨度（把「为什么不能合并这两个常量」写进测试）；③ 锁住 8 倍关系。
