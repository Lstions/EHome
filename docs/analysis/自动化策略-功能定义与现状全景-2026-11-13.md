## 0. 结论摘要

1. **引擎主体是完整的**：`sensor_threshold` / `time_window` / `sun_event` 三类触发器全链路可用（求值 → 规划 → 执行 → 审计 → 保留）；`event` 仍是占位。
2. **产品定义与实现的差距不在「能不能跑」，而在「语义边界没被界面表达出来」**：附加条件只在 `sensor_threshold` 触发期求值；`literal` 选择器绕过 `value_type` 门禁；动作级 `enabled` 只存不用。
3. **交互层已经完成从「手输」到「选择」的迁移**：旧版 26 个表单项里 6 项「系统内有权威候选却要手打」全部接上（字段目录 / 词表 / 试算 / 动作目录 / 参数 schema / 时区）；剩余手输项是经纬度与高级 JSON 两种「确实没有候选」的场景。
4. **数据依赖是「帧驱动」而不是「表查询驱动」**：求值只消费本帧解析后的字段，`sensor_field_obs` 只做目录与展示，不进热路径。这条口径决定了「为什么告警能用、自动化也能用，但字段类型陷阱只在 family 路径暴露」。
5. **三张表撑起全部语义**：`automation_rules`（规则，30+ 列）+ `automation_rule_actions`（多动作，子表权威、单动作列降级为镜像）+ `automation_events`（17 个结果码的执行审计）。
6. **生产尚未使用**：`automation_rules` / `automation_events` / `automation_rule_actions` / `alert_rules` 均 0 行；`sensor_field_obs` 71 行、`sensor_field_meta` 71 行。功能改造的零迁移窗口仍然成立。
7. **有三处「静默」风险需要产品级裁决**：动作级 `enabled` 不生效（禁用动作仍执行）、保存期不校验 `conditions_json` 结构（非法 JSON 只能运行期 Warn）、`literal` 路径不做类型门禁（能选中即死）。
8. **前端两处「看得见但不完整」**：保存失败只显示固定文案「保存失败」（后端 400 原文不呈现）；事件结果筛选缺 3 个 `source_*` 码。
9. **保留策略按结果码白名单分层**（遥测 30 天 / 执行 400 天），但白名单外的诊断码永不清理，长期会单调增长。
10. **事件驱动的前置条件不是代码而是语义冻结**（事件词表 / 触发证据列 / 不补触发 / 幂等），冻结稿 1 页，v1 估 3–4 人日。

## 1. 产品功能定义

### 1.1 一句话定位

> 一条策略 = 1 个触发器 + 0..N 个附加条件（全部 AND）+ 1..N 个动作 + 执行约束。触发 ≠ 执行：触发器只回答「条件是否满足」，由 Planner 决定「这次到底执行不执行」。

设计上的三条硬边界（`docs/设计/自动化策略引擎方案.md:51-68`）：

| 边界 | 含义 | 现状 |
|---|---|---|
| 求值在后端 | 边缘设备是透明执行者，不感知策略 | 成立 |
| 动作唯一入口 | `device_action` 必须走 `commandexec.Service.Create`（9 项 availability gate + 幂等 + 审计 + verify），禁止直连 `SendPeriphCmd` / 裸 MQTT | 成立（`planner.go:425-440`） |
| 声明式条件 | 只支持比较 + AND，不做脚本 / 表达式 / workflow | 成立 |

### 1.2 触发器（4 类，3 类可用）

| 类型 | 语义 | 驱动方式 | 关键参数 | 边界语义 | 状态 |
|---|---|---|---|---|---|
| `sensor_threshold` | 字段比较，连续满足 `duration_sec` 后触发 | 数据驱动：每个解析帧回调一次 | `trigger_sensor_name`（selector）、`comparator`、`threshold`、`duration_sec`、设备或来源组 | `duration=0` 首个满足帧立即触发；冷却期内窗口冻结 | 可用（`evaluator.go:986-1089`） |
| `time_window` | 每天固定 `HH:MM` 区间的进入 / 离开 / 区间内 | 时钟驱动：1 分钟 ticker | `window_start`、`window_end`、`window_edge ∈ enter/exit/inside` | 跨零点支持；`start==end` 视为全天；重启后 enter 首 tick 在窗内即触发、exit 不补触发 | 可用（`evaluator.go:830-889`） |
| `sun_event` | 日出 / 日落时刻 ± 偏移分钟 | 时钟驱动：同一个 1 分钟 ticker | `sun_kind ∈ sunrise/sunset`、`sun_offset_min ∈ [-720,720]`、坐标/时区（规则级可覆盖节点级） | 每本地日只触发一次；首 tick 对已过事件保守跳过；极昼/极夜落显式审计 | 可用（`evaluator.go:657-750`） |
| `event` | 节点上下线、告警 firing 等系统事件 | 无 | 无专属字段 | 语义未冻结 | **仅占位**（`models/automation.go:22`） |

补充两点产品语义：

1. **时间窗口不是 cron 轮询**：它是「每分钟检查一次边沿」，触发点由本地时间决定，节点离线时照常求值，执行阶段被 `node_status` gate fail-closed 拦截。
2. **触发器类型不是运行期分派键**：`sensor_threshold` 走数据路径，`time_window` / `sun_event` 走时钟路径，两条路径由不同的入口进入，而不是「一个 evalRule 里 switch」。这正是 `event` 规则「有类型、无路径、所以必须禁创建」的原因。

### 1.3 附加条件（0..N，全部 AND）

```
conditions_json = [{ "sensor_name": "temperature_2", "comparator": "gt", "threshold": 45 }, ...]
```

| 维度 | 定义 | 证据 |
|---|---|---|
| 结构 | 扁平数组，每项 3 个业务字段（`sensor_name` / `comparator` / `threshold`）；无嵌套、无 OR、无 NOT、无时序算子 | `models/automation.go:141-145` |
| 算子 | `gt / gte / lt / lte / eq / neq`；未知算子 fail-closed 返回 false | `evaluator.go:1128-1150` |
| 选择器 | 条件项与触发器共用同一 selector 契约：字面量 / `prefix_*:agg` / `@semantic` / `virtual:` | `evaluator.go:1026-1030`、`selector.go:202-259` |
| 空条件 | 视为「无条件」，循环零次直接 true | `evaluator.go:1025-1034` |
| 非法 JSON | 运行期 Warn + 不触发；执行前复核期落 `condition_changed` | `evaluator.go:1019-1024`、`source_f4.go:131-134` |
| 求值时机 | **仅 `sensor_threshold` 在触发期求值**；`time_window` / `sun_event` 触发期不求值，其存量条件只在**执行前 F4 复核**时作为闸门参与（且仅当动作集合含 `device_action`） | `evaluator.go:994/1010`、`planner.go:223-234`、`source_f4.go:167-190` |
| 保存期校验 | **不校验**结构（只有 precheck 会 `json.Unmarshal` 一次），Create/Update 直接写库 | `handler_automation.go:1391-1400`、`:334`、`:642-644` |

> 设计取舍（不是遗漏）：时钟类规则在 UI 上**不渲染条件编辑器**；若该规则存量带条件，只显示一行「当前触发类型不会求值」的提示（`ConditionEditor.vue:117-127`），保存时按原值保留。后端 precheck 同样只对 `sensor_threshold` 做 selector 诊断（`handler_automation.go:1385-1387` 注释）。
>
> 隐患只有一条：API 直连可以写出一条「时钟触发 + 有条件」的规则，这些条件只在执行前 F4 复核时生效——语义成立，但与 UI 表达不一致（见 §4.8 B3）。

### 1.4 动作（1..N，串行）

| 维度 | 定义 | 证据 |
|---|---|---|
| 类型 | `device_action`（受控命令链路）/ `notification`（纯通知，退化告警） | `models/automation.go:37-40` |
| 权威存储 | `automation_rule_actions` 子表（`rule_id + seq` 唯一），`automation_rules` 的 5 个动作列降级为只读镜像 | `models/automation.go:377-403`、`database/automation_rule_actions.go:53-65` |
| 顺序 | `seq` 升序串行；第 k 个失败即中止剩余动作 | `planner.go:378-380`、`:407-457` |
| 部分失败 | 写 `partial_failure` + `action_seq=k`，并**不写冷却锚点** | `planner.go:484-490`、`:358-364` |
| 幂等键 | `automation:<rule>:<yyyymmdd>:<triggerSeq>:<actionSeq>` | `planner.go:421-422` |
| 动作级开关 | 子表有 `enabled` 列，落库、回显、参与比较，但**执行循环不检查** | `models/automation.go:396-398`、`planner.go:407-457` |

### 1.5 执行约束（触发 ≠ 执行）

Planner 的固定检查顺序（自动路径）：**日熔断 → 规则级确认 → F4 条件复核 → 动作循环**（`planner.go:188-234`）。

| 约束 | 语义 | 默认 | 异常落库 | 证据 |
|---|---|---|---|---|
| `cooldown_sec` | 上次**触发**后 N 秒内不再触发；到期即回 armed（不等条件复位） | 创建时 300s | `suppressed_cooldown`（同冷却窗只落首条） | `evaluator.go:40-46`、`:1048-1058`、`:1091-1110` |
| `max_daily_exec` | 按触发时刻的本地日统计 `executed`，0 = 不限 | 0 | `suppressed_daily_limit` | `planner.go:188-196`、`:1162-1174` |
| `require_confirmed` | 只落 `pending_confirm` + 通知，人工确认后才下发 | false | `pending_confirm` / 24h 后 `expired` | `planner.go:205-213`、`:1586-1617` |
| 风险动作授权 | 风险动作 + 未授权 + 不要求确认 ⇒ 保存期 400；授权列 `risk_acknowledged_at`，动作集合变更即清空 | NULL | `confirmation_required` | `handler_automation.go:1043-1090`、`commandexec/service.go:536-551` |
| 冷却锚点 | 持久列 `last_triggered_at`（触发时刻），与事件表物理解耦，避免「删审计改行为」 | NULL | — | `models/automation.go:282-300`、`planner.go:553-557` |

`duration_sec` 只对 `sensor_threshold` 生效：`>0` 要求窗口内**所有**样本满足且跨度 ≥ duration；`=0` 只保留最新样本、首帧即触发。`time_window` / `sun_event` 上的 `duration_sec` 无校验也无使用。

### 1.6 审计与结果码（17 个）

`automation_events` 一行 = 一次触发决策，回填 `command_id` 关联 `command_executions`。结果码分五族：

| 族 | 取值 | 语义 |
|---|---|---|
| 执行 | `executed`、`partial_failure`、`notification` | 成功 / 部分成功 / 纯通知 |
| 抑制 | `suppressed_cooldown`、`suppressed_daily_limit`、`suppressed_no_solar_event` | 冷却、日熔断、极昼极夜 |
| 待办 | `pending_confirm`、`expired` | 等待确认 / 超时 |
| 失败与配置 | `condition_changed`、`failed_gate`、`failed_dispatch`、`confirmation_required`、`unresolved_selector`、`field_resolver_disabled` | 条件失效 / 门禁 / 下发 / 确认门 / 选择器 / 解析层开关 |
| 来源组 | `source_member_changed`、`source_stale`、`source_degraded` | 成员变化 / 证据过期 / 降级求值 |

三向一致性门禁：`models` 常量 == `simulation/catalog/audit.go` 白名单 == 前端 `AutomationEventResult` 联合类型（`backend/internal/models/automation_result_threeway_test.go`）。

### 1.7 明确非目标（设计裁决，不是遗漏）

- 不做边缘自治（断网兜底属后续演进）；
- 不做脚本 / 任意表达式；
- 不做跨设备编排（workflow 引擎）：跨设备场景由多条独立规则表达；
- 不改变告警语义（`alert_rules` 行为不变，两套并存）；
- 不做 cron 式主动轮询（时间维度由 ticker + 窗口表达）。

### 4.5 字段类型如何进入求值

```
sensor_field_meta.value_type
   ├─ number（或未知） → 参与数值比较
   └─ boolean / enum / bitmask / string / raw → fieldNumeric=false
          ├─ family / semantic / virtual 路径：该成员视为缺失 → partial_frame / unbound → 规则不触发 + 审计
          └─ literal 路径：matchField + compare **不看类型** → 照常比较（H3）
```

## 6. 产品视角：用户现在能做什么 / 不能做什么

**能（`2fbdecce` 代码，部署后生效）**

- 用「选择」而不是「手打」创建三类规则：设备 → 字段（中文名 + 单位 + 最近上报）→ 比较 → 阈值 → 时长；
- 时间窗与日出日落用控件配置，坐标 / 时区可继承节点；
- 用条件行表达复合条件（仅传感器阈值规则参与触发期判定）；
- 多动作串行，按目录选动作、按 schema 填参数，风险动作逐项勾选确认；
- 保存前看到阻断 / 警告、24h 试算结论、风险清单；
- 事件按规则 / 结果筛选、分页、查看命令详情、确认待确认事件、手动触发。

**不能**

- 不能用系统事件触发（节点上下线 / 告警 firing / 命令终态）；
- 不能让「时间窗口 / 日出日落」与附加条件形成联合判定；
- 不能单独禁用某个动作（列存在但不生效）；
- 不能在保存失败时看到后端给出的具体原因；
- 不能按时间范围筛选事件，也不能看到来源成员快照与第几个动作失败；
- 不能用 `virtual:` 派生量（后端支持、前端未开放）；
- 不能用告警联动设备动作（告警只能发通知）。
