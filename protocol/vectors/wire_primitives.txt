# EHomeSystem 3.0 线路格式 golden vector（S0：冻结契约）
#
# 为什么存在这个文件（设计文档 §3 迁移路径 S0）：
#   ESP32 端（components/msgcodec）与后端（backend/pkg/frame）是【两套独立实现】，
#   各自带着各自的黄金向量。两端可能【同时自洽却互相不通】——
#   这正是 S0 要在任何重构之前拦住的事：设计原文为
#   "必须先有 S0 契约，否则重构中两端会各自漂移"。
#
# 本文件是【唯一】的向量来源。三处独立校验：
#   - 后端 Go：backend/pkg/frame/golden_vectors_test.go（解析本文件）
#   - ESP32 C ：host_tests/golden_vectors_tests.c（解析本文件）
#   - 独立第三份实现：esp32-collector/tools/check_golden_vectors.py（Python）
# 任何一端改了编码而本文件不变 ⇒ 那一端变红。
# 要改格式，必须【同时】改本文件与两端实现，并在提交信息里说明。
#
# 语法（刻意极简、语言中立）：
#   #  注释
#   case <名字>           开始一个用例
#   type <u8 十进制>      消息类型字节（帧首字节）；子结构用 sub
#   u64 <字段号> <值>      varint 字段（十进制，最大 2^64-1）
#   bytes <字段号> <hex>   长度定界字段（十六进制；空用 -）
#   wire <hex>            期望编码结果（唯一权威）
#   end                   结束该用例
#
# 重要：本文件的 wire 值【不允许手写】，必须由实现生成后再粘入。
#   2026-10-06 第一版手写了 12 条，Python 门禁当场抓出 9 条错
#   （字段号 2 写成 tag 0x02、类型字节错、长度前缀错、128 字节写成 130 字节）。
#   本版全部 wire 由 encode_case() 生成。

# --- 基线：直接取自后端既有 Go 测试 TestLegacyWriteCmdGoldenVector ---

end

# --- v3.0 远程运维（0x22 下行 / 0x23 上行）---
#
# ⚠ 这一组是本文件**存在理由**的直接体现：
#   后端 Go（pkg/frame/device_op_wire.go）与固件 C（handler_device_op.c）
#   各自独立实现了同一份字段约定，而两边**从未在真实链路上对话过**。
#   两端各自单测全绿、合起来却不通 —— 正是 S0 要在重构中拦住的事。
#   加进本文件后，Go 测试、C 宿主测试、Python 门禁会**各自独立**校验同一串字节。
#
# 字段约定（两端必须一致）：
#   0x22 下行：field 1 op_code(varint)、field 2 request_id(bytes)
#   0x23 上行：field 1 result_code(varint)、field 2 request_id(bytes)、field 3 detail(bytes, 可选)
#
# request_id 故意选 10 字节（op-node1-1）：长度前缀 0x0a 与单字节值能区分开，
# 若有人把长度前缀写成定长或漏掉，这里会红。
# 最后一条用 result=9（未定义码）：**未知结果码必须原样保留数字**，
# 折叠成某个已知值就等于把"设备比服务端新"误报成"操作失败"。
