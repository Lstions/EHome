# ESP32-S3 UART0（TX43/RX44）+ ADUM1201 通讯验证

> 状态：**已实测**（2026-10-02）；方法：PC 侧 CP2102(COM5) 注入 JBD 响应帧，
> 以生产服务端（`192.168.20.6:18090`）的 `device_data` 落库与 `edge_devices` 状态为判据。
> 被测链路假设：`ESP32-S3 UART0(TX43/RX44) → ADUM1201 → CP2102 → PC(COM5)`，
> 即 COM5 位于 ADUM1201 的隔离侧，**双向数据均穿越 ADUM1201**。

## 1. 结论

| 方向 | 路径 | 结果 |
|---|---|---|
| ESP32 → PC | UART0 TX(43) → ADUM1201 → COM5 RX | ✅ 通 |
| PC → ESP32 | COM5 TX → ADUM1201 → UART0 RX(44) → MQTT → 服务端 | ✅ 通 |

**ADUM1201 双通道均正常，ESP32-S3 UART0 收发链路可用。**

## 2. 被测对象

| 项 | 值 |
|---|---|
| 节点 | `30EDA0A9A808`（ESP32S3，固件 2.5.28，协议 2.6） |
| 通道 | `channel_id=2`，`UART0`（`hw_tables.c`: S3 UART0 = TX 43 / RX 44） |
| 设备 | `edge_device id=2` `BMS-UART0`（`jiabaida_bms`，间隔 5000ms） |
| PC 侧 | COM5 = Silicon Labs CP210x (USB\VID_10C4&PID_EA60) |
| 串口参数 | **9600 8N1**（由实测帧自证，非假设） |

## 3. 关键判据：为什么"发一帧看回没回"会误判

ESP32 对带 `read_size` 的命令**只在攒够该长度时才上报**：

```c
/* bus_worker.c:818-822 — 需 10ms 空闲且 len >= expected(=read_size) */
if (len > 0 && state->last_rx_us > 0 &&
    esp_timer_get_time() - state->last_rx_us >= 10000) {
  *out_len = len;
  return expected == 0 || len >= expected;
}
```

JBD `read_basic_info` 的 `read_size` 是 **60**（`jiabaida_control.go` 回读步骤）。
本剧本首次注入 36 字节帧 → **无任何反应**；补足到 **60 字节** → **立即生效**。
故"响应长度必须 ≥ 命令的 read_size"是本次验证的核心约束。

## 4. 证据

### 4.1 ESP32 → PC（TX43 方向）

9600 下 12s 抓到 2 帧，**长度恰为 7 的倍数**、周期 **≈5.00s**（与通道 `interval_ms=5000` 一致）：

```
dda50300fffd77   dda50300fffd77     ← JBD 读基本信息轮询，间隔 5.000s
```

同端口 115200 下同窗口抓到 48 字节全 `0x00`（乱码），**不构成有效帧** —— 反证 9600 才是真实波特率。
（CP210x 在 115200 无训练数据时输出前导 0，属桥接器空载噪声。）

### 4.2 PC → ESP32 → 服务端（RX44 方向）

同步到 ESP32 自身轮询帧后再应答（避免碰撞），注入 60 字节 JBD 0x03 响应：

```
dd030035 14c8 00fa 2710 2710 000c 0000 0000 0000 0001 64 03 1e 0f 0ba5×15 f296 77
```

服务端落库（`edge-device id=2` 的 `device_data`）：

| 记录 | 原始帧前缀 | total_voltage | current | remaining_capacity | rsoc |
|---|---|---|---|---|---|
| 7370–7390（9 条） | `dd03003514…` | **53.20 V** | **2.50 A** | **100.00 Ah** | 100 % |
| 7414–7424（6 条，换值复测） | `dd03003512…` | **48.50 V** | **-1.25 A** | **77.00 Ah** | 77 % |

**字节级闭合**：`14c8`=5320→53.20V、`00fa`=250→2.50A、`2710`=10000→100.00Ah、
`0ba5`=2981→24.95°C（×15 温度点全部解析）。第二组换成 `12f2`/`ff83`/`1e14` 后读数同步改变，
排除了"读到旧值/缓存"的可能 —— 数据确实由本次注入产生并经 ESP32 上行。

### 4.3 状态面佐证

- `last_data_at`: `null` → `2026-10-02T09:08:06Z`（注入窗口内）
- `status`: 注入期间由 `offline` 翻回 `active`（`09:10:26` 仍在收数）
- 停注 ~5s 后自动回落 `offline` —— 与"停止应答即无数据"完全一致
- 复测共落库 **17 条**，时间戳间隔 ≈5.00s，与轮询同频

## 5. 重要发现（非本次链路故障）

### 5.1 服务端「通道终端」在生产上被关闭

`raw_diagnostics_enabled=false`（`backend/config.yaml:21`），生产实测：

| 入口 | 返回 |
|---|---|
| `GET /api/v1/channels/2/terminal` | `410 raw terminal diagnostics are disabled` |
| `POST /api/v1/channels/2/terminal/write` | `410 raw terminal writes are disabled` |
| `POST /api/v1/channels/2/write` | `410 raw channel writes are disabled` |
| `WS /api/v1/ws/terminal` + `send` | `{"type":"error","message":"raw terminal writes are disabled; use an audited diagnostics service"}` |

这是**设计上的安全闸门**（未审计 raw 写默认关闭），本次验证未绕过它。
因此本次不能走「通道终端」页面，而改用 MQTT 上行 + 落库作为判据 —— 判据更强（端到端、可复核）。

### 5.2 `error_code=3` 会粘住

设备长期显示 `error_code=3`（命令超时）。固件只在"命令出错"时才把设备放进
`StatusReport.EdgeDeviceHealth` 子帧，恢复后该子帧消失、服务端收不到显式"已恢复"信号。
后端已有补偿（`consumers_heavy.go:404-418`：成功采样即清零），但本次注入的
`device_data` 走的是**非 `IsScheduledSample` 路径**，故 `error_code` 未清零。
⇒ 若要让它归零，需让**周期性采样**（而非单次回读）拿到响应。

### 5.3 无设备应答的样本不落库

30s 无注入时 `device_data` 计数不变（0 条），确认判据无假阳性：
**没有注入就绝对没有数据**。

## 6. 复现步骤

```python
import serial, time
# 1) 构造恰好 60 字节的 JBD 0x03 响应（LEN=53）
def cks(b): return ((~(sum(b) & 0xFFFF)) + 1) & 0xFFFF
LEN = 53
data  = (5320).to_bytes(2,'big')      # 53.20 V
data += (250).to_bytes(2,'big')       # 2.50 A
data += (10000).to_bytes(2,'big')*2   # 容量
data += (12).to_bytes(2,'big')        # 循环次数
data += b'\x00\x00'*4                # 日期/均衡/保护
data += bytes([1,100,3,30,15])        # 版本/RSOC/FET/串数/NTC数
data += (2981).to_bytes(2,'big')*15   # 15×温度
frame = bytes([0xDD,0x03,0x00,LEN]) + data \
      + cks(bytes([LEN])+data).to_bytes(2,'big') + bytes([0x77])
assert len(frame) == 60

# 2) 同步到 ESP32 自己的轮询再应答（9600 8N1，DTR/RTS 勿拉高）
POLL = bytes.fromhex('dda50300fffd77')
s = serial.Serial(port='COM5', baudrate=9600, timeout=0.02, dtr=False, rts=False)
buf = bytearray()
while True:
    buf.extend(s.read(512))
    if POLL in buf:
        i = buf.find(POLL); del buf[:i+len(POLL)]
        time.sleep(0.04)          # 让 TX 完全静默后再驱动总线
        s.write(frame); s.flush()
```

判据：`GET /api/v1/edge-devices/2/data` 出现 `dd030035…` 且
`total_voltage=53.2`、`current=2.5`，`last_data_at` 刷新。
