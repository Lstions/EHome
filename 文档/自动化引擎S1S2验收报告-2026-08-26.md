## 修复的设计/实现 bug（全部代码层）

### Bug 1: nodemgr setter 时序（**自动化引擎从未生产**）

**位置**: `backend/internal/nodemgr/manager.go`

**现象**: 自 6262d67d (2026-08-21) 引入 alert 引擎起，alert + automation 引擎在生产环境**从未真正工作过**。

**根因**: `NewManager()` 在构建 sensor_parser consumers 时读取 `mgr.alertEvaluator` / `mgr.automationEvaluator`，但这两个字段是 main.go 在 `NewManager` 之后调用 `SetAlertEvaluator()` / `SetAutomationEvaluator()` 才赋值的——consumers 拿到的 sink 永远是 nil。单测全绿是因为单测直接调 `Evaluate()` 绕过了接线。

**修复**:
- `Manager` 持有 `parserConsumers []*databus.SensorParserConsumer` 引用
- 三个 setter（`SetLatestSinkFn`/`SetAlertEvaluator`/`SetAutomationEvaluator`）在赋值后**同时推送 sink 到所有已构建的 consumers**

**测试证据**: 修复后 `Manager.Start: automationEval_nil=false alertEval_nil=false`（修复前两者皆 true）。

### Bug 2: latest_value_cache 缓存键错误（**F4 条件复核永远失败**）

**位置**: `backend/internal/api/latest_value_cache.go`

**现象**: 自动化 planner 的 F4 条件复核永远返回 `latest value unavailable`，规则触发但执行被拒。

**根因**: `SetLatestValue` 检查 `rec.EdgeDeviceID == nil`，但 `unified_data.edge_device_id` 字段是 NULL（写入路径只填了 `DeviceID`，v2.2 注释明确 `DeviceID` 即 edge_device_id 语义）。

**修复**: 改用 `DeviceID` 作为缓存键（与 unified_data 实际写入对齐），`WarmupLatestValues` 的 SQL 同步改为 `DISTINCT ON (device_id)`。

**测试证据**: 修复前 `latest value unavailable for edge_device_id=7053`，修复后规则正常 executed。

### Bug 3: dispatcher channel 锁不区分 transport（**PeriphCmd 永远失败**）

**位置**: `backend/internal/commandexec/dispatcher.go`

**现象**: 自动化 GPIO 命令的 `command_executions.status=FAILED, final_reason='deadline expired before dispatch'`，`command_outboxes.state='CANCELLED'`。

**根因**: dispatcher 在 dispatch 前用 `execution.channel_id` 去 channels 表加锁，periph 动作（gpio_set）的 `channel_id=0` → `record not found` → 任务卡 QUEUED 直到 deadline。

**修复**: dispatcher 在锁 channel 前判断 `deviceaction.IsPeriphAction(execution.ActionID)`，periph 跳过 channel 锁（periph 是节点级资源，无物理 channel 互斥语义）。

**测试证据**: 修复前 `lock command channel: record not found`，修复后 PeriphCmd 正常 DISPATCHED。

### Bug 4: commandexec 缺 system actor 概念（**自动化引擎被 confirmation 拦截**）

**位置**: `backend/internal/commandexec/service.go`

**现象**: 自动化 planner 调 `Create` 落 `failed_dispatch: confirmation is required`，因为 `gpio_set` 是 medium risk。

**根因**: commandexec 的 `confirmationRequired()` 对 medium+ 全部强制 confirmation token，未区分调用方是用户还是系统内部。

**修复**:
- `CreateInput` 加 `ActorKind` 字段（`ActorKindUser`/`ActorKindSystem`）
- 确认制门禁改为：`high`/`critical` 一律须 confirmation；`medium` 仅人工路径须 confirmation；`low` 仍不需
- audit `ActorType` 用 `actorTypeForAudit()` 映射（空/未知 → user，system → system）
- `automation/planner.go` 的 `executeDeviceAction` 传 `ActorKind=ActorKindSystem`

**测试证据**: 新增 4 个用例全过；端到端 S1 完整跑通。

### Bug 5: 模拟器资源上报缺 buses/channels blob（**ChannelCmdV2 无法通过 capability 校验**）

**位置**: `scripts/esp32_simulator.py`

**现象**: `ConfirmEvent` 报 `currentCapabilities: node command capability is absent or stale` → `applied_manifest` gate 失败。

**根因**: simulator 的 ResourceRpt (0x19) 缺少 field 3 (buses blob) 和 field 4 (channels blob)。

**修复**: 补全 buses blob (UART entry + GPIO entry) + channels blob (channel_id=2, bus_type=UART, hw_id=0) + command_engine 子消息。

**测试证据**: `ResourceReport decoded: 1 uart, 1 gpio, 1 channels`，capability 校验通过。

### Bug 6: 模拟器 PeriphRsp 缺 field 7 (action)

**位置**: `scripts/esp32_simulator.py`

**现象**: 后端报 `PeriphRsp missing required field 7`。

**根因**: PeriphRsp 必备字段：1=request_id, 2=success, 5=periph_type, 6=resource_id, **7=action**。模拟器漏了 action。

**修复**: 应答中加 `ev(7, action)`。

### Bug 7: 模拟器 ChannelCmdV2 应答格式错误（**batch envelope 协议**）

**位置**: `scripts/esp32_simulator.py`

**现象**: 后端报 `ChannelCmdV2 final verification failed: batch envelope: invalid step count`。

**根因**: `set_mos_policy` 是 `bounded_sequence`（write 0xE1 + readback 0x03 两个 step），后端期望**单帧 batch envelope**：`N(1B) + per step kind(1B) + length_le(2B) + response bytes`。模拟器只回了单帧嘉佰达响应。

**修复**:
- 解析 field 15 (repeated Plan 子消息) 提取每个 step 的 tx_data
- 逐 step 执行业务（区分 write `0x5A` / read `0xA5` 方向）
- 打包 batch envelope: N + per step (kind, length_le, response)

### Bug 8: 模拟器 MOS 写帧语义错位（**fet_status 反向**）

**位置**: `scripts/esp32_simulator.py`

**现象**: `jiabaida set_mos_policy readback mismatch: fet_status=0x01 charge bit=1 want 0 discharge bit=0 want 1`。

**根因**: 嘉佰达 E1 写帧 bit0=charge_close / bit1=discharge_close，但 readback 的 fet_status bit0=charge_open / bit1=discharge_open（**反向**）。模拟器把 close_bits 直接当 fet_status 用。

**修复**: `fet_status = (~close_bits) & 0x03`。

**测试证据**: write `close_bits=0x01` → readback `fet_status=0x02` → readback 校验通过。

## 端到端验收证据

### S1: rsoc < 50 → GPIO pin 5 高电平（全自动，无确认）

**规则**: id=1, `trigger_edge_device_id=7053, sensor=rsoc, comparator=lt, threshold=50, action=gpio_set(pin=5, level=1), cooldown=5s, require_confirmed=false`

**持续证据** (simulator `--rsoc 4 --interval 30` 跑 ~2 分钟)：

```
21:33:52  PeriphCmd req_id=907664148 GPIO[5] -> 1 / PeriphRsp success=1
21:34:22  PeriphCmd req_id=907664149 GPIO[5] -> 1 / PeriphRsp success=1
```

每次 rsoc=4 上报 → 触发 → executed → DISPATCHED → PeriphCmd 0x1B 实发 → 模拟器回 PeriphRsp success → command_executions 落 SUCCEEDED。

**automation_events** (rule_id=1)：

| id | result | command_id | trigger_value |
|---|---|---|---|
| 214 | executed | ... | 4 |
| 212 | executed | ... | 4 |

**command_executions**：

| command_id | action_id | status | actor_user_id | idempotency_key |
|---|---|---|---|---|
| f8520504-... | gpio_set | DISPATCHED | 1 | automation:1:20260826:N |

**审计**: `security_audit_events.actor_type=system, event_name=device_action.created, result=queued`

**幂等键**: `automation:1:20260826:1`, `:2`, ... 序号正确递增（每日序号单调）。

**冷却抑制**: 冷却期内（5s）再触发 → `suppressed_cooldown` 落事件，无 command 下发。

### S2: rsoc < 10 → set_mos_policy（高risk，确认制闭环）

**规则**: id=3, `trigger_edge_device_id=7053, sensor=rsoc, comparator=lt, threshold=10, action=set_mos_policy(charge_closed=true, discharge_closed=false, priority=user), cooldown=5s, require_confirmed=true`

**链路证据** (event id=211)：

1. rsoc=4 < 10 → 规则触发 → `pending_confirm` 落事件
2. Notification 落库: `source=automation_rule, source_id=3, message 含 event_id=211`
3. 调 confirm API: `POST /api/v1/automation-events/211/confirm {"reason":"verify S2"}`
4. IssueConfirmation 通过（capability 校验）
5. Create + ConfirmationToken 消费 → command_executions 落 QUEUED
6. Dispatcher 取出 → ChannelCmdV2 0x15 实发（plan_steps=2: write_mos + readback_fet）
7. 模拟器收到 `>> ChannelCmdV2 edge=7053 ch=2 tx=dd5ae1020001ff1c77 plan_steps=2`
8. 模拟器执行 + 回 batch envelope (`02 01 07 00 dde10000000077 02 26 00 dd03001f...`)
9. 后端解析 batch envelope → readback fet_status=0x02 → 与期望 (charge_closed → bit0=0, discharge_open → bit1=1) 匹配
10. `command_executions.status=SUCCEEDED, final_reason=final_succeeded`

**数据库证据**:

```
command_id                              | action_id      | status    | final_reason
ab55bb50-edc0-4669-89ef-71a550301242 | set_mos_policy | SUCCEEDED | final_succeeded
```

**模拟器业务状态**:

```
BMS MOS set: close_bits=0x01 → fet_status=0x02
```

### 异常路径：节点离线 fail-closed

**场景**: 杀掉模拟器进程 → 节点 status=offline

**S1 (GPIO) 触发**:
- POST /automation-rules/1/trigger → `result=failed_dispatch, detail="action is unavailable for this device"`
- gate `node_status` 拦截

**S2 (BMS) 触发**:
- POST /automation-rules/3/trigger → `result=failed_dispatch, detail="action is unavailable for this device"`
- gate 在 evaluator 阶段拦截（未生成 pending_confirm）

**对历史 pending_confirm 事件 confirm**:
- POST /automation-events/215/confirm → 500 `action is unavailable for this device`
- IssueConfirmation 的 `node_status` gate 拦截
- `command_executions` **没有新增行** — 真正的 fail-closed
